    Part 6 · Data Access, Transactions & Security · Lecture 32

    Master Spring Data JPA

    21 sections · interview-oriented · both themes

    Scope evidence: "Master Spring Data JPA in one video | JpaRepository, JPQL, Pagination" (playlist map, verified). Repo folder for this lecture is the springDataJPADemo project: repository.StudentRepository extending JpaRepository, service.StudentService, entity.Student, and application.properties, plus this lecture's notes.

    JPA and Hibernate removed most hand-written SQL, but every application still wrote the same repository class again and again.

    Spring Data JPA answers that remaining repetition: declare an interface, and Spring builds the implementation at runtime.

    This lecture covers the persistence layer, repository boilerplate, derived query methods, JPQL, native SQL, sorting, and pagination, and explains what happens under a studentRepository.findById(1L) call.

    The goal is a mental model where the repository is not magic but a proxy over the same EntityManager and Hibernate machinery.

    1. The Persistence Layer after Hibernate and JPA

    Before JPA and Hibernate, persistence code used JDBC or Spring JDBC.

    A lookup needed the SQL text, a row mapper, and parameter binding, roughly jdbcTemplate.queryForObject(sql, studentRowMapper, id).

    The developer had to handle SQL statements, parameter binding, result-set mapping, object creation, and database-specific details.

    JPA and Hibernate remove much of this work: the same lookup collapses to entityManager.find(Student.class, id).

    They provide:

    • object-relational mapping;
    • entity state management;
    • the persistence context;
    • dirty checking;
    • relationship mapping;
    • SQL generation;
    • first-level caching;
    • transaction synchronization.

    An application still needs a dedicated persistence layer: business services focus on use cases, while repositories hold data-access logic.

    Without Spring Data JPA, a hand-written repository still used EntityManager directly through persist(), find(), and remove(), inside a @Repository class with a @PersistenceContext field.

    The key idea: JPA and Hibernate do not eliminate the repository layer; they simplify the persistence logic written inside it. The full stack, top to bottom:

    Application service -> Spring Data JPA repository -> JPA EntityManager
    -> Hibernate -> JDBC driver -> relational database

    Important: Spring Data JPA sits above JPA and Hibernate. It does not replace either; it removes repository boilerplate while the same EntityManager and Hibernate machinery still execute the work.

    2. The Repository Boilerplate Problem

    Suppose an application contains three entities: Student, Department, and Course.

    Without Spring Data JPA, each entity tends to need its own repository implementation, and each repeatedly implements the same basic operations:

    • save an entity;
    • find an entity by ID;
    • find all entities;
    • check whether an entity exists;
    • count entities;
    • delete an entity.

    Only two pieces of information usually change between them: the entity type and the identifier type.

    That common structure can be represented generically as Repository<EntityType, IdentifierType>, for example:

    Repository<Student, Long>
Repository<Department, Long>
Repository<Course, Integer>

    This generic repository idea is the foundation of Spring Data: instead of copying a class per entity, one parameterized contract captures every entity and key combination.

    Interviewer's perspective: The two generic parameters are the whole trick. JpaRepository<Student, Long> means "repository for Student keyed by Long." Candidates who cannot name the second parameter are usually guessing at the abstraction.

    3. Spring Data and Spring Data JPA

    These two names are related but not interchangeable. Spring Data is an umbrella project that provides a consistent, repository-based programming model for different persistence technologies.

    Its modules include Spring Data JPA, Spring Data MongoDB, Spring Data Redis, Spring Data JDBC, Spring Data Elasticsearch, Spring Data Cassandra, and Spring Data Neo4j.

    The central idea is simple: define a repository interface for a domain type, and let the appropriate Spring Data module provide the supporting implementation and infrastructure.

    The implementation underneath depends on the selected module:

    Spring Data JPA repository -> EntityManager -> JPA provider (Hibernate) -> relational database
Spring Data MongoDB repository -> MongoDB infrastructure -> MongoDB

    Spring Data JPA is the Spring Data module designed for applications that use the Jakarta Persistence API.

    Instead of manually implementing a repository class, the developer declares an interface, for example public interface StudentRepository extends JpaRepository<Student, Long> {}.

    The repository can then be injected and used like a normal Spring bean:

    @Service
public class StudentService {
    private final StudentRepository studentRepository;

    public StudentService(StudentRepository studentRepository) {
        this.studentRepository = studentRepository;
    }
}

    Common operations become immediately available: save(), findById(), deleteById(), and findAll().

    At startup, Spring Data detects the interface and creates a repository bean for it; no implementation class is written by the developer.

    Golden rule: Define the interface, not the implementation. If you are hand-writing a ...RepositoryImpl class for standard CRUD, you have not yet understood what Spring Data is for.

    4. JPA vs Spring Data JPA

    This is the single most common comparison on this topic.

    Aspect JPA Spring Data JPA
    Nature Jakarta specification Spring framework module
    What it defines Persistence concepts and APIs A repository abstraction on top of JPA
    Core surface EntityManager, JPQL Repository interfaces, query-method support
    Provider need Requires a persistence provider Uses the configured JPA provider underneath
    JpaRepository Not present in the specification Provided by Spring Data JPA
    Typical operations persist(), find(), remove() save(), findById(), deleteById()

    What JPA itself provides includes @Entity, @Id, @OneToMany, @ManyToOne, EntityManager, EntityManagerFactory, and TypedQuery.

    Typical JPA operations are entityManager.persist(student), entityManager.find(Student.class, 1L), and entityManager.remove(student).

    Spring Data JPA provides Repository, CrudRepository, ListCrudRepository, PagingAndSortingRepository, JpaRepository, @Query, @NativeQuery, @Modifying, @EntityGraph, and JpaSpecificationExecutor. Its main responsibilities are common CRUD operations, a runtime repository implementation, query derivation from method names, custom JPQL and native SQL via @Query, and sorting and pagination.

    Important: JpaRepository is part of Spring Data JPA, not part of the JPA specification. The specification has no concept of a repository interface at all.

    What Spring Data JPA does not do: it does not remove the need to understand entity mapping, transactions, managed versus detached entity states, lazy loading and fetching, SQL performance, indexes and constraints, or the N+1 query problem. It reduces repository boilerplate; it does not replace sound persistence design.

    5. Repository Interface Hierarchy

    The important repository abstractions form a hierarchy:

    Repository<T, ID>
 +-- CrudRepository<T, ID>
 |    +-- ListCrudRepository<T, ID>
 |         +-- PagingAndSortingRepository<T, ID>
 |              +-- ListPagingAndSortingRepository<T, ID>
 +-- JpaRepository<T, ID>
      +-- ListCrudRepository<T, ID>
      +-- ListPagingAndSortingRepository<T, ID>
      +-- QueryByExampleExecutor<T>

    Repository<T, ID> is primarily a marker interface. It identifies the domain type T, the identifier type ID, and the interface as a Spring Data repository.

    Extending it does not automatically expose the full CRUD API, which allows a restricted repository contract: a repository extending Repository that declares only save(), findById(), and findAll() cannot delete, because no delete method is declared.

    CrudRepository<T, ID> extends Repository and provides generic CRUD operations: <S extends T> S save(S entity), Optional<T> findById(ID id), Iterable<T> findAll(), boolean existsById(ID id), long count(), void deleteById(ID id), and void delete(T entity).

    ListCrudRepository<T, ID> offers CRUD functionality similar to CrudRepository, but methods returning multiple entities return a List instead of an Iterable.

    PagingAndSortingRepository<T, ID> adds sorted and paginated retrieval through Iterable<T> findAll(Sort sort) and Page<T> findAll(Pageable pageable).

    Since Spring Data 3, the sorting repository hierarchy is separate from the CRUD hierarchy. Extending only PagingAndSortingRepository does not guarantee methods such as save() and deleteById(). To combine the lower-level contracts explicitly:

    public interface StudentRepository
        extends ListCrudRepository<Student, Long>,
                ListPagingAndSortingRepository<Student, Long> {
}

    In a JPA application, extending JpaRepository is normally more convenient because it already combines these capabilities.

    Mnemonic for the main chain: "Really Clever Pandas Jump" - Repository, CrudRepository, PagingAndSortingRepository, JpaRepository (each with <T, ID>).

    Important: The hierarchy is not "more methods means better." A restricted contract built on Repository is a legitimate design when you want to expose only reads or only specific writes.

    6. Declaring a Repository Interface

    A typical declaration needs no implementation class and no @Repository, and is picked up by Spring Boot scanning under the application's base package.

    The interface can combine inherited CRUD with derived methods, @Query, and paging/sorting parameters:

    public interface StudentRepository
        extends JpaRepository<Student, Long> {

    Optional<Student> findByEmail(String email);
    List<Student> findByAgeGreaterThan(Integer age);
    List<Student> findTop5ByActiveTrueOrderByAgeDesc();
    boolean existsByEmail(String email);
    long countByActiveTrue();

    @Query("""
        SELECT s
        FROM Student s
        WHERE s.email = :email
        """)
    Optional<Student> findStudentByEmail(@Param("email") String email);

    Page<Student> findByActiveTrue(Pageable pageable);
    List<Student> findByActiveTrue(Sort sort);
}

    @EnableJpaRepositories is generally unnecessary in a standard Spring Boot project, but it can be used for explicit or custom repository scanning. Repository methods fall into two main categories:

    Category Examples How they are handled
    Inherited methods save(), findById(), findAll() Implemented by the repository base class
    Declared query methods findByEmail(), findByAgeGreaterThan() Converted into or associated with queries

    The interface cannot be instantiated directly: new StudentRepository(); is a compilation error.

    7. Repository Proxy Internals

    Why can an interface be injected at all? Because Spring Data creates a runtime object that implements the repository interface. This runtime-generated object is called a repository proxy.

    StudentService -> StudentRepository proxy
    -> classifies the invoked method -> chooses the correct execution path

    For an inherited method, studentRepository.findById(1L) goes to the proxy, then to SimpleJpaRepository.findById(1L), then to EntityManager.find(...).

    For a derived method, studentRepository.findByEmail(email) goes to the proxy, then to prepared query-method execution, then the parameter is bound, and finally EntityManager executes the query.

    SimpleJpaRepository<T, ID> is the standard base implementation behind most JpaRepository operations. Conceptually it holds an EntityManager and a JpaEntityInformation<T, ?> and implements methods such as save(), findById(), findAll(), existsById(), count(), delete(), flush(), saveAndFlush(), and getReferenceById().

    Why the proxy is still necessary: SimpleJpaRepository knows how to execute standard repository operations, but it cannot contain every application-specific method such as findByEmail() or findByDepartmentName(). The proxy combines multiple sources of behavior:

    Method type Execution source
    Standard CRUD method SimpleJpaRepository
    Derived query method Query created from the method name
    Declared JPQL or SQL query @Query
    Default interface method Java interface default method
    Custom repository fragment Developer-provided implementation

    Spring Data JPA remains a layer above JPA. Its base implementation ultimately delegates persistence work to EntityManager, whose implementation is commonly provided by Hibernate.

    8. Important JpaRepository Methods

    JpaRepository provides three broad groups of operations:

    • CRUD: save(), saveAll(), findById(), findAll(), existsById(), count(), delete(), deleteById(), deleteAll();
    • sorting and pagination: findAll(Sort sort), findAll(Pageable pageable);
    • JPA-specific: flush(), saveAndFlush(), saveAllAndFlush(), getReferenceById(), deleteAllInBatch(), deleteAllByIdInBatch().

    Batch delete methods can behave differently from deleting managed entities one by one; use them deliberately when cascades, lifecycle callbacks, or the current persistence context matter.

    A few methods deserve individual attention:

    • save() does not simply mean "execute an INSERT." It means the entity state should become persistent.
    • Spring Data decides whether the entity is new: yes routes to EntityManager.persist(entity), no routes to EntityManager.merge(entity).
    • saveAll() conceptually calls save() for each entity; it does not itself guarantee one multi-row SQL statement, since batching is a separate optimization with its own configuration and identifier-strategy requirements.
    • findById() checks the persistence context first; a managed entity is returned directly, otherwise the database is queried if necessary. It returns Optional because a row with the requested ID may not exist.
    • findAll() loads every matched entity; it is suitable for small datasets but dangerous for large tables, since Spring Data cannot infer that pagination was intended.
    • existsById() expresses an existence question rather than a full load, commonly using a count or equivalent mechanism.
    • count() conceptually runs SELECT COUNT(*) FROM students.
    • delete() must ultimately operate on a managed entity; a detached entity may be obtained or merged into managed state before removal.
    • deleteAll() is broad and potentially expensive; it may process entities individually.
    • flush() synchronizes pending changes in the persistence context with the database but does not commit the transaction.
    • saveAndFlush() conceptually is save(student); flush(); return result;; use it to force immediate synchronization, for example to detect a constraint violation before the normal commit point, not automatically on every save.

    Important: flush() is not commit(). Flushing only pushes pending SQL to the database while the transaction remains open and can still roll back.

    9. save() vs Dirty Checking

    Consider a managed entity loaded inside a transaction: a service method annotated @Transactional calls studentRepository.findById(id).orElseThrow() and then student.setName(newName).

    No call to save() is required for JPA to update the row. The process is:

    Repository loads Student -> Student becomes managed
    -> application changes the managed object -> dirty checking detects the change
    -> UPDATE is generated during flush/commit

    Calling save() for an already-managed entity is usually redundant from a pure JPA perspective. It may still be used when a team deliberately follows the repository abstraction consistently, but it is not what causes dirty checking.

    save() is important when:

    1. persisting a new entity;
    2. reattaching state from a detached entity through merge();
    3. returning the managed instance produced by merge().

    The return value matters when merge() is used: Student managedStudent = studentRepository.save(detachedStudent);. merge() returns a managed instance; the detached object passed as the argument does not automatically become managed.

    Interviewer's perspective: "Do you always need save() to update an entity?" The strong answer is no: for a managed entity dirty checking flushes the change automatically; save() matters for new or detached entities, and merge() returns a managed copy rather than mutating the argument.

    10. Derived Query Methods

    Query derivation lets a method name become a query. Without derivation you write the query explicitly with @Query; with derivation you write only Optional<Student> findByEmail(String email);.

    Spring Data parses the name: find -> selection operation; By -> beginning of the predicate; Email -> the Student.email property. Conceptual JPQL:

    SELECT s
FROM Student s
WHERE s.email = ?1

    The default lookup strategy first checks for a declared query and derives a query from the method name if none is found.

    Subject and predicate: findByEmail contains two logical sections. findBy is the subject; Email is the predicate.

    The subject describes the operation, for example findByEmail(...), existsByEmail(...), countByActiveTrue(), deleteByActiveFalse(), or findTop5ByActiveTrueOrderByAgeDesc().

    The predicate describes the matching condition, for example findByAgeGreaterThanAndActiveTrue(Integer age).

    Common query keywords:

    Keyword Repository method Meaning
    Equality findByEmail(String email) email = ?
    And findByNameAndAge(String name, Integer age) Both conditions must match
    Or findByNameOrEmail(String name, String email) Either condition may match
    GreaterThan findByAgeGreaterThan(Integer age) age > ?
    LessThan findByAgeLessThan(Integer age) age < ?
    Between findByAgeBetween(Integer min, Integer max) Inclusive range
    Like findByNameLike(String pattern) Caller supplies the pattern
    Containing findByNameContaining(String value) Value is contained
    In findByAgeIn(Collection<Integer> ages) Belongs to the collection
    IsNull findByDepartmentIsNull() Property is null
    True findByActiveTrue() Boolean property is true
    IgnoreCase findByNameIgnoreCase(String name) Case-insensitive comparison
    OrderBy findByActiveTrueOrderByNameAsc() Static ordering
    Top / First findTop5ByOrderByAgeDesc() Limit the result

    Like versus Containing matters. With Like, the caller supplies the wildcard characters (studentRepository.findByNameLike("%har%")). With Containing, Spring Data adds the contains pattern itself (studentRepository.findByNameContaining("har") binds a pattern such as %har%).

    Limiting results: List<Student> findTop5ByActiveTrueOrderByAgeDesc(); means select active students, sort them by age descending, and return at most five. An explicit order is important; without it, "top five" has no reliable business meaning because a relational database does not guarantee a natural row order. Similarly, Optional<Student> findFirstByDepartmentNameOrderByAgeDesc(String departmentName) returns one result with a defined order.

    Limitations: derived queries are ideal while the name stays short and readable, but they become difficult to maintain when they grow into long query-language sentences such as findTop10ByNameContainingIgnoreCaseAndAgeGreaterThanAndActiveTrueAndDepartmentNameOrderByAdmissionDateDesc(...).

    Main limitations:

    • long names are difficult to read;
    • complex And/Or grouping is hard to express clearly;
    • the method name cannot show complicated joins and projections well;
    • database-specific behavior may require native SQL.

    For such cases, use @Query, specifications, Query by Example, Querydsl, or a custom repository implementation depending on the problem.

    11. Custom JPQL Queries with @Query

    @Query keeps a custom query close to the repository method that executes it. JPQL queries operate on entity names, entity fields, and entity relationships; JPQL does not directly use table names and database column names.

    In SELECT s FROM Student s, Student is the entity name and s is its query alias.

    Named parameters are usually easier to read and maintain, as in WHERE s.age >= :minimumAge AND s.age <= :maximumAge with @Param("minimumAge") and @Param("maximumAge").

    Positional parameters exist too, and their indexes are one-based (?1, ?2, ...).

    Relationship joins follow the entity relationship. If Student contains @ManyToOne private Department department;, an explicit join is SELECT s FROM Student s JOIN s.department d WHERE d.active = true.

    JPQL uses s.department, not a database expression such as s.department_id = d.id; Hibernate already knows the join-column mapping from the entity relationship.

    Implicit versus explicit joins can express the same filtering. An explicit join is useful when the joined entity needs an alias; several conditions refer to the joined entity; the join type must be controlled; or the query selects data from both entities. An inner join (JOIN s.department d) includes a student only when a matching department exists, so a student whose department is null is excluded. A left join preserves students without a department:

    SELECT s.name, d.name
FROM Student s
LEFT JOIN s.department d

    For production code, a DTO or interface projection is usually clearer than exposing Object[] to higher layers.

    Static ordering in JPQL is appropriate when the business operation always requires the same order, for example ... WHERE s.active = true ORDER BY s.name ASC; multiple sort fields use ORDER BY d.name ASC, s.name ASC. Dynamic ordering with Sort keeps the predicate fixed while the caller controls the order, as in List<Student> findActiveStudents(Sort sort); used with Sort.by("name").ascending().

    12. Native Queries

    JPQL operates on the entity model. Native SQL is useful when a query needs database-specific functions, vendor-specific syntax, precise control over the SQL statement, existing SQL that cannot be expressed cleanly in JPQL, or common table expressions and advanced SQL features. Use @Query(nativeQuery = true):

    @Query(
    value = """
        SELECT *
        FROM students
        WHERE email = :email
        """,
    nativeQuery = true
)
Optional<Student> findByEmailUsingNativeQuery(@Param("email") String email);

    nativeQuery = true tells Spring Data to interpret the string as database SQL instead of JPQL. Recent Spring Data JPA versions also provide @NativeQuery, a composed form designed specifically for native queries, for example @NativeQuery("SELECT * FROM students WHERE email = :email"). Native named and positional parameters behave like their JPQL counterparts, but the value is real SQL.

    A native query is coupled to the database schema and possibly to the selected database vendor. Use it when the benefit outweighs the loss of portability.

    Important: JPQL speaks entity names and entity fields; native SQL speaks table names and column names. Mixing the two mentally is the fastest way to a query that fails at startup or runtime.

    13. Sorting with Sort

    Without ORDER BY, a relational database does not guarantee a meaningful result order. Sorting is therefore part of query design, not just presentation.

    A sort is created with Sort.by("name"); ascending order is the default, and an explicit form is Sort.by(Sort.Direction.ASC, "name"), used as studentRepository.findAll(sort). The Sort argument must not be null; use Sort.unsorted() when no ordering is required.

    Ascending and descending use Sort.by("name").ascending() and Sort.by("admissionDate").descending().

    Multiple properties chain with and, for example Sort.by("department.name").ascending().and(Sort.by("name").ascending()), which conceptually becomes ORDER BY department.name ASC, student.name ASC.

    Sort properties refer to entity properties, not database column names, so Sort.by("admissionDate") uses the property name even if the column is named differently.

    Dynamic sorting with a query method keeps the predicate fixed while the caller controls the order, for example List<Student> findByActiveTrue(Sort sort); used with Sort.by(Sort.Order.desc("age"), Sort.Order.asc("name")).

    Validating user-controlled sorting matters. If an API accepts GET /students?sortBy=name&direction=asc, do not pass arbitrary client input directly into Sort; validate it against an allowlist of entity properties. A helper can check Set.of("name", "age", "admissionDate"), reject unsupported properties with IllegalArgumentException, then build the sort with Sort.Direction.fromString(direction).

    Validation prevents invalid property paths and keeps the API contract intentional.

    Important: An unvalidated sortBy parameter is both an injection-style risk and a stability risk. Only entity properties from a fixed allowlist should reach Sort.

    14. Pagination with Pageable and PageRequest

    Suppose a table contains two million students. Calling studentRepository.findAll(); can cause problems throughout the stack:

    • the database reads too many rows;
    • the network transfers too much data;
    • Hibernate creates too many entity objects;
    • the persistence context consumes excessive memory;
    • the JSON response becomes enormous;
    • the client cannot use the entire result effectively.

    Pagination changes the request from "Give me every student" to "Give me a controlled window of students." With zero-based page indexing and a page size of 10, page 0 holds records 1-10, page 1 holds 11-20, and page 2 holds 21-30.

    The conceptual offset is offset = page number x page size; for page 2 with size 10, offset = 2 x 10 = 20. Conceptual SQL is SELECT * FROM students ORDER BY id LIMIT 10 OFFSET 20;, but the actual pagination syntax is database-dependent and generated by Hibernate.

    Pageable describes the requested page number, the requested page size, sort information, and whether the request is paged or unpaged. Pageable is an interface; PageRequest is its commonly used implementation.

    An unsorted request is PageRequest.of(0, 10), a sorted request is PageRequest.of(0, 10, Sort.by("name").ascending()), and the convenience form is PageRequest.of(0, 10, Sort.Direction.ASC, "name"). PageRequest.of() requires a non-negative page number and a page size greater than zero.

    The last page may contain fewer elements:

    Total elements = 45, page size = 20
Page 0 -> 20 elements
Page 1 -> 20 elements
Page 2 -> 5 elements

    Sorting and pagination must work together: a stable and deterministic order is important because page boundaries depend on the ordering. If the primary sort field is not unique, add a unique tie-breaker such as id with Sort.by("name").ascending().and(Sort.by("id").ascending()).

    At the API boundary, validate the page size and enforce a maximum value to prevent clients from requesting an unreasonably large page.

    Important: Page indexes are zero-based in Spring Data. "Page 2" is the third window of results, and the offset is page number times page size.

    15. Page vs Slice and Count Queries

    A Page<Student> contains both the current content and pagination metadata, obtained as page = studentRepository.findAll(PageRequest.of(0, 10)). Its common methods are:

    • page.getContent() - the List<Student> for the current page;
    • page.getNumber(), page.getSize(), page.getNumberOfElements();
    • page.getTotalElements(), page.getTotalPages();
    • page.isFirst(), page.isLast(), page.hasNext(), page.hasPrevious();
    • page.getSort().

    The content contains only the entities in the current page; for a page size of 10, its size can be between 0 and 10. Page extends Slice and adds the total number of matching elements and the total number of pages.

    A Slice represents the current chunk of data and whether another chunk is available, declared as Slice<Student> findByActiveTrue(Pageable pageable);. Its methods mirror Page for content, number, size, first/last, and next/previous, but a Slice does not provide getTotalElements() or getTotalPages().

    Requirement Page Slice
    Current content Yes Yes
    Page number and size Yes Yes
    Has next/previous Yes Yes
    Total elements Yes No
    Total pages Yes No
    Count query commonly required Yes No

    Slice can be more efficient when the client only needs to know whether more data is available:

    Page  -> limited content query -> often an additional count query
Slice -> limited query -> commonly fetches one extra row to determine hasNext

    Use Page when the UI needs information such as "page 3 of 25." Use Slice for experiences such as "load more" or infinite scrolling, where the exact total is unnecessary.

    Count queries: suppose the content query returns ten rows. Those ten rows alone cannot reveal whether the complete result contains 10, 11, 1,000, or 10 million rows.

    To calculate totalElements and totalPages, a paged operation commonly needs two queries: a content query and a count query.

    For a simple derived method such as Page<Student> findByActiveTrue(Pageable pageable);, Spring Data can derive both queries. Complex JPQL can provide an explicit countQuery alongside the value in @Query, reproducing the filtering logic while omitting unnecessary ordering and fetching; this is particularly useful when the content query contains complex joins, grouping, projections, fetch joins, or native SQL.

    Important: Page trades an extra count query for total metadata; Slice skips that cost and only reports whether another chunk exists. Choosing wrongly is a performance decision, not a cosmetic one.

    16. Complete Mental Model

    When the application calls an inherited method:

    studentRepository.findById(1L) -> repository proxy receives the call
    -> SimpleJpaRepository handles the method -> EntityManager performs the JPA operation
    -> Hibernate checks the persistence context -> Hibernate executes SQL if required
    -> database returns the result

    When the application calls a derived query method:

    studentRepository.findByEmail(email) -> repository proxy receives the call
    -> prepared repository query is selected -> method arguments are bound
    -> EntityManager executes the query -> Hibernate generates and executes SQL
    -> results are mapped to entities

    Spring Data JPA therefore removes repetitive repository implementation code while continuing to use the same JPA and Hibernate machinery underneath.

    17. Myth vs Reality

    Myth Reality
    "Spring Data JPA replaces JPA and Hibernate" It is a repository abstraction built on top of them; they still execute the work
    "Naming a repository is enough for CRUD, no matter the parent" Repository is a marker; CRUD arrives only from CrudRepository or JpaRepository
    "JpaRepository is part of the JPA specification" It belongs to Spring Data JPA, not the spec
    "You must write an implementation class for a repository interface" Spring creates a repository proxy at runtime; no class is written
    "save() always issues an INSERT" It maps to persist() for new entities and merge() for existing ones
    "save() is always required to update a managed entity" Dirty checking updates managed entities during flush/commit without an explicit save()
    "flush() commits the transaction" Flush only sends pending SQL; the transaction can still roll back
    "Derived method names scale forever" Long names become unreadable; use @Query or other options for complex logic
    "JPQL and native SQL use the same names" JPQL uses entity names; native SQL uses table and column names
    "Page and Slice are interchangeable" Page gives totals and often a count query; Slice does not

    18. Common Trap Questions

    Trap 1 - Is JpaRepository part of JPA? Verdict: False. JpaRepository is provided by Spring Data JPA. The JPA specification itself has no repository interfaces.

    Trap 2 - "Spring Data JPA replaces Hibernate." Verdict: False. Spring Data JPA sits above JPA and delegates to an EntityManager whose provider is commonly Hibernate. It removes boilerplate, not the persistence engine.

    Trap 3 - "You must call save() to update a loaded entity." Verdict: False, for a managed entity inside a transaction. Changing the managed object triggers dirty checking and an UPDATE during flush/commit. save() matters for new or detached entities.

    Trap 4 - "flush() and commit() are the same." Verdict: False. flush() pushes pending SQL to the database; commit() permanently completes the transaction. A transaction can still roll back after a flush.

    Trap 5 - "findByEmail is implemented by SimpleJpaRepository." Verdict: False. Standard CRUD comes from SimpleJpaRepository; a derived method is turned into a query from the method name by the repository proxy.

    Trap 6 - "A repository interface can be instantiated with new." Verdict: False. new StudentRepository() is a compile error; Spring supplies a runtime proxy that implements the interface.

    Trap 7 - "findAll() is safe on a two-million-row table." Verdict: False. findAll() loads every row and entity and can exhaust memory; use Pageable/Page to request a controlled window, and enforce a maximum page size.

    19. Points to Remember

    1. JPA is the specification, Hibernate is a common provider, and Spring Data JPA is the repository abstraction built on top of both.
    2. The repository generics capture the two changing pieces: JpaRepository<EntityType, IdentifierType>.
    3. The hierarchy is Repository -> CrudRepository -> ListCrudRepository -> PagingAndSortingRepository, with JpaRepository combining capabilities.
    4. Repository is a marker; extending it does not expose CRUD, which enables restricted contracts.
    5. Spring creates a repository proxy at runtime; standard methods are primarily handled by SimpleJpaRepository.
    6. save() chooses between persist() and merge() by deciding whether the entity is new, and merge() returns the managed instance.
    7. Managed entities are updated through dirty checking, even without an explicit save() call; flush() sends pending SQL but does not commit.
    8. Derived query methods parse the method name into a query but should stay short; otherwise use @Query, specifications, or a custom implementation.
    9. JPQL works with entity names and relationships; native SQL works with table and column names and couples the query to the schema or vendor.
    10. Sorting must be explicit when order matters, and pagination needs a stable order plus a validated page size; Page provides totals and commonly a count query, while Slice omits totals and can be more efficient.

    20. Likely Interview Questions

    Question Crisp Answer
    What is Spring Data JPA? The Spring Data module that adds a repository abstraction over JPA, removing boilerplate while delegating to an EntityManager.
    JPA vs Spring Data JPA? JPA is a specification defining persistence APIs; Spring Data JPA is a Spring module providing repository interfaces and query methods on top of it.
    What do the two generics in JpaRepository<Student, Long> mean? The entity/domain type (Student) and the identifier type (Long).
    How can an interface be injected without an implementation class? Spring Data creates a runtime proxy that implements the interface and dispatches each method to the correct execution path.
    What is SimpleJpaRepository? The standard base implementation behind most JpaRepository operations, delegating to EntityManager.
    Does save() always INSERT? No; it maps to persist() for new entities and merge() for existing/detached ones, returning a managed instance on merge.
    Do you always need save() to update an entity? No; a managed entity is updated by dirty checking during flush/commit, so an explicit save is usually redundant for it.
    Difference between flush() and commit()? Flush sends pending SQL to the database; commit permanently completes the transaction. A flush does not commit.
    What are derived query methods? Query methods whose query is generated by parsing the method name, such as findByEmail or findByAgeGreaterThan.
    JPQL vs native SQL? JPQL queries the entity model (entity names, fields, relationships); native SQL queries the database (tables and columns).
    What does nativeQuery = true do? Tells Spring Data to interpret the @Query string as database SQL instead of JPQL.
    Difference between Page and Slice? Page adds total elements and total pages and commonly needs a count query; Slice omits totals and can be more efficient.
