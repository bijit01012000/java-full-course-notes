    Part 3 · OOP Deep Dive · Lecture 21

    Immutable Classes in Java | How to Create Immutable Objects

    17 sections · interview-oriented · both themes

    Scope evidence: "Immutable Classes in Java | How to Create Immutable Objects" (playlist map, verified). Repo evidence: 2 Demo files.

    An immutable object is one whose state cannot change after it has been constructed. The JDK is full of them — String, the wrapper classes, LocalDate and BigDecimal — and this lecture shows how to build the same guarantee into your own classes. It covers the construction recipe, why the class itself must be final, the defensive copies that protect mutable fields, and the wither and builder patterns used for functional-style updates. The topic follows encapsulation and inheritance (Lecture 16) and the final keyword (Lecture 15), and it forwards to the Object contract (Lecture 22) and concurrency (Lecture 50).

    1. What Immutability Means

    An immutable object is an object whose observable state cannot change after its constructor returns. Once you hold a reference to it, every field keeps the value it was given, and every method that appears to "change" it returns a new object instead.

    Three ideas are easy to conflate but are different:

    1. Unmodifiable reference — a final variable cannot be reassigned, yet the object it points at may still change.
    2. Unmodifiable container — List.of(...) and Map.of(...) reject structural edits, yet their elements may be mutable.
    3. Immutable object — the entire reachable state is fixed; nothing a caller can do changes it.

    Only the third is true immutability. The JDK's canonical examples are String, Integer and the other wrappers, BigDecimal, and the java.time types such as LocalDate.

    Important Immutability is a promise about the reachable state, not about a single variable. A field, a container and an object can each be "unmodifiable" at one level while remaining mutable underneath.

    2. The Recipe: How to Build an Immutable Class

    Every correct immutable class is assembled from the same short list of rules:

    1. Declare the class final so no subclass can weaken or extend the contract.
    2. Make every field private and final; assign them once.
    3. Provide no setters and no other mutating methods.
    4. Set all state in the constructor, so an object is never observed half-built.
    5. Defensively copy every mutable input in the constructor (on the way in).
    6. Defensively copy every mutable field before returning it from a getter (on the way out).
    7. Deep-copy nested mutable state, not just the top-level reference.

    Memory aid — F-P-N-C: Final class, Private final fields, No setters, Copies of every mutable input and output. If any of the four letters is missing, the class is not immutable.

    3. Why the Class Must Be final

    Marking the class final is not decoration. If a subclass is allowed, it can subvert an otherwise perfect class in at least two ways:

    1. Add mutable state — a subclass introduces a field and a setter, so instances of the subclass now change over time.
    2. Override behaviour — a subclass overrides a getter to compute and return a different value each call, or overrides equals/hashCode inconsistently.

    Both break the guarantee that callers rely on, even though the parent class is untouched. The alternatives to final are a private constructor with static factory methods (the List.of style) or a constructor that is not reachable by subclasses, but final is the simplest and clearest.

    Interviewer's perspective "Why can't an immutable class be extended?" Because a subclass reopens the door that the parent closed: it can add state or override methods and break the immutability contract. Only a final class, a private constructor, or an unextendable factory design keeps the guarantee intact.

    4. Why Immutability Pays Off

    The design costs a little more code but returns several concrete benefits:

    1. Thread-safety without synchronization — an object whose state never changes cannot suffer a data race, so it can be shared freely across threads with no locks (forward reference: Lecture 50).
    2. Safe hash keys and cache entries — because the state is fixed, hashCode is stable, so an immutable object can be a HashMap key or a cache key without lookup failures (forward reference: Lecture 22).
    3. No defensive copies for callers — passing an immutable object around never risks the receiver mutating it, so callers stop copying defensively.
    4. Easier reasoning and testing — an object that cannot change has one meaningful state, which simplifies assertions and eliminates action-at-a-distance bugs.
    5. Free sharing and interning — identical immutable values can be cached or reused (as the string pool does), reducing allocation.
    6. Failure atomicity — if a construction or update fails, no partially modified object is left behind.

    5. The final Reference Trap

    A final reference guarantees only that the reference itself is never reassigned; it says nothing about the object on the other end. This is the single most common confusion in the topic and was introduced with the final keyword in Lecture 15.

    // Demo.java — final stops reassignment, not mutation
import java.util.ArrayList;
import java.util.List;

public class Demo {
    public static void main(String[] args) {
        final List<String> list = new ArrayList<>();
        list.add("a");          // legal: the object is mutated
        list.add("b");          // legal
        // list = new ArrayList<>();  // compile error: the reference is final
        System.out.println(list);  // [a, b]
    }
}

    The reference is locked, but the list is not. Immutability requires that the object be unchangeable, which is a deeper property than final on the variable.

    Important final on a variable means "this name cannot point somewhere else". Immutability means "this object's state cannot change". The two are independent.

    6. Defensive Copies: On the Way In and On the Way Out

    A mutable field such as Date, an array or a List must be copied twice: once when it enters the object and once when it leaves. Skipping either copy lets a caller reach the internal state.

    // Demo2.java — before: a mutable Date leaks in both directions
import java.util.Date;

public final class Person {
    private final String name;
    private final Date birthday;

    public Person(String name, Date birthday) {
        this.name = name;
        this.birthday = birthday;      // BUG: caller keeps the same Date
    }
    public Date getBirthday() {
        return birthday;               // BUG: exposes the internal Date
    }
    public static void main(String[] args) {
        Date d = new Date(0L);
        Person p = new Person("Asha", d);
        d.setTime(1_000_000_000L);     // changes the Date inside p
        p.getBirthday().setTime(0L);   // changes p from the outside
    }
}

    The corrected version copies on the way in and on the way out, so the internal Date is unreachable in both directions:

    // Demo2.java — after: copy IN and copy OUT
import java.util.Date;

public final class Person {
    private final String name;
    private final Date birthday;

    public Person(String name, Date birthday) {
        this.name = name;
        this.birthday = new Date(birthday.getTime());   // copy IN
    }
    public Date getBirthday() {
        return new Date(birthday.getTime());            // copy OUT
    }
}

    7. Deep Immutability and Nested Mutable State

    A shallow copy duplicates the outer object but shares the objects it points at. A collection of mutable elements therefore needs deep copying: copy the collection and each element. Arrays follow the same rule — array.clone() copies the array but not the objects inside it.

    // Demo2.java — deep copy a list of mutable Dates
import java.util.ArrayList;
import java.util.Date;
import java.util.List;

public final class Schedule {
    private final List<Date> dates;

    public Schedule(List<Date> dates) {
        this.dates = new ArrayList<>();
        for (Date d : dates) {
            this.dates.add(new Date(d.getTime()));      // copy every element IN
        }
    }
    public List<Date> dates() {
        List<Date> copy = new ArrayList<>();
        for (Date d : dates) {
            copy.add(new Date(d.getTime()));            // copy every element OUT
        }
        return copy;                                    // never return the internal list
    }
}

    Deep immutability is only as strong as the least-copied nested object. The rule is not "always copy deeply"; it is "copy deeply every nested object that is mutable and reachable".

    8. A Fully Correct Immutable Class

    The following Money class applies the whole recipe: final class, private final fields, no setters, state set in the constructor, defensive checks, and update methods that return a new instance.

    // Demo.java — a fully correct immutable value class with a wither
import java.util.Objects;

public final class Money {
    private final String currency;
    private final long cents;

    public Money(String currency, long cents) {
        this.currency = Objects.requireNonNull(currency, "currency");
        this.cents = cents;
    }
    public String currency() { return currency; }
    public long cents() { return cents; }

    public Money plus(Money other) {                 // returns a NEW object
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("currency mismatch");
        }
        return new Money(currency, cents + other.cents);
    }
    public Money withCents(long newCents) {          // wither
        return new Money(currency, newCents);
    }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;
        return cents == m.cents && currency.equals(m.currency);
    }
    @Override public int hashCode() {
        return Objects.hash(currency, cents);
    }
}

    plus and withCents never touch the receiver; they construct and return a new Money. That is exactly how String.concat and LocalDate.plusDays behave.

    9. Wither Methods and the Builder Pattern

    A wither (or "with-style" method) is an instance method that returns a fresh copy of the object with one field replaced. It is the functional-update idiom: money.withCents(500) reads like a change but produces a new object, leaving the original untouched.

    When a class has many fields, calling constructors with long argument lists becomes error-prone, so the builder pattern is used instead: a mutable builder object collects the values, and its build() method produces one immutable instance. The builder itself is mutable and short-lived; the result is immutable. Since Java 16, a record gives a concise immutable carrier for the common case of final fields, an all-arguments constructor and accessors.

    Interviewer's perspective "How do you update one field of an immutable object?" You cannot mutate it; you create a new instance. Small classes use a wither or a constructor; classes with many fields use a builder, whose build() performs the one and only construction of the immutable result.

    10. Mutable vs Immutable

    Aspect Mutable object Immutable object
    State after construction Can change through setters or fields Fixed forever
    Thread-safety Requires synchronization Safe without synchronization (Lecture 50)
    Safe as a hash key No - hashCode may change (Lecture 22) Yes - stable hashCode
    Sharing across callers Needs defensive copies Freely shared, no copies needed
    Cost of a change Cheap in place Allocates a new object
    Aliasing risk High None - state cannot change
    Examples StringBuilder, Date, ArrayList String, Integer, LocalDate, BigDecimal

    The table's spine: mutation trades safety for cheap updates, while immutability trades allocation for safety and shareability.

    11. Shallow vs Deep Immutability

    Field kind Shallow immutability Deep immutability
    Primitive (int, double) Already safe - copied by value Same
    Immutable reference (String, Integer) Safe - the object cannot change Same
    Mutable reference (Date, array) Unsafe - the shared object can still change Copy the object in and out
    Collection of immutables Unsafe if the internal collection is returned Return or wrap an unmodifiable copy
    Collection of mutables Unsafe on two levels Copy the collection and every element
    Nested object graph Inner objects remain shared The reachable graph is duplicated

    Shallow immutability rules out reassignment but not aliasing; deep immutability rules out aliasing too. Choose deep whenever a nested object is mutable.

    12. Common Pitfalls

    Pitfall What goes wrong Fix
    Returning an internal list or array directly The caller mutates the object's state Return a copy, or an unmodifiable view of a copied collection
    Storing a constructor-assigned mutable object The caller still holds the same object and can change it Defensive-copy the input in the constructor
    Treating a final reference as immutable The referenced object is still mutable Lock the object's state, not just the variable (Lecture 15)
    Assuming Map.of/List.of are deeply immutable The container is unmodifiable but elements may be mutable Copy or make the elements immutable
    Caching hashCode before construction completes A partially built object can leak and cache a wrong value Compute after all fields are set; avoid this escape
    Ignoring serialization Deserialization can create new instances and bypass normal construction Guard with readResolve or copy fields after readObject
    Non-final class or public constructor A subclass adds mutable state or overrides behaviour Make the class final or use private constructors with factories

    13. Myth vs Reality

    Myth Reality
    "final means immutable" final on a reference stops reassignment only; the object it points at may still be mutated (Lecture 15).
    "A class with only getters is immutable" If a getter returns an internal mutable object, the caller can still change the state.
    "List.of and Map.of are immutable" They are unmodifiable containers; their elements may be mutable.
    "Immutable objects need synchronization to be shared" Their state never changes, so no synchronization is required.
    "Two immutable objects with equal fields are the same object" Value equality is not identity; they are distinct objects that are equal (Lecture 22).

    14. Common Trap Questions

    Trap 1 — "A final field is the same as an immutable field, right?" No. final prevents reassignment of the field, but a final field can still hold a mutable object whose contents change.

    Trap 2 — "My class has only private final fields and getters, so it is immutable?" Only if every returned value is itself immutable or a defensive copy. A getter that hands back an internal List or Date breaks the guarantee.

    Trap 3 — "Does an immutable object need a copy constructor or clone?" No. Because its state cannot change, sharing the reference is always safe; there is nothing to protect against.

    Trap 4 — "Can I compute and cache hashCode inside the constructor?" Only with care. If this escapes before construction finishes, a partially built object could expose a cached value; compute once all fields are set, or avoid the escape entirely.

    Trap 5 — "I used Map.of('k', list) — so the map is immutable, correct?" The map is unmodifiable, but the list value is still mutable. Deep immutability requires the values to be immutable as well.

    Trap 6 — "Does serialization preserve immutability?" Deserialization creates a new instance through a path that can bypass your constructor, so a malformed stream may leave internal state reachable; use readResolve or re-copy fields in readObject.

    15. Points to Remember

    1. An immutable object's state cannot change after construction.
    2. The JDK's natives are String, the wrappers, BigDecimal and the java.time types.
    3. The recipe is F-P-N-C: final class, private final fields, no setters, copies of mutable inputs and outputs.
    4. Set all state in the constructor so an object is never observed half-built.
    5. A final reference is not an immutable object (Lecture 15).
    6. A final class stops a subclass from adding mutable state or overriding behaviour.
    7. Immutability gives thread-safety without synchronization (Lecture 50).
    8. A stable hashCode makes an object a safe map or cache key (Lecture 22).
    9. Wither methods return a new instance; builders help when there are many fields.
    10. Map.of and List.of are unmodifiable containers, not deeply immutable values.

    16. Likely Interview Questions

    Question Crisp Answer
    What is an immutable object? An object whose state cannot change after construction; all its reachable state is fixed.
    Name some immutable classes in the JDK. String, the wrapper classes (Integer, Double), BigDecimal, and java.time types such as LocalDate.
    How do you create an immutable class? Make the class final, all fields private final, provide no setters, set state in the constructor, and defensively copy mutable inputs and outputs.
    Why must an immutable class be final? A subclass could add mutable state or override methods and break the immutability contract.
    Is a final field enough? No. final stops reassignment; a final field can still hold a mutable object.
    What is a defensive copy? A private duplicate of a mutable input (on the way in) or field (on the way out) so external code cannot reach the internal state.
    What is the difference between shallow and deep immutability? Shallow fixes the top-level references but shares nested objects; deep duplicates the entire reachable mutable graph.
    Why are immutable objects thread-safe? Their state never changes, so concurrent readers cannot race; no synchronization is needed (Lecture 50).
    Why are immutable objects good hash keys? Their hashCode cannot change after insertion, so map lookups remain correct (Lecture 22).
    What is a wither method? An instance method that returns a new immutable instance with one field changed, leaving the original untouched.
    Why use a builder? To construct an immutable object with many fields without a long, error-prone constructor argument list.
    Are List.of and Map.of deeply immutable? No - the container is unmodifiable, but its elements may still be mutable.

    17. Final Summary

    mutable input --copy IN--> private final fields --copy OUT--> caller
        subclasses?      -> class must be final         final reference -> not immutable
        immutable object -> thread-safe, stable hashCode, freely shared, no defensive copies
    • Immutable → state fixed after construction; String, wrappers, LocalDate, BigDecimal.
    • Recipe → F-P-N-C: final class, private final fields, no setters, copies in and out.
    • final class → blocks subclasses from adding mutable state or overriding behaviour.
    • Defensive copies → mutable inputs copied in the constructor, mutable fields copied in getters; deep-copy nested state.
    • final trap → a final reference can still point at a mutable object (Lecture 15).
    • Benefits → thread-safe without synchronization (Lecture 50), stable hashCode keys (Lecture 22), safe sharing, easier testing.
    • Updates → wither methods return a new instance; builders handle many fields.
    • Pitfalls → leaking internal collections, confusing unmodifiable with immutable, caching hashCode too early.

    Golden rule Immutability is about the reachable state, not the variable: a final reference is not an immutable object, and one uncopied mutable field undoes the whole design.

    One-line takeaway: build immutability with a final class, private final fields, no setters, and defensive copies in and out — and you gain thread-safety, stable hashing and free sharing in return.
