    Part 6 · Optional, Exceptions & Memory · Lecture 47

    Introduction to Multithreading in Java | Process vs Thread

    18 sections · interview-oriented · both themes

    Scope evidence: "Introduction to Multithreading in Java | Process vs Thread" plus the lecture's own notes terms (program/process/thread/core/concurrency/parallelism), playlist map, verified. Repo evidence: code/Demo.java.

    Every Java program you have written so far ran as a single sequence of steps, and that is enough until something must respond, compute and wait at the same time. This lecture builds the vocabulary that all of multithreading rests on: program, process, thread, CPU core, concurrency and parallelism. It traces a Java source file from a passive stored program, through an executing process, down to the threads that actually do the work on a core. Mastering these distinctions is what separates guessing about concurrent behaviour from reasoning about it.

    1. The Six Terms: From Stored File to Running Code

    Multithreading sits on a chain of ideas that describe how code moves from a stored file to actual execution:

    Program  →  Process  →  Thread  →  CPU Core
(stored)    (running)   (execution)   (hardware that runs it)

Concurrency  →  overlapping progress (can happen on one core)
Parallelism  →  simultaneous execution (needs multiple cores)
    1. Program — a set of instructions stored in a file; passive.
    2. Process — a program in execution; active, isolated, resource-owning.
    3. Thread — a unit of execution inside a process; shares the process memory, owns a stack.
    4. CPU Core — the hardware unit that actually executes machine instructions.
    5. Concurrency — dealing with many tasks by interleaving their progress.
    6. Parallelism — executing many tasks at the same physical instant on multiple units.

    Memory aid A program is a recipe at rest, a process is the meal being cooked, and threads are the cooks working inside one kitchen. One core is one stove: cooks can take turns, but only one uses it at a time.

    2. What Is a Program? Instructions at Rest

    A program is a set of instructions written to make a computer perform a particular task. Examples include a Java source file, a compiled Java class file, a browser application, a code editor and a media player.

    // Demo.java — a program stored as source
public class Demo {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}

    This source can be stored in Demo.java. After compilation, the bytecode is stored in Demo.class. Both are programs in stored form: they contain instructions, but those instructions are not currently being executed.

    A program is a passive entity:

    Program  →  instructions stored in a file  →  not currently executing

    The program file itself occupies storage space. It does not receive its own active process memory, CPU scheduling or execution resources until it is launched. An operating system may cache file contents in memory for performance, but caching does not mean the program is actively executing as a process.

    Is bytecode also a program? Yes. Java source is the human-readable program; Java bytecode is the JVM-executable representation of the same program. Bytecode becomes active only when a JVM loads and executes it.

    Important A .java file and a .class file are both programs. Neither is a process, and neither is executing simply because it exists on disk.

    3. What Is a Process? A Program in Execution

    A process is a running instance of a program. The distinction is the entire point:

    Program  →  passive instructions
Process  →  active execution of those instructions

    When we run java Demo, the operating system starts a process that contains the JVM and the Java application being executed. Launching a real application such as VS Code, Chrome, IntelliJ IDEA or Spotify likewise creates one or more processes, so one visible window does not always correspond to exactly one process — a browser may create separate processes for its interface, tabs, extensions, graphics and network services.

    When a process is created, the operating system provides an execution environment with several parts:

    1. Memory — a virtual address space holding executable code, runtime data, heap memory, thread stacks, memory-mapped files and loaded libraries.
    2. CPU scheduling — the OS scheduler decides when the process's threads receive processor time. The process does not execute instructions directly; its threads do.
    3. Resources — files, network sockets, input and output devices, database connections, shared libraries and operating-system handles.

    A process has three defining properties:

    • Independent execution environment — each process has its own execution context; if one process crashes, other processes normally continue. Applications can still affect one another indirectly through shared files, databases, services or OS resources.
    • Separate address space — one process cannot normally access another process's memory directly.
    • Managed by the operating system — creation, termination, memory allocation, CPU scheduling, resource access and security boundaries are all OS responsibilities.

    Because address spaces are separate, communication between processes needs dedicated mechanisms — pipes, sockets, shared memory, files, message queues and remote calls. This collection is called inter-process communication (IPC), and it is heavyweight compared with talking between threads.

    Where does the JVM fit? Running java Demo starts an operating-system process that contains a JVM runtime, which in turn runs the Java application:

    Operating-system process
+-- JVM runtime
    +-- Java application

    The JVM is not a separate process living inside another unrelated Java process; it is the runtime executing within the process the OS started. Each process also has a PID that identifies it to the operating system.

    Important Process A memory ≠ Process B memory. Isolation is what makes processes robust, and it is also exactly why IPC is comparatively costly.

    4. What Is a Thread? The Unit of Execution

    A thread is an independent path of execution inside a process. A process can contain one or more threads, and the threads execute instructions belonging to the process:

    Program    →  launched as a process
Process    →  contains threads
Thread     →  executes instructions

    A thread carries its own execution-related state: program counter, call stack, stack frames, local variables and current instruction position. Threads inside the same process generally share heap objects, static variables, loaded classes, open files and network resources. The resulting core model is:

    Private execution stacks  +  shared process memory

    This is why a thread is often called a lightweight process: threads are cheaper to create than processes, they share the same process memory, communication between them is faster, and switching between threads is cheaper than switching between processes. A thread is still not a separate process, and it does not normally have its own independent address space.

    A process must contain at least one executing thread. When a normal Java application begins, the JVM creates a thread that invokes main() — the main thread.

    One process
+-- Main thread
+-- Worker thread 1
+-- Worker thread 2
+-- Background thread

    The main thread can create more worker threads, and now each thread has its own Java stack and program counter while all of them can read and write the same shared heap objects.

    Memory aid Stack is private, heap is shared. A thread's local variables live in its own stack; every object it references lives in the shared heap.

    5. Program vs Process vs Thread

    Aspect Program Process Thread
    What it is A set of instructions stored in a file A program in execution A unit of execution inside a process
    Nature Passive (at rest) Active (running instance) Active (execution path)
    Memory Lives on disk as a file Own virtual address space Shares the process heap; own stack
    State Not executing Has a lifecycle; may be running or suspended Has a lifecycle (Lecture 48)
    Resources Only the file itself Files, sockets, handles, PID Uses the process's resources
    Example Demo.java, Demo.class java Demo while it runs The main thread, worker threads

    Reading the table: a program becomes a process when launched, and the actual work inside that process is performed by threads.

    6. Process vs Thread

    Aspect Process Thread
    Definition Running instance of a program Execution path inside a process
    Address space Independent address space Shares the process address space
    Creation cost Higher Usually cheaper
    Context switch Generally heavier Generally lighter
    Communication Requires IPC (pipes, sockets, shared memory) Through shared memory (the heap)
    Isolation Strong Weak (shared memory)
    Crash impact Usually does not directly terminate other processes A serious failure can affect the entire process
    Managed by The operating system JVM plus the OS scheduler

    The trade-off is one sentence: shared memory makes threads fast to communicate with but risky, while process isolation makes them safe but slow to coordinate.

    7. CPU Cores: The Hardware That Executes Instructions

    The CPU ultimately executes native machine instructions, never Java source code directly. Java bytecode may be interpreted by the JVM, compiled into native code by the JIT compiler, or executed as optimized native instructions — but the hardware unit doing the work is the CPU core.

    On a single-core CPU, only one runnable thread can execute on that core at one exact instant. If the process has a main thread and two workers, the scheduler interleaves them:

    Main → Thread-1 → Main → Thread-2 → Thread-1

    The switching can happen so quickly that the threads appear to run together. That switching is a context switch: the CPU stops executing one thread and begins executing another.

    Running Thread-A
→ save Thread-A execution context
→ select Thread-B
→ restore Thread-B execution context
→ continue Thread-B

    The saved execution context may include the instruction pointer, CPU registers, stack pointer, processor state and scheduling information. Context switching is not free: it involves scheduler work, saving and restoring state, cache disruption, translation-lookaside-buffer effects and possibly moving execution between cores. Too many threads can reduce performance because the system spends more time switching than doing useful work.

    Important The OS does not simply copy all CPU register values into Java stack frames. The native thread context is saved in OS- and runtime-managed structures. A safe mental model is: thread execution state is saved, then another thread's state is restored.

    On a multi-core CPU, different threads may execute at the same instant — for example, Core-1 to the main thread, Core-2 to Worker-1, Core-3 to Worker-2 and Core-4 to Worker-3. That is parallel execution.

    8. Concurrency vs Parallelism

    These two words are the most commonly conflated pair in threading:

    • Concurrency means multiple tasks are in progress during overlapping periods of time, but they do not necessarily execute at the exact same instant. It is about managing multiple tasks, and it can exist even with one processor core.
    • Parallelism means multiple tasks are executing at the same physical instant on different processing units. It is about executing multiple tasks simultaneously, and it normally requires multiple cores, processors or hardware execution units.
    Aspect Concurrency Parallelism
    Definition Multiple tasks make progress in overlapping periods Multiple tasks execute at the same instant
    Timing Not necessarily simultaneous Simultaneous by definition
    Hardware Can happen on one core Usually requires multiple cores
    Concern Task coordination and interleaving Simultaneous execution
    Mechanism Scheduling and time slicing Actual hardware execution
    Speed guarantee Does not guarantee speed improvement Can improve throughput when work is parallelizable

    A program can therefore be concurrent but not parallel (several threads on one CPU core) or concurrent and parallel (several coordinated threads executing on multiple cores).

    Two related words should be kept separate as well:

    Term Meaning Isolation
    Multitasking The OS manages multiple tasks or applications during the same period Usually multiple processes
    Multithreading One process contains multiple threads of execution Multiple threads sharing one address space

    9. Why Multithreading (and When It Backfires)

    Multithreading exists because it buys three things:

    1. Responsiveness — a UI thread stays responsive while background work proceeds on another thread.
    2. Throughput — a server can process many requests concurrently; several request-processing threads run the same controller code for different HTTP requests.
    3. Core utilisation — multiple CPU cores can only be used if there are multiple runnable threads to place on them.

    Consider a Spring Boot application. The JAR is a program stored on disk; java -jar application.jar starts an OS process containing a JVM with a main thread, web-server threads, garbage-collection threads, database-pool threads and application worker threads. Those threads share the application objects on the heap, which is exactly why thread safety matters in server applications.

    But threads are not free, and more threads do not always mean more speed:

    • Each thread consumes memory for its stack.
    • Every context switch costs scheduler work plus cache and TLB disruption.
    • Once the number of runnable threads exceeds the number of usable cores, the extra threads mostly wait and switch, so throughput can fall.
    • Shared mutable state invites contention and races (Lecture 50), so coordination can cost more than the parallelism gains.

    Golden rule Multithreading is a tool for overlapping wait time and using idle cores — not a volume knob for speed. Past a point, more threads means more overhead, not more work done.

    10. Shared Heap, Private Stack: Why Threads Race

    The reason threads are both powerful and dangerous is the memory model: they share the heap but not their stacks. Heap objects and static variables are common property; local variables and method-call frames are private to a thread (Lecture 45). When two threads read and write the same mutable heap location without coordination, the result depends on timing — a data race (forward reference, Lecture 50).

    The classic demonstration is a counter incremented by two threads. counter++ is not one operation; it is read, add, then write, and the interleaving can lose updates.

    Important The output of the counter program below is often less than the expected total. That is not a bug in Thread; it is a race on shared mutable state, and it is the subject of Lecture 50.

    11. Java's Threading Model

    Java's model rests on a few facts:

    1. A platform thread maps one-to-one to an operating-system thread; the OS schedules it.
    2. The JVM itself runs threads: the main thread, garbage-collection threads, JIT compiler threads and others, even before main() runs.
    3. Higher-level APIs (executors, thread pools) build on the same separation between a task and its execution (Lecture 48).
    4. Virtual threads (Project Loom, Java 21) multiplex many lightweight virtual threads onto a small number of platform threads — a forward reference to Lecture 57.

    Interviewer's perspective "How many threads does a simple Java program have?" More than one. At minimum the JVM starts the main thread plus internal threads for garbage collection and JIT compilation, so a "single-threaded" Java program is only single-threaded from the programmer's point of view.

    12. Code: The Main Thread and a Concurrency Hint

    Every Java program already runs on a thread. The first program prints the name of the thread executing main():

    // Demo.java — every program already runs on a thread
public class Demo {
    public static void main(String[] args) {
        Thread current = Thread.currentThread();
        System.out.println("Running on: " + current.getName());
        // Running on: main
    }
}

    The second program shows threads sharing the heap. Two threads increment one shared counter; the result hints at a race, which is fully treated later:

    // Demo.java — two threads share the heap; the result hints at a race
public class Demo {
    static int counter = 0;                 // shared mutable state on the heap

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter++;                  // read, add, write — not atomic
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(counter);        // often less than 200000
    }
}

    The third program shows one process with several threads and asks how many cores are available:

    // Demo.java — one process, several threads, one or many cores
public class Demo {
    public static void main(String[] args) {
        System.out.println("Cores: " + Runtime.getRuntime().availableProcessors());
        for (int i = 1; i <= 3; i++) {
            final int id = i;
            new Thread(() -> System.out.println(
                    "Task " + id + " on " + Thread.currentThread().getName()
            )).start();
        }
    }
}

    The order of the printed lines is not guaranteed: on one core the threads interleave (concurrency), and on several cores they can run at the same instant (parallelism).

    13. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Confusing program, process and thread Wrong mental model for every later topic Program is stored instructions; process is a running instance; thread is an execution path
    Mixing up concurrency and parallelism Expecting speedup from one core Concurrency interleaves; parallelism needs multiple cores
    "More threads is always faster" Context-switch and contention overhead Size pools to the workload and core count
    Assuming threads are free Extra stack memory and scheduling cost Create threads deliberately, or use a pool
    Sharing mutable state without synchronization Lost updates and data races Coordinate access (Lecture 50)
    Believing all threads run at the exact same instant on one core Wrong reasoning about timing On one core they take turns; simultaneity needs multiple cores
    Treating a .class file as a running process A stored program mistaken for execution It is active only when a JVM loads and runs it in a process
    Assuming java Demo creates one thread Underestimating JVM threads The JVM also starts GC, JIT and other internal threads

    14. Myth vs Reality

    Myth Reality
    "A program and a process are the same thing." A program is passive stored instructions; a process is an active running instance.
    "Starting a Java program starts only one thread." The JVM starts the main thread plus internal threads such as GC and JIT before and around main().
    "Threads always run at the exact same instant." Only on multiple cores; on a single core they interleave through time slicing.
    "More threads always means more speed." Beyond the usable core count, threads add context-switch overhead and can slow the system down.
    "Each thread has its own copy of every variable." Threads share heap objects and static variables; only stack locals are private.

    15. Common Trap Questions

    Trap 1 — Is a .class file a process? No. It is a program in stored form. It becomes active only when a JVM loads and executes it inside a process.

    Trap 2 — Does the JVM run in a different process from the Java application? No. The process started by java Demo contains the JVM runtime, which in turn runs the application.

    Trap 3 — Is it concurrency or parallelism on a single core? Concurrency. Parallelism requires multiple cores or hardware execution units.

    Trap 4 — Do threads share the stack or the heap? They share the heap; each thread has its own stack and program counter (Lecture 45).

    Trap 5 — Can two processes access each other's memory directly? No. Processes have separate address spaces; they need IPC such as pipes, sockets or shared memory.

    Trap 6 — Can a process run without any thread? No. A process must contain at least one executing thread; a process with no thread cannot do work.

    Trap 7 — Do more threads guarantee higher throughput? No. Extra threads bring context-switch and contention overhead, so throughput can fall after a point.

    Trap 8 — Is IPC as cheap as thread communication? No. Threads communicate through shared heap memory; processes must use OS-mediated IPC, which is heavier.

    16. Points to Remember

    1. A program is passive stored instructions; a process is a program in execution; a thread is an execution path inside a process.
    2. Demo.java source and Demo.class bytecode are both programs in stored form; neither is executing.
    3. Running java Demo creates an OS process containing the JVM runtime and the application.
    4. Each process has its own virtual address space, resources and PID; processes are isolated.
    5. A process must contain at least one thread; the JVM starts a main thread that invokes main().
    6. Threads share the process heap, static data and open resources but have private stacks and program counters (Lecture 45).
    7. Creating threads is cheaper than creating processes, and thread context switches are generally lighter than process switches.
    8. A single core executes one thread at an instant; concurrency on one core is achieved by time slicing.
    9. Concurrency is overlapping progress; parallelism is simultaneous execution on multiple cores.
    10. More threads do not guarantee more speed: context switching, cache disruption and shared-state contention create diminishing returns (Lecture 50).

    17. Likely Interview Questions

    Question Crisp Answer
    What is a program? A set of instructions stored in a file; a passive entity that is not executing.
    What is a process? A running instance of a program, with its own address space, resources and PID, managed by the OS.
    What is a thread? An independent path of execution inside a process; it has its own stack and program counter.
    Difference between a program and a process? A program is stored instructions; a process is that program in active execution.
    Difference between a process and a thread? A process has its own address space and is isolated; a thread shares the process address space and is cheaper to create and switch.
    Why is a thread called a lightweight process? It is cheaper to create, shares process memory, communicates faster and switches more cheaply than a process.
    Do threads share memory? Which parts? They share the heap, static variables and open resources; each thread has its own stack, PC register and local variables.
    Can a process exist without a thread? No; a process must contain at least one executing thread.
    What is concurrency? Multiple tasks make progress during overlapping periods, not necessarily at the same instant; possible on one core.
    What is parallelism? Multiple tasks execute at the same physical instant on different cores, requiring multiple hardware units.
    What is a context switch, and why is it costly? The CPU saves one thread's state and restores another's; it costs scheduler work, cache and TLB disruption.
    Why does the JVM start multiple threads? It needs threads for main, garbage collection, JIT compilation and other runtime services, not just application code.

    18. Final Summary

    Program   : Demo.java  → javac → Demo.class            (stored, passive)
Process   : java Demo  → OS process → JVM runtime      (running, isolated, owns resources)
Thread    : main + workers inside the process          (execution; private stack, shared heap)
CPU Core  : one core = one thread at an instant        (scheduler interleaves, context switch costs)
Concurrency  → overlapping progress  → possible on one core
Parallelism  → simultaneous execution → needs multiple cores
    • Program → stored instructions; .java and .class are both programs, neither is executing.
    • Process → a running instance with its own address space, resources and PID; isolation makes IPC heavyweight.
    • Thread → the unit of execution inside a process; private stack, shared heap, cheaper to create and switch.
    • CPU core → the hardware that runs native instructions; one core executes one thread at an instant.
    • Concurrency → interleaving for progress; can happen on a single core.
    • Parallelism → true simultaneous execution; requires multiple cores.
    • JVM → runs several threads (main, GC, JIT); platform threads map one-to-one to OS threads, with virtual threads in Lecture 57.
    • Danger → shared mutable heap means races; coordination is Lecture 50.

    Golden rule A program becomes active as a process, the work inside that process is performed by threads, and whether those threads merely interleave or truly run together depends on the number of CPU cores.

    One-line takeaway: a program is stored instructions, a process is that program running in isolation, and threads are the execution paths inside it that share the heap and race toward the cores.
