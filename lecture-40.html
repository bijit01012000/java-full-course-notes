    Part 5 · Collections, Lambdas & Streams · Lecture 40

    Java Stream Methods Deep Dive | All Intermediate & Terminal Operations

    17 sections · interview-oriented · both themes

    Scope evidence: "Java Stream Methods Deep Dive | All Intermediate & Terminal Operations" (playlist map, verified). Repo evidence: 3 Demo files.

    Lecture 39 introduced how streams are created and how the pipeline is architected. This lecture builds the method catalogue on top of that architecture: the lazy intermediate operations that shape a pipeline, the eager terminal operations that trigger it, the short-circuiting terminals that let infinite streams finish, and the collector factory that reshapes results. It also settles the two pairs that beginners confuse most: map versus flatMap, and reduce versus collect. The governing idea is that a stream pipeline is a declarative query which stays completely inert until a terminal operation asks for an answer.

    1. A Stream Pipeline Has Two Kinds of Operations

    A stream is a sequence of elements supporting sequential and parallel aggregate operations. It is not a collection: it does not store data, it does not expose indexes, and it is single-use — once a terminal operation runs, the stream is consumed. A pipeline always has the same three-part shape:

    1. A source — a collection, an array, a generator or an I/O channel (Lecture 39).
    2. Intermediate operations — zero or more stages that return another Stream and are lazy.
    3. A terminal operation — exactly one final stage that produces a result or a side effect and is eager.

    The defining property is laziness: chaining filter, map and sorted runs no code at all. Only when the terminal operation is invoked does the pipeline execute, element by element, pulling data through the whole chain.

    // Demo.java — a pipeline is inert until the terminal operation runs
import java.util.*;
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        List<String> names = List.of("Ada", "Alan", "Grace", "Edsger");

        Stream<String> pipeline = names.stream()      // source
                .filter(n -> n.length() > 3)          // intermediate (lazy)
                .map(String::toUpperCase);            // intermediate (lazy)
        System.out.println("Nothing has run yet");

        pipeline.forEach(System.out::println);        // terminal (eager)
        // ADA, ALAN, GRACE, EDSGER
    }
}

    Important The word "intermediate" describes the return type, not the effort: it always returns a Stream, so stages compose. The word "terminal" describes the effect: it returns something other than a Stream, which is why it must be last and why it fires the pipeline.

    2. Intermediate Operations vs Terminal Operations

    Intermediate operations are lazy and return a Stream; terminal operations are eager and return a result or perform a side effect.

    Intermediate operation What it does Shape
    filter(Predicate) keep elements matching the predicate Stream<T> to Stream<T>
    map(Function) transform each element, one to one Stream<T> to Stream<R>
    mapToInt / mapToLong / mapToDouble transform to a primitive stream Stream<T> to IntStream (and so on)
    flatMap(Function) replace each element by a stream, then concatenate Stream<T> to Stream<R>
    distinct() remove duplicates using equals/hashCode Stream<T> to Stream<T>
    sorted() / sorted(Comparator) stable sort by natural or given order Stream<T> to Stream<T>
    peek(Consumer) run an action per element, for debugging Stream<T> to Stream<T>
    limit(n) cap the stream to the first n elements Stream<T> to Stream<T>
    skip(n) discard the first n elements Stream<T> to Stream<T>
    takeWhile(Predicate) take until the predicate first fails (Java 9) Stream<T> to Stream<T>
    dropWhile(Predicate) drop until the predicate first fails (Java 9) Stream<T> to Stream<T>
    boxed() wrap primitives as objects IntStream to Stream<Integer>
    Terminal operation Result Short-circuits Note
    forEach(Consumer) void no order not guaranteed in parallel
    forEachOrdered(Consumer) void no respects encounter order, even in parallel
    collect(Collector) a container or value no mutable reduction
    reduce(...) Optional<T> or T no immutable reduction
    count() long no counts elements
    min(Comparator) / max(Comparator) Optional<T> no needs a comparator
    findFirst() Optional<T> yes first in encounter order
    findAny() Optional<T> yes any element; non-deterministic in parallel
    anyMatch(Predicate) boolean yes true at the first match
    allMatch(Predicate) boolean yes false at the first counterexample
    noneMatch(Predicate) boolean yes false at the first match
    toArray() / toArray(IntFunction) Object[] or T[] no materializes the stream

    Memory aid Intermediate = lazy + returns a Stream; terminal = eager + returns a result. If the method name is followed by another dot in valid code, it was intermediate.

    3. The Intermediate Operations in Detail

    • filter keeps the elements for which the predicate is true. It never changes an element's type or value.
    • map applies a function and changes the element type. map is stateless and is the standard field extractor (map(Person::name)).
    • mapToInt / mapToLong / mapToDouble produce primitive streams such as IntStream, which expose numeric terminals — sum(), average(), max(), min() — and, through summaryStatistics(), all of them at once. They also avoid the boxing cost of mapping to Integer.
    • flatMap maps each element to a stream and then concatenates those streams. It is the tool for one-to-many expansion and for flattening nested structures (Section 6).
    • distinct removes duplicates by equals and hashCode, exactly like a HashSet (Lecture 22). It preserves the first occurrence and is a stateful operation.
    • sorted() sorts by natural order (the elements must be Comparable); sorted(comparator) sorts by a supplied comparator. For ordered streams the sort is stable, so equal elements keep their original relative order.
    • peek runs a Consumer on each element as it flows past. It exists for debugging only: it is lazy, it can be skipped by a short-circuiting terminal, and its interleaving with parallel chunks is not guaranteed. Using it for business logic is a defect.
    • limit(n) stops the pipeline after n elements and skip(n) discards the first n. Both make a stream smaller and are how an infinite stream is bounded.
    • takeWhile and dropWhile (Java 9) operate on a predicate: takeWhile stops at the first failing element and keeps everything before it; dropWhile discards everything before the first failure and keeps the rest. Unlike filter, takeWhile stops scanning once the predicate fails.
    • boxed() converts a primitive stream back to a stream of wrapper objects, for example IntStream to Stream<Integer>.

    Interviewer's perspective "Why is peek discouraged for real work?" Three reasons: it is an intermediate operation, so it may be optimized away or skipped by a short-circuiting terminal; its side effects are not ordered under parallel execution; and the contract of peek explicitly documents it as existing for debugging, so relying on it is undefined ground.

    4. The Terminal Operations in Detail

    • forEach applies a Consumer to every element for its side effect. Under a parallel stream the visit order is not specified; forEachOrdered forces encounter order at the cost of parallelism (Lecture 42).
    • collect is the general mutable reduction: it accumulates elements into a mutable container described by a Collector (Section 8).
    • reduce is the general immutable reduction: it folds the elements into a single new value (Section 7).
    • count returns the number of elements as a long. A sized source such as a list can answer without traversal.
    • min / max need a Comparator and return an Optional because a stream may be empty.
    • findFirst / findAny also return Optional; both may stop early (Section 5).
    • anyMatch / allMatch / noneMatch return a boolean and are the boolean counterparts of existence, universality and emptiness.
    • toArray materializes the stream, either as Object[] or, with an IntFunction generator (String[]::new), as a correctly typed array.

    Important min and max do not mean numeric comparison unless you say so: they compare with the Comparator you supply. min(Comparator.comparing(Person::age)) is the youngest, not the "smallest" object.

    5. Short-Circuiting and Infinite Streams

    A short-circuiting operation can produce a result without consuming every element. This is what makes infinite streams usable. The short-circuiting terminal operations are findFirst, findAny, anyMatch, allMatch and noneMatch; the intermediate limit (and takeWhile) bounds the input they scan.

    Operation Kind Why it can stop early
    findFirst terminal the first matching element is already the answer
    findAny terminal any matching element is acceptable
    anyMatch terminal one true proves the result
    allMatch terminal one false disproves the result
    noneMatch terminal one true disproves the result
    limit(n) intermediate only n elements are ever demanded

    An infinite stream terminates only if something downstream is short-circuiting or bounding:

    // Stream.iterate is infinite; anyMatch bounds the scan
boolean found = Stream.iterate(1, n -> n + 1)
        .anyMatch(n -> n == 100);          // stops at 100 -> true

    By contrast, sorted() on an infinite stream never terminates: sorting must see every element before it can emit the first one. The same is true of count on an infinite stream. Order matters: put limit before sorted if you want only the first n sorted, and never place sorted before a bound on an unbounded source.

    Golden rule An infinite stream plus a short-circuiting terminal is a legitimate, terminating program. An infinite stream plus sorted, collect or count is a program that never returns.

    6. map vs flatMap

    map maps one element to exactly one element. flatMap maps one element to a stream of zero or more elements and then flattens all those streams into one. The classic case is a list of lists: map(List::stream) yields a Stream<Stream<T>>, while flatMap(List::stream) yields the flat Stream<T> and removes the extra level.

    Aspect map flatMap
    Mapping one element to one element one element to zero or more
    Function returns a value R a Stream<R>
    Result shape Stream<R> a flattened Stream<R>
    Nesting may create nested structures removes one level of nesting
    Cardinality preserved (before other stages) may change
    Typical use transform a field expand and merge a collection per element 
    // Demo2.java — flatMap flattens a list of lists and expands a word to letters
import java.util.*;
import java.util.stream.*;

public class Demo2 {
    public static void main(String[] args) {
        List<List<Integer>> nested = List.of(
                List.of(1, 2),
                List.of(3, 4, 5),
                List.of(6));

        List<Integer> flat = nested.stream()
                .flatMap(List::stream)       // Stream<List<Integer>> -> Stream<Integer>
                .collect(Collectors.toList());
        System.out.println(flat);            // [1, 2, 3, 4, 5, 6]

        List<String> words = List.of("ab", "cd");
        List<String> letters = words.stream()
                .flatMap(w -> Arrays.stream(w.split("")))   // one word -> many characters
                .collect(Collectors.toList());
        System.out.println(letters);         // [a, b, c, d]
    }
}

    Memory aid map = one in, one out. flatMap = one in, many out, then flatten. If your mapping function returns a collection or a stream, you almost certainly want flatMap.

    7. reduce: The Three Forms

    Reduction folds a stream into a single value by repeatedly applying an accumulator. Java exposes three overloads, distinguished by whether an identity is supplied and whether a combiner is required.

    1. reduce(identity, accumulator) returns T. The identity is the seed and must be a true identity for the operation (0 for sum, 1 for product, "" for string concatenation). An empty stream returns the identity.
    2. reduce(accumulator) returns Optional<T>. There is no identity, so an empty stream has no answer and the result is Optional.empty().
    3. reduce(identity, accumulator, combiner) returns T. The combiner merges partial results produced by parallel chunks; it is required when the reduction runs in parallel.
    // Demo3.java — identity, accumulator-only, and combiner forms of reduce
import java.util.*;
import java.util.stream.*;

public class Demo3 {
    public static void main(String[] args) {
        List<Integer> nums = List.of(1, 2, 3, 4, 5);

        int sum = nums.stream()
                .reduce(0, Integer::sum);                 // form 1 -> 15

        Optional<Integer> max = nums.stream()
                .reduce(Integer::max);                    // form 2 -> Optional[5]

        int parallelSum = nums.parallelStream()
                .reduce(0, Integer::sum, Integer::sum);   // form 3 -> 15

        System.out.println(sum + " " + max.orElse(-1) + " " + parallelSum);
    }
}

    For an object result, reduce can also carry a partially built value, but remember that it creates a new value each step. When the result is a container you intend to keep mutating, collect is the correct tool (Section 9).

    Important The identity constraint is not a suggestion. reduce("", String::concat) is correct because "" is the identity of concatenation; reduce("x", String::concat) prepends an unwanted x (and, in parallel, may prepend it several times). A wrong identity silently produces wrong answers.

    8. collect and the Collectors Catalogue

    collect is a mutable reduction: the stream is accumulated into a mutable container, and a Collector describes how. Collectors is the factory of ready-made collectors.

    Collector Produces Note
    toList() List<T> mutable list; use toUnmodifiableList for an immutable one
    toSet() Set<T> duplicate elements collapse
    toMap(key, value) Map<K,V> duplicate keys throw IllegalStateException
    toMap(key, value, merge) Map<K,V> the merge function resolves duplicate keys
    joining(delimiter) String concatenates CharSequence elements
    groupingBy(classifier) Map<K, List<T>> one group per key
    groupingBy(classifier, downstream) Map<K, D> group, then reduce each group
    partitioningBy(predicate) Map<Boolean, List<T>> exactly two groups, true and false
    counting() Long number of elements, often a downstream
    summingInt(mapper) Integer sum of a derived int
    averagingInt(mapper) Double mean of a derived int
    mapping(mapper, downstream) depends on downstream map before the downstream collector
    summarizingInt(mapper) IntSummaryStatistics count, sum, min, max and average together
    teeing(a, b, merger) R Java 12: feed two collectors and merge their results 
    // Demo2.java — groupingBy with a downstream, and counting per group
import java.util.*;
import java.util.stream.*;

public class Demo2 {
    static class Person {
        private final String name;
        private final String city;
        Person(String name, String city) { this.name = name; this.city = city; }
        String name() { return name; }
        String city() { return city; }
    }

    public static void main(String[] args) {
        List<Person> people = List.of(
                new Person("Ada", "London"),
                new Person("Alan", "London"),
                new Person("Grace", "New York"),
                new Person("Edsger", "Austin"));

        Map<String, List<String>> byCity = people.stream()
                .collect(Collectors.groupingBy(
                        Person::city,
                        Collectors.mapping(Person::name, Collectors.toList())));
        System.out.println(byCity);
        // {New York=[Grace], Austin=[Edsger], London=[Ada, Alan]}

        Map<String, Long> countByCity = people.stream()
                .collect(Collectors.groupingBy(Person::city, Collectors.counting()));
        System.out.println(countByCity);
        // {New York=1, Austin=1, London=2}
    }
}

    The downstream collector is the key idea: groupingBy(classifier, downstream) groups first and then applies the downstream collector to each bucket, so counting, summing, averaging and mapping compose naturally. partitioningBy is the two-bucket special case for a predicate, and teeing (Java 12) runs two collectors over the same stream and merges their results.

    Interviewer's perspective "What happens if toMap sees two elements with the same key?" It throws IllegalStateException with a message naming the duplicate key. The fix is not to catch it but to supply a merge function, for example (a, b) -> a (keep the first) or (a, b) -> a + ", " + b (combine), or to switch to groupingBy when the intent is a list per key.

    9. reduce vs collect

    reduce performs an immutable reduction: each step produces a new value. collect performs a mutable reduction: elements are folded into one mutable container that is updated in place. The distinction is not cosmetic; it decides both performance and parallel safety.

    Aspect reduce collect
    Nature immutable reduction mutable reduction
    Combines into a new value each step a single mutable container
    Seed an identity value a supplier of a container
    Description identity plus accumulator (plus combiner) a Collector (supplier, accumulator, combiner, finisher)
    Parallel fit accumulator must be associative and stateless designed for parallel accumulation into chunks
    Result type T or Optional<T> any container: List, Set, Map, String
    Typical use sum, product, max, string concatenation toList, toMap, groupingBy, joining
    Cost profile allocates a value per step mutates one accumulator, usually cheaper

    Memory aid reduce builds a new value; collect fills a container. If the answer is a single number, reduce; if the answer is a collection, map, or string, collect.

    10. Ordering and Stability

    Encounter order is the order in which the source presents its elements. Several stream methods make promises about it:

    • sorted() is stable for ordered streams — elements that compare equal retain their relative encounter order.
    • distinct() preserves the first occurrence — it keeps the earliest of each duplicate group.
    • forEach does not guarantee order under parallel execution; forEachOrdered does, at the cost of some parallelism.
    • findFirst respects encounter order; findAny does not. In a parallel pipeline findAny may return any matching element, which is faster but non-deterministic.
    • unordered() records that order does not matter, allowing some operations to run more freely; it can change the results of order-sensitive operations.
    • peek and map do not reorder on a sequential ordered stream; they see elements in encounter order, but only for elements the pipeline actually demands.

    Important sorted being stable is a property of ordered streams. On an unordered stream any permutation is acceptable, so equal elements have no promised relative order.

    11. Worked Examples: The toMap Duplicate-Key Trap and joining

    The single most common collector bug is toMap on data that is not unique by key. The collector refuses to guess and throws.

    // Demo3.java — toMap duplicate-key trap, the merge fix, and joining
import java.util.*;
import java.util.stream.*;

public class Demo3 {
    public static void main(String[] args) {
        List<String> words = List.of("apple", "banana", "avocado");

        try {
            Map<Character, String> first = words.stream()
                    .collect(Collectors.toMap(w -> w.charAt(0), w -> w));
            System.out.println(first);
        } catch (IllegalStateException e) {
            System.out.println("Duplicate key -> " + e.getMessage());
        }

        Map<Character, String> merged = words.stream()
                .collect(Collectors.toMap(
                        w -> w.charAt(0),           // key
                        w -> w,                      // value
                        (a, b) -> a + ", " + b));    // merge function
        System.out.println(merged);                  // {a=apple, avocado, b=banana}

        String joined = words.stream()
                .collect(Collectors.joining(", "));  // delimiter
        System.out.println(joined);                  // apple, banana, avocado
    }
}

    The first toMap throws because apple and avocado share the key a. The second supplies the merge function (a, b) -> a + ", " + b, which folds the colliding values instead of failing. joining is the string-specialized collector: joining(), joining(delimiter) and joining(delimiter, prefix, suffix).

    12. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    toMap on duplicate keys IllegalStateException supply a merge function, or use groupingBy
    Using peek for real work may be skipped by a short-circuit, order not guaranteed in parallel do the work in map, forEach or collect
    Stateful lambdas (mutating a shared variable or list) wrong results under parallel execution use collect/reduce; revisit parallel rules in Lecture 42
    Assuming collect(toList) is immutable the returned list is mutable use toUnmodifiableList (Java 10) or List.copyOf
    forEach order in a parallel stream elements arrive in no defined order use forEachOrdered
    Reusing a stream IllegalStateException on the second terminal build a fresh stream from the source each time
    Boxing overhead in numeric pipelines Stream<Integer> allocates wrappers use mapToInt and the primitive streams
    findAny when order matters non-deterministic element returned use findFirst
    sorted on an infinite stream never terminates bound with limit before sorting
    takeWhile treated as filter elements after the first failure are lost use filter when you must scan the whole stream

    Golden rule Streams are single-use pipelines, not reusable collections. A stream that has been operated upon is closed forever; if you need the data twice, obtain it twice.

    13. Myth vs Reality

    Myth Reality
    "Intermediate operations run as they are chained." They are lazy; nothing runs until a terminal operation is invoked.
    "peek is a good place to do real work." peek is for debugging; it may be skipped and its timing is not guaranteed.
    "reduce and collect are interchangeable." reduce is immutable reduction; collect is mutable reduction into a container.
    "findAny and findFirst mean the same." findFirst respects encounter order; findAny may return any element, especially in parallel.
    "toMap silently overwrites duplicate keys." It throws IllegalStateException; only a supplied merge function resolves duplicates.

    14. Common Trap Questions

    Trap 1 — Laziness: "A pipeline calls filter and map but no terminal operation. How many elements are processed?" Zero. Intermediate operations are lazy; the pipeline executes only when a terminal operation is invoked.

    Trap 2 — peek guarantees: "peek prints every element, so the print is reliable, right?" No. peek is lazy, may be skipped by a short-circuiting terminal, and its interleaving under parallel execution is not guaranteed. It is a debugging aid only.

    Trap 3 — Duplicate keys: "What does Collectors.toMap do when two elements share a key?" It throws IllegalStateException unless a merge function (a, b) -> ... is supplied; use groupingBy when a list per key is intended.

    Trap 4 — findFirst versus findAny: "In a parallel stream, does findAny return the first element?" No. findAny may return any matching element and is deliberately non-deterministic for speed; use findFirst when encounter order matters.

    Trap 5 — Stream reuse: "Can I call stream.count() and then stream.forEach(...) on the same stream?" No. A stream is single-use; the second terminal operation throws IllegalStateException.

    Trap 6 — Infinite sorted: "Will Stream.iterate(1, n -> n + 1).sorted().findFirst() ever finish?" No. sorted must see every element before it can emit one, and the source never ends, so it hangs.

    Trap 7 — Wrong identity: "What does Stream.of("a", "b").reduce("x", String::concat) return?" "xab". The first argument is a seed, not a neutral value; with a wrong identity the seed contaminates the result (and may be inserted once per parallel chunk).

    Trap 8 — takeWhile versus filter: "Does takeWhile(n -> n < 3) behave like filter(n -> n < 3)?" No. takeWhile stops at the first element that fails and drops everything after it; filter scans the whole stream and keeps every match.

    15. Points to Remember

    1. A stream pipeline is a source, zero or more lazy intermediate operations, and exactly one eager terminal operation.
    2. Intermediate operations return a Stream and run nothing until a terminal operation executes.
    3. Terminal operations return a result or cause a side effect; short-circuiting terminals can stop early.
    4. distinct uses equals/hashCode and keeps the first occurrence; sorted is stable for ordered streams.
    5. peek exists for debugging only; it is lazy and must never carry business logic.
    6. map is one-to-one; flatMap is one-to-many and flattens nested streams such as Stream<List<T>> to Stream<T>.
    7. reduce has three forms: identity plus accumulator returns T; accumulator-only returns Optional<T>; the three-argument form adds a combiner for parallel execution.
    8. collect is mutable reduction through Collectors; toMap throws on duplicate keys unless a merge function is supplied, and joining builds strings.
    9. groupingBy with a downstream collector, partitioningBy, counting, summingInt, summarizingInt, mapping and teeing compose to express most reporting queries.
    10. Streams are single-use; prefer toUnmodifiableList for immutable results, avoid stateful lambdas, and defer parallel-stream semantics to Lecture 42.

    16. Likely Interview Questions

    Question Crisp Answer
    Difference between intermediate and terminal operations? Intermediate operations return a Stream and are lazy; terminal operations produce a result or side effect and trigger execution.
    Why are streams lazy? To allow fusion, optimization and short-circuiting; work happens only when a terminal operation demands elements.
    Difference between map and flatMap? map transforms one element to one; flatMap transforms one element to many and flattens the resulting streams.
    Difference between map and mapToInt? map yields a boxed Stream<R>; mapToInt yields an IntStream with numeric terminals and no boxing.
    What is distinct based on? equals and hashCode; it preserves the first occurrence.
    Is sorted stable? Yes for ordered streams: equal elements keep their original relative order.
    Which operations short-circuit? Terminal findFirst, findAny, anyMatch, allMatch, noneMatch, plus intermediate limit and takeWhile.
    Difference between findFirst and findAny? findFirst returns the first element in encounter order; findAny returns any element and is non-deterministic, which helps in parallel.
    What does reduce do and what are its forms? Immutable reduction: identity plus accumulator returns T; accumulator-only returns Optional<T>; identity plus accumulator plus combiner supports parallel.
    Difference between reduce and collect? reduce folds into a new value; collect accumulates into a mutable container via a Collector.
    What happens when toMap meets duplicate keys? It throws IllegalStateException unless a merge function is provided.
    Can a stream be reused? No; a stream is single-use and throws IllegalStateException if operated upon twice.

    17. Final Summary

    source  →  [ intermediate operations: lazy, return Stream ]  →  terminal operation (eager)
             filter map mapToInt flatMap distinct sorted peek
             limit skip takeWhile dropWhile boxed
                                   |
             forEach forEachOrdered collect reduce count min max
             findFirst findAny anyMatch allMatch noneMatch toArray

short-circuit : findFirst findAny anyMatch allMatch noneMatch (+ limit)
map      : 1 -> 1                 flatMap : 1 -> many (flatten Stream<List<T>> -> Stream<T>)
reduce   : immutable              collect : mutable
collectors: toList toSet toMap joining groupingBy partitioningBy
            counting summingInt averagingInt mapping summarizingInt teeing
toMap    : duplicate key -> IllegalStateException unless a merge function is supplied
    • Intermediate → lazy, return a Stream; nothing runs until a terminal operation fires the pipeline.
    • Terminal → eager, produce a result or side effect; short-circuiting terminals stop early and tame infinite streams.
    • map vs flatMap → transform one-to-one versus expand one-to-many and flatten.
    • reduce vs collect → immutable folding versus mutable accumulation into a container.
    • Collectors → the factory for collect: toMap needs a merge function, joining builds strings, groupingBy plus a downstream aggregates.
    • Ordering → sorted stable, distinct keeps the first, forEachOrdered versus forEach, findFirst versus findAny.
    • Traps → peek is not for logic, streams are single-use, toMap rejects duplicate keys, sorted on an infinite stream never returns.

    Golden rule A stream is a lazy query, not a loop: chain the intermediate operations you need, close the pipeline with the right terminal operation, and let laziness, short-circuiting and the collectors do the work.

    One-line takeaway: intermediate operations build a lazy Stream, terminal operations force an eager answer, and the collector factory — with flatMap, reduce and collect understood — is what turns a stream of data into exactly the shape you need.
