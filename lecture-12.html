    Part 2 · Arrays & OOP Core · Lecture 12

    Object Oriented Programming in Java — Classes, Objects & the new Keyword

    20 sections · interview-oriented · both themes

    Scope evidence: lecture title "Object Oriented Programming in Java | Classes, Objects, new Keyword" (playlist map, verified). Repo evidence: code/Demo.java.

    Object-oriented programming is the paradigm Java is built around: instead of one long list of instructions, a program is a set of objects that hold state and expose behaviour. This lecture defines the class as a blueprint and the object as a runtime instance, dissects the new keyword that connects the two, and draws the line between an object and the reference variable that points at it. It also covers class members, the dot operator, instance state independence, and the pitfalls — null references, a forgotten new, and identity comparison — that trip up beginners. Constructors, this, static members, memory internals and the Object class are previewed here and examined in their own lectures.

    1. The OOP Paradigm: Programs as Interacting Objects

    Procedural programming organizes a program as a sequence of functions acting on shared data; object-oriented programming organizes it as a collection of objects that each bundle their own data and the operations on that data, and that interact by calling one another's methods. An object is defined by three things:

    1. State — the data it holds (fields).
    2. Behaviour — the operations it performs (methods).
    3. Identity — the fact that it is a distinct entity, even if another object holds identical data.

    A class is the user-defined type that describes state and behaviour; an object is one concrete value of that type. Java is not fully object-oriented (it has primitive types such as int and double, Lecture 3), but every non-primitive value in a Java program is an object built from some class.

    Memory aid — an object is a noun with a memory: the class says what the noun knows (state) and what it can do (behaviour), and each object remembers its own version.

    2. Class = Blueprint, Object = Instance in Memory

    A class is a blueprint: it defines field names and types and method bodies, but it occupies no per-object storage by itself. An object — also called an instance — is what exists at runtime once the blueprint is instantiated. The distinction is the same as a house plan versus the houses built from it: one plan, many houses, each with its own paint colour.

    Aspect Class Object
    What it is Blueprint, specification, template Instance created from the blueprint
    Nature Logical, declared at compile time Physical, exists at runtime
    Memory Field definitions only; loaded once Heap memory for its instance fields (Lecture 45)
    Created by class keyword new keyword
    How many One definition Any number of instances
    Analogy House plan The built houses

    The class is a type, so it can be used in declarations (Student s;); the object is a value, so it must be created (new Student()). A common beginner error is to treat the declaration of a reference variable as the creation of an object — Section 6 makes that distinction precise.

    3. Class Members: Fields, Methods and Constructors

    Everything declared inside a class body is a member. The three member kinds introduced here are:

    1. Fields (instance variables) — the state each object carries. Declared with a type and a name; each object gets its own copy.
    2. Methods — the behaviour. A method has a return type, a name, a parameter list and a body; calling it is a message to the object.
    3. Constructors — the initializer that runs when new creates the object. It has the class name and no return type. (Signatures, overloading and this are the whole of Lecture 13.)
    // Demo.java — a class is a blueprint; objects are built from it
class Student {
    String name;     // field (instance variable)
    int marks;       // field (instance variable)

    void show() {    // method (behaviour)
        System.out.println(name + " scored " + marks);
    }
}

public class Demo {
    public static void main(String[] args) {
        Student s1 = new Student();   // object created on the heap
        s1.name = "Aarav";
        s1.marks = 91;
        s1.show();                    // Aarav scored 91

        Student s2 = new Student();   // a second, independent object
        s2.name = "Diya";
        s2.marks = 78;
        s2.show();                    // Diya scored 78
    }
}

    If a constructor is not written, the compiler inserts a default constructor (no arguments, empty body). Fields that are not assigned explicitly receive default values — 0, 0.0, '\u0000', false, and null for references — but local variables do not, which is why an uninitialized local reference is a compile-time error rather than a silent null.

    Important A .java file may declare several classes, but at most one may be public, and the file must be named after it. In Demo.java above, Student is package-private and Demo is public — that is legal because the file is named Demo.java.

    4. Instance Variables vs Class Variables

    A field declared without static is an instance variable: every object owns a separate copy, so changing s1.marks never affects s2.marks. A field declared static is a class variable: one copy for the entire class, shared by all objects, initialized when the class is loaded.

    Aspect Instance variable Class variable (static)
    Copies One per object One per class, shared by all
    Declared with No modifier static keyword
    Access style object.field ClassName.field (preferred)
    Changes affect Only that object Every object of the class
    Deep dive This lecture Lecture 15

    Memory aid — instance = mine, static = ours. The full treatment of static methods, static blocks and String[] args is Lecture 15; here it only matters that the two kinds of state live in different places.

    5. The new Keyword: Allocate, Construct, Reference

    The new operator does three things, in order, every time it runs:

    1. Allocates memory for a fresh object on the heap, sized to hold all instance fields.
    2. Runs the constructor of the named class (after default field initialization).
    3. Returns a reference — the address of the new object — which the expression yields.
    Student s = new Student();
//  ^    ^      ^
//  |    |      +-- allocate + construct + return reference
//  |    +--------- reference variable (holds the address, not the object)
//  +-------------- declared type

    So the declaration has two halves: Student s creates a variable of type Student, and new Student() creates the object. The = copies the returned reference into the variable. new never returns the object's contents; it returns a handle to the object. Repeated calls create distinct objects, each with its own fields.

    Interviewer's perspective "Does new call the constructor or the constructor call new?" The new expression allocates first, then invokes the constructor on the freshly allocated memory. The constructor never allocates the object it initializes — which is exactly why this inside it already refers to a valid object (Lecture 13).

    6. Object vs Reference Variable

    A variable of a class type does not contain an object; it contains a reference to one. This single fact explains aliasing, null and reference comparison:

    Student a = new Student();
a.name = "Aarav";

Student b = a;                // b receives the same reference — alias
b.name = "Rohan";
System.out.println(a.name);   // Rohan: a and b name the SAME object

Student c = null;             // a reference that points at no object
System.out.println(c);        // null
c.show();                     // NullPointerException at runtime

    Three consequences follow:

    1. Many references, one object — a and b above are two handles on one object, so a change made through either is visible through both.
    2. A reference can be null — it points to no object; dereferencing it (calling a method or reading a field) throws NullPointerException.
    3. Reassignment rebinds the handle, not the object — b = new Student() makes b point elsewhere; the original object is untouched (and may become garbage, Section 13).

    7. The Dot Operator: Accessing Fields and Methods

    The dot operator (.) navigates from a reference to a member of the object it points at: reference.field reads or writes state, and reference.method(args) sends a message to the object.

    Student s = new Student();
s.name = "Aarav";        // write a field
System.out.println(s.marks);   // read a field (0 here, the int default)
s.show();                // call a method

    The dot chain is itself an expression: in System.out.println(...), System is a class, out is a static field holding a print stream object, and println is a method called on that object. Java requires a reference (or class name for static members) on the left of every dot; there is no implicit destructuring of an object into its fields.

    Important Accessing a static member through an object (s.someStatic()) compiles but is discouraged — it hides the fact that the member belongs to the class, not the object. Use ClassName.member. Static is Lecture 15.

    8. Instance State Independence

    Because instance fields are stored per object, two objects of the same class evolve independently. This is the property that makes objects useful for modelling many entities at once.

    Student s1 = new Student();
Student s2 = new Student();
s1.marks = 91;
s2.marks = 78;
System.out.println(s1.marks);   // 91 — unaffected by s2
System.out.println(s2.marks);   // 78 — unaffected by s1

    Contrast this with an array of primitives (Lecture 9): there, position identifies the value; here, the object's identity owns its state. Independence is lost only when two reference variables alias the same object (Section 6) — then the "two objects" are really one, viewed twice.

    The first table compresses Section 2; the second compresses Section 6. Read them together: the object is the heap entity, the class is its description, and the reference is the variable that reaches it.

    The key reading: == on two class-typed variables tests whether they name the same object, not whether the objects hold equal data. Content equality needs equals, which is Lecture 22's subject.

    10. Heap vs Stack: Where the Object and the Reference Live

    When you write Student s = new Student(); inside a method, two regions of memory are involved. The stack holds the local reference variable s; the heap holds the object and its fields.

    reference variable s (stack) --points to--> Student object {name, marks} (heap)
    1. Stack — frames for method calls; primitives and local references live here; freed automatically when the method returns.
    2. Heap — all objects created with new; shared across the program; reclaimed only by the garbage collector.
    3. A field of a class type stores a reference inside the heap object, so object graphs form chains of heap references.

    This section is a forward reference: the complete treatment of stack, heap, method area and the PC register is Lecture 45. The one durable takeaway now is that the reference is not the object — they live in different regions and have different lifetimes.

    11. Object Identity and the Default toString

    Every object has an identity independent of its data. Two freshly created Student objects with identical names and marks are still two distinct entities, and the root class Object (which every class extends) models this directly.

    Student s = new Student();
Student t = new Student();
System.out.println(s);        // Student@1b6d3586  (class name + '@' + hash)
System.out.println(s == t);   // false — distinct objects
System.out.println(s == s);   // true  — same reference

    The default toString() inherited from Object returns the fully qualified class name, followed by @, followed by the object's hash code in hexadecimal. The hash code is derived from identity by default, which is why two objects can print the same data but different hashes. == between references compares identity, not content. Both toString and the equals/hashCode contract that makes content comparison possible are the subject of Lecture 22; here the goal is only to recognize Student@1b6d3586 as the default identity string and to distrust == for object content.

    12. A Real-World Model: BankAccount

    The value of the class/object split shows up when a real entity has both lasting state and rules about how that state may change. A bank account is the standard minimal example.

    // Demo.java — modelling an entity with state and guarded behaviour
class BankAccount {
    String owner;
    double balance;

    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    boolean withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
            return true;
        }
        return false;
    }
}

public class Demo {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount();   // fresh object, defaults: null, 0.0
        acc.owner = "Aarav";
        acc.deposit(1000);                     // balance 1000.0
        acc.withdraw(250);                     // balance 750.0
        System.out.println(acc.owner + ": " + acc.balance);   // Aarav: 750.0
    }
}

    Two points matter. First, withdraw guards its state: it refuses to overdraw rather than blindly subtracting. Second, the guard is a rule about the behaviour, not about the caller, so every caller is protected. That idea — data plus the rules that protect it — is the seed of encapsulation (Lecture 16), where the fields themselves are hidden behind these methods.

    13. this, Object Lifecycle and GC Eligibility

    Inside an instance method or constructor, the keyword this is an implicit reference to the object on which the member was invoked (this.name means "this object's name"). It disambiguates a field from a same-named parameter and is essential to constructor chaining — both covered fully in Lecture 13. For now, this exists only inside instance context; a static method has no this because it runs for the class, not an object.

    An object's lifecycle is: created by new → reachable through at least one live reference → unreachable when no reference reaches it → eligible for garbage collection → eventually reclaimed by the GC. Two corrections are worth memorizing:

    1. Garbage collection is based on reachability, not reference counting. A set of objects that reference only one another in a cycle, but that no live root reaches, is still collectable.
    2. Reassigning a reference (b = null;) makes the object eligible, not immediately freed. When and how the GC runs is up to the JVM.

    The heap and the collection algorithms are Lecture 46; here the lifecycle simply closes the loop opened by new.

    Important System.gc() is only a hint; the JVM may ignore it. You cannot force collection, and correct program logic must never depend on an object being reclaimed at a particular moment.

    14. The Four Pillars: A Roadmap

    The mechanisms in this lecture are the foundation of the four classical pillars of OOP, each expanded in a later lecture:

    1. Encapsulation — bundling state with the methods that guard it and hiding internals (Lecture 16).
    2. Inheritance — building a new class from an existing one to reuse and extend state and behaviour (Lecture 16, with super and packages).
    3. Polymorphism — one reference type, many runtime behaviours, resolved by the object's actual class (Lecture 17).
    4. Abstraction — exposing essential behaviour while hiding implementation detail, via abstract classes and interfaces (Lecture 17).

    Memory aid — E-I-P-A: Encapsulate, Inherit, Polymorph, Abstract. Encapsulation is the earliest to appear because the BankAccount guard in Section 12 is already a primitive form of it.

    15. The Pitfall Catalogue

    Pitfall Example What happens Fix
    Null reference Student s = null; s.show(); NullPointerException at runtime Create with new or check for null first
    Forgetting new (field) Field left unassigned, then used Field is null; dereference throws NPE Assign in a constructor (Lecture 13)
    Forgetting new (local) Student s; s.show(); Compile error: variable might not be initialized Student s = new Student();
    Sharing via alias Student b = a; b.marks = 0; a sees the change — one object, two names Copy fields, or clone (Lecture 14)
    == on objects s1 == s2 for equal data false — compares addresses Use equals (Lecture 22)
    Static/instance confusion Writing to a shared static field All objects change together Use instance fields for per-object state
    Memory misconception "Each object stores the methods too" Methods are shared via class metadata Only instance fields cost heap per object

    The last row is the conceptual bug behind many others: the class (definitions and method code) is loaded once, and each object stores only the values of its instance fields plus a header. Two Student objects do not each carry a private copy of show().

    16. Myth vs Reality

    Myth Reality
    "A class occupies memory for every object" The class is loaded once; only the instance fields consume heap per object.
    "The object is stored inside the variable" The variable stores a reference; the object lives on the heap (Lecture 45).
    "Forgetting new still yields an object" The reference stays null (or the local fails to compile); using it throws NPE.
    "== compares the contents of two objects" == compares references (identity); content equality is equals (Lecture 22).
    "Two variables always mean two objects" References may alias one object, so a change through one is seen through the other.

    17. Common Trap Questions

    Trap 1 — Null dereference: "Student s = null; System.out.println(s.name); — compile error or runtime error?" Runtime: NullPointerException. The compiler is satisfied because s is of type Student; only at run time is there no object to read name from.

    Trap 2 — Uninitialized local vs field: "Why does Student s; s.show(); fail to compile, while an unassigned field does not?" Java does not default-initialize local variables, so the local is definitely unassigned and the compiler rejects the use. Fields receive defaults (null for references), so the method compiles but throws NPE — a compile-time vs runtime split worth stating precisely.

    Trap 3 — Aliasing: "I did Student b = a; b.marks = 0; and a.marks also became 0. Did I copy the object?" No — b = a copied the reference, so both names point at one object. A genuine copy needs a new object with copied fields (Lecture 14).

    Trap 4 — Identity comparison: "Do two new objects with identical data satisfy ==?" No. == compares references, and each new yields a distinct object, so the result is false even when every field is equal. Content comparison is equals (Lecture 22).

    Trap 5 — What new returns: "Does new Student() return the object?" It returns a reference to the newly allocated object. Java never exposes the object itself as a value; assignment copies the reference.

    Trap 6 — Shared static state: "s1.count++ changed s2.count. Why?" count must be declared static, so it is one variable shared by the class, not per-object state. Instance variables would have stayed independent (Lecture 15).

    18. Points to Remember

    1. A class is a blueprint/specification; an object is an instance of it living on the heap.
    2. State = fields, behaviour = methods, plus identity; constructors initialize new objects (Lecture 13).
    3. new allocates heap memory, runs the constructor, and returns a reference — in that order.
    4. A reference variable holds an address, not the object; reference != object.
    5. Many references may point at one object (aliasing); a reference may point at null.
    6. The dot operator navigates from a reference to a field or method.
    7. Instance fields are per-object and independent; static (class) fields are shared (Lecture 15).
    8. Objects live on the heap, references (usually) on the stack — different regions, different lifetimes (Lecture 45).
    9. == on references compares identity; the default toString prints ClassName@hexHash (Lecture 22).
    10. Reassigning or nulling the last reference makes an object GC-eligible, not immediately collected (Lecture 46).
    11. Encapsulation, inheritance, polymorphism and abstraction are the four pillars built on this base (Lectures 16–17).
    12. If no constructor is written, the compiler supplies a default no-argument constructor.

    19. Likely Interview Questions

    Question Crisp Answer
    What is a class? A user-defined type/blueprint that declares fields, methods and constructors; loaded once at runtime.
    What is an object? An instance of a class in heap memory, with its own state, behaviour and identity.
    Class vs object in one line? The class is the design; the object is a thing built from it.
    What does the new keyword do? Allocates heap memory, invokes the constructor, and returns a reference to the new object.
    What does new return — the object or a reference? A reference to the object; the object itself is never a directly usable value.
    Where do objects live — stack or heap? On the heap; the reference variable that points to them is typically on the stack (Lecture 45).
    What is a reference variable? A variable of a class type that stores the address of an object (or null), not the object.
    Can two references point to one object? Yes — that is aliasing; a change through either reference is visible through the other.
    What happens if you use a null reference? A NullPointerException at runtime, because there is no object to dereference.
    Does == compare object contents? No — it compares references (identity); content equality uses equals (Lecture 22).
    What does the default toString print? The class name, @, and the hash code in hex, for example Student@1b6d3586 (Lecture 22).
    Instance vs static variable? Instance variables are one per object; static variables are one per class, shared by all (Lecture 15).
    When is an object eligible for garbage collection? When no live reference chain reaches it; collection time is decided by the JVM (Lecture 46).

    20. Final Summary

    class definition --new--> heap object --assigns--> reference variable --.--> fields & methods
                                                  |
                            reassign / null ------+--> object becomes GC-eligible (Lecture 46)
    • Class → blueprint/spec; loaded once; no per-object field storage.
    • Object → heap instance with state, behaviour and identity.
    • new → allocate, construct, return reference — in that order.
    • Reference variable → holds an address; can alias another reference; can be null.
    • Dot operator → reference.field and reference.method() navigate to members.
    • Instance fields → per-object and independent; static fields → shared (Lecture 15).
    • Identity → == compares addresses; default toString prints ClassName@hexHash (Lecture 22).
    • Lifecycle → unreachable means GC-eligible, not immediately freed (Lecture 46).
    • Pillars → encapsulation and inheritance (Lecture 16), polymorphism and abstraction (Lecture 17).

    Golden rule You never hold an object in your hand — you hold a reference to it, and every bug in this lecture comes from forgetting that the handle is not the thing.

    One-line takeaway: a class is the blueprint, new builds one object from it on the heap and hands back a reference, and the rest of OOP is learning what those references may safely do and how objects relate, protect and reuse one another.
