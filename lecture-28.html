    Part 4 · Strings, Generics & Collections · Lecture 28

    Wildcards in Generics | ?, ? extends, ? super

    18 sections · interview-oriented · both themes

    Scope evidence: "Wildcards in Generics | ?, ? extends, ? super" (playlist map, verified). Repo evidence: 5 Demo files.

    Lecture 27 established that generics are invariant: List<Integer> is not a List<Number>, even though Integer is a Number. That rule is safe, but it is also inflexible — a method that should accept "any list of numbers" cannot be typed as List<Number>. Wildcards are Java's controlled escape hatch: they describe a family of parameterised types without abandoning compile-time safety. This lecture covers the unbounded wildcard ?, the upper bound ? extends T, the lower bound ? super T, the PECS mnemonic, the canonical Collections.copy signature, the read/write rules each form obeys, wildcard capture, and the API-design conventions that keep wildcards in parameter positions.

    1. The Invariance Problem from Lecture 27

    A generic type is invariant in its type argument. List<Integer> and List<Number> are unrelated types, and the compiler refuses to treat one as the other: writing List<Number> nums = new ArrayList<Integer>(); is rejected as "incompatible types".

    The rejection is deliberate. If List<Number> nums = ints; compiled, then nums.add(3.14) would put a Double into a structure that everything else believes is List<Integer>, and a later Integer x = ints.get(0); would throw ClassCastException — the very heap pollution that arrays suffer through covariant assignment (Object[] a = new String[1]; a[0] = 3.14; throws ArrayStoreException at runtime). Generics moved that failure from runtime to compile time by forbidding the assignment entirely.

    The cost is lost flexibility. A method whose job is to sum any list of numbers would like the signature sum(List<Number>), but that rejects List<Integer> and List<Double>. Wildcards restore exactly the flexibility that is provably safe, and nothing more.

    Important Invariance is the default. A wildcard is a use-site annotation that widens the accepted set of types; the underlying generic declaration (class Box<T>) never changes.

    2. The Unbounded Wildcard ?

    The unbounded wildcard ? means "a list of some one unknown element type". List<?> is a supertype of List<Integer>, List<String>, List<Number> and every other List<X>.

    // Demo.java — unbounded wildcard: any element type, read-only
import java.util.*;

public class Demo {
    static void printAll(List<?> list) {          // accepts any List<X>
        for (Object o : list) {                   // every element reads as Object
            System.out.println(o);
        }
        // list.add("x");                         // Incorrect: type is unknown
        list.add(null);                           // Correct: null fits every type
    }

    public static void main(String[] args) {
        printAll(Arrays.asList(1, 2, 3));
        printAll(Arrays.asList("a", "b"));
    }
}

    The essential facts:

    1. You can read any element, but only as Object — the compiler cannot know the element type.
    2. You can add nothing except null. Adding null is legal because null is a member of every reference type.
    3. List<?> is not the same as List<Object>. List<Object> is assignable to List<?>, but not the reverse.

    Memory aid List<?> means "some list, I don't know which". You may take things out (as Object), but you may not put things in, because you do not know what the container accepts.

    3. Upper-Bounded Wildcard ? extends T (Covariant Producer)

    ? extends T means "T or any subtype of T". It is covariant: List<Integer> is assignable to List<? extends Number> because Integer lies within the bound.

    // Demo2.java — upper bound: a Producer you can read from
import java.util.*;

public class Demo2 {
    static double sum(List<? extends Number> nums) {   // reads as Number
        double total = 0;
        for (Number n : nums) {                        // Number or a subtype
            total += n.doubleValue();
        }
        // nums.add(1);                                // Incorrect: no add is allowed
        return total;
    }

    public static void main(String[] args) {
        System.out.println(sum(List.of(1, 2, 3)));     // 6.0
        System.out.println(sum(List.of(1.5, 2.5)));    // 4.0
    }
}

    Reading works, writing does not. The read type is the bound T (here Number): whatever the real element type is, it is guaranteed to be a Number, so n.doubleValue() is always safe. The write is forbidden because the concrete type argument is unknown — the actual list might be a List<Double> or a List<Integer>, and adding an arbitrary Number could violate it. This asymmetry is why ? extends T is called a producer: it produces values for the caller to read.

    Important ? extends T is not a container you fill; it is a source you drain. The compiler protects the unknown element type by refusing every add except null.

    4. Lower-Bounded Wildcard ? super T (Contravariant Consumer)

    ? super T means "T or any supertype of T". It is contravariant: List<Number> and List<Object> are both assignable to List<? super Integer> because both are supertypes of Integer.

    // Demo3.java — lower bound: a Consumer you can write to
import java.util.*;

public class Demo3 {
    static void fill(List<? super Integer> dest) {     // writes Integer
        dest.add(42);                                  // Correct: element type absorbs Integer
        Object first = dest.get(0);                    // reading yields only Object
        System.out.println(first);
    }

    public static void main(String[] args) {
        fill(new ArrayList<Number>());                 // backed by Number
        fill(new ArrayList<Object>());                 // backed by Object
    }
}

    Writing works, reading does not (as T). Because every legal type argument is a supertype of Integer, an Integer (and any subtype) can be stored safely. The read type, however, is only Object — the list might be a List<Number>, or a List<Object>, and Object is the only type guaranteed to cover all of them. This asymmetry is why ? super T is called a consumer: it consumes values supplied by the caller.

    Interviewer's perspective The read-from-? super T surprise is the classic follow-up. "You can add an Integer to List<? super Integer>, so can you read an Integer back?" No — reading yields Object, because the declared lower bound says nothing about what the actual type argument is above Integer.

    5. PECS: Producer Extends, Consumer Super

    PECS — Producer Extends, Consumer Super — is the one-line rule that picks the correct wildcard.

    1. If the collection produces values you read out of it, use ? extends T.
    2. If the collection consumes values you write into it, use ? super T.
    3. If it does both, use an exact T (do not use a wildcard).
    4. If it does neither and you only need "any list", use ?.

    Consider a method that reads from src and writes to dest. Its source parameter is typed ? extends T because the method only pulls items out; its destination parameter is typed ? super T because the method only pushes items in. A caller may then pass a List<Integer> as the producer and a List<Number> as the consumer — exactly the flexibility invariance denied. The runnable form of this pattern is Demo4 in the next section.

    Memory aid PECS: the Producer Extends (read), the Consumer Super (write). Picture the data flowing from the producer into the consumer — reading on the left, writing on the right.

    6. The Canonical JDK Example: Collections.copy

    The standard library uses PECS in java.util.Collections.copy, whose signature is public static <T> void copy(List<? super T> dest, List<? extends T> src). The parameter order encodes the data flow: src is a producer (? extends T, read from) and dest is a consumer (? super T, written to). Demo4 writes the same method by hand and calls it.

    // Demo4.java — PECS in practice: read src, write dest (as Collections.copy does)
import java.util.*;

public class Demo4 {
    static <T> void copy(List<? super T> dest, List<? extends T> src) {
        for (int i = 0; i < src.size(); i++) {
            dest.set(i, src.get(i));                 // read producer, write consumer
        }
    }

    public static void main(String[] args) {
        List<Number> dest = new ArrayList<>(List.of(0, 0, 0));
        List<Integer> src = List.of(1, 2, 3);
        copy(dest, src);
        System.out.println(dest);                    // [1, 2, 3]
    }
}

    If the signature were the invariant copy(List<T> dest, List<T> src), then T would have to unify to a single type and copy(List<Number>, List<Integer>) would fail to compile. The wildcards let the source and destination element types differ, provided one is a subtype of the other.

    7. Comparison: ? extends vs ? super vs Unbounded

    Wildcard Meaning Variance Role Typical use
    ? exactly one unknown type none (any) generic read-only access accept any list; print, count, copy out
    ? extends T T or a subtype covariant Producer (read) iterate and consume values from a source
    ? super T T or a supertype contravariant Consumer (write) collect and store values into a sink

    Read the table downward as the data-flow decision: unknown type first, then "am I reading or writing?". If reading, extend; if writing, super.

    8. Read/Write Capability Matrix

    Declaration Read element as Add T Add subtype of T Add null Role
    List<T> (exact) T yes yes yes read and write
    List<? extends T> T no no yes producer (read-only)
    List<? super T> Object yes yes yes consumer (write-only)
    List<?> Object no no yes any list, read-only

    The matrix is the single most reliable way to answer any "can I add / can I read" question: extends gives read access but blocks writes; super gives write access but degrades reads to Object; the unbounded ? gives read access as Object and blocks writes; only an exact T gives both.

    Important null is the sole exception that every list accepts, including List<?> and List<? extends T>. This is a consequence of the null type being a subtype of every reference type, not a special rule for wildcards.

    9. Assignment Compatibility Between List Types

    The following table records which assignments compile. "Source → Target" is read as Target ref = source;.

    Source type Target type Legal? Reason
    List<Integer> List<Number> no generics are invariant
    List<Integer> List<? extends Number> yes Integer is within the upper bound
    List<Number> List<? extends Number> yes a type lies within its own bound
    List<Double> List<? extends Number> yes Double is within the upper bound
    List<Integer> List<? super Integer> yes a type is a supertype of itself
    List<Number> List<? super Integer> yes Number is a supertype of Integer
    List<Object> List<? super Integer> yes Object is a supertype of Integer
    List<Double> List<? super Integer> no Double is not a supertype of Integer
    List<? super Integer> List<Object> no a wildcard is not an exact type argument
    List<? extends Number> List<Number> no an upper bound is not the exact type
    List<Integer> List<?> yes every list matches the unbounded wildcard
    List<Object> List<?> yes every list matches the unbounded wildcard
    List<?> List<Object> no the unknown element type may not be Object
    List<? super Integer> List<?> yes any parameterised type upcasts to List<?>
    List<? extends Number> List<?> yes any parameterised type upcasts to List<?>

    The asymmetry in the middle block is the surprising one: List<Number> is assignable to both List<? extends Number> and List<? super Integer>, yet List<? super Integer> cannot be assigned back to List<Object>. A wildcard describes a set of possible types; an exact type argument names one. Widening from a specific type to a wildcard is safe; narrowing from a wildcard to a specific type is not.

    10. Wildcard Capture and the Private Helper

    The unbounded ? is not a type you can write down. A method that must both read and write the same element position cannot express that with List<?>. The textbook case is swap:

    // Demo5.java — wildcard capture needs a private generic helper
import java.util.*;

public class Demo5 {
    static void swap(List<?> list, int i, int j) {
        swapHelper(list, i, j);                      // capture ? into a fresh T
    }

    private static <T> void swapHelper(List<T> list, int i, int j) {
        T tmp = list.get(i);                         // T is a usable type here
        list.set(i, list.get(j));
        list.set(j, tmp);
    }

    public static void main(String[] args) {
        List<String> words = new ArrayList<>(List.of("a", "b", "c"));
        swap(words, 0, 2);
        System.out.println(words);                   // [c, b, a]
    }
}

    Writing list.set(i, list.get(j)) directly inside swap(List<?>) fails to compile: the compiler has a captured type for list's element, but it cannot prove that the value returned by one get is acceptable to the same set, because each wildcard occurrence captures independently. The workaround is capture conversion: passing List<?> to a method whose parameter is List<T> asks the compiler to name the unknown type once as T, after which get and set agree.

    Important The helper must be private. It exists only to give the captured type a name and should never leak into the public API; the public method keeps the clean List<?> signature.

    11. Wildcards vs Method Type Parameters

    A wildcard and a method type parameter can express overlapping ideas, but they are not interchangeable:

    Aspect void f(List<?>) <T> void f(List<T>)
    The element type one unknown, cannot be named one named type variable
    Multiple parameters each occurrence may capture differently all occurrences must share the same T
    Relating arguments cannot say "the two lists have the same type" can, via the shared T
    Return type cannot return the element type can return T
    Body read-only (Object) or delegate read and write the element type
    Best for accepting any list, no relationship needed tying several arguments to one type

    The rule of thumb: if the type must be named — to return it, to write it, or to link two parameters — use <T>. If the type is genuinely unknown and only read, a wildcard is simpler and gives the caller more freedom.

    12. Return Types and API Design

    Wildcards belong in method parameters, not in return types. A method declared List<? extends Number> getNumbers() forces every caller to deal with a wildcard they did not ask for, and makes it impossible to add to the returned list. The idiomatic guideline is use wildcards on the way in, concrete types on the way out.

    Inside a body, return the exact type; let the caller widen it if needed. The standard advice appears in Effective Java as Item 31: "Use bounded wildcards to increase API flexibility", applied to parameters such as pushAll and popAll, never to return types.

    Golden rule Accept widely (? extends, ? super, ?), return narrowly (the exact T). A wildcard return type is a design smell.

    13. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Adding to List<? extends T> Compile error: capture of ? cannot be converted Treat it as a producer and use an exact List<T> when you must write
    Assigning List<? super Integer> to List<Object> Compile error: wildcard is not an exact type argument Accept the wildcard type or copy into a new List<Object>
    Expecting Integer back from List<? super Integer> Reading yields Object, not Integer Downcast only with a proven invariant, or redesign to List<Integer>
    Writing set(get(...)) on List<?> Compile error: independent captures Route through a private <T> capture helper
    Assuming a wildcard permits any add List<?> and ? extends reject all non-null adds Re-check the capability matrix before writing
    Mixing raw List with wildcards Raw types disable generic checking and can hide errors Use List<?> rather than raw List for "unknown element type"
    Believing ? equals adding anything ? fixes one unknown type for the whole expression Choose ? extends or ? super by read/write direction
    Using a wildcard in a return type Callers cannot add to or reliably use the result Return the exact T; widen at the parameter instead

    14. Myth vs Reality

    Myth Reality
    "A wildcard lets me add whatever I want" ? and ? extends T forbid every non-null add; only ? super T and exact List<T> accept writes.
    "List<? extends Number> can accept more Numbers via add" It is a read-only producer; the concrete element type is unknown, so add is a compile error.
    "List<? super Integer> is a kind of List<Object>" No such assignment exists; a lower-bounded wildcard is not an exact type argument.
    "Generics are covariant like arrays" Generics are invariant; arrays are covariant and pay for it with runtime ArrayStoreException.
    "? and <T> are interchangeable" <T> names one type usable in many positions (including return); ? is an unnamed existential usable once.
    "Wildcards are useful in return types too" They say "one of many types" and force the caller to handle it; parameters are the right place.

    15. Common Trap Questions

    Trap 1 — The forbidden add: "Can you add an Integer to a List<? extends Number>?" No. Reading yields Number, but the concrete type might be List<Double>, so the compiler rejects every non-null add.

    Trap 2 — The failed upcast: "Is List<? super Integer> assignable to List<Object>?" No. A wildcard is a set of possible type arguments, not one type argument; assign it to List<?> instead.

    Trap 3 — The read surprise: "What does list.get(0) return when list is List<? super Integer>?" Object. The lower bound guarantees only that Integer can go in, not what comes out.

    Trap 4 — Invariance: "Why does List<Number> n = new ArrayList<Integer>(); fail?" Generics are invariant; the two type arguments are unrelated, and allowing the assignment would permit heap pollution.

    Trap 5 — Capture: "Why does swap(List<?>) require a private helper?" Each occurrence of ? captures independently, so get and set cannot be proven compatible; a <T> helper names the captured type once.

    Trap 6 — The null exception: "Can you add anything at all to List<?>?" Only null, because null is a member of every reference type; no real value is type-safe.

    Trap 7 — Return type: "A method returns List<? extends Number>. Can the caller add a Number?" No. The wildcard survives into the return type, so the caller faces the same read-only restriction.

    16. Points to Remember

    1. Generics are invariant: List<Integer> is never a List<Number>; wildcards restore only the flexibility that is provably safe.
    2. List<?> accepts any element type, reads every element as Object, and permits only null to be added.
    3. ? extends T is covariant and a producer — read T, write nothing (except null), because the concrete type is unknown.
    4. ? super T is contravariant and a consumer — write T and its subtypes, but read only Object.
    5. PECS: Producer Extends, Consumer Super; apply it by asking whether the collection is read from or written to.
    6. Collections.copy(List<? super T> dest, List<? extends T> src) is the canonical PECS signature: read src, write dest.
    7. A wildcard narrows safety, not flexibility: widening from a specific type to a wildcard is legal, narrowing a wildcard back to a specific type is not.
    8. Unbounded and upper-bounded lists are read-only for adds; lower-bounded and exact lists accept writes; null is the universal exception.
    9. Wildcard capture is the compiler's mechanism for naming an unknown type; a private generic helper (<T>) is its standard workaround.
    10. Put wildcards in parameters, keep exact types in return values; a wildcard return type is poor API design.

    17. Likely Interview Questions

    Question Crisp Answer
    Why are generics invariant? To preserve compile-time type safety; covariant assignment would allow heap pollution and runtime ClassCastException.
    What does List<?> mean? A list of some single unknown element type; read as Object, add only null.
    Difference between ? extends T and ? super T? extends is covariant and a producer (read T); super is contravariant and a consumer (write T, read Object).
    What is PECS? Producer Extends, Consumer Super — choose extends for read-only sources and super for write-only sinks.
    Explain Collections.copy's signature. <T> void copy(List<? super T> dest, List<? extends T> src) — reads the producer src, writes the consumer dest.
    Can you add to List<? extends Number>? No; only null. The real element type could be any subtype, so add is a compile error.
    What can you read from List<? super Integer>? Object, never Integer directly, because the actual type argument is only known to be a supertype.
    Is List<Object> the same as List<?>? No. List<Object> is assignable to List<?>, but not vice versa; List<?> can also be List<String>.
    What is wildcard capture? The compiler's naming of a wildcard's unknown type (? becomes a fresh T via capture conversion); a private <T> helper is the usual fix.
    Why does swap(List<?>) need a helper? Each ? occurrence captures separately, so get/set cannot be related; a generic helper names one T for both.
    Wildcards vs method type parameters? <T> names a type usable across parameters and return; ? is an unnamed type for one use, often simpler for read-only parameters.
    Should a method return a wildcard type? Generally no; use wildcards in parameters and return the exact T to keep the API usable.

    18. Final Summary

    List<Integer>  ≠  List<Number>          invariance (Lecture 27)
        |
   add a wildcard at use site
        |
        +-- List<?>             read Object      add null only
        +-- List<? extends T>   read T           add nothing   (Producer)
        +-- List<? super T>     read Object      add T         (Consumer)

PECS:   Producer Extends (read)  -->  Consumer Super (write)
JDK:    copy(List<? super T> dest, List<? extends T> src)
    • Invariance → generics are not covariant; a wildcard is the safe, use-site widening.
    • Unbounded ? → any element type; read as Object, write null only.
    • ? extends T → covariant producer; read T, never write (except null).
    • ? super T → contravariant consumer; write T, read only Object.
    • PECS → decide by data flow: reading wants extends, writing wants super.
    • Collections.copy → ? super T destination and ? extends T source encode read-then-write.
    • Capture → ? is unnamed; a private <T> helper names it when both read and write are needed.
    • API rule → wildcards in parameters, exact types in return values.

    Golden rule A wildcard widens what a method accepts without weakening what the compiler proves: extends when you read, super when you write, ? when you only look.

    One-line takeaway: wildcards turn invariance into controlled flexibility — ? reads anything as Object, ? extends T produces T but cannot be written, and ? super T consumes T but can only be read as Object, with PECS choosing the right one.
