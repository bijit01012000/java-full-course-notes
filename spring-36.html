    Part 6 · Data Access, Transactions & Security · Lecture 36

    Spring Security DB Authentication & Password Security

    21 sections · interview-oriented · both themes

    Scope evidence: "Spring Security DB Authentication & Password Security" (playlist map, verified). Repo lecture folder points at the springPracticalDemo project: User/Role entities, UserRepository/RoleRepository, AuthService registration logic, SecurityConfig, register request/response DTOs, plus the lecture notes on database authentication and password hashing.

    Spring Security ships with a working login out of the box, but that login lives in memory and evaporates on restart. Real applications need users in a database, need to distinguish identity from credentials, and need to store passwords in a form that survives a database breach. This lecture builds that story from the first principle - authentication needs a trusted source of truth - all the way to a registration service that hashes a password with BCrypt before it ever touches the database. Deep login internals (how DaoAuthenticationProvider runs the verification) belong to Lecture 37; here we prepare everything the login path will later consume.

    1. From Default In-Memory Authentication to Database Authentication

    Adding one dependency is enough to secure a Spring Boot application:

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

    With no further configuration, Spring Boot:

    • creates a user with the username user;
    • prints a randomly generated password in the console;
    • secures every endpoint;
    • provides form login and HTTP Basic authentication.

    After a successful authentication, Spring Security creates an Authentication object that represents the currently authenticated user:

    Authentication
-----------------------------
principal    = user
credentials  = protected/erased
authorities  = ROLE_USER
authenticated = true

    That object is what the rest of the application reads to answer "who is logged in?" and "what is that user allowed to do?" But the default setup raises the important question this lecture answers:

    Where does Spring Security obtain the information required to verify a user?

    The default answer - a user generated into memory at startup - is fine for a demo and useless for a product.

    Important: The generated default user is not a security feature, it is a convenience for getting started. The moment you have real accounts, the source of truth has to move out of memory.

    2. Authentication Requires a Source of Truth

    Suppose a client submits:

    username = aditya
password = secret123

    Spring Security cannot automatically know whether these credentials are correct. It needs trusted information against which it can validate the claim.

    User-submitted information
-----------------------------
username = aditya
password = secret123

Trusted information
-----------------------------
username      = aditya
passwordHash  = ...
roles         = ...
accountStatus = ...

    Authentication can therefore be understood as this three-step flow:

    Claimed identity + credential
        |
        v
Validation against
        |
        v
Trusted user information

    The trusted information can live anywhere: application memory, a relational database, MongoDB, LDAP, an external identity provider, or a separate authentication service. In this application the source of truth is a MySQL database:

    Spring Boot Application
        |
        v
MySQL Database

    Golden rule: Authentication is not about deciding what a password "should" be. It is about comparing a claim against a trusted record that the application already holds.

    3. Why the Default User Is Not Enough

    Spring Security's generated user is useful for learning and testing, but it is not a practical user-management system.

    A real learning platform could have thousands of users. Every user may have their own identity, password, roles, and account status. This information must survive application restarts, server restarts, deployments, and application scaling. An in-memory user dies with the JVM; a scaled deployment would have a different random password on every instance.

    The users must therefore be stored in persistent storage such as a database. Persistence is not an optimization here, it is the requirement that turns a demo login into a real account system: the default user does not survive a restart, supports only one account, hard-codes its role, and has no per-user status flags.

    4. Why Spring Security Does Not Depend on Our Domain Entity

    Every application has a different database design.

    One application may use a users table with fields such as id, email, password, phone, created_at, and enabled. Another may use an employees table with employee_id, corporate_email, credential_hash, department, and active. Other systems may call the same concept customers, members, or accounts and may use a completely different database technology.

    Spring Security cannot require every application to use the same table name, column names, or database design. Instead, it defines common security abstractions. One of the most important is UserDetails, which represents the user information Spring Security needs during username-and-password authentication.

    Application-specific database model
        |
        v
Adapter
        |
        v
Spring Security's UserDetails

    This separation keeps Spring Security independent of the application's database structure. It is a contract, not coupling.

    Interviewer's perspective: If asked "why not make Spring Security read our User entity directly?", the strong answer is that a framework must not know thousands of different schemas. Abstractions such as UserDetails are exactly how a framework stays reusable across applications.

    5. Identity vs Credentials

    Authentication must answer two questions:

    Who are you?        -> Identity
Can you prove it?   -> Credential

    For username-and-password authentication:

    username or email  -> identity
password           -> credential

    Identity is the claim of who the user is. A credential is the secret the user presents to prove that claim. They are different concepts and are stored with different intentions: identity is safe to look up and display, a credential must never be exposed.

    Username versus email

    An application does not have to use a traditional username as the login identifier. It may use a username, an email address, an employee ID, a phone number, or any other value that uniquely identifies an account. For example, an application can use:

    findByEmail(email);

    instead of:

    findByUsername(username);

    Spring Security APIs use historical names such as loadUserByUsername(...) and getUsername(). However, the value can still represent an email address if that is the application's login design. The name is a historical contract; the meaning is whatever uniquely identifies the account.

    The login identifier must uniquely identify exactly one account. These rows would make authentication ambiguous because the identifier is not unique:

    ID | EMAIL
1  | aditya@gmail.com
2  | aditya@gmail.com

    The login identifier should therefore have a unique database constraint. This example uses username to keep the terminology aligned with Spring Security's interfaces.

    Memory aid: "Identity tells us who; credential proves it." A mnemonic for the two questions is W-P - Who are you, Prove it.

    6. Designing the Authentication Database

    The absolute minimum information required for username-and-password authentication is:

    User
|-- username
`-- password

    A minimal users table could be:

    users
-------------------------------
id        BIGINT PRIMARY KEY
username  VARCHAR UNIQUE
password  VARCHAR

    In a realistic application, account status and roles are also useful, so the table grows:

    users
-------------------------------
id | username | password | enabled

    Notice that password here really means the encoded password. The column stores a hash, never the original text.

    Column Purpose Notes
    id Primary key Surrogate identity
    username Login identifier UNIQUE, identifies exactly one account
    password Encoded password Stores the hash, never the raw value
    enabled Account status flag Allows the account to exist but stay inactive

    7. The UserDetails Contract

    A simplified view of Spring Security's UserDetails interface is:

    public interface UserDetails {
    String getUsername();
    String getPassword();
    Collection<? extends GrantedAuthority> getAuthorities();
    boolean isAccountNonLocked();
    boolean isAccountNonExpired();
    boolean isCredentialsNonExpired();
    boolean isEnabled();
}

    It contains three main categories of information:

    1. Identity - getUsername()
    2. Credential - getPassword()
    3. Authorities and account status
    Member Category Meaning
    getUsername() Identity The unique login identifier
    getPassword() Credential The encoded password Spring Security will verify against
    getAuthorities() Authorization Granted roles/permissions (for example ROLE_USER)
    isAccountNonLocked() Status false when the account is temporarily blocked
    isAccountNonExpired() Status false when the account itself is no longer valid
    isCredentialsNonExpired() Status false when the credential must be renewed
    isEnabled() Status false when the account is inactive

    Enabled and disabled accounts

    An account may need to remain in the database even when it should no longer be allowed to authenticate:

    User exists
but
User cannot authenticate

    For this requirement, the user table can contain an enabled field:

    users
-------------------------------
id | username | password | enabled

    1 | aditya | $2a$... | true is an enabled user and may continue through authentication. 2 | rohit | $2a$... | false is a disabled user and is not eligible for successful authentication. The row still exists, so history and references survive; only the ability to log in is removed.

    Disabled versus locked

    Disabled -> The account is inactive.
Locked   -> The account exists, but authentication is temporarily blocked.

    An account might be locked after repeated failed login attempts without being permanently disabled. Disabled is a deliberate, lasting state; locked is usually a temporary safety response.

    Account and credential expiration

    isAccountNonExpired() says whether the account itself is still valid (for example, a temporary employee's contract ended); isCredentialsNonExpired() says whether the credential is still valid (for example, a password must be changed every 90 days). Account expired means the account is no longer valid; credentials expired means the account is valid but its credential must be renewed. Spring Security provides hooks for these states, but every application does not need a separate database column for each one; an implementation that does not support account expiration can simply return true from isAccountNonExpired().

    Mnemonic for the contract categories: I-C-A-S - Identity, Credential, Authorities, Status.

    8. The Initial User Entity and Domain vs UserDetails

    The first version of the User entity looks like this:

    @Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String username;

    @Column(nullable = false)
    private String password;

    private boolean enabled = true;
}

    The unique = true constraint is important because one username must identify only one account.

    Domain User versus Spring Security UserDetails

    The application's User entity and Spring Security's UserDetails abstraction belong to different layers:

    Application/domain layer - User Entity
|-- email
|-- profile
|-- createdAt
|-- password
`-- roles

        | adapt

Spring Security layer - UserDetails
|-- username
|-- password
|-- authorities
`-- account status

    The User entity models what the application wants to store. UserDetails models what Spring Security needs for authentication. They can be connected through an adapter without treating them as the same concept.

    Important: Do not make the domain User entity implement UserDetails "just to save a class" without thinking. That decision couples the persistence model to a security contract and drags security methods into every place the entity appears.

    9. Introducing Roles: ROLE_USER and ROLE_ADMIN

    Authentication establishes who the user is. Authorization determines what that authenticated user is allowed to do.

    A learning platform might define:

    STUDENT -> View courses
TEACHER -> Create courses
ADMIN   -> Delete users

    A user may have one or more roles:

    Aditya
|-- ROLE_USER
`-- ROLE_ADMIN

Rohit
`-- ROLE_USER

    The database structure splits the concern into three tables:

    users
-----------------------------
id | username | password | enabled

roles
-----------------------------
id | name

user_roles
-----------------------------
user_id | role_id

    Example data:

    users
1 | aditya | $2a$... | true
2 | rohit  | $2a$... | true

roles
1 | ROLE_USER
2 | ROLE_ADMIN

user_roles
1 | 1
1 | 2
2 | 1

    The join-table entries mean that Aditya has both roles, while Rohit has only ROLE_USER. Keeping the role names in their own table means a role can be reused across users without repeating strings, and the set of roles is data rather than hard-coded logic.

    Interviewer's perspective: A frequent question is "why a join table instead of a role column on users?" The answer is the many-to-many reality: one user can hold many roles and one role can belong to many users, which is exactly what a join table models.

    10. JPA Entity Model for Roles (ManyToMany)

    The Role entity:

    @Entity
@Table(name = "roles")
public class Role {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String name;
}

    The updated User entity gains the role relationship:

    @Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String username;

    @Column(nullable = false)
    private String password;

    private boolean enabled = true;

    @ManyToMany
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id")
    )
    private Set<Role> roles = new HashSet<>();
}

    The mapping is unidirectional because the authentication use case needs user.getRoles() but does not currently require role.getUsers(). A bidirectional relationship should be added only if the application genuinely needs navigation in both directions; otherwise it adds maintenance cost on both sides for no benefit.

    11. The Repository Layer and the Missing Bridge

    The application needs a repository to retrieve users by their login identifier:

    public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByUsername(String username);
    boolean existsByUsername(String username);
}

    A role repository may also be useful during registration or role management:

    public interface RoleRepository extends JpaRepository<Role, Long> {
    Optional<Role> findByName(String name);
}

    At this stage, Spring Security still does not directly call userRepository.findByUsername(...). There is a deliberate gap:

    Database
   ^
UserRepository
   ^
Missing bridge
   ^
Spring Security

    The missing bridge is UserDetailsService. DaoAuthenticationProvider uses UserDetailsService to load the username, encoded password, authorities, and account-status information required for authentication. That bridge is the subject of Lecture 37; for now we recognize the shape of the gap.

    Important: The repository is an application concern; UserDetailsService is the adapter Spring Security recognizes. Keeping them separate is what allows the login provider to work with any database design.

    12. Why Raw Passwords Must Never Be Stored

    Consider a registration request:

    POST /register
Content-Type: application/json

{
  "username": "aditya",
  "password": "secret123"
}

    The simplest implementation would save the password directly:

    User user = new User();
user.setUsername(request.getUsername());
user.setPassword(request.getPassword());
userRepository.save(user);

    The database would then contain:

    id | username | password
----------------------------
1  | aditya   | secret123

    This may work functionally, but it is extremely unsafe. If the database is compromised, every stored password is immediately exposed. The damage may extend beyond this application because users frequently reuse the same password on multiple services.

    An application should never intentionally store a user's raw password.

    Golden rule: Treat the raw password as radioactive. It may exist for the few milliseconds needed to process a request, and it must never be logged, returned, or persisted.

    13. Why Password Encryption Is Not the Right Solution

    Encryption is reversible:

    Plaintext
   |
   v encryption + key
Ciphertext
   |
   v decryption + key
Plaintext

    If passwords are encrypted, the application must keep a decryption key capable of recovering every original password. If an attacker obtains both the database and the key, all passwords can be recovered. Encryption moves the risk to key management but never removes the ability to reverse the secret.

    The more fundamental question is:

    Does the application ever need to recover a user's original password?

    No. During login, the application only needs to determine whether the password entered now matches the password registered earlier. It never needs the original text back. Therefore passwords need a one-way transformation rather than reversible encryption.

    Aspect Encryption Hashing
    Direction Reversible (two-way) One-way
    Needs a key Yes, to decrypt No decryption key exists
    Purpose Hide data that must be recovered Store a secret that is only compared
    Breach + key All passwords recovered Passwords still hard to reverse
    Suitable for passwords No Yes
    Example AES BCrypt

    14. Password Hashing and Why Fast Hashes (SHA-256) Are Unsuitable

    Hashing changes the security model:

    secret123
   |
   v
One-way password function
   |
   v
Encoded representation

    The encoded representation is stored in the database. There should be no operation that converts it back into the original password. During login, the system performs verification:

    Entered raw password
        +
Stored encoded password
        |
        v
Does the entered password correspond to this stored representation?
        |
        v
true / false

    Spring Security expresses this operation through:

    passwordEncoder.matches(rawPassword, encodedPassword);

    Why a fast hash such as SHA-256 is not enough

    A general-purpose cryptographic hash such as SHA-256 is designed to be fast. Speed is valuable for many computing tasks, but it is dangerous for password storage.

    If attackers steal a password-hash database, they can perform an offline guessing attack:

    password      -> hash and compare with stolen value
123456        -> ...
qwerty        -> ...
secret123     -> ...
welcome123    -> ...
...

    For every guess they calculate a hash and compare it with the stolen value. A very fast algorithm allows attackers to test an enormous number of guesses quickly, often on powerful GPUs. Password-storage algorithms are deliberately designed to make every guess computationally expensive.

    Fast general-purpose hash -> Attackers can test guesses rapidly.
Adaptive password hash    -> Every guess requires more computation.

    Spring Security supports adaptive one-way password functions such as BCrypt for this purpose.

    Aspect Fast hash (SHA-256) BCrypt (adaptive)
    Design goal Maximize throughput Deliberately slow per guess
    Speed abused by attackers Yes, billions of guesses/sec possible No, cost factor throttles guessing
    Salt Not built in Built into the encoded output
    Same password twice Same hash Different hash each time
    Cost tunable No Yes (work factor)
    Suitable for passwords No Yes

    Important: The problem with SHA-256 is not weakness of the function, it is its speed. For passwords you actively want the computation to be slow and repeatedly salted.

    15. BCrypt, PasswordEncoder, and Salt

    Spring Security provides BCryptPasswordEncoder, which implements the PasswordEncoder abstraction:

    PasswordEncoder
   | implements
BCryptPasswordEncoder

    The encoder can be registered as a Spring bean:

    @Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

    Depending on the abstraction allows the application to change the concrete password-encoding strategy without rewriting all authentication code.

    Core operations:

    String encoded = passwordEncoder.encode("secret123");
System.out.println(encoded);                                        // $2a$10$...
System.out.println(passwordEncoder.matches("secret123", encoded));  // true
System.out.println(passwordEncoder.matches("wrongPassword", encoded)); // false

    The application never needs to decrypt the stored value.

    Salt and BCrypt

    A stolen database can also be attacked using precomputed password-hash dictionaries, commonly associated with rainbow-table attacks:

    password   -> known hash 1
123456     -> known hash 2
secret123  -> known hash 3
admin123   -> known hash 4

    A salt adds unique random data to the password-hashing process:

    Aditya
secret123 + randomSaltA
        |
        v BCrypt
encodedValueA

Rohit
secret123 + randomSaltB
        |
        v BCrypt
encodedValueB

    Even though both users selected the same password, their stored BCrypt values are different. That defeats precomputed tables, because an attacker cannot look up a single hash that maps to secret123.

    BCrypt includes the salt and algorithm parameters inside the encoded value stored in the database. A separate salt column is therefore not required when using the standard BCrypt representation. A quick demonstration:

    System.out.println(passwordEncoder.encode("secret123")); // $2a$10$A...
System.out.println(passwordEncoder.encode("secret123")); // $2a$10$B...

    The two results should be different.

    How does matches() work if every encoding is different?

    A common wrong idea is that matches() encodes the raw password again with a new salt and compares the two strings with .equals(...). That approach would fail because each new encoding normally uses a different random salt. Instead, matches() reads the salt and other required parameters from the stored BCrypt value and applies those parameters while verifying the submitted raw password:

    passwordEncoder.matches(rawPassword, storedEncodedPassword);

    Spring Security hides the algorithm-specific verification details behind the PasswordEncoder interface.

    Interviewer's perspective: "If BCrypt salts every hash differently, how can verification ever succeed?" The answer is that the salt is not secret and travels inside the stored value. Verification reuses that stored salt instead of generating a new one, which is why matches() works while naive encode().equals() does not.

    16. Registration Flow from First Principles

    The client sends:

    POST /register
Content-Type: application/json

{
  "username": "aditya",
  "password": "secret123"
}

    The registration flow is:

    RegisterRequest
|-- username = aditya
`-- password = secret123
        |
        v
PasswordEncoder
        |
        v
BCrypt
        |
        v
Encoded password
        |
        v
User entity
        |
        v
UserRepository
        |
        v
Database

    In short: raw password -> PasswordEncoder.encode() -> BCrypt-encoded password -> database. Password encoding occurs before the user entity is saved. The raw password must never be persisted.

    Registration DTOs

    A simple request DTO can validate the incoming values:

    public class UserRegisterRequestDto {
    @NotBlank
    private String username;

    @NotBlank
    @Size(min = 8)
    private String password;
}

    @Size(min = 8) demonstrates basic length validation. A production password policy may require additional rules, but password validation and password encoding solve different problems:

    Validation       -> Decides whether the submitted password is acceptable.
Password encoding -> Protects the password representation stored in the database.

    The response DTO deliberately omits the password, so the encoded value is never leaked back to the client; it carries only fields such as id and username.

    Registration service

    The service must check whether the username already exists, encode the raw password, assign the default role on the server side, create the entity, and then save it. A minimal framing of the service:

    @Service
public class AuthService {
    private final UserRepository userRepository;
    private final RoleRepository roleRepository;
    private final PasswordEncoder passwordEncoder;

    public AuthService(UserRepository userRepository,
                       RoleRepository roleRepository,
                       PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.roleRepository = roleRepository;
        this.passwordEncoder = passwordEncoder;
    }

    public UserRegisterResponseDto register(UserRegisterRequestDto request) {
        if (userRepository.existsByUsername(request.getUsername())) {
            throw new IllegalArgumentException("Username is already registered");
        }

        Role userRole = roleRepository.findByName("ROLE_USER")
                .orElseThrow(() -> new IllegalStateException("Default role missing"));

        User user = new User();
        user.setUsername(request.getUsername());
        user.setPassword(passwordEncoder.encode(request.getPassword()));
        user.setEnabled(true);
        user.setRoles(Set.of(userRole));

        User saved = userRepository.save(user);
        return new UserRegisterResponseDto(saved.getId(), saved.getUsername());
    }
}

    The critical line is:

    user.setPassword(passwordEncoder.encode(request.getPassword()));

    The value received in the request is raw. The value saved in the database is BCrypt-encoded:

    Request DTO
-----------------------------
secret123
raw password

Database
-----------------------------
$2a$10$...
encoded password

    The raw password should exist only for the short time required to process the registration request. It should not be logged, returned in the response, or stored anywhere.

    Two server-side rules matter as much as the encoding:

    • The default role is assigned by the server, not chosen by the client. Never trust a role sent in the request body; a malicious client could otherwise register as ROLE_ADMIN.
    • The response DTO excludes the password entirely, so no encoded value ever travels back out.

    Complete conceptual picture

    Registration and login use the password encoder differently:

    During registration

    Registration is the encode path; login is the matches path. Both exist so that the original password is never recoverable from what is stored.

    17. Myth vs Reality

    Myth Reality
    "The default user is enough once the app is real" It lives in memory, is lost on restart, and cannot model thousands of accounts
    "Spring Security should read our User entity directly" It depends on UserDetails; our entity is adapted to that contract
    "Username and password are the same kind of data" Username is identity (safe to look up); password is a credential that must be protected
    "Any unique-looking email field is fine as a login id" The login identifier must have a unique constraint; duplicates make authentication ambiguous
    "Encryption is safer than hashing for passwords" Encryption is reversible and needs a key; hashing is one-way and needs no decryption
    "SHA-256 is secure enough for passwords" It is fast and unsalted, so offline guessing and rainbow tables are cheap; BCrypt is adaptive and salted
    "A salt column must be added to the users table" BCrypt embeds the salt and parameters in the encoded value, so no separate column is needed
    "matches() re-encodes with the same salt and compares strings" It reads the salt and parameters from the stored value, which is why every fresh encode differs
    "The client may send the role during registration" The server assigns the default role; trusting a client role is a privilege-escalation hole

    18. Common Trap Questions

    Trap 1 - "Spring Security should just query our users table." Verdict: False. It depends on the UserDetails contract. Our User entity is an application concern, and an adapter bridges the two so the framework stays schema-independent.

    Trap 2 - "Username and email must be the same column." Verdict: False. Any unique identifier works (username, email, employee ID, phone). Only the requirement of uniqueness is fixed, and Spring Security's getUsername() name is historical.

    Trap 3 - "Encrypt the password so we can decrypt it if a user forgets." Verdict: False. No legitimate need exists to recover the original password. Encryption keeps the risk of key compromise; use one-way hashing and a reset flow instead.

    Trap 4 - "SHA-256 is a strong hash, so it is fine for passwords." Verdict: False. Strength against collisions is not the issue; speed is. A fast hash lets attackers test enormous numbers of guesses, and it is not salted by default. Use an adaptive hash such as BCrypt.

    Trap 5 - "Two users with the same password would have the same stored hash." Verdict: False with a proper salted algorithm. BCrypt generates a unique salt per encoding, so the same password produces different stored values for different users.

    Trap 6 - "matches() re-hashes the raw password and compares the resulting strings." Verdict: False. Every encode uses a fresh salt, so a new hash would never equal the stored one. matches() extracts the salt and parameters from the stored value and verifies against them.

    Trap 7 - "The registration response can include the saved user with its password field." Verdict: False. The response DTO omits the password, and the raw password must not be logged or returned. The server also assigns the default role rather than trusting the client.

    19. Points to Remember

    1. Authentication always needs a trusted source of truth; the default in-memory user is only a learning convenience.
    2. The source of truth can be memory, a relational database, MongoDB, LDAP, an external identity provider, or a dedicated auth service; here it is MySQL.
    3. Spring Security avoids direct coupling to application schemas by defining abstractions, the key one being UserDetails.
    4. Identity (who you are) and credential (proof) are different concepts; the login identifier must uniquely identify exactly one account.
    5. UserDetails exposes identity (getUsername), credential (getPassword), authorities (getAuthorities), and account-status flags (isEnabled, isAccountNonLocked, isAccountNonExpired, isCredentialsNonExpired).
    6. The domain User entity and Spring Security's UserDetails live in different layers and are linked by an adapter, not identified with each other.
    7. Authorization (roles such as ROLE_USER and ROLE_ADMIN) is modeled with users, roles, and a user_roles join table, mapped as @ManyToMany.
    8. UserRepository (findByUsername, existsByUsername) and RoleRepository (findByName) provide data access; UserDetailsService is the missing bridge Spring Security will use in Lecture 37.
    9. Raw passwords must never be stored, logged, or returned; encryption is reversible and therefore wrong for passwords, so use a one-way hash.
    10. Fast hashes such as SHA-256 are unsuitable; use BCrypt, which is adaptive, salted, embeds its parameters, and is used through PasswordEncoder.encode() and matches().

    20. Likely Interview Questions

    Question Crisp Answer
    Why is the default Spring Security user not enough? It is an in-memory account lost on restart, with no persistence, no per-user roles or status, and no support for scaling.
    Where does Spring Security get the data to verify a user? From a trusted source of truth (memory, database, LDAP, or an identity provider); here it is a MySQL database.
    What is UserDetails and why does it exist? A Spring Security contract describing the identity, credential, authorities, and account status needed for authentication, so the framework stays independent of any application schema.
    Identity vs credential? Identity is who the user claims to be (username/email); credential is the secret proving it (password).
    Can the login identifier be an email? Yes, any value that uniquely identifies one account works; only uniqueness is mandatory, and getUsername() is a historical name.
    What does the UserDetails contract expose? getUsername, getPassword, getAuthorities, and the four status flags for locked, expired, credentials-expired, and enabled.
    How are roles modeled in the database? A roles table, a users table, and a user_roles join table, mapped in JPA as @ManyToMany with a @JoinTable.
    Why not store encrypted passwords? Encryption is reversible and requires a key; if the database and key leak, all passwords are recovered. Passwords must be one-way hashed.
    Why is SHA-256 unsuitable for passwords? It is deliberately fast and unsalted, enabling rapid offline guessing and rainbow-table attacks; BCrypt is adaptive and salted.
    Why does BCrypt give different output for the same password? It uses a unique random salt per encoding and stores that salt (plus parameters) inside the encoded value.
    How does matches() work with a random salt? It reads the salt and parameters from the stored encoded value and verifies the submitted password against them, rather than re-encoding with a new salt.
    What must the registration service do? Validate input, reject duplicate usernames, encode the password, assign the default role on the server, save, and return a response DTO without the password.
