    Part 2 · Configuration & First Projects · Lecture 11

    Spring Boot CRUD Project from Scratch

    21 sections · interview-oriented · both themes

    Scope evidence: "Spring Boot CRUD Project from Scratch | Create API & Architecture" (playlist map, verified). Repo lecture folder is the crudSpringBootDemo Maven project: entity, controller, service, repository packages plus application.properties, pom.xml, and the cached lecture notes.

    This lecture stops talking about Dependency Injection in console examples and puts it to work in a real Spring Boot backend. We build a Student Management API that performs all four CRUD operations through HTTP, and we design the layered architecture that keeps the code clean as it grows. The whole value of the lecture is not the five endpoints themselves; it is the reason each layer exists and what happens to a request as it travels from Postman to MySQL and back.

    1. What Exactly Is a CRUD Application?

    Almost every application does four basic things with data:

    1. Create data
    2. Read data
    3. Update data
    4. Delete data

    Those four words are the initial letters of CRUD. A CRUD application is an application whose core purpose is to manage records of some kind through those four operations.

    The examples are everywhere:

    Application Create Read Update Delete
    YouTube video system Create video Read video Update title/description Delete video
    Instagram post system Create post Read post Update caption Delete post 
    CRUD = Create + Read + Update + Delete

    Important: CRUD is not a database feature and not a framework feature. It is the smallest complete set of operations any data-driven system must support.

    2. Why CRUD Is Not Beginner Content

    Many students think CRUD is basic. The source states the opposite plainly: CRUD is the foundation of most backend systems.

    The reason is that a huge share of professional backend work is CRUD wearing different clothes. A payments service creates a charge, reads a balance, updates a status, deletes a failed attempt. A food-delivery backend creates an order, reads the menu, updates the address, deletes a cart item. The domain vocabulary changes; the skeleton does not.

    CRUD is the basic skeleton of backend development.

    If you internalize CRUD and the architecture around it now, every larger system later is just more CRUD with more rules. That is why this project is worth doing carefully rather than fast.

    Interviewer's perspective: A candidate who calls CRUD "easy" and cannot explain where the business rules live usually has not built anything real. The depth of a CRUD answer reveals the depth of backend understanding.

    3. The Student Management API: Six APIs to Build

    The project is a Student Management API. An admin manages student records. The source describes six main APIs to build:

    1. Create Student - Admin can add a new student. POST /api/students/
    2. Get All Students - Admin can see all active students. GET /api/students/
    3. Get Student by ID - Admin can fetch one student. GET /api/students/1
    4. Update Student - Admin can update student details. PUT /api/students/1
    5. Delete Student - Admin can permanently delete a student. DELETE /api/students/1

    The list also introduces both delete styles, which is why the project feels real-world:

    • Soft delete -> the row remains, and isDeleted becomes true.
    • Hard delete -> the row is permanently removed.

    Example request body for creating a student:

    {
  "name": "Rahul Sharma",
  "email": "rahul@example.com",
  "course": "Spring Boot",
  "age": 22,
  "rollNo": 101
}

    Creating a resource inserts a row into the database. Fetching GET /api/students/1 uses 1 as the student ID and is the place where @PathVariable is explained: the value comes from the URL.

    The update flow is described as a very important backend pattern, with three steps:

    1. First find student by ID
    2. Then update fields
    3. Then save updated student
    POST   create
GET    read
PUT    update
DELETE delete

    4. CRUD Mapping with HTTP Methods

    CRUD is a data concept; HTTP methods are the web vocabulary that expresses it. This table is the bridge, and it should be memorized because it is the first thing an interviewer sketches on a whiteboard.

    CRUD Operation HTTP Method Example URL Meaning
    Create POST /api/students/ Add new student
    Read All GET /api/students/ Get all students
    Read One GET /api/students/{id} Get one student
    Update PUT /api/students/{id} Replace/update student details
    Hard Delete DELETE /api/students/{id} Remove permanently

    Two rules fall straight out of the table:

    • The same URL can host different operations; the HTTP method disambiguates them. POST /api/students/ and GET /api/students/ share a path but create versus read.
    • A path variable ({id}) appears when the operation targets one specific row, while collection operations carry no id.

    Mnemonic for the mapping: "Post Creates, Get Reads, Put Updates, Delete Deletes" - and note that both Read operations use GET, differing only by whether {id} is present.

    5. What the Database Table Looks Like

    The data will live in a table called students. The columns and types are:

    Column Type Meaning
    id BIGINT Unique student ID
    name VARCHAR Student name
    email VARCHAR Student email
    course VARCHAR Student course
    age INT Student age
    roll_no INT Roll Number

    The Java class that represents this table is sketched with fields that line up with those columns:

    public class Student {
    private String name;
    private String email;
    private int rollNo;
    private int age;
    private String subject;
}

    This is the moment students should see the point: a Java object can connect to a database table. That sentence is the foundation of JPA. The object fields map to columns, so code can think in Student objects while the database thinks in rows.

    Golden rule: JPA is the bridge between the object world and the table world. Once you see Student on one side and students on the other, the rest of the project is plumbing that connects the two.

    6. The Student Entity: Java Object Meets Table

    The table row is represented by a class in the entity package, and the class is annotated @Entity:

    @Entity
public class Student {
    private String name;
    private String email;
    private int rollNo;
    private int age;
    private String subject;
    private boolean isDeleted;
}

    The extra isDeleted field exists because the project supports soft delete: a deleted student can stay in the table with isDeleted = true. The source notes that entity classes represent database tables, and JPA maps this object to the students table.

    Java field Table column Role
    name name student name
    email email student email
    rollNo roll_no roll number
    age age student age
    subject / course course course
    isDeleted (delete flag) soft-delete marker

    @Entity is the contract that tells JPA: this class is not an ordinary Java class; treat it as a mapped table. The object then travels between the layers, carrying data.

    7. Why We Need Architecture

    Imagine writing the whole CRUD code inside one class:

    @RestController
public class StudentController {
    // receive request
    // validate data
    // write business logic
    // update student
    // delete student
    // talk to database
}

    Technically, for a very small demo, this may work. But it is not a good backend design, and the reason is that one class ends up doing everything:

    • Receiving HTTP request
    • Processing business logic
    • Talking to database
    • Deciding response
    • Managing update/delete rules

    This becomes messy very quickly. As soon as the project grows - a Teacher, a Course, a Batch, a Payment, an Attendance, an Enrollment - the single class turns into a swamp. Real applications divide responsibility instead. That is the main reason we create layers.

    One class doing everything:
  HTTP + validation + business logic + SQL + response rules

Many classes doing one thing each:
  Controller  ->  Service  ->  Repository  ->  Database

    Important: The problem is not that one class is impossible. The problem is that it mixes concerns that change for different reasons, so every new rule forces you to touch code that should have been unrelated.

    8. The Final Architecture: Postman to Database

    The application follows one core flow:

    Postman
   |
   v
Controller
   |
   v
Service
   |
   v
Repository
   |
   v
Database

    This is the core structure of the project. Postman is acting like a client. In real life the request may come from a React frontend, an Angular frontend, a mobile app, another backend service, or Postman. All of them are just clients sending HTTP to our Spring Boot application.

    The response travels the same path in reverse:

    Database
   |
   v
Repository
   |
   v
Service
   |
   v
Controller
   |
   v
Postman

    Here is the layer-by-layer responsibility table the source says should definitely be shown:

    Layer Main Responsibility Example
    Postman Sends HTTP request POST /api/students
    Controller Handles API request StudentController
    Service Contains business logic StudentService
    Repository Performs database operations StudentRepository
    Database Stores actual data MySQL students table
    Entity/Model Represents table as Java object Student class

    Mnemonic for the request path: P-C-S-R-D (Postman, Controller, Service, Repository, Database). Read it like a postal route: the client posts a letter, the gate receives it, the office decides, the records room files it, and the archive stores it.

    9. Step 1 and Step 2: Postman Sends, the Controller Receives

    Step 1: Postman sends request. Postman sends data to our Spring Boot application. It is a stand-in for any client.

    Step 2: Controller receives request. The first Java layer that handles the request is the Controller. Its job is not to write all the logic. The controller's job is mainly to:

    • Receive request
    • Read input data
    • Call service layer
    • Return response

    The controller is like the entry gate of the application. Its shape follows directly from that responsibility:

    // controller/StudentController.java - the entry gate, only routes and delegates
@RestController
@RequestMapping("/api/students")
public class StudentController {
    private final StudentService studentService;

    public StudentController(StudentService studentService) {
        this.studentService = studentService;
    }

    @PostMapping
    public Student create(@RequestBody Student student) {
        return studentService.createStudent(student);
    }

    @GetMapping("/{id}")
    public Student getById(@PathVariable Long id) {
        return studentService.getStudentById(id);
    }
    // @GetMapping for all, @PutMapping("/{id}"), @DeleteMapping("/{id}")
}

    @RestController marks the class as an HTTP entry point, @RequestMapping("/api/students") fixes the base path, and the method annotations (@PostMapping, @GetMapping, @PutMapping, @DeleteMapping) map each operation. @RequestBody reads the JSON body into a Student, and @PathVariable takes the id from the URL. The controller delegates; it does not decide business rules.

    10. Step 3: The Service Layer and Business Logic

    The controller calls the service. In the source the call is studentService.createStudent(student);.

    The service layer contains the actual business rules. The source lists the kinds of questions a service answers:

    • Should this student be saved?
    • Should deleted students be hidden?
    • How should update happen?
    • What should happen if student ID does not exist?
    • Soft delete or hard delete?

    In this first CRUD app, the business logic will be simple, but the layer still matters because that is where complexity will later live. Its shape:

    // service/StudentService.java - business rules live here
@Service
public class StudentService {
    private final StudentRepository studentRepository;

    public StudentService(StudentRepository studentRepository) {
        this.studentRepository = studentRepository;
    }

    public Student createStudent(Student student) {
        return studentRepository.save(student);
    }
    // getAllStudents(), getStudentById(Long), updateStudent(Long, Student), deleteStudent(Long)
}

    @Service marks the class as a business-logic bean, and the constructor injection is exactly the Dependency Injection practiced earlier in the course, now inside a real application. The service depends on the repository, not on HTTP and not on SQL.

    The update rule from Section 3 belongs here: find the student by ID, update the fields, then save. That is the "very important backend pattern" the source highlights - and it is a service decision, which is why it is not in the controller.

    11. Step 4: The Repository Talks to the Database

    The service calls the repository with studentRepository.save(student);.

    The repository is responsible for database operations. The critical point is that we will not write SQL manually for basic operations. Spring Data JPA gives ready-made methods:

    • save()
    • findAll()
    • findById()
    • deleteById()

    So the repository is the layer that connects Java code with database operations. Its shape is small precisely because the framework does the heavy lifting:

    // repository/StudentRepository.java - Spring Data JPA supplies the SQL
public interface StudentRepository extends JpaRepository<Student, Long> {
    // save(), findAll(), findById(), deleteById() come ready-made
}
    Repository method CRUD operation Used by
    save() Create / Update create and update flows
    findAll() Read all get all students
    findById() Read one get student by ID
    deleteById() Delete delete student

    Important: save() serves both create and update. The update flow finds the existing student, changes its fields, and calls save() again; there is no separate update-all method to remember.

    12. Step 5 and Where Entity/Model Fits

    Step 5: Database stores the data. Finally the data reaches MySQL. A new row is inserted into the students table. Then the response travels back up the chain: Database -> Repository -> Service -> Controller -> Postman.

    The entity deserves its own note because it is special. In the diagram we usually write:

    Controller -> Service -> Repository -> Database

    But there is one more important part: Entity / Model. The entity is not exactly a flow layer like controller or service. Instead, it is the object that travels between layers:

    • Controller receives Student data.
    • Service works with the Student object.
    • Repository saves the Student object.
    • JPA converts the Student object into a students table row.
    Student student  ->  travels through every layer
JPA maps it      ->  students table row
    Thing Is it a flow layer? Does it do work?
    Controller Yes routes and delegates
    Service Yes applies business rules
    Repository Yes runs database operations
    Entity / Model No carries and represents data

    This distinction is a favorite interview probe: naming Student as "the fourth layer" is imprecise. It is the payload, and JPA is the mapper.

    13. Project Setup and Dependencies

    For this CRUD project, add these dependencies:

    1. Spring Web
    2. Spring Data JPA
    3. MySQL Driver

    Why Spring Web? Without it, our application is like a normal backend app, but it will not expose HTTP endpoints like:

    GET /api/students
POST /api/students
PUT /api/students/1
DELETE /api/students/1

    Spring Web gives us the annotations: @RestController, @RequestMapping, @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, @PatchMapping.

    Why Spring Data JPA? It is needed because we want to perform database operations without writing basic SQL manually. It reduces boilerplate database code.

    Why MySQL Driver? Our Spring Boot app is Java code. MySQL is a separate database. Java needs a driver to communicate with MySQL, so we add mysql-connector-j.

    Dependency Purpose What it unlocks
    Spring Web Build APIs HTTP endpoint annotations
    Spring Data JPA Database operations without manual SQL save, findAll, findById, deleteById
    MySQL Driver Talk to MySQL the driver class Spring uses for jdbc:mysql

    These are declared in pom.xml, and the database connection details (URL, username, password) live in src/main/resources/application.properties.

    14. The Empty-App Startup Failure and Auto-Configuration

    Before writing any code, the source runs the empty app to show what happens. The app failed because Spring Data JPA and the MySQL Driver were added, so Spring Boot assumed: "This project wants to connect to a database." During startup it tried to auto-create a DataSource for MySQL. But the project did not yet have database details like URL, username, and password, so it failed with:

    Failed to configure a DataSource: 'url' attribute is not specified
Reason: Failed to determine a suitable driver class

    This is auto-configuration working from dependencies: Spring Boot auto-configuration works based on the JAR dependencies present in your project. If a database library is present and you have not manually configured a database bean, Spring Boot tries to configure one automatically.

    Dependency present Spring Boot assumes It configures
    spring-boot-starter-web This looks like a web application Tomcat, DispatcherServlet, web MVC setup, JSON support
    spring-boot-starter-data-jpa + mysql-connector-j This looks like a database/JPA application DataSource, Hibernate, EntityManagerFactory, TransactionManager, Repository support

    The failure actually showed while creating entityManagerFactory, because the DataSource could not be created without the DB URL details. The fix is to supply spring.datasource.url, spring.datasource.username, and spring.datasource.password.

    Interviewer's perspective: "Why did a brand-new app fail before you wrote any code?" The strong answer is dependency-driven auto-configuration: JPA plus a driver means Spring expects a DataSource, and a missing URL is a configuration error, not a coding bug.

    15. Folder Structure and the Main Application Class

    Imagine writing everything inside the main package directly:

    com.coderarmy.studentcrud
|-- StudentCrudApplication
|-- StudentController
|-- StudentService
|-- StudentRepository
`-- Student

    This will still work. But as soon as the project grows it becomes messy. Suppose later we add Teacher, Course, Batch, Payment, Attendance, Enrollment - the package becomes crowded. So instead of keeping all classes together, we divide them based on responsibility into packages:

    controller
service
repository
entity

    Each package has a clear purpose. The main application class is the starting point of the Spring Boot application, and it should stay in the root package (in.strikes.crudSpringBootDemo in this project, shown generically as the root package in the source). Why? Because @SpringBootApplication includes component scanning. By default, Spring scans the package where this class is present and its subpackages. Put the entry class in the root and every layer package under it is discovered automatically.

    root package
   |-- CrudSpringBootDemoApplication   (@SpringBootApplication, scans here)
   |-- controller/  StudentController
   |-- service/     StudentService
   |-- repository/  StudentRepository
   `-- entity/      Student

    16. MySQL Setup and Creating the Database

    Why MySQL for this project? Because it is popular, beginner-friendly, easy to inspect using MySQL Workbench or the terminal, and commonly used with Spring Boot.

    First understand the difference between three things:

    • MySQL Server = the actual database engine.
    • MySQL Client = the terminal command used to connect to MySQL Server.
    • MySQL Workbench = the GUI application used to manage MySQL visually.

    On macOS, install and start with Homebrew:

    brew install mysql
brew services start mysql
brew services list
mysql --version
mysql_secure_installation
mysql -u root -p

    On Windows, use the MySQL Installer, choose Developer Default, keep port 3306, set the root password, and run it as a Windows Service (net start MySQL80).

    The database we create is named student_crud_db. Inside it, JPA will later create the table students:

    MySQL Server
   |
   v
student_crud_db
   |
   v
students table
   |
   v
student rows

    The key point: at this stage we only create the database. We do not manually create the table. The table can be created automatically by JPA when we run the application with proper configuration.

    Task Who does it
    Create the student_crud_db schema we create it (manually)
    Create the students table JPA/Hibernate at startup
    Insert/update/delete rows repository methods at runtime

    17. Myth vs Reality

    Myth Reality
    "CRUD is beginner content, not real backend work" CRUD is the foundation of most backend systems; larger systems are CRUD plus rules
    "The controller should contain the business logic" The controller is the entry gate; business rules belong in the service layer
    "The repository is where we hand-write SQL" For basic operations Spring Data JPA supplies save, findAll, findById, deleteById; no manual SQL
    "Entity is the fourth flow layer" Entity is the object that travels between layers; JPA maps it to a table row
    "A new Spring Boot app never fails before you write code" Adding JPA plus a driver makes Boot auto-configure a DataSource and fail without a URL
    "Save and update need different repository methods" save() handles both create and update
    "We must create the students table by hand" We create only the database; JPA creates the table at startup
    "Any URL change needs a new endpoint shape" The same path with a different HTTP method is a different operation
    "Soft delete and hard delete are the same" Soft delete keeps the row (isDeleted = true); hard delete removes the row permanently

    18. Common Trap Questions

    Trap 1 - "CRUD is just beginner stuff." Verdict: False. CRUD is the basic skeleton of backend development and the foundation of most backend systems.

    Trap 2 - "Put all the CRUD logic in the controller." Verdict: False. A single class doing HTTP, business logic, and DB work becomes messy; divide responsibility into controller, service, and repository.

    Trap 3 - "The controller should decide soft delete versus hard delete." Verdict: False. That is a business rule and belongs in the service layer, which calls the repository.

    Trap 4 - "Creating and updating use different repository methods." Verdict: False. save() serves both: insert for a new object, update for an existing one after fields are changed.

    Trap 5 - "A brand-new Spring Boot app cannot fail before you write code." Verdict: False. JPA plus the MySQL driver make Boot auto-configure a DataSource, which fails without spring.datasource.url, username, and password.

    Trap 6 - "The entity is the fourth layer in the flow." Verdict: False. The flow is Controller -> Service -> Repository -> Database; the entity is the object that travels between the layers.

    Trap 7 - "We must manually create the students table before running." Verdict: False. We create only the student_crud_db database; JPA creates the students table automatically with proper configuration.

    19. Points to Remember

    1. CRUD = Create, Read, Update, Delete, and it is the foundation of most backend systems, not beginner-only content.
    2. The mapping is POST = create, GET = read (all or one), PUT = update, DELETE = delete.
    3. The six APIs live under /api/students, and the single-student operations use /api/students/{id} with @PathVariable.
    4. Update follows one pattern: find by ID, update fields, then save.
    5. Layers divide responsibility: Controller (entry gate), Service (business logic), Repository (database operations), Database (storage), Entity (object between layers).
    6. The request path is Postman -> Controller -> Service -> Repository -> Database, and the response returns along the same path in reverse.
    7. Spring Data JPA provides save(), findAll(), findById(), and deleteById(), so basic operations need no manual SQL; save() handles both create and update.
    8. Dependencies: Spring Web (API endpoints), Spring Data JPA (database operations), MySQL Driver (Java-to-MySQL communication).
    9. Adding JPA plus a driver triggers DataSource auto-configuration, which fails until spring.datasource.url, username, and password are set.
    10. Packages controller, service, repository, entity keep classes organized, and the main class stays in the root package so @SpringBootApplication component scanning finds everything.

    20. Likely Interview Questions

    Question Crisp Answer
    What is CRUD? The four basic data operations: Create, Read, Update, Delete.
    Why is CRUD important? It is the foundation of most backend systems; the YouTube and Instagram examples are just CRUD with rules.
    How does CRUD map to HTTP methods? POST creates, GET reads, PUT updates, DELETE deletes.
    What does the controller do? Receives the request, reads input, calls the service, returns the response - the entry gate.
    What does the service layer do? Contains business rules such as hiding deleted students, update behavior, missing-ID handling, and soft versus hard delete.
    What does the repository do? Performs database operations using Spring Data JPA methods like save, findAll, findById, deleteById.
    Which repository method handles both create and update? save() - insert for a new object, update for an existing one after changing fields.
    Where does the entity fit in the architecture? It is not a flow layer; it is the object that travels between layers and is mapped by JPA to a table row.
    What dependencies does the project need? Spring Web, Spring Data JPA, and MySQL Driver.
    Why did the empty app fail to start? JPA plus the driver made Boot auto-configure a DataSource, but spring.datasource.url and credentials were missing.
    Why keep the main class in the root package? @SpringBootApplication component scanning covers its package and subpackages, so all layers are found.
    Why create only the database and not the table? JPA/Hibernate creates the students table automatically from the entity when the app runs with proper configuration.

    21. Final Summary

    Postman (client: React / Angular / mobile / another service)
        |
        v
Controller   -> receives HTTP request, reads input, calls service    (StudentController)
        |
        v
Service      -> business rules: save? hide deleted? update how? soft or hard delete?  (StudentService)
        |
        v
Repository   -> database operations: save / findAll / findById / deleteById  (StudentRepository)
        |
        v
Database     -> MySQL student_crud_db -> students table -> student rows
        |
        v
Response     -> Database -> Repository -> Service -> Controller -> Postman
    • CRUD (Create, Read, Update, Delete) is the skeleton under YouTube, Instagram, and most backend systems.
    • HTTP mapping: POST create, GET read, PUT update, DELETE delete, all under /api/students.
    • Layers divide one messy class into Controller (gate), Service (rules), Repository (data), Database (storage).
    • The entity (Student) is the object travelling between layers; JPA maps it to the students table row.
    • Spring Boot auto-configures from dependencies, which is exactly why the empty app failed until the DataSource details were supplied.

    One-line takeaway: A CRUD project is not five endpoints glued together; it is a request that enters a gate, gets its rules applied, reaches the database through a repository, and returns as a response - and understanding each layer's job is the whole point.
