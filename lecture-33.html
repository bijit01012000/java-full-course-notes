    Part 5 · Collections, Lambdas & Streams · Lecture 33

    Set & Map Interface in Java | Internal Working of HashMap, HashSet & TreeMap

    17 sections · interview-oriented · both themes

    Scope evidence: "Set & Map Interface in Java | Internal Working of HashMap, HashSet & TreeMap" (playlist map, verified). Repo evidence: code/Demo.java.

    Lecture 29 mapped the Collections Framework and noted that Map sits outside the Collection hierarchy. This lecture covers the two remaining core interfaces, Set and Map, and then opens the internals of their most used implementations: HashSet, HashMap and TreeMap. It explains why a HashSet is a HashMap in disguise, how a bucket array, a load factor and a resize keep HashMap near constant time, and why equals and hashCode decide whether a key is found at all. The constant theme is that the interface fixes the contract while the backing structure fixes the cost.

    1. The Set Interface: No Duplicates, No Index

    A Set<E> is a Collection that models mathematical set membership: it stores each element at most once and exposes no positional access. There is no get(int) and no index, so the only ways to reach an element are to iterate the set or to ask whether an element is present. The nesting is:

    Iterable  ⊃  Collection  ⊃  Set  ⊃  (HashSet, LinkedHashSet, TreeSet)

    Two guarantees define it:

    1. No duplicates — adding an element equal to one already present is rejected and the call returns false.
    2. No index — position is meaningless; the interface makes no promise about iteration order.

    Duplicate detection is not free: the hash-based sets use equals and hashCode, while TreeSet uses compareTo (or a Comparator). The implementation, not the interface, supplies the ordering.

    Important Set is not "a List without duplicates"; it is a different contract. List guarantees position and permits duplicates, Set guarantees uniqueness and offers no position.

    2. The Three Set Implementations

    All three accept the same add, contains, remove and size calls, but they choose different data structures and therefore different costs.

    // Demo.java - the three Set implementations side by side
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Set<String> hash = new HashSet<>();
        hash.add("banana"); hash.add("apple"); hash.add("cherry"); hash.add("apple");
        System.out.println(hash);        // unordered; duplicate ignored

        Set<String> linked = new LinkedHashSet<>();
        linked.add("banana"); linked.add("apple"); linked.add("cherry");
        System.out.println(linked);      // [banana, apple, cherry] insertion order

        Set<String> tree = new TreeSet<>();
        tree.add("banana"); tree.add("apple"); tree.add("cherry");
        System.out.println(tree);        // [apple, banana, cherry] sorted
    }
}
    Aspect HashSet LinkedHashSet TreeSet
    Backing structure Hash table (HashMap) Hash table + doubly linked list Red-black tree (TreeMap)
    Iteration order Unordered Insertion order Sorted ascending
    Typical cost O(1) add / contains / remove O(1) with list overhead O(log n)
    Null elements One null One null None (NullPointerException)
    Duplicate rule equals + hashCode equals + hashCode compareTo / Comparator
    Extra interface Set Set NavigableSet
    Best used when Fast membership tests Order matters but sorting is unnecessary Sorted or range-based access

    Reading the table: HashSet is the default membership set, LinkedHashSet trades a little memory for a predictable encounter order, and TreeSet pays a logarithmic cost to keep elements sorted at every moment.

    Memory aid Hash = fastest, no order. Linked = insert order. Tree = sorted order. The order guarantee always costs something.

    3. HashSet Is Backed by a HashMap

    The single most useful internal fact about HashSet is that it contains no hashing code of its own. It delegates to a HashMap and uses a dummy constant as the value:

    private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();

    Every operation is a thin wrapper:

    HashSet call What it does Result
    add(e) map.put(e, PRESENT) true only if the key was new
    contains(e) map.containsKey(e) membership test
    remove(e) map.remove(e) == PRESENT true if it was present
    size() map.size() number of distinct elements

    This one fact explains several behaviours at once. A HashSet inherits the same default capacity of 16, the same load factor of 0.75, the same collision list, the same treeify rule and the same null rule (one null element, because a HashMap permits one null key). Iteration order is the order of the underlying bins, which is why it looks arbitrary.

    Interviewer's perspective "How is HashSet implemented internally?" The full answer is: it wraps a HashMap, stores each element as a key, and stores a shared constant PRESENT object as the value. Every uniqueness guarantee is really the map's key uniqueness.

    4. The Map Interface: Key to Value Bindings

    A Map<K,V> stores associations: each unique key maps to exactly one value. Keys are unique, values may repeat, and a second put of an existing key overwrites the old value and returns it. Unlike List and Set, Map is not a Collection (cross-reference Lecture 29): it has no add, it is not an Iterable, and it lives in a separate hierarchy.

    Operation Meaning
    V put(K key, V value) insert or overwrite; returns the previous value or null
    V get(Object key) value for a key, or null if absent
    V getOrDefault(Object key, V def) value for a key, or def if absent
    boolean containsKey(Object key) is this key present
    boolean containsValue(Object value) is this value present anywhere
    V remove(Object key) delete the binding, returns the old value
    Set<K> keySet() a view of all keys
    Collection<V> values() a view of all values
    Set<Map.Entry<K,V>> entrySet() a view of all key-value pairs

    The three views are backed by the map: removing through keySet() removes from the map itself. Iterating entrySet() is the idiomatic and fastest way to walk a map, because each Map.Entry already holds both fields.

    // Demo.java - HashMap key to value operations
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Map<String, Integer> stock = new HashMap<>();
        stock.put("apple", 10);
        stock.put("banana", 5);
        System.out.println(stock.put("apple", 12));        // 10 (old value)
        System.out.println(stock.get("apple"));            // 12
        System.out.println(stock.getOrDefault("kiwi", 0)); // 0
        System.out.println(stock.containsKey("banana"));   // true
        System.out.println(stock.get("kiwi"));             // null (absent key)
    }
}

    5. HashMap Internals: Bucket Array and Hashing

    A HashMap is an array of bins called the table, declared as Node<K,V>[] table. Each Node stores four fields:

    final int hash;    // cached spread hash of the key
final K key;
V value;
Node<K,V> next;    // next node in the same bin

    The table is lazily allocated: an empty new HashMap<>() builds nothing until the first put, at which point the array is created with capacity 16. Two steps turn a key into a bin index:

    // step 1 - spread the raw hashCode so high bits influence low bits
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// step 2 - map the spread hash onto a power-of-two table
int index = (n - 1) & hash;   // n = table length

    The spread h ^ (h >>> 16) mixes the top 16 bits down into the low bits, because (n - 1) & hash only reads the low bits when n is a power of two. A null key hashes to 0 and therefore lands in bucket 0.

    Memory aid Hash, spread, mask: hashCode() → h ^ (h >>> 16) → (n - 1) & hash. Modern HashMap is a hash table whose worst-case bins upgrade to a red-black tree.

    6. HashMap Internal Constants

    The tuning of a HashMap is not magic; it is a handful of named constants. Knowing them answers most internals questions precisely.

    Constant Value Meaning
    DEFAULT_INITIAL_CAPACITY 16 (1 << 4) Default number of buckets
    MAXIMUM_CAPACITY 1 << 30 Largest permitted table size
    DEFAULT_LOAD_FACTOR 0.75 Fraction of buckets filled before resizing
    TREEIFY_THRESHOLD 8 Bin length that triggers treeify (when capacity >= 64)
    UNTREEIFY_THRESHOLD 6 Tree bin collapses back to a list below this
    MIN_TREEIFY_CAPACITY 64 Minimum table capacity before treeify is allowed

    The threshold is capacity × loadFactor, so a default map resizes when it holds more than 16 × 0.75 = 12 entries. Capacity is always rounded up to a power of two so the (n - 1) & hash mask works.

    Important The load factor is a pure time-space trade-off. A lower factor (say 0.5) means fewer collisions and faster lookups but more empty buckets and more resizing; a higher factor saves memory but lengthens average bin chains. 0.75 is the empirical compromise.

    7. Collisions, Treeify and Resize

    Two different keys can share a bucket; this is a collision. A HashMap handles collisions in two stages:

    1. Linked list. Colliding nodes are chained through the next pointer. A lookup walks the chain comparing hash first, then equals.
    2. Red-black tree. When a bin's chain reaches TREEIFY_THRESHOLD (8) and the table has at least MIN_TREEIFY_CAPACITY (64), the bin converts to a TreeNode tree, bounding that bin at O(log n). If the table is smaller than 64, the map resizes instead of treeifying. When a tree shrinks below UNTREEIFY_THRESHOLD (6), it reverts to a list.

    Resize doubles the capacity when size > threshold. Rehashing is cheap by design: each node stays at the same index or moves to index + oldCap, decided by one bit test.

    newIndex = (e.hash & oldCap) == 0 ? oldIndex : oldIndex + oldCap

    Two historical points matter. JDK 7 inserted new nodes at the head of a bin, which under concurrent resizing could create a cycle and an infinite loop; JDK 8 inserts at the tail, removing that loop bug. Neither change makes HashMap thread-safe; it remains a single-threaded structure.

    Interviewer's perspective "When does a bucket become a tree in HashMap?" When a bin holds 8 nodes and capacity is at least 64. Below 64 the map grows the table instead, because resizing is the cheaper fix for a small table.

    8. equals() and hashCode(): The Key Contract

    A hash-based Set or Map finds a key in two phases: locate the bucket by hashCode, then confirm identity with equals. For that to work, both methods must obey the contract from Lecture 22:

    • If a.equals(b) is true, then a.hashCode() == b.hashCode() must also be true.
    • Equal objects must be equal in every field that participates in equals, and hashCode must be computed from the same fields.
    // Demo.java - a Set removes duplicates using equals and hashCode
import java.util.*;

class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

public class Demo {
    public static void main(String[] args) {
        Set<Point> set = new HashSet<>();
        set.add(new Point(1, 2));
        System.out.println(set.add(new Point(1, 2))); // false (equal to the first)
        System.out.println(set.size());               // 1
    }
}

    Two failures follow from breaking the contract. equals without hashCode: equal keys compute different hashes and land in different buckets, so the set reports two elements and the map stores two entries. Mutable keys: if a field used by hashCode is changed after insertion, the lookup recomputes a different bucket and the entry becomes unreachable even though it is still in the table.

    Golden rule equals decides whether, hashCode decides where. Break either half and hash collections silently lose their guarantees.

    9. TreeMap: Sorted Keys and NavigableMap

    A TreeMap<K,V> keeps its keys in a red-black tree, a self-balancing binary search tree, so all keys are always in sorted order. Entries are ordered by Comparable natural ordering, or by a Comparator passed to the constructor. Every put, get, remove and contains is O(log n) — slower than a hash map, but it buys sorted iteration and range queries through the NavigableMap interface.

    // Demo.java - TreeMap keeps keys sorted and supports range queries
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        TreeMap<Integer, String> map = new TreeMap<>();
        map.put(30, "C"); map.put(10, "A"); map.put(20, "B"); map.put(40, "D");
        System.out.println(map.keySet());       // [10, 20, 30, 40] sorted

        System.out.println(map.firstKey());     // 10
        System.out.println(map.lastKey());       // 40
        System.out.println(map.floorKey(25));   // 20 (greatest key <= 25)
        System.out.println(map.ceilingKey(25)); // 30 (least key >= 25)
        System.out.println(map.headMap(20));    // {10=A} (keys < 20)
        System.out.println(map.subMap(20, 40)); // {20=B, 30=C} (20 in, 40 out)
    }
}

    The NavigableMap methods fall into three families: endpoints (firstKey, lastKey), nearest (floorKey is the greatest key less than or equal to the argument, ceilingKey the least key greater than or equal to it, with lowerKey and higherKey strict), and ranges (headMap, tailMap, subMap — all views with an inclusive start and exclusive end unless you pass boolean flags).

    Important TreeMap sorts by compareTo, not by equals. A TreeMap therefore treats two keys as duplicates whenever compareTo returns 0, even if equals says they differ. When the two methods disagree, the sorted map wins.

    10. The null Rules Across Map Implementations

    Null handling is a frequent source of surprise, and the rules differ per implementation:

    Implementation One null key Null values Reason
    HashMap Yes Yes hash(null) is defined as 0
    LinkedHashMap Yes Yes inherits the HashMap behaviour
    TreeMap No Yes needs compareTo, which throws on null
    Hashtable No No legacy class explicitly rejects nulls
    ConcurrentHashMap No No rejects nulls to avoid ambiguity in concurrent reads

    A TreeMap with natural ordering throws NullPointerException on a null key. A Comparator can in principle accept null, but relying on that is discouraged. The concurrent and legacy maps reject nulls for a practical reason: in a concurrent map, a null return could mean either "absent" or "value is null", and the ambiguity is not worth the convenience.

    11. Map Implementation Comparison

    Aspect HashMap LinkedHashMap TreeMap Hashtable ConcurrentHashMap
    Order Unordered Insertion (or access) order Sorted by key Unordered Unordered
    Structure Hash table + tree bins Hash table + doubly linked list Red-black tree Hash table Hash table + tree bins
    Null key One One Not allowed Not allowed Not allowed
    Null values Yes Yes Yes Not allowed Not allowed
    Thread-safe No No No Yes (every method) Yes (lock striping)
    Typical get / put O(1) O(1) O(log n) O(1) O(1)
    Concurrent edits Fail-fast Fail-fast Fail-fast Fail-fast iterator; Enumeration is not Weakly consistent
    Best used when General-purpose map Predictable iteration order needed Sorted keys and range queries Legacy code only Shared access across threads

    Reading the table: choose HashMap by default; choose LinkedHashMap when encounter order must be reproducible; choose TreeMap when sorted access or ranges are required; treat Hashtable as legacy; choose ConcurrentHashMap when threads share the map.

    12. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Override equals but not hashCode Equal keys land in different buckets, so duplicates appear Always override both, using the same fields
    Use a mutable key Mutating a hashed field strands the entry in the wrong bucket Make keys immutable, or never mutate hashed fields
    Assume a HashSet is ordered Iteration follows bin order and changes as the set grows Use LinkedHashSet or TreeSet when order matters
    Put non-Comparable keys in a TreeMap ClassCastException at insert or first comparison Use Comparable keys or pass a Comparator
    Ignore the false from HashSet.add A duplicate was silently not added; code assumes it was Check the returned boolean when uniqueness matters
    Rely on hashCode order as sorted order Hash order is not sorted and not stable across runs Sort explicitly, or use TreeMap / TreeSet
    Under-size a large HashMap Repeated resizes copy the whole table during growth Pass an initial capacity near the expected size
    Set a very low load factor Fewer collisions but many more buckets and resizes Keep the default 0.75 unless measurements justify a change
    Call get then getOrDefault on absent keys null is indistinguishable from a stored null value Use containsKey to test presence
    Assume HashMap is thread-safe Concurrent writes can lose updates or corrupt state Use ConcurrentHashMap or external locking

    Golden rule Hash collections are only as correct as your equals/hashCode pair and only as ordered as the implementation you chose.

    13. Myth vs Reality

    Myth Reality
    "HashSet is its own data structure." It wraps a HashMap, storing elements as keys and a shared PRESENT constant as values.
    "HashMap keeps keys in insertion order." HashMap makes no order promise; only LinkedHashMap preserves encounter order.
    "A HashMap lookup is always O(1)." It is O(1) on average; a worst-case bin is O(log n) after treeify, still not O(1).
    "HashMap is the thread-safe map." It is not. Hashtable and ConcurrentHashMap are, and Hashtable is the legacy one.
    "TreeMap finds duplicates with equals." It uses compareTo (or a Comparator); a 0 comparison means duplicate regardless of equals.

    14. Common Trap Questions

    Trap 1 — "Why does my HashSet still contain two equal objects?" You overrode equals but not hashCode, so the two equal objects hash into different buckets. Override both from the same fields.

    Trap 2 — "What does new HashSet<Integer>().add(1) return the first and second time?" true the first time and false the second. The set already contains a value equal to 1, so the duplicate is rejected.

    Trap 3 — "Can a HashMap have a null key? Can a TreeMap?" A HashMap may have exactly one null key and any number of null values. A TreeMap rejects a null key with NullPointerException under natural ordering, though it accepts null values.

    Trap 4 — "How many entries before a default HashMap resizes?" The threshold is capacity × loadFactor = 16 × 0.75 = 12. The thirteenth insert triggers a resize to 32.

    Trap 5 — "Why can a lookup fail after I mutate a key in a HashMap?" The key now hashes to a different bucket, so the map searches the wrong bin and never finds the entry. Use immutable keys.

    Trap 6 — "Does a bin become a tree as soon as it reaches 8 collisions?" Only if the table capacity is at least 64. Below 64 the map resizes the table instead of treeifying the bin.

    Trap 7 — "Is Map a Collection?" No. Map stores key-value bindings and is not Iterable; only its keySet(), values() and entrySet() views implement Collection (Lecture 29).

    15. Points to Remember

    1. Set forbids duplicates and has no index; Map stores unique keys mapped to values and is not a Collection.
    2. HashSet is backed by a HashMap, using PRESENT as a dummy value for every element.
    3. LinkedHashSet preserves insertion order; TreeSet keeps elements sorted in a red-black tree at O(log n).
    4. A HashMap is a lazily allocated Node[] table; the first put creates it with capacity 16.
    5. The spread h ^ (h >>> 16) mixes high bits down; the index is (n - 1) & hash.
    6. Defaults: capacity 16, load factor 0.75, threshold capacity × loadFactor (12 for a default map).
    7. A bin treeifies at 8 nodes only when capacity >= 64, untreeifies below 6; resize doubles capacity.
    8. JDK 8 changed bin insertion from head to tail, removing the JDK 7 resize loop under concurrency, but HashMap is still not thread-safe.
    9. equals and hashCode must agree; a mutable hashed field strands the entry in the wrong bucket.
    10. TreeMap judges duplicates by compareTo; HashMap allows one null key, TreeMap none, and Hashtable/ConcurrentHashMap reject all nulls.

    16. Likely Interview Questions

    Question Crisp Answer
    What is a Set, and how is it different from a List? A Set stores each element at most once and has no index; a List is ordered, indexed and allows duplicates.
    How is HashSet implemented internally? As a wrapped HashMap; each element is a key and each value is the shared constant PRESENT.
    HashSet vs LinkedHashSet vs TreeSet? HashSet is unordered and O(1); LinkedHashSet keeps insertion order; TreeSet keeps sorted order at O(log n).
    Why is Map not a Collection? It stores key-value bindings rather than single elements and is not Iterable; only its views are Collections.
    What are the default capacity and load factor of HashMap? Capacity 16 and load factor 0.75, so the threshold is 12 entries.
    What is the load factor? The fraction of buckets that may fill before the table doubles; it trades memory against collision cost.
    How does a HashMap compute a bucket index? It spreads the hash with h ^ (h >>> 16) and masks with (n - 1) & hash.
    What happens on a collision? Nodes chain in a linked list; a bin of 8 nodes treeifies to a red-black tree once capacity reaches 64.
    When does a HashMap resize, and what does it cost? When size exceeds capacity × loadFactor; it doubles the table and rehashes, each node staying or moving by oldCap.
    Why do equals and hashCode matter for map keys? The bucket is chosen by hashCode and confirmed by equals; if they disagree, equal keys are stored twice or lost.
    How is TreeMap implemented? As a red-black tree ordered by Comparable or a Comparator, giving O(log n) operations and sorted iteration.
    Does HashMap allow null keys and values? Yes — one null key and any number of null values; TreeMap rejects null keys, and Hashtable/ConcurrentHashMap reject all nulls.

    17. Final Summary

    Collection  ⊃  Set  ⊃  (HashSet, LinkedHashSet, TreeSet)
                    HashSet  -> wraps HashMap, PRESENT dummy value, one null, O(1), unordered
                    LinkedHashSet -> insertion order
                    TreeSet  -> red-black tree, sorted, NavigableSet, O(log n), no null

Map (NOT a Collection)  ⊃  (HashMap, LinkedHashMap, TreeMap, Hashtable, ConcurrentHashMap)

HashMap internals:
   Node[] table  (lazy, default 16, load factor 0.75, threshold = capacity × loadFactor)
   hash:  key.hashCode()  →  h ^ (h >>> 16)  →  index = (n - 1) & hash
   collision: linked list -> treeify at 8 nodes && capacity >= 64 -> untreeify below 6
   resize: doubles capacity, rehashes by (e.hash & oldCap)
   JDK 8: head insertion -> tail insertion (kills the JDK 7 loop bug; still not thread-safe)
   keys: equals + hashCode must agree; mutable keys corrupt lookups

TreeMap: red-black tree, natural order or Comparator, O(log n), firstKey lastKey floorKey ceilingKey headMap subMap
nulls: HashMap 1 null key + null values · TreeMap no null key · Hashtable / ConcurrentHashMap no nulls
    • Set → uniqueness, no index; HashSet = a HashMap with a constant value.
    • Map → unique keys to values; not a Collection, but its views are.
    • HashMap → bucket array, spread hash, treeified collisions, resize by doubling, near O(1), not thread-safe.
    • TreeMap → red-black tree, sorted keys, range queries, O(log n).
    • Keys → equals and hashCode decide membership; mutable keys break lookups.
    • nulls → one null key in HashMap, none in TreeMap, Hashtable and ConcurrentHashMap.

    Golden rule A Set answers "is it there", a Map answers "what does it map to", and both rely on the same hashing agreement: equals must match hashCode, and an ordered structure sorts by compareTo.

    One-line takeaway: HashSet is a HashMap in disguise, HashMap is a bucket array with treeified collisions and a 0.75 load factor, and TreeMap trades constant-time hashing for sorted, range-capable O(log n) keys.
