    Part 2 · Arrays & OOP Core · Lecture 13

    Constructors in Java Explained — Constructor Chaining, Overloading & the this Keyword

    16 sections · interview-oriented · both themes

    Scope evidence: lecture title "Constructors in Java | Constructor Chaining, Overloading & this" (playlist map, verified). Repo evidence: 3 Demo files (Demo.java, Demo2.java, Demo3.java).

    Every object begins its life in a constructor, and the constructor is the one method-like member that the JVM calls for you rather than you calling it. This lecture covers what a constructor is, the compiler-supplied default constructor, parameterized constructors and overloading, the this keyword in both its field-disambiguation and constructor-chaining roles, the exact order in which field initializers, instance blocks and static blocks run, constructor visibility, and the copy-constructor pattern. It closes with the comparison tables, the pitfall catalogue (a stray return type silently demotes a constructor to a method), and the forward links to inheritance chaining (Lecture 16), static initialization (Lecture 15) and deep versus shallow copy (Lecture 14).

    1. What a Constructor Is

    A constructor is a special member that initializes a newly created object. Four facts define it:

    1. Its name is exactly the class name — no exceptions, no aliases.
    2. It has no return type, not even void. void Demo() is an ordinary method.
    3. It is invoked once per new, never called like a method.
    4. It runs after memory is allocated, so it exists to put the fresh object into a valid state.
    // Demo.java — a constructor runs once per new
public class Demo {
    int id;

    Demo() {                           // same name as the class, no return type
        id = 101;
        System.out.println("constructor ran");
    }

    public static void main(String[] args) {
        Demo d1 = new Demo();          // constructor runs here
        Demo d2 = new Demo();          // runs again for the second object
        System.out.println(d1.id + " " + d2.id);   // 101 101
    }
}

    The expression new Demo() does two distinct things: the new operator allocates and zeroes the object, then the constructor runs on that object. You cannot write d1.Demo() — the constructor is not reachable as a call.

    Important "No return type" is not the same as "returns nothing". A method may return nothing (void); a constructor has no return type clause at all. Writing void Demo() compiles as a method and is the single most common constructor mistake.

    Memory aid — same name, no type, called by new.

    2. The Default Constructor

    If a class declares no constructor at all, the compiler inserts a public no-arg constructor with an empty body — public class Box {} is compiled as if it also contained public Box() {}.

    The default constructor is supplied only when no constructor is declared. The moment any constructor exists — no-arg or parameterized — the compiler stops generating one:

    1. class Box {} — compiler adds Box(), so new Box() compiles.
    2. class Box { Box(int n) {} } — no default is added, so new Box() is now a compile error.

    Interviewer's perspective The classic trap: "I added a parameterized constructor and now new Foo() fails to compile — why?" Because declaring any constructor suppresses the compiler-generated default. If both forms are wanted, the no-arg constructor must be written by hand.

    Note also that the generated default carries the access modifier of the class — a package-private class gets a package-private default constructor. A constructor and a method can share a name; only the absence of a return type makes the member a constructor.

    3. Parameterized Constructors and Overloading

    A parameterized constructor accepts arguments so each object can be created with its own state. Constructor overloading is simply declaring several constructors with the same class name but different parameter lists:

    // Demo2.java — parameterized constructors and overloading
public class Demo2 {
    String name;
    int age;

    Demo2() {                       // overload 1: no-arg
        this("unknown", 0);         // delegate — Section 4
    }

    Demo2(String name) {            // overload 2: one argument
        this(name, 18);
    }

    Demo2(String name, int age) {   // overload 3: two arguments
        this.name = name;           // this.field resolves shadowing
        this.age = age;
    }

    public static void main(String[] args) {
        Demo2 a = new Demo2();
        Demo2 b = new Demo2("Ravi");
        Demo2 c = new Demo2("Mira", 25);
        System.out.println(a.name + " " + b.name + " " + c.age);   // unknown Ravi 25
    }
}

    Overloading rules, identical to method overloading (Lecture 12):

    1. The parameter list must differ — count, types or order. Return type is irrelevant and cannot be the only difference.
    2. Two constructors differing only in parameter names are a duplicate-method compile error.
    3. The correct overload is chosen at compile time by the static types of the arguments.
    4. Constructors can be overloaded but never overridden — they are not inherited (Lecture 16).

    4. Constructor Chaining with this()

    One constructor can delegate to another using this(...). This is constructor chaining, and it removes duplicated initialization:

    // Demo3.java — field initializers run before the constructor body
public class Demo3 {
    int x = initX();                            // field initializer (textual order first)
    { System.out.println("instance block"); }   // instance initializer block

    Demo3() {
        System.out.println("constructor body: x = " + x);
    }

    static int initX() {
        System.out.println("field initializer");
        return 7;
    }

    public static void main(String[] args) {
        new Demo3();   // field initializer -> instance block -> constructor body: x = 7
    }
}

    Chaining is subject to three hard rules:

    1. this(...) must be the first statement in the constructor body. Anything before it is a compile error.
    2. At most one this(...) call per constructor.
    3. Chaining cannot form a cycle. A() { this(1); } and A(int n) { this(); } is a recursive constructor invocation compile error.

    The chain unwinds into a single initialization path:

    new Demo2("Mira", 25) --> Demo2(String,int) --> object ready
new Demo2("Ravi")     --> Demo2(String) --> this(name,18) --> Demo2(String,int) --> object ready
new Demo2()           --> Demo2() --> this("unknown",0) --> Demo2(String,int) --> object ready

    Important this(...) and super(...) are mutually exclusive as the first statement: a constructor may delegate within the class or to the parent, never both. In an inheritance chain the parent runs first (Lecture 16).

    5. The this Keyword: Disambiguation and Delegation

    this is a reference to the current object. Inside a constructor it does two jobs:

    Use Form Meaning
    Field disambiguation this.name = name; Resolves shadowing when the parameter shares the field name
    Constructor delegation this(...) Calls another constructor of the same class
    Pass current object on other.register(this) Sends the partially built object to another collaborator
    Return current object return this; Enables fluent/builder APIs
    1. Without this, name = name; assigns the parameter to itself and leaves the field unchanged — a silent no-op.
    2. this cannot be used in a static context, because no instance exists there.
    3. Using this in a constructor before the delegated this(...)/super(...) call is illegal, since the object is not yet initialized.

    Memory aid — this.name picks the field; this(...) picks the constructor.

    6. Constructor vs Method

    Aspect Constructor Method
    Purpose Initialize a new object Perform behaviour on an existing object
    Name Must equal the class name Any legal identifier
    Return type None — not even void Required (void or a type)
    Invocation Implicitly by new, this(...), super(...) Explicitly on an object or class
    Times called Exactly once per object Zero or many times
    Overloading Allowed Allowed
    Overriding Not applicable (never inherited) Allowed — runtime polymorphism
    static Cannot be static Can be static
    abstract/final Cannot be either Can be either
    Supplied by compiler Yes, when none is declared No

    Reading the table: the first four rows are the ones examiners probe — a member missing any of them is not a constructor.

    7. Default vs Parameterized Constructor

    Aspect Default (no-arg) Parameterized
    Parameters None One or more
    Supplied by Compiler, only if none is declared The programmer
    Initial field values 0/false/null, or field initializers Caller-supplied values
    Object state Uniform and generic Customized per object
    Fate after any declaration Removed from generation Coexists with the other overloads
    Typical use Frameworks, simple value-less objects Required state, validation, invariants
    Calling form new Demo() new Demo(args)

    The decisive distinction is origin: the default constructor is generated, the parameterized constructor is written, and the former exists only in the absence of the latter.

    8. Field Initialization Order

    The full construction sequence for an object, in order:

    allocate (zeroed memory) --> super constructor --> field initializers + instance blocks (textual order) --> constructor body
    1. Memory is allocated and all fields are set to their default values (0, false, null).
    2. The superclass constructor completes first.
    3. Instance field initializers and instance initializer blocks run in the textual order in which they appear in the source.
    4. Only then does the constructor body execute — so a constructor body always sees fields already initialized.

    Separately, static initializer blocks run once, at class load, before any instance exists (Lecture 15). Do not confuse the two: static blocks belong to the class, instance blocks to each object.

    9. Constructor Visibility

    Constructors obey access modifiers, and each level has a design purpose:

    Modifier Who can create Typical use
    public Everyone Ordinary instantiable classes
    protected Same package and subclasses Abstract base classes (Lecture 17)
    package-private (default) Same package only Package-internal collaborator types
    private Nobody outside the class Utility classes, singletons, static factories
    1. A class of only static utilities uses a private constructor to make instantiation impossible — for example Math and Collections themselves.
    2. A singleton exposes one static instance and hides the constructor.
    3. A protected constructor on an abstract class lets subclasses initialize the base while preventing new on the abstract type (Lecture 17).

    Important A private constructor is not a dead member — it is still callable from inside the class, which is exactly how the singleton holds its own instance and how a static factory builds objects.

    10. The Copy Constructor Pattern

    Java has no built-in copy constructor; you write one by hand. It takes a single argument of the same type and copies state field by field:

    // CopyDemo.java — manual copy constructor (shallow here)
class Point {
    int x, y;

    Point(int x, int y) { this.x = x; this.y = y; }

    Point(Point other) {          // copy constructor
        this.x = other.x;
        this.y = other.y;
    }

    public static void main(String[] args) {
        Point p1 = new Point(2, 3);
        Point p2 = new Point(p1); // copy constructor
        p2.x = 99;                // independent copy for primitives
        System.out.println(p1.x + " " + p2.x);   // 2 99
    }
}
    1. For primitive fields a field-by-field copy is a full deep copy of the value.
    2. For reference fields the copy is shallow — both objects point at the same inner object. A true deep copy must recursively copy each referenced object.
    3. The full deep-versus-shallow treatment is Lecture 14.

    11. Pitfalls

    Pitfall Example What happens Fix
    A return type is added void Demo() {...} Compiles as a method; new runs the default constructor instead, so the "constructor" never executes Delete the return type
    this() is not first int x = 1; this(2); Compile error: this call must be first Move this(...) to the top
    Recursive chaining A() { this(1); } / A(int n) { this(); } Compile error: recursive constructor invocation Break the cycle
    Overridable call in constructor Constructor calls doWork(), overridden in subclass Subclass fields are still default values, so the override sees a half-built object Call only private/final methods from constructors
    Constructor explosion Many overloads with long parameter lists Call sites become error-prone Use a builder or static factory
    Shadowing ignored name = name; Assigns the parameter to itself; field stays null this.name = name;

    Interviewer's perspective "Why is calling an overridable method from a constructor dangerous?" Because the subclass override executes while the subclass fields are still at their default values — a classic source of null-driven bugs and one of the few places where Java's initialization order actively bites.

    12. Myth vs Reality

    Myth Reality
    "A constructor returns an object." It returns nothing; new allocates the object and the constructor only initializes it.
    "The default constructor is always available." It exists only when no constructor is declared; any declaration removes it.
    "Constructors are inherited by subclasses." They are not inherited and cannot be overridden; a subclass reaches a parent constructor with super(...).
    "this() can appear anywhere in a constructor." It must be the first statement, and at most one such call is allowed.
    "A void method with the class name is a constructor." It is an ordinary method; the missing return type is what makes a member a constructor.
    "Adding a return type is harmless." It silently converts the constructor into a method, so new falls back to the default constructor and your code never runs.

    13. Common Trap Questions

    Trap 1 — "Can a constructor be static?" No. A constructor initializes an instance, so it cannot be static; static context has no this and no instance to build.

    Trap 2 — "Can a constructor be final or abstract?" Neither. Constructors are never inherited, so final and abstract are meaningless for them and are compile errors.

    Trap 3 — "Is void a legal constructor return type?" No — and this is the trap. void Demo() compiles, but as a method, so new Demo() uses the default constructor and the method is never called by new.

    Trap 4 — "Can this(...) and super(...) both be the first statement?" No. They are mutually exclusive; a constructor either delegates within its own class or calls up to its parent, never both.

    Trap 5 — "Do field initializers run before or after the constructor body?" Before. Field initializers and instance blocks execute in textual order, and the constructor body runs last, so it observes initialized fields.

    Trap 6 — "Why does a private constructor not prevent the singleton from existing?" Because the constructor is private to the outside; the class itself constructs its single instance inside its own static context.

    Trap 7 — "Does a subclass automatically get its parent's constructors?" No. Constructors are not inherited; the subclass must invoke a parent constructor through super(...), explicitly or implicitly (Lecture 16).

    14. Points to Remember

    1. A constructor has the class name and no return type — not even void — and is invoked by new, never called explicitly.
    2. The compiler supplies a default constructor only when the class declares none; declaring any constructor removes it.
    3. Constructor overloading is same name with different parameter lists; the argument types decide which runs, resolved at compile time.
    4. this.field resolves parameter/field shadowing; this.name = name is the canonical fix.
    5. this(...) delegates to another constructor and must be the first statement, at most once per constructor.
    6. Recursive constructor chaining is a compile error; a delegation cycle cannot be closed.
    7. this(...) and super(...) cannot both appear as the first statement of a constructor.
    8. Instance field initializers and initializer blocks run in textual order before the constructor body, after the super constructor.
    9. Static initializer blocks run once at class load, not per object (Lecture 15).
    10. Constructors can be private (utility/singleton/static factory) or protected (abstract base, Lecture 17), and adding a return type silently demotes one to a method.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a constructor? A member with the class name and no return type that initializes an object; the JVM invokes it once per new.
    Does a constructor have a return type? No — not even void. A constructor with a return type becomes an ordinary method.
    When does the compiler provide a default constructor? Only when the class declares no constructor; any declaration suppresses it.
    Can constructors be overloaded? Yes — same name, different parameter lists; the compiler picks the matching overload.
    What is constructor chaining? Calling one constructor from another via this(...) (same class) or super(...) (parent), so initialization is not duplicated.
    Why must this() be the first statement? Because the object must be fully delegated before any initialization runs; it enforces a single, ordered initialization path.
    Can you call this() recursively? No — a delegation cycle is a compile error (recursive constructor invocation).
    Difference between a constructor and a method? A constructor has the class name, no return type, is called once by new; a method has any name, a return type, and is called explicitly any number of times.
    Can a constructor be private? Yes — for utility classes, singletons and static factories; it blocks external new.
    What is a copy constructor? A constructor taking one argument of the same type that copies field by field; shallow for references unless deep-copied (Lecture 14).
    Are constructors inherited? No; they are never inherited or overridden. A subclass reaches the parent through super(...) (Lecture 16).
    What runs first: field initializer or constructor body? Field initializers and instance blocks run first, in textual order; the constructor body runs last.

    16. Final Summary

    new ClassName(args)
   -> allocate (fields = 0/false/null)
   -> super(...) [parent constructor, Lecture 16]
   -> field initializers + instance blocks (textual order)
   -> constructor body
   -> object ready
static blocks: once at class load (Lecture 15)
    • Constructor → class name, no return type, runs once per new; never called like a method.
    • Default constructor → compiler-generated only when none is declared; vanishes once any constructor exists.
    • Overloading → same name, different parameter lists; resolved at compile time.
    • this → this.field disambiguates shadowing; this(...) chains constructors and must be first.
    • Chaining → no cycles, one this(...) per constructor, mutually exclusive with super(...).
    • Initialization order → field initializers and instance blocks (textual order), then the constructor body.
    • Visibility → private for utility/singleton, protected for abstract bases (Lecture 17).
    • Copy constructor → manual, field by field; shallow unless deep-copied (Lecture 14).
    • Pitfall → a stray return type turns the constructor into a method that new never calls.

    Golden rule A constructor is defined by two absences — no return type and no explicit call site — and every rule in this lecture follows from preserving those two absences.

    One-line takeaway: the constructor has the class name, no return type, and exactly one caller named new — master this(...) chaining, the default-constructor rule and the initialization order, and every object in Java starts life predictably.
