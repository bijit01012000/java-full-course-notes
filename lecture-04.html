    Part 1 · Java Basics · Lecture 04

    How Java Stores Negative & Floating Point Numbers

    15 sections · interview-oriented · both themes

    Scope evidence: lecture title "How Java Stores Negative & Floating Point Numbers" (playlist map, verified). Repo lecture-04 folder contains one code file, Demo.java.

    Every variable in a Java program is just a finite sequence of bits, and a bit pattern carries no sign of its own. Two conventions decide what those bits mean: two's complement for integers and IEEE 754 for floating point. This topic matters whenever code sits near its limits — overflow bugs, money calculations, and precision questions fail silently, with no exception thrown. Interviewers use these boundaries precisely because they expose whether a candidate understands the machine underneath the language.

    1. The Core Problem: Pure Bits Carry No Sign

    A bit can be 0 or 1. Memory has no "-" glyph and no decimal point. So the language must answer two independent questions by convention:

    1. How is the sign of an integer encoded? (Java's answer: two's complement.)
    2. How are fractions such as 0.1 stored in binary? (Java's answer: IEEE 754 sign + biased exponent + mantissa.)

    Definitions used throughout this note:

    • Two's complement — the integer encoding where the negation of a value is computed as "invert all bits, then add 1".
    • Biased exponent — an exponent stored as actual exponent + bias (a plain unsigned field), so negative exponents need no separate sign.
    • Mantissa (fraction) — the digit part of a floating point number; the exponent scales it by a power of two.
    • Precision — how many bits hold significant digits: 24 for float, 53 for double.

    Getting either convention wrong does not crash the program. It quietly produces wrong numbers, which is the more dangerous failure.

    2. Two Candidate Designs for Signed Integers

    History offers three ways to fold a sign into bits:

    Aspect Sign-Magnitude One's Complement Two's Complement
    How to negate Flip the sign bit Invert all bits Invert all bits, then add 1
    Representation of zero Two zeros (+0, -0) Two zeros (+0, -0) One zero
    Hardware adder Needs special sign logic Needs end-around carry fix Plain binary adder works for all cases
    Zero pattern 0000 and 1000 0000 and 1111 0000 only
    Used by Java No No Yes

    Memory aid — the winning design keeps it singular: one zero, one adder, one rule ("invert and add 1").

    Interviewer's perspective "Why two's complement and not a plain sign bit?" The crisp answer has three parts: there is exactly one zero (no +0/-0 ambiguity), the same adder circuit performs addition and subtraction because a - b becomes a + (-b), and wrapping behaves like modular arithmetic, which keeps range checks simple. Two engineering consequences, not an aesthetic choice.

    3. Deriving Two's Complement on a 4-Bit Machine

    Four bits give 16 patterns. Read them as unsigned, then as two's complement:

    Bit pattern As unsigned As two's complement
    0000 0 0
    0001 1 1
    0010 2 2
    0011 3 3
    0100 4 4
    0101 5 5
    0110 6 6
    0111 7 maximum
    1000 8 -8 (most negative)
    1001 9 -7
    1010 10 -6
    1011 11 -5
    1100 12 -4
    1101 13 -3
    1110 14 -2
    1111 15 -1

    Forming -5 in 4 bits: write 5 as 0101, invert to get 1010, add 1 to get 1011. Verify by addition: 0101 + 1011 = 1 0000 — the carry out is discarded, the result is 0000, exactly zero. That is the design goal: a value plus its negation must be zero with no special casing.

    Subtraction reuses the same trick. 7 - 5 becomes 7 + (-5): 0111 + 1011 = 1 0010 — discard the carry, read 0010 = 2. One adder handles both operations.

    Negative patterns are recognisable at a glance: every negative number has 1s in the leading positions. -1 is all ones, -2 is all ones except a trailing 0, and so on.

    4. Scaling Up: the 32-Bit int and Its Siblings

    The same table scales by width. For n bits the range is [-2^(n-1), 2^(n-1) - 1]:

    • 4 bits: [-8, 7]
    • 32 bits (int): [-2^(31), 2^(31) - 1] = [-2,147,483,648 to 2,147,483,647]
    • 64 bits (long): [-2^(63), 2^(63) - 1]

    The range is asymmetric by exactly one on the negative side because zero consumes one of the 2^n patterns; -2^(n-1) has no positive twin of the same magnitude. Memory aid: "the bottom drops one" — the lower bound is -2^(n-1), the upper bound is 2^(n-1) minus one.

    Type Bits Minimum Maximum
    byte 8 -128 127
    short 16 -32,768 32,767
    int 32 -2,147,483,648 2,147,483,647
    long 64 -9,223,372,036,854,775,808 9,223,372,036,854,775,807
    char 16 0 65,535 (unsigned — no negatives)

    The constants Integer.MIN_VALUE, Integer.MAX_VALUE, Long.MIN_VALUE and so on come from the wrapper types, and their values are fixed on every platform (architecture neutrality, Lecture 3). char is the one integer type where two's complement never applies, since it has no sign.

    5. Overflow: Silent Wraparound and Math.addExact

    Two's complement arithmetic is modular. Past the top of the range, the value wraps to the bottom of the range — and Java throws nothing:

    // OverflowDemo.java — int arithmetic never throws on overflow
int max = Integer.MAX_VALUE;                // 2,147,483,647 = 0111...1111
System.out.println(max + 1);                // -2,147,483,648: wraps to MIN_VALUE
System.out.println(Integer.MIN_VALUE - 1);  // 2,147,483,647: wraps the other way
int n = Integer.MIN_VALUE;
System.out.println(-n);                     // -2,147,483,648: negating MIN overflows too
try {
    Math.addExact(max, 1);                  // detects overflow explicitly
} catch (ArithmeticException e) {
    System.out.println("caught: " + e);     // integer overflow
}

    The bit view explains it: MAX_VALUE is 0111...1111; adding 1 flips it to 1000...0000, which is Integer.MIN_VALUE. No error bit is checked, so the wrap is silent.

    Detection is opt-in through the *Exact family: Math.addExact, Math.subtractExact, Math.multiplyExact, Math.negateExact — each throws ArithmeticException on overflow. Math.negateExact(Integer.MIN_VALUE) throws, because its positive twin does not exist.

    Important Plain int arithmetic never throws on overflow — not +, not -, not *, and not casting (narrowing is covered in Lecture 5). Only the Math.*Exact methods throw.

    6. The Bitwise View of Negatives

    Three facts collapse into one identity:

    1. Adding a value to its bitwise complement fills the pattern with 1s: x + ~x = 111...111, and all-ones as two's complement represents -1.
    2. Therefore ~x = -1 - x, which is the examinable identity: ~x = -(x + 1).
    3. For a negative value, the magnitude is recovered by the same recipe used to build it: invert the bits and add 1.

    Concrete checks worth remembering: ~-7 = 6, ~5 = -6, Integer.toHexString(-1) is ffffffff, and Integer.toBinaryString(-5) prints 32 characters: 11111111111111111111111111111011 — the "leading 1s" are visible directly.

    Consequence: Math.abs(Integer.MIN_VALUE) returns Integer.MIN_VALUE itself, in both the int and long versions. The absolute value 2^31 cannot fit, so negation wraps back down.

    7. Floating Point: The IEEE 754 Layout

    Floating point is scientific notation in binary: a sign, a scaled exponent, and a fractional digit field — stored with no overall sign field for the exponent (that is what the bias replaces).

    value = (-1)^sign  *  1.mantissa  *  2^(stored exponent - bias)
    Property float (32 bits) double (64 bits)
    Sign bit 1 1
    Exponent field 8 bits 11 bits
    Mantissa (fraction) bits 23 52
    Exponent bias 127 1023
    Effective exponent range -126 to 127 -1022 to 1023
    Largest exact integer 2^24 = 16,777,216 2^53 = 9,007,199,254,740,992
    Approximate magnitude +/-3.4 * 10^38 +/-1.8 * 10^308
    Literal default double, suffix f for float double (the default)

    The mantissa stores only the fraction; the leading 1 is implied and costs no bit. That is why a 23-bit fraction field delivers 24 bits of precision. double, at 1 + 11 + 52 bits, delivers a 53-bit mantissa. Memory aid for the splits: float is "1-8-23", double is "1-11-52" — and a full deck of cards (52) tells you which one is the double.

    Why a bias instead of a signed exponent? One unsigned field covers negative and positive exponents, and comparing the raw exponent field orders numbers by magnitude — the hardware Comparator comes free.

    This table extends Lecture 3's data-type list with the internal view: literals like 3.14 and 1e3 are double by default; 3.14f and 1e3f are float. Scientific-notation literals (1e3, 2.5E-4) are one storage scheme away from what follows: decode 0.1 and you get sign 0, stored exponent 127 - 4 = 123 (since 0.1 = 1.6 x 2^-4), and a fraction field holding the repeating pattern 1001 1001 1001.... The pattern is infinite; the 52 available bits are not. That is the entire origin of the next section's surprises.

    8. Special Values: Infinity, NaN and Signed Zero

    IEEE 754 defines four reserved patterns and their arithmetic (positive infinity, negative infinity, NaN, and a signed zero):

    Expression Result Why
    1.0 / 0.0 Infinity IEEE 754 defines division to infinity; no exception (unlike int 1/0)
    -1.0 / 0.0 -Infinity Sign folds into infinity
    0.0 / 0.0 NaN Undefined value — not a number
    Math.sqrt(-9) NaN No real result
    Infinity - Infinity NaN Indeterminate form
    0.0 == -0.0 true == cannot see the sign of zero 
    // SpecialsDemo.java — NaN and the two zeros
System.out.println(1.0 / 0.0);                 // Infinity
System.out.println(0.0 / 0.0);                 // NaN
double nan = Math.sqrt(-1);
System.out.println(nan == Double.NaN);         // false: NaN equals nothing, not even itself
System.out.println(Double.isNaN(nan));         // true: the correct check
double z1 = 0.0, z2 = -0.0;
System.out.println(z1 == z2);                  // true: == reports both zeros equal
System.out.println(1.0 / z2);                  // -Infinity: the sign of zero surfaces here
System.out.println(Double.compare(z1, z2));    // -1: Double.compare distinguishes them

    Interviewer's perspective A sharp follow-up is: "Why does halving integers wrap silently while floating division to zero produces Infinity?" Answer: the integer spec keeps wraparound for hardware simplicity and defines no infinity for ints, while IEEE 754 explicitly designs infinity and NaN in so that partial results never abort a long computation. Both "silent" behaviours are specification, not negligence.

    9. Precision Problems: 0.1 + 0.2 and BigDecimal for Money

    Binary fractions can only be sums of negative powers of two: 1/2, 1/4, 1/8, and so on. Storing 1/10 needs an infinite repeating pattern, so every "nice" decimal is stored as a nearby binary approximation. The errors are tiny individually — and they compound:

    // PrecisionDemo.java — approximations and the exact tool
System.out.println(0.1 + 0.2);                 // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3);          // false
System.out.println(1.0 - 0.9);                 // 0.09999999999999998
System.out.println(0.1f);                      // 0.1 prints literal-style, but ...
System.out.println(0.1f == 0.1);               // false: float and double store different approximations
BigDecimal a = new BigDecimal("0.1");          // String constructor: exact decimal digits
BigDecimal b = new BigDecimal("0.2");
System.out.println(a.add(b));                  // 0.3
System.out.println(a.equals(b.add(a)));        // false: equals() compares scale, use compareTo

    Rules for money and other exact quantities:

    1. Never accumulate double/float values and compare with ==.
    2. Use BigDecimal built from a String literal — new BigDecimal("0.1"). Do not pass the double (new BigDecimal(0.1) captures the binary approximation it was given).
    3. Compare BigDecimal with compareTo (equals is scale-sensitive: 1.0 vs 1.00).
    4. Compare doubles numerically with an epsilon: Math.abs(x - y) < 1e-9, or Double.compare.

    10. Comparison and Rounding Traps

    Comparing an int with a float mixes the two encodings: binary numeric promotion widens the int to float first (the full conversion ladder — Lecture 5), and wide integers can lose precision on the way because float holds only 24 bits of mantissa:

    • 16777217 == 16777216f is true. The int 16777217 (2^24 + 1) needs 25 bits; converted to float it rounds down to 16777216f, so the comparison compares 16777216f with 16777216f.
    • The exactness limit is 2^24 for float and 2^53 for double. Past those points, consecutive integers stop being distinguishable.

    Rounding has its own asymmetry. Math.round rounds half up — toward positive infinity, not away from zero:

    1. Math.round(2.5) is 3 — half up.
    2. Math.round(-2.5) is -2 — still half up, which for negative halves means toward +infinity.
    3. Math.round returns long for a double argument and int for a float argument.
    4. Contrast: Math.rint(2.5) is 2 (ties to even, IEEE default), and BigDecimal with RoundingMode.HALF_UP on -2.5 gives -3 (away from zero) — so "half up" means different things in different APIs. For money, name your RoundingMode explicitly.

    11. Myth vs Reality

    Myth Reality
    "Negative numbers are stored as sign bit + magnitude" Java uses two's complement: negate = invert + 1. The leading 1 in a negative pattern is a consequence, not a sign flag.
    "Integer overflow throws an exception" +, -, * wrap silently (MAX_VALUE + 1 == MIN_VALUE); only the Math.*Exact methods throw.
    "float and double can store 0.1 exactly" 1/10 is a repeating binary fraction; both types store approximations. Use BigDecimal with a String for exact decimals.
    "NaN is equal to NaN" NaN == NaN is false by design; test with Double.isNaN or Double.compare.
    "A float can hold any int exactly" float carries a 24-bit mantissa: integers above 16,777,216 (2^24) round, and int-to-float comparisons silently compare rounded values.
    "The literal 1e3 is a float" Scientific-notation literals are double by default; 1e3f is the float form (Lecture 3).
    "Math.round(-2.5) is -3" Math.round is half up toward +infinity: -2.5 rounds to -2. Only BigDecimal HALF_UP rounds away from zero.

    12. Common Trap Questions

    Trap 1 — Range off-by-one: "int's range is -2^31 to +2^31." Wrong on both ends' shapes: it is [-2^(31), 2^(31) - 1]. The one-pattern asymmetry exists because zero occupies a pattern. Same shape at 4 bits: [-8, 7].

    Trap 2 — "Integer.MAX_VALUE + 1 throws an exception." No. It silently wraps to Integer.MIN_VALUE. Java only throws through the Math.*Exact methods (an ArithmeticException). This is the single most repeated overflow fact in interviews.

    Trap 3 — "If a number fits in int's range, a float can store it exactly." No. float has a 24-bit mantissa: 16,777,217 (2^24 + 1) is not representable, and 16777217 == 16777216f is true — the int is widened to float and rounded before the comparison.

    Trap 4 — "0.1 + 0.2 != 0.3 is a Java bug; casting or double arithmetic fixes it." No fix exists in binary floating point: 0.1 is not representable exactly at any precision. The fix is BigDecimal from a String (or epsilon comparison), not another cast.

    Trap 5 — "Check for NaN with d == Double.NaN." Never true — NaN is defined unequal to everything, including itself. Use Double.isNaN(d), d != d, or Double.compare(d, Double.NaN) == 0.

    Trap 6 — "Math.round is symmetric: round(2.5) = 3, so round(-2.5) = -3." The second half is false. Math.round is half up (toward +infinity): round(-2.5) = -2, round(-0.5) = 0.

    Trap 7 — "Dividing by zero behaves the same for int and double." Different by design: 1 / 0 throws ArithmeticException, while 1.0 / 0.0 produces Infinity and 0.0 / 0.0 produces NaN.

    13. Points to Remember

    1. Integers use two's complement: negate = invert all bits, then add 1; a value plus its negation is always 0 with no special case.
    2. There is exactly one zero pattern; hence the range for n bits is [-2^(n-1), 2^(n-1) - 1] — the negative side is one larger in magnitude.
    3. int range: -2,147,483,648 to 2,147,483,647. Subtraction is hardware addition: a - b == a + (-b).
    4. Overflow wraps silently: Integer.MAX_VALUE + 1 == Integer.MIN_VALUE; Math.addExact and the *Exact family throw ArithmeticException instead.
    5. ~x == -(x + 1); -1 is all 1s (0xffffffff); the magnitude of a negative is recovered by invert + 1; Math.abs(Integer.MIN_VALUE) is still Integer.MIN_VALUE.
    6. Floating point is IEEE 754: 1 sign bit + biased exponent + mantissa; float is 1-8-23 with bias 127, double is 1-11-52 with bias 1023.
    7. The exponent is stored biased (actual + 127 or + 1023) so a single unsigned field expresses negative exponents.
    8. Binary fractions cannot represent 0.1 exactly; 0.1 + 0.2 == 0.3 is false; money belongs to BigDecimal built from Strings, compared with compareTo.
    9. NaN equals nothing (Double.isNaN to test), infinity absorbs overflow in floating arithmetic, 0.0 == -0.0 is true but Double.compare separates them.
    10. Math.round is half up toward +infinity (round(-2.5) == -2); scientific-notation literals are double by default (Lecture 3); conversion precision loss on int-to-float comparison is a Lecture 5 topic.

    14. Likely Interview Questions

    Question Crisp Answer
    How are negative integers stored in Java? Two's complement: negate = invert bits + 1. The leading 1 of a negative pattern is a consequence, not a sign flag.
    Why two's complement instead of sign-magnitude? One representation of zero, and the plain adder does subtraction as addition of the complement — no extra circuitry.
    What is the exact range of int and why is it asymmetric? [-2,147,483,648, 2,147,483,647] = [-2^31, 2^31 - 1]; zero consumes one pattern, so the negative bound goes one lower.
    What does Integer.MAX_VALUE + 1 print, and why? -2,147,483,648. Silent wraparound (modular two's complement); no exception at runtime.
    How do you detect integer overflow safely? Math.addExact / subtractExact / multiplyExact / negateExact — they throw ArithmeticException on overflow.
    What does ~x evaluate to? -(x + 1), because x + ~x leaves all 1s, which represent -1 in two's complement.
    What does Math.abs(Integer.MIN_VALUE) return? Integer.MIN_VALUE itself: 2^31 does not fit in int, so negation overflows back.
    How is a floating point number stored in memory? IEEE 754: 1 sign bit, biased exponent (8 bits/bias 127 for float; 11 bits/bias 1023 for double), mantissa fraction (23/52 bits).
    Why is the exponent stored biased? A single unsigned field then covers negative and positive exponents, and raw-field ordering matches numeric ordering.
    Why is 0.1 + 0.2 != 0.3? 0.1 is a repeating binary fraction; both stored operands are approximations and their sum misses 0.3's approximation.
    How should money be computed in Java? BigDecimal from String literals, explicit RoundingMode, compareTo for equality — never raw double accumulation.
    How do you test whether a double is NaN? Double.isNaN(x) (or x != x). x == Double.NaN is always false because NaN is unequal to everything.

    15. Final Summary

    integers in memory:   two's complement → negate = invert + 1 → one zero → [-2^(n-1), 2^(n-1) - 1]
overflow:             past the range → wraparound (MAX_VALUE + 1 == MIN_VALUE) → detected by Math.*Exact
bitwise shorthand:    ~x → -(x + 1)  |  -1 → all 1s  |  magnitude of negative → invert + 1
floating in memory:   sign (1) + biased exponent (8/11) + mantissa (23/52) → (-1)^s * 1.m * 2^(e - bias)
specials:             overflow of division → Infinity  |  undefined → NaN (never == NaN)  |  two zeros, one ==, two values
decimals:             binary fractions → 0.1 approximate → 0.1 + 0.2 = 0.300...004 → BigDecimal(String) for money
    • Two's complement → one zero, subtraction-free hardware, wraparound range
    • Floats → sign + biased exponent + mantissa; precision is 24/53 significant bits
    • Approximation → every decimal like 0.1 is inexact in binary; BigDecimal is the exact tool
    • Specials → Infinity and NaN designed in; signed zero equal under ==, distinct under compare
    • Rounding → Math.round is half up toward +infinity; BigDecimal takes an explicit RoundingMode

    Golden rule Integers wrap silently because the encoding is modular; decimals approximate because binary fractions cannot spell most decimal digits. Every surprise in this note follows from those two facts.

    One-line takeaway: negative integers live as "invert and add 1" patterns that wrap like an odometer, and floating point numbers live as approximate powers of two — forget either and the machine quietly decides correctness for you.
