    Part 5 · Collections, Lambdas & Streams · Lecture 39

    Introduction to Java Streams | Creation & Architecture

    17 sections · interview-oriented · both themes

    Scope evidence: "Introduction to Java Streams | Creation & Architecture" (playlist map, verified). Repo evidence: code/Demo.java.

    Collections already give Java a way to store and group data; Streams, added in Java 8, give it a way to describe what to do with that data as a pipeline instead of a loop. A stream is not a container - it is a view over a source that carries values through a chain of operations. This lecture defines what a Stream is and is not, contrasts it with a Collection, lays out the source to intermediate to terminal architecture, catalogs the ways to create a stream, and examines laziness, short-circuiting, single-use behaviour and primitive streams.

    1. What a Stream Is — and What It Is Not

    java.util.stream.Stream<T> is a sequence of elements supporting sequential and parallel aggregate operations. It is declarative: you state the result you want (keep these, transform them, gather them) rather than the index-by-index steps that produce it.

    Five properties define it:

    1. Not a data structure. A stream has no backing array, node or bucket structure of its own; it holds no storage.
    2. Does not store elements. It is a view that pulls values from a source on demand and passes them along the pipeline.
    3. Lazy. Intermediate operations only describe work; nothing executes until a terminal operation runs.
    4. Single-use. Once a terminal operation consumes a stream, the stream is spent; a second terminal call fails.
    5. Can be parallel. The same pipeline can be run sequentially (default) or split across threads with parallel().

    Important A stream is computed, not stored. It is closer to a recipe than to a container: the source keeps the ingredients, the stream describes the dish, and the terminal operation cooks it. (Stream internals and BaseStream are covered further in Lecture 40.)

    2. Stream vs Collection

    Both deal with groups of elements, but they play opposite roles: a Collection stores data, a Stream processes it.

    Aspect Collection Stream
    Storage Stores its elements in memory Does not store elements; a view over a source
    Traversal External iteration (for-each, Iterator) Internal iteration (the library controls the walk)
    Reuse Can be traversed many times Single-use; consumed by one terminal operation
    Laziness Operations execute immediately (eager) Intermediate operations are lazy until the terminal
    Size Usually known (size() is O(1)) May be unknown or infinite; count() consumes it
    Parallelism None of its own; manual threads required parallelStream() and parallel() built in
    Construction A data structure you build and fill A pipeline you construct from a source
    Mutation Mostly mutable (add, remove, set) Structurally immutable; no add or remove of elements
    Computation Data exists at creation Work happens at the terminal operation

    Reading the table: a Collection answers "what do I have?", a Stream answers "what do I want to compute from it?". The stream borrows the collection, computes, and leaves the collection untouched.

    Memory aid — the assembly line: a Collection is the warehouse that stores parts; a Stream is the conveyor belt that transforms them as they pass. The belt holds nothing between stations.

    3. The Pipeline Architecture: Source, Intermediate, Terminal

    Every stream program has the same three-part shape:

    source (create) --> intermediate ops (zero or more, lazy) --> terminal op (exactly one, runs)
   collection          filter, map, sorted, limit              collect, forEach, reduce, count
    1. Source. Where the elements come from: a collection, an array, a generator, a file, a range. Creation is covered in Section 4.
    2. Intermediate operations. Zero or more lazy stages such as filter, map or sorted. Each returns a new Stream, which is why they can be chained.
    3. Terminal operation. Exactly one operation such as collect, forEach or reduce. It consumes the stream, triggers the whole pipeline and produces a result (or void).

    The critical rule: nothing in the pipeline runs until the terminal operation is invoked. Without a terminal, the chain is a description that never executes.

    // Demo.java - source, two lazy intermediates, one terminal
import java.util.*;
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        List<String> names = List.of("Ann", "Bob", "Amy", "Carl");
        List<String> upper = names.stream()          // source
                .filter(n -> n.startsWith("A"))      // intermediate: lazy
                .map(String::toUpperCase)            // intermediate: lazy
                .collect(Collectors.toList());       // terminal: triggers the work
        System.out.println(upper);                   // [ANN, AMY]
    }
}

    Removing the collect line compiles but prints nothing - the filter and map never fire.

    4. Creating Streams

    A stream is always obtained from a source. The standard factories:

    Creation call Source kind Notes
    collection.stream() Collection Every Collection implements this.
    Arrays.stream(array) Array Works for object and primitive arrays.
    Stream.of(a, b, c) Literals / varargs Convenient for fixed values.
    Stream.iterate(seed, f) Infinite, ordered Java 8; each value derived from the previous.
    Stream.iterate(seed, pred, f) Bounded Java 9 three-arg form; stops when pred is false.
    Stream.generate(supplier) Infinite, unordered Each value from a Supplier.
    IntStream.range(a, b) Primitive range a inclusive, b exclusive.
    IntStream.rangeClosed(a, b) Primitive range Both ends inclusive.
    Stream.builder() Builder Add elements, then call build().
    Files.lines(path) File Lazy lines; close with try-with-resources.
    Stream.empty() Empty A stream with no elements.
    new Random().ints() Infinite random Primitive random values. 
    // Demo.java - a few of the creation sources side by side
import java.util.*;
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        Stream<String> a = Arrays.stream(new String[]{"x", "y"});
        Stream<String> b = Stream.of("x", "y");
        Stream<String> c = List.of("x", "y").stream();
        Stream<Integer> d = new Random().ints(1, 100).limit(3).boxed();
        System.out.println(a.count() + b.count() + c.count() + d.count()); // 9
    }
}

    Files.lines is the one source that owns an OS resource: it must be closed, so wrap it in try-with-resources.

    5. Intermediate Operations — The Lazy Stage

    Intermediate operations transform one stream into another and are lazy. They fall into a handful of families. The full treatment is Lecture 40; this is the map.

    Operation Purpose Nature
    filter(Predicate) Keep only matching elements Stateless
    map(Function) One-to-one transform Stateless
    mapToInt / mapToLong / mapToDouble Convert to a primitive stream Stateless
    flatMap(Function) One-to-many, then flatten to one stream Stateless
    distinct() Remove duplicates Stateful
    sorted() Sort by natural order or a comparator Stateful
    limit(n) Truncate to at most n elements Stateful, short-circuiting
    skip(n) Drop the first n elements Stateful
    peek(Consumer) Observe each element (debugging) Stateless
    takeWhile(p) Take while p is true (Java 9) Stateful, short-circuiting
    dropWhile(p) Drop while p is true (Java 9) Stateful

    Interviewer's perspective If asked "when does a stream actually do something?", the precise answer is: intermediate operations only build the pipeline; the work begins at the terminal operation and may stop early if a short-circuiting operation is present. Naming flatMap as the fix for a stream of streams is the detail that shows real use.

    6. Terminal Operations — The One That Runs the Pipeline

    A terminal operation consumes the stream and yields a result. There can be exactly one per stream. Full detail is Lecture 40.

    Terminal operation Returns Purpose
    forEach(Consumer) void Act on each element
    collect(Collector) A result container Mutable reduction into a list, set, map
    reduce(...) Optional or value Fold the elements to one value
    count() long Number of elements
    min / max Optional Extremes by a comparator
    findFirst() Optional First element
    findAny() Optional Any element (parallel-friendly)
    anyMatch / allMatch / noneMatch boolean Predicate testing
    toArray() Array Materialize the elements

    Rules to remember: collect and reduce are reductions that build a result; forEach is for side effects only; count, findFirst and the match operations can stop early.

    7. Primitive Streams: IntStream, LongStream, DoubleStream

    A Stream<Integer> boxes every element, which allocates. Java provides three primitive specializations that store raw int, long and double values and therefore avoid boxing.

    Method Direction Effect
    mapToInt / mapToLong / mapToDouble Object stream to primitive Unbox into a primitive stream
    mapToObj Primitive to object stream Convert back to Stream<U>
    boxed() Primitive to object stream Explicitly box to Stream<Integer>
    sum() Terminal Sum of the elements
    average() Terminal Mean as OptionalDouble
    max() Terminal Largest as OptionalInt
    range(a, b) / rangeClosed(a, b) Factory Numeric range source 
    // Demo.java - primitive streams avoid boxing and add numeric aggregates
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        int sum = IntStream.rangeClosed(1, 5).sum();            // 15
        double avg = IntStream.range(1, 5).average().orElse(0); // (1+2+3+4)/4 = 2.5
        System.out.println(sum + " " + avg);                    // 15 2.5
    }
}

    Important sum(), average() and max() exist only on primitive streams. On a Stream<Integer> you must call mapToInt(...) first; that single conversion is what removes the boxing cost.

    8. Stateless vs Stateful Intermediate Operations

    An intermediate operation is stateless if each element can be processed independently, and stateful if it must remember something about other elements seen so far.

    Aspect Stateless Stateful
    Examples filter, map, flatMap, peek sorted, distinct, limit, skip, takeWhile
    Per-element state None Must track seen elements or a count
    Parallel behaviour Any element can be handled on any thread May need a barrier or buffering to coordinate
    Infinite streams Safe when combined with a short-circuit sorted and distinct may never finish
    Memory Constant (O(1)) Can be O(n) because elements are buffered

    Reading the table: stateless operations preserve the element-by-element, lazy model; stateful operations break it because they must see multiple elements before emitting one. That is why chaining filter and map before sorted is the usual and most efficient order.

    9. Lazy Evaluation and Short-Circuiting

    Laziness is what makes infinite streams safe. Stream.iterate and Stream.generate can produce endless values, but because the pipeline is lazy and some operations short-circuit, only as many elements as needed are ever produced. A terminal operation is still required to trigger even that.

    // Demo.java - an infinite stream is safe because limit short-circuits
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        long count = Stream.iterate(1, n -> n + 1)   // infinite: 1, 2, 3, ...
                .skip(5)                             // drop 1..5 -> 6, 7, 8, ...
                .limit(3)                            // take 6, 7, 8
                .count();                            // terminal: runs the pipeline
        System.out.println(count);                   // 3
    }
}

    The short-circuiting operations are limit, findFirst, findAny, anyMatch, allMatch, noneMatch, takeWhile and dropWhile. An infinite stream feeding a stateful operation such as sorted with no bound will never terminate.

    Memory aid — the tap: the source is an endless water main; limit is the tap that lets through only three cups. Without a terminal operation, nobody opens the tap at all.

    10. A Stream Is Single-Use

    A stream is not reusable. The moment a terminal operation consumes it, the stream is closed, and any second attempt fails with IllegalStateException.

    // Demo.java - reusing a consumed stream throws
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        Stream<String> s = Stream.of("a", "b", "c");
        s.forEach(System.out::println);   // first terminal: consumes the stream
        s.forEach(System.out::println);   // IllegalStateException: stream has already been operated upon or closed
    }
}

    The fix is always to obtain a fresh stream from the source: call list.stream() again for each pass. This is the single most common stream bug and is examined again in Section 12.

    11. Parallel Streams: A First Look

    A pipeline can run in parallel by calling collection.parallelStream() or .parallel() on an existing stream. The work is split by a Spliterator (introduced in Lecture 30) and executed across the common Fork-Join pool.

    list.parallelStream().filter(...).map(...).collect(...)   // same pipeline, split across threads

    Parallelism changes execution, not the operations: the program is unchanged, only the thread that runs each element differs. It is not automatically faster, and it must never be used with stateful lambdas that mutate shared data. This is a teaser only; the full treatment belongs to Lecture 42.

    Important Prefer sequential streams by default. Parallelism pays off only for large data sets, CPU-bound work and operations that are genuinely independent.

    12. Common Pitfalls and Errors

    Pitfall What happens Fix
    Reusing a consumed stream IllegalStateException Obtain a new stream from the source each time
    Forgetting the terminal operation Nothing runs; no output, no error Always finish with collect, forEach, count, etc.
    Side effects in forEach Hard to test and unsafe in parallel Prefer collect / reduce to build a result
    Streams for a trivial loop Extra machinery for no gain Keep a plain for-loop for simple iteration
    map returning a stream A stream of streams, not flat data Use flatMap instead of map
    Infinite stream without short-circuit Program hangs, never completes Add limit, findFirst, anyMatch or takeWhile
    Boxing in primitive pipelines Unnecessary allocation Use mapToInt and primitive streams
    Assuming order Results vary with source and parallelism Use sorted() or an ordered source
    Mutating the source during the pipeline Undefined results or ConcurrentModificationException Do not modify the backing collection while streaming

    13. Myth vs Reality

    Myth Reality
    "A Stream is a new kind of collection." A stream is not a data structure; it stores no elements, it is a view over a source.
    "Streams are always faster than loops." Speed is often comparable; the real gains are readability and built-in parallelism.
    "The pipeline runs as each operation is written." Intermediate operations are lazy; only the terminal operation triggers execution.
    "A stream can be reused like a collection." A stream is single-use; a second terminal operation throws IllegalStateException.
    "Streams modify their source." Streams are non-mutating; they produce a new result and leave the source untouched.

    14. Common Trap Questions

    Trap 1 — Is a Stream a container? No. It does not store elements. It is a pipeline view over a source, closer to an iterator than to a List.

    Trap 2 — Does calling filter or map execute anything? No. Intermediate operations are lazy descriptions; execution begins only at the terminal operation.

    Trap 3 — Can the same stream be traversed twice? No. A stream is single-use; the second terminal operation throws IllegalStateException, and the fix is to create a fresh stream.

    Trap 4 — Does an infinite stream hang immediately? No. Because intermediate operations are lazy and short-circuiting operations exist, Stream.iterate(...).limit(...) is perfectly safe; a terminal operation is still required to start it.

    Trap 5 — Do intermediate operations change the original collection? No. The source is untouched; streams never mutate the collection they read from.

    Trap 6 — Is IntStream simply a Stream<Integer>? No. It is a primitive specialization that stores raw int values and avoids boxing; mapToObj or boxed() converts it back.

    15. Points to Remember

    1. A Stream is a declarative pipeline over a sequence of elements; it is not a data structure and stores no elements.
    2. A Collection stores data; a Stream processes data using internal iteration.
    3. Every stream program has the shape source to intermediate operations to exactly one terminal operation.
    4. Intermediate operations are lazy; nothing executes until the terminal operation runs.
    5. Intermediate operations return new streams, which is what allows chaining.
    6. Common creation sources: stream(), Arrays.stream, Stream.of, iterate, generate, IntStream.range, builder, Files.lines.
    7. Stateless operations (filter, map) process elements independently; stateful operations (sorted, distinct, limit) must track state.
    8. Laziness plus short-circuiting (limit, findFirst, anyMatch) makes infinite streams safe to use.
    9. A stream is single-use; consuming it twice throws IllegalStateException.
    10. IntStream, LongStream and DoubleStream avoid boxing and provide sum, average and max; parallel() splits the work across threads (Lecture 42).

    16. Likely Interview Questions

    Question Crisp Answer
    What is a Stream in Java? A sequence of elements supporting sequential and parallel aggregate operations, added in Java 8 as a declarative processing pipeline.
    Is a Stream a data structure? No. It stores no elements; it is a view that pulls values from a source on demand.
    Collection vs Stream? A Collection stores elements and is reusable; a Stream processes elements, is lazy and is single-use.
    When does a stream execute? Only when the terminal operation is invoked; intermediate operations are lazy.
    What are the three parts of a stream pipeline? Source, zero or more intermediate operations, and exactly one terminal operation.
    Name common stream-creation methods. collection.stream(), Arrays.stream(...), Stream.of(...), Stream.iterate, Stream.generate, IntStream.range, Stream.builder, Files.lines.
    Can a stream be reused? No. After a terminal operation it is consumed; reuse throws IllegalStateException.
    What is a stateless vs stateful intermediate operation? Stateless ones (filter, map) process each element independently; stateful ones (sorted, distinct, limit) must remember other elements.
    Are infinite streams safe? Yes, if the pipeline has a short-circuit (limit, findFirst, anyMatch) that stops production early; a terminal op is still needed.
    Why primitive streams? IntStream, LongStream and DoubleStream avoid boxing and add sum, average and max.
    How do you convert an object stream to an IntStream? Call mapToInt; use mapToObj or boxed() to convert back.
    How do you make a stream parallel? Call parallelStream() on a collection or .parallel() on a stream; the same pipeline then runs across threads.

    17. Final Summary

    source (collection / array / generator / file)
        --> intermediate ops (filter, map, sorted, limit)   [lazy, zero or more]
        --> terminal op (collect, forEach, reduce, count)   [runs the whole pipeline, exactly one]
    • A Stream → declarative, non-storing view over a source; not a data structure
    • Collection vs Stream → stores vs processes; reusable vs single-use
    • Pipeline → source → intermediate (lazy) → terminal (triggers)
    • Creation → stream, Arrays.stream, Stream.of, iterate, generate, IntStream.range, builder, Files.lines
    • Intermediate → filter/map/flatMap stateless; sorted/distinct/limit stateful
    • Laziness → infinite streams are safe with short-circuiting operations
    • Single-use → consuming a consumed stream throws IllegalStateException
    • Primitive streams → IntStream, LongStream, DoubleStream avoid boxing
    • Parallel → parallelStream() and parallel() (Lecture 42)

    Golden rule Use a Collection to store data and a Stream to compute from it; build the pipeline with lazy intermediate operations and run it with exactly one terminal operation, then throw the stream away.

    One-line takeaway: a Stream is a lazy, single-use pipeline that flows elements from a source through intermediate operations into a terminal operation - it computes over data, it does not store it.
