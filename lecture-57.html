    Part 7 · Concurrency · Lecture 57

    CompletableFuture, Fork-Join Pool, ThreadLocal & Virtual Threads

    27 sections · interview-oriented · both themes

    Scope evidence: "CompletableFuture, ForkJoinPool and Virtual Threads in Java" plus the lecture's own repo notes (each tool solves a different problem), playlist map, verified. Repo evidence: notes.pdf only.

    Java ships several concurrency tools, and their real value is not in their method names but in the distinct problems they solve: Future represents the eventual result of one asynchronous task, CompletableFuture lets asynchronous operations be chained, transformed and combined, ForkJoinPool is built for divide-and-conquer computations, and virtual threads make thread-per-task programming practical when there are large numbers of blocking operations. This lecture revisits Future, builds the full CompletableFuture pipeline model, explains the fork-join work-stealing engine, covers ThreadLocal and its request-context role, and closes with virtual threads. The governing idea, stated in the notes themselves, is that understanding the distinction between these tools matters more than memorising their methods.

    1. Four Concurrency Tools, Four Different Problems

    The lecture opens by mapping each tool to the problem it was designed to solve. Reusing one tool for another tool's job is the most common source of concurrency confusion.

    Tool Problem it solves Core idea
    Future<T> Represent the eventual completion of one asynchronous task A placeholder returned by submit()
    CompletableFuture<T> Chain, transform and combine asynchronous operations Composable completion stages
    ForkJoinPool Parallelise a divisible, CPU-bound computation Divide and conquer with work stealing
    Virtual threads Handle many concurrent blocking tasks cheaply Many virtual threads over few carrier threads

    Memory aid Result that arrives later → Future; pipeline around completion → CompletableFuture; divisible CPU-bound work → ForkJoinPool; many waiting tasks → virtual threads.

    2. Future, Revisited — What a Future Represents

    A Future<T> represents the pending result of an asynchronous task. The lifecycle is simple: the task is submitted now, it executes separately, its result may become available later, and the Future represents that pending result in the meantime.

    // FutureDemo.java — submit an asynchronous task and read its result later
import java.util.concurrent.*;

public class FutureDemo {
    public static void main(String[] args)
            throws InterruptedException, ExecutionException {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        Future<Integer> future = executor.submit(() -> 50);

        // Independent work can happen here before the result is required
        Integer result = future.get();
        System.out.println("Result: " + result);
        executor.shutdown();
    }
}

    The task may still be running when submit() returns. The returned Future gives the caller a way to wait for the result, check whether the task has completed, cancel the task, and observe an exception raised by the task.

    3. The Three Common Forms of submit()

    ExecutorService.submit() returns a Future in three common shapes.

    1. Submit a Callable — use it when the task must return a value. The value is later retrieved with future.get().
    2. Submit a Runnable — it returns no value, but submit() still returns a Future<?>. After successful completion, future.get() returns null.
    3. Submit a Runnable with a predefined result — a result can be supplied separately while submitting a Runnable. The Runnable still returns nothing, but the executor returns the predefined value after successful completion.
    Future<String> future = executor.submit(
        () -> System.out.println("Task running"),
        "SUCCESS"
);                       // future.get() -> "SUCCESS"

    A Future can be used to track completion, failure and cancellation regardless of which form produced it.

    4. Core Methods of Future

    • get() is a blocking operation. If the result is ready it returns immediately; if not, the calling thread waits. It can throw InterruptedException (the waiting thread was interrupted), ExecutionException (the task failed — the original exception is available through exception.getCause()), or CancellationException (the task was cancelled before its result could be returned).
    • get(timeout, unit) waits only for the specified duration, throwing TimeoutException if the task does not complete in time. A timeout prevents the calling thread from waiting indefinitely.
    • isDone() is non-blocking and reports whether the task has reached a terminal state — successful completion, exceptional completion or cancellation. Therefore isDone() == true does not necessarily mean the task succeeded.
    • cancel(boolean mayInterruptIfRunning) is a request, not a guaranteed forceful termination. If the task has not started, cancellation can prevent it from starting. If it is already running, the argument controls whether interruption may be attempted; for interruption to stop a running task, the task must cooperate (while (!Thread.currentThread().isInterrupted())).
    • isCancelled() reports whether the task was cancelled before completing normally.
    Method Behaviour
    isDone() Performs a non-blocking status check
    get() Waits when the result is not ready
    isCancelled() Checks whether cancellation occurred

    Important isDone() asks "has execution finished in any way?" while get() asks "give me the result, or report failure/cancellation". A failed task reports isDone() == true and then get() throws ExecutionException.

    5. Why Future Is Not Enough

    A traditional Future only lets the caller wait, poll, cancel and retrieve. It does not directly provide a fluent way to declare: when this task completes, transform its result, run another operation, combine it with another result, and handle failure. That gap pushes callers toward blocking code such as Integer result = future.get(); between every step.

    CompletableFuture<T> implements both Future<T> and CompletionStage<T>. This gives it two roles: as a Future it represents a pending result, and as a CompletionStage it represents one stage in a larger asynchronous pipeline. The result of one stage can automatically trigger another, so the caller does not have to block between every step.

    Fetch data → Transform data → Validate data → Save data → Send response

    6. Creating a CompletableFuture

    runAsync() is used when the task does not return a value; its result type is CompletableFuture<Void>. supplyAsync() is used when the task returns a value.

    Method Functional interface Result
    runAsync() Runnable No value (CompletableFuture<Void>)
    supplyAsync() Supplier<T> Returns a value

    A future can also be created already completed with CompletableFuture.completedFuture(value), useful for tests and for short-circuiting a stage that needs no asynchronous work.

    When no executor is supplied, asynchronous CompletableFuture methods normally use ForkJoinPool.commonPool(). A custom executor can be supplied explicitly with supplyAsync(supplier, executor). Using a custom executor is useful when the common pool should not be shared with the workload, when a specific concurrency limit is needed, when tasks perform blocking I/O, when thread naming or monitoring is required, or when different task categories need isolation.

    7. Chaining Completion Stages

    Each chaining method answers a slightly different question.

    • thenApply() receives the previous result and returns a transformed value; it behaves like a Function<T,R>. Type transformation is possible (for example CompletableFuture<Integer> becomes CompletableFuture<String>).
    • thenAccept() receives the previous result but produces no new value; it behaves like a Consumer<T>. It is used to print, save, send a notification or write to an external system.
    • thenRun() does not receive the previous result and does not return a new value. Use it when only completion matters.
    • thenCompose() flattens a dependency where the next stage is itself asynchronous: a function returning CompletableFuture<R> is joined into a single stage rather than nested. Use it instead of thenApply() whenever the mapping function itself returns a CompletableFuture.
    Method Receives previous result? Produces a new result? Main purpose
    thenApply() Yes Yes Transform
    thenAccept() Yes No Consume
    thenRun() No No Run after completion

    8. Sync vs Async Continuations

    A non-Async continuation does not promise a new thread. It may run in the thread that completes the previous stage, or in the thread attaching the continuation if the stage is already complete. Therefore the statement "thenApply() always runs in the same thread" is incorrect. The accurate rule is: a non-Async stage may run in a thread involved in completing or registering the stage.

    An Async continuation schedules the continuation using the stage's default asynchronous executor, which for a normal CompletableFuture is usually the common ForkJoin pool. A specific executor can also be provided with thenApplyAsync(fn, executor).

    Version Execution policy
    thenApply() May execute in a thread involved in completion
    thenApplyAsync() Scheduled using the default async executor
    thenApplyAsync(fn, executor) Scheduled using the supplied executor

    The same pattern exists for thenAccept()/thenAcceptAsync() and thenRun()/thenRunAsync().

    Interviewer's perspective "Does thenApply guarantee a new thread?" No. Only the Async variants guarantee scheduling on an executor; the plain variants may run on whichever thread completes or attaches the stage.

    9. Combining Futures: thenCombine, allOf, anyOf

    thenCombine() combines the successful results of two independent futures. The combining function runs after both stages complete normally — the two independent operations can run concurrently while the caller waits on the combined stage.

    // CombineDemo.java — wait for many independent futures with allOf
import java.util.concurrent.*;

public class CombineDemo {
    static String fetchUser()    { return "User"; }
    static String fetchOrders()  { return "Orders"; }
    static String fetchInvoice() { return "Invoice"; }

    public static void main(String[] args) {
        CompletableFuture<String> user =
                CompletableFuture.supplyAsync(CombineDemo::fetchUser);
        CompletableFuture<String> orders =
                CompletableFuture.supplyAsync(CombineDemo::fetchOrders);
        CompletableFuture<String> invoice =
                CompletableFuture.supplyAsync(CombineDemo::fetchInvoice);

        CompletableFuture<Void> all =
                CompletableFuture.allOf(user, orders, invoice);

        CompletableFuture<String> report = all.thenApply(ignored ->
                user.join() + " | " + orders.join() + " | " + invoice.join());
        System.out.println(report.join());
    }
}

    allOf() completes when every supplied future completes; the individual results are then read from the component futures. anyOf() completes when the first future completes and returns that result. thenCombine() is for exactly two futures, allOf/anyOf for many.

    10. Handling Completion and Failure

    • exceptionally() provides a recovery value when a previous stage fails; it is similar to a fallback operation and runs only on failure.
    • whenComplete() observes success or failure without normally changing the result. It is used for logging, metrics, cleanup and observing the final outcome.
    • handle() receives both the result and the exception and can produce a new result in either case, so it transforms both the success and failure paths.
    // PipelineDemo.java — a chain with a failure-recovery stage
import java.util.concurrent.*;

public class PipelineDemo {
    static String loadUser() { return "harshita"; }

    static String enrich(String user) {
        if (user.isEmpty()) {
            throw new RuntimeException("Empty user");
        }
        return user + "@example.com";
    }

    public static void main(String[] args) {
        CompletableFuture<Void> pipeline =
                CompletableFuture
                        .supplyAsync(PipelineDemo::loadUser)
                        .thenApply(String::toUpperCase)
                        .thenApply(PipelineDemo::enrich)
                        .exceptionally(exception -> {
                            System.out.println(
                                    "Recovering: " + exception.getMessage());
                            return "FALLBACK";
                        })
                        .thenAccept(result ->
                                System.out.println("Result: " + result));

        pipeline.join();
    }
}
    Method Runs on success Runs on failure Can transform result
    exceptionally() No Yes Yes
    whenComplete() Yes Yes Normally observes only
    handle() Yes Yes Yes

    11. Blocking vs Non-Blocking Composition

    A CompletableFuture can still be waited on. get() and join() both block when the result is not ready; the main difference is exception handling. get() wraps failures in the checked ExecutionException (and requires handling InterruptedException), while join() uses the unchecked CompletionException.

    Method Failure wrapper
    get() ExecutionException (checked)
    join() CompletionException (unchecked)

    Avoid blocking between every stage — firstResult = firstFuture.get(); secondResult = secondFuture.get(); total = firstResult + secondResult; defeats the purpose of composition. Prefer declaring the relationship with firstFuture.thenCombine(secondFuture, Integer::sum) so the pipeline proceeds automatically.

    Three design points matter:

    1. Asynchronous does not mean non-blocking work. A task is asynchronous when the caller does not execute the work directly, but the worker thread executing it may still block during a database call. Asynchronous and non-blocking are different ideas.
    2. Be careful with blocking work in the common pool. The common ForkJoin pool is shared by different APIs and components; long blocking operations can occupy its workers and reduce progress for unrelated tasks. For blocking I/O, consider a dedicated executor, a bounded I/O pool, or virtual threads.
    3. Do not ignore the final stage. In a short main() method the JVM may terminate before asynchronous work visibly finishes; for demonstrations, wait with pipeline.join(). In server applications the lifecycle normally stays active independently.

    12. ForkJoinPool: Divide-and-Conquer Parallelism

    A normal thread pool works well when independent tasks are submitted to a shared executor: workers take tasks from a queue and execute them. Some computations instead have a recursive structure — a large problem splits into smaller problems, each smaller problem splits again, and all partial results are combined. Summing a large array, merge sort, recursive search, image processing, tree traversal and mathematical divide-and-conquer algorithms are examples. ForkJoinPool is designed for this pattern.

    The strategy is:

    1. Check whether the problem is small enough.
    2. If yes, solve it directly.
    3. Otherwise, split it into subtasks.
    4. Execute subtasks in parallel.
    5. Combine their results.

    This requires a threshold: a problem size <= threshold is solved directly, while a size above it is split again. Without a threshold, recursive splitting would continue unnecessarily and create excessive overhead — too small creates too many tasks, too large reduces parallelism.

    13. Fork, Join and Work Stealing

    Fork schedules a subtask for asynchronous execution (leftTask.fork()); join waits for a subtask to finish and obtains its result (leftTask.join()). In a divide-and-conquer computation different workers may generate different amounts of work: one worker may have many pending subtasks while another finishes early. Leaving the idle worker waiting wastes available CPU.

    ForkJoinPool workers maintain worker-local queues. A worker generally processes tasks from its own queue; when it runs out of work it looks for work in another worker's queue, steals an available task, and both workers continue processing. This is work stealing, and it balances irregular recursive workloads without requiring every worker to compete constantly for one central queue.

    Main task submitted → splits into subtasks → subtasks enter worker-local queues
→ worker starts computation → idle workers steal available subtasks
→ small tasks are solved directly → partial results are joined → final result returned
    Method Purpose
    pool.invoke(task) Submit a top-level task and wait for its result
    task.fork() Schedule a subtask asynchronously
    task.join() Wait for a subtask and obtain its result
    task.compute() Execute the task logic directly in the current worker

    14. ForkJoinTask Types and a Parallel Sum

    RecursiveTask<V> is used when the computation returns a result; RecursiveAction is used when it does not. Both extend ForkJoinTask.

    Type Result
    RecursiveTask<V> Returns a value
    RecursiveAction Returns no value 
    // ForkJoinDemo.java — sum an array in parallel with RecursiveTask
import java.util.concurrent.*;

class SumTask extends RecursiveTask<Integer> {
    private static final int THRESHOLD = 2;
    private final int[] numbers;
    private final int start;
    private final int end;

    SumTask(int[] numbers, int start, int end) {
        this.numbers = numbers;
        this.start = start;
        this.end = end;
    }

    @Override
    protected Integer compute() {
        int length = end - start;
        if (length <= THRESHOLD) {
            return calculateDirectly();
        }
        int middle = start + length / 2;
        SumTask leftTask  = new SumTask(numbers, start, middle);
        SumTask rightTask = new SumTask(numbers, middle, end);
        leftTask.fork();
        int rightResult = rightTask.compute();
        int leftResult  = leftTask.join();
        return leftResult + rightResult;
    }

    private int calculateDirectly() {
        int sum = 0;
        for (int i = start; i < end; i++) {
            sum += numbers[i];
        }
        return sum;
    }
}

public class ForkJoinDemo {
    public static void main(String[] args) {
        int[] numbers = {1, 2, 3, 4, 5, 6, 7, 8};
        ForkJoinPool pool = new ForkJoinPool();
        SumTask task = new SumTask(numbers, 0, numbers.length);
        int result = pool.invoke(task);
        System.out.println("Final sum: " + result);
        pool.shutdown();
    }
}

    The base case (length <= THRESHOLD) prevents further splitting when the problem becomes small. The standard fork-join pattern forks one subtask, directly computes the other with compute(), then joins the forked task and combines both results. This is generally better than immediately forking both tasks and waiting, because it keeps the current worker productive and reduces scheduling overhead.

    15. The Common Pool and When to Use ForkJoinPool

    Java maintains a shared pool, ForkJoinPool.commonPool(), used by many CompletableFuture async methods, parallel streams, and ForkJoinTask.fork() when called outside another ForkJoinPool. Because it is shared, long-running blocking tasks should not occupy it carelessly. A work-stealing executor can also be created with Executors.newWorkStealingPool() (optionally with a target parallelism, newWorkStealingPool(4)); it is useful for many small independent or recursively generated tasks but does not guarantee task execution order.

    ForkJoinPool is best suited to workloads that are CPU-bound, divisible into independent subtasks, recursive or naturally decomposable, composed of many relatively small computations, and capable of combining partial results. It is usually not the best choice when tasks spend most of their time waiting for network I/O, block on database calls, hold locks for long durations, depend heavily on task ordering, or cannot be divided into independent computations. Blocking a worker can reduce the pool's ability to process other tasks — for blocking workloads a dedicated executor or virtual threads are often more appropriate.

    Golden rule ForkJoinPool is a CPU-bound divide-and-conquer engine, not a universal executor. Do not park its workers on blocking I/O.

    16. ThreadLocal: A Separate Value Per Thread

    A ThreadLocal<T> associates a separate value with each thread. One ThreadLocal object is shared, but every thread sees its own stored value — for example, thread 1 sees userName = "Harshita" while thread 2 sees userName = "Aditya". The three core operations are get() (read the current thread's value), set(value) (store it) and remove() (erase it).

    A normal local variable is ideal when the value is needed inside one method or can be passed explicitly. ThreadLocal becomes useful when contextual information must be available across several method calls without being passed through every method — request identifiers, tracing information, security context, transaction context or tenant information flowing from Controller to Service to Repository. Because this creates hidden data flow, it must be used carefully.

    ThreadLocal.withInitial(supplier) provides a default value so get() never returns null for an unset thread.

    17. ThreadLocal in Pools: Leaks and remove()

    Worker threads in a pool are reused: Task A uses worker 1, Task A completes, and Task B later uses worker 1. If Task A leaves a ThreadLocal value behind, Task B may observe stale data — and because the worker thread is long-lived, the value also stays reachable and cannot be collected. Values must always be cleaned up in a finally block.

    // RequestContextDemo.java — always remove() in a finally block
public class RequestContextDemo {
    private static final ThreadLocal<String> REQUEST_ID =
            new ThreadLocal<>();

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            REQUEST_ID.set("REQ-" + Thread.currentThread().getName());
            try {
                System.out.println(
                        Thread.currentThread().getName()
                                + " -> " + REQUEST_ID.get());
            } finally {
                REQUEST_ID.remove();
            }
        };

        Thread first  = new Thread(task, "Thread-1");
        Thread second = new Thread(task, "Thread-2");
        first.start();
        second.start();
        first.join();
        second.join();
    }
}

    Important CONTEXT.set(value); try { performWork(); } finally { CONTEXT.remove(); } — cleanup is not optional on pooled threads.

    Two related facts belong here. InheritableThreadLocal passes the parent thread's value to a child thread created afterwards, but this caveat matters: inheritance happens at thread creation, so it is unreliable with reused pool threads and is not the mechanism for propagating context across a virtual-thread-per-task executor. Java's forward-looking alternative is ScopedValue (preview), which binds an immutable value for a bounded scope, is inherited naturally by child scopes and structured-concurrency subtasks, and needs no remove().

    18. Platform Threads vs Virtual Threads

    Traditional Java threads are called platform threads. They are typically mapped closely to operating-system threads: Java platform thread → operating-system thread → CPU. Operating-system threads are relatively expensive resources, so a server that creates one platform thread for every concurrent blocking request may eventually face high memory consumption, thread-creation overhead, excessive context switching and operating-system thread limits.

    Consider a server request: receive request → call database → wait for database → call another API → wait for response → return result. The thread may spend most of its lifetime waiting rather than using the CPU. With platform threads, high concurrency requires many operating-system threads merely to represent all those waiting tasks; virtual threads reduce the cost of representing that concurrency.

    Aspect Platform threads Virtual threads
    Backing Closely mapped to OS threads Scheduled by the JVM over carrier threads
    Cost per thread Relatively expensive Very cheap
    Pooling Often pooled to avoid creation cost Not pooled; one new thread per task
    Best for Moderate concurrency, CPU-bound work High-concurrency blocking work
    Blocking cost Occupies an OS thread while blocked Normally unmounts and releases the carrier
    Default count Bounded by OS thread limits Can be millions, limited by memory

    19. What Is a Virtual Thread: Mount, Unmount, Carrier

    A virtual thread is a lightweight Java thread scheduled by the Java runtime rather than directly by the operating system: virtual threads → JVM scheduler → carrier platform threads → operating system and CPU. Many virtual threads can be scheduled over a much smaller number of platform threads. The platform thread temporarily running a virtual thread is called its carrier thread.

    When a virtual thread is ready it is mounted on a carrier and executes Java code. When it reaches a supported blocking operation such as waiting for I/O, the runtime can normally unmount it: the carrier becomes available and another virtual thread can run. When the operation becomes ready, the virtual thread later resumes on the same or a different carrier. Application code still sees the virtual thread — Thread.currentThread() returns the virtual thread, not the carrier. Thread.currentThread().isVirtual() reports true inside a virtual thread.

    Virtual threads do not create more CPU. They improve scalability for tasks that spend significant time waiting; a CPU-bound task remains limited by available CPU. Creating thousands of virtual threads for a CPU-intensive calculation does not make the CPU execute thousands of calculations simultaneously. For CPU-bound divide-and-conquer work, ForkJoinPool is generally more suitable.

    20. Creating Virtual Threads and the Per-Task Executor

    Virtual threads became a permanent Java feature in Java 21, so the following APIs can be used without preview features: Thread.ofVirtual(), Thread.startVirtualThread(...), and Executors.newVirtualThreadPerTaskExecutor(). Thread.startVirtualThread(task) creates and starts a virtual thread and is equivalent to Thread.ofVirtual().start(task). The builder also supports .name("order-task") and .unstarted(task) followed by thread.start().

    Executors.newVirtualThreadPerTaskExecutor() starts a new virtual thread for each submitted task. It is not a traditional thread pool — virtual threads are cheap enough that each task receives its own thread, and the executor does not reuse virtual threads after tasks finish.

    // VirtualThreadExecutorDemo.java — one virtual thread per task
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class VirtualThreadExecutorDemo {
    public static void main(String[] args) {
        try (ExecutorService executor =
                     Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 1; i <= 5; i++) {
                int taskId = i;
                executor.submit(() ->
                        System.out.println(
                                "Task " + taskId +
                                        " executed by " +
                                        Thread.currentThread()));
            }
        }
    }
}

    The try-with-resources block closes the executor and waits for submitted tasks to finish. A blocking-I/O example can submit ten thousand tasks that each Thread.sleep(Duration.ofSeconds(1)); while a virtual thread waits, its carrier can normally execute another virtual thread, so the whole set completes in roughly one second rather than ten thousand.

    21. Virtual Threads Are Not a License for Unlimited Work

    Virtual threads work especially well for web requests, REST API calls, database operations, file and network I/O, blocking queues, message processing, request-per-thread server designs and workloads with many concurrent waiting tasks. They allow straightforward blocking code to scale without expressing every operation as a callback chain. They do not provide a major advantage when work is long-running and CPU-intensive, dominated by calculations rather than waiting, limited by a small downstream resource, or already naturally handled as data parallelism (video encoding, image rendering, large numerical computations, encryption, recursive array processing).

    • Threads may be cheap, dependencies are not. Even when virtual threads are inexpensive, the resources they use may remain limited: database connection pools, external API rate limits, memory, file descriptors, sockets and downstream service capacity. Creating 100,000 virtual threads does not safely create 100,000 database connections; concurrency should be limited around the scarce resource, for example with new Semaphore(50). Virtual threads make waiting threads cheap, not every system limit disappear.
    • Do not pool virtual threads. With platform threads, pooling avoids expensive creation; with virtual threads the intended model is one task → one new virtual thread → the thread terminates with the task. Do not build a small fixed pool of virtual threads; use Executors.newVirtualThreadPerTaskExecutor() and limit the constrained resource instead.
    • Virtual threads and synchronized. Modern JDKs have reduced important sources of virtual-thread pinning, including monitor-related improvements introduced after virtual threads first became permanent. However, long blocking operations while executing native or foreign code can still occupy a carrier thread. The practical rule remains: keep critical sections small, do not hold locks while performing long external I/O, and measure real applications rather than assuming every blocking operation scales perfectly. Pinning does not make code incorrect, but excessive carrier blocking reduces scalability.
    • Structured concurrency preview. StructuredTaskScope (preview) lets a group of subtasks be treated as one unit with clear lifetimes and failure propagation, pairing naturally with virtual threads so that sequential-looking code can fan out and join safely.

    Memory aid Virtual threads remove the thread bottleneck, not the resource bottleneck. The limit moves to the database, the API or the socket — so guard those, not the thread count.

    22. Choosing the Correct Tool

    The tools are complementary, not interchangeable replacements.

    Requirement Better choice
    Track one task's result Future
    Wait or cancel one task Future
    Build a chain of dependent operations CompletableFuture
    Transform a result automatically CompletableFuture
    Combine independent async results CompletableFuture
    Handle a completion pipeline declaratively CompletableFuture
    Aspect ForkJoinPool Virtual threads
    Primarily suited to CPU-bound parallel work High-concurrency blocking work
    Unit of work Subtasks of one computation One lightweight thread per task
    Scheduling Work stealing JVM scheduling over carrier threads
    Best for Divide and conquer Thread-per-request/task
    Parallelism Limited by useful CPU capacity Concurrency may far exceed CPU count
    Blocking Avoid long blocking operations Blocking is the primary use case

    CompletableFuture represents work as completion stages, attaches callbacks, and composes results declaratively — useful when asynchronous pipelines are natural, several independent results must be combined, a framework already works with completion stages, or callback-style composition is desirable. Virtual threads let normal sequential blocking code run on one thread per task while the JVM handles large concurrency — useful when the workflow is naturally sequential, code makes blocking I/O calls, imperative readability matters, or thread-per-request programming is preferred.

    Important A virtual-thread version String user = fetchUser(); String orders = fetchOrders(); is easier to read but performs the two calls sequentially unless separate virtual threads or structured concurrency are used; the CompletableFuture thenCombine version runs them concurrently.

    23. Myth vs Reality

    Myth Reality
    "One tool fits all concurrency needs." Each tool solves a different problem: Future for a single pending result, CompletableFuture for pipelines, ForkJoinPool for CPU-bound divide and conquer, virtual threads for blocking concurrency.
    "thenApply() always runs on a new thread." Plain continuations may run in the thread that completes or attaches the stage; only the Async variants are scheduled on an executor.
    "isDone() means the task succeeded." It only means a terminal state was reached; the task may have completed exceptionally or been cancelled.
    "Virtual threads make CPU-bound work faster." They do not add CPU cores; they help tasks that spend time waiting. CPU-bound work belongs to ForkJoinPool.
    "ForkJoinPool is a universal executor." It is for CPU-bound, decomposable work; blocking its workers on I/O reduces throughput for unrelated tasks.

    24. Common Trap Questions

    Trap 1 — "Does creating 100,000 virtual threads create 100,000 database connections?" No. Threads are cheap, dependencies are not. Limit the scarce resource (for example with a Semaphore) rather than the virtual-thread count.

    Trap 2 — "I called future.cancel(true) while the task is running — it has definitely stopped, right?" No. cancel is a request, not a guarantee. For a running task to stop, the task must cooperate by checking interruption or a flag.

    Trap 3 — "Should I pool virtual threads like platform threads?" No. The intended model is one new virtual thread per task; use newVirtualThreadPerTaskExecutor() and do not reuse virtual threads.

    Trap 4 — "I set a ThreadLocal in a pool task and never removed it. Is that fine?" No. Pooled worker threads are reused, so the next task can observe stale data and the value stays reachable; always call remove() in a finally block.

    Trap 5 — "Can I use InheritableThreadLocal to pass context to virtual-thread executor tasks?" Not reliably. Inheritance occurs at thread creation; pooled and per-task threads do not guarantee the intended parent. Prefer explicit parameters or ScopedValue (preview).

    Trap 6 — "Should I use ForkJoinPool for a task that blocks on a database call?" No. Blocking a fork-join worker reduces the pool's ability to process other tasks; use a dedicated executor or virtual threads.

    Trap 7 — "get() and join() are the same, aren't they?" Both block, but get() throws checked ExecutionException while join() throws unchecked CompletionException.

    25. Points to Remember

    1. Future<T> represents the eventual result of one asynchronous task and supports waiting, polling, cancellation and exception observation.
    2. get() blocks and can throw InterruptedException, ExecutionException and CancellationException; isDone() is non-blocking and does not imply success.
    3. CompletableFuture implements both Future and CompletionStage, so it is both a pending result and a composable stage.
    4. runAsync() uses a Runnable and yields CompletableFuture<Void>; supplyAsync() uses a Supplier and returns a value; completedFuture(v) creates an already-complete future.
    5. thenApply transforms, thenAccept consumes, thenRun ignores the result, and thenCompose flattens nested asynchronous stages.
    6. Plain continuations may run on a completing/attaching thread; Async variants use the common pool or a supplied executor.
    7. Combine two futures with thenCombine, many with allOf (all complete) or anyOf (first completes); recover with exceptionally, observe with whenComplete, transform either path with handle.
    8. ForkJoinPool targets CPU-bound recursive work: RecursiveTask<V> returns a result, RecursiveAction does not; fork() schedules, join() waits, invoke() runs a top-level task, and idle workers steal work from busy workers' local queues.
    9. ThreadLocal stores a separate value per thread for requested context; on pooled threads always remove() in a finally, and use ThreadLocal.withInitial for defaults.
    10. Virtual threads (permanent in Java 21) run many-to-one over carrier threads, unmount on supported blocking operations, are not for CPU-bound work, should not be pooled, and must respect scarce downstream resources.

    26. Likely Interview Questions

    Question Crisp Answer
    What is a Future? A placeholder for the pending result of an asynchronous task; it lets the caller wait, check completion, cancel and observe exceptions.
    What does isDone() guarantee? Only that a terminal state was reached — success, failure or cancellation — not that the task succeeded.
    Difference between isDone() and get()? isDone() is a non-blocking status check; get() blocks until the result is available or an exception/cancellation is reported.
    What problems does Future have that CompletableFuture fixes? Future cannot declaratively chain, transform, combine or handle failure; CompletableFuture adds composable completion stages.
    How do you create a CompletableFuture? runAsync() for no result, supplyAsync() for a result, or completedFuture(v) for an already-complete one, with the common pool or a custom executor.
    Difference between thenApply, thenAccept and thenRun? thenApply transforms and returns; thenAccept consumes and returns nothing; thenRun ignores the previous result and only runs after completion.
    Difference between thenApply and thenApplyAsync? thenApply may run on a completing/attaching thread; thenApplyAsync schedules the continuation on the default or supplied executor.
    What do allOf and anyOf do? allOf completes when every future completes; anyOf completes with the first future to complete.
    Difference between get() and join()? Both block; get() throws checked ExecutionException, join() throws unchecked CompletionException.
    What is ForkJoinPool for and what is work stealing? It parallelises divisible CPU-bound computations; idle workers steal queued subtasks from busy workers' local queues.
    RecursiveTask vs RecursiveAction? RecursiveTask<V> returns a result; RecursiveAction performs work without returning one.
    What is a virtual thread and when should it not be used? A JVM-scheduled lightweight thread for high-concurrency blocking work; it should not be used for CPU-bound computation and should not be pooled.

    27. Final Summary

    Future<T>            submit one task → receive a placeholder → wait / check / cancel
CompletableFuture<T> represent a stage → transform & combine stages → react to completion/failure
ForkJoinPool         split CPU-bound problem → workers process subtasks → steal work → join partial results
Virtual threads      one lightweight thread per task → blocking releases the carrier → many waiting tasks become practical
    • Future → represents the eventual result of one task; get() blocks, isDone() checks, cancel() requests.
    • CompletableFuture → Future + CompletionStage; create with runAsync/supplyAsync/completedFuture, chain with thenApply/thenAccept/thenRun/thenCompose, combine with thenCombine/allOf/anyOf, recover with exceptionally/whenComplete/handle.
    • ForkJoinPool → CPU-bound divide and conquer; fork one side, compute the other, join; workers steal from peers' local queues.
    • ThreadLocal → one value per thread for request context; always remove() on pooled threads; withInitial for defaults; InheritableThreadLocal is unreliable across pools; ScopedValue is the preview alternative.
    • Virtual threads → Java 21, many over few carrier threads, unmount on blocking, not for CPU-bound work, never pooled, limited by downstream resources.
    • Choosing → match the tool to the workload: result placeholder (Future), pipeline (CompletableFuture), divisible CPU work (ForkJoinPool), many blocking tasks (virtual threads).

    Golden rule The correct tool depends on the nature of the workload — not simply on which API looks more modern.

    One-line takeaway: Future answers "what result will arrive later?", CompletableFuture answers "how do I build a pipeline around completion?", ForkJoinPool answers "how do I parallelise a divisible CPU-bound computation?", and virtual threads answer "how do I handle many concurrent blocking tasks without the same number of OS threads?"
