    Part 5 · Collections, Lambdas & Streams · Lecture 34

    Set & Map Methods Explained | EnumMaps, IdentityHashMaps & More

    23 sections · interview-oriented · both themes

    Scope evidence: "Set & Map Methods Explained | EnumMaps, IdentityHashMaps & More" (playlist map, verified). Repo evidence: 5 Demo files.

    The previous lecture opened the Set and Map families; this lecture walks their full method surface and then follows each implementation to the point where it stops behaving like the others. It covers the core Set and Map operations, the bulk algebra of addAll/retainAll/removeAll, entry-set iteration, the Java 9 immutable factories, and the specialized containers: EnumSet and EnumMap, IdentityHashMap, WeakHashMap, LinkedHashMap in access-order mode, and the sorted NavigableMap. The recurring theme is that one interface hides radically different key semantics, ordering rules and memory profiles, and the correct choice is dictated by the one property the algorithm actually depends on.

    1. The Set and Map Contracts

    A Set is a Collection that forbids duplicates: it models mathematical membership. A Map is not a Collection at all; it models a dictionary, a mapping from unique keys to values. Both live in java.util, in two deliberately parallel trees:

    Iterable ⊃ Collection ⊃ Set ⊃ (HashSet, LinkedHashSet, TreeSet, EnumSet)

Map (separate root) ⊃ (HashMap, LinkedHashMap, TreeMap, EnumMap, IdentityHashMap, WeakHashMap)

    A Set can be viewed as a Map with only keys, which is literally how HashSet is built: it wraps a HashMap. That is why the same questions about equals, hashCode and ordering reappear in both families.

    Important Map is the only major collection that does not extend Collection. It has no iterator() of its own; iteration is offered through its three views: keySet(), values() and entrySet().

    2. Set Methods: Membership and Size

    The core Set surface is small, because a set has no positions:

    Method Returns Meaning
    add(E e) boolean adds if absent; false if the element already existed
    remove(Object o) boolean removes the element if present; true if it was
    contains(Object o) boolean membership test
    size() int number of elements
    isEmpty() boolean size() == 0
    clear() void removes every element
    iterator() Iterator<E> the only cursor for the set
    toArray() Object[] a snapshot array

    The distinguishing feature is the return value of add. A List.add always appends, but Set.add reports whether the set actually changed, so a duplicate can be detected without a second lookup.

    Memory aid Set.add returns false when nothing changed — the opposite intuition from List.add, which returns true on every successful append.

    3. Set Bulk Operations: addAll, retainAll, removeAll, containsAll

    Every Collection supplies four bulk operations, and on a Set they read as set algebra:

    Method Set algebra Effect on the receiver Mutates?
    addAll(c) union adds every element of c, discarding duplicates yes
    retainAll(c) intersection keeps only elements also in c yes
    removeAll(c) difference (minus) removes every element also in c yes
    containsAll(c) superset test true if the receiver contains every element of c no

    Two rules matter. First, removeAll is asymmetric: A.removeAll(B) removes B's elements from A, while B.removeAll(A) does the reverse, and the two results differ. Second, the three mutating methods return boolean, true only when the receiver changed, which makes them honest about whether they did anything.

    Interviewer's perspective "How do you compute the intersection of two sets?" a.retainAll(b) turns a into the intersection in place. If the original a must survive, copy first: Set<E> in = new HashSet<>(a); in.retainAll(b);.

    4. Iterating a Set: No Indexed Access

    A Set is not indexed: there is no get(int), no set(int, E) and no subList. The only cursors are iterator() and the for-each loop, which is syntax over it. The iteration order depends entirely on the implementation:

    1. HashSet — no promised order; order may change as the table resizes.
    2. LinkedHashSet — insertion order.
    3. TreeSet — sorted order by compareTo or a Comparator.
    4. EnumSet — the enum's declaration order.

    Removing while iterating is done through the iterator, exactly as with a List; the fail-fast rule is identical.

    // Demo.java — Set membership, bulk algebra and safe removal
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Set<String> a = new HashSet<>(List.of("red", "green", "blue", "red")); // red once
        Set<String> b = new HashSet<>(List.of("green", "blue", "yellow"));

        System.out.println(a.add("red"));        // false: already present
        System.out.println(a.contains("blue"));  // true
        System.out.println(a.size());            // 3

        Set<String> union = new HashSet<>(a);
        union.addAll(b);                         // union
        Set<String> inter = new HashSet<>(a);
        inter.retainAll(b);                      // intersection
        Set<String> diff = new HashSet<>(a);
        diff.removeAll(b);                       // difference
        System.out.println(union + " " + inter + " " + diff);
        System.out.println(a.containsAll(inter)); // true (superset test)

        Iterator<String> it = a.iterator();
        while (it.hasNext()) if (it.next().equals("green")) it.remove();
        System.out.println(a);                   // red, blue
    }
}

    5. Map Methods: The Basic Surface

    The Map surface is organised around one key:

    Method Returns Meaning
    put(k, v) previous value or null insert or overwrite
    get(k) value or null lookup; null also means "absent"
    getOrDefault(k, d) value or d default when no mapping exists
    putIfAbsent(k, v) previous value or null insert only if not already mapped
    remove(k) removed value or null unconditional removal
    remove(k, v) boolean remove only if currently mapped to v
    replace(k, v) previous value or null overwrite only if present
    replace(k, old, new) boolean overwrite only if currently old
    containsKey(k) boolean key presence test
    containsValue(v) boolean value presence test, O(n)
    size() / isEmpty() int / boolean entry count
    clear() void removes every entry

    The overloaded replace and remove pairs are the emblems of the lecture: they are conditional updates, the one-call primitives that a plain read-then-write cannot express.

    Trap get returning null is ambiguous: it can mean "no mapping" or "mapped to null". When null values are legal, test with containsKey(k), not with get(k) == null.

    6. The Compute Family: compute, computeIfAbsent, computeIfPresent, merge

    Java 8 added four methods that compute a new value from the key, the current value, or both, and write the result in one call:

    Method Runs when Function shape Result null means
    computeIfAbsent(k, f) key absent or mapped to null k -> v no mapping is created
    computeIfPresent(k, f) key present and non-null (k, v) -> v the mapping is removed
    compute(k, f) always (k, v) -> v the mapping is removed
    merge(k, v, f) always (old, v) -> v existing mapping removed

    merge is the odd one: if the key is absent (or mapped to null) it simply stores v; otherwise it applies f(oldValue, v). That makes it the standard word-count idiom.

    // Demo2.java — the compute family and merge
import java.util.*;

public class Demo2 {
    public static void main(String[] args) {
        Map<String, Integer> counts = new HashMap<>();
        for (String w : "a b a c a b".split(" ")) {
            counts.merge(w, 1, Integer::sum);          // merge: count occurrences
        }
        System.out.println(counts);                     // {a=3, b=2, c=1}

        Map<String, List<Integer>> index = new HashMap<>();
        index.computeIfAbsent("evens", k -> new ArrayList<>()).add(2); // build once
        index.computeIfAbsent("evens", k -> new ArrayList<>()).add(4);
        System.out.println(index);                      // {evens=[2, 4]}

        System.out.println(counts.computeIfPresent("c", (k, v) -> v + 10)); // 11
        System.out.println(counts.getOrDefault("z", 0));                    // 0
        counts.putIfAbsent("z", 0);                     // insert only if absent
        System.out.println(counts);
    }
}

    Important computeIfAbsent returning null leaves no mapping at all. That is why computeIfAbsent(k, k -> null) never "records a null"; it records nothing and returns null.

    7. Views: keySet, values, entrySet

    A map's three views are live windows, not copies:

    1. keySet() — a Set of keys; remove on it removes the whole entry.
    2. values() — a Collection of values; it is not a Set, because values may repeat.
    3. entrySet() — a Set of Map.Entry objects, the only view exposing key and value together.

    Because the views are backed by the map, a structural change through a view is a structural change to the map, and vice versa. keySet().remove(k) is therefore a legal way to delete an entry, and map.clear() empties all three views at once. The view to prefer for iteration is entrySet(), because it avoids the second lookup that keySet() plus get(k) would force.

    Memory aid keySet, values and entrySet are windows, not photographs: closing a curtain on one changes the room the others see.

    8. Iterating a Map: Map.Entry and forEach(BiConsumer)

    Map.Entry is the pair type inside entrySet(); it exposes getKey(), getValue() and setValue(v). In most implementations setValue writes straight through to the map, so iterating an entry set is also a way to update values in place. The Java 9 static Map.entry(k, v) builds an immutable pair, useful with Map.ofEntries.

    // Demo3.java — entrySet iteration, setValue, forEach and immutable factories
import java.util.*;

public class Demo3 {
    public static void main(String[] args) {
        Map<String, Integer> stock = new HashMap<>();
        stock.put("apples", 3);
        stock.put("pears", 5);

        for (Map.Entry<String, Integer> e : stock.entrySet()) {
            e.setValue(e.getValue() * 10);           // writes back to the map
        }
        System.out.println(stock);                   // {apples=30, pears=50}

        stock.forEach((k, v) -> System.out.println(k + "=" + v)); // BiConsumer

        Map<String, Integer> frozen = Map.of("a", 1, "b", 2);     // Java 9: immutable
        Set<String> names = Set.of("x", "y");                     // Java 9: immutable
        System.out.println(frozen.getOrDefault("c", -1));         // -1
        // frozen.put("c", 3);  // UnsupportedOperationException
    }
}

    Interviewer's perspective "Why iterate entrySet instead of keySet?" Both are correct, but entrySet yields the value already, while keySet forces a map.get(k) per key. One traversal beats n separate lookups.

    9. Immutable Factories (Java 9)

    Java 9 added static factories for small, immutable collections:

    Factory Notes
    List.of(...) ordered, immutable, rejects null
    Set.of(...) unordered, rejects duplicates with IllegalArgumentException
    Map.of(k1, v1, ...) up to ten key-value pairs, rejects duplicate keys
    Map.ofEntries(Map.entry(...), ...) unbounded via Map.Entry varargs
    List.copyOf / Set.copyOf / Map.copyOf defensive immutable copy

    All of them are null-hostile: a null element, key or value throws NullPointerException at creation. All of them are unmodifiable: any mutating call throws UnsupportedOperationException. copyOf returns the same instance when the argument is already an immutable collection of the right type, and otherwise makes a copy.

    Trap "Unmodifiable" is not "deeply immutable". The factory never copies the elements themselves; it only freezes the collection structure. And it rejects null, so Map.of("k", null) compiles and then throws.

    10. EnumSet: A Bit Vector in Disguise

    An EnumSet is a specialized Set for a single enum type. Internally it is a bit vector (a long per 64 constants), so membership is a bit test and the whole set is tiny and cache friendly. Every operation is extremely fast, and iteration follows declaration order.

    // Demo4.java — EnumSet and EnumMap
import java.util.*;

public class Demo4 {
    enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

    public static void main(String[] args) {
        EnumSet<Day> weekend = EnumSet.of(Day.SAT, Day.SUN);
        EnumSet<Day> workdays = EnumSet.range(Day.MON, Day.FRI);
        EnumSet<Day> none = EnumSet.noneOf(Day.class);
        EnumSet<Day> week = EnumSet.complementOf(weekend); // everything else

        System.out.println(weekend + " " + workdays + " " + week);
        System.out.println(none.isEmpty());                 // true

        EnumMap<Day, String> plan = new EnumMap<>(Day.class);
        plan.put(Day.MON, "study");
        plan.put(Day.SAT, "rest");
        System.out.println(plan.get(Day.SAT));              // rest
    }
}

    The factories are EnumSet.of(...), EnumSet.range(from, to), EnumSet.noneOf(Class), EnumSet.allOf(Class), EnumSet.complementOf(anotherEnumSet) and EnumSet.copyOf(...).

    Important EnumSet is not backed by a hash table and has no public constructor; it is always built through the factories. All elements must be constants of the same enum type (cross-reference Lecture 23).

    11. EnumMap: An Array Keyed by Ordinal

    An EnumMap is a Map whose keys are constants of one enum type. It is backed by a plain array indexed by ordinal(), so get, put and containsKey are constant time with no hashing and no collisions. Iteration follows key declaration order.

    The key restrictions are strict:

    1. The key type is one specific enum, fixed at construction: new EnumMap<>(Day.class).
    2. null keys are rejected with NullPointerException at put/get.
    3. Non-enum keys are impossible, because the key type is bounded to Enum.

    Interviewer's perspective "Why is EnumMap faster than HashMap?" A HashMap hashes the key, masks the hash into a bucket and resolves collisions. An EnumMap skips all of that: the key's ordinal is the array index, so lookup is a direct slot access.

    12. IdentityHashMap: Identity, Not Equality

    IdentityHashMap deliberately violates the Map contract's reliance on equals. It compares keys with == (reference identity) and hashes with System.identityHashCode, so two equal-but-distinct keys become two separate entries.

    Its legitimate uses are algorithms whose nodes are objects whose equals is either absent or would merge distinct nodes: graph traversal, topology, cycle detection, and deep copy with a visited map keyed by object identity. In those cases a HashMap would collapse nodes that equals considers equal.

    Trap IdentityHashMap breaks the normal Map contract, and its own Javadoc says so. Avoid it as a general-purpose map. If two String keys hold the same text but are different objects, they are two entries here.

    13. WeakHashMap: Entries That Disappear

    A WeakHashMap holds its keys through WeakReference. When no strong reference to a key remains, the garbage collector may reclaim it, and the corresponding entry is silently removed. This suits caches and canonicalising maps where an entry should live only as long as the key is used elsewhere.

    Two cautions:

    1. Entries can vanish between calls, so never rely on size() or persistence.
    2. Values are held strongly; if a value refers back to its key, the key is no longer weakly reachable and the entry will not be collected.

    Important "Weak key" means GC-leaning, not deterministic: the entry disappears at some point after the last strong reference to the key goes away, governed by the collector.

    14. LinkedHashMap: Order, accessOrder and the LRU Cache

    LinkedHashMap keeps a doubly linked list through its entries on top of a hash table. Two orderings exist:

    1. Insertion order (default) — entries iterate in the order they were added.
    2. Access order — construct with new LinkedHashMap<>(capacity, loadFactor, true); then get/put moves the touched entry to the tail.

    Access order plus one override produces the classic LRU cache. removeEldestEntry(Map.Entry) is called after every insertion; returning true removes the eldest entry, which in access-order mode is the least recently used.

    // Demo5.java — an LRU cache and identity-keyed behaviour
import java.util.*;

public class Demo5 {
    static <K, V> Map<K, V> lru(int capacity) {
        return new LinkedHashMap<>(16, 0.75f, true) {   // access order
            protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                return size() > capacity;                // evict when over capacity
            }
        };
    }

    public static void main(String[] args) {
        Map<String, Integer> cache = lru(3);
        cache.put("a", 1);
        cache.put("b", 2);
        cache.put("c", 3);
        cache.get("a");          // "a" becomes most recently used
        cache.put("d", 4);       // evicts "b"
        System.out.println(cache);            // {c=3, a=1, d=4}

        Map<String, String> ids = new IdentityHashMap<>();
        String x = new String("k");
        String y = new String("k");
        ids.put(x, "first");
        ids.put(y, "second");    // distinct references -> distinct entries
        System.out.println(ids.size());       // 2, unlike HashMap
    }
}

    This is the most-asked interview construction in the collections chapter: an O(1) LRU built from a hash map and a linked list, supplied by the JDK in a single anonymous subclass.

    15. SortedMap and NavigableMap: Range Queries

    SortedMap adds sorted-key behaviour; NavigableMap (Java 6) extends it with navigation and range methods. TreeMap is the standard implementation, backed by a red-black tree, so all operations are O(log n).

    Method family Returns Boundary
    firstKey() / lastKey() lowest / highest key inclusive
    floorKey(k) greatest key <= k inclusive lower
    ceilingKey(k) least key >= k inclusive upper
    lowerKey(k) greatest key < k exclusive lower
    higherKey(k) least key > k exclusive upper
    headMap(k) keys < k to exclusive
    tailMap(k) keys >= k from inclusive
    subMap(from, to) from <= keys < to half-open

    The Entry counterparts (firstEntry, floorEntry, ...) return key-value pairs, and pollFirstEntry/pollLastEntry remove as they return. When a comparator is supplied, "sorted" means that comparator's order, not natural order.

    Memory aid floor / ceiling are inclusive (a floor you can stand on, a ceiling that covers you); lower / higher are exclusive. headMap keeps the head (smaller keys); tailMap keeps the tail (larger keys).

    16. Map Implementations Compared

    Aspect HashMap LinkedHashMap TreeMap EnumMap IdentityHashMap WeakHashMap
    Ordering none insertion or access sorted by key enum declaration none none
    Key identity equals/hashCode equals/hashCode compareTo or Comparator ordinal (enum only) == equals/hashCode
    null keys one one no (natural order) no yes yes
    Typical lookup O(1) O(1) O(log n) O(1) O(1) O(1)
    Memory table + nodes table + list + nodes tree nodes one array table table + refs
    Backing bucket array hash table + list red-black tree ordinal array bucket array hash + WeakReference
    Use when general purpose order or LRU matters sorted/range queries keys are one enum identity is the key GC-driven cache

    Reading the table: HashMap is the default; reach for a neighbour only when its special property is the point. TreeMap is the only one giving ordered range queries, EnumMap the only one that turns a key into an index, and IdentityHashMap the only one that changes what "same key" means.

    17. Sorted and Navigable Methods at a Glance

    This table pairs the query with the result on a map keyed by 10, 20, 30:

    Call Result Why
    firstKey() 10 lowest key
    lastKey() 30 highest key
    floorKey(25) 20 greatest key <= 25
    ceilingKey(25) 30 least key >= 25
    lowerKey(20) 10 greatest key < 20
    higherKey(20) 30 least key > 20
    headMap(20) {10} keys < 20
    tailMap(20) {20, 30} keys >= 20
    subMap(10, 30) {10, 20} 10 <= keys < 30

    The two boundary conventions are the frequent source of off-by-one bugs: headMap excludes its argument, tailMap includes it, and subMap is half-open.

    18. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Treating get(k) == null as "absent" A key mapped to null looks identical to a missing key Use containsKey(k) when null values are legal
    computeIfAbsent(k, k -> null) No mapping is created; the call silently does nothing Return a real value, or initialise with put
    Mutating an immutable factory UnsupportedOperationException on put/add/remove Copy into new HashMap<>(...) or new HashSet<>(...) before editing
    Map.of(k, null) or Set.of((String) null) NullPointerException at creation The factories reject null; supply a sentinel instead
    Removing during a for-each over a map ConcurrentModificationException Remove via entrySet().iterator().remove() or entrySet().removeIf(...)
    IdentityHashMap with logically equal keys Two entries where one was expected Use HashMap unless identity is genuinely required
    Relying on insertion order with HashMap Iteration order is unspecified and changes on resize Use LinkedHashMap when order must be stable
    EnumMap with a null key NullPointerException immediately Keys must be non-null constants of the declared enum
    containsValue in a hot loop It scans every entry, O(n) Maintain a reverse index or a second map

    Golden rule Every method with a null-taking or null-returning ambiguity should be paired with containsKey; every conditional update should use putIfAbsent, replace or the compute family instead of read-then-write.

    19. Myth vs Reality

    Myth Reality
    "A Set is just a Map without values, so Set has no own behaviour." It is true that HashSet is backed by a HashMap, but Set adds the duplicate-free contract and set algebra (retainAll, removeAll).
    "HashMap preserves insertion order." It does not; order is unspecified and can change on resize. LinkedHashMap preserves order.
    "IdentityHashMap is a faster HashMap." It is not faster in general; it changes semantics to ==, breaking the normal equals-based Map contract.
    "WeakHashMap entries stay until I remove them." The GC may reclaim weakly held keys, silently dropping entries, so size() is not stable.
    "Map.of(...) returns a mutable map I can later put into." It returns an unmodifiable map; mutation throws UnsupportedOperationException, and null is rejected at creation.

    20. Common Trap Questions

    Trap 1 — The ambiguous get: "map.containsKey(k) is false; can map.get(k) still be non-null?" No. If the key is absent, get returns null. The dangerous direction is the reverse: a present key mapped to null also returns null, so get == null cannot distinguish the two.

    Trap 2 — computeIfAbsent with a null result: "What does map.computeIfAbsent(k, x -> null) do?" It inserts nothing and returns null; a null mapping-function result means "make no change", not "store null".

    Trap 3 — Mutating an immutable factory: "Set<String> s = Set.of("a"); s.add("b"); — what happens?" UnsupportedOperationException at runtime; the factory collection is unmodifiable. Copy it first if mutation is needed.

    Trap 4 — Concurrent modification: "Can I call map.remove(k) inside map.forEach(...)?" That can trigger ConcurrentModificationException. Remove through an Iterator, or use map.entrySet().removeIf(...).

    Trap 5 — EnumMap keys: "What happens on new EnumMap<>(Day.class).put(null, "x")?" NullPointerException; EnumMap forbids null keys. A non-enum key is impossible at compile time given the type bound.

    Trap 6 — Identity versus equality: "Two distinct String objects with the same text as keys in an IdentityHashMap." They are two separate entries, because the comparison is ==, not equals.

    Trap 7 — LRU construction: "How do you build an LRU cache in one expression?" Subclass LinkedHashMap with accessOrder = true and override removeEldestEntry to return true once size() exceeds the capacity.

    Trap 8 — Sorted boundaries: "On a NavigableMap, does headMap(20) include 20?" No; headMap is exclusive of its argument. Use tailMap(20) to include it, or subMap for a half-open range.

    21. Points to Remember

    1. Set forbids duplicates and has no indexed access; Map maps unique keys to values and does not extend Collection.
    2. Set.add returns false when the element already existed; remove/contains return boolean; set algebra is addAll union, retainAll intersection, removeAll asymmetric difference, containsAll superset test.
    3. Map basics: put, get, getOrDefault, putIfAbsent, remove(k) and remove(k, v), replace, containsKey, containsValue, size, isEmpty.
    4. The compute family: compute, computeIfAbsent, computeIfPresent, merge; a null result means "remove", and for computeIfAbsent it means "do nothing".
    5. Iterate a map with entrySet(); Map.Entry offers getKey, getValue, setValue; forEach takes a BiConsumer.
    6. The Java 9 factories Map.of, Map.ofEntries, Set.of, List.of and copyOf are null-hostile and unmodifiable.
    7. EnumSet is a bit vector and EnumMap is an ordinal array; both are extremely fast and confined to one enum type (Lecture 23).
    8. IdentityHashMap compares keys with ==; WeakHashMap holds keys weakly and can lose entries to GC.
    9. LinkedHashMap with accessOrder = true plus a removeEldestEntry override is the canonical O(1) LRU cache.
    10. SortedMap/NavigableMap gives firstKey/lastKey, floor/ceiling (inclusive), lower/higher (exclusive), headMap (exclusive), tailMap (inclusive) and subMap (half-open); remember that get(k) == null is ambiguous when null values are legal.

    22. Likely Interview Questions

    Question Crisp Answer
    How does Set guarantee no duplicates? It defines add to return false if an equal element is already present, relying on equals/hashCode (or ordering) to detect it.
    Difference between the Set bulk methods? addAll is union, retainAll is intersection, removeAll is asymmetric difference, containsAll is a superset test.
    get vs getOrDefault? get returns null when absent; getOrDefault returns the supplied default instead. Neither distinguishes a present null mapping.
    Why use putIfAbsent over get then put? It expresses "insert only if absent" in one call and is the conditional-update primitive (atomic only on a concurrent map).
    What does computeIfAbsent do if the function returns null? No mapping is created and the method returns null.
    compute vs merge? compute always runs the function with the current value (possibly null); merge stores the given value when absent and otherwise combines it with the old value.
    Why iterate entrySet instead of keySet? entrySet yields key and value together, avoiding a map.get(k) lookup per key.
    What are the Java 9 immutable factories? List.of, Set.of, Map.of, Map.ofEntries and the copyOf methods; all reject null and are unmodifiable.
    Why is EnumMap faster than HashMap? It indexes an array by the key's ordinal(), so there is no hashing and no collision handling.
    When is IdentityHashMap appropriate? When reference identity, not equals, must distinguish keys: graph/topology algorithms, cycle detection, identity-keyed deep copy.
    How do you build an LRU cache? Extend LinkedHashMap with accessOrder = true and override removeEldestEntry to evict beyond a capacity.
    floorKey vs lowerKey? floorKey returns the greatest key <= the argument (inclusive); lowerKey returns the greatest key strictly < (exclusive).

    23. Final Summary

    Set  : add / remove / contains / size / isEmpty     -> membership, no index
       addAll = union · retainAll = intersection
       removeAll = difference · containsAll = superset

Map  : put / get / getOrDefault / putIfAbsent       -> dictionary
       compute / computeIfAbsent / computeIfPresent / merge
       replace · remove(k, v) · containsKey · keySet / values / entrySet

views  : entrySet ⊃ Map.Entry(getKey / getValue / setValue)
Java 9 : Map.of / Map.ofEntries / Set.of / List.of / copyOf   -> null-hostile, unmodifiable
special: EnumSet (bit vector) · EnumMap (ordinal array) · IdentityHashMap (==)
         WeakHashMap (weak keys) · LinkedHashMap (LRU) · NavigableMap (ranges)
    • Set → duplicate-free membership; bulk methods are set algebra; iterate with for-each because there is no index.
    • Map → key to value; get == null is ambiguous, so use containsKey; conditional updates via putIfAbsent, replace, compute, merge.
    • Iteration → entrySet for key and value; Map.Entry.setValue writes through; forEach(BiConsumer).
    • Immutable factories → reject null, throw UnsupportedOperationException on mutation.
    • Specialized → EnumSet bit vector, EnumMap ordinal array, IdentityHashMap by ==, WeakHashMap weak keys.
    • LRU → LinkedHashMap(accessOrder = true) plus a removeEldestEntry override.
    • Sorted → NavigableMap: floor/ceiling inclusive, lower/higher exclusive; head exclusive, tail inclusive, subMap half-open.

    Golden rule A Map is only as safe as its null discipline and only as fast as the right implementation: choose the map by its ordering, identity rule and memory profile, and never trust get == null to mean "absent".

    One-line takeaway: Set gives duplicate-free membership and set algebra, Map gives keyed conditional updates, and the specialized containers — EnumMap, IdentityHashMap, WeakHashMap, LinkedHashMap and NavigableMap — each trade generality for one sharp property.
