    Part 2 · Configuration & First Projects · Lecture 10

    Spring Boot application properties, @Value & Runner Interface

    21 sections · interview-oriented · both themes

    Scope evidence: "Spring Boot application properties, @Value & Runner Interface" (playlist map, verified). The repo lecture folder is a demo Spring Boot project whose src/main/resources carries application.properties, with PaymentProperties, DemoRunner, PaymentGateway and DemoApplication under in.strikes.demo, alongside the notes for this lecture.

    Configuration is the layer that lets one compiled application behave differently in development, testing and production. This lecture starts from the pain of hardcoded values, moves to application.properties and externalized configuration, then teaches two ways to read those values: @Value and @ConfigurationProperties. It closes with the runner interfaces, which give a non-web application a clean place to execute startup logic after the Spring container is ready.

    1. Why Do We Need Configuration?

    In real applications, not every value should be hardcoded inside Java classes. The source shows a component whose values are fixed in the source code. Simplified, it looked like this:

    private String providerName = "Razorpay";
private int retryCount = 3;

    This code works, but the values are fixed inside the Java source code. Now imagine that tomorrow we want to change the payment provider from Razorpay to Stripe. If the value is hardcoded, we would need to:

    1. Change the Java code.
    2. Recompile the project.
    3. Rebuild the application.
    4. Redeploy the application.

    For values that may change across environments or over time, this is not a clean approach. Examples of such values:

    • payment provider name;
    • retry count;
    • timeout value;
    • feature enabled/disabled flag;
    • database URL;
    • API key;
    • server port;
    • external service URL.

    These values are better kept outside the main business logic. This is where configuration files come in.

    Important: Configuration is not "extra settings for later." It keeps values which change outside the code which does not change.

    2. What Is application.properties?

    application.properties is a key-value configuration file that Spring Boot automatically reads by convention. The default location is:

    src/main/resources/application.properties

    Example from the source:

    payment.provider=Razorpay
payment.retry-count=3
payment.enabled=true
payment.timeout=5000

    Here, the values are no longer written directly inside the Java class. They are now configuration values. Spring Boot automatically loads this file when the application starts.

    The convention does the work: because the file has this exact name and sits in this exact folder, Spring Boot finds and loads it without any import or annotation.

    Interviewer's perspective: A strong answer names both the file and the convention: "Spring Boot loads application.properties from the classpath root automatically, and its key-value pairs become part of the Spring Environment." Naming the Environment shows you understand where @Value actually reads from.

    3. YAML as an Alternative: application.yml

    Spring Boot also supports YAML configuration using application.yml. The same values can be written in nested form:

    payment:
  provider: Razorpay
  retry-count: 3
  enabled: true
  timeout: 5000

    Both application.properties and application.yml are used for configuration. The difference is mainly in the writing style: one is flat key-value, the other is a nested tree. The keys still mean the same thing, and the Java code that reads them does not care which file supplied them.

    Golden rule: The file name and the property keys matter; the file format is a matter of taste. Keep one format per project so the team reads configuration the same way.

    4. Is application.properties Really External?

    This is the subtle point. When application.properties is placed inside src/main/resources, it becomes part of the application build. That means it is packaged inside the final JAR file.

    So technically, if we only change this internal file in the source code, we still need to rebuild the application.

    But Spring Boot provides externalized configuration, which means these values can also be supplied or overridden from outside the packaged application. For example, Spring Boot can read configuration from:

    • application.properties;
    • application.yml;
    • environment variables;
    • command-line arguments;
    • system properties;
    • external config files.

    So the main idea is: keep changeable values outside Java business logic so the code remains clean and flexible.

    Common trap in disguise: "If it is in a properties file, it is automatically external." Not always. A file inside src/main/resources travels inside the JAR; true externalization comes from the override sources listed above or from a config file placed outside the packaged artifact.

    5. Externalized Configuration Across Environments

    Externalized configuration means keeping configuration values outside the Java code. Instead of hardcoding private String providerName = "Razorpay";, we write the value in a configuration file as payment.provider=Razorpay, then inject that value into the Java class.

    This makes the application easier to manage across different environments. For example, in development we might use payment.provider=Razorpay with payment.retry-count=3, while in production we might use payment.provider=TestProvider with payment.retry-count=1. The Java code can remain the same. Only the configuration changes.

    Aspect Hardcoded value Externalized configuration
    Where it lives Inside the Java class properties / yml / env vars / args
    To change it Edit code, recompile, rebuild, redeploy Override the value, restart
    Environment fit One value for every environment Different value per environment
    Code cleanliness Business logic mixed with data Business logic stays clean
    Secrets Sit in source control Can be supplied from outside the build

    Important: The goal is not to delete values from the project. The goal is to stop shipping them glued to the business logic, so the same build can run in many environments.

    6. Reading Values with @Value

    Once values are present in application.properties, we need a way to use them inside Java classes. One simple way is to use @Value. Example with constructor injection:

    @Component
public class PaymentGateway {
    private final String providerName;
    private final int retryCount;

    public PaymentGateway(
            @Value("${payment.provider}") String providerName,
            @Value("${payment.retry-count}") int retryCount) {
        this.providerName = providerName;
        this.retryCount = retryCount;
    }

    public void pay() {
        System.out.println("Payment done using " + providerName);
        System.out.println("Retry count: " + retryCount);
    }
}

    Here @Value("${payment.provider}") means: go to the Spring Environment, find the property named payment.provider, and inject its value here. Similarly, @Value("${payment.retry-count}") means: find the property named payment.retry-count and inject it into this parameter.

    The ${...} placeholder is the key detail. It is not a Java variable; it is a lookup request that Spring resolves at startup.

    7. Default Value with @Value

    Sometimes a property may be missing from application.properties. If the property is missing and no default value is provided, the application may fail during startup. To avoid this, we can provide a default value.

    @Value("${payment.provider:DefaultProvider}")
private String providerName;

    Here ${payment.provider:DefaultProvider} means:

    • use payment.provider if it is available;
    • if it is not available, use DefaultProvider.

    The same syntax works in a constructor parameter, and it is useful when a property is optional.

    Points of the syntax: the placeholder is ${key} and the default is ${key:default}. The colon is the separator, so a misplaced colon silently changes the key you are asking for.

    8. Problem with Too Many @Value

    @Value is simple and useful for small cases. But imagine we have many related properties, such as payment.provider, payment.retry-count, payment.enabled and payment.timeout. If we use @Value, we need to inject every value separately:

    @Value("${payment.provider}") private String provider;
@Value("${payment.retry-count}") private int retryCount;
@Value("${payment.enabled}") private boolean enabled;
@Value("${payment.timeout}") private int timeout;

    This works, but it becomes messy when the number of properties increases. Every new property means another annotation, another field, and another place to keep in sync. For grouped configuration, Spring Boot provides a cleaner option: @ConfigurationProperties.

    Interviewer's perspective: This is the "when not to use @Value" question. The expected answer is not "it is wrong" but "it does not scale for a group of related keys; the boilerplate grows and the grouping is lost."

    9. What Is @ConfigurationProperties?

    @ConfigurationProperties is used to bind a group of related configuration properties to a Java object. Instead of injecting every property separately, we create one configuration class:

    package in.strikes.demo;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.stereotype.Component;

@Component
@ConfigurationProperties(prefix = "payment")
public class PaymentProperties {
    private String provider;
    private int retryCount;
    private boolean enabled;
    private int timeout;

    public String getProvider() { return provider; }
    public void setProvider(String provider) { this.provider = provider; }

    public int getRetryCount() { return retryCount; }
    public void setRetryCount(int retryCount) { this.retryCount = retryCount; }

    public boolean isEnabled() { return enabled; }
    public void setEnabled(boolean enabled) { this.enabled = enabled; }

    public int getTimeout() { return timeout; }
    public void setTimeout(int timeout) { this.timeout = timeout; }
}

    The prefix is @ConfigurationProperties(prefix = "payment"). This means Spring Boot will look for all properties starting with payment, then bind them to this class:

    Property key Java field
    payment.provider provider
    payment.retry-count retryCount
    payment.enabled enabled
    payment.timeout timeout

    Now this configuration class can be injected wherever needed. PaymentGateway simply takes PaymentProperties in its constructor and reads getProvider(), getRetryCount(), isEnabled() and getTimeout(). This is cleaner because all payment-related configuration is stored in one object. The business class now depends on one typed object instead of four loose strings.

    10. Relaxed Binding: payment.retry-count to retryCount

    Why does payment.retry-count map to retryCount? This happens because of relaxed binding. Spring Boot is flexible with property names, so this property:

    payment.retry-count=3

    can bind to the Java field private int retryCount;. Spring Boot understands different naming formats such as retry-count, retry_count and RETRY_COUNT. In Java, we usually write field names in camelCase: retryCount. In properties files, we usually write names in kebab-case: retry-count. Spring Boot can connect both of them. For beginners, the simplest way to explain it is: Spring Boot can automatically convert common property naming styles into Java field naming style.

    Mnemonic: "Kebab in the file, camel in the field, Spring bridges the two" -> K-F-C (Kebab, Field, Connection).

    Important: Relaxed binding is a feature of @ConfigurationProperties. @Value("${payment.retry-count}") must match the exact key text; it does not get the same relaxed name conversion.

    11. @Value vs @ConfigurationProperties

    Use @Value when you need one or two simple values. Use @ConfigurationProperties when many related values belong to the same group.

    Aspect @Value @ConfigurationProperties
    Best for Single value, small demo Grouped configuration
    Binding One annotation per value One class per prefix
    Boilerplate Grows with each key Constant after the class exists
    Naming Exact key text Relaxed binding supported
    Type safety Field-level Typed object
    Readability Fine for a few keys Better for many keys
    Large applications Repetitive Cleaner

    Simple rule: for one or two values, @Value is fine. For a group of related values, prefer @ConfigurationProperties.

    Golden rule: If your keys share a common prefix, that prefix is telling you to make a @ConfigurationProperties class.

    12. Why Do We Need Runner Interfaces?

    In a web application, code usually runs when an HTTP request comes:

    Browser/Postman sends request
        |
        v
Controller receives request
        |
        v
Service method executes

    But in this lecture we are not using spring-boot-starter-web with a controller endpoint, a browser request or a Postman request. So we need a way to run some code after the Spring Boot application starts. Spring Boot gives us two common interfaces for this:

    • CommandLineRunner;
    • ApplicationRunner.

    These interfaces allow us to run code after the Spring container is ready. That is the key phrase: after the container is ready, which means dependencies are injected and configuration is bound.

    Interviewer's perspective: "Runner" confuses people because it sounds like you start it. You do not. You register a bean; Spring Boot finds it and invokes it once after startup.

    13. Why Not Call the Bean Manually from main()?

    Technically, we can do this inside main():

    ConfigurableApplicationContext context = SpringApplication.run(DemoApplication.class, args);
PaymentGateway paymentGateway = context.getBean(PaymentGateway.class);
paymentGateway.pay();

    This works. But this should not be the main approach in a Spring Boot application. Why? Because it brings us back to a manual style:

    1. start context manually;
    2. fetch bean manually;
    3. call method manually.

    A better Spring Boot style is: let Spring create a bean that runs automatically after startup. That is where runner interfaces help.

    Important: The runner is itself a bean. You do not call it. Spring discovers it and calls its run method for you, which is exactly the Inversion of Control that Spring Boot is built on.

    14. CommandLineRunner and Passing Arguments

    CommandLineRunner is a Spring Boot interface used to run code after the Spring application has started. Example:

    package in.strikes.demo;

import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

@Component
public class DemoRunner implements CommandLineRunner {
    private final PaymentGateway paymentGateway;

    public DemoRunner(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    @Override
    public void run(String... args) {
        paymentGateway.pay();
    }
}

    What happens here:

    Spring creates DemoRunner as a bean
        |
        v
Spring injects PaymentGateway into DemoRunner
        |
        v
Spring Boot sees DemoRunner implements CommandLineRunner
        |
        v
Spring Boot calls run() after startup
        |
        v
paymentGateway.pay() executes

    The method signature is public void run(String... args). Here String... args means the method can receive multiple command-line arguments as strings.

    Suppose we run the application from the terminal as java -jar app.jar hello world. Then inside CommandLineRunner, a loop over args prints:

    hello
world

    CommandLineRunner receives arguments as a simple string array.

    15. ApplicationRunner

    ApplicationRunner is similar to CommandLineRunner. The difference is that it provides arguments in a more structured form using ApplicationArguments. Its method signature is public void run(ApplicationArguments args). Instead of raw string arguments, Spring Boot gives us an ApplicationArguments object, and this object can understand option arguments more clearly.

    For example, if we run java -jar app.jar --provider=Razorpay --retry=3, ApplicationRunner can read these as named options using args.getOptionValues("provider") and args.getOptionValues("retry").

    Aspect CommandLineRunner ApplicationRunner
    Method run(String... args) run(ApplicationArguments args)
    Argument form Raw string array Structured object
    Option parsing Do it yourself Built into ApplicationArguments
    Named options Not distinguished Read via getOptionValues(name)
    When to use Simple arguments Options like --key=value
    Timing After startup After startup

    So the simple difference is: CommandLineRunner gives raw String arguments; ApplicationRunner gives structured ApplicationArguments.

    Interviewer's perspective: The expected distinction is not "they are the same." It is: both run after startup, but ApplicationRunner gives you parsed, named access to arguments while CommandLineRunner hands you the raw array.

    16. Complete Startup Flow

    A simplified Spring Boot startup flow looks like this:

    main() method starts
        |
        v
SpringApplication.run() executes
        |
        v
Spring Boot prepares the Environment
        |
        v
Configuration values are loaded
(application.properties, application.yml,
 environment variables, command-line arguments, etc.)
        |
        v
ApplicationContext is created
        |
        v
@SpringBootApplication is processed
        |
        v
@ComponentScan scans the package
        |
        v
@Component / @Service / @Repository / @Controller
classes are discovered
        |
        v
@EnableAutoConfiguration checks dependencies on the classpath
        |
        v
Matching auto-configurations are applied
        |
        v
Beans are created
        |
        v
Dependencies are injected
        |
        v
Configuration values are injected or bound
(@Value / @ConfigurationProperties)
        |
        v
CommandLineRunner / ApplicationRunner executes
        |
        v
Application either exits or keeps running
depending on the type of application

    In simple words: Spring Boot starts the container, loads configuration, scans classes, creates beans, injects dependencies, applies auto-configuration, and finally runs startup logic.

    Important: Notice the order. Configuration is loaded into the Environment before beans are created, which is why @Value and @ConfigurationProperties can be satisfied during bean creation. The runners run last, after everything is ready.

    17. Myth vs Reality

    Myth Reality
    "Values in application.properties are automatically external." A file under src/main/resources is packaged in the JAR; externalization comes from override sources or an external file.
    "@Value and @ConfigurationProperties are interchangeable." Both read config, but @Value injects one key and @ConfigurationProperties binds a group to a typed object.
    "Renaming application.properties is fine." The name and location are the convention Spring Boot loads by default.
    "Spring Boot only supports .properties." It also supports application.yml; the difference is mainly writing style.
    "A runner is called by main()." A runner is a bean; Spring discovers it and calls run after startup.
    "CommandLineRunner and ApplicationRunner differ in timing." Both run after startup; they differ in how arguments are delivered.
    "@Value can leave a missing property silent." A missing property with no default may fail startup; use ${key:default} when optional.

    18. Common Trap Questions

    Trap 1 - "A properties file is always external configuration." Verdict: Partly false. Placed in src/main/resources, it is packaged inside the JAR and still needs a rebuild when changed in source. True externalization means overriding from outside: env vars, command-line args, system properties, or an external file.

    Trap 2 - "application.properties is the only supported format." Verdict: False. Spring Boot also supports application.yml; both hold the same configuration, differing mainly in writing style.

    Trap 3 - "@Value is always better than @ConfigurationProperties." Verdict: False. @Value is fine for one or two simple values; for many related properties it becomes repetitive and messy.

    Trap 4 - "payment.retry-count cannot bind to retryCount." Verdict: False. Relaxed binding converts kebab-case, snake_case and upper-case forms into the camelCase field name.

    Trap 5 - "If a property is missing, @Value quietly uses null." Verdict: False. Without a default, a missing property may fail during startup; provide ${payment.provider:DefaultProvider} for optional values.

    Trap 6 - "Runners run while the container is still starting." Verdict: False. CommandLineRunner and ApplicationRunner run after the Spring container is ready and dependencies are injected.

    Trap 7 - "Calling context.getBean(...) from main() is the Spring way." Verdict: False. It compiles and runs, but it is manual style. The Spring Boot way is to let a bean run automatically, which is what runners are for.

    19. Points to Remember

    1. Hardcoding values forces change code, recompile, rebuild and redeploy cycles.
    2. application.properties is a key-value file loaded by convention from src/main/resources.
    3. YAML (application.yml) is an equally valid format with a different writing style.
    4. A file inside src/main/resources is packaged in the JAR; externalization means overriding from outside.
    5. Externalized configuration keeps changeable values out of Java business logic.
    6. @Value("${key}") injects a single value; ${key:default} supplies a fallback.
    7. Many related properties make @Value repetitive and hard to maintain.
    8. @ConfigurationProperties(prefix = "payment") binds a group of keys to a typed Java object.
    9. Relaxed binding maps kebab-case keys to camelCase fields (payment.retry-count to retryCount).
    10. CommandLineRunner gives raw strings; ApplicationRunner gives structured ApplicationArguments, both after startup.

    20. Likely Interview Questions

    Question Crisp Answer
    Why do we need configuration in Spring Boot? To keep values that change (provider, timeout, flags, URLs, ports, keys) out of Java code, avoiding recompile/rebuild/redeploy for every change.
    What is application.properties? A key-value configuration file Spring Boot reads automatically from src/main/resources by convention.
    Is it really external? Not automatically; when packaged it lives in the JAR. True externalization overrides it from env vars, command-line args, system properties or external files.
    How does @Value work? It reads a property from the Spring Environment using ${key} and injects it into a field or constructor parameter.
    How do you give a default with @Value? Use ${key:default}; the value after the colon is used when the property is missing.
    Why not use @Value everywhere? It becomes repetitive and messy when many related properties are injected one by one.
    What is @ConfigurationProperties? An annotation that binds a group of related properties sharing a prefix to a Java object's fields.
    How does payment.retry-count map to retryCount? Relaxed binding; Spring Boot converts kebab-case, snake_case and upper-case names to camelCase fields.
    @Value vs @ConfigurationProperties? @Value for one or two simple values; @ConfigurationProperties for a group of related values and cleaner code.
    Why runner interfaces? A web app runs on requests; runners let a non-web app run code after the container is ready.
    CommandLineRunner vs ApplicationRunner? CommandLineRunner gives raw String... args; ApplicationRunner gives structured ApplicationArguments with named options.
    Why not call the bean manually from main()? It works but is manual style (start context, fetch bean, call method); runners let Spring invoke startup logic automatically.

    21. Final Summary

    Hardcoded values
        |
        v
application.properties / application.yml
        |
        v
Externalized configuration
(env vars, command-line args, system properties, external files)
        |
        v
@Value (single value)  |  @ConfigurationProperties (group)
        |
        v
Spring loads Environment -> creates beans -> injects / binds values
        |
        v
CommandLineRunner / ApplicationRunner run after startup
    • Hardcoding forces change, recompile, rebuild, redeploy; configuration removes that cycle.
    • application.properties is a key-value file loaded by convention; YAML is an alternative style.
    • A file in src/main/resources is packaged in the JAR; externalization overrides it from outside.
    • @Value injects one value, with ${key:default} for optional properties.
    • Too many @Value annotations become repetitive; @ConfigurationProperties(prefix = "payment") binds the group.
    • Relaxed binding connects kebab-case keys to camelCase fields.
    • Runners execute startup logic after the container is ready; CommandLineRunner is raw, ApplicationRunner is structured.

    One-line takeaway: keep changeable values in configuration, inject them with @Value or bind them with @ConfigurationProperties, and let runner interfaces execute startup logic after the container is ready.
