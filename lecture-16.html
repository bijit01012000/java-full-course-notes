    Encapsulation & Inheritance in Java | Java Packages & Super Keyword

    17 sections · interview-oriented · both themes

    Scope evidence: lecture title "Encapsulation & Inheritance in Java | Java Packages & Super Keyword" (playlist map, verified). Repo evidence: 5 Demo files (Demo.java..Demo5.java) plus code/college/Student.java, code/college/Teacher.java, code/school/Student.java. The cached lecture PDF is image-only and is ignored per project rules.

    Encapsulation and inheritance are the first two of the four pillars of object-oriented programming, and they answer two different questions: how do we protect an object's state, and how do we reuse and specialise behaviour across types? This lecture covers data hiding with private fields and public accessors, the full access-modifier visibility matrix, the package system that gives classes unique names and controls access, the extends relationship and what is (and is not) inherited, and the super keyword in all three of its forms. Constructor order, the classic protected-across-packages nuance, and the inheritance-versus-composition trade-off close the loop before method overriding proper arrives in Lecture 17.

    1. Encapsulation and Data Hiding

    Encapsulation is the bundling of data (fields) and the operations that act on that data (methods) into one unit, the class, while restricting direct access to the internal state from outside. Data hiding is the mechanism that enforces it: fields are declared private, and the outside world touches them only through methods that the class itself controls.

    // Demo.java — encapsulation: private state, validated mutators
public class Demo {
    public static void main(String[] args) {
        Account a = new Account("A001", 500);
        a.deposit(250);                        // validated write
        a.withdraw(10000);                     // rejected by the invariant
        System.out.println(a.getBalance());    // 750.0
        System.out.println(a.getAccountId());  // read-only: no setter exists
    }
}

class Account {
    private final String accountId;   // write once, read only
    private double balance;           // guarded by invariants

    Account(String accountId, double opening) {
        if (opening < 0) throw new IllegalArgumentException("negative opening");
        this.accountId = accountId;
        this.balance = opening;
    }

    public String getAccountId() { return accountId; }  // getter only = read-only
    public double getBalance()   { return balance; }

    public void deposit(double amount) {
        if (amount <= 0) return;                        // validation gate
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= 0 || amount > balance) return;    // invariant preserved
        balance -= amount;
    }
}

    Why bother, when a public double balance would compile just as well? Four reasons, in the order an interviewer wants them:

    1. Invariants and validation — withdraw can refuse to drive the balance negative. A public field cannot say no.
    2. Control over access — getter-only produces a read-only property; a setter-only produces a write-only one; a getter can compute rather than expose storage.
    3. Security — sensitive state (as introduced in Lecture 1) never leaks through an unguarded reference.
    4. Maintainability — the internal representation (say, cents stored as int) can change while the public method signatures stay fixed, so no caller breaks.

    Important Encapsulation is not "make everything private and generate getters and setters for all of it". A setter that assigns blindly to a private field preserves the syntax of encapsulation but discards its purpose. Accessors exist to protect an invariant, not to route around one.

    2. The Access Modifier Matrix

    Java has exactly four access levels. Reading them as a widening ladder — private → default → protected → public — makes the table trivial to reconstruct in an interview.

    Modifier Same class Same package Subclass in another package Unrelated class, other package
    private Yes No No No
    default (package-private, no keyword) Yes Yes No No
    protected Yes Yes Yes (via inheritance) No
    public Yes Yes Yes Yes

    Two facts the table hides and exams love:

    1. Default is not a keyword — it is the absence of a modifier, hence "package-private": visible anywhere inside the same package and nowhere else.
    2. protected in another package is narrower than it looks. A subclass in a different package may access an inherited protected member only through its own type (or a subtype), never through an arbitrary reference of the parent type. That nuance is dissected in Section 11.

    3. Packages: Namespaces and the Directory Convention

    A package is a namespace for classes plus an access boundary. Its name mirrors the directory on disk, and the package declaration must be the very first statement in the file (comments and blank lines aside): package college; compiles to college/Student.class.

    The compiler and the JVM use the package name to build the fully-qualified name of the class: college.Student is not school.Student, even though both are simple-named Student. The convention is lowercase, dot-separated, and often reversed-domain (com.example.app), which guarantees global uniqueness for published libraries.

    The repository for this lecture is organised exactly this way:

    code/
  Demo.java  Demo2.java  Demo3.java  Demo4.java  Demo5.java   (default package)
  college/
    Student.java
    Teacher.java
  school/
    Student.java

    Two Student classes coexist because their packages differ — the collision this lecture is built to demonstrate.

    4. Two Students, Two Packages: Resolving a Name Collision

    // code/college/Student.java
package college;

public class Student {
    private String name;            // private → not accessible in any subclass
    int roll;                       // package-private → visible only inside college
    protected String program;       // visible to subclasses in any package

    public Student(String name, int roll, String program) {
        this.name = name;
        this.roll = roll;
        this.program = program;
    }
    public String getName() { return name; }
}

    // code/school/Student.java — same simple name, different package
package school;

public class Student {
    private String name;
    public Student(String name) { this.name = name; }
    public String getName() { return name; }
}

    // Demo2.java — same simple name, resolved by the import
import college.Student;                 // the simple name "Student" now means college.Student
// import school.Student;               // would be a compile error: duplicate simple name

public class Demo2 {
    public static void main(String[] args) {
        Student c = new Student("Asha", 12, "BSc");       // college.Student
        school.Student s = new school.Student("Ravi");    // fully-qualified to disambiguate
        System.out.println(c.getName() + " / " + s.getName());
    }
}

    Rules the example demonstrates:

    1. You cannot import two classes with the same simple name — the second import is a compile error. One gets the simple name via import; the other must always be written fully qualified (school.Student).
    2. A fully-qualified name always works and can be used inline anywhere a type is expected.
    3. java.lang (String, System, Object, Math, ...) is auto-imported into every file; all other packages require an explicit import or a fully-qualified name.

    5. import, Wildcards and Fully-Qualified Names

    Form Syntax Scope Trade-off
    Single-type import import java.util.ArrayList; Exactly one class Precise, self-documenting; the recommended default
    On-demand (wildcard) import java.util.*; All types in the package Shorter, but hides dependencies and risks accidental collisions
    Fully-qualified name java.util.ArrayList list = ...; The single reference No import needed; verbose; the tool for disambiguation
    Auto-import java.lang.* (implicit) Every compilation unit Convenient; java.lang classes need no import

    Wildcard imports do not cost performance and do not "import the whole package" at runtime — they are compile-time conveniences only. Their real cost is readability: a long list of explicit imports tells a reviewer precisely where each type comes from. When two wildcards collide on the same simple name (java.util.Date and java.sql.Date), neither is imported and compilation fails until you write one fully qualified.

    Interviewer's perspective "Does import java.util.*; slow the program down?" No. The import section is purely a compile-time naming aid; the JVM loads only the classes actually referenced. The argument against wildcards is clarity and collision-safety, not speed.

    6. Inheritance: extends and the is-a Relationship

    Inheritance lets a class acquire the accessible members of another class, modelling an is-a relationship: a Student is a Person; a Car is a Vehicle. The subclass (child, derived) uses extends to name its superclass (parent, base), as in class Student extends Person { ... }.

    The rules:

    1. Single inheritance of classes. A Java class extends exactly one class. You cannot write class X extends A, B. (Multiple type inheritance is available only through interfaces — Lecture 24.)
    2. Members inherited — accessible fields and methods are inherited as if declared in the child. The child may add new members or override inherited behaviour.
    3. private members are not inherited. They exist in the parent subobject, but the child cannot name them directly; it reaches them only through inherited public or protected accessors.
    4. Constructors are not inherited. They are not members in the inheritable sense; the child declares its own and chains to a parent constructor explicitly.
    5. Object is the root of every class. Write class A { } and it is really class A extends Object, inheriting toString, equals, hashCode, and the rest (Lecture 22).

    Important "Not inherited" for private deserves precision: the private field still exists inside a child object (the parent subobject is constructed), but the child's code has no name that resolves to it. Its value is reachable only via whatever the parent exposes.

    7. The super Keyword: Constructors, Fields and Methods

    super is a reference to the immediate superclass subobject, and it has exactly three uses.

    // Demo3.java — super(...), super.field, super.method()
class Person {
    String name;
    Person(String name) { this.name = name; }
    void introduce() { System.out.println("Person: " + name); }
}

class Student extends Person {
    int roll;
    Student(String name, int roll) {
        super(name);                 // 1) parent constructor — MUST be the first statement
        this.roll = roll;
    }
    @Override
    void introduce() {
        super.introduce();           // 3) call the parent version ...
        System.out.println("Student roll: " + roll);   // ... then extend the behaviour
    }
}

public class Demo3 {
    public static void main(String[] args) {
        Student s = new Student("Meera", 7);
        s.introduce();
    }
}
    1. super(...) invokes a parent constructor. It must be the first statement in the child constructor. If you write none, the compiler inserts an implicit no-argument super() call — so a parent that declares only parameterised constructors and no no-arg constructor makes the child fail to compile until it chains explicitly. Because every chain bottoms out at Object, the implicit call ultimately reaches Object().
    2. super.field reads a parent field that has been shadowed by a same-named child field. Shadowing is legal but confusing; prefer distinct names in real code.
    3. super.method() invokes the parent's implementation from a method that the child has overridden — the standard way to extend rather than replace behaviour.

    Note what super is not: it is not a reference to a parent object. There is one object, built from the parent part outwards; super merely selects the parent's version of a member.

    8. Method Overriding Preview and Blocking Inheritance

    Overriding is the runtime-polymorphism mechanism that Lecture 17 develops fully; here we cover just enough to make super meaningful. A child overrides a method by declaring the same signature (name plus parameter types) and the same or a covariant return type. The @Override annotation is optional but strongly recommended: it makes the compiler verify that a parent method really is being overridden, catching typos that would otherwise silently overload instead.

    Aspect Overriding Overloading
    Where it happens Parent and child classes Usually one class
    Signature Identical (name + parameters) Same name, different parameters
    Return type Same, or a covariant subtype Unconstrained
    Binding Runtime (dynamic dispatch) Compile time (static)
    Annotation @Override recommended None
    Visibility May widen, never narrow Irrelevant
    Purpose Specialise inherited behaviour Convenience variants of one operation

    Two constructs stop inheritance from being usable where it is unwanted (both from the final family, Lecture 15):

    1. A final method cannot be overridden — the parent's behaviour is locked.
    2. A final class cannot be extended at all — used for security- and correctness-sensitive types such as String.

    9. Inheritance vs Composition

    Behaviour reuse has a second, often safer route: hold the other object as a field and delegate to it. This is composition, and its rule of thumb — favour composition over inheritance — comes from the cost of coupling to a parent's internals.

    Aspect Inheritance (is-a) Composition (has-a)
    Relationship Student is a Person Car has an Engine
    Mechanism class Student extends Person private Engine engine;
    Coupling Tight — child depends on parent internals Loose — only the collaborator's interface matters
    Binding Fixed at compile time Swappable at runtime via the reference
    Change impact Fragile base class — parent edits ripple down Isolated — the wrapped type can change freely
    Multiple reuse One superclass only Compose arbitrarily many
    Encapsulation Breaks it unless designed carefully Preserves it by default
    Guidance Use for a genuine is-a that respects the LSP Prefer for behaviour reuse and flexibility

    The fragile base class problem is the concrete failure: a parent adds a new method or changes an existing one, and an unrelated child method collides with it — the child compiles and behaves wrongly without its author touching a line. Composition cannot suffer this because the collaborator's methods are named through a distinct field.

    10. Constructor Chaining Across the Hierarchy

    Construction always runs from the root down. The super() call (explicit or implicit) means Object's constructor body completes before Person's, and Person's before Student's — even though the child's constructor is the one you called.

    new Student(...)
      |
      v
Student constructor
      |  super(...)  (first statement; implicit no-arg if absent)
      v
Person constructor
      |  super()     (implicit — Person extends Object)
      v
Object constructor          <-- runs first (root), then unwinds back down:
      |                          Object body -> Person body -> Student body
      v
object fully initialised

    The ordering rule in one line: initialisation runs root-first, but the constructor bodies execute in the order the chain unwinds, parent-before-child. This is why a parent constructor that calls a method the child overrides is dangerous — see the pitfall catalogue.

    11. The protected-Across-Packages Nuance

    The single most examined access rule: protected grants a subclass in another package access only through inheritance. Concretely, if college.Student declares protected String program;, then a school.Teacher extends college.Student may read this.program (allowed — the inherited protected member) and other.program where other is another Teacher (allowed — the subclass's own type), but plain.program where plain is a college.Student reference is a compile error (the access is not through the subclass's own type).

    The rationale is encapsulation: the parent lets subclasses use the member to build themselves, but does not let the subclass reach into arbitrary parent instances and read their internals. Meanwhile, a default (package-private) member of college.Student is not visible to school.Teacher at all — a separate subclass elsewhere never inherits package-private access.

    Interviewer's perspective "Can a subclass in a different package access a protected member of its parent?" Yes — through inheritance, on its own type. The follow-up that separates candidates is "can it access it on a plain parent reference?" No. Both halves are required for the mark.

    12. The Pitfall Catalogue

    Pitfall What goes wrong Correct approach
    Child reads a private parent field directly Compile error — private members are not accessible to the child Use the parent's public/protected accessor
    super() not the first statement Compile error: "call to super must be first statement" Move super(...) to line one of the child constructor
    Parent has no no-arg constructor Child constructor fails to compile when the implicit super() is inserted Chain explicitly: super(args)
    Calling an overridable method from a constructor Child field is still at its default value when the parent calls the override — silent wrong results Avoid overridable calls in constructors; make them private/final (Lecture 13)
    Package-private member expected in an outside subclass Invisible — default access does not cross packages Widen to protected or public deliberately
    Parent reference to a protected member from a subclass Compile error in the other package Access it only through the subclass's own type
    Deep inheritance hierarchies Brittle, hard to reason about, fragile base class Keep hierarchies shallow; favour composition
    this.method() vs super.method() confusion this. dispatches to the override; super. forces the parent version Choose deliberately; super. for extension
    Reducing visibility when overriding Compile error — an override may not be more restrictive Keep or widen the access modifier
    Public fields with no accessors Invariants unenforced; representation frozen Encapsulate from the start

    13. Myth vs Reality

    Myth Reality
    "A private field is inherited because the object contains it" The field's storage exists in the parent subobject, but the child has no accessible name for it — private members are not inherited in the usable sense.
    "Constructors are inherited" No constructor is inherited; the child declares its own and explicitly or implicitly chains to a parent constructor.
    "A class can extend multiple classes" Java permits single class inheritance only; multiple type inheritance is available via interfaces (Lecture 24).
    "super refers to a separate parent object" There is one object; super is a typed view that selects the parent's version of a member.
    "Wildcard imports slow the program" Imports are compile-time naming only; runtime loading is driven by actual references.

    14. Common Trap Questions

    Trap 1 — The implicit super: "A parent declares only Parent(int x). Why does a child constructor fail to compile?" The compiler inserts an implicit super() (no-arg) as the child's first statement, but no no-arg parent constructor exists. Fix: chain explicitly with super(arg) as the first statement.

    Trap 2 — The protected reference: "Subclass B extends A in another package — can B read A's protected field f on a variable of type A?" No. Protected access across packages is granted only through inheritance: B may touch f on this or on a B, not on an arbitrary A reference.

    Trap 3 — Calling an overridable method in a constructor: "Why is name still null when the parent constructor calls print(), which the child overrides?" The parent constructor runs before the child's field initialisers and constructor body. The override executes against the child before the child's fields are set, so it sees default values. Make the called method final or private.

    Trap 4 — Package-private in a far subclass: "A default field in college.Student — is it visible to school.Teacher extends college.Student?" No. Default access stops at the package boundary; only protected (via inheritance) and public cross into a subclass in another package.

    Trap 5 — Duplicate simple names: "Can I import college.Student; and import school.Student; in the same file?" No — a compile error on the duplicate simple name. Import one and fully-qualify the other (school.Student).

    Trap 6 — Redefining main: "The child inherits main from the parent — does the JVM launch the parent or the child?" Neither automatically. The JVM launches the exact class you name on the command line and looks for main there; if that class declares none, it may inherit the parent's public static void main. Launch the class whose behaviour you intend.

    15. Points to Remember

    1. Encapsulation = private state plus controlled accessors; its purpose is invariants, control, security and maintainability, not ceremony.
    2. Access ladder widens private → default → protected → public; only public is visible everywhere.
    3. Default (package-private) access never crosses a package boundary, even for subclasses.
    4. protected crosses into a subclass in another package, but only through inheritance (the subclass's own type).
    5. A package is a namespace and an access boundary; its name mirrors the directory, and package is the first statement in the file.
    6. java.lang is auto-imported; other packages need import or a fully-qualified name; two same-simple-name imports collide.
    7. Inheritance models is-a through extends; Java allows single class inheritance only, with Object as the universal root.
    8. Private members are not accessible to children; constructors are never inherited; accessible fields and methods are.
    9. super(...) must be the constructor's first statement; if absent, an implicit no-arg super() is inserted; super.field and super.method() select the parent version.
    10. Overriding is same-signature, runtime-dispatched, annotated @Override; overloading is same-name, different-parameters, compile-time — final methods and classes block inheritance, and composition is favoured over inheritance for reuse.

    16. Likely Interview Questions

    Question Crisp Answer
    What is encapsulation? Bundling state and behaviour in a class and hiding the state behind controlled accessors; ensures invariants and allows the representation to change.
    Difference between encapsulation and abstraction? Encapsulation hides how data is stored and protected; abstraction hides what an implementation does behind a contract (Lecture 17).
    Explain the four access modifiers. private (class only), default/package-private (package only), protected (package plus subclasses via inheritance), public (everywhere).
    Can a subclass access a private parent field? Not directly; only through an inherited public/protected accessor. The field's storage exists but has no accessible name in the child.
    Are constructors inherited? No. The child declares its own and chains to a parent constructor with super(...) or an implicit no-arg call.
    What are the uses of super? super(...) for the parent constructor (first statement), super.field for a shadowed field, super.method() for the parent's implementation.
    Does Java support multiple inheritance? Not of classes — one extends only. Multiple type inheritance comes from interfaces (Lecture 24).
    What is the root class of every Java class? java.lang.Object; direct or indirect, every class extends it (Lecture 22).
    How does a subclass in another package use a protected member? Only through inheritance — on itself or another instance of the subclass, not on a plain parent reference.
    Overriding vs overloading in one line? Overriding is runtime, same signature, parent/child; overloading is compile-time, same name with different parameters, usually one class.
    How do you prevent inheritance or overriding? Mark the class final to block extension; mark the method final to block overriding (Lecture 15).
    Inheritance or composition — which and why? Prefer composition for behaviour reuse — looser coupling and runtime flexibility; use inheritance only for a genuine is-a that respects substitutability.

    17. Final Summary

    Account ----------> private balance  <== getters/setters ==>  outside world
one class, one unit: data + behaviour, state guarded by invariants

package college.Student  \  same simple name
package school.Student   /  distinct fully-qualified names
import one, fully-qualify the other; java.lang is free

new Student(...)  ->  Student ctor  ->super->  Person ctor ->super-> Object ctor
                                                        (root initialises first)

extends = is-a   |   super(...) first   |   super.method() = parent version
private not accessible to child   |   constructors not inherited   |   single inheritance
    • Encapsulation → private fields, public accessors, protected invariants; read-only via getter only.
    • Access matrix → public ⊃ protected (package + subclasses) ⊃ default (package) ⊃ private (class); only public is visible everywhere.
    • Packages → namespace + access boundary; directory-mirrored names; college.Student ≠ school.Student; import resolves simple names, fully-qualified names break ties.
    • Inheritance → extends for is-a; single class only; Object at the root; private members and constructors are not inherited.
    • super → super(...) (must be first, implicit no-arg if omitted), super.field, super.method() for the parent implementation.
    • Construction → root-first initialisation; parent constructor body always completes before the child's.
    • Design → favour composition over inheritance; final blocks extension and overriding; overriding proper belongs to Lecture 17.

    Golden rule Encapsulation protects state by keeping fields private and letting methods guard the invariants, while inheritance reuses behaviour only when the is-a relationship is genuine — and super is how a child deliberately builds on, rather than blindly replaces, what the parent provides.

    One-line takeaway: hide the data behind validated accessors, name every class uniquely through its package, extend only a true is-a, and use super to chain construction and invoke the parent's version when a child specialises behaviour.
