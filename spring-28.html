    Part 5 · Persistence & ORM · Lecture 28

    Hibernate Fundamentals with Spring Boot

    16 sections · interview-oriented · both themes

    Scope evidence: "Hibernate Fundamentals with Spring Boot | CRUD & Entity Mapping" (playlist map, verified). Repo folder is the hibernateDemo project (package in.coderarmy.hibernateDemo): HibernateDemoApplication, model.Student, model.Address (@Embeddable), model.StudentStatus enum, model.BooleanToStringConverter (@Converter), plus repository.StudentRepository, service.StudentService, controller.StudentController, application.properties, and the lecture notes cached in the repo.

    This lecture is the bridge from raw data access to real persistence. It starts with the structural gap between Java objects and relational tables, shows why Spring JDBC alone still leaves manual work, and then introduces ORM, the JPA specification, and Hibernate as its implementation. From there it walks the entity mapping annotations field by field: identity, columns, enums, embeddables, converters, and transient fields, ending with CRUD through a Spring Data JPA repository running against MySQL.

    1. Java Objects vs Relational Tables

    Consider a plain Java class:

    public class Student {
    private Long id;
    private String name;
    private String email;
    private Integer age;
}

    The equivalent relational representation might be:

    CREATE TABLE students (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE,
    age INT
);

    The object and the row contain similar information, but they are fundamentally different structures. Java understands classes, objects, references, inheritance, encapsulation, object identity, method behaviour, and collections. A relational database understands tables, rows, columns, primary keys, foreign keys, constraints, joins, and SQL data types.

    Java world Relational world
    Classes Tables
    Objects Rows
    Fields Columns
    References Foreign keys
    Collections Related rows
    Object identity Primary key
    Inheritance / polymorphism No direct equivalent
    Method behaviour No direct equivalent
    Encapsulation Constraints

    Important: Because the two worlds disagree, Java cannot directly save an object into MySQL. The object must first be translated into SQL-compatible values, and this translation is exactly what persistence frameworks are built to handle.

    A quick mnemonic for the mapping direction: T-R-C (Tables for Classes, Rows for Objects, Columns for Fields), extended by References for foreign keys and Collections for related rows.

    2. Persistence with Spring JDBC and Its Remaining Limitation

    Spring JDBC is already a large improvement over raw JDBC. An insertion may look like this:

    public int save(Student student) {
    String sql = """
        INSERT INTO students(name, email, age)
        VALUES (?, ?, ?)
        """;
    return jdbcTemplate.update(
        sql,
        student.getName(),
        student.getEmail(),
        student.getAge()
    );
}

    This is much cleaner than raw JDBC, but the developer still performs the translation manually. Spring JDBC manages much of the JDBC infrastructure, yet it does not understand the semantic relationship between the Student class and the students table.

    The manual work shows up in three places:

    1. Manual SQL writing. Every operation needs hand-written SQL:
    Insert:  INSERT INTO students(name, email, age) VALUES (?, ?, ?);
Select:  SELECT id, name, email, age FROM students WHERE id = ?;
Update:  UPDATE students SET name = ?, email = ?, age = ? WHERE id = ?;
Delete:  DELETE FROM students WHERE id = ?;

    1. Manual parameter binding. Spring JDBC removes direct PreparedStatement handling, but values must still be passed in the correct order. First ? is name, second is email, third is age, fourth is id. A wrong order may not cause a compilation error at all.

    2. Manual row-to-object mapping. When reading data, the opposite translation is needed:

    private final RowMapper<Student> studentRowMapper =
    (resultSet, rowNumber) -> {
        Student student = new Student();
        student.setId(resultSet.getLong("id"));
        student.setName(resultSet.getString("name"));
        student.setEmail(resultSet.getString("email"));
        student.setAge(resultSet.getInt("age"));
        return student;
    };

    This is not necessarily bad. SQL gives precise control. The problem appears when an application has hundreds of entities, many relationships, and repeated CRUD operations: the amount of repetitive translation code grows rapidly.

    Interviewer's perspective: Expect "Why not just use Spring JDBC?" The right answer is not "it is bad." Spring JDBC is excellent for fine-grained SQL. The issue is that it still forces a human to translate objects to rows and rows back to objects for every single operation.

    3. What Is ORM? The Object-Relational Impedance Mismatch

    The differences between object models and relational models are collectively called object-relational impedance mismatch.

    Object-Relational Mapping, or ORM, is the process of defining how:

    • Java classes map to database tables;
    • Java objects map to database rows;
    • Java fields map to database columns;
    • Java references map to foreign-key relationships;
    • Java collections map to related rows.

    For example, a Student class declares that the class maps to the students table, the id field maps to the id column, and the name field maps to its column. This metadata tells the framework how to translate, and it is declared once and reused during inserts, selects, updates, and deletes.

    An ORM framework normally handles several responsibilities:

    Responsibility What it means
    Mapping metadata Understands how classes and attributes correspond to tables and columns
    SQL generation Generates SQL based on entity operations
    Parameter binding Extracts values from the entity and binds them to JDBC parameters
    Result-set mapping Converts database rows back into entity objects
    Relationship management Turns object references and collections into foreign-key and join-table operations
    Caching May avoid unnecessary database access via first-level and optional second-level caches
    Transaction integration Coordinates entity operations with database transactions

    Golden rule: Declare the mapping once, and every future operation benefits. The annotation metadata is the single source of truth for how objects become rows and rows become objects.

    4. Hibernate: JPA Specification vs Hibernate Implementation

    Hibernate is an ORM framework for Java and JVM applications. Hibernate operates above JDBC:

    Application
    |
    v
Hibernate
    |
    v
JDBC
    |
    v
JDBC Driver
    |
    v
Database

    JPA originally meant Java Persistence API. The current standard is named Jakarta Persistence, though developers still commonly use the term JPA. It defines contracts such as jakarta.persistence.Entity, jakarta.persistence.Id, jakarta.persistence.EntityManager, jakarta.persistence.EntityManagerFactory, and jakarta.persistence.PersistenceContext.

    A specification does not perform the work by itself. An implementation is required, and Hibernate implements the Jakarta Persistence specification. Therefore, when application code uses import jakarta.persistence.EntityManager;, the interface is defined by Jakarta Persistence but the runtime object may be implemented by Hibernate. This resembles other interface-and-implementation relationships, such as the List interface and the ArrayList implementation.

    Layer What it is Role
    Jakarta Persistence (JPA) Specification Defines the ORM API and contracts
    Hibernate Implementation Does the real ORM work at runtime
    Spring Data JPA Spring abstraction Repository-style data access on top

    Other JPA providers have historically included EclipseLink and OpenJPA, but Spring Boot commonly uses Hibernate when the JPA starter is present.

    Mnemonic: JPA says what; Hibernate does how.

    Interviewer's perspective: "JPA vs Hibernate" is a spec-versus-implementation question. A strong answer also names the analogy (List vs ArrayList) and notes that Spring Boot wires Hibernate in automatically through the JPA starter.

    5. Required Dependencies, Project Structure, and MySQL Setup

    Create a Spring Boot project with two dependencies:

    1. Spring Data JPA. The starter spring-boot-starter-data-jpa brings configuration and dependencies. In this lecture we deliberately focus on the lower-level operations first; Spring Data repositories would otherwise hide many of these operations.
    2. MySQL Driver.

    Hibernate can manage tables, but for a basic MySQL setup the database is created first:

    CREATE DATABASE student_db;
USE student_db;

    The project structure:

    hibernate-demo
+-- pom.xml
+-- src
    +-- main
        +-- java
        |   +-- in.coderarmy.hibernateDemo
        |       +-- HibernateDemoApplication.java
        |       +-- model
        |       |   +-- Student.java
        |       |   +-- Address.java
        |       |   +-- StudentStatus.java
        |       |   +-- BooleanToStringConverter.java
        |       +-- repository
        |       |   +-- StudentRepository.java
        |       +-- service
        |       |   +-- StudentService.java
        |       +-- controller
        |           +-- StudentController.java
        +-- resources
            +-- application.properties

    DataSource configuration in application.properties:

    spring.datasource.url=jdbc:mysql://localhost:3306/hibernate_demo
spring.datasource.username=root
spring.datasource.password=your_password

    Spring Boot uses these properties to configure a DataSource. The DataSource supplies JDBC connections to Hibernate.

    Schema generation is controlled by ddl-auto:

    Value Behaviour
    none Hibernate performs no schema action
    validate Hibernate checks whether the existing schema matches the entity mappings; creates nothing
    update Hibernate attempts to update the schema to match the mappings
    create Hibernate drops and recreates the mapped schema at startup; existing data may be lost
    create-drop Hibernate creates the schema at startup and drops it when the persistence factory closes

    For learning, spring.jpa.hibernate.ddl-auto=update is convenient, but it is not a production migration system; production schema changes are usually managed with tools such as Flyway or Liquibase.

    Enable generated SQL while learning:

    spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

    Important: ddl-auto is a development convenience, not a migration strategy. create and create-drop can destroy data, and update is too weak to be a real production change-management tool.

    6. The Entity Class: @Entity, @Table, @Id, @GeneratedValue

    An initial entity looks like this:

    package in.coderarmy.hibernateDemo.model;

import jakarta.persistence.*;

@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private Integer age;

    protected Student() {
    }

    public Student(String name, String email, Integer age) {
        this.name = name;
        this.email = email;
        this.age = age;
    }
    // getters and setters
}

    The annotations, one by one:

    1. @Entity marks the class as a persistent entity that Hibernate manages.
    2. @Table(name = "students") maps the class to the students table.
    3. @Id marks the primary-key field.
    4. @GeneratedValue(strategy = GenerationType.IDENTITY) delegates id generation to the database's identity column.
    5. A no-argument constructor is required by the provider (often declared protected); a convenience constructor is added for application code, and getters and setters complete the bean.

    The class-to-table and field-to-column mapping is metadata Hibernate reads once and reuses for every insert, select, update, and delete.

    Golden rule: The entity is the mapping. Once @Entity, @Table, @Id, and @GeneratedValue are declared, Hibernate knows how to persist the object without a single line of hand-written SQL.

    7. @Column and Field Mapping Options

    @Column tunes how a field maps to a column. Important options include:

    Option Meaning
    name Controls the mapped column name
    nullable Used in schema generation to indicate whether the column may be null
    unique Declares a single-column uniqueness constraint during schema generation
    length Provides the expected string-column length for generated schema
    insertable Controls whether the column appears in generated insert statements
    updatable Controls whether the column appears in generated update statements

    Applied to the entity:

    @Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Column(name = "student_name", nullable = false, length = 100)
private String name;

@Column(nullable = false, unique = true, length = 150)
private String email;

private Integer age;

    For decimal precision, use precision and scale, and prefer BigDecimal when decimal precision matters:

    @Column(precision = 5, scale = 2)
private BigDecimal percentage;

    Conceptually, precision is the total number of digits and scale is the digits after the decimal point.

    Date and time mapping should normally use the modern Java date/time classes:

    Java type Conceptual database type Example
    LocalDate DATE 2000-08-21
    LocalTime TIME 10:30
    LocalDateTime TIMESTAMP 2026-07-25T10:30:00

    Large objects use @Lob, which instructs the provider to use a database-native large-object mapping:

    @Lob
private String profileDescription;

@Lob
private byte[] profileImage;

    Storing large files directly inside the database should be an intentional architectural decision; often the database stores file metadata and an object-storage URL instead.

    Important: nullable, unique, and length are primarily schema-generation hints. When the table already exists, they do not silently rewrite it; the physical schema and the migration tooling remain in charge.

    8. Enum Mapping: @Enumerated ORDINAL vs STRING

    Consider an enum:

    public enum StudentStatus {
    ACTIVE,
    INACTIVE,
    SUSPENDED
}

    An entity field is mapped with @Enumerated:

    @Enumerated(EnumType.STRING)
private StudentStatus status;

    With EnumType.STRING, the database stores the enum names: ACTIVE, INACTIVE, SUSPENDED.

    EnumType.ORDINAL is the default and stores the index position instead. The two behave very differently over time:

    Aspect EnumType.ORDINAL EnumType.STRING
    What is stored The integer index (0, 1, 2) The enum name (ACTIVE)
    Readability in the database Poor; opaque numbers Clear and self-documenting
    Default Yes No, must be declared
    Safety if constants are reordered Fragile; old rows change meaning Safe; names are stable
    Storage size Smallest Larger, but predictable
    Recommendation Avoid for durable data Prefer for durable data

    Interviewer's perspective: The enum trap is reordering. Add a new constant in the middle with ORDINAL and every existing row silently points at the wrong value. The professional choice is @Enumerated(EnumType.STRING), even though it costs a little storage.

    9. Value Types: @Embeddable, @Embedded, @AttributeOverride, @ElementCollection

    Consider a student and an address. A student has independent identity and continues to exist even if the address changes. An address often has no independent identity in the domain: house number, street, city, state, and postal code exist only as part of another object. A student owns the address, which makes Address a good candidate for a value type. Hibernate classifies value types as values whose lifecycle is owned by an entity, whereas entities have independent identity.

    Aspect Entity type Value type (@Embeddable)
    Identity Has its own @Id No independent id
    Lifecycle Managed independently Owned by the embedding entity
    Storage Usually its own table Stored inside the owner's table
    Reuse Can be shared and referenced Copied into each owner
    Example Student, Department Address, PhoneNumber

    Define the value type:

    package in.coderarmy.hibernateDemo.model;

import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;

@Embeddable
public class Address {
    @Column(name = "address_line")
    private String addressLine;
    private String city;
    private String state;
    @Column(name = "postal_code")
    private String postalCode;

    protected Address() {
    }

    public Address(String addressLine, String city, String state, String postalCode) {
        this.addressLine = addressLine;
        this.city = city;
        this.state = state;
        this.postalCode = postalCode;
    }
}

    @Embeddable means the class does not represent an independent entity; its state may be embedded inside an owning entity. An embeddable has no @Id of its own. Its state is stored as an intrinsic part of its owner.

    Use the value inside Student:

    @Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    @Embedded
    private Address address;
}

    The resulting table becomes:

    students
+-- id
+-- name
+-- address_line
+-- city
+-- state
+-- postal_code

    There is no separate address table by default. @Embedded declares an entity attribute whose value is an embeddable object, and the object structure is flattened into the owner's row.

    Why use an embeddable instead of separate fields? Without it, the entity carries addressLine, city, state, and postalCode as unrelated primitives. With it, the Java model becomes more expressive.

    When a student has two addresses, both embeddables would contribute the same column names, which creates conflicting column mappings:

    @Embedded
private Address currentAddress;
@Embedded
private Address permanentAddress;

    The clash is resolved with @AttributeOverride, which replaces a basic mapping originally declared by the embeddable for a particular embedding location:

    @Embedded
@AttributeOverrides({
    @AttributeOverride(name = "addressLine", column = @Column(name = "current_address_line")),
    @AttributeOverride(name = "city", column = @Column(name = "current_city")),
    @AttributeOverride(name = "state", column = @Column(name = "current_state")),
    @AttributeOverride(name = "postalCode", column = @Column(name = "current_postal_code"))
})
private Address currentAddress;

    The resulting table contains id, current_address_line, current_city, current_state, current_postal_code, and the matching permanent_* columns.

    An entity may also own a collection of value types, such as Set<String> skills. A collection cannot normally fit into one relational column, so it is stored in a separate table using @ElementCollection and @CollectionTable:

    @ElementCollection
@CollectionTable(
    name = "student_skills",
    joinColumns = @JoinColumn(name = "student_id")
)
@Column(name = "skill")
private Set<String> skills = new HashSet<>();

    Possible database structure:

    students
+-- id
+-- name

student_skills
+-- student_id
+-- skill

    The values in student_skills are not independent entities; each string belongs to the owning Student. The same approach works for a collection of value objects such as PhoneNumber.

    Important: Use an entity when the object has independent identity (a department exists independently of a particular student, can be shared, queried, updated, and referenced by an identifier). Use an embeddable value when the object lives and dies with its owner.

    10. Attribute Converters (@Convert) and @Transient

    Sometimes the database stores a representation that differs from the Java type. Suppose the database stores Y or N, but Java should use Boolean. An attribute converter bridges the two:

    package in.coderarmy.hibernateDemo.model;

import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

@Converter
public class BooleanToStringConverter
        implements AttributeConverter<Boolean, String> {

    @Override
    public String convertToDatabaseColumn(Boolean attribute) {
        if (attribute == null) {
            return null;
        }
        return attribute ? "Y" : "N";
    }

    @Override
    public Boolean convertToEntityAttribute(String databaseValue) {
        if (databaseValue == null) {
            return null;
        }
        return "Y".equals(databaseValue);
    }
}

    Use it on the field with @Convert:

    @Convert(converter = BooleanToStringConverter.class)
private Boolean active;

    The converter gives the entity a clean Java type while the database keeps its own representation. convertToDatabaseColumn runs on the way out; convertToEntityAttribute runs on the way back in.

    Not every field should be persisted. Sometimes an entity needs a field that lives only in memory:

    @Transient
private String displayName;

    Hibernate ignores a @Transient field entirely: it is never mapped, never written, and never read back.

    Important: @Transient (the JPA annotation) is not the same as Java's transient keyword, even though both mean "not persisted." In JPA code, use @Transient so the provider knows to skip the field.

    11. CRUD with Spring Data JPA and the Entity Lifecycle

    The repository is the entry point for CRUD. A Spring Data JPA repository is declared as an interface:

    package in.coderarmy.hibernateDemo.repository;

import in.coderarmy.hibernateDemo.model.Student;
import org.springframework.data.jpa.repository.JpaRepository;

public interface StudentRepository extends JpaRepository<Student, Long> {
}

    The inherited operations cover the whole CRUD cycle:

    Operation Repository method Typical use
    Create save(student) Insert a new student
    Read one findById(id) Fetch by primary key
    Read all findAll() Fetch every student
    Update save(student) on a managed entity Change fields
    Delete deleteById(id) or delete(student) Remove a row

    Underneath Spring Data JPA, the JPA EntityManager performs the primitive operations: persist(student) inserts, find(Student.class, id) reads, and remove(student) marks an entity for deletion. These operations run inside a transaction, usually opened by @Transactional on the service layer.

    A subtle but important point: for an update, there is no explicit update call. Load a managed entity, change a field, and commit the transaction. Hibernate detects that the loaded object changed and generates the update during flushing; neither an EntityManager.update(student) nor a repository.save(student) is required for an already-managed entity.

    At a high level, an entity moves through lifecycle states:

    new / transient  --persist-->  managed  --commit/flush-->  database
                                   |
                             remove(student)
                                   |
                                   v
                                removed  --flush-->  database delete

    The persistence context tracks managed entities, which is exactly why dirty checking works. The full mechanics belong to the persistence-context discussion; the mental model here is enough.

    Important: remove() operates on a managed entity; Hibernate marks that entity for deletion and the delete is synchronized with the database during flushing. The service layer typically guards against a null lookup and throws an IllegalArgumentException when the id does not exist.

    Interviewer's perspective: The favorite probe is "Where is the update method?" The answer is that update happens implicitly through the managed entity and dirty checking. Candidates who only memorized save miss the whole point of a persistence context.

    12. Myth vs Reality

    Myth Reality
    "Java can save an object directly to MySQL" Java objects and relational rows are different structures; the object must be translated to SQL-compatible values
    "Spring JDBC removes the need to write SQL" It removes much infrastructure boilerplate but SQL, parameter order, and row mapping are still manual
    "JPA and Hibernate are the same thing" JPA/Jakarta Persistence is the specification; Hibernate is one implementation of it
    "ORM means you never touch SQL" ORM generates and manages SQL; it does not remove the relational model or the need to understand it
    "@Enumerated stores the enum name by default" The default is ORDINAL, which stores the index; use EnumType.STRING for durable data
    "An @Embeddable gets its own table and id" It has no @Id; its state is flattened into the owner's table unless it is placed in an element collection
    "@Column(nullable = false) always enforces NOT NULL" It is primarily a schema-generation hint; an existing schema is governed by migration tooling
    "Updates need an explicit update call" A managed entity is flushed automatically; changing a field inside a transaction signals the update

    13. Common Trap Questions

    Trap 1 - "Why can Java not persist an object directly?" Verdict: Because objects and relational tables are fundamentally different structures. Java thinks in classes, objects, references, and identity; the database thinks in tables, rows, columns, keys, and constraints.

    Trap 2 - "Spring JDBC already removes boilerplate, so why use Hibernate?" Verdict: Spring JDBC manages infrastructure but still leaves manual SQL, manual parameter ordering, and manual row mapping. With hundreds of entities and repeated CRUD, that repetitive translation grows rapidly.

    Trap 3 - "JPA and Hibernate are the same." Verdict: False. Jakarta Persistence (JPA) is the specification defining contracts such as Entity, Id, and EntityManager; Hibernate implements that specification. The relationship is like List and ArrayList.

    Trap 4 - "@Enumerated stores the enum name by default." Verdict: False. The default is EnumType.ORDINAL, which stores the integer index. Reordering constants then corrupts the meaning of existing rows, so durable data should use EnumType.STRING.

    Trap 5 - "An @Embeddable needs its own @Id and table." Verdict: False. An embeddable has no independent identity and no @Id; its state is stored as an intrinsic part of the owning entity. @ElementCollection is what puts value types into a separate table.

    Trap 6 - "Updating a field requires calling an update method." Verdict: False. For a managed entity, change the field inside a transaction and commit. Hibernate detects the change and flushes the update; no explicit update call is needed.

    Trap 7 - "ddl-auto=update is safe for production schema management." Verdict: Misleading. It is convenient for learning and early development but is not a migration system; production uses tools such as Flyway or Liquibase.

    14. Points to Remember

    1. Java objects and relational tables are different structures; an object cannot be saved directly, it must be translated into SQL-compatible values.
    2. Spring JDBC removes much JDBC infrastructure boilerplate but still leaves manual SQL, manual parameter ordering, and manual row-to-object mapping.
    3. The gap between the two models is the object-relational impedance mismatch; ORM declares the mapping once and reuses it for inserts, selects, updates, and deletes.
    4. Jakarta Persistence (JPA) is the specification; Hibernate is the implementation; Spring Data JPA sits on top with repository-style access.
    5. Required dependencies are spring-boot-starter-data-jpa plus the MySQL driver; the connection details live under spring.datasource.* in application.properties.
    6. @Entity plus @Table map the class to a table; @Id plus @GeneratedValue(strategy = GenerationType.IDENTITY) map the identity.
    7. @Column tunes name, nullable, unique, length, insertable, and updatable; use precision and scale for BigDecimal, and @Lob for large objects.
    8. @Enumerated(EnumType.STRING) stores enum names and is safer than the default ORDINAL, which stores indexes and breaks when constants are reordered.
    9. @Embeddable and @Embedded store a value type inside the owner's table; @AttributeOverride resolves column clashes and @ElementCollection uses a separate table.
    10. @Convert with an AttributeConverter changes the stored representation, @Transient skips a field, and CRUD runs through the repository with dirty checking handling updates.

    15. Likely Interview Questions

    Question Crisp Answer
    Why can Java not save an object directly into a relational database? Objects and tables are different structures; the object must be translated into SQL-compatible values first.
    What is the object-relational impedance mismatch? The collective difference between object models (classes, references, identity) and relational models (tables, keys, constraints).
    What is ORM? Object-Relational Mapping: defining how classes map to tables, objects to rows, fields to columns, references to foreign keys, and collections to related rows.
    JPA vs Hibernate? JPA/Jakarta Persistence is the specification; Hibernate is the implementation that does the work at runtime.
    Which dependencies are needed? spring-boot-starter-data-jpa and the MySQL driver; Spring Boot's JPA starter brings Hibernate, Spring Data JPA, and Spring ORM.
    What does @Entity and @Table do? @Entity marks a managed class; @Table(name = "...") maps it to a specific database table.
    What is @GeneratedValue(strategy = GenerationType.IDENTITY)? It tells the provider to let the database identity column generate the primary-key value.
    What does @Column(nullable = false, unique = true, length = 150) mean? Schema-generation hints: the column is non-null, unique, and expected to be 150 characters long.
    ORDINAL vs STRING enum mapping? ORDINAL (default) stores the index and is fragile; STRING stores the enum name and is safe across reordering.
    Entity type vs value type? Entities have independent identity and lifecycle; value types (@Embeddable) are owned and stored inside the owner's table.
    What does an AttributeConverter do? It converts between the Java attribute type and the database column type, e.g. Boolean to Y/N via @Convert.
    Does an update need an explicit call? No. A managed entity is watched; changing a field inside a transaction is flushed automatically (dirty checking).
