    Part 1 · Java Basics · Lecture 07

    Java Conditional Statements — If, If-Else, If-Else-If Ladder & Switch

    16 sections · interview-oriented · both themes

    Scope evidence: lecture title "Java Conditional Statements | If, If-Else, If-Else-If Ladder, Switch Explained" (playlist map, verified). This lecture's repo folder contains two code files: Demo.java and Demo2.java. The cached notes PDF is image-only and is ignored per project rules.

    Programs stop being straight-line scripts the moment they can choose between two or more paths, and in Java those choices are written with if, if-else, the if-else-if ladder, the ternary operator and switch. This lecture covers the mechanics of each form, the two rules that make up almost every trap question (conditions must be boolean, and else binds to the nearest if), the classic statement form of switch with its fall-through behaviour, and the modern Java 14+ switch expression with arrow labels and yield. It closes with the decision tables an interviewer expects: when to reach for a ladder versus a switch, and the pitfalls that break careless code.

    1. The Simple if Statement

    The if statement executes a block only when its condition is true. If the condition is false, the block is skipped and execution continues after it.

    // Demo.java — the simplest decision form
public class Demo {
    public static void main(String[] args) {
        int age = 20;
        if (age >= 18) {                    // condition must be boolean
            System.out.println("Eligible to vote");
        }
        System.out.println("Always printed");
    }
}

    Three mechanics:

    1. The condition is evaluated once, and its result must be a boolean — true or false, nothing else.
    2. The controlled block runs only when the condition is true; there is no "otherwise" branch.
    3. The line after the block runs unconditionally — a common source of "why did this print?" confusion.

    Without braces, an if controls exactly one statement:

    if (age >= 18)
    System.out.println("Eligible ");   // the only statement controlled by if
System.out.println(" Done");           // always runs — not part of the if

    Memory aid — think of if as a gate: the condition is the guard, and the block is the room behind it. No pass (true), no entry.

    2. The if-else Statement

    if-else adds the second road: one block runs when the condition is true, the other when it is false. Exactly one of the two runs — never both, never neither.

    public class Demo2 {
    public static void main(String[] args) {
        int n = 7;
        if (n % 2 == 0) {
            System.out.println("Even");
        } else {
            System.out.println("Odd");
        }
    }
}

    Key points:

    1. The else branch belongs to an if — it can never appear alone.
    2. Since the condition is boolean, there is no need for the popular C-style redundancy if (flag == true); write if (flag) and if (!flag) (comparison operators of Lecture 6).
    3. Each branch is a block: multiple statements, all-or-nothing execution.

    3. The if-else-if Ladder

    When there are more than two mutually exclusive outcomes, conditions are chained: if, then any number of else if, then an optional trailing else. The ladder is checked strictly from top to bottom, and the first condition that evaluates to true wins — every later branch is ignored.

    // Grade ladder — first true condition wins, the rest are skipped
int marks = 78;
if (marks >= 90) {
    System.out.println("Grade A");
} else if (marks >= 75) {
    System.out.println("Grade B");      // 78 lands here and stops
} else if (marks >= 40) {
    System.out.println("Grade C");
} else {
    System.out.println("Fail");
}

    Ladder rules worth memorising:

    1. Evaluation is sequential — order matters. A condition placed early shadows the same condition placed later.
    2. Because the first match skips the rest, the trailing else means "none of the above passed" — a natural default case.
    3. The final else is optional; without it, all-false ladders simply do nothing.
    4. Ranges work because each branch is reached only when earlier conditions failed — marks >= 75 here implicitly means 75 <= marks < 90.

    4. Nested if and the Dangling else Problem

    An if may live inside another if. Nesting expresses dependencies: the inner decision is inspected only when the outer guard passes.

    int age = 20;
boolean hasId = false;
if (age >= 18) {
    if (hasId) {
        System.out.println("Entry allowed");
    } else {
        System.out.println("ID required");
    }
}

    The dangling else question — asked in interviews in some form for decades:

    // Which if owns this else?
if (a > 0)
    if (b > 0)
        System.out.println("Both positive");
else
    System.out.println("a is small");

    The rule resolves it: else binds to the nearest unmatched if. The indented layout above lies; the else actually belongs to the inner if (b > 0), so the "a is small" line prints when a > 0 but b <= 0, and nothing prints when a <= 0.

    Important Java resolves the dangling else by structure, not indentation. Braces remove all doubt — the example above means what a reader likely guesses only after adding explicit { } around the inner if.

    5. The Condition Must Be boolean

    Java is strict about what counts as a condition. Parentheses must contain an expression of type boolean.

    int x = 1;
if (x) { }            // compile error: incompatible types: int cannot be converted to boolean
if (x == 1) { }       // fine — produces a boolean
if (1) { }            // compile error — no truthy integers

    This is a deliberate break from C and C++, where any non-zero integer means true. The classic C clip-fault is also a Java compile error:

    int x = 0;
if (x = 5) { }        // compile error: int cannot be converted to boolean
if (x == 5) { }       // what was intended
    1. float f = ...; if (f) — invalid; every numeric family must produce its comparison explicitly.
    2. Note that the assignment type matters: even in C, if (x = 5) for a boolean variable would type-check, but in Java if (b = true) { } compiles — it assigns and uses the assigned value — which is why reviewers still flag assignments inside conditions.

    Memory aid — Java has no "truthy": a condition is a question answered with true/false, never a number.

    6. The Ternary Operator — if-else as an Expression

    if-else is a statement; the ternary conditional operator ? : is the value-producing twin. It has three parts — condition, value-if-true, value-if-false — and yields one result.

    int a = 11, b = 20;
int max = (a > b) ? a : b;            // expression form of if-else

// Nested ternary — legal, but readability collapses fast
String grade = (marks >= 90) ? "A" : (marks >= 75) ? "B" : "C";

    Two fluid traps:

    1. Type promotion. The two arms are unified into one type. true ? 1 : 2.0 is a double — the int 1 is promoted, so the result prints 1.0, not 1. Assigning the result to an int becomes a compile error.
    2. Readability. One level of ternary is idiomatic (a null/default choice); chains of nested ternaries hide the ladder inside an expression and should be rewritten as if-else-if for review.

    Memory aid — ?: is if-else on value; if-else is ?: on action. Choose by what you need: a value or a side effect.

    Interviewer's perspective The ternary promotion question divides candidates instantly. System.out.println(true ? 1 : 2.0); prints 1.0 — because binary numeric promotion converts both operands to double before the choice is made. Saying "it prints 1 because the condition is true" is the trap.

    7. The Classic switch Statement — Cases, break and default

    switch compares one expression against a fixed set of constant labels and jumps to the matching case. The classic statement form supports:

    • byte, short, char, int (and their wrappers Byte, Short, Character, Integer via autoboxing)
    • String (Java 7+)
    • enum (Java 5+, see Lecture 23)
    • long, float, double, boolean are not allowed.
    // Classic switch — note the int expression and constant labels
int day = 3;
switch (day) {
    case 1:
        System.out.println("Monday");
        break;                          // break stops the fall-through
    case 2:
    case 3:                             // stacked labels share one action
        System.out.println("Mid week");
        break;
    default:
        System.out.println("Unknown day");
}

    Case-sensitivity rules:

    1. The char case compares character values — 'a' and 'A' are different labels; and a String switch uses String.equals underneath, so "JAVA" and "java" are different cases.
    2. Every label must be a compile-time constant — variables, method calls and ranges are illegal.
    3. default may appear anywhere among the cases (top, middle, last); it runs when no label matches. With a break at the end of each block, position has no effect on behaviour — but when default lacks a break while sitting at the end, its statements simply spill into nothing, so the safe habit is break (or return) in every branch.
    4. Duplicate case values are a compile error even if spread across labels.
    5. Passing null into a String switch throws NullPointerException before any case or default is entered — the classic statement switch cannot guard against null with a label.

    8. Fall-Through and the Missing break

    The classic switch's defining behaviour: after a matching case, execution falls through into the next case's statements until a break, return or the end of the switch is reached. Matching jumps to the label; breaking must be earned.

    int level = 1;
switch (level) {
    case 1:
        System.out.println("Step 1");   // matches, prints...
    case 2:
        System.out.println("Step 2");   // ...falls through, prints...
    case 3:
        System.out.println("Step 3");   // ...and this too — no breaks above
        break;
    default:
        System.out.println("Done");
}
// Output: Step 1, Step 2, Step 3
    1. Bug form: a forgotten break makes unrelated cases execute silently — the number one switch bug in production code.
    2. Feature form: stacked labels deliberately use fall-through to group cases (case 2: case 3: sharing one action) and to build flows like case 1: // fall through case 2: in old parsers (a comment documenting the intent).
    3. Jump semantics: control enters at the label and runs straight down; labels are addresses, not rules.

    Important Fall-through means the block of a case does not belong to the case. It belongs to the switch. Whether that is a bug or a design is decided only by the presence of break.

    9. Switch Expressions (Java 14+) — Arrow Labels, yield and Exhaustiveness

    The switch expression (standard from Java 14, previewed in 12-13) is the redesign that removes the sharp edges: arrow labels select one block, blocks never fall through, and the whole form produces a value.

    // Switch expression — arrow form, no fall-through, value result
String type = switch (day) {
    case 1, 7 -> "Weekend";             // multiple labels, one block
    case 2, 3, 4, 5, 6 -> {
        String s = "Weekday " + day;
        yield s;                        // yield returns a value from a block
    }
};

    What changed, element by element:

    1. Arrow labels -> — the code after the arrow runs and the switch exits. No break needed, ever.
    2. Multiple labels — case 1, 2 -> replaces stacked case 1: case 2: grouping.
    3. yield — the way a { } block hands back a value; a simple -> value needs no block and no yield.
    4. Exhaustiveness — as an expression the switch must cover every possible value: all enum constants or a default. The compiler rejects a missing branch — a whole class of bug moves from runtime to compile time.
    5. default remains available (older Java allowed default -> with no labels; newer JDKs also allow case null -> and MPL labels in pattern-switch drafts — beyond interview scope, but know the keyword placement).
    Aspect switch statement switch expression
    Introduced Java 1.0 Java 14+ (verified standard)
    Result Produces nothing; acts by side effect Produces a value you can assign/return
    Label form case X: case X -> (colon form still legal)
    Fall-through Yes — until break No — each label is a self-contained block
    Multiple labels Stacked case 1: case 2: case 1, 2 ->
    Returning a value from a block Not applicable yield value;
    Exhaustive Not required Required — a default or all cases must exist
    Ability to guard None — jump-based Strict compile-time checking

    Interviewer's perspective "Why did Java introduce the switch expression?" Two reasons, both quotable: (1) fall-through bugs disappear because arrow blocks do not leak; (2) exhaustiveness turns an incomplete switch from a silent bug into a compile error — which matters most with enums (Lecture 23).

    10. if-else vs switch — Choosing Between Them

    The forms are not interchangeable; each earns its keep on a different kind of decision.

    Aspect if / if-else-if ladder switch (classic statement)
    Decision basis Any boolean expression One expression compared to constant labels
    Supports Ranges, compound logic (&&, ||), booleans, floats byte, short, char, int, String (7+), enum (5+)
    Range checking (x > 90) Natural — ladder is built for it Not possible with classic labels
    Equality style Any relational/logical test Equality against constants only
    Data-type flexibility Any type via conditions Restricted label types
    Fall-through risk None Present in classic form
    Multi-value dispatch Long chains, verbose Compact, reads like a table
    Compiler help on coverage None Full in expression form
    Typical use Grading bands, thresholds, flags Days, menu choices, enum states, command codes

    Selection rule of thumb: a small, fixed, discrete set of known values → switch (arrow form by default); anything involving ranges, conditions or mixed logic → ladder. When a switch's cases would each need a sub-condition anyway, the ladder has already won.

    11. Common Pitfalls

    Each pitfall below breaks real code and appears as a "what does this print / does this compile" question.

    1. Assignment in condition. if (x = 5) does not compile — Java requires a boolean, and the assignment yields int. But if (b = true) for a boolean b compiles and always runs the block: an assignment that always evaluates to true, usually a typo for ==.
    2. Floating-point equality in conditions. 0.1 + 0.2 == 0.3 is false — binary floating point cannot store the values exactly. Accumulated error makes direct == on double/float unreliable.
    3. Missing break. Handled in section 8 — the case block is not yours until you break.
    4. Switch on null. String s = null; switch (s) throws NullPointerException before default — classic switch has no null case. Expressions in newer Java can declare case null only, which is outside the classic statement.
    5. Ternary arm promotion. true ? 1 : 2.0 produces 1.0 in double form — the int arm is widened, and printing loses the integer shape.
    6. Dangling else. Section 4 — the else never follows indentation, only the nearest unmatched if.
    7. ; after if. if (cond); terminates the if immediately — the "guarded" block always runs afterwards, because it was never guarded.

    12. Myth vs Reality

    Myth Reality
    "switch works on any numeric type, like long" Only byte, short, char, int (+ wrappers), String and enum; long, float, double and boolean are compile errors in the classic switch.
    "if (x) works when x is 1, like C" Java has no truthy integers — the condition must be boolean or the code does not compile.
    "The switch expression is just a shorter switch statement" Different semantics: arrow labels, no fall-through, yield, and compiler-enforced exhaustiveness.
    "default always runs last" default may be placed anywhere; label position never changes which cases run — only matching and break do.
    "Ternary true ? 1 : 2.0 prints 1 because the true arm wins" Binary numeric promotion unifies both arms to double first — the output is 1.0.

    13. Common Trap Questions

    Trap 1 — Dangling else re-indent: "int x = -1, y = 2; if (x > 0) if (y > 0) print 'both'; else print 'x small'; — what prints?" Nothing. The else binds to the inner if (y > 0), so for x <= 0 no branch executes at all. Re-indenting the source cannot change Java's parse.

    Trap 2 — "System.out.println(true ? 1 : 2.0); what prints?" 1.0. Both ternary arms are promoted to the common type double before the condition is honoured. Same shape of trap for byte arms promoted to int.

    Trap 3 — "int day = 3; switch (day) { case 1: ... case 3: print 'X' — with no breaks — what prints?" Whatever sits between case 3: and the next break/end of switch — fall-through executes it. With breaks at case 1 only, matching case 3 still runs case-3 statements and everything below them, uncovered.

    Trap 4 — "String s = null; switch (s) { ... default: ...} — does default catch null?" No. A classic switch computes the label mapping first and throws NullPointerException before any case — including default — is entered.

    Trap 5 — "Can the same value appear in two cases of a switch?" Compile error: duplicate case labels. Wrappers make it sneakier — case 1: and the autoboxed equivalent collide once constant expressions are folded.

    Trap 6 — "if (x = 5) — does Java compile it like C?" No. The condition type must be boolean; the assignment result here is int, so compilation fails. if (b = true) is the sneakier legal cousin that always runs the block.

    Trap 7 — "Does switch accept double/float/boolean?" Not in the classic form — none of the three is permitted. They stay in the if-ladder world (a boolean condition is just the if itself).

    14. Points to Remember

    1. Every condition in Java is boolean — if (x) with a numeric x never compiles.
    2. else always pairs with the nearest unmatched if; use braces to make intent visible and to defeat the dangling else.
    3. An else may have no body (if without else is legal) but an else can never exist without its if.
    4. The ladder evaluates top-down and the first true branch wins; the trailing else is the "none of the above" bucket.
    5. Classic switch labels: byte, short, char, int (+ wrappers), String (Java 7+), enum (Java 5+); labels are compile-time constants and duplicates are errors.
    6. Classic switch falls through until break, return or the end — missing break is the classic defect; stacked labels are the deliberate form.
    7. default runs when nothing matched and can be placed anywhere — placement never changes matching, only readability.
    8. Switch expressions (Java 14+) use arrow labels, accept case 1, 2 -> grouping, never fall through, require exhaustiveness, and yield values with yield.
    9. Ternary is if-else for values; watch arm-type promotion (true ? 1 : 2.0 → 1.0) and avoid chained nested ternaries.
    10. Floating-point == and assignment-in-condition are the two condition-writing traps that survive code review.

    15. Likely Interview Questions

    Question Crisp Answer
    What does if-else-if ladder evaluate as? A sequence of top-down guards; the first true condition runs its block and the whole ladder exits.
    Which types can a classic switch operate on? byte, short, char, int plus wrappers, String (Java 7+) and enum (Java 5+); not long/float/double/boolean.
    What happens if break is omitted in a case? Execution falls through into the next case's statements until a break/return/end of switch — silent multi-case execution.
    Why does Java allow String in switch? Java 7 added it as a convenience; it desugars to String.equals/hashCode-based dispatch — labels stay constants.
    Is default placement meaningful? It runs only when no case matched; it may sit anywhere and its position has no behavioural effect (break hygiene still applies).
    Why must the if condition be boolean? Java dropped C's truthy integers for type safety — a condition is a real boolean expression; assignments like if (x = 5) fail to compile.
    How does Java resolve the dangling else? else binds to the nearest unmatched if — structural, independent of indentation; braces make it explicit.
    Statement switch vs switch expression? Statement acts by side effects with colon labels and fall-through; expression (Java 14+) produces a value, uses ->, never falls through and must be exhaustive with yield in blocks.
    Which value does true ? 1 : 2.0 produce? 1.0 — arms are promoted to the common type double; assigning to an int then fails.
    When do you choose a ladder over a switch? Ranges, compound logic, multiple interacting conditions, or any non-discrete decision — a switch's labels cannot express x > 90.
    Can case labels be variables? No — they must be compile-time constants (literals, constant finals, enum constants, String literals).
    What does switch throw on a null String? NullPointerException — computed before matching, before default.

    16. Final Summary

    condition (boolean) -> if -> true block -> continue after
                    -> else if chain -> first true wins -> exit ladder
                    -> else -> fallback bucket
switch (classic)    -> match constant label -> fall-through until break
switch expression   -> match arrow label -> one block -> yield value -> done
    • Ladder for ranges and boolean logic; switch for discrete constants.
    • Conditions are strictly boolean — no truthy shortcuts from C.
    • Dangling else: structure wins over indentation; braces are the fix.
    • Classic switch: fall-through until break — bug or grouping, decided by break.
    • Switch expression: arrow labels, case 1, 2 ->, yield, exhaustiveness at compile time.
    • Ternary: value form of if-else — mind the arm-type promotion.
    • Traps worth reciting: if (x = 5) fails, floating == fails, switch-on-null throws.

    Golden rule A switch picks one of many known constants; an if-ladder answers any boolean question. Fall-through is classic-switch baggage — the arrow form (Java 14+) removes it and makes coverage the compiler's job.

    One-line takeaway: if-else answers questions, switch matches values — pick by the shape of the decision, and in modern Java let the arrow form and compiler-checked exhaustiveness write your switches safely.
