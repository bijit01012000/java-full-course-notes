    Part 4 · Strings, Generics & Collections · Lecture 25

    Java Strings | String Pool, Immutability, Internals

    17 sections · interview-oriented · both themes

    Scope evidence: "Java Strings | String Pool, Immutability, Internals" (playlist map, verified). Repo evidence: 3 Demo files.

    String is the most used class in Java and the one with the most hidden machinery. This lecture covers what String actually is, how it stores characters, why it is immutable, how the string constant pool and interning work, and the traps around ==, new String, concatenation and substring. It follows immutable classes (Lecture 21) and the Object contract (Lecture 22), and it forwards to string building (Lecture 26), hashing (Lecture 22) and map keys (Lecture 33).

    1. String Is a Class, Not a Primitive

    String is a reference type in the java.lang package; there is no String primitive. It is declared final, so no class may extend it — the same guarantee required of any immutable class (Lecture 21). It implements three important contracts: CharSequence (a readable sequence of char values), Comparable<String> (a natural ordering) and Serializable (it can be written to a stream). Because a literal needs no constructor, beginners mistake it for a primitive.

    // Demo.java — String is a final java.lang class, not a primitive
public class Demo {
    public static void main(String[] args) {
        String s = "abc";                                       // no new keyword needed
        System.out.println(s.length());                         // 3
        System.out.println(s instanceof CharSequence);          // true
        System.out.println(s instanceof Comparable);            // true
        System.out.println(s instanceof java.io.Serializable);  // true
    }
}

    Important String is a class; the compiler only makes literal syntax ("abc") convenient. A String variable holds a reference, exactly like any other object variable.

    2. How String Stores Characters Internally

    Historically String stored a char[] value, one UTF-16 code unit per element. Since Java 9 the compact strings change (JEP 254) stores a byte[] value plus a coder field that records the encoding: LATIN1 (one byte per character) or UTF16 (two bytes per character). The class chooses the narrower form automatically, so Latin-1 text uses roughly half the memory.

    Memory aid — B-C: modern String is a Byte array plus a Coder, not a char[].

    3. Immutability: Every "Change" Creates a New String

    A String is immutable: once constructed, its characters cannot change. Methods such as concat, toUpperCase, replace and trim never edit the receiver; they allocate and return a new String and leave the original untouched. A caller who "forgets" to store the result keeps the old value, which is correct behaviour, not a bug.

    // Demo2.java — apparent "changes" produce new objects
public class Demo2 {
    public static void main(String[] args) {
        String a = "hello";
        String b = a.toUpperCase();   // new object
        String c = a.concat("!");     // new object
        System.out.println(a);        // hello   (a is untouched)
        System.out.println(b);        // HELLO
        System.out.println(c);        // hello!
        System.out.println(a == b);   // false
    }
}

    4. Why Immutability Is Deliberate

    Immutability is not an accident of the design; four concrete benefits depend on it:

    1. String-pool sharing safety — many references may point at one pooled object only because nobody can alter it.
    2. Cached hashCode — the hash is computed once and stored, so equal strings always produce the same key (Section 8).
    3. Thread-safety — an object that never changes cannot suffer a data race, so it can be shared across threads with no synchronization (Lecture 50).
    4. Security — class names, file paths, network hosts and URLs are validated and then used; if any caller could mutate the string after the check, the check would be defeated.

    Interviewer's perspective "Why is String immutable?" The strong answer names the consequences: safe pooling and interning, stable hashing for map keys, free thread-safety, and a security guarantee for values used in file, network and class-loading decisions.

    5. The String Constant Pool

    The string constant pool (often called the string literal pool) is a special region of stored String objects. When the compiler meets a literal such as "abc", it places one canonical copy in the pool; every later literal with the same text reuses that copy. This process is called interning. Since Java 7 the pool lives in the heap, not in the permanent generation (PermGen), so interned strings are garbage-collected with everything else.

    String constant pool (lives in the heap since Java 7)

  "abc"  <-- the interned literal, stored once
    ^
    |  referenced by
   s1 ---\
   s2 -----> same pooled object   (s1 == s2 is true)

  new String("abc")  -->  a separate heap object, NOT the pooled one

    Important Pool location changed in Java 7: before, the pool was part of PermGen and could throw OutOfMemoryError: PermGen space; now it is ordinary heap memory.

    6. Literal vs new String("abc")

    A literal reuses the pooled instance; new String(...) always creates a distinct object on the heap. The two are equal in content but are different objects.

    // Demo.java — literal reuses the pool; new forces a fresh object
public class Demo {
    public static void main(String[] args) {
        String a = "abc";
        String b = "abc";
        String c = new String("abc");
        System.out.println(a == b);            // true   (same pooled literal)
        System.out.println(a == c);            // false  (c is a separate object)
        System.out.println(a == c.intern());   // true   (intern returns the pool copy)
        System.out.println(a.equals(c));       // true   (content is equal)
    }
}

    .intern() looks up the string in the pool and returns the pooled instance, adding one if the text is absent. It is rarely needed in ordinary code and carries a lookup cost.

    7. == vs equals on Strings

    == is an operator that compares references (identity). equals is a method that String overrides to compare character content. The classic trap is that == sometimes appears to work: it returns true whenever both references happen to point at the same interned literal.

    Aspect == equals
    Compares References (identity) Character content (value)
    Kind Operator Method on Object, overridden by String
    Literal vs literal Usually true (both interned) true
    Literal vs new String false true
    Two new String objects false true
    Intended use Identity checks Value equality
    Aspect String s = "abc"; String s = new String("abc");
    Objects created Zero new objects; the pooled literal is reused One new String object on the heap
    Pool interaction Reuses the interned literal Creates a separate object; does not intern it
    s == "abc" true false
    s.equals("abc") true true
    Typical use Normal Java code Rarely needed; only to force a distinct instance

    The lesson from both tables: use equals for content, and reserve == for genuine identity checks such as null guards.

    8. hashCode Caching and HashMap Keys

    String computes its hashCode lazily on the first call and stores it in a private int field (historically named hash). Because the object is immutable, the value never changes, so a String is a perfect HashMap/HashSet key: lookups always find the bucket the entry was inserted into (Lecture 22, Lecture 33). If a key's hashCode could change after insertion, the entry would become unreachable.

    Interviewer's perspective "Why are Strings such good HashMap keys?" Immutability guarantees a stable hashCode and stable equals, so the key cannot drift out of its bucket after insertion. The cached hash also makes repeated lookups cheap.

    9. Concatenation: Constant Folding and StringBuilder

    When every operand is a compile-time constant, + is folded by the compiler into a single literal, which is then interned. When any operand is a runtime value, the compiler emits string-building code: historically a StringBuilder, and on Java 9+ an invokedynamic call linked to StringConcatFactory. Either way, a + inside a loop creates a new builder and a new String each iteration, which is why loops should use an explicit StringBuilder (forward reference: Lecture 26).

    // Demo.java — compile-time folding vs runtime concatenation
public class Demo {
    public static void main(String[] args) {
        String a = "ja" + "va";           // folded at compile time -> "java"
        System.out.println(a == "java");  // true (interned constant)

        String p = "ja";
        String b = p + "va";              // built at runtime -> new String
        System.out.println(b == "java");  // false
    }
}

    Memory aid — a + of literal constants is a folded literal; a + involving a variable is a build.

    10. substring: Copy Now, Shared Backing Array Before Java 7

    From Java 7u6 onward, substring copies the requested range into a new String, so the result is a small independent object. Before that release, substring shared the original backing array through an offset and count, so a two-character substring of a megabyte string kept the whole megabyte alive — a genuine memory leak and a favourite historical interview point. The modern copy behaviour removes the leak but costs an allocation.

    11. How Many Objects Does new String("abc") Create?

    The number depends on whether the pool already contains the literal:

    1. If "abc" is not yet in the pool — the compiler must first create the interned literal (one object), then new String(...) creates a second object. Total: two objects.
    2. If "abc" is already interned (because another literal with the same text appears in the program) — the literal argument reuses the pooled copy, and only new String(...) allocates. Total: one object.

    Interviewer's perspective The expected answer names both cases rather than a bare "one" or "two". State that the literal is interned once per class, then each new String adds one heap object; the count is one or two depending on pool state.

    12. String[] Arrays Are Mutable Even Though Strings Are Not

    Immutability is a property of the String object, not of every variable or container that holds one. An array of String elements is itself mutable: an element can be reassigned and the array reference can be pointed at a new array. The same holds for a List<String> whose structure can change.

    // Demo3.java — the array is mutable even though String is immutable
public class Demo3 {
    public static void main(String[] args) {
        String[] names = { "Asha", "Ravi" };
        names[0] = "Meera";             // legal: the array changes
        names = new String[] { "X" };   // legal: the reference is reassigned
        System.out.println(names[0]);   // X
    }
}

    13. Myth vs Reality

    Myth Reality
    "String is a primitive like int" String is a final class in java.lang; only its literal syntax is special.
    "== compares string content" == compares references; equals compares character content.
    "new String("abc") is how you create a string" Literals are the normal form; new forces an unnecessary extra object outside the pool.
    "Immutability means a String[] cannot change" The String objects are immutable; the array that holds their references is fully mutable.
    "substring always shares memory with the original" Since Java 7u6 it copies; sharing was the pre-Java 7 behaviour that caused a leak.

    14. Common Trap Questions

    Trap 1 — "s1 == s2 returned true, so == is safe for strings, right?" Not safe. Two literals share the same pooled object, so == returns true by interning coincidence; a new String or a runtime-built value with the same text returns false.

    Trap 2 — "How many objects does new String("abc") create?" One or two. If "abc" is not yet interned the literal adds one object and new adds another (two); if it is already interned, only new allocates (one).

    Trap 3 — "Does .intern() make my program faster?" Usually not. It trades a hash lookup and a possible pool insertion for memory savings only when many equal strings exist; calling it eagerly is a performance anti-pattern.

    Trap 4 — "Is String s = "a" + b + "c"; compiled into a StringBuilder?" On Java 9+ the compiler emits invokedynamic linked to StringConcatFactory, not a literal StringBuilder; the effect is still a fresh String per evaluation.

    Trap 5 — "I changed a String in a loop with += and it stayed correct, so there is no cost?" Correctness and cost are different. Each += allocates a new builder and a new String; inside a loop this is quadratic work — use StringBuilder (Lecture 26).

    Trap 6 — "substring on a huge string is cheap because it shares the array, right?" Only on Java releases before 7u6. Modern substring copies, so it is safe from leaks but still allocates; the old sharing behaviour is the historical interview point.

    15. Points to Remember

    1. String is a final class in java.lang, not a primitive; it implements CharSequence, Comparable<String> and Serializable.
    2. Internally String used a char[] historically and, since Java 9, uses a byte[] plus a coder (LATIN1 or UTF16).
    3. String is immutable: concat, toUpperCase and friends return new objects and never edit the receiver.
    4. Immutability enables pool sharing, cached hashCode, thread-safety and security checks on paths, hosts and class names.
    5. The string constant pool interns literals; since Java 7 the pool lives in the heap, not PermGen.
    6. new String("abc") creates a separate object; .intern() returns the pooled instance.
    7. == compares references; equals compares content — use equals for value comparisons.
    8. String.hashCode is cached, so strings are ideal HashMap keys (Lecture 22, Lecture 33).
    9. Literal + is constant-folded; runtime + becomes string-building code (StringBuilder, invokedynamic on Java 9+) — use StringBuilder in loops (Lecture 26).
    10. substring copies since Java 7u6, and a String[] array remains mutable even though its elements do not.

    16. Likely Interview Questions

    Question Crisp Answer
    Is String a primitive or a class? A final class in java.lang; the literal syntax is compiler sugar, not a primitive type.
    Why is String immutable? To make pool sharing safe, cache hashCode, allow lock-free sharing across threads, and protect security-sensitive values.
    What is the string constant pool? A stored set of interned String literals; identical literals reuse one object. It has lived in the heap since Java 7.
    What does intern() do? Returns the pooled instance for the string's content, adding it to the pool if absent.
    Difference between == and equals for strings? == compares references; equals compares character content.
    Why can s1 == s2 be true for two literals? Both literals resolve to the same interned pool object, so their references are identical.
    How many objects does new String("abc") create? One if "abc" is already interned, otherwise two (the interned literal plus the new heap object).
    Why are strings good HashMap keys? Immutability gives a stable cached hashCode and stable equals, so entries never drift between buckets.
    How is string concatenation compiled? Constant operands are folded at compile time; runtime + becomes StringBuilder (older) or invokedynamic/StringConcatFactory (Java 9+).
    What changed in String internals in Java 9? Compact strings: byte[] plus a coder replaced the UTF-16 char[], halving memory for Latin-1 text.
    Did substring always copy? No. Before Java 7u6 it shared the backing array and could retain large memory; since then it copies.
    Does immutability make a String[] immutable? No. The array and its element references are mutable; only the String objects themselves are immutable.

    17. Final Summary

    "abc" (literal)     --intern-->  pool (heap since Java 7)  --shared by many references
new String("abc")   -->         separate heap object       --intern()--> returns pool copy

==       -> references (identity)        equals -> content (value)
hashCode -> cached once                 -> ideal HashMap key (Lecture 22, Lecture 33)
+ literals -> compile-time folded       runtime + -> builder / invokedynamic (Java 9+) (Lecture 26)
substring -> copies since Java 7u6      String[] -> mutable container of immutable values
    • String → a final java.lang class, CharSequence + Comparable + Serializable; not a primitive.
    • Internals → byte[] + coder (LATIN1/UTF16) since Java 9; char[] historically.
    • Immutable → every modification returns a new object; the receiver never changes.
    • Pool → interned literals are shared; the pool lives in the heap since Java 7.
    • new String → a separate object; .intern() returns the pooled copy.
    • == vs equals → references versus content; literal interning is the reason == sometimes lies.
    • hashCode → cached and stable, making strings excellent map keys.
    • Concatenation → folded for constants, built at runtime otherwise; use StringBuilder in loops (Lecture 26).
    • substring → copies now; shared array before Java 7u6 was a real leak.
    • Arrays → a String[] is mutable even though each String is not.

    Golden rule String is an immutable class, not a primitive: literals live in the shared pool, new String escapes it, and == tests identity while equals tests content.

    One-line takeaway: String is a final, immutable class whose literals are interned in a heap pool, so compare with equals, build with StringBuilder, and trust its cached hash as a map key.
