    DTOs & Validations in Spring Boot

    21 sections · ~26 min read · interview-oriented · both themes

    Scope evidence: "DTOs & Validations in Spring Boot | Make Your REST API Professional" (playlist map, verified). Repo lecture folder is the dtoDemo project: a dto package with Create/Update Request and Response DTOs, plus entity, controller, service, repository packages and the cached lecture notes.

    A working CRUD API is not the same as a professional CRUD API. The same Student entity that maps neatly to a database table becomes dangerous the moment it is also used as the request body and the response body. This lecture explains why passing the entity everywhere breaks the API boundary, and then fixes it with DTOs: separate request and response objects backed by validation rules. By the end we have a request pipeline where bad data is rejected with a clean 400 before it ever touches the service or the database.

    1. The Real Problem

    Suppose we are building a simple Student Management Application. It supports basic CRUD operations: create student, get all students, get student by ID, update student, and delete student.

    While creating a student, the client may send this request body:

    {
  "name": "Amit",
  "email": "amit@gmail.com",
  "age": 21
}

    Now the important backend question is: when this request reaches our Spring Boot application, which layer receives it, which layer processes it, which layer talks to the database, and which layer returns the response? This is where layered architecture becomes important, and it is also where the real design problem starts.

    2. The Four Layers of a CRUD Project

    A simple Spring Boot CRUD project commonly works with four parts, each with one clear responsibility:

    Layer Main responsibility
    Controller Handles HTTP requests and sends HTTP responses
    Service Contains business logic
    Repository Communicates with the database
    Entity Represents a database table

    A clean backend application should keep these responsibilities separate. When the separation is respected, each layer changes for one reason only.

    Important: The four layers are not decoration. The Controller owns HTTP, the Service owns business rules, the Repository owns persistence, and the Entity owns the database shape. Mixing their jobs is exactly how the problems in Section 7 are born.

    3. Entity: The Class Connected to the Database

    An Entity is a Java class mapped to a database table.

    @Entity
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String email;
    private Integer age;
}

    Because of the @Entity annotation, JPA/Hibernate understands that this class should be mapped to a database table. The class Student becomes a table student, and its fields id, name, email, and age become columns with the same names.

    At the database level, the table may look like this:

    id name email age
    1 Amit amit@gmail.com 21
    2 Neha neha@gmail.com 22

    The first important point is this: an Entity is mainly designed to represent the database structure. Nothing about it was written for the outside world.

    4. The Complete Create API Flow

    In a normal create API, the flow looks like this:

    Client
  |
  v
Controller
  |
  v
Service
  |
  v
Repository
  |
  v
Database

    The same flow in ten explicit steps:

    1. Client sends a POST request with JSON data.
    2. Controller receives the request.
    3. Spring/Jackson converts JSON into a Java object.
    4. Controller calls the Service layer.
    5. Service applies business logic.
    6. Service calls the Repository.
    7. Repository saves data into the database.
    8. Database returns the saved data.
    9. Service prepares the response.
    10. Controller sends the HTTP response back to the client.

    This flow is correct. The problem starts when we use the same Entity class everywhere.

    5. Two Worlds: Outside API vs Inside Database

    A backend application mainly deals with two worlds:

    Outside world Inside world
    API request / API response Database / business logic
    Frontend, mobile app, Postman Database tables, entity classes
    Third-party client, another backend service Repository layer, business logic, internal fields

    The key principle is:

    Golden rule: The outside world should not directly control or depend on the internal database structure.

    In a beginner CRUD project, we often pass the Student entity everywhere: Controller -> Service -> Repository -> Database. The same Student entity may be used for:

    1. Representing the database table.
    2. Receiving request data.
    3. Moving data through the service layer.
    4. Getting saved by the repository.
    5. Returning the API response.

    For a small demo project, this works. But in real-world applications, this becomes a bad design, because it quietly erases the wall between the two worlds.

    6. Entity Has One Specific Purpose

    An Entity is created mainly for database mapping. It belongs to the internal side of the application because it is closely connected to:

    • the database table;
    • columns;
    • the primary key;
    • relationships;
    • Hibernate/JPA.

    On the other hand, request and response objects belong to the external API side. So a clean separation should be:

    Entity            -> Internal database model
Request/Response  -> External API model

    But when we pass the Entity everywhere, we are effectively doing this:

    Entity = Database model
Entity = Request model
Entity = Response model

    This is the root problem. One class is now three contracts at once, and any change to one contract risks breaking the other two.

    7. The Five Problems of Exposing the Entity

    But when we accept and return entities directly, we start exposing the internal structure of our application. Five concrete problems follow.

    Problem 1: the client can send fields they should not send. Suppose the entity grows internal fields such as id, isDeleted, createdAt, and updatedAt. Because the controller directly accepts Student, the client may send extra fields:

    {
  "id": 100,
  "name": "Amit",
  "email": "amit@gmail.com",
  "age": 21,
  "isDeleted": true,
  "createdAt": "2026-07-04T10:00:00",
  "updatedAt": "2026-07-04T10:00:00"
}

    The client should not decide values like id, isDeleted, createdAt, updatedAt, or internal status fields. These fields should be controlled by the backend. Entity exposes internal fields to the outside world.

    Problem 2: the client can modify sensitive or internal data. As the entity grows, it may contain password, role, isVerified, internalRemark, and more. During update, a client could send:

    {
  "name": "Amit",
  "email": "amit@gmail.com",
  "age": 21,
  "role": "ADMIN",
  "isVerified": true,
  "isDeleted": false
}

    This is dangerous. The user should not be able to make themselves ADMIN, verified, premium, not deleted, or approved. These values should be controlled by business logic, not by the client. This problem is commonly called the mass assignment problem: the client sends more data than required, and the backend accidentally accepts it.

    Problem 3: the response may leak unwanted data. When the controller returns the entity directly, the API response may accidentally expose internal or sensitive fields. The client usually does not need password, isDeleted, internalRemark, internal flags, or backend-only metadata. Returning the entity directly can leak unwanted internal data.

    Problem 4: request and response usually need different structures. For creating a student, the client may send only name, email, and age. But after creating the student, the API may return:

    {
  "id": 1,
  "name": "Amit",
  "email": "amit@gmail.com",
  "message": "Student created successfully"
}

    The request does not need id or message. The response may need id and message. So request and response should not always use the same class.

    Problem 5: database changes can break the API contract. Suppose name is split into firstName and lastName for database design reasons. If we return the entity directly, the API response changes with it, but the frontend may still be expecting the old "name": "Amit Sharma" shape. One internal database change can break the external API contract. A good API should not break just because the database structure changed internally.

    8. The Main Design Issue

    A class should ideally have one clear responsibility. But when we pass the Entity everywhere, the Entity becomes responsible for too many things:

    • database mapping;
    • request handling;
    • response handling;
    • business data transfer;
    • the external API contract.

    This is why we introduce DTOs.

    9. What Is a DTO? Types and Location

    DTO stands for Data Transfer Object. A DTO is a simple object used to transfer data between layers or between client and server. In simple terms: a DTO carries only the data required for a particular request or response, and it is not created for database mapping.

    Class type Main purpose
    Entity Represents the database table
    DTO Transfers data in a request/response or between layers

    In a normal CRUD project, we commonly create two main types of DTOs: a Request DTO and a Response DTO. In real projects we may create more specific ones: CreateStudentRequestDto, UpdateStudentRequestDto, StudentResponseDto, StudentSummaryResponseDto, and StudentDetailResponseDto.

    A common package structure keeps DTOs in their own folder:

    src/main/java/com/example/studentapp
|-- controller
|-- service
|-- repository
|-- entity
`-- dto

    The dto package contains request and response DTO classes.

    10. Request DTO and Response DTO

    A Request DTO represents the data that the client is allowed to send to the API. It is part of the API contract:

    public class StudentRequestDto {
    private String name;
    private String email;
    private Integer age;
}

    Now the controller can receive this DTO instead of the Entity, which clearly says: for creating a student, the client can send only name, email, and age. The Request DTO protects the API boundary and prevents the client from directly controlling internal database fields.

    A Response DTO represents the data that the API wants to send back to the client:

    public class StudentResponseDto {
    private Long id;
    private String name;
    private String email;
    private Integer age;
    private String message;
}

    This DTO allows us to decide exactly what should be visible in the API response.

    Instead of mixing student data and the message at the same level, we can also create a cleaner, more structured response:

    {
  "studentInfo": {
    "id": 1,
    "name": "Amit",
    "email": "amit@gmail.com",
    "age": 21
  },
  "message": "Student created successfully"
}

    For that we create separate response classes: CreateStudentResponseDto holding a StudentInfoDto and a message, and StudentInfoDto holding id, name, email, and age.

    DTO naming convention

    For beginners, simple names are fine: StudentRequestDto and StudentResponseDto. In real projects, more specific names are better, because different APIs may require different request and response structures. A create request may allow email, while an update request may not allow changing email. DTOs allow each API to define its own contract clearly.

    Level Request DTO Response DTO
    Beginner StudentRequestDto StudentResponseDto
    Real project CreateStudentRequestDto, UpdateStudentRequestDto StudentResponseDto, StudentDetailsResponseDto, StudentListResponseDto

    11. Manual Mapping: Why, How, Where

    A DTO and an Entity are two different classes, so we need to convert one into another. There are two common mappings:

    StudentRequestDto -> Student Entity
Student Entity    -> StudentResponseDto

    Mapping 1: Request DTO to Entity. When the client sends data, the controller receives a StudentRequestDto, but the repository cannot save a StudentRequestDto; the repository saves the Entity. So we convert:

    private Student mapToEntity(StudentRequestDto requestDto) {
    Student student = new Student();
    student.setName(requestDto.getName());
    student.setEmail(requestDto.getEmail());
    student.setAge(requestDto.getAge());
    return student;
}

    Mapping 2: Entity to Response DTO. After saving or fetching data from the database we get a Student entity, but we do not want to return the Entity directly, so we convert:

    private StudentResponseDto mapToResponseDto(Student student) {
    StudentResponseDto responseDto = new StudentResponseDto();
    responseDto.setId(student.getId());
    responseDto.setName(student.getName());
    responseDto.setEmail(student.getEmail());
    responseDto.setAge(student.getAge());
    return responseDto;
}

    Where should mapping happen? For a beginner project, mapping can be done inside the Service layer. The Service sits between the Controller and the Repository, so it works as the bridge:

    Controller
  | DTO
  v
Service
  | Entity
  v
Repository

    The Controller should not know too much about the Entity, and the Repository should not know anything about DTOs. That is why the Service layer is a clean place for mapping in a beginner project. In larger projects, we can create a separate mapper class or use mapping libraries like MapStruct.

    Interviewer's perspective: The mapping direction is the tell. A candidate who says "map request DTO to entity before saving, and entity to response DTO before returning" understands the boundary; a candidate who "returns the entity" has not felt the problem yet.

    12. CRUD APIs Rewritten With DTOs

    Create API. The controller accepts the request DTO and returns the response DTO, and the service maps in both directions:

    @PostMapping
public StudentResponseDto createStudent(@RequestBody StudentRequestDto requestDto) {
    return studentService.createStudent(requestDto);
}

    public StudentResponseDto createStudent(StudentRequestDto requestDto) {
    Student student = mapToEntity(requestDto);
    Student savedStudent = studentRepository.save(student);
    return mapToResponseDto(savedStudent);
}

    The full create flow with DTOs:

    Client JSON
  |
  v
StudentRequestDto
  |
  v
Student Entity
  |
  v
Database
  |
  v
Student Entity
  |
  v
StudentResponseDto
  |
  v
Client Response

    Get all students API. The service returns a list of response DTOs instead of a list of entities, mapping each entity as it goes:

    @GetMapping
public List<StudentResponseDto> getAllStudents() {
    return studentService.getAllStudents();
}

    public List<StudentResponseDto> getAllStudents() {
    List<Student> students = studentRepository.findAll();
    return students.stream()
            .map(this::mapToResponseDto)
            .toList();
}

    Here, for every Student entity we call mapToResponseDto(student), so the API returns a list of response DTOs instead of a list of entities.

    Get student by ID API. The Repository returns an Entity, the Service converts that Entity into a Response DTO, and the Controller returns only the DTO:

    @GetMapping("/{id}")
public StudentResponseDto getStudentById(@PathVariable Long id) {
    return studentService.getStudentById(id);
}

    public StudentResponseDto getStudentById(Long id) {
    Student student = studentRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Student not found"));
    return mapToResponseDto(student);
}

    Update API. We do not create a completely new entity during update. We first fetch the existing entity, update allowed fields, save it again, and return a response DTO:

    public StudentResponseDto updateStudent(Long id, StudentRequestDto requestDto) {
    Student existingStudent = studentRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Student not found"));
    existingStudent.setName(requestDto.getName());
    existingStudent.setEmail(requestDto.getEmail());
    existingStudent.setAge(requestDto.getAge());
    Student updatedStudent = studentRepository.save(existingStudent);
    return mapToResponseDto(updatedStudent);
}

    Delete API. Many projects return only a message. A more professional response wraps it in a simple response DTO such as ApiResponseDto with a single message field:

    {
  "message": "Student deleted successfully"
}

    13. Validation: Without vs With, and the Dependency

    Whenever a backend receives data from outside, the data is not guaranteed to be correct. The client may send invalid data such as an empty name, a wrong-email address, or an age of -5, or nulls where values are required. This data should not directly reach the service layer or the database. Validation means: before accepting request data, check whether the data follows the rules of the application.

    Without validation, the controller accepts the DTO, invalid data reaches the service layer, the service maps it to an Entity, and the repository saves it. Bad input enters the system and the bad row sits in the database.

    With validation, we declare rules like: name should not be blank, name should have at least 2 characters, email should not be blank, email should be valid, age should not be null, and age should be at least 18. The correct flow becomes:

    Client sends JSON
  |
  v
Controller receives request
  |
  v
Validation happens
  |
  +--> If valid   -> Service method runs
  |
  `--> If invalid -> Error response goes back

    Validation protects the service layer and the database from invalid input.

    In Spring Boot, validation support usually comes from this dependency:

    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

    If we are using Spring Initializr, we can add it by selecting the Validation starter.

    14. Common Validation Annotations

    Validation annotations are placed on fields. For example, @NotBlank private String name; means names cannot be null, empty, or only spaces.

    Annotation Used for Meaning
    @NotNull Any object Value cannot be null
    @NotBlank String Value cannot be null, empty, or only spaces
    @NotEmpty String, Collection, Array Value cannot be null or empty
    @Email String Value should be a valid email format
    @Min(value) Number Minimum allowed value
    @Max(value) Number Maximum allowed value
    @Size(min, max) String, Collection Length or size should be within range
    @Pattern(regexp) String Value should match a regex pattern
    @Positive Number Value should be positive
    @Past Date/time Date should be in the past
    @Future Date/time Date should be in the future

    @NotNull vs @NotBlank vs @NotEmpty

    @NotNull checks only one thing: the value should not be null. It is useful for numbers like Integer, Long, and Double. But for strings, @NotNull is often not enough because "name": "" is not null. For fields like name, email, title, and city, @NotBlank is usually better because it rejects null, empty, and whitespace-only strings. @NotEmpty checks that a value is neither null nor empty, and it is useful for lists, arrays, and collections - for normal strings, prefer @NotBlank.

    Point @NotNull @NotBlank @NotEmpty
    Rejects null Yes Yes Yes
    Rejects "" (empty) No Yes Yes
    Rejects " " (spaces only) No Yes No
    Works on numbers Yes No No
    Works on collections/arrays Yes No Yes
    Best for Integer/Long/Double name, email, title List/array fields

    Where should we add validations?

    A common question is whether validations should be added in the Entity or in the Request DTO. For request validation, validations should be added in the Request DTO, because validation rules are about what the client is allowed to send, and the client sends request data. So request validation naturally belongs to the Request DTO.

    The updated request DTO with validations:

    import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public class StudentRequestDto {
    @NotBlank(message = "Student name is required")
    @Size(min = 2, max = 50, message = "Student name must be between 2 and 50 characters")
    private String name;

    @NotBlank(message = "Student email is required")
    @Email(message = "Student email should be valid")
    private String email;

    @NotNull(message = "Student age is required")
    @Min(value = 18, message = "Student age must be at least 18")
    @Max(value = 60, message = "Student age must not be greater than 60")
    private Integer age;
}

    This DTO clearly defines the rules: name cannot be blank, name length should be between 2 and 50 characters, email cannot be blank, email should be valid, age cannot be null, and age should be between 18 and 60.

    15. @Valid, Internal Steps, and the 400 Error

    Adding validation annotations in the DTO is not enough. To trigger validation for request body data, we use @Valid in the controller:

    import jakarta.validation.Valid;

@PostMapping
public StudentResponseDto createStudent(
        @Valid @RequestBody StudentRequestDto requestDto) {
    return studentService.createStudent(requestDto);
}

    The same thing can be done for the update API by putting @Valid before the @RequestBody. Now Spring validates StudentRequestDto before calling the service method. The important line @Valid @RequestBody StudentRequestDto requestDto means two separate things:

    Part Meaning
    @RequestBody Convert JSON into a Java object
    @Valid Apply the validation rules on that Java object

    Suppose the client sends name empty, email as wrong-email, and age as 15. Spring performs these steps:

    1. JSON is converted into StudentRequestDto.
    2. Because @Valid is present, Spring checks the validation annotations.
    3. It checks name; name is blank, so validation fails.
    4. It checks email; email format is invalid, so validation fails.
    5. It checks age; age is less than 18, so validation fails.
    6. The service method is not called.
    7. An error response goes back to the client.

    Important: If validation fails, the request does not reach the service layer. So validation protects both business logic and the database from bad input.

    Validation annotations vs @Valid

    Both parts are important. The annotations (@NotBlank, @Email, @Min, @Max, @Size) define the rules. @Valid tells Spring to apply those rules. In one line: validation annotations define the rules, and @Valid triggers the validation process.

    Point Validation annotations @Valid
    Role Define the rules Triggers the validation process
    Placed on Fields of the Request DTO The controller method parameter
    Examples @NotBlank, @Email, @Min, @Size @Valid @RequestBody StudentRequestDto requestDto
    Alone Inactive until triggered Has nothing to check without rules
    Result when rule fails One field-level violation A 400 Bad Request before the service runs

    What status code is returned?

    When validation fails, Spring Boot returns HTTP 400 Bad Request. It is 400 because the client sent invalid request data; the problem is with the request body, and the server is working fine. It is not 500 Internal Server Error.

    The default error response is technically correct, but it is not always clean or frontend-friendly. A frontend usually wants a simple response such as a map of field to message, or a structured response like this:

    {
  "success": false,
  "message": "Validation failed",
  "errors": {
    "name": "Student name is required",
    "email": "Student email should be valid",
    "age": "Student age must be at least 18"
  }
}

    Spring Boot may not give this exact clean format automatically. That is why we later use Global Exception Handling, which allows us to control the exact error response format.

    Custom validation messages

    Without a custom message, @NotBlank private String name; may return a generic default like must not be blank. A better approach is a clear custom message such as @NotBlank(message = "Student name is required") or @Email(message = "Student email should be valid"). Custom messages make validation errors easier to understand for frontend developers and API users.

    Putting all of it together, the clean and professional flow is:

    Client sends JSON

@Valid checks request data

  `--> If valid:

    This is a cleaner and more professional API design.

    17. Myth vs Reality

    Myth Reality
    "The entity is good enough as the request body" Any internal field then becomes client-controllable; that is the mass assignment problem.
    "The entity is good enough as the response body" Returning the entity can leak password, isDeleted, and internal metadata.
    "DTOs are only for large projects" Even a small CRUD project exposes its database model the moment it returns the entity.
    "One DTO can serve every API" Create and update often allow different fields; separate DTOs define separate contracts.
    "Adding validation annotations is enough" Without @Valid in the controller, the annotations are never triggered.
    "Validation failure should be a 500" It is a 400 Bad Request; the client's data is wrong, not the server.
    "Validation belongs on the entity" Request validation belongs on the Request DTO, because it governs what the client may send.
    "Mapping is unnecessary if names match" The entity and DTO are different classes; something must still copy the values.

    18. Common Trap Questions

    Trap 1 - "We have DTOs, so we no longer need entities." Verdict: False. Entities still own database mapping; DTOs only own transport. They solve different problems and coexist.

    Trap 2 - "DTO means Data Transfer Object, so any object is a DTO." Verdict: Misleading. A DTO is deliberately shaped for one request or response contract, not for the database.

    Trap 3 - "Validation annotations run by themselves once added to the DTO." Verdict: False. @Valid (or @Validated) must be present in the controller to trigger validation of the request body.

    Trap 4 - "For a String field, @NotNull is enough." Verdict: False. An empty string "" is not null; use @NotBlank for strings, and @NotEmpty for lists and arrays.

    Trap 5 - "The repository can save the request DTO directly." Verdict: False. The repository understands the Entity, not the DTO; the Service must map the DTO to an entity first.

    Trap 6 - "A failed validation returns 500." Verdict: False. It returns 400 Bad Request; the request body is invalid, not the server.

    Trap 7 - "Update should build a brand-new entity from the request DTO." Verdict: False. Update fetches the existing entity, changes allowed fields, saves it again, and returns a response DTO.

    19. Points to Remember

    1. Layered architecture separates Controller (HTTP), Service (business logic), Repository (database), and Entity (table mapping).
    2. An Entity is designed for database mapping; it belongs to the internal side of the application.
    3. Passing the entity everywhere makes one class the database model, the request model, and the response model at once.
    4. The five problems are: forbidden client fields, mass assignment, response leakage, different request/response shapes, and database changes breaking the API contract.
    5. A DTO is a Data Transfer Object: it carries only the data needed for one request or response and is never used for database mapping.
    6. Request DTOs define what the client may send; response DTOs define what the API returns; both live in the dto package.
    7. Mapping runs both ways: request DTO to entity before saving, and entity to response DTO before returning; the Service layer is the beginner-friendly place for it.
    8. Validation belongs on the Request DTO, because the rules describe what the client is allowed to send.
    9. @Valid in the controller triggers validation; annotations such as @NotBlank, @Email, @Min, and @Size only define the rules.
    10. Failed validation returns 400 Bad Request (never 500), and invalid data never reaches the service or the database.

    20. Likely Interview Questions

    Question Crisp Answer
    What is a DTO? A Data Transfer Object: a simple object used to carry only the data required for a particular request, response, or layer boundary.
    Why not expose the entity directly? It exposes internal structure, allows mass assignment, leaks sensitive fields, couples the API to the table, and breaks the contract on schema changes.
    What is the mass assignment problem? The client sends more fields than required (like role or isVerified) and the backend accidentally accepts them into the entity.
    Entity vs DTO? Entity maps to a database table (internal); DTO transfers data across the API boundary (external) and holds only the needed fields.
    Request DTO vs Response DTO? Request DTO = what the client may send; Response DTO = what the API returns; they usually have different fields.
    Where should DTOs live? In a dedicated dto package alongside controller, service, repository, and entity.
    Why is mapping required? DTO and Entity are different classes; the repository saves entities and the controller speaks DTOs, so values must be copied across.
    Where should mapping happen? In the Service layer for beginner projects; a separate mapper or MapStruct in larger projects.
    Where do validations go? On the Request DTO, because they describe what the client is allowed to send.
    Difference between validation annotations and @Valid? Annotations define the rules; @Valid triggers Spring to apply them to the request body.
    @NotNull vs @NotBlank vs @NotEmpty? @NotNull rejects only null; @NotBlank rejects null/empty/spaces for strings; @NotEmpty rejects null/empty for strings, lists, and arrays.
    What status code does failed validation return? 400 Bad Request, because the client's request data is invalid; the server itself is fine.

    • Entity = database mapping; DTO = data transfer; keep the two worlds separate.

    • The five problems all trace to one root cause: one class serving three contracts.
    • Mapping belongs in the Service layer for beginners, a mapper class for larger projects.

    • Custom validation messages make errors understandable for frontend developers and API users.

    Mnemonic: "Entity guards the table, DTO guards the door." The entity never leaves the database side; the DTO is the only thing that crosses the API boundary. For the five problems, remember "Forbidden, Forged, Leaked, Different, Broken."

    One-line takeaway: Professional REST APIs do not expose the database; they exchange purpose-built DTOs and reject invalid input at the boundary with a validated 400 before a single bad row can reach the database.
