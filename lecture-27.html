    Part 4 · Strings, Generics & Collections · Lecture 27

    Java Generics Deep Dive | Bounded Types using extends

    18 sections · interview-oriented · both themes

    Scope evidence: "Java Generics Deep Dive | Bounded Types using extends" (playlist map, verified). Repo evidence: 7 Demo files.

    Generics arrived in Java 5 to move the type check from runtime to compile time: instead of storing everything in Object and casting on the way out, a class or method declares the types it works with, and the compiler enforces them. This lecture builds the whole model from the pre-generics problem upward: generic classes, interfaces and methods, the naming conventions for type parameters, upper bounds using extends (including intersection bounds), and the erasure machinery that makes generics a compile-time-only feature. It then shows why List<Integer> is not a List<Number>, why raw types generate unchecked warnings, and why primitives cannot be type arguments — with Lecture 18 autoboxing and the Lecture 28 wildcard system as the two deliberate forward references.

    1. Why Generics — The Case for Compile-Time Type Safety

    Before Java 5, the only general-purpose container was a holder of Object. It worked, but it deferred every type problem to runtime and forced a cast at every retrieval. Generics were introduced in Java 5 (JSR 14) to change exactly that:

    1. Compile-time type safety — a wrong insertion is rejected by javac, not by an exception at 3 a.m. in production.
    2. No casts — a parameterized container returns the declared type, so (String) box.get() disappears.
    3. Reusable code — one Box<T> serves String, Integer, Employee and any future class without duplicating the class.
    4. Self-documenting APIs — List<String> states its element type in the signature, where a raw List says nothing.

    Important Generics are a compile-time mechanism. Almost none of the type information survives into the bytecode — a fact called type erasure (section 8) that explains nearly every "strange" rule in this lecture.

    2. The Pre-Generics Problem: Object + Cast

    A generic type parameter compiles to a real check; a raw Object field compiles to nothing. The difference is where the failure lands.

    // Demo.java — the pre-generics Object-and-cast pattern
public class Demo {
    static class OldBox {
        private Object value;
        void set(Object value) { this.value = value; }
        Object get() { return value; }
    }

    public static void main(String[] args) {
        OldBox box = new OldBox();
        box.set("hello");
        String s = (String) box.get();      // mandatory cast
        System.out.println(s.length());     // 5

        box.set(42);
        String n = (String) box.get();      // compiles, fails at runtime
        System.out.println(n);              // ClassCastException
    }
}

    The failure mode is the point: box.set(42) is perfectly legal, the cast (String) box.get() even compiles, and the program dies with ClassCastException only when that line executes. The compiler had enough information to reject it, but the raw Object type threw that information away.

    Interviewer's perspective "What problem do generics solve?" The precise answer is type safety without casts, enforced at compile time. Runtime ClassCastException does not become impossible — erasure and raw types (section 10) can still produce it — but correct generic code turns the class of bug into a compile error.

    3. Generic Classes: Box<T>

    A type parameter is a placeholder for a type, written inside angle brackets after the class name. It is not a field and not a value; it is a compile-time symbol the compiler substitutes for the actual type argument supplied at use site.

    // Demo2.java — a generic class with a type parameter
public class Demo2 {
    static class Box<T> {
        private T value;
        void set(T value) { this.value = value; }
        T get() { return value; }
    }

    public static void main(String[] args) {
        Box<String> s = new Box<>();
        s.set("hello");
        String text = s.get();              // no cast needed

        Box<Integer> i = new Box<>();
        i.set(42);
        int number = i.get();               // auto-unboxed (Lecture 18)
        System.out.println(text + " " + number);   // hello 42
    }
}

    Mechanics worth naming:

    1. T is declared on the class and used in fields, parameters and return types; each new Box<X> binds T to X.
    2. s.set(42) is a compile error — the compiler knows s is a Box<String>.
    3. The diamond operator <> (Java 7) infers the argument from the left-hand side: new Box<>() instead of new Box<String>().
    4. Only reference types may be type arguments — Box<int> is illegal (section 11).

    Important The type parameter is a contract with the compiler, not a runtime field. After compilation, Box<String> and Box<Integer> are both just Box (section 8).

    4. Generic Interfaces and Generic Methods

    The same type-parameter grammar applies to interfaces and to individual methods.

    • Generic interface — the most famous is Comparable<T>, which declares int compareTo(T o). A class implementing Comparable<Employee> can only be compared with another Employee, and Collections.sort knows it.
    • Generic method — the type parameter is declared before the return type, making the method generic independently of its class:
    // Demo3.java — generic methods with and without bounds
public class Demo3 {
    static <T> T pick(T a, T b) {                     // unbounded type parameter
        return a;
    }

    static <T extends Comparable<T>> T max(T a, T b) {   // bounded (section 7)
        return a.compareTo(b) >= 0 ? a : b;
    }

    public static void main(String[] args) {
        String s = pick("one", "two");                 // T inferred as String
        Integer n = pick(1, 2);                        // T inferred as Integer
        System.out.println(max(10, 7));                // 10
        System.out.println(max("apple", "mango"));     // mango
    }
}

    Type inference means the compiler usually derives T from the arguments, so pick("one", "two") is a String-returning call with no explicit <String> needed. When inference fails, the explicit form is Demo3.<String>pick(...).

    Interviewer's perspective A generic method's type parameter lives only for that method call and is inferred at each call site; a generic class's type parameter is fixed for the lifetime of each instance. Mixing the two — a static method trying to use its class's T — is a compile error (section 13).

    5. Type Parameter Naming Conventions

    The letters are not magic; they are a widely followed readability convention. Any identifier works, but the alphabet below is what reviewers and interviewers expect.

    Letter Convention Typical use
    T Type the general first choice
    E Element collection element types, as in List<E>
    K Key map keys, as in Map<K, V>
    V Value map values
    N Number numeric element types
    R Result / return a method's return type
    S, U, V second, third types additional parameters

    Rules: multiple parameters are comma-separated (Map<K, V>), a class may not shadow a type parameter name with a nested class's own, and the letter should never be a real type name such as String — that obscures which identifiers are placeholders.

    6. Bounded Type Parameters: <T extends Number>

    An upper bound restricts what a type argument may be. The keyword is extends even for interfaces — there is no implements bound.

    Form Meaning Example
    <T> Unbounded; the implicit bound is Object static <T> T pick(T a, T b)
    <T extends Number> T is Number or any subtype static double half(T x)
    <T extends Comparable<T>> Self-referential (recursive) bound static <T> T max(...)
    <T extends A & B> Intersection: at most one class, then interfaces <T extends Number & Comparable<T>>
    <T extends A & B & C> Multiple interface bounds <T extends Runnable & Cloneable>

    Three facts to internalize:

    1. One class may precede any number of interfaces, and the class must come first if both are present. <T extends Comparable<T> & Number> is a compile error.
    2. extends is used for interfaces too; there is no implements in a bound.
    3. The bound decides how the body may treat T: only members guaranteed by the bound are callable.

    7. Bounded Generic Method: max with Comparable

    The bound is what unlocks behavior. Without <T extends Comparable<T>>, the compiler sees only Object and refuses to call compareTo; with it, the method may sort, compare or order any type that promises it.

    // reprinted from Demo3.java — the bound unlocks compareTo
static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

    The same idea unlocks numeric operations through Number:

    static <T extends Number> double sum(T x, T y) {
    return x.doubleValue() + y.doubleValue();   // doubleValue() is guaranteed by Number
}

    Without the bound, x.doubleValue() does not compile because T would be only Object. The bound is the bridge between "any type" and "any type that has these methods" — and because the bound's methods are invoked through the erased type, this is the rare place where erasure and polymorphism visibly cooperate (section 8).

    Trap — A bound is a promise the caller must keep, not a conversion. sum(3, 4) works because Integer is a Number, but passing a String fails to compile — the bound is checked where the call is written, not inside the method.

    8. Type Erasure and Its Consequences

    Type erasure is the compiler's strategy for backward compatibility with pre-Java-5 bytecode: it deletes type parameters and replaces each with its bound (or Object when unbounded), then inserts the casts the programmer used to write by hand.

    What the compiler actually does:

    1. Replaces each type parameter with its leftmost bound, or Object if unbounded.
    2. Inserts casts at every use site that needs the concrete type.
    3. Inserts bridge methods so overriding still works after erasure (for example, when Integer.compareTo(Integer) becomes the erased compareTo(Object)).
    Source construct After erasure Consequence
    Box<T> Box No runtime type parameter exists
    <T extends Number> erased to Number Number's methods are callable
    field T value Object or the bound The field itself carries no runtime type
    new T() illegal Cannot instantiate a type parameter
    new T[5] illegal Cannot create a generic array
    new List<String>[] illegal Generic array creation is forbidden
    instanceof List<String> illegal No runtime type info; use List<?>
    catch (T e) illegal Cannot catch a type parameter
    static T field; illegal Static context cannot use the class parameter 
    // Demo4.java — type erasure removes the parameter at runtime
import java.util.ArrayList;
import java.util.List;

public class Demo4 {
    public static void main(String[] args) {
        List<String> a = new ArrayList<>();
        List<Integer> b = new ArrayList<>();
        System.out.println(a.getClass() == b.getClass());   // true — both are ArrayList
        System.out.println(a.getClass().getName());         // java.util.ArrayList

        // Object o = a;                       // legal: a raw view of the list
        // if (o instanceof List<String>) { }  // compile error: no runtime type info
    }
}

    The true on that line is the whole story: at runtime, List<String> and List<Integer> are the same class. Erasure also forbids overloading two methods that differ only by type parameter — void f(List<String>) and void f(List<Integer>) erase to the same void f(List), a name clash compile error.

    Important Because of erasure, the compiler's generic type checks happen only at source compilation. If a raw type sneaks a wrong element past the compiler, no runtime check catches it — that is heap pollution (section 10).

    9. Invariance: List<Integer> Is Not a List<Number>

    Although Integer extends Number, List<Integer> is not a subtype of List<Number>. This is invariance, and it exists for type safety:

    List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;      // compile error — and correctly so

    The rejected assignment is exactly what would break the world. If nums were legal, then nums.add(3.14) — legal for a List<Number> — would put a Double into a list that was declared to hold Integer, and a later int x = ints.get(0) would explode. The compiler refuses the alias rather than allow the contamination.

    Generics are invariant in their type arguments by default; List<? extends Number> (Lecture 28) restores the read-only covariant view safely.

    Interviewer's perspective "Is List<Integer> a subtype of List<Number>?" No. Arrays are covariant (Integer[] is a Number[]) and that covariance famously causes ArrayStoreException; generics chose invariance to avoid the same hole. This is the single most important misconception the wildcard lecture (Lecture 28) fixes.

    10. Raw Types and Heap Pollution

    A raw type is a generic type used without type arguments — List rather than List<String>. Raw types exist only for backward compatibility with 2004-era code, and using them trades away the type checker.

    // Demo5.java — mixing raw and parameterized types causes unchecked warnings
import java.util.ArrayList;
import java.util.List;

public class Demo5 {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        List raw = names;                   // raw type: unchecked assignment
        raw.add(42);                        // heap pollution: an Integer in a List<String>
        String first = names.get(0);        // ClassCastException on read
        System.out.println(first);
    }
}

    The compiler emits an unchecked warning at List raw = names; and then stays silent — the damage surfaces only when names.get(0) is cast back to String at runtime. This is heap pollution: a variable of a parameterized type refers to an object holding a wrong-typed element.

    Aspect Raw type (List) Parameterized (List<String>)
    Type checking None Compile-time
    Casts at retrieval Required Inserted by the compiler
    Warning unchecked warning None
    Runtime safety ClassCastException possible Type errors caught earlier
    When to use Legacy interop only Always, in new code

    11. Generics and Primitives

    A type argument must be a reference type. List<int> and Box<double> do not compile; the workaround is the wrapper classes with autoboxing from Lecture 18.

    Attempted use Allowed Workaround
    List<int> No List<Integer> with autoboxing on insert
    Map<long, double> No Map<Long, Double>
    Box<char> No Box<Character>
    ArrayList<boolean> No ArrayList<Boolean>
    int[] Yes (array, not generic) Arrays are unaffected by erasure

    The cost is the boxing overhead described in Lecture 18: putting an int into an ArrayList<Integer> allocates an Integer, and reading it allocates nothing but unboxes. This is why the JDK keeps primitive-specialised classes such as IntStream (Lecture 39) and why hot numeric loops should use int[] and stay away from generic collections.

    12. Wildcard Teaser (Forward Reference — Lecture 28)

    A wildcard is the question mark ?, used as a type argument that stands for "some unknown type". The three forms you will meet next are:

    1. List<?> — a list of some unknown type; read-only for safe element use.
    2. List<? extends Number> — an upper-bounded wildcard (covariant, producer side).
    3. List<? super Integer> — a lower-bounded wildcard (contravariant, consumer side).

    They are the declared-argument counterpart to the bounded type parameters of section 6: a bounded type parameter (<T extends Number>) fixes one type for the whole method, whereas a wildcard leaves it unknown at each use. The producer/consumer rule ("extends read, super write") and the PECS mnemonic belong to Lecture 28; here it is enough to know that wildcards exist and that invariance (section 9) is what motivates them.

    13. Pitfalls Catalogue

    1. new T() — illegal; the type parameter has no constructor after erasure.
    2. new T[N] and new List<String>[N] — generic array creation is illegal; use an Object[] or an unbounded List<?>.
    3. instanceof List<String> — illegal; there is no runtime type information. Use instanceof List<?>.
    4. Overload clash after erasure — f(List<String>) and f(List<Integer>) erase to the same signature: a compile error.
    5. Static context cannot use the class's type parameter — static T value; or static T identity(T x) inside a generic class does not compile; the static member needs its own <T>.
    6. Generic static fields are impossible — a static field is shared by every instantiation, so it cannot depend on an instance's type parameter.
    7. Casting to a generic type is unchecked — (List<String>) someObject compiles with a warning and can fail later; List<String> in a cast is not verifiable.
    8. Raw types defeat the checker — mixing raw and parameterized types triggers unchecked warnings and heap pollution (section 10).
    9. Assuming a runtime type check — List<String> and List<Integer> are the same class at runtime; no check will separate them.
    10. A bound does not widen the caller's types — a String still fails the <T extends Number> call; the bound constrains, it does not convert.

    Trap — "But new T[5] sometimes works if I cast it!" (T[]) new Object[5] compiles with an unchecked warning and defers the ClassCastException to the caller. It is a known workaround, not a guarantee; the array has no element type and is still a lie about T[].

    14. Myth vs Reality

    Myth Reality
    "Generics exist only to remove casts." They also move type checking to compile time and enable type-safe reusable APIs; removing casts is a visible side effect.
    "Type information is available at runtime." Erasure removes it: List<String> and List<Integer> are the same class at runtime (section 8).
    "List<Integer> is a List<Number> because Integer is a Number." Generics are invariant; the assignment is rejected to prevent contamination (section 9).
    "List<int> works with autoboxing." No — type arguments must be reference types; List<Integer> boxes on insert (section 11).
    "A bound may list interfaces before a class." A single class must come first in an intersection bound: <T extends A & B> (section 6).

    15. Common Trap Questions

    Trap 1 — "Does List<String> compile? Does instanceof List<String>?" The first compiles; the second does not, because erasure leaves no runtime type to test. instanceof List<?> is the legal form.

    Trap 2 — "Can we overload f(List<String>) and f(List<Integer>)?" No — both erase to f(List), a name clash at compile time.

    Trap 3 — "Can T be instantiated or array-created?" No: new T() and new T[5] are both illegal because the constructor and element type do not exist after erasure.

    Trap 4 — "Is <T extends Number> valid? <T extends Runnable>? <T extends Number & Runnable>?" All three are valid; extends bounds interfaces too, and an intersection may combine one class with interfaces.

    Trap 5 — "Can a static method use the enclosing class's T?" No — static context cannot reference the class type parameter; it must declare its own <T>.

    Trap 6 — "What happens when raw and generic types mix?" The compiler issues an unchecked warning and heap pollution becomes possible; the ClassCastException is deferred to the read site.

    Trap 7 — "Why does a.getClass() == b.getClass() print true for List<String> and List<Integer>?" Because both erase to ArrayList; the type arguments exist only in source.

    16. Points to Remember

    1. Generics (Java 5) provide compile-time type safety, remove casts and enable reusable parameterized APIs.
    2. The pre-generics Object holder compiled fine but raised ClassCastException at runtime; generics move the check earlier.
    3. A generic class declares a type parameter (Box<T>); a generic method declares it before the return type (static <T> T pick(...)).
    4. Conventions: T type, E element, K key, V value, N number, R result.
    5. Upper bounds use extends for classes and interfaces; a single class must precede interfaces in <T extends A & B>.
    6. A bound unlocks the bound's members — <T extends Number> enables doubleValue(), <T extends Comparable<T>> enables compareTo.
    7. Erasure replaces a type parameter with its bound (or Object), inserts casts, and inserts bridge methods.
    8. Erasure forbids new T(), new T[], instanceof List<String>, generic static fields, and overloads differing only by type parameter.
    9. Generics are invariant: List<Integer> is not a List<Number>; wildcards (Lecture 28) provide safe variance.
    10. Primitives cannot be type arguments; use wrappers with autoboxing (Lecture 18). Raw types cause unchecked warnings and heap pollution.

    17. Likely Interview Questions

    Question Crisp Answer
    Why were generics introduced? Compile-time type safety, no casts, and reusable type-correct code (Java 5).
    What is a type parameter? A compile-time placeholder for a type, declared in angle brackets and bound to a real type argument at the use site.
    What is type inference? The compiler deriving type arguments from context, as in pick("a", "b") or the diamond new Box<>().
    What is a bounded type parameter? An upper restriction written with extends, valid for classes and interfaces, e.g. <T extends Number>.
    Why extends for interfaces? The bound syntax uses extends for both; there is no implements form.
    Can a bound name a class and interfaces? Yes, one class first then interfaces: <T extends Number & Comparable<T>>.
    What does a bound give you? The guarantee that T has the bound's members, so they can be called inside the method.
    What is type erasure? The compiler deleting type parameters, replacing them with their bound or Object, and inserting casts and bridge methods.
    Name three things erasure forbids. new T(), new T[], and instanceof List<String>; also generic static fields and type-only overloads.
    Is List<Integer> a List<Number>? No — generics are invariant; only wildcards (Lecture 28) allow safe variance.
    What is heap pollution? A parameterized variable referring to an object with an element of the wrong type, usually via raw types.
    Why can't generics use primitives? Type arguments must be reference types, so wrappers plus autoboxing are used instead (Lecture 18).

    18. Final Summary

    pre-generics:  Object holder --> cast (String) --> ClassCastException at runtime
generics:      Box<T> --> compile-time check --> no cast --> safety before runtime

Box<T>, Comparable<T>, <T> T pick(T,T)        (type parameters)
<T extends Number>, <T extends A & B>         (bounds; class first, then interfaces)
erasure: T --> bound/Object + inserted casts + bridge methods
consequence: no new T(), no new T[], no instanceof List<String>, no generic statics
invariance:  List<Integer> ≠ List<Number>    --> wildcards (Lecture 28)
    • Why → compile-time safety, no casts, reusable code; removes the runtime ClassCastException trap of Object.
    • Declare → generic classes (Box<T>), interfaces (Comparable<T>), methods (<T> T pick(...)); name by convention T, E, K, V, N.
    • Bound → extends for classes and interfaces; <T extends A & B> (class first); unlocks the bound's methods.
    • Erasure → type parameters vanish, casts and bridge methods are inserted; no runtime generic type exists.
    • Invariance → List<Integer> is not List<Number>; wildcards are the safe escape (Lecture 28).
    • Raw types → unchecked warnings and heap pollution; primitives need wrappers with autoboxing (Lecture 18).

    Golden rule A type parameter is a promise made to the compiler and erased before the JVM ever sees it — so put the type check where it matters (in the source), bound it to unlock behavior, and never trust a generic type to be verified at runtime.

    One-line takeaway: generics turn the Object-plus-cast pattern into a compile-time contract, bounds using extends decide what that contract may do, and erasure ensures the whole apparatus costs nothing at runtime — at the price of no runtime type information and invariance in the type arguments.
