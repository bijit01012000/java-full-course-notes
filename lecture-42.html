    Part 6 · Optional, Exceptions & Memory · Lecture 42

    Parallel Streams in Java Explained | Primitive Optional Classes

    19 sections · interview-oriented · both themes

    Scope evidence: "Parallel Streams in Java Explained | Primitive Optional Classes" (playlist map, verified). Repo evidence: code/Demo.java.

    Lecture 40 catalogued the stream operations and Lecture 41 introduced Optional as a null-safe container for a possibly missing value. This lecture turns a stream into a multi-threaded pipeline with parallel() and parallelStream(), explains the Fork/Join common pool that silently backs every parallel stream, and states the correctness rules a parallel lambda must obey. It then covers the primitive-optional family — OptionalInt, OptionalLong and OptionalDouble — which the numeric streams return so that no boxing is needed. The governing lesson is that parallelism is an optimization, not a default: it pays only for large, CPU-bound, easily splittable, stateless work, and it silently corrupts results when those conditions are not met.

    1. What a Parallel Stream Is

    A parallel stream is a stream whose operations may execute concurrently: the source is partitioned into chunks, the chunks are processed on several threads, and the partial results are combined into one answer. Everything from Lecture 40 still holds — laziness, single-use, intermediate versus terminal operations — but the pipeline now has a hidden concurrency dimension.

    There are three spellings, and they are not different things:

    1. collection.parallelStream() — obtains a parallel stream directly from a Collection.
    2. stream.parallel() — marks an existing sequential stream as parallel and returns the same stream type.
    3. stream.sequential() — the inverse; it marks the pipeline sequential again.

    The backing engine is the ForkJoinPool.commonPool(). Its default parallelism is Runtime.getRuntime().availableProcessors() - 1, so an eight-core machine runs seven worker threads by default. The internal task-stealing mechanics are covered in Lecture 56 and Lecture 57.

    Important Parallel is a property of the stream instance, not of the terminal operation. list.stream().parallel() and list.parallelStream() have the same effect; the mode is fixed at the moment the terminal operation fires.

    Memory aid Sequential means one thread, encounter order. Parallel means a pool of threads, no promised order. The word "parallel" never appears in the result — it only changes how the result is computed.

    2. How Work Is Split: The Spliterator

    Every stream is fed by a Spliterator (splittable iterator), the source abstraction that can divide itself. Under parallel() the framework repeatedly calls trySplit() to break the source into roughly equal chunks, runs the pipeline per chunk, then merges the partial results. How well a source splits therefore decides whether parallelism helps at all.

    Sources that split well — random access or O(1) division:

    • ArrayList, plain arrays, IntStream.range and IntStream.rangeClosed.
    • Arrays.stream(...), and the key sets of HashMap/HashSet.

    These carry SIZED, SUBSIZED and ORDERED characteristics, so trySplit() divides them cleanly.

    Sources that split poorly:

    • LinkedList — splitting needs traversal, so the halves are unbalanced and the overhead grows.
    • Stream.iterate(...) — inherently sequential and often infinite, so there is almost nothing to split.
    • Some I/O sources such as BufferedReader.lines().

    Golden rule A parallel stream over a poorly splittable source is usually slower than the sequential stream, because the framework pays splitting and merging costs and receives little real concurrency in return.

    3. Making a Stream Parallel

    // Demo.java — the three spellings of a parallel pipeline
import java.util.*;
import java.util.stream.*;

public class Demo {
    public static void main(String[] args) {
        List<Integer> nums = List.of(1, 2, 3, 4, 5, 6, 7, 8);

        int a = nums.parallelStream()
                .mapToInt(Integer::intValue)
                .sum();

        int b = nums.stream()
                .parallel()                          // same effect as parallelStream()
                .mapToInt(Integer::intValue)
                .sum();

        boolean isParallel = nums.stream().parallel().isParallel();   // true
        System.out.println(a + " " + b + " " + isParallel);           // 36 36 true
    }
}

    isParallel() reports the current mode, and it is the only honest way to confirm that a pipeline is parallel after a chain of conversions.

    4. Sequential vs Parallel Streams

    Aspect Sequential stream Parallel stream
    Threads the calling thread only Fork/Join common pool workers
    Chunking none, element by element Spliterator splits into chunks
    Encounter order preserved by default guaranteed only by the ordered terminals
    Overhead low splitting, task scheduling, merging
    Best for small data, I/O, order-sensitive work large, CPU-bound, splittable, stateless work
    Lambda contract lenient must be stateless and non-interfering
    Creation stream() parallelStream() or parallel()
    Default pool size not applicable availableProcessors - 1

    Reading the table: the parallel column is not a strict upgrade. Every entry that costs something — chunking, overhead, the lambda contract — is a condition that must be satisfied before parallel is a win.

    5. When Parallel Helps and When It Hurts

    Condition Parallel helps Parallel hurts
    Data size large (hundreds of thousands of elements or more) small (overhead dominates the useful work)
    Work type CPU-bound computation I/O-bound waiting
    Splittability ArrayList, array, IntStream.range LinkedList, Stream.iterate
    State stateless, side-effect-free lambdas shared mutable state
    Ordering order not required sorted, forEachOrdered, findFirst
    Nesting a single parallel pipeline parallel inside parallel
    Determinism result independent of execution order result depends on execution order

    Interviewer's perspective The expected answer is never "parallel is faster". It is "parallel can be faster when the data is large, the work is CPU-bound, the operations are stateless, and the source splits well; otherwise it adds overhead or introduces bugs, so measure before switching."

    6. Correctness Rules: Stateless, Non-Interfering, No Shared Accumulators

    A parallel lambda must satisfy three contracts:

    1. Stateless — it must not depend on mutable state that can change between invocations.
    2. Non-interfering — it must not modify the stream source while the pipeline runs.
    3. No shared mutable accumulators — concurrent updates to one list, map or array element are a data race.

    The classic broken example mutates a shared ArrayList:

    // Demo2.java — shared mutable accumulator: wrong under parallel
import java.util.*;
import java.util.stream.*;

public class Demo2 {
    public static void main(String[] args) {
        List<Integer> nums = IntStream.rangeClosed(1, 1000)
                .boxed()
                .collect(Collectors.toList());

        List<Integer> shared = new ArrayList<>();
        nums.parallelStream().forEach(shared::add);   // data race: entries lost or corrupt
        System.out.println(shared.size());            // usually less than 1000
    }
}

    The fix is to let the framework own the accumulation:

    // Demo2.java — the correct, parallel-safe replacement
List<Integer> safe = nums.parallelStream()
        .collect(Collectors.toList());            // framework merges chunk results

    The same defect appears with a captured array slot (int[] total = {0}; stream.forEach(x -> total[0] += x)) and with a captured mutable counter. The cure is always the same: express the intent as reduce or collect, never as a side effect on shared state.

    7. reduce and collect in Parallel

    reduce performs an immutable reduction: it folds the elements into one new value. In parallel, the two-argument form reuses the accumulator as the combiner, so the operation must be associative and the identity must be a true identity. When the accumulated type differs from the element type, the three-argument form supplies an explicit combiner that merges the per-chunk partials.

    // Demo2.java — a correct parallel reduction and a parallel collector
import java.util.*;
import java.util.stream.*;

public class Demo2 {
    public static void main(String[] args) {
        List<Integer> nums = IntStream.rangeClosed(1, 1000)
                .boxed()
                .collect(Collectors.toList());

        int sum = nums.parallelStream()
                .reduce(0, Integer::sum, Integer::sum);   // identity, accumulator, combiner

        Map<Integer, List<Integer>> byParity = nums.parallelStream()
                .collect(Collectors.groupingBy(n -> n % 2));   // framework merges buckets

        System.out.println(sum);                          // 500500
        System.out.println(byParity.get(0).size());       // 500
    }
}

    collect is built for parallelism: the standard collectors use a per-thread container and a combiner. For a shared concurrent container, Collectors.groupingByConcurrent(...) and Collectors.toConcurrentMap(...) write into a ConcurrentHashMap, which can reduce merging work. The trade-off is that a concurrent collector does not promise encounter order, so use it only when order is irrelevant.

    Important A non-associative combiner silently produces wrong answers in parallel. reduce(0, (a, b) -> a - b) is fine sequentially and wrong in parallel, because subtraction has no associativity to rely on.

    8. Ordering Under Parallelism

    Encounter order is the order in which the source presents its elements. Parallel execution may process them in any order, so the terminals that promise order pay a coordination cost.

    Terminal Order guarantee Parallel fit
    forEach none in parallel excellent, order-agnostic
    forEachOrdered encounter order enforced works, but reduces the speedup
    findFirst first in encounter order possible, less parallel
    findAny any matching element preferred under parallel
    collect(toList) preserves encounter order for ordered streams good
    sorted stable for ordered streams needs every element before emitting

    Memory aid forEach races, forEachOrdered queues; findAny picks, findFirst waits. Reach for the second of each pair only when the semantics truly require it.

    9. Performance Caveats

    • The common pool is shared across the whole JVM. A blocking task — a sleep, a network call, a lock — occupies a worker and can starve unrelated parallel streams. Never do blocking I/O inside a parallel stream.
    • Parallelism has fixed overhead: splitting, task creation and merging. On small data it is pure loss.
    • Measure, do not guess. Use a real benchmark harness (JMH) and account for JIT warm-up; a single cold timing run is misleading.
    • Amdahl's law intuition: the sequential fraction of the work caps the speedup, however many cores exist.
    • Thread count is not throughput. Seven threads doing trivial work is slower than one.
    • Nested parallel pipelines oversubscribe the pool and rarely help; flatten them.

    Golden rule Reach for sequential first; switch to parallel only when the workload is large, CPU-bound, stateless and easily split, and only after measuring both versions.

    10. The Primitive Optional Classes

    Lecture 41 introduced Optional<T> for reference types. Using Optional<Integer> for a numeric result would reintroduce the very boxing the primitive streams were built to avoid, so Java ships three primitive specializations:

    • OptionalInt — a container for a possibly absent primitive int.
    • OptionalLong — a container for a possibly absent primitive long.
    • OptionalDouble — a container for a possibly absent primitive double.

    They are not generic and are not subtypes of Optional; they are separate value-type-specific containers with their own API. Their common methods are:

    Purpose Method Note
    Create present OptionalInt.of(5) null is not allowed
    Create absent OptionalInt.empty() shared empty instance
    Test presence isPresent(), isEmpty() isEmpty is Java 11
    Read getAsInt() throws NoSuchElementException when empty
    Default orElse(0), orElseGet(...) orElseGet takes a supplier
    Act ifPresent(...), ifPresentOrElse(...) Java 9 adds the two-branch form
    Convert stream() (Java 9), then boxed() turns it into an IntStream/Stream<Integer>

    Important getAsInt() is the OptionalInt analogue of Optional.get() and it fails the same way on an empty container. Prefer orElse, orElseGet or ifPresent.

    11. Stream Integration: Numeric Terminals Return Primitive Optionals

    The numeric streams terminate into primitive optionals because a stream may be empty and a result may not exist.

    // Demo3.java — primitive optionals produced by IntStream terminals
import java.util.*;
import java.util.stream.*;

public class Demo3 {
    public static void main(String[] args) {
        int[] values = {4, 9, 2, 7, 5};

        OptionalInt max = Arrays.stream(values).max();          // OptionalInt
        OptionalInt min = Arrays.stream(values).min();          // OptionalInt
        OptionalDouble avg = Arrays.stream(values).average();   // OptionalDouble

        System.out.println(max.getAsInt());                     // 9
        System.out.println(min.orElse(-1));                     // 2
        System.out.println(avg.orElse(0.0));                    // 5.4

        max.ifPresent(m -> System.out.println("max=" + m));     // max=9

        Optional<Integer> boxed = max.stream().boxed().findFirst();
        System.out.println(boxed.orElse(-1));                   // 9
    }
}

    An empty numeric stream therefore yields OptionalInt.empty() or OptionalDouble.empty() rather than a default sentinel. The terminal map is: max(), min() and findFirst()/findAny() on an IntStream return OptionalInt; average() returns OptionalDouble; summaryStatistics() returns a statistics object, not an optional.

    12. OptionalInt vs Optional

    Aspect Optional<Integer> OptionalInt
    Element type reference wrapper Integer primitive int
    Boxing allocates a wrapper no boxing
    Generic yes, works for any T no, int only
    Library use general-purpose APIs numeric stream terminals
    Read method get() getAsInt()
    Default method orElse(Integer) orElse(int)
    Produced by Stream<Integer> terminals IntStream terminals
    Conversion not specialized opt.stream().boxed().findFirst() returns Optional<Integer>
    Siblings none OptionalLong, OptionalDouble

    Reading the table: choose OptionalInt whenever the value is a primitive int produced by a numeric stream; choose Optional<Integer> when the container must participate in generic code.

    13. Worked Example: Parallel Sum, Ordered Print, and findAny

    // Demo4.java — parallel sum of a large range, ordered printing, parallel search
import java.util.*;
import java.util.stream.*;

public class Demo4 {
    public static void main(String[] args) {
        long total = IntStream.rangeClosed(1, 10_000_000)
                .parallel()
                .asLongStream()                 // avoid int overflow
                .sum();
        System.out.println(total);              // 50000005000000

        IntStream.range(1, 10)
                .parallel()
                .forEachOrdered(System.out::print);   // 123456789
        System.out.println();

        OptionalInt any = IntStream.rangeClosed(1, 1_000_000)
                .parallel()
                .filter(n -> n % 100_000 == 0)
                .findAny();                     // parallel-friendly search
        System.out.println(any.orElse(-1));
    }
}

    The first pipeline demonstrates a large, splittable, associative sum — the ideal case. The second shows why forEachOrdered exists: plain forEach would print the digits in no defined order. The third shows findAny, the search terminal built for parallel execution.

    14. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Using parallel by default overhead makes small or I/O work slower keep sequential; parallelize only after measurement
    Shared mutable accumulator lost updates and corrupt results use reduce or collect
    Assuming order in forEach nondeterministic output use forEachOrdered when order matters
    Blocking call inside parallel starves the shared common pool keep I/O out, or use a dedicated executor
    Parallel over I/O threads idle while waiting use async I/O or remain sequential
    Nested parallel pipelines oversubscription, little speedup flatten to one parallel pipeline
    Non-associative combiner silently wrong result use associative operations
    LinkedList or Stream.iterate source poor splitting, slower than sequential use ArrayList, an array or IntStream.range
    Mistaking thread count for speed more threads, no more throughput benchmark with JMH
    getAsInt() on empty throws NoSuchElementException use orElse/orElseGet/ifPresent

    15. Myth vs Reality

    Myth Reality
    "Parallel is always faster." Overhead and poor splitting make it slower for small data and sequential sources.
    "parallelStream() uses one thread per element." It uses the shared common pool, with parallelism availableProcessors - 1.
    "forEach preserves order in parallel." Order is unspecified; use forEachOrdered when order is required.
    "OptionalInt is just Optional<Integer>." It is a non-generic primitive specialization that avoids boxing.
    "reduce works in parallel with any combiner." The combiner must be associative, or results are silently wrong.

    16. Common Trap Questions

    Trap 1 — Pool size: "How many threads does a parallel stream use on an eight-core machine?" Seven — the common pool's parallelism is availableProcessors - 1; it is shared JVM-wide.

    Trap 2 — Order in forEach: "Does a parallel forEach print elements in source order?" No. The visit order is unspecified; forEachOrdered enforces encounter order at the cost of some speedup.

    Trap 3 — Shared list: "Why does parallelStream().forEach(list::add) lose elements?" Concurrent mutation of an unsynchronized ArrayList is a data race; use collect(Collectors.toList()).

    Trap 4 — findAny versus findFirst: "In a parallel stream, does findAny return the first match?" No. It may return any match and is deliberately non-deterministic; use findFirst when order matters.

    Trap 5 — Empty primitive optional: "What does IntStream.empty().max().getAsInt() do?" It throws NoSuchElementException; max() returns OptionalInt.empty(), so guard with orElse.

    Trap 6 — Splitting quality: "Is a parallel stream over a LinkedList faster than sequential?" Usually not. LinkedList splits poorly, so the framework pays overhead without gaining parallelism; Stream.iterate is worse still.

    Trap 7 — Blocking the pool: "Is it safe to call a slow network service inside a parallel stream?" No. The common pool is shared; blocking workers can starve every other parallel stream in the JVM.

    Trap 8 — Return types: "What does IntStream.max() return — int or OptionalInt?" OptionalInt. A stream may be empty, so the terminal cannot return a bare primitive.

    17. Points to Remember

    1. A parallel stream splits the source, processes chunks on the Fork/Join common pool, and merges results.
    2. parallelStream(), parallel() and the inverse sequential() control the mode; isParallel() reports it.
    3. Default common-pool parallelism is availableProcessors - 1; the pool is shared JVM-wide (Lecture 56/57).
    4. The Spliterator decides splitting quality: ArrayList, arrays and IntStream.range split well; LinkedList and Stream.iterate split poorly.
    5. Parallel pays off for large, CPU-bound, stateless, easily splittable work and costs for small, I/O-bound or order-sensitive work.
    6. Lambdas must be stateless, non-interfering and free of shared mutable accumulators.
    7. reduce needs an associative accumulator and combiner; collect merges per-chunk containers, with groupingByConcurrent for shared concurrent maps.
    8. Ordering: forEach is unordered in parallel, forEachOrdered enforces encounter order, findAny is parallel-friendly, findFirst is not.
    9. OptionalInt, OptionalLong and OptionalDouble avoid boxing and are returned by numeric stream terminals such as max(), min(), average() and findFirst().
    10. Never add parallel by default; measure with a real benchmark and honor Amdahl's law before trusting a speedup.

    18. Likely Interview Questions

    Question Crisp Answer
    What is a parallel stream? A stream whose operations may run concurrently: the source is split into chunks, processed on pool threads, and merged.
    How do you create a parallel stream? collection.parallelStream(), or stream.parallel(); sequential() reverses it.
    Which thread pool backs parallel streams? The shared ForkJoinPool.commonPool(), whose parallelism defaults to availableProcessors - 1.
    What decides whether parallel helps? Data size, CPU-bound work, stateless operations and how well the Spliterator splits the source.
    Why can a LinkedList parallel stream be slower? Its Spliterator splits poorly, so splitting and merging overhead is paid without real parallelism.
    Why must parallel lambdas be stateless? Shared mutable state is updated concurrently and produces data races and wrong results.
    How do you accumulate correctly in parallel? Use reduce with an associative combiner, or collect with a collector; never mutate a shared container.
    Difference between forEach and forEachOrdered? forEach gives no order in parallel; forEachOrdered enforces encounter order at reduced parallelism.
    Difference between findFirst and findAny? findFirst respects encounter order; findAny may return any element and suits parallel search.
    Does collect(groupingBy(...)) preserve order in parallel? The standard collector preserves encounter order for ordered streams; groupingByConcurrent does not.
    What are the primitive optional types? OptionalInt, OptionalLong and OptionalDouble — non-generic containers that avoid boxing for numeric streams.
    Why does IntStream.max() return OptionalInt? A stream may be empty, so the terminal returns a container; getAsInt() throws when it is empty.

    19. Final Summary

    sequential : one thread, encounter order, low overhead
parallel   : ForkJoinPool.commonPool (parallelism = availableProcessors - 1)
             Spliterator.trySplit() -> chunks -> merge

splits well : ArrayList, arrays, IntStream.range
splits badly: LinkedList, Stream.iterate

helps  : large data · CPU-bound · stateless · splittable source · order not needed
hurts  : small data · I/O-bound · shared mutable state · order-sensitive · nested parallel

rules  : stateless, non-interfering, no shared accumulators
         reduce(identity, accumulator, combiner)  combiner must be associative
         collect(toList / groupingBy)             groupingByConcurrent -> no order promise

order  : forEach (none)  vs  forEachOrdered (encounter order)
         findAny (any)   vs  findFirst (encounter order)

primitive optionals : OptionalInt · OptionalLong · OptionalDouble
   IntStream.max()/min()/findFirst() -> OptionalInt
   IntStream.average()               -> OptionalDouble
   opt.stream().boxed().findFirst()  -> Optional<Integer>
    • Modes → parallelStream() or parallel(); isParallel() confirms it; the shared common pool does the work.
    • Splitting → the Spliterator decides success; random-access sources split, linked and iterate sources do not.
    • Fit → large, CPU-bound, stateless, splittable, order-agnostic work only; otherwise parallel is slower.
    • Correctness → stateless non-interfering lambdas plus reduce/collect, never shared mutable accumulators.
    • Ordering → forEach versus forEachOrdered, findAny versus findFirst, collect preserves encounter order.
    • Performance → the common pool is shared; don't block it; measure with JMH and remember Amdahl's law.
    • Primitive optionals → OptionalInt/OptionalLong/OptionalDouble avoid boxing; boxed() crosses back to the generic world.

    Golden rule Use parallel streams only when the work is large, CPU-bound, stateless and easily split; use OptionalInt and its siblings whenever a numeric stream hands back a possibly absent primitive.

    One-line takeaway: a parallel stream is an optimization that the shared common pool performs only when the source splits, the work is stateless and CPU-bound and the data is large, while OptionalInt, OptionalLong and OptionalDouble keep numeric results unboxed and null-safe.
