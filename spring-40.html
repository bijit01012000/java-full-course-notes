    Part 7 · Auth, Testing & Capstone Projects · Lecture 40

    Testing Spring Boot Applications

    19 sections · interview-oriented · both themes

    Scope evidence: "Testing Spring Boot Applications | JUnit 5, Mockito & MockMvc" (playlist map, verified). Repo folder is the springTestingDemo project: entity.Product, repository.ProductRepository, service.ProductService, service.PriceCalculator, controller.ProductController, plus test classes PriceCalculatorTest, ProductServiceTest, ProductControllerTest, and ProductRepositoryTest.

    Writing code and proving it behaves correctly are two different activities. This lecture turns testing into a layered discipline: plain JUnit for pure logic, JUnit plus Mockito for a service with dependencies, @WebMvcTest plus MockMvc for a controller's HTTP contract, and @DataJpaTest plus a real database for repository queries. Every test answers one question: how much real application infrastructure must participate to prove this one behaviour?

    1. Why Testing Exists

    Consider this method:

    public int calculateFinalPrice(int price, int discountPercentage) {
    return price - (price * discountPercentage / 100);
}

    The method appears to work, but "looks correct" is not evidence. A manual run with price 1000, discount 20, and expected result 800 returns the right number, yet several questions remain:

    • What happens when the discount is 0?
    • What happens when the discount is 100?
    • What happens when the discount is negative?
    • What happens when the discount is greater than 100?
    • What happens if someone changes the formula later?

    Testing verifies that the behaviour of the code matches its requirements. A single happy-path run proves almost nothing; the edge cases above are exactly where production bugs live.

    Important: A test is not "proof that the code runs." It is proof that a specific input produces a specific, expected output. A suite's value comes from the number of truthful behaviours it pins down.

    2. Manual Testing vs Automated Testing

    Manual testing means a developer performs a sequence by hand:

    1. Starts the application.
    2. Prepares a request.
    3. Calls the endpoint.
    4. Inspects the response.
    5. Decides whether the result is correct.

    This can work for a small application, but it becomes slow and unreliable as the application grows.

    An automated test does the same reasoning without a human in the loop:

    1. Provides a known input.
    2. Executes the production code.
    3. Compares the actual result with the expected result.
    4. Reports whether the test passed or failed.
    Known input -> execute production code -> actual output
            -> compare with expected output -> pass or fail
    Aspect Manual testing Automated testing
    Who executes A human clicks and inspects A test runner executes code
    Speed Slow, repeated by hand Fast, repeatable in seconds
    Reliability Tired humans miss regressions Same check on every run
    Cost as app grows Grows with every feature Written once, rerun forever
    Feedback After a manual click-through Immediately, in the build
    Regression safety Almost none Strong: old behaviour stays pinned
    Best for Exploratory checks, demos Behaviour that must never break

    Interviewer's perspective: "Why automate?" The honest answer is not "tests are good." It is that manual testing does not scale: paths grow faster than human attention, so regressions slip through unless a machine re-checks every promise on every change.

    3. Test Cases: Arrange, Act, Assert

    A test case contains three fundamental parts: the initial condition, the action, and the expected result.

    Initial condition: Price is 1000 and discount is 20%
Action:            Calculate the final price
Expected result:   Final price should be 800

    In testing terminology this is commonly called Arrange, Act and Assert:

    • Arrange - prepare the data and environment required by the test.
    • Act - execute the behaviour being tested.
    • Assert - compare the actual result with the expected result.
    // Arrange
int price = 1000;
int discount = 20;

// Act
int actualPrice = calculator.calculateFinalPrice(price, discount);

// Assert
assertEquals(800, actualPrice);

    Mnemonic: AAA - "Arranger sets the stage, Act performs, Assert proves." The names are Arranger-Act-Assert because each block has one job.

    Golden rule: One test asserts one behaviour. If a test name needs the word "and", it is probably two tests wearing one coat.

    Tests are written for the behaviours a method promises, not for its lines. The requirement "a discount must be between 0 and 100" hides four behaviours: a valid discount calculates the final price; a discount below 0 is rejected; a discount above 100 is rejected; a negative price is rejected.

    4. Unit Tests vs Integration Tests and the Test Pyramid

    A common Spring Boot flow is Controller -> Service -> Repository -> Database.

    A unit test verifies a small unit of behaviour in isolation. A test for ProductService should not require the Spring ApplicationContext, Tomcat, a real database, or an HTTP request. If ProductService depends on ProductRepository, the real repository can be replaced with a controlled test double.

    An integration test checks whether multiple real components work together, for example Repository + Hibernate + H2/MySQL, or Controller + Service + Repository + Database.

    The important question is not which annotation is used. The real question is: how much real application infrastructure participates in the test?

    Test type What is real? Relative speed Main purpose
    Unit test One class or unit of behaviour Fastest Verify business logic
    Slice test One application layer Fast Verify a specific Spring layer
    Integration test Multiple components Slower Verify components work together
    End-to-end test Complete application flow Slowest Verify the complete user journey

    A healthy suite is a pyramid: many fast unit tests, fewer integration tests, very few end-to-end tests. If every test starts Spring Boot and connects to a database, the suite becomes slow and developers stop running it.

    5. What Deserves a Unit Test

    Prioritize code that contains behaviour or decisions: business calculations, conditional branches, data transformations, validation rules, exception conditions, authorization decisions, service-layer orchestration, and important edge cases.

    Usually avoid unit-testing plain getters and setters, framework behaviour, built-in methods of JpaRepository, and code with no meaningful decision or transformation. There is no need to prove that Spring Data's save() works. The important part is whether the application calls save() under the correct business conditions.

    Important: Test your decisions, not the framework's. A test that asserts a mocked save() returns what the mock was told to return has tested Mockito, not your code.

    6. JUnit Fundamentals

    JUnit provides annotations such as @Test, a programming model for declaring tests, test discovery and execution, integration with Maven, Gradle and IDEs, and assertions such as assertEquals(). The annotations used in modern Spring Boot tests belong to JUnit Jupiter: org.junit.jupiter.api.Test.

    A Spring Boot project normally includes the test starter:

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>

    The test scope means these libraries are available for compiling and running tests but are not included as normal production dependencies. spring-boot-starter-test bundles JUnit, Mockito, AssertJ, Hamcrest, Spring Test, and JSON testing utilities.

    Production code belongs in src/main/java; test code belongs in src/test/java. The test package should normally mirror the production package:

    src/main/java/com/example/demo/service/ProductService.java
src/test/java/com/example/demo/service/ProductServiceTest.java

    This keeps a production class and its corresponding test easy to locate.

    7. Writing the First JUnit Test

    Production class PriceCalculator:

    public class PriceCalculator {
    public int calculateFinalPrice(int price, int discountPercentage) {
        if (price < 0) {
            throw new IllegalArgumentException("Price cannot be negative");
        }
        if (discountPercentage < 0 || discountPercentage > 100) {
            throw new IllegalArgumentException("Discount must be between 0 and 100");
        }
        return price - (price * discountPercentage / 100);
    }
}

    Test class PriceCalculatorTest:

    import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

class PriceCalculatorTest {

    private PriceCalculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new PriceCalculator();
    }

    @Test
    void shouldApplyDiscountToPrice() {
        // Arrange
        int price = 1000;
        int discount = 20;

        // Act
        int actualPrice = calculator.calculateFinalPrice(price, discount);

        // Assert
        assertEquals(800, actualPrice);
    }

    @Test
    void shouldRejectDiscountAboveHundred() {
        IllegalArgumentException exception = assertThrows(
            IllegalArgumentException.class,
            () -> calculator.calculateFinalPrice(1000, 120)
        );
        assertEquals("Discount must be between 0 and 100", exception.getMessage());
    }
}

    This test does not use @SpringBootTest or @Autowired, and it does not start the Spring ApplicationContext. PriceCalculator is a regular Java class, so it can be created with new. Spring Boot applications are still Java applications; the container should not be started when the behaviour can be tested directly.

    @Test tells JUnit to discover and execute the method as a test case. Names should describe behaviour (shouldApplyDiscountToPrice()); avoid test1() or checkMethod().

    8. Assertions and Test Lifecycle

    An assertion describes a condition that must be true for the test to pass.

    Assertion Use it when Example
    assertEquals() Comparing expected with actual assertEquals(800, actualPrice);
    assertTrue() / assertFalse() Checking a boolean state assertTrue(result.isActive());
    assertNull() / assertNotNull() Checking presence or absence assertNotNull(savedProduct.getId());
    assertThrows() An exception is the expected behaviour assertThrows(IllegalArgumentException.class, () -> ...);

    assertThrows() returns the thrown exception, so the message can be checked too. The test passes only when the specified code throws IllegalArgumentException; if no exception is thrown, the test fails.

    @BeforeEach runs before every test method and is useful for preparation shared by multiple tests (for example, creating calculator). @AfterEach runs after every test method and is useful when a test manually opens a resource that must be closed. There is no need to add an empty @AfterEach merely because the annotation exists.

    Run tests from IntelliJ, or run the complete Maven suite with ./mvnw test. Green means the expected behaviour was observed; red means expected and actual behaviour did not match. A failing test may mean the test's expectation is incorrect, the production code is incorrect, or the requirement has changed.

    9. Unit Testing the Service Layer with Mockito

    Consider ProductService, which depends on ProductRepository:

    @Service
public class ProductService {
    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    public Product getProductById(Long id) {
        return productRepository.findById(id)
            .orElseThrow(() -> new ProductNotFoundException("Product not found: " + id));
    }

    public Product createProduct(Product product) {
        if (productRepository.existsByName(product.getName())) {
            throw new IllegalArgumentException("Product already exists");
        }
        return productRepository.save(product);
    }
}

    ProductService cannot be created without a ProductRepository. Using the real repository could require a Spring Data proxy, EntityManager, Hibernate, DataSource, and a database, and a failure could then come from the database instead of the service logic. That would no longer be an isolated unit test, so the dependency is replaced with a controlled test double.

    Double What it is
    Dummy An object passed only because a method requires it; its behaviour is not used
    Stub An object that returns predefined answers (e.g. findById(1) returns a fixed product)
    Fake A simplified but working implementation, such as a HashMap-backed in-memory repository
    Mock A configurable double that returns values, throws, records calls, and can be verified

    Mockito creates mocks without manually written fake repository classes:

    import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class ProductServiceTest {

    @Mock
    private ProductRepository productRepository;

    @InjectMocks
    private ProductService productService;
}

    @ExtendWith(MockitoExtension.class) connects Mockito's lifecycle with JUnit Jupiter and initializes the annotated fields, because JUnit does not process Mockito annotations by itself. @Mock makes Mockito create an object that implements ProductRepository - not a Spring bean, not a Spring Data proxy, not connected to a database. @InjectMocks makes Mockito create ProductService and inject the available mock into its constructor, like new ProductService(Mockito.mock(ProductRepository.class)). It is a Mockito convenience, not Spring dependency injection.

    Important: Mockito is not testing the repository. It is creating a predictable environment in which the service can be tested. A mock's return value proves nothing about the real database.

    @ExtendWith(MockitoExtension.class)
class ProductServiceTest {

    @Mock
    private ProductRepository productRepository;

    @InjectMocks
    private ProductService productService;

    @Test
    void shouldReturnProductWhenProductExists() {
        // Arrange
        Product product = new Product(1L, "Laptop", 10);
        when(productRepository.findById(1L)).thenReturn(Optional.of(product));

        // Act
        Product result = productService.getProductById(1L);

        // Assert
        assertEquals(1L, result.getId());
        assertEquals("Laptop", result.getName());
        verify(productRepository).findById(1L);
    }

    @Test
    void shouldRejectProductWhenNameAlreadyExists() {
        // Arrange
        Product request = new Product(null, "Keyboard", 20);
        when(productRepository.existsByName("Keyboard")).thenReturn(true);

        // Act and Assert
        assertThrows(
            IllegalArgumentException.class,
            () -> productService.createProduct(request)
        );

        verify(productRepository).existsByName("Keyboard");
        verify(productRepository, never()).save(any(Product.class));
    }
}

    The stubbing when(productRepository.findById(1L)).thenReturn(Optional.of(product)); means: if findById(1L) is called on this mock, return the predefined Product. The final verification matters: the rule says a duplicate must not be saved, so the absence of the save() call is part of the required behaviour. A missing product is tested the same way by stubbing findById(99L) with Optional.empty() and asserting ProductNotFoundException.

    10. Stubbing, Assertion and Verification

    These three concepts have different responsibilities:

    Concept Code Responsibility
    Stubbing when(repository.findById(1L)).thenReturn(Optional.of(product)); Defines how the dependency should behave
    Assertion assertEquals("Laptop", result.getName()); Checks the observable result
    Verification verify(repository).findById(1L); Checks whether the interaction happened 
    when()   -> Control the dependency
assert() -> Check the result
verify() -> Check the interaction
    Aspect Stubbing (when(...).thenReturn(...)) Verification (verify(...))
    Direction "When asked, answer this" "Did you get asked?"
    Purpose Set up a predictable return value Assert the interaction happened
    Runs Before the Act step After the Act step
    Fails when The stubbed method is never used (with strict stubs) The expected call did not occur, or occurred the wrong number of times
    Example when(repo.findById(1L)).thenReturn(...) verify(repo).findById(1L)
    Optional? Required for every value the code reads Only when the interaction is the behaviour

    verify() need not be called for every mocked method; use it when the interaction itself is part of the behaviour being tested. Argument matchers (any(), anyLong(), anyString(), eq(value)) allow flexible stubbing and verification: use exact values when the exact argument matters, matchers when only the type matters. When a matcher is used for one argument of a multi-argument method, use matchers for all arguments: when(repository.search(eq("Laptop"), eq(true))).thenReturn(products);

    11. Testing Spring MVC Controllers with MockMvc

    The controller is responsible for the HTTP contract: which URL and method are accepted, how JSON converts to Java, whether path variables are read correctly, whether validation runs, which status code and JSON are returned, how exceptions become HTTP responses, and whether security permits the request. A controller test should not repeat all service business-logic tests; that belongs in the service unit tests.

    Calling controller.getProduct(1L) and checking the ResponseEntity tests the Java method, but it does not verify @GetMapping("/{id}"), @PathVariable conversion, @RequestBody deserialization, @Valid validation, HTTP status handling, JSON serialization, Spring Security filters, or global exception handlers. The controller must therefore be tested through Spring MVC's request-processing infrastructure.

    @WebMvcTest(ProductController.class) creates a limited Spring ApplicationContext containing components relevant to the web layer. Loaded: controller, DispatcherServlet, Jackson JSON conversion, validation, controller advice, MVC configuration, and security filters. Not loaded: the real service, real repository, Hibernate, database, or complete application. This is a test slice: only the part of the application required by the test is loaded.

    MockMvc creates an HTTP-like request without starting a real web server:

    Mock HTTP request -> Spring Security filter chain -> DispatcherServlet
                  -> Controller -> HTTP-like response

    There is no localhost, no port 8080, no running Tomcat, and no Postman, yet Spring MVC still processes the request using its real web infrastructure.

    In the service unit test, @Mock created a plain Mockito field because there was no Spring context. In a controller test, Spring creates ProductController, whose constructor requires a ProductService bean, so the mock must be placed inside Spring's test context.

    Annotation Managed by Placed in the Spring context?
    @Mock Mockito No
    @MockitoBean Spring Test and Mockito Yes

    @MockitoBean creates or replaces the corresponding bean in the Spring test ApplicationContext with a Mockito mock. For current Spring versions use @MockitoBean; older Spring Boot projects may use the now-deprecated @MockBean.

    @WebMvcTest(ProductController.class)
class ProductControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private ProductService productService;

    @Test
    @WithMockUser
    void shouldReturnProductWhenProductExists() throws Exception {
        // Arrange
        Product product = new Product(1L, "Laptop", 10);
        when(productService.getProductById(1L)).thenReturn(product);

        // Act and Assert
        mockMvc.perform(get("/api/products/1")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.id").value(1))
            .andExpect(jsonPath("$.name").value("Laptop"))
            .andExpect(jsonPath("$.stock").value(10));

        verify(productService).getProductById(1L);
    }
}

    Key pieces: mockMvc.perform(...) creates and executes the mock request; .andExpect(status().isOk()) verifies 200 OK; content().contentTypeCompatibleWith(...) verifies the body represents JSON; and jsonPath("$.name").value("Laptop") verifies a field inside the response. For the response {"id": 1, "name": "Laptop", "stock": 10}, the JSON paths are $.id, $.name, and $.stock.

    A POST test verifies that the POST mapping works, JSON converts into a Product, the controller calls the service, the status is 201 Created, and the saved product becomes response JSON. Send the body with .content(requestBody) and .contentType(MediaType.APPLICATION_JSON), stub with when(productService.createProduct(any(Product.class))).thenReturn(savedProduct), assert status().isCreated() and the jsonPath fields, then verify. For unsafe methods (POST, PUT, DELETE), include .with(csrf()) when CSRF protection is enabled.

    If Spring Security protects the endpoint, an unauthenticated request may return 401 Unauthorized; use @WithMockUser to run a test as an authenticated user (@WithMockUser(username = "aditya", roles = "ADMIN")). For Spring Boot 4, add the technology-specific spring-boot-starter-security-test starter with test scope.

    12. What Happens During a MockMvc Call

    When the test sends GET /api/products/1, Spring MVC must:

    1. Match the request with @GetMapping("/{id}").
    2. Extract 1 from the URL.
    3. Convert it into a Long.
    4. Call the controller method.
    5. Serialize the returned Product into JSON.
    6. Generate an HTTP response.
    GET /api/products/1
    -> 1. match mapping    -> @GetMapping("/{id}")
    -> 2. extract path var -> "1"
    -> 3. convert type     -> Long 1
    -> 4. call controller  -> getProduct(1L)
    -> 5. serialize JSON   -> {"id":1,"name":"Laptop","stock":10}
    -> 6. build response   -> 200 OK + JSON body

    Every step is real Spring MVC machinery. That is why a controller test beats calling controller.getProduct(1L) directly: steps 1, 2, 3, 5, and 6 never run when you call the method yourself.

    13. Repository and Integration Testing

    Mocking a repository does not prove that the real query works:

    ProductRepository repository = mock(ProductRepository.class);
when(repository.findByNameIgnoreCase("laptop")).thenReturn(Optional.of(product));

    This only proves that Mockito returns the value configured in the test; it does not execute or validate the real query.

    @DataJpaTest loads the JPA-related slice of the application. Loaded: entities, Spring Data repositories, Hibernate, EntityManager, DataSource, and an embedded database. Not loaded: controllers, normal service beans, web server, or complete application. When an embedded database is present, Spring Boot configures it for the test. Data JPA tests are transactional and their changes are rolled back after each test.

    H2 is an embedded database that runs inside the test process:

    <dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>

    Benefits of H2 for tests: no separate installation, no database server to start, fast execution, and a fresh, isolated environment.

    14. Choosing the Smallest Test Environment

    Area under test Main tool or annotation Real components Replaced components Main confidence provided
    Plain Java logic JUnit, @Test Class under test None Calculations, validation and edge cases behave correctly
    Service layer Mockito, @Mock, @InjectMocks Class under test Repository or other dependencies Business logic and orchestration behave correctly
    MVC controller MockMvc, @WebMvcTest, @MockitoBean Spring MVC web layer Service HTTP mappings, JSON, status codes, validation and security behave correctly
    Repository @DataJpaTest and H2 Repository, Hibernate and database Other application layers Entity mappings and repository queries work correctly
    Full integration @SpringBootTest Complete application context Nothing Real components from several layers work together
    Annotation Slice loaded Speed Typical use
    @WebMvcTest Web layer only Fast HTTP contract of a controller
    @DataJpaTest JPA layer only Fast Entity mapping and real query correctness
    @SpringBootTest Complete application context Slowest Full integration across layers

    Golden rule: Use the smallest test environment that can prove the behaviour being tested.

    Fast unit tests and focused integration tests work together to give reliable feedback without making the suite unnecessarily slow.

    15. Myth vs Reality

    Myth Reality
    "If the method runs and returns a number, it is correct" Running and being correct are different; edge cases (0, 100, negative, above 100) are where behaviour is proven
    "Manual and automated testing find the same bugs" Manual checks are slow and miss regressions; automated tests rerun every promise on every build
    "A test case is just calling the code" A real test case is Arrange, Act, Assert - a known input, an executed action, and an asserted result
    "Unit tests need @SpringBootTest" Pure Java classes can be created with new; starting the whole container for them is overhead, not coverage
    "A @Mock repository behaves like the real one" A mock returns only what the test configured; it never executes the query or validates mapping
    "MockMvc starts Tomcat on port 8080" MockMvc builds an HTTP-like request and runs it through Spring MVC without a real server, localhost, or Postman
    "@Mock and @MockitoBean are interchangeable" @Mock is a plain Mockito field; @MockitoBean replaces a bean inside the Spring test context that the controller needs
    "More tests always means a better suite" Tests that all start Spring and hit a database make the suite slow, so developers stop running it; the pyramid favors many fast unit tests

    16. Common Trap Questions

    Trap 1 - "This calculation returned 800 for one input, so it is tested." Verdict: False. A single happy path ignores the real risk: discount 0, 100, negative, and above 100, plus a negative price. Tests pin behaviour at the boundaries.

    Trap 2 - "Unit and integration tests are the same thing with different names." Verdict: False. The deciding question is how much real infrastructure participates. A unit test isolates one class; an integration test runs multiple real components together.

    Trap 3 - "I can test the controller by calling controller.getProduct(1L) directly." Verdict: Misleading. That checks the Java method and skips mapping matching, path-variable conversion, JSON serialization, validation, and real status handling that the HTTP contract depends on.

    Trap 4 - "@Mock is enough for a controller test." Verdict: False. @WebMvcTest builds a Spring context where the controller needs a ProductService bean. Use @MockitoBean to place the mock inside that context.

    Trap 5 - "I mocked the repository, so I proved the query works." Verdict: False. The mock returns what the test told it to return. Real query and mapping correctness require @DataJpaTest with a database.

    Trap 6 - "verify(repo).save(...) and verify(repo, never()).save(...) mean the same." Verdict: False. The first asserts the save happened; the second asserts it must not happen, which is exactly how a "duplicate must not be saved" rule is tested.

    Trap 7 - "If a test fails, the production code must be wrong." Verdict: False. A red test can mean the expectation is wrong, the production code is wrong, or the requirement changed. Reading the failure honestly is part of testing.

    17. Points to Remember

    1. Writing code and proving it behaves correctly are separate activities; testing verifies that behaviour matches requirements.
    2. Manual testing is a five-step human loop that degrades as the app grows; automated testing supplies a known input, executes the code, compares actual with expected, and reports pass or fail.
    3. A test case has three parts - initial condition, action, expected result - known as Arrange, Act, Assert (AAA).
    4. Tests verify the behaviours a method promises, not its lines; boundaries such as 0, 100, negative, and above 100 carry the real risk.
    5. The test type is decided by how much real infrastructure participates: unit (one class), slice (one layer), integration (multiple components), end-to-end (full flow), arranged as a pyramid.
    6. spring-boot-starter-test is test scoped and bundles JUnit, Mockito, AssertJ, Hamcrest, Spring Test, and JSON utilities; tests live in src/test/java mirroring the production package.
    7. @Test discovers and runs a test; @BeforeEach/@AfterEach prepare and clean per test; assertEquals, assertTrue/assertFalse, assertNull/assertNotNull, and assertThrows are the core assertions.
    8. Mockito test doubles replace dependencies: @Mock creates a controlled object that returns, throws, records, and can be verified; @InjectMocks constructs the class under test and injects available mocks (it is not Spring DI).
    9. Stubbing (when(...).thenReturn(...)) controls the dependency, assertions check the result, and verification (verify(...), verify(..., never()), matchers like any(...)) checks the interaction.
    10. Each layer gets its own environment: @WebMvcTest + MockMvc for the HTTP contract, @MockitoBean for a service bean in the web slice, and @DataJpaTest + H2 for real repository queries; use the smallest environment that can prove the behaviour.

    18. Likely Interview Questions

    Question Crisp Answer
    Why is testing necessary if the code already runs? Running is not proof; tests verify that behaviour matches requirements, including edge cases a single run never exercises.
    Manual vs automated testing? Manual: a human starts the app, calls it, and inspects. Automated: known input, execute, compare actual with expected, report pass or fail - fast and repeatable.
    What is a test case made of? Initial condition, action, and expected result - commonly Arrange, Act, Assert.
    Unit test vs integration test? Unit tests one small behaviour in isolation; integration tests multiple real components together. The deciding factor is how much real infrastructure participates.
    What is spring-boot-starter-test? A test-scoped starter bundling JUnit, Mockito, AssertJ, Hamcrest, Spring Test, and JSON testing utilities; it is not a production dependency.
    What do @Test, @BeforeEach and @AfterEach do? @Test marks a method as a test; @BeforeEach runs before every test to set state; @AfterEach runs after every test to clean resources.
    @Mock vs @InjectMocks? @Mock creates a controlled test double; @InjectMocks creates the class under test and injects available mocks into it (Mockito, not Spring DI).
    Stubbing vs verification? Stubbing controls what a dependency returns (when(...).thenReturn(...)); verification checks whether the interaction happened (verify(...)).
    Why use MockMvc instead of calling the controller method? Calling the method skips mapping matching, path-variable conversion, JSON serialization, validation, status handling, security filters, and exception handlers; MockMvc runs the real MVC machinery.
    What does @WebMvcTest load? The web slice: controller, DispatcherServlet, Jackson JSON conversion, validation, controller advice, MVC configuration, and security filters - not services, repositories, or the database.
    What does @MockitoBean do? It creates or replaces a bean in the Spring test context with a Mockito mock, so a web slice can inject a mocked service.
    Why use @DataJpaTest? A mocked repository never executes the real query; @DataJpaTest loads entities, repositories, Hibernate, DataSource, and an embedded database so mapping and queries are proven.
    What is @SpringBootTest for? Loading the complete application context when a test genuinely needs real components from several layers wired together - the heaviest option, reserved for full integration.

Test pyramid: many unit + fewer integration + very few end-to-end
    • Testing verifies behaviour against requirements; boundary inputs (0, 100, negative, above 100) matter more than the happy path.
    • Automated tests replace the slow manual loop: known input, execute, compare actual with expected, report pass or fail.
    • Arrange, Act, Assert structures every test case; @BeforeEach/@AfterEach keep each test starting from a predictable state.
    • Mockito isolates the service: @Mock builds the double, @InjectMocks wires it in, stubbing controls the return, and verify (including never()) checks the interaction.

    • @DataJpaTest + H2 proves real entity mapping and queries; @SpringBootTest is reserved for tests that truly need the whole context.
    • The principle that ties it together: use the smallest test environment that can prove the behaviour being tested.

    One-line takeaway: testing Spring Boot well means matching each behaviour to the smallest environment that can prove it - plain JUnit for logic, Mockito for service dependencies, MockMvc for the HTTP contract, and a real database only when the query itself is the behaviour.
