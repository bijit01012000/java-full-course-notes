    Part 2 · Arrays & OOP Core · Lecture 14

    Objects Deep Dive — Object Size, Call by Value vs Reference, Shallow vs Deep Copy

    17 sections · interview-oriented · both themes

    Scope evidence: lecture title "Objects Deep Dive | Size, Call by Value vs Reference | Shallow vs Deep Copy" (playlist map, verified). Repo evidence: 2 Demo files (Demo.java, Demo2.java). The cached lecture PDF is image-only and is ignored per project rules.

    Two objects can look identical in source and yet behave differently in memory once one is copied and the other is shared. This lecture opens an object up and measures it: what bytes an object really occupies, why an empty object is never free, and why Java's calling convention is always pass-by-value even for objects. It then builds the two coping strategies for an object graph — the cheap shallow copy that shares its insides, and the expensive deep copy that owns them — and finishes with the clone() contract and the aliasing bug that shallow copying is famous for. The class/object basics come from Lecture 12, constructors and this from Lecture 13, and the equals/hashCode comparison is a preview of Lecture 22.

    1. What an Object Is: Identity, State and the Reference

    An object is a heap-allocated region of memory that bundles three things:

    1. Identity — a unique existence independent of its values, represented by the reference that points at it.
    2. State — the values stored in its instance fields.
    3. Behaviour — the methods defined by its class.

    A variable of a class type does not hold an object; it holds a reference — a value that identifies a heap location. That single fact explains both halves of this lecture: object size is the size of the heap region, and pass-by-value is the copying of the reference value rather than the object. Identity is what makes copying subtle: if you copy the reference, two names now describe one identity; if you copy the object, one identity becomes two.

    Important A reference is a value in its own right. You can copy it, compare it, reassign it and pass it — all without ever touching the object it points to. Confusing the reference with the object is the root of almost every misconception in this lecture.

    2. Object Size in Memory: Header, Fields and Padding

    An object's footprint is not simply the sum of its fields. On a 64-bit HotSpot JVM it is:

    object size = header + instance fields + padding
    1. Object header (~12–16 bytes) — the mark word (8 bytes: hash, GC age, lock state) plus the class pointer (4 bytes with compressed oops, 8 without), totalling 12 or 16 bytes.
    2. Instance fields — the declared non-static fields of the class and its superclasses. A reference field costs 4 bytes with compressed oops (heap up to 32 GB), 8 bytes otherwise. boolean/byte cost 1 byte each (not 1 bit).
    3. Padding — the JVM aligns every object so its start address is a multiple of 8 bytes. The tail is padded out to that boundary.
    4. Arrays add a length field — an array has the header, a 4-byte length, then the elements, then padding.

    So an empty object is never 0 bytes — it is at least the header (12 bytes, padded to 16). A class with two int fields (class Point { int x; int y; }) stores 8 bytes of state on top of that header, then pads; the JOL tool (ClassLayout.parseInstance(obj).toPrintable()) prints the exact header, fields and padding rather than leaving it to guesswork. Note that the exact layout depends on the JVM, whether compressed oops are on, and field ordering, which the JVM may reorder for packing.

    Interviewer's perspective "How big is an Integer object?" The field is one int (4 bytes), but the object is header (12) + value (4) + padding (0) = 16 bytes. Relating the wrapper size to a primitive's 4 bytes is the whole point of the question, and it forwards to the autoboxing discussion (Lecture 18).

    3. Java Is Always Pass-by-Value: Primitives

    Java has exactly one argument-passing mechanism: pass-by-value. A method receives a copy of whatever expression the caller evaluated. For a primitive argument, the copy is the primitive value itself, so the method can change its local copy but never the caller's variable.

    // Demo.java — primitives: the value is copied
public class Demo {
    static void change(int x) {
        x = 99;                     // rebinds the local copy only
    }
    static void swap(int a, int b) {
        int t = a; a = b; b = t;    // swaps the copies; caller is untouched
    }
    public static void main(String[] args) {
        int n = 10;
        change(n);
        System.out.println(n);              // 10 — unchanged
        int a = 1, b = 2;
        swap(a, b);
        System.out.println(a + " " + b);    // 1 2 — the classic failed swap
    }
}

    The failed swap is the cleanest proof that Java does not pass by reference: if a and b were references to the caller's variables, the swap would work. It cannot, because the method only ever owned copies.

    4. Pass-by-Value for Objects: The Reference Value Is Copied

    For an object argument, the value that gets copied is the reference — the address of the object, not the object. This produces two very different behaviours inside the method's body:

    1. Mutating the object through the copied reference (box.value = 99;) writes into the one shared object, so the caller sees the change.
    2. Reassigning the parameter (box = new Box(0);) rebinds only the local copy of the reference; the caller's reference still points at the original object, so the caller sees no change.
    // Demo2.java — objects: the reference value is copied
class Box { int value; Box(int v) { value = v; } }

public class Demo2 {
    static void mutate(Box box) {
        box.value = 99;             // follows the copied reference: caller sees it
    }
    static void reassign(Box box) {
        box = new Box(0);           // rebinds the local copy only
    }
    public static void main(String[] args) {
        Box b = new Box(10);
        mutate(b);
        System.out.println(b.value);    // 99 — mutation is visible
        reassign(b);
        System.out.println(b.value);    // 99 — caller's reference unchanged
    }
}

    The correct phrasing is therefore "Java passes the reference by value", or more simply "Java is always pass-by-value; for objects the copied value is a reference". "Java passes objects by reference" is wrong, because the parameter is still a copy — it just happens to be a copy of an address.

    Important Mutate through the parameter and the caller sees it; reassign the parameter and the caller does not. Holding both rules at once is the mark of someone who truly understands Java's calling convention.

    5. Pass-by-Value Illustrated

    Argument kind What is copied Mutation inside the method Reassignment inside the method
    Primitive (int, double) The primitive value Local copy only — caller unchanged Local copy only — caller unchanged
    Object reference The reference value (address) Visible to the caller — same object is written Caller's reference unchanged
    Array reference The reference value (address) arr[i] = x is visible; element writes persist arr = new int[5] is local — caller's array unchanged
    String reference The reference value (address) No mutation possible — String is immutable (Lecture 25) Caller's reference unchanged
    final parameter The value, as always Object contents may still be mutated Reassignment is a compile error

    Reading the table: the left column never changes — the value is always copied. What varies is whether that copied value is a primitive or an address, and therefore whether an operation through it can reach the caller's state.

    6. The Swap That Never Works and the == vs equals Preview

    The failed swap of Section 3 generalizes: no method can reassign a caller's variable in Java. The usual workarounds are to return a new value, swap array elements (arr[0]/arr[1] are reached through the copied array reference), or use a holder object whose fields the method sets.

    Copying also raises the question of comparing the two references. Two references are equal with == only when they point at the same object (same identity), while equals asks whether two objects are logically equivalent. So for Box a = new Box(10); Box b = new Box(10);, a == b is false (two distinct objects) and a.equals(b) is also false by default, because the inherited Object.equals is identity comparison (==) until it is overridden. This lecture only needs the distinction so that shallow/deep copies can be reasoned about; the full contract — equals, hashCode and toString — is Lecture 22.

    Interviewer's perspective "Can a Java method swap two objects?" Not by reassigning its parameters. You can swap the contents through a shared array or holder, and you can return both, but the parameters themselves are copies. The answer tests Sections 3 and 4 in one breath.

    7. Shallow Copy: One New Object, Shared Insides

    A shallow copy creates a new object whose primitive fields are copied by value, but whose reference fields copy only the address — so the new object points at the same nested objects as the original. There is one new shell around the same contents.

    The default mechanics are:

    1. Object.clone() — the shallow case is its default behaviour.
    2. A copy constructor that copies each field with a plain assignment (this.field = other.field;).

    The danger is aliasing: because both copies share the nested object, mutating it through one copy silently changes the other.

    // Demo2.java — shallow copy shares the nested Address
class Address { String city; Address(String c) { city = c; } }

class Person implements Cloneable {
    String name; Address address;
    Person(String n, String c) { name = n; address = new Address(c); }
    @Override public Person clone() throws CloneNotSupportedException {
        return (Person) super.clone();   // shallow: address is shared, not copied
    }
}

public class Demo2 {
    public static void main(String[] args) throws CloneNotSupportedException {
        Person p1 = new Person("Asha", "Pune");
        Person p2 = p1.clone();
        p2.address.city = "Delhi";             // writes through the shared Address
        System.out.println(p1.address.city);   // Delhi — aliasing bug
    }
}

    Here p1 was never touched directly, yet its address changed. That single line is the entire case against careless shallow copying.

    8. Deep Copy: Independent Object Graphs

    A deep copy creates a new object and then recursively copies every nested object, so the two copies share no mutable state at all. Mutating one copy can never be observed through the other. Three implementation routes exist:

    1. Copy-constructor chain — each class takes an instance of itself and constructs fresh copies of its reference fields: this.address = new Address(other.address);.
    2. Manual clone chain — override clone in every class of the graph and clone each reference field after super.clone().
    3. Serialization round-trip — serialize the object and deserialize it; the result is a structurally independent graph, at the cost of performance and the Serializable requirement.
    // Demo2.java — deep copy via a copy-constructor chain
class Address {
    String city;
    Address(String c) { city = c; }
    Address(Address other) { this.city = other.city; }        // copy constructor
}

class Person {
    String name; Address address;
    Person(Person other) {                                    // deep copy
        this.name = other.name;
        this.address = new Address(other.address);            // nested object copied
    }
}

    The trade-off is direct: deep copying is safe but expensive (the whole reachable graph is allocated), while shallow copying is cheap but vulnerable to aliasing. Choose deep when the copies must evolve independently, and shallow when nested state is immutable or intentionally shared.

    Important A shallow copy of a String field is safe because String is immutable (Lecture 25) — nothing can write through the shared reference. The rule is not "always copy deeply"; it is "copy deeply any nested object that is mutable and shared".

    9. Shallow vs Deep Copy

    Aspect Shallow copy Deep copy
    What is copied Primitive field values; reference field addresses Field values; nested objects recreated recursively
    Nested object shared Yes — both copies point at the same nested object No — each copy owns its own nested objects
    Mutating a nested field Visible in the other copy (aliasing) Isolated to the copy that was mutated
    Cost Cheap — a single object allocated Expensive — the reachable object graph is allocated
    Default behaviour Object.clone() and naive field-copy constructors Must be implemented explicitly
    Safety Low — hidden shared state High — genuine independence
    Typical tools super.clone(); field-by-field assignment Copy-constructor chain; clone chain; serialization round-trip
    Best used when Nested state is immutable or sharing is intended Copies must diverge and nested state is mutable

    The table's second row is the one to memorize: shallow shares, deep duplicates. Everything else — cost, safety, tools — follows from that single difference.

    10. The clone() Contract and Why It Is Awkward

    Object.clone() is Java's built-in copying hook, and its contract is a list of interview favourites:

    1. Cloneable is a marker interface — it declares no methods. Implementing it merely tells Object.clone() that cloning this class is legal.
    2. clone is protected and native — outside the class (or its package) you cannot call super.clone; a public override is needed to expose it.
    3. It throws CloneNotSupportedException — a checked exception, thrown if the class does not implement Cloneable.
    4. It returns Object — callers must cast, which is unsafe at compile time.
    5. It is shallow by default — reference fields are shared, which becomes the aliasing bug of Section 7 unless every class in the graph overrides clone.

    The awkwardness is visible in one line: on a class that does not implement Cloneable, n.clone() fails to compile because the inherited method is protected; casting to Object makes it compile, but the call then throws CloneNotSupportedException at runtime. Cloneable plus a checked exception plus a protected method plus a cast plus shallow-by-default is a lot of ceremony for one operation. That combination is why most code prefers copy constructors or static copy factories, and why "why is clone() considered broken?" is a perennial interview question.

    Interviewer's perspective "Why is Cloneable a marker interface?" Because Object.clone() checks for it at runtime via instanceof. It carries no methods, so it is a capability flag, not a contract of behaviour — the same pattern as Serializable.

    11. Copy Constructor vs clone() vs Static Copy Factory

    Approach Signature Depth by default Notes
    Copy constructor Person(Person other) Whatever you code (commonly deep) Explicit, no checked exception, no cast; cannot force subclasses, but can be overridden
    clone() Object clone() Shallow Needs Cloneable, protected override, cast, checked exception
    Static copy factory Person.copyOf(other) Whatever you code Clear intent, can return a subtype; no language ceremony
    new ArrayList<>(list) Constructor Shallow — element references copied Standard for collections
    Arrays.copyOf(arr, n) Static method Shallow — for object arrays the references are copied New array, same element objects
    List.copyOf(list) Static method Shallow, and immutable — rejects nulls A defensive immutable snapshot, not a deep copy

    The important reading: the collection factories are shallow. List.copyOf(list) protects the list structure (it cannot be modified) but not the elements — if the elements are mutable, the copy still exposes them.

    12. Pitfalls and Best Practices

    Pitfall What goes wrong Fix
    Saying "objects are passed by reference" The argument is a copied reference; reassignment is invisible to the caller Say "the reference is passed by value"
    Mutating a shared list through a shallow copy The original list's elements change too Deep-copy the elements or use an immutable element type
    Assuming clone() is deep Nested references are shared Override clone per class or use a deep strategy
    Using List.copyOf on mutable elements You get an unmodifiable view of the same elements Copy each element, or make elements immutable
    Changing fields of a copied equals key hashCode no longer matches; map lookups fail (Lecture 22) Make keys immutable, or stop mutating after insertion
    Measuring object size by adding fields The header and padding dominate small objects Use JOL; remember the 8-byte alignment

    The unifying lesson: a copy is only as independent as its least-independent nested object. Audit the graph, not just the top-level fields.

    13. Myth vs Reality

    Myth Reality
    "Java passes objects by reference" Java is always pass-by-value; for objects the value passed is the reference, and the parameter is still a copy.
    "An empty object takes 0 bytes" The header alone is roughly 12–16 bytes before any field, and the object is padded to an 8-byte boundary.
    "clone() gives a deep copy" Object.clone() is shallow; nested reference fields are shared unless every class overrides clone.
    "Reassigning a parameter changes the caller's variable" Parameters are copies; reassigning one is local and invisible to the caller — the swap method proves it.
    "A shallow copy of a String field is dangerous" String is immutable, so sharing it in a shallow copy is safe; only mutable nested objects cause aliasing.

    14. Common Trap Questions

    Trap 1 — "Objects are passed by reference, right?" No. Java is always pass-by-value. For an object argument, the copied value is the reference, so mutating the object is visible to the caller, but reassigning the parameter is not. The correct phrase is "the reference is passed by value".

    Trap 2 — "Write a swap(Object a, Object b) method." It cannot work by reassigning the parameters, because each parameter is a copy of the caller's reference. Swap the referenced contents instead (for example via a shared array or holder object), or return the two values.

    Trap 3 — "I shallow-copied a Person and edited the copy's Address; why did the original change?" The copy's address field holds the same reference as the original, so both point at one Address. The edit went through that shared object. Deep-copy the Address to isolate them.

    Trap 4 — "new NoClone().clone() — does it compile and run?" It does not compile, because clone() is protected in Object. Casting to Object makes it compile but then throws CloneNotSupportedException unless the class implements Cloneable.

    Trap 5 — "How big is new Object()?" Not zero. It carries the mark word plus the class pointer (about 12 bytes on a 64-bit JVM with compressed oops) and is padded to an 8-byte multiple — typically 16 bytes. Exact numbers require JOL.

    Trap 6 — "Is List.copyOf(list) a deep copy?" No. It produces an immutable list that shares the same element objects — a shallow, structural copy. If the elements are mutable, both lists still expose the same mutable state.

    15. Points to Remember

    1. A class-type variable holds a reference, not the object; copying the reference copies an address, copying the object creates a new identity.
    2. Object size = header (~12–16 bytes) + instance fields + padding to an 8-byte boundary; use JOL to measure it.
    3. An empty object is never 0 bytes; arrays add a 4-byte length after the header.
    4. Reference fields cost 4 bytes with compressed oops (heap up to 32 GB), 8 bytes otherwise; boolean/byte cost 1 byte, not 1 bit.
    5. Java is always pass-by-value; for primitives the value is copied, for objects the reference value is copied.
    6. Mutating an object through a parameter is visible to the caller; reassigning the parameter is not — so the classic swap fails.
    7. == compares identity (same object); equals compares logical equality when overridden — full contract in Lecture 22.
    8. A shallow copy creates a new object but shares nested reference fields; Object.clone() and naive copy constructors are shallow.
    9. A deep copy recursively duplicates the object graph; use a copy-constructor chain, a manual clone chain, or serialization.
    10. Shallow is cheap and alias-prone; deep is safe and expensive — copy deeply any nested object that is mutable and shared.
    11. Cloneable is a marker interface, clone is protected and throws CloneNotSupportedException, returns Object, and is shallow — hence copy constructors are usually preferred.
    12. Copying an object that is a key in a hash-based collection and then mutating its fields breaks lookups — keep map keys immutable (Lecture 22).

    16. Likely Interview Questions

    Question Crisp Answer
    Is Java pass-by-value or pass-by-reference? Always pass-by-value. Primitives copy the value; objects copy the reference value.
    Then why can a method modify the caller's object? Because the copied reference points at the same object; writing through it mutates the shared object.
    Why does swap(a, b) not work? The parameters are copies of the caller's values/references; reassigning them only rebinds locals.
    How big is an object in Java? Header (mark word + class pointer, ~12–16 bytes) + fields + padding to an 8-byte boundary; arrays add a length.
    How big is new Object()? The header plus padding — about 16 bytes on a 64-bit HotSpot JVM; never 0.
    How big is a reference? 4 bytes with compressed oops (heap up to ~32 GB), otherwise 8 bytes.
    What tool measures object layout? JOL (Java Object Layout), which prints the header, fields and padding.
    What is a shallow copy? A new object whose primitive fields are copied and whose reference fields are shared with the original.
    What is a deep copy? A new object with the entire nested object graph recursively duplicated, so no mutable state is shared.
    How do you make a deep copy? Copy-constructor chain, manual clone chain, or a serialization/deserialization round-trip.
    Why is clone() considered awkward? It needs the Cloneable marker, is protected, throws a checked exception, returns Object, and is shallow by default.
    Is copying an object with a String field unsafe? No — String is immutable, so sharing it is safe; only mutable shared state causes aliasing (Lecture 25).

    17. Final Summary

    object on heap  =  header (mark word + class pointer)  +  fields  +  padding (to 8 bytes)
argument passing:  caller value --copy--> parameter   (primitives: value; objects: reference)
                        mutate through reference -> caller sees it     reassign parameter -> caller does not

shallow copy  ->  new shell, shared nested objects   (cheap, aliasing risk)
deep copy     ->  new shell, duplicated graph         (expensive, safe)
    • Object → identity + state + behaviour; a reference identifies it on the heap.
    • Size → header (~12–16 bytes) + fields + padding; empty objects cost 16 bytes, arrays add a length field; JOL measures it.
    • Pass-by-value → primitives copy the value, objects copy the reference; mutation through the reference is visible, reassignment is not.
    • Swap → impossible by parameter reassignment; swap contents through a shared holder instead.
    • Shallow copy → clone() default and naive constructors; nested references are shared (aliasing).
    • Deep copy → copy-constructor chain, manual clone chain, or serialization round-trip; safe but costly.
    • clone() → marker Cloneable, protected, checked CloneNotSupportedException, Object return, shallow default — prefer copy constructors.
    • Copy factories → Arrays.copyOf and List.copyOf are shallow; List.copyOf is additionally immutable.

    Golden rule Java copies values, never variables — and a copy is only as independent as its least-copied nested object.

    One-line takeaway: an object is a header plus fields plus padding reached through a copied reference, so passing mutates but reassigning does not, and shallow copies share their insides while deep copies own them.
