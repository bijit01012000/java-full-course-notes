    Java Enums — Why Not Use int/String for Constants?

    18 sections · interview-oriented · both themes

    Scope evidence: "Java Enums | Why Not Use int/String for Constants?" (playlist map, verified). Repo evidence: 5 Demo files.

    An enum declares a variable whose value must come from a fixed, named set, and the lecture title asks the right question: why not simply use int or String constants? This lecture defines what an enum is, what the compiler generates behind it, the built-in methods every enum inherits, and exactly why int and String constants fail as soon as the allowed set matters. It then covers enums with fields, constructors, methods and constant-specific bodies, their use in switch and for-each, the enum singleton, the ordinal() trap, and the specialized EnumSet/EnumMap collections. Constants built from static final fields are Lecture 15 material, and the equals/hashCode/toString behaviour every enum inherits is Lecture 22.

    1. What Is an Enum

    An enum is a special data type that enables a variable to hold one value out of a predefined, fixed list of constants. It is declared with the enum keyword, and the constants are written as a comma-separated list:

    // Demo.java — declaring and consuming an enum
public class Demo {
    enum Day { MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY }

    public static void main(String[] args) {
        Day d = Day.WEDNESDAY;
        System.out.println(d);              // WEDNESDAY (toString)
        System.out.println(d.name());       // WEDNESDAY
        System.out.println(d.ordinal());    // 2

        for (Day x : Day.values()) System.out.print(x + " ");   // all seven

        Day f = Day.valueOf("FRIDAY");      // parse a constant by name
        System.out.println(f.compareTo(d)); // 3 (5 - 2, by ordinal)
    }
}

    Three facts about the type itself: an enum implicitly extends java.lang.Enum, it is implicitly final (no enum can be extended), and each constant is a public static final instance of the enum type.

    Memory aid — an enum is a class wearing a badge: the seven Day constants are seven pre-built, immutable objects of a class you never had to instantiate by hand.

    2. What the Compiler Generates

    When the compiler sees enum Day { ... }, it produces a class equivalent to the following shape:

    1. The class extends java.lang.Enum — so Enum's methods are inherited automatically.
    2. The class is final — you cannot subclass an enum.
    3. Each constant is a public static final Day field initialised with a private constructor.
    4. A synthetic values() method returning a fresh Day[] each call.
    5. A synthetic valueOf(String) method that looks up a constant by name.
    6. A private constructor (never callable from outside).

    Because the class already extends Enum, an enum cannot extend another class — Java allows only single inheritance (Lecture 16). This is the single most common compile-time surprise: an enum may implement interfaces, but it can never be a subclass.

    3. Built-in Methods Every Enum Inherits

    Method Returns Notes
    values() Day[] A fresh array on every call; the canonical iteration source
    valueOf(String) Day Parses by exact name; throws IllegalArgumentException on an unknown name
    name() String The declared identifier; final and not overridable
    ordinal() int Zero-based declaration position
    compareTo(E) int Ordering by ordinal(); negative, zero or positive
    equals / hashCode boolean / int Inherited from the identity semantics of Enum; suitable for collections
    toString() String Defaults to name() but is overridable

    Important name() and ordinal() are final; toString() is not. Overriding toString() changes display text only — name() and valueOf continue to use the declared identifier.

    4. Why Not Use int Constants

    The classic pre-enum idiom was a row of static final int fields. It compiles, but it offers no protection at all:

    // Demo2.java — int constants fail; an enum fixes the same job
public class Demo2 {
    static final int RED = 1, GREEN = 2;   // no type safety

    enum Color { RED, GREEN }              // a type-safe set

    static void paintInt(int c) { System.out.println("paint " + c); }
    static void paint(Color c)  { System.out.println("paint " + c); }

    public static void main(String[] args) {
        paintInt(RED);          // OK
        paintInt(999);          // compiles: an invalid value sails through
        paintInt(RED + GREEN);  // compiles: meaningless arithmetic
        paint(Color.RED);       // OK
        // paint(999);          // compile error: not a Color
    }
}

    The failure modes are structural, not accidental:

    1. No type safety — paintInt accepts any int; the compiler cannot know 999 is illegal.
    2. No compile-time checking — the validity of a value is a runtime hope, not a compiler guarantee.
    3. No namespacing — RED floats in the enclosing scope; another RED collides.
    4. No iteration — you cannot list all legal colours; you must maintain a parallel array by hand.
    5. No printing — you get 1, not RED; a debugging log loses meaning.
    6. No fixed set — RED + GREEN and 999 are as valid as RED to the compiler.

    The enum version fixes every point: paint(999) does not compile, Color.values() iterates the set, and Color.RED prints its own name.

    5. Why Not Use String Constants

    public static final String constants are worse in one specific way: a typo compiles.

    static final String OPEN = "OPEN";
static final String CLOSED = "CLOSED";
// caller writes "OPNE" — no compile error, silently a new value
    1. Typos compile — "OPNE" is a perfectly valid String; the mistaken constant is caught only when a comparison fails at runtime.
    2. No fixed set — any string is acceptable, so the set is whatever the developer remembers.
    3. Equality traps — strings must be compared with equals, and == silently compares references (Lecture 25).
    4. No iteration and no namespace — the same as the int case, plus string interning confusion.
    5. Printing is ambiguous — "OPEN" might be a status, a state, or a message.

    An enum turns all of these into compile-time errors: the set is closed, the names are checked, and == compares identity safely.

    6. enum vs int/String vs static final Class Constants

    Aspect enum public static final int / String
    Type safety Yes — a distinct type No — any int/String is accepted
    Compile-time validity Invalid values do not compile Invalid values compile freely
    Namespacing Constants live under the enum name Names leak into the enclosing scope
    Iteration values() lists the whole set Manual parallel array needed
    Printing Prints the constant name by default Prints the bare value
    Fixed set Closed and enforced Open — new values appear silently
    Equality == is safe and null-safe == on String compares references
    Behaviour Can carry fields and methods Plain values only

    The second comparison is against a class that only groups constants:

    Aspect enum Class of static final constants
    Instances Exactly the declared constants Unbounded — anyone can new it
    Constructor Implicitly private Must be made private by hand
    Extensibility final by construction Extendable unless marked final
    Iteration Built-in values() None
    Switch support Yes, natively No
    Singleton guarantee Free, one instance per constant Must be enforced manually
    Serialization Safe by the JVM Depends on the class
    Methods/fields Supported per constant Supported, but no per-instance meaning

    Reading the two tables together: an enum is not "constants with nicer syntax" — it is a type whose entire value space the compiler knows.

    7. Enums with Fields, Constructors and Methods

    An enum may declare fields, a constructor and methods. The constructor is implicitly private, so constants are the only instances that ever exist:

    // Demo3.java — fields, a private constructor, methods and constant bodies
interface Describable { String describe(); }

public class Demo3 {
    enum Planet implements Describable {
        MERCURY(3.30e23), EARTH(5.97e24);

        private final double mass;
        Planet(double mass) { this.mass = mass; }   // constructor is private

        public double mass() { return mass; }
        public String describe() { return name() + " mass " + mass; }
    }

    enum Op {
        ADD { int apply(int a, int b) { return a + b; } },
        MUL { int apply(int a, int b) { return a * b; } };
        abstract int apply(int a, int b);
    }

    public static void main(String[] args) {
        System.out.println(Planet.EARTH.describe());  // EARTH mass 5.97E24
        System.out.println(Op.ADD.apply(2, 3));       // 5
        System.out.println(Op.MUL.apply(2, 3));       // 6
    }
}

    Key rules:

    1. Constructor is implicitly private — an explicit public Planet(...) is a compile error; you can never write new Planet(...).
    2. Arguments follow the constant, as in MERCURY(3.30e23); the constructor body runs once per constant, at class initialisation.
    3. Fields should be final — an enum is a constant, so its state should be immutable once built.
    4. Enums may implement interfaces (here Describable) — the one extension mechanism open to them.
    5. Enums cannot extend a class — the slot is already taken by java.lang.Enum.

    8. Constant-Specific Class Bodies

    In Op above, ADD and MUL each provide their own implementation of the abstract apply method. This is a constant-specific class body: the compiler turns each constant into a tiny anonymous subclass of the enum type. It is the idiomatic way to attach per-constant behaviour without a chain of if or switch statements.

    The rule to remember: if an enum declares an abstract method, every constant must supply a body for it. The enum type itself stays final, but its constants may have anonymous subtypes — this is the only place an enum-like type is subclassed, and it is done by the compiler.

    9. Enums in switch and for-each

    Enums are the natural partner of switch (Lecture 7): the cases are written unqualified, and the compiler can check that every legal value is handled.

    // Demo4.java — switch on an enum, for-each over values(), identity check
public class Demo4 {
    enum Status { OPEN, CLOSED, PENDING }

    public static void main(String[] args) {
        Status s = Status.PENDING;

        switch (s) {                        // cases are unqualified
            case OPEN:    System.out.println("open");    break;
            case PENDING: System.out.println("pending"); break;
            case CLOSED:  System.out.println("closed");  break;
        }

        for (Status x : Status.values()) System.out.print(x.ordinal() + ":" + x + " ");

        System.out.println(Status.valueOf("OPEN") == Status.OPEN);  // true
    }
}
    1. Unqualified case labels — write case OPEN, not case Status.OPEN.
    2. Exhaustiveness — the compiler knows the set, so a switch over an enum is checkable and self-documenting.
    3. for-each over values() — the standard way to walk every constant.
    4. Identity comparison — because there is exactly one instance per constant, == and equals give the same answer.

    Important A switch on a null enum reference throws NullPointerException at runtime — switch calls ordinal() on the selector. Guard for null when the value comes from outside.

    10. The Enum Singleton

    A single-constant enum is the simplest correct singleton in Java (Effective Java, Item 3):

    // Demo5.java — the enum singleton (Effective Java)
public class Demo5 {
    enum Registry {
        INSTANCE;
        private int count;
        void add()   { count++; }
        int  count() { return count; }
    }

    public static void main(String[] args) {
        Registry.INSTANCE.add();
        Registry.INSTANCE.add();
        System.out.println(Registry.INSTANCE.count());  // 2
    }
}

    Why it is the best default:

    1. Thread-safe — the JVM initialises enum constants once, under class-initialisation locking.
    2. Serialization-safe — the JVM guarantees deserialization returns the same instance, without a custom readResolve.
    3. Reflection-proof — the constructor is not reflectively callable, so a second instance cannot be created.
    4. Concise — one line of constant declaration replaces a private constructor, a static field and a null check.

    11. ordinal() vs name() — Do Not Persist Ordinals

    d.ordinal()  // 2 — fragile position in the declaration order
d.name()     // "WEDNESDAY" — stable declared identifier
    Aspect ordinal() name()
    Returns int position, zero-based String declared identifier
    Stability Changes if constants are reordered or inserted Stable unless the constant is renamed
    Safe to persist No — reordering silently corrupts stored data Yes — a name survives reordering
    Human-readable No — a bare number Yes
    Reverse lookup No direct parse from an ordinal valueOf(name)
    Cost A field read A String
    Recommended use In-memory ordering, array indexing Persistence, wire formats, logs

    Interviewer's perspective "You stored status.ordinal() in a database and later inserted a new constant in the middle. What happens?" Every previously stored row now maps to a different constant, because ordinals are positions, not identities. The correct fix is to persist name() or an explicit stable code field (OPEN(1)), never the ordinal.

    12. Related: EnumSet, EnumMap and Inherited Contracts

    1. EnumSet / EnumMap (Lecture 34) — specialized collections for enum keys; EnumSet is a compact bitset and EnumMap is an array, both faster than the general HashSet/HashMap.
    2. Comparable — every enum is automatically comparable, using ordinal() order; no compareTo needed.
    3. Serializable — every enum is serializable by the JVM, with identity preserved across serialization.
    4. values() returns a copy — mutating the returned array does not affect the enum's constants.

    These are inherited from java.lang.Enum, not declared by the author, which is why every enum gets them for free.

    13. Pitfalls and Common Errors

    Pitfall What happens Fix
    == vs equals Both are correct for enums; == is additionally null-safe Prefer == for identity
    Mutating enum fields The constant is shared globally, so state leaks Keep enums immutable (final fields)
    Mutating values() result The array is a fresh copy each call; no effect on the enum Assign and mutate freely — the constants are safe
    Persisting ordinal() Reordering constants corrupts stored data Persist name() or a stable code field
    Calling the constructor explicitly new Color(...) is a compile error Constants are the only instances
    switch on a null enum NullPointerException from ordinal() Guard for null first
    valueOf("UNKNOWN") IllegalArgumentException at runtime Validate the name, or catch the exception
    Reordering for compareTo Comparisons follow declaration order, not meaning Order constants deliberately

    14. Myth vs Reality

    Myth Reality
    "An enum is just a bunch of static final fields" It is a real type that extends java.lang.Enum, is final, and has exactly one instance per constant.
    "I can extend an enum like any class" No — an enum already extends Enum, and Java has single inheritance; it may only implement interfaces.
    "values() returns a reference I can edit to change the constants" It returns a fresh copy on every call; mutations never reach the enum.
    "ordinal() is a safe identifier to store in a database" It is a position, not an identity; inserting a constant silently remaps stored data.
    "Enums can only be names, no data or behaviour" Enums may hold final fields, private constructors, methods, and constant-specific class bodies.

    15. Common Trap Questions

    Trap 1 — Extending an enum: "Can class Foo extends Status compile?" No. Status is implicitly final, and it already extends java.lang.Enum. Enums implement interfaces; they cannot be subclassed.

    Trap 2 — Comparing enums: "Is status == Status.OPEN wrong, and must I use equals?" == is correct and preferred — one instance per constant guarantees identity. It is also null-safe; equals on a null reference would throw.

    Trap 3 — Persisting ordinals: "I store ordinal(). Is that fine if I never rename constants?" Reordering or inserting a constant is enough to corrupt the data, because ordinals are positions. Store name() or an explicit code field instead.

    Trap 4 — values() mutability: "I sorted Day.values() and printed Day.values() again — why is nothing sorted?" Each call returns a new array. Your sort changed a local copy; the enum's constants are unaffected.

    Trap 5 — switch on a null: "What does switch (s) do when s is null?" NullPointerException — the compiler expands the switch using s.ordinal(). Guard the selector.

    Trap 6 — Constructor visibility: "Can I make the enum constructor public to create more constants?" No — the constructor is implicitly private; an explicit public access modifier is a compile error, so the set stays closed.

    16. Points to Remember

    1. An enum is a special type holding a fixed set of constants; each constant is a public static final instance.
    2. Every enum implicitly extends java.lang.Enum and is implicitly final.
    3. Built-in methods: values(), valueOf(String), name(), ordinal(), compareTo, plus inherited equals/hashCode/toString.
    4. values() returns a fresh array on each call; mutating it does not touch the constants.
    5. name() and ordinal() are final; toString() may be overridden for display.
    6. int/String constants offer no type safety, no compile-time validity, no namespacing, no iteration and no fixed set.
    7. Enums may declare fields, a private constructor, methods, constant-specific class bodies, and implement interfaces.
    8. Enums cannot extend a class because they already extend Enum.
    9. Use enums natively in switch and iterate with for-each over values().
    10. A single-constant enum is the simplest thread-safe, serialization-safe, reflection-proof singleton.
    11. Never persist ordinal(); prefer name() or an explicit stable code field.
    12. EnumSet/EnumMap (Lecture 34) are the specialized collections; every enum is Comparable and Serializable.

    17. Likely Interview Questions

    Question Crisp Answer
    What is an enum in Java? A special type representing a fixed set of constants, where each constant is a public static final instance of an implicitly final class extending java.lang.Enum.
    Why prefer an enum over int constants? Type safety, compile-time validity, namespacing, iteration and printing; the compiler rejects values outside the set.
    Why not use String constants? Typos compile silently, the set is not closed, == compares references, and there is no iteration or namespace.
    Which class does an enum extend? java.lang.Enum — so an enum cannot extend any other class.
    What does values() return, and is it cached? A Day[] of all constants; a fresh copy on every call.
    name() vs toString()? name() is final and returns the declared identifier; toString() defaults to it but can be overridden.
    valueOf on an unknown name? Throws IllegalArgumentException at runtime.
    Is == or equals correct for enums? Both work because there is one instance per constant; == is preferred and null-safe.
    Can an enum have a constructor? Yes, implicitly private; it runs once per constant and cannot be invoked from outside.
    Can an enum have methods and fields? Yes, including constant-specific class bodies that implement an abstract method per constant.
    Can an enum implement an interface? Yes — it may implement any number of interfaces; it just cannot extend a class.
    Why is an enum singleton preferred? The JVM guarantees one instance, safe against threads, serialization and reflection, with no boilerplate.
    Why should you not persist ordinal()? Ordinals are positions; reordering or inserting a constant remaps stored values. Persist name() or a code field.

    18. Final Summary

    int/String constants  ->  no type safety, no fixed set, typos compile
                       ->  enum: compiler-checked, iterable, namespaced type
enum Day { ... }       =  class extends Enum, final, one instance per constant
                       ->  values() / valueOf() / name() / ordinal() / compareTo
                       ->  fields + private ctor + methods + constant bodies
                       ->  switch, for-each, EnumSet/EnumMap, enum singleton
    • Enum → a closed, type-safe set of named constants; each constant is one immutable instance.
    • int/String constants → no compile-time protection, no iteration, no namespace; String typos compile.
    • Built-ins → values() (fresh array), valueOf, name, ordinal, compareTo; toString overridable.
    • Extras → fields, private constructors, methods, constant-specific bodies, interfaces.
    • Singleton → one-constant enum is thread-, serialization- and reflection-safe.
    • Caution → never persist ordinal(); prefer name() or a stable code field.
    • Related → EnumSet/EnumMap (Lecture 34); every enum is Comparable and Serializable.

    Golden rule An enum is a type, not a list of labels: if the compiler can know the valid set, no int or String should be asked to pretend it can.

    One-line takeaway: use an enum whenever a value must come from a fixed set — it gives type safety and iteration for free, while int and String constants only postpone the mistake until runtime.
