    Part 3 · OOP Deep Dive · Lecture 17

    Abstraction & Polymorphism in Depth | Abstract Class vs Interfaces

    17 sections · interview-oriented · both themes

    Scope evidence: "Abstraction & Polymorphism in Depth | Abstract Class vs Interfaces" (playlist map, verified). Repo evidence: 3 Demo files.

    Abstraction and polymorphism are the third and fourth pillars of object-oriented programming, and they answer two more questions: how do we expose intent while hiding implementation, and how can one reference type express many behaviours? This lecture covers abstract classes and abstract methods, interfaces as pure contracts, the two kinds of polymorphism (compile-time overloading and runtime overriding through dynamic dispatch), and the traps that decide interview outcomes. Along the way it settles the abstract-class-versus-interface question that every Java interview asks, and shows why fields and static methods do not participate in runtime polymorphism.

    1. Abstraction: Expose the What, Hide the How

    Abstraction is the design act of exposing only the essential behaviour of a type and hiding the machinery that produces it. A caller should know what a method promises and should not depend on how it is implemented. The interface of an object is its contract; the implementation is its private business.

    Recall from Lecture 16 that encapsulation hides data behind accessors. Abstraction is the sibling idea at the behaviour level: encapsulation protects state, abstraction simplifies behaviour. Java gives two tools for abstraction, and the whole lecture turns on choosing between them:

    1. Abstract classes - a partly built type that can hold state and shared code.
    2. Interfaces - a pure contract that promises behaviour without any state.

    Memory aid: an abstract class is a half-built house you finish; an interface is a building code that any house must satisfy.

    2. Abstract Classes

    An abstract class is declared with the abstract keyword. It cannot be instantiated with new, but it can do everything a normal class does: it may declare fields, constructors, static members, final methods, and concrete methods that subclasses inherit and reuse.

    // Shape.java - abstract class: shared state and shared behaviour
abstract class Shape {
    protected String name;              // state is allowed
    Shape(String name) { this.name = name; }   // constructors are allowed
    abstract double area();             // abstract method - no body
    void describe() {                    // concrete method - shared code
        System.out.println(name + " area=" + area());
    }
}

    Three facts that make abstract classes useful, and examinable:

    1. They cannot be instantiated. new Shape("x") is a compile error; the class is incomplete by design.
    2. They can mix abstract and concrete methods. Shared behaviour lives once in the base; varying behaviour is deferred to subclasses.
    3. They can hold state and constructors. A subclass chains to the abstract parent with super(...), so shared fields are initialised once (Lecture 13).

    Important An abstract class may declare zero abstract methods and still be abstract. The keyword prevents instantiation and marks the type as incomplete; it does not require any abstract method to exist.

    3. Abstract Methods

    An abstract method declares a signature and a semicolon, and has no body:

    abstract double area();   // no braces, no implementation

    The rules are tight and follow from its purpose:

    1. It can appear only inside an abstract class or an interface.
    2. It cannot be private, static, or final - each of those would block the overriding that an abstract method demands.
    3. A concrete subclass must implement every inherited abstract method, or it fails to compile.
    4. If a subclass does not implement all of them, that subclass must itself be declared abstract.

    The abstract method is the enforcement mechanism of abstraction: the base type dictates what must exist, and each subclass supplies how.

    4. Runtime Polymorphism with an Abstract Shape

    The abstract Shape becomes powerful the moment several subclasses implement area() and a parent-typed array holds them all.

    class Circle extends Shape {
    private final double r;
    Circle(double r) { super("Circle"); this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

class Rectangle extends Shape {
    private final double w, h;
    Rectangle(double w, double h) { super("Rectangle"); this.w = w; this.h = h; }
    @Override double area() { return w * h; }
}

public class Demo {
    public static void main(String[] args) {
        Shape[] shapes = { new Circle(2), new Rectangle(3, 4) };
        for (Shape s : shapes) {
            s.describe();               // one call site, many behaviours
        }
    }
}

    The loop body never mentions Circle or Rectangle. It asks each Shape to describe() itself, and the JVM runs the area() of the object's real type. This is polymorphism in one picture: the same call, different behaviour.

    5. Interfaces: The Pure Contract

    An interface is a reference type that declares a contract with no state and no constructors. A class promises to honour it with the implements keyword. An interface can be implemented by many unrelated classes, and a class may implement several interfaces at once.

    The implicit modifiers are a favourite interview point:

    1. Every method declared without a body is implicitly public abstract.
    2. Every field is implicitly public static final - that is, a constant.
    3. An interface cannot be instantiated: new Drawable() is a compile error.
    4. It has no constructors and no instance fields, because it holds no per-object state.
    5. An interface can extends several other interfaces, giving multiple type inheritance.
    // Drawable.java - a pure capability contract
interface Drawable {
    int BORDER = 1;                 // public static final constant
    void draw();                    // public abstract, implicitly
}

interface Fillable { void fill(); }

class Circle implements Drawable {
    public void draw() { System.out.println("draw circle"); }
}

class Square implements Drawable, Fillable {   // two contracts at once
    public void draw() { System.out.println("draw square"); }
    public void fill() { System.out.println("fill square"); }
}

    Important The implicit public on interface methods is why implementers must write public void draw(). Copying the declaration without public narrows the access and causes a compile error. Since Java 8 the language adds default and static methods, and Java 9 adds private ones - the full treatment belongs to Lecture 24.

    6. Abstract Class vs Interface

    This is the comparison the title is named after, and the one interviewers pursue hardest.

    Aspect Abstract class Interface
    Keyword abstract class interface
    State (instance fields) Allowed - any kind Not allowed - only public static final constants
    Constructors Allowed, called via super(...) None at all
    Methods Mix of abstract and concrete Abstract by default; default/static since Java 8 (Lecture 24)
    Inheritance A class extends one abstract class only A class implements many interfaces
    Type inheritance Single A class or interface may extend multiple interfaces
    Access modifiers Any, following normal rules Methods implicitly public; no private state
    Instantiation Never Never
    Relationship modelled Is-a with shared state and code Capability a type can promise
    When to choose Common state plus partial implementation Unrelated types share a contract; multiple inheritance needed

    The shortcut: choose an abstract class for "is-a plus shared state", and an interface for "capability contract". Because Java allows only single class inheritance, the interface is the only route to multiple type inheritance.

    7. Polymorphism: Two Kinds

    Polymorphism means "many forms": one name or one reference type taking on several behaviours. Java implements it in exactly two ways, separated by when the choice is made.

    Aspect Compile-time (static) Runtime (dynamic)
    Also called Static binding, early binding Dynamic binding, late binding
    Achieved by Method overloading (Lecture 11) Method overriding plus dynamic dispatch
    Decided by The compiler The JVM
    Decided from Reference type and argument types Actual object type
    Method shape Same name, different parameter lists Same name, identical parameter list
    Typical example add(int, int) vs add(int, int, int) Shape.area() overridden by Circle
    Cost Slightly cheaper - chosen once One virtual lookup per call

    Underneath, runtime polymorphism is dynamic dispatch: the compiler emits a virtual call, and the JVM selects the override belonging to the object's actual class, not the reference's declared class.

    8. Compile-Time Polymorphism: Overloading

    Method overloading is the same method name with different parameter lists (Lecture 11). The compiler resolves every call using the static types of the arguments, so the choice is frozen into the bytecode before the program runs.

    class Calculator {
    int add(int a, int b)          { return a + b; }
    int add(int a, int b, int c)   { return a + b + c; }
    double add(double a, double b) { return a + b; }
}

    Overloading depends only on the parameter list and the reference types at the call site. It is decided at compile time; it is not polymorphism of the object at all.

    9. Runtime Polymorphism: Overriding and Dynamic Dispatch

    Method overriding is a subclass redefining an inherited method with the same signature. The call is resolved at run time from the actual object, which is exactly what Section 4 demonstrated.

    The enabling move is upcasting, an implicit widening reference conversion:

    Shape s = new Circle(2);      // upcast: Circle -> Shape, always safe (is-a)
double a = s.area();          // Circle.area() runs, not a Shape version

    What the JVM does: the bytecode contains an invokevirtual instruction. At run time the JVM consults the actual object's class, finds the most specific area() implementation, and dispatches to it. The @Override annotation is optional but recommended - it makes the compiler verify that a parent method really is being overridden (Lecture 16).

    Interviewer's perspective "How does the JVM choose the method when the reference is Shape but the object is Circle?" The variable's declared type only lets the compiler check that area() exists. The actual method executed is chosen at run time from the object's real class through virtual dispatch. Reference type = what is legal; object type = what runs.

    10. Fields Are Not Polymorphic; Static Methods Are Hidden

    Two things that look polymorphic but are not - the classic trap.

    class Parent {
    int x = 1;
    static void who() { System.out.println("Parent"); }
    void hello() { System.out.println("Parent hello"); }
}
class Child extends Parent {
    int x = 2;                       // hides the parent field
    static void who() { System.out.println("Child"); }   // hides, not overrides
    @Override void hello() { System.out.println("Child hello"); }
}
public class Demo2 {
    public static void main(String[] args) {
        Parent p = new Child();
        System.out.println(p.x);    // 1 - field chosen by reference type
        p.who();                    // Parent - static resolved by reference type
        p.hello();                  // Child hello - instance override dispatched at runtime
    }
}
    1. Fields are resolved at compile time from the reference type. p.x reads the parent field even though the object is a child.
    2. Static methods are hidden, not overridden. p.who() runs the parent version because the compiler binds it from the reference type.
    3. Only overridable instance methods dispatch at run time. p.hello() runs the child override.

    Memory aid: reference type decides fields, statics and overloads; object type decides overridden instance methods.

    11. Why Java Has Both, and When to Choose

    Java offers both mechanisms because each solves a problem the other cannot. An abstract class gives one inheritance chain a shared state and shared code; an interface gives many unrelated types a common contract without forcing them into one hierarchy. The design guidance that follows is the principle program to an interface, not to an implementation: callers should depend on the contract, so the concrete type can change later without breaking them.

    Design question Prefer
    Is-a with shared state and partial implementation? Abstract class
    A capability several unrelated types can promise? Interface (for example Drawable \| Serializable)
    Need multiple type inheritance? Interface - a class extends one class at most
    Need to add methods to an existing hierarchy safely? default methods on the interface (Lecture 24)
    Need constructors, fields, or protected helpers? Abstract class

    A hybrid is common and legal: class Circle extends Shape implements Drawable reuses shared state from the base and promises a capability through the interface.

    12. Pitfalls and Design Guidance

    Pitfall What goes wrong Correct approach
    new on an abstract class or interface Compile error - neither can be instantiated Instantiate a concrete subclass
    Forgetting to implement an abstract method Concrete subclass fails to compile Implement it, or declare the subclass abstract
    Field hiding confusion Reads the parent field because the reference type wins Avoid shadowing fields; use accessors
    Confusing overloading with overriding Expects a runtime choice from an overloaded call Overloads bind at compile time; overrides at runtime
    Calling an overridable method from a constructor The override runs before child fields are set, seeing defaults Avoid overridable calls in constructors (Lecture 13)
    Forgetting @Override A typo silently creates a new method instead of an override Annotate every intended override
    Trying to override final or static methods A final method cannot be overridden; a static method is only hidden Respect the final family (Lecture 15)
    Narrowing visibility on an override Compile error - an override may not be more restrictive Keep or widen the access modifier

    13. Myth vs Reality

    Myth Reality
    "An abstract class must contain at least one abstract method" It may contain zero; abstract still blocks instantiation.
    "An interface can hold instance state" It cannot; its fields are implicitly public static final constants.
    "Fields behave polymorphically like overridden methods" Field access is resolved at compile time from the reference type.
    "Static methods are overridden" They are hidden; the reference type selects which one runs.
    "A class can extend many classes and many interfaces" It extends one class and implements many interfaces.

    14. Common Trap Questions

    Trap 1 - Instantiating the abstract: "Can I write new Shape() if Shape has no abstract methods?" No. A class marked abstract cannot be instantiated regardless of how many abstract methods it declares.

    Trap 2 - Field polymorphism: "Parent p = new Child(); Both declare int x. What does p.x print?" The parent value. Fields are resolved at compile time from the reference type, so the child field is hidden, not selected.

    Trap 3 - Static hiding: "p.who() where who is static in both classes - which runs?" The parent version, because static methods are chosen from the reference type at compile time. They are hidden, never overridden.

    Trap 4 - Overload or override: "I changed the parameter type of the method in the subclass. Did I override it?" No. A changed parameter list is an overload, bound at compile time. Overriding requires an identical signature.

    Trap 5 - Constructor dispatch: "A parent constructor calls print(), which the child overrides. Why is the child field still null?" The parent constructor runs before the child's field initialisers and body. The override executes early and sees default values; avoid overridable calls in constructors (Lecture 13).

    Trap 6 - Interface methods without public: "I implemented draw() without public. Why does it not compile?" Interface methods are implicitly public; the implementation cannot narrow the access to package-private.

    Trap 7 - Overriding final: "Why can I not override this inherited final method?" final on a method forbids overriding by design; final on a class forbids extension entirely (Lecture 15).

    15. Points to Remember

    1. Abstraction exposes what a type does and hides how it does it; encapsulation protects state, abstraction simplifies behaviour.
    2. An abstract class is declared with abstract, cannot be instantiated, and may mix abstract and concrete methods, fields and constructors.
    3. An abstract method has no body, lives only in an abstract class or an interface, and forces every concrete subclass to implement it.
    4. An interface is a pure contract: methods are implicitly public abstract, fields are implicitly public static final, and it has no constructors or instance state.
    5. A class extends one class but implements many interfaces; an interface may extend several interfaces.
    6. Compile-time polymorphism is method overloading, decided by the compiler from reference types and argument types.
    7. Runtime polymorphism is method overriding plus dynamic dispatch, decided by the JVM from the actual object type.
    8. Upcasting (Shape s = new Circle()) is an implicit, always-safe is-a conversion; the reference type controls what you may call, the object type controls what runs.
    9. Fields, static methods and overloads bind at compile time from the reference type; only overridable instance methods dispatch at run time.
    10. Choose an abstract class for is-a with shared state, an interface for a capability contract, and prefer programming to the interface; default methods are covered in Lecture 24.

    16. Likely Interview Questions

    Question Crisp Answer
    What is abstraction? Exposing the essential behaviour of a type while hiding the implementation detail that produces it.
    What is an abstract class? A class marked abstract that cannot be instantiated and may contain abstract and concrete methods, fields and constructors.
    Can an abstract class have no abstract methods? Yes. The abstract keyword alone prevents instantiation; it need not declare any abstract method.
    Can an abstract class have constructors? Yes, and they run via super(...) when a subclass is constructed; it just cannot be instantiated directly.
    What is an interface? A pure contract of implicitly public abstract methods and public static final constants, with no state or constructors.
    Abstract class vs interface? Abstract class: single inheritance, shared state and code. Interface: multiple inheritance, pure capability contract.
    Can a class implement two interfaces? Yes: class A implements X, Y. That is Java's route to multiple type inheritance.
    What is polymorphism? One name or reference type taking many behaviours; in Java it is compile-time overloading and runtime overriding.
    Compile-time vs runtime polymorphism? Overloading is resolved by the compiler from reference types; overriding is resolved by the JVM from the actual object type.
    What is dynamic dispatch? The JVM selects the override of the object's actual class at run time, even when the reference type is a parent.
    Are fields polymorphic? No. Field access is resolved at compile time from the reference type, so a hidden field is not selected at run time.
    Are static methods overridden? No. They are hidden; the version chosen follows the reference type, not the object.

    17. Final Summary

    abstraction:  expose WHAT  ---  hide HOW
abstract class  (state + abstract + concrete)  --extends-->   one subclass chain
interface       (pure contract, no state)       --implements--> many unrelated types

Shape s = new Circle();   reference type Shape  -> legal calls (compile time)
                          object type Circle    -> area() runs (runtime dispatch)

compile time decides:  fields | static methods | overloads
runtime   decides:     overridden instance methods
    • Abstraction -> expose intent, hide implementation; implemented by abstract classes and interfaces.
    • Abstract class -> abstract, non-instantiable, may hold state, constructors and mixed methods; forces subclass completion.
    • Abstract method -> no body, cannot be private/static/final, must be implemented by a concrete subclass.
    • Interface -> pure contract, implicitly public abstract methods and public static final constants; multiple inheritance.
    • Polymorphism -> compile-time (overloading, Lecture 11) and runtime (overriding plus dynamic dispatch).
    • Binding -> reference type decides fields, statics and overloads; object type decides overridden methods.
    • Design -> is-a plus shared state favours an abstract class; capability favours an interface; program to an interface.

    Golden rule Use an abstract class to share state and code down one is-a chain, use an interface to promise a capability across many types, and remember that only overridden instance methods are chosen at run time - fields, statics and overloads are fixed at compile time.

    One-line takeaway: abstract classes and interfaces both expose a contract and hide an implementation, but only overridden instance methods are dispatched at run time; fields, static methods and overloads are bound by the reference type at compile time.
