    Part 7 · Auth, Testing & Capstone Projects · Project 01

    GateKeeper: Custom API Gateway with Spring Boot

    20 sections · interview-oriented · both themes

    Scope evidence: "Build a Production-Grade Full Stack Project with Spring Boot | Microservices, Kafka & Redis | #1" (playlist map, verified). The repository folder is the SpringBoot Project/code/gatekeeper monorepo with three Maven modules - smart-gateway-service, api-management-service and analytics-service - each carrying its own pom.xml, application.properties, a config.SecurityConfig, a controller.HealthController and a dto.responseDto.HealthResponse, alongside the notes that describe them. This is the architecture and overview note for the GateKeeper project (part 1).

    GateKeeper is a backend-focused API gateway and API management platform built with Spring Boot, direct HTTP communication, Redis and Kafka. This note explains why a gateway is needed at all, what belongs inside it versus what must stay in the backend services, how the three applications divide their responsibilities, and where the project deliberately draws its scope line. Nothing here is deep implementation yet: the first milestone is simply three Spring Boot applications that start independently and answer a health check. Everything below is the design the upcoming lectures will build against.

    1. Why an API Gateway Is Needed

    An application may start with one backend. The frontend communicates with one server, and that server handles authentication, requests and business logic. Life is simple because there is exactly one address and one place where every concern lives.

    When the backend is split into services, direct access becomes harder to manage. The client may need to know:

    • where each service runs;
    • which service handles each operation;
    • what changes when a service moves.

    Every client would otherwise have to track the topology of the backend, and that topology changes as the system grows. The moment a service is renamed, relocated or split, every client is affected.

    There is a second, quieter problem. Several services may also repeat the same technical work:

    • validating authentication tokens;
    • checking broad access permissions;
    • applying request limits;
    • creating request IDs;
    • recording access information;
    • handling technical errors.

    That list is not business logic. It is identical plumbing copied into service after service, and it drifts out of sync the moment one service is updated and another is not.

    An API gateway provides one controlled entry point in front of these backend services. The client sends requests to the gateway, which applies the relevant rules and forwards each request to its destination.

    Important: The gateway exists to centralise technical entry rules and hide backend topology. It is a single, controlled front door, not a place to grow business logic.

    2. What an API Gateway Is and Its Three Main Jobs

    An API gateway is a server between API clients and backend services. It receives a request, applies entry-point policies, forwards it to the appropriate service and returns the response.

    There are two viewpoints to hold at once:

    • For the client, the gateway acts as the API server.
    • For the backend service, it acts as the caller.

    That double identity is the whole trick. The client never learns where the real service lives, and the real service never learns how many distinct clients exist.

    The three main jobs:

    Job What it means
    Routing Select the target service using the request and route configuration.
    Policy enforcement Check authentication, permissions, request limits and other configured rules.
    Reverse proxying Send the HTTP request to the target and return its response.

    The one-line relationship to memorise:

    Routing chooses the destination. Proxying performs the exchange.

    Mnemonic: R-P-P - Routing picks the target, Policy decides whether the request may proceed, Proxy performs the round trip.

    Interviewer's perspective: A weak answer says "a gateway just forwards requests." A strong answer separates the three jobs and notes that policy enforcement is what distinguishes a gateway from a plain proxy.

    3. Forward Proxy vs Reverse Proxy

    Proxy direction is defined by whose behalf the proxy is acting on:

    • A forward proxy acts on behalf of clients when they contact servers.
    • A reverse proxy acts on behalf of servers when clients contact them.

    A forward proxy hides clients from servers. A reverse proxy hides servers from clients.

    An API gateway performs reverse proxying and adds API-specific policies around it. So the gateway sits on the server side of the conversation, presenting one face to the outside world while quietly choosing among many internal services.

    Setup Path What it hides
    Forward proxy Client -> proxy -> Server The client, from the server
    Reverse proxy Client -> proxy -> Server(s) The servers, from the client
    API gateway Client -> gateway -> target + policies The servers, and it adds entry rules

    4. What Belongs in the Gateway vs the Backend

    The gateway handles technical entry rules. Backend services remain responsible for business rules.

    The source gives one sharp example. The gateway can require an administrator role for a protected operation. The target service must still check whether that administrator is allowed to modify a particular resource.

    That split matters because the two questions are different:

    • "Is this caller an administrator?" is an entry rule the gateway can answer.
    • "May this administrator modify this specific resource?" is a domain rule only the service that owns the resource can answer.

    Moving resource ownership checks and domain logic into the gateway would couple it to every backend service. Over time, it would become another large application that must change whenever business rules change. The gateway would then need to be redeployed every time a single service adjusted a permission rule - exactly the coupling the architecture was meant to remove.

    Concern Lives in the gateway Lives in the backend service
    Token validation Yes (technical entry rule) No
    Broad role requirement Yes (coarse policy) Sometimes, as a second gate
    Request limits Yes (traffic policy) No
    Request IDs / correlation Yes (entry bookkeeping) Consumes the propagated value
    Access logging Yes (entry recording) No
    Resource ownership check No Yes (domain rule)
    Business validation No Yes (domain rule)

    Golden rule: The gateway controls entry. The target service validates the business operation. Moving domain logic into the gateway couples it to every service behind it.

    5. Related Components: In Scope vs Excluded

    API gateways live in a neighbourhood of related components. Several sound similar but solve different problems, so the project states plainly which are in scope and which are excluded.

    Component Main responsibility GateKeeper scope
    API gateway Route API traffic and apply entry policies. Smart Gateway Service
    Reverse proxy Forward requests and return backend responses. Part of the Smart Gateway
    API management Define, store and update routes and policies. API Management Service
    Load balancer Select an instance of a service. Excluded
    Service discovery Locate running service instances. Excluded; target addresses are configured
    Service mesh Manage internal service-to-service traffic. Excluded

    The excluded entries are not mistakes. Load balancing and service discovery are real production needs, but this project configures target addresses directly so that the routing and policy story stays readable.

    6. What GateKeeper Is (and Is Not)

    GateKeeper is a backend-focused API gateway and API management platform built with Spring Boot, direct HTTP communication, Redis and Kafka.

    The project demonstrates how gateway responsibilities work internally. It is an educational implementation with a defined scope, rather than a replacement for a mature production gateway.

    It is worth being honest about the trade. A production gateway may need high concurrency, connection pooling, streaming, multiple protocols, certificate management, service discovery, load balancing, resilience mechanisms, monitoring and ongoing security maintenance. Building all of that from scratch is a much larger commitment.

    GateKeeper focuses on a smaller set of responsibilities so that the underlying design is easier to understand. In doing so it brings together Spring Security, filters, interceptors, HTTP communication, Redis, Kafka, database ownership, exception handling and AOP in one project.

    Important: Educational scope is a deliberate choice, not a limitation to apologise for. The value is a clear, readable implementation of the responsibilities a real gateway must own.

    7. Main Applications, Demo Targets and Planned Capabilities

    GateKeeper is built from three main applications, plus two small demo targets.

    Application Purpose
    Smart Gateway Service Handle and forward live client requests.
    API Management Service Manage users, routes and gateway policies.
    Analytics Service Process access events and provide request statistics.

    Small Catalog and Order demo services act as targets behind the gateway. Their purpose is to demonstrate forwarding and policies; they are not separate, full-sized business projects.

    The planned capabilities span the whole request lifecycle:

    Area Capability
    Request identification Generate or propagate a correlation ID.
    Routing Match active routes using configuration held in memory.
    Security Validate JWTs locally and enforce route-level role requirements.
    Traffic control Use Redis for rate limiting.
    Duplicate request handling Use Redis for configured POST idempotency.
    Forwarding Proxy HTTP requests with route-specific timeouts.
    Transformation Rewrite paths and add or remove selected headers.
    Error handling Return consistent gateway errors.
    Analytics Publish access events to Kafka for later processing.
    Configuration Store and version route settings; notify the gateway about changes.
    Auditing Record administrative actions using focused AOP auditing.

    Note the recurring shape: each capability is a narrow, named job. That is what keeps the gateway from turning into the "large application" that Section 4 warned about.

    8. Dynamic Routing: Routes as Configuration

    Dynamic routing means that routes are stored as configuration instead of being hard-coded into a large conditional block. This is the difference between a gateway that can be reconfigured and a gateway that must be recompiled.

    A route describes information such as:

    • its destination;
    • allowed methods;
    • authentication requirements;
    • permitted roles;
    • request limit;
    • timeout;
    • active status.

    The flow of route ownership is:

    Management Service stores routes in MySQL
        |
        v
Gateway loads ACTIVE routes into memory
        |
        v
Gateway uses in-memory routes for matching
        |
        v
Updating a route does NOT require rebuilding the Gateway source code

    The Management Service stores these settings in MySQL. The Gateway loads active routes into memory and uses them for route matching. Updating a route does not require changing and rebuilding the Gateway's source code.

    That last sentence is the entire point of dynamic routing. Routing decisions stop being code and become data.

    9. Data Plane and Control Plane

    Separating live traffic from configuration management is a central design decision.

    Plane Service Responsibility
    Data plane Smart Gateway Apply existing rules to live requests.
    Control plane API Management Define and change those rules.

    The two planes have different performance goals:

    • The data plane needs a short, predictable request path.
    • The control plane handles administration and durable configuration storage.

    Because the planes are separate, the Gateway can keep serving after it has loaded its routes even during a temporary Management Service outage. The catch is symmetric: new configuration loads and updates depend on the Management Service becoming available again.

    This separation is what allows a configuration change to be a rare, deliberate event rather than something that touches the hot path of every request.

    Interviewer's perspective: "What happens to live traffic if the control plane goes down?" The correct answer is that already-loaded routes keep working; only administration and refreshes pause. Candidates who conflate the planes say the gateway stops, which is exactly the failure the design avoids.

    10. How the Design Controls Latency

    A gateway adds an extra network hop and processing work. It cannot provide zero additional latency. What it can do is refuse to add unnecessary latency.

    GateKeeper keeps that extra work limited by avoiding unnecessary synchronous dependencies. If the Gateway contacted separate authentication, routing, logging and analytics services for every request, each call would add time and another possible point of failure.

    Instead, GateKeeper:

    • keeps routing and token validation local;
    • consults Redis for policies that require shared state;
    • contacts the target service over HTTP.
    Work Where it happens Reason
    Route matching Gateway memory Avoid a Management or database call for every request.
    JWT validation Gateway process Verify the token using configured key material.
    Role checks Gateway process Compare the authenticated roles with the loaded route policy.
    Rate limiting Redis Maintain shared counters with atomic operations.
    Idempotency checks Redis Coordinate duplicate requests using shared temporary state.
    Path and header changes Gateway process Apply the loaded transformation rules locally.
    Analytics storage Analytics Service Process events outside the live response path.

    Two design notes sit underneath this table.

    Local JWT validation: the Management Service will authenticate users and issue signed JWTs. The Gateway will validate those tokens locally rather than calling the Management Service for every protected request. This removes a recurring network call. It also means the Gateway is not fetching current user information on every request. Token expiry, key rotation and revocation are separate concerns; full revocation is outside this project's scope.

    Routes in memory: MySQL remains the durable source of route configuration. The Gateway's in-memory registry is the copy used for fast request processing. Routes are loaded at startup and refreshed when configuration changes. The Gateway does not read MySQL directly.

    11. Redis: Immediate Shared State

    Redis is a fast key-value data store. GateKeeper uses it for short-lived state needed while deciding whether a request can continue.

    Why not use only Java memory? Memory belongs to one running process. If multiple Gateway instances maintained separate counters, each instance would see only the requests it received. Redis provides shared state that those instances can consult. Even with one Gateway running locally, this demonstrates the reason for separating shared runtime state from process memory.

    Key concepts:

    Concept Meaning
    Key Identifies a stored value.
    Value The counter, status or response information stored under a key.
    TTL A time limit after which the key expires automatically.
    Atomic operation A change performed as one indivisible operation.

    Atomicity matters when requests arrive together. Separate reads and writes can allow two requests to act on the same old value. A Redis Lua script can group related counter and expiry operations into one atomic operation.

    Rate limiting: rate limiting restricts how many requests a user or client may make to a route within a time window. Redis holds the counter. The Gateway updates it atomically, checks the configured limit and rejects requests that exceed it. Expiration removes counters after their useful window.

    POST idempotency: idempotency handling helps avoid repeating an operation when a client resends the same request. For configured routes, Redis will hold temporary processing state and a saved successful response associated with an idempotency key. A matching completed request can receive the saved response without forwarding the operation again. This is different from general response caching. It is tied to identifying a repeated operation. The detailed implementation and failure cases are reserved for later lectures.

    Redis boundaries: Redis does not hold the authoritative route configuration or analytics history. MySQL and MongoDB have those responsibilities.

    Important: Redis in GateKeeper is short-lived coordination state (rate-limit counters and idempotency records), not a general response cache and not a source of truth.

    12. Kafka: Asynchronous Events

    Kafka is a durable event-streaming platform. A producer writes an event to a topic, and a consumer reads it independently. The consumer does not need to process the event immediately. Kafka retains records according to its configured retention, allowing consumers to process them later.

    Term Meaning GateKeeper example
    Producer Publishes events. Gateway or Management Service
    Topic A named stream of events. Access events or configuration events
    Consumer Reads and processes events. Analytics Service or Gateway
    Partition An ordered subdivision of a topic. Allows work to be distributed.
    Offset A record's position within a partition. Tracks reading progress.
    Consumer group Consumers sharing the work of a topic. Analytics consumers working together.

    Access events: the Gateway publishes request outcome metadata to gateway-access-events. The Analytics Service consumes these events and stores them in MongoDB. Useful metadata includes the event ID, correlation ID, route, request method, outcome, duration and whether a rate-limit rejection or idempotency replay occurred. Passwords, JWTs, cookies and authorization headers must not be included in access events.

    Configuration events: the Management Service publishes route-change notifications to gateway-configuration-events. A notification identifies what changed. The Gateway then fetches the latest configuration from the Management Service and refreshes its in-memory registry. The event is a notification; MySQL remains the source of truth through the Management Service.

    Duplicate events: a consumer may receive an event again during failure recovery. The Analytics Service will use a unique eventId to avoid storing the same access event twice. A correlationId serves a different purpose: it links work associated with one incoming request. An eventId identifies one event for deduplication.

    Redis and Kafka serve different needs:

    Question Redis Kafka
    What does it provide here? Immediate shared state Asynchronous event delivery
    Typical data Counters and idempotency state Access and configuration events
    Why does the Gateway use it? Obtain a result needed for a policy decision Notify another component about an outcome or change
    How long is data retained? Usually a short period controlled by TTL According to topic retention

    The Gateway does not wait for Analytics or MongoDB to finish processing an event. Publishing still has a cost, and producer failures need handling; an asynchronous send alone does not guarantee that events can never be lost.

    13. Service Responsibilities and Infrastructure Ownership

    Smart Gateway Service: the public entry point and data plane. Its planned responsibilities are route matching, correlation IDs, JWT validation, role checks, rate limiting, idempotency, path and header rules, forwarding, timeouts, gateway errors and access-event publication. It holds active routes in memory and uses Redis for temporary policy state. It loads configuration through the Management Service and contacts target services over HTTP. It has no MySQL or MongoDB database and owns no business-domain tables.

    API Management Service: the control plane for users, routes and policies. It will manage credentials and roles, issue JWTs, store route configuration, maintain configuration versions and publish change notifications. AOP will support auditing of administrative actions. It owns MySQL data for users, roles, routes, policy settings, versions and audit records. Other services must not directly modify its tables.

    Analytics Service: processes Gateway access events into operational information. It will consume events, deduplicate them, store event documents and support statistics such as request counts, outcomes, average duration, slow routes, rate-limit rejections and idempotency replays. It owns MongoDB data for access events and processed-event records. It does not change route configuration or participate in forwarding live requests.

    Catalog and Order demo services: small downstream services used to demonstrate routing, authorization, path rewriting, header propagation, timeouts and duplicate request handling. Their business logic stays deliberately small. They remain responsible for their own business-level validation and authorization.

    Infrastructure ownership:

    Component Used or owned by Data or purpose
    MySQL Owned by API Management Durable users, roles, routes, versions and audits
    MongoDB Owned by Analytics Access-event documents and processing records
    Redis Used by the Gateway's policy layer Rate-limit counters and idempotency state
    Kafka Shared event infrastructure Access events and route-change notifications

    Golden rule: Each service controls its own persistent data. No service reaches into another service's database.

    14. Failure Behavior and Architectural Boundaries

    Separation reduces unnecessary dependencies. It does not make the system immune to failures: a component required for the current request can still affect that request. The design states the intended behaviour for each failure.

    Component unavailable Intended effect
    API Management Already-loaded routes remain usable; administration and refreshes pause.
    Analytics Forwarding continues; retained Kafka events can be processed later.
    MongoDB Forwarding continues; analytics storage is affected.
    Target service Requests to that target fail through the Gateway.
    Slow target The configured route timeout limits waiting.
    Redis Routes requiring Redis-backed policy decisions fail closed in this project.
    Kafka Event publication or delivery is affected; producer failures need explicit handling.

    Fail closed means refusing a request when a required policy cannot be checked, rather than silently bypassing the policy. For a rate-limited route, failing closed is safer than letting unlimited traffic through because the counter store is down.

    Architectural boundaries worth remembering:

    • Only the Smart Gateway forwards live target API traffic.
    • The Gateway accesses route configuration through Management, not through MySQL.
    • The Gateway does not call Analytics or MongoDB during forwarding.
    • Analytics does not administer routes.
    • Each service controls its own persistent data.
    • Target services retain business-specific security checks.

    Interviewer's perspective: "Why fail closed on a Redis outage?" Because a policy that cannot be enforced should not be silently skipped. Fail-open would trade availability for a security hole; this project chooses refusal.

    15. Initial Setup and Project Structure

    The first implementation milestone uses three Spring Boot applications:

    • smart-gateway-service
    • api-management-service
    • analytics-service

    Each application should start independently, use a distinct port and answer a simple health-check request. The health check confirms that the application can start and respond over HTTP. It does not, by itself, prove that Redis, Kafka, MySQL, MongoDB or the complete gateway workflow is ready.

    The repository is a monorepo under SpringBoot Project/code/gatekeeper, with one Maven module per application. Each module has its own pom.xml, its own application.properties, a health controller and a health response DTO, and a security configuration.

    // SpringBoot Project/code/gatekeeper  (monorepo, one Maven module per service)

    The supplied script does not include the health-check implementation, so no controller code, endpoint path or port values are reproduced here. What the milestone proves is narrow and honest: three independent applications that boot and answer over HTTP.

    16. Myth vs Reality

    Myth Reality
    "An API gateway is just a reverse proxy." It is a reverse proxy plus API-specific policies: routing, policy enforcement and proxying.
    "The gateway should own business and resource-access rules." It owns technical entry rules; business and ownership checks stay in the target service.
    "The gateway looks up routes from the database on every request." Routes are loaded into memory; MySQL is durable storage behind the Management Service.
    "The gateway calls the auth service for every protected request." JWTs are validated locally; the Management Service is not contacted per request.
    "Redis is the general response cache for the gateway." Redis holds short-lived rate-limit counters and idempotency state, not general cached responses.
    "Kafka delivery is synchronous and loss-proof." It is asynchronous; publishing has a cost and producer failures need explicit handling.
    "A passing health check means the whole system is ready." It only proves the application starts and responds over HTTP.
    "GateKeeper is a production-grade gateway replacement." It is an educational implementation with a deliberately defined scope.

    17. Common Trap Questions

    Trap 1 - "The gateway should contain the business logic." Verdict: False. The gateway controls entry; the target service validates the business operation. Putting domain logic in the gateway couples it to every service and forces redeployment whenever a business rule changes.

    Trap 2 - "The gateway must query the Management Service or MySQL for routes on every request." Verdict: False. Active routes are stored in memory and matched locally. MySQL is the durable source behind the Management Service, and the Gateway does not read MySQL directly.

    Trap 3 - "Local JWT validation means the gateway knows everything about the user." Verdict: Misleading. The Gateway verifies the token locally using configured key material, but it is not fetching current user information per request. Expiry, key rotation and revocation are separate concerns, and full revocation is out of scope.

    Trap 4 - "An API gateway is a load balancer or service discovery layer." Verdict: False. A load balancer selects an instance and service discovery locates instances; both are excluded here. The gateway routes, enforces policy and reverse-proxies, with target addresses configured directly.

    Trap 5 - "Redis is the gateway's response cache." Verdict: False. Redis is used for rate-limit counters and POST idempotency state. It is short-lived coordination state, not general response caching, and it does not hold authoritative route configuration.

    Trap 6 - "The gateway waits for analytics before returning the response." Verdict: False. Access events are published to Kafka and the client does not wait for Analytics or MongoDB. The trade-off is that producer failures still need explicit handling.

    Trap 7 - "A passing health check proves the gateway is production-ready." Verdict: False. The health check only proves the application starts and responds over HTTP; it says nothing about Redis, Kafka, MySQL, MongoDB or the full request workflow.

    18. Points to Remember

    1. An API gateway is one controlled entry point in front of backend services; the client sees the gateway as the API server and the backend sees the gateway as the caller.
    2. Its three jobs are routing, policy enforcement and reverse proxying: routing chooses the destination, proxying performs the exchange.
    3. A forward proxy acts for clients; a reverse proxy acts for servers. An API gateway is a reverse proxy with API-specific policies around it.
    4. The gateway handles technical entry rules (tokens, broad roles, limits, IDs, logging, errors); the target service handles business and resource-ownership rules.
    5. Dynamic routing stores routes as configuration - destination, methods, auth, roles, limit, timeout, active status - so route changes do not require rebuilding the Gateway.
    6. The data plane (Smart Gateway) applies existing rules to live requests; the control plane (API Management) defines and stores those rules in MySQL.
    7. Latency is controlled by keeping routing and JWT validation local and consulting Redis only for shared-state policies such as rate limiting and idempotency.
    8. Redis provides short-lived shared state (counters, idempotency) with atomic operations; it is not the source of truth for routes or analytics.
    9. Kafka delivers events asynchronously: the Gateway publishes access events and the Management Service publishes configuration notifications; MySQL stays the source of truth.
    10. The first milestone is three independently starting Spring Boot applications - smart-gateway-service, api-management-service, analytics-service - each answering a health check over HTTP.

    19. Likely Interview Questions

    Question Crisp Answer
    Why do we need an API gateway? To give clients one controlled entry point and to centralise repeated technical work such as token validation, permissions, rate limits, request IDs, access logging and technical errors.
    What are the three main jobs of a gateway? Routing (choose the target), policy enforcement (check configured rules), reverse proxying (perform the HTTP exchange).
    Forward proxy vs reverse proxy? A forward proxy acts on behalf of clients; a reverse proxy acts on behalf of servers. An API gateway does reverse proxying plus API policies.
    What belongs in the gateway vs the backend? The gateway owns entry rules; the backend owns business and resource-ownership rules. Moving domain logic into the gateway couples it to every service.
    What is dynamic routing? Storing routes as configuration and matching them from memory, instead of hard-coding routing into conditional code, so route changes do not require rebuilding the Gateway.
    Data plane vs control plane? The data plane (Smart Gateway) applies existing rules to live requests; the control plane (API Management) defines and stores those rules.
    Why keep JWT validation local? It removes a network call to the Management Service on every protected request. Expiry, key rotation and full revocation are treated as separate concerns.
    Why does the gateway need Redis? For shared, short-lived runtime state: rate-limit counters and POST idempotency. Process memory cannot be shared across multiple Gateway instances.
    Why use Kafka here? To publish access events and configuration-change notifications asynchronously, so analytics processing happens outside the live response path.
    What is fail closed? Refusing a request when a required policy cannot be checked, rather than silently bypassing the policy.
    What does the health-check milestone prove? Only that each application starts independently and responds over HTTP - not that Redis, Kafka, MySQL or MongoDB are ready.
    Is GateKeeper a production gateway? No. It is a backend-focused, educational API gateway and management platform built with Spring Boot, direct HTTP, Redis and Kafka.
