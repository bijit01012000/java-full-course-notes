    Part 4 · Strings, Generics & Collections · Lecture 31

    Java Collection Interface Deep Dive | Methods & Internals

    18 sections · interview-oriented · both themes

    Scope evidence: "Java Collection Interface Deep Dive | Methods & Internals" (playlist map, verified). Repo evidence: code/Demo.java.

    Collection<E> is the root of the single-element part of the Java Collections Framework, the common contract shared by List, Set and Queue. It defines the operations every one of those types must understand, yet it also marks many of them as optional, which is why an apparently correct call can throw at runtime. This lecture walks through the single-element and bulk methods, array conversion, the meaning of the optional-operation contract, the Java 8 default methods, the skeletal abstract classes, and the equals/hashCode rules that differ by collection type. The goal is to know not only what compiles but what is guaranteed.

    1. The Root of the Collections Hierarchy

    Collection<E> is a generic interface declared in java.util. It is the superinterface of List<E>, Set<E> and Queue<E>; Deque<E> extends Queue. It does not cover Map<K,V>, because a map stores key-value bindings rather than a sequence of single elements. Map is therefore a separate hierarchy, and the collections returned by map.keySet(), map.values() and map.entrySet() are views that do implement Collection.

    Collection extends Iterable<E>. That inheritance is what supplies iterator() and, in turn, the enhanced for-each loop (Lecture 30). The relationship is a chain of capability:

    Iterable<E>  ⊃  Collection<E>  ⊃  { List<E>, Set<E>, Queue<E> }
Map<K,V>  ->  separate hierarchy, not a Collection

    Important "Map is a Collection" is false. Map does not extend Collection; only the views it exports (keySet, values, entrySet) do.

    2. The Hierarchy at a Glance

    Iterable<E>
  |
  +-- Collection<E>
        |
        +-- List<E>    ordered, indexed, duplicates allowed
        +-- Set<E>     no duplicates
        +-- Queue<E>   FIFO or priority ordering
              |
              +-- Deque<E>  double-ended queue
Map<K,V>   separate hierarchy; does NOT extend Collection

    The interfaces are backed by skeletal abstract classes (AbstractCollection, AbstractList, AbstractSet, AbstractQueue) and by concrete implementations (ArrayList, LinkedList, HashSet, TreeSet, ArrayDeque, PriorityQueue). This lecture fixes the contract; Lecture 32 examines the List implementations in detail.

    3. Single-Element Methods

    The single-element methods operate on one element at a time and are declared directly on Collection:

    Method Signature Meaning
    add boolean add(E e) Adds one element; returns whether the collection changed
    remove boolean remove(Object o) Removes one element equal to o; returns whether it was found
    contains boolean contains(Object o) Membership test using equals
    size int size() Number of elements currently held
    isEmpty boolean isEmpty() Equivalent to size() == 0
    clear void clear() Removes every element
    iterator Iterator<E> iterator() Inherited from Iterable; the iteration primitive
    stream Stream<E> stream() Default method returning a sequential stream (Lecture 39)

    Notice the asymmetry in signatures: insertion is typed E, but remove and contains accept Object. This keeps the contract usable with legacy code and with raw collections; the cost is that a wrong-typed argument is a silent false instead of a compile error.

    Single-Element vs Bulk Methods

    Aspect Single-element methods Bulk methods
    Examples add, remove, contains addAll, removeAll, retainAll, containsAll
    Argument One element (E or Object) An entire Collection<?>
    Return A value or a change flag A change flag (except containsAll, a pure test)
    Typical cost Roughly one element of work Often O(n), and up to O(n × m)
    Atomicity One logical change Not guaranteed atomic; partial application is allowed

    4. Bulk Operations

    Bulk operations treat an entire collection as the argument. They are the natural way to combine two data sets:

    Bulk method Signature Set-theoretic meaning
    addAll boolean addAll(Collection<? extends E> c) Union: add every element of c
    removeAll boolean removeAll(Collection<?> c) Difference: remove every element also in c
    retainAll boolean retainAll(Collection<?> c) Intersection: keep only elements also in c
    containsAll boolean containsAll(Collection<?> c) Subset test: are all elements of c present?

    Each returns boolean reporting whether the receiver changed (except containsAll, which reports membership only). A subtle and important detail: removeAll and retainAll reason about elements via equals, never about positions or indices.

    import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Collection<String> a = new ArrayList<>(Arrays.asList("A", "B", "C", "D"));
        Collection<String> b = new ArrayList<>(Arrays.asList("C", "D", "E"));

        System.out.println(a.containsAll(b));       // false: E is missing

        Collection<String> union = new ArrayList<>(a);
        union.addAll(b);                            // [A, B, C, D, C, D, E]
        System.out.println(union);

        Collection<String> intersection = new ArrayList<>(a);
        intersection.retainAll(b);                  // [C, D]
        System.out.println(intersection);

        Collection<String> difference = new ArrayList<>(a);
        difference.removeAll(b);                    // [A, B]
        System.out.println(difference);
    }
}

    Memory aid Read retainAll as "retain what is in the argument" (intersection) and removeAll as "remove what is in the argument" (difference). The receiver always keeps its identity; only its contents change.

    5. removeAll Is Difference, retainAll Is Intersection

    Given a = {A, B, C, D} and b = {C, D, E}:

    • a.retainAll(b) leaves {C, D} — the intersection, written intersection(a, b).
    • a.removeAll(b) leaves {A, B} — the difference, written difference(a, b) or a minus b.
    • a.addAll(b) grows a to {A, B, C, D, C, D, E} because a List permits duplicates.

    Two consequences follow. First, for a Set, addAll and removeAll behave exactly like set union and set difference; for a List, duplicate handling makes the result multiset-like. Second, retainAll is the correct way to prune a collection down to an allowed whitelist, while removeAll is the correct way to purge a blacklist. Neither touches elements that are not named in the argument.

    Trap removeAll on a List<Integer> does not remove by index. It removes every element equal to some element of the argument collection. Index-based removal is List.remove(int).

    6. Array Conversion: toArray and toArray(T[])

    Collection exposes two conversions to arrays:

    Overload Signature Result
    Untyped Object[] toArray() Always a new Object[]; no type information survives erasure
    Typed <T> T[] toArray(T[] a) A T[]; if a is large enough it is filled and returned, otherwise a new T[] is allocated 
    import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Collection<String> c = new ArrayList<>(Arrays.asList("x", "y", "z"));

        Object[] raw = c.toArray();                 // Object[]
        String[] typed = c.toArray(new String[0]);  // preferred modern style

        System.out.println(Arrays.toString(raw));
        System.out.println(Arrays.toString(typed));
    }
}

    The typed version needs an array of the correct runtime component type for two reasons. First, an Object[] can never be assigned to a String[], so the untyped form usually forces a manual copy. Second, the JVM uses the passed array's component type to allocate a correctly typed array when the input is too small, and it uses the input directly when it is large enough. Passing new String[0] is the idiomatic choice because it lets the collection allocate an exactly-sized result; passing an oversized array works but the trailing slots are set to null.

    Important toArray() returns Object[] even when the collection holds Strings. A cast such as (String[]) c.toArray() throws ClassCastException unless the collection's backing array already has that component type.

    7. Optional Operations and UnsupportedOperationException

    The Collection contract divides its methods into required and optional operations. An optional operation is legal to declare and legal to call, but an implementation is permitted to reject it by throwing UnsupportedOperationException. "Optional" here does not mean "nullable" or "may be skipped"; it means "the implementation may not support this mutation".

    Operation Required or optional Typical implementations that reject it
    size, isEmpty, contains, iterator Required No conforming implementation may reject these
    toArray Required No conforming implementation may reject these
    add, addAll Optional Arrays.asList, List.of and the other immutable factories
    remove, removeAll, retainAll Optional List.of, Collections.unmodifiableList and read-only views
    clear Optional Fixed-size and immutable collections
    removeIf (default) Optional Delegates to remove/iterator.remove, so it inherits their optionality

    Arrays.asList("a", "b", "c") returns a fixed-size list: set is supported, but add and remove throw. List.of("a", "b", "c") returns an immutable list: even set throws. The distinction between "fixed-size" and "immutable" is one of the most reliable interview questions in this area.

    import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<String> fixed = Arrays.asList("a", "b", "c");
        fixed.set(0, "z");            // allowed: replacement is supported

        try {
            fixed.add("d");          // structurally unsupported
        } catch (UnsupportedOperationException e) {
            System.out.println("fixed-size: add rejected");
        }

        List<String> immutable = List.of("a", "b", "c");
        try {
            immutable.set(0, "z");   // even replacement is rejected
        } catch (UnsupportedOperationException e) {
            System.out.println("immutable: set rejected");
        }
    }
}

    Interviewer's perspective When asked "is a Collection mutable?", the precise answer is: not necessarily. The interface declares mutation methods, but each may be optional, so mutability is a property of the implementation, not of the type. This is why APIs often return Collection<E> for a view that is structurally read-only.

    8. Default Methods (Java 8)

    Before Java 8, adding a method to Collection would have broken every existing implementation. Default methods solved the evolution problem: new behaviour is added to the interface with a body, and implementors inherit it for free.

    Default method Signature Purpose
    removeIf boolean removeIf(Predicate<? super E> filter) Removes every element matching the predicate
    forEach void forEach(Consumer<? super E> action) Runs an action for each element
    stream Stream<E> stream() Returns a sequential stream (Lecture 39)
    spliterator Spliterator<E> spliterator() Traversal/partitioning primitive used by streams (Lecture 39)

    Default methods may still be optional in effect: removeIf is implemented in terms of iterator.remove() or remove, so calling it on an immutable collection throws, even though the method itself is inherited.

    import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Collection<Integer> c = new ArrayList<>(Arrays.asList(1, 2, 3, 4, 5, 6));

        c.removeIf(n -> n % 2 == 0);                 // removes 2, 4, 6
        c.forEach(n -> System.out.print(n + " "));   // 1 3 5
        System.out.println();

        long big = c.stream().filter(n -> n > 1).count();   // 2 (Lecture 39)
        System.out.println(big);
    }
}

    9. Skeletal Implementations: AbstractCollection and AbstractList

    Writing a full Collection from scratch means implementing every abstract method, including the optional ones reduced to a sensible default. The JDK removes that burden with skeletal implementations:

    • AbstractCollection<E> implements contains, containsAll, toArray, removeAll, retainAll, clear and toString in terms of iteration; add and remove are given rejecting bodies, so only size() and iterator() remain abstract for a read-only subclass.
    • AbstractList<E> extends AbstractCollection and implements get(int)-based logic, equals, hashCode, indexOf, lastIndexOf, iterator, subList and listIterator.
    • AbstractSet<E>, AbstractQueue<E> and AbstractMap<K,V> play the same role for their branches.

    The design point is reuse by inheritance: ArrayList extends AbstractList, HashSet extends AbstractSet, and so on. A custom mutable collection can therefore subclass AbstractCollection and override only size(), iterator() and the optional add()/remove() it actually supports.

    Important AbstractCollection is not magic; it is ordinary code. If a subclass throws from iterator().remove(), then inherited bulk methods such as removeAll and retainAll may throw as a consequence.

    10. equals and hashCode Contracts by Collection Type

    Collection itself does not strengthen equals/hashCode beyond Object; the meaningful contracts live in its subinterfaces. This is the single most common source of "why are these not equal?" bugs.

    Type equals semantics hashCode
    List Order matters; two lists are equal iff the same elements appear in the same positions. [1, 2] is not equal to [2, 1]. Depends on element order
    Set Order is irrelevant; two sets are equal iff they contain the same elements. {1, 2} equals {2, 1}. Independent of iteration order
    Queue Inherited contract; implementations generally do not define element-wise equality Identity, unless overridden
    Collection used directly No element-wise contract; effectively identity unless the concrete class overrides Identity, unless overridden

    Because equals is defined by the contract and not by the concrete class, an ArrayList and a LinkedList with the same elements are equal, and a HashSet and a TreeSet with the same elements are equal. The rule of thumb: use List when order is part of identity; use Set when membership is the identity.

    Golden rule The equals/hashCode contract is inherited from the subinterface, never from the storage strategy. equals is about logical contents, not about the implementation class.

    11. The Collections Utility Class

    java.util.Collections (plural) is a utility class of static methods that operate on Collection instances. It is easily confused with the Collection (singular) interface.

    Utility Returns Behaviour
    Collections.unmodifiableCollection A read-only view Mutations throw UnsupportedOperationException
    Collections.synchronizedCollection A thread-safe wrapper Serialises access; iteration still needs external synchronisation (forward-ref)
    Collections.emptyList / emptySet / emptyMap Immutable empty singletons Safe, reused empty instances
    Collections.singleton / singletonList Immutable one-element collections Useful for addAll of a single element

    Wrapping with unmodifiableCollection does not copy the data; it is a view that forwards reads and blocks writes, so changes made through the original collection remain visible through the wrapper. synchronizedCollection likewise wraps rather than copies, and its iteration is not atomic, so concurrent iteration requires manual synchronized blocks.

    12. size() vs capacity

    Collection.size() reports the number of elements currently stored, and every conforming implementation must support it. Capacity is a different concept: it is internal storage reserved for growth, and it applies only to implementations that use a backing array. For an ArrayList, size() can be smaller than capacity, and trimToSize() can shrink the array to fit. Capacity is not part of the Collection contract and most collections never expose it; the ArrayList internals are covered in Lecture 32.

    Important size() is required and universal. capacity is implementation-specific and belongs to ArrayList, Vector, ArrayDeque and the other array-backed classes, not to Collection.

    13. Common Errors and Pitfalls

    Pitfall What happens Correct approach
    Assuming a returned collection is mutable UnsupportedOperationException on add/remove/set Check the documentation; copy first if mutation is needed
    Confusing List and Set equality [1, 2] compares unequal to [2, 1], but {1, 2} equals {2, 1} Choose the type that matches the identity you need
    Mutating while iterating ConcurrentModificationException (Lecture 30) Use iterator.remove() or the Java 8 removeIf
    Treating removeAll/retainAll as index-based Wrong elements removed Remember they are equals-based; use List.remove(int) for indices
    Expecting toArray() to be typed ClassCastException on (String[]) Use toArray(new String[0])
    Passing primitives to contains/remove Silent autoboxing on every call Prefer typed references; be aware of allocation cost
    Assuming all collections accept null NullPointerException from List.of/Set.of Know each implementation's null policy; ArrayList allows null, the factories do not

    14. Myth vs Reality

    Myth Reality
    "Map is a Collection" Map does not extend Collection; only its keySet, values and entrySet views do.
    "Every Collection supports add and remove" These operations are optional; fixed-size and immutable collections throw UnsupportedOperationException.
    "removeAll removes elements by index" It removes by equals; only List.remove(int) is index-based.
    "toArray() returns a String[] for a collection of strings" It always returns Object[]; use the typed overload for a String[].
    "Two sets with different order are unequal" Set equality ignores order; List equality depends on order.

    15. Common Trap Questions

    Trap 1 — Interfaces vs utility class: "Is Collections the same thing as Collection?" No. Collection (singular) is the root interface; Collections (plural) is a utility class of static algorithms and wrappers.

    Trap 2 — The index ambiguity: "A List<Integer> contains the values [10, 20, 30]. What does list.remove(1) remove?" Index 1, that is, the value 20, leaving [10, 30]. To remove the value 1, use list.remove(Integer.valueOf(1)).

    Trap 3 — Direction of intersection: "Does a.retainAll(b) keep a's elements that are in b, or b's elements that are in a?" It mutates a, keeping only the elements of a that are also in b. The result is the intersection, stored in a.

    Trap 4 — Fixed-size vs immutable: "Can I call set on the list returned by Arrays.asList?" Yes, replacement is allowed. Only structural changes (add, remove, clear) throw. List.of forbids even set.

    Trap 5 — The typed array: "Is toArray(new String[c.size()]) better than toArray(new String[0])?" Both are correct. The zero-length form is the modern idiom and lets the collection allocate an exactly-sized array; an oversized array is filled and null-padded.

    Trap 6 — Equality across implementations: "Are new ArrayList<>(List.of(1, 2)) and new LinkedList<>(List.of(1, 2)) equal?" Yes. Both implement the List contract, so equals compares contents in order regardless of the concrete class.

    Trap 7 — Optionality of defaults: "removeIf has a body, so it cannot fail on an immutable collection, right?" Wrong. removeIf is inherited, but it is implemented through remove/iterator.remove, so it throws UnsupportedOperationException on immutable collections.

    16. Points to Remember

    1. Collection<E> is the root interface for List, Set and Queue; Map is a separate hierarchy that does not extend it.
    2. Collection extends Iterable, so iterator() and the for-each loop are available on every collection.
    3. Single-element methods are add, remove, contains, size, isEmpty, clear, iterator and the default stream.
    4. Bulk operations are addAll (union), removeAll (difference), retainAll (intersection) and containsAll (subset test).
    5. removeAll and retainAll compare elements with equals, never by index or position.
    6. toArray() returns Object[]; toArray(T[]) returns a typed array and new T[0] is the preferred argument.
    7. Many methods are optional: an implementation may throw UnsupportedOperationException; "optional" is a contract term, not a nullability term.
    8. Java 8 default methods (removeIf, forEach, stream, spliterator) let the interface evolve without breaking implementors.
    9. AbstractCollection, AbstractList, AbstractSet and AbstractQueue are skeletal implementations that supply default behaviour for concrete classes.
    10. List equality is order-sensitive, Set equality is order-insensitive, and Collections is a utility class distinct from the Collection interface.

    17. Likely Interview Questions

    Question Crisp Answer
    What is the Collection interface? The root interface of the single-element collections hierarchy, extended by List, Set and Queue, and itself extending Iterable.
    Does Map extend Collection? No. Map is a separate hierarchy; only its keySet, values and entrySet views are collections.
    Why does Collection extend Iterable? So every collection is directly iterable, enabling iterator() and the for-each loop.
    Name the bulk operations. addAll, removeAll, retainAll and containsAll.
    What does retainAll do? Keeps only the receiver's elements that are also present in the argument, computing the intersection.
    What does removeAll do? Removes every receiver element that is also present in the argument, computing the difference.
    Difference between toArray() and toArray(T[])? The first returns Object[]; the second returns an array of type T, reusing the passed array or allocating a new one.
    What does "optional operation" mean? An implementation may legally reject the operation by throwing UnsupportedOperationException; mutability is implementation-specific.
    Give a fixed-size versus a truly immutable example. Arrays.asList is fixed-size (set allowed, add/remove throw); List.of is immutable (set also throws).
    How does List equality differ from Set equality? List equality is order-sensitive and position-wise; Set equality ignores order and compares membership.
    What are AbstractCollection and AbstractList for? They are skeletal implementations that provide most method bodies so custom collections need only implement the core ones.
    Why were default methods added to Collection? To add new behaviour (removeIf, stream, forEach, spliterator) in Java 8 without breaking every existing implementation.

    18. Final Summary

    Collection<E>  ⊃  List<E> | Set<E> | Queue<E>
   extends Iterable<E>          Map<K,V> = separate hierarchy (≠ Collection)

single:  add · remove · contains · size · isEmpty · clear · iterator · stream
bulk:    addAll(union) · retainAll(intersection) · removeAll(difference) · containsAll(subset)
arrays:  toArray() -> Object[]      toArray(new T[0]) -> T[]

optional ops  --rejected by-->  UnsupportedOperationException  (Arrays.asList, List.of, unmodifiable views)
defaults      --added in Java 8-->  removeIf · forEach · stream · spliterator
skeletal      --supply bodies-->  AbstractCollection · AbstractList · AbstractSet · AbstractQueue
equality:     List order matters  ≠  Set order ignored  ·  Collections = utility class
    • Collection<E> is the root contract for List, Set and Queue, extends Iterable, and excludes Map.
    • Single-element and bulk methods form the API; bulk methods are equals-based set operations, not index operations.
    • toArray() yields Object[]; the typed overload requires a correctly-typed, correctly-sized array argument.
    • Many operations are optional, so mutability depends on the implementation, not on the interface type.
    • Java 8 default methods and the skeletal abstract classes let the contract evolve and be implemented cheaply.
    • equals/hashCode semantics come from the subinterface: order matters for List, is irrelevant for Set.

    Golden rule The Collection interface promises the vocabulary, not the mutability: always read the implementation's contract before assuming add, remove or set will succeed.

    One-line takeaway: Collection<E> is the shared, partly-optional contract beneath List, Set and Queue — learn its bulk set operations, its toArray conversion and its per-subinterface equality rules, and the rest of the framework becomes predictable.
