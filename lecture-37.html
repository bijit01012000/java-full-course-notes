    Part 5 · Collections, Lambdas & Streams · Lecture 37

    Java Lambdas & Functional Interfaces | Comparator Interface

    18 sections · interview-oriented · both themes

    Scope evidence: "Java Lambdas & Functional Interfaces | Comparator Interface" (playlist map, verified). Repo evidence: 2 Demo files. The cached lecture PDF is image-only and is ignored per project rules.

    Lecture 24 established the functional interface as an interface with exactly one abstract method, and promised that lambdas would use it as a target. This lecture delivers on that promise: it defines what a lambda expression is, enumerates its four syntactic forms, explains target typing (why a lambda has no type of its own), and pins down the capture rules and the surprising meaning of this inside a lambda. It then catalogues the java.util.function family, contrasts anonymous classes with lambdas, and applies the whole idea to Comparator, the standard functional interface that this lecture treats as its running example. Method references and composition follow in Lecture 38, and streams in Lecture 39.

    1. What a Lambda Is

    A lambda expression is a compact block of code that is a value: it represents an operation you can pass around, store in a variable, and invoke later. Before Java 8, the only way to hand a piece of behaviour to a method was an anonymous class, which forced a full class declaration, a new, and a method signature for what was often a single expression. A lambda keeps only the essential part — a parameter list, the arrow token ->, and a body — and lets the surrounding context supply the rest.

    Two facts fix the whole mental model:

    1. A lambda is not a standalone value; it has no type until the compiler is told which functional interface it must satisfy.
    2. A lambda is an object at runtime (the JVM materialises it), but that object implements a functional interface and has no name of its own.

    Memory aid A lambda is a verb looking for a noun. The behaviour is the verb; the functional interface is the noun that gives it a type and a method name.

    2. Functional Interfaces: The SAM Contract (Recap from Lecture 24)

    A functional interface is an interface that declares exactly one abstract method, often written SAM (Single Abstract Method). That lone method is the contract a lambda fulfils. @FunctionalInterface is optional but recommended: it makes the compiler verify the SAM rule at the interface declaration, so a mistake is reported where it is made rather than at every call site.

    Three counting rules decide what a functional interface really is:

    1. Exactly one abstract method. Zero abstract methods or two abstract methods both disqualify the interface as a lambda target.
    2. Object methods do not count. Redeclaring equals(Object), hashCode() or toString() does not raise the abstract-method total, because every class already inherits those from Object.
    3. default and static methods do not count. Only body-less (abstract) methods count toward the single-method rule.

    Important The SAM rule is about abstract methods only. An interface may declare many default and static methods and still be functional, because none of them is abstract. This is exactly why Comparator (many default and static methods, one abstract compare) is a valid lambda target.

    3. The Four Lambda Forms

    Every lambda is a parameter list, the arrow token ->, and a body. The body is either a single expression (no braces, no return) or a block (braces, explicit return for a non-void result). The parameter list has four shapes.

    Form Example Notes
    no parameters () -> expr empty parentheses are required; matches a no-arg SAM such as Supplier.get or Runnable.run
    one parameter x -> expr the parentheses around a single inferred parameter are optional
    two or more parameters (x, y) -> expr parentheses are mandatory from two parameters onward
    block body (x, y) -> { ...; return r; } use braces when the body has multiple statements; a non-void SAM needs an explicit return 
    // Demo.java — the four lambda forms against three functional interfaces
import java.util.function.Supplier;

public class Demo {
    interface IntOp { int apply(int a, int b); }
    interface Mapper { int map(String s); }

    public static void main(String[] args) {
        Supplier<String> hello = () -> "hi";              // no parameters
        Mapper length        = s -> s.length();           // one inferred parameter
        IntOp add            = (a, b) -> a + b;           // expression body
        IntOp max            = (a, b) -> {                // block body
            int r = Math.max(a, b);
            return r;
        };
        System.out.println(hello.get() + " " + length.map("java")
                + " " + add.apply(2, 3) + " " + max.apply(9, 4));   // hi 4 5 9
    }
}

    The arrow token is not an operator and has no precedence; it simply separates the parameters from the body. A lambda body may read as an expression only when the SAM returns a value or void and the body is a single expression.

    4. Target Typing: A Lambda Has No Standalone Type

    A lambda has no type by itself. The compiler never infers "a lambda type"; it only checks that the lambda is a compatible implementation of a target type supplied by the surrounding context. Java calls this target typing, and it works in exactly four places:

    1. Assignment — Comparator<String> c = (a, b) -> a.length() - b.length();
    2. Method argument — list.sort((a, b) -> a.compareTo(b));
    3. Return statement — returning a lambda from a method whose return type is a functional interface.
    4. Cast — (Runnable) () -> run();

    Consequences follow directly:

    • var f = x -> x + 1; and Object o = x -> x; do not compile — neither supplies a functional-interface target.
    • The same lambda text can mean different things against different targets, because the target fixes the parameter types and the return type.
    • Parameter types inside the lambda are usually inferred from the target's SAM; they may be written explicitly when inference is not enough (for example, (Person p) -> p.age).

    Interviewer's perspective "What is the type of a lambda?" The honest answer is that a lambda has no denotable type. The runtime object implements the target functional interface, but the expression itself must be typed by context. This is why getClass() on a lambda reveals a synthetic, unnamed class, and why a bare lambda cannot be assigned to var or Object.

    5. Variable Capture and the this Question

    A lambda may read local variables from the enclosing method, but only under a strict rule: the captured local must be effectively final — assigned once and never reassigned. Attempting to capture a variable that is later modified is a compile error, because the lambda may outlive the method call that created that variable.

    int limit = 3;                          // effectively final: never reassigned
Predicate<Integer> small = n -> n < limit;    // legal

int counter = 0;
Predicate<Integer> bad = n -> n < counter;    // legal while counter stays fixed
counter++;                                    // now 'bad' no longer compiles

    Two more points complete the picture:

    1. Instance and static fields are not restricted. Only locals and method parameters must be effectively final; a lambda may freely read and write the enclosing object's fields, because those live on the instance, not the stack frame.
    2. this has no lambda meaning. Inside a lambda, this refers to the enclosing instance — the object that created the lambda — not to the lambda itself. A lambda has no instance of its own. An anonymous class behaves differently: its this is the anonymous object. This single difference is the most common source of confusion when converting between the two.

    Memory aid Capture rule: locals must be frozen (effectively final); fields are fair game; this always means the enclosing object, never the lambda.

    6. Anonymous Class vs Lambda

    The anonymous class is the older tool for the same job; Lecture 19 covered it in depth. The table below contrasts the two for the case they overlap: implementing a functional interface.

    Aspect Anonymous class Lambda
    Syntax new Iface() { public R m(...) { ... } } — full boilerplate (a, b) -> ... — parameters, arrow, body only
    this inside refers to the anonymous instance refers to the enclosing instance
    Applicable to any interface or class (can extend a class, implement many methods) only a functional interface (exactly one abstract method)
    Generated class file one synthetic Outer$1.class per site no per-site class file; invokedynamic-based, materialised on demand
    Captured locals must be effectively final must be effectively final
    Instance state may declare fields; each instance has its own stateless: no fields are possible
    Readability verbose and explicit terse and behaviour-focused
    Choose it when you need state, several methods, or to extend a class you need one behaviour passed as a value

    The decisive limits of a lambda are therefore statelessness and one method. If either constraint is unacceptable, an anonymous class (or a named class) is still the correct tool.

    7. The java.util.function Catalogue

    The JDK ships ready-made functional interfaces so that common shapes of behaviour do not need a custom interface. Runnable and Comparator predate Java 8; the java.util.function family was added with it.

    Interface Abstract method (SAM) Input → Output Purpose
    Supplier<T> T get() none → T supply a value lazily
    Consumer<T> void accept(T) T → none consume a value for its side effect
    Function<T,R> R apply(T) T → R transform one value into another
    BiFunction<T,U,R> R apply(T, U) T, U → R transform two inputs into one result
    Predicate<T> boolean test(T) T → boolean test a value; the basis of filtering
    UnaryOperator<T> T apply(T) T → T transform a value into the same type
    BinaryOperator<T> T apply(T, T) T, T → T combine two same-typed values into one
    Runnable void run() none → none run a task; no result, no checked exception
    Callable<V> V call() throws Exception none → V run a task that returns a value and may throw (forward-ref Lecture 56)

    Reading the family by shape is the efficient way to remember it: supply (get), consume (accept), transform (apply), test (test), combine (operator). The primitive specialisations (IntSupplier, IntPredicate, ToIntFunction and many more) exist only to avoid boxing and follow the same shapes.

    Important Function<T,R> is the general transform; UnaryOperator<T> is the special case where input and output types are identical; BinaryOperator<T> is the two-argument same-type variant. BiFunction<T,U,R> is the general two-argument transform. Choosing the narrowest interface that fits keeps the intent readable.

    8. Comparator: The Canonical Fitting Interface

    Comparator<T> is the perfect illustration of the whole lecture, because it is a functional interface that the course already met through Comparable in Lecture 36. It declares exactly one abstract method:

    int compare(T a, T b);   // negative if a < b, zero if equal, positive if a > b

    Everything else on Comparator is default or static — reversed(), thenComparing(...), comparing(...), nullsFirst(...) — and none of those counts toward the SAM. A comparator supplied as a lambda answers one question: when two elements are compared, which comes first? The sign of the returned int is the whole contract.

    • A negative result means a sorts before b.
    • Zero means the two are equal for this ordering.
    • A positive result means a sorts after b.

    Interviewer's perspective Comparator shows why a functional interface may carry many default methods and still be a lambda target: the SAM count ignores them. It also shows the design intent behind static interface methods (Lecture 24) — factory helpers such as Comparator.comparing(...) live on the interface without polluting implementors.

    9. Comparator Factory Methods

    Since Java 8, Comparator can often be built without writing compare at all. The factory methods below compose an ordering from keys, which is both shorter and less error-prone than hand-written subtraction.

    Factory method Returns Effect
    Comparator.comparing(Function) Comparator<T> orders by a derived key that is itself Comparable
    Comparator.comparingInt(ToIntFunction) Comparator<T> orders by an int key without boxing
    Comparator.comparingLong / Comparator.comparingDouble Comparator<T> primitive-key variants of the above
    Comparator.thenComparing(...) Comparator<T> breaks ties with a secondary comparator or key
    Comparator.reversed() Comparator<T> flips the current ordering
    Comparator.naturalOrder() Comparator<T> the elements' own Comparable order
    Comparator.nullsFirst(cmp) / Comparator.nullsLast(cmp) Comparator<T> wraps another order and places nulls first or last

    Chaining reads left to right: primary key, then tie-breaker, then direction. Comparator.comparingInt(p -> p.age).reversed().thenComparing(p -> p.name) orders by age descending and breaks ties by name ascending.

    Memory aid Factory chain order: key → tie-breaker → direction. Read it aloud as "sort by age, then by name, descending" and the call writes itself.

    10. Code: Sorting People with a Lambda Comparator

    The two-code-file nature of the examples mirrors the repo evidence: Demo.java explores the java.util.function shapes, and Demo2.java is the comparator file.

    // Demo2.java — anonymous class replaced by a lambda Comparator
import java.util.*;

class Person {
    final String name;
    final int age;
    Person(String name, int age) { this.name = name; this.age = age; }
    public String toString() { return name + "(" + age + ")"; }
}

public class Demo2 {
    public static void main(String[] args) {
        List<Person> people = new ArrayList<>(List.of(
                new Person("Ada", 36),
                new Person("Bjarne", 70),
                new Person("Grace", 45)));

        Comparator<Person> byAgeAnon = new Comparator<Person>() {   // old style
            public int compare(Person a, Person b) {
                return Integer.compare(a.age, b.age);
            }
        };
        Comparator<Person> byAgeLambda = (a, b) -> Integer.compare(a.age, b.age);

        people.sort(byAgeLambda);                  // List.sort takes a Comparator
        System.out.println(people);                // [Ada(36), Grace(45), Bjarne(70)]
        people.sort(byAgeAnon.reversed());
        System.out.println(people);                // [Bjarne(70), Grace(45), Ada(36)]

        // the same ordering built from key extractors, no hand-written compare
        Comparator<Person> byAgeDescThenName =
                Comparator.comparingInt((Person p) -> p.age).reversed()
                          .thenComparing(p -> p.name);
        people.sort(byAgeDescThenName);
        System.out.println(people);                // [Bjarne(70), Grace(45), Ada(36)]
    }
}

    Note Integer.compare(a.age, b.age) in preference to a.age - b.age. The subtraction form can overflow and silently produce the wrong sign for extreme values; the named comparison method cannot.

    11. Code: A Consumer in a for-each Loop

    Consumer<T> is the natural fit for Iterable.forEach and for any operation whose result is a side effect rather than a value.

    // Demo.java (continued) — a lambda as a Consumer
import java.util.*;
import java.util.function.Consumer;

public class Demo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>(List.of("Ada", "Grace", "Bjarne"));
        Consumer<String> echo = s -> System.out.println(s);
        names.forEach(echo);                       // forEach takes a Consumer

        Consumer<String> loud = s -> System.out.println(s.toUpperCase());
        names.forEach(loud);                       // ADA, GRACE, BJARNE
    }
}

    forEach accepts a Consumer<? super String>; the lambda satisfies it without naming the interface. The two consumers show that the same loop skeleton can be parameterised by behaviour — the central idea of passing code as data.

    12. Code: A Predicate Filter in a Plain Loop

    Predicate<T> returns a boolean and is the standard shape for selection. Streams (Lecture 39) build directly on it, but the same interface works in an ordinary loop.

    // Demo.java (continued) — a lambda as a Predicate, for-each style
import java.util.*;
import java.util.function.Predicate;

public class Demo {
    public static void main(String[] args) {
        List<String> input = List.of("Ada", "Bo", "Grace", "Ed");
        Predicate<String> longName = s -> s.length() > 2;

        List<String> kept = new ArrayList<>();
        for (String s : input) {
            if (longName.test(s)) {                // Predicate.test returns boolean
                kept.add(s);
            }
        }
        System.out.println(kept);                  // [Ada, Grace]
    }
}

    The loop is explicit because streams have not arrived yet. In Lecture 39 the same predicate becomes input.stream().filter(longName).toList(), which is why understanding Predicate here pays off immediately.

    13. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Capturing a mutable local Compile error: local variables referenced from a lambda must be final or effectively final Assign once, or copy into a fresh local; move mutable state to a field or object
    Forgetting the target type var f = x -> x + 1; and Object o = ... -> ... do not compile Assign to a functional interface, pass as an argument, return, or cast
    Overload ambiguity Two overloads accept compatible functional interfaces; the lambda is ambiguous Add an explicit cast, or use distinct interfaces, or a method reference
    Interface with two abstract methods A lambda cannot target it; compile error Keep exactly one abstract method, or use an anonymous/named class
    Side effects in a lambda Hidden mutation of shared state hurts clarity and breaks parallel assumptions Prefer pure transformations; confine effects to a deliberate Consumer
    Lambda this surprise this inside a lambda is the enclosing instance, not the lambda Remember a lambda has no own instance; use an anonymous class if you need one
    Serialising a lambda Not guaranteed to be Serializable; may throw at runtime Extend the target interface with Serializable deliberately, or use a named class
    Excessively long lambda body Deeply nested, hard-to-read blocks inline in a call Extract a private method and pass a method reference (Lecture 38)

    Important Overload ambiguity (Trap 3 below) is the most instructive failure: the compiler cannot choose between two methods whose parameter types are equally compatible functional interfaces, because the lambda satisfies both equally well. A cast such as (Comparator<String>) (a, b) -> ... supplies the missing target.

    14. Myth vs Reality

    Myth Reality
    "A lambda has its own type, like a class." A lambda has no standalone type; it must be target-typed by a functional-interface context.
    "Any interface can be implemented by a lambda." Only a functional interface (exactly one abstract method) can be a lambda target.
    "this inside a lambda is the lambda." this refers to the enclosing instance; a lambda has no instance of its own.
    "Lambdas can capture and modify any local variable." Captured locals must be effectively final; mutation after capture is a compile error.
    "An anonymous class and a lambda are interchangeable." A lambda is stateless and single-method; an anonymous class may hold fields, implement many methods, or extend a class.

    15. Common Trap Questions

    Trap 1 — The mutated local: "A lambda captures int count, and later count++ runs. Does it compile?" No. The captured local must be effectively final, so any later reassignment makes the capture illegal.

    Trap 2 — The bare lambda: "Is var f = (int x) -> x + 1; valid?" No. var has no target type to infer from; the arrow expression must be assigned to a functional interface (or passed as such an argument).

    Trap 3 — The ambiguous overload: "Two methods run(Runnable) and run(Callable<V>) exist. Will run(() -> System.out.println()) compile?" It depends on the body. A body that returns a value selects Callable; a void body can still be ambiguous, and the compiler rejects the call. An explicit cast resolves it.

    Trap 4 — The extra abstract method: "Can a lambda implement an interface with one abstract method and one default method?" Yes. default methods do not count toward the SAM, so the interface is still functional.

    Trap 5 — The this difference: "Converting an anonymous class that prints this to a lambda — does the output change?" Yes. In the anonymous class this is the anonymous instance; in the lambda it is the enclosing instance, so toString may differ completely.

    Trap 6 — The subtraction comparator: "Is (a, b) -> a.age - b.age a safe comparator?" Not in general. Subtraction can overflow and return the wrong sign; use Integer.compare(a.age, b.age) or Comparator.comparingInt.

    Trap 7 — The serialised lambda: "Can a lambda always be written to a file because the target interface is Serializable?" No. A lambda is serialisable only when the target interface itself extends Serializable; otherwise it is not, and serialising it fails.

    16. Points to Remember

    1. A lambda is behaviour as a value: a parameter list, ->, and an expression or block body.
    2. A functional interface has exactly one abstract method (SAM); @FunctionalInterface verifies it; Object, default and static methods do not count.
    3. The four lambda forms are () -> expr, x -> expr, (x, y) -> expr, and (x, y) -> { ...; return ...; }.
    4. A lambda has no standalone type; it is typed by its context: assignment, method argument, return, or cast.
    5. Captured local variables must be effectively final; instance and static fields are not restricted.
    6. Inside a lambda this means the enclosing instance, unlike an anonymous class where this is the anonymous object.
    7. Lambda vs anonymous class: a lambda is stateless and single-method; an anonymous class may hold state, implement many methods, or extend a class.
    8. java.util.function shapes: Supplier.get, Consumer.accept, Function.apply, BiFunction.apply, Predicate.test, UnaryOperator.apply, BinaryOperator.apply; Runnable.run and Callable.call sit in the same family (Lecture 56).
    9. Comparator is the canonical fitting interface: one abstract compare, many default/static helpers; factories include comparing, comparingInt, thenComparing, reversed, nullsFirst/nullsLast, and naturalOrder.
    10. Prefer Integer.compare (or a factory) over subtraction in a comparator, keep lambdas short, and reach for method references next (Lecture 38).

    17. Likely Interview Questions

    Question Crisp Answer
    What is a lambda expression? A concise, unnamed implementation of a functional interface; it passes behaviour as a value with a parameter list, ->, and a body.
    What is a functional interface? An interface with exactly one abstract method; Object, default and static methods do not count, and lambdas use it as their target type.
    What are the four lambda forms? No parameters () -> e; one inferred parameter x -> e; multiple parameters (x, y) -> e; and a block body (x, y) -> { ...; return r; }.
    What is target typing? A lambda has no standalone type; the compiler uses the surrounding functional-interface context (assignment, argument, return, cast) to type it.
    Why does var f = () -> 1; fail? var provides no functional-interface target, and a lambda has no independent type to infer.
    What is the capture rule? A lambda may capture locals only if they are effectively final; it may freely access instance and static fields.
    What does this mean inside a lambda? The enclosing instance that created the lambda; a lambda has no instance of its own, unlike an anonymous class.
    Lambda or anonymous class? Use a lambda for a stateless, single-method behaviour; use an anonymous class when you need fields, several methods, or to extend a class.
    What does Predicate<T> do? It tests a value and returns a boolean via test(T), the standard shape behind filtering.
    What does Function<T,R> do? It transforms a T into an R via apply(T), the general mapping interface; UnaryOperator<T> is its same-type special case.
    Why is Comparator a functional interface if it has many methods? Its only abstract method is int compare(T, T); reversed, thenComparing, comparing and the rest are default or static, so the SAM rule holds.
    How do you sort by a property? list.sort(Comparator.comparingInt(p -> p.age)) or list.sort((a, b) -> Integer.compare(a.age, b.age)); chain thenComparing for ties.

    18. Final Summary

    lambda forms:  () -> e        x -> e        (x, y) -> e        (x, y) -> { ...; return r; }

target typing:  assignment / argument / return / cast  -->  functional interface (SAM)

capture:  locals effectively final   ·   fields free   ·   this = enclosing instance

java.util.function:  Supplier.get  Consumer.accept  Function.apply  BiFunction.apply
                     Predicate.test  UnaryOperator / BinaryOperator  Runnable.run  Callable.call

Comparator:  int compare(T, T)  -->  (a, b) -> ...
             comparing / comparingInt / thenComparing / reversed / nullsFirst / naturalOrder
    • Lambda → anonymous behaviour with no name; four forms; body is expression or block; -> separates parameters from body.
    • Functional interface → exactly one abstract method; Object and default/static methods are excluded from the count (Lecture 24).
    • Target typing → a lambda needs a context: assignment, argument, return, or cast; bare lambdas do not compile.
    • Capture → locals must be effectively final; fields are accessible; this is the enclosing instance.
    • Lambda vs anonymous class → lambda is stateless and single-method; anonymous class may hold state, have several methods, or extend a class (Lecture 19).
    • java.util.function → supply, consume, transform, test, combine; primitive specialisations avoid boxing.
    • Comparator → the canonical fitting interface; factories turn key extraction and chaining into short, safe orderings.
    • Next → method references and composition deepen the same idea (Lecture 38); streams build on Predicate and Function (Lecture 39).

    Golden rule A lambda is behaviour without a name, and a functional interface is the name that behaviour borrows: supply the target and the lambda becomes an object; forget the target and it becomes a compile error.

    One-line takeaway: a lambda is a stateless, single-method implementation of a functional interface, typed by its context and best demonstrated by a Comparator built from (a, b) -> ....
