    Part 3 · Web Internals & MVC · Lecture 14

    How Java Web Apps Actually Work

    16 sections · interview-oriented · both themes

    Scope evidence: "How Java Web Apps Actually Work | Servlets, Tomcat & WAR Files" (playlist map, verified). The ServletCrudDemo Maven project contains the servlet package (servlet.HelloServlet, servlet.UserServlet), a service.UserService, a model.User, an entry point at in.strikes.Main, plus pom.xml and lecture notes.

    This lecture answers a question most Java developers cannot explain cleanly: how does text arriving on a network port end up as a method call on a Java class? We start from a raw browser request, watch Java open a socket, and then watch the servlet container (Tomcat) take that pain away by handling HTTP and calling our object. By the end, the words Servlet, Tomcat, WAR, provided scope, init(), destroy(), embedded Tomcat, and DispatcherServlet all sit inside one connected mental model.

    1. Why Do We Need Servlets?

    Start with what actually happens when a browser hits an address:

    http://localhost:8080/hello

    The browser does not say "please call HelloServlet.java". A browser has no idea what a Java class, Java method, or Java object is. It only understands HTTP. So it sends text that follows HTTP rules:

    GET /hello HTTP/1.1
Host: localhost:8080

    This is just text. The real question is: who receives it?

    • A Java class does not automatically receive browser requests.
    • Something must be a running server process, sitting on a port, able to receive that request.

    The browser is the client. On the other side there must be a server process that is already alive and listening. Servlets exist to answer the question of how Java code plugs into that server process.

    2. Java Can Listen on a Port, But the Manual Work Is Huge

    Java can do networking through the java.net package. Using ServerSocket, Java can open a port and wait for connections:

    // Java can open a port and wait for a connection
ServerSocket serverSocket = new ServerSocket(8080);

    So technically we can write a Java program that receives browser requests. The problem is that the browser sends HTTP text, and with raw networking we must handle everything ourselves. We would have to manually:

    1. read the raw HTTP text;
    2. parse the URL;
    3. parse headers;
    4. parse query parameters;
    5. parse the request body;
    6. identify GET, POST, PUT, DELETE;
    7. create the response text;
    8. add the status code;
    9. add response headers;
    10. send the response back to the browser;
    11. manage multiple users at the same time;
    12. manage threads;
    13. keep the server running continuously.

    Java can be a server. Building a full web application directly on low-level sockets is difficult, repetitive, and error-prone. This is the first major problem that servlets help solve.

    Important: The language is not the gap. The gap is that HTTP semantics (methods, headers, routing, threading) are not part of Core Java, so every developer would rewrite the same plumbing.

    3. Normal Java Program vs Web Application, and Static vs Dynamic Websites

    In a normal Java program, the entry point is public static void main(String[] args). The program starts, executes code, prints output, and usually finishes. A web application must not start once and stop immediately. It should keep running and wait for HTTP requests from many users.

    Normal Java program          Web application
Start                        Start
Run instructions             Keep running
Finish                       Wait for requests
Exit                         Process every request
                             Send every response

    A normal Java class alone is not enough for that; a web application needs a long-running server environment.

    A second distinction explains why Java logic is needed at all.

    Static website: an HTML file such as <h1>Welcome to my website</h1> is returned as-is for GET /index.html. No Java logic is required. The same request always gives the same pre-written response. Static files: HTML, CSS, JavaScript, images, videos.

    Dynamic website: a request such as GET /user?id=101 produces a response that depends on the id. For id=101 the server may return "Name: Rahul, Email: rahul@test.com"; for id=102 it may return "Name: Priya, Email: priya@test.com". Now the server needs logic: read the id, connect to a database, fetch details, prepare the response, send it back. This is where Java becomes useful, because Java is good at business logic.

    Aspect Static website Dynamic website
    Example request GET /index.html GET /user?id=101
    Response source Pre-written file Generated by server logic
    Same request, same response? Yes, always No, it depends on input/data
    Java logic needed? No Yes (business logic)
    Typical files HTML, CSS, JS, images, videos Servlets/controllers + templates + data

    4. The Main Problem Before Servlets, and What a Servlet Did Conceptually

    Before servlets, every developer building a Java web application had to write a large amount of low-level networking and HTTP handling code manually. The flow looked like this:

    Browser
   |
   v
Raw HTTP request
   |
   v
Java socket code
   |
   v
Manual HTTP parsing
   |
   v
Manual routing
   |
   v
Manual response creation

    This is not practical for every web application. Developers should focus on business logic, not on manually parsing HTTP again and again. So Java needed a standard way where low-level HTTP work is handled by a server/container, and business logic is written by the developer. That standard idea is the Servlet. It solves one central gap: how will the HTTP request enter Java code?

    The servlet introduced a simple idea: instead of every developer manually handling raw HTTP, let a container handle HTTP and call our Java class. The flow became:

    Browser
   |
   v
HTTP Request
   |
   v
Tomcat
   |
   v
HttpServletRequest object
HttpServletResponse object
   |
   v
Our Servlet class

    Tomcat handles the low-level HTTP work. Our servlet handles the application logic. Instead of reading raw HTTP text, we receive ready-made Java objects:

    • HttpServletRequest request gives us the URL, HTTP method, headers, query parameters, request body, and cookies.
    • HttpServletResponse response helps us send data back to the browser.

    Interviewer's perspective: When asked "what problem do servlets solve", do not say "they make web apps". The precise answer is: they define a standard contract so a container owns sockets and HTTP parsing while the developer writes only the Java handling logic.

    5. The Simplest Meaning of a Servlet, and Why It Does Not Listen on a Port

    A Servlet is a Java class used to handle web requests and generate web responses. In practical words, it is a Java class that Tomcat can call when an HTTP request comes.

    // A servlet is just a class that Tomcat calls
public class HelloServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request,
                         HttpServletResponse response) {
        // Logic for a GET request
    }
}

    The browser does not directly call doGet(). Tomcat calls doGet() when a matching GET request comes.

    A common beginner mistake is thinking: "the servlet is listening on port 8080." That is not technically correct. The correct mental model is:

    • Tomcat listens on the port.
    • The servlet lives inside Tomcat.
    • When a matching request comes, Tomcat calls the servlet.
    Port 8080
   |
   v
Tomcat is listening
   |
   v
Request comes: /hello
   |
   v
Tomcat checks URL mapping
   |
   v
Tomcat calls HelloServlet

    So the servlet is not directly connected to the network. Tomcat is the long-running server process. The servlet is a Java object managed by Tomcat.

    Golden rule: Tomcat listens, Tomcat receives the HTTP request, Tomcat converts it into Java-friendly objects, Tomcat calls your servlet, your servlet writes the response, Tomcat sends it back.

    6. What Is Tomcat, What Is a Servlet Container, and Inversion of Control

    Tomcat is a Java-based server that can run Java web applications. More specifically, Tomcat is a Servlet Container. This means Tomcat provides the environment where servlets can live, run, and handle HTTP requests.

    The word "container" is very important. A container means something that creates, manages, and controls objects. In Spring Core we say the Spring Container manages beans. In the servlet world, the Servlet Container manages servlets.

    Tomcat controls:

    1. servlet object creation;
    2. the init() method call;
    3. the service() method call;
    4. doGet() / doPost() / doPut() / doDelete() method calls;
    5. the destroy() method call;
    6. request object creation;
    7. response object creation;
    8. thread management;
    9. URL mapping;
    10. sending the response back to the browser.

    So we do not manually create servlet objects. Tomcat creates and manages them. This is the same idea as Inversion of Control. In normal Java, we write new HelloServlet() and call the method ourselves, so control sits with our code. In a servlet application, Tomcat creates the object and Tomcat calls the method. The control is not with our code; the control is with the container.

    World Object managed by
    Servlet world Tomcat / Servlet Container
    Spring world Spring Container

    The framework calls us, not the other way around - the seed of Spring's entire object model.

    Mnemonic for Tomcat's job, L-M-C-C-S: Listen, Map, Convert, Call, Send.

    7. Tomcat Startup, Per-Request Flow, and When the Servlet Is Created

    When Tomcat starts, it becomes a long-running server process. It does not start, run one method, and stop. It keeps waiting for HTTP requests.

    Tomcat starts
   |
   v
Tomcat opens port 8080
   |
   v
Tomcat waits for HTTP requests
   |
   v
Browser sends request
   |
   v
Tomcat receives request
   |
   v
Tomcat finds matching application
   |
   v
Tomcat finds matching servlet
   |
   v
Tomcat calls servlet method
   |
   v
Servlet prepares response
   |
   v
Tomcat sends response back to browser

    Suppose the request is GET /myapp/hello. Tomcat checks: which application? -> myapp. Which URL? -> /hello. Which servlet? -> HelloServlet. Which method? -> doGet(). Then Tomcat calls something conceptually similar to helloServlet.doGet(request, response);. Tomcat is the bridge between the HTTP world and the Java world. The browser sends HTTP; Tomcat converts that request into Java-friendly objects; our servlet uses those objects.

    The URL itself decomposes neatly:

    Part Meaning
    localhost My own machine
    8080 Port where Tomcat is listening
    /hello Path requested by the browser

    The request first reaches Tomcat. Then Tomcat decides which Java code should handle the request.

    By default, Tomcat creates the servlet object when the first matching request comes. For the first request to /hello: Tomcat creates the HelloServlet object, calls init(), then calls doGet(). After that, the same servlet object can handle future requests. But we can also configure Tomcat to load a servlet during application startup.

    Behavior Meaning
    Default behavior Servlet loads on the first request
    Startup loading Servlet loads when the application starts

    Important: The browser only cares about the HTTP response. It does not care whether the backend is Java, Python, Node.js, PHP, or Go. That is why HTTP is the real contract at the edge.

    8. External Tomcat, WAR Files, and Many Applications

    In traditional Java web development, Tomcat is installed separately. This is called using external Tomcat. The flow is:

    1. Install Tomcat on your machine/server
2. Build the Java web application as a WAR file
3. Put the WAR file inside Tomcat
4. Start Tomcat
5. Tomcat runs the application

    Mental model: the application goes inside Tomcat.

    A WAR file means Web Application Archive: a packaged Java web application. Just as a normal Java project packages as myapp.jar, a traditional Java web application packages as myapp.war. A WAR can contain compiled classes, servlet classes, HTML/CSS/JS, libraries, web.xml, and configuration files. WAR = complete web application package, and external Tomcat knows how to run it.

    External Tomcat can host multiple Java web applications at the same time:

    External Tomcat
+-- app1
|   \-- HelloServlet
+-- app2
|   \-- LoginServlet
\-- app3
    \-- ProductServlet

    Each application can have its own servlets. A request to /app1/hello goes to the servlet inside app1; /app2/login goes to app2. This is another reason Tomcat is called a container; it can contain and manage many web applications.

    To start external Tomcat on Mac/Linux, go inside the Tomcat folder (cd ~/Downloads/apache-tomcat-10.1.x), where you see folders like bin, conf, logs, and webapps. Check the port in conf/server.xml:

    <Connector port="8080" protocol="HTTP/1.1"
           connectionTimeout="20000"
           redirectPort="8443" />

    This means Tomcat will listen on port 8080. On Mac/Linux give permission with chmod +x bin/*.sh. Run in the foreground with ./bin/catalina.sh run; you should see "Server startup in ... milliseconds", and http://localhost:8080 shows the Tomcat welcome page. For background mode use ./bin/startup.sh and ./bin/shutdown.sh (Windows: bin\startup.bat, bin\shutdown.bat). If port 8080 is busy, check lsof -i :8080 and kill the process.

    To deploy a WAR, copy target/servlet-crud.war into the webapps folder. Tomcat extracts servlet-crud.war into webapps/servlet-crud, and http://localhost:8080/servlet-crud/ should show "Servlet CRUD App is running".

    9. Packaging and Parameters: provided Scope and Query Parameters

    In a servlet project we use servlet classes such as HttpServlet, HttpServletRequest, and HttpServletResponse. These classes are needed to compile our code. But at runtime these servlet classes are already provided by Tomcat. External Tomcat has its own lib folder:

    apache-tomcat-10
+-- bin
+-- conf
+-- lib
+-- logs
\-- webapps

    Inside Tomcat's lib, Tomcat already has the servlet-related classes needed to run web applications. So Maven needs the servlet dependency only during compilation. At runtime, Tomcat provides it. That is exactly what provided means.

    <!-- Servlet API: needed to compile, supplied by Tomcat at runtime -->
<dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.0.0</version>
    <scope>provided</scope>
</dependency>

    Simple meaning: I need this dependency while compiling my code, but do not package it inside my final WAR, because the runtime environment will provide it.

    Phase Who provides the Servlet API
    Compile time Maven dependency (compile classpath)
    Runtime Tomcat (lib folder)

    If we remove <scope>provided</scope>, Maven uses the default scope compile, which means Maven may package the Servlet API inside the WAR. But Tomcat already has the Servlet API, so two copies may exist: one inside Tomcat and one inside the application WAR. This can create classloading conflicts or confusing runtime issues. Container APIs like the Servlet API should be provided by the container, not packaged by the application.

    A related small decision: why the first demo uses query parameters instead of a POST body. In the first servlet example, query parameters are easier to use: /users?name=Rahul&email=rahul@test.com. A JSON request body requires extra work: read the body manually, parse JSON manually, add a Jackson or Gson dependency, map JSON to a Java object, and handle invalid JSON. So query parameters keep the focus on the main concept: how Tomcat receives a request and calls our servlet. JSON body handling can come later.

    Important: provided does not mean "not needed". It means "needed to compile, supplied by the environment at runtime". Dropping it does not fail the build; it produces a subtly broken WAR. The query-parameter choice is a teaching choice, not a technical rule.

    10. The Servlet Lifecycle: init(), service(), doGet(), destroy()

    Servlet lifecycle means the complete journey of a servlet object. The basic lifecycle is:

    Servlet object creation
   |
   v
init()
   |
   v
service()
   |
   v
doGet() / doPost() / doPut() / doDelete()
   |
   v
destroy()

    Tomcat controls this lifecycle. We do not manually create or destroy servlet objects.

    init() is called when the servlet object is initialized. By default, Tomcat creates the servlet object on the first matching request, then calls init():

    First GET /lifecycle
Constructor runs
   |
   v
init() runs
   |
   v
service() runs
   |
   v
doGet() runs

    If another request comes, only service() and doGet() run again. The constructor and init() do not run again for every request. init() is used for one-time setup work: load configuration, create expensive resources, initialize helper objects, open a connection pool, prepare a cache.

    service() is called for every request (GET, POST, PUT, DELETE all reach service()). But when we extend HttpServlet we usually do not write all logic inside service(), because HttpServlet already has a service() method that checks the HTTP method and forwards to the correct method: GET -> doGet(), POST -> doPost(), PUT -> doPut(), DELETE -> doDelete(). So the internal flow is service() -> checks HTTP method -> calls the matching doXxx(). In real servlet code we usually override those doXxx() methods and not service(), unless we have a specific reason.

    Method When it runs Typical purpose
    Constructor Once, on object creation Plain object setup
    init() Once, after construction One-time setup (config, pools, caches)
    service() Every request Dispatches to the correct doXxx()
    doGet() Every GET Read/fetch data
    doPost() Every POST Create new data
    doPut() Every PUT Update existing data
    doDelete() Every DELETE Delete data
    destroy() Once, before removal Release resources, flush, stop tasks

    destroy() is called when the servlet is being removed from service. This can happen when Tomcat stops, the application is undeployed, the application is reloaded, or a new WAR replaces the old WAR. Uses of destroy(): release memory-heavy objects, close resources, stop background tasks, flush pending data. destroy() is called once before the servlet is removed. After destroy(), the servlet object becomes eligible for garbage collection.

    To see destroy() output, stop Tomcat (./bin/shutdown.sh on Mac/Linux, shutdown.bat on Windows). When Tomcat stops, it removes the servlet from service and calls destroy().

    The most important lifecycle point: usually Tomcat creates one servlet object and reuses it for multiple requests. So the flow is not "every request -> new servlet object". The better mental model is "one servlet object -> many requests". That is why we must be careful with instance variables inside servlets, especially when multiple users send requests at the same time.

    Mnemonic for the lifecycle: C-I-S-D (Create, Init, Service, Destroy) - created once, initialized once, serviced many times, destroyed once.

    Golden rule: One servlet object serves many requests. Instance fields are shared state across concurrent users; keep per-request data in local variables or in the request object.

    11. Embedded Tomcat vs External Tomcat, and Traditional Servlets vs Spring MVC

    In traditional servlet applications, the application goes inside Tomcat. But in Spring Boot, we usually do not install Tomcat separately. Spring Boot brings Tomcat inside the application through spring-boot-starter-web. When we run SpringApplication.run(MyApp.class, args) inside main(), Spring Boot starts the application and also starts embedded Tomcat internally. So in Spring Boot: Tomcat is inside the application.

    Aspect Traditional Java web app Spring Boot web app
    Tomcat Installed separately (external) Bundled inside the app (embedded)
    Package WAR Usually an executable JAR
    Start Install -> build WAR -> deploy -> start Tomcat Run main()
    Mental model Application is deployed into the server Server starts inside the application
    Steps to run Configure Tomcat, build WAR, deploy, start, debug Run main(), app starts, server starts, API ready

    Spring Boot makes Java web applications easier to run. Without embedded Tomcat: install Tomcat, configure Tomcat, build WAR, deploy WAR, start server, debug deployment issues. With embedded Tomcat: run main(), application starts, server starts, API is ready. Spring Boot did not remove the Servlet Container concept; it simply made it easier to use. Internally, Tomcat is still there.

    Now the second half of the story: how requests are routed. In a traditional servlet application, we may create different servlets for different features: /users -> UserServlet, /products -> ProductServlet, /orders -> OrderServlet. With @WebServlet("/users") on public class UserServlet extends HttpServlet, Tomcat checks the URL and directly calls the matching servlet. This works, but as the application grows we may end up creating many servlets, and each one may handle request reading, response writing, validation, routing, error handling, and business flow. Slowly the code becomes difficult to manage.

    Spring MVC also uses the servlet concept, but instead of asking us to manually create many servlets, Spring MVC gives us one central servlet: DispatcherServlet. The idea is simple: let all incoming requests first come to one central servlet, and then that servlet decides which controller method should handle the request.

    Browser/Postman
   |
   v
Tomcat
   |
   v
DispatcherServlet
   |
   v
Controller
   |
   v
Service
   |
   v
Response
    Aspect Traditional servlet style Spring MVC style
    Servlets One servlet per URL/feature One central DispatcherServlet
    Routing Tomcat maps URL to each servlet DispatcherServlet maps to controller methods
    Controller code doGet/doPost per servlet @GetMapping/@PostMapping methods
    Data binding Manual getParameter and casts @RequestParam, @RequestBody
    JSON Manual conversion needed Automatic JSON conversion
    Structure Boilerplate grows with app size Cleaner Controller-Service-Repository separation 
    // Spring MVC: Tomcat calls DispatcherServlet, which calls this method
@RestController
public class UserController {
    @GetMapping("/users")
    public String getUsers() {
        return "All users";
    }
}

    A Spring MVC controller is not directly called by the browser. The browser does not know about UserController, getUsers(), or @GetMapping. The browser only sends GET /users. The actual flow is: browser sends HTTP request -> Tomcat receives request -> Tomcat calls DispatcherServlet -> DispatcherServlet checks Spring MVC mappings -> the correct controller method is called -> the response goes back.

    Why Spring MVC is powerful: with traditional servlets we manually read parameters, call the service, prepare the response, convert objects to JSON, and handle errors. Spring MVC gives us @Controller/@RestController, @GetMapping/@PostMapping, @RequestParam, @RequestBody, @ResponseBody, automatic JSON conversion, and a cleaner Controller-Service-Repository separation. Internally the foundation is still servlet: Spring MVC built a better framework on top of servlet.

    Important: The browser still sends HTTP, Tomcat still receives it, and a servlet is still the Java entry point. Spring MVC only replaces "many custom servlets" with "one DispatcherServlet plus annotated methods".

    12. Myth vs Reality

    Myth Reality
    "The servlet listens on port 8080" Tomcat listens on the port; the servlet lives inside Tomcat and is called by it
    "A new servlet object is created for every request" One servlet object is created and reused for many requests
    "The browser calls doGet()" Tomcat calls doGet() when a matching GET request arrives
    "We should override service() for each method" HttpServlet.service() dispatches to doGet/doPost; override those instead
    "WAR and JAR are the same" WAR is a complete web application package (classes, web.xml, web files, libs); JAR is a general archive
    "provided scope means the dependency is unnecessary" It is needed at compile time; the container supplies it at runtime
    "Spring Boot removed Tomcat" Spring Boot embeds Tomcat; the servlet container is still there
    "Spring MVC stopped using servlets" Spring MVC is built on servlets and uses DispatcherServlet

    13. Common Trap Questions

    Trap 1 - "A servlet is listening on port 8080." Verdict: False. Tomcat owns the port and the network. The servlet is a Java object managed by Tomcat; it is not connected to the network directly.

    Trap 2 - "Tomcat creates a new servlet object for every request." Verdict: False. By default Tomcat creates the object on the first matching request and reuses one object for many requests. This is why instance variables are dangerous under concurrency.

    Trap 3 - "You should override service() to handle GET and POST." Verdict: False. HttpServlet.service() already inspects the HTTP method and forwards to doGet()/doPost()/doPut()/doDelete(). Override those, not service().

    Trap 4 - "A WAR is just a renamed JAR." Verdict: Misleading. A WAR is a Web Application Archive: a complete web app package that can contain servlet classes, web.xml, HTML/CSS/JS, and libraries, and external Tomcat knows how to deploy it.

    Trap 5 - "provided means the servlet API is not on the compile classpath." Verdict: False. provided keeps the dependency for compilation but excludes it from the packaged WAR, because Tomcat's lib supplies it at runtime.

    Trap 6 - "Spring Boot does not use Tomcat anymore." Verdict: False. Spring Boot embeds Tomcat via spring-boot-starter-web. The container concept is unchanged; only the setup changed.

    Trap 7 - "If two copies of the Servlet API end up in the WAR and Tomcat, nothing happens." Verdict: False. Two copies can cause classloading conflicts and confusing runtime issues, which is exactly why provided scope exists.

    14. Points to Remember

    1. A browser understands only HTTP; it never calls Java classes or methods directly.
    2. Java can open a port with ServerSocket, but manual HTTP parsing, routing, threading, and response building are huge and repetitive.
    3. A normal program starts and exits; a web application must keep running and serve many requests.
    4. Static sites return pre-written files; dynamic sites generate a response from logic and data.
    5. A servlet is a Java class that Tomcat calls to handle a web request and generate a response.
    6. Tomcat is a servlet container: it owns ports, parsing, request/response objects, threads, URL mapping, and the servlet lifecycle.
    7. Control is inverted: the container creates the object and calls the method, not our code.
    8. External Tomcat runs deployed WAR files and can host many applications; embedded Tomcat runs inside a Spring Boot app started by main().
    9. The servlet API uses provided scope: needed to compile, supplied by Tomcat at runtime.
    10. One servlet object handles many requests, so shared instance state is unsafe across concurrent users.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a servlet? A Java class that handles web requests and generates web responses, managed and called by a servlet container.
    What problem do servlets solve? They let a container handle low-level HTTP so developers write only business logic in Java.
    Does a servlet listen on a port? No. Tomcat listens on the port; the servlet lives inside Tomcat and is invoked by it.
    What is a servlet container? A component that creates, manages, and controls servlet objects, request/response objects, threads, URL mapping, and the lifecycle.
    What is the servlet lifecycle? Object creation -> init() -> service() -> doGet()/doPost()/doPut()/doDelete() -> destroy().
    init() vs service()? init() runs once for one-time setup; service() runs for every request and dispatches to the doXxx() method.
    When is destroy() called? Once, when the servlet is removed from service: Tomcat stops, undeploy, reload, or WAR replacement.
    How many servlet objects exist? Usually one object per servlet, reused for many requests. Be careful with instance variables.
    What is a WAR file? Web Application Archive: a packaged Java web application containing classes, web.xml, web files, and libraries.
    Why is the servlet API scope provided? It is needed at compile time but supplied by Tomcat at runtime, so it must not be packaged in the WAR.
    External vs embedded Tomcat? External: app deployed into Tomcat. Embedded: Tomcat runs inside the Spring Boot app started by main().
    How does Spring MVC relate to servlets? It is built on servlets, using one central DispatcherServlet that routes requests to controller methods.

    16. Final Summary

    Browser (client)
   |
   v

   |
   v

   |
   v
Tomcat parses HTTP, builds HttpServletRequest / HttpServletResponse
   |

    • Browser speaks HTTP; Java writes business logic; Tomcat connects the two worlds.
    • The servlet is the Java class Tomcat calls; it never listens on the port itself.
    • A servlet is created once, initialized once, serviced many times, and destroyed once.
    • External Tomcat runs WAR files; embedded Tomcat runs inside a Spring Boot app.
    • The servlet API is provided: Maven compiles against it, Tomcat supplies it at runtime.
    • Spring MVC keeps the servlet foundation and adds one DispatcherServlet plus annotated controllers.

    One-line takeaway: Tomcat owns the port and the HTTP work, the servlet owns only the business logic, and Spring MVC layers a single DispatcherServlet and annotated controllers on top of that same servlet foundation.
