    Part 7 · Concurrency · Lecture 54

    Lock-Free Concurrency in Java | AtomicVariables & CAS Explained

    27 sections · interview-oriented · both themes

    Scope evidence: "Lock-Free Concurrency in Java | AtomicVariables & CAS Explained" plus the lecture's own repo notes (count++ read-modify-write, lost update, CAS), playlist map, verified. Repo evidence: 2 Demo files.

    Concurrency problems often begin with a single shared variable, and the plain count++ is the smallest possible example of everything that can go wrong. This lecture shows why count++ is not one atomic step, how two threads can lose an update even though both incremented, and how the lock-free alternative works from the ground up. It then covers compare-and-set (CAS) as a single atomic hardware instruction, the java.util.concurrent.atomic classes, the AtomicInteger API, functional update methods, AtomicBoolean state transitions, and AtomicReference identity semantics. The governing idea is that atomics make one variable's transition indivisible, but they never make a sequence of separate operations atomic.

    1. The Broken Counter: count++ Is a Three-Step Sequence

    A counter looks trivially safe:

    // Demo.java — the broken counter: count++ is not one step
class Counter {
    private int count = 0;
    public void increment() { count++; }
    public int getCount() { return count; }
}

    The method appears to be one operation, but count++ is conceptually a read-modify-write sequence:

    int current = count;   // read
int updated = current + 1; // modify
count = updated;       // write

    If two threads execute these steps at the same time, one update can overwrite the other. This is a race condition caused by a non-atomic compound operation.

    Important count++ is a compound operation. The JLS-level guarantee is not "one indivisible increment"; it is three separate steps, and any of them can be interleaved with another thread.

    2. Atomicity: All-or-Nothing under the Java Memory Model

    An operation is atomic when other threads cannot observe or interfere with a partially completed version of that operation.

    atomic operation = all-or-nothing operation

    From the perspective of other threads, the operation appears to happen as one indivisible step. This does not necessarily mean that only one machine instruction is involved. It means the operation has a single visible effect under the Java Memory Model.

    Term Meaning
    Atomic operation Appears indivisible to other threads
    Non-atomic operation Other threads can observe an intermediate state
    Race condition The result depends on uncontrolled thread timing

    3. The Lost-Update Interleaving, Step by Step

    Start with count = 10 and two threads that both increment:

    Initial count = 10
Thread A reads 10
Thread B reads 10
Thread A calculates 11
Thread B calculates 11
Thread B writes 11
Thread A writes 11

    Two increments occurred, but the final value is only 11. Thread A's write overwrote Thread B's completed increment, and Thread B's increment is lost. The bug is non-deterministic: the interleaving determines the result.

    Memory aid Lost update = "both read the same old value, both wrote the same new value". One of the two updates silently disappears.

    4. The Traditional Solution: synchronized

    The counter can be protected using synchronized:

    class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
    public synchronized int getCount() { return count; }
}

    A lock ensures that only one thread executes the protected critical section at a time.

    Thread A acquires lock
Thread B waits
Thread A updates count
Thread A releases lock
Thread B continues

    Locks are necessary when several related operations or variables must be protected as one critical section. For small updates to a single value, Java also provides atomic classes.

    5. What "Lock-Free" Means

    A lock-free algorithm does not require threads to acquire a traditional mutual-exclusion lock before making progress. Threads usually:

    1. read the current state
    2. calculate a desired new state
    3. attempt an atomic update
    4. retry if another thread changed the state first
    Read
  |
  v
Calculate
  |
  v
Compare and update
  +-- Success → finish
  \-- Failure → read latest state and retry

    Lock-free does not mean:

    • every thread completes immediately
    • lock-free code is always faster
    • threads never wait in any form

    It means that system-wide progress is possible without one thread owning a traditional lock that every other thread must acquire.

    6. Progress Guarantees: Blocking, Lock-Free, Wait-Free, Obstruction-Free

    The word "non-blocking" covers several different guarantees.

    Guarantee Promise Consequence
    Blocking A thread may wait for another thread that owns a lock Thread B cannot continue until A releases the lock
    Lock-Free At least one competing thread is guaranteed to make progress An individual thread may repeatedly lose the race and retry
    Wait-Free Every participating thread completes in a bounded number of steps Stronger than lock-free, harder to design
    Obstruction-Free A thread makes progress when it eventually runs without interference Weakest of the non-blocking guarantees

    For most application-level Java code, the practical distinction is between traditional lock-based coordination and atomic lock-free updates.

    7. Compare-and-Set (CAS): One Atomic Hardware Instruction

    CAS is the primitive that makes lock-free updates possible. compareAndSet(expected, update) replaces the value only when its current value still equals expected, and it returns a boolean telling the caller whether the swap happened:

    boolean changed = count.compareAndSet(10, 20);

    Conceptually:

    if (current == expected) {
    current = update;
    return true;
}
return false;

    CAS is a single atomic hardware instruction, so no thread can observe a half-completed compare-and-swap. That indivisibility is what removes the lost update.

    Aspect Detail
    Signature boolean compareAndSet(T expected, T update)
    Success Current value equaled expected; value replaced; returns true
    Failure Current value differed; nothing changed; returns false
    Atomicity Performed as one hardware-level atomic instruction
    Typical response to failure Re-read the latest value and retry

    An atomic incrementAndGet() is built on exactly this primitive: internally it runs a CAS retry loop so that callers never see the retry.

    8. The java.util.concurrent.atomic Package

    Java provides atomic classes for safely updating individual values. These classes supply:

    • atomic reads and writes
    • atomic read-modify-write operations
    • visibility guarantees
    • compare-and-set operations
    • functional update methods

    Important An atomic class protects atomic operations performed through that class. It does not automatically make a sequence of separate operations atomic.

    9. AtomicInteger: The Thread-Safe Counter

    AtomicInteger stores an integer that can be updated atomically by multiple threads.

    // Demo.java — the atomic counter: every increment is atomic
import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); }
    public int getCount() { return count.get(); }
}

public class Demo {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable job = () -> {
            for (int i = 0; i < 1_000; i++) {
                counter.increment();
            }
        };
        Thread firstThread = new Thread(job);
        Thread secondThread = new Thread(job);
        firstThread.start();
        secondThread.start();
        firstThread.join();
        secondThread.join();
        System.out.println(counter.getCount()); // 2000
    }
}

    Each increment is performed atomically, so one thread cannot overwrite another thread's completed increment; the output is 2000.

    10. The AtomicInteger API

    Method Effect Rough equivalent
    get() Returns the current value value
    set(int newValue) Sets a new value value = newValue
    incrementAndGet() Increments, returns the updated value ++value
    getAndIncrement() Returns the old value, then increments value++
    decrementAndGet() Decrements, returns the updated value --value
    getAndDecrement() Returns the old value, then decrements value--
    addAndGet(int delta) Adds, returns the updated result value += delta
    getAndAdd(int delta) Returns the old value, then adds value += delta (old returned)
    getAndSet(int newValue) Atomically replaces and returns the previous value swap
    compareAndSet(int expected, int update) Updates only if the current value equals expected; returns boolean conditional swap

    11. Functional Update Methods and the Retry-Safety Rule

    Atomic classes can calculate a new value with a function:

    int updated = count.updateAndGet(current -> current * 2);
int previous = count.getAndUpdate(current -> current * 2);
int combined = count.accumulateAndGet(5, Integer::sum);
    • updateAndGet() atomically applies the function and returns the updated value.
    • getAndUpdate() returns the old value.
    • accumulateAndGet() combines the current value and the supplied argument atomically.

    Important The function supplied to an atomic update method may execute more than once when contention causes retries. Therefore it should be side-effect free, deterministic, inexpensive, and never perform work such as sending a notification — that side effect could fire several times even though the final update happens once.

    12. AtomicLong

    AtomicLong provides the same style of operations for long values.

    import java.util.concurrent.atomic.AtomicLong;

class IdGenerator {
    private final AtomicLong sequence = new AtomicLong(0);
    public long nextId() { return sequence.incrementAndGet(); }
}

    Possible uses include sequence numbers, locally generated identifiers, total bytes processed, statistics, and counters.

    Important An atomic increment only guarantees uniqueness within that particular AtomicLong instance and process. It is not automatically a distributed ID generator.

    13. AtomicBoolean

    AtomicBoolean stores a boolean value with atomic operations.

    import java.util.concurrent.atomic.AtomicBoolean;

class Service {
    private final AtomicBoolean running = new AtomicBoolean(true);
    public void stop() { running.set(false); }
    public void runTask() {
        while (running.get()) {
            performWork();
        }
    }
    private void performWork() { /* Work */ }
}

    For a simple stop flag, a volatile boolean can also provide the required visibility. The main reason to use AtomicBoolean is when an atomic state transition is needed.

    14. Atomic State Transitions: The Test-and-Set Pattern

    Suppose only one thread should initialise a resource:

    class Initializer {
    private final AtomicBoolean initialized = new AtomicBoolean(false);
    public boolean initialize() {
        if (!initialized.compareAndSet(false, true)) {
            return false;
        }
        performInitialization();
        return true;
    }
    private void performInitialization() {
        System.out.println("Initialized once");
    }
}

    Several threads may call initialize(), but only one can successfully change false → true. This pattern is sometimes called test-and-set.

    Trap If initialization can fail, changing the flag before the work completes may leave the object marked as initialized incorrectly. A more complete state model may be required: NOT_STARTED → INITIALIZING → INITIALIZED or FAILED. An AtomicReference<State> is better when more than two states exist.

    15. AtomicReference: Atomic Replacement of a Reference

    AtomicReference<V> performs atomic operations on an object reference. It protects replacement of the reference; it does not automatically make the referenced object's internal mutable fields thread-safe.

    AtomicReference<List<String>> reference =
        new AtomicReference<>(new ArrayList<>());

    Atomically replacing the list reference is safe. Mutating the same ArrayList from several threads is still unsafe.

    // Demo2.java — atomic reference replacement (swap)
import java.util.concurrent.atomic.AtomicReference;

public class Demo2 {
    public static void main(String[] args) {
        AtomicReference<String> reference = new AtomicReference<>("Hello");
        reference.set("World");
        String old = reference.getAndSet("Java");            // returns "World"
        boolean changed = reference.compareAndSet("Java", "Concurrency");
        System.out.println(old);                 // World
        System.out.println(changed);             // true
        System.out.println(reference.get());     // Concurrency
    }
}

    Basic operations: get(), set(), getAndSet(), and compareAndSet().

    16. AtomicReference in Action: Seat Booking

    The non-atomic version contains a check-then-act race:

    class SeatBooking {
    private String seat = "EMPTY";
    public boolean bookSeat(String person) {
        if (seat.equals("EMPTY")) {
            seat = person;
            return true;
        }
        return false;
    }
}

    Two threads can both observe the seat as empty, both write, and both return true, yet only one name remains. The atomic version collapses check-and-act into one CAS:

    import java.util.concurrent.atomic.AtomicReference;

class SeatBooking {
    private final AtomicReference<String> seat = new AtomicReference<>("EMPTY");
    public boolean bookSeat(String person) {
        return seat.compareAndSet("EMPTY", person);
    }
    public String getBookedBy() { return seat.get(); }
}

    Thread A: CAS(EMPTY → Aditya) → succeeds
Thread B: CAS(EMPTY → Rahul)  → fails

    Only one transition can observe and replace the expected value atomically.

    17. Reference Equality in compareAndSet

    For AtomicReference, compareAndSet() compares object references using identity semantics:

    currentReference == expectedReference

    It does not call currentReference.equals(expectedReference).

    record User(String name) {}

AtomicReference<User> reference =
        new AtomicReference<>(new User("Aditya"));
User expected = new User("Aditya");
boolean changed = reference.compareAndSet(expected, new User("Rohit"));

    Even though the two User objects are logically equal, they are different object references, so the CAS fails. The expected value should normally be the exact reference previously obtained using get().

    18. synchronized vs AtomicInteger vs LongAdder

    Both lock-based and lock-free approaches can be correct; the choice depends on what is being protected.

    Aspect synchronized AtomicInteger LongAdder
    Mechanism Intrinsic monitor lock CAS on one variable Striped cells summed on demand
    Best for Multi-variable invariants, compound sections One independent value, moderate contention Very high-throughput counters under contention
    Blocking Yes; waiting threads block No; internal retry loop No; contention spread across cells
    Deadlock risk Possible None None
    Read cost Requires the lock Single volatile-like read sum() aggregates all cells
    Read accuracy Exact when held Exact sum() is not atomic; a weak snapshot
    Scope Any number of fields or steps One variable One contended counter

    Golden rule Use an atomic variable when one independent value is updated and the change is a single atomic transition. Use a lock when several fields must change together or multiple steps form one invariant.

    19. Atomic Variables Are Not Magic

    This code is unsafe:

    if (count.get() > 0) {
    count.decrementAndGet();
}

    The logic contains two independent operations:

    1. Check whether count is positive.
    2. Decrement count.
    Initial count = 1
Thread A checks: 1 > 0
Thread B checks: 1 > 0
Thread A decrements to 0
Thread B decrements to -1

    The individual methods are atomic, but the compound rule is not. A CAS retry loop, a lock, or a single functional update such as updateAndGet that encodes the whole rule is required.

    20. When Atomics Are Not Enough, and the volatile Connection

    Use an atomic variable when:

    • one independent value is being updated
    • the operation can be expressed as one atomic transition
    • lock-free progress is useful
    • the critical operation is very small

    Use a lock (or a concurrent collection) when:

    • several fields must change together
    • multiple steps must be protected as one invariant
    • a condition must be awaited
    • a collection of actions must be isolated
    • the operation is easier to understand as a critical section

    Correctness is more important than avoiding locks. Atomic classes also provide memory-visibility guarantees equivalent to volatile for the variable they hold: a successful write is visible to a subsequent read, and a CAS both reads and writes with the same visibility discipline. That is why AtomicBoolean can replace a stop flag, and why a plain volatile field is enough when only visibility (not atomic transition) is required.

    Important If an invariant spans more than one field, no single atomic variable can protect it. Reach for synchronized, a Lock, or a java.util.concurrent collection that already maintains the invariant.

    21. CAS Failure Causes and the ABA Preview

    A CAS can fail for several distinct reasons, and the correct response differs.

    Cause What happened Response
    Competing update Another thread changed the value first Re-read and retry (internally in atomics, or in your loop)
    Wrong expected value expected no longer equals the current value Pass the exact value returned by get()
    Side-effecting function The update function ran again on retry Keep the function pure, deterministic, and cheap
    Identity mismatch For AtomicReference, expected is equal by equals() but not the same reference Use the exact reference obtained from get()
    ABA The value changed and later returned to its original appearance Use a version stamp (detailed in Lecture 55)

    The ABA problem is previewed here: a CAS succeeds on a stale assumption because the value happened to return to the same state. AtomicStampedReference<V> and AtomicMarkableReference<V> exist precisely to attach a version or marker to the reference (Lecture 55).

    22. The Atomic Classes Catalogue

    Class Purpose
    AtomicInteger Atomic integer operations
    AtomicLong Atomic long operations
    AtomicBoolean Atomic boolean state transitions
    AtomicReference<V> Atomic object-reference replacement
    AtomicIntegerArray Atomic operations on integer array elements
    AtomicLongArray Atomic operations on long array elements
    AtomicReferenceArray<E> Atomic reference operations per array index
    AtomicStampedReference<V> Reference plus integer version
    AtomicMarkableReference<V> Reference plus boolean marker
    LongAdder High-throughput counter under contention

    23. Myth vs Reality

    Myth Reality
    "count++ is a single atomic operation." It is read-modify-write; two threads can interleave and lose an update.
    "Atomic classes make compound logic atomic." Each method is atomic; a check-then-act across two method calls is still a race.
    "Lock-free means every thread finishes immediately." It means system-wide progress without lock ownership; an individual thread may retry.
    "AtomicReference makes the object it points to thread-safe." It protects replacing the reference, not mutation of the referenced object's fields.
    "compareAndSet compares with equals()." For AtomicReference it compares identity with ==.
    "An AtomicLong increment is a distributed ID generator." It guarantees uniqueness only within one instance and process.

    24. Common Trap Questions

    Trap 1 — "Is count++ thread-safe because it is one line?" No. It expands to read, modify, write; concurrent threads can lose updates.

    Trap 2 — "Is the function passed to updateAndGet guaranteed to run once?" No. Under contention it may run more than once, so it must be side-effect free and deterministic.

    Trap 3 — "Will compareAndSet(expected, update) succeed for a logically equal but different object?" For AtomicReference, no. It compares identity; pass the exact reference from get().

    Trap 4 — "Is if (count.get() > 0) count.decrementAndGet(); safe?" No. Each method is atomic, but the check and the decrement are separate operations; two threads can both pass the check.

    Trap 5 — "Does one atomic variable make my whole sequence of operations atomic?" No. Atomicity applies only to operations performed through that variable.

    Trap 6 — "Is LongAdder.sum() an exact atomic snapshot?" No. sum() is not atomic; under concurrent updates it returns a weak snapshot that can lag.

    Trap 7 — "Do I need AtomicBoolean for a stop flag?" Often a volatile boolean suffices for visibility; use AtomicBoolean when an atomic state transition (test-and-set) is required.

    Trap 8 — "If a CAS fails, is my data corrupted?" No. A failed CAS changes nothing; the correct response is to re-read and retry.

    25. Points to Remember

    1. count++ is a three-step read-modify-write, so concurrent increments can lose updates.
    2. An atomic operation is all-or-nothing from the perspective of other threads under the Java Memory Model.
    3. synchronized guarantees mutual exclusion; locks are required when several variables form one critical section.
    4. Lock-free means system-wide progress without a traditional lock, not that threads never wait or that it is always faster.
    5. CAS, exposed as compareAndSet(expected, update), is a single atomic hardware instruction that returns boolean.
    6. Atomic classes internally use a CAS retry loop, so caller code does not have to write one.
    7. The java.util.concurrent.atomic package provides atomic reads, writes, read-modify-write operations, visibility, and compare-and-set.
    8. Functional update methods may run their function more than once; keep the function pure, deterministic, and inexpensive.
    9. AtomicReference protects the reference, not the object; its CAS uses identity (==), not equals().
    10. Atomics fit a single independent value; multi-field invariants need locks or concurrent collections, and the ABA problem requires a stamped reference (Lecture 55).

    26. Likely Interview Questions

    Question Crisp Answer
    Why is count++ not thread-safe? It is a read-modify-write sequence; two threads can read the same value and one update is lost.
    What is a race condition? A result that depends on uncontrolled thread timing, typically from a non-atomic compound operation.
    What does atomic mean? The operation is all-or-nothing with a single visible effect to other threads under the Java Memory Model.
    What is CAS? Compare-and-set: replace the value only if it still equals the expected value, as one atomic hardware instruction, returning a boolean.
    What is a CAS retry loop? Read the value, compute the update, attempt CAS; on failure re-read the latest value and retry.
    What is lock-free progress? At least one competing thread is guaranteed to make progress; individual threads may retry.
    Difference between lock-free and wait-free? Lock-free guarantees system-wide progress; wait-free guarantees every thread finishes in a bounded number of steps.
    Name the common atomic classes. AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference, the atomic arrays, and LongAdder, among others.
    What is the difference between incrementAndGet and getAndIncrement? incrementAndGet returns the new value (++value); getAndIncrement returns the old value (value++).
    Why must atomic update functions be side-effect free? Retries under contention can run the function more than once, so side effects could occur multiple times.
    What does AtomicReference protect? Replacement of the reference atomically; it does not make the referenced object's mutable fields thread-safe.
    How does AtomicReference.compareAndSet compare values? By reference identity (==), not by equals(), so pass the exact reference obtained from get().
    When should you prefer synchronized over atomics? When several fields must change together, a condition must be awaited, or multiple steps form one invariant.

    27. Final Summary

    count++  →  read → modify → write   →  lost update under interleaving
     |
     +-- synchronized        (mutual exclusion; blocking; multi-field invariants)
     \-- AtomicInteger       (CAS; lock-free; single independent value)
                              |
                              v
            compareAndSet(expected, update)
              +-- true  → swap done
              \-- false → re-read latest value and retry   (retry loop inside the atomic)

single value, one atomic transition  →  atomic classes
several fields / compound invariant  →  synchronized, Lock, concurrent collections
stale-value CAS (ABA)                →  AtomicStampedReference (Lecture 55)
    • Broken counter → count++ is read-modify-write; concurrent increments lose updates (final 11, not 12).
    • Traditional fix → synchronized protects a critical section but blocks other threads.
    • Lock-free fix → atomic classes use CAS, a single hardware instruction that compares and swaps atomically.
    • AtomicInteger API → incrementAndGet, getAndIncrement, addAndGet, getAndSet, compareAndSet, and functional updateAndGet/getAndUpdate/accumulateAndGet.
    • Reference semantics → AtomicReference replaces the reference atomically and compares by identity; ABA needs a stamped reference.
    • Scope → atomics give visibility and one-transition atomicity; multi-field invariants still need locks or concurrent collections.

    Golden rule An atomic variable makes one transition indivisible; it never makes a sequence of separate operations atomic. If several fields or steps must change together, use a lock.

    One-line takeaway: count++ loses updates because it is a read-modify-write; CAS turns the update into one atomic compare-and-swap, and Java's atomic classes wrap that retry loop for a single variable at a time.
