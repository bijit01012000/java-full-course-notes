    Part 3 · OOP Deep Dive · Lecture 22

    Most Important Class in Java — Object Class (equals, hashCode, toString)

    15 sections · interview-oriented · both themes

    Scope evidence: lecture title "Most Important Class in Java | Object Class (equals, hashCode, toString)" (playlist map, verified). Repo evidence: 2 Demo files (Demo.java, Demo2.java).

    Every class you ever write silently inherits from one class, and that class decides how your objects behave when they are printed, compared and stored in hash-based collections. This lecture examines java.lang.Object — the root of the entire Java type hierarchy — and the three methods that cause the most real production bugs: toString(), equals(Object) and hashCode(). It separates identity from logical equality, states the contracts that both methods must obey, and shows exactly how breaking those contracts corrupts a HashMap. The object-copying and pass-by-value background comes from Lecture 14, wrapper caching is a preview of Lecture 18, and the hash-collection internals that consume hashCode are Lecture 33.

    1. java.lang.Object: The Root of Every Class

    java.lang.Object is the ultimate superclass of every reference type in Java. If a class declares no extends clause, the compiler inserts extends Object implicitly, so the hierarchy is a single tree whose root is Object.

    1. Every class, array and enum inherits it. String, int[], your own Money, and even an anonymous class all have Object at the top of their ancestry.
    2. A variable of type Object can reference any object. Object o = new Money(...) or Object o = "text" compiles, because every reference is a subtype of Object.
    3. It provides the methods every object already has. Printing, comparing and hashing work even before you write a single method, because the behaviour is inherited.

    The subtree of Object includes every other class:

    Object (root)
  ├── String, Integer, Money, Point, ...   (classes)
  ├── int[], String[]                       (arrays — also objects)
  └── enum constants, records, anonymous classes

    Memory aid — the family name: nothing is an orphan in Java. Whatever you write, Object is already on the birth certificate, so its methods are inherited whether you like it or not.

    2. The Complete Object Method Inventory

    Object ships eleven instance methods, and they fall into four groups:

    Method Purpose Typical handling
    toString() Textual representation of the object Override for readable output
    equals(Object) Logical equality test Override for value semantics
    hashCode() Integer hash for hash-based collections Override whenever equals is overridden
    getClass() Runtime class of the object (a Class token) final — cannot be overridden
    clone() Shallow copy (Lecture 14) protected; needs Cloneable; often avoided
    finalize() Pre-GC cleanup hook Deprecated — do not override; use try-with-resources or cleaners
    wait(), wait(long), wait(long, int) Suspend a thread until notified Monitor methods — Lecture 52
    notify(), notifyAll() Wake waiting threads Monitor methods — Lecture 52

    The monitor group deserves a note: wait/notify/notifyAll live on Object, not on Thread, because every object can act as a lock (its monitor). Synchronization and inter-thread signalling were designed to work on any object, which is why the methods are universal — the intrinsic lock of any instance can be waited on. Threading itself is forwarded to Lecture 52.

    Interviewer's perspective "Name the methods of Object." The expected set is toString, equals, hashCode, getClass, clone, finalize, and the five monitor methods wait/notify/notifyAll. Mentioning that wait lives on Object because every object is a monitor is the detail that separates recall from understanding.

    3. toString(): Default ClassName@hexHash and Why to Override It

    The default implementation returns the class name, an @, and the unsigned hexadecimal of the object's identity hash:

    Money@1b6d3586

    That string is useless for debugging: it tells you nothing about the state. The convention is to override toString() so it returns a concise, human-readable summary of the important fields — it is the single most useful override in day-to-day coding.

    // Demo.java — a useful toString for readable output
class Money {
    final int amount;             // stored in the smallest unit (paise)
    final String currency;
    Money(int amount, String currency) { this.amount = amount; this.currency = currency; }

    @Override public String toString() {
        return currency + " " + (amount / 100.0);   // state, not identity
    }
}

public class Demo {
    public static void main(String[] args) {
        Money m = new Money(1099, "INR");
        System.out.println(m);                 // INR 10.99
        System.out.println("Paid: " + m);      // concatenation calls toString() too
    }
}

    Two behaviours are worth pinning down:

    1. println calls toString() on a reference. System.out.println(m) is equivalent to System.out.println(String.valueOf(m)), which dispatches to m.toString().
    2. String concatenation calls toString() implicitly. In "Paid: " + m, the compiler inserts a StringBuilder/invokedynamic concatenation that calls m.toString() — so a bad toString corrupts every log line and concatenated message.

    Rules for a good override: include the identifying fields, never include the identity hash, avoid printing enormous object graphs, and do not leak secrets. Overriding toString does not affect equals/hashCode — the three methods are independent contracts.

    Important println, logging frameworks and string concatenation all invoke toString(). If you do not override it, every log line shows ClassName@1b6d3586 and you lose the ability to debug by inspection.

    4. equals(Object): Identity by Default, and the Contract When Overridden

    Object.equals compares identity: return (this == obj);. Two distinct objects are never equal by default, even when their fields match. Compare Box a = new Box(10); Box b = new Box(10); — a.equals(b) is false until you override the method.

    The equals contract, stated by the JDK, has five clauses that any override must satisfy for the objects that are compared:

    1. Reflexive — x.equals(x) must be true.
    2. Symmetric — x.equals(y) is true if and only if y.equals(x) is true.
    3. Transitive — if x.equals(y) and y.equals(z), then x.equals(z).
    4. Consistent — repeated calls return the same result as long as no relevant state changes.
    5. Null-safe — x.equals(null) must return false (never throw; the default handles this via the == check).

    The canonical step-by-step override mirrors the clauses:

    1. if (this == obj) return true; — the identity fast path (also handles x.equals(x)).
    2. if (obj == null || getClass() != obj.getClass()) return false; — the null and type guard.
    3. MyType other = (MyType) obj; — the cast, now provably safe.
    4. Compare the significant fields (primitives with ==, references with Objects.equals, or Arrays.equals for arrays) and return the conjunction.

    Memory aid — the four beats: "same? null/type? cast; fields." Identity, guard, cast, compare — in that order.

    5. hashCode(): The Contract and the equals/hashCode Partnership

    hashCode() returns an int used to choose a bucket in hash-based collections (HashMap, HashSet, LinkedHashMap, ConcurrentHashMap). Its contract is short and unforgiving:

    1. Consistent — the integer must stay stable while the object is in a collection, as long as the fields used in equals do not change.
    2. Equal objects must have equal hash codes — if x.equals(y) then x.hashCode() == y.hashCode().
    3. Unequal objects may collide — unequal objects are allowed to share a hash code (that is why hash tables store chains/trees in a bucket). The reverse of clause 2 is therefore not required.
    4. equals overridden ⟹ hashCode must be overridden. If you override equals but keep the identity hash, clause 2 breaks immediately: two logically equal objects get different hash codes and land in different buckets.

    The consequence is concrete: a HashMap finds a key by (a) computing hashCode to locate the bucket, then (b) walking the bucket and comparing with equals. If step (a) takes you to the wrong bucket, equals is never even consulted — so the key is effectively lost.

    Important The two methods are a married pair. equals decides same bucket contents; hashCode decides which bucket. Break either and every hash-based lookup, insert and remove can silently misbehave (Lecture 33 has the internals).

    6. == vs equals()

    == compares values; equals compares meaning. For references, == asks "same object?" while equals asks "equivalent object?" — and only the override makes the second question interesting.

    Aspect == equals(Object)
    Operand types Primitives or references References (an object argument)
    Semantic for primitives Value comparison Not applicable — no equals on primitives
    Semantic for references Identity — same address Logical equality — depends on the override
    Default reference behaviour Identity Identity (Object.equals is this == obj)
    Overridable No — an operator Yes — a method
    null behaviour x == null is safe x.equals(null) must be false; x itself may NPE
    Inheritance Final behaviour May be overridden by subclasses

    Two caveats turn this table into interview material:

    • String literals are interned. "abc" == "abc" is usually true because the compiler pools identical literals, but new String("abc") == new String("abc") is false. Always compare strings with equals — the interning details are Lecture 25.
    • Boxed Integer caching hides the bug. Integer.valueOf(100) == Integer.valueOf(100) is true because of the -128..127 cache, while the same code with 1000 is false. This makes == look correct in tests and fail in production — full treatment in Lecture 18.

    Interviewer's perspective "== or equals for strings?" Always equals. == happened to work in your test because the literals were interned or the boxed values were cache hits; it compares identity, not text.

    7. Overriding equals Correctly: getClass() vs instanceof

    Step 2 of the override has two defensible forms, and choosing wrongly breaks symmetry:

    Form Accepts Symmetry risk Use when
    getClass() != obj.getClass() Exact class only Safe — the two objects must be the same runtime type Value classes that must not equal their subclasses
    obj instanceof MyType The class and every subclass Broken when a subclass adds state: super.equals(sub) may be true while sub.equals(super) is false Rarely — only for classes that admit no meaningful subclass state (e.g. some collection contracts)

    The subclass-proxy problem: if Point uses instanceof Point and a subclass ColouredPoint adds a colour field, then point.equals(colouredPoint) can be true while colouredPoint.equals(point) is false, violating symmetry. The robust default for ordinary value classes is therefore getClass(), which restricts equality to exact runtime types. instanceof is chosen deliberately only when equal-by-contract across subtypes is intended.

    Objects.equals(a, b) is the null-safe helper for comparing two reference fields; Objects.hash(field1, field2, ...) is the convenience builder for hashCode. Both avoid hand-written null checks and are the modern idiom.

    Important "instanceof inside equals" is not automatically wrong, but it is the standard cause of the symmetry violation with inheritance. Prefer getClass() unless you can state precisely why subclasses should compare equal.

    8. A Correct equals and hashCode for Money

    The reference implementation for a value class: identity fast path, null/type guard, cast, field comparison — plus a matching hash over the same fields.

    // Demo.java — the correct equals/hashCode pair for a value class
import java.util.Objects;

class Money {
    final int amount;             // paise
    final String currency;
    Money(int amount, String currency) { this.amount = amount; this.currency = currency; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;                          // 1. identity
        if (o == null || getClass() != o.getClass())         // 2. null + exact type
            return false;
        Money other = (Money) o;                             // 3. cast
        return amount == other.amount                        // 4. compare fields
            && Objects.equals(currency, other.currency);
    }

    @Override public int hashCode() {
        return Objects.hash(amount, currency);               // same fields as equals
    }

    @Override public String toString() {
        return currency + " " + (amount / 100.0);
    }
}

    The three overrides are coherent: the same fields feed equals and hashCode, and toString reports the state. Objects.hash(...) builds a well-distributed code by combining the field hashes (a multiplier, commonly 31, is applied between fields). If equals used amount only but hashCode used amount and currency, the pair would be inconsistent and equal objects could still land in different buckets.

    Memory aid — the triangle: equals, hashCode and (optionally) toString should agree about which fields define the object. Whoever owns the identity fields owns all three.

    9. What Breaks When equals Is Overridden Without hashCode

    Overriding equals alone is the most common contract violation in Java. The map's lookup path computes a hash first; with the identity hash still in place, a logically equal key hashes elsewhere.

    // Demo2.java — overridden equals, inherited identity hashCode: broken lookup
import java.util.*;

class Key {
    final int id;
    Key(int id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof Key && ((Key) o).id == id;   // no hashCode override
    }
}

public class Demo2 {
    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();
        map.put(new Key(1), "one");
        System.out.println(map.get(new Key(1)));   // null — hashed to a different bucket
        System.out.println(map.size());            // 1 — the entry exists, but is unreachable
    }
}

    The entry is physically present but unreachable: get, remove and containsKey all fail because they look in a bucket the new equal object never hashes to. Insert the same logical key twice and the map holds two entries that equals says are the same — duplicate entries in sets, inflated maps, and memory leaks that look like phantom bugs.

    equals hashCode Contract HashMap / HashSet result
    Not overridden Not overridden Legal — identity semantics Consistent identity-based storage
    Overridden Not overridden Violated Lost keys, duplicate entries, failed get/remove
    Overridden Overridden over same fields Correct Reliable logical-key lookup
    Overridden Overridden over different fields Violated Equal objects can hash apart — lost keys
    Not overridden Overridden Legal but pointless Identity equality with a custom hash; collisions, no correctness gain
    Overridden Overridden over mutable fields Broken after mutation Key hashes differently once fields change — key lost in place

    The last row deserves emphasis: if a key's hashed fields are mutated after insertion, its hash changes while its bucket does not, and the entry becomes unreachable. Keep hash-relevant fields immutable, or never mutate an object that is a live map key.

    Important HashMap needs both methods to agree. hashCode picks the bucket; equals confirms the key inside it. Overriding only equals is like changing a house's name while leaving its address wrong — the mail never arrives.

    10. Pitfalls and Best Practices

    Pitfall What goes wrong Fix
    equals without hashCode Equal objects hash apart; map/set lookups fail Always override both over the same fields
    Mutable fields in hashCode Key's hash changes after insertion; entry lost Use immutable identity fields; freeze keys
    HashSet/HashMap corruption Duplicate logical entries; unreachable keys Obey the pair contract; prefer immutable keys
    == on String or boxed types Identity/cache comparison, not value Use equals, or compare primitives/Objects.equals
    instanceof breaking symmetry super.equals(sub) true while sub.equals(super) false Use getClass(), or design inheritance deliberately
    NPE in equals Calling field.equals(other.field) with a null field Use Objects.equals(a, b)
    equals not null-safe x.equals(null) throws instead of returning false Guard null first; use the four-step template
    Inconsistent toString Logs show ClassName@hash or omit key state Override to print the identifying fields
    Calling equals across unrelated types Returns false or misbehaves Guard with getClass()/type check before comparison

    The unifying rule: one set of fields defines the object, and equals, hashCode and toString all reflect it. Any drift between them is a latent bug.

    11. Myth vs Reality

    Myth Reality
    "Every object already has a useful toString" The default is ClassName@hexHash; it is only identity, not state.
    "equals compares field values by default" Object.equals is identity (==); field comparison requires an override.
    "Overriding equals is enough" You must override hashCode too, or hash-based collections break.
    "== works for all comparisons, including strings" == is identity; String/boxed comparisons must use equals despite interning and caching.
    "instanceof in equals is always fine" It commonly violates symmetry once subclasses add state; prefer getClass().
    "x.equals(null) may throw" The contract requires it to return false; only x itself being null may NPE.
    "Records need hand-written equals/hashCode/toString" Records (Java 16+) auto-generate all three from their components.

    12. Common Trap Questions

    Trap 1 — "I overrode equals; why does map.get(new Key(1)) return null?" hashCode was not overridden, so the new equal key hashes to a different bucket and the entry is never found. Override both, over the same fields.

    Trap 2 — "x.equals(null) — what happens?" For a well-formed override it returns false, as the contract requires. It throws NullPointerException only if the implementation dereferences null or if you call it on a null x (i.e. null.equals(x)).

    Trap 3 — "Does a.equals(b) imply a.hashCode() == b.hashCode()?" Yes — equal objects must have equal hash codes. The converse is false: equal hash codes do not imply equality (collisions are legal).

    Trap 4 — "What does the default toString print?" ClassName@hexHash, where the hex is the identity hash — for example Money@1b6d3586. It conveys no field state.

    Trap 5 — "Can I use == for strings if the test passes?" No. == on String compares references; it passes only due to literal interning (Lecture 25) or the Integer cache (Lecture 18) and fails for runtime-built values.

    Trap 6 — "Why is wait() on Object and not on Thread?" Because every object owns a monitor and can serve as a lock; wait/notify are monitor operations, so they belong to Object (Lecture 52).

    Trap 7 — "If two objects have the same hashCode, are they equal?" Not necessarily. A collision is permitted; equality is still decided by equals inside the bucket.

    13. Points to Remember

    1. java.lang.Object is the root of every class; an omitted extends is implicitly extends Object.
    2. Object's methods: toString, equals, hashCode, getClass, clone, finalize, and the monitor methods wait/notify/notifyAll.
    3. Every object is a monitor, which is why the thread-signalling methods live on Object (Lecture 52).
    4. Default toString is ClassName@hexHash; override it to print identifying state, because println and concatenation both call it.
    5. Default equals is identity (this == obj); override it for value semantics.
    6. The equals contract: reflexive, symmetric, transitive, consistent, and x.equals(null) == false.
    7. The override template is four beats: identity check, null/type guard, cast, compare fields.
    8. hashCode contract: consistent; equal objects must have equal codes; unequal objects may collide.
    9. Override equals ⟹ override hashCode, always over the same fields.
    10. HashMap/HashSet locate a bucket by hashCode and confirm by equals; a broken hash loses keys and duplicates entries (Lecture 33).
    11. getClass() keeps equals symmetric for value classes; instanceof invites the subclass-proxy problem.
    12. Mutating a key's hashed fields after insertion makes the entry unreachable — keep hash-relevant fields immutable.
    13. == compares identity/value; equals compares logical meaning; String interning (Lecture 25) and Integer caching (Lecture 18) make == deceptively correct.
    14. Objects.equals and Objects.hash are the null-safe, modern helpers.
    15. Records (Java 16+) auto-generate equals, hashCode and toString from their components.

    14. Likely Interview Questions

    Question Crisp Answer
    Which methods does Object define? toString, equals, hashCode, getClass, clone, finalize, and wait/notify/notifyAll.
    What does the default toString return? ClassName@hexHash, built from the identity hash — no state.
    Why override toString? To print meaningful field state; println, logging and concatenation all call it.
    What does the default equals do? Compares identity with ==; two distinct objects are never equal, even with equal fields.
    What is the equals contract? Reflexive, symmetric, transitive, consistent, and x.equals(null) is false.
    What is the hashCode contract? Consistent; equal objects must share a hash code; unequal objects may collide.
    Why override hashCode when overriding equals? Equal objects must hash equally, or hash-based collections lose the key.
    How do HashMap and hashCode cooperate? hashCode selects the bucket; equals identifies the key within it (Lecture 33).
    getClass() or instanceof in equals? getClass() for exact-type value classes; instanceof risks symmetry violations with subclasses.
    == vs equals for strings and boxed types? == is identity — deceptively correct due to interning/caching; use equals (Lectures 25, 18).
    Why is wait() declared on Object? Every object is a monitor and can be a lock, so the signalling methods are universal (Lecture 52).
    How do records change this? Records (Java 16+) generate equals, hashCode and toString from their components automatically.

    15. Final Summary

    Object (root of all classes)
   toString()  ->  default: ClassName@hexHash      override -> readable state
   equals()    ->  default: this == obj (identity)  override -> logical equality
   hashCode()  ->  default: identity hash           override -> hash of equals fields

contract:  equals overridden  =>  hashCode MUST be overridden (same fields)
HashMap path:  key --hashCode--> bucket --equals--> entry
               broken hashCode  ->  wrong bucket  ->  key lost / duplicated
==  ->  identity (same object)          equals ->  logical equivalence (override)
    • Object → the universal superclass; every class, array and enum inherits its methods implicitly.
    • Methods → toString, equals, hashCode, getClass, clone, deprecated finalize, and monitor wait/notify/notifyAll.
    • toString → default is ClassName@hexHash; override with identifying state; called implicitly by printing and concatenation.
    • equals → default is identity; override with identity check, null/type guard, cast, field comparison; obey reflexive/symmetric/transitive/consistent/null-false.
    • hashCode → consistent, equal objects share codes, collisions allowed; the inseparable partner of equals.
    • getClass() vs instanceof → exact type keeps symmetry; instanceof breaks it when subclasses add state.
    • == vs equals → identity vs meaning; String interning and Integer caching make == deceptively correct.
    • Pitfalls → equals without hashCode, mutable hash fields, == on references, broken symmetry, NPE.
    • Modern → records (Java 16+) auto-generate all three methods.

    Golden rule If you override equals, you must override hashCode over the same fields — otherwise every HashMap and HashSet in your program silently lies.

    One-line takeaway: Object gives every class identity, printing and hashing for free, but the moment you define logical equality with equals you owe hashCode the same fields, or hash-based collections will lose your keys.
