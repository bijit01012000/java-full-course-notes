    Part 4 · Strings, Generics & Collections · Lecture 30

    Iterable Interface in Java | Why Iterator Exists? | For-Each Loop

    16 sections · interview-oriented · both themes

    Scope evidence: "Iterable Interface in Java | Why Iterator Exists? | For-Each Loop" (playlist map, verified). Repo evidence: 3 Demo files. Demo.java traverses collections with an Iterator, Demo2.java implements a custom Iterable, Demo3.java triggers ConcurrentModificationException.

    Every container in Java stores its data differently — an ArrayList is backed by a growable array, a LinkedList by linked nodes, a HashSet by hash buckets — yet all of them can be walked with the same three-call pattern. That uniformity exists because of two small interfaces: Iterable<T>, which promises a container can be traversed, and Iterator<T>, the cursor that actually performs the walk. This lecture explains why the naive index loop breaks down, how the compiler rewrites the for-each loop into Iterator calls, why the only safe removal during iteration is Iterator.remove(), and how ConcurrentModificationException is detected.

    1. The Traversal Problem and Why Iterator Exists

    The obvious way to walk a collection is an index loop: for (int i = 0; i < list.size(); i++) { System.out.println(list.get(i)); }.

    This works only for List, and it fails in three ways:

    1. Not every collection is index-based. Set, Queue and Map expose no get(i) at all — there is no integer index into a hash bucket or a tree node.
    2. Even List is not always efficient. ArrayList.get(i) is O(1), but LinkedList.get(i) must walk from the head each time, turning the loop into O(n^2).
    3. It couples the caller to the internals. The caller must know whether the container is array-backed, node-backed or bucket-backed; changing new ArrayList<>() to new LinkedList<>() silently degrades the loop.

    The fix is to move the walking logic into the container itself and expose only a small cursor. The container says "I know how to advance through my own data; if you want to visit my elements one at a time, ask me for a cursor". That cursor is an Iterator, and the promise that a container can hand one out is Iterable. This is the Iterator design pattern: traversal is separated from storage, so the caller never touches the internal structure.

    Memory aid — the tour guide: Iterable is the museum that offers a guided tour; Iterator is the guide who knows the corridors. Visitors never wander the storage rooms themselves.

    2. Iterable<T> — The Root Interface That Enables For-Each

    java.lang.Iterable<T> is the root of the collection hierarchy. It declares one abstract method, iterator(), which returns a cursor over the elements:

    public interface Iterable<T> {
    Iterator<T> iterator();                          // the only abstract method
    default void forEach(Consumer<? super T> action) // Java 8
    default Spliterator<T> spliterator()             // Java 8
}
    • The abstract method iterator() is the whole contract: any class that can be walked must supply a cursor.
    • The two default methods arrived in Java 8. forEach takes a lambda (Lecture 37) and spliterator supports parallel streams (Lecture 39); neither is required to understand the for-each loop.
    • The hierarchy is Iterable ⊃ Collection ⊃ List, Set, Queue. Because every collection is Iterable, every collection can be used in a for-each loop.
    • Map is the notable exception: it does not extend Iterable, because a map is key-value pairs rather than a sequence of single elements. Its views (entrySet(), keySet(), values()) do implement Iterable, so the map is still traversable through them.

    Interviewer's perspective "What single method makes for-each possible?" It is iterator() on Iterable. A class is foreach-able if and only if it is an array or implements Iterable; there is no other route. Mentioning that Map is not Iterable but its views are is the detail that shows real understanding.

    3. Iterator<T> — The Cursor: hasNext(), next(), remove()

    java.util.Iterator<E> is the cursor itself. It exposes three methods:

    Method Signature Behaviour
    hasNext() boolean hasNext() Returns true if another element remains.
    next() E next() Returns the next element and advances the cursor. Throws NoSuchElementException past the end.
    remove() default void remove() Removes the element last returned by next(). Optional; the default throws UnsupportedOperationException.

    The protocol is strict and order-dependent:

    1. Always call hasNext() before next() — the loop condition does exactly this.
    2. next() both returns the current element and moves forward; it never returns the same element twice.
    3. remove() may be called at most once per next(), and only after a next(). Calling it before any next(), or twice in a row, throws IllegalStateException.

    Important remove() is a default method, so an implementation may legitimately refuse it by throwing UnsupportedOperationException. Read-only views and immutable collections do exactly that. The two methods every iterator must implement are hasNext() and next().

    4. Traversing a Collection with an Iterator

    The canonical traversal loops on hasNext() and reads with next():

    // Demo.java — the same cursor code works for any collection type
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(10, 20, 30, 40, 50));

        Iterator<Integer> it = list.iterator();
        while (it.hasNext()) {
            int value = it.next();
            System.out.println(value);
        }
    }
}

    The important property is what did not change: replacing new ArrayList<>() with new LinkedList<>() leaves the traversal untouched. The container decides internally how next() advances — index increment for an array list, pointer follow for a linked list, bucket-by-bucket for a hash set, in-order for a tree. The caller sees none of it.

    Calling list.iterator() again returns a brand-new cursor positioned before the first element. This is why the same collection can be traversed repeatedly, and why two nested loops can each hold their own independent cursor.

    5. Iterable vs Iterator

    The two names sound alike but play opposite roles: Iterable is the factory that produces cursors, and Iterator is the cursor itself.

    Aspect Iterable<T> Iterator<E>
    Role A container that can be traversed The cursor that performs traversal
    Package java.lang java.util
    Key methods iterator() (plus forEach, spliterator) hasNext(), next(), remove()
    Implemented by Collection and therefore List, Set, Queue Each collection's private iterator class
    Number of abstract methods One Two (hasNext, next); remove is default
    Holds cursor state No Yes — position is stored in the iterator
    Re-iterable Yes — each iterator() call is fresh No — it is one-shot and exhausted at the end
    Required by for-each Yes — the object being looped must be Iterable No — it is an implementation detail of for-each
    Relationship Produces an Iterator Is produced by an Iterable

    Reading the table: you loop over an Iterable (the collection), and the compiler obtains an Iterator (the cursor) on your behalf. An Iterator is exhausted once it reaches the end; an Iterable can mint a new one on demand.

    6. The For-Each Loop Is Syntactic Sugar

    The enhanced for loop is not a new kind of loop. The compiler rewrites it into an Iterator loop:

    // what you write
for (int x : list) {
    System.out.println(x);
}

// what the compiler produces (equivalent logic, hidden iterator)
for (Iterator<Integer> it = list.iterator(); it.hasNext(); ) {
    int x = it.next();
    System.out.println(x);
}

    Because the rewrite begins with list.iterator(), the loop expression must be an array or an Iterable. Anything else fails to compile with for-each not applicable to expression type. A Map cannot be looped directly for the same reason; iterate map.entrySet(), map.keySet() or map.values() instead.

    Two practical consequences follow from the hidden iterator:

    1. No index is available. If the loop body needs the position (i), for-each cannot supply it; use an index loop.
    2. No remove() is exposed. The cursor is hidden, so a structural change must go through the overloaded methods examined next.

    Memory aid — the sugar coating: for-each is a thin coating over the Iterator loop. Remove the coating and the verbose cursor code is exactly what the JVM executes.

    7. Removing the Wrong Way: ConcurrentModificationException

    Modifying a collection directly while iterating it is the classic bug:

    // Demo3.java — WRONG: direct removal during iteration throws ConcurrentModificationException
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
for (Integer x : list) {
    if (x == 3) {
        list.remove(x);      // direct structural modification
    }
}

// CORRECT: let the iterator perform the removal, so both counters stay in step
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    if (it.next() == 3) {
        it.remove();         // safe: updates modCount and expectedModCount together
    }
}

    The exception is thrown even though only one thread is involved. The mechanism is a modification counter:

    1. Every structural change (add or remove that changes the size) increments an internal field, modCount.
    2. When an iterator is created, it copies the current modCount into its own expectedModCount.
    3. On each next(), the iterator checks modCount == expectedModCount. A mismatch means the collection changed behind the iterator's back, so it fails fast by throwing ConcurrentModificationException.

    The fix is the second half of the snippet above: let the iterator perform the removal, so it can update both counters in step.

    An equivalent modern alternative is the collection-side list.removeIf(x -> x == 3), which performs the same coordinated removal internally.

    Important The name is misleading: ConcurrentModificationException does not require two threads. It only means the collection was modified while an iterator was in flight — almost always by the same thread. It is a bug detector, not a synchronization guarantee.

    8. Fail-Fast vs Fail-Safe Iterators

    Collections differ in how they react to modification during iteration. Fail-fast iterators detect the change and throw; fail-safe iterators iterate over a snapshot and never throw.

    Aspect Fail-Fast Fail-Safe
    Examples ArrayList, LinkedList, HashMap, HashSet CopyOnWriteArrayList, CopyOnWriteArraySet, ConcurrentHashMap
    Detection mechanism modCount vs expectedModCount check Iterates a snapshot or a concurrent structure
    On structural modification Throws ConcurrentModificationException No exception — iteration continues over the old view
    Memory and cost No copy; cheap Snapshot copy or concurrent traversal; more expensive
    Visibility of changes Not applicable (it aborts) Weakly consistent; may not show changes made after the snapshot
    Guarantee Best-effort detection, not thread safety Safe under concurrency, but possibly stale

    Reading the table: fail-fast collections are the everyday ones and are safe only when a single thread owns the collection. Fail-safe collections are the concurrent ones; they trade memory and freshness for the ability to iterate while others modify. The internals of HashMap are the subject of Lecture 33, and the concurrent collections appear in Lecture 56.

    Memory aid — check-and-shout vs copy-and-continue: fail-fast checks a counter and shouts; fail-safe copies the data and keeps going.

    9. Iterator.remove(), ListIterator, and Iterating a Map

    Three refinements complete the picture:

    1. Iterator.remove() removes the element most recently returned by next(). It is the only safe structural modification allowed through a fail-fast iterator, and it may be called once per next().
    2. ListIterator is a richer cursor available only from List. In addition to hasNext/next/remove, it offers hasPrevious() and previous() for backward movement, add(E) and set(E) for insertion and replacement, and nextIndex()/previousIndex(). This is why bidirectional walking and in-place addition belong to List and not to Iterator.
    3. Iterating a Map. A Map is not Iterable, but its three views are. Iterate entries directly with for-each over map.entrySet(), reading each e.getKey() and e.getValue().

    Iterating entrySet() supplies both key and value in one pass. Using keySet() and then calling map.get(key) inside the loop performs a second lookup per entry, and values() discards the keys entirely.

    Interviewer's perspective "How do you iterate a HashMap and why?" Answer: through entrySet(), because each Map.Entry carries both the key and the value, avoiding the extra lookup that keySet() plus get() would require. Adding that HashMap iteration order is unspecified — unlike LinkedHashMap or TreeMap — is the sentence that reveals production experience.

    10. Implementing a Custom Iterable

    Any class can become foreach-able by implementing Iterable and returning a cursor from iterator(). The following range type walks from start (inclusive) to end (exclusive):

    // Demo2.java — a custom container that participates in for-each
import java.util.*;

class Range implements Iterable<Integer> {
    private final int start, end;

    Range(int start, int end) {
        this.start = start;
        this.end = end;
    }

    @Override
    public Iterator<Integer> iterator() {
        return new Iterator<Integer>() {
            private int current = start;

            @Override
            public boolean hasNext() {
                return current < end;
            }

            @Override
            public Integer next() {
                if (!hasNext()) {
                    throw new NoSuchElementException();
                }
                return current++;
            }
        };
    }
}

public class Demo2 {
    public static void main(String[] args) {
        for (int n : new Range(1, 6)) {
            System.out.print(n + " ");        // prints 1 2 3 4 5
        }
    }
}

    The cursor state (current) lives in the anonymous iterator, not in the Range object. That single design decision is the entire reason Iterable exists: because each iterator() call creates a fresh cursor, nested loops and repeated traversal work without interfering. If the position were a field on Range itself, the inner loop of a nested pair would corrupt the outer loop's position — the exact failure that motivated separating storage from traversal in Section 1.

    11. Common Pitfalls and Errors

    Symptom Cause Fix
    NoSuchElementException next() called when hasNext() is false Guard every next() with the hasNext() loop condition.
    IllegalStateException remove() before the first next(), or twice after one next() Call next() first, then remove() once per element.
    ConcurrentModificationException list.remove(...) or add(...) through the collection during iteration Use iterator.remove() or removeIf(...).
    for-each not applicable to expression type Looping a non-Iterable, non-array object such as a Map Loop entrySet()/keySet()/values().
    Wrong element type / compile error Iterator generic type does not match the collection Align the generic parameter, e.g. Iterator<Integer>.
    Unexpected ConcurrentModificationException in nested loops One iterator reused by both loops Call collection.iterator() for each loop.

    12. Myth vs Reality

    Myth Reality
    "You must use an index to iterate a collection." Set and Queue have no index at all; Iterator walks any collection uniformly.
    "For-each is a faster loop." For-each is compiled into the same hasNext()/next() calls; it is sugar, not speed.
    "ConcurrentModificationException means two threads." It is usually one thread modifying a collection while iterating it.
    "An Iterator is a copy of the collection." It is a cursor into the live collection; only fail-safe iterators work over a snapshot.
    "Calling iterator() twice gives the same cursor." Every call returns a new, independent cursor positioned at the start.

    13. Common Trap Questions

    Trap 1 — Does Iterable or Iterator enable the for-each loop? Iterable. The compiler calls iterator() on the object being looped, so the object itself must be Iterable (or an array); Iterator is only what comes back.

    Trap 2 — Can you remove an element inside a for-each? Not safely. For-each hides its iterator, so any direct collection.remove(...) throws ConcurrentModificationException. Use an explicit Iterator with remove(), or removeIf(...).

    Trap 3 — Must an iterator implement remove()? No. It is a default method; the base version throws UnsupportedOperationException, and read-only iterators rely on that.

    Trap 4 — Does HashMap implement Iterable? No. A Map is not a Collection and is not Iterable; its entrySet(), keySet() and values() views are.

    Trap 5 — Is ConcurrentModificationException proof of a threading bug? No. It means the collection changed during iteration, which happens in single-threaded code most of the time.

    Trap 6 — Does next() return the current element without moving? No. next() returns the element and advances; calling it twice yields two different elements.

    Trap 7 — Do two iterators over one list interfere with each other? No. Each is a separate cursor with its own position, which is exactly what makes nested iteration possible.

    14. Points to Remember

    1. Iterable<T> declares one abstract method, iterator(); a class is foreach-able if it is an array or implements Iterable.
    2. Iterator<E> is the cursor and exposes hasNext(), next() and remove().
    3. Collection extends Iterable, so List, Set and Queue are all foreach-able; Map is not, but its views are.
    4. Iterator exists to traverse any container uniformly, without the caller knowing its internal structure.
    5. Each iterator() call returns a fresh, independent cursor — the reason nested loops and re-iteration work.
    6. For-each is compiler sugar: for (T x : c) { ... } becomes an iterator() loop with hasNext() and next().
    7. Never modify a fail-fast collection through the collection while iterating; use Iterator.remove().
    8. ConcurrentModificationException is detected by comparing modCount with the iterator's expectedModCount.
    9. Fail-safe iterators such as CopyOnWriteArrayList and ConcurrentHashMap iterate a snapshot and do not throw.
    10. ListIterator adds bidirectional movement plus add/set, and is available only from List.

    15. Likely Interview Questions

    Question Crisp Answer
    What is Iterable? The root interface of the collection hierarchy that declares iterator(); implementing it makes a class usable in a for-each loop.
    What is Iterator? The cursor interface with hasNext(), next() and remove() that traverses a collection element by element.
    Difference between Iterable and Iterator? Iterable is the container that can be traversed and produces cursors; Iterator is the one-shot cursor that performs the traversal.
    Why does Iterator exist? To traverse any collection uniformly without exposing its internal structure, coupling iteration to an interface instead of a data structure.
    How does the for-each loop work internally? The compiler rewrites it into an Iterator loop using iterator(), hasNext() and next().
    Why can't you use for-each on a Map? A Map does not implement Iterable; iterate entrySet(), keySet() or values() instead.
    Why does list.remove() inside a for-each throw? Direct modification changes modCount, while the hidden iterator still expects the old value, so the next next() throws ConcurrentModificationException.
    What is the only safe structural removal during iteration? Iterator.remove(), because it updates modCount and expectedModCount together; removeIf is the modern shorthand.
    What is fail-fast vs fail-safe? Fail-fast iterators detect modification and throw; fail-safe iterators traverse a snapshot and do not throw.
    How does an iterator detect modification? It stores expectedModCount at creation and compares it with the collection's modCount on each next().
    What does ListIterator add? Backward traversal (hasPrevious/previous), insertion (add) and replacement (set); only List provides it.
    What happens if next() is called past the end? It throws NoSuchElementException; always check hasNext() first.

    16. Final Summary

    Collection --iterator()--> Iterator cursor
    while (it.hasNext()) { E x = it.next(); ... }
    for (E x : collection)   --compiler-->   the same hasNext()/next() loop
    collection.remove(x) during iteration -->  ConcurrentModificationException  (fail-fast)
    it.remove()                            -->  coordinated, safe removal
    • Iterable<T> → one method, iterator(); the contract that enables for-each
    • Iterator<T> → the cursor: hasNext(), next(), remove()
    • For-each → syntactic sugar over iterator(), hasNext(), next()
    • Iterator exists → uniform traversal plus independent cursors, decoupled from storage
    • Safe removal → Iterator.remove() or removeIf(...); never the collection directly
    • Fail-fast → modCount check (ArrayList, HashMap); fail-safe → snapshot (CopyOnWriteArrayList, ConcurrentHashMap)

    Golden rule Loop over the Iterable, let the compiler obtain the Iterator, and perform any structural change through Iterator.remove() — the collection itself must stay untouched until the loop ends.

    One-line takeaway: Iterable promises that a container can be traversed, Iterator does the traversing, and the for-each loop is merely the compiler's sugar over those two interfaces.
