    Java Functions Deep Dive | Recursion | Method Overloading

    21 sections · interview-oriented · both themes

    Scope evidence: lecture title "Java Functions Deep Dive | Recursion | Method Overloading" (playlist map, verified). Repo evidence: the lecture-11 folder contains four code files (Demo.java, Demo2.java, Demo3.java, Demo4.java). The cached lecture PDF is image-only and is ignored per project rules.

    A method is the smallest reusable unit of behaviour in Java, and almost every design question later in the course — inheritance, polymorphism, interfaces, lambdas — is a question about how methods are declared, chosen and dispatched. This lecture takes the humble method apart: its anatomy, the difference between a parameter and an argument, the method signature, method overloading (compile-time polymorphism), and recursion with its base case, call stack and failure mode. It then closes the loop with scope, varargs and the pitfall catalogue that interviewers reuse every season.

    1. What a Method Is, and Why Java Is Built Around Them

    A method is a named block of statements that performs one task, optionally accepts inputs (parameters), and optionally produces a result (a return value). Methods are the unit of behaviour: a class with fields but no methods is a data shell, while a class's real contract is the set of methods it exposes.

    Three properties define a method:

    1. Named — the name is the handle callers use; it must be a legal identifier (Lecture 3).
    2. Typed interface — inputs have types, and the output has a type (or void for none).
    3. Encapsulated body — callers see the interface, never the statements inside; this is the abstraction that makes large programs tractable.

    Java has no free functions. Every method lives inside a class, interface, enum, record or annotation — which is exactly why even main is a method (Section 5, and Lecture 2/15).

    Memory aid — a method is a contract: give it inputs, it gives you a result, and everyone else may ignore how the result is produced.

    2. Method Anatomy — The Seven Parts

    Every method declaration is assembled from seven parts, and naming them precisely is what earns marks:

    1. Access modifier — public, protected, package-private (no keyword) or private; controls visibility.
    2. static or instance — static methods belong to the class and have no this; instance methods need an object (Lecture 12, Lecture 15).
    3. Return type — any type, including void for "returns nothing".
    4. Name — a verb in camelCase by convention (calculateTotal, not CalculateTotal).
    5. Parameter list — zero or more comma-separated type name pairs inside parentheses.
    6. Body — the brace-delimited block of statements.
    7. Return statement — return value; for a value, or bare return; in a void method.
    // Demo.java — method anatomy and a void method
public class Demo {
    // access  static  return  name  parameters
    public   static   int     add   (int a, int b) {
        return a + b;                  // return statement: value of type int
    }
    public static void greet(String name) {
        if (name == null) return;      // bare return: legal early exit in void
        System.out.println("Hello, " + name);
    }
    public static void main(String[] args) {
        System.out.println(add(2, 3)); // 5
        greet("Ada");                  // Hello, Ada
        greet(null);                   // prints nothing
    }
}

    main itself is a method with the special signature public static void main(String[] args): public so the launcher can reach it, static so it runs without an object, void because it returns to the JVM, and String[] because the launcher passes command-line arguments (Lecture 2/15).

    Important A non-void method must return on every possible path, or javac rejects it with "missing return statement". The compiler proves reachability statically, not at runtime.

    3. Parameters vs Arguments, and Pass-by-Value (Lecture 14 Preview)

    The two words are not synonyms:

    • A parameter is the variable declared in the method header (int a in add(int a, int b)).
    • An argument is the actual value supplied at the call site (add(2, 3) passes the arguments 2 and 3).

    Java is strictly pass-by-value. For a primitive parameter, the method receives a copy of the value, so assigning to the parameter never touches the caller's variable. For an object parameter, the method receives a copy of the reference: mutating the object is visible to the caller because both references point at the same heap object, but reassigning the parameter to a new object is not visible. The full call-by-value versus call-by-reference discussion belongs to Lecture 14.

    // Demo4.java — pass-by-value (primitive copy vs object reference)
public class Demo4 {
    static void trySwap(int a, int b) {   // copies of the caller's ints
        int t = a; a = b; b = t;          // caller's values are untouched
    }
    static void setZero(int[] arr) {      // arr is a copy of the reference
        arr[0] = 0;                       // mutates the shared array object
    }
    public static void main(String[] args) {
        int x = 1, y = 2;
        trySwap(x, y);                    // still x=1, y=2
        int[] data = {5, 6, 7};
        setZero(data);                    // data[0] becomes 0
        System.out.println(x + " " + y + " " + data[0]);  // 1 2 0
    }
}

    The result 1 2 0 is the whole lesson in one line: primitives were immune, the array was mutated. The method never had access to the caller's variable x — only to its value.

    4. void, Return Values, Multiple Returns and Early Return

    A method's return type is a promise about what the call expression evaluates to:

    1. void — no value; the call is a statement, and bare return; may exit early.
    2. A concrete type — exactly one value of that type (or a widening-compatible type, Lecture 5); the call is an expression that can be assigned, printed or nested.
    3. return — exits the current method immediately, returning control to the caller and, if a value is given, the type must match the declared return type.

    Multiple return statements are perfectly legal: control leaves at the first one reached. The idiomatic use is the early return (guard clause), which checks the invalid cases first and lets the main logic run at the bottom, unindented:

    static int safeDivide(int a, int b) {
    if (b == 0) return 0;      // guard: reject the bad case first
    return a / b;              // happy path, no else needed
}

    Two rules follow. First, statements after an unconditional return in the same block are unreachable code and will not compile (Lecture 8). Second, return exits only the method it appears in — it does not terminate the program, unlike System.exit.

    5. The Method Signature — Name Plus Parameter Types

    The method signature is the method name plus the ordered list of its parameter types:

    add(int, int)          -> signature
add(double, double)    -> a different signature

    Everything else is deliberately not part of the signature:

    Declaration element Part of signature? Consequence
    Method name Yes add and sum are different methods
    Parameter types (ordered) Yes add(int, long) and add(long, int) differ
    Parameter names No add(int a, int b) and add(int x, int y) clash
    Return type No int add(int, int) and double add(int, int) clash — compile error
    Access modifier No public add(int) and private add(int) clash
    static keyword No a static and an instance method with one signature clash
    throws clause No cannot be the only difference between two methods

    This single definition explains two otherwise puzzling rules: you cannot overload a method by changing only its return type, and you cannot overload by changing only parameter names.

    6. Method Overloading: Compile-Time (Static) Polymorphism

    Method overloading is declaring two or more methods with the same name but different parameter lists in one class. The compiler picks the best match from the static types of the arguments at the call site — hence the names compile-time polymorphism, static polymorphism and early binding. The overloaded methods are unrelated at runtime; only the selected one is invoked.

    1. Differ by number of parameters: add(int, int) versus add(int, int, int).
    2. Differ by type of parameters: add(int, int) versus add(double, double).
    3. Differ by order of parameter types: log(String, int) versus log(int, String).
    // Demo2.java — overloading by count and type
public class Demo2 {
    static int add(int a, int b)          { return a + b; }
    static double add(double a, double b) { return a + b; }
    static int add(int a, int b, int c)   { return a + b + c; }
    // static double add(int a, int b) { return a + b; } // ILLEGAL: same signature as line 3
    public static void main(String[] args) {
        System.out.println(add(2, 3));        // add(int, int) -> 5
        System.out.println(add(2.0, 3.0));    // add(double, double) -> 5.0
        System.out.println(add(1, 2, 3));     // add(int, int, int) -> 6
    }
}

    The commented line is the classic exam trap: changing only the return type from int to double does not create a new signature, so it is a duplicate-method compile error. Overloading is what makes System.out.println work for every argument type and Math.abs work for int, long, float and double.

    7. Overloading Rules and Ambiguity

    The rules are mechanical once the signature definition is accepted:

    Candidate overloads differ by Legal? Why
    Number of parameters Yes Different signature
    Parameter types Yes Different signature
    Order of parameter types Yes Different ordered signature
    Parameter names only No Same signature
    Return type only No Return type is not in the signature
    Access modifier only No Access is not in the signature
    static versus instance only No Static is not in the signature

    When several overloads are applicable, the compiler resolves in phases, and the first phase that finds a match wins:

    1. Exact or widening primitive match — foo(long) is chosen over foo(Integer) for foo(5), because int widens to long in phase one while boxing happens in phase two.
    2. Autoboxing / unboxing — Integer arguments can match int parameters and vice versa (Lecture 18).
    3. Varargs — a foo(int...) is considered only when no fixed-arity overload applies.

    Two consequences deserve memorising. A widening match beats a boxing match (foo(long) over foo(Integer)), and both beat a varargs match. Where no candidate is unambiguously most specific, the compiler reports reference to foo is ambiguous — a compile error, not a runtime choice:

    static void m(int a, long b) { }    // consider m(1, 2)
static void m(long a, int b) { }    // both are applicable, neither is more specific

    A null argument is a special ambiguity source: it matches any reference type, so m(String) versus m(Object) picks String (most specific), while m(String) versus m(Integer) has no most-specific winner and fails to compile. Cast the null (m((String) null)) to disambiguate.

    Interviewer's perspective The favourite question is "which overload runs for foo(5) if both foo(long) and foo(Integer) exist?" The answer is foo(long): primitive widening is phase one, boxing is phase two, and Java always prefers the earlier phase. Candidates who answer "it depends on the JVM" have confused compile-time overload selection with runtime dispatch.

    8. Overloading vs Overriding (Lecture 17 Preview)

    Overloading is often confused with overriding, which is a different mechanism and the topic of Lecture 17. The distinction is fundamental:

    Aspect Overloading Overriding
    Where Same class (or inherited methods) Subclass replaces a superclass method
    Resolved Compile time, from static types Runtime, from the actual object type
    Signature Must differ in parameter list Must be identical
    Return type May differ freely Same or a covariant subtype
    Access Any May widen, never reduce visibility
    static / final / private Can be overloaded Cannot be overridden (static is hidden)
    Binding Early binding Late binding (dynamic dispatch)
    Also called Static polymorphism Runtime polymorphism

    The mental split: overloading is about the call site (many methods, one name, chosen by arguments); overriding is about the object (one method name, many implementations, chosen by the receiver). Both are forms of polymorphism, but only overriding needs extends and an object (Lecture 16).

    9. Recursion: The Base Case and the Recursive Case

    Recursion is a method calling itself. A correct recursive method has exactly two kinds of branch:

    1. Base case — the smallest input, where the method returns a value directly without recursing. This is what stops the chain.
    2. Recursive case — the method calls itself on a smaller or simpler input and combines that result with local work.

    Two obligations follow: the base case must be reachable for every legal input, and each recursive call must make progress toward it. A recursion that guarantees both terminates; one that misses either runs forever until the call stack is exhausted (Section 10).

    The structure is a contract: assume the recursive call is already correct for the smaller input, and use its answer. This "recursive leap of faith" is the reason recursive code is short — the method solves one step and delegates the rest.

    10. The Call Stack, Frames and StackOverflowError

    Every method call pushes a stack frame onto the JVM's call stack: the frame holds the parameters, the local variables and the return address. A normal method pops its frame on return. A recursive method cannot pop until the innermost call returns, so the frames pile up:

    factorial(4)
  -> factorial(3)
       -> factorial(2)
            -> factorial(1)
                 base case: returns 1     (frame pops)
            <- returns 2 * 1 = 2
       <- returns 3 * 2 = 6
  <- returns 4 * 6 = 24
    1. On the way down, frames are pushed and nothing is computed yet.
    2. At the base case, the stack is at its deepest.
    3. On the way up (unwinding), each frame multiplies and returns.

    If the base case is missing or unreachable, frames push until the stack space is exhausted and the JVM throws StackOverflowError. This is an Error, not an Exception (Lecture 43): it signals a broken program, not a recoverable condition, and should generally not be caught. The stack is created per thread and sized by -Xss; its full memory picture is Lecture 45.

    Important Depth is the enemy, not the number of calls. A recursion that is n levels deep needs n live frames at once, even if it makes only n calls in total.

    11. Classic Recursion: Factorial and Fibonacci

    Two examples anchor the topic: one linear, one exponential.

    // Demo3.java — factorial and naive fibonacci
public class Demo3 {
    static long factorial(int n) {
        if (n <= 1) return 1;              // base case
        return n * factorial(n - 1);       // one recursive call, depth n
    }
    static long fib(int n) {
        if (n <= 1) return n;              // base case: fib(0)=0, fib(1)=1
        return fib(n - 1) + fib(n - 2);    // two calls: exponential without caching
    }
    public static void main(String[] args) {
        System.out.println(factorial(5));  // 120
        System.out.println(fib(10));       // 55
    }
}

    factorial makes one recursive call per level, so it takes O(n) time and O(n) stack depth. fib makes two calls per level, so the same subproblem is recomputed again and again: fib(n) calls roughly phi^n times (about 1.6^n), which is exponential. fib(40) is around a billion calls and takes seconds; fib(50) is impractical.

    The cure is memoization — cache each computed result so a subproblem is solved once, reducing fib to O(n) time at the cost of O(n) memory. Iterative dynamic programming and the general streams/collections machinery arrive in later lectures; the point here is recognising the exponential shape. Note also that factorial overflows long at 21!, because long saturates around 9.2 × 10^18 (Lecture 3).

    12. Recursion vs Iteration

    Anything recursive can be rewritten iteratively, and vice versa — the two are equally powerful but not equally convenient:

    Aspect Recursion Iteration
    Mechanism Method calls itself Loop repeats a block
    Stopping rule Base case Loop condition
    Extra memory O(depth) stack frames O(1) extra state (usually)
    Constant factor Call overhead per level, slower Loop overhead, faster
    Failure mode StackOverflowError Infinite loop (silently hot)
    Readability Natural for trees, divide-and-conquer, backtracking Natural for linear scans and counters
    Debugging Harder — deep stack traces Easier — one frame to inspect
    Best when The problem itself is nested or self-similar Repetition is flat and count-driven

    Practical guidance: use recursion when the data structure is recursive (tree traversal, directory walk, divide-and-conquer like merge sort, backtracking like N-queens), and use iteration for flat repetition (summing a range, scanning an array). Recursion buys clarity; iteration buys memory and speed. A recursive solution with no natural nesting is usually a mnemonic for a loop.

    13. Tail Recursion — Java Does Not Optimize It

    A recursive call is tail-recursive when it is the last operation of the method — nothing happens after it returns. Some languages (Scheme, Scala with an annotation) reuse the current frame for such calls, a technique called tail-call optimisation (TCO), turning the recursion into a loop at the machine level.

    Java does not perform TCO. The language specification gives no such guarantee and HotSpot does not implement it, so every tail-recursive call still pushes a new frame. A tail-recursive accumulator that would be safe in Scala can still throw StackOverflowError in Java on a deep input. The Java-idiomatic answer is to write the loop by hand:

    static long factorialIter(int n) {
    long acc = 1;
    for (int i = 2; i <= n; i++) acc *= i;   // manual TCO: explicit loop
    return acc;
}

    This is a favourite interview point because it separates "recursion is a language feature" from "recursion is free".

    14. Scope and Lifetime Inside Methods (Lecture 45 Preview)

    Parameters and local variables live on the method's stack frame, and their scope and lifetime are tied to the method execution:

    1. A parameter is in scope for the whole method body and is local to that call.
    2. A local variable is in scope from its declaration to the end of its enclosing block.
    3. Each call gets fresh copies; nothing survives from the previous call unless it was stored in a field or passed back.
    4. Locals are invisible outside the method; a caller cannot read them, only the returned value.
    5. A local may shadow a field of the same name, in which case this.name (Lecture 12) reaches the field.

    Because frames are per-call, recursion's correctness depends on locals being independent per frame — factorial(3) and factorial(2) never share an n. The physical layout of the stack, heap and method area is Lecture 45; static members, which live off the frame, are Lecture 15.

    15. Varargs: int... nums

    Varargs (variable arity) lets a method accept zero or more arguments of one type. The syntax is the type followed by ...:

    static int sum(int... nums) {          // nums is really an int[]
    int s = 0;
    for (int n : nums) s += n;
    return s;
}
// sum()            -> 0
// sum(1, 2, 3)     -> 6
// sum(new int[]{4, 5}) -> 9

    The rules are few but exact:

    1. The varargs parameter must be the last parameter; nothing may follow it.
    2. There can be at most one varargs parameter in a method.
    3. Inside the body it is an array — the compiler wraps the arguments into a new array (or passes your array through unchanged).
    4. It is compatible with zero arguments; beware methods like sum(int first, int... rest) if both are numbers.
    5. main(String[] args) and main(String... args) are the same signature, so declaring both is a compile error (Lecture 2/15).

    Varargs and overloading interact cautiously: a fixed-arity overload always wins over a varargs one when both apply, which is why adding sum(int a, int b) beside sum(int... nums) silently reroutes two-argument calls.

    16. The Pitfall Catalogue

    Pitfall Trigger Result Fix
    Overload by return type only Same name, same params, different return Compile error (duplicate method) Change the parameter list
    Infinite recursion Missing or unreachable base case StackOverflowError Add a base case; ensure progress
    Primitive "not changing" trySwap(x, y) Caller's values unchanged Return a value or use an object/array
    Object reassignment ignored p = new Point() inside the method Caller still sees the old object Mutate the object, or return the new one
    null overload ambiguity m(null) with unrelated reference overloads Compile error Cast: m((String) null)
    Mixed-order ambiguity m(int, long) and m(long, int) Compile error Retype arguments or rename methods
    Varargs plus array duplicate f(int[]) and f(int...) in one class Compile error (same signature) Keep only one
    Static versus instance clash Same params, one static Compile error Change the signature
    Unreachable code after return Statements after an unconditional return Compile error Move or delete the statements
    Confusing hiding with overriding Overriding a static method Hidden, not dispatched Override instance methods only (Lecture 17)

    17. Myth vs Reality

    Myth Reality
    "The return type can distinguish overloads." It cannot — the signature is name plus parameter types, so returning a different type changes nothing.
    "Java passes objects by reference." Java is pass-by-value for everything; object parameters receive a copy of the reference, so mutation is visible but reassignment is not (Lecture 14).
    "Recursion is always slower than a loop." Only the call overhead and extra memory are the cost; for self-similar problems recursion is clearer and often correct where a hand-rolled loop is not (tree traversal).
    "Java optimises tail recursion." It does not. Every tail call still pushes a frame; convert deep tail recursion to a loop by hand (Section 13).
    "static methods can be overridden." They are hidden, not overridden. Overriding is resolved at runtime by the receiver, and static has no receiver (Lecture 17).

    18. Common Trap Questions

    Trap 1 — Overloading by return type: "Can I write int f() and double f() in the same class?" No. Return type is not part of the signature, so both declare the same method f() and the compiler reports a duplicate. Give them different parameter lists instead.

    Trap 2 — void with a value: "Is return x; legal inside a void method?" No. A void method may only use the bare return;. Returning an expression is a compile error, because the method's declared type promises nothing.

    Trap 3 — The object parameter: "I did p = new Point(0, 0) inside the method — why is the caller's point unchanged?" Assigning to the parameter rebinds only the local copy of the reference. The caller's variable still points at the original object. Mutate the object's fields, or return the new reference.

    Trap 4 — The null call: "With m(String) and m(Object) available, which runs for m(null)?" m(String), because String is the more specific reference type. Swap one of them for an unrelated type such as Integer and the call becomes ambiguous — a compile error.

    Trap 5 — Missing base case: "What error does recursion with no stopping condition throw?" StackOverflowError (an Error, not an Exception) once the stack fills. It is not a RuntimeException, and catching it is discouraged because the stack is already broken (Lecture 43).

    Trap 6 — Varargs signature: "Can sum(int...) and sum(int[]) coexist?" No. A varargs parameter is an array parameter, so the two declarations are the same signature and the class fails to compile.

    Trap 7 — Static hiding: "If the subclass defines a static method with the same signature, is that overriding?" No, it is method hiding. The call is resolved from the reference's static type at compile time, so no dynamic dispatch occurs (Lecture 17).

    19. Points to Remember

    1. A method has seven parts: access modifier, static/instance, return type, name, parameter list, body and return statement.
    2. A parameter is declared; an argument is supplied. Java is pass-by-value: primitives copy, objects copy the reference (Lecture 14).
    3. void methods return nothing and may use a bare return;; non-void methods must return on every reachable path.
    4. Multiple return statements are legal; control leaves at the first one reached, and code after an unconditional return is unreachable (Lecture 8).
    5. The signature is name plus ordered parameter types — return type, access modifier, parameter names and static are excluded.
    6. Overloading is same name, different parameter list, resolved at compile time from static types (static polymorphism).
    7. Resolution prefers widening over autoboxing over varargs; no most-specific winner means a compile-time ambiguity error (Lecture 5).
    8. Overriding (Lecture 17) is subclass replacement with an identical signature, resolved at runtime by dynamic dispatch; static methods are hidden, not overridden.
    9. Recursion needs a reachable base case and progress toward it; each call pushes a frame, and exhaustion throws StackOverflowError.
    10. Naive fib is exponential because it recomputes subproblems; memoization restores linear time (Section 11).
    11. Java has no tail-call optimisation — deep tail recursion still overflows; write the loop instead.
    12. Varargs (Type...) must be last, at most one, and is an array inside; keep receiver's main(String[] args) and main(String... args) as one method (Lecture 2/15).

    20. Likely Interview Questions

    Question Crisp Answer
    What is a method in Java? A named, typed block of statements inside a class that performs one task, optionally takes parameters and optionally returns a value.
    What is the difference between a parameter and an argument? A parameter is the declared variable in the header; an argument is the value passed at the call site.
    Is Java pass-by-value or pass-by-reference? Strictly pass-by-value. Primitives copy the value; object parameters copy the reference, so mutation is visible but reassignment is not (Lecture 14).
    What is a method signature? Method name plus the ordered list of parameter types. Return type, access modifier, names and static are not part of it.
    What is method overloading? Same name, different parameter lists in one class, resolved at compile time from the arguments' static types (static polymorphism).
    Can you overload a method by changing only the return type? No — that leaves the signature identical, producing a duplicate-method compile error.
    Which overload wins for foo(5) if both foo(long) and foo(Integer) exist? foo(long); resolution runs in phases — exact/widening first, then boxing/unboxing, then varargs — and no most-specific match is a compile error.
    Overloading vs overriding? Overloading: compile-time, different parameters. Overriding: runtime, identical signature, subclass replaces superclass (Lecture 17).
    What are the two required parts of recursion? A base case that returns without recursing and a recursive case that makes progress toward the base case.
    Why is naive Fibonacci exponential? Each call spawns two calls (fib(n-1) and fib(n-2)), so the same subproblems are recomputed, giving roughly 1.6^n calls.
    Does Java optimise tail recursion? No. Java performs no tail-call optimisation, so deep tail recursion still throws StackOverflowError.
    What happens with varargs in the method body? The parameter is an array; the compiler packs the arguments (or passes your array through). It must be the last parameter, at most one per method.

    21. Final Summary

    call add(2, 3) -> compiler picks overload -> frame pushed (params + locals + return address)
               -> body runs -> return value -> frame popped
recursion: call -> ... -> base case -> unwind (frame pops on each return)
iteration: loop condition -> body -> update -> condition   (one frame, no growth)
    • Anatomy → access, static/instance, return type, name, parameters, body, return; non-void must return on every path.
    • Signature → name + ordered parameter types; return type, access, names and static are excluded.
    • Overloading → same name, different parameter list, compile-time choice; widening ⊃ autoboxing ⊃ varargs; ambiguity is a compile error.
    • Overriding → same signature in a subclass, runtime dispatch; static is hidden, not overridden (Lecture 17).
    • Recursion → base case + recursive case; frames grow with depth; missing base case → StackOverflowError.
    • Factorial → O(n) time and stack; naive Fibonacci → exponential, fixed by memoization.
    • Recursion vs iteration → clarity for nested/self-similar data, memory and speed for flat repetition; Java adds no tail-call optimisation.
    • Pass-by-value → primitives copy; object references copy, so mutation shows but reassignment does not (Lecture 14).
    • Varargs → Type... last and single, treated as an array; main is just a method with a special signature.

    Golden rule The compiler chooses the overload from the arguments' static types; the runtime chooses the override from the receiver's actual type — keep those two decisions apart and most method questions answer themselves.

    One-line takeaway: a method is a typed contract, overloading is the compiler picking the right contract by arguments, overriding is the object picking the right implementation at runtime, and recursion is a method that trusts its smaller self until the base case pays the debt.
