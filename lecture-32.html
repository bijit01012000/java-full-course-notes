    Java List Interface Deep Dive | ArrayList, LinkedList, Vector, Stack

    18 sections · interview-oriented · both themes

    Scope evidence: "Java List Interface Deep Dive | ArrayList, LinkedList, Vector, Stack" (playlist map, verified). Repo evidence: code/Demo.java.

    Lecture 31 introduced the Collection interface as the root contract of the framework. This lecture drills into List, its first and most used subinterface: an ordered, index-addressed sequence that permits duplicates. It then opens the four classic implementations that ship with the JDK and shows how their internals decide which one to reach for: the growable array behind ArrayList, the doubly linked chain behind LinkedList, the synchronized legacy of Vector, and the LIFO Stack built on top of it. The constant theme is that the same interface promises the same operations while the four backings deliver very different costs.

    1. The List Interface: Ordered, Indexed, Duplicates Allowed

    A List is a subinterface of Collection that adds positional access. Where a plain Collection only knows membership, a List imposes a strict order: every element sits at a zero-based index, the order is stable unless you change it, and the same value may appear many times. The nesting is:

    Iterable  ⊃  Collection  ⊃  List  ⊃  (ArrayList, LinkedList, Vector, Stack)

    Three guarantees define it:

    1. Ordered — iteration returns elements in index order, not an arbitrary set order.
    2. Indexed — every element is reachable by an int position, so get(3) is meaningful.
    3. Duplicates allowed — [a, a, b] is a valid list, unlike a Set.

    A List also permits null elements in general, though how many and where depends on the implementation (LinkedList allows many; List.of(...) allows none because it is immutable). Because position matters, List complements Collection with its own cursor, the ListIterator, which can walk both directions and change elements in place.

    Important List is an interface, not a data structure. It promises behaviour; ArrayList, LinkedList, Vector and Stack decide the performance. Choosing the interface type for a variable (List<String> names = new ArrayList<>();) keeps callers free to swap the implementation later.

    2. The Index-Based Method Surface

    The methods that make a List a list are the ones that take an index:

    Method Meaning Cost note (ArrayList)
    E get(int index) read the element at a position O(1)
    E set(int index, E element) replace, returns the old element O(1)
    void add(int index, E element) insert at a position, shifting the tail right O(n)
    boolean add(E e) append at the end amortized O(1)
    E remove(int index) delete a position, shifting the tail left O(n)
    boolean remove(Object o) delete the first matching element O(n)
    int indexOf(Object o) first index of a value, or -1 O(n)
    int lastIndexOf(Object o) last index of a value, or -1 O(n)
    List<E> subList(int from, int to) a view of a range, from inclusive, to exclusive O(1) view
    ListIterator<E> listIterator() bidirectional cursor with add/set/remove -
    void sort(Comparator<? super E> c) stable in-place sort (Java 8 default) O(n log n)

    Two subtleties matter early. First, set returns the element it displaced, so the old value is not lost. Second, add(E e) and remove(Object o) return a boolean, while remove(int index) returns the removed element — a difference that powers the ambiguity of Section 12.

    Memory aid The List extras are exactly the methods that mention an index. If an operation does not need a position, it already lived on Collection.

    3. ArrayList Internals: The Growable Array

    ArrayList is backed by a plain Object[] elementData plus an int size. Its whole design is "array, but resizable".

    • Lazy default capacity. new ArrayList<>() does not immediately allocate ten slots. DEFAULT_CAPACITY is 10, but the backing array starts as a shared empty array and is only allocated on the first add. This avoids wasting memory on lists that stay empty.
    • Growth by 1.5x. When the array is full, a new one is created with newCapacity = oldCapacity + (oldCapacity >> 1) — the shift adds half, so capacity grows by roughly 50 percent. The elements are copied with System.arraycopy (or Arrays.copyOf).
    • O(1) random access. Indexing is pointer arithmetic: elementData[index]. Reading or replacing any position is constant time.
    • O(n) middle insertion and deletion. Inserting at the front shifts every following element one slot right; deleting at the front shifts them left. Both are done by System.arraycopy.
    • Amortized O(1) append. A single append is usually O(1); occasionally it triggers the 1.5x copy, and averaging those rare copies over many appends yields amortized constant time.
    • Fail-fast. A modCount field tracks structural changes. An iterator created from the list remembers modCount and throws ConcurrentModificationException if the list is modified through any other route while iterating.

    Interviewer's perspective "Why is add at the end described as amortized O(1)?" Because growth is geometric, not linear. Doubling-style growth means the total copying for n appends is bounded by a constant multiple of n, so the average per append is constant.

    4. ArrayList in Practice

    // Demo.java — the core List operations on an ArrayList
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>();
        list.add("Ada");            // append
        list.add("Alan");
        list.add(0, "Grace");       // insert at index 0 (shifts right)
        System.out.println(list);   // [Grace, Ada, Alan]

        System.out.println(list.get(1));        // Ada
        System.out.println(list.set(1, "Edsger")); // Ada (returned old value)
        System.out.println(list.indexOf("Alan")); // 2
        System.out.println(list.subList(1, 3));   // [Edsger, Alan] (a view)

        list.sort(Comparator.naturalOrder());
        System.out.println(list);   // [Alan, Edsger, Grace]

        Iterator<String> it = list.iterator();
        while (it.hasNext()) {
            if (it.next().equals("Alan")) {
                it.remove();        // legal: removal through the iterator
            }
        }
        System.out.println(list);   // [Edsger, Grace]
    }
}

    Notice the last block: removal happens through Iterator.remove(), not list.remove(...). Calling the list directly during iteration is the fail-fast violation described in Section 13.

    5. LinkedList Internals: The Doubly Linked List

    LinkedList stores each element in a Node object holding three fields: item, prev and next. The list keeps references to first and last, so it can reach either end instantly, but reaching the middle means walking node by node.

    • O(1) at the ends. Adding or removing at the head or tail is constant time: relink a few references.
    • O(n) random access. get(i) walks from whichever end is closer, counting until it reaches i. There is no index arithmetic.
    • Per-node overhead. Every element costs a node object with two references on top of the value — heavy compared with a bare array slot.
    • Implements Deque. It is simultaneously a List, a Queue and a Deque, which is why it works well as a queue or a stack.

    Important LinkedList shines when the workload is "add and remove at the ends". It is the wrong tool for "read index i repeatedly", because each get(i) is a fresh walk. Section 13 shows the quadratic trap this creates.

    6. LinkedList as a Deque: Queue and Stack Operations

    Because LinkedList implements Deque, it exposes both end-friendly APIs directly:

    // Demo.java — the same LinkedList used as a queue and as a stack
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Deque<String> queue = new LinkedList<>();
        queue.offer("first");            // enqueue at tail
        queue.offer("second");
        System.out.println(queue.poll()); // first  (FIFO: head out)

        Deque<String> stack = new LinkedList<>();
        stack.push("bottom");            // push to head
        stack.push("top");
        System.out.println(stack.peek()); // top    (LIFO: head in)
        System.out.println(stack.pop());  // top
    }
}

    offer/poll/peek are the queue vocabulary (they return null on empty rather than throwing); push/pop are the stack vocabulary. Both act on the head for stack semantics and on opposite ends for queue semantics.

    Memory aid LinkedList = "cheap ends, expensive middle". ArrayList = "cheap middle-by-index, expensive middle-by-insert".

    7. Vector: The Legacy Synchronized List

    Vector predates the Collections Framework (Java 1.0) and is, structurally, an ArrayList that makes a different concurrency choice.

    • Every public method is synchronized. A single lock guards the whole object, so concurrent calls are serialized. This makes individual operations thread-safe but limits throughput.
    • Growth by 2x (or by capacityIncrement). When full, Vector doubles its capacity, or grows by the capacityIncrement you passed to the constructor if it is non-zero. This is more aggressive than ArrayList's 1.5x.
    • Enumeration. It exposes the older elements() cursor returning an Enumeration, alongside the modern Iterator.
    • Largely obsolete. Synchronizing every method is coarse and slow; modern code prefers ArrayList for single-threaded use and CopyOnWriteArrayList or Collections.synchronizedList for concurrent use (Lecture 33 and Lecture 56).

    Important Vector being synchronized does not make compound actions atomic. Checking size() then calling get(...) is still a race unless you hold the same lock across both calls. Synchronization on each method is not the same as synchronization on your sequence of methods.

    8. Stack: LIFO on Top of Vector

    Stack extends Vector and adds the last-in-first-out discipline: push, pop, peek, empty and search. Inheriting from Vector means it also inherits all the List methods, including indexed access and insertion — so you can legally add(0, x) a Stack, which breaks the LIFO abstraction.

    // Demo.java — legacy Stack versus the modern replacement ArrayDeque
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        Stack<Integer> legacy = new Stack<>();
        legacy.push(1);
        legacy.push(2);
        System.out.println(legacy.pop());   // 2

        Deque<Integer> modern = new ArrayDeque<>();  // preferred stack
        modern.push(1);
        modern.push(2);
        System.out.println(modern.pop());   // 2
    }
}

    The standard advice is to prefer ArrayDeque for a stack: it is not synchronized, it is backed by a resizable circular array, and it is not encumbered with the List methods that corrupt LIFO semantics.

    Interviewer's perspective "Why is Stack considered a design mistake?" Because it extends Vector rather than composing it. Inheriting List means callers can insert and remove by index, leaving a Stack in a state that is no longer a stack. ArrayDeque avoids the inheritance leak.

    9. ArrayList vs LinkedList vs Vector vs Stack

    Aspect ArrayList LinkedList Vector Stack
    Structure Resizable Object[] Doubly linked nodes Resizable Object[] Vector subclass
    Random access get(i) O(1) O(n) O(1) O(1)
    Add/remove at ends amortized O(1) at tail O(1) at either end amortized O(1) at tail O(1) at tail
    Add/remove in middle O(n) O(n) (walk plus relink) O(n) O(n)
    Synchronized No No Yes (every method) Yes (inherited)
    Legacy No No Yes (Java 1.0) Yes (Java 1.0)
    Special API ensureCapacity, trimToSize Deque queue/stack methods Enumeration push/pop/peek/empty/search
    Best used when Frequent indexed reads, appends Frequent add/remove at ends, queue or stack Almost never; legacy code only Almost never; use ArrayDeque

    Reading the table: ArrayList wins the common case of "read a lot, append a lot". LinkedList wins a narrow case of end edits. Vector and Stack survive mostly for backward compatibility.

    10. Big-O of the Core List Operations

    Operation ArrayList LinkedList Vector Stack
    get(index) O(1) O(n) O(1) O(1)
    add(end) amortized O(1) O(1) amortized O(1) amortized O(1)
    add(index) O(n) O(n) O(n) O(n)
    remove(index) O(n) O(n) O(n) O(n)
    remove(Object) O(n) O(n) O(n) O(n)
    contains(Object) O(n) O(n) O(n) O(n)
    add(front) O(n) O(1) O(n) O(n)
    remove(front) O(n) O(1) O(n) O(n)

    The asymmetry is the whole lesson: ArrayList is index-cheap and shift-expensive; LinkedList is end-cheap and index-expensive. Neither is universally "faster".

    11. ArrayList vs a Plain Array

    An array is the primitive structure; ArrayList is a wrapper that trades a little overhead for flexibility.

    Aspect int[] / E[] array ArrayList<E>
    Size Fixed at creation Resizable
    Length / size arr.length (field) list.size() (method)
    Primitives Holds int, double, ... directly Holds only objects; primitives are boxed
    Generics No; arrays are covariant and unchecked Yes; compile-time type safety
    Fixed overhead None beyond the data Object header plus capacity slack
    Capacity vs size Same thing capacity >= size(); slack is spare room
    Shrink / reserve Not possible trimToSize(), ensureCapacity(n)
    Indexed read arr[i] list.get(i)
    Header position arr[0] list.get(0)

    Two tuning levers follow. trimToSize() shrinks the backing array down to the current size to release the slack, and ensureCapacity(n) pre-allocates room up front so a burst of appends does not trigger repeated 1.5x copies. When the final size is known in advance, passing an initial capacity (for example new ArrayList<>(10_000)) avoids all the intermediate reallocations.

    Memory aid Array = length, fixed, primitives. ArrayList = size(), resizable, objects. The extra layer buys growth and methods at the cost of boxing and overhead.

    12. The Classic Trap: remove(int) vs remove(Object)

    The same call looks like it does one thing and does another, depending purely on the argument's static type.

    // Demo.java — index removal versus object removal
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(10, 20, 30, 20));

        list.remove(1);                     // remove INDEX 1 -> removes 20
        System.out.println(list);           // [10, 30, 20]

        list.remove(Integer.valueOf(20));   // remove OBJECT 20 -> first match
        System.out.println(list);           // [10, 30]
    }
}

    The compiler picks the most specific overload. The literal 1 is an int, so it matches remove(int index) and deletes position 1. Wrapping the value with Integer.valueOf(20) produces an Integer object, so it matches remove(Object) and deletes the first element equal to 20.

    Trap With List<Integer>, list.remove(1) deletes the value at index 1, not the number 1. To delete the object 1, write list.remove(Integer.valueOf(1)). The same confusion exists between add(int index, E) and add(E) when E is Integer.

    13. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    for (int i = 0; i < list.size(); i++) list.get(i) on a LinkedList Each get(i) walks from an end, so the loop is O(n^2) Use the for-each loop or an Iterator (O(n) total)
    Removing during a for-each loop ConcurrentModificationException from the fail-fast iterator Remove through Iterator.remove() or removeIf(...)
    Treating subList as a copy It is a view; a structural change to the parent invalidates it Copy the range with new ArrayList<>(parent.subList(a, b)) when you need an independent list
    Forgetting Vector and Stack lock every method Slower than ArrayList with no benefit in single-threaded code Use ArrayList; use CopyOnWriteArrayList for concurrency
    Assuming ArrayList is thread-safe Concurrent writes corrupt state or throw Synchronize externally or use a concurrent list (Lectures 33, 56)
    Autoboxing on every write and read List<Integer> allocates/boxes each value; reading a null unboxes to NullPointerException Prefer plain arrays or primitives when the loop is hot; guard nulls
    Passing a type to remove by accident remove(int) fires when you meant remove(Object) Use Integer.valueOf(...) to force object removal
    Trusting ensureCapacity to set size Capacity is spare room, not elements; size() stays 0 Capacity is not content; use add to populate

    Golden rule Pick the implementation from the operation you do most: index reads point to ArrayList, end edits point to LinkedList, and concurrency points to a concurrent collection — never to Vector by reflex.

    14. Myth vs Reality

    Myth Reality
    "All List implementations perform the same." Same interface, very different costs: ArrayList is O(1) random access, LinkedList is O(n).
    "new ArrayList<>() immediately allocates ten slots." Default capacity is 10, but the array is allocated lazily on the first add.
    "LinkedList is always faster for insertion." Only at the ends. Inserting in the middle still needs an O(n) walk to find the position.
    "Vector is the thread-safe choice, so prefer it." Its coarse per-method lock is slow; CopyOnWriteArrayList / Collections.synchronizedList are the modern options.
    "subList returns a new independent list." It returns a view backed by the parent; structural changes to the parent invalidate it.

    15. Common Trap Questions

    Trap 1 — Index or object: "For List<Integer> l = new ArrayList<>(List.of(5, 6, 7));, what does l.remove(1) do?" It removes the element at index 1 (the value 6), returning the removed element. To remove the value 1, call l.remove(Integer.valueOf(1)).

    Trap 2 — The linked-list loop: "Is for (int i = 0; i < list.size(); i++) sum += list.get(i); fine on a LinkedList?" No. Each get(i) walks the chain, making the loop O(n^2). Use the for-each loop, which uses the iterator and is O(n).

    Trap 3 — Capacity versus size: "After new ArrayList<>(100), what is size()?" 0. The constructor sets the initial capacity to 100; no elements exist yet, so size() is 0.

    Trap 4 — The subList view: "List<Integer> sub = list.subList(0, 2); list.add(99); then sub.get(0) — what happens?" Accessing the view after a structural change to the parent generally throws ConcurrentModificationException. It is a view, not a snapshot.

    Trap 5 — Fail-fast during iteration: "Can I call list.remove(...) inside a for-each over the same list?" No: the iterator detects the structural change and throws ConcurrentModificationException. Remove through the iterator, or use removeIf.

    Trap 6 — Growth factor: "How much does ArrayList grow by, and how much does Vector?" ArrayList: 1.5x (oldCapacity + (oldCapacity >> 1)). Vector: 2x, or by capacityIncrement if one was supplied.

    Trap 7 — Unboxing a null: "List<Integer> l contains null; what does int x = l.get(0); do?" It unboxes null, throwing NullPointerException at the assignment. Use Integer x = l.get(0); to avoid the unboxing.

    16. Points to Remember

    1. List is an ordered, index-addressed Collection; it allows duplicates and (usually) null.
    2. Index methods are get, set, add(int, E), remove(int), indexOf, lastIndexOf, subList, listIterator and sort.
    3. ArrayList is backed by a resizable Object[]; default capacity is 10, allocated lazily on first add.
    4. ArrayList grows by 1.5x via oldCapacity + (oldCapacity >> 1) and shifts elements with System.arraycopy.
    5. ArrayList gives O(1) random access, amortized O(1) append, and O(n) middle insert/delete, and is fail-fast.
    6. LinkedList is a doubly linked list: O(1) at both ends, O(n) random access, per-node memory overhead, and it implements Deque.
    7. Vector is legacy: every method is synchronized, growth is 2x (or by capacityIncrement), and it exposes Enumeration.
    8. Stack extends Vector and adds LIFO push/pop/peek/empty/search; prefer ArrayDeque for a stack.
    9. subList returns a view, not a copy; a structural change to the parent invalidates it.
    10. remove(int) removes by index while remove(Object) removes by value — with List<Integer>, use Integer.valueOf(...) to force the object overload; prefer ArrayDeque and concurrent collections over Vector/Stack.

    17. Likely Interview Questions

    Question Crisp Answer
    What is the List interface? A subinterface of Collection that adds ordering, zero-based indexing and duplicate tolerance.
    ArrayList vs LinkedList? ArrayList is a resizable array with O(1) random access; LinkedList is a doubly linked list with O(1) end edits but O(n) access.
    Why is ArrayList good for random access? Its backing array allows index arithmetic in constant time: elementData[index].
    How does ArrayList grow? When full, a new array of oldCapacity + (oldCapacity >> 1) (about 1.5x) is created and the elements copied.
    Why is ArrayList.add amortized O(1)? Geometric growth bounds total copying by a constant multiple of n, so the average append is constant.
    When would you choose LinkedList? When most operations add or remove at the ends, or when you need the Deque queue/stack API.
    What is Vector, and why is it obsolete? A legacy synchronized list from Java 1.0; its per-method lock is coarse and slow, so ArrayList plus a concurrent list is preferred.
    Why prefer ArrayDeque over Stack? Stack extends Vector, so it leaks List methods that break LIFO; ArrayDeque is faster and not synchronized.
    What does remove(1) do on List<Integer>? It removes the element at index 1. Use remove(Integer.valueOf(1)) to remove the value 1.
    Is subList a copy? No, it is a view backed by the parent list; structural changes to the parent invalidate it.
    What is fail-fast iteration? An iterator throws ConcurrentModificationException when it detects a structural change made outside the iterator.
    Are ArrayList and LinkedList thread-safe? No. Use Collections.synchronizedList, CopyOnWriteArrayList, or external locking (Lectures 33 and 56).

    18. Final Summary

    Collection  ⊃  List            (ordered, indexed, duplicates allowed)
   |
   +-- ArrayList  : Object[]   -> O(1) get, amortized O(1) add, 1.5x growth, fail-fast, not synchronized
   +-- LinkedList : nodes      -> O(1) ends, O(n) get, implements Deque (queue/stack), not synchronized
   +-- Vector     : Object[]   -> every method synchronized, 2x growth, Enumeration, legacy
   +-- Stack      : Vector     -> LIFO push/pop/peek, legacy; prefer ArrayDeque

index methods: get set add(i) remove(i) indexOf lastIndexOf subList listIterator sort
classic trap: remove(int) = index   ≠   remove(Object) = value
array vs ArrayList: fixed vs resizable · primitives vs boxed · length vs size()
                    capacity >= size() · trimToSize · ensureCapacity
    • List → the interface: order, index, duplicates; the implementation decides the cost.
    • ArrayList → default choice: array-backed, O(1) access, amortized O(1) append, lazy capacity 10, 1.5x growth.
    • LinkedList → end-editing and Deque: O(1) ends, O(n) access, extra node memory.
    • Vector / Stack → legacy: synchronized everywhere, 2x growth, LIFO on a leaky List base; prefer ArrayDeque and concurrent lists.
    • Trap → remove(int) is by index, remove(Object) is by value; subList is a view; fail-fast iterators punish mid-loop edits.
    • Array vs ArrayList → fixed versus resizable, primitives versus boxed, length versus size(), with trimToSize and ensureCapacity as tuning levers.

    Golden rule The List interface fixes the contract, never the cost: choose ArrayList for indexed reads, LinkedList for end edits, and reach for a concurrent collection — not Vector — when threads are involved.

    One-line takeaway: List promises order, index and duplicates; ArrayList, LinkedList, Vector and Stack each pay for that promise differently, so the right pick is the one whose weak operation you never call.
