    Part 3 · Web Internals & MVC · Lecture 19

    Spring Boot Filters

    16 sections · interview-oriented · both themes

    Scope evidence: "Spring Boot Filters | FilterChain, Logging, Auth & Request Flow" (playlist map, verified). Repo folder is the filterDemo project: a filter package holding LoggingFilter and AuthenticationFilter, plus controller (StudentController), service (StudentService), and dto (Student), together with the notes.

    Every real web application needs the same jobs done on every request: log it, authenticate it, time it, add headers to the response. Writing that logic inside each controller turns clean endpoints into plumbing. Spring Boot Filters give one reusable, Servlet-level checkpoint where request and response logic can live once and apply everywhere. This lecture shows where filters run in the request lifecycle, how FilterChain moves a request forward, and how a filter can stop a request cleanly and return JSON.

    1. Why Do We Need Filters?

    A beginner imagines the request flow like this:

    Client / Browser / Postman  ->  Spring Boot Application  ->  Controller Method  ->  Response

    In a real application the request does not go straight to the controller. Before the controller runs, the application often has to do common work:

    • log the request URL;
    • check an authentication token;
    • block suspicious requests;
    • measure request execution time;
    • add common response headers;
    • apply character encoding;
    • create a request or trace ID.

    A naive developer writes all of that inside the controller method:

    @GetMapping("/students")
public List<Student> getStudents(HttpServletRequest request) {
    System.out.println("Request URL: " + request.getRequestURI());
    // Authentication check
    // Logging
    // Timing logic
    return studentService.getAllStudents();
}

    The code works, but it creates four design problems:

    1. The same infrastructure logic is repeated across multiple APIs.
    2. Controller methods become difficult to read.
    3. Developers may forget to add the logic to newly created APIs.
    4. Controllers stop focusing on their primary responsibility: handling application use cases.

    A Filter provides one common place for request-level logic that must apply to multiple endpoints.

    Important: A filter is a single place to write infrastructure logic once, so controllers can stay focused on business use cases.

    2. Cross-Cutting Concerns

    Tasks that apply across many parts of an application are known as cross-cutting concerns. Common examples include request logging, authentication and authorization checks, security checks, character encoding, request timing, audit tracking, correlation or trace IDs, and rate limiting.

    These concerns are not part of the business logic of a particular controller, service, or repository. They operate across multiple requests, which makes Filters suitable when the work belongs to the HTTP or Servlet layer.

    Business logic   -> one controller or service (belongs there)
Cross-cutting    -> many requests at once (belongs in a Filter)

    Golden rule: If the logic has to run for many endpoints, it is cross-cutting, and it belongs in a Filter, not copy-pasted into controllers.

    3. Request-Response Flow in Spring Boot

    A simplified request flow in a Spring Boot web application is:

    Client -> Servlet Container (Tomcat) -> Filters -> DispatcherServlet
       -> Interceptors -> Controller -> Service -> Repository

    The response returns through the same components in reverse order:

    Repository -> Service -> Controller -> Interceptors
           -> DispatcherServlet -> Filters -> Client

    Filters belong to the Servlet layer. They execute before the request reaches Spring MVC's DispatcherServlet. Because a Filter executes before the DispatcherServlet, it can reject a request before Spring MVC performs controller mapping. A Filter operates at a lower web level than a Spring MVC Interceptor.

    Where does a filter execute?

    Client -> Tomcat -> Filter 1 -> Filter 2 -> DispatcherServlet -> Controller

    4. What Is a Filter?

    A Filter acts like a checkpoint through which an HTTP request and response pass. It can run logic before the request continues, and logic after downstream request processing returns. Conceptually, a Filter works like this:

    doSomethingBefore();
chain.doFilter(request, response);
doSomethingAfter();

    The call to chain.doFilter(...) passes control to the next component in the request-processing chain.

    A Filter can inspect request headers, cookies, query parameters, and other metadata; add response headers; log request and response details; measure total request duration; validate authentication information; wrap the request or response; allow the request to continue; or stop the request immediately.

    Because Filters operate at the Servlet layer, they are not limited to controller endpoints. Depending on their registration, they may also apply to paths such as /error, /favicon.ico, /static/logo.png, Servlet endpoints, and Spring MVC endpoints.

    5. Filters Come from the Servlet API

    Filters are not originally a Spring feature. They are defined by the Servlet specification. In Spring Boot 3 and modern Jakarta-based applications, the Filter interface is available from jakarta.servlet.Filter. A simplified version of the interface looks like this:

    public interface Filter {

    default void init(FilterConfig filterConfig)
            throws ServletException {
    }

    void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain
    ) throws IOException, ServletException;

    default void destroy() {
    }
}

    The Filter lifecycle contains three methods:

    Method Purpose
    init() Called when the Filter is initialized
    doFilter() Called when a matching request passes through the Filter
    destroy() Called when the Filter is removed or the application shuts down

    In most Spring Boot applications, custom Filter logic is mainly written inside doFilter().

    Spring Boot 2 vs Spring Boot 3 Imports

    Spring Boot 2 applications generally used the javax.servlet package; Spring Boot 3 uses jakarta.servlet:

    Spring Boot 2 (javax) Spring Boot 3 (jakarta)
    import javax.servlet.Filter; import jakarta.servlet.Filter;
    import javax.servlet.FilterChain; import jakarta.servlet.FilterChain;
    import javax.servlet.ServletRequest; import jakarta.servlet.ServletRequest;
    import javax.servlet.ServletResponse; import jakarta.servlet.ServletResponse;

    For Spring Boot 3, use import jakarta.servlet.Filter;. Do not use import javax.servlet.Filter;.

    Interviewer's perspective: The javax to jakarta rename comes from Java EE moving to the Eclipse Foundation as Jakarta EE. Mixing the two packages in one project is a classic "why does my filter not compile or run" interview story.

    Why Filter Uses ServletRequest and ServletResponse

    The standard Filter interface uses generic Servlet abstractions, ServletRequest and ServletResponse. These types are not limited to HTTP-specific operations. In a normal Spring Boot web application requests are HTTP requests, so they can be cast to HTTP-specific types:

    HttpServletRequest httpRequest = (HttpServletRequest) request;
httpRequest.getMethod();
httpRequest.getRequestURI();
httpRequest.getHeader("Authorization");

HttpServletResponse httpResponse = (HttpServletResponse) response;
httpResponse.setStatus(401);
httpResponse.setHeader("X-App-Name", "Student API");

    After casting, we can access HTTP-specific information. This is why the interface uses generic types: a Filter must work at the Servlet layer, before any HTTP-aware Spring MVC processing begins.

    Role of DispatcherServlet

    DispatcherServlet is the central Servlet of Spring MVC. It coordinates the MVC request-processing flow. Its responsibilities include finding the correct controller method, resolving controller method arguments, invoking the controller, handling controller return values, converting Java objects into JSON, coordinating exception handling, and producing the HTTP response. Filters execute before this Spring MVC processing begins:

    Tomcat -> Registered Filters -> DispatcherServlet -> Controller Mapping and Execution

    At filter time Spring MVC has usually not yet selected the controller method. A Filter can access HTTP method, request URI, query parameters, headers, cookies, remote address, and the request body stream, but not controller metadata such as StudentController.getStudentById() or @GetMapping("/api/students/{id}"). Logic that depends on the selected handler is generally better suited to a Spring MVC Interceptor.

    Aspect Filter Interceptor
    Defined by Servlet API Spring MVC
    Runs Before DispatcherServlet After DispatcherServlet, before controller
    Sees controller method No (not yet selected) Yes (handler is known)
    Typical use Logging, auth, encoding, headers, blocking Handler-aware logic
    Level Lower, Servlet layer Higher, Spring MVC layer

    6. Creating a Custom Filter

    A basic custom Filter can be created by implementing the Filter interface and registering the class as a Spring bean.

    package in.strikes.filterdemo.filter;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import org.springframework.stereotype.Component;

import java.io.IOException;

@Component
public class LoggingFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain
    ) throws IOException, ServletException {
        System.out.println("Request entered the Filter");
        chain.doFilter(request, response);
        System.out.println("Response passed through the Filter");
    }
}

    What does the Filter receive?

    Parameter Meaning
    request The incoming request
    response The outgoing response
    chain The remaining Filters and final target Servlet
    • Before-chain logic: System.out.println("Request entered the Filter"); runs before the request reaches the next Filter or DispatcherServlet.
    • Continuing the request: chain.doFilter(request, response); passes the request to the next Filter, or to the DispatcherServlet when the current Filter is the final Filter.
    • After-chain logic: System.out.println("Response passed through the Filter"); runs after downstream processing returns.

    7. Understanding doFilter() and FilterChain

    The main method of a Filter is doFilter(ServletRequest, ServletResponse, FilterChain).

    The request object provides general request information such as getParameter("name"), getRemoteAddr(), and getContentType(). For HTTP-specific information, cast it, then use methods such as getMethod(), getRequestURI(), getRequestURL(), getHeader("Authorization"), getCookies(), getQueryString(), and getSession().

    The response object represents the outgoing response. It can set the status, set headers, set the content type, and write to the response body:

    httpResponse.setStatus(401);
httpResponse.setHeader("X-App", "Demo");
httpResponse.setContentType("application/json");
httpResponse.getWriter().write("...");

    FilterChain represents everything that remains after the current Filter: other registered Filters, DispatcherServlet, controller execution, service and repository calls, and response conversion. The current Filter does not need to know which exact component comes next. It only calls:

    chain.doFilter(request, response);

    Suppose an application contains three Filters: AuthenticationFilter, LoggingFilter, and TimingFilter. The request-processing chain may look like this:

    AuthenticationFilter -> LoggingFilter -> TimingFilter -> DispatcherServlet

    Every Filter has two choices.

    • Continue the request: chain.doFilter(request, response);
    • Stop the request: response.setStatus(HttpServletResponse.SC_UNAUTHORIZED); return;

    If a Filter does not call chain.doFilter(...), the request does not continue to the remaining Filters or the controller.

    8. Request and Response Execution Order and @Order

    Filters surround the remaining request-processing chain. Suppose two Filters are registered:

    AuthenticationFilter -> LoggingFilter -> Controller

    The incoming request executes in normal order, while the response-side logic executes in reverse order.

    @Component
@Order(1)
public class AuthenticationFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
            FilterChain chain) throws IOException, ServletException {
        System.out.println("Authentication before");
        chain.doFilter(request, response);
        System.out.println("Authentication after");
    }
}

@Component
@Order(2)
public class LoggingFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
            FilterChain chain) throws IOException, ServletException {
        System.out.println("Logging before");
        chain.doFilter(request, response);
        System.out.println("Logging after");
    }
}

@GetMapping("/hello")
public String hello() {
    System.out.println("Controller");
    return "Hello";
}

    Output:

    Authentication before
Logging before
Controller
Logging after
Authentication after

    The execution can be visualized as:

    AuthenticationFilter before -> LoggingFilter before -> Controller
     -> LoggingFilter after -> AuthenticationFilter after

    Mnemonic: FILO - First In, Last Out. The first filter's before-logic runs first, and its after-logic runs last.

    Filter Ordering with @Order

    When multiple Filters are registered, their order affects request and response processing. Annotate each filter with @Order(n); lower numbers run earlier on the incoming request.

    @Component
@Order(1)
public class FirstFilter implements Filter {
    // Filter logic
}

@Component
@Order(2)
public class SecondFilter implements Filter {
    // Filter logic
}

    For an incoming request:

    FirstFilter -> SecondFilter -> DispatcherServlet

    For the returning response:

    DispatcherServlet -> SecondFilter -> FirstFilter

    What happens without @Order? A Filter registered as a Spring bean still executes. However, when several Filters depend on a particular sequence, the application should define their order explicitly instead of relying on an observed default order.

    9. Common Use Cases of Filters

    Request Logging

    A Filter can log common request information for every API.

    String method = httpRequest.getMethod();
String uri = httpRequest.getRequestURI();
String remoteAddress = httpRequest.getRemoteAddr();
String userAgent = httpRequest.getHeader("User-Agent");

    Example log: Method: GET, URI: /api/students, Remote IP: 192.168.1.10, User-Agent: PostmanRuntime.

    Authentication Token Inspection

    A Filter can inspect an authentication header:

    String token = httpRequest.getHeader("Authorization");

    It may then check whether the token exists, validate it, reject invalid requests, extract user information, and populate security-related context. Spring Security itself relies heavily on a chain of Filters. In a real secured application, authentication should normally be integrated with Spring Security rather than implemented through an unrelated custom Filter.

    Character Encoding

    A Filter can enforce consistent request and response encoding with request.setCharacterEncoding("UTF-8") and response.setCharacterEncoding("UTF-8"). Spring also provides built-in support such as CharacterEncodingFilter.

    Common Response Headers

    A Filter can add headers that should appear in multiple responses:

    httpResponse.setHeader("X-Application-Name", "Student Service");
httpResponse.setHeader("X-Content-Type-Options", "nosniff");

    Common purposes include security headers, request tracking, application metadata, and cache control.

    Measuring Request Duration

    A Filter can measure the time spent in the downstream request-processing chain.

    long startTime = System.currentTimeMillis();
chain.doFilter(request, response);
long duration = System.currentTimeMillis() - startTime;
System.out.println("Duration: " + duration + " ms");

    This generally includes processing performed by remaining Filters, DispatcherServlet, Interceptors, Controller, Service, Repository, and response conversion. The exact measurement depends on the position of the Filter and how the response is handled.

    Correlation or Trace IDs

    A Filter can generate a unique ID for every request:

    String requestId = UUID.randomUUID().toString();
httpResponse.setHeader("X-Request-Id", requestId);

    The same ID can be included in application logs, response headers, downstream service calls, and error reports, making it easier to trace one request across multiple log entries or services.

    Blocking Unwanted Requests

    A Filter can reject a request before it reaches Spring MVC:

    String apiKey = httpRequest.getHeader("X-API-KEY");
if (apiKey == null) {
    httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
chain.doFilter(request, response);

    The return statement stops the current Filter method. Because chain.doFilter(...) was not called, the controller does not execute.

    10. Blocking a Request and Returning JSON

    A Filter can directly create an error response without allowing the request to reach the controller.

    package in.strikes.filterdemo.filter;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.stereotype.Component;

import java.io.IOException;

@Component
public class ApiKeyFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain
    ) throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String apiKey = httpRequest.getHeader("X-API-KEY");
        if (apiKey == null || !apiKey.equals("secret123")) {
            httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            httpResponse.setContentType("application/json");
            httpResponse.setCharacterEncoding("UTF-8");
            httpResponse.getWriter().write(
                    """
                    {
                      "message": "Invalid or missing API key"
                    }
                    """
            );
            return;
        }
        chain.doFilter(request, response);
    }
}

    Request flow when the API key is valid:

    API key is valid -> chain.doFilter(...) -> Request continues

    Request flow when the API key is invalid:

    API key is missing or invalid -> Write a 401 response
     -> Return without calling chain.doFilter(...) -> Request stops

    The hard-coded key in this example is only for understanding Filter behaviour. Real authentication should use a proper security mechanism.

    Using try-finally for Timing and Cleanup

    If downstream processing throws an exception, the statement after chain.doFilter(...) may not execute normally:

    chain.doFilter(request, response);
System.out.println("Request completed");

    A safer pattern for timing, cleanup, or final logging is:

    long startTime = System.currentTimeMillis();
try {
    chain.doFilter(request, response);
} finally {
    long duration = System.currentTimeMillis() - startTime;
    System.out.println("Duration: " + duration + " ms");
}

    The finally block executes whether downstream processing completes normally or throws an exception.

    Important: Put timing and final logging in a finally block. Plain statements after chain.doFilter(...) are skipped when a downstream exception propagates.

    11. Complete Logging Filter, Logging Safety, and Responsibilities

    Complete Request Logging Filter

    The following Filter logs HTTP method, request path, query string, remote IP address, response status, and total duration.

    package in.strikes.filterdemo.filter;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

import java.io.IOException;

@Component
public class RequestLoggingFilter implements Filter {

    private static final Logger logger =
            LoggerFactory.getLogger(RequestLoggingFilter.class);

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain
    ) throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String method = httpRequest.getMethod();
        String requestUri = httpRequest.getRequestURI();
        String queryString = httpRequest.getQueryString();
        String remoteAddress = httpRequest.getRemoteAddr();

        String completePath = queryString == null
                ? requestUri
                : requestUri + "?" + queryString;

        long startTime = System.currentTimeMillis();
        logger.info("Incoming request: method={}, path={}, ip={}",
                method, completePath, remoteAddress);

        try {
            chain.doFilter(request, response);
        } finally {
            long duration = System.currentTimeMillis() - startTime;
            logger.info("Request completed: method={}, path={}, status={}, duration={}ms",
                    method, completePath, httpResponse.getStatus(), duration);
        }
    }
}

    Using a logging framework such as SLF4J is preferred over System.out.println() in real applications because logs can be configured, filtered, stored, and integrated with monitoring tools.

    Where Should Response Logic Be Placed?

    Adding a response header after downstream processing may work when the response has not yet been committed:

    chain.doFilter(request, response);
httpResponse.setHeader("X-Test", "value");

    However, once the response body or headers have been flushed, changing the status or headers may be too late. Headers that must definitely be present should generally be added before continuing the chain:

    httpResponse.setHeader("X-Test", "value");
chain.doFilter(request, response);
    • Good candidates for pre-processing: request validation, authentication checks, required response headers, character encoding, request setup.
    • Good candidates for post-processing: logging the final response status, measuring duration, metrics collection, cleanup operations.

    Logging Safety

    Filters can access sensitive request information, but not every value should be written to logs. Avoid logging authorization tokens, session cookies, API keys, passwords, credit card information, and sensitive personal information. Logging entire request headers or bodies without filtering can create serious security and privacy problems. Log only the information required for debugging, auditing, or monitoring, and mask sensitive values wherever necessary.

    Filter Responsibilities at a Glance

    Requirement Is a Filter suitable?
    Log all incoming HTTP requests Yes
    Read or validate request headers Yes
    Add a common response header Yes
    Block a request before Spring MVC Yes
    Apply character encoding Yes
    Measure overall request duration Yes
    Work with the selected controller method Usually no; prefer an Interceptor
    Implement full application security manually No; prefer Spring Security
    Execute business logic for one API No; keep it in controller or service layers

    Interviewer's perspective: The strongest filter answer always includes the boundary: yes for HTTP-level, cross-cutting work; no for handler-aware logic (Interceptor) or real security (Spring Security).

    12. Myth vs Reality

    Myth Reality
    "Filters are a Spring feature" Filters come from the Servlet API (jakarta.servlet.Filter); Spring Boot just registers and orders them.
    "A Filter knows which controller method will run" No; controller mapping happens later in DispatcherServlet. Use an Interceptor for handler-aware logic.
    "Filters and Interceptors are the same thing" Filters sit at the Servlet layer before DispatcherServlet; Interceptors sit inside Spring MVC after it.
    "You can return from doFilter and the request still continues" Returning without calling chain.doFilter(...) stops the request before the controller.
    "Statements after chain.doFilter always run" They can be skipped on a downstream exception; use try-finally for timing and cleanup.
    "Spring Boot 2 and Spring Boot 3 imports are interchangeable" No; Boot 2 uses javax.servlet, Boot 3 uses jakarta.servlet.
    "A filter can safely log all headers" No; tokens, cookies, API keys, and personal data must not be logged.
    "Filter order never matters" Order changes request and response processing; define it with @Order when sequence matters.

    13. Common Trap Questions

    Trap 1 - "Filters are part of Spring MVC." Verdict: False. Filters are defined by the Servlet specification. They run at the Servlet layer before Spring MVC's DispatcherServlet even starts.

    Trap 2 - "Skipping chain.doFilter just skips the next filter." Verdict: False. Skipping chain.doFilter(...) stops the whole remaining chain, including the controller, so the request never reaches it.

    Trap 3 - "A Filter can inspect @GetMapping annotations and handler metadata." Verdict: False. At filter time the controller method has not been selected. That kind of logic belongs in a Spring MVC Interceptor.

    Trap 4 - "The response-side code after chain.doFilter always executes." Verdict: False. If downstream processing throws, it may be skipped. Wrap the call in try-finally to guarantee timing and cleanup.

    Trap 5 - "javax.servlet.Filter still works in Spring Boot 3." Verdict: False. Spring Boot 3 uses jakarta.servlet.Filter; mixing the old javax package is a compile/run failure.

    Trap 6 - "You can add any response header after chain.doFilter." Verdict: Only if the response is not yet committed. Once headers or body are flushed, later changes are too late; add required headers before continuing the chain.

    Trap 7 - "A custom auth filter is the right way to do real security." Verdict: Misleading. Custom filters are fine for learning and simple checks, but production authentication belongs in Spring Security, which is itself a filter chain.

    14. Points to Remember

    1. Filters handle cross-cutting, HTTP-level concerns that would otherwise be copy-pasted into controllers.
    2. Filters come from the Servlet API (jakarta.servlet.Filter), not from Spring MVC.
    3. A Filter runs before the DispatcherServlet, so it can reject a request before controller mapping.
    4. doFilter() is the main method; init() and destroy() handle lifecycle only.
    5. chain.doFilter(request, response) continues the request to the next filter or the target Servlet.
    6. Not calling chain.doFilter(...) stops the request immediately (short-circuit).
    7. Request-side filter logic runs in order; response-side logic runs in reverse order (FILO).
    8. Use @Order when the sequence of multiple filters matters instead of relying on defaults.
    9. Wrap chain.doFilter(...) in try-finally for guaranteed timing, cleanup, and final logging.
    10. Never log tokens, cookies, API keys, passwords, or personal data; prefer SLF4J over System.out.println().

    15. Likely Interview Questions

    Question Crisp Answer
    What is a Filter in Spring Boot? A Servlet-layer checkpoint that runs logic before a request reaches DispatcherServlet and after processing returns.
    Why do we need Filters? To centralize cross-cutting HTTP logic (logging, auth, timing, headers) so controllers stay focused and no endpoint is forgotten.
    Where does a Filter run in the request flow? In the Servlet layer, after Tomcat and before the DispatcherServlet; the response returns through it in reverse.
    What is chain.doFilter()? The call that passes control to the remaining filters and finally the target Servlet; without it the request stops.
    What are the three Filter lifecycle methods? init() on initialization, doFilter() on each matching request, destroy() on shutdown or removal.
    Difference between javax.servlet and jakarta.servlet? Spring Boot 2 used javax.servlet; Spring Boot 3 uses jakarta.servlet after the Java EE to Jakarta EE rename.
    Why does doFilter use ServletRequest/ServletResponse? The Filter interface is generic to the Servlet layer, not HTTP-only; cast to HttpServletRequest/HttpServletResponse for HTTP details.
    Filter vs Interceptor? A Filter runs before DispatcherServlet at the Servlet layer; an Interceptor runs inside Spring MVC after it and can see the handler.
    How do you block a request in a Filter? Set the status/body and return without calling chain.doFilter(...), so the controller never executes.
    Why use try-finally around chain.doFilter? Statements after the call can be skipped on an exception; finally guarantees timing and cleanup execute.
    How do you control filter order? Annotate each filter with @Order(n); lower numbers run earlier on the request and later on the response.
    What should never be logged in a Filter? Authorization tokens, session cookies, API keys, passwords, card details, and sensitive personal data.
