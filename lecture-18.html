    Part 3 · OOP Deep Dive · Lecture 18

    AutoBoxing, Abstract classes & POJOs | Why only one public class in java file

    15 sections · interview-oriented · both themes

    Scope evidence: "AutoBoxing, Abstract classes & POJOs | Why only one public class in java file" (playlist map, verified). Repo evidence: 4 Demo files.

    Java has exactly two kinds of type — primitives and references — yet the collections framework, generics and reflection all demand objects, so the wrapper classes exist to bridge the gap. Once wrappers exist, the compiler can convert between primitive and object for you, and that convenience is exactly where the traps begin. This lecture covers the eight wrappers, the Java 5 autoboxing and unboxing machinery, the Integer cache that makes == on wrappers unreliable, and the pitfalls of silent boxing. It then recaps abstract classes through the Number hierarchy, defines the POJO contract every framework reflects over, and explains why a .java file may hold only one public top-level class.

    1. Why Wrapper Classes Exist

    A wrapper class is a reference type that packages one primitive value inside an object. Four concrete pressures make them necessary:

    1. Collections and generics require objects. Generics are erased to reference types, so ArrayList<int> is a compile error while ArrayList<Integer> is correct. Wrappers are the only way to put numbers in a collection.
    2. Objects carry methods. Primitives have no methods, so Integer.parseInt("42"), Double.parseDouble("3.14"), Integer.toBinaryString(5), Character.isDigit('7') and Boolean.parseBoolean("true") all live on the wrappers. Parsing and conversion (Lecture 5) are wrapper services.
    3. null must be representable. A database column with no value or an optional JSON field cannot be stored in an int; an Integer can be null.
    4. Utility constants. Integer.MAX_VALUE, Integer.MIN_VALUE, Long.MAX_VALUE, Double.NaN and Double.POSITIVE_INFINITY are wrapper constants used throughout the language (Lecture 4).

    All eight wrappers live in java.lang, which is imported automatically, so no import statement is ever needed for them.

    Important A wrapper is an object, so it lives on the heap and its variable is a reference. Assigning, comparing and unboxing wrappers are therefore object operations, not primitive operations — the entire pitfall catalogue follows from this one sentence.

    2. The Eight Wrapper Types

    There is exactly one wrapper per primitive, and each extends a hierarchy rather than a single root:

    Primitive Wrapper Parsing method (example) Extends
    byte Byte Byte.parseByte("12") Number
    short Short Short.parseShort("12") Number
    int Integer Integer.parseInt("42") Number
    long Long Long.parseLong("42") Number
    float Float Float.parseFloat("3.14") Number
    double Double Double.parseDouble("3.14") Number
    char Character Character.isDigit('7') Object
    boolean Boolean Boolean.parseBoolean("true") Object

    Two structural facts interviewers like:

    1. The six numeric wrappers extend the abstract class Number (section 7); Character and Boolean extend Object directly because they are not numeric.
    2. Wrappers are immutable — once constructed, the value never changes. x++ on an Integer builds a new object and rebinds the variable; it does not mutate the old one.

    Memory aid — the wrapper name is always the primitive name capitalised, with the only full-word exception being int to Integer and char to Character.

    3. Autoboxing and Unboxing (Java 5)

    Before Java 5, wrapping was manual: Integer i = Integer.valueOf(42); and int n = i.intValue();. Java 5 added the compiler sugar that does it for you:

    • Autoboxing — automatic conversion of a primitive to its wrapper: Integer i = 42;
    • Unboxing — automatic conversion of a wrapper back to its primitive: int n = i;

    Conversion happens at four sites: assignment, method arguments and returns, collection operations, and mixed arithmetic. The compiler inserts the valueOf / intValue call invisibly.

    // Demo.java — autoboxing and unboxing in everyday code
import java.util.ArrayList;

public class Demo {
    public static void main(String[] args) {
        Integer boxed = 42;            // autoboxing: int -> Integer (Integer.valueOf(42))
        int unboxed = boxed;           // unboxing: Integer -> int  (boxed.intValue())

        ArrayList<Integer> list = new ArrayList<>();
        list.add(7);                   // boxed automatically on insert
        int first = list.get(0);       // unboxed automatically on read

        System.out.println(boxed + unboxed + first);   // 42 + 42 + 7 = 91
    }
}

    Interviewer's perspective The correct vocabulary is that boxing is a compiler transformation, not a JVM feature. There is no bytecode instruction called autoboxing — javap shows an ordinary invokestatic java/lang/Integer.valueOf. Saying "the JVM boxes" loses the point.

    4. The Integer Cache — Why == on Wrappers Lies

    Autoboxing does not call new Integer(...); it calls the static factory Integer.valueOf(int). That factory keeps a cache of pre-built objects for the range -128 to 127, so small wrappers share instances:

    // Demo2.java — the cache trap in one program
public class Demo2 {
    public static void main(String[] args) {
        Integer a = 127, b = 127;
        Integer c = 128, d = 128;

        System.out.println(a == b);        // true  — same cached object
        System.out.println(c == d);        // false — two distinct objects
        System.out.println(c.equals(d));   // true  — same content
    }
}

    The rule and its consequences:

    1. == compares references for wrappers, so results inside the cache differ from results outside it — a nonsensical-seeming split with no basis in the values.
    2. Always use equals (or unbox to int first) to compare wrapper content. Never rely on ==.
    3. The cache is mandated for -128 to 127 by the JLS; Boolean caches both values, Byte caches its entire range, and Character caches 0 to 127. A JVM may cache more, so code that depends on identity beyond the standard range is fragile.

    Important The cache is an implementation of valueOf; new Integer(100) bypasses it, which is exactly why the constructor form is deprecated since Java 9. Use Integer.valueOf(100) or the implicit literal.

    5. Autoboxing Pitfalls

    The sugar is convenient but hides allocations and hazards. The recurring failures:

    Pitfall Example What goes wrong
    NPE on unboxing null Integer x = null; int y = x; Throws NullPointerException at the unboxing site
    Identity comparison a == b for two wrappers Compares references, not values; cache-dependent
    Hidden allocation in loops for (Integer i = 0; i < n; i++) Boxes a new object per iteration, taxing the GC
    Overload ambiguity foo(long) vs foo(Integer) for foo(5) Primitive widening wins before boxing (Lecture 11)
    Ternary unboxing map.get(k) == 0 ? ... The 0 forces unboxing of a possibly-null value 
    // Demo3.java — unboxing a null wrapper throws NullPointerException
public class Demo3 {
    static Integer maybe = null;

    public static void main(String[] args) {
        int value = maybe;                 // unboxing null -> NullPointerException
        System.out.println(value);
    }
}

    Performance guidance: in hot loops and numeric code, prefer primitive int, long, double variables and let boxing happen only at the collection boundary. The object overhead measured in Lecture 14 (an Integer is far larger than an int) is why boxing in a tight loop is a real cost, not a stylistic preference.

    Trap — "But the loop works!" Mixed wrapper and primitive arithmetic silently unboxes at each step, so the code is both correct and slow; correctness is not evidence that boxing is not happening.

    6. Primitive vs Wrapper

    Aspect Primitive Wrapper
    Kind Value type, not an object Reference type, an object on the heap
    Examples int, double, char, boolean Integer, Double, Character, Boolean
    null allowed No Yes
    Default (field) 0, 0.0, false, '\u0000' null
    Usable in collections/generics No Yes
    Methods available No Yes (parseInt, equals, toString)
    Memory Narrow, fixed size (Lecture 3) Object header plus value, larger
    == meaning Value comparison Reference comparison
    Content comparison == equals
    Best used for Numeric computation and hot loops Collections, generics, nullable fields

    Reading the table: use primitives whenever a value suffices, and reach for wrappers only where the API or a null demands an object.

    7. Abstract Classes Recap (Refer to Lecture 17)

    An abstract class is a class declared with the abstract keyword that is incomplete by design and therefore cannot be instantiated with new. It exists to be extended.

    Feature Abstract class Concrete class
    Instantiable No — new is a compile error Yes
    Abstract methods Allowed; subclasses must implement unless they too are abstract Not allowed
    Concrete methods Allowed (any mix) Allowed
    Constructors Allowed — run via super(...) when a child is built Allowed
    Fields and state Allowed, including shared state Allowed
    Purpose Partial implementation plus a contract for subclasses Full implementation

    Rules that matter here:

    1. An abstract method has no body and must be implemented by the first concrete subclass; an abstract class may have zero abstract methods (then its only purpose is to block instantiation).
    2. An abstract method can never be private, static, final or a constructor — each of those would make overriding or interaction impossible.
    3. The Number hierarchy proves the pattern: java.lang.Number is an abstract class declaring intValue(), longValue(), floatValue() and doubleValue(). Integer, Long, Double, Float, Short and Byte extend it and supply the conversions. Code can hold a Number and call doubleValue() polymorphically without knowing the subclass.

    Interviewer's perspective "Can an abstract class have a constructor?" Yes — it runs when a concrete subclass is instantiated through super(). "Can it have no abstract methods?" Also yes. "Can it be final?" No — abstract and final are contradictory and a compile error (Lecture 17).

    8. POJOs, JavaBeans, DTO, Entity and VO

    A POJO (Plain Old Java Object) is a class with private fields, a public no-arg constructor, public getters and setters, and no dependency on any framework base class or interface. It is the ordinary object that every modern framework reflects over.

    // Demo4.java — a POJO with private fields, a no-arg constructor and accessors
public class Demo4 {
    private String name;
    private int age;

    public Demo4() { }                          // no-arg constructor (reflection needs it)

    public String getName() { return name; }    // getter
    public void setName(String name) { this.name = name; }   // setter
    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }

    public static void main(String[] args) {
        Demo4 person = new Demo4();
        person.setName("Java");
        person.setAge(30);
        System.out.println(person.getName() + " " + person.getAge());
    }
}

    JavaBeans naming conventions give reflection something predictable to read: getX / setX for properties (with isX for boolean getters), a public no-arg constructor, and serializable state. Spring, Hibernate and Jackson all rely on these naming rules to bind JSON, rows and beans without being told the field names.

    Three labels that are often confused:

    • DTO (Data Transfer Object) — a POJO whose only job is to carry data across a boundary (for example, between layers or over the wire).
    • Entity — a POJO mapped to a persistent store, usually with an identity (a primary key) and lifecycle managed by a persistence framework.
    • VO (Value Object) — a POJO whose identity is its data, ideally immutable and compared by value.

    Important "POJO" says nothing about getters and setters being present; it says the class depends on no framework. A class with public fields and no methods is still a POJO, but it violates the JavaBeans conventions and is invisible to most frameworks.

    9. Why Only One Public Class per .java File

    Java enforces a file-name/class-name agreement for public top-level types:

    1. A .java file may contain many top-level classes, but at most one of them may be public.
    2. If a class is public, the file must be named after it: public class Hello must live in Hello.java. Otherwise the compiler reports class Hello is public, should be declared in a file named Hello.java (Lecture 2).
    3. The other top-level classes in the file may exist, but they are package-private (no modifier) — visible only within the same package.
    4. The JVM does not load files; it loads classes by name from .class files. javac Hello.java produces a separate Hello.class for every top-level class it declares, so java Hello can find Hello regardless of how many classes shared the source file.

    The reason is a design contract: a public type is reachable by its fully qualified name, so the toolchain needs one canonical source location for it. A mismatched file name breaks that contract, and two public classes in one file would demand two file names at once — impossible.

    Important The public restriction is on top-level classes only. public nested classes are fully legal inside another class or a source file (developed in Lecture 19), because their binary names are derived from the enclosing class, not from the file.

    10. Pitfalls Catalogue

    1. Unboxing null — Integer to int on a null throws NullPointerException; guard with x != null or use Objects.requireNonNullElse.
    2. Cached == confusion — == on wrappers is reference identity, true only inside the cache range; use equals.
    3. Autoboxing in loops — accumulator wrappers create a new object per iteration; use a primitive accumulator.
    4. Filename/public-class mismatch — a public class in a wrongly named file is a compile error.
    5. Two public classes in one file — also a compile error, because the file cannot match both names.
    6. equals on primitives — int x; x.equals(5) does not compile; primitives have no methods.
    7. Wrapper compared with primitive — Integer a versus int b unboxes a; if a is null this is an NPE, not false.
    8. Overload resolution surprise — primitive widening beats boxing, so foo(5) picks foo(long) over foo(Integer) (Lecture 11).
    9. Ternary unboxing — a wrapper and a primitive in one ternary expression force unboxing of the wrapper.
    10. Deprecated constructors — new Integer(42) bypasses the cache and is deprecated; prefer Integer.valueOf(42).

    11. Myth vs Reality

    Myth Reality
    "Integer and int are interchangeable everywhere." They differ in nullability, storage, comparison and whether they can be type arguments.
    "a == b is true whenever the values are equal." For wrappers == compares references; it is true only when both share a cached or same instance.
    "Autoboxing means the JVM converts primitives automatically." It is a compile-time transformation that inserts valueOf and intValue calls.
    "A .java file can hold only one class." It can hold many top-level classes; only one may be public, and the file is named after it.
    "POJO means a class needs getters and setters." POJO means no framework dependency; getters/setters are the separate JavaBeans convention.

    12. Common Trap Questions

    Trap 1 — Integer a = 127, b = 127; a == b is true, but the same with 128 is false. The cache range -128 to 127 is the reason; equals would return true in both cases.

    Trap 2 — Integer x = null; int y = x; throws NullPointerException, not a compile error and not a default value. The unboxing call runs at runtime.

    Trap 3 — "Does ArrayList<int> compile?" No — generics accept reference types only; ArrayList<Integer> is correct and boxes on insert.

    Trap 4 — "Can a .java file contain two classes?" Yes, if at most one is public. Two public classes are a compile error.

    Trap 5 — "Can Number be instantiated?" No — it is abstract; you instantiate its subclasses and rely on doubleValue() polymorphism.

    Trap 6 — "Is a class with public fields a POJO?" Structurally yes, but it breaks the JavaBeans naming convention that frameworks use for reflection.

    Trap 7 — "Does comparing a primitive with a wrapper use equals?" No — one operand being primitive forces unboxing, so Integer.valueOf(0) == 0 is a value comparison, and a null wrapper throws.

    13. Points to Remember

    1. Wrappers exist because generics, collections, methods and null all require objects.
    2. The eight wrappers are Integer, Long, Double, Float, Short, Byte, Character, Boolean.
    3. The six numeric wrappers extend the abstract class Number; Character and Boolean do not.
    4. Autoboxing and unboxing arrived in Java 5 and are compiler sugar, not JVM instructions.
    5. Integer.valueOf caches -128 to 127, so == on wrappers is cache-dependent; always use equals.
    6. Unboxing a null wrapper throws NullPointerException.
    7. Boxing inside hot loops allocates objects and pressures the GC; prefer primitives.
    8. An abstract class cannot be instantiated, may hold abstract and concrete methods, and may have constructors and fields.
    9. A POJO is a framework-free object following the JavaBeans getter/setter and no-arg-constructor conventions that frameworks reflect over.
    10. A .java file may hold many top-level classes but only one public, and the file must be named after it; the JVM loads classes by name from .class files.

    14. Likely Interview Questions

    Question Crisp Answer
    What is a wrapper class? A reference type that packages one primitive as an object so it can be used with generics, collections and methods.
    Name the eight wrappers. Integer, Long, Double, Float, Short, Byte, Character, Boolean — all in java.lang.
    Why do wrappers exist? Collections and generics need objects, primitives need methods like parseInt, and some fields must be null.
    What is autoboxing and unboxing? Compiler-inserted conversion between primitives and wrappers: Integer.valueOf on the way in, intValue on the way out (Java 5).
    Why is Integer a = 127, b = 127; a == b true but false for 128? The Integer cache holds -128 to 127; == compares references, so only cached values share an instance.
    How should wrappers be compared? With equals, or by unboxing to a primitive first; never with ==.
    What happens when you unbox null? A NullPointerException at runtime.
    Is autoboxing a JVM feature? No, a compile-time transformation expressed as ordinary valueOf/xxxValue calls.
    Can an abstract class have a constructor? Yes; it runs through super(...) when a concrete subclass is instantiated, even though the abstract type itself cannot be new-ed.
    What is a POJO? A plain Java object with no framework dependencies, typically private fields with getters/setters and a no-arg constructor (the JavaBeans convention).
    DTO vs entity vs VO? DTO carries data across a boundary; entity is persisted with an identity; VO is an immutable value compared by its data.
    Why only one public class per file? The file must be named after its single public top-level class; the JVM loads classes by name from separate .class files.

    15. Final Summary

    primitive (int) --autoboxing--> wrapper (Integer) --cache -128..127--> equals() for content
primitive (int) <--unboxing--- wrapper (Integer)   (null unbox -> NullPointerException)

Number (abstract) ⊃ Integer, Long, Double, Float, Short, Byte
POJO: private fields + no-arg constructor + getters/setters + no framework
One file --> many classes, one public --> file named after it --> one .class per class
    • Wrappers → objects for generics, methods and null; six extend abstract Number
    • Autoboxing → Java 5 compiler sugar; valueOf in, intValue out
    • Cache → -128 to 127 shared instances; compare wrappers with equals, never ==
    • Abstract class → cannot instantiate, may hold state and constructors, contract for subclasses
    • POJO → framework-free object with JavaBeans accessors that frameworks reflect over
    • File rule → one public top-level class, file named after it; the JVM loads classes by name

    Golden rule Treat a wrapper as an object the moment it appears: never compare it with ==, never unbox it before checking for null, and never box inside a hot loop — and let the abstract Number hierarchy do the polymorphism.

    One-line takeaway: wrappers turn primitives into objects (with a cache that breaks ==), abstract classes supply partial contracts like Number, POJOs are the framework-free objects reflected over at runtime, and the one-public-class-per-file rule is what lets the JVM find every class by name.
