    Part 5 · Collections, Lambdas & Streams · Lecture 36

    Comparable Interface in Java | Collections class | Comparing Objects

    18 sections · interview-oriented · both themes

    Scope evidence: "Comparable Interface in Java | Collections class | Comparing Objects" (playlist map, verified). Repo evidence: 2 Demo files (code/Demo.java, code/Demo2.java).

    Any collection that must be ordered, searched, deduplicated or prioritized needs an ordering rule, yet the JVM cannot know which field of a custom object decides "smaller". Java therefore exposes two contracts for object comparison: Comparable<T>, the natural ordering a class carries inside itself, and Comparator<T>, an ordering supplied from outside. This lecture defines both, examines the compareTo sign convention and its contract, maps the JDK sorting APIs, tours the Collections utility class, and isolates the traps that break sorted collections: subtraction overflow, and an ordering that disagrees with equals.

    1. Why Order Objects at All

    An ordering is the price of admission for every sorted or prioritized structure in the JDK. Four consumers need it immediately:

    1. Sequence sorting — Collections.sort, List.sort and Arrays.sort must decide the relative order of every pair.
    2. Sorted collections — TreeSet and TreeMap (Lecture 33) keep their entries in red-black tree order and re-compare on every insert, lookup and delete.
    3. Heaps — PriorityQueue (Lecture 35) uses comparison to sift elements up and down so the smallest or highest-priority element surfaces first.
    4. Searching — Collections.binarySearch only works on a list that has already been ordered with the same rule.

    The JDK already knows how to order primitives, String, and the wrapper classes, because those types implement Comparable. For a user-defined class such as Person, the programmer must state the rule. Java offers exactly two interfaces for that job, and the rest of this lecture builds them out.

    Comparable<T>  -> int compareTo(T o)      natural order, inside the class, java.lang
Comparator<T>  -> int compare(T a, T b)   custom order, outside the class, java.util

    Memory aid Comparable is "I am comparable to my own kind". Comparator is "a third party compares two of them".

    2. The Comparable Interface: Natural Ordering

    java.lang.Comparable<T> declares a single method:

    int compareTo(T o);

    A class that implements it defines its natural ordering — the default rule the JDK will use whenever no other rule is supplied. compareTo returns an int whose sign carries the whole meaning:

    Return value Meaning
    negative (< 0) this comes before o
    zero (0) this and o are equal in this ordering
    positive (> 0) this comes after o

    Only the sign is contractual; the magnitude is an implementation detail. Returning exactly -1, 0 or 1 is sufficient, and returning the difference of two fields is a common but dangerous shortcut (Section 11).

    The key property of Comparable is that it is implemented once, by the class itself, and becomes that type's default everywhere: Collections.sort(list) with no second argument, a TreeSet<Person> with no comparator, and a PriorityQueue<Person> all fall back to compareTo.

    Important String, Integer, Double, LocalDate and every other JDK value type already implement Comparable. Your custom class does not, and is therefore not sortable by natural order until you make it so.

    3. The compareTo Contract

    compareTo is not a free-form comparison; it is a mathematical total order. The Comparable documentation states four requirements:

    1. Antisymmetry — the sign must flip when the operands swap: if a.compareTo(b) < 0 then b.compareTo(a) > 0, and a.compareTo(b) == 0 implies b.compareTo(a) == 0.
    2. Transitivity — if a.compareTo(b) > 0 and b.compareTo(c) > 0, then a.compareTo(c) > 0; the same holds for < 0 and for == 0.
    3. Sign consistency — if a.compareTo(b) == 0, then a.compareTo(c) and b.compareTo(c) must have the same sign for every c.
    4. Consistency with equals (recommended) — a.compareTo(b) == 0 should hold exactly when a.equals(b) is true. This is strongly recommended, not strictly required, but breaking it produces the notorious TreeSet/TreeMap surprises of Section 10.

    Passing null to compareTo should throw a NullPointerException; the natural-ordering sort APIs do so on encountering a null element. Violating any of the first three rules makes a "sorted" collection behave as if it were unsorted, and in the worst case makes the JDK throw the contract exception described in Section 13.

    Interviewer's perspective The classic counter-example to rule 4 is BigDecimal: new BigDecimal("1.0") and new BigDecimal("1.00") are unequal under equals but return 0 from compareTo. Keep that example ready — it is the standard proof that "consistent with equals" is recommended, not guaranteed.

    4. Comparator: External Ordering

    java.util.Comparator<T> declares one abstract method:

    int compare(T a, T b);

    It obeys the same sign convention as compareTo, but the logic lives outside the class being compared. That single design choice unlocks everything Comparable cannot do:

    • A type can have many different orderings at once: by name, by age, by salary, descending, case-insensitive.
    • A class you do not own (a third-party or JDK type) can still be ordered without modifying it.
    • The ordering can be swapped at runtime, per call site, by passing a different comparator.

    A comparator is handed to the same APIs that accept natural order: list.sort(cmp), Collections.sort(list, cmp), Arrays.sort(array, cmp), and the constructors of TreeSet, TreeMap and PriorityQueue. Because the comparison lives outside, the class stays untouched and equals/hashCode keep their meaning.

    // Demo.java — external ordering via Comparator (by name)
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<Person> people = new ArrayList<>(List.of(
                new Person("Ada", 36),
                new Person("Alan", 41),
                new Person("Grace", 36)));

        Comparator<Person> byName = new Comparator<Person>() {
            @Override
            public int compare(Person a, Person b) {
                return a.getName().compareTo(b.getName());
            }
        };

        people.sort(byName);              // List.sort, Java 8+
        System.out.println(people);       // [Ada(36), Alan(41), Grace(36)]

        Collections.sort(people, byName); // equivalent legacy call
    }
}

    The anonymous class is deliberate here to show the raw shape of the interface; from Java 8 a lambda (a, b) -> a.getName().compareTo(b.getName()) is the idiomatic form (Lectures 37 and 38).

    5. Comparable vs Comparator

    Aspect Comparable Comparator
    Package java.lang java.util
    Method int compareTo(T o) int compare(T a, T b)
    Receiver compares this with the argument compares two arguments passed in
    Where the logic lives inside the class being ordered in a separate class, lambda or factory
    Number of orderings exactly one (the natural order) as many as you like
    Class must be modified Yes — it must implement the interface No — the class stays untouched
    Sort call Collections.sort(list) Collections.sort(list, cmp)
    Used by TreeSet/TreeMap when no comparator is supplied when a comparator is passed to the constructor
    Typical choice the obvious, single default order alternate or context-specific orders

    Reading the table: Comparable answers "what is this type's default order?", while Comparator answers "in what order do I want these two arranged this time?". A well-designed class often implements Comparable for its most obvious order and exposes Comparator constants for the rest.

    6. Sorting APIs Compared

    Every sorting entry point accepts the two kinds of ordering, but they differ in stability, target and platform.

    API Target Ordering argument Stable Notes
    Collections.sort(list) List natural (compareTo) Yes TimSort; Java 8+
    Collections.sort(list, cmp) List Comparator Yes TimSort; Java 8+
    list.sort(cmp) List Comparator Yes default method, Java 8+
    Arrays.sort(array) object array natural (compareTo) Yes TimSort for Object[]
    Arrays.sort(array, cmp) object array Comparator Yes TimSort
    Arrays.sort(array) primitive array not applicable No dual-pivot quicksort
    Stream.sorted() / Stream.sorted(cmp) stream natural or Comparator Yes stable for ordered streams (Lecture 40)

    Two practical notes follow from the table. First, Collections.sort and list.sort are the same operation in modern Java — Collections.sort(list, cmp) simply delegates to list.sort(cmp). Second, primitives can never carry a Comparator: an int[] has no objects to compare, so only natural numeric order exists, and its dual-pivot quicksort is not stable.

    Important Arrays.sort is overloaded. With an Object[] (for example String[] or Person[]) it uses stable TimSort. With int[], long[] or char[] it uses dual-pivot quicksort, which is faster but not stable. The element type, not the method name, decides.

    7. Stability: Why It Matters

    A sort is stable when elements that compare equal keep their original relative order. Stability is what lets you sort a list repeatedly by different keys and get a predictable result:

    // Demo.java — stable sorts compose into a multi-key ordering
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<Person> people = new ArrayList<>(List.of(
                new Person("Ada", 36),
                new Person("Grace", 36),
                new Person("Alan", 41)));

        people.sort(Comparator.comparingInt(Person::getAge));    // primary key: age
        // [Ada(36), Grace(36), Alan(41)] — Ada and Grace keep input order
    }
}

    Because TimSort is stable, sorting first by name and then by age leaves same-age people in name order — the classic "least significant key first" idiom. Collections.sort, List.sort, Arrays.sort(Object[]) and Stream.sorted are all stable; the primitive-array quicksort in Section 6 is the exception.

    Memory aid Objects use TimSort (stable). Primitive arrays use dual-pivot quicksort (unstable). "Objects keep ties in place; primitives may not."

    8. The Collections Utility Class

    java.util.Collections is a static utility class (not to be confused with the Collection interface) holding algorithms that operate on collections. The core one-liners:

    Method One-line meaning
    Collections.sort(list) stable sort into natural order
    Collections.sort(list, cmp) stable sort into a custom order
    Collections.reverse(list) reverse the current order in place
    Collections.shuffle(list) random permutation, in place
    Collections.swap(list, i, j) exchange the elements at two positions
    Collections.rotate(list, d) rotate elements by d positions (negative rotates the other way)
    Collections.max(coll) / max(coll, cmp) largest element, by natural or custom order
    Collections.min(coll) / min(coll, cmp) smallest element, by natural or custom order
    Collections.binarySearch(list, key) index of key in an already-sorted list (negative if absent)
    Collections.frequency(coll, obj) how many elements equal obj
    Collections.fill(list, obj) overwrite every element with obj
    Collections.unmodifiableList(list) a read-only view; writes throw UnsupportedOperationException 
    // Demo2.java — the Collections utility class in one pass
import java.util.*;

public class Demo2 {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(30, 10, 20, 10));

        Collections.sort(list);                  // [10, 10, 20, 30]
        Collections.reverse(list);               // [30, 20, 10, 10]
        Collections.swap(list, 0, 3);            // [10, 20, 10, 30]
        Collections.rotate(list, 1);             // [30, 10, 20, 10]
        System.out.println(Collections.max(list));              // 30
        System.out.println(Collections.frequency(list, 10));    // 2

        Collections.sort(list);                  // binarySearch needs sorted input
        System.out.println(Collections.binarySearch(list, 20)); // 2

        Collections.fill(list, 7);               // [7, 7, 7, 7]
        Collections.shuffle(list);               // random order

        List<Integer> readOnly = Collections.unmodifiableList(list);
        // readOnly.add(1);  -> UnsupportedOperationException
    }
}

    Important Collections.unmodifiableList returns a view, not a copy: writes are rejected, but writes made through the original list are still visible through the view. Use it to publish a read-only facade, not to take a snapshot.

    9. Code: Natural Order by Age, Custom Order by Name

    The two contracts side by side on the same Person class. Comparable fixes the default (age); a Comparator supplies the alternative (name) without touching the class.

    // Demo.java — Comparable gives the default order; Comparator overrides it
import java.util.*;

class Person implements Comparable<Person> {
    private final String name;
    private final int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    String getName() { return name; }
    int getAge() { return age; }

    @Override
    public int compareTo(Person other) {
        return Integer.compare(this.age, other.age);   // natural order: ascending age
    }

    @Override
    public String toString() {
        return name + "(" + age + ")";
    }
}

public class Demo {
    public static void main(String[] args) {
        List<Person> people = new ArrayList<>(List.of(
                new Person("Ada", 36),
                new Person("Alan", 41),
                new Person("Grace", 36)));

        Collections.sort(people);                                 // compareTo -> by age
        System.out.println(people);                               // [Ada(36), Grace(36), Alan(41)]

        people.sort(Comparator.comparing(Person::getName));       // Comparator -> by name
        System.out.println(people);                               // [Ada(36), Alan(41), Grace(36)]
    }
}

    Both orders are legitimate; the class chose one as its identity and the caller chose the other for this call. This is exactly the division of labour between Comparable and Comparator.

    10. TreeSet and TreeMap Compare — They Do Not Use equals

    TreeSet and TreeMap (Lecture 33) are ordered by comparison, not by equality. On every insert they call compareTo or compare on the new key; a result of 0 means "already present", and the insert is rejected. They never consult equals or hashCode.

    That has two consequences whenever the ordering is not consistent with equals:

    • Silent duplicates. Two distinct objects that compare as 0 are treated as the same key, so the second is silently dropped.
    • Misleading lookups. contains/get succeed when the probe compares as 0 to a stored element, even if the two objects are not equals.
    // Demo2.java — TreeSet uses compareTo, never equals
import java.util.*;

public class Demo2 {
    public static void main(String[] args) {
        Set<Person> set = new TreeSet<>();
        set.add(new Person("Ada", 36));
        set.add(new Person("Grace", 36));       // compareTo returns 0 -> duplicate
        System.out.println(set.size());         // 1  — Grace is dropped

        System.out.println(set.contains(new Person("Alan", 36))); // true — not equals
    }
}

    Trap HashSet uses equals/hashCode; TreeSet uses compareTo/compare. A Person whose compareTo only looks at age therefore collapses everyone of the same age into one entry — a different set than HashSet would produce. If you need both, make the comparison fall back to the remaining fields, or order by Comparator.comparing(...).thenComparing(...).

    11. The Integer Subtraction Overflow Bug

    The most common defective compareTo in the wild is:

    public int compareTo(Person o) {
    return this.age - o.age;   // WRONG for large or negative ints
}

    The intention is "negative if I am younger, positive if older", and for small positive numbers it works. But int arithmetic wraps on overflow, so the sign can flip. If this.age is -2_000_000_000 and o.age is 2_000_000_000, the subtraction overflows and yields a positive number, reversing the intended order. Sorting then produces garbage, and TreeSet/TreeMap may misplace keys.

    The correct form is the type-safe comparator:

    // Demo2.java — Integer.compare avoids overflow
public int compareTo(Person o) {
    return Integer.compare(this.age, o.age);   // sign is always correct
}

    Integer.compare, Long.compare, Double.compare, Character.compare and the compare methods of the other wrappers implement the comparison without subtraction and are the recommended building blocks. The same bug reappears inside a Comparator whenever someone writes (a, b) -> a.getAge() - b.getAge().

    Golden rule Never return a - b from compareTo or compare. Return Integer.compare(a, b) (or the matching wrapper's compare) and let the JDK handle overflow, NaN and sign correctly.

    12. Composing Comparators (Preview of Lectures 37 and 38)

    From Java 8 the Comparator interface offers static factory methods that build complex orders from simple ones:

    Factory Effect
    Comparator.comparing(keyExtractor) order by a derived key, using its natural order
    .thenComparing(other) break ties with a second comparator
    .reversed() invert the current order
    Comparator.nullsFirst(cmp) put nulls first, then apply cmp
    Comparator.nullsLast(cmp) put nulls last, then apply cmp 
    // Demo.java — chaining factories (full treatment in Lectures 37-38)
Comparator<Person> order = Comparator
        .comparing(Person::getName)          // primary: name ascending
        .thenComparingInt(Person::getAge)    // tie-break: age ascending
        .reversed();                         // invert the whole order

    These methods are covered in depth in Lectures 37 and 38, once lambdas and method references have been introduced. The important point here is that a Comparator is not just a callback: it is a composable value that can be stored in a field, passed around and built up from parts.

    13. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    return a - b; int overflow flips the sign for large or negative operands Use Integer.compare(a, b) (Section 11)
    Ordering inconsistent with equals TreeSet/TreeMap drop "duplicates" or answer contains misleadingly Compare all identity fields, or keep such types out of sorted collections
    Comparing a null field NullPointerException inside compareTo/compare Use Comparator.nullsFirst/nullsLast, or guard the field
    Mutating a field used in comparison The element's sort position becomes stale; sorted collections corrupt Make compared fields final/immutable while the object is in a sorted collection
    Omitting the generic argument Comparable on a raw type forces casts and risks ClassCastException Always write Comparable<Person> / Comparator<Person>
    Adding a non-comparable element to TreeSet/PriorityQueue ClassCastException when a comparison is attempted Implement Comparable or pass a Comparator to the constructor
    Comparator that is not transitive TimSort throws IllegalArgumentException: Comparison method violates its general contract! Make the comparator a genuine total order (Section 3's rules)

    The last row is worth emphasis: since Java 7 the object sorts use TimSort, which detects a comparator that violates transitivity and throws rather than silently mis-sorting. A comparator that returns 1 whenever either side is null, for example, is not transitive and will fail on a sufficiently large input.

    Interviewer's perspective "Why does Collections.sort sometimes throw IllegalArgumentException: Comparison method violates its general contract!?" Because the comparator is not a valid total order (typically not transitive). TimSort's merge phase can detect the inconsistency. The old legacy merge sort silently tolerated it, which is why this error appeared after Java 7.

    14. Myth vs Reality

    Myth Reality
    "A class needs both Comparable and Comparator to be sorted." Either suffices: Comparable for natural order, or a Comparator passed to the sort.
    "compareTo must return -1, 0 or 1 exactly." Only the sign matters; magnitude is ignored, so returning differences is legal — just overflow-prone.
    "TreeSet removes duplicates using equals." It uses compareTo/compare; equals is never consulted.
    "return a - b is the easy way to compare two ints." It is the classic overflow bug; use Integer.compare(a, b).
    "Arrays.sort is always stable." Stable for Object[] (TimSort); int[]/long[]/char[] use unstable dual-pivot quicksort.

    15. Common Trap Questions

    Trap 1 — Overflow: "Is (a, b) -> a - b a valid Comparator<Integer>?" Yes syntactically, but wrong for large or negative values: the subtraction overflows and the sign flips. Use Integer.compare(a, b).

    Trap 2 — TreeSet duplicates: "Two Person objects differ by name but share an age, and compareTo sorts by age. How many entries in a TreeSet?" One. compareTo returns 0 for equal ages, so the set treats them as duplicates and drops the second.

    Trap 3 — Inconsistent with equals: "set.contains(probe) returned true, but no stored element equals the probe. How?" A TreeSet compares rather than tests equality, so a probe that compares as 0 to a stored element matches even without equals.

    Trap 4 — ClassCastException: "What happens when a non-comparable object is added to a TreeSet with no comparator?" The first add may succeed (no comparison yet); the second triggers a comparison and throws ClassCastException.

    Trap 5 — Nulls: "Sorting a list that contains null with natural order — what happens?" A NullPointerException, because compareTo is invoked on or against a null. Use Comparator.nullsFirst(cmp) or nullsLast(cmp).

    Trap 6 — Duplicate tie-break: "After sorting by name with a stable sort, in what order are people with equal names?" Their original relative order, because the sort is stable. This is what makes the multi-key sort idiom work.

    Trap 7 — Contract violation: "Collections.sort threw IllegalArgumentException: Comparison method violates its general contract! — why?" The comparator is not transitive (or otherwise not a total order); TimSort detected the inconsistency.

    16. Points to Remember

    1. Comparable<T> lives in java.lang, declares int compareTo(T o), and defines a class's single natural ordering.
    2. The sign of compareTo/compare is the contract: negative means before, zero means equal, positive means after.
    3. compareTo must be antisymmetric, transitive, sign-consistent, and is strongly recommended to agree with equals.
    4. Comparator<T> lives in java.util, declares int compare(T a, T b), and supplies an external, reusable ordering.
    5. A type has one natural order but any number of comparator orders; use the latter for context-specific or third-party types.
    6. Collections.sort, List.sort and Arrays.sort(Object[]) are stable TimSort; primitive-array Arrays.sort is unstable dual-pivot quicksort.
    7. Collections is a static utility class: sort, reverse, shuffle, swap, rotate, max, min, binarySearch, frequency, fill, unmodifiableList.
    8. TreeSet/TreeMap order and deduplicate by compareTo/compare, never by equals; inconsistency with equals drops keys or makes lookups miss.
    9. Never return a - b from a comparison; use Integer.compare(a, b) (or the matching wrapper) to avoid overflow.
    10. A malformed comparator that breaks transitivity makes TimSort throw IllegalArgumentException: Comparison method violates its general contract!.

    17. Likely Interview Questions

    Question Crisp Answer
    What is Comparable? The java.lang interface with int compareTo(T o) that gives a class its single natural ordering.
    What is Comparator? The java.util interface with int compare(T a, T b) that supplies an external ordering, possibly several per type.
    Comparable vs Comparator? Comparable is internal, one natural order, in java.lang; Comparator is external, many orders, in java.util.
    What does the sign of compareTo mean? Negative: this before the argument; zero: equal; positive: this after the argument.
    Why use Integer.compare instead of subtraction? Subtraction overflows for large or negative ints and can flip the sign; Integer.compare cannot.
    Which sort does Arrays.sort use? TimSort (stable) for Object[]; dual-pivot quicksort (unstable) for primitive arrays.
    Is Collections.sort stable? Yes; both overloads use TimSort, as does List.sort.
    Does TreeSet use equals? No; it uses compareTo (or the constructor's Comparator), so duplicate detection follows the ordering, not equals.
    What is the danger of compareTo inconsistent with equals? TreeSet/TreeMap drop "duplicates" that merely compare equal, and contains/get may match elements that are not equals.
    When does ClassCastException occur with sorted collections? When a non-Comparable element is added without a comparator and a comparison is attempted.
    What causes "Comparison method violates its general contract!"? A comparator that is not a valid total order, typically not transitive; TimSort detects it.
    How do you make a read-only list? Collections.unmodifiableList(list) returns a read-only view backed by the original.

    18. Final Summary

    ordering needed by:  Collections.sort · List.sort · Arrays.sort
                     TreeSet · TreeMap · PriorityQueue · Collections.binarySearch
                     |
      +--------------+--------------+
      |                             |
 Comparable<T>                Comparator<T>
 compareTo(T o)               compare(T a, T b)
 java.lang · inside class     java.util · outside class
 one natural order            many custom orders
      |                             |
      +--------------+--------------+
                     |
 sorting: Objects -> TimSort (stable)   primitives -> dual-pivot quicksort (unstable)
 traps:   a - b overflow -> Integer.compare
          compareTo ≠ equals -> TreeSet drops / misses
          non-transitive comparator -> IllegalArgumentException (general contract)
    • Comparable -> the class's single natural order, compareTo, in java.lang.
    • Comparator -> external, reusable and composable orders, compare, in java.util.
    • Sign convention -> negative before, zero equal, positive after; only the sign is contractual.
    • Sorting APIs -> Collections.sort, List.sort, Arrays.sort (object form stable, primitive form not), Stream.sorted.
    • Collections -> static helpers: sort, reverse, shuffle, swap, rotate, min, max, binarySearch, frequency, fill, unmodifiableList.
    • Sorted collections -> TreeSet/TreeMap compare, never use equals; inconsistency drops or hides entries.
    • Traps -> subtraction overflow, ordering inconsistent with equals, null fields, mutable compared fields, non-transitive comparators.

    Golden rule Implement Comparable when a type has one obvious default order; reach for Comparator when the order is a matter of context — and always compare with Integer.compare, never subtraction.

    One-line takeaway: Comparable gives a class its one natural order and Comparator supplies the many external ones, while the Collections class and the sorted collections consume whichever rule you provide — so honor the sign convention, the contract, and the no-subtraction rule, or the "sorted" result will be quietly wrong.
