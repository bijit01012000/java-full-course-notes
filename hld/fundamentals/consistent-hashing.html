In one lineConsistent hashing maps keys and servers onto the same ring so that adding or removing one server moves only a small slice of the keys instead of reshuffling the whole cluster.
Hash ring
A fixed circular hash space (for example 0 to 2^32 - 1) on which both servers and keys are placed; after the last position it wraps back to zero.
Modulo hashing
Assigning a key with hash(key) % N, where N is the live server count. Simple, but every change to N remaps most keys.
Virtual node (vnode)
One of several ring positions created by hashing identifiers like S1-0, S1-1; each position points back to the same physical server.
Key space
The range of hash values a function can produce. A larger space makes collisions rare and gives room for many vnodes.
Clockwise lookup
The rule that a key belongs to the first server position at or after the key's hash, wrapping to the smallest position when the ring ends.
Rebalancing
Moving ownership after membership changes. Consistent hashing limits which keys change owner; it does not physically move data.
Hot spot
A server or ring range receiving disproportionate traffic because ranges are uneven or the key distribution is skewed.
Replication factor
The number of copies kept for a key, chosen by walking clockwise to distinct physical servers.
Rendezvous hashing
An alternative that scores every server for a key and picks the highest score, avoiding a ring structure entirely.
Fixed partitions
Hashing keys into a constant number of logical partitions and keeping a separate partition-to-server assignment table.

01The routing question

A distributed cache or storage tier has to answer one question for every request: which server owns this key? If the answer changes for no reason, cached data is stranded and requests pay a database round trip.

  • Suppose user profiles are cached across five servers, S0 through S4.
  • Sending a request to a random server is wasteful: the profile may already be cached elsewhere, so the hit rate collapses.
  • The key must map deterministically, so every request for user:42 reaches the same server while membership is stable.
  • The real challenge is membership change: a server is added for capacity or lost to a failure.
  • A good scheme keeps most keys where they are and moves only what must move.
  • This is a placement problem, not a load-balancing problem: ownership must be stable per key, not merely spread evenly.
Client asks for a key→Hash the key→Find the owning server→Read or write the key there

02Modulo hashing

The simplest scheme hashes the key and takes the remainder modulo the number of servers, which yields a server index from 0 to N - 1.

  • Formula: server = hash(key) % N, where N is the current server count.
  • With five servers, a key hashing to 42 maps to 42 % 5 = 2, so it goes to S2.
  • A different key hashing to 17 also maps to S2; collisions in the index are expected and harmless.
  • With a well-distributed hash, each server owns roughly 1 / N of the keys.
  • While N is constant, the mapping is stable and lookup is O(1).
  • The design is fine as long as the server set never changes — which is not a realistic assumption.

03What breaks when servers change

Add one server and the divisor changes from 5 to 6. Every key's index is recomputed against a different modulus, so ownership changes almost everywhere.

  • Adding S5 makes the formula hash(key) % 6; key 42 moves from S2 to S0, key 17 moves from S2 to S5.
  • Most keys move even though only one server joined; in the source example four of five sampled keys changed owners.
  • Cached entries still sit on the old servers, so requests hitting new owners miss and refetch from the database.
  • Removing a server is the same story in reverse: dropping from five to four changes the modulus to 4 and reshuffles again.
  • A cache miss storm after a resize can overwhelm the database that the cache was protecting.
  • The cost is proportional to the fraction of keys remapped, so the goal is to make that fraction small.

04The hash ring

Consistent hashing fixes the hash space instead of fixing the server count. Both servers and keys are placed in the same space, and the space wraps into a ring.

  • Use a large fixed range such as 0 to 2^32 - 1; positions after the maximum wrap back to zero.
  • Hash each server identifier to place that server on the ring, for example S0 at 100 and S4 at 900.
  • Each server owns the arc between the previous server position and its own position.
  • The server set is data in the ring, not a divisor in a formula, so membership changes do not force a global recompute.
  • The ring is a logical structure: in code it is a sorted array of positions, not an actual circle.
  • Because the space is fixed, the hash of a key never changes; only the nearest server position can change.

05Looking up a key

A lookup hashes the key, lands on a point in the ring, and walks clockwise to the first server position. That server is the owner.

  • Key at position 250 walks clockwise to S1 at 300, so S1 owns it.
  • Key at 620 walks to S3 at 700.
  • Key at 950 passes the end of the ring, wraps to 0, and reaches S0 at 100.
  • A key that lands exactly on a server position belongs to that server; use >= in the search, not >.
  • Ownership intervals are half-open: a server owns keys strictly after the previous position up to and including its own.
  • This rule is all that is needed to route, which is why the ring can be replicated as a small sorted list of positions.

06Adding a server

A new server is hashed onto the ring and takes over only the arc between its predecessor and itself.

  • S5 joins at position 400, between S1 at 300 and S2 at 500.
  • Before the join, S2 owned 301–500; after the join it owns only 401–500.
  • S5 takes 301–400, so key 350 moves from S2 to S5.
  • Key 450 still goes to S2; keys elsewhere on the ring do not move at all.
  • The moved keys are exactly the ones the new server now owns, which is why the churn is bounded.
  • For a cache this is a partial miss; for persistent storage it is a real data transfer that must be executed by some other component.

07Removing a server

  • When S4 at 900 leaves, its arc 701–900 has no owner until the ring is re-read.
  • Those keys continue clockwise, wrap past 999, and land on S0 at 100.
  • Key 850 moves from S4 to S0; key 620 stays on S3; key 250 stays on S1.
  • Removal and failure use the same mechanism, which is why consistent hashing tolerates node loss without a full remap.
  • The successor inherits the whole failed arc, so one neighbor can absorb a large load spike — the motivation for virtual nodes.
  • Until the successor actually has the data, reads for the inherited keys miss or fail; repair is a separate concern.

08How many keys move

  • With balanced positions, adding one server to N servers moves roughly 1 / (N + 1) of the keys.
  • Growing from five servers to six therefore moves about one sixth of the keys, not most of them.
  • The exact fraction depends on where the new server lands: in the example S5 took 100 of 1,000 positions, so about 10% moved.
  • Removing one server from N moves roughly 1 / N of the keys, again only its own arc.
  • This is the core win over modulo hashing, where a divisor change remaps the majority of keys.
  • Consistent hashing changes ownership only. Copying or deleting the data is a separate process you still have to build.

09The problem of uneven ranges

Evenly spaced positions in a diagram are a teaching device. Hashing real server names produces gaps of very different sizes.

  • One server may own a tiny arc while another owns nearly half the ring.
  • In the source example S2 owns almost half the positions while S1 owns about a twentieth, so S2 handles roughly ten times the traffic.
  • A server with a large arc needs more memory and serves more requests, so it saturates first and wastes the rest of the cluster.
  • With one position per server, a failure hands that entire arc to a single clockwise neighbor.
  • If S2 fails, S3 can jump from a small arc to most of the ring and collapse under the inherited traffic.
  • The fix is not a better hash function; it is giving each physical server many small positions.

10Virtual nodes

A virtual node is an extra ring position for the same physical server, created by hashing a derived identifier such as S2-0, S2-1, or S2-2.

  • Hash many identifiers per server so each physical machine appears at dozens of points around the ring.
  • Lookup is unchanged: walk clockwise to the first position and route to the physical server behind it.
  • A key still has exactly one primary owner; vnodes split that server's ownership into smaller arcs, they do not duplicate data.
  • Many small arcs average out, so each server's total share converges toward an equal fraction.
  • A failed server's arcs are inherited by several different successors, spreading the recovery load.
  • A larger machine can be given more vnodes, so capacity weighting becomes a configuration choice.
  • Tens to a few hundred vnodes per server is a common starting range; measure the real distribution rather than trusting the theory.
  • More vnodes mean more metadata and more positions to update on every membership change.

Why virtual nodes help

  • Balance: many small ranges even out the large and small gaps produced by hashing a few names.
  • Failure handling: a lost server's ranges are distributed across multiple neighbors instead of one.
  • Capacity weighting: a stronger server can be assigned more vnodes to take a larger share.
  • Cost: more metadata and more routing-table work whenever membership changes.
  • Vnodes improve balance statistically; they do not guarantee equal load for a skewed key distribution.

11Implementing the ring

  • Represent the ring as a sorted array of vnode positions plus a map from position to physical server.
  • Hash the key, then binary search for the first position >= the hash.
  • If no position is at or after the hash, wrap around and take the first entry.
  • If the ring is empty, there is no owner, so return an error instead of guessing.
  • Handle vnode hash collisions deterministically — for example, keep the vnode whose server id sorts first — so all clients agree.
  • Lookup costs O(log V) where V is the number of vnodes; adding or removing a server costs O(R log V) for R vnodes.
  • Use a fast, stable, well-distributed non-cryptographic hash such as MurmurHash, xxHash, or CityHash; cryptographic hashes are slower for no placement benefit.
  • Every client must share the same server list and hash function, so publish ring updates from one place — a configuration or coordination service — and version the membership.
import bisect, hashlib

class Ring:
    def __init__(self, servers, vnodes=100):
        self.positions = []
        self.owner = {}
        for server in servers:
            for i in range(vnodes):
                p = self._hash(f"{server}-{i}")
                self.positions.append(p)
                self.owner[p] = server
        self.positions.sort()

    @staticmethod
    def _hash(key):
        return int(hashlib.md5(key.encode()).hexdigest()[:8], 16)

    def get(self, key):
        if not self.positions:
            raise RuntimeError("empty ring")
        h = self._hash(key)
        i = bisect.bisect_left(self.positions, h)
        if i == len(self.positions):
            i = 0
        return self.owner[self.positions[i]]
Binary search over a sorted array is enough for most clusters. Very large rings may use a tree or a fixed-partition table instead.

12Replication on the ring

The ring decides a primary owner. For durability or availability you keep additional copies by continuing clockwise to distinct physical servers.

  • Start at the key's position and take the first vnode as the primary copy.
  • Walk clockwise and take the next vnode only if it belongs to a different physical server.
  • For key 75 with primary S2-1 at 80, replica one is S3-1 at 90 and replica two is S1-2 at 120.
  • If the next vnode belongs to an already-used server, skip it; a second copy on the same machine does not survive that machine failing.
  • Continue until you have the desired replication factor; a small cluster may run out of distinct servers.
  • Spread replicas across racks or availability zones so one power or network failure cannot take all copies.
  • The ring only chooses where copies live. Writing, acknowledging, and repairing replicas are separate mechanisms.
  • Replica placement also affects read locality: a nearby replica can serve a read when consistency rules permit.

13When to use consistent hashing

  • Good fit: caches, storage shards, and stateful routing where a key should usually reach the same server.
  • Poor fit: stateless services where any healthy server can handle any request — a normal load balancer is simpler.
  • Rendezvous (highest-random-weight) hashing scores every server per key and picks the winner; no ring to maintain, but every lookup considers all servers.
  • Fixed partitions hash keys into a constant number of logical partitions and keep a table mapping partitions to servers; the partition count never changes, so modulo still works.
  • Fixed partitions are common in systems that move whole partitions, such as logs, queues, and some databases.
  • Whatever the scheme, the operational requirements are the same: one shared membership view, a stable hash, and a plan for moving or rebuilding data.
  • Choose consistent hashing when membership changes are frequent and per-key locality matters.

↔Trade-offs to say out loud

  • Consistent hashing limits key movement on membership change, but adds a ring structure, vnode metadata, and a shared membership view to maintain.
  • Modulo hashing is trivial to implement and O(1) to look up, but a single server change remaps most keys and can cause a cache-miss storm.
  • More virtual nodes improve balance and spread failure load, but increase routing metadata and the cost of every membership change.
  • One vnode per server keeps the ring tiny, but produces uneven arcs and concentrates a failed server's load on one neighbor.
  • Capacity-weighted vnodes let stronger machines take more keys, but couple placement to a hand-tuned configuration that must be maintained.
  • Replicating clockwise improves availability, but consumes storage and write bandwidth and requires a repair process for missed writes.
  • Fixed partitions avoid rehashing entirely and make data movement explicit, but the partition count is a long-term commitment and hot partitions remain possible.
  • Rendezvous hashing removes ring maintenance and handles membership changes gracefully, but costs O(N) per lookup and is awkward for very large server sets.

?Interview questions

Answer aloud before opening the outline.

1. What problem does consistent hashing solve?

It keeps the mapping from key to server stable when servers join or leave. With modulo hashing, changing the server count changes the divisor and remaps most keys; consistent hashing moves only the arcs affected by the membership change.

2. Walk me through a lookup on the ring.

Hash the key into the fixed hash space, then scan clockwise to the first server position. If the key's hash is beyond the largest position, wrap to the smallest. That server is the owner, and the same key always maps there while membership is unchanged.

3. Why does adding one server to five move about one sixth of the keys?

A new server inserts one more position into the ring and takes over the arc between its predecessor and itself. With balanced positions that arc is about 1 / (N + 1) of the space, so roughly that fraction of keys changes owner.

4. Does consistent hashing move the data for you?

No. It only decides ownership. For a cache, the new owner simply misses and reloads. For persistent storage you need a separate transfer or repair process, plus a rule for reads during the transition.

5. What happens if a server fails without virtual nodes?

Its entire arc moves to the next server clockwise. That neighbor can suddenly receive a large multiple of its previous traffic and may fail too, which is why production rings use many vnodes per server.

6. What are virtual nodes and why do they help?

A vnode is an extra ring position for the same physical server, produced by hashing identifiers like S2-1. Many small arcs average out uneven gaps, spread a failed server's load across several neighbors, and allow capacity weighting.

7. Do virtual nodes guarantee even load?

No. They improve balance statistically and reduce variance as the vnode count grows. A skewed key distribution, hot keys, or heterogeneous request costs can still overload one server, so you measure the actual distribution.

8. How would you implement the ring efficiently?

Keep a sorted array of vnode positions and a map from position to server. Hash the key, binary search for the first position >= the hash, and wrap to index zero if none exists. Lookup is O(log V).

9. What breaks if two clients have different ring views?

The same key can route to two different owners. Reads may miss data that was just written, and caches diverge. Publish ring updates from one authority and version the membership so clients converge.

10. How do you place replicas on a consistent hash ring?

Take the primary owner, then walk clockwise and pick the next vnodes that belong to distinct physical servers until the replication factor is met. Spread them across racks or zones where possible.

11. Consistent hashing vs rendezvous hashing?

Consistent hashing maintains a ring and finds a neighbour in O(log V). Rendezvous hashing scores every server for the key and picks the maximum, costing O(N) but requiring no ring state. Rendezvous is attractive for smaller, frequently changing server sets.

12. When would you use fixed partitions instead?

When you want to move whole units of data — logs, queue partitions, database shards. The partition count is fixed, so modulo hashing on the partition id is stable, and a separate assignment table maps partitions to servers.

13. When is consistent hashing the wrong choice?

For stateless services where any server can handle any request. A plain load balancer spreads traffic with far less machinery, and there is no per-key locality to preserve.

!Traps

  • Claiming consistent hashing moves data — it only changes ownership; the transfer or rebuild is a separate process.
  • Forgetting that modulo hashing on a changing server count remaps most keys, then being surprised by a cache-miss storm.
  • Using one ring position per server in production and creating hot spots and single-neighbour failure overload.
  • Assuming virtual nodes guarantee perfectly even load rather than reducing variance.
  • Placing replicas on the next vnode without checking that it belongs to a different physical server.
  • Letting clients compute membership independently so different nodes disagree about the owner of a key.
  • Hashing unstable server identifiers such as ephemeral IPs, which silently reshuffles the ring on every restart.
  • Treating the ring as a data-movement mechanism and forgetting reads that arrive before the data has been transferred.
