In one lineAvailability is how often users can actually reach and use the system — engineered by removing single points of failure, adding redundancy that survives correlated failures, and containing the blast radius when a dependency breaks.
Availability
The fraction of time, or the fraction of requests, for which users can successfully access and use the system.
Reliability
Whether the system continues to behave correctly over time, without wrong results, lost data, or duplication.
Nines
A shorthand for availability targets: 99.9% is three nines, 99.99% is four, and each additional nine cuts allowed downtime by about ten times.
Series dependency
A component that every request must pass through; if it fails, the request fails, so availability multiplies downward.
Redundancy
A spare component or path that can take over when the primary fails, converting a single failure into a survivable one.
Failover
The process of detecting a failed primary, promoting a standby, and redirecting traffic to it.
Split-brain
A failure mode where two nodes both believe they are primary and accept writes, risking divergent data.
Active-active
A redundant setup where multiple nodes serve traffic simultaneously behind a load balancer.
Health check
A probe that tests whether an instance can actually serve requests, used by a load balancer to remove unhealthy nodes.
Circuit breaker
A protection that stops calling a failing dependency after a threshold, then probes cautiously for recovery.

01The problem

An online store runs on one application server connected to one database. Browsing, carts, and checkout work until the application server crashes.

  • The database is still healthy, but customers cannot reach the store because the only path to it is gone.
  • A system can be fast and scalable and still fail users if one required component takes the whole thing down.
  • Handling more load and staying online during failures are related but separate problems.
  • Availability is about the second problem: keeping the service present when users need it.
  • The fix is not simply more servers; it is removing single points of failure and ensuring a usable path remains.
  • Every required component in the request path is another opportunity for the whole request to fail.

02What availability means

Availability measures how often users can access and use the system. It is narrower than general quality and broader than a single server being powered on.

  • Scalability asks whether the system can handle more load; availability asks whether users can reach it at all.
  • Reliability asks whether it behaves correctly over time; a store can be available while a bug computes wrong order totals.
  • A system that processes ten thousand orders per minute but goes offline for an hour after one crash has solved scalability, not availability.
  • Availability is experienced per operation: browsing may work while checkout is completely broken.
  • It is usually expressed as a percentage over a stated window, not as a vague claim that the system is up.
  • Users judge availability by whether their task succeeds, not by whether every internal component is healthy.

03Measuring availability

The basic formula is uptime divided by total time, where total time is uptime plus downtime.

  • Availability = Uptime / (Uptime + Downtime), usually multiplied by 100 for a percentage.
  • Being available for 364 of 365 days gives roughly 99.73% availability.
  • A single number is meaningless without a stated scope (which operation or component) and window (month, quarter, year).
  • Measure per operation: a store this month might show 99.99% browsing, 99.95% add-to-cart, and 99.5% checkout.
  • The averaged whole-store figure can hide the checkout outage that the business actually cares about.
  • Track availability from the user's side with success rate and latency, not only from internal infrastructure health.
  • Report both the aggregate and the worst important operation; the worst one drives user trust and revenue.

04The nines of availability

Availability targets are described in nines. Each additional nine cuts the allowed downtime by roughly a factor of ten.

  • Two nines allow days of downtime per year; three nines allow hours; four nines allow under an hour.
  • At four nines, a single one-hour incident can consume the entire year's downtime budget.
  • Less allowed downtime also means less time to detect, diagnose, and recover.
  • Higher targets require more redundancy, spare capacity, automation, monitoring, testing, and faster recovery.
  • The target should come from the business cost of downtime, not from a desire to sound impressive.
  • A useful design question: which operations truly need five nines, and which can tolerate minutes of unavailability?

What each target demands

  • Three nines: a second server, basic monitoring, and a person who can respond within hours.
  • Four nines: automatic failover, health checks, an on-call rotation, and tested recovery procedures.
  • Five nines: redundancy at every layer, multiple locations, and automated recovery with no human in the loop.
  • The cost grows sharply with each nine, so apply the highest target only to the operations that justify it.

05Components in series

A request that must pass through a web server, an application server, and a database has a series dependency: all three must be available for the request to succeed.

  • For independent failures, multiply the component availabilities: 0.999 × 0.999 × 0.999 ≈ 0.997, or about 99.7%.
  • The combined availability is lower than the weakest single component, not equal to it.
  • Five components at 99.9% each combine to about 99.5%, nearly 44 hours of downtime per year instead of under 9.
  • Every required component is another point of failure, even when each one is individually well built.
  • Adding a synchronous dependency to the critical path makes the whole path less available.
  • Reduce the number of required hops, make non-critical hops optional, or put redundancy in parallel at each layer.
  • This is why an architecture with many mandatory chained services can be less available than a simpler one.
Request arrives→Web server must be available→Application server must be available→Database must be available→All three succeed for the request to succeed

06Components in parallel

With two application servers where either can handle the request, the servers are redundant rather than serial. The system fails only if both fail at once.

  • If each server is 99.9% available, each is down 0.1% of the time.
  • Assuming independent failures, both are down with probability 0.1% × 0.1% = 0.0001%.
  • That gives the pair a theoretical availability of 99.9999%, or six nines.
  • The math assumes traffic can actually reach the healthy server, so the load balancer and network must also be available.
  • It also assumes the survivor has enough spare capacity to absorb the failed server's load.
  • The figure covers only those two servers; the database and other required components still multiply into the request path.
  • Series and parallel are mirror images: series fails if any part fails, parallel fails only if every redundant part fails.

07Why independence matters

The parallel calculation collapses if failures are correlated. Two servers are not truly redundant when the same cause can take both down.

  • Hardware: servers sharing a rack, power feed, or switch can fail together.
  • Software: the same buggy release, memory leak, or deadlock can hit every instance running it.
  • Network: a shared path, DNS entry, or partition can make all replicas unreachable at once.
  • Human error: one bad configuration or accidental deletion applied to the fleet hits everything.
  • At small scale a server failure feels rare; across thousands of machines, drive and power failures are routine.
  • Redundancy must be placed in separate failure domains — different racks, zones, or regions — to be meaningful.
  • Adding machines without separating their dependencies provides capacity but not real availability.

08Active-passive redundancy

In active-passive, one component handles traffic while another stays ready as a standby. A common example is a primary database replicating to a standby.

  • The primary accepts writes and replicates changes to the standby.
  • If the primary fails, a monitor detects it, promotes the standby, and redirects application connections.
  • One active writer makes data changes easier to coordinate: there is a single authority for the latest state.
  • The cost is a brief interruption while detection, promotion, and reconnection complete.
  • A standby that never serves traffic can be untested and may fail under real production load.
  • If the monitor promotes the standby while the old primary is still alive, both may accept writes — split-brain.
  • Fencing, quorum, or a single coordination service is needed to prevent two writers.

Pros and cons

  • Pro: one clear writer, so coordination is simple and the latest copy is unambiguous.
  • Pro: lower resource use, because the standby does not serve production traffic.
  • Con: failover takes time and users see a brief interruption.
  • Con: the standby may be stale, misconfigured, or too small to carry the load.
  • Con: split-brain risk if the old primary is still accepting writes.

Standby readiness

  • A cold standby is not running and may need data restored; failover takes minutes.
  • A warm standby is running and configured but needs to catch up and be promoted; failover takes seconds to minutes.
  • A hot standby is running, in sync, and ready to serve; failover takes seconds.
  • The faster the standby, the higher the cost, because more infrastructure sits ready.

09Active-active redundancy

In active-active, multiple nodes serve traffic simultaneously through a load balancer. If one fails, the others are already running and continue immediately.

  • There is no promotion step, so there is no failover delay for application servers.
  • Every node is exercised under real production load, so there is no untested backup.
  • Hardware is used more efficiently because no machine sits idle.
  • Each surviving node must have enough spare capacity to absorb the failed node's share.
  • Any node must be able to handle any request, so cart and session state must live in a shared store.
  • Stateless application servers are the natural fit for active-active.
  • Databases are harder: multiple active writers must coordinate, which reintroduces consistency trade-offs.

Health checks and the load balancer

  • The load balancer removes a server from rotation when its health check fails.
  • Detection is not instant: checks run every few seconds, and a server is usually marked unhealthy after several consecutive failures.
  • Requests already in progress, or sent during that window, may still fail.
  • A good health check verifies the ability to serve requests, not merely that the process is alive.
  • The load balancer itself needs redundancy; otherwise it becomes the single point of failure for every healthy server.
  • Managed cloud load balancers are built redundantly; self-managed setups often share a virtual IP between two instances.

10Spreading across locations

Redundant components in the same building still share a facility-wide power or network failure. Spreading them across locations creates independent failure domains.

  • Availability zones are separate data centers in one region, connected by fast links; they protect against one data center failing.
  • Regions are separate geographic areas; they protect against regional disasters but add tens of milliseconds or more between copies.
  • Multiple cloud providers protect against a provider-wide outage but multiply operational complexity and tooling differences.
  • Wider separation introduces a replication trade-off between write latency and potential data loss.
  • The right level depends on which failures must be survived and how much cost and complexity are acceptable.
  • For most applications, two or more availability zones is the sensible default; multi-region is for when a regional outage is unacceptable.
  • Redundancy is not free: every standby, replica, and location costs money and adds something to operate.

Synchronous vs asynchronous replication

  • Synchronous: the write succeeds only after the remote replica confirms it; no data loss on failover, but every write waits for the round trip.
  • Asynchronous: the write is confirmed immediately and the replica catches up later; no added write latency, but recent changes may be lost.
  • Choose synchronous for the data whose loss is unacceptable, and asynchronous where write latency matters more.
  • A mixed strategy is common: synchronous within a region and asynchronous across regions.

11Handling overload with queues

Availability can fail from overload rather than breakage. A sale spike can make confirmation emails slow enough to slow checkout itself.

  • If checkout waits for the email provider, the provider's latency becomes checkout's latency.
  • Save the order first, then place an email job in a durable queue.
  • Background workers process the job separately, so customers see confirmation without waiting for email delivery.
  • If a worker crashes mid-job, the queue holds the message until another worker confirms completion.
  • Queues absorb bursts and let producers and consumers scale independently.
  • The user gets eventual completion rather than immediate completion; that must be acceptable for the work being deferred.
  • Monitor queue depth, message age, retries, and dead-letter messages; a growing backlog is an availability warning.
Customer places an order→App server saves the order→App server enqueues an email job→Customer receives confirmation→Workers deliver email at their own pace

12Containing cascading failures

A slow recommendation service can exhaust application threads and connections, spreading the slowdown to checkout, which never needed recommendations. This is a cascading failure.

  • Timeouts stop a request from waiting indefinitely on a slow dependency.
  • Circuit breakers stop calling a dependency that keeps failing, then probe cautiously for recovery.
  • Fallbacks return a reduced but usable response, such as a product page without recommendations.
  • Bulkheads isolate resources so one dependency cannot consume every thread or connection.
  • Load shedding rejects low-priority work early when capacity is exhausted, preserving critical paths.
  • The goal is not to keep every feature working; it is to keep the critical user journey working.
  • A dependency that is down should look contained, not contagious.

Circuit breaker states

  • Closed: calls pass through and failures are counted.
  • Open: failures crossed the threshold, so calls are rejected immediately without waiting.
  • Half-open: after a cooldown, a few test requests are allowed through.
  • Success in half-open closes the circuit; failure reopens it.
Closed→Failure threshold exceeded→Open→Cooldown expires→Half-open test→Closed on success or Open on failure

13Putting it together

  • Measure availability per operation, over a stated window, weighted toward the operations users and the business care about.
  • Remove single points of failure from the critical path, then add redundancy in independent failure domains.
  • Use active-passive with tested failover for stateful primaries; use active-active behind a load balancer for stateless application servers.
  • Spread across availability zones by default; add regions when a regional outage is unacceptable.
  • Move deferrable work to durable queues so overload in a secondary feature does not slow the critical path.
  • Add timeouts, circuit breakers, and fallbacks so a slow dependency stays contained.
  • Test the failure paths under realistic load; an untested standby or failover script is an assumption, not a control.
  • Higher availability is bought with redundancy, spare capacity, automation, and operational discipline — not with a slogan.

↔Trade-offs to say out loud

  • Active-passive keeps one clear writer and is simpler to reason about, but failover causes an interruption and the standby may be untested.
  • Active-active removes failover delay and exercises every node, but requires spare capacity in each node and shared state outside the servers.
  • A hot standby recovers fastest but costs the most, because a full copy sits ready and idle.
  • Multi-region deployment survives regional outages but adds replication latency, duplicate infrastructure, and operational complexity.
  • Synchronous replication avoids data loss on failover but makes every write pay the remote round trip.
  • Asynchronous replication keeps writes fast but risks losing recent changes when a region fails.
  • Durable queues absorb overload and survive worker crashes but introduce eventual completion, duplicates, and backlog monitoring.
  • Circuit breakers and fallbacks contain cascading failure but may reject otherwise valid requests and show users a reduced experience.
  • Higher nines reduce downtime but demand more redundancy, automation, testing, and on-call effort at sharply rising cost.

?Interview questions

Answer aloud before opening the outline.

1. What is availability, and how is it different from reliability and scalability?

Availability is how often users can reach and use the system. Scalability is the ability to handle more load, and reliability is whether the system behaves correctly over time. A store can be available but unreliable if it accepts orders and calculates the wrong total.

2. How do you calculate availability?

Divide uptime by total time: Uptime / (Uptime + Downtime). Being up 364 of 365 days gives about 99.73%. The number is only meaningful when you state which operation and which time window you are measuring.

3. Why measure availability per operation?

An aggregate can hide a serious outage. Browsing might be 99.99% available while checkout is 99.5%, yet the whole-store average looks acceptable. Per-operation measurement shows where users actually fail and lets you apply the highest targets to the operations that matter most.

4. What does four nines mean in practice?

99.99% allows about 52.6 minutes of downtime per year, 4.38 minutes per month, or about a minute per week. A single hour-long incident would exhaust the annual budget, so four nines requires automatic failover, health checks, on-call response, and tested recovery.

5. How does availability combine for components in series?

Multiply the independent availabilities. Three components at 99.9% give roughly 99.7%, and five give about 99.5%. The system is less available than any single component because every required hop is another chance for the request to fail.

6. How does availability combine for components in parallel?

Multiply the failure probabilities. Two 99.9% servers each fail 0.1% of the time, so both fail together only 0.0001% of the time, giving a theoretical 99.9999%. This assumes independent failures, reachable healthy nodes, and enough spare capacity in the survivor.

7. Why is independence important in redundancy calculations?

If both servers share a rack, power feed, network path, deployment pipeline, or configuration, one cause can take both down. The parallel math then overstates availability. Redundancy only helps when the copies sit in separate failure domains.

8. Explain active-passive and its main risks.

One node serves traffic while a standby stays ready. On failure, a monitor promotes the standby and redirects connections. The main risks are failover interruption, an untested or undersized standby, and split-brain if the old primary is still accepting writes while the new one is promoted.

9. What are cold, warm, and hot standbys?

A cold standby is not running and may need data restored, so recovery takes minutes. A warm standby is running and configured but needs to catch up and be promoted, taking seconds to minutes. A hot standby is in sync and ready, taking seconds, at the highest cost.

10. What does active-active require that active-passive does not?

Every node must be able to serve any request, so session and cart state must be shared outside the servers. Each node also needs spare capacity to absorb the others' load. For databases, multiple active writers must coordinate, which is considerably harder than a single primary.

11. How do availability zones and regions differ?

Availability zones are separate data centers within one region with low-latency links, protecting against a single facility failure. Regions are geographic separations that protect against regional disasters but add tens of milliseconds or more between replicas. Multi-region is justified when a regional outage is unacceptable.

12. Synchronous or asynchronous replication for availability?

Synchronous replication waits for the remote copy, so failover loses no data but every write pays the round trip. Asynchronous confirms locally and replicates later, keeping writes fast but risking loss of recent changes. Many systems use synchronous within a region and asynchronous across regions.

13. How do queues improve availability?

They remove slow work from the request path and absorb bursts, so a slow email provider or worker crash does not fail checkout. Messages persist until processed and can be retried. The cost is eventual completion, possible duplicates, and the need to monitor backlog and dead-letter queues.

14. How do you stop a cascading failure?

Put timeouts on every network call, use circuit breakers to stop calling a failing dependency, provide fallbacks for non-critical features, isolate resources with bulkheads, and shed low-priority load when saturated. The objective is to keep the critical user journey working while the dependency recovers.

!Traps

  • Reporting one availability number for the whole product and hiding a broken checkout path.
  • Multiplying component availability without checking whether their failures are actually independent.
  • Assuming two servers in the same rack or behind the same deployment are redundant.
  • Treating failover as instantaneous and forgetting detection, promotion, and reconnection time.
  • Keeping a standby that has never been tested under production-like load or cannot handle the traffic.
  • Running active-active without shared session state, so a surviving server cannot serve the user's request.
  • Choosing synchronous replication everywhere without accounting for the write-latency cost.
  • Adding a queue or circuit breaker without idempotency, fallback behavior, or backlog monitoring.
