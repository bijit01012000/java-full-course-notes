In one lineLambda architecture runs a batch pipeline for correctness and a streaming pipeline for freshness over the same immutable data, then merges their outputs at query time so results are immediate and eventually exact.
Batch layer
The pipeline that reprocesses the full immutable history on a schedule and produces authoritative, corrected views.
Speed layer
The streaming pipeline that processes only recent events to produce low-latency views covering the gap since the last batch run.
Serving layer
The queryable store that holds batch views plus realtime views and merges them for readers.
Master dataset
The append-only, immutable record of all raw events from which every view can be recomputed.
Batch view
A precomputed, indexed result built from the full history; accurate but stale by the batch interval.
Realtime view
A transient result computed from the newest events; fresh but superseded once the batch layer catches up.
Recomputation
Rebuilding views from the master dataset after a logic fix, which is how the batch layer recovers from wrong code.
Human fault tolerance
The property that bad code or bad data can be corrected by replaying history rather than patching damaged state in place.
Merge rule
The query-time rule that combines a batch view with the corresponding realtime delta for the uncovered time range.
Dual implementation
Maintaining the same business logic twice, once in batch code and once in streaming code, which is Lambda's core cost.

01Two requirements that pull apart

Analytical systems are asked for a number that is fresh now and also correct in the long run, and those two demands favour different pipelines.

  • Batch processing over the full history is accurate and reprocessable, but results arrive only when the job finishes, often hours later.
  • Stream processing produces results in seconds, but a bug in a live pipeline has already emitted wrong output before anyone notices.
  • Correcting a streaming pipeline means reprocessing history, which a pure streaming design must build separately.
  • Many products need both: an operational dashboard that moves now, and a settled number used for billing, reporting, or reconciliation.
  • Lambda answers this by running both pipelines over the same source data and combining their outputs.
  • The design accepts duplicated computation as the price of getting low latency without giving up the ability to recompute.

02The three layers

  • Batch layer owns the full history, recomputes views on a schedule, and is the source of eventual correctness.
  • Speed layer consumes only the recent stream, fills the gap since the last batch view, and is optimised for latency.
  • Serving layer indexes both outputs and answers queries by combining them.
  • All three read from one immutable input, so there is no separate ingestion truth to reconcile.
  • Each layer can be scaled, deployed, and tuned independently because their contracts are just views over data.
  • The batch layer is authoritative; the speed layer is a temporary compensation that is discarded as batch catches up.
Events append to the immutable master log→Batch job recomputes full views on schedule→Stream job computes realtime deltas continuously→Batch views load into the serving store→Realtime views load into the serving store→Query merges batch view with the realtime delta

03The batch layer

  • It stores the master dataset: raw events appended and never edited, so history is always available for replay.
  • A scheduled job reads all or a bounded slice of history and rebuilds the derived tables from scratch.
  • Recomputing from scratch is deliberately simple: there is no need to reason about incremental state or partial corrections.
  • The output is written as an immutable, versioned batch view that can be swapped in atomically.
  • If a business rule was wrong, the fix is a code change plus a rerun, not a manual repair of corrupted aggregates.
  • The cost is that the batch layer's latency equals the schedule interval, and full recomputation grows with history size.
The batch layer's superpower is not speed; it is the ability to throw everything away and derive it again from raw facts.

04The speed layer

  • It reads the live event stream and maintains only the state needed for the period the batch layer has not yet covered.
  • Its output is a realtime view, usually a small delta: counts, sums, or latest values since a known cutoff.
  • Because the window it covers is short, its state is small and can often be held in memory or a local store.
  • It must be idempotent or exactly-once enough that a restart does not double-count events.
  • When a new batch view covering the same period is published, the corresponding realtime state can be discarded.
  • A speed-layer bug produces wrong numbers only for its short window, which the next batch run corrects, provided the merge is designed correctly.

05The serving layer and the merge

  • The serving store holds indexed batch views keyed for fast lookup, and a smaller store for realtime views.
  • A query reads the batch value and adds the realtime delta for the time range the batch view does not include.
  • The merge is only correct if the two views represent the same aggregation over disjoint, clearly bounded time ranges.
  • For additive metrics such as counts and sums, merging is simple addition; for distinct counts or percentiles, it needs mergeable sketches or a different design.
  • The cutoff must be explicit: the query needs to know which events the batch view already includes, or it will double-count.
  • Common implementations store the batch view with a version or watermark and let the serving API subtract the overlapping realtime window.

06Why the architecture was introduced

  • It was a response to the difficulty of making a streaming system both low latency and fully correctable.
  • The immutable master dataset provides human fault tolerance: fixes are expressed as new code over old data.
  • Batch recomputation gives a simple recovery story for bugs, bad deploys, and corrupted derived state.
  • The streaming layer exists only to hide batch latency, not to be the system of record.
  • This separation lets each layer use the tool best suited to it: a batch engine for full scans, a stream engine for continuous deltas.
  • It also predates mature unified engines, when one system could not credibly do both latencies well.

07The dual-logic problem

  • The same business rule must be implemented in the batch code and again in the streaming code, in two languages or two APIs.
  • The two implementations inevitably drift: a filter, a join, or a rounding rule changes in one and not the other.
  • Drift shows up as a discontinuity: the number jumps when the batch view replaces the realtime view.
  • Tests must compare batch and stream outputs on the same input, which is the only reliable defence against divergence.
  • Sharing a library or a declarative transformation layer reduces duplication but rarely removes it entirely.
  • Every new metric doubles the work: design, review, deploy, monitor, and debug in two pipelines.
If batch and speed logic disagree even slightly, users see the system contradict itself at every batch boundary.

08Reprocessing and backfill

  • A logic fix requires rerunning the batch layer over the affected history, which can take hours or days depending on volume.
  • Reprocessing should write to a new view version and swap it in only when complete, so readers never see a partial rebuild.
  • Backfills compete with scheduled batch work for the same cluster, so they need queueing, prioritisation, or dedicated capacity.
  • The speed layer cannot be backfilled the same way; it is simply reset and rebuilt from the new cutoff.
  • Downstream consumers may have cached or exported the old numbers, so a correction needs a communication path as well as a technical one.
  • Retention of raw events is therefore a hard requirement; if the master dataset is trimmed, recomputation becomes impossible.

09Failure modes to design for

  • The batch job fails or runs long, so the realtime window grows and the speed layer must hold more state than planned.
  • A speed-layer restart without idempotent writes double-counts the events it replays.
  • The cutoff is recorded inconsistently, so a query double-counts or misses the boundary events.
  • Batch and stream views use different time semantics, for example ingestion time versus event time, and disagree on late events.
  • A schema change reaches one pipeline before the other, and the merge breaks on missing fields.
  • Serving-layer indexes fall behind the published views, so readers see a mix of versions.
  • Monitoring only the batch job hides a stalled stream, and the dashboard silently freezes.

10Variants and alternatives

  • Some teams keep the three layers but implement both paths in one engine, using the same API for batch and streaming modes.
  • Micro-batch processing collapses the two paths into one pipeline with a short interval, trading some latency for one codebase.
  • Kappa architecture drops the batch layer and reprocesses by replaying the stream log through a new job version.
  • A hybrid keeps Lambda for a few critical metrics and uses unified streaming elsewhere, rather than applying one pattern everywhere.
  • Unified engines reduce duplicate code but do not remove the need to reason about late data, state, and exactly-once sinks.
  • The choice is really about whether replaying history through one pipeline is cheap and reliable enough for the organisation.

11When Lambda is still the right call

  • Choose it when batch recomputation over the full history is the only trusted way to correct results, such as regulated reporting or billing.
  • Choose it when the streaming path is genuinely best-effort and the batch path is the contract of record.
  • Choose it when the team already has strong batch tooling and the streaming volume is modest.
  • Avoid it when two codebases would be maintained by a small team with no capacity to test them against each other.
  • Avoid it when the same logic changes weekly, because dual implementations turn into a permanent source of bugs.
  • Avoid it when replay through a single streaming pipeline is affordable, which is the case Kappa was designed for.

12Designing Lambda in an interview

  • State the freshness target for the speed layer and the correctness target for the batch layer separately.
  • Define the cutoff precisely: which timestamp, which offset, and how the query knows where batch ends and stream begins.
  • Say how the merge handles non-additive metrics such as distinct users or percentiles.
  • Explain how batch and speed logic stay in sync: shared library, generated code, or comparison tests.
  • Describe the reprocessing path end to end, including how readers avoid partial results during the swap.
  • Name the operational cost: two pipelines, two on-call surfaces, and two sets of dashboards.

↔Trade-offs to say out loud

  • Low latency plus full reprocessing are both achieved, but only by running and maintaining two pipelines over the same data.
  • Immutable master data makes correction and audit possible, but storage grows forever and every rebuild scans more history.
  • Batch authority gives trustworthy numbers, but the batch interval sets the worst-case staleness and the recovery time after a bug.
  • Small speed-layer state keeps streaming cheap, but any batch delay widens the realtime window and can exceed designed capacity.
  • Simple additive merges work well for counts and sums, but distinct counts and percentiles need mergeable sketches or a serving-layer recompute.
  • Dual implementations let each layer use the best engine, but duplicate logic drifts and produces visible discontinuities at batch boundaries.
  • Full recomputation is conceptually simple, but cost and runtime scale with total history rather than with new data.
  • Unified engines reduce code duplication but can blur the boundary between provisional and authoritative results if the design is not explicit.

?Interview questions

Answer aloud before opening the outline.

1. What is the Lambda architecture in one sentence?

A design that runs a batch pipeline over full history for correctness and a streaming pipeline over recent events for freshness, then merges their outputs in a serving layer so queries are fast and eventually exact.

2. What are the three layers and what does each own?

The batch layer owns immutable history and recomputes authoritative views. The speed layer consumes recent events and produces deltas for the period batch has not covered. The serving layer indexes both and merges them at query time.

3. Why does the batch layer recompute from scratch instead of updating incrementally?

Recomputation keeps the logic simple and makes recovery from bugs trivial: change the code and rerun. Incremental state is faster but accumulates errors and requires careful correction logic. The cost is that runtime grows with history.

4. How exactly does the query merge batch and realtime results?

The batch view covers history up to a known cutoff, and the realtime view covers events after it. For additive metrics the query adds them. The cutoff must be recorded with the batch view so the boundary is never counted twice or skipped.

5. What is the biggest operational problem with Lambda?

Maintaining the same business logic twice. The batch and streaming implementations drift, and the symptom is a jump in the metric whenever the batch view replaces the realtime view. Shared libraries and comparison tests reduce but do not eliminate it.

6. How do you correct a bug in the streaming logic?

Fix the batch logic and recompute the affected views, then reset the speed layer from the new cutoff. The wrong realtime numbers are superseded rather than repaired in place, which is why the immutable master data matters.

7. Which metrics are hard to merge and why?

Distinct counts, percentiles, and anything non-additive. You cannot simply add a batch distinct count to a realtime distinct count because the same user may appear in both. Use mergeable sketches or compute those metrics only in one layer.

8. What happens if the batch job is delayed by a day?

The realtime window grows, so the speed layer must retain and process more state than planned. If it was sized for a few hours, it may fall behind or fail. Alert on window age, not just on job success.

9. How does Lambda compare with Kappa?

Kappa keeps one streaming pipeline and reprocesses by replaying a retained log through a new job version. Lambda keeps two pipelines and reprocesses with batch. Kappa removes duplicate logic; Lambda remains stronger when full batch recomputation is the trusted correction path.

10. When would you choose Lambda today?

When authoritative reporting or billing requires periodic recomputation over complete history, the streaming path is explicitly provisional, and the team can afford to own two pipelines. It is a poor fit for small teams changing logic frequently.

11. What do you monitor in a Lambda system?

Batch duration and completion, realtime window age and state size, merge correctness at boundaries, and divergence between batch and stream outputs for overlapping periods. Also monitor consumer lag and sink failures in both paths.

12. How would you explain the value of immutability here?

If raw events are append-only, every derived view is a pure function of history. That makes bugs recoverable, audits possible, and new metrics retroactive. Mutable state destroys that property because the original facts are gone.

!Traps

  • Implementing the batch and streaming logic separately without comparison tests, then being surprised by jumps at the batch boundary.
  • Leaving the batch cutoff implicit, so boundary events are counted twice or dropped entirely.
  • Using additive merges for distinct counts or percentiles.
  • Sizing the speed layer for a few hours and assuming the batch job will always run on time.
  • Forgetting that reprocessing needs retained raw events and enough spare compute.
  • Claiming exactly-once while the streaming sink is not idempotent.
  • Publishing a rebuilt batch view in place so readers see a partially loaded table.
