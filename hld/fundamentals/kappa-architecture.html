In one lineKappa architecture keeps one streaming pipeline and treats the retained event log as the system of record, so historical reprocessing is just a new job replaying the log from the beginning.
Event log
An append-only, ordered, partitioned store of events that keeps history for a retention period and can be read from any offset.
Offset
The position of an event within a partition, which lets a reader start, resume, or rewind processing at an exact point.
Replay
Reading the log again from an earlier offset, usually into a new version of the job, to rebuild results with corrected logic.
Retention
How long the log keeps events; it bounds how far back a replay can go without an external archive.
Versioned job
A new deployment of the streaming application writing to a new output location, run alongside the old one until cutover.
Cutover
The moment readers switch from the old output to the reprocessed output once the new job has caught up.
Checkpoint
A durable snapshot of operator state and input positions that lets a job restart without losing or repeating work.
Watermark
A progress claim about event time that tells operators when a window is unlikely to receive more late events.
Idempotent sink
A write path where repeating the same output record has no additional effect, which makes replay and retries safe.
Log compaction
A retention mode that keeps only the latest record per key, which preserves current state but destroys full event history.

01The problem Kappa addresses

  • A streaming pipeline gives fresh results but has no natural way to recompute the past when the logic was wrong.
  • Lambda solves that with a second, batch pipeline, which means two codebases and two sets of results that can disagree.
  • The duplication is not just code: it is two deployments, two test suites, two on-call rotations, and two consistency stories.
  • Kappa asks a simpler question: if the input events are retained and replayable, why not reprocess with the same streaming code?
  • Then there is exactly one implementation of the business logic and one processing model to reason about.
  • The architecture is therefore a statement about the log: the log is the source of truth, and every derived store is disposable.

02What Kappa is

  • One streaming pipeline consumes the log, maintains state, and writes derived outputs such as tables, indexes, or caches.
  • There is no batch layer; the same code path handles live traffic and historical replays.
  • The log retains events long enough to cover the reprocessing horizon the business needs.
  • Derived outputs are treated as caches of the log, so they can be rebuilt rather than repaired.
  • Readers query the derived store, not the log, so query latency is decoupled from stream processing.
  • The design depends on three things being true: the log is durable, replay is fast enough, and outputs are safe to rebuild.
Producers append events to the log→Streaming job reads from an offset→Operators update keyed state→Job writes derived output idempotently→Readers query the derived store→On a logic change, a new job replays from offset zero

03The log as the system of record

  • Events are appended in order within a partition and are immutable once written.
  • Partitioning by an entity key preserves per-key order, which matters for stateful operations such as sessions or accounts.
  • Consumers track offsets independently, so one slow or broken consumer does not hold back the others.
  • Retention is time-based or size-based; the log is not infinite, so the retention window is a design parameter.
  • Durability comes from replication across brokers; losing the log means losing the ability to recompute.
  • The log decouples producers from consumers, which is also what makes adding a second, reprocessing consumer cheap.
Treat retention as a budget: it determines how far back you can fix a mistake without restoring from an archive.

04How reprocessing works

  • Deploy the corrected job as a new version pointed at a new output location, not in place over the old one.
  • Start it at the earliest retained offset and let it consume the backlog as fast as the cluster allows.
  • While it catches up, the old job continues serving live traffic and writing the current output.
  • When the new job reaches the head of the log, it is processing live events at the same rate as the old one.
  • Compare outputs for a period, then switch readers to the new output and stop the old job.
  • The old output is kept briefly for rollback, then deleted; the log itself is never rewritten.

05Why versioned output is mandatory

  • Replaying into the live output table would make readers see a mixture of old and corrected results.
  • A separate output prefix or table lets the new job write freely without disturbing production reads.
  • Atomic cutover needs a pointer, alias, or view that readers resolve, so the switch is one change rather than a data migration.
  • Dual writing during replay doubles output storage and write throughput for the duration, which must be provisioned.
  • A rollback is trivial while the old output still exists, which is why cleanup waits until the new version is proven.
  • Schema changes are safer because the new output can use a new schema while the old one keeps serving.

06Correctness: offsets, checkpoints, and sinks

  • A checkpoint records both operator state and the input offsets that state corresponds to.
  • On restart, the job restores state and resumes from the checkpointed offset instead of the latest one.
  • Checkpointed offsets alone do not prevent duplicates: output written after the last checkpoint may be produced again.
  • An idempotent sink keyed by a deterministic event or window identifier makes the repeat harmless.
  • Transactional sinks commit output and offsets together, which gives exactly-once only if the sink and the source can participate in the same transaction boundary.
  • Replay magnifies any non-determinism: timestamps taken from the wall clock, random keys, or lookups of mutable tables produce different results on rerun.

07Event time, windows, and late data

  • Kappa does not remove the hard parts of streaming; it concentrates them in one pipeline.
  • Aggregations use event time, the time the event happened, not the time it was processed, or replays would produce different results.
  • Windows need a watermark policy so the operator knows when to emit a result and stop holding state.
  • Late events either update an already-emitted window, land in a side output for correction, or are dropped by policy.
  • A replay must use the same watermark and allowed-lateness settings, or the rebuilt result will not match the original.
  • Changing window semantics is a logic change like any other: it requires a replay, not a configuration tweak on live state.

08State size and performance

  • Stateful operators keep working sets on local disk or memory, backed by a changelog or snapshot for recovery.
  • Replay reads history far faster than real time in many setups, but the operators still perform the same per-event work.
  • A replay that must rebuild a large join or dedup state is bounded by state size and shuffle throughput, not by log read speed.
  • Unbounded state, such as retaining every user forever, makes both normal operation and replay expensive.
  • Use TTLs, windowing, and incremental cleanup so state tracks the business horizon rather than all history.
  • A replay competes with live processing for the same cluster, so capacity planning must include reprocessing headroom.

09When the log cannot hold enough history

  • Retention is finite, so the replay horizon is finite unless history is archived somewhere cheaper.
  • A common pattern is tiered storage: recent events in the log, older events in object storage, both readable by the same job API.
  • An archive of raw events in open files can be re-ingested into the log for a one-off rebuild.
  • If the log is compacted rather than retained, only the latest record per key survives, so full event history is gone and replay can only rebuild current state.
  • Deletes and tombstones interact badly with audits: a compacted log cannot prove what happened historically.
  • Teams that need long-horizon correction must budget for archive storage and a tested restore path.

10Trade-offs against Lambda

  • Kappa has one codebase, one processing model, and no batch-versus-stream divergence.
  • Lambda can recompute from cold storage cheaply and is not bounded by log retention.
  • Kappa's reprocessing cost is streaming compute over the whole history, which can be more expensive than a batch scan.
  • Kappa requires a mature streaming platform: durable log, checkpointing, state backends, and idempotent sinks.
  • Lambda tolerates a weaker streaming story because the batch layer is the safety net; Kappa has no such net.
  • For a fixed, audited reporting cadence, batch is still simpler; for continuously derived state, one pipeline is simpler.

11Failure modes and operational requirements

  • Replay takes longer than the retention window, so the job can never catch up before old data expires.
  • A replay saturates the cluster and delays live processing, causing consumer lag and stale outputs.
  • Non-deterministic logic makes the rebuilt result differ from production, and the difference is discovered only at cutover.
  • A cutover without a rollback pointer leaves no way back if the new output is wrong.
  • Unmonitored consumer lag means the derived store silently falls behind while dashboards look healthy.
  • Schema evolution in the log breaks old job versions during replay unless the reader handles every historical version.
  • Deleting the old output too early removes the evidence needed to debug a discrepancy.

12Choosing Kappa in an interview

  • Confirm that the business can tolerate the replay horizon implied by log retention and archive cost.
  • Confirm that reprocessing the full history through the streaming engine fits the time and compute budget.
  • Confirm that the team can operate checkpointing, state backends, and idempotent sinks reliably.
  • Describe the reprocessing runbook: new output, replay, validate, cut over, roll back window, cleanup.
  • Explain how late data and event time are handled, since that is where streaming correctness actually lives.
  • Say plainly when you would still pick Lambda or plain batch: audited periodic reporting, or history too large to replay affordably.
Detect a logic bug→Deploy a new job version to a new output→Replay from the earliest needed offset→Catch up to the head of the log→Compare outputs, then cut readers over→Keep the old output until the rollback window closes

↔Trade-offs to say out loud

  • One pipeline removes batch-versus-stream divergence, but leaves no independent layer to cross-check results against.
  • The log as system of record makes replay natural, but ties the correction horizon to retention and archive policy.
  • Replay through the streaming engine reuses the same code, but usually costs more compute than a batch scan over cold files.
  • Versioned outputs make cutover safe and reversible, but double storage and write throughput during the rebuild.
  • Longer retention widens the fixable window, but increases broker storage and replay time.
  • Compacted logs keep storage bounded and preserve current state, but destroy the event history needed for true recomputation.
  • Exactly-once sinks remove duplicate output on retries, but require sink support, deterministic keys, and transactional coordination.
  • Single pipeline simplicity lowers code cost but raises the platform bar: checkpointing, state management, and lag monitoring become critical.

?Interview questions

Answer aloud before opening the outline.

1. What is the Kappa architecture?

A streaming-only design in which the retained, replayable event log is the system of record. All derived state is produced by one streaming pipeline, and corrections are made by replaying history through a new version of that same job.

2. How does Kappa reprocess history without a batch layer?

It starts a new job version at an earlier offset, often the earliest retained one, and lets it consume the backlog into a new output location. When it catches up and the outputs are validated, readers are switched over and the old job is retired.

3. Why must the reprocessed output go somewhere new?

Writing corrections into the live table would expose readers to a mix of old and new results during the replay. A separate output plus an atomic pointer or alias makes the switch instant and gives a clean rollback path.

4. What limits how far back Kappa can replay?

Log retention and archive availability. If events older than the retention window matter, they must be archived cheaply and re-ingested, or the correction is simply impossible. Retention is therefore a business decision, not only an ops setting.

5. What is the difference between a retained log and a compacted log for replay?

A retained log keeps every event, so replay can rebuild any derived result. A compacted log keeps only the latest record per key, so replay can rebuild current state but not history, counts, or audits.

6. How do you avoid duplicates when replaying?

Checkpoint state and offsets together, and make the sink idempotent using a deterministic key such as event id or window end. Duplicates from a restart or replay then overwrite the same record instead of adding a second one.

7. Why is determinism critical in Kappa?

Replay must reproduce what the original run would have produced with the new logic. Wall-clock timestamps, random identifiers, or lookups of changing reference data make the rebuild differ, and you cannot tell a genuine fix from a replay artefact.

8. What happens to state during a big replay?

The job rebuilds state from the beginning, so joins, dedup tables, and aggregates grow to their full size. That makes state size and shuffle throughput the practical limits, and it competes with live processing for cluster capacity.

9. When is Kappa a bad fit?

When history is too large or too old to replay affordably, when audited periodic reporting needs a batch snapshot, or when the team cannot operate checkpointing, state backends, and idempotent sinks. Then Lambda or plain batch is safer.

10. How does Kappa handle late-arriving events?

With event-time windows, watermarks, and an explicit allowed-lateness policy. Late events either update already-emitted windows, go to a side output, or are dropped. Replays must use the same policy or results will not match.

11. What do you monitor in a Kappa system?

Consumer lag and its trend, checkpoint duration and failures, state size, watermark progress, sink write errors, and output freshness. During replay, also monitor catch-up rate against remaining backlog and the retention deadline.

12. How would you compare Kappa and Lambda to an interviewer?

Both solve fresh-plus-correct. Lambda uses two pipelines and pays in duplicated logic; Kappa uses one pipeline and pays in replay cost and platform maturity. The deciding factors are retention horizon, reprocessing budget, and how much the team can trust a single path.

!Traps

  • Assuming the log is infinite and discovering at the first incident that the retention window is too short.
  • Replaying into the live output table and exposing readers to half-corrected data.
  • Using a compacted topic as the system of record and then trying to recompute historical counts.
  • Leaving non-deterministic logic in the job, so replay cannot reproduce the original result.
  • Sizing the cluster for steady-state traffic and having no headroom for a full replay.
  • Cutting over and deleting the old output in the same step, removing the rollback path.
  • Treating exactly-once as a configuration flag while the sink is not idempotent.
