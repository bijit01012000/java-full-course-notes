FaaS
Function as a Service: an event-triggered function that the platform runs on demand, scales automatically, and bills per invocation and duration.
BaaS
Backend as a Service: managed building blocks such as databases, auth, storage, and queues that remove server operations.
Cold start
The extra latency when a function needs a new execution environment: scheduling, pulling the image, starting the runtime, and initializing code.
Event source
The trigger that invokes a function — an HTTP request, queue message, object upload, schedule, or database change.
Execution timeout
A hard platform limit on how long one invocation may run; work that exceeds it is terminated.
Concurrency limit
The cap on simultaneous executions, either per function or per account/region, above which invocations are throttled or queued.
Idempotency
Designing a handler so repeated delivery of the same event produces the same result exactly once in effect.
Provisioned concurrency
Pre-initialized execution environments kept warm so requests skip the cold-start path, at extra cost.
Ephemeral storage
Temporary local disk or in-memory state that exists only for one execution environment and cannot be relied on across invocations.
Vendor lock-in
The cost of moving away when your code, triggers, and permissions are tightly coupled to one provider's runtime and services.

01The problem with managing servers

Running your own services means provisioning machines, planning capacity, patching operating systems, and paying for hardware that sits idle.

  • Capacity planning is guesswork: provision for peak and waste money at night, or provision for average and fail at peak.
  • Someone must patch the OS, runtime, and dependencies, and restart things when they break.
  • Idle servers still cost money and still need monitoring, backups, and security updates.
  • Scaling a traditional fleet requires load balancers, health checks, and autoscaling rules you must tune.
  • Much of this work does not improve the product; it merely keeps the product runnable.
  • Serverless moves that undifferentiated work to the provider — but not the system design.

02What serverless actually means

  • There are still servers; you just do not provision, patch, or see them. The abstraction is over capacity and operations.
  • The core is FaaS: small functions invoked by events, scaled by the platform, billed per use.
  • The surrounding part is BaaS: managed databases, object storage, queues, auth, and gateways.
  • A serverless system is usually an assembly of managed services glued together by events, not a single deployable.
  • You give up long-lived processes, local state, and fine-grained runtime control in exchange for elastic capacity.
  • You still own event design, retries, idempotency, data modeling, timeouts, and cost.
  • Serverless is a spectrum: functions plus managed services at one end, containers with a serverless control plane at the other.

03Execution model and lifecycle

  • An event arrives from a trigger and the platform routes it to an execution environment.
  • If no warm environment exists, the platform creates one — this is the cold start path.
  • The handler runs with a configured memory size, which usually also determines CPU share.
  • The platform may reuse the same environment for later invocations, which is why a global variable can act as a cache — but it is never guaranteed.
  • When the invocation ends, the environment is frozen or destroyed; local disk and memory do not survive reliably.
  • Concurrency is handled by running many isolated environments, not by threads inside one process.
  • Billing typically combines a per-request charge with a duration charge based on allocated memory.
Event arrives→Find or create environment→Initialize runtime and code→Invoke handler→Return or timeout→Freeze or destroy

04Triggers and event sources

  • HTTP triggers: an API gateway or HTTP endpoint maps a request to a function invocation.
  • Queue and stream triggers: messages invoke the function, often in batches, with retries on failure.
  • Object storage events: an upload fires a function to resize an image, scan a file, or index content.
  • Scheduled triggers: cron-like timers for cleanup, reports, and periodic syncs.
  • Database and change-stream triggers: react to inserts and updates without polling.
  • Event shape, batch size, and retry behavior are defined by the trigger — not by your code.
  • The same function can have several triggers, but mixing very different event shapes usually hurts clarity.
A queue trigger and an HTTP trigger have completely different failure semantics: HTTP returns an error to the caller, while a queue retries and may eventually dead-letter.

05Scaling and concurrency

  • The platform scales out per event: one invocation per event, or one per batch, up to account and regional limits.
  • Scaling is effectively unbounded from the developer's view, which means downstream systems become the real limit.
  • A sudden burst can open hundreds of connections to a database or third-party API and overwhelm it.
  • Use reserved or provisioned concurrency to cap or guarantee capacity for critical functions.
  • Throttling behavior differs by trigger: HTTP returns errors, queues buffer, streams may retry the same batch.
  • Warm environments are reused when traffic is steady, so cold starts mostly affect scale-out and idle-then-burst patterns.
  • Fan-out designs need backpressure and concurrency limits, or one popular event becomes an accidental load test.

06Cold starts

  • A cold start includes scheduling a sandbox, pulling the deployment package or image, starting the runtime, and running initialization code.
  • The cost depends on package size, runtime, memory, VPC attachment, and how much work happens at module load.
  • Cold starts hurt interactive, latency-sensitive endpoints more than asynchronous background jobs.
  • Mitigations: keep packages small, lazy-load heavy dependencies, choose a fast-starting runtime, and initialize clients outside the handler.
  • Provisioned or reserved concurrency keeps environments warm at the cost of paying for idle capacity.
  • Scheduled pings can reduce cold starts but are unreliable and do not guarantee warmth at scale.
  • Measure the actual cold-start latency in your runtime instead of assuming a number.

07Limits and statelessness

  • Every invocation has a maximum duration; long batch jobs must be split into chunks or moved to another compute service.
  • Memory is capped and usually priced in steps; CPU scales with it.
  • Request and response payloads have size limits, so large files must go through object storage and be referenced by key.
  • Local disk is small, temporary, and tied to one environment — never treat it as durable.
  • In-memory state may survive a warm invocation but is not shared across concurrent environments and can vanish at any time.
  • State belongs in a database, cache, or object store, with the event carrying only identifiers and small payloads.
  • Network connections should be reused within an environment but assumed to be recreated often.
The stateless rule is not stylistic: concurrent environments cannot see each other's memory, so any coordination must go through an external store.

08BaaS building blocks

  • Managed databases provide storage without patching, but connection limits and cold latency still shape the design.
  • Object storage is the default home for files, images, and artifacts; functions stream references, not bytes.
  • Managed queues and pub/sub provide the buffering that makes bursty serverless systems reliable.
  • Managed auth and identity services remove a large amount of security-sensitive code.
  • Managed caches reduce database load but add another network hop and another bill.
  • Glue services — API gateways, schedulers, workflow engines — replace code that would otherwise be a service.
  • Each managed service has its own limits, quotas, and failure modes; the architecture is the sum of them.

09The cost model

  • You generally pay per invocation plus execution duration weighted by memory, with a free tier in many providers.
  • Idle costs almost nothing, which is a huge win for spiky, low-volume, or per-tenant workloads.
  • At sustained high utilization, per-request pricing can become more expensive than a reserved server or container.
  • Cost is driven by invocation count, duration, memory, and the managed services around the function.
  • Waste hides in retries, polling, chatty calls between functions, and over-allocated memory.
  • Observability and data transfer can quietly dominate the bill.
  • Model cost at both average and peak load, not just at the demo scale.

10Reliability: retries, duplicates, and dead letters

  • Asynchronous triggers usually retry on failure, so the same event may invoke your function more than once.
  • Idempotency is mandatory: use a natural key, a deduplication table, or conditional writes so repeats are harmless.
  • Set a maximum retry count and route exhausted events to a dead-letter queue for inspection.
  • Distinguish retryable errors (timeouts, throttling) from permanent ones (validation failures) and fail fast on the latter.
  • Batch triggers need per-record failure handling, or one poison message blocks the whole batch.
  • Timeouts interact with retries: a function killed at the limit may leave partial side effects.
  • Wrap multi-step workflows in an orchestrator or saga so progress is recorded and resumable.
Event delivered→Handler checks idempotency key→Work and commit→Ack→Retry or dead-letter on failure

11Observability, testing, and local development

  • Each invocation is a short-lived, isolated unit, so traditional host metrics are not enough.
  • Emit structured logs with a request or trace ID, and propagate context through events and downstream calls.
  • Use distributed tracing to see the path across gateway, function, queue, and database.
  • Track invocations, errors, duration percentiles, throttles, cold starts, and concurrent executions.
  • Local emulation never matches the cloud exactly; test against a real environment for triggers, IAM, and limits.
  • Unit-test the handler as a pure function of event and context, and integration-test the trigger wiring.
  • Load-test the downstream systems, because serverless will happily scale the caller faster than they can absorb.

12Vendor lock-in and portability

  • Handlers often depend on provider-specific event shapes, SDKs, identity, and managed services.
  • Triggers, IAM policies, and deployment configuration are usually provider-specific even when the code is portable.
  • Deep integration with managed queues, databases, and auth gives the most leverage and the most lock-in.
  • Portability improves with thin handlers, explicit interfaces, and standard protocols such as HTTP and SQL.
  • Containers and Kubernetes reduce lock-in at the cost of more operational work.
  • A realistic strategy is deliberate coupling for commodity glue and isolation for core business logic.
  • Estimate migration cost before adopting exotic provider features in critical paths.

13When to use it, and when not to

  • Good fit: spiky or unpredictable traffic, event-driven glue, scheduled jobs, webhooks, image and file processing, and per-tenant isolation.
  • Good fit: small teams that want to ship without owning infrastructure or capacity planning.
  • Poor fit: sustained high-throughput services where per-request pricing dominates.
  • Poor fit: long-running compute, heavy stateful sessions, or workloads needing custom kernels and networking.
  • Poor fit: latency-critical paths that cannot tolerate cold starts or concurrency throttling.
  • Many real systems are hybrid: serverless at the edge and for events, containers for steady-state core services.
  • Decide with the workload shape and the team's operational capacity, not with fashion.
Characterize traffic shape→Check latency budget→Check duration and payload limits→Estimate cost at peak→Choose functions, containers, or hybrid

↔Trade-offs to say out loud

  • No server management removes patching and capacity planning but transfers control of the runtime and network to the provider.
  • Automatic scaling absorbs spikes but can overwhelm downstream databases and third-party APIs.
  • Pay per use is cheap when idle but can exceed reserved capacity at sustained high throughput.
  • Cold starts are avoided with provisioned concurrency, which reintroduces the cost of idle capacity.
  • Statelessness makes scaling trivial but pushes every piece of state into another service and another network hop.
  • Managed services reduce operational work but add per-service limits, quotas, and billing surprises.
  • Deep provider integration accelerates delivery but increases lock-in and migration cost.
  • Fine-grained functions isolate failures and permissions but multiply invocations, latency, and observability complexity.
  • Execution limits protect the platform but force long jobs into chunking, orchestration, or different compute.

?Interview questions

Answer aloud before opening the outline.

1. What does serverless mean if servers still exist?

It means the provider owns provisioning, patching, scaling, and availability of the servers. You deploy code and managed services and are billed per use. The abstraction is over capacity and operations, not over hardware.

2. What is the difference between FaaS and BaaS?

FaaS runs your event-triggered code on demand, scaling per invocation. BaaS is the managed backing set — databases, storage, queues, auth. Real serverless systems combine both; functions alone are not an architecture.

3. Walk through a function invocation.

An event arrives from a trigger, the platform finds a warm environment or creates one, initializes the runtime and code, invokes the handler with the event and context, then returns the result and freezes or destroys the environment. Cold-start cost sits in environment creation and initialization.

4. What causes cold starts and how do you reduce them?

New environments must be scheduled, have code or images pulled, the runtime started, and module-level code initialized. Reduce them with smaller packages, lazy loading, fast runtimes, initialized clients outside the handler, and provisioned concurrency for latency-critical paths.

5. Why must serverless functions be stateless?

Concurrent invocations run in separate isolated environments, so in-memory state is not shared or durable. Warm reuse is best-effort. State must live in a database, cache, or object store, with the event carrying identifiers.

6. How does automatic scaling become a problem?

The platform will open concurrency as fast as events arrive, so a burst can exhaust database connections or third-party rate limits. Buffer with queues, cap concurrency, use connection poolers, and add backpressure so downstream systems set the real limit.

7. How do you handle retries and duplicate events?

Assume at-least-once delivery: make handlers idempotent with a deduplication key or conditional write, cap retries, and send exhausted events to a dead-letter queue. Separate permanent failures from transient ones so poison messages do not loop forever.

8. When is serverless more expensive than servers?

At sustained high utilization, because you pay per invocation and per unit of duration on top of managed-service charges. Reserved containers or servers amortize constant load better. Retries, polling, and over-allocated memory also inflate the serverless bill.

9. What are the main execution limits?

Maximum duration, memory, payload size, temporary disk, and concurrency quotas. These force long jobs into chunks or other compute, large files into object storage, and bursts into queues instead of direct invocation.

10. How do you observe a serverless system?

Structured logs with trace IDs, distributed tracing across gateway, function, queue, and database, and metrics for invocations, errors, duration percentiles, throttles, cold starts, and concurrency. Host-level metrics do not exist in the same way because environments are ephemeral.

11. Is serverless always cheaper?

No. It is cheapest for spiky, low-average, event-driven workloads. For steady high throughput, the per-request and per-duration charges can exceed reserved capacity, and the surrounding managed services can dominate the bill.

12. How do you deal with vendor lock-in?

Keep handlers thin, isolate business logic behind interfaces, prefer standard protocols, and accept deliberate coupling only for commodity glue. Containers reduce lock-in but add operational work. Estimate migration cost before using unique provider features on critical paths.

13. How do you test serverless applications?

Unit-test handlers as functions of event and context, contract-test trigger payloads, and integration-test in a real cloud account for IAM, triggers, and limits. Load-test downstream dependencies, since local emulation cannot reproduce scale-out behavior.

14. When would you choose containers over serverless?

For steady high throughput, long-running processes, custom runtimes or networking, predictable latency, and when per-request pricing loses to reserved capacity. Containers trade operational work for control and cost efficiency at scale.

!Traps

  • Calling any managed service serverless without checking whether you still provision capacity.
  • Assuming function instances are reused, so in-memory caches or state appear to work in testing.
  • Ignoring concurrency limits until scale-out exhausts the database connection pool.
  • Writing non-idempotent handlers on at-least-once triggers.
  • Using the request/response path for work that exceeds the execution timeout.
  • Passing large files or payloads through function arguments instead of object storage references.
  • Forgetting that retries and polling inflate both cost and downstream load.
  • Estimating cost only at low traffic and being surprised by the bill at peak.
