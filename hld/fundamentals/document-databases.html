Referencing
Storing related data in a separate document and holding its id, like a foreign key without database enforcement.

An index on an array field that creates one index entry per array element, so queries can match inside arrays.

An ordered series of stages that filter, group, project, and sort documents, each stage feeding the next.
Replica set
A primary plus secondaries that copy the primary's operation log and can elect a new primary after a failure.

How many replica members must acknowledge a write before the driver reports success.
Shard key
The field that decides which shard owns a document; queries that include it avoid fanning out to every shard.

01The problem document databases solve

A product catalog holds things that do not share attributes: a shoe has sizes and a material, a laptop has a processor and memory, a book has an author and a page count.

  • One wide table needs a column for every possible attribute, and most columns stay empty for most rows.
  • One table per product type avoids empty columns but requires a schema change for every new product type.
  • A generic (product_id, attribute, value) table is flexible but makes every query a join and a pivot.
  • A second problem is assembly: one product page may need rows from products, variants, images, and specifications.
  • The application has to join four tables just to rebuild one object it already knows the shape of.
  • A document database stores that whole object as one record, matching how the application uses it.

02What a document database is

  • A document is a self-contained record, usually a JSON-like structure; MongoDB stores a binary form called BSON.
  • Documents are grouped into collections, and each document has a unique identifier such as MongoDB's _id.
  • Unlike a table, documents in one collection may have different fields, so a shoe and a laptop can coexist.
  • The mental mapping is: table to collection, row to document, column to field, foreign key to embedded data or a reference.
  • Queries address fields inside the document, so the engine must understand its contents — unlike a pure key-value store.
  • Popular engines include MongoDB, Couchbase, Firestore, and Cosmos DB; DynamoDB can also store document-style items.

03Document structure and IDs

  • A document can hold simple fields such as name, brand, and price.
  • It can hold an array, such as the available sizes.
  • It can hold a nested object, such as a specifications block with material and weight.
  • It can hold an array of objects, such as variants that each carry a color, size, and stock count.
  • Because everything sits together on disk, one read returns the whole product — no joins, no fan-out.
  • The _id choice matters: database-generated ids are convenient and roughly ordered, UUIDs can be created by any service, and business ids avoid an extra mapping.
  • A time-ordered id keeps recent documents adjacent in the index, which helps range reads but can create a write hotspot if it is also the shard key.

04Flexible schema and its responsibilities

  • Two documents in one collection can have completely different fields, so a new product type needs no migration.
  • The application simply starts writing the new field; older documents keep their old shape.
  • The cost is that every reader must handle missing fields, legacy formats, and unexpected types.
  • So structure does not disappear — it moves into code, where each service must agree on what a valid document looks like.
  • Most engines offer optional schema validation, requiring certain fields and types while allowing the rest to vary.
  • In production, schemaless should mean a predictable core shape with variation only where the data genuinely varies.
  • That balance keeps flexibility without forcing every reader to defend against every historical shape.

05Querying documents

  • Because the engine understands the document, you can filter on any field, not only the id.
  • Queries use a structured filter document rather than a string language, which composes easily in application code.
  • An aggregation pipeline chains stages: filter last month's orders, group by customer and sum totals, sort by spending.
  • Each stage transforms its input and passes the result on, which makes complex reporting expressible without application-side loops.
  • A lookup stage can join another collection, but it is usually cheaper to model documents so joins are unnecessary.
  • Pipelines can use indexes only for the stages that can push a filter down, so stage order affects performance.
  • Complex multi-collection reporting remains less natural than in SQL, which is the main querying limitation.

06Indexes

  • Without an index, a query scans every document in the collection.
  • Single-field and compound indexes work as they do in a relational engine.
  • A multikey index on an array creates one entry per element, so a search for size 9 can use the index directly.
  • Indexes on nested paths such as specifications.material are supported, which keeps embedded data queryable.
  • Text indexes support basic full-text matching; TTL indexes expire documents such as sessions or tokens automatically.
  • The usual cost applies: every write must update every index, and indexes occupy memory and disk.
  • A multikey index over a large array grows quickly, because one document produces many entries.

07Embedding versus referencing

This is the central modeling decision in a document database, and it decides both read cost and update cost.

  • Embed data that is read together, owned by the parent, and bounded in size — order line items, a shipping address.
  • Reference data that is shared, updated independently, or able to grow without limit — a customer, an author.
  • Embedding gives one read and atomic single-document updates, but duplicates data that must then be kept in sync.
  • Referencing keeps one authoritative copy and smaller documents, but needs extra reads and has no enforced foreign keys.
  • A common hybrid stores a reference and a snapshot: the order points at the customer, yet embeds the shipping address as it was at purchase.
  • Snapshots are correct for history — if the customer moves or a price changes, the old order should not change with it.
  • Growth is the deciding factor: an unbounded array turns every append into a rewrite of a larger and larger document.

08A modeling example: a blog

  • Tags are small, belong to the post, and are read with it, so they are embedded as an array.
  • The author is shared across many posts, so the post stores the author id and optionally a display name.
  • Comments look embeddable because they are displayed with the post, but a popular post can collect an unbounded number.
  • An ever-growing array means each new comment rewrites a larger document; MongoDB also caps a document at 16 MB.
  • So comments live in their own collection, each referencing the post id, with indexes on that reference and on time.
  • The post may still embed the few most recent comments, so the first page render needs no second query.
  • The lesson generalizes: model around how the application reads and writes, not around a fixed rule.

09Updates and transactions

  • Partial updates change one field, increment a counter, or push onto an array without rewriting the whole document from the client.
  • Operations on a single document are atomic: if three fields change, either all three or none.
  • That is a strong argument for embedding data that must change together, such as an order and its line items.
  • Changes across several documents need multi-document transactions, which MongoDB added in 4.0 and extended to sharded clusters in 4.2.
  • Those transactions cost more than single-document writes and hold resources longer, so they are the exception rather than the default.
  • Good document design keeps most related changes inside one document precisely so transactions stay rare.
  • If nearly every write needs a multi-document transaction, the model is probably more relational than document-shaped.

10Replication

  • Document databases usually replicate data for availability; in MongoDB the group is a replica set.
  • A replica set has one primary and usually two or more secondaries.
  • All writes go to the primary, which records them in an ordered log called the oplog.
  • Secondaries copy and apply that log, so they converge to the primary's state.
  • If the primary fails, the remaining members hold an election and promote a secondary, usually within seconds.
  • A write concern of majority confirms a write only after most members have it, protecting it against a primary failure right after the acknowledgment.
  • Reads can be served from secondaries to spread load, but those reads may be stale because replication lags.
  • Read preference is therefore a per-query consistency decision, not a global setting.

11Sharding

  • When a collection outgrows one replica set, it is split across shards, and each shard is itself a replica set.
  • The shard key is a field present in every document, such as customer_id on an orders collection.
  • Ranged sharding keeps nearby key values together, which suits range queries but risks concentrating writes at one end.
  • Hashed sharding spreads keys evenly, which balances writes but scatters ranges across shards.
  • A router receives queries and forwards each one to the shards that can answer it.
  • If the query includes the shard key, it targets one shard; if not, it becomes a scatter-gather across all shards.
  • So the shard key should match the most common query, not just the most even distribution.
  • A poor key creates hotspots: low-cardinality fields cannot spread data, and a ranged timestamp sends every new write to the newest range.

12Document versus relational

  • Relational layout normalizes facts and combines them with joins; document layout keeps related data together, shaped for reading.
  • Relational schema is fixed and enforced; document schema is flexible with optional validation.
  • Relational strength is complex joins and ad hoc queries across many entities; document strength is fast read and write of whole objects for one main entity.
  • Relational transactions are multi-row by default; document atomicity is per document, with multi-document transactions available but costlier.
  • The line has blurred: PostgreSQL indexes JSON columns, and MongoDB supports joins and transactions.
  • So the choice is less about feature checklists and more about which model matches your data and access patterns.
  • A useful smell: if you reference everything and join on almost every query, the data is probably relational.

13When to use a document database

  • The data is naturally an object with nested detail: product catalogs, content management, user profiles, game state.
  • Records vary in structure, or the model changes often enough that migrations would dominate delivery.
  • Most requests read or write one main entity: one product, one article, one user.
  • It is a weaker fit when many entities must be combined in different ways, as in financial reporting across accounts, transactions, and customers.
  • It is also weak when aggregates must span the whole collection rather than one document.
  • The design test is whether the data is read in the same shape it is stored; if not, the joins you keep writing are the signal.
  • A common production pattern keeps the relational database as the source of truth and uses documents for the read-optimized view.

↔Trade-offs to say out loud

  • Embedding gives single-read, atomic updates but duplicates data and can produce ever-growing documents.
  • Referencing keeps one authoritative copy and small documents but adds reads and provides no enforced foreign keys.
  • Flexible schema removes migration friction but pushes validation into every reader and lets formats drift.
  • Data locality makes whole-object reads fast but works against queries that need fields across many entities.
  • Multikey indexes make array membership queryable but multiply index entries per document and inflate write cost.
  • Single-document atomicity is cheap and reliable but only covers changes you managed to keep inside one document.
  • Multi-document transactions extend correctness but add coordination cost and hold resources longer.
  • Sharding by a hash balances writes but scatters ranges; sharding by range keeps ranges local but risks hot ranges.
  • Majority write concern protects acknowledged writes but adds latency to every write.
  • Secondary reads spread load but can return data that lags the primary.

?Interview questions

Answer aloud before opening the outline.

1. What is a document database in one sentence?

A database that stores each entity as a self-contained JSON-like document with nested objects and arrays, grouped into collections and read as a whole. It is designed so one request that touches one entity becomes one read, without joins.

2. Why does a product catalog fit documents well?

Products share a core shape but differ widely in attributes, so a fixed table would be mostly empty columns or need constant schema changes. A document holds exactly the fields each product has, and one read returns everything a product page needs.

3. What is data locality?

Keeping related data together in one document so the storage engine can return it in a single read. It removes the join work but means the same data may be copied into several documents, which must then be kept in sync.

4. Embed or reference: what is the rule?

Embed when the data is read together, owned by the parent, and bounded in size. Reference when it is shared, updated independently, or unbounded — an ever-growing array turns each append into a rewrite of a larger document and eventually hits the document size limit.

5. Why is 'schemaless' misleading?

Because the structure still exists in the application code that reads and writes documents. Nothing enforces it, so readers must handle missing fields and old formats, and different services can write incompatible shapes. Optional schema validation restores a predictable core.

6. How do multikey indexes work?

An index on an array field creates one entry per array element, each pointing back to the owning document. A query for one element value can then use the index instead of scanning. The cost is that one document with a long array produces many index entries, so index size and write cost grow with array length.

7. What does the aggregation pipeline give you?

A sequence of stages where each transforms the data and passes it on — filter, group, sum, sort, project. It lets the database do reporting work that would otherwise be application loops. A lookup stage can join another collection, but modeling to avoid that join is usually faster.

8. What is atomic in a document database?

Operations on a single document are atomic: all field changes apply or none do. That is why embedding related data helps correctness as well as speed. Cross-document changes need multi-document transactions, which exist but cost more.

9. How does a replica set handle a primary failure?

Secondaries copy the primary's oplog and apply it. If the primary fails, the remaining members hold an election and promote one secondary. Writes acknowledged with majority write concern survive that failure; writes acknowledged by the primary alone may not.

10. How should you choose a shard key?

Match the most common query and spread writes. A high-cardinality key included in typical queries keeps reads on one shard; a low-cardinality key cannot spread data, and a ranged timestamp sends every new write to the newest range. Hashing helps balance writes but scatters ranges.

11. What is a scatter-gather query and why is it bad?

If a query does not include the shard key, the router cannot know which shard holds the matching documents, so it sends the query to all shards and merges the results. Latency becomes the slowest shard's, and cost grows with shard count.

12. When is a relational database the better choice?

When many entities must be combined in different ways, when reporting spans the whole data set, or when multi-row correctness is the norm. If you reference almost everything and join on every query, the data is relational in shape regardless of the engine you picked.

!Traps

  • Embedding an unbounded array such as comments or events, then hitting document size limits and rewrite costs.
  • Choosing randomness for ids without checking how it interacts with index locality and the shard key.
  • Treating schemaless as requiring no validation, so every reader defends against unknown shapes.
  • Assuming multi-document writes are atomic because single-document writes are.
  • Sharding on a low-cardinality field such as status and expecting even distribution.
  • Reading from secondaries for a flow that must show the user their own write.
  • Modeling like a relational schema — one small collection per entity — and then joining on every query.
