In one lineA CDN is a globally distributed cache that serves content from an edge location near the user, so latency and origin load drop — as long as the content is shareable, cacheable, and safely invalidated.
Edge location (PoP)
A CDN site close to users that accepts requests, stores cached responses, and forwards misses to the origin.
Origin
The authoritative source of content — an application server, object storage bucket, load balancer, or API gateway.
Origin shield
An intermediate cache layer between edge servers and the origin that collapses duplicate misses into one origin fetch.
Cache key
The set of request attributes — usually URL plus selected query parameters, headers, or cookies — that decides whether two requests share a cached response.
TTL
Time to live: how long an edge may reuse a cached object before treating it as stale.
Cache-Control
The HTTP response header that tells browsers and shared caches whether, and for how long, a response may be stored.
Purge
An explicit invalidation that removes or stops serving a cached object before its TTL expires.
Pull CDN
A CDN that fetches content from the origin on the first request for it at each edge, then caches it.
Push CDN
A CDN that the application uploads content to ahead of time, distributing it to edges before users ask for it.
Cache hit ratio
The share of requests served from the edge instead of the origin; the primary measure of CDN effectiveness.

01The problem

One origin in one region is the simplest deployment, and it works until users are far away or traffic is large.

  • Distance is latency: a request from India to a Virginia origin crosses a long network path in both directions, and TCP plus TLS setup multiplies the round trips.
  • Popular static files are byte-identical for every user, so the origin re-sends the same image, script, or video segment millions of times.
  • Origin bandwidth, connection counts, and CPU saturate first during launches, sales, and viral traffic.
  • Writes, personalized responses, and uncached objects still must reach the origin, so a CDN reduces backend load rather than removing the backend.
  • The fix is to keep copies of popular content near users and let the origin handle only misses, dynamic requests, and writes.

02Edge locations

  • CDN servers are deployed in many cities; each site is an edge location or point of presence (PoP).
  • An edge accepts user requests, stores cached responses, and forwards requests it cannot satisfy to the origin.
  • Proximity usually shortens the network path, which lowers round-trip latency and improves throughput.
  • Because most requests terminate at the edge, the origin sees far fewer connections and much less egress traffic.
  • Edge sites differ in capacity and health, so a nearby PoP that is saturated or degraded may be bypassed for another.
  • Edges are also where TLS termination, WAF rules, bot filtering, and DDoS absorption usually run.

03Life of a CDN request

  • The client resolves the CDN hostname and receives the address of a nearby edge, not the origin.
  • On a cache hit, the edge returns the stored response and the origin never sees the request.
  • On a cache miss, the edge fetches the object from the origin, returns it, and stores it if the response is cacheable.
  • Whether a response may be stored depends on the method, status code, caching headers, and provider rules; a POST or a Set-Cookie response is normally not shared.
  • The next request for that object in the same region becomes a hit, which is the entire point of the layer.
  • Encrypted or authenticated responses add a wrinkle: the edge may terminate TLS but still must not share one user's private response with another.

04What CDNs cache

  • Static assets are the natural fit: images, JavaScript, CSS, fonts, video segments, and software downloads are read often and rarely change.
  • The decisive test is shareability: can many different users reuse exactly the same response?
  • The second test is staleness tolerance: can this content be a little old for a known period?
  • Some dynamic content qualifies too — a public product page or a list of supported countries may be identical for everyone.
  • Poor fits are account pages, carts, checkout, payment flows, admin pages, and anything that depends on a private cookie or login state.
  • Video is usually delivered as many small segments rather than one huge file, so each segment behaves like a cacheable static object.

05HTTP caching headers

The origin declares cacheability with response headers; the CDN enforces them unless its own configuration overrides them.

  • public permits shared caches such as a CDN to store the response; private restricts it to the end user's browser.
  • max-age is freshness in seconds; s-maxage overrides it for shared caches only.
  • no-store forbids storage entirely; no-cache permits storage but requires revalidation before each reuse.
  • immutable tells caches the bytes at that URL will not change while fresh, so revalidation is pointless.
  • stale-while-revalidate allows a stale copy to be served briefly while a background refresh runs.
  • ETag and Last-Modified enable conditional requests: an unchanged object returns a small 304 Not Modified instead of the full body.
  • Headers are a contract, not a suggestion — a CDN rule that overrides them can keep serving content the origin considers private.

06TTLs

  • The TTL is how long an edge may reuse an object before it must revalidate or refetch it.
  • A long TTL raises the hit ratio and cuts origin traffic, but widens the window in which users see old content.
  • A short TTL keeps content fresher but sends more requests to the origin and lowers the hit ratio.
  • Versioned or content-hashed assets can carry a very long TTL because the URL itself changes when the content changes.
  • Fast-moving API responses may need only seconds or minutes, and some should not be cached at all.
  • Set the TTL from how often the object changes and how much staleness the product tolerates — not from a single global default.
  • The cost of one stale response, not engineering habit, should drive the number.

07Purging and versioned URLs

  • Sometimes you cannot wait for a TTL, because a wrong image, a bad config, or a security fix is already cached around the world.
  • There are two answers: force the old copy out (purge), or never reuse the same key for new content (versioned URLs).
  • Purging is an operational action with propagation delay; versioning is a design choice made at build time.
  • Versioned URLs are the default for build artifacts; purging is the exception for stable URLs that must change immediately.
  • Both approaches must handle the traffic that follows: a purge creates misses, and a new version creates a new cold key.

Purging

  • A purge (invalidation) removes or stops serving the cached object; the next request becomes a miss and refetches from the origin.
  • Scope can be a single URL, a path prefix, or a group of objects tagged together.
  • Global purges propagate through many PoPs and can take time to reach every edge.
  • Providers limit purge volume and often charge for it, so purging cannot be the normal update path.
  • Every purged object turns a hit into a miss; a mass purge can send a burst of traffic straight to the origin.

Versioned URLs

  • Publish logo.v2.png or app.a7b9.js instead of overwriting logo.png.
  • A new URL is a new cache entry, so nothing needs to be invalidated and old copies stop being requested.
  • Content-addressed names let you cache for a very long time with immutable, giving both strong caching and reliable updates.
  • The build system should generate the hash so a human cannot forget to bump it.
  • Some URLs must stay stable, such as HTML entry points: give those a short TTL, purge on deploy, or rely on ETag revalidation.

08Pull CDNs and push CDNs

  • A pull CDN fills each edge on demand: the first request is a miss that fetches from the origin and caches the result.
  • Pull is simple because the CDN manages content automatically; the application does nothing per file.
  • Its cost is a cold miss: the first user in a region waits for the full origin round trip, and every new edge repeats it.
  • A push CDN uploads content ahead of time and the CDN distributes it to the edge network.
  • Push removes the first-request miss and suits large, known releases such as software downloads, media, or a launch catalog.
  • Push costs coordination: the application must track what was uploaded, when it changed, and which version is live.
  • Pull is the default for general web content; push is a deliberate choice for large or pre-announced content.

09Origin shield

  • An origin shield is an extra cache layer between the edges and the origin, often called a mid-tier or shielding layer.
  • Without it, one hundred edges that all miss the same object can produce one hundred origin requests.
  • With it, the edges miss to the shield, and the shield fetches from the origin once and serves the rest.
  • It is most valuable when many regions need the same content at roughly the same time — a launch, a news event, or a synchronized expiry.
  • The costs are an extra hop on shield misses and a regional component whose failure can affect many edges at once.
  • Place the shield near the origin or where traffic concentrates so its own cache is likely to be warm.

10How requests are routed to an edge

  • DNS-based routing: the CDN's authoritative DNS answers the hostname with an edge address chosen by geography, measured latency, or load.
  • Anycast: many PoPs advertise the same IP address, so internet routing delivers the user to a nearby available site.
  • The closest PoP on a map is not always chosen; network path, peering, edge capacity, and health all influence the result.
  • Routing happens before the object is known, so content-aware steering — such as sending video to a streaming tier — is configured separately.
  • Bad routing shows up as consistently high latency for one region even though the cache itself is healthy.
  • Validate routing with real user monitoring from the regions that matter, not with assumptions about distance.

11Cache keys

  • The cache key decides when two requests may share one cached response; the URL is almost always part of it.
  • A key that is too narrow — every query parameter, every cookie — stores duplicates of the same bytes and destroys the hit ratio.
  • A key that is too broad — ignoring the image width or Accept-Language — serves the wrong content.
  • Normalize what is safe: drop tracking parameters, sort the remaining ones, and lowercase the host.
  • Leave cookies out unless the response genuinely varies by cookie.
  • Vary on a header only when the response body actually differs by that header.
  • Cache key design is a correctness decision first and a hit-ratio decision second; most CDNs let you configure exactly which attributes count.
Example: /img.png?w=200&utm_source=news should usually key on w and ignore utm_source.

12Cache stampedes and cold misses

  • A stampede is many edges missing the same object at once, usually right after it expires, producing a spike at the origin.
  • TTL jitter adds small random variation so copies in different locations do not expire together.
  • Request coalescing lets one origin fetch satisfy all concurrent misses for the same key.
  • Stale-while-revalidate keeps serving the old copy while a single background refresh runs.
  • Origin shielding reduces the number of independent fetches the origin must handle.
  • Cold content has no cached copy anywhere, so a launch needs pre-warming or a push rather than a clever TTL.
  • The origin must also be sized for the miss path, because that path is the only one it still serves.

13Personalized content and API responses

  • A CDN only pays off when many users can share one response; personalization removes exactly that property.
  • A response containing a name, balance, cart, or account state is unique per user, and caching it in a shared cache leaks data between users.
  • Putting user identity into the cache key avoids the leak but creates one entry per user, so the hit ratio collapses.
  • The common split is shared assets and public data at the edge, with personalized requests continuing to the application backend.
  • Public API responses such as a country list or catalog metadata can be cached at the edge if the key covers authentication, locale, and location.
  • Endpoints like /api/me or /checkout should skip the shared cache entirely.
  • Never store a response to a request carrying a session cookie or Authorization header unless the design has been reviewed for privacy.

14Operating a CDN: large files, reliability, and metrics

  • Range requests let a client fetch part of a file, which is how video players seek without downloading the whole object.
  • Serving large downloads from edges removes bandwidth that would otherwise dominate origin cost and connection capacity.
  • If the origin is briefly unavailable, some CDNs keep serving cached content, so static parts of the site survive a backend outage.
  • CDNs absorb DDoS traffic and add WAF rules, bot filtering, rate limits, and TLS management — useful, but not a replacement for application security.
  • Track cache hit ratio overall and per important route, plus origin request volume, latency, bandwidth, evictions, error rate, and stale-served traffic.
  • Response headers such as Age and provider-specific hit/miss headers show what actually happened to a request; names vary by provider.
  • Choose a provider on user geography, cloud fit, cache-rule flexibility, purge speed, shielding and coalescing support, observability, security, and egress pricing.

↔Trade-offs to say out loud

  • Long TTLs raise the hit ratio and cut origin load but widen the window for stale or wrong content.
  • Short TTLs keep content fresh but push more requests to the origin and can erase the CDN's cost benefit.
  • Versioned URLs give safe long-lived caching without purge risk, but require build-time discipline and stable entry points that cannot be versioned.
  • Purging gives immediate corrections at the cost of propagation delay, provider limits, and a burst of origin misses.
  • Pull CDNs remove per-file management but expose a cold miss for the first user at each edge; push CDNs remove that miss but add upload coordination.
  • Origin shielding reduces duplicate origin fetches and protects against expiry bursts but adds a hop and another component to operate.
  • Narrow cache keys protect correctness while lowering the hit ratio; broad keys raise the ratio while risking wrong or leaked responses.
  • Edge caching in general improves latency, availability, and cost, but adds configuration surface, provider dependency, and harder debugging of what version a user actually received.

?Interview questions

Answer aloud before opening the outline.

1. What is a CDN and why does it reduce latency?

A CDN is a network of edge caches deployed close to users. The client connects to a nearby PoP instead of a distant origin, so the network path is shorter and repeated round trips for static content disappear. It also removes load from the origin because most requests never reach it.

2. Walk me through a CDN request on a hit and on a miss.

The hostname resolves to an edge address. On a hit, the edge returns the stored response and the origin is untouched. On a miss, the edge fetches from the origin, optionally stores the response according to its headers and cache rules, and returns it. Later requests in that region then hit.

3. Pull CDN versus push CDN — when do you choose which?

Pull fills edges on first request; it is the default for general web content because the CDN manages everything. Push uploads content ahead of time, avoiding the first-request miss and suiting large planned releases like software or media. The cost of push is that the application must manage uploads and versions.

4. What is the difference between max-age, s-maxage, and no-cache?

max-age is freshness in seconds for any cache. s-maxage overrides it for shared caches such as a CDN, which is how you can cache longer at the edge than in the browser. no-cache allows storage but requires revalidation before each reuse; it is not the same as no-store, which forbids storage.

5. How do you choose a TTL?

From the object's change frequency and the product's tolerance for staleness. Hash-named assets can be cached for a very long time, HTML needs a short TTL or purge-on-deploy, and volatile APIs may need seconds or no caching at all. The cost of one stale response should drive the number.

6. How do you make an urgent content change visible immediately?

Purge the affected URLs, prefixes, or tags and accept propagation delay and origin refetches. For static assets, the better long-term answer is a versioned URL: publish a new filename, reference it from the deployment, and let the old entry age out.

7. Why are versioned URLs better than purging?

A new URL is a new key, so there is nothing to invalidate, no provider purge limits, no propagation window, and no correctness risk from an old edge copy. It also allows immutable caching for a year. Purging remains necessary for stable URLs such as HTML entry points.

8. What is an origin shield and when does it help?

It is an intermediate cache between edges and the origin. It helps when many edges miss the same object at once: the edges fetch from the shield and the shield fetches from the origin once. It also reduces origin load during launches and synchronized expiries, at the cost of an extra hop.

9. How do you design a CDN cache key?

Start from the URL, include only the query parameters and headers that actually change the response, and exclude tracking parameters and cookies that do not. Too broad serves wrong content; too narrow duplicates entries and lowers the hit ratio. Validate with real request variants, not guesses.

10. What is a cache stampede and how do you prevent it?

It is a burst of misses for the same popular object, usually after it expires, which hits the origin all at once. Mitigate with TTL jitter, request coalescing, stale-while-revalidate, and origin shielding. Cold content also needs pre-warming because no technique can serve a copy that does not exist.

11. How do you handle personalized content at the edge?

Normally you do not cache it in the shared layer. Serve it from the application, or split the page into a shared shell at the edge and personalized fragments from the backend. Putting user identity in the cache key is safe only if every entry is truly per-user, which usually destroys the benefit.

12. Which CDN metrics matter?

Cache hit ratio overall and per important route, origin request volume, latency, bandwidth, evictions, error rate, and how much traffic is served stale. A high global hit ratio can hide a bad path, so segment by route and region.

13. How does a CDN route a user to an edge?

Usually by authoritative DNS that returns a nearby or least-latency edge, or by anycast where many PoPs advertise the same IP and BGP picks a nearby path. Capacity, health, and network conditions matter, so the geographically closest site is not guaranteed.

14. What happens when the origin goes down?

Cached content can still be served, so static pages may keep working for the TTL window. Anything not cached, and all writes, fail. This is why the CDN reduces blast radius but never replaces backend availability, and why a stale-serving policy should be an explicit decision.

!Traps

  • Caching a response that contains user-specific data in a shared edge cache and leaking it to other users.
  • Putting every cookie and tracking parameter in the cache key, then blaming the CDN for a poor hit ratio.
  • Assuming a purge is instant and global when it propagates asynchronously across PoPs.
  • Overwriting a static filename in place and expecting every user to receive the new bytes immediately.
  • Giving HTML a long TTL while asset filenames are versioned, so users keep loading an old page that references old assets.
  • Planning a launch without pre-warming or accounting for cold misses at every edge.
  • Measuring only the global hit ratio and missing a critical route or region with a terrible one.
  • Treating the CDN as a substitute for backend availability, authentication, or application-level security.
