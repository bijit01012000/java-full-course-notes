In one lineQuery optimization is the work of making a query read only the rows it needs — usually a far better return than a bigger server, a read replica, or a cache layered over a query that scans 50 million rows to return 20.
Declarative query
SQL states the result you want, not the algorithm; the database chooses indexes, join order, and execution strategy.
Query plan
The tree of operations the executor will run: scans, joins, sorts, aggregates, and the access method for each table.
Cost-based optimizer
The planner component that estimates the cost of alternative plans using statistics and picks the cheapest.
Cardinality estimate
The optimizer's prediction of how many rows a step will produce; wrong estimates cascade into bad join orders.
Statistics
Per-table summaries such as row counts, distinct values, most common values, and histograms of distribution.
Sequential scan
Reading every row of a table and filtering as it goes; correct but expensive when the filter is selective.
Sargable predicate
A filter the index can be used for, such as col = ? or col > ?, as opposed to a function applied to the column.
Nested loop join
For each row of the outer input, look up matching rows in the inner input; cheap for small inputs, disastrous for large ones.
Hash join
Builds a hash table from one input and probes it with the other; good for large unsorted inputs with equality joins.
N+1 query
One query to fetch a list plus one query per item, turning a single logical read into hundreds of round trips.

01The problem: the query did not change, the data did

An orders page loaded instantly with a few thousand rows. Two years later the table holds 50 million rows and the same query takes seconds, even though no application code changed.

  • The query now does far more work: more rows to examine, more pages to read, more rows to sort.
  • The instinct is to scale up, add a replica, or add a cache — all of which mask the symptom.
  • A query that reads 50 million rows to return 20 will be slow on almost any hardware.
  • If the query reads only the rows it needs, one well-sized primary can often absorb much more traffic.
  • Latency growth is often nonlinear because an index stops fitting in memory or the planner switches strategies.
  • Optimization is about rows and pages touched, not about the elegance of the SQL text.
  • Fix the work first; add hardware only when the work is already minimal.

02How a database runs a query

SQL is declarative. You say what you want; the database decides how to get it. That translation happens in four stages.

  • Parse: check syntax and confirm the tables, columns, and types exist; produce a parse tree.
  • Rewrite: normalize the query into an equivalent but easier form — simplify expressions, flatten views, turn some subqueries into joins.
  • Plan: the optimizer enumerates access paths and join orders, estimates each cost, and selects a plan.
  • Execute: the executor runs the plan tree and streams rows back, or buffers them for sorting and aggregation.
  • The plan is a tree: each node consumes rows from its children and emits rows upward.
  • The same SQL text can map to thousands of plans; the difference between the best and worst is often orders of magnitude.
  • Prepared statements may cache a plan, so the plan chosen for one parameter set can be reused for a very different one.
  • Because the plan is derived, changing data or statistics can change performance without any code change.
SQL text→Parse→Rewrite→Plan→Execute→Rows returned
This is why 'the query is the same as day one' is not a defense: the plan is an output of the data, not of the text.

03The cost-based optimizer

Most relational databases use a cost-based optimizer. For each query it considers alternative plans and estimates which one will do the least work.

  • Should it read the whole table sequentially, or use an index and follow row references?
  • For a three-table join, which table should be read first, and which join algorithm should combine them?
  • Should it sort the result, or read rows from an index that is already in the required order?
  • Should it materialize a subquery once, or re-evaluate it per outer row?
  • To estimate row counts it uses statistics: table size, distinct values, most common values, and histograms.
  • Cardinality estimates propagate upward: each node's estimated output becomes the next node's input estimate.
  • Cost combines estimated I/O (pages read) with CPU work, weighted by the engine's cost constants.
  • It picks the cheapest plan it found, not the global optimum: the search is bounded for large joins, so heuristics and pruning matter too.

04When statistics mislead the optimizer

  • Estimates are only as good as the statistics; stale statistics after a large load are a classic cause of a sudden plan change.
  • The optimizer assumes columns are independent; correlated columns (city and postal code) multiply selectivities and undercount matches.
  • Histograms have limited buckets, so values in the tail can be badly misestimated.
  • Skewed data means the average case is not the case you are running; a tenant with millions of rows behaves differently from one with ten.
  • A prepared plan built for a common value can be terrible for a rare value — the same cached plan serves both.
  • Uniformly distributed parameters hide the problem in testing and expose it in production.
  • A wrong estimate at the bottom of the plan compounds: a nested loop chosen for 10 rows but fed 100,000 becomes a disaster.
  • Fixes include refreshing statistics, extended or multi-column statistics, plan hints, and restructuring the query so estimates are less fragile.
When the plan looks insane, compare estimated rows to actual rows. The mistake is usually an estimate, not the SQL.

05Finding the queries worth optimizing

  • Do not start from the query that annoys you; start from the queries that consume the most total database time.
  • Rank by total time = calls × average latency, not by the single slowest outlier.
  • Use the slow query log for outliers and a statement-statistics view for aggregate cost, calls, and rows.
  • Look for queries with a very high rows examined to rows returned ratio; that gap is wasted work.
  • Separate read queries from write queries; the fixes and the risks differ.
  • Sample production parameters, not synthetic ones, because plans depend on value distribution.
  • Correlate with application traces to find the endpoint and user action responsible.
  • Optimize one query, re-measure, and confirm the database-wide time actually dropped rather than shifting elsewhere.

06Reading the query plan

  • EXPLAIN shows the plan the optimizer chose without running the query; EXPLAIN ANALYZE runs it and reports actual times and rows.
  • Read the plan inside out and bottom up: leaves are scans, upper nodes combine and transform.
  • Check the access method first: sequential scan, index scan, index-only scan, or bitmap scan.
  • For each node, compare estimated rows with actual rows; a large gap explains most bad plans.
  • Look for the node where actual time drops sharply — the expensive work happens below it.
  • Watch for explicit sorts and hash operations that spill to disk when the working set exceeds memory.
  • A high number of loop iterations on a nested loop means the inner side is being re-read many times.
  • Beware of EXPLAIN ANALYZE on writes: it really executes them, so wrap it in a transaction you roll back.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
Buffers matter: they show whether the time is disk I/O or CPU, and whether the plan is touching far more pages than the result needs.

07Reducing the rows and pages read

  • Make predicates sargable: compare the bare column, not an expression around it.
  • WHERE date(created_at) = '2026-01-01' usually cannot use an index on created_at; rewrite as a half-open range.
  • WHERE name LIKE '%shoes%' cannot use a normal B-tree; a leading wildcard forces a scan.
  • Avoid wrapping indexed columns in functions or implicit casts that change the comparison type.
  • Select only needed columns; SELECT * widens rows, defeats covering indexes, and increases network cost.
  • Filter early and push predicates as close to the scan as possible; reduce rows before joins and sorts.
  • Replace repeated correlated subqueries with a join or a lateral aggregate when the planner re-executes them per row.
  • Use EXISTS rather than COUNT(*) when you only need to know whether a row exists.

08Indexing for the query shape

  • An index helps only if its leading columns match how the query filters; column order is part of the design.
  • For a query filtering one column and sorting by another, a composite index in equality-then-sort order can remove the sort entirely.
  • A covering index that includes every referenced column can answer the query without fetching table rows.
  • Add the ordering column to the index rather than sorting a large result at query time.
  • Partial or filtered indexes help when queries always target a small subset, such as unresolved jobs.
  • An index on a low-selectivity column is often ignored; put it in a composite index where another column narrows first.
  • Indexes cost write throughput and storage, so add the smallest set that supports the measured queries.
  • Verify with the plan: an index that exists but is not used changes nothing.

09Join strategy and join order

  • A nested loop is efficient when the outer side is small and the inner side has an index on the join key.
  • A hash join handles large unsorted inputs and equality joins, but builds a hash table that must fit in memory to stay fast.
  • A merge join exploits sorted inputs and works well when both sides are already ordered by the join key.
  • Join order matters most when intermediate results are large; a selective table should usually be read first.
  • Filtering before the join reduces the rows that every later node must process.
  • Missing indexes on join columns force repeated scans of the inner table.
  • Join types must match data types and collations; an implicit cast can prevent index use on the join key.
  • When the planner's order is wrong because of bad estimates, fix statistics before reaching for hints.

10Sorting, aggregation, and pagination

  • An explicit sort costs memory and spills to disk when the row set exceeds the sort budget.
  • Reading rows from an index that is already ordered avoids the sort entirely, especially with a small LIMIT.
  • Aggregating over a huge table is expensive; pre-aggregated rollups or materialized views move the cost off the request path.
  • COUNT(*) over a large table must count rows; approximate or cached counts are a product decision.
  • OFFSET n makes the database produce and discard n rows, so deep pages get progressively slower.
  • Keyset pagination uses the last seen sort key in the WHERE clause and seeks directly with an index.
  • Grouping by a high-cardinality column builds a huge hash table; grouping by a low-cardinality column is cheaper.
  • Window functions can be cheaper than self-joins for running totals and rankings, but still require sorting.
-- keyset pagination instead of OFFSET
SELECT id, created_at, total
FROM orders
WHERE customer_id = 42
  AND created_at < $1
ORDER BY created_at DESC
LIMIT 20;
Keyset pagination is stable only with a deterministic tiebreaker, such as (created_at, id).

11N+1 queries and application-level patterns

  • The N+1 pattern issues one query for a list and then one per item, multiplying round-trip latency and database load.
  • It often hides inside an ORM that lazily loads an association while rendering a page.
  • Fix it by batch loading the related rows with a single IN query and joining in memory, or by using a join.
  • Check the query count per request in a trace; latency that scales with result size is the signature.
  • Avoid unbounded IN lists and SELECT * in batch queries; chunk very large id sets.
  • Connection pool exhaustion is often an N+1 symptom, not a pool-size problem.
  • Caching a query result is valid only when the invalidation story is clear; otherwise it hides staleness.
  • Denormalization and materialized views are legitimate end states, but only after the query itself is efficient.

12Fix, verify, and keep it fixed

  • Change one thing at a time: index, query rewrite, or schema — not all three — so you can attribute the improvement.
  • Re-run EXPLAIN ANALYZE after each change and compare rows read, buffers, and actual time.
  • Test with production-shaped data and parameters; a small dataset will happily choose a plan that fails at scale.
  • Add the query to a performance regression check so a future schema change cannot silently reintroduce the scan.
  • Update statistics after large backfills or bulk loads so plans reflect the new distribution.
  • Watch for plan changes after upgrades; optimizer versions and cost constants change behavior.
  • Retire indexes that no query uses; they slow writes and add planning work.
  • Only after the query reads a sensible number of rows should you consider replicas, caching, or a bigger machine.
Find the expensive query→Read the plan→Compare estimates to actuals→Fix the access path→Re-measure→Guard against regression
A cache in front of a query that scans 50 million rows turns one slow query into a fast one and a cold-start outage.

↔Trade-offs to say out loud

  • Adding an index speeds the targeted read but slows every insert, update, and delete on that table.
  • Covering indexes eliminate table lookups but widen the index and increase storage and maintenance cost.
  • Rewriting a query is free in infrastructure but can reduce readability and must be re-verified against every data distribution.
  • Denormalization or rollups make reads cheap but move cost to write time and introduce staleness.
  • Caching results cuts latency and load but adds invalidation logic and a cold-start failure mode.
  • Keyset pagination is fast at any depth but forbids jumping to an arbitrary page number.
  • Optimizer hints rescue one bad plan but freeze it, so it can become wrong as data changes.
  • Scaling hardware is immediate and code-free but leaves the wasted work in place and raises cost permanently.
  • Prepared statements reduce planning overhead but risk reusing a plan that fits a different parameter value.

?Interview questions

Answer aloud before opening the outline.

1. What is query optimization?

Reducing the work a query does — rows read, pages touched, sorts, and joins — so it returns the same result with less I/O and CPU. It is usually about the access path and the plan, not about rewriting SQL for style.

2. Why did a query get slow when nothing in the code changed?

The data grew. More rows mean more pages to scan, indexes that no longer fit in memory, and different planner choices. The plan is derived from statistics about the data, so the same SQL can map to a very different plan over time.

3. Walk through how a database executes a query.

It parses and validates the SQL, rewrites it into an equivalent form, plans it by estimating the cost of alternative access paths and join orders, then executes the chosen plan tree and returns rows. The plan step determines almost all of the performance.

4. How does a cost-based optimizer choose a plan?

It uses table statistics — row counts, distinct values, most common values, histograms — to estimate how many rows each step will produce. It assigns each candidate plan a cost from estimated I/O and CPU, then picks the cheapest plan it explored, which is not necessarily the true optimum.

5. What are the most common causes of a bad plan?

Bad cardinality estimates: stale statistics, correlated columns the optimizer assumes are independent, skewed data, and a cached plan built for a different parameter value. A wrong estimate at the bottom turns a nested loop into millions of lookups.

6. How do you find which queries to optimize?

Rank by total database time, which is calls times average latency, and by rows examined versus rows returned. Use the slow query log for outliers and statement statistics for aggregate load, with real production parameters.

7. How do you read an EXPLAIN plan?

Read bottom-up: scans at the leaves, joins and sorts above. Check the access method, then compare estimated rows to actual rows at each node. The node where actual time drops sharply marks where the expensive work happens. Buffers tell you whether it is I/O or CPU.

8. What makes a predicate non-sargable?

Anything that prevents the engine from seeking the index on the bare column: a function on the column, a leading-wildcard LIKE, an implicit cast, or arithmetic around the column. Rewriting it as a range comparison on the column usually restores index use.

9. Why is a composite index better than two single-column indexes for some queries?

A composite index is ordered by its leading column and then by the next, so it can satisfy an equality filter and an ordering in one seek, avoiding a sort. Two separate single-column indexes usually require the engine to intersect row sets and still sort.

10. When is a sequential scan the right choice?

When the predicate matches a large fraction of the table, when the table is small, or when the index would require many random row fetches. Reading pages in order is cheaper than scattering across the table, so the optimizer may correctly ignore a usable index.

11. What is an N+1 query and how do you fix it?

One query fetches a list, then one query per item fetches related data. Batch the related fetch with a single IN query or use a join, and confirm with a per-request query count. Connection pool exhaustion is often a symptom.

12. Why is OFFSET pagination slow at depth?

The database must generate and discard every row before the offset, so page 10,000 does far more work than page 1 for the same page size. Keyset pagination filters on the last seen sort key and seeks directly into the index.

13. How do you stop a query from regressing after an upgrade?

Keep a performance test with production-shaped data, capture the plan and rows read for critical queries, and alert on changes. Refresh statistics after bulk loads and review new indexes and schema changes for their effect on existing plans.

14. The query is already optimal but still too slow — what next?

Then add capacity or remove the work from the request path: read replicas, caching with a clear invalidation story, pre-aggregation, or archiving old rows so the hot table stays small. Do this after fixing the plan, not instead of it.

!Traps

  • Adding a read replica or a cache before reading the query plan; both hide a bad access path instead of fixing it.
  • Joining on a column with a mismatched type or collation and wondering why the index is ignored.
  • Wrapping an indexed column in a function inside the WHERE clause.
  • Trusting a plan generated on a tiny staging dataset with different parameter values.
  • Deep OFFSET pagination on a large ordered result.
  • Treating a single slow outlier as the priority while a frequent mediocre query consumes more total time.
  • Adding indexes until writes suffer, without checking which indexes are actually used.
  • Running EXPLAIN ANALYZE on an UPDATE or DELETE in production and actually applying it.
