In one lineA deployment strategy is the plan for moving traffic from the old version to the new one, trading off downtime, blast radius, rollback speed, and extra infrastructure.
Deployment strategy
The procedure that shifts production traffic from the running version to a new version, including how servers are replaced and how failures are contained.
Blast radius
The share of users or requests that a defect can affect before the problem is detected and stopped.
Recreate deployment
Stop every instance of version 1, then start every instance of version 2, accepting a period of unavailability.
Rolling deployment
Replace instances in batches so that most of the fleet keeps serving traffic throughout the rollout.
Blue-green deployment
Run two identical environments and flip the router from the old one to the new one in seconds, keeping the old one as a rollback target.
Canary release
Send a small slice of production traffic to the new version, compare its metrics against the old version, and widen the slice only if it looks healthy.
Shadow deployment
Mirror copies of live requests to the new version while discarding its responses, so users never see the new behavior.
Deploy vs release
Deploying puts code into production; releasing makes a feature visible to users. Feature flags let the two happen at different times.

01Why deployments are risky

Software releases are one of the most common causes of production incidents, because a deployment is the moment untested assumptions meet real traffic.

  • Staging can never fully replicate production: different data volume, different dependency versions, different traffic shapes.
  • A bug that never appeared in tests can surface within seconds once real requests arrive.
  • The system is not frozen during a deploy: connections are open, requests are in flight, caches hold old values, and background jobs are mid-execution.
  • Version 1 and version 2 may disagree about API shapes, database columns, cached payloads, or queue message formats.
  • The goal is not only to ship version 2, but to ship it with a bounded and reversible failure mode.
  • Health checks that only prove a process is running do not prove it can serve real requests.

02The four questions every strategy answers

  • Downtime: will users get errors or a maintenance page while the new version rolls out?
  • Exposure: how many users see version 2 at the same moment, and therefore how large is the blast radius of a bad release?
  • Rollback speed: how long until traffic is back on the last known good version, and does rollback itself cause downtime?
  • Extra infrastructure: how much duplicate capacity must exist during the deployment window?
  • Every strategy is strong on some of these and weak on others; there is no dominant choice.
  • Cost is the fifth, implicit question: paying for a second fleet permanently is different from paying for it for twenty minutes.
Answer these four questions for your service before comparing strategies; the answer usually eliminates most of the options.

03Recreate (big bang)

Recreate is the simplest strategy: stop all instances of version 1, then start all instances of version 2.

  • Implementation is trivial and the mental model is clear, which makes it attractive for small teams.
  • Only one version ever runs, so no backward-compatibility work is needed across API, schema, or cache formats.
  • Between shutdown and readiness the service is fully unavailable, so any user request in that window fails.
  • A defect in version 2 hits every user immediately, because exposure is total.
  • Rollback is another full restart in reverse, so it costs a second outage rather than saving one.
  • It remains reasonable for internal tools, batch jobs, scheduled maintenance windows, and stateful systems where two versions cannot safely coexist.

04Rolling deployments

A rolling deployment updates the fleet in batches instead of replacing it wholesale.

  • Remove a small batch of instances from the load balancer, upgrade them, wait for health checks to pass, then return them to rotation.
  • Repeat batch by batch until every instance runs version 2.
  • Capacity is preserved if the remaining instances can absorb the traffic of the batch being upgraded.
  • Kubernetes uses rolling updates by default for Deployments and exposes two knobs: maxUnavailable and maxSurge.
  • maxUnavailable caps how many instances may be down at once, protecting capacity.
  • maxSurge allows extra instances to be created temporarily, speeding the rollout at the cost of transient capacity.
  • Setting one to a non-zero value while the other is zero gives a strictly safer or strictly faster rollout.
Drain a batch from the load balancer→Upgrade those instances→Pass readiness health checks→Return them to rotation→Repeat for the next batch

05Rolling trade-offs: two live versions and slow rollback

  • Mid-rollout, some servers run version 1 and others run version 2, so both must satisfy the same requests.
  • A single user can hit version 2 on one request and version 1 on the next, which is visible when responses or UI differ.
  • Both versions must tolerate the same database schema, cache entries, and queue message formats.
  • Rollback repeats the batch process in reverse, so it is as slow as the rollout and the bug keeps affecting users meanwhile.
  • Health checks that are too shallow let broken instances return to rotation; checks that are too aggressive stall the rollout.
  • Autoscaling can add instances with the new version mid-rollout, silently changing the mix of versions.

06Blue-green deployments

Blue-green keeps two full environments: blue runs version 1 and serves production traffic, green runs version 2 and waits.

  • Green receives no real user traffic initially, so it can be warmed, migrated, and smoke-tested in isolation.
  • The switch is a router or load balancer change, so it completes in seconds rather than minutes.
  • Blue stays running after the switch, which makes rollback a second router change back to a known good environment.
  • Because traffic moves all at once, every user starts using version 2 at the same instant.
  • The old environment must be kept in a deployable, healthy state; if it is scaled down or reconfigured, rollback is no longer instant.
  • Both environments usually share one database, so data compatibility decides whether rollback is truly possible.
Deploy version 2 to green→Warm caches and run smoke tests→Flip the router to green→Observe→Reuse blue as the next green (or flip back)

07Blue-green trade-offs

  • Cost: two complete production environments must run during the deployment, doubling compute and often doubling idle capacity.
  • Database coupling: if version 2 applies a schema change that version 1 cannot read, switching back to blue does not restore service.
  • All-at-once exposure: a defect that only appears under real traffic affects the whole user base before anyone can react.
  • Shared state such as sessions, caches, search indexes, and object storage must be compatible with both versions.
  • Configuration, secrets, and third-party integrations must exist symmetrically in both environments or the switch fails.
  • Green needs realistic warm-up: an unwarmed cache makes the first seconds after the switch look like an outage.

08Canary releases

A canary release deploys version 2 alongside version 1 and sends it a small share of production traffic before committing.

  • Start with a small slice of traffic and compare error rate, latency, saturation, and business metrics against version 1.
  • If the canary looks healthy, widen the slice in stages until it carries all traffic.
  • If any stage looks unhealthy, send traffic back to version 1 while most users never saw the new code.
  • The technique converts a single risky switch into a sequence of small, observable bets.
  • Old and new versions run side by side for the whole ramp, so backward compatibility is still required.
  • Rollback is fast but incomplete: users already served by the canary keep their state on the new version.
Route a small slice to version 2→Compare metrics per version→Widen the slice→Repeat while healthy→Promote to 100% or revert

09What canary releases require

  • Per-version metrics: dashboards and alerts must be split by version, or the canary is invisible in aggregate numbers.
  • Enough traffic: a service with a handful of requests per minute cannot reach statistical confidence from a small slice.
  • Sticky routing: keep each user on one version, typically by hashing a stable identifier, so behavior does not flip mid-session.
  • Automation: a controller compares canary and baseline metrics at each step and decides to promote or abort.
  • Defined success criteria: decide the acceptable delta for error rate, latency percentiles, and business conversion before the rollout starts.
  • Non-user traffic such as cron jobs, webhooks, and queue consumers also needs a version split, or it silently bypasses the canary.

10Shadow deployments (traffic mirroring)

  • Version 1 serves every user; a copy of each request is also sent to version 2.
  • Version 2 processes the copy but its responses are discarded, so user experience is unchanged.
  • This exposes the new version to real production traffic shapes without any user risk.
  • Latency, error rate, and even response bodies can be diffed between versions before any traffic is switched.
  • It suits rewrites of performance-sensitive paths such as search, ranking, or recommendations.
  • The main hazard is side effects: a mirrored request that charges a card, sends an email, or places an order would execute twice.
Mirror only read paths, or replace outbound writes with stubs and point writes at isolated test storage.

11Feature flags: separating deploy from release

  • The new code ships to production with its feature disabled behind a flag.
  • Users keep the old behavior until the flag is turned on, even though the new code is already running.
  • Enablement can be staged: internal users, then a small percentage of customers, then everyone.
  • Turning a flag off is a configuration change, not a deployment, so it takes effect without a rebuild or rollout.
  • This separates deploy (code in production) from release (feature visible to users).
  • Flags compose with any deployment strategy: ship with rolling, then ramp exposure with the flag.

12Choosing a strategy

  • Start with the downtime budget: if a maintenance window is acceptable, recreate is sufficient.
  • Weigh the cost of a failed release: an internal dashboard tolerates a rolling deploy with good health checks.
  • For critical paths such as checkout or payments, prefer canary for bounded exposure or blue-green for instant rollback.
  • Check monitoring quality first: canary is only as good as the per-version metrics behind it.
  • Check database compatibility: every strategy except recreate runs mixed versions against one schema at some point.
  • Consider effort: recreate and rolling need almost no new infrastructure, blue-green needs a duplicate environment, canary needs traffic splitting and analysis.

13Combining strategies

  • Real teams layer techniques rather than picking exactly one.
  • Rolling ships the code without a second full fleet; canary ramps traffic with metric gates; flags control individual features.
  • Each layer catches a different class of failure: staging catches obvious bugs, canary catches production-only behavior, flags catch product-level risk.
  • Backward-compatible APIs, schema changes, and message formats are the shared prerequisite for every multi-version strategy.
  • Reliable readiness checks and per-version observability are what make any of these strategies safe rather than merely available.
Test in staging→Roll out code in batches→Ramp traffic with a canary→Release features behind flags→Watch metrics and revert the smallest step that failed

↔Trade-offs to say out loud

  • Recreate is the simplest to build and needs no compatibility work, but it costs downtime and exposes every user to a bad release.
  • Rolling avoids downtime and extra infrastructure, but runs two versions side by side and makes rollback as slow as the rollout.
  • Blue-green gives near-instant rollback and a clean cutover, at the price of a duplicate environment and all-at-once exposure.
  • Canary bounds the blast radius and validates with real traffic, but requires traffic volume, per-version metrics, and traffic-splitting machinery.
  • Shadow tests under real traffic with zero user impact, but discards responses and requires careful side-effect isolation.
  • Feature flags decouple release from deploy and make shutdown instant, but add configuration surface, stale-flag debt, and a new dependency at request time.
  • Automation makes rollouts repeatable and fast, but an automated controller with bad health signals can promote a broken version confidently.
  • Fast rollback shrinks outage duration but encourages riskier shipping if teams stop investing in pre-production testing.

?Interview questions

Answer aloud before opening the outline.

1. What is a deployment strategy, and why does it matter?

It is the plan for moving production traffic from the old version to the new one: which servers are replaced, in what order, and how traffic is shifted. It matters because releases are a leading cause of incidents, and the strategy decides how much of the user base is exposed and how quickly you can recover.

2. Why is a staging environment not enough?

Staging cannot reproduce production's real traffic volume, real data distribution, dependency versions, and live in-flight state. Bugs that depend on scale, data shape, or concurrent load only appear once real requests arrive, which is why production-side containment strategies exist.

3. Explain recreate and when you would still use it.

Recreate stops all version 1 instances and then starts version 2, accepting downtime. It is appropriate for internal tools, batch jobs, planned maintenance windows, and stateful systems where two versions cannot safely share storage. The benefit is that only one version ever runs, so compatibility work disappears.

4. How does a rolling deployment work?

Instances are upgraded in batches: a batch is drained from the load balancer, upgraded, health-checked, and returned to rotation before the next batch starts. Capacity is preserved as long as the remaining instances can carry the traffic of the batch being upgraded. maxUnavailable and maxSurge control the safety and speed of that process.

5. What is the biggest risk in a rolling deployment?

Two versions serving traffic simultaneously. A user can hit version 2 and then version 1, and both versions share the same database, caches, and queues, so every contract between them must remain compatible. The second risk is slow rollback, since reverting means rolling the fleet again.

6. What do maxUnavailable and maxSurge control?

maxUnavailable bounds how many instances may be unavailable at once, protecting serving capacity. maxSurge allows temporary extra instances so the rollout can proceed without reducing capacity. Together they trade rollout speed against cost and capacity headroom.

7. How does blue-green achieve fast rollback?

Two identical environments exist, with the old version still running in the idle one. Traffic cutover is a router change measured in seconds, and reverting is the same change in reverse. This only works if the old environment is kept healthy and the shared database remains readable by both versions.

8. Why can blue-green rollback still fail?

Because both environments usually share one database. If version 2 applied a destructive or incompatible schema change, routing traffic back to version 1 does not help — the old code now reads a schema it cannot handle. Rollback is only as reliable as the data layer's backward compatibility.

9. What makes a canary release trustworthy?

Per-version metrics, enough traffic for the sample to be meaningful, stable user-to-version routing, and predefined thresholds for error rate, latency, and business metrics. Without these, a canary produces noise rather than a decision, and promotion becomes a guess.

10. Why is sticky routing important for canaries?

If a user alternates between versions on consecutive requests, they can see inconsistent UI or API behavior mid-session, which pollutes both the user experience and the metrics. Hashing a stable identifier such as user ID keeps each session on one version while still splitting the population.

11. What is the main danger of shadow deployments?

Duplicated side effects. A mirrored request that writes to the database, charges a payment, or sends an email executes twice if the shadow version performs real writes. Shadow traffic is therefore safe mainly for read-only paths, or with outbound writes stubbed and writes redirected to isolated storage.

12. How do feature flags relate to deployment strategies?

They are orthogonal. A deployment strategy controls how code is distributed across servers; a feature flag controls whether users can reach the feature. You can ship with a rolling deploy and then ramp the feature on with a flag, which makes disabling a problem a configuration change instead of a redeploy.

!Traps

  • Assuming a passing health check means the new version can serve real requests, when it only proves the process started.
  • Running mixed versions without making APIs, schemas, cache values, and queue messages backward compatible.
  • Choosing canary for a low-traffic service where the sample size can never support a decision.
  • Switching blue-green traffic without warming the green environment, then treating the cold-cache spike as a code defect.
  • Letting the old blue environment drift or scale down, so rollback is no longer a fast router flip.
  • Mirroring write traffic in a shadow deployment and doubling payments, emails, or orders.
  • Treating a deployment strategy as a substitute for monitoring; every strategy depends on per-version signals to be safe.
