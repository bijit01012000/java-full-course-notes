01The problem: near-duplicate content

A search engine crawls billions of pages, and a large fraction of them are almost the same as each other.

  • The same news article appears on many sites with only the header and footer changed.
  • One product page is reachable through several URLs with different tracking parameters.
  • A blog post is copied with a few words altered or a paragraph removed.
  • Showing all of these in results wastes crawl budget and crowds out distinct content.
  • The system needs to group pages whose content is very similar, not just identical.
  • Doing it pairwise over the whole corpus is computationally impossible, so the comparison must be restructured.

02Why exact hashing does not help

  • Exact duplicate detection is easy: hash each page and group by equal hashes.
  • A cryptographic or content hash changes completely when a single character changes, which is the property that makes it good for integrity.
  • That same avalanche effect destroys any notion of degree: two pages that are 95% identical produce unrelated hashes.
  • So hashing answers equality, while the problem is similarity.
  • What is needed is a summary that changes gradually as content changes, and a way to compare summaries cheaply.
  • MinHash provides the summary; locality-sensitive hashing provides the cheap comparison.

03Jaccard similarity

  • Similarity must be defined before it can be estimated, and Jaccard is the standard choice for sets.
  • It is the size of the intersection divided by the size of the union.
  • Identical sets score 1; disjoint sets score 0; everything else falls in between.
  • For sets of four items sharing three, the union has five items, so the similarity is 3/5 = 0.6.
  • The measure ignores order, repetition, and magnitude — only membership matters.
  • That makes it robust to insertions and deletions of single elements but blind to structure.
  • Choosing a different similarity measure means choosing a different sketch, so the decision comes first.

04Turning documents into shingles

  • Documents are sequences of words, not sets, so they must first be converted into sets.
  • A shingle is a short run of consecutive words or characters, taken as one element.
  • With three-word shingles, a five-word sentence yields three overlapping shingles.
  • Overlapping shingles preserve some word order, so documents that share phrases share shingles.
  • A single changed word affects only the shingles that span it; the rest are untouched, so similarity stays high.
  • Shingle length is a real decision: too short and unrelated documents collide, too long and minor edits drop similarity.
  • Character shingles help for short texts and for languages without easy word boundaries; word shingles are the common default.

05Two problems at scale

  • The first problem is set size: a long article contains many shingles, so comparing two sets directly is expensive.
  • The second problem is pair count: with a billion pages there are on the order of 5×10^17 pairs.
  • Even a microsecond per comparison would take longer than the age of the system.
  • These are separate problems and need separate solutions, which is the key structural insight.
  • MinHash makes each individual comparison cheap by shrinking the set to a fixed signature.
  • LSH avoids most comparisons by bucketing signatures so only plausible pairs are examined.
  • Neither alone is sufficient: a cheap comparison still leaves too many pairs, and bucketing alone still needs a compact key.

06What MinHash is

  • Choose k independent random hash functions that map elements to numbers.
  • For each function, compute the minimum value over all elements of the set.
  • Those k minima form the signature, a fixed-size vector regardless of set size.
  • Two sets are compared by the fraction of positions where their signatures agree.
  • That fraction estimates their Jaccard similarity.
  • The signature is computed in one pass per set and needs no pairwise work.
  • The estimate is statistical, so more hash functions mean less variance, not exactness.
Shingle the document→Hash every shingle k ways→Keep the minimum per hash→Store the k-length signature→Compare signatures position by position

07Why it works

  • Consider the union of two sets and the single element with the smallest hash value under one function.
  • That element is equally likely to be any member of the union, because the hash is random.
  • The two sets produce the same minimum exactly when that element belongs to the intersection.
  • The probability of that is the intersection size divided by the union size — Jaccard similarity.
  • So each hash function is a Bernoulli trial whose success probability is the similarity.
  • Averaging k trials gives an unbiased estimate with variance shrinking as k grows.
  • This is why the estimate is principled rather than a heuristic: the collision probability equals the quantity being measured.

08Signature size and accuracy

  • Estimator variance is proportional to 1/k, so error falls with the square root of the signature length.
  • The standard guidance is that k scales with 1/ε^2 for a target error ε.
  • A signature of a few hundred values already compares thousands of shingles in a fixed budget.
  • Signature length also controls storage: every document stores k values.
  • Each value is a hash, typically stored as a fixed-width integer, so memory is predictable.
  • Very short signatures are noisy enough to reorder near-duplicate candidates.
  • The same k and the same hash functions must be used across the corpus, or signatures are incomparable.

09Locality-sensitive hashing with bands

  • Split each signature into b bands of r consecutive rows, so b * r = k.
  • Hash each band into a bucket table, and treat any two documents sharing a bucket as a candidate pair.
  • A pair becomes a candidate if they agree on all rows of at least one band.
  • The probability of that is 1 - (1 - s^r)^b for similarity s.
  • This is an S-curve: low-similarity pairs are almost never candidates, high-similarity pairs almost always are.
  • Only candidate pairs get a full signature or document comparison.
  • Banding converts an all-pairs problem into a small number of hash lookups per document.

10Tuning the banding scheme

  • The steep part of the S-curve sits near (1/b)^(1/r), which is the effective similarity threshold.
  • Decide the threshold from the product: what counts as a near-duplicate for this corpus.
  • Then choose r to place the curve and b to make it steep enough.
  • More bands increase recall but generate more candidates and more comparison work.
  • Fewer bands reduce work but silently miss duplicate pairs, which is usually the worse failure for deduplication.
  • Always measure precision and recall on a labeled sample; the formula assumes independent hash functions.
  • Duplicates in a bucket must be deduplicated before comparison, or the same pair is evaluated many times.

11Variants and implementation notes

  • One-permutation hashing derives many signature values from a single permutation, cutting hashing cost at a small accuracy cost.
  • b-bit MinHash stores only a few low bits per value, which can greatly shrink the index with modest error.
  • Densification reuses hash values across bands to reduce computation.
  • MinHash can be computed in a streaming pass over documents, which suits large crawls.
  • Signature computation parallelizes per document; banding and candidate generation parallelize per bucket.
  • Hash functions must be independent and stable across runs, or signatures change between rebuilds.
  • Store signatures in a columnar or key-value layout so band lookups are cheap.

12Uses and limits

  • Web crawl deduplication and search-result diversity.
  • Plagiarism and copy detection across documents or code.
  • News and feed deduplication where the same story appears with different framing.
  • Recommender systems that measure set overlap between users, items, or tags.
  • Clustering and near-duplicate joins in analytics pipelines.
  • Limits: it estimates Jaccard over sets, so it is blind to order beyond what shingles capture, and it is sensitive to shingle length.
  • It gives candidate pairs, not final answers; the candidates still need an exact or more expensive check.

↔Trade-offs to say out loud

  • Longer signatures reduce estimation error but increase compute and storage per document.
  • Shorter signatures save space but blur the ranking of near-duplicate candidates.
  • More bands raise recall but generate more candidate pairs to verify.
  • Fewer bands cut comparison work but miss true duplicates below the threshold.
  • Smaller shingles catch paraphrases and edits but create accidental similarity between unrelated texts.
  • Larger shingles reduce false matches but make real edits look less similar.
  • Jaccard on sets is cheap and order-insensitive but cannot express positional or semantic similarity.
  • Candidate generation makes the problem tractable but introduces false positives and false negatives before any exact check.

?Interview questions

Answer aloud before opening the outline.

1. Why doesn't a normal hash find near-duplicate pages?

A content hash changes completely when a single byte changes, which is exactly what integrity checking wants. Two pages that are 95% identical therefore produce unrelated digests. MinHash instead produces a summary whose agreement rate reflects how much the sets overlap.

2. What is Jaccard similarity?

It is the size of the intersection divided by the size of the union of two sets. Identical sets score 1 and disjoint sets score 0. It measures membership overlap and ignores order and repetition, which is why documents must first be turned into sets of shingles.

3. Why shingle a document instead of using its words?

Word sets discard order, so "dog bites man" and "man bites dog" look identical. Overlapping shingles retain local word order, so shared phrases produce shared elements. They also localize edits: changing one word affects only the shingles that span it.

4. How does MinHash compress a set?

It applies k random hash functions to every element and keeps the minimum value each function produces. The resulting k values are the signature, whose size is independent of the set size. Similarity is estimated by the fraction of positions where two signatures agree.

5. Why does signature agreement estimate Jaccard similarity?

Under a random hash, the smallest hash in the union is equally likely to come from any element of the union. Two sets share that minimum exactly when the element is in their intersection, which happens with probability equal to Jaccard similarity. Averaging over many hash functions concentrates the estimate.

6. What are the two scaling problems MinHash addresses?

Large sets make each comparison expensive, and a huge corpus makes the number of pairs astronomical. MinHash fixes the first by replacing a set with a fixed-length signature. LSH fixes the second by bucketing signatures so only likely pairs are compared.

7. How does banding work?

Split the signature into b bands of r rows and hash each band into a bucket table. Two documents become candidates if they land in the same bucket for at least one band, meaning they agree on all rows of that band. The candidate probability is 1 - (1 - s^r)^b.

8. How do you choose the number of bands and rows?

Pick the similarity threshold that should count as a duplicate, then choose r so the S-curve's steep region sits there and b so it is steep enough. More bands raise recall and cost, fewer bands raise precision and risk missing duplicates. Validate with a labeled sample.

9. Does MinHash give exact similarity?

No, it estimates it. The estimate is unbiased, and its variance falls as the signature grows, so longer signatures are more accurate. Two runs with different hash functions can produce slightly different scores for the same pair.

10. What are the failure modes in production?

Banding can miss true duplicates below the threshold, and popularity effects can cluster unrelated documents in shared buckets. Wrong shingle length either creates false similarity or hides real edits. Stale signatures after content changes are the other common source of wrong results.

11. How would you deduplicate a web crawl end to end?

Normalize and shingle each page, compute a MinHash signature, and index the bands to generate candidate pairs. Verify candidates with a full Jaccard computation or a stronger check, then cluster and keep one representative per cluster. Tune the banding threshold against a labeled duplicate set.

12. MinHash or a similarity search index over embeddings?

MinHash measures set overlap, is cheap, interpretable, and strong for near-verbatim text. Embeddings capture paraphrase and semantics but cost more to compute and need an approximate nearest-neighbor index. Many pipelines use MinHash for exact-ish duplicate removal and embeddings for topical similarity.

!Traps

  • Forgetting that similarity is measured on shingles, so shingle length silently defines what counts as a duplicate.
  • Using different hash functions or signature lengths across the corpus, making signatures incomparable.
  • Tuning bands for precision only, then wondering why real duplicates survive deduplication.
  • Treating candidate pairs as final duplicates without an exact verification step.
  • Comparing signatures position by position when the positions came from different hash seeds.
  • Choosing Jaccard when the product actually needs order-sensitive or semantic similarity.
