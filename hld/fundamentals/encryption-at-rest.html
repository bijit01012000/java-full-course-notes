In one lineEncryption at rest assumes the storage itself will be stolen — a discarded disk, a public backup bucket, a shared snapshot — and makes the bytes useless without a key that lives somewhere else.
Encryption at rest
Encrypting data while it is stored — on disk, in a database, in object storage, or in a backup — so raw files are unreadable without the key.
Data encryption key (DEK)
The symmetric key that actually encrypts a record, file, or volume; it is itself protected by a key-encryption key.
Key encryption key (KEK)
A longer-lived key, held in a KMS or HSM, used to wrap and unwrap data encryption keys rather than to encrypt data directly.
Envelope encryption
Encrypting the data with a DEK and then encrypting or wrapping that DEK with a KEK, so the DEK can be rotated cheaply.
KMS
A key management service that generates, stores, authorizes access to, rotates, and audits the use of cryptographic keys.
Transparent data encryption (TDE)
Database-level encryption of files and pages that is invisible to queries, so the engine decrypts on read and encrypts on write.
Field-level encryption
Encrypting specific columns or attributes in the application before storage, giving the finest granularity and the strongest isolation from the database operator.
Key rotation
Replacing a key with a new version, ideally without rewriting all data by rewrapping the DEK instead.
Crypto-shredding
Destroying the key so the encrypted data becomes permanently unrecoverable, which is faster and more reliable than deleting every copy.
HSM
A hardware security module that stores keys and performs cryptographic operations in tamper-resistant hardware, so keys never leave it in the clear.

01The threat: reading the storage instead of the database

Access controls, network rules, and database passwords only apply when an attacker goes through the database. Many incidents never touch it.

  • A disk or drive is decommissioned or resold without being properly wiped.
  • A backup file is written to a storage bucket that was accidentally made public.
  • A database snapshot is shared with the wrong account or copied to a test environment.
  • A storage volume is detached and attached to an attacker-controlled instance.
  • An insider or a compromised service account reads object storage directly, bypassing the query layer.
  • In all of these cases the attacker reads raw bytes, so plaintext storage means every record is exposed.
  • Encryption at rest is the control that makes those bytes worthless without the key.

02What encryption at rest means

  • Data is transformed with a cipher and a key before it is written to persistent storage, and decrypted only when legitimately read.
  • It complements encryption in transit: transit protects data moving between systems, at rest protects data sitting in storage.
  • The ciphertext is only as safe as the key; if the key is stored next to the data, the encryption is mostly theater.
  • It applies to more than the primary database: backups, snapshots, replicas, caches, message queues, log stores, and analytics copies.
  • Modern cloud storage and managed databases often enable it by default, which makes is it on a weak question and who can use the key the real one.
  • The design question is not whether to encrypt but at which layer, under whose key control, and with what granularity.

03What it protects against — and what it does not

  • Protects: stolen or improperly disposed media, leaked backups, misconfigured public storage, and snapshot sharing.
  • Protects: the storage provider or an operator with physical access but no key access.
  • Does not protect: a compromised application that legitimately decrypts data before returning it.
  • Does not protect: SQL injection, authorization bugs, or an attacker with valid credentials — the data is decrypted for them.
  • Does not protect: metadata such as row counts, access patterns, and file sizes, which can still leak information.
  • It reduces the blast radius of storage exposure; it is not a substitute for authentication, authorization, and input validation.
  • Treat it as one layer in defense in depth, specifically the layer that covers the disk walked away.

04The layers where encryption can be applied

  • Disk or volume: full-disk encryption at the block layer; protects against physical theft, transparent to everything above.
  • Database or filesystem (TDE): the engine encrypts pages and files; queries are unchanged, but anyone with database credentials sees plaintext.
  • Object storage: server-side encryption where the provider holds the key, holds a key you supply per request, or uses a key from your KMS.
  • Application-level: the service encrypts specific fields before writing; the database only ever stores ciphertext.
  • Client-side: the end user's device encrypts before upload; the server cannot read the data at all.
  • Higher layers give finer granularity and stronger separation from the storage operator, but lose query capability and require key handling in code.
  • Many systems combine layers: volume encryption for everything, plus field-level encryption for the most sensitive attributes.

05Key hierarchy and envelope encryption

Encrypting data directly with a long-lived master key is inflexible: rotating it means rewriting everything. Envelope encryption decouples the two.

  • Generate a DEK per object, per tenant, or per time period, and encrypt the data with it.
  • Store the encrypted data alongside the wrapped DEK — the DEK encrypted under a KEK held in a KMS or HSM.
  • On read, ask the KMS to unwrap the DEK, decrypt the data, and discard the plaintext key from memory.
  • Rotation of the KEK only requires rewrapping DEKs, not re-encrypting the data.
  • The KEK is protected by a root key in hardware, so the plaintext KEK never exists in application memory.
  • Per-tenant or per-object DEKs limit blast radius: one leaked key exposes one tenant's data, not the whole store.
  • Envelope encryption also makes crypto-shredding practical: delete the wrapped DEK and that data is gone.
Request data key for a new object→KMS generates DEK and returns plaintext plus wrapped form→Application encrypts data with the plaintext DEK→Store ciphertext and wrapped DEK together→On read, send wrapped DEK to KMS for unwrapping→Decrypt, use, and clear the plaintext DEK from memory

06Key management is the hard part

  • Key generation must use a cryptographically secure source; weak randomness breaks the cipher regardless of algorithm.
  • Keys need a home with access control, audit logging, and no plaintext copies in config files, environment dumps, or code.
  • Separate duties: the team that can read data should not automatically be able to export or delete keys.
  • Grant keys per service and per environment; a staging key must not decrypt production data.
  • Log every key use — who, when, which key, which operation — because key access is the real access log.
  • Plan for key loss: a lost key means permanently lost data, so backup and recovery of keys is itself a critical process.
  • Prefer managed KMS or HSM-backed keys over custom crypto; rolling your own key management is where most failures happen.

07Rotation

  • Rotate on a schedule and on events: staff departure, suspected exposure, vendor change, or compliance requirement.
  • With envelope encryption, rotate the KEK by rewrapping DEKs; data is untouched and the operation is cheap.
  • Rotating a DEK requires re-encrypting the data it protects, which is expensive and must be done in the background.
  • Keep old key versions available for decryption during the transition, and track which objects still use which version.
  • Never delete a retired key until every object encrypted under it has been re-encrypted or intentionally shredded.
  • Automate rotation, because manual rotation is skipped under pressure and leaves keys in service for years.
  • Test the rotation procedure; a rotation that breaks decryption is an outage with no rollback.

08The cost: what encryption breaks

  • Encrypted columns cannot be indexed normally, so equality, range, and sort queries on them become impossible or expensive.
  • Deterministic encryption allows equality search but leaks frequency patterns, since equal plaintexts produce equal ciphertexts.
  • Randomized encryption is safer but prevents server-side search entirely; filtering must happen in the application.
  • Joins, aggregations, and unique constraints on encrypted fields usually have to move to a blind index or a tokenized surrogate.
  • LIKE queries, fuzzy search, and full-text search over encrypted data are effectively unavailable without specialized schemes.
  • Application-level encryption complicates key access in batch jobs, analytics pipelines, and reporting tools.
  • The honest trade-off is often: encrypt the fewest fields that satisfy the threat model, and keep the rest under storage-level encryption.

09Backups, snapshots, and derived copies

  • Backups are the most commonly exposed copy of the data, because they are copied widely and protected less carefully.
  • Encrypt backups with a separate key from production, so a leaked production key does not open the archives.
  • Snapshots inherit encryption only if the key is available to whoever restores them; check cross-account and cross-region sharing.
  • Analytics warehouses, search indexes, and log stores hold copies of the same records and need the same treatment.
  • Test restores: an encrypted backup with an unavailable key is not a backup.
  • Expire backups on a schedule, because old encrypted copies still widen the exposure surface.

10Crypto-shredding and deletion

  • Deleting rows from a live database rarely removes them from replicas, backups, and caches immediately.
  • If each record or tenant has its own DEK, deleting the wrapped key makes all copies permanently unreadable.
  • This gives a verifiable deletion story that satisfies erasure requirements without hunting every replica.
  • Crypto-shredding requires per-tenant or per-record key granularity; a single global key cannot be destroyed without losing everything.
  • Key deletion must be irreversible and audited, with a delay window to prevent accidental destruction.
  • It does not remove metadata or access logs, which may still be subject to retention rules.

11Operational failure modes

  • KMS unavailability becomes a full outage: no key, no decryption, no reads.
  • KMS throttling under high request rates turns every read into a queued dependency; cache unwrapped DEKs briefly and safely.
  • A key policy change that revokes a service's access breaks that service instantly, often discovered in production.
  • Region or account isolation fails when the key lives in one region and the data is replicated to another.
  • Accidental key deletion is catastrophic and usually irreversible; require approval and a waiting period.
  • Per-object DEKs create millions of key operations and a metadata burden that must be planned for.
  • Debugging gets harder: support staff cannot read ciphertext, so tooling must decrypt through the application or not at all.
Encryption adds a hard dependency on the key service. Its availability, latency, and authorization model belong in the system's SLOs, not in a footnote.

12Choosing a design

  • Start from the threat model: who are you protecting against — a thief, a cloud operator, an insider, or a compromised app?
  • For physical theft and lost media, storage-level or TDE is sufficient and operationally simple.
  • For regulatory separation from the storage operator, use provider keys you control through your own KMS.
  • For the most sensitive fields, encrypt in the application and accept that they become unsearchable.
  • Always pair at-rest encryption with encryption in transit, least-privilege access, and audit logging.
  • Document which key protects which data and how it rotates, because undocumented key topology is unmaintainable.
  • Verify with a real test: can someone with only storage access read a record? If yes, the design has a gap.

↔Trade-offs to say out loud

  • Volume or disk encryption is transparent and cheap but protects only against physical theft, not credential compromise.
  • Database TDE needs no application change but leaves plaintext visible to anyone with database access.
  • Application field-level encryption strongly isolates sensitive data but breaks indexing, sorting, and range queries.
  • Deterministic encryption permits equality search but leaks patterns through repeated ciphertexts.
  • Per-object data keys limit blast radius and enable crypto-shredding but multiply key operations and metadata.
  • Frequent rotation limits key exposure but adds rewrap or re-encryption work and versioning complexity.
  • HSM-backed keys keep key material out of software but add cost, latency, and operational constraints.
  • Client-side encryption gives the strongest trust boundary but prevents the server from processing the data.

?Interview questions

Answer aloud before opening the outline.

1. What is encryption at rest?

It is encrypting stored data so the raw bytes are unreadable without the correct key, covering disks, databases, object storage, and backups. It addresses threats where an attacker obtains the storage rather than going through the application. It is distinct from encryption in transit, which protects data on the network.

2. What does encryption at rest not protect against?

It does not stop an attacker who compromises the application or presents valid credentials, because the data is decrypted for them. It does not prevent SQL injection, authorization bugs, or insider misuse through legitimate interfaces. It also cannot hide access patterns, row counts, or file sizes.

3. Why does storing the key next to the data defeat the purpose?

Because whoever obtains the storage usually obtains everything on it, including the key file or configuration. The key must live in a separate trust domain with its own access control and audit trail, such as a KMS or HSM. Otherwise the attacker decrypts the data as easily as you do.

4. Explain envelope encryption.

Data is encrypted with a data encryption key, and that DEK is encrypted or wrapped by a key encryption key held in a KMS. The ciphertext stores the wrapped DEK alongside the data. On read, the KMS unwraps the DEK and the application decrypts, which lets you rotate the KEK by rewrapping keys instead of rewriting data.

5. What are the layers where you can apply encryption at rest?

Disk or volume level, database or filesystem level such as TDE, object storage server-side encryption, application-level field encryption, and client-side encryption before upload. Each layer changes who can read plaintext and what queries remain possible. Systems often combine storage-level encryption with field-level encryption for the most sensitive attributes.

6. Why is field-level encryption usually the strongest option?

Because the database only ever stores ciphertext, so database credentials, backups, and snapshots do not expose those values. Only the application, which has key access, can decrypt them. The cost is that encrypted fields cannot be indexed or filtered normally, so it is reserved for the data that justifies that loss.

7. What is the trade-off with deterministic encryption?

It lets you perform equality searches and joins because the same plaintext always produces the same ciphertext. That also leaks frequency information and allows an attacker to group identical values. It is a reasonable compromise for lookup fields when the leak is acceptable, and a poor choice for low-entropy or highly sensitive values.

8. How does key rotation work without downtime?

With envelope encryption, the new KEK wraps DEKs while old versions remain available for decryption, so data is untouched. Rewrapping happens in the background and is tracked per object. A DEK rotation that requires re-encrypting data must run as a dual-read migration, accepting both old and new keys until every record is converted.

9. How do backups change the design?

Backups are copied widely and often protected less carefully, so they need their own encryption keys and access policy. Using a separate backup key means a production key leak does not expose the archive. Restoration must be tested, because an encrypted backup whose key is unavailable is worthless.

10. What is crypto-shredding?

Deleting the key that protects a set of data so all copies become permanently unreadable. This is faster and more reliable than chasing every replica, snapshot, and backup when a record must be erased. It requires per-record or per-tenant keys, and the key deletion must be irreversible and audited.

11. What operational risks does encryption introduce?

The key service becomes a hard dependency: if it is unavailable or throttling, reads fail or slow down. Key policy mistakes can lock a service out of its own data, and accidental key deletion is catastrophic. Replication across regions and accounts must carry key access with it, or restores will not decrypt.

12. How would you decide which encryption layer to use?

Start from the threat model. If the risk is stolen media, storage-level encryption is enough. If it is the storage operator or a leaked backup, use keys you control in your own KMS. If it is insiders or database credential compromise, encrypt those fields in the application and accept the query limitations.

!Traps

  • Enabling storage encryption but storing the key in the same bucket or repository as the data.
  • Claiming compliance from TDE alone while anyone with database credentials can read every row in plaintext.
  • Encrypting a column that the product needs to filter, sort, or join on, then discovering the feature cannot be built.
  • Forgetting replicas, snapshots, analytics copies, and search indexes, which all hold the same plaintext.
  • Deleting a rotated key before all data encrypted under it has been migrated.
  • Adding a KMS call to every read without caching or capacity planning, turning encryption into a latency and availability bottleneck.
  • Assuming encryption at rest protects against application compromise or authorization bugs.
