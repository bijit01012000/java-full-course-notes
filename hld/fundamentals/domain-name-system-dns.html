In one lineDNS is the internet's hierarchical, heavily cached naming system: it turns a domain name into the records a client needs, and its TTLs decide how quickly a change can reach everyone.
DNS
Domain Name System: a distributed hierarchy of name servers that maps names to records such as IP addresses.
Recursive resolver
The server that does the walking for the client: it queries root, TLD, and authoritative servers and returns one final answer.
Authoritative name server
The server that holds the real records for a zone and answers from its own configuration rather than from cache.
Delegation
A parent zone handing responsibility for a child zone to a specific set of name servers via NS records.
Zone
The portion of the namespace a single authority manages, for example example.com or api.example.com.
TTL
Time To Live: the number of seconds a resolver may reuse a cached record before it must fetch a fresh copy.
A / AAAA record
The records that map a name to an IPv4 address (A) or an IPv6 address (AAAA).
CNAME record
An alias that points one name at another name, so the target's records are followed instead of storing an address.
Negative caching
Caching the fact that a name or record type does not exist, so repeated failures do not re-query the authority.
Anycast
Announcing the same resolver or root address from many locations so queries land at a nearby instance.

01What DNS does

Every connection begins with a lookup: the client has a name, but the network needs an address.

  • DNS translates a human-readable name such as api.example.com into the records a client needs, usually an IPv4 or IPv6 address.
  • It is a distributed directory, not one central database: each zone is served by its own authoritative name servers.
  • The name is a stable indirection layer; the address behind it can change without any client changing configuration.
  • That indirection is what makes blue-green deploys, regional failover, and CDN steering possible.
  • DNS answers are cached, so what a client sees can lag the authoritative record by up to one TTL.
  • DNS serves more than web traffic: mail routing (MX), service location (SRV), and ownership or policy metadata (TXT) all live here.

02The DNS hierarchy

DNS is organized as a tree of delegations, and each level only needs to know where the next level lives.

  • The root sits at the top and refers queries for a TLD to that TLD's servers.
  • Below it are the top-level domains such as .com, .org, and .io.
  • Below the TLD is the registered domain, such as example.com.
  • Below that are subdomains such as api.example.com or blog.example.com.
  • Each level is responsible only for pointing at the next level, which is why no single server holds every record.
  • Root servers do not know the address of every website; they know which servers are authoritative for each TLD.
  • The .com servers do not know your address either; they know which name servers are authoritative for your domain.
  • Only the authoritative name servers for a zone hold its actual records.
LevelExampleResponsibility

This hierarchy is why DNS can scale to billions of names without a central database: work is delegated and repeated lookups are cached.

03How DNS resolution works

A cold lookup walks the tree from the client's caches down to the authoritative server and back.

  • The browser cache is checked first, keyed by hostname.
  • On a miss, the operating system checks its own cache and the local hosts file.
  • On another miss, the query goes to a recursive resolver, usually the ISP's or a public resolver.
  • The resolver asks a root server, which returns a referral to the relevant TLD servers.
  • The resolver asks the TLD server, which returns a referral to the domain's authoritative name servers.
  • The resolver asks the authoritative server, which returns the actual record with its TTL.
  • The answer is cached at each layer on the way back, so the next lookup is usually a cache hit.
  • Only after the address is known does the client open a TCP or QUIC connection to the server.
Browser cache lookup→OS cache / hosts file lookup→Recursive resolver cache lookup→Root server: referral to the TLD→TLD server: referral to the authoritative name servers→Authoritative server: the actual record plus TTL→Answer cached and returned to the client→Client connects to the resolved address
A lookup is on the critical path of the first request. Every missed cache layer adds a network round trip before any application data moves.

04Recursive vs iterative queries

The two query styles split the work differently: one asks for the final answer, the other asks for the next lead.

  • Recursive means "find the final answer for me"; the server must resolve or return an error.
  • Iterative means "tell me what you know, or point me at the next server to ask".
  • The client sends a recursive query to its resolver; it does not want to contact root, TLD, and authoritative servers itself.
  • The resolver performs iterative queries, walking root, TLD, and authoritative servers in turn.
  • The resolver then returns the single final answer to the client, hiding the walk.
  • Recursive resolvers therefore carry the caching and the query volume, which is why they are the main scaling point of DNS.

RecursiveClient to recursive resolver"Find the final answer for me."
IterativeResolver to root, TLD, and authoritative servers"Tell me what you know, or point me to the next server."

05DNS caching

Without caching, every request would repeat the full walk through root, TLD, and authoritative servers.

  • Caching happens at several layers: the browser, the operating system, and the recursive resolver.
  • A resolver cache is shared by many users, so one lookup can serve a large population.
  • A hundred clients behind the same resolver can collapse into one query to the authoritative server.
  • Caching makes lookups fast and keeps traffic off authoritative servers, which is what lets them stay small.
  • Each record carries a TTL; the cache may reuse it only until that timer expires.
  • When the entry expires, the next lookup fetches a fresh copy, so the cache is never authoritative.
  • Cached data is invisible to the operator: you cannot purge a public resolver's cache, only wait it out.
Cache expiry is the reason "DNS propagation" is mostly a waiting game rather than an active push.

06TTL trade-offs

TTL is the single knob that trades caching efficiency against how fast a change takes effect.

  • A long TTL raises hit rates, cuts DNS traffic, and usually makes lookups faster.
  • A short TTL makes changes visible sooner, which helps failover and traffic shifting.
  • Short TTLs mean more queries reach authoritative servers and more chances for a lookup to fail.
  • Long TTLs mean a bad or stale record can keep serving traffic long after you fixed it.
  • Values in the range of tens of seconds to a few minutes are used for records that may need to move quickly.
  • Values of an hour or more are used for stable records where lookup cost matters more than flexibility.
TTL rangeBehaviorTrade-off
30-60 secondsChanges take effect quicklyMany more lookups reach DNS servers
300-600 secondsA common default for many servicesChanges take a few minutes to appear
3600+ secondsHigh cache hit rate, low DNS trafficOld answers can linger for hours
Pick TTL per record: stable infrastructure can be cached for a long time; a record used for failover should be short well before you need to fail over.

07Common DNS record types

  • A maps a name to an IPv4 address; AAAA does the same for IPv6.
  • CNAME maps a name to another name, so the target's records are used and follow its changes.
  • NS names the authoritative name servers for a zone and is the mechanism behind delegation.
  • MX names the mail servers that receive email for the domain, with a preference value.
  • TXT stores arbitrary text, widely used for domain verification, SPF, and policy metadata.
  • SOA describes the zone itself: its primary server, contact, and the timers used for negative caching.
  • Each record type has its own TTL, so you can keep addresses short-lived while leaving mail records stable.

CNAME rules that bite

  • A CNAME cannot coexist with other records at the same name, because the name must resolve to exactly one target.
  • The zone apex normally holds NS and SOA records, so it usually cannot be a CNAME; use a provider-specific alias or flattening feature.
  • Aliasing many hostnames to one target means one address change updates all of them at once.
  • Long CNAME chains add lookups and make failures harder to trace; keep them one hop where possible.

08DNS propagation and record changes

When you change a record, the new value does not appear everywhere at once.

  • What people call propagation is mostly cache expiration; nothing pushes the new value to resolvers.
  • Resolvers with no cached copy see the new value immediately.
  • Resolvers still holding the old record keep answering with it until that record's TTL runs out.
  • For a period, different users legitimately receive different answers for the same name.
  • Before a planned migration, lower the TTL first, wait for the old longer TTL to expire, then change the record.
  • Waiting matters: lowering the TTL only affects new cache entries, not copies already stored with the old TTL.
  • After the change stabilizes, raise the TTL again so normal traffic is cheap to serve.
Resolver stateAnswer right after the change
No cached entryNew value
Cached old value, TTL still runningOld value
Cached old value, TTL expiredNew value after a fresh lookup
Lower the TTL well before the change→Wait at least the previous TTL→Change the record→Monitor queries until old answers disappear→Raise the TTL back to normal

09Transport, response size, and encryption

  • DNS conventionally uses UDP port 53, because a small query and answer fit in one datagram with no handshake.
  • It falls back to TCP port 53 when an answer is too large or when the client sets the truncated flag.
  • TCP is also required for zone transfers between primary and secondary name servers.
  • EDNS(0) advertises a larger UDP buffer so large answers do not immediately force a TCP retry.
  • DNS over TLS and DNS over HTTPS encrypt the lookup path and hide it from the local network.
  • DNS over QUIC applies the same idea over UDP with stream multiplexing.
  • Encrypted DNS protects the query in transit but does not change caching, delegation, or TTL behavior.
Anycast lets many physical resolver instances share one address, so a query is routed to a nearby instance and DDoS traffic is spread across the footprint.

10Failure modes and response codes

  • NXDOMAIN means the name does not exist; NODATA means the name exists but has no record of that type.
  • Negative answers are cached too, using the zone's SOA minimum, so a typo can stay broken after you fix it.
  • SERVFAIL means the resolver could not get a usable answer: broken delegation, unreachable authority, or DNSSEC validation failure.
  • A lame delegation points at a name server that is not actually authoritative for the zone, producing timeouts and SERVFAIL.
  • Because DNS precedes every connection, a resolver outage looks like a total outage of everything downstream.
  • Clients and libraries cache independently, so two processes on one host can disagree about an address.
  • A dangling CNAME or forgotten subdomain can be claimed by someone else and served under your domain.

11DNS in system design

  • Round-robin A records spread clients across addresses, but DNS has no idea which backend is healthy or busy.
  • Weighted record sets shift a share of traffic, which is useful for canaries and gradual migrations.
  • Health-checked failover DNS removes a failed endpoint, but only after the record's TTL and the health-check interval.
  • Geo-steering returns a regional endpoint so users connect to a nearer point of presence.
  • SRV records advertise host and port for service discovery, used by protocols that support them.
  • Split-horizon DNS returns internal addresses to internal clients and public addresses to everyone else.
  • DNS is a coarse routing signal: it decides which address a client learns, not which instance handles each request.
For fast failover, pair a short TTL with an actual load balancer or anycast layer. DNS alone keeps sending some clients to the dead address until their caches expire.

12What to remember

  • DNS is a hierarchy of delegations: root to TLD to authoritative, with each level only pointing at the next.
  • Clients send one recursive query; the resolver performs the iterative walk.
  • Caching at browser, OS, and resolver is what makes DNS fast and authoritative servers small.
  • TTL is the trade-off between cache efficiency and how fast a change can take effect.
  • Record types describe intent: A/AAAA for addresses, CNAME for aliases, NS for delegation, MX for mail, TXT for metadata.
  • Changes are not pushed; they appear as caches expire, so lower the TTL before a planned move.
  • DNS is a dependency of everything else, so treat resolver availability and record correctness as production concerns.

↔Trade-offs to say out loud

  • Long TTLs improve cache hit rate and reduce DNS traffic but keep stale or wrong answers alive for longer after a change.
  • Short TTLs make failover and migrations fast but increase lookup volume and expose clients to more resolver failures.
  • A hierarchical delegation lets DNS scale to billions of names but makes a single broken delegation break an entire zone.
  • Resolver caching cuts latency and authoritative load but removes the operator's ability to force an immediate update.
  • DNS-based load balancing is simple and globally distributed but blind to backend health, load, and connection state.
  • CNAME aliases centralize address changes but add a lookup hop, cannot coexist with other records, and are awkward at the zone apex.
  • Encrypted DNS protects queries from local observers but adds setup cost and can bypass enterprise or parental controls.
  • Aggressive negative caching protects authoritative servers from repeated bad lookups but makes a fixed typo linger for users.

?Interview questions

Answer aloud before opening the outline.

1. What problem does DNS solve?

It maps stable human-readable names to the addresses and records clients need. That indirection lets the address behind a name change — for a deploy, a failover, or a CDN — without clients changing anything.

2. Walk me through resolving example.com with empty caches.

The browser checks its cache, then the OS checks its cache and hosts file. The OS sends a recursive query to a resolver, which asks a root server for .com, asks the .com servers for example.com's name servers, then asks those authoritative servers for the record. The answer comes back with a TTL and is cached at each layer before the client connects.

3. Recursive versus iterative query — what is the difference?

A recursive query asks a server to produce the final answer or an error. An iterative query asks for the best information the server has, typically a referral to the next server. Clients send recursive queries to resolvers; resolvers send iterative queries to root, TLD, and authoritative servers.

4. Why can root servers handle the load of the entire internet?

Because they only answer referrals for TLDs, not individual domains, and resolvers cache those referrals for a long time. Anycast spreads queries across many instances, so most traffic never reaches a single physical server.

5. What is a TTL and how do you choose one?

TTL is how long a cache may reuse a record. Choose it from how fast the record may need to change: stable infrastructure can use a long TTL, while records used for failover or migration should be short. Short TTLs cost more lookups and more exposure to resolver failures.

6. A teammate says DNS is propagating. What is actually happening?

Nothing is being pushed. Each resolver keeps answering from its cache until the record's TTL expires, then fetches the new value. Until then, different users can legitimately get different answers.

7. How do you make a DNS change roll out quickly?

Lower the TTL before the change, wait at least the old TTL so existing cached copies expire, then change the record. After things settle, raise the TTL again. Trying to rush the change without pre-lowering means waiting out whatever TTL was already cached.

8. Explain A, AAAA, CNAME, NS, MX, and TXT.

A and AAAA map a name to an IPv4 or IPv6 address. CNAME aliases one name to another. NS names the authoritative servers for a zone and implements delegation. MX names mail servers. TXT holds arbitrary text used for verification, SPF, and similar metadata.

9. Why can't you put a CNAME at the zone apex?

Because the apex must also carry NS and SOA records, and a CNAME cannot coexist with other records at the same name. Providers work around this with alias or CNAME-flattening features that resolve the target at query time.

10. What is the difference between NXDOMAIN and SERVFAIL?

NXDOMAIN is a definitive negative answer: the name does not exist. NODATA means the name exists but has no record of the requested type. SERVFAIL means resolution failed — a broken delegation, an unreachable authority, or a validation error — and the client should consider retrying or trying another resolver.

11. How would you use DNS for failover, and what are its limits?

Use health-checked records with a short TTL and remove the failed endpoint so new lookups get a healthy address. The limits are caching and detection delay: clients that already resolved the dead address keep using it until their TTL expires, and DNS cannot see per-connection load or health.

12. Why is DNS a common cause of total outages?

Every connection depends on a lookup first. If the resolver is unreachable, the zone is misconfigured, or the delegation is lame, clients cannot even reach a healthy service. That is why resolvers are usually redundant and DNS changes are treated as high-risk.

13. How can DNS be abused for subdomain takeover?

A CNAME or delegated subdomain can point at a resource that no longer exists, such as a deleted cloud bucket or app. An attacker who claims that target can serve content under your domain, so dangling records must be removed.

14. What is negative caching and why does it matter?

Resolvers cache the fact that a name or type does not exist, using the zone's SOA timer. It protects authoritative servers from repeated bad queries, but it also means a typo or a record you just created can stay invisible for the negative TTL.

!Traps

  • Describing DNS changes as a push and assuming every resolver updates immediately.
  • Leaving a long TTL on a record you intend to fail over, then discovering clients keep hitting the dead address.
  • Lowering the TTL at the same moment as the change instead of well before it, and not waiting out the old TTL.
  • Treating DNS round-robin as a health-aware load balancer that reacts to backend failures.
  • Placing a CNAME at the zone apex or creating long CNAME chains that are hard to debug.
  • Ignoring resolver and OS caching during testing, then concluding a change worked because one machine saw it.
  • Assuming all resolvers return the same answer at the same time across regions and providers.
  • Hardcoding IP addresses in clients to avoid DNS, which silently defeats failover and migration.
