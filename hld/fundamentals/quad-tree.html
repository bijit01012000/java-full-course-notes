01The problem with one fixed grid

A nearby-places app holds a very large number of places, each with a latitude and longitude, and must answer "what is closest to this point?" quickly.

  • The obvious structure is a uniform grid: divide the map into equal cells, assign each place to its cell, then search the user's cell and its neighbors.
  • Places are not evenly distributed: one downtown cell can hold thousands of places while a desert cell of the same size holds none.
  • Large cells make dense-city searches return far too many candidates to filter.
  • Small cells create a huge number of empty cells and force rural searches to walk many of them.
  • Scanning every point works for a small dataset but collapses when the count reaches millions.
  • What is needed is a grid that adapts to the data: fine where places are packed, coarse where they are sparse.

02What a quadtree is

  • A quadtree is a tree whose root covers the whole map and whose nodes cover nested rectangles.
  • Each node has at most four children, one for each quadrant: north-west, north-east, south-west, south-east.
  • A node splits only when it holds more than its capacity, so subdivision follows density rather than a global rule.
  • Dense areas therefore end up with small, deep cells; empty areas stay as large shallow leaves.
  • Every item lives in exactly one leaf, which avoids the duplication that cell-based indexes suffer with shapes.
  • Search descends only into subtrees whose bounding box can intersect the query, which is where the speedup comes from.
  • The structure is a spatial analogue of a binary search tree, generalized from two branches to four.

03Node layout and capacity

  • A leaf stores a small list of items plus the rectangle it covers.
  • An internal node stores four child pointers and no items of its own; routing replaces storage.
  • The capacity is a configured constant, typically small, chosen so that scanning a leaf is cheap.
  • A larger capacity means a shorter tree and fewer pointer hops, but more work per leaf.
  • A smaller capacity means deeper trees and more memory overhead per item.
  • Many implementations store the rectangle implicitly, deriving it from the path from the root, which saves memory.
  • Whether items live only in leaves or also in internal nodes is an implementation choice that affects insertion and deletion code.

04Subdivision

  • When a leaf exceeds capacity, it is split at the midpoint of both axes, producing four equal quadrants.
  • Each stored item is re-bucketed into the quadrant that contains it.
  • The split is local: only that node's contents move, not the whole tree.
  • A max depth is required, otherwise a cluster of identical or near-identical coordinates splits forever.
  • At max depth the leaf simply grows beyond capacity, accepting a slower scan for that small region.
  • Points exactly on a split line need a deterministic tie-break rule, or the same point can migrate between quadrants.
  • Splitting is cheap in isolation but repeated splits during a bulk load are the main construction cost.

05Insertion

  • Start at the root and compare the point against each node's midpoint to choose a quadrant.
  • Descend until a leaf is reached, then append the item to that leaf.
  • If the leaf is now over capacity and depth remains, split and continue routing the overflowing items.
  • Insertion cost is proportional to tree depth, which is logarithmic when the data is reasonably spread.
  • Skewed or duplicate-heavy data degrades the tree toward a linear chain of splits.
  • Bulk loading is much faster when points are sorted into Morton order first, because locality reduces repeated splitting.
  • An update that moves a point is a delete followed by an insert, since its quadrant may change entirely.

06Range and radius search

  • A query carries a region — a rectangle for a bounding-box search, or a circle for a radius search.
  • At each node, test whether the node's rectangle can intersect the query region.
  • If it cannot, prune the entire subtree without touching its contents.
  • If it can, recurse into children and test individual items only at leaves.
  • For a circle, the cheap test is against the circle's bounding square; the exact distance check happens on the surviving candidates.
  • Pruning is what makes the structure fast: empty space is skipped in large blocks.
  • A query whose region covers everything degenerates to a full scan, which is expected but worth knowing.

07Nearest-neighbor search

  • Exact k-nearest-neighbor search explores nodes in order of the minimum possible distance from the query point to the node's rectangle.
  • A priority queue ordered by that lower bound gives best-first traversal.
  • Once the queue's best bound is farther than the current worst of the k results, the search stops.
  • This avoids visiting subtrees that cannot beat an already-found answer.
  • A simpler alternative is an expanding ring search: start at the leaf, then widen through neighbors until k results are found.
  • Ring search is easier to implement but can visit far more nodes than best-first when density varies.
  • Both approaches depend on the leaf's contents being small enough to scan cheaply.

08Deletion and rebalancing

  • Locate the item by descending to its leaf, then remove it from that leaf's list.
  • Store a parent pointer or keep the path, otherwise deletion requires a fresh search.
  • After a removal, a parent whose four children together hold few enough items can be collapsed back into a leaf.
  • Merging keeps the tree shallow when an area empties out, such as a fleet of drivers dispersing.
  • Many production uses skip merging and rebuild the tree periodically instead, because empty nodes are cheap to prune.
  • Frequent insert-and-delete churn in the same region is the case where stale structure hurts most.
  • Deletion must preserve the invariant that each item sits in the leaf matching its coordinates.

09Variants worth knowing

  • Point quadtree: splits at the inserted point rather than the rectangle center, producing uneven cells.
  • Region quadtree: subdivides an image or grid while a block is not uniform, the basis of quadtree image compression.
  • Bucket PR quadtree: the point-region form with a capacity per leaf, which is what most nearby-search implementations mean by quadtree.
  • Linear quadtree: stores cells as Morton-order integers so the structure becomes a sorted index rather than a pointer graph.
  • Octree: the three-dimensional generalization, splitting each node into eight children.
  • The disk-friendly variants matter because pointer-based trees are awkward to persist and page in.

10Limitations

  • Performance depends on data distribution; a heavily skewed dataset produces deep, unbalanced branches.
  • Pointer chasing is cache-unfriendly compared with scanning a flat array of cells.
  • The tree lives in memory comfortably; persisting it and querying it from disk is where most implementations stop.
  • Rebalancing after large deletions is usually manual or periodic, not automatic.
  • It indexes points well but handles polygons and lines badly, because a shape spanning quadrants must be stored in several.
  • A fixed grid of geohash strings is simpler when the data is roughly uniform and the database is the source of truth.
  • Concurrent updates need locking around splits, which can serialize writers in hot regions.

11Tuning and operating it

  • Tune capacity against leaf scan cost: it is the difference between a shallow tree with fat leaves and a deep tree with thin ones.
  • Set max depth deliberately; without it, duplicate coordinates create unbounded depth.
  • Rebuild from scratch on a schedule when churn is high, which is cheaper than maintaining perfect balance.
  • Measure query candidate counts, not just latency: a bad capacity shows up as many survivors after pruning.
  • Keep the tree per shard or per region rather than one global tree, so updates stay local.
  • Snapshot or rebuild on restart rather than serializing the pointer graph.
  • Log depth and node count, because silent skew is the failure mode that appears only under real traffic.

12Where it fits

  • In-memory spatial indexes: nearby places, nearby drivers, points of interest in a game world.
  • Collision detection, where only objects in overlapping quadrants need pairwise tests.
  • Image and terrain compression through region quadtrees, plus level-of-detail rendering.
  • Spatial joins and analytics over unevenly distributed point data.
  • Choose a quadtree when density varies widely and the index can live in memory or be rebuilt cheaply.
  • Choose a geohash when the index must be a plain database column, and an R-tree when the objects are shapes rather than points.

↔Trade-offs to say out loud

  • Adaptive subdivision keeps candidate sets small in dense areas but makes the tree shape depend on the data.
  • Larger leaf capacity shortens the tree and improves cache behavior but increases the scan at each leaf.
  • Smaller leaf capacity prunes more precisely but adds depth, pointers, and split work.
  • Deep subdivision separates nearby points but risks unbounded depth on duplicate coordinates without a cap.
  • Best-first nearest-neighbor search visits the fewest nodes but needs a priority queue and distance-to-box math.
  • Periodic rebuild is simpler than incremental merging but costs a full reconstruction window.
  • In-memory indexes answer fast but must be rebuilt or warmed after a restart.
  • Per-shard trees keep writes local but make global queries fan out across shards.

?Interview questions

Answer aloud before opening the outline.

1. What problem does a quadtree solve that a fixed grid does not?

Data density varies enormously across a map, so no single cell size is right everywhere. A quadtree splits only where items accumulate, giving small cells in cities and large cells in empty regions. The result is that a search prunes large empty areas while still keeping dense-area candidate sets modest.

2. How does a quadtree decide when to split?

A leaf splits when it holds more than its configured capacity. It is divided at the midpoints of both axes into four quadrants, and the existing items are redistributed. A max depth stops the process when items share nearly identical coordinates.

3. Walk through a radius query.

Start at the root and test whether each node's rectangle can intersect the circle's bounding box. Rectangles that cannot are pruned entirely; the rest are descended recursively. At each leaf the stored points are distance-checked exactly, and the survivors are filtered by the radius.

4. How does nearest-neighbor search differ from a range query?

A range query tests every subtree that could intersect a fixed region. Nearest-neighbor search instead explores nodes in order of the minimum distance from the query point to their rectangle, then stops when no unexplored node can beat the current k-th result. That bound ordering is what keeps it from visiting the whole tree.

5. What happens if you set no maximum depth?

Many points with identical or nearly identical coordinates can never be separated by further subdivision, so the leaf splits forever. A depth cap makes the node stop splitting and accept a larger bucket, trading a slower local scan for termination.

6. Why does deletion often trigger a merge?

When an area empties, its internal nodes keep four children with almost nothing in them, which wastes memory and traversal time. If a parent's children together hold few enough items, collapsing them back into one leaf restores the adaptive shape. Many systems defer this and rebuild periodically instead.

7. Is a quadtree a good choice for delivery-zone polygons?

Usually not. A polygon that spans several quadrants must be stored in several nodes or pushed up to a node where more queries must inspect it. An R-tree, which groups shapes by bounding rectangle, handles overlapping and intersecting shapes far better.

8. Quadtree or geohash for nearby search?

Choose a quadtree when the data is very uneven and the index can live in memory or be rebuilt. Choose a geohash when the index must be an ordinary database column, when the data is roughly uniform, or when the same key also serves for sharding and aggregation.

9. What is a linear quadtree and why does it exist?

It encodes each cell as an integer in Morton order, so the tree's structure becomes a sortable key rather than a graph of pointers. That makes the index storable in a database or file and range-scannable, at the cost of losing cheap incremental splits.

10. Why is bulk loading faster than repeated insertion?

Repeated insertion re-splits the same nodes as points arrive in arbitrary order, and each split redistributes items. Sorting points by spatial locality first lets the loader build leaves in one pass and touch each node once.

11. What workload makes a quadtree degrade?

Heavily skewed data plus churn: a few hot regions receive most inserts and deletes, producing deep branches that are edited constantly. Duplicate coordinates at max depth and a stale structure after mass deletion are the other common degradations.

12. How would you scale a quadtree across servers?

Partition the map into regions, keep one tree per region, and route queries to the regions the search area overlaps. Global queries fan out and merge results, so keep regions balanced by splitting hot ones — the same skew problem the tree solves locally reappears at the partition level.

!Traps

  • Assuming a quadtree always balances itself; it is shaped by insertion order and density.
  • Omitting a max depth and letting duplicate coordinates split forever.
  • Storing polygons in a point-oriented quadtree and duplicating them across quadrants.
  • Treating bounding-box intersection as the final answer instead of filtering by exact distance.
  • Forgetting to re-bucket items after a split, which leaves points in the wrong quadrant.
  • Using a quadtree as a disk-backed index and paying for pointer chasing on every page fault.
  • Never merging emptied nodes, so the tree stays deep long after the data moved away.
