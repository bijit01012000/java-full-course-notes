01What a heartbeat is

A node cannot observe another node's process directly. It can only observe whether messages are arriving. A heartbeat turns liveness into a message-arrival question.

  • A heartbeat is a small message sent on a fixed schedule that says the sender is still running.
  • The receiver stores a per-node timestamp: the last time it heard from that node.
  • While heartbeats keep arriving, the node stays in the healthy set and continues to receive work.
  • When the gap since the last heartbeat exceeds a threshold, the receiver starts treating the node as failed.
  • The only question a heartbeat answers is have I heard from this node recently enough to keep trusting it?
  • Heartbeats drive concrete actions: stop routing requests, reassign tasks, remove a replica, or page an operator.

02How a check works

A monitor keeps one row per node and compares now - last_heartbeat against its timeout on every evaluation tick.

  • Each worker sends a heartbeat every interval; the monitor only records the arrival time.
  • The monitor evaluates all rows periodically rather than reacting to each message, which bounds its own work.
  • A row whose age exceeds the timeout is marked failed and handed to the recovery path.
  • The decision is a local judgement based on local information — the monitor cannot see the node, only its silence.
  • Recovery is a separate policy: stop sending work first, then reassign, then decide whether to replace the node.
  • Evaluation granularity matters: checking every few seconds adds that much delay on top of the timeout.

03Push versus pull

  • In the push model each node emits heartbeats and the monitor only listens.
  • Push needs no registry of node addresses and lets nodes start reporting without being asked.
  • Push concentrates risk in the receiver: an overloaded or unreachable monitor makes healthy nodes look dead.
  • In the pull model the monitor probes each node's health endpoint on its own schedule.
  • Pull gives the monitor control over timing and lets it apply consistent checks, which is why load balancers use it.
  • Pull requires knowing every address and costs one outbound request per node per round, which hurts in very large clusters.
  • Real systems mix both: nodes push metrics and status, the platform pulls readiness for routing decisions.

04Interval, timeout, and failure threshold

  • The interval sets detection resolution: no failure is noticed faster than one interval plus the timeout.
  • The timeout should be several times the interval so one dropped packet or a short scheduling delay is harmless.
  • A common shape is a 1 s interval with a 5 s timeout, giving roughly five chances before a verdict.
  • Many systems express the timeout as a failure threshold: act after N consecutive missed heartbeats.
  • Count-based thresholds tolerate variable intervals; time-based thresholds tolerate variable processing delay.
  • Detection latency is roughly timeout + evaluation period, so both settings belong in your failure budget.
  • Tune from measured network jitter and pause times, not from intuition.
Timeout is a policy statement about how much evidence you require, not a measurement of the network.

05The detection trade-off

Every heartbeat configuration trades detection speed against false alarms. There is no universally correct value; the cost of each wrong answer decides.

  • A short timeout detects crashes quickly but converts slow GC, CPU starvation, or a congested link into a failure verdict.
  • A long timeout tolerates noise but keeps sending work to a dead node and delays recovery.
  • A short interval improves resolution but multiplies traffic and wakeups; with thousands of nodes, small messages add up.
  • A long interval reduces overhead but blurs the line between a pause and a crash.
  • The asymmetry matters: a false positive can trigger a failover that is far more damaging than a late detection.
  • Match the timeout to the action — removing a node from a load balancer is cheap and reversible, promoting a primary is not.

06Why a healthy node can miss heartbeats

  • The network can drop, delay, or reorder the heartbeat message; the sender has no proof it arrived.
  • The node may be CPU-starved, so its heartbeat thread is scheduled late even though it is alive.
  • A long garbage collection pause freezes the whole process, including the thread that sends heartbeats.
  • A virtual machine or container can be paused by its host for migration, CPU throttling, or noisy-neighbour effects.
  • A blocked thread pool or deadlock can stall application work while a background timer keeps firing.
  • From the receiver's side these are indistinguishable from a crash, which is why heartbeats produce suspicion, not certainty.
  • This is the core limitation: a missing heartbeat says I have not heard from you, never you are dead.

07The suspect state and rejoin

A staged verdict converts one binary decision into two cheaper ones: stop trusting the node now, declare it dead later.

  • After a few missed heartbeats the node becomes suspect: stop assigning new work but do not start expensive recovery.
  • If a heartbeat arrives before the longer deadline, the node returns to healthy with minimal disruption.
  • If silence continues past the outer timeout, the node is declared failed and recovery begins.
  • This absorbs temporary network blips and avoids unnecessary failovers that cost more than the outage.
  • When a failed node starts reporting again, do not trust it immediately: move it to a recovering state.
  • Recovery checks include catching up on missed data, replaying a log, warming caches, and passing a readiness probe.
  • Only after those checks should the node receive full traffic again.
Healthy: heartbeats arriving→Suspect: threshold missed, stop new work→Failed: outer deadline passed, start recovery→Recovering: node returns, run catch-up checks→Healthy: restore full traffic

08Heartbeats at scale

  • A central monitor is the simplest design but processes every heartbeat and becomes a single point of failure.
  • All-to-all heartbeats remove the central node, but each node contacts every other node, so message count grows quadratically.
  • With n nodes, all-to-all produces on the order of n * (n - 1) messages per round, which stops being viable as the cluster grows.
  • Gossip keeps the message count linear: each node contacts a few random peers per round and merges what it learns.
  • Gossip spreads liveness information over several rounds, so different nodes briefly disagree about who is alive.
  • Central monitors are fine for hundreds of nodes or for one coordinator managing workers; gossip wins for large peer-to-peer clusters.
  • Whichever you pick, isolate the failure-detection path from application load so a busy cluster does not lose its own health signal.

09What a heartbeat can carry

  • Since the message is already being sent, it can carry load and capacity data at no extra round trip.
  • A worker can report CPU, memory, queue depth, or in-flight tasks so a scheduler assigns work to less busy nodes.
  • A storage node can report free disk and replica lag so placement decisions stay informed.
  • A sequence number that increases with each message lets the receiver detect gaps, duplicates, and reordering.
  • A piggybacked clock or term value helps the receiver discard outdated reports from a previously failed incarnation.
  • Keep the payload small: per-node fields multiply by node count and frequency.
  • Do not let rich payloads make the heartbeat path heavy — a large or slow heartbeat is itself a liveness risk.

10Sending heartbeats is not the same as doing work

  • A separate background thread can keep sending heartbeats while the main processing thread is stuck in a loop or blocked on a dependency.
  • The node then looks perfectly healthy while it serves no requests — the most dangerous failure because it attracts traffic.
  • The fix is to make the health signal reflect progress, not just the scheduler: last successful request, last poll, queue drain.
  • Kafka consumers demonstrate the distinction: heartbeats show group membership, but a consumer that stops polling is removed from the group anyway.
  • Kubernetes separates liveness (restart this container) from readiness (send it traffic) precisely because they prompt different actions.
  • A readiness failure should remove traffic and be cheap to reverse; a liveness failure should restart, which is disruptive.
  • Design the check so a healthy answer requires evidence of useful work, not merely a running event loop.

11False positives, leases, and fencing

Because a suspect node may still be alive and reachable by some clients, recovery must assume the old node can still act.

  • A node marked failed can come back; assume it will and make the system safe for that case.
  • If replicas stop hearing from a primary during a partition and promote a new one, the old primary may still accept writes — this is split-brain.
  • Missed heartbeats should only start the process; promotion needs agreement from a majority, not one observer's suspicion.
  • A lease gives leadership a deadline: a node may act only while its lease is valid, so a paused node cannot act indefinitely.
  • A fencing token that increases with each leadership grant lets the storage layer reject writes from an old leader.
  • Make removal idempotent and observable: record why a node was removed so operators can tell a real crash from a false alarm.
  • Prefer reversible actions first (drain traffic) and irreversible ones (data deletion, primary promotion) only with quorum-backed evidence.

12Practical guidelines and decision rules

  • Set the timeout to several times the interval, and base it on measured jitter and pause times.
  • Add jitter to intervals so thousands of nodes do not synchronise into a heartbeat storm.
  • Choose the timeout from the cost of a wrong decision: cheap and reversible actions can react fast, irreversible ones must wait longer.
  • Use a suspect state to separate cheap suspicion from expensive recovery.
  • Send the heartbeat on a path that stays healthy under load, and never let it depend on the work it is supposed to report on.
  • At scale, prefer gossip or a sharded monitor over one receiver for the whole fleet.
  • Always pair failure detection with quorum, leases, or fencing before granting exclusive authority.
  • Track detection latency and false-positive rate as product metrics; tune from data rather than defaults.
Pick interval from jitter and required resolution→Set timeout as a multiple of the interval→Add jitter to spread the load→Define suspect and failed thresholds→Bind each verdict to a reversible action→Guard leadership changes with quorum and fencing

↔Trade-offs to say out loud

  • Short timeouts cut detection latency but convert GC pauses and packet loss into failovers.
  • Long timeouts suppress false positives but keep traffic flowing to dead nodes for longer.
  • Frequent heartbeats improve resolution but add network and CPU cost that scales with fleet size.
  • Push avoids a node registry but makes the receiver a bottleneck and a single point of failure.
  • Pull gives the monitor control and consistent checks but costs one request per node per round.
  • Gossip scales linearly in messages but delivers an eventually consistent, slightly stale view of liveness.
  • Suspect states reduce unnecessary failovers at the cost of slower recovery and more state to reason about.
  • Rich heartbeat payloads enable better scheduling but enlarge the message every node sends every interval.

?Interview questions

Answer aloud before opening the outline.

1. What is a heartbeat and what does it actually prove?

A small message sent on a schedule to show the sender is still running. It proves only that a message arrived recently, not that the node is healthy or able to do work.

2. How do you choose the heartbeat interval and timeout?

Start from measured network jitter and process pause times, then set the timeout to several times the interval so a single miss is harmless. Refine both against the cost of a false positive versus the cost of late detection.

3. Push or pull: which would you pick?

Push when many workers report to a coordinator and you do not want to maintain an address list. Pull when the component doing the checking must control timing and apply a uniform probe, as load balancers do. Large systems often use push for metrics and pull for routing readiness.

4. Why can a healthy node be marked failed?

Packet loss, CPU starvation, a long garbage collection pause, host-level VM pauses, or a wedged thread pool can all delay heartbeats. The receiver cannot distinguish these from a crash, so it can only suspect.

5. What is a suspect state and why add it?

An intermediate verdict after a few missed heartbeats: stop assigning new work but delay expensive recovery. If a heartbeat arrives, the node simply returns to healthy. It absorbs transient blips without an unnecessary failover.

6. How do heartbeats scale to thousands of nodes?

All-to-all grows quadratically and a central monitor becomes a hot single point of failure. Gossip keeps messages linear by having each node exchange a small table with a few random peers, at the cost of delayed and temporarily inconsistent views.

7. What can a heartbeat message carry besides liveness?

Load metrics, queue depth, free disk, capacity hints, and a sequence number for gap detection. Keep the payload small because every extra field is multiplied by node count and frequency.

8. Why is sending heartbeats not the same as being healthy?

A background thread can keep sending while the request-handling path is blocked or looping. Such a node looks alive and keeps attracting traffic while completing nothing, so health checks should test real progress such as last successful request or last poll.

9. What is the difference between liveness and readiness?

Liveness asks whether the container should be restarted because it is wedged. Readiness asks whether it should receive traffic right now. They lead to different actions, so conflating them causes either restart loops or traffic to broken instances.

10. How do you prevent split-brain after a missed heartbeat?

Treat the missing heartbeat only as a trigger. Require a majority of nodes to agree before promoting a new leader, and use leases plus fencing tokens so the old leader's writes are rejected by the storage layer.

11. Why add jitter to heartbeat intervals?

If every node starts at the same time and uses the same interval, their heartbeats arrive in synchronised bursts. Randomising the interval spreads the load so the monitor sees a smooth stream instead of spikes.

12. What should happen when a failed node comes back?

Do not restore traffic immediately. Move it to a recovering state, let it catch up on missed data or replay the log, verify it with readiness checks, then return it to the healthy set.

!Traps

  • Treating a missed heartbeat as proof of death rather than evidence of silence.
  • Setting the timeout close to the interval, so one dropped packet triggers a failover.
  • Promoting a primary on a single observer's suspicion instead of a majority decision.
  • Letting heartbeats run on the same thread as the work they are supposed to report on.
  • Assuming a healthy heartbeat means the node can serve requests.
  • Sending heartbeats from every node on the same schedule with no jitter.
  • Forgetting that a suspected node may still be alive and able to write.
