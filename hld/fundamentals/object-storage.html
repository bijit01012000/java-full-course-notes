In one lineObject storage is a flat, HTTP-addressable store for whole blobs — images, video, backups, model datasets — built to scale capacity and durability far beyond a single filesystem, at the cost of POSIX semantics and cheap queries.
Object
The stored unit: the data bytes plus system metadata and user metadata, addressed as one indivisible blob.
Bucket
A namespace that holds objects and defines region, access policy, versioning, and lifecycle rules.
Key
The unique name of an object inside a bucket; it looks like a path but the store does not treat it as one.
Flat namespace
There are no real directories — prefixes are just parts of the key, and listing is a lexicographic range scan.
Erasure coding
Splitting data into fragments plus parity so a subset of nodes can rebuild a lost fragment without a full copy.
ETag
An identifier for a specific object version, used for caching and for conditional writes.
Presigned URL
A time-limited, signed URL that lets a client upload or download directly from storage without holding credentials.
Multipart upload
Splitting a large object into parts uploaded in parallel and assembled on commit, so one failure does not restart everything.
Storage class
A durability/availability/retrieval-cost tier; colder classes are cheaper to keep and more expensive to read.
Lifecycle rule
A policy that transitions, expires, or deletes objects automatically based on age or prefix.

01What object storage is

Modern applications store enormous volumes of unstructured data: images, video, documents, backups, logs, and machine-learning datasets. Object storage is the model behind S3, Google Cloud Storage, Azure Blob Storage, and MinIO.

  • Data is stored as whole objects addressed by a key, not as blocks on a device or files in a mounted directory.
  • Clients talk to it over HTTP with simple verbs: put, get, head, delete, list.
  • It is built for capacity and durability, spreading objects across many machines and failure domains.
  • There is no filesystem to mount in the normal case and no partial in-place edit of an object.
  • It holds unstructured or opaque bytes; the service does not interpret the contents.
  • It is the default home for large binary assets and for data-lake style analytical input.
  • It is not a database: it offers no joins, no secondary indexes, and no multi-object transactions.

02Objects, buckets, and keys

  • A bucket is the top-level namespace and the unit of policy, region, and billing.
  • Bucket names are globally unique in most public clouds, because the name becomes part of the URL.
  • An object consists of the bytes, system metadata (size, content type, ETag, timestamps), and optional user metadata.
  • The key is an arbitrary string; users/42/avatar.png is one key, not a directory plus a file.
  • Prefixes are a naming convention that the service exploits for listing and policy, not a real hierarchy.
  • Objects are immutable in practice: an overwrite replaces the whole object, it does not patch bytes.
  • A common layout puts a high-cardinality component early in the key, such as a tenant or hash prefix, to spread load.
  • Object size limits exist per service; large files must be uploaded in parts rather than as one request.

Content-Length: 48213

Rename is a copy plus a delete, and it is not atomic. Design keys so objects rarely need to move.

03Metadata and the flat namespace

  • System metadata covers size, content type, checksum, storage class, and timestamps; user metadata is a small set of key-value pairs.
  • Metadata is what a HEAD request returns and what lifecycle and policy rules evaluate.
  • You cannot efficiently filter a bucket by user metadata at scale; that requires an external index.
  • Listing returns keys in lexicographic order, which makes prefix scans and date-prefixed keys cheap.
  • A deep hierarchy is only simulated: deleting a prefix is a bulk operation over matching keys.
  • Because there are no directories, an object can exist under a key whose 'parent folder' was never created.
  • Search over object contents is not provided; text search needs a separate search index built from the objects.
  • Store queryable business attributes in a database row that points to the key, not in object metadata.

04The HTTP API and access control

  • PUT writes or replaces a whole object; GET reads it; HEAD returns metadata; DELETE removes it.
  • Range requests return a byte range, which is how video players seek and how large files resume.
  • Every request is authenticated and authorized; bucket policies and IAM decide who may read or write which prefix.
  • A presigned URL delegates a single operation for a limited time, so browsers upload without long-lived credentials.
  • Conditional requests use If-Match or If-None-Match with an ETag to avoid overwriting a concurrent change.
  • Errors distinguish missing objects from denied access, and clients must handle both without leaking existence information.
  • The API is intentionally small, which is why almost every language and tool can integrate with it.
  • Server-side encryption and TLS are configured at the bucket or request level, not invented per application.
Client asks app for upload slot→App checks permission→App returns presigned PUT URL→Client uploads bytes directly→Storage confirms, app records the key
The direct-upload pattern keeps large payloads off the application servers and out of their memory.

05How object storage scales internally

The reason object storage reaches huge scale is that it separates the namespace and metadata from the bytes, and spreads both across many machines.

  • A metadata layer maps bucket plus key to object location, size, and attributes; it is the part that must be highly available.
  • A data layer stores immutable chunks on many storage nodes, often with its own local redundancy.
  • Placement usually hashes the key or an object id to choose a set of nodes, so no central directory tracks every byte.
  • Because objects are immutable, replicas never need in-place reconciliation of divergent writes.
  • Large objects are chunked so they can be spread across nodes and rebuilt in parallel.
  • Adding capacity means adding nodes and rebalancing chunks; the namespace does not have to be repartitioned like a B-tree.
  • Metadata operations (list, head, policy check) are the usual bottleneck under many small objects.
  • Hot keys or a poorly distributed prefix can concentrate traffic on a small set of nodes.
Request: bucket + key→Metadata service resolves location→Client or gateway reads chunks→Response streamed back
This is the same separation of concerns as a database with a primary index and separate heap files, applied to blobs.

06Durability and repair

  • Durability comes from redundancy across independent failure domains, not from one reliable disk.
  • Replication keeps full copies on different nodes or zones; simple to reason about, but storage cost multiplies.
  • Erasure coding stores data fragments plus parity, so a lost fragment can be recomputed from the others at lower storage overhead.
  • Erasure coding saves capacity but makes reads and repairs more CPU- and network-intensive than a plain replica read.
  • Background scrubbing compares checksums and rebuilds damaged or missing fragments before a second failure compounds.
  • Cross-region replication protects against losing an entire region, at the cost of bandwidth and write latency.
  • Durability is not backup: an application bug or a bad delete propagates instantly to every replica.
  • Versioning and object lock are the practical defenses against accidental or malicious deletion.

07Consistency, versioning, and concurrent writes

  • Modern object stores generally give strong read-after-write consistency for new objects and overwrites, but you must verify the guarantee for your provider and operation.
  • Listing is the operation most likely to lag, so a client that just wrote a key may not see it in a prefix listing immediately.
  • With versioning on, an overwrite creates a new version and the old bytes remain recoverable until a lifecycle rule expires them.
  • Concurrent writers to the same key follow last-writer-wins unless conditional writes or versioning are used.
  • Two clients can each believe they wrote the object; the loser is silently overwritten.
  • A common fix is a unique key per write (content hash or UUID) plus a database pointer to the current one.
  • Delete markers in a versioned bucket make an object look absent while its versions remain, which confuses naive tooling.
  • Cross-region replication is asynchronous, so a reader in another region can briefly see the old version.
If two users can edit the same asset, treat the object as immutable and store the authoritative pointer with a compare-and-set in the database.

08Upload and delivery patterns

  • Upload directly from the client with a presigned URL so application servers never buffer large files.
  • For large assets, use multipart upload: parts upload in parallel, retries are per part, and the commit is explicit.
  • An abandoned multipart upload leaves invisible parts that still cost money until an abort lifecycle rule cleans them up.
  • Validate content type and size after upload; never trust the client's declared metadata.
  • Process asynchronously: the upload event triggers a queue, and workers generate thumbnails, transcode video, or extract text.
  • Serve public or cacheable content through a CDN so repeat reads never touch the origin store.
  • Use signed CDN URLs for private content, so authorization happens before the edge serves bytes.
  • Stream large downloads with range support instead of loading the whole object into memory.
Presign→Multipart upload→Commit→Event to queue→Derived assets written→CDN serves reads
The object store is the durable blob layer; the database holds the row that says which blob is current and who may see it.

09Cost model and lifecycle

  • You pay for stored bytes per month, and the rate depends on the storage class.
  • You also pay per request, which makes millions of tiny objects expensive in a way that one large object is not.
  • Cold classes have cheaper storage but charge for retrieval and impose a minimum retention period.
  • Egress — bytes leaving the provider's network — is often the largest surprise in the bill, especially for media.
  • Lifecycle rules transition objects to colder classes, expire old versions, and abort incomplete multipart uploads automatically.
  • A common policy keeps recent data hot, moves older data to infrequent-access tiers, then expires it or archives it.
  • Small-file workloads cost more per byte because metadata and request overhead dominate.
  • Aggregating small records into larger objects before writing usually cuts both request count and metadata pressure.

10Where object storage does not fit

  • There are no multi-object transactions: writing two objects can partially succeed.
  • There is no in-place partial update; changing one byte means rewriting the object or using a different store.
  • Rename and move are copy plus delete, so directory-style workloads become slow and error-prone.
  • Latency per request is network-bound, so it is a poor fit for hot metadata lookups or per-request small reads.
  • There is no file locking, no append in the POSIX sense, and no memory-mapped file access.
  • Querying is limited to listing by prefix; anything richer needs a database or an external index.
  • Running a traditional database on top of object storage adds latency and complexity; it is a backup or tiering target, not a local disk.
  • Small-file-heavy workloads suffer from per-object overhead and listing costs.

11Failure modes and operational rules

  • A failed upload can leave an orphaned object with no database row; reconcile with a periodic sweep or a write-then-commit ordering.
  • A failed database write after a successful upload leaves bytes nobody references — the mirror image of the same problem.
  • Deleting the database row first and the object second risks leaking bytes; deleting the object first risks broken references.
  • A 403 is often a policy or signing problem, not a missing file — do not map every error to 404.
  • Listing an entire bucket to find one object is a scalability bug; keep an index in the database.
  • Public buckets are a recurring data-leak cause; default to private and grant per prefix.
  • Retries must be idempotent: a repeated PUT of the same key is fine, a repeated 'create new key' is not.
  • Monitor request error rates, multipart aborts, lifecycle transitions, and egress, not just stored bytes.
Write object to a temporary key→Commit database row→Mark key current→Async cleanup of stale temporary keys
Pick an ordering and a reconciliation job. Two systems cannot be updated atomically, so eventual repair is part of the design.

↔Trade-offs to say out loud

  • Object storage gives near-unlimited capacity and high durability but gives up POSIX semantics, low latency, and partial updates.
  • Flat keys make prefix listing cheap but make renames, moves, and hierarchy-wide operations expensive.
  • Erasure coding lowers storage cost versus replication but increases read and repair work.
  • Immutability simplifies replication and caching but turns every edit into a full rewrite.
  • Versioning protects against overwrites and deletion but multiplies storage cost and hides old bytes in the bill.
  • Direct client uploads keep application servers light but require presigning, validation, and orphan cleanup.
  • CDN in front of storage cuts latency and egress but adds invalidation and cache-key design work.
  • Cold storage tiers reduce retention cost but add retrieval charges, latency, and minimum-stay rules.
  • Storing blobs outside the database keeps rows small and backups fast but creates a two-system consistency problem.

?Interview questions

Answer aloud before opening the outline.

1. What is object storage?

A flat, HTTP-addressable store for whole blobs. Each object has a key, its bytes, and metadata, and lives in a bucket. It scales capacity and durability across many machines instead of exposing a filesystem or a block device.

2. How is it different from a file system?

A file system has real directories, in-place edits, appends, locks, and POSIX calls. Object storage has a flat key namespace, immutable whole-object writes over HTTP, and much higher latency per operation. Prefixes only look like folders because listing is lexicographic.

3. How is it different from block storage?

Block storage exposes fixed-size blocks that a host formats with a filesystem, which is what databases and VM disks need. Object storage exposes whole named objects over a network API and is meant for large unstructured data, not for random small writes.

4. How does object storage achieve durability?

By keeping redundant copies or erasure-coded fragments across independent nodes and failure domains, then continuously scrubbing checksums and rebuilding lost fragments. Durability protects against hardware loss, not against application bugs or bad deletes.

5. What is erasure coding, and why use it?

Data is split into fragments with parity fragments added, so any sufficient subset can reconstruct the object. It achieves redundancy with less storage overhead than full replication, at the cost of more CPU and network work on reads and repairs.

6. Why can't you rename an object cheaply?

Because the key is the address and there is no directory entry to update. A rename is a copy of the bytes to a new key plus a delete of the old one, which costs time and is not atomic. Key designs that embed mutable fields make this worse.

7. How do you upload a large file?

Use multipart upload from the client with a presigned URL: split the file, upload parts in parallel, retry individual failures, then commit. Abort incomplete uploads with a lifecycle rule so orphaned parts do not accumulate cost.

8. How do you serve private media at scale?

Authorize in the application, then redirect to a signed CDN URL with a short expiry. The edge caches the bytes, so repeat views do not hit the origin, and the signature prevents sharing outside the allowed window.

9. How do you keep object storage and a database consistent?

You cannot make them atomic, so pick an ordering and reconcile. A common approach writes the object under a temporary or unique key, commits the database row, then marks it current, with a background job deleting unreferenced bytes and repairing missing ones.

10. What happens when two clients write the same key?

By default the last write wins and the earlier object is lost. Use conditional writes with an ETag, versioning, or a unique key per write plus a compare-and-set pointer in the database when concurrent edits matter.

11. Why is listing objects a scalability concern?

Listing is a metadata range scan, not a cheap directory read, and it returns paginated results. Calling it per request to find an object turns a key lookup into a scan. Keep a searchable index in a database instead.

12. When would you not use object storage?

When you need random writes, fsync, file locks, low-latency small reads, multi-object transactions, or rich queries. A database, block volume, or file system fits those better. Object storage is for large immutable blobs and bulk data.

13. How do storage costs get out of control?

Old versions, incomplete multipart uploads, millions of tiny objects with per-request charges, cold-tier retrieval fees, and egress. Lifecycle rules, content-hash deduplication, batching small records, and a CDN address most of them.

14. Design the image pipeline for a photo app.

Client requests a presigned upload, uploads directly, and the app records the key only after the object exists. An event triggers a queue; workers generate resized variants and write them back under derived keys. Reads go through a CDN with signed URLs, and originals are kept in a colder tier with lifecycle expiry for temporary uploads.

!Traps

  • Treating object storage as a filesystem and building logic around cheap rename or directory operations.
  • Storing queryable business attributes only in object metadata, then discovering you cannot filter on them.
  • Forgetting to abort incomplete multipart uploads, which quietly accumulate storage charges.
  • Assuming a successful upload means the database row exists — or the reverse — without a reconciliation job.
  • Making buckets public for convenience and exposing user data through predictable keys.
  • Listing a bucket on every request instead of maintaining an index in a database.
  • Assuming cross-region replication is synchronous and reading stale bytes during failover.
  • Ignoring egress and request pricing when estimating the cost of a media-heavy design.
