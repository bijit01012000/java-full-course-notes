A database server holding a copy of the same data as another server.

The node that accepts writes; also called the leader, it logs changes and ships them to replicas.

The ordered record of changes — logical operations or physical page changes — that replicas replay.

A mode where the primary acknowledges a write only after at least one replica has confirmed it.
Asynchronous replication
A mode where the primary acknowledges the write immediately and replicas catch up afterwards.

The delay between a change committing on the primary and becoming visible on a replica.

A guarantee that a user who just wrote can immediately read their own change, usually by routing that user's reads to the primary briefly.

Promoting a replica to primary after the original primary fails, then redirecting writes.

A failure state where two nodes both believe they are the authoritative writer and diverge.

An architecture where more than one node accepts writes and changes are exchanged between them, requiring conflict resolution.

01The problem: one database server

A single database is simple until it becomes the critical dependency for everything else. At that point its failure and its capacity both become the system's limits.

  • If the only database server fails, the application loses access to all of its data.
  • As traffic grows, one machine must absorb every read and every write.
  • Read-heavy products exhaust the database long before the application tier is stressed.
  • Users in distant regions pay round-trip latency on every query.
  • Adding copies of the data addresses availability, read capacity, and geography at once.
  • The copies must be kept in sync, and that synchronization is where the real complexity lives.

02What replication is

  • Replication means keeping copies of the same data on multiple database servers.
  • A write is applied on one server and then propagated so other servers update their copies.
  • All replicas hold the whole dataset, which is what separates replication from sharding.
  • Replication is continuous, not a periodic export: changes stream as they happen.
  • The application usually does not see replicas as different databases; routing decides which copy serves a query.
  • The core question is always how far behind a replica is allowed to be.

03Primary and replica architecture

  • One node is the primary (leader) and accepts all writes: inserts, updates, deletes.
  • The primary records each change and streams it to the replicas.
  • Replicas apply the same changes in order to their own copies.
  • Reads can go to the primary, but are often distributed across replicas.
  • Offloading reads lets the primary spend its resources on writes and its log.
  • The primary is still a single write bottleneck and a single point of failure until failover happens.
Client sends a write to the primary→Primary validates and appends the change to its log→Change is streamed to each replica→Replica applies the change to its copy→Replica reports its progress back to the primary

04How replication works

Replication transmits changes rather than recopying the database for every update. What counts as a change differs by system.

  • Statement-based: the SQL statement is shipped and re-executed; compact but fragile with nondeterministic functions.
  • Logical / row-based: row-level before-and-after images are shipped; safer, larger, and readable by other systems.
  • Physical: low-level storage or WAL block changes are shipped; fastest to apply, tightly coupled to the engine version.
  • Replicas must apply changes in commit order, or they will observe states the primary never had.
  • A replica usually persists how far it has consumed, so it can resume after a restart.
  • The log is also what makes point-in-time recovery and change data capture possible.
The mechanism decides what a replica can be used for. Logical replication can feed a different schema or a warehouse; physical replication can only feed the same engine.

05Why use replication

  • Availability: if one server dies, another copy of the data still exists and can be promoted.
  • Read scalability: read traffic spreads over several machines instead of one.
  • Geographic latency: a replica in each region lets users read from a nearby database.
  • Maintenance windows: a replica can serve traffic while the primary is upgraded or rebuilt.
  • Analytics isolation: heavy reporting can run on a replica instead of competing with production writes.
  • Replication does not increase write capacity; all writes still pass through one primary in a single-primary design.

06Synchronous replication

  • The primary writes locally, sends the change to one or more replicas, and waits for confirmation.
  • Only after the required replica acknowledges does the client get a success response.
  • Durability is stronger: if the primary dies immediately after the ack, the change already exists elsewhere.
  • Write latency now includes a network round trip to the replica.
  • If the required replica is slow or unreachable, writes stall or fail even though the primary is healthy.
  • A common compromise is quorum sync: wait for any one of several replicas, not for all of them.

07Asynchronous replication

  • The primary stores the write locally and acknowledges the client immediately.
  • Replicas receive and apply the change shortly afterwards.
  • Write latency stays low because the client never waits for another machine.
  • If the primary fails after acknowledging but before shipping, the latest writes are lost.
  • A promoted replica may be missing the most recent transactions.
  • This is the default for most cross-region and read-scaling setups because the latency cost of sync is too high.

08Replication lag

  • Lag is the gap between the primary's latest commit and what a replica has applied.
  • It is normally small but grows during write bursts, network trouble, or a slow replica.
  • A lagging replica is not corrupt; it is simply behind.
  • Reads routed to it can return stale rows that the user already changed.
  • Lag also delays failover: promoting a lagging replica loses recent writes.
  • Monitor lag in seconds and bytes, and alert on sustained growth rather than a single spike.
Lag is a property of asynchronous designs. It cannot be eliminated, only bounded and hidden where it matters.

09Read-after-write consistency

Lag becomes a user-visible bug: the app confirms a username change, the page refreshes, and the old name reappears from a replica that has not caught up.

  • Route a user's reads to the primary for a short window after that user writes.
  • Or track replication position per session and only use replicas that have caught up to the write's log position.
  • Or read the just-written record from the primary and the rest from replicas.
  • Sticky routing to the primary is the simplest fix but adds primary read load.
  • The goal is narrow: this user must see their own write, not global consistency.
  • Monotonic reads matter too: a user should not move backwards to an older replica on the next request.

10Read replicas in practice

  • Read replicas are the standard way to scale a read-heavy workload with a modest write rate.
  • All writes still go to the primary; reads are spread across replicas by the app, a proxy, or a driver.
  • Adding replicas multiplies read capacity roughly linearly until the primary's log shipping saturates.
  • Each replica is another thing to monitor: lag, disk, connections, and replication errors.
  • Replicas are also useful for failover candidates, backups, and heavy analytical queries.
  • Replicas do not help write-bound systems; that requires partitioning, batching, or sharding.

11Failover and split brain

  • Failover promotes a replica to primary and redirects writes to it.
  • Automated failover must detect the failure, choose the most up-to-date replica, promote it, and repoint clients.
  • Detection is the hard part: a slow primary and a dead primary look similar from outside.
  • Promoting the wrong replica silently discards the writes it never received.
  • Split brain happens when the old primary is alive but unreachable and a replica promotes itself, so two nodes accept writes.
  • The two histories then diverge and reconciling them is painful or impossible.
  • Quorums, leader election, fencing tokens, and STONITH-style isolation keep only one writer authoritative.
Monitor detects primary unavailability→Elect a replica with the highest applied log position→Fence the old primary so it cannot accept writes→Promote the new primary→Redirect clients and rebuild the remaining replicas

12Multi-primary replication

  • Multi-primary (multi-leader) allows more than one node to accept writes.
  • A common layout is one writable database per region, each serving local users.
  • Local writes cut cross-region latency dramatically.
  • Concurrent updates to the same record in two regions create a conflict that must be resolved.
  • Resolution options include last-write-wins, version vectors, application merge logic, or per-record ownership.
  • Last-write-wins is easy but silently discards one user's write.
  • This design is significantly more complex than single-primary and should be justified by a real latency need.

13Replication is not backup, and not sharding

  • A replicated DROP TABLE or bad update propagates to every replica within seconds.
  • Replication protects against server failure; backups protect against losing a previous version.
  • Production systems generally need both, plus point-in-time recovery.
  • Replication copies all data to each node; sharding gives each node a slice.
  • Replication buys availability and read scale; sharding buys storage and write scale.
  • Large systems combine them: each shard has its own replicas.
  • Use replication when availability, read throughput, or regional latency is the problem — not when writes are the bottleneck.

↔Trade-offs to say out loud

  • Synchronous replication strengthens durability and eases failover, but raises write latency and lets a slow replica block commits.
  • Asynchronous replication keeps writes fast and survives replica outages, but can lose recent commits and exposes stale reads.
  • Adding read replicas multiplies read throughput, but adds lag-sensitive read paths, monitoring, and cost.
  • Automatic failover shortens outages, but risks split brain and premature promotion without fencing.
  • Multi-primary reduces regional write latency, but forces conflict detection and merge logic into the design.
  • Read-after-write routing fixes the user-visible staleness bug, but shifts read load back onto the primary.
  • Geographic replicas cut read latency for distant users, but cross-region replication lag is larger and harder to bound.
  • Replication itself improves availability, but it duplicates mistakes as faithfully as it duplicates good data, so backups remain mandatory.

?Interview questions

Answer aloud before opening the outline.

1. What is database replication?

Keeping copies of the same data on multiple database servers and continuously propagating changes between them. One node usually accepts writes and streams its change log to replicas, which replay it. Replication improves availability, read capacity, and regional latency.

2. Walk through what happens on a write in a primary-replica setup.

The client sends the write to the primary, which validates it and appends it to its replication log. The change is streamed to each replica, which applies it in commit order. In synchronous mode the primary waits for an acknowledgement; in asynchronous mode it replies immediately.

3. Synchronous vs asynchronous replication — how do you choose?

Use synchronous when losing the last few writes is unacceptable and replicas are close enough that the round trip is cheap. Use asynchronous when write latency matters more or replicas are far away, and accept that a failover may lose recent commits. Many systems use quorum sync for critical writes and async for read replicas.

4. What is replication lag and why does it matter?

It is the delay between a commit on the primary and its visibility on a replica. During that window, reads from the replica return old data, which can look like a failed update to the user. Lag also determines how much data a promoted replica is missing during failover.

5. How do you implement read-after-write consistency?

After a user writes, route that user's reads to the primary for a short period, or track the write's log position and only read from replicas that have reached it. A narrower variant reads just the modified record from the primary. The goal is per-user, not global, consistency.

6. What is split brain and how do you prevent it?

It is when a partition or detection failure leaves two nodes both acting as primary, so writes diverge. Prevention requires making sure only one node can be authoritative: quorum-based election, fencing tokens that invalidate the old primary, and isolating or shutting down the old leader before promoting a new one.

7. What makes failover hard?

You must distinguish a dead primary from a slow or partitioned one, pick the replica with the most recent data, and stop the old primary from accepting writes. Each step can go wrong: promoting a lagging replica loses writes, and skipping fencing causes split brain. Clients and connection pools also need to be redirected.

8. When is multi-primary replication worth it?

When users are spread across regions and cross-region write latency is a real product problem. The cost is conflict handling: two regions may update the same record concurrently, and the system needs detection plus a resolution rule. If writes can be routed to one region, single-primary is much simpler.

9. Why is replication not a backup?

Replication copies every change, including mistakes. An accidental table drop, a bad migration, or corrupted data reaches all replicas within seconds. Backups preserve a previous point-in-time version, which is what you restore from after logical damage.

10. How is replication different from sharding?

Replication puts all the data on every node, which helps availability and read throughput. Sharding puts a slice on each node, which helps storage size and write throughput. They are complementary: a common design shards the dataset and replicates each shard.

11. Do read replicas increase write capacity?

No. All writes still pass through the primary in a single-primary design, and every replica adds log-shipping work to it. Write-bound systems need batching, partitioning, or sharding. Replicas only scale reads and improve availability.

12. How would you detect and handle a lagging replica?

Track lag in seconds and in bytes behind the primary's log, and alert when it grows steadily rather than on a single spike. Temporarily remove the replica from the read pool if lag exceeds a threshold, and investigate causes such as long transactions, insufficient I/O, or network issues. A replica that keeps falling behind should be rebuilt rather than trusted.

!Traps

  • Treating replicas as backups and having no point-in-time restore path.
  • Assuming all replicas are consistent and sending read-after-write traffic to any of them.
  • Enabling synchronous replication to a distant region and then wondering why writes are slow.
  • Promoting a replica without fencing the old primary, then hitting split brain.
  • Adding replicas to fix a write-bound database.
  • Forgetting that a failover loses any writes the promoted replica never received.
  • Ignoring replica health until the day failover needs the most up-to-date copy.
