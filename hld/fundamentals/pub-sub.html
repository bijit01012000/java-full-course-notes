Topic
A named channel for one kind of event, such as OrderPlaced or PaymentCompleted.
Subscription
The link between one subscriber and a topic; it tracks that subscriber's own progress through the stream.
Fan-out
Delivering one published message to every subscription on the topic, which is the defining behavior of pub/sub.
Consumer group
A set of workers that share one subscription's work; every group sees every event, but each event goes to only one worker inside a group.
Offset
A consumer group's recorded position in a partitioned log, which can be advanced or rewound.
Consumer lag
How far a consumer group is behind the latest message in its partitions; a rising lag means processing cannot keep up.
Ephemeral pub/sub
A model that delivers only to subscribers connected at publish time, with no backlog and no replay.
Replay
Reprocessing previously delivered events by rewinding a consumer's position in a retained log.
Transactional outbox
Writing the business row and the event row in one database transaction, then publishing from the outbox so the two cannot diverge.
Idempotent consumer
A subscriber that can safely process the same event twice without changing the outcome.

01The coupling problem

When an order is placed, inventory, email, analytics, and fraud all need to react. Calling each one directly from the order service works only while the list is short and everyone is healthy.

  • The order service must know every downstream service and be redeployed whenever a new team wants to react to orders.
  • A slow email provider lengthens the customer's checkout request even though email has nothing to do with placing the order.
  • If analytics is down, the order service must invent a policy: fail the order, retry, buffer, or silently drop the event.
  • Direct calls create a chain of synchronous dependencies, so one degraded service can stall or fail the whole flow.
  • What the order service actually wants to say is "an order was placed" — not "run these four RPCs in this order".
  • Publishing that fact to a broker inverts the dependency: the producer announces, and consumers decide what to do.

02The core model

  • Publishers produce messages; subscribers consume them; a broker sits between and organizes messages into topics.
  • A publisher sends to a topic and does not know which services subscribe, how many there are, or where they run.
  • A subscriber registers interest in a topic, and the broker delivers a copy of every message on that topic to each subscription.
  • One OrderPlaced publish becomes four independent deliveries to inventory, email, analytics, and fraud.
  • A new recommendation service can subscribe next month with no change and no redeploy of the order service.
  • The broker owns delivery state — which subscribers have acknowledged what — so producers and consumers never coordinate directly.

03Pub/sub versus message queues

  • In a queue, each message is handled by one consumer from a pool; the purpose is to spread work.
  • In pub/sub, each message is delivered to every subscriber; the purpose is to broadcast a fact.
  • The producer's intent differs: a queue message says "someone should do this task"; an event says "this thing happened".
  • A queue scales throughput by adding workers; pub/sub scales reach by adding subscriptions.
  • The rule of thumb: use a queue when exactly one worker should do the job, and pub/sub when several services may care.
  • Pub/sub also tolerates a subscriber being down, because a durable subscription holds its copy until it catches up.

04The life of a message

  • Publish and store: the broker writes the message durably — often to disk and to replicas — before acknowledging the publish.
  • The publish acknowledgment tells the producer the message is safe, so it can stop retrying.
  • Fan-out: the broker makes the message available to every subscription on the topic, not to every process.
  • Process and acknowledge: each subscriber handles its copy and acks; an unacked message is redelivered later.
  • Each subscription tracks its own progress, so a lagging analytics service does not slow down email delivery.
  • That independence is the main operational benefit: one slow consumer creates its own backlog instead of imposing backpressure on the producer.
Publisher sends OrderPlaced to the orders topic→Broker stores the message durably and acknowledges the publish→Broker fans out one copy to each subscription→Each subscriber processes its copy at its own pace→Subscriber acknowledges; the broker records its progress

05Fan-out and combining pub/sub with queues

  • Fan-out at the topic gives every subscriber an independent copy, so one consumer's failure or slowness does not affect the others.
  • A subscription can also represent a group of workers, in which case the group shares the work rather than each worker getting a copy.
  • A common production shape is a topic feeding one queue per service (for example SNS to SQS): the topic handles fan-out, and each queue buffers work for its owner.
  • Per-service queues add retry policies, dead-letter queues, and buffering that a bare push subscription does not provide.
  • Fan-out multiplies storage and network cost: N subscriptions mean N copies delivered, even if some subscribers do nothing useful with them.
  • Every new subscription also multiplies the blast radius of a bad event, because more consumers will process the same poison message.
  • Filtering at the broker can scope a subscription to a subset of events, which is cheaper than fanning out everything and discarding most of it.

06Push versus pull delivery

  • Push: the broker sends messages to an endpoint the subscriber exposes, usually over HTTP.
  • Push is simple — no polling loop — but the broker sets the pace, so it must detect a slow or failing subscriber and back off.
  • A push endpoint must stay reachable; a serverless function or a public webhook fits, a private batch job usually does not.
  • Pull: the subscriber asks for the next batch when it is ready, so it controls rate, batch size, and concurrency.
  • Pull handles bursts better and enables efficient batching, but requires long-running polling workers.
  • Pull is usually the better fit for high-throughput backend processing; push fits simple integrations and event-driven functions.

07Ephemeral, durable, and replayable pub/sub

  • Ephemeral brokers such as Redis Pub/Sub forward a message to whoever is connected right now, then forget it.
  • A subscriber disconnected for a few seconds misses everything published in that window; there is no backlog and no replay.
  • Ephemeral is right for live cursor positions, typing indicators, and presence, where only the latest state matters.
  • Durable systems keep a message until each subscription acknowledges it or a retention period expires.
  • A durable subscription lets a service be down for maintenance and still receive its events when it returns.
  • Replayable logs such as Kafka retain messages for a configured time whether or not anyone read them, and each consumer group tracks an offset.
  • Rewinding an offset replays history: useful for reprocessing after a bug fix or for a new service building state from past events.
  • Replay is not free — it re-runs side effects, so consumers must be idempotent and downstream systems must tolerate duplicates.

08Delivery guarantees, duplicates, and idempotency

  • Most practical systems give at-least-once delivery: a message is never silently lost, but it may arrive more than once.
  • Duplicates arise when a subscriber processes a message and crashes before acknowledging it, or when the broker retries an unconfirmed delivery.
  • Replay and outbox relays add more duplicate sources, so duplicates are a normal operating condition, not an edge case.
  • Make consumers idempotent: record processed event IDs, or write with an upsert keyed by event ID so a repeat is a no-op.
  • Business operations should be expressed as idempotent state changes ("set status to shipped") rather than increments ("add one shipment").
  • Exactly-once is usually a bounded claim — exactly-once within one broker and one transactional consumer — not across arbitrary external systems.
  • Pair at-least-once delivery with a dead-letter queue so a message that always fails stops blocking the subscription.

09Message ordering

  • Pub/sub generally does not guarantee order across an entire topic, because messages are spread over partitions and retries can reorder them.
  • A subscriber can therefore see OrderCancelled before the OrderCreated that logically preceded it.
  • The practical guarantee is ordering per key: all messages with the same key (for example an order ID) go to one partition and are consumed in order.
  • Different keys still process in parallel, which is how ordering coexists with throughput.
  • Ordering costs parallelism: a hot key funnels all its traffic through one partition and one consumer, and adding consumers does not help.
  • Choose the ordering key from what the business actually requires, not from the primary key of convenience.
  • When order can still break, carry a version number and drop events older than the latest version already applied.
  • Design consumers to be tolerant anyway: an out-of-order event should be parked or reconciled, not allowed to corrupt state.

10Scaling subscribers

  • Scale a slow subscription by adding workers to its consumer group, so the group's partitions are shared across more processes.
  • Every group still receives every event; within a group, each event is handled by exactly one worker.
  • In Kafka, a partition is assigned to only one consumer in a group at a time, so the partition count caps parallelism — extra consumers sit idle.
  • Plan partition count for future throughput, because increasing it later changes key-to-partition mapping and can break per-key ordering.
  • Watch consumer lag per partition; a steadily rising lag is the earliest signal that consumers cannot keep up.
  • Lag can also grow because of a slow downstream dependency, so check whether adding workers would just add pressure to a saturated database.
  • Rebalancing when consumers join or leave briefly pauses partition assignment, which can cause latency spikes during autoscaling.

11Publishing reliably: the outbox pattern

There is a failure mode on the producer side that no amount of broker durability fixes.

  • If the order service commits the order and then crashes before publishing, the order exists but no other service ever hears about it.
  • If it publishes first and the database write then fails, subscribers act on an order that does not exist.
  • This is the dual-write problem: two systems are updated without a transaction that covers both.
  • The transactional outbox writes the business row and an event row to the same database in one transaction, so both or neither persist.
  • A relay process reads new outbox rows and publishes them, resuming safely after a crash.
  • The relay can publish the same event twice if it crashes after publishing but before marking the row sent, so consumers still need idempotency.
  • Change data capture tools can read the database log instead of polling the outbox table, reducing latency and polling load.

12Designing events and evolving schemas

  • Name events for facts in the past tense — OrderPlaced, not SendEmail — so the publisher does not encode another team's behavior.
  • Include an event ID for deduplication, an event type, a timestamp, a schema version, and the payload.
  • A command-style event forces the publisher to know consumers, which recreates the coupling pub/sub was meant to remove.
  • Add new optional fields rather than renaming or removing existing ones; unknown fields should be ignored by consumers.
  • A schema registry with Avro or Protobuf can reject incompatible changes before they are deployed.
  • Organize topics by domain (orders.events, payments.events) instead of creating one topic per tiny variation.
  • Use attribute filtering so a subscription receives only the events it cares about instead of parsing and discarding most of them.
  • Keep payloads small: publish an ID and a reference to large objects rather than embedding megabytes in the event.

13When to use pub/sub — and what it costs

  • Good fits: order and payment events, user activity tracking, notifications, cache invalidation across servers, and real-time fan-out to WebSocket servers.
  • It is also the right shape when teams must evolve independently or when a spike must not overwhelm downstream services.
  • It is a poor fit when the caller needs an immediate answer, such as checking whether a payment was approved before rendering the next page.
  • The system becomes eventually consistent: different services are updated at different times, and the UI must reflect that.
  • Debugging gets harder because one user action becomes a chain of events across services; distributed tracing becomes mandatory.
  • Operating a broker adds a critical dependency, retention storage, schema governance, and monitoring for lag and dead letters.
  • Every subscriber must be designed for duplicates, retries, and replay — that is the price of decoupling.

↔Trade-offs to say out loud

  • Decoupling lets new subscribers join without touching the publisher, but the publisher loses visibility into who consumes its events and how they behave.
  • Asynchronous fan-out absorbs spikes and isolates failures, but the system becomes eventually consistent and harder to reason about end to end.
  • Durable subscriptions survive subscriber downtime, but require retention storage, replay discipline, and idempotent consumers.
  • Ephemeral pub/sub is cheap and low-latency, but any disconnected subscriber loses messages permanently.
  • Per-key ordering makes related events safe to process, but concentrates a hot key onto one partition and limits parallelism.
  • Push delivery removes polling and suits serverless, but hands rate control to the broker and requires a reachable endpoint.
  • Pull delivery gives the consumer control over rate and batching, but needs always-on workers and careful lag monitoring.
  • Replay enables reprocessing and state rebuilds, but re-runs side effects and can double-charge or double-notify without idempotency.
  • The transactional outbox removes the dual-write gap, but adds a table, a relay, and duplicate publishes that consumers must tolerate.

?Interview questions

Answer aloud before opening the outline.

1. What is pub/sub in one sentence?

A messaging pattern where publishers send events to a topic and a broker delivers a copy to every subscription, so producers do not know or care which services consume them.

2. How is pub/sub different from a message queue?

A queue delivers each message to exactly one worker to spread work. Pub/sub delivers each message to every subscriber to broadcast a fact. In practice many systems combine them: a topic fans out into one queue per service.

3. What is fan-out and what does it cost?

Fan-out is delivering one published message to every subscription. It gives independent progress and failure isolation, but multiplies delivery, storage, and compute cost, and sends the same bad event to every consumer.

4. Why must subscribers be idempotent?

Because delivery is usually at-least-once. A consumer can crash after doing the work but before acking, the broker redelivers, and the work runs twice. Replays and outbox relays create more duplicates. Deduplicate by event ID or make writes naturally idempotent.

5. Push versus pull delivery — how do you choose?

Push is simpler and fits serverless or webhook-style integrations, but the broker controls the pace and the endpoint must be reachable. Pull lets the consumer control rate and batching, which suits high-throughput backend workers that can poll continuously.

6. What happens to messages when a subscriber is offline?

In an ephemeral system they are lost. In a durable system the broker retains each subscription's copy until it is acked or retention expires, so the subscriber catches up later. In a replayable log, the group's offset determines where it resumes.

7. How does Kafka replay work?

Kafka keeps an append-only log for a retention period and each consumer group stores an offset. Rewinding the offset re-reads older records, which is useful after a bug fix or for bootstrapping a new service. Replay re-executes side effects, so consumers must tolerate duplicates.

8. Does pub/sub guarantee ordering?

Not across a whole topic. Partitioning and retries reorder messages. Most systems guarantee order per key by routing all messages with that key to the same partition. That preserves order for one entity while different entities process in parallel.

9. What is the cost of per-key ordering?

Reduced parallelism. All messages for a key go through one partition and one consumer, so a hot key becomes a bottleneck that more consumers cannot fix. Partition count also caps the number of consumers in a group.

10. How do you scale a slow subscriber?

Add workers to its consumer group, up to the partition count, and check that the bottleneck is not a shared downstream dependency. Watch consumer lag per partition to see whether scaling is actually helping.

11. What is consumer lag?

The distance between a consumer group's committed offset and the latest message in each partition. Rising lag means arrival outpaces processing; it is the primary health metric for a subscription.

12. What is the dual-write problem and how does the outbox fix it?

Updating the database and publishing an event are two systems with no shared transaction, so one can succeed while the other fails. The outbox writes the business row and the event row in one local transaction, then a relay publishes from the outbox. The relay may publish twice, so consumers deduplicate.

13. How should an event be designed?

As a past-tense fact such as OrderPlaced, with an event ID, type, timestamp, schema version, and payload. It should describe what happened, not instruct a specific consumer. Schemas evolve by adding optional fields, ideally enforced by a schema registry.

14. When would you not use pub/sub?

When the caller needs an immediate answer, such as validating a password or confirming a payment before continuing. A direct synchronous call is simpler and easier to reason about. Pub/sub also adds broker operations and eventual consistency that a small system may not need.

!Traps

  • Treating pub/sub as a work queue and expecting each message to be processed by only one consumer.
  • Assuming messages arrive exactly once, then double-charging or double-notifying on redelivery or replay.
  • Promising global ordering across a topic when only per-key ordering exists.
  • Publishing the event inside the same request as the database write without an outbox, then losing events on a crash.
  • Using a hot ordering key and wondering why adding consumers does not increase throughput.
  • Forgetting that partition count caps consumer-group parallelism and that changing it later can break key ordering.
  • Publishing command-style events such as SendEmail, recreating the coupling the broker was meant to remove.
  • Ignoring consumer lag until the backlog is hours deep and the retention window is about to drop events.
