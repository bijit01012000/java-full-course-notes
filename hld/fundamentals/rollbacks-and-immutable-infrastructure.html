A model where servers and containers are never modified after creation; changes produce a new versioned artifact that replaces the old one.
Golden image
A prebuilt, versioned machine or container image containing the application and its dependencies, used to launch identical instances.
Configuration drift

Artifact retention
Keeping previous build artifacts available so a rollback can redeploy exactly what ran before.

Restoring the previous known-good version, configuration, and data compatibility after a failed release.
Roll forward
Fixing the defect with a new release instead of reverting, which is faster when a rollback is unsafe but requires a working fix path.

The recorded link between a running instance and the commit, artifact digest, and configuration that produced it.

01Rollback is a capability, not a command

When production breaks, reverting is only easy if the last good version still exists and can be deployed quickly.

  • A rollback command that rebuilds from source is not a rollback; it is a new release under pressure.
  • If the previous artifact was overwritten or deleted, the previous version is gone even though the code is in git.
  • If servers are patched in place, there is no clean previous state to return to.
  • Rollback capability must be designed and rehearsed before an incident, not discovered during one.
  • The measure that matters is time from decision to serving the old version, not the elegance of the process.
  • Every additional manual step in the recovery path is a step that can fail at the worst moment.

02Mutable infrastructure and drift

  • In a mutable model, servers are provisioned once and then patched, reconfigured, and hot-fixed over time.
  • Each server accumulates a unique history, so no two are truly identical even if they started the same.
  • Drift makes environments unreproducible: a problem cannot be recreated because the failing state cannot be rebuilt.
  • Rolling back means reversing a sequence of undocumented changes, which is usually impossible.
  • Snowflake servers become unremovable because nobody knows what depends on their accumulated state.
  • The failure mode is gradual: drift is invisible until a deploy or an autoscaling event exposes it.

03Immutable infrastructure

  • Servers and containers are created from a versioned image and are never modified after launch.
  • A change produces a new image version, which replaces the old instances rather than patching them.
  • Every running instance is traceable to an image digest, which is traceable to a commit and build.
  • Replacing instead of patching means the previous image is still a valid, deployable artifact.
  • Reproducibility improves: the same image produces the same environment anywhere.
  • Rollback becomes a redeploy of a known image, which uses the same tested path as a normal deploy.
Build image from commit→Test the image→Publish immutable version→Launch new instances→Shift traffic→Keep the old image available

04Bake versus fry

  • Baking puts dependencies, runtime, and configuration into the image at build time; startup is fast and deterministic.
  • Frying injects configuration at boot from a config service or environment variables; the same image runs everywhere.
  • Baking improves immutability but requires a rebuild for every configuration change.
  • Frying improves flexibility but reintroduces runtime variation and can hide environment-specific failures until launch.
  • A common compromise bakes the application and runtime, and fries only environment-specific settings and secrets.
  • Whatever the split, the boundary must be explicit, or the same image behaves differently in two places.

05Making the previous version deployable

  • Retain a bounded history of artifacts, at least enough to cover the rollback window you promise.
  • Tag artifacts by commit or digest, never by a mutable label, so the previous version is unambiguous.
  • Keep the previous version's configuration available too; an old binary with new configuration can fail identically.
  • Verify that the old artifact still starts in the current environment before you need it.
  • Record which version is deployed where, so recovery does not begin with an inventory exercise.
  • Expire old artifacts deliberately with a policy, not accidentally by overwriting a tag.

06Layers of rollback

  • Feature flag: turn off the behavior in seconds without touching infrastructure; fastest and least invasive.
  • Traffic switch: move users back to the previous environment, as in blue-green.
  • Redeploy: launch the previous artifact through the normal pipeline; slower but works for any code defect.
  • Configuration revert: restore the previous settings when the release itself was fine.
  • Data restore: the last resort, because it loses writes made after the snapshot.
  • Use the cheapest layer that actually removes the harm; escalating to a redeploy for a flag-gated bug wastes the outage window.

07Rollback is not only code

  • Schema changes may be irreversible, so the old code cannot simply be redeployed.
  • Data written in a new format can be unreadable by the previous version.
  • Messages already published to queues will be consumed by whichever version is running.
  • External side effects such as emails, payments, or third-party calls cannot be undone by a deployment.
  • Cache entries written by the new version may persist after the rollback.
  • This is why backward-compatible migrations and idempotent effects are prerequisites for a credible rollback story.

08Triggers: manual versus automated

  • Manual rollback depends on someone noticing, deciding, and acting, which is slow at night and under stress.
  • Automated triggers compare error rate, latency, and saturation against thresholds and revert without waiting.
  • Automated triggers need debouncing, or normal variance produces repeated deploy-revert flapping.
  • Thresholds should be tied to user-facing objectives rather than raw infrastructure counters.
  • Keep a manual override for cases automation cannot judge, such as a business metric anomaly.
  • Every automated rollback should produce a notification and a record of the metrics that triggered it.

09Rollback versus roll forward

  • Roll back when the previous version is known good, still deployable, and data-compatible.
  • Roll forward when the rollback is unsafe, for example after an irreversible migration.
  • Roll forward requires a ready fix and a fast pipeline, which may not exist at that moment.
  • Rolling forward under incident pressure risks compounding the original defect with a rushed fix.
  • Decide the default policy before the incident, and define which conditions force the other path.
  • If the fix is small and the rollback is expensive, roll forward; if the rollback is cheap, revert first and fix calmly.

10Rehearsing recovery

  • Practice rollbacks in production-like environments during normal operations, not during incidents.
  • Measure the actual time from trigger to healthy, and fix the steps that dominate it.
  • Test the oldest artifact you promise to support, not just the most recent one.
  • Simulate a failed release end to end: alert, decision, revert, verification, and communication.
  • Include the database in the rehearsal, because data-related rollbacks are the ones that surprise teams.
  • Record findings as pipeline or infrastructure fixes so the next rehearsal is faster.

11Failure modes

  • Missing artifact: the previous image was overwritten or garbage-collected, so there is nothing to redeploy.
  • Config mismatch: old code starts with new configuration and fails in a novel way.
  • Irreversible migration: the schema moved forward and the old code cannot run.
  • Rollback storm: automation flips between versions repeatedly on a noisy metric.
  • Partial rollback: some instances revert while others stay on the new version, creating a mixed state nobody designed.
  • Untested path: the rollback procedure references a script or permission that no longer exists.

12Adopting immutable infrastructure

  • Start by moving application deployment to versioned images, even if some infrastructure remains mutable.
  • Define the build once, promote everywhere rule so the artifact tested is the artifact deployed.
  • Remove SSH-based patching from the normal path; if a change is needed, build a new image.
  • Automate instance replacement with a rollout strategy so replacement is routine rather than exceptional.
  • Keep configuration and secrets outside the image but version them, so a config revert is also auditable.
  • Immutable infrastructure is a prerequisite for reliable rollback, not an end in itself.

↔Trade-offs to say out loud

  • Immutable infrastructure makes rollback and reproducibility reliable but requires image build, registry, and replacement automation.
  • Baking configuration improves determinism but makes every configuration change a full rebuild.
  • Frying configuration speeds changes but reintroduces runtime variation and environment-specific surprises.
  • Long artifact retention keeps rollback possible but costs storage and invites deploying long-obsolete versions.
  • Automated rollback shortens outages but can flap on noisy thresholds and hide the underlying defect.
  • Rolling forward avoids an unsafe revert but requires a working fix path under incident pressure.
  • Frequent rehearsals keep the recovery path real but consume engineering time that could ship features.
  • Aggressive garbage collection saves registry cost but can delete the exact artifact needed during an incident.

?Interview questions

Answer aloud before opening the outline.

1. What makes a rollback actually work?

The previous version must still exist as a deployable artifact, its configuration must still be available, the data layer must remain compatible, and the redeploy must use a path that has been exercised. If any of those is missing, the rollback is a rebuild or a restore, not a revert.

2. What is immutable infrastructure?

A model where instances are never modified after launch. Any change produces a new versioned image, and instances are replaced rather than patched. The benefit is that every running instance is reproducible and traceable, and the previous version remains a valid deployable artifact.

3. Why is mutable infrastructure bad for rollback?

Because each server accumulates an undocumented history of patches, so no clean previous state exists. Reverting means reversing a sequence nobody recorded. Drift also makes failures unreproducible, since the failing environment cannot be rebuilt.

4. What is configuration drift?

The gradual divergence of running servers from their intended state, caused by manual patches, ad-hoc config edits, and inconsistent provisioning. It is invisible until a deploy or scaling event exposes it, and it is the main reason environments stop matching.

5. Bake versus fry: what is the trade-off?

Baking puts configuration in the image, so startup is deterministic but every change needs a rebuild. Frying injects configuration at boot, so changes are fast but the same image can behave differently per environment. Many teams bake the runtime and fry only environment-specific settings and secrets.

6. What are the layers of rollback?

From cheapest to most expensive: disable a feature flag, switch traffic back to the previous environment, redeploy the previous artifact, revert configuration, and finally restore data from a backup. You should use the least invasive layer that removes the harm.

7. Why can a code rollback still fail after a database migration?

Because the schema may have moved forward irreversibly, or the new version may have written data in a format the old code cannot read. Redeploying old code against a changed schema produces errors that look unrelated to the original bug. This is why migrations must be backward compatible.

8. When would you roll forward instead of back?

When the rollback is unsafe or impossible, such as after an irreversible migration, or when the fix is small and the pipeline is fast. Roll forward is riskier under pressure, so the default policy should be decided in advance and documented.

9. What signals should trigger an automatic rollback?

User-facing objectives such as error rate, latency percentiles, and saturation crossing agreed thresholds for a sustained period. Triggers need debouncing to avoid flapping, and they should record the metrics that fired so the decision can be reviewed afterwards.

10. How do you keep rollback fast as the system grows?

Retain immutable artifacts, automate the redeploy through the same pipeline as a normal deploy, keep the previous environment warm where possible, and practice. Every manual step and every missing artifact adds minutes exactly when they matter most.

11. What is the relationship between immutable infrastructure and deployment strategies?

Immutable images make rolling, blue-green, and canary practical, because each version is a complete replaceable unit. Without them, strategies degrade into patching live servers, which has no clean rollback point. Immutability supplies the unit of deployment that strategies assume.

12. How would you rehearse a rollback?

Run a game day that deploys a deliberately faulty version, lets monitoring detect it, triggers the rollback, and times recovery to healthy. Include the database and the communication steps. Record where time was lost and fix the pipeline rather than adding documentation.

!Traps

  • Overwriting a mutable image tag so the previous version no longer exists to redeploy.
  • Promising fast rollback while running only one environment and no retained artifacts.
  • Redeploying old code against a schema that was already migrated forward.
  • Forgetting that configuration and secrets also need a previous version.
  • Letting a rollback trigger flap between two versions on a noisy metric.
  • Patching servers over SSH and calling the fleet reproducible.
  • Assuming automation covers the whole revert when a manual approval or manual step remains in the path.
