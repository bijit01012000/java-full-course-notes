01The problem with one central server

In a client-server system, every client depends on the same central servers for bandwidth, storage, and compute. For some workloads, that point becomes the limit.

  • Distributing a large file to many users means the server's uplink is the ceiling, no matter how many clients want it.
  • Capacity must be provisioned for peak demand and paid for even when idle.
  • The central server is a single point of failure and a single point of censorship.
  • Every byte crosses the operator's infrastructure, which concentrates cost and legal exposure.
  • Adding clients adds load rather than capacity — the opposite of what a broadcast workload needs.
  • Replicating servers helps, but it is still a small set of well-known endpoints.

02What peer-to-peer architecture is

  • Participants, called peers, exchange resources directly with each other.
  • Each peer is both a client and a server: it downloads chunks and uploads chunks it already has.
  • Capacity grows with the number of participants, because every new peer brings bandwidth and storage.
  • There is no assumption of a reliable always-on node; peers join, leave, and fail constantly.
  • The network is defined by a protocol and an overlay topology, not by a fixed set of machines.
  • Trust is not assumed: data must be verifiable and peers may be selfish or malicious.
  • Most real systems are hybrids — a small central service for discovery, signalling, or indexing, with data flowing peer to peer.
Peer joins→Discovers other peers→Exchanges availability→Transfers chunks directly→Verifies and re-shares

03Pure, hybrid, structured, unstructured

  • Pure P2P: no central component at all; discovery and data transfer are fully peer driven.
  • Hybrid P2P: a central server handles discovery, indexing, or signalling, while data moves between peers.
  • Structured P2P: peers and keys are arranged by a deterministic rule such as a DHT, giving efficient lookup.
  • Unstructured P2P: peers connect arbitrarily and search by flooding or random walks, which is simple but less efficient.
  • Structured networks give predictable lookup but are fragile under churn and harder to build.
  • Unstructured networks tolerate churn well but can miss content that exists, or generate heavy query traffic.
  • BitTorrent is hybrid and partly structured; early Gnutella was unstructured; Kademlia is structured.

04Overlay networks and routing

  • The overlay is a logical graph on top of the physical internet; each edge is a connection between peers.
  • Routing means forwarding a request hop by hop toward a peer likely to hold the answer.
  • The overlay does not control the underlying network, so a logical neighbour can be far away in latency.
  • Topology choice trades lookup efficiency against resilience: more neighbours means more state but faster failure recovery.
  • Peers must maintain neighbour lists and detect dead connections, because the graph changes constantly.
  • Routing loops and stale entries are normal, so protocols need hop limits and fallbacks.
  • Good designs keep neighbour sets diverse to avoid partitioning when a well-connected peer disappears.

05Discovery: trackers, DHTs, and gossip

  • Before exchanging data, a peer must find others who have it — discovery is the first hard problem.
  • Trackers are simple and fast but centralize metadata and become a dependency and a failure point.
  • DHTs distribute the index across peers so no single node knows everything.
  • Gossip spreads membership and updates epidemically without any central directory.
  • Peer exchange lets connected peers share their own lists, reducing tracker dependence.
  • Many systems bootstrap from a small known list or a central service, then switch to distributed discovery.
  • Discovery metadata is often more sensitive than the data itself, because it reveals who is interested in what.

06DHT mechanics

  • Keys and peers are mapped into the same identifier space by hashing.
  • Each peer is responsible for the keys closest to its own identifier, forming a distributed index.
  • Kademlia uses XOR distance and keeps a routing table of peers at exponentially increasing distances.
  • A lookup converges in a number of hops that grows logarithmically with network size.
  • Each peer stores only a small routing table and a subset of keys, so state per node stays manageable.
  • Entries must be republished and replicated because peers leave and their keys would otherwise vanish.
  • DHTs give exact-match lookup, not search: you must know the key, which is why content hashes are used.
Hash the key→Compare with local ID→Forward to a closer peer→Repeat until responsible peer→Return value or peers

07Gossip and epidemic dissemination

  • Each peer periodically picks a small random set of neighbours and exchanges state with them.
  • Push sends updates outward; pull asks neighbours for updates; push-pull converges fastest.
  • Information spreads exponentially at first and converges in a logarithmic number of rounds.
  • Gossip is extremely resilient: no central node, no fixed topology, and lossy delivery still converges.
  • The cost is redundant messages, so fanout and interval must be tuned against bandwidth.
  • Anti-entropy runs periodically to repair peers that missed updates.
  • Gossip is used for membership, failure detection, and eventually consistent state, not for low-latency lookups.

08Churn

  • Peers join and leave at any time, often without warning, so availability is probabilistic.
  • Replication is the main defence: store each item on several peers so one departure is not fatal.
  • Replication factor and repair rate decide how much data survives steady churn.
  • Graceful departure lets a peer hand off its responsibilities before leaving; crashes do not.
  • Failure detection uses timeouts, heartbeats, and gossip suspicion rather than a central health check.
  • Data may need to be re-replicated when the number of live replicas falls below a threshold.
  • Frequent membership changes make strong consistency expensive; most P2P systems choose availability.
In P2P, a node being present is an assumption with an expiry time, not a fact.

09NAT traversal and connectivity

  • Most peers sit behind NATs and cannot accept inbound connections directly.
  • Hole punching has both peers attempt outbound connections simultaneously so each router creates a mapping.
  • STUN lets a peer discover its public address and port as seen from outside.
  • TURN relays traffic through a server when direct connection fails; reliable but costly and centralizing.
  • Symmetric NATs assign different external ports per destination, which often defeats hole punching.
  • A signalling service is needed to exchange candidates and coordinate attempts, even though data flows peer to peer.
  • Always design a relay fallback; connectivity is a spectrum, not a binary.

10Trust, identity, and attack surface

  • Peers are anonymous by default, so the protocol must assume some participants are adversarial.
  • Encrypt transfers so a relay or network observer cannot read content.
  • Content addressing lets the receiver verify that a chunk matches its hash, regardless of who sent it.
  • A Sybil attack creates many identities to dominate routing, storage, or voting; identity should be costly or bounded.
  • Eclipse attacks surround a victim with malicious peers and cut it off from honest ones; neighbour diversity helps.
  • Poisoning and free-riding are handled with verification and incentive schemes, not trust.
  • Reputation is local and easy togame, so it complements verification rather than replacing it.
  • Legal and abuse concerns are real: an open network can distribute content the operator cannot inspect or remove.

11Integrity, incentives, and fairness

  • Split content into chunks so transfers can be parallel, resumable, and verified independently.
  • A Merkle tree over chunks proves a single chunk belongs to the file without downloading everything.
  • BitTorrent-style tit-for-tat rewards peers that upload by giving them better download chances.
  • Free-riders consume capacity without contributing; without incentives, the network degrades to client-server.
  • Rarest-first chunk selection improves availability of scarce pieces across the swarm.
  • Choking algorithms limit the number of active uploads so each peer can manage its own bandwidth.
  • Incentives can be tokenized, but that adds economic and regulatory complexity and new attack surfaces.

12Where P2P fits

  • File distribution: large files or software updates served by the swarm rather than one origin.
  • Blockchain: peers replicate and validate a ledger without a central authority.
  • Content-addressed storage: networks that address data by hash and fetch it from any holder.
  • Real-time communication: WebRTC calls send media directly between participants after signalling.
  • Collaboration: local-first apps syncing changes peer to peer and reconciling later.
  • Edge and CDN assistance: nearby devices share cached content to reduce origin load.
  • Poor fit: authoritative ledgers with strict consistency, private data requiring access control, and workloads where peers cannot stay online.

13Trade-offs and when to use it

  • P2P removes the bandwidth bottleneck and the single point of failure, but replaces them with churn and unreliable peers.
  • Capacity grows with popularity, which is exactly when a central server struggles.
  • Discovery, NAT traversal, verification, and incentives are substantial engineering work.
  • Latency is unpredictable because peers are heterogeneous and topologically distant.
  • Observability is harder: there is no single place to see the whole system.
  • Regulatory and abuse handling become difficult when the operator cannot inspect traffic.
  • Use P2P when the workload is broadcast-heavy, content is verifiable, and peers can contribute resources; otherwise a CDN is simpler.

↔Trade-offs to say out loud

  • Scalable capacity grows with participants but depends on strangers contributing bandwidth and storage.
  • No central server removes a single point of failure but makes discovery, monitoring, and abuse handling much harder.
  • Structured DHTs give efficient exact-match lookup but are complex and need replication under churn.
  • Unstructured networks tolerate churn but waste query traffic and may not find existing content.
  • Replication improves durability under churn but multiplies storage and repair traffic.
  • Direct connections avoid relay costs but fail behind symmetric NATs and restrictive networks.
  • Content addressing makes data verifiable but prevents mutable content without an extra naming layer.
  • Incentives encourage contribution but add complexity and can be gamed.
  • Anonymity protects users but raises abuse, legal, and Sybil-resistance problems.

?Interview questions

Answer aloud before opening the outline.

1. What is peer-to-peer architecture?

A design where participants exchange resources directly instead of through a central server. Each peer acts as both client and server, so capacity grows with the number of participants. The trade-off is churn, unpredictable connectivity, and the need to distrust other peers.

2. How is P2P different from client-server?

Client-server concentrates data and control in a small set of servers, giving predictable performance and easy security but a bandwidth ceiling and single point of failure. P2P distributes both capacity and responsibility, gaining scale and resilience at the cost of coordination and trust.

3. What is a hybrid P2P system?

One with a small central component for discovery, indexing, or signalling while the actual data flows between peers. Most real systems are hybrids because fully decentralized discovery is hard and a tracker or signalling server is cheap to run.

4. How does a DHT work?

Keys and peers are hashed into the same identifier space, and each peer is responsible for keys near its own ID. A lookup hops toward progressively closer peers, converging in logarithmically many steps, while each node stores only a small routing table.

5. Why is churn hard?

Peers leave without warning, so stored data and routing entries disappear. Systems need replication, failure detection, and repair to keep availability, and must avoid strong consistency assumptions that a stable membership would allow.

6. What is NAT traversal and why is it needed?

Most peers are behind NATs and cannot accept inbound connections. Hole punching, STUN, and TURN establish a path, often with a signalling service to coordinate. Symmetric NATs frequently defeat direct connections, so a relay fallback is required.

7. How do you stop peers from sending corrupt data?

Verify content by hash. Content addressing and Merkle trees let a receiver check each chunk independently, so it does not matter who served it. Encryption protects confidentiality, but integrity comes from verification.

8. What is a Sybil attack?

One operator creates many fake peer identities to dominate routing, storage, or voting. Defences include making identity costly, limiting influence per identity, ensuring neighbour diversity, and using verifiable work or stake where appropriate.

9. How does gossip spread information?

Each peer periodically exchanges state with a small random set of neighbours. Updates spread exponentially and converge in logarithmically many rounds, with redundancy providing resilience. The cost is duplicate messages, so fanout and interval must be tuned.

10. What are the main P2P use cases?

File distribution and software updates, blockchain ledgers, content-addressed storage, WebRTC media, local-first collaboration, and edge caching. They share a need for many participants to contribute capacity without a central origin.

11. How do you motivate peers to upload?

Use reciprocity such as tit-for-tat, where good uploaders get better download priority, plus rarest-first selection to keep scarce chunks available. Token incentives can work but add economic complexity and new attack surfaces.

12. When would you not use P2P?

When you need strict consistency, access control over private data, predictable latency, or simple operations. A CDN or central service is easier to secure, observe, and govern. P2P pays off mainly for broadcast-heavy, verifiable content.

13. How do you observe a P2P network?

Instrument peers to emit local metrics and aggregate them, and sample the overlay from several vantage points. Track peer counts, churn rate, replication health, lookup latency, and transfer success. There is no single place that sees everything.

!Traps

  • Assuming peers are always online and treating membership as stable.
  • Designing discovery as fully decentralized when a small tracker or signalling service would be simpler.
  • Forgetting a relay fallback for peers behind symmetric NATs.
  • Trusting a peer's data without verifying hashes because the connection is encrypted.
  • Ignoring free-riding, so the network degrades into a few peers serving everyone.
  • Guaranteeing global ordering or strong consistency across unreliable peers.
  • Underestimating legal and abuse handling for content you cannot inspect or delete.
