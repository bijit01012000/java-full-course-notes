Blue-green deployment
A release model with two production-equivalent environments where one serves live traffic and the other hosts the next version.
Cutover
The moment traffic is redirected from the old environment to the new one, usually at a load balancer, proxy, or DNS layer.
Environment parity
Keeping both environments identical in configuration, dependencies, secrets, and infrastructure so the idle one is a genuine substitute.
Rollback target
The previous environment kept running and healthy so that reverting is a routing change rather than a rebuild.
Shared database
The single data store both environments use, which makes schema compatibility a hard requirement for fast rollback.
Warm-up
Pre-loading caches and connection pools in the idle environment so the first requests after cutover are not pathologically slow.
DNS TTL
The cache lifetime of a DNS record; a long TTL makes DNS-based cutover slow and partially propagated.
Smoke test
A small set of end-to-end checks run against the idle environment before it receives real traffic.

01The question blue-green answers

When a release breaks in production, the only question that matters is how quickly users can be back on the last working version.

  • Rolling deployments recover by rolling the fleet backwards, which takes as long as the rollout did.
  • Recreate deployments recover by taking the service down again.
  • Blue-green reduces recovery to a single routing decision, measured in seconds.
  • It does this by never destroying the previous version during the risky window.
  • The trade is cost and environment complexity, not speed: you pay for a second environment to buy back time.
  • It is most valuable for critical services where minutes of degradation are expensive.

02How the two environments work

  • Blue runs version 1 and holds all production traffic.
  • Green is an identical environment running version 2 and receiving no user traffic at first.
  • Version 2 is deployed to green while blue continues serving normally, so the deploy itself is invisible to users.
  • Green is warmed and smoke-tested in isolation, which is impossible during a rolling upgrade of live instances.
  • When green is trusted, the router or load balancer sends production traffic to it.
  • Blue keeps running afterwards, holding the previous version as an instant rollback target.
Deploy version 2 to green→Warm caches and run smoke tests→Redirect traffic to green→Watch metrics→Keep blue as rollback, or recycle it as the next green

03How traffic is switched

  • A load balancer or reverse proxy switch is the cleanest cutover: it is immediate and fully reversible.
  • DNS switching is slower and messier because resolvers cache records for the TTL, so some clients stay on blue and some move to green.
  • A long DNS TTL turns a seconds-long rollback into a minutes-long, partially applied one.
  • Weighted routing can move traffic in steps instead of all at once, which blends blue-green into a canary.
  • Long-lived connections such as WebSockets need explicit draining from the old environment.
  • Keep the switch mechanism external to the application so it works even when the new version is failing.
If rollback depends on a control plane that the failing release can also break, it is not a reliable rollback path.

04Validating the idle environment

  • Run smoke tests against green through the same entry point users will use, not against a pod directly.
  • Verify configuration, secrets, and feature-flag state are present in green before the switch.
  • Warm caches and connection pools so the cutover does not present as a latency spike.
  • Check dependency connectivity: databases, queues, caches, and third-party endpoints must all be reachable from green.
  • Confirm capacity: green must handle full production load alone, because blue is no longer absorbing its share.
  • Validate data compatibility in both directions, not just that green can read the current schema.

05Rollback reality

  • Rollback is a routing change back to blue, which is fast only if blue is still running, healthy, and correctly sized.
  • Blue must not be scaled down, reconfigured, or repurposed before the new version is proven.
  • If the cutover included a destructive data change, routing back does not restore service.
  • In-flight requests on green complete against the new version, so a small amount of new-version behavior survives the rollback.
  • Sessions created on green may not be understood by blue unless session format is compatible.
  • Rehearse rollback as a normal operation; a rollback path exercised only during incidents tends to fail.

06The database problem

Both environments almost always share a single database, which quietly turns every schema change into a rollback constraint.

  • If version 2 adds a column with a default and drops the old one, version 1 can no longer run against the schema.
  • Safe schema changes are additive: add first, backfill, dual-write or dual-read, then remove later.
  • The removal step must happen in a separate release, after blue is no longer needed as a rollback target.
  • Data written by version 2 in a new format may be unreadable by version 1, so rollback can corrupt or fail.
  • A separate database per environment solves schema coupling but creates a data-merge problem that is usually worse.
  • Migrations that rewrite large tables lock them, which can make the cutover fail for reasons unrelated to application code.

07Shared state beyond the database

  • Sessions must be stored in a shared, version-tolerant format or users will be logged out on rollback.
  • Cached values written by one version can be read by the other, so cache key versions help separate incompatible payloads.
  • Queue messages outlive deployments; consumers must tolerate messages produced by either version.
  • Search indexes and materialized views are shared state too, and a mapping change can break the old version.
  • Object storage paths and file formats must remain readable after a switch back.
  • Third-party integrations configured per environment can silently diverge, making green behave differently from blue.

08Cost and environment parity

  • Two complete production environments double compute and often double idle capacity during the release window.
  • Parity is expensive to maintain: drift in configuration, dependencies, or infrastructure makes the idle environment a poor substitute.
  • Some teams rotate roles — after a stable period, blue becomes the next release target — which keeps both environments exercised.
  • Keeping blue warm for rollback costs money for as long as the rollback guarantee is promised.
  • Scaling green up just for the cutover and down afterwards saves cost but removes the spare capacity needed for rollback.
  • Environment parity is the core engineering cost: infrastructure as code and identical configuration management are prerequisites, not nice-to-haves.

09Observability and all-at-once exposure

  • The switch moves every user at the same moment, so a production-only defect affects the entire user base immediately.
  • Post-cutover monitoring must be able to distinguish the new environment from the old one in metrics and logs.
  • Define automatic revert conditions — error rate, latency percentiles, business metrics — before the switch, not after.
  • Watch saturation as well as errors, because a green environment sized correctly on paper may still run hotter under real traffic.
  • Keep the old environment's dashboards live during the observation window so the comparison is immediate.
  • An observation window that ends before slow-burn problems appear turns the fast rollback into a false comfort.

10Variations

  • Blue-green with weighted routing moves a percentage of traffic first, combining fast rollback with bounded exposure.
  • Per-tenant cutover switches specific customers, which suits B2B products where tenants can be moved individually.
  • Blue-green for stateful services is much harder, because the data layer cannot be duplicated cheaply or consistently.
  • Some teams run blue-green at the cluster level and rolling within the cluster, so a switch still has internal batching.
  • A 'green by default' model keeps the idle environment continuously deployed, shrinking the release window.
  • Without parity and monitoring, these variations degrade into an expensive way to do recreate.

11Failure modes

  • Cold start: green serves with empty caches, producing a latency spike that looks like a code regression.
  • Schema lock-in: version 2 makes a change that makes rollback impossible, discovered only during the incident.
  • Config drift: green is missing a secret or environment variable that only exists in blue.
  • Partial cutover: DNS caching leaves some users on blue, so behavior and data diverge across the population.
  • Rollback unavailable: blue was scaled down or redeployed, so the promised seconds-long recovery does not exist.
  • Silent capacity shortfall: green cannot carry the full load alone and degrades under the cutover.

12When to choose blue-green

  • Choose it when rollback speed dominates and the service is critical enough to justify a duplicate environment.
  • Choose it when the new version needs isolated warm-up and smoke testing before exposure.
  • Avoid it when the budget cannot absorb a second full environment for the release window.
  • Avoid it when the data layer makes simultaneous versions unsafe and cannot be made backward compatible.
  • Avoid it when all-at-once exposure is unacceptable and traffic splitting is available — then use a canary.
  • In practice, combine it with flags: switch environments, then release features gradually for finer control.

↔Trade-offs to say out loud

  • Blue-green gives near-instant rollback and isolated pre-release testing, but requires two full environments running at once.
  • Router cutover is immediate and reversible but moves all users at once, so a production-only defect hits everyone.
  • DNS cutover avoids load balancer churn but propagates slowly and unevenly because of resolver caching.
  • Keeping blue warm preserves the rollback guarantee but doubles idle cost for the whole observation window.
  • Rotating environments keeps both sides tested but adds operational discipline and cleanup work to every release.
  • A separate database per environment removes schema coupling but introduces data replication and merge complexity.
  • Weighted cutover reduces blast radius but is effectively a canary and needs traffic analysis to be meaningful.
  • Aggressive cost cutting on the idle environment saves money but quietly converts fast rollback into a rebuild.

?Interview questions

Answer aloud before opening the outline.

1. What is a blue-green deployment?

Two production-equivalent environments where blue serves live traffic and green hosts the next version. Once green is validated, the router sends traffic to it, and blue stays running as a rollback target. The release becomes a routing change rather than a fleet upgrade.

2. Why is rollback faster than in a rolling deployment?

Because the previous version was never destroyed and does not need to be redeployed. Reverting is the same router change in the opposite direction, so it takes seconds instead of the length of a full rollout. The guarantee depends entirely on blue staying healthy and correctly sized.

3. What is the biggest hidden risk in blue-green?

The shared database. If version 2 applies an incompatible or destructive schema change, version 1 can no longer serve traffic, so the fast rollback does not restore service. Schema changes must be backward compatible and split across releases.

4. How do you handle database changes with blue-green?

Expand and contract: add the new structure without removing the old, keep both versions compatible, backfill and switch reads, then remove the old structure in a later release after blue is retired. The removal must never happen in the same release as the addition.

5. What is the difference between load-balancer cutover and DNS cutover?

A load balancer switch is immediate and fully under your control, so rollback is deterministic. DNS changes propagate according to TTL and resolver behaviour, so some clients move before others and rollback is partial for a while. Prefer the load balancer for the actual switch, and use DNS only for coarse routing.

6. Why does the idle environment need warm-up?

An unwarmed environment starts with empty caches and cold connection pools, so the first requests after cutover hit the database and downstreams hard. That latency spike looks exactly like a regression and can trigger a needless rollback. Warm-up makes the cutover comparable to steady state.

7. What shared state must both environments tolerate?

Sessions, caches, queue messages, search indexes, and object storage all outlive a deployment. Any of them written in a format only one version understands will break the other. Versioning cache keys and keeping message formats additive are the usual mitigations.

8. How does blue-green handle blast radius?

Poorly on its own: flipping the router moves every user at once. A defect that only appears under real production traffic can affect the whole user base before anyone reacts. Weighted cutover or a canary stage reduces exposure, at the cost of more machinery.

9. What does environment parity mean and why does it matter?

Both environments must have the same configuration, dependencies, secrets, and infrastructure shape. Without parity, green behaves differently from blue for reasons unrelated to the code, and the smoke tests validate the wrong thing. Parity is usually achieved with infrastructure as code and shared configuration management.

10. How would you reduce blue-green cost?

Rotate environments instead of keeping a permanently idle fleet, scale the standby to a smaller but sufficient size, or use weighted cutover so the duplicate capacity is needed for a shorter window. Each saving trades away part of the rollback guarantee, so make the trade explicit.

11. How is blue-green different from canary?

Blue-green moves all traffic at one switch point; canary moves a small share first and grows it while comparing metrics. Blue-green optimizes recovery speed, canary optimizes exposure size. Blue-green with weighted routing is effectively a canary that keeps a full standby.

12. When should you not use blue-green?

When the budget cannot support two production environments, when the data layer cannot tolerate two versions, or when blast radius matters more than rollback speed. In those cases rolling, canary, or a maintenance window is a better fit.

!Traps

  • Promising seconds-long rollback while scaling down or redeploying the blue environment right after cutover.
  • Applying a destructive schema change in the same release as the code that needs it.
  • Switching DNS and assuming the cutover is instant when resolver caching spreads it over many minutes.
  • Skipping warm-up and then misreading the cold-cache latency spike as a code defect.
  • Letting configuration drift between environments so green fails for reasons unrelated to the release.
  • Using a cutover mechanism that lives inside the application being released.
  • Observing for a few seconds and declaring success before slow-burn errors and saturation appear.
