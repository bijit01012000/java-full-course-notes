01Three metrics, one highway

Latency, throughput, and bandwidth are often used interchangeably, but they measure different things. A highway analogy separates them cleanly.

  • Bandwidth is the number of lanes: how many cars the road can carry at once.
  • Throughput is the number of cars that actually arrive per hour; congestion, accidents, or roadwork can push it well below capacity.
  • Latency is how long one car takes to travel between the two cities.
  • Adding lanes raises capacity but does not make any single car arrive sooner; distance and speed limit are unchanged.
  • Improving one metric therefore does not imply the others improve, so a performance requirement must name the metric it constrains.
  • The same three ideas exist inside a machine: memory bandwidth, disk throughput, and per-query latency.

02Latency

Latency measures how long something takes to get from one point to another. For a network it is packet travel time; for an application it is the gap between sending a request and receiving the response.

  • At the network level this is usually round-trip time (RTT), which includes both directions.
  • For an application, total latency includes network time plus queueing, server processing, database queries, and response assembly.
  • Latency is measured in units of time, usually milliseconds or microseconds — never in requests per second.
  • A single request's latency is a sum of stages, so the slowest stage usually dominates the total.
  • Latency is a distribution, not a number: two systems with the same average can feel completely different.
  • Propagation delay is bounded by physics, so the only fix for distance is to move the data or the computation closer.
Client sends request→Network transit→Server processing→Database or dependency calls→Response assembly→Network transit back

03Where network latency comes from

Four delays add up on every hop. Knowing which one dominates tells you which fix is worth doing.

  • Propagation delay: time for the signal to physically travel the medium. Light in fiber moves at roughly two-thirds of its vacuum speed, so distance sets a hard floor.
  • Transmission delay: time to push all the bits onto the link. Larger messages and slower links take longer.
  • Queuing delay: time packets wait in a router buffer because the outgoing link is busy. This is the part that grows under load.
  • Processing delay: time devices spend inspecting, decrypting, and forwarding packets.
  • Real paths are not straight lines and include many hops, so measured RTT is always worse than the theoretical minimum.
  • Because propagation is physics-bound, caching, CDNs, and multi-region deployment are the only real levers for it.

PropagationPhysical distance through fiberCDN, edge regions, placing compute near users
TransmissionMessage size and link rateSmaller payloads, compression, faster links

04What a full request pays

  • Before any data is sent, a new connection pays setup costs that are pure latency.
  • A DNS lookup resolves the hostname and may itself require a round trip if not cached.
  • A TCP handshake costs one round trip before the first byte of the request can flow.
  • A TLS handshake adds further round trips for HTTPS; TLS 1.3 and session resumption reduce them.
  • Server-side processing then adds parsing, authorization, database queries, and downstream service calls.
  • Reusing connections removes most of the setup cost from subsequent requests, which is why connection pools matter.
  • Fan-out multiplies latency: a request that waits on several sequential dependencies pays their sum, not their maximum.
DNS resolution→TCP handshake→TLS handshake→Send request→Server processing and dependencies→Response returns

05Measuring latency with percentiles

Averages hide the experience of slow users. If 98 requests take 50 ms and 2 take 2 seconds, the average is about 89 ms — which sounds fine and describes nobody.

  • P50 (median) is the typical experience: half of requests are faster than this.
  • P95 shows the boundary for the slowest twentieth of traffic.
  • P99 captures the worst 1%; in the example above, 50 ms at P50 but 2 seconds at P99.
  • Report percentiles per endpoint and per dependency, not just for the whole service.
  • Alert on the tail, not the mean; a rising P99 is an early signal of saturation or a slow dependency.
  • Percentiles cannot be averaged across instances — aggregate the underlying distributions or use histogram buckets.

Tail latency

  • A page that makes 20 backend calls in parallel finishes only when the slowest call completes.
  • If each call independently has a 1% chance of being slow, the chance that at least one is slow across 20 calls is roughly one in five.
  • So a 1% backend tail can affect a large share of page loads; fan-out amplifies the tail.
  • Reduce fan-out, hedge slow requests, set per-dependency timeouts, and cache to keep the tail short.
  • Garbage collection pauses, retries, and lock contention are common hidden tail producers.

06Bandwidth and bits vs bytes

Bandwidth is the maximum data a connection can carry per unit time. It is a capacity, not a measurement of what is currently flowing.

  • Network bandwidth is quoted in bits per second: Mbps or Gbps.
  • File sizes and memory are quoted in bytes, and one byte is eight bits.
  • A 1 Gbps link can theoretically carry about 125 megabytes per second; divide by eight to convert.
  • That number is a ceiling. Protocol overhead, retransmissions, and congestion control keep real throughput below it.
  • Internal components have bandwidth too: disks, memory buses, and network interfaces each impose their own ceiling.
  • A fast NIC in front of a slow disk does not make writes faster; the smallest ceiling wins.

07Throughput and the bottleneck

  • Throughput is work actually completed per unit time: bytes delivered, requests served, transactions committed.
  • Network throughput can never exceed bandwidth, and in practice is lower.
  • Protocol overhead: headers from Ethernet, IP, and TCP consume capacity without delivering payload.
  • Retransmissions: lost packets are sent again, using bandwidth without delivering new data.
  • Congestion control: TCP deliberately slows down when it detects loss, so a connection may not fill the link.
  • The system limit is the largest bottleneck, not the network: CPU, memory, disk I/O, connection pools, or lock contention.
  • A 10 Gbps network writing to a disk that sustains only 200 MB/s yields a 200 MB/s system, not a 1.25 GB/s system.
  • Improving a non-bottleneck resource changes nothing, which is why profiling precedes optimization.

08Latency vs bandwidth: which dominates

A useful estimate is: total time ≈ latency + (data size / bandwidth). The relative size of the two terms tells you what to optimize.

  • Small requests are latency-bound. A 1 KB API call takes about 8 microseconds to transmit at 1 Gbps, while a 50 ms round trip dominates completely.
  • Upgrading that connection to 10 Gbps would barely change the response time.
  • Large transfers are bandwidth-bound. A 10 GB backup at 1 Gbps takes roughly 80 seconds to transmit; 50 ms of latency is noise.
  • For small-request workloads, cut round trips, reuse connections, and move servers closer.
  • For bulk transfer, raise bandwidth, compress data, and parallelize streams.
  • Many real systems are mixed: a small metadata call plus a large payload, so both terms matter.
  • The same logic applies to database calls: many tiny queries are latency-bound, one huge scan is throughput-bound.

09The TCP window and the bandwidth-delay product

  • TCP limits how much unacknowledged data can be in flight; that limit is the window.
  • Throughput is bounded by roughly window size / round-trip time.
  • A 64 KB window with a 100 ms RTT caps throughput near 640 KB/s — roughly 5 Mbps — even on a 1 Gbps link.
  • The connection is not slow because of bandwidth; it is slow because acknowledgements arrive too slowly to keep the pipe full.
  • The bandwidth-delay product (bandwidth × RTT) is how much data must be in flight to fill the link: 1 Gbps at 100 ms needs about 12.5 MB.
  • Modern TCP supports much larger and dynamically adjusted windows, which mitigates but does not eliminate the problem.
  • For high-latency paths, use multiple parallel connections, larger buffers, or a protocol with better flow control.
  • This is why long-haul transfers often need tuning that a LAN never does.

A window smaller than the BDP leaves bandwidth idle, no matter how fast the link is.

10Little's Law inside a service

Inside a server, latency and throughput are tied together by Little's Law: concurrency = throughput × latency.

  • If a service handles 1,000 requests per second and each takes 200 ms, then 1,000 × 0.2 = 200 requests are in progress on average.
  • If a dependency slows requests to 1 second, sustaining 1,000 RPS would require 1,000 concurrent requests.
  • If only 200 threads or database connections exist, throughput cannot be sustained and requests queue.
  • Queueing raises latency further, which raises required concurrency again — a feedback loop that ends in an outage.
  • For capacity planning, invert the formula: required concurrency = target RPS × per-request latency.
  • A service targeting 5,000 RPS at 20 ms needs about 100 requests in flight, so pools and workers must support at least that.
  • Little's Law also explains why a small latency regression can force a large capacity increase.

11Trade-offs: batching and utilization

Some of the most effective throughput techniques deliberately add latency. The right choice depends on whether the user is waiting.

  • Batching amortizes per-item overhead: collect messages briefly, then write them together.
  • Each item may wait for the batch to fill or the timer to fire, so per-item latency rises while throughput improves.
  • Kafka producers expose this directly through linger.ms (how long to wait for more records) and batch.size.
  • Databases use group commit, sharing one disk flush across several transactions.
  • The trade is worthwhile for analytics, logs, and background jobs, and usually wrong for an interactive request.
  • Higher utilization raises throughput but increases waiting time non-linearly as queues build.
  • The last few percent of utilization cost far more latency than the first, so production keeps headroom and scales before saturation.
  • Admission control and load shedding protect latency by refusing work rather than queueing it indefinitely.

Utilization and queueing

  • At low utilization, requests rarely wait and latency is close to service time.
  • Near capacity, arrivals increasingly find the server busy and wait behind other work.
  • Latency stays flat for a while, then rises sharply — the classic queueing curve.
  • Running at 95% utilization can maximize throughput while producing unpredictable tail latency.
  • Keep spare capacity, autoscale ahead of demand, and set timeouts so one saturated dependency does not stall everything.

12Improving latency

  • Move data closer: CDNs and multi-region deployments cut propagation delay, which no amount of code optimization can remove.
  • Cache: memory reads beat a remote database round trip for hot data.
  • Cut round trips: reuse connections, combine small requests, and run independent calls in parallel instead of sequentially.
  • Use modern protocols: TLS 1.3 and HTTP/3 reduce connection setup round trips.
  • Get work off the critical path: send email, generate reports, and update feeds asynchronously through a queue.
  • Optimize the work: add indexes, fix queries, remove unnecessary processing and payload.
  • Defend the tail: set timeouts on every dependency, limit retries, and watch for GC pauses.
  • Measure per stage; optimizing a stage that is only 2% of total time is invisible to users.
Measure per-stage latency→Find the dominant stage→Apply the matching fix→Re-measure P50 and P99

13Improving throughput and using bandwidth well

  • Find the bottleneck first — adding capacity to a non-bottleneck changes nothing.
  • Horizontal scaling: more servers behind a load balancer, or partitioned data across machines.
  • Parallel processing: split large jobs into independent tasks that run concurrently.
  • Batching: group writes, network calls, or messages when latency requirements permit.
  • Queues: buffer bursts so producers and consumers each run at their own sustainable rate.
  • Connection pooling: avoid paying handshake and setup cost per request.
  • Send less data: compress text responses, drop unnecessary fields, paginate large result sets.
  • Offload static content to a CDN so origin bandwidth goes to dynamic work.

14Which metric matters for your system

Different products optimize different metrics. Naming the priority early prevents arguing about the wrong number later.

  • Trading platform or multiplayer game: latency dominates; a few milliseconds can change the outcome.
  • Data pipeline or nightly backup: throughput dominates; finishing the job on schedule matters more than any single record.
  • Video streaming: bandwidth per viewer plus aggregate throughput at peak.
  • Most user-facing apps: both — fast individual requests and enough capacity for peak traffic.
  • A good requirement states both, for example: keep P99 latency below 200 ms while sustaining 10,000 requests per second.
  • Ask which factor becomes the bottleneck first and what trade-off you are willing to accept to move it.
  • Track the metric you promise; a system that optimizes average latency while P99 degrades has not met its goal.

↔Trade-offs to say out loud

  • Batching raises throughput by amortizing overhead, but every item waits for the batch, so per-item latency rises.
  • High utilization maximizes throughput per dollar, but queueing makes tail latency unpredictable near saturation.
  • Adding bandwidth helps large transfers, but barely changes small-request latency, which is dominated by round trips.
  • Moving compute to the edge cuts propagation delay, but multiplies deployment targets and data-consistency problems.
  • Caching reduces both latency and backend load, but accepts staleness and invalidation complexity.
  • Parallel fan-out lowers latency when calls are independent, but increases load and amplifies tail latency.
  • Larger TCP windows and parallel connections fill high-latency links, but consume memory and can crowd out other flows.
  • Asynchronous processing removes slow work from the request path, but converts an immediate result into eventual completion.

?Interview questions

Answer aloud before opening the outline.

1. Define latency, throughput, and bandwidth in one sentence each.

Latency is how long one request takes end to end. Throughput is how much work actually completes per second. Bandwidth is the maximum rate a link can carry — a ceiling that throughput never exceeds.

2. Why doesn't adding bandwidth always make an application faster?

For small requests, transfer time is negligible and round-trip latency dominates. More bandwidth cannot shorten the distance, the handshakes, or the server processing. It only helps when the workload is actually moving large amounts of data.

3. How do you measure latency properly?

Use percentiles — P50, P95, P99 — rather than the average, and report them per endpoint and per dependency. Averages hide the slow requests that users actually notice, and percentile aggregation must be done over distributions, not averaged.

4. What is tail latency and why does it matter?

It is the slow end of the distribution where a small fraction of requests take much longer. When one page makes many parallel backend calls, the slowest call gates the response, so a small per-call tail can affect a large share of page loads.

5. Where does network latency come from?

Propagation delay from physical distance, transmission delay from putting bits on the link, queuing delay in congested buffers, and processing delay in network devices. Only propagation is truly physics-bound; the others respond to capacity and protocol choices.

6. A 1 Gbps link and a 100 ms RTT — why might a single TCP connection only reach a few Mbps?

Throughput is bounded by window / RTT. A 64 KB window at 100 ms allows roughly 640 KB/s. Filling the link requires enough data in flight to cover the bandwidth-delay product, which is about 12.5 MB here.

7. State Little's Law and use it for capacity planning.

Concurrency = throughput × latency. To serve 5,000 requests per second at 20 ms each, you need about 100 requests in flight, so thread pools, connection pools, and worker counts must support at least that.

8. How can a slow dependency cause an outage?

If latency rises and concurrency is capped, throughput falls. Requests queue, which raises latency further and consumes the remaining capacity. This positive feedback explains how one slow database turns into a full-service outage without any increase in traffic.

9. What is the trade-off in batching?

Batching amortizes fixed overhead and raises throughput, but each item waits for the batch, so latency increases. Settings like linger.ms and batch.size tune that trade-off; interactive paths usually keep batches small or skip them.

10. Why is 100% utilization a bad target?

Queueing delay rises non-linearly as utilization approaches capacity, so the last few percent of throughput cost a large multiple in latency. Production systems keep headroom and autoscale before saturation.

11. How would you reduce P99 latency?

Find the dominant stage, add timeouts and retry budgets, reduce fan-out, cache hot paths, and remove GC or lock pauses. Hedged requests and per-dependency circuit breakers keep one slow service from gating the whole response.

12. How would you raise throughput?

Identify the bottleneck, then scale out, partition data, parallelize independent work, batch where latency permits, add queues to absorb bursts, and pool connections. Also reduce bytes sent through compression and pagination.

13. Which metric matters for a nightly ETL job versus a game?

The ETL job is throughput-bound: finishing the whole job within its window matters more than any single record. A game is latency-bound: a few milliseconds of delay changes the outcome. Most user-facing apps need both and should state a combined budget.

!Traps

  • Reporting only average latency and missing the P99 that users actually experience.
  • Assuming more bandwidth will fix a latency problem caused by round trips and distance.
  • Confusing bits and bytes, producing an eight-times error in capacity estimates.
  • Calling a link's bandwidth its throughput; real throughput is lower due to overhead, retransmissions, and congestion control.
  • Scaling a tier that is not the bottleneck and concluding scaling does not work.
  • Ignoring Little's Law when sizing thread or connection pools, then blaming the database for queueing.
  • Running servers at near-100% utilization and treating the resulting tail latency as a mystery.
  • Averaging percentiles across instances instead of aggregating the underlying distributions.
