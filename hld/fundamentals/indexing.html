01What is a database index?

Suppose a users table has millions of rows and we want one user by email. Without an index, the database may examine rows one by one until it finds the match — a full table scan.

  • An index is a separate structure built to make certain lookups fast; the table still holds the full rows.
  • It stores the indexed column values in sorted order along with a reference to the row that owns each value.
  • The table rows themselves are in no particular order — only the index is sorted.
  • A lookup is two steps: search the index for the value, then follow the row reference to fetch the row.
  • The second step is skipped when the index already contains everything the query needs.
  • Creating one is a single statement, but building it reads the table and sorts the key values.
  • An index does not change query results; it changes how quickly the engine can find them.
Index entry (sorted)Row
alice@example.comrow 7
bob@example.comrow 3
carol@example.comrow 9
dave@example.comrow 1
CREATE INDEX idx_users_email ON users (email);

SELECT id, name FROM users WHERE email = 'alice@example.com';
Rows 7, 3, 9, 1 are in insertion order; only the index is ordered by email.

02Why indexes are faster

  • A search at each tree level decides which branch could contain the value and skips the rest of the tree.
  • Each level eliminates most remaining candidates, so the number of steps grows with the logarithm of the row count.
  • A full scan on a 10-million-row table can examine up to 10 million rows; a B-tree lookup reads a few pages and then one row.
  • The gain comes from reading pages, not bytes: one page brings many keys into memory at once.
  • The index is usually far smaller than the table, so more of it stays cached.
  • You do not need to reason about tree traversal when writing SQL; what matters is which queries an index can serve.
  • The database chooses between the index and a scan by estimating cost, so an index is an option, not a command.

03How a B-tree index works

A database B-tree is not a binary tree. Each node is a page that holds many keys, which keeps the tree shallow even for enormous tables.

  • The root page holds separator keys that divide the value space into ranges.
  • An internal page points to child pages covering narrower ranges, and each child repeats the split.
  • Leaf pages hold the actual key entries and row references, and are linked so the engine can walk them in order.
  • To find a value, compare at the root, descend into the matching child, and repeat until a leaf is reached.
  • Pages that cannot contain the value are never read, so most of the tree is untouched.
  • Wide pages mean high fanout: hundreds of keys per page, so only a few levels cover millions of rows.
  • The tree stays balanced through splits and merges, which keeps worst-case lookup depth predictable.
  • This is why B-trees are the default index for most CREATE INDEX statements in relational databases.
Root [300K | 700K]→500K falls in the middle range→Child [450K | 550K]→Leaf containing 500K→Row reference
The example uses two keys per page for clarity. Real pages hold far more, which is exactly why the depth stays small.

04Indexes and range queries

Because keys are stored in order, an index also accelerates ranges and ordering — not just equality.

  • For created_at BETWEEN a AND b, the engine seeks to the first matching key then reads neighboring leaves in order.
  • Only one tree search is needed; the matching entries are physically adjacent.
  • Works for =, >, <, >=, <=, and BETWEEN.
  • Supports ORDER BY: reading an index already ordered by created_at avoids sorting a large result set.
  • With ORDER BY ... LIMIT, the engine can read a few entries from one end and stop.
  • Prefix matches such as name LIKE 'Al%' can use the index; a leading wildcard %Al usually cannot.
  • A range on a later column is far more efficient when the leading columns are fixed by equality.
  • Reading many scattered rows via an index can still lose to a sequential scan when the range is broad.

05Single-column and composite indexes

A composite index spans multiple columns. Conceptually it is sorted by the first column, then by the second within each group of equal first values, and so on.

  • An index on (customer_id, created_at) finds a customer's orders and reads them already in timestamp order, with no separate sort.
  • Column order is part of the definition: (customer_id, created_at) is not the same index as (created_at, customer_id).
  • In the reversed index, one customer's orders are scattered across the whole structure.
  • A useful rule of thumb: equality filters first, range filters next, ordering columns last.
  • The same index can serve queries that filter on just the leading column, so it may replace a narrower index.
  • The rule is a starting point, not a law; verify with the actual plan because engines and data distributions differ.
  • Adding a column to an index widens every entry, increasing storage and write cost.
  • A composite index is not a substitute for two independent access paths; a query on only the second column may not use it.
CREATE INDEX idx_orders_customer_created
  ON orders (customer_id, created_at DESC);

SELECT id, total
FROM orders
WHERE customer_id = 123
ORDER BY created_at DESC
LIMIT 20;
Matching the index's sort direction to the query's avoids a backward scan or an explicit sort in some engines.

06The leftmost prefix rule

With an index on (country, city, created_at), entries are grouped by country, then by city inside each country, then by time inside each city. That physical ordering decides which filters the index can serve.

  • Filter on country alone: uses the index well, because it is the leading column.
  • Filter on country and city: uses the first two columns in order.
  • Filter on all three: uses the full index, including the range on time.
  • Filter on city only: usually no efficient use, because entries for one city are spread across every country.
  • Filter on city and created_at, skipping country: the leading column is missing, so the index ordering does not line up.
  • Some engines can use a skip scan in limited cases, but it is not a guarantee and depends on the leading column's cardinality.
  • Consequence: design composite indexes from real queries rather than from columns that merely seem related.
  • A query that filters on the leading column and sorts by the second gets ordering and filtering from one structure.

07Covering indexes

  • An index covers a query when it contains every column the query reads.
  • The engine can then return results directly from the index and skip the table lookup entirely.
  • For a query selecting email and signup date by id, an index on (id, email, signup_date) can cover it.
  • PostgreSQL reports this as an index-only scan when its visibility rules allow it.
  • PostgreSQL also supports INCLUDE to add payload columns without making them part of the sort key.
  • Covering a query removes random row fetches, which is the dominant cost when many rows match.
  • The cost is a wider index: more storage, more write work, and fewer entries per page.
  • Use covering indexes for important, frequently executed queries where you have measured the benefit.
CREATE INDEX idx_users_id_email_signup
  ON users (id) INCLUDE (email, signup_date);

SELECT email, signup_date FROM users WHERE id = 42;
An index-only scan still needs a visibility check in some engines; very recent writes can force heap access, so the win is largest on stable data.

08Indexes are not free

Indexes trade read speed for write work. Inserting one row into a table with several indexes updates every affected index.

  • One logical insert becomes several physical writes: the table row plus one entry in each index.
  • Deletes must remove entries from every index; updates touch indexes for changed columns and sometimes migrate entries.
  • Each index consumes disk and grows backup size and restore time.
  • Index pages compete with table pages for the buffer cache, so extra indexes can push useful data out of memory.
  • Building an index on a large table takes time and I/O, and a non-concurrent build may block writes.
  • Every additional index gives the planner more alternatives to cost, increasing planning work.
  • Write-heavy tables suffer most, which is why over-indexing is a common cause of unexplained write latency.
  • The trade is only worth it when the read pattern is frequent enough to justify the permanent write tax.

09Selectivity matters

Selectivity describes how well a column distinguishes rows. In plain terms: how much does this filter narrow the search?

  • An email column is highly selective because one value usually matches one row.
  • A status column with a handful of values is weakly selective; filtering on the common value still matches most of the table.
  • An index on a column that matches millions of rows forces millions of row lookups, which can be slower than one sequential scan.
  • The optimizer estimates selectivity from statistics such as distinct counts and histograms.
  • Low-selectivity columns can still be useful as part of a composite index where another column does the narrowing.
  • An index on a boolean alone is usually weak, because half the table matches either value.
  • Selectivity is about the query, not just the column: a rare status value is more selective than a common one.
  • Indexes pay off when they reduce the candidate set enough that random row fetches beat sequential reading.

10Why the database might ignore an index

  • The optimizer compares the estimated cost of an index access with a sequential scan and may choose the scan.
  • If the filter matches a large percentage of the table, scanning in order is cheaper than scattered row fetches.
  • On a very small table, the extra index lookup costs more than reading the whole table.
  • If the index does not match the query shape — wrong leading column, function on the column, leading wildcard — it cannot be used efficiently.
  • Stale statistics make the cost estimates wrong, so the optimizer misjudges both options.
  • Type mismatches and implicit casts can prevent the comparison from using the indexed ordering.
  • A query that needs most columns may still use the index for filtering but then fetch so many rows that a scan wins.
  • The existence of an index is not a guarantee of use; EXPLAIN shows what was actually chosen.

11Primary keys and unique indexes

  • Most relational databases automatically create an index to enforce a primary key and make lookups by it efficient.
  • A primary key index is also the target of foreign key references, so joins on it are fast by default.
  • A unique constraint is usually implemented as a unique index, serving lookups and enforcement at once.
  • On insert, the database checks the unique index for an existing entry instead of scanning the table.
  • Uniqueness enforcement means the index must be updated inside the write, adding cost to every insert.
  • A surrogate key such as a sequence id is compact and keeps secondary index entries small.
  • A natural key such as email can be unique and useful, but it is wider and harder to change.
  • Do not add a redundant index on a column that already has a unique or primary key index.
ALTER TABLE users ADD CONSTRAINT users_email_unique UNIQUE (email);
-- implemented as a unique index: fast lookup plus uniqueness enforcement
On a unique index, a duplicate insert fails rather than returning a second row; application code must handle that error path.

12When to add an index

  • Start from real query patterns, not from the column list.
  • Index columns that appear frequently in WHERE clauses, join conditions, ORDER BY, and range predicates.
  • Common candidates: foreign keys, lookup identifiers such as email or order id, and timestamps used for recent-item queries.
  • Ask how often the query runs, how many rows it returns, how expensive it is today, and how often the table is written.
  • Ask whether an existing index already supports the query, which is how redundant indexes creep in.
  • Put equality columns first, then the range or sort column, and confirm with EXPLAIN.
  • A composite index on (customer_id, created_at) can replace a single-column index on customer_id.
  • Measure before and after; an index that is never chosen is pure write cost.

13Too many indexes

  • A table with an index on almost every column pays write cost for structures that are rarely or never read.
  • Storage grows, backups grow, and restore and migration times grow with every index.
  • More index pages compete for cache, so the indexes that do matter may become slower.
  • Some indexes duplicate the leading columns of a wider composite index and add nothing.
  • Most databases report index usage counts, which makes unused and redundant indexes findable.
  • Review indexes over time, not only when adding them; query patterns change and old indexes linger.
  • Drop unused indexes deliberately after confirming no reporting job or failover path depends on them.
  • The goal is the smallest useful set of indexes that supports the important query patterns.
Index hygiene is a recurring maintenance task: add for measured reads, remove for measured waste.

↔Trade-offs to say out loud

  • Adding an index speeds the targeted read but adds a write to every insert, update, and delete.
  • Composite indexes serve filter-plus-sort queries in one structure but only help when the leading columns match.
  • Covering indexes remove table lookups but widen the index and increase storage and maintenance cost.
  • High selectivity makes an index decisive, while low selectivity can make it slower than a sequential scan.
  • More indexes give the optimizer more options but increase planning time, storage, and cache pressure.
  • Unique indexes enforce correctness and speed lookups but add a constraint check to every write.
  • Wide indexes avoid sorts and fetches but reduce fanout, deepen the tree, and slow maintenance.
  • Dropping unused indexes improves write throughput and storage but risks a hidden reporting query that relied on them.
  • Index-only scans are fastest on stable data because visibility checks can still require table access on recent writes.

?Interview questions

Answer aloud before opening the outline.

1. What is a database index?

A separate data structure that stores values from one or more columns in sorted order with a reference to each row. The table still holds the data; the index is an extra path that avoids scanning every row.

2. Why is a B-tree index fast on a huge table?

Each page holds many keys, so the tree has high fanout and stays only a few levels deep even for millions of rows. A lookup reads a handful of pages along one path and ignores the rest of the tree.

3. Why does an index help a range query and not just equality?

Keys are stored in order, so the engine seeks once to the start of the range and then reads adjacent leaf entries until the range ends. The same ordering can also satisfy ORDER BY and avoid a sort.

4. What is a composite index?

An index over multiple columns, sorted by the first column, then by the second within each equal first value, and so on. It is what lets one structure satisfy a filter on one column and an ordering on another.

5. Explain the leftmost prefix rule.

A composite index can be used efficiently when the query filters on a prefix of its columns starting from the left. With (country, city, created_at), a query on city alone skips the leading column, so entries for one city are scattered across every country and the ordering is useless.

6. What is a covering index?

An index that contains every column the query needs, so the engine answers from the index without fetching table rows. It removes random row lookups but makes the index wider and more expensive to maintain, so reserve it for measured, frequent queries.

7. What does an index cost on writes?

Every insert, update, and delete must maintain each affected index. One logical write becomes one table write plus one entry update per index, plus WAL and page splits. Indexes also consume storage, cache, and backup capacity.

8. What is selectivity?

How well a column distinguishes rows — how much a filter on it narrows the result. Email is highly selective; a boolean or status column is not. An index on a low-selectivity column may be ignored because fetching millions of matching rows costs more than scanning.

9. Why would the optimizer ignore an existing index?

Because the estimated cost is higher than a sequential scan: the filter matches a large fraction of the table, the table is small, the index does not match the query shape, or statistics are stale and mislead the estimate. Existence is not the same as usefulness.

10. How do you decide which columns to index?

Look at real queries: frequent WHERE, join, ORDER BY, and range predicates. Check how many rows the query returns, how often it runs, how heavily the table is written, and whether an existing index already supports it. Then confirm with the plan.

11. In what order should columns go in a composite index?

A practical rule is equality columns first, then range columns, then columns used for ordering. The leading column must be the one queries filter on most. Verify with the real plan, because distribution and engine behavior can change the answer.

12. Can an index make a query slower?

Yes. If a filter matches most of the table, using the index means many random row fetches instead of one ordered scan. Extra indexes also slow all writes and compete for cache, so an unused index is a net loss.

13. How do you find unused indexes?

Most databases expose per-index usage counters and sizes. Combine low usage with a check for indexes whose leading columns are duplicated by a wider composite index, then verify no reporting or failover workload depends on them before dropping.

14. How would you index a query that filters by customer and sorts by date?

Create a composite index on (customer_id, created_at). The equality on customer positions the seek, and the date ordering inside that customer satisfies the sort, so the engine can read the newest entries and stop at the limit.

!Traps

  • Indexing every column and calling it optimization; writes, storage, and cache all pay for it.
  • Building a composite index in the wrong column order and then blaming the database for ignoring it.
  • Indexing a low-selectivity column such as a boolean or status and expecting a large speedup.
  • Forgetting that LIKE '%term%' and functions on the indexed column defeat a normal B-tree.
  • Adding a duplicate index on a column already covered by a unique or composite index.
  • Trusting that an index exists means it is used, without checking the plan.
  • Optimizing for a rare query while the frequent query still scans the table.
