In one lineA rolling deployment replaces instances a few at a time so the service stays online without a second full copy of production — at the cost of running two versions side by side and rolling back slowly.
Rolling deployment
A rollout that upgrades instances in batches, draining, replacing, and health-checking each batch before moving to the next.
Batch (or surge group)
The set of instances upgraded together in one step of the rollout.
maxUnavailable
The maximum number of instances allowed to be unavailable at the same time, which bounds the capacity dip.
maxSurge
The maximum number of extra instances that may exist temporarily above the desired count, which speeds the rollout at extra cost.
Readiness probe
A check that decides whether an instance should receive traffic, as opposed to whether its process is alive.
Graceful shutdown
Draining in-flight requests and releasing resources after an instance stops accepting new traffic.
Mixed-version window
The period during a rollout when old and new code both serve production traffic.
Backward-compatible change
A change that keeps the old version working, such as adding a nullable column before the new code reads it.

01Why rolling deployments exist

Most services want two things from a deployment: stay online, and avoid paying for a second complete production fleet.

  • Recreate satisfies neither: it takes the service down and still exposes everyone to the new version at once.
  • Blue-green satisfies both goals partially but requires a duplicate environment for the whole deployment.
  • Rolling spreads the change across the existing fleet, so most instances keep serving at all times.
  • It is the default deployment strategy on many platforms because it needs no extra infrastructure and no traffic-splitting logic.
  • The saving is capacity, and the price is time: a rollout is minutes, not seconds, and rollback is just as slow.
  • It works best for stateless services with several instances behind a load balancer.

02How a rollout proceeds

  • The controller takes a batch of instances out of the load balancer's rotation.
  • Each instance finishes in-flight requests, then shuts down gracefully.
  • New instances with version 2 start in place of the removed ones.
  • Each new instance must pass its readiness probe before it is added back to rotation.
  • Only after the batch is healthy does the controller move to the next batch.
  • The rollout ends when every instance runs version 2, and stops immediately if a readiness check fails.
Drain batch from rotation→Graceful shutdown→Start version 2 instances→Pass readiness probe→Add back to rotation→Next batch

03Controlling speed and safety

  • maxUnavailable bounds how much serving capacity can disappear at once; setting it to zero forces a surge-first rollout.
  • maxSurge allows temporary extra instances so capacity never dips, at the cost of running above the desired count.
  • Large batches finish faster but create bigger capacity dips and wider exposure if version 2 is broken.
  • Small batches are safer and slower, and they lengthen the mixed-version window.
  • A rollout with both parameters at zero cannot progress; the controller needs room to move.
  • Slow readiness checks effectively reduce rollout speed regardless of batch size, because each batch waits for the slowest instance.

04Health checks decide what actually happens

  • A liveness check answers whether the process should be restarted; a readiness check answers whether it can serve traffic.
  • Using liveness as readiness causes traffic to be sent to instances that cannot handle requests.
  • Readiness should exercise real dependencies — database connectivity, cache, required downstreams — not just open a port.
  • Too strict a probe makes a rollout stall or flap; too loose a probe returns broken instances to rotation.
  • Set an initial delay or startup probe so slow-booting instances are not killed before they are ready.
  • Configure a termination grace period longer than the longest acceptable in-flight request.
A probe that always returns success is worse than no probe: it hides failures while giving false assurance.

05Two versions, one contract

  • Mid-rollout, some instances run version 1 and others version 2, and both serve the same users.
  • A user can hit version 2 on one request and version 1 on the next, so responses must stay compatible.
  • API changes must be additive: add fields and endpoints before removing them.
  • Database changes must be backward compatible: add and backfill before reading, drop only after old code is gone.
  • Cached values and queue messages written by one version may be read by the other, so their format must remain readable.
  • Session and token formats must remain valid across both versions or users get logged out mid-rollout.

06State, sessions, and routing

  • Stateless instances make rolling deployments trivial, because any instance can serve any request.
  • Local session state forces sticky routing, which makes the mixed-version window visible: a user pinned to an old instance stays on old behavior.
  • Sticky sessions also survive a drained instance poorly, since the user is rescheduled and may notice a behavior change.
  • Move sessions to a shared store or use signed tokens so routing does not need to be sticky.
  • Long-lived connections such as WebSockets need explicit draining, not just removal from the load balancer.
  • Background workers consume from queues and need their own rollout discipline, or they process messages with stale code.

07Rollback is the same process in reverse

  • Reverting means rolling the fleet back to the previous version in batches, which takes about as long as the rollout.
  • Users keep hitting the defective version while the rollback progresses, so the outage lasts for the duration of the reversal.
  • Rollback is only possible if the previous artifact still exists and the previous configuration is still valid.
  • If version 2 wrote data in a new format, version 1 may not be able to read it, so rollback needs a data story too.
  • Pausing a rollout at the first failed readiness check limits how much of the fleet runs the bad version.
  • An automated rollback trigger on error-rate thresholds shortens the window substantially compared with manual detection.

08Observability during a rollout

  • Track metrics per version, because aggregate numbers hide a broken new version behind healthy old instances.
  • Watch error rate, latency percentiles, saturation, and restart counts as the rollout advances.
  • Compare the new version against the old one with the same dashboards, not with different queries.
  • Alert on rollout progress stalls: a rollout that stops advancing is usually a failing probe.
  • Log the version and instance identifier on every request so failures can be attributed quickly.
  • Business metrics matter too: a version can be technically healthy while checkout conversion drops.

09Autoscaling and the controller interact

  • Autoscaling during a rollout can add instances with the new version, changing the version mix outside the controller's plan.
  • Scaling down during a rollout can remove capacity the controller assumed was available.
  • A rollout that depends on spare capacity needs headroom; running at full utilization makes a surge-based rollout impossible.
  • Instance churn from node failures slows rollouts, because replacements must be scheduled and warmed.
  • Freeze autoscaling policy changes during a release if the two systems are not coordinated.
  • Track rollout duration as a metric; a rollout that takes far longer than expected usually indicates scheduling or probe problems.

10Failure modes

  • Stalled rollout: the new version never becomes ready, so the controller holds at a partial mix of versions indefinitely.
  • Capacity exhaustion: batches drain faster than replacements become ready, and the remaining instances are overloaded.
  • Broken dependency assumption: new code requires a migration that has not run yet.
  • Probe mismatch: readiness depends on a downstream that is also being rolled out, creating a deadlock.
  • Stuck connections: long-lived requests outlast the grace period and are killed, producing user-visible errors.
  • Half-migrated data: some rows are in the old format, some in the new, and neither version handles both.

11When rolling is the right default

  • Choose rolling for stateless, multi-instance services where a slow rollback is acceptable.
  • Avoid it when all users must move together, as with a coordinated schema cutover.
  • Avoid it when rollback must be measured in seconds rather than minutes; blue-green or canary fits better.
  • Avoid it for single-instance services, where a rolling update is just a brief outage.
  • Combine it with feature flags so code rolls out gradually while behavior stays dark until release.
  • Combine it with a canary step when metrics can distinguish versions and traffic volume is sufficient.

↔Trade-offs to say out loud

  • Rolling avoids downtime and extra infrastructure, but keeps two versions live against one data layer for the whole rollout.
  • Large batches finish quickly but create a bigger capacity dip and expose more users to a bad build at once.
  • Small batches limit exposure but stretch the mixed-version window and delay detection of fleet-wide problems.
  • maxSurge preserves capacity during the rollout but costs extra compute and can hit quota limits.
  • Strict readiness probes prevent bad instances from serving but can stall rollouts and mask progress.
  • Sticky sessions simplify state handling but expose users to version changes and complicate draining.
  • Fast automated rollback reduces outage time but can thrash if thresholds are noisy and cause repeated flip-flopping.
  • Aggressive rollout speed shortens the change window but leaves less time to observe a bad batch before the next one starts.

?Interview questions

Answer aloud before opening the outline.

1. What is a rolling deployment?

A rollout that replaces instances in batches instead of all at once. Each batch is drained, shut down, replaced with the new version, health-checked, and returned to rotation before the next batch begins. The service stays available if the remaining instances can carry the load.

2. What do maxUnavailable and maxSurge actually control?

maxUnavailable caps how many instances may be down simultaneously, protecting serving capacity. maxSurge allows temporary extra instances so the rollout can proceed without reducing capacity. Together they set the speed of the rollout and the capacity headroom it needs.

3. Why is a rolling deployment risky even when it causes no downtime?

Because two versions run simultaneously against the same database, caches, and queues. A user can be served by either version on consecutive requests, so API shapes, data formats, and message schemas must remain compatible. The absence of downtime does not mean the absence of inconsistent behavior.

4. How do you make a schema change safe during a rolling deploy?

Use expand-and-contract: add the new column or table without removing the old one, make both versions tolerate both shapes, backfill, switch reads, then drop the old structure only after the old code is fully gone. Each step must be compatible with the version mix that exists at that moment.

5. What is the difference between liveness and readiness?

Liveness asks whether the process should be restarted; readiness asks whether the instance should receive traffic. A rolling deployment depends on readiness, because a starting instance is alive but not yet able to serve. Confusing the two sends traffic to instances that cannot handle it or restarts healthy ones unnecessarily.

6. Why is rollback slow in a rolling deployment?

Because reverting means running the same batch process in reverse, replacing instances one batch at a time. Until it finishes, part of the fleet still runs the broken version and keeps serving users. Duration scales with fleet size and readiness time, not with the size of the bug.

7. How can you shorten the exposure window during a bad rollout?

Abort as early as possible: pause on the first failed readiness check, use automated metric thresholds to trigger rollback, and start with a small batch. Per-version metrics and fast alerts are what make early detection possible. Blue-green or canary shortens recovery further if instant switch-back is required.

8. What happens if an instance is removed from the load balancer while requests are in flight?

Without graceful shutdown, those requests fail. The instance should stop accepting new connections, finish in-flight work within a grace period, then exit. The grace period must exceed the longest acceptable request, or long-lived calls are cut off mid-response.

9. How do sticky sessions interact with rolling deployments?

Sticky routing keeps a user on one instance, which preserves local session state but means some users stay on the old version for the entire rollout. When their instance is drained, they are rescheduled and may see changed behavior. Moving sessions to a shared store removes the constraint entirely.

10. What role does autoscaling play during a rollout?

It can add or remove instances while the controller is mid-rollout, changing the version mix and the available capacity. A surge-based rollout needs headroom, which autoscaling may remove under load. Coordinate the two or freeze scaling policy during a release.

11. When would you not choose a rolling deployment?

When recovery must be near-instant, when every user must move together, when the service is a single instance, or when a coordinated data cutover makes mixed versions unsafe. Blue-green, canary, or a maintenance window fits those cases better.

12. How does a rolling deploy combine with feature flags?

The rolling deploy distributes the code safely across the fleet while the feature stays disabled. Once the rollout completes and metrics are healthy, the flag ramps exposure to users. This separates infrastructure risk from product risk, and makes disabling the feature instant.

!Traps

  • Assuming no downtime means no risk, then shipping a schema change that only one version can read.
  • Setting both maxUnavailable and maxSurge to zero, which makes the rollout unable to make progress.
  • Using a liveness probe as the readiness signal so traffic reaches instances that cannot serve requests.
  • Rolling out a service at full utilization with a surge-based strategy and then blaming the platform for the capacity dip.
  • Forgetting that queue consumers and cron workers also need a rollout discipline.
  • Relying on manual detection to trigger rollback, which turns a small bad batch into a fleet-wide incident.
  • Dropping the old database column as soon as the new code ships, breaking instances still running the old version.
