In one lineThe Strangler Fig pattern replaces a legacy system incrementally: a routing layer sends one slice of traffic to new code at a time until the old system has nothing left to serve.
Strangler fig pattern
Growing a new system around an old one and moving functionality across piece by piece until the old system can be retired.
Big-bang rewrite
Building a complete replacement and switching all traffic over on one day, concentrating risk into a single launch.
Routing layer
A facade, proxy, or gateway that decides per request whether the old or new implementation handles it.
Seam
A place in the legacy system where behaviour can be intercepted and redirected without rewriting everything around it.
Branch by abstraction
Introducing an internal abstraction so old and new implementations can coexist behind one interface during a migration.
Dual write
Writing the same change to both old and new stores during coexistence, with reconciliation to catch divergence.
Change data capture
Streaming committed database changes to another system so the new store stays current without application dual writes.
Parallel run
Executing old and new implementations on the same input and comparing results before trusting the new one.
Anti-corruption layer
A translation layer that keeps the legacy model from leaking into the new system's domain model.
Decommissioning
Removing the legacy code path, data, and infrastructure once traffic no longer depends on it.

01The problem with big-bang rewrites

A ten-year-old commerce monolith handles products, carts, orders, payments, and accounts in one codebase, and change has become slow and risky.

  • The team decides to move to a new architecture.
  • The tempting option is to build the replacement from scratch and switch over on one day.
  • That is a big-bang rewrite, and it concentrates years of work into one launch.
  • The business cannot pause new features while the rewrite runs.
  • Nobody can fully specify the legacy behaviour, because much of it lives in code and habit.
  • The cutover becomes a single moment where every user is exposed at once.
  • Most organizations underestimate how long this takes and how much risk it carries.

02Why rewrites fail

  • It takes years, and the business keeps moving during that time.
  • New features must be built twice or the replacement ships already behind.
  • Hidden rules and edge cases exist only in the legacy code and in support tickets.
  • Undocumented behaviour is discovered when the new system answers differently.
  • The old system keeps changing, so the rewrite target moves.
  • One big switchover means one large rollback if anything is wrong.
  • Morale and funding are hard to sustain through a multi-year invisible project.

03Where the name comes from

  • Martin Fowler named the pattern in 2004 after strangler fig trees in Queensland rainforests.
  • A strangler fig starts as a seed in the branches of a host tree.
  • It sends roots to the ground and grows around the host over years.
  • The fig gradually shades and outcompetes the host while standing in the same place.
  • The host dies away and the fig remains, with no single moment of replacement.
  • The metaphor maps directly: new code grows around the legacy system until the legacy system is unnecessary.
  • The important property is continuous operation throughout.

04The pattern

  • Put a routing layer in front of the legacy system so traffic can be directed per capability.
  • Pick one slice of functionality with a clean boundary.
  • Build that slice in the new system while the old one keeps serving everything else.
  • Shift traffic for that slice to the new implementation.
  • Verify behaviour, then delete the corresponding legacy code path.
  • Repeat with the next slice until the old system serves nothing and can be shut down.
  • Each step is independently releasable and reversible.
Introduce a routing layer→Choose one capability with a clean seam→Build it in the new system→Route a small share of traffic to it→Increase traffic while comparing outcomes→Remove the legacy path for that capability→Repeat until the legacy system is empty

05The routing layer

  • The facade is what makes incremental migration possible, and it is the piece teams most often under-build.
  • Options include an API gateway, a reverse proxy, a feature-flag service, or a routing module inside the monolith.
  • Routing can key on path, host, header, user cohort, tenant, or percentage of traffic.
  • Decisions should be configurable at runtime so shifting traffic does not need a deploy.
  • The layer must be observable: every response should say which implementation served it.
  • Keep routing rules simple; a tangle of per-user exceptions becomes unmaintainable.
  • The facade eventually becomes the permanent new edge, so design it as production infrastructure.

06Choosing the first slice

  • Prefer a capability with a clear seam and limited data coupling.
  • Prefer something valuable enough to prove the approach, but not the most critical path.
  • Notifications, search, and reporting are common first candidates.
  • Avoid slices whose data model is entangled with everything else.
  • Avoid slices with the highest regulatory or financial risk for the first attempt.
  • Estimate the data migration effort before committing, not after.
  • The first slice should teach the team how to do the next five.

07Moving traffic gradually

  • Start by sending a small percentage or an internal cohort to the new path.
  • Use shadow traffic to exercise the new code without affecting users.
  • Compare old and new responses on the same inputs to catch behavioural drift.
  • Increase traffic in steps, watching error rate, latency, and business metrics.
  • Keep a fast rollback that flips routing back to the legacy path.
  • Shift per tenant or region when isolation makes incidents easier to bound.
  • Do not declare success on error rates alone; compare business outcomes too.

08Data migration

  • Code is usually the easy part; shared data is what makes migrations long.
  • Decide early whether the new slice owns its data or shares the legacy schema.
  • Backfill existing rows into the new store before or during the traffic shift.
  • Keep the backfill repeatable and idempotent so it can be re-run after a fix.
  • Choose a sync mechanism: dual write, change data capture, or event publication from the legacy system.
  • Plan the write cutover separately from the read cutover; they rarely happen at once.
  • Define reconciliation: how you detect and repair rows that differ between stores.
The riskiest moment is usually the write cutover, because two writers can silently diverge.

09Keeping two systems consistent

  • Dual writes are simple to start but not atomic: one store can succeed while the other fails.
  • Write to the legacy store as the source of truth first, then propagate, and reconcile failures.
  • Change data capture moves committed changes without changing legacy application code.
  • Events published by the legacy system give the new system intent rather than raw row diffs.
  • An anti-corruption layer translates the legacy model so new code does not inherit its concepts.
  • Reconciliation jobs must compare counts, checksums, and sampled records, not just totals.
  • Every temporary sync path needs a removal date, or it becomes permanent plumbing.

10Decommissioning the old path

  • Retiring the legacy code is the step that turns a migration into a completed one.
  • Prove the old path receives zero traffic before deleting it.
  • Remove routing rules, feature flags, and coexistence code together.
  • Archive or delete legacy data according to retention and legal requirements.
  • Shut down unused infrastructure so cost actually falls.
  • Update runbooks, dashboards, and on-call rotations to match the new reality.
  • Celebrate and record the playbook; the next slice will reuse it.

11Failure modes

  • The migration stalls after the first slice and two systems coexist indefinitely.
  • Dual writes drift, and no one notices until a customer reports missing data.
  • Routing logic accumulates exceptions and becomes harder to reason about than the monolith.
  • The new slice silently changes behaviour that downstream systems depend on.
  • Backfills are slow, non-idempotent, or run against a live primary and hurt latency.
  • The team keeps the legacy path as a fallback forever, inheriting both costs.
  • Ownership blurs: the legacy team and new team each assume the other maintains the seam.

12Measuring progress and governance

  • Track the percentage of traffic and the percentage of capabilities migrated.
  • Track the removal of legacy code, not just the addition of new services.
  • Set exit criteria per slice: behaviour match, traffic shifted, legacy path deleted.
  • Publish a migration map so everyone sees what is left.
  • Budget migration work explicitly; feature work will otherwise consume all capacity.
  • Assign one owner per slice with authority to delete the old path.
  • Time-box coexistence and escalate when a slice sits half-migrated.

13Related patterns and decision rules

  • Branch by abstraction creates an internal seam when you cannot route at the edge.
  • Parallel run compares outputs before trusting the new implementation.
  • Expand and contract handles schema changes in compatible steps.
  • Anti-corruption layer keeps legacy concepts out of the new model.
  • Use strangler fig when the old system must keep serving users during modernization.
  • Avoid it when the legacy system is small enough to replace outright or is being retired anyway.
  • It is not a licence to avoid decisions: each slice still needs a target design.

↔Trade-offs to say out loud

  • Incremental delivery reduces launch risk but spreads cost and coordination over a long period.
  • Coexistence keeps users served but doubles infrastructure, data sync, and on-call surface.
  • Routing layer enables gradual cutover but becomes critical infrastructure that must be highly available.
  • Gradual traffic shifts bound incidents to a cohort but require reliable observability to detect drift.
  • Dual writes are easy to start but risk divergence without reconciliation and cleanup.
  • CDC and events avoid application dual writes but add pipeline latency and operational dependencies.
  • Clean seams make extraction cheap but may require refactoring the monolith first.
  • Long migrations preserve business continuity but risk fatigue, stalled slices, and permanent coexistence.

?Interview questions

Answer aloud before opening the outline.

1. What is the Strangler Fig pattern?

It replaces a legacy system incrementally by growing a new system around it. A routing layer sends one capability at a time to the new implementation, and once a slice is proven the old code is removed, until the legacy system can be shut down.

2. Why is a big-bang rewrite risky?

It takes years while the business keeps changing, forces features to be built twice, and depends on undocumented legacy behaviour that is discovered late. All risk lands on one switchover where every user is affected at once.

3. Why is it called strangler fig?

Martin Fowler named it after fig trees that grow around a host tree, gradually taking its place until the host dies. There is no moment where the old tree is removed and replaced, which mirrors incremental migration without a single cutover.

4. What does the routing layer do?

It decides per request whether the legacy or new implementation handles it, based on path, header, tenant, cohort, or traffic percentage. It must be runtime-configurable, observable, and highly available, because it becomes the permanent edge.

5. How do you choose the first capability?

Pick one with a clean seam, limited data coupling, and enough value to prove the approach, but not the most critical or highest-risk path. Notifications, search, and reporting are common starting points. The first slice should teach the team how to do the rest.

6. How do you move traffic safely?

Shadow real traffic and discard responses, then serve internal users, then a canary percentage or region, then ramp in steps while watching errors, latency, and business metrics. Keep a fast routing rollback at every stage.

7. What makes data migration harder than code migration?

Data is shared and stateful: it must be backfilled, kept in sync during coexistence, and cut over for writes without divergence. Code can be routed per request; data needs reconciliation, idempotent backfills, and a clear owner of truth.

8. What is the difference between dual write and CDC?

Dual write makes the application write to both stores, which is simple but not atomic and can diverge. Change data capture reads the legacy database's change log and propagates it, avoiding application changes but adding pipeline latency.

9. How do you detect divergence between old and new systems?

Compare counts, checksums, and sampled records on a schedule, and in a parallel run compare actual outputs for the same inputs. Divergence needs an owner, an alert, and an automated or scripted repair path.

10. Why is decommissioning important?

Without deleting the legacy path, you pay for two systems forever and the migration never finishes. Traffic must be proven zero, routing rules and flags removed, data archived, and infrastructure shut down so cost and complexity actually fall.

11. How do you keep a long migration from stalling?

Set exit criteria per slice, track legacy code removal rather than new services added, budget migration capacity explicitly, give each slice one owner, and time-box coexistence with escalation when a slice sits half-done.

12. When is strangler fig a bad fit?

When the legacy system is small enough to replace outright, is being retired anyway, or has no usable seam to intercept. The pattern pays off when the old system must keep serving real users throughout the change.

!Traps

  • Building the new system for years and planning a single cutover anyway, which is a big-bang rewrite with extra steps.
  • Skipping the routing layer and coupling clients directly to the new services during migration.
  • Dual writing with no reconciliation, so the stores silently diverge.
  • Never deleting the legacy path, leaving permanent coexistence and doubled cost.
  • Letting routing rules accumulate per-user exceptions until nobody can predict behaviour.
  • Migrating the most critical, most entangled capability first and exhausting trust on the hardest slice.
  • Measuring progress by new services built instead of legacy functionality removed.
