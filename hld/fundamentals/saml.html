01The problem: twenty apps, twenty credentials

A company runs email, chat, a code repository, a CRM, an HR portal, and many internal tools. Each with its own username and password.

  • Employees juggle many credential sets and inevitably reuse passwords or write them down.
  • IT creates accounts one by one when someone joins, which is slow and inconsistent.
  • When someone leaves, every application must be disabled individually; one missed account is a standing backdoor.
  • Each application implements its own password policy, reset flow, and MFA, so the weakest one sets the standard.
  • Auditors cannot answer who has access to what without querying every system separately.
  • The fix is central authentication: one place that proves identity, and applications that trust it.
  • SAML is the enterprise standard for that trust relationship, especially in packaged and B2B software.

02What SAML is, and the roles involved

  • SAML is an XML-based standard for exchanging authentication and authorization data between two parties.
  • The principal is the user trying to reach an application.
  • The identity provider authenticates the principal — checking password, MFA, device posture — and issues a signed assertion.
  • The service provider is the application; it does not authenticate, it verifies the assertion and creates a session.
  • Trust is established in advance by exchanging metadata: endpoints, bindings, and signing certificates.
  • The IdP is the single point of authentication and deprovisioning, which is exactly why enterprises adopt it.
  • SAML carries authentication and attributes such as email, groups, and roles, which the SP uses for authorization.

03The SP-initiated login flow

Most integrations use SP-initiated login, where the user starts at the application and is redirected to the IdP.

  • The user requests a protected resource and has no local session, so the SP creates an AuthnRequest.
  • The SP redirects the browser to the IdP's single sign-on endpoint with the request, its issuer, and a request ID.
  • The IdP authenticates the user if needed — password, MFA — and may reuse an existing IdP session.
  • The IdP builds an assertion for that user and returns it to the SP's assertion consumer service.
  • The browser POSTs the response to the SP, which validates the signature, conditions, and audience.
  • The SP maps the asserted identity to a local account, creates its own session, and redirects to the original resource.
  • The browser is only a courier: the security comes from the signature, not from the channel that delivered the message.
User hits a protected page at the SP→SP redirects with a signed AuthnRequest→IdP authenticates the user or reuses its session→IdP returns a signed assertion via the browser→SP validates signature, audience, recipient, and timing→SP creates a session and serves the page

04IdP-initiated login, and its risks

  • In IdP-initiated flow the user starts at the IdP portal and clicks an application tile; the IdP sends an unsolicited assertion.
  • There is no AuthnRequest, so the SP cannot correlate the response with a request it made.
  • That removes the InResponseTo check, which is one of the strongest replay defenses.
  • It is popular because it gives users a single portal, but it weakens validation and complicates session handling.
  • Some SPs disable unsolicited assertions entirely; check before designing a portal-based experience.
  • Where it is required, compensate with strict audience, recipient, timing, and one-time-use checks.
  • Prefer SP-initiated flows unless a product requirement forces the portal pattern.

05Inside the assertion

  • Issuer: which IdP produced the assertion; the SP must match it against configured metadata.
  • Subject and NameID: the user identifier, plus the format that explains how to interpret it.
  • AuthnStatement: when and how the user authenticated, including the method and session index.
  • Conditions: validity window (NotBefore, NotOnOrAfter) and audience restriction to one SP.
  • AttributeStatement: claims such as email, display name, group membership, and role.
  • Signature: a digital signature over the assertion, the response, or both, proving the IdP produced it.
  • Attributes are assertions, not facts — the SP must decide which ones it trusts and how they map to permissions.

06Bindings: how the message travels

  • HTTP-Redirect puts a deflated, base64-encoded message in a query parameter; it is signed but travels through the browser URL bar.
  • HTTP-POST delivers the message as a base64 form field in an auto-submitted HTML form; the usual choice for responses.
  • POST avoids URL length limits and keeps the assertion out of browser history and referrer headers.
  • Artifact binding sends a short reference and the SP retrieves the assertion over a direct back channel.
  • Most deployments use Redirect for the request and POST for the response.
  • Because everything passes through the browser, TLS on both legs is mandatory but is not what authenticates the assertion.
  • Logging full SAML messages is useful for debugging and dangerous for security, since they contain identity data and signatures.

07What a service provider must validate

  • Verify the XML signature with the IdP's configured certificate, and reject unsigned assertions.
  • Confirm the issuer matches the expected IdP entity ID.
  • Enforce the audience restriction so an assertion minted for another application cannot be replayed here.
  • Check NotBefore and NotOnOrAfter with a small, deliberate clock-skew allowance.
  • Check Destination and Recipient against the actual receiving endpoint.
  • Match InResponseTo against a pending request ID, and expire pending requests quickly.
  • Reject replayed assertion IDs by tracking consumed IDs for the validity window.
Every one of these checks has been the sole cause of a real SAML vulnerability. Skipping one turns the IdP into an open door.

08XML signature pitfalls

  • A SAML response is XML, so the SP's parser is part of the attack surface, not just the crypto library.
  • Signature wrapping attacks add a second, forged assertion and move the signed one, exploiting code that validates one element but reads another.
  • Defend by validating the signature over the exact element you then consume, and by rejecting documents with multiple assertions or unexpected structure.
  • XML canonicalization differences can make a valid signature appear invalid, or let an attacker change what was signed.
  • Disable DTD processing and external entity resolution to prevent XXE attacks that read local files or reach internal services.
  • Reject duplicate IDs and any assertion whose ID does not match the signed reference.
  • Use a maintained SAML library rather than hand-parsing XML; the edge cases are exactly where implementations fail.

09Replay, time windows, and session lifetime

  • An assertion is a bearer credential: whoever holds it can present it until it expires.
  • Short validity windows limit the damage of interception, but break with large clock skew, so keep hosts time-synchronized.
  • One-time-use enforcement requires shared state across SP instances; without it, a load-balanced fleet may accept a replay.
  • The SP's own session lifetime is a separate decision from assertion validity; long SP sessions extend exposure after a compromise.
  • On logout or role change, the SP must be able to invalidate its session even if the IdP still has an active session.
  • Re-authentication can be forced by requesting a fresh authentication rather than accepting a cached IdP session.
  • Single logout is best-effort: if one SP is unreachable, the chain breaks, so SPs also need their own timeouts.

10Metadata and certificate rotation

  • Metadata declares entity IDs, endpoints, bindings, and signing certificates; exchanging it is the setup step for trust.
  • Entity IDs must be stable and unique; changing one looks like a different IdP or SP and breaks trust.
  • Certificates expire, and an expired signing certificate takes down every integration at once, so track expiry centrally.
  • Rotation requires publishing the new certificate in metadata before switching signing, so SPs can trust both during the overlap.
  • Some SPs only accept one certificate; coordinate the window or the login will fail mid-rotation.
  • Never disable signature validation to fix a certificate mismatch; fix the metadata or the clock.
  • Automate metadata refresh where the platform supports it, and alert when it fails, because silent staleness precedes an outage.

11Provisioning, attributes, and deprovisioning

  • Just-in-time provisioning creates the local account on first successful login from assertion attributes.
  • Attribute mapping decides identity: which claim is the username, which groups become roles, which department drives access.
  • Trusting an arbitrary attribute for authorization is dangerous; validate it against a known set and apply least privilege.
  • Multi-valued group attributes need a mapping policy, not an implicit first value wins.
  • Deprovisioning is only as good as the IdP's lifecycle: disable the IdP account and access stops at the next login or session expiry.
  • Existing SP sessions survive IdP deactivation unless the SP checks back or enforces short session lifetimes.
  • For sensitive applications, combine SAML with SCIM-style provisioning so accounts and roles are pushed, not just inferred at login.

12SAML versus OIDC, and common failures

  • SAML is XML and browser-post based; OpenID Connect is JSON and OAuth 2.0 based, with tokens over HTTP.
  • SAML dominates enterprise and packaged software; OIDC dominates mobile, single-page apps, and modern APIs.
  • SAML assertions are signed documents; OIDC uses signed ID tokens plus access tokens for APIs.
  • Both solve SSO; the choice is usually dictated by what the application and the IdP support, not by protocol preference.
  • Common failure: certificate expired or rotated without updating metadata, producing a login outage for every user.
  • Common failure: clock skew outside the validity window, causing intermittent failures that look random.
  • Common failure: a permissive implementation that skips audience or signature checks, which is invisible until it is exploited.

↔Trade-offs to say out loud

  • Central SSO through SAML simplifies access and deprovisioning but makes the IdP a single point of failure for every application.
  • IdP-initiated flow offers a convenient portal but loses the request-correlation check that blocks replays.
  • Short assertion validity limits replay exposure but breaks under clock skew and slow networks.
  • JIT provisioning removes a provisioning integration but leaves accounts created from unverified attributes.
  • Single logout improves the security story but is unreliable across SPs and often best-effort.
  • HTTP-POST binding keeps assertions out of URLs but requires an auto-submitting form and careful CSP handling.
  • Rich attribute mapping enables fine-grained authorization but couples app permissions to IdP group hygiene.
  • Strict signature validation blocks wrapping attacks but requires a correct, maintained XML stack that is harder to debug.

?Interview questions

Answer aloud before opening the outline.

1. What problem does SAML solve?

It centralizes authentication so users log in once at an identity provider and many applications trust that assertion. That removes per-application credentials, makes onboarding and deprovisioning a single action, and gives IT a consistent place to enforce MFA and policy. The applications keep their own authorization and sessions.

2. What are the roles in a SAML deployment?

The principal is the user, the identity provider authenticates them and issues a signed assertion, and the service provider validates that assertion and grants access. Trust is established in advance by exchanging metadata containing endpoints and certificates. The browser carries messages between the two parties.

3. Walk through an SP-initiated login.

The user requests a protected resource and the SP redirects them to the IdP with an AuthnRequest. The IdP authenticates or reuses a session, builds a signed assertion, and returns it through the browser to the SP's assertion consumer service. The SP validates signature, issuer, audience, recipient, timing, and request correlation, then creates its own session.

4. Why is IdP-initiated login riskier?

Because there is no AuthnRequest from the SP, so the response cannot be correlated with a pending request and the InResponseTo replay defense is unavailable. The SP must rely more heavily on audience, recipient, timing, and one-time-use checks. It is convenient for portals but should be avoided when SP-initiated flow is possible.

5. What is inside a SAML assertion?

An issuer, a subject with a NameID, an authentication statement describing when and how the user authenticated, conditions with a validity window and audience restriction, and an attribute statement with claims such as email and groups. The whole document, or the response containing it, is digitally signed by the IdP.

6. Why must the SP check the audience restriction?

An assertion is valid only for the application it was minted for. Without an audience check, an assertion obtained for one application could be replayed against another that trusts the same IdP. Audience plus recipient and destination checks bind the assertion to one specific endpoint.

7. What is a signature wrapping attack?

It exploits XML parsing ambiguity: the attacker keeps the genuinely signed assertion somewhere in the document but inserts a forged one where the application actually reads identity data. The signature still validates, yet the effective identity is the attacker's. Defenses include validating and consuming the same element, rejecting extra assertions, and using a hardened library.

8. How do you prevent assertion replay?

Use short validity windows, enforce audience and recipient, correlate responses to pending requests with InResponseTo, and reject assertion IDs already consumed during their validity window. The last check needs shared state across instances, which is easy to miss behind a load balancer. Keep hosts synchronized so the window is not widened by clock skew.

9. How does certificate rotation work in SAML?

Publish the new signing certificate in metadata while the old one is still valid, so service providers can trust both, then switch signing and later remove the old certificate. The overlap window is essential because many SPs accept only one certificate. Track expiry centrally, since an expired certificate breaks every integration at once.

10. Does SAML handle user provisioning and deprovisioning?

Only partially. SAML can carry attributes and support just-in-time account creation at first login, but it does not push updates or deletions. Deprovisioning relies on the IdP disabling the account, and existing SP sessions persist until they expire. For strict lifecycle control, pair SAML with a provisioning protocol that pushes account state.

11. SAML or OIDC — how do you choose?

Choose based on what the application and IdP support and on the client type. SAML is the norm for enterprise and packaged software, while OIDC fits mobile apps, single-page apps, and API access with bearer tokens. Both provide SSO; the difference is XML documents versus JSON tokens and the ecosystem around each.

12. What usually breaks a SAML integration in production?

Expired or rotated certificates that were not published in metadata, clock skew outside the validity window, and mismatched entity IDs or assertion consumer URLs. Permissive validation that skips signature or audience checks is worse, because it fails silently and securely only by luck. Central expiry monitoring and message-level logging catch most of these early.

!Traps

  • Skipping audience or recipient validation because the signature checked out.
  • Hand-parsing SAML XML and validating a different element than the one used to identify the user.
  • Rotating the IdP signing certificate without publishing it in metadata first, causing a total login outage.
  • Relying on IdP-initiated assertions for sensitive apps and assuming replay protection is still in place.
  • Treating SAML attributes as trusted roles without validating them against an allowlist.
  • Assuming deprovisioning is instant when existing SP sessions remain valid until expiry.
  • Enabling full SAML message logging in production and leaking identity data and long-lived assertions.
