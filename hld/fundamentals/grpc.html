01What gRPC is

  • You describe a service and its methods in a .proto file, and tooling generates client and server code.
  • Calling a remote method looks like calling a local function, which keeps service code readable.
  • The framework handles serialization, transport, deadlines, and status propagation.
  • It is strongly typed: the schema is the contract, and generated stubs prevent drift between services.
  • It is designed primarily for internal service-to-service traffic, not for browser-facing APIs.
  • Browsers cannot speak raw gRPC, so public surfaces usually use gRPC-Web, a proxy, or a REST facade.
  • The initial learning cost is tooling and build integration, not the call model itself.

02Protocol Buffers and the .proto contract

  • Messages are declared as typed fields, each with a name, type, and a numeric field number.
  • The wire format is binary and uses field numbers, not names, so payloads are compact and parsing is fast.
  • Fields are optional by default in proto3, with explicit optional presence where you need it.
  • Repeated fields model lists, and nested messages model structure, so the schema is a real data model.
  • Enums are numeric on the wire, so unknown values must be handled rather than crashing.
  • Never reuse or renumber a field number; reserve retired numbers and names instead.
  • JSON is available as an alternative encoding, which helps debugging but gives up the size advantage.
  • The same message definitions can generate code for many languages, which is why polyglot fleets use it.
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrders (WatchRequest) returns (stream OrderEvent);
}

message GetOrderRequest {
  string order_id = 1;
}

message Order {
  string order_id = 1;
  int64 total_cents = 2;
  string currency = 3;
}

03HTTP/2 transport

  • gRPC uses HTTP/2 as its transport, which gives multiplexed streams over one connection.
  • Many concurrent calls share a connection, so you avoid a handshake per request.
  • Header compression reduces repeated metadata overhead across calls.
  • Binary framing carries length-prefixed messages, which is what enables streaming.
  • Flow control per stream stops a fast sender from overwhelming a slow receiver.
  • Because one connection carries many calls, connection-count-based load balancing is misleading for gRPC.
  • Some proxies and load balancers handle HTTP/2 unevenly, so check end-to-end support before designing around it.

04Communication patterns

  • Unary: one request, one response, the default for ordinary RPCs.
  • Server streaming: one request, many responses, good for feeds, logs, and progress.
  • Client streaming: many requests, one response, good for uploads and aggregation.
  • Bidirectional streaming: independent streams both ways, used for chat and real-time sync.
  • Streaming keeps a call open, so it needs explicit deadlines, cancellation, and backpressure handling.
  • Streams are not resumable by default: if the connection drops, the call fails and the client must restart.
  • Choose streaming only when the interaction is genuinely incremental; a unary call is simpler to operate.

05Code generation and schema evolution

  • The .proto file is the source of truth; generated code is a build artifact, not something to hand-edit.
  • Changing a field number or type breaks compatibility with peers built against the old schema.
  • Adding a new field with a new number is backward compatible: old readers ignore it, new readers default it.
  • Removing a field requires reserving its number and name so nobody reuses them by accident.
  • Renaming a field changes generated code but not the wire format, so it breaks source compatibility, not data compatibility.
  • Version the package or service name when a change cannot be made additively.
  • Keep generated code in the build pipeline so contract changes are reviewed like any other API change.
Field numbers are the contract; field names are a convenience for developers. That distinction explains most protobuf compatibility rules.

06Deadlines, cancellation, and retries

  • Every call should set a deadline, and the remaining budget should propagate to downstream calls.
  • When a deadline expires the call fails with a status code, and the server should stop working on it.
  • Cancellation propagates through context, so abandoned client work does not keep consuming server capacity.
  • Without deadlines, a slow dependency turns into thread or connection exhaustion across the fleet.
  • Retries belong in an interceptor with a policy: only retry idempotent methods or transient status codes.
  • Retries need backoff, jitter, and a budget, or a degraded service receives multiplied traffic.
  • Because a timeout is an unknown outcome, non-idempotent calls need an idempotency key before retrying.

07Metadata, interceptors, and auth

  • Metadata carries key-value pairs such as bearer tokens, trace IDs, and tenant identifiers.
  • Interceptors are the middleware layer: authentication, logging, metrics, retries, and rate limiting.
  • Server interceptors can enforce auth uniformly instead of repeating checks in every handler.
  • Client interceptors attach credentials and propagate tracing headers automatically.
  • Metadata is not a place for large payloads; it is transmitted per call and often compressed with headers.
  • Use mutual TLS or token-based auth for service identity, and keep authorisation decisions in the service.
  • Propagate the same request ID across services so one trace shows the whole call graph.

08Load balancing and service discovery

  • Because HTTP/2 multiplexes, a single long-lived connection can pin all traffic to one backend.
  • Client-side load balancing lets the caller spread calls across endpoints it discovers itself.
  • Layer 7 proxies that understand HTTP/2 can balance per stream instead of per connection.
  • Headless service discovery plus client-side balancing is the common Kubernetes pattern for gRPC.
  • Least-request or power-of-two policies fit better than connection counts for multiplexed traffic.
  • The gRPC health checking protocol lets balancers and orchestrators probe real service health.
  • Service mesh sidecars can handle balancing, mTLS, and retries without changing application code.
The classic “connections are balanced but all traffic goes to one pod” failure is a gRPC-specific trap caused by connection-level balancing.

09Performance characteristics

  • Binary Protobuf payloads are typically smaller and cheaper to parse than JSON text.
  • Connection reuse and multiplexing remove repeated handshakes under high call volume.
  • Streaming avoids repeated request overhead when transferring many small messages.
  • Schema-based code generation removes runtime reflection and hand-written mapping in many cases.
  • These gains are largest for high-volume internal calls and smallest for low-traffic public endpoints.
  • Payload size is not the only cost: serialization, TLS, and network hops often dominate.
  • Measure before assuming gRPC is faster; a JSON API with connection reuse can be fast enough.

10gRPC vs REST, and when to use it

  • Choose gRPC for internal, high-volume, strongly typed service calls, especially in polyglot systems.
  • Choose it when streaming or low per-call overhead is a real requirement.
  • Choose REST for public APIs, browser clients, and anything that benefits from HTTP caching and ubiquity.
  • Choose GraphQL when client-driven response shaping matters more than call efficiency.
  • gRPC's weakness is operational and human: binary payloads are harder to debug, and browser support needs a bridge.
  • Contracts need governance, because a shared .proto becomes a dependency between teams.
  • A common architecture uses gRPC internally with a REST or GraphQL edge for clients.

↔Trade-offs to say out loud

  • Binary Protobuf is compact and fast but unreadable without tooling during debugging.
  • Schema-first contracts prevent drift but make every change a cross-team coordination event.
  • HTTP/2 multiplexing cuts handshakes but breaks connection-count load balancing.
  • Streaming enables incremental interaction but adds backpressure, cancellation, and non-resumable failure.
  • Code generation removes boilerplate but couples builds to the protobuf toolchain.
  • Deadlines everywhere prevent runaway work but require careful budget propagation across services.
  • Interceptors centralise cross-cutting concerns but can hide retries and auth behind opaque layers.
  • Binary protocols discourage casual inspection, which is good for efficiency and bad for incident response.
  • A shared proto repository improves consistency but creates a release-coupling bottleneck.

?Interview questions

Answer aloud before opening the outline.

1. What is gRPC in one paragraph?

A remote procedure call framework where a service is defined in a .proto contract, client and server code is generated, and calls run over HTTP/2 with compact binary messages. It makes a remote call look like a local method while the framework handles serialization, deadlines, and status codes.

2. How does gRPC differ from REST?

REST is a resource-oriented style over HTTP with text representations such as JSON, while gRPC is a method-oriented RPC framework with a required schema and binary payloads over HTTP/2. gRPC is better for internal high-volume calls; REST is better for public, cacheable, browser-facing APIs.

3. Why does gRPC use HTTP/2?

HTTP/2 provides multiplexed streams over one connection, header compression, and binary framing with flow control. Those features make many concurrent calls and true streaming possible without opening a connection per request.

4. What are the four call types?

Unary (one request, one response), server streaming (one request, many responses), client streaming (many requests, one response), and bidirectional streaming (independent streams both ways). Unary covers ordinary CRUD; streaming suits feeds and real-time sync.

5. Why must you never reuse a protobuf field number?

The wire format identifies fields by number, not name. Reusing a retired number makes an old peer interpret a new field as the old one, silently corrupting data, so retired numbers and names should be reserved.

6. How do you evolve a proto safely?

Add fields with new numbers and leave existing ones alone. When removing a field, reserve its number and name, and start a new package or service version for changes that cannot be made additively.

7. Why are deadlines important in gRPC?

A deadline bounds how long a call may take and propagates the remaining budget downstream, so abandoned work is cancelled instead of consuming capacity. Without them, one slow dependency can exhaust threads and connections across the fleet.

8. What is the gRPC connection-pinning problem?

Since HTTP/2 reuses one long-lived connection for many calls, a connection-level load balancer sends all of a client's traffic to one backend. Fix it with client-side balancing, per-stream L7 balancing, or a service mesh.

9. How does gRPC handle errors?

It uses canonical status codes plus optional error details, returned as trailers. Handlers map domain failures onto these codes so clients can branch on a stable, protocol-level signal instead of parsing messages.

10. Can browsers call gRPC directly?

No. Browsers do not expose the HTTP/2 features gRPC requires, so you need gRPC-Web with a proxy or a REST or GraphQL facade at the edge.

11. Where do interceptors fit?

They are the middleware layer around calls and streams, used for authentication, metadata propagation, tracing, metrics, retries, and rate limiting. Centralising them keeps handlers focused on business logic and makes policy consistent.

12. When should you avoid gRPC?

For public APIs and browser clients where ubiquity and HTTP caching matter, for simple low-volume endpoints where tooling cost outweighs the benefit, and for teams without the build and debugging tooling to support binary protocols.

!Traps

  • Balancing gRPC by connection count and sending all traffic to a single healthy pod.
  • Omitting deadlines, so a slow dependency exhausts capacity across the fleet.
  • Reusing retired protobuf field numbers and silently corrupting data for older peers.
  • Retrying non-idempotent calls in an interceptor without an idempotency key.
  • Exposing raw gRPC to browsers and expecting it to work without a proxy.
  • Treating a shared proto repository as free, then blocking every team on one release.
  • Assuming binary encoding alone makes the system fast, without measuring actual latency.
