01The problem block storage solves

A database updates thousands of small pieces of data per second: one balance, one order row, one index entry. Each change touches a few kilobytes somewhere in the middle of a large set of files.

  • Object storage treats each object as an indivisible unit, so changing a few bytes means rewriting the whole object.
  • Object requests travel over HTTP, which adds latency a millisecond-scale database cannot absorb.
  • A database needs disk-like behaviour: fast access at any offset and in-place updates of small regions.
  • Block storage provides exactly that by exposing addressable fixed-size blocks.
  • The cost is that block storage knows nothing about files, so something above it must supply that structure.
  • Choosing block storage is really choosing a low-level, high-performance substrate for a stateful component.

02What block storage is

  • Data is stored as a sequence of fixed-size blocks, each identified only by a numeric address.
  • There are no file names, no directories, and no metadata describing meaning.
  • The device understands essentially two operations: read this block, write this block.
  • A common block size is 4 KB, so a 1 TB volume is roughly 268 million blocks.
  • The disk in a laptop is block storage; in the cloud it is a virtual disk attached to a server.
  • Because blocks are addressable, the server can overwrite any region without touching the rest.
The absence of structure is the feature: the upper layer decides what the bytes mean, and block storage just moves them.

03How files map to blocks

Attaching a volume gives the operating system a raw disk. Formatting it with a file system such as ext4, XFS, or NTFS creates the mapping from files to blocks.

  • The application asks the file system to write a number of bytes at an offset in a file.
  • The file system translates that offset into one or more block addresses.
  • The block device overwrites only those blocks; nothing else on the volume changes.
  • This is what makes small, random, in-place updates cheap.
  • Databases sometimes bypass the page cache with direct I/O so they control their own buffering.
  • Underneath either approach, the device sees the same thing: reads and writes to numbered blocks.
Database requests an 8 KB write at an offset→File system maps the offset to block addresses→Block device overwrites exactly those blocks→Write is acknowledged once the device has persisted it

04Local block storage

  • The disk is physically inside or directly attached to the server, typically NVMe or SSD.
  • Traffic never crosses a network, so latency is the lowest available, often well under a millisecond.
  • It can deliver very high IOPS and throughput for the price.
  • The data is bound to that machine: if the server fails, the data is lost or stranded.
  • Cloud local disks are usually ephemeral and survive only a reboot, not a stop or host failure.
  • It fits caches, temporary and spill files, and systems that already replicate data across nodes.

05Network-attached block storage

  • The volume lives on separate storage hardware and the server reaches it over the network.
  • From the server's view it is still a normal disk: format it, mount it, read and write blocks.
  • Traditional data centres use a SAN with iSCSI or Fibre Channel; clouds offer the same model as a managed service.
  • Because storage is independent of compute, a replacement server can attach the same volume and continue.
  • Volumes can usually be resized, retiered, and snapshotted without touching the server.
  • The trade-off is a network hop, so latency is higher than a local NVMe drive.

06Measuring performance: IOPS, throughput, and latency

  • IOPS counts individual operations per second; small random database reads are limited by it.
  • Throughput measures bytes per second; large sequential scans and backups are limited by it.
  • The two are linked: throughput = IOPS × operation size.
  • A 4 KB random workload can exhaust IOPS long before it uses the available bandwidth.
  • A large sequential read can hit the throughput ceiling with very few operations per second.
  • Latency is the time for one operation; a transaction doing several dependent reads accumulates it.
  • Latency rises sharply as a volume approaches its limits because requests begin to queue.
  • Cloud providers usually let you provision IOPS and throughput separately, at a price.

07Inside cloud block storage

  • A cloud volume is not one physical disk; it is split into pieces spread across many storage servers.
  • Each piece is replicated to multiple servers, so one disk or server failure does not lose data.
  • A write travels over the network to the storage servers responsible for that block.
  • The write is acknowledged only after the replicas have stored it.
  • Replication usually stays inside a single availability zone to keep write latency low.
  • That ties the volume to one zone: a server in another zone generally cannot attach it.
  • A zone-wide outage therefore makes the volume unavailable even though the data is replicated.
  • This is why snapshots and cross-zone database replicas still matter.
Replication protects against device failure inside the zone. It does not protect against zone failure or operator error.

08One volume, one server

  • A block volume is normally attached to exactly one server at a time.
  • The reason is the file system: it assumes it is the only writer and caches its own block allocation state.
  • Two servers writing through ordinary file systems can allocate the same block to different files and corrupt both.
  • Some providers offer multi-attach, but only for volume types designed for it.
  • Safe multi-attach requires a cluster-aware file system or an application that coordinates block access itself.
  • When many servers must share the same files, file storage is usually the simpler answer.
  • Shared-nothing designs avoid the problem by giving each node its own volume and replicating at the application layer.

09Snapshots

  • A snapshot captures the volume's state at a point in time.
  • Snapshots are typically incremental: the first copies all data blocks, later ones store only changed blocks.
  • Each snapshot still restores the full volume because it references unchanged blocks held by earlier ones.
  • Snapshots usually live in object storage, which is far more durable than the volume itself.
  • They support backups, cloning a volume for testing, and moving data across zones or regions.
  • Consistency matters: a snapshot of a live database can look like an abrupt power loss.
  • Databases should flush writes first or rely on their own crash recovery, such as replaying a write-ahead log.
  • A volume restored from a snapshot can be slow at first while blocks are lazily fetched.

10Scaling block storage

  • Block storage scales vertically: grow the volume, or move it to a faster tier with more provisioned IOPS.
  • On many cloud platforms these changes can happen while the volume stays attached.
  • After resizing, the file system must still be extended to use the new space.
  • Every volume type has hard maximums for size, IOPS, and throughput.
  • Because a volume serves one server, it cannot absorb unlimited traffic from many machines.
  • Past those limits, add servers each with their own volume — read replicas, shards, or partitioned brokers.
  • Striping several volumes with software RAID 0 adds their IOPS and throughput, but losing one volume loses the array.
  • Striping is only safe when the data is protected elsewhere, such as by replication.

11Where block storage sits in a design

  • Relational databases store data files and write-ahead logs on block volumes.
  • NoSQL databases such as MongoDB and Cassandra do the same on each node.
  • Message brokers store log segments on a volume attached to each broker.
  • Search engines keep their indexes on block storage.
  • Every cloud virtual machine boots from a block volume.
  • In each case the application owns the higher-level concerns: replication across zones and sharding across nodes.
  • A single volume in one zone does not make a component highly available; the database or managed service must add that.

12When to use block storage

  • Choose block storage when one server needs fast, low-latency access to frequently changing data.
  • Classic fits: databases, transaction logs, virtual machine disks, and search indexes.
  • Choose local storage for the lowest latency when the application already replicates data elsewhere.
  • Choose network-attached storage when data must survive server failure and you want snapshots and resizing.
  • Avoid block storage when many servers need to share the same files; use file storage.
  • Avoid it for huge amounts of media, backups, or logs; object storage is cheaper and simpler.
  • Match the choice to the access pattern, not to what is familiar.

↔Trade-offs to say out loud

  • Block storage gives low-latency random access, but it has no structure of its own, so a file system or database must impose one.
  • Local NVMe offers the best latency and IOPS, but the data dies with the instance and cannot be resized.
  • Network-attached volumes survive server loss and support snapshots and resizing, but every I/O pays a network hop.
  • In-zone replication keeps write latency low, but leaves the volume vulnerable to a zone outage.
  • Incremental snapshots are cheap to take repeatedly, but restoring produces a cold volume with slow first reads.
  • Vertical scaling avoids distributed complexity, but each volume type has a hard ceiling on size and IOPS.
  • Striping volumes multiplies throughput, but any single volume loss destroys the whole array.
  • Multi-attach lets several servers reach one volume, but only with cluster-aware file systems and careful coordination.

?Interview questions

Answer aloud before opening the outline.

1. What is block storage?

Storage exposed as a sequence of fixed-size blocks, each identified by a numeric address, with no file names or metadata. A file system on the server maps files onto those blocks. This allows small, random, in-place reads and writes.

2. Why not put a database on object storage?

Object storage treats each object as a whole, so changing a few bytes requires rewriting the entire object. Requests also go over HTTP, which adds far too much latency for a database needing millisecond responses. Databases need addressable, in-place writes, which is what block storage provides.

3. How does a file system relate to block storage?

The file system is the layer that gives blocks meaning: it tracks which blocks belong to which file and translates a file offset into block addresses. The block device itself only knows reads and writes at addresses. Formatting a fresh volume creates that mapping.

4. Local vs network-attached block storage — how do you choose?

Choose local when you need the lowest possible latency and the data is replicated elsewhere, as in Cassandra, Kafka, or Elasticsearch clusters. Choose network-attached when data must survive server failure and you need snapshots, resizing, and reattachment to a new server.

5. Explain IOPS, throughput, and latency together.

IOPS is operations per second, throughput is bytes per second, and latency is time per operation. They are linked by throughput = IOPS × operation size, which is why a small-random workload hits the IOPS limit first and a large-sequential workload hits the throughput limit first. Latency rises when the volume is saturated and requests queue.

6. Why can a volume be attached to only one server?

Because the file system assumes it is the sole writer and caches block allocation state. Two servers writing through ordinary file systems can allocate the same block to different files and corrupt both. Multi-attach needs a cluster-aware file system or coordinated access.

7. What happens inside a cloud block volume?

The volume is split into pieces spread across many storage servers, and each piece is replicated. A write travels over the network to the responsible servers and is acknowledged after the replicas store it. Replication usually stays within one availability zone to keep latency low.

8. Does in-zone replication make a volume durable enough?

It protects against individual disk and server failures, but not against a full zone outage or an operator deleting data. The volume is tied to its zone, so a zone failure makes it unavailable. Snapshots and cross-zone replicas are still required for real durability and availability.

9. How do snapshots work?

The first snapshot copies all data blocks; later snapshots store only blocks that changed, yet each can still restore the full volume by referencing earlier blocks. They are usually stored in object storage, which is more durable than the volume. They enable backups, cloning, and moving data across zones.

10. What consistency issue do snapshots have?

A snapshot of a live database captures disk state as if the machine lost power, so data still in memory is missing. The restored volume then needs crash recovery, such as replaying the write-ahead log. For clean backups, flush or quiesce writes first.

11. How does block storage scale?

Mostly vertically: enlarge the volume or move to a faster tier with more provisioned IOPS, then extend the file system. Each volume type has maximum size, IOPS, and throughput. Beyond that, add servers with their own volumes and distribute data through replicas or sharding.

12. When is RAID 0 striping of volumes appropriate?

When one server needs more IOPS or throughput than a single volume allows and the data is protected elsewhere, for example by application-level replication. Striping adds the volumes' performance, but losing any one volume destroys the array, so it is not a durability strategy.

!Traps

  • Treating a single-zone volume as highly available because it is replicated inside the zone.
  • Attaching one volume to multiple servers with a normal file system and corrupting the data.
  • Sizing for capacity while ignoring IOPS and throughput ceilings.
  • Assuming a restored snapshot volume performs at full speed immediately.
  • Forgetting to extend the file system after growing the volume.
  • Using block storage for shared files or cheap archives that file or object storage handles better.
  • Taking database snapshots without flushing writes and then finding the backup needs crash recovery.
