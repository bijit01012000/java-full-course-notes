A central repository that holds raw and processed data from many sources in its native format, usually on object storage.
Schema-on-read
The reader interprets the data's structure at query time, so no schema is enforced when the data is written.
Object storage
Durable, cheap, flat-namespaced storage such as S3 or GCS, the usual foundation for a lake.
Data catalog
A metadata service that records datasets, schemas, locations, owners, and partitions so data can be discovered.
Partitioning
Physically organizing files by column values, such as date or region, so queries can skip irrelevant data.
Columnar format
A file layout such as Parquet or ORC that stores values by column, enabling compression and column pruning.
Lakehouse
A lake plus an open table format that adds ACID transactions, schema enforcement, and time travel.
Data swamp
A lake without ownership, cataloging, or quality control, where data exists but cannot be trusted or found.
Small-file problem
A layout with many tiny files that overwhelms metadata operations and degrades query planning.

01Why data lakes exist

A warehouse expects data to be cleaned and modeled before loading. A lake takes the opposite approach: keep everything in its original form and decide later.

  • Companies produce far more data than they can model upfront: events, logs, queries, exports, images, audio, and documents.
  • Some of that data has no known schema yet, and modeling it early would discard detail or block ingestion.
  • Cheap object storage makes it practical to retain raw history at a fraction of warehouse cost.
  • Different teams want different transformations of the same source, so the raw copy becomes the shared origin.
  • A lake also holds non-tabular data that a relational warehouse handles poorly.
  • Flexibility is the selling point and also the risk: without discipline, the lake becomes an unqueryable dump.

02Storage and zones

  • The physical foundation is object storage: durable, replicated by the provider, and effectively unbounded.
  • Object stores offer simple put, get, list, and delete operations; they are not POSIX file systems.
  • Data is organized into zones such as raw, cleaned, and curated or trusted.
  • The raw zone is append-only and immutable; reprocessing starts from it when logic changes.
  • The cleaned zone has parsed, typed, deduplicated data; the curated zone serves analysts and models.
  • Each zone should have named owners, retention rules, and access controls.
  • Separation of storage from compute lets many engines query the same bytes without copying them.
Sources→Raw zone (immutable)→Cleaned zone→Curated zone→Consumers
Keeping the raw layer immutable is what makes a lake replayable. If the first transform overwrites the source data, you lose the ability to fix history.

03Schema-on-read

  • Data is written without a enforced table schema; the reader supplies column names and types when querying.
  • This allows ingestion before the shape or use case is fully known.
  • It also means one bad file can break a query, because nothing rejected it at write time.
  • Different readers may interpret the same files differently, producing inconsistent answers.
  • Type mismatches, changed columns, and corrupt records surface at query time rather than at load time.
  • A catalog with declared schemas restores much of the safety while keeping flexible ingestion.
  • Schema-on-read shifts validation work from the writer to every reader and to the platform team.

04File formats and compression

  • CSV and JSON are easy to produce and read but verbose, weakly typed, and slow to scan at scale.
  • Parquet and ORC are columnar: queries read only the columns they need and compress well.
  • Avro is row-based with a schema, which suits write-heavy event data and schema evolution.
  • Compression such as Snappy, Zstandard, or gzip reduces storage and I/O, at some CPU cost.
  • Columnar files store statistics that let readers skip row groups that cannot match a filter.
  • Many small files are worse than fewer large files; aim for a sensible target file size.
  • Format choice must match access: full-row event replay favors Avro, analytical scans favor Parquet.

05Layout and partitioning

  • Partition by the columns most queries filter on, usually date and sometimes region or tenant.
  • Partitioning creates directory-like prefixes that let engines skip entire groups of files.
  • Over-partitioning produces too many small files and directories, which slows listing and planning.
  • High-cardinality keys such as user ID make poor partition columns; cluster or sort within files instead.
  • A consistent path convention and partition naming scheme is part of the data contract.
  • Late data must still land in the correct partition, so the writer, not the clock, decides the path.
  • Compaction jobs merge small files and rewrite partitions to keep scan performance stable.
Partition pruning only helps if queries filter on the partition column. A beautiful layout that nobody queries by is pure overhead.

06Catalog and metadata

  • A catalog records datasets, schemas, locations, formats, partitions, and ownership.
  • It is the difference between a searchable lake and a bucket that only its author understands.
  • Catalogs support discovery, access control, and lineage integration with the query engine.
  • Schema versions should be tracked so readers know what a table looked like at a given time.
  • Statistics such as row counts and min/max values help the query planner avoid unnecessary scans.
  • A crawler can infer schemas, but inferred types are often wrong and need review.
  • The catalog must be updated as part of the write path, not as an occasional manual cleanup.

07Query engines and separation of storage and compute

  • Engines such as Trino, Presto, Spark, Athena, and warehouse query services read directly from object storage.
  • Storage and compute scale independently: keep petabytes resident and spin up compute only for queries.
  • This makes it cheap to retain data but easy to create runaway query cost.
  • Each engine has its own SQL dialect, functions, and performance characteristics, which affects portability.
  • Query performance depends heavily on file layout, partitioning, and statistics rather than only on engine power.
  • A metastore or catalog shared across engines keeps definitions consistent.

08Governance and security

  • The lake crosses many teams, so access must be controlled per dataset, column, and sometimes row.
  • Classify data at ingestion: public, internal, confidential, and personal data each need different handling.
  • Mask, tokenize, or encrypt sensitive fields such as email, phone, and government IDs.
  • Enforce retention and deletion; a lake that never deletes is a compliance liability.
  • Track lineage from source to derived table so a deletion request or bad source can be traced.
  • Audit who read which dataset and when, especially for regulated data.
  • Without ownership, nobody fixes quality or responds when a dataset is wrong.

09The lakehouse: adding warehouse guarantees

A lakehouse keeps lake storage but adds a table layer that provides the reliability analysts expect from a warehouse.

  • Open table formats such as Delta Lake, Apache Iceberg, and Apache Hudi add a transaction log over data files.
  • They provide ACID commits, so readers never see a half-written batch.
  • They support MERGE, deletes, and updates, which plain Parquet directories cannot do safely.
  • Schema enforcement and evolution become explicit rather than accidental.
  • Time travel queries let teams reproduce a report or roll back a bad write.
  • Background compaction and file pruning manage the small-file problem.
  • The lakehouse narrows the gap with a warehouse but still requires cataloging, governance, and modeling.

10Failure modes and the data swamp

  • No catalog or ownership: data exists, but nobody can find it or knows whether it is current.
  • No quality checks: dashboards read corrupt or duplicated files and look authoritative.
  • Unbounded raw ingestion with no retention policy turns storage into a cost and compliance problem.
  • Too many small files make even simple queries slow and expensive.
  • Schema drift breaks readers because nothing validated the writer's output.
  • Duplicate pipelines compute the same metric differently, so two teams report different numbers.
  • Sensitive data lands in an open bucket because access control was added later.
The lake did not fail because of object storage. It failed because ingestion was treated as the end of the project rather than the start of stewardship.

11Choosing lake, warehouse, or lakehouse

  • Choose a warehouse when the questions are known, the data is structured, and governed SQL performance matters most.
  • Choose a lake when you must retain raw and unstructured data cheaply and use cases are still emerging.
  • Choose a lakehouse when you want lake economics and open formats but need transactions and updates.
  • Most organizations end up with both: a lake for raw and ML data, a warehouse or lakehouse marts layer for BI.
  • The deciding constraints are usually governance, concurrency, query latency, and cost — not storage format alone.
  • Whatever you choose, the catalog and quality layer matter more than the label.

12Designing a lake in an interview

  • Start with the sources and the questions; do not start by naming a file format.
  • Define zones and ownership, and make the raw zone immutable.
  • Choose formats per access pattern: columnar for analytics, row-based for event replay.
  • Partition by the dominant filter column and compact small files on a schedule.
  • Register every dataset in a catalog with schema, owner, and classification.
  • Add quality checks, lineage, retention, and access control before opening the lake to analysts.
  • Plan for backfills by keeping raw history and making derived partitions rebuildable.
Sources→Immutable raw→Catalog and classify→Clean and conform→Quality checks→Curated tables→Governed access

↔Trade-offs to say out loud

  • Schema-on-read speeds ingestion and preserves flexibility but defers errors to query time and every reader.
  • Raw retention enables replay and new use cases but increases storage cost and compliance exposure.
  • Many small files make writes simple but degrade query planning and metadata operations.
  • Partitioning prunes scans but over-partitioning creates a small-file and directory explosion.
  • Open formats avoid lock-in and support many engines but lack the mature optimizer of a proprietary warehouse.
  • Lakehouse table formats add ACID and updates but introduce compaction, catalog, and concurrency complexity.
  • Central lake ownership improves governance but can bottleneck teams; federated ownership moves faster but drifts.
  • Keeping everything maximizes future optionality but conflicts with deletion requirements and cost control.

?Interview questions

Answer aloud before opening the outline.

1. What is a data lake?

A central repository that stores raw and processed data from many sources in native formats, typically on object storage. It is queried by multiple engines and relies on schema-on-read and a catalog rather than upfront modeling.

2. How does a lake differ from a warehouse?

A warehouse enforces schema and modeling before load and optimizes structured SQL. A lake accepts raw data cheaply and applies structure at read time. Warehouses favor governance and performance; lakes favor flexibility, volume, and varied data types.

3. What is schema-on-read and what is the cost?

The reader interprets structure at query time, so ingestion does not need a fixed schema. The cost is that bad or changed data is discovered late, different readers may disagree, and every query pays interpretation overhead.

4. Why does file format matter in a lake?

Analytical queries benefit from columnar formats that read only needed columns and compress well. Row formats suit full-record replay. Poor formats and many small files turn cheap storage into slow, expensive scans.

5. How do you organize a lake?

Use immutable raw, cleaned, and curated zones with named owners. Partition by the dominant filter column, keep files reasonably large, register datasets in a catalog, and apply classification and retention rules.

6. What does a catalog do?

It stores dataset names, schemas, locations, partitions, owners, and statistics so users and engines can find and correctly read data. It is also the anchor for access control and lineage.

7. What is a data swamp and how do you avoid it?

A lake that has lost discoverability and trust. Avoid it with ownership, a catalog, ingestion contracts, quality checks, retention rules, and access control enforced from the start rather than added later.

8. What is a lakehouse?

Lake storage plus an open table format that adds a transaction log, ACID commits, schema enforcement, upserts, and time travel. It gives warehouse-like reliability without moving data into a proprietary store.

9. How do you handle updates and deletes in a lake?

Use a table format that supports MERGE and deletes with snapshot isolation, or rewrite the affected partitions. Plain Parquet directories cannot do this safely under concurrent writers.

10. What is the small-file problem?

Many tiny files force the engine to open and plan across huge numbers of objects, which dominates query time. Compact files periodically and avoid over-partitioning or per-event files.

11. How do you secure a data lake?

Classify data on ingestion, enforce least-privilege access at dataset and column level, mask or tokenize personal data, encrypt at rest and in transit, audit access, and apply retention and deletion policy.

12. When would you still choose a warehouse over a lake?

When the questions are well known, data is structured, many analysts need fast concurrent SQL, and strong governance matters more than raw flexibility. A lakehouse can cover both, but a warehouse is simpler if the scope is narrow.

!Traps

  • Calling any bucket of files a data lake and skipping the catalog.
  • Assuming schema-on-read means no schema management is needed.
  • Partitioning by a high-cardinality column such as user ID.
  • Letting every event become its own small file.
  • Storing personal data in the lake without classification or deletion policy.
  • Building a lakehouse table format and assuming it solves ownership and quality by itself.
  • Keeping raw data forever without a retention or cost plan.
