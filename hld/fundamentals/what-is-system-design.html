In one lineSystem design is the process of deciding which components a system needs, what each one owns, how they communicate, and how data flows between them — so the system meets its functional and non-functional requirements at a level above writing code.

System design
The process of choosing components, assigning responsibilities, defining communication, and shaping data flow to satisfy requirements.
Functional requirement
A statement of what the system must do, such as upload a photo, follow a user, or show a feed.
Non-functional requirement
A statement of how well the system must do something: latency, availability, durability, consistency, or cost.
Building block
A reusable infrastructural component — load balancer, cache, queue, database, object store, CDN — with a known role and cost.
Data flow
The ordered path a request or event takes through clients, services, storage, and asynchronous workers.
Bottleneck
The component or resource whose capacity limits the end-to-end system, and therefore the next thing to fix.
Trade-off
A gain in one quality that is paid for by a loss in another, such as lower read latency at the cost of stale data.
Back-of-the-envelope estimate
A rough calculation of users, requests per second, storage, and bandwidth used to locate pressure points before designing.
Evolutionary design
Adding components only when a measured problem justifies them, rather than building the final architecture on day one.
Pre-signed URL
A time-limited URL that lets a client upload or download directly from object storage without routing bytes through the app server.

01The problem

A photo-sharing app on a single server is a perfectly good design for its first few thousand users. Growth does not change the upload code; it changes the set of problems the architecture must answer.

  • Storage: hundreds of terabytes of photos do not belong in the same database rows as user profiles and captions.
  • Failure: when one server holds the app, the database, and the files, a single crash removes all three at once.
  • Distance: a feed request from India to a server in the United States pays a round-trip penalty on every call.
  • Spikes: a popular account posting a photo can send a million readers at the same object at the same moment.
  • These problems cannot be solved inside one function; they are decided by how the parts are separated and connected.
  • The same feature set can require radically different designs at a thousand users and at ten million.
Growth pressureDesign response
Photo volumeObject storage plus a CDN
Server crashRedundant app servers and failover
Global usersEdge caching and regional deployment
Traffic spikeCache, queue, autoscaling, rate limits
Data growthReplication, partitioning, sharding
A single server is not a mistake at small scale. The mistake is assuming it remains sufficient without measuring.

02What system design means

System design sits one level above code. Code asks whether an algorithm is correct and efficient; design asks whether the components can carry the load and what happens when one of them fails.

  • It decides which components exist and where the boundaries between them are drawn.
  • It assigns each component a responsibility, including which data it owns and which data it only reads.
  • It chooses communication style: synchronous HTTP calls, asynchronous messages, or shared storage.
  • It defines data flow, including where data is cached, replicated, and transformed.
  • It must describe failure behavior, not only the happy path.
  • The architecture diagram is an output of these decisions, not the design itself.
Writing codeDesigning a system
PrimitivesFunctions, classes, data structuresServers, databases, caches, queues, storage
ConnectionsFunction calls and return valuesNetwork requests, messages, replication
Core questionIs this correct and efficient?Can these components handle load, and what happens when one fails?
Unit of changeA function or moduleA component, contract, or deployment topology

03Starting with requirements

You cannot evaluate a design until you know what it must do. Requirements split into functional requirements, which define behavior, and non-functional requirements, which define quality.

  • Functional requirements become features, and each feature maps to an API and a set of components.
  • Non-functional requirements decide capacity, redundancy, storage class, and where the system runs.
  • A 200 ms feed target pushes the design toward caching; an availability target forces more than one server.
  • A durability target changes how and where photos are stored, not just how they are served.
  • Ambiguous requirements are a design risk: write down assumptions and confirm them before drawing components.
  • Start from forces, not products: high write volume, spikes, and asynchronous processing points to a queue, while use Kafka is a conclusion without a reason.

Mapping features to components

  • POST /photos touches the app server, metadata database, and object storage.
  • POST /follows and POST /likes mostly touch the app server and database, but likes may also fan out to feeds.
  • GET /feed touches the app server, cache, database, and CDN for the images.
FeatureAPIComponents involved
Upload a photoPOST /photosApp server, database, object storage, queue
Follow a userPOST /followsApp server, database
Like a postPOST /likesApp server, database, cache
View the feedGET /feedApp server, cache, database, CDN

Estimating scale

  • Convert users into requests per second for reads and writes separately.
  • Multiply average size by volume to estimate storage and egress; photos dominate both.
  • Use the read/write ratio to decide whether caching or write partitioning matters first.
  • Treat estimates as order-of-magnitude inputs, not predictions, and state the assumptions aloud.

04The building blocks

Large systems are assembled from a small vocabulary of components. Most of the design work is choosing which ones are needed and how they connect.

  • Clients and DNS — browsers and mobile apps initiate requests, and DNS turns a domain into a reachable address.
  • Load balancers spread requests across healthy application servers.
  • Application servers run business logic and should stay stateless where possible.
  • Databases store structured data such as users, follows, and photo metadata.
  • Object storage holds large immutable files such as the photos themselves.
  • Caches keep hot reads in memory to avoid repeated database work.
  • CDNs keep copies of static content near users.
  • Message queues move work that does not need to finish during the request into background workers.

05Following an upload through the system

The upload path shows why components are separated. The expensive bytes bypass the application server entirely, and slow post-processing is moved out of the request.

  • The client sends the upload request through the load balancer to an application server.
  • The server writes metadata — owner, caption, timestamp — to the database.
  • The server returns a pre-signed URL so the client can upload the image directly to object storage.
  • Routing image bytes around the app server prevents large uploads from consuming its memory and connection pool.
  • After the upload, the server enqueues a processing job instead of generating thumbnails inline.
  • Workers generate thumbnails and update followers' feeds asynchronously.
  • The user gets a fast acknowledgement while the slow work continues in the background.
Client requests an upload→Load balancer forwards to an app server→App server saves metadata→App server returns a pre-signed URL→Client uploads the image to object storage→App server enqueues a processing job→Worker generates thumbnails and updates feeds

06Following a feed read through the system

Reads take a different path from writes. The goal is to avoid touching the database and the origin image store for every request.

  • The app server checks the cache for the list of post IDs and metadata.
  • On a cache hit, it returns the cached list immediately.
  • On a cache miss, it reads from the database and stores the result in the cache for later requests.
  • Images are served from a CDN, so users download them from a nearby edge node rather than the origin.
  • Each layer exists for a specific reason: CDN for distance, cache for repeated reads, object storage for scale, queue for slow work.
  • A feed read that hits cache and CDN may never touch the database or origin storage at all.

07What we design for

A design is judged against a small set of qualities. They interact, and improving one usually puts pressure on another.

  • Scalability: handling more users, traffic, and data as demand grows.
  • Availability: keeping the service reachable when components fail.
  • Reliability: continuing to behave correctly without losing, duplicating, or corrupting data.
  • Performance: latency per request and throughput across the system.
  • Consistency: whether users and services see the same up-to-date view.
  • Maintainability: how easily the system can be operated, debugged, and extended.
  • Cost: meeting requirements without excess servers, storage, bandwidth, or engineering effort.
QualityQuestion it answersPhoto app example
ScalabilityCan it absorb growth?A few thousand to ten million users

ReliabilityIs the behavior correct over time?A photo is never lost or saved twice

ConsistencyDo all readers see the same truth?Everyone sees the same like count
MaintainabilityCan we change it safely?Add a feature without breaking uploads
CostIs the spend justified?Two servers instead of ten

08Every choice is a trade-off

There is rarely a design that is best at everything. Mature design work is choosing which qualities matter most and explaining the cost of that choice.

  • A cache lowers database load and read latency but introduces staleness and invalidation work.
  • Replication and redundancy improve availability and read capacity but add cost and operational complexity.
  • A queue improves response time and absorbs spikes but makes completion asynchronous and adds duplicates to handle.
  • Sharding improves write scale and storage capacity but makes joins and transactions expensive.
  • Strong consistency simplifies reasoning but usually costs latency or availability.
  • The right question is not which option is best, but which cost is acceptable for these requirements.
ChoiceWhat improvesWhat it costs
Add a cacheRead latency and database loadStaleness, invalidation, another tier
Add replicasRead throughput and failoverReplication lag and routing complexity
Add a queueResponse time and burst absorptionEventual completion and duplicate handling
Shard the databaseWrite scale and data sizeCross-shard queries, resharding, operations

09Designs evolve

Real systems are not built in their final form. They start simple and gain components when a measured bottleneck appears.

  • Start with the simplest topology that meets today's requirements and leaves room to grow.
  • Add a cache when repeated reads overload the database, not because caching is expected.
  • Add a CDN when image delivery distance is the visible problem.
  • Add a queue when background work starts delaying user requests.
  • Adding all of these too early creates more complexity, more debugging surface, and higher cost without proven value.
  • Each new component also adds a failure mode, so it must earn its place.
SymptomTargeted fix
Database overloadedCache or read replicas
Images load slowlyCDN
Background work delays requestsMessage queue
One server cannot hold trafficLoad balancer and more app servers
One database cannot hold writesPartitioning or sharding
Observe a bottleneck→Add one component→Measure again→Keep or remove it

10Why learn system design

Even small features contain design decisions. The Like button is a compact example of caching, synchronization, and spike handling.

  • Cache the like count? Yes, because it is read far more often than it changes — at the cost of a briefly stale count.
  • Update synchronously or asynchronously? A queue gives a fast reply but adds moving parts to run and monitor.
  • What happens during a spike? Add capacity and spread load, which raises cost.
  • The value is not memorizing answers; it is recognizing the forces and explaining the trade-off.
  • These decisions appear in code review and incident response, not only in interviews.

11System design in interviews

The interview is open-ended and has no single correct answer. Interviewers are evaluating how you clarify, estimate, structure, and reason about trade-offs.

  • Clarify requirements before drawing: agree on core features and non-functional targets.
  • Estimate scale with rough users, requests per second, and storage to show where pressure will be.
  • Sketch a high-level design with the main building blocks and the request path.
  • Go deeper into a few important areas such as the database, caching, data flow, or failure handling.
  • Narrate decisions and their trade-offs as you go; a silent diagram communicates very little.
  • The round often influences the level and compensation of the offer, so structure matters as much as breadth.
  • You do not need to memorize known designs if you can reason from building blocks and constraints.
Clarify requirements→Estimate scale→Sketch the high-level design→Go deep on database, caching, data flow, and failures→Summarize trade-offs and open risks
A typical round runs about 45 to 60 minutes. Budget time for requirements and deep dives instead of spending it all on boxes.

12A repeatable way to reason

  • State the problem in one sentence, then list the functional and non-functional requirements.
  • Estimate the dominant load — reads, writes, storage, or bandwidth — before choosing components.
  • Draw the minimum set of components that satisfies the requirements.
  • Trace one write and one read end to end, naming what each component owns.
  • Ask what happens when each component is slow, overloaded, or unavailable.
  • Name the trade-off behind every non-obvious choice.
  • Leave the design evolvable: record what you would add when a specific bottleneck appears.
  • A good design meets today's requirements without spending tomorrow's complexity budget in advance.

↔Trade-offs to say out loud

  • Caching improves read latency and database load but accepts staleness and adds invalidation work.
  • Redundancy improves availability but increases cost and the number of components to operate.
  • Asynchronous processing improves response time and absorbs spikes but gives up immediate completion and introduces duplicate handling.
  • Object storage with pre-signed URLs keeps large files off app servers but adds a second data store and a URL lifecycle to manage.
  • Denormalization and precomputation speed up reads but increase write cost and the risk of inconsistent copies.
  • Strong consistency makes reasoning simple but usually costs latency or availability during failures.
  • Adding components early can future-proof the design but creates complexity before there is evidence it is needed.
  • Optimizing cost can reduce over-provisioning but leaves less headroom for spikes and failover.

?Interview questions

Answer aloud before opening the outline.

1. What is system design?

It is the process of deciding which components a system needs, what each owns, how they communicate, and how data flows between them so the system meets its requirements. It operates at the level of servers, databases, caches, queues, and networks rather than individual functions.

2. How is system design different from writing code?

Code concerns correctness and efficiency inside a program. Design concerns capacity, failure behavior, and coordination across components. A system can have correct code and still fail because the database is a single point of failure or a dependency is slow.

3. What is the difference between functional and non-functional requirements?

Functional requirements say what the system does — upload a photo, follow a user, show a feed. Non-functional requirements say how well it does it — latency, availability, durability, consistency, and cost. Features determine the components; quality targets determine how those components are built and deployed.

4. Why start with requirements instead of choosing technologies?

Technology choices are conclusions, not inputs. Requirements reveal the forces — write volume, spikes, read/write ratio, latency targets — that make one option appropriate. Starting with a tool list produces complexity that may not address the actual bottleneck.

5. Which building blocks appear in most large systems?

Clients, DNS, load balancers, stateless application servers, databases, caches, object storage, CDNs, and message queues. Most designs are a specific arrangement of these, with the interesting decisions in what each component owns and how failure is handled.

6. Walk me through a photo upload.

The client sends the request through the load balancer to an app server. The server stores metadata in the database and returns a pre-signed URL; the client uploads the image directly to object storage. The server then enqueues a job so workers can generate thumbnails and update feeds outside the request path.

7. Why upload directly to object storage instead of through the app server?

Image bytes are large and would consume the app server's memory, bandwidth, and connection slots. A pre-signed URL lets the client write to durable storage directly, keeping the app tier free to handle requests. The trade-off is a more involved upload protocol and URL expiry to manage.

8. Why cache the feed, and what breaks?

The feed is read far more often than it changes, so caching avoids repeated database work and reduces latency. The cost is staleness: a new post may not appear immediately, and invalidation or a short TTL is required. The design must decide how much delay is acceptable.

9. What qualities do we evaluate a design against?

Scalability, availability, reliability, performance (latency and throughput), consistency, maintainability, and cost. They interact: redundancy improves availability but raises cost, and caching improves performance but weakens freshness.

10. Give an example of a system design trade-off.

Adding read replicas increases read throughput and provides failover capacity, but replication is usually asynchronous, so some reads may be stale and read-after-write may need to go to the primary. The benefit is real, but it is not free.

11. Why not add caches, queues, and a CDN on day one?

Each component adds a failure mode, an operational burden, and cost. Without a measured bottleneck, you cannot tell whether the complexity helped. A better approach is to add the component that addresses the current problem and re-measure.

12. How do you estimate scale in an interview?

Start with daily active users and actions per user, convert to average and peak requests per second, separate reads from writes, and estimate storage from item size and retention. State assumptions explicitly and use the numbers to identify which tier feels the most pressure.

13. What is the interviewer actually evaluating?

How you clarify ambiguity, make reasonable estimates, structure a coherent design, trace data flow, and justify trade-offs. They are not looking for a memorized diagram or compilable code; they want to see how you think when requirements change or a component fails.

14. How would you approach a system you have never designed before?

Reduce it to requirements, dominant load, and standard building blocks. Trace the main write and read paths, then examine failure and growth points. Most unfamiliar systems are recombinations of the same primitives, so reasoning from constraints is more reliable than recalling a specific architecture.

!Traps

  • Opening with a technology list such as Kafka, Redis, and Kubernetes before stating requirements.
  • Treating non-functional requirements as optional, then discovering that latency or durability targets invalidate the design.
  • Drawing boxes without assigning responsibilities or tracing which component owns which data.
  • Designing for ten million users on day one and burying the actual requirement in unnecessary complexity.
  • Describing only the happy path and never asking what happens when a dependency is slow or a node dies.
  • Reporting a single availability number for the whole product when checkout is the operation that matters.
  • Mistaking the architecture diagram for the design; the diagram is only a summary of decisions.
  • Ignoring cost and operability, then presenting a design the team could not run or afford.
