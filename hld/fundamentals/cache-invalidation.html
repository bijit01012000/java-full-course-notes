In one lineCache invalidation is how a cached copy is expired, deleted, or refreshed when the source of truth changes — the hard part is doing it without races, misses, or stampedes.
Source of truth
The authoritative store such as a database or object store; a cached value is only ever a copy of it.
Stale data
A cached value that no longer matches the source of truth after an update.
Bounded staleness
An explicit limit on how old a cached value may be, chosen to be acceptable for that feature.
TTL
A time-to-live after which a cached entry expires automatically, regardless of writes.
Invalidation
Removing or refreshing a cached entry when the underlying data changes.
Cache-aside
The application reads the cache, loads from the source on a miss, then writes the value into the cache.
Versioned key
Embedding a version or generation number in the cache key so old entries are simply never read again.
Cache stampede
Many concurrent readers missing on the same key and all hitting the source of truth at once.
Negative caching
Caching the absence of a value so repeated misses for missing data do not hit the source.

01Why invalidation is necessary

Caching keeps frequently accessed data in a faster layer. The problem is that the original data can change while the cached copy does not, and a cached value is only a copy.

  • Product 123 is cached at $100; the database later says $90 and the cache still says $100.
  • Any read served from the cache now returns the wrong price to users.
  • The system holds multiple copies of the same fact, and copies diverge whenever a write happens.
  • Invalidation exists to ensure a cached copy does not stay stale forever.
  • It is a consistency mechanism, not a performance optimization; its failures are correctness bugs.
  • Most production bugs attributed to 'the cache' are actually missing or incomplete invalidation.

02Source of truth and bounded staleness

  • Designate one store as authoritative: the database, object store, or owning service.
  • The cache never decides truth; on disagreement the source wins.
  • Perfect freshness is rarely the goal for every value, and pursuing it defeats the point of caching.
  • Bounded staleness sets an explicit maximum age and states why that age is acceptable for the feature.
  • A price display, an inventory count, and an avatar URL can tolerate very different freshness windows.
  • Writing the tolerated staleness down per data type turns a vague argument into a testable requirement.
DataTypical toleranceReason
Static asset or imageHours or longerContent is immutable or versioned
Product catalog descriptionMinutesOccasional edits, low harm
Price or inventorySeconds or noneWrong values cause direct business harm
User permissionsEffectively noneStale permissions are a security issue

03The three things you can do with a stale entry

  • Expire it: let a TTL remove it after a fixed time, so the next read reloads.
  • Delete it: remove the entry on write so the next read misses and repopulates.
  • Update it: write the new value into the cache at the same time as the source.
  • Each has different failure behavior: expiry tolerates staleness, delete risks a miss storm, update risks writing the wrong value.
  • Most production systems combine them, for example delete on write with a TTL as a safety net.
  • The combination matters more than any single technique.
Write happens at the source→Choose: expire, delete, or update the cached copy→Next read either hits fresh data or misses and reloads→TTL guarantees an upper bound if the explicit step fails

04TTL expiry

  • A TTL is the simplest mechanism: no coordination and no write-path changes.
  • It guarantees staleness is bounded by the TTL, which is often enough.
  • Every expiry also creates a future miss, so a short TTL raises source load.
  • Synchronized TTLs across many keys can expire together and produce a periodic load spike.
  • Randomize TTLs slightly (jitter) so expirations spread out.
  • A TTL is a safety net, not a substitute for handling writes that must be visible immediately.

05Delete on write (cache-aside invalidation)

  • The common pattern: write the database, then delete the cache key.
  • The next read misses and reloads the current value, so the cache converges to the source.
  • Deleting is safer than updating because an update can write a value computed from stale state.
  • The delete can fail — the process dies, the network drops, the cache is briefly unavailable — so a TTL is still required.
  • Ordering matters: delete after the database commit, not before.
  • If the delete fails, the key stays stale until TTL or an explicit repair.
Application updates the database→Transaction commits→Application deletes the cache key→Delete fails -> stale until TTL or repair job→Next read repopulates from the source

06Update on write and write-through

  • Updating the cache on write keeps it warm and avoids a miss after each write.
  • The risk is writing a value derived from stale read state, especially under concurrent writers.
  • If two writers interleave, the slower one can overwrite the newer cached value.
  • Write-through writes the cache and the source in the same logical operation, adding write latency.
  • Write-behind writes the cache first and persists later, which is fast but can lose acknowledged writes on failure.
  • Updating is reasonable when writes are serialized per key or when the update is a pure assignment of the new value.
ApproachLatencyMain risk
Delete on writeLow write cost, extra read missFailed delete leaves staleness
Update on writeLow read costConcurrent writers write out of order
Write-throughHigher write latencyPartial write across two stores
Write-behindLowest write latencyAcknowledged writes lost on crash

07The races that break naive invalidation

  • Stale repopulation: reader misses, loads old value from the source, and writes it to cache after a writer already deleted the key.
  • Delete-before-commit: the cache is cleared, a reader reloads the pre-commit value, and the commit then makes it stale.
  • Delayed double delete: delete, commit, wait briefly, delete again to catch a concurrent repopulation — a mitigation, not a proof.
  • Update with stale computation: a writer computes the new cached value from data it read before another writer committed.
  • Every one of these produces a permanently stale entry that only a TTL will eventually repair.
  • The general defense is to shorten the exposure window and always keep an expiry bound.
Stale repopulation is the classic cache-aside race. It is rare per key and inevitable across a large key space.

08Versioning and generation keys

  • Put a version or generation number in the cache key, such as product:123:v7.
  • An invalidation increments the version, so old entries are simply never read again and expire naturally.
  • Readers never race with writers because the key identity changes instead of the value.
  • The version pointer becomes a small, hot piece of state that must itself be consistent.
  • This pattern is the basis of versioned asset URLs and cache-busting for static content.
  • It trades storage (old entries linger until eviction) for correctness and simplicity.

09Event-driven invalidation

  • Instead of every writer remembering to clear the cache, publish a change event and let a subscriber invalidate.
  • Change data capture from the database log keeps invalidation close to the actual commit, including changes made outside the application.
  • A shared invalidation channel matters when many services write the same data.
  • Events can be lost or delayed, so idempotent invalidation plus a TTL is still required.
  • Invalidation events must include the key or enough data to derive it, and ideally a version to ignore out-of-order delivery.
  • This decouples services but adds a dependency on the messaging path.

10Invalidating across multiple cache layers

  • Requests may pass a browser cache, a CDN, a reverse proxy, an application cache, and a distributed cache.
  • Each layer holds its own copy and must have its own expiry or purge mechanism.
  • Purging the origin cache does not touch a CDN edge or a browser's local copy.
  • Use versioned URLs or explicit purge APIs for shared edge layers; short TTLs for browser layers.
  • Forgetting one layer looks like random staleness that cannot be reproduced in a single environment.
  • Document the invalidation story per layer, not just for the cache closest to the database.
LayerTypical control
BrowserShort TTL or versioned URL
CDN edgeTTL plus explicit purge
Reverse proxyTTL or purge hook
Application / distributed cacheDelete on write, TTL, version key

11Stampedes and thundering herds

  • Deleting a hot key means the next reads all miss simultaneously.
  • Without coordination, every miss queries the source of truth at once.
  • Mitigations: a per-key lock so only one loader refreshes, request coalescing, or serving stale data briefly while refreshing.
  • Keeping a slightly stale value during refresh (stale-while-revalidate) protects availability at the cost of freshness.
  • Warming keys after a purge reduces the empty window for known-hot data.
  • Jittered TTLs prevent many keys expiring in the same second.

12Choosing an approach

  • Start with delete-on-write plus a TTL: simple, and the TTL caps any failure window.
  • Add versioned keys when correctness under concurrency matters more than storage.
  • Use event-driven invalidation when many writers or services touch the same data.
  • Use update-on-write only when writes are naturally serialized or the new value is a complete assignment.
  • Tighten the TTL for data where bounded staleness must be small; lengthen it for immutable data.
  • Whatever you choose, monitor hit ratio, miss latency, and stale-read reports to validate it.
Classify the data and its staleness tolerance→Choose delete, update, or expire→Add a TTL as the bound on failure→Add versioning or events if concurrency demands it→Measure hit ratio and source load

↔Trade-offs to say out loud

  • Short TTLs bound staleness tightly but raise miss rates and source load.
  • Long TTLs protect the source but leave stale data visible for longer after a missed invalidation.
  • Delete on write avoids writing wrong values, but creates a miss immediately after every write.
  • Update on write keeps reads fast, but risks out-of-order writes from concurrent writers.
  • Versioned keys make invalidation race-free, but leave old entries occupying memory until eviction.
  • Event-driven invalidation centralizes logic and covers multiple writers, but adds a messaging dependency and new failure modes.
  • Stale-while-revalidate protects availability during refresh, at the cost of explicitly serving older data.
  • A per-key lock prevents stampedes, but serializes refresh and can become a bottleneck on hot keys.
  • Purging every cache layer gives immediate correctness, but adds operational surface per layer.
  • No TTL at all saves on misses, but turns any missed invalidation into permanent corruption.

?Interview questions

Answer aloud before opening the outline.

1. Why does cache invalidation exist?

A cached value is a copy, and the source of truth can change without the copy changing. Invalidation removes or refreshes the copy so users do not keep receiving outdated results. It is fundamentally a consistency problem, not a performance one.

2. What are the three basic options once data changes?

Expire the entry with a TTL, delete it so the next read reloads, or update it with the new value. Most systems combine them, typically deleting on write and keeping a TTL as a safety net in case the delete fails.

3. What is bounded staleness?

An explicit maximum age a cached value may reach, chosen so the feature still behaves acceptably. Instead of demanding perfect freshness everywhere, you state the tolerance per data type and design the TTL and invalidation to meet it.

4. Why delete instead of update on write?

An update writes a value that may have been computed from stale state, and concurrent writers can apply values out of order. Deleting defers the value computation to the next read, where it comes fresh from the source. The cost is a cache miss after each write.

5. Describe the classic cache-aside race.

A reader misses, reads the old value from the database, and is delayed. A writer commits a new value and deletes the key. The reader then writes its old value into the cache, which stays stale. Only a TTL bounds how long the incorrect value survives.

6. How do versioned keys prevent that race?

Invalidation changes the key's version, for example from product:123:v7 to v8. A late reader writing to the old key does not affect reads, because nobody reads that key anymore. Correctness comes from changing identity instead of racing on the value.

7. Why is a TTL still needed if you invalidate explicitly?

Explicit invalidation can fail: the process can crash, the network can drop, or the cache can be briefly unavailable. A TTL ensures the worst case is bounded staleness rather than permanent staleness, which is what makes the design safe.

8. What is a cache stampede and how do you prevent it?

It is many concurrent misses on the same key all querying the source of truth at once. Prevent it with a per-key refresh lock, request coalescing, staggered TTLs, key warming, or serving slightly stale data while one request refreshes.

9. Your CDN still serves old content after you cleared the origin cache. Why?

Each layer holds an independent copy. Clearing the application cache does not purge CDN edges or browsers. Use versioned URLs or an explicit purge for edge layers, and short TTLs for browser caches.

10. When is event-driven invalidation worth it?

When several services or code paths write the same data and each would otherwise need to remember to invalidate. Publishing change events or using change data capture centralizes the logic and catches writes the application does not control, at the cost of a messaging dependency.

11. How would you pick a TTL for a product price?

Start from the business tolerance: a wrong price is harmful, so the window should be short, and the write path should delete the key explicitly. Then measure source load at that TTL and decide whether the freshness requirement or the capacity constraint has to move.

12. How do you know invalidation is working in production?

Track hit ratio, source load, and age of cached entries, and capture reports of stale values as bugs with the key and timestamp. A sudden hit-ratio drop or rising source load often means invalidation is firing too aggressively or failing repeatedly.

!Traps

  • Adding a cache without any invalidation plan and relying on eviction to fix staleness.
  • Deleting the cache key before the database commit, so a reader repopulates the pre-commit value.
  • Deleting once and assuming it worked, with no TTL as a fallback when the delete fails.
  • Updating the cache from stale read state and overwriting a newer value.
  • Caching permissions or balances with a long TTL and treating staleness as a performance topic.
  • Invalidating a hot key with no stampede protection and knocking over the database.
  • Forgetting that a purge has to reach every cache layer, not just the origin.
