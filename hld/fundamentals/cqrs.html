Command
An intent to change state, such as Place Order or Change Email; it is validated, may be rejected, and does not return query data.
Query
A request for data that must not change state, shaped to answer a specific read need.
Write model
The model that enforces invariants and records state changes, optimized for correctness rather than reporting.
Read model
A denormalized, query-optimized projection of data, often one per screen or use case.
Projection
The process or component that consumes change events and updates one or more read models.
Eventual consistency
A guarantee that a read model will converge to the write state after some delay, not immediately.
Task-based UI
A user interface organized around intents such as cancel or approve, which maps naturally to commands.
Idempotency
The property that applying the same change twice produces the same state, essential when projections consume at-least-once events.
Read-your-writes
A consistency guarantee that a user immediately sees their own successful command reflected in subsequent reads.

01The problem with one model for everything

Most applications start with a single data model used to create, update, and read data. That is usually the right place to start.

  • Writes care about correctness: invariants, uniqueness, and transaction boundaries.
  • Reads care about shape and speed: one response for one screen, without joins at request time.
  • A normalized write schema avoids duplication but forces expensive joins and assembly for display.
  • A denormalized read schema is fast to read but risky to write through without breaking invariants.
  • The same object becomes a compromise: too heavy for writes, too awkward for reads.
  • As read and write volumes diverge, the compromise gets more expensive on both sides.

02What CQRS is: commands versus queries

  • CQRS means Command Query Responsibility Segregation: one model for changing state, another for reading it.
  • A command expresses intent and can be rejected; it does not return query results.
  • A query returns data and must not mutate state.
  • The separation can be only in code, or all the way to separate stores and services.
  • It is a pattern for a bounded context, not a global rule for every table.
  • CQRS is often confused with event sourcing; they are independent choices that combine well.
  • The simplest CQRS is two different models over the same database.

03The write side

  • The write model holds the aggregates and invariants of the domain.
  • Commands are validated against current state before anything is persisted.
  • Writes are transactional over the smallest set of data that must change together.
  • The write side emits facts about what happened — domain events or change records — for the read side.
  • It does not try to answer reporting questions and does not build screen-shaped views.
  • Optimistic concurrency, unique constraints, and version numbers protect against lost updates.
  • Keeping the write model narrow makes invariants easier to reason about.

04The read side

  • Each read model is a denormalized view built for a specific query or screen.
  • Read models can live in a different store: a search index, a document database, or a cache.
  • Multiple read models over the same events are normal, for example a list view and a detail view.
  • Queries never need to join across aggregates; the join happened when the projection was written.
  • Read models can be rebuilt from scratch by replaying the source of change.
  • Because they are disposable, changing a read model is cheaper than migrating the write schema.
  • Isolation lets read traffic scale independently of write traffic.

05Two levels of separation

CQRS is a spectrum. Most teams should start at the light end.

  • Light CQRS: separate command handlers and query objects over one database and one schema.
  • Separate read tables: projections write denormalized tables in the same database.
  • Separate stores: the read side lives in another database, search engine, or cache.
  • Separate services: write and read sides deploy and scale independently.
  • Each step adds capability and adds sync lag, operational surface, and failure modes.
  • Choose the lightest level that fixes the actual problem you measured.
  • Separate stores make the most sense when read and write load profiles differ sharply.

06Keeping the read side in sync

  • The write side publishes changes as events after the transaction commits.
  • A projection subscribes, translates each event, and upserts the read model.
  • Delivery is usually at-least-once, so projections must be idempotent.
  • Ordering matters: an update older than the current row must not overwrite newer data.
  • A durable log or outbox prevents publishing events that never reach the projector.
  • Backfills rebuild new read models from the write side or from retained events.
  • Sync lag is a first-class metric, not an implementation detail.
Command validated against write model→Transaction commits new state→Change event written durably→Projection consumes the event→Read model updated→Query returns the new view

07Eventual consistency and the user experience

  • After a successful command, a query may briefly return the previous view.
  • Users notice this most on save-then-redirect screens and on lists they just edited.
  • Options include reading your own write from the write side, optimistic UI, or waiting for a version token.
  • A read-your-writes route can send a user's reads to a fresher source for a short window.
  • The UI should show a pending state rather than silently displaying stale data.
  • Some domains cannot tolerate lag — for example, a balance check before a withdrawal.
  • Decide the acceptable lag per query, not once for the whole system.
State the lag budget explicitly. A projection that is normally fast but unbounded under backlog is a correctness problem, not a performance one.

08Where CQRS fits

  • Read and write workloads with very different volume or scaling needs.
  • Complex domains where invariants need a clean, narrow write model.
  • Reporting or search needs that do not match the transactional schema.
  • Collaborative or task-based systems where users issue explicit intents.
  • Systems already using events, where projections are a natural consumer.
  • Audit-heavy domains that need a durable record of changes.
  • It fits poorly in small CRUD systems with balanced, simple traffic.

09CQRS and event sourcing are not the same

  • CQRS separates read and write models; event sourcing makes events the source of truth.
  • You can do CQRS with a normal relational write model and no event log.
  • You can do event sourcing with a single model that also serves reads, though it is awkward.
  • Together they are powerful: events are both the history and the feed for projections.
  • Combining them multiplies operational complexity, so adopt each for its own reason.
  • CQRS without event sourcing still needs a change feed, often an outbox or CDC stream.
  • Event sourcing without CQRS usually means rebuilding state on every read, which needs snapshots.

10Failure modes and correctness risks

  • A projection crash creates lag; a poison event can stall an entire partition.
  • Duplicate delivery without idempotency double-counts totals or duplicates rows.
  • Out-of-order events can resurrect deleted records or overwrite newer values.
  • Publishing inside the write transaction without an outbox can lose events on rollback or crash.
  • A read model that silently diverges is worse than a slow one; reconciliation jobs catch drift.
  • Rebuilds can saturate the source database and the projection workers at the same time.
  • Schema changes to events break projections that were not versioned.

11Operational cost and when not to use it

  • Two models to design, test, deploy, monitor, and migrate.
  • Projection infrastructure: consumers, retries, dead letters, checkpoints, replay tooling.
  • Consistency reasoning moves into the application and the UI.
  • Debugging spans the command, the event, the projection, and the query.
  • Small teams with simple domains pay all of this for little benefit.
  • Default to a single model until a measured read or write problem justifies the split.
  • If you only need faster reads, caching or a read replica is usually cheaper.

12Worked example and decision checklist

An order system takes orders and also shows an operations dashboard with totals, statuses, and search.

  • Commands: place order, cancel order, mark shipped — validated against order invariants.
  • Events: OrderPlaced, OrderCancelled, OrderShipped.
  • Projections: an order detail view, an operations list, and a search index.
  • Queries read only the projections and never touch the order aggregate.
  • The dashboard can lag briefly; the confirmation screen reads its own write.
  • A nightly reconciliation compares projection totals with the write database.
  • Decision rule: adopt CQRS when read shape or read scale genuinely conflicts with write correctness.

↔Trade-offs to say out loud

  • Specialized models make reads fast and writes safe but require two models and a translation layer.
  • Independent read scaling absorbs heavy query load but adds stores, infrastructure, and cost.
  • Denormalized read models remove joins at query time but duplicate data and require rebuilds.
  • Event-driven sync decouples the sides but introduces lag, duplicates, and ordering concerns.
  • Rebuildable projections make schema change cheap but demand durable events and replay tooling.
  • Task-based commands clarify intent and validation but push consistency handling into the UI.
  • Separate deployment lets teams move independently but expands the debugging and tracing surface.
  • Event sourcing plus CQRS gives full history and flexible views but is one of the heaviest designs to operate.

?Interview questions

Answer aloud before opening the outline.

1. What does CQRS stand for and what does it separate?

Command Query Responsibility Segregation. It separates the model used to change state from the model used to read it, so writes can enforce invariants and reads can be shaped for specific queries.

2. Why is one model often a problem?

Writes need normalization and invariants; reads need denormalized, screen-shaped data. Forcing one model to do both produces awkward queries and fragile write paths, and read and write load cannot scale independently.

3. What is the difference between a command and a query?

A command expresses an intent to change state, is validated, and can be rejected; it does not return query data. A query returns data and must not mutate anything. The distinction is about responsibility, not about HTTP verbs.

4. Is CQRS the same as event sourcing?

No. CQRS separates read and write models; event sourcing makes an event log the source of truth. You can do CQRS with a normal relational write model, and you can do event sourcing without separate read models. They combine well but are independent decisions.

5. How do the read and write sides stay in sync?

The write side publishes committed changes as events, usually through an outbox or change data capture. Projections consume them idempotently and update the read models, tracking a checkpoint so they can resume and replay.

6. What consistency does CQRS give?

Strong consistency inside the write model for each command, and eventual consistency between the write model and the read models. The lag is usually small but must be bounded and monitored, because it is a correctness property, not just latency.

7. How do you handle read-your-writes?

Route a user's reads to the write side or a fresh replica for a short window after their command, use a version token to wait for the projection to catch up, or show an optimistic pending state. Which one depends on how much the user notices the gap.

8. What happens if a projection processes an event twice?

Nothing if projections are idempotent: upserts keyed by entity and version, deduplication by event ID, or conditional writes that ignore older versions. Without that, duplicates inflate totals and create repeated rows.

9. How do you rebuild a read model?

Reset the projection checkpoint, replay retained events or run a backfill query from the write side, then switch reads over once the rebuild catches up. This requires durable events or a reliable change feed and enough capacity to replay without harming live traffic.

10. When would you not use CQRS?

Small CRUD systems with balanced, simple traffic, or cases where caching or a read replica solves the read problem. CQRS adds a second model, sync infrastructure, and consistency reasoning that must be justified by a measured conflict between read and write needs.

11. What is the lightest form of CQRS?

Separate command handlers from query objects while sharing one database and schema. It clarifies code and validation without distributed sync. If reads still hurt, add denormalized read tables, and only then consider separate stores or services.

12. How does CQRS affect the UI?

Commands map to explicit user intents, which suits task-based interfaces. The UI must handle the possibility that a query briefly lags a just-completed command, so it needs pending states, version checks, or a read-your-writes path.

!Traps

  • Applying CQRS to every bounded context instead of the one place where read and write needs actually conflict.
  • Claiming strong consistency between write and read models while syncing asynchronously.
  • Publishing events inside the write transaction without an outbox, losing them on rollback or crash.
  • Writing non-idempotent projections and then discovering at-least-once delivery duplicates data.
  • Treating eventual consistency as a latency detail instead of a user-visible correctness concern.
  • Building CQRS without replay or reconciliation tooling, so a diverged read model cannot be repaired.
  • Confusing CQRS with event sourcing and adopting both when only one was needed.
