01Why HTTP falls short for real-time communication

HTTP is request-response: the client asks, the server answers. That works when the client knows when it needs data.

  • Real-time data arrives when the server learns about it, which the client cannot predict: a chat message, a price change, a cursor move.
  • With plain HTTP the client must keep asking, so requests are spent on asking rather than on data.
  • Short polling asks every few seconds; most responses are empty and an update that lands just after a poll waits for the next one.
  • Long polling holds the request open until data exists, which lowers delay but still ends the request after every update.
  • Long polling also ties up server resources per waiting client and re-establishes a connection after each response.
  • WebSockets remove the asking: the connection stays open and the server sends the moment it has something.
  • The same connection can also carry client-to-server messages, so chat does not need a second channel.

Short pollingUp to one poll intervalMany wasted requests
Long pollingLow, but one request per updateHeld connections, reconnect per event

02What is a WebSocket?

  • A WebSocket is a persistent, two-way connection; the client opens it once and keeps it alive instead of creating a request per update.
  • Persistent: one connection carries many messages for minutes or hours.
  • Low overhead: messages do not repeat full HTTP headers, so many small messages are cheap.
  • Ordered and reliable: WebSockets run over TCP, so messages arrive in order and lost packets are retransmitted.
  • Message-based: applications send text or binary messages, not a raw byte stream.
  • Once connected, either side can send independently; this is full-duplex communication.
  • The trade is that the server now owns connection state, which is exactly what stateless HTTP avoided.

03The WebSocket handshake

A WebSocket connection usually begins as a normal HTTP request that asks the server to upgrade it.

  • The client connects to a URL such as ws://example.com/chat; wss:// is WebSocket over TLS and should be used in production.
  • The request carries Upgrade: websocket and Connection: Upgrade, which together are the request to switch protocols.
  • Sec-WebSocket-Key is a random value from the client.
  • The server hashes that key into Sec-WebSocket-Accept, which proves it actually understood the WebSocket handshake.
  • If the server accepts, it replies 101 Switching Protocols.
  • No new connection is created: the same underlying TCP connection is now used for WebSocket frames.
  • The connection ends when the client closes it, the server closes it, or the network fails; the first two are graceful Close frames.
Client sends HTTP GET with Upgrade: websocket→Server validates the key and protocol→Server replies 101 Switching Protocols→Same TCP connection becomes a WebSocket→Both sides exchange frames until a Close frame or network failure

Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

04WebSocket frames

  • After the handshake, data travels in frames rather than full HTTP messages.
  • Each frame has a small header, typically 2 to 14 bytes, followed by the payload; HTTP headers are usually hundreds of bytes.
  • The header records whether this is the final frame of a message, the frame type, and the payload length.
  • Text frames carry UTF-8 text, commonly JSON; binary frames carry images, audio, or Protobuf.
  • Ping and Pong frames check liveness; one side pings, the other answers.
  • Close frames end the connection gracefully with a status code and optional reason.
  • One application message may fit in one frame or be split across several; browsers reassemble them for you.
  • Small per-message overhead is why WebSockets suit frequent small messages, not bulk file transfer.

05A basic implementation

  • A minimal server accepts the upgrade, listens for messages, and can send to any tracked connection.
  • Node's ws library and the browser's built-in WebSocket object are enough to demonstrate the protocol.
  • The client opens the socket, registers onmessage, and calls send to push data.
  • This echo-server level of code proves the protocol works but handles none of the production concerns.
  • It has no authentication, no heartbeat, no reconnect, no backpressure, and no way to reach a user on another process.
  • The rest of the design is about adding those pieces without losing the simplicity of the wire protocol.
// server (Node.js, ws)
wss.on('connection', (socket, req) => {
  socket.on('message', (data) => {
    socket.send('echo: ' + data);
  });
});

// browser
const socket = new WebSocket('wss://example.com/chat');
socket.onmessage = (event) => console.log(event.data);
socket.onopen = () => socket.send('hello');

06Single-server architecture

Start with one WebSocket server that keeps every active connection in memory, usually a map from user ID to connection.

  • Alice sends a message over her existing connection.
  • The server validates the message and checks permissions.
  • The server optionally stores it in a database so it survives restarts and appears in history.
  • The server looks up Bob's connection in its in-memory map.
  • The server pushes the message directly to Bob over that connection.
  • Everything is in one place, so routing is trivial and latency is minimal.
  • The limit is real: each connection consumes memory, a file descriptor, and CPU for messages and heartbeats, and the server is a single point of failure.
In-memory maps are fine for live routing but must not be the only copy of message history or subscription state.

07Scaling WebSockets horizontally

  • Run several WebSocket servers behind a load balancer; each new connection is assigned to one server.
  • Each server now holds only a subset of connections, and adding servers adds capacity.
  • The key difference from HTTP: connections are long-lived, so they stay attached to the server that accepted them.
  • Normal HTTP requests can go to any healthy instance and finish in milliseconds; a WebSocket may live for hours.
  • If Alice is on server 1 and Bob on server 3, server 1's local map has no entry for Bob.
  • So horizontal scaling of the connection tier does not by itself solve message routing.
  • You need either a shared connection registry or, more commonly, a shared messaging layer.

08Routing messages across servers

  • A shared connection registry stores which server each user is on, for example in Redis.
  • Server 1 looks up Bob, finds server 3, and routes the message there directly.
  • The registry is hard to keep correct: users connect, disconnect, open multiple tabs, switch networks, and reconnect elsewhere.
  • Every change is a write, stale entries misroute messages, and servers need a direct path to each other.
  • The shared messaging layer avoids all of that: server 1 publishes an event and never needs to know where Bob is.
  • The messaging layer delivers to whichever server currently holds Bob's connection.
  • This is the standard approach because it removes direct server-to-server wiring and tolerates reconnects.

09Connecting WebSocket servers with pub/sub

  • All WebSocket servers connect to a shared pub/sub layer, often with one channel per user or per room.
  • When Bob connects to server 3, server 3 subscribes to Bob's channel; when he disconnects, it unsubscribes.
  • Alice sends to server 1, which processes the message and publishes an event to Bob's channel.
  • The pub/sub layer delivers the event to every server subscribed to that channel, here server 3.
  • Server 3 finds Bob's local connection and pushes the message to him.
  • The WebSocket servers never talk to each other; adding a server means subscribing it to the layer, not wiring it to every peer.
  • Redis Pub/Sub is good for simple, low-latency, transient events; messages are not stored, so a server not subscribed at publish time misses them.
  • Kafka fits when you need durability, replay, or large-scale event processing, because events are kept in a log.
Bob connects to server 3→Server 3 subscribes to Bob's channel→Alice sends to server 1→Server 1 publishes to the channel→Pub/sub delivers to server 3→Server 3 writes to Bob's socket

10Load balancing and connection draining

  • Once a load balancer routes a connection, that connection stays on the same server until it closes.
  • So the balancer mainly decides where each connection starts, not where each message goes.
  • Least connections usually balances better than round robin because connections accumulate unevenly over time.
  • Sticky sessions are not required for the socket itself, since it is already pinned for its lifetime.
  • Sticky sessions matter when a library falls back to HTTP long polling, as Socket.IO can, because those requests must reach the same server.
  • Terminating a server with tens of thousands of connections at once causes a mass disconnect and a reconnect storm.
  • Instead, drain: stop new connections, give clients time to leave, send Close frames a few at a time, then shut down after a deadline.
  • The load balancer, proxy, and CDN on the path must all support upgrade and long-lived connections.

11Handling failures and reconnection

  • If a server crashes, its clients lose the connection and must establish a new one, possibly on a different server.
  • So critical state must not live only in local memory; history, user state, and subscriptions belong in databases, caches, or brokers.
  • Local memory should hold only what can be rebuilt: the socket and its current subscriptions.
  • Disconnects are normal: laptops sleep, phones switch networks, proxies close idle connections, and deploys restart servers.
  • On reconnect the client should authenticate again, re-subscribe to its rooms, and resume from the last event ID when replay is needed.
  • Clients should not queue unlimited messages while offline and should show a disconnected state when it matters.
  • Exponential backoff with jitter prevents a million clients from reconnecting at the same instant: each doubles its delay up to a cap and adds randomness.
  • Without jitter, synchronized retries create a traffic spike that can overload the servers still running and slow recovery.
let attempt = 0;
function connect() {
  const socket = new WebSocket(url);
  socket.onopen = () => { attempt = 0; resubscribe(); };
  socket.onclose = () => {
    const base = Math.min(30000, 500 * 2 ** attempt++);
    const delay = base / 2 + Math.random() * (base / 2);
    setTimeout(connect, delay);
  };
}

12WebSocket infrastructure requirements

  • Clients rarely connect directly; traffic passes through CDNs, reverse proxies, and load balancers.
  • Every layer must forward the Upgrade header and allow long-lived connections, or the handshake fails before reaching your app.
  • Nginx, for example, only forwards the upgrade when explicitly configured to do so.
  • Idle timeouts are a common trap: proxies often close quiet connections after around 60 seconds.
  • Heartbeats (Ping/Pong) keep the connection alive and reveal dead peers that never sent a Close frame.
  • The heartbeat interval must be shorter than the shortest idle timeout on the path.
  • Browser JavaScript does not expose protocol-level ping, so browser clients often send an application-level heartbeat.
  • Deployments need connection draining, and capacity planning must include file descriptors, memory per connection, and TLS handshake cost.

13When to use WebSockets

  • Use WebSockets when you truly need frequent, low-latency, bidirectional communication.
  • For normal request-response operations, HTTP is simpler to build, cache, and scale.
  • If updates are infrequent, polling may be entirely adequate.
  • If only the server pushes, SSE is simpler: plain HTTP, automatic reconnect, no custom protocol.
  • WebSockets add persistent connections, reconnects, state recovery, timeouts, and cross-server routing to your operational load.
  • Typical fits: chat, live notifications, multiplayer games, collaborative editors, real-time dashboards, and live order tracking.
  • A useful decision rule: if the client sends rarely and the server pushes often, prefer SSE; if both sides talk constantly, use WebSockets.

↔Trade-offs to say out loud

  • WebSockets remove polling latency and header overhead but replace stateless requests with connection state the server must manage.
  • One persistent connection is efficient for many small messages but concentrates risk: one crash disconnects every client on that server.
  • Horizontal scaling adds capacity but forces cross-server routing through a shared registry or pub/sub layer.
  • Redis Pub/Sub is low-latency and simple but transient; a disconnected server misses events, so replay needs Kafka or a store.
  • Least-connections balancing spreads long-lived sockets better than round robin but still leaves uneven load after mass reconnects.
  • Connection draining makes deploys safe but lengthens rollout time and requires coordination with the load balancer.
  • Aggressive heartbeats detect dead connections quickly but add traffic and CPU; lazy heartbeats let zombies linger.
  • Client-side buffering preserves messages across brief drops but risks unbounded memory and stale sends after reconnect.
  • WebSockets versus SSE: WebSockets give two-way traffic but much more operational work; SSE gives simpler one-way push but no client channel.

?Interview questions

Answer aloud before opening the outline.

1. Why is HTTP a poor fit for real-time updates?

HTTP is request-response, so the client must ask before the server can answer. When updates arrive unpredictably, the client either polls and wastes requests or holds long polls that end after every update. WebSockets keep one connection open and let the server push immediately.

2. Walk through the WebSocket handshake.

The client sends an HTTP GET with Upgrade: websocket, Connection: Upgrade, and a random Sec-WebSocket-Key. The server returns 101 Switching Protocols with a derived Sec-WebSocket-Accept, and the same TCP connection then carries WebSocket frames.

3. What is the difference between short polling, long polling, SSE, and WebSockets?

Short polling asks repeatedly and mostly gets nothing. Long polling holds one request until data arrives, then reconnects. SSE keeps one HTTP stream open but only server-to-client. WebSockets keep one connection open in both directions with small frame overhead.

4. What is in a WebSocket frame header?

A small header, typically 2–14 bytes, recording the frame type, the payload length, and whether it is the final frame of the message. The payload follows. Control frames include ping, pong, and close.

5. Why is a WebSocket connection harder to scale than an HTTP request?

An HTTP request can go to any healthy instance and finishes quickly. A WebSocket stays attached to one server for its lifetime, so the server holds per-connection state and users on different servers cannot reach each other without a shared routing layer.

6. How do you deliver a message from a user on server 1 to a user on server 3?

Either keep a shared registry of user-to-server mappings and route directly, or publish the message to a pub/sub channel that server 3 subscribes to. The pub/sub approach is preferred because it avoids stale mappings and direct server-to-server wiring.

7. Why not just use a Redis registry of connections?

It can work, but the mapping changes constantly with connects, disconnects, multiple tabs, and network switches. Stale entries misroute messages, every change is a write, and servers still need a direct path to each other.

8. Redis Pub/Sub or Kafka for WebSocket fan-out?

Redis Pub/Sub for simple low-latency transient events, since it does not store messages. Kafka when you need durability, replay after a server restart, or large-scale event processing.

9. How do you deploy a WebSocket server without disconnecting everyone?

Drain connections: stop the load balancer from sending new ones, let clients reconnect elsewhere, send Close frames in small batches, and shut down after a deadline. Clients use backoff with jitter so the reconnect wave is spread out.

10. Why is exponential backoff with jitter necessary?

After a mass disconnect, synchronized retries create a spike that can overload the remaining servers and slow recovery. Backoff reduces retry frequency, and jitter spreads clients so they do not retry at the same instant.

11. Where should chat history and subscriptions live?

In shared durable storage, not only in the WebSocket server's memory. When a client reconnects to a different server it needs to recover history and subscriptions; local memory should hold only what can be rebuilt.

12. Why do WebSocket systems need heartbeats?

Proxies and load balancers close idle connections, and a dead peer may never send a Close frame. Ping/Pong keeps the connection active and detects broken links. The interval must be shorter than the shortest idle timeout on the path.

13. When would you choose SSE over WebSockets?

When only the server needs to push and the client rarely sends: notifications, progress bars, or streamed model output. SSE uses plain HTTP, reconnects automatically, and avoids custom connection management.

14. What breaks in production that does not break locally?

Proxies that strip the Upgrade header, idle timeouts around 60 seconds, TLS termination, load balancer limits on connection duration, and deploys that kill sockets. Local testing usually skips every one of those layers.

!Traps

  • Assuming a WebSocket is stateless like HTTP and storing user state only in the server's local map.
  • Forgetting to configure the reverse proxy or load balancer to forward the Upgrade header.
  • Setting the heartbeat interval longer than the proxy idle timeout, so connections die silently.
  • Reconnecting immediately without backoff or jitter, producing a reconnect storm after a deploy or outage.
  • Using round-robin balancing for long-lived connections and ending up with heavily skewed servers.
  • Choosing WebSockets for one-way notifications where SSE or polling would be simpler.
  • Killing a WebSocket server with thousands of connections instead of draining it first.
  • Assuming Redis Pub/Sub is durable and then losing events when a server is momentarily unsubscribed.
