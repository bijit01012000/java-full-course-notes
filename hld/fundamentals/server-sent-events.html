Server-Sent Events
A one-way streaming protocol where the server holds an HTTP response open and writes events to it as they occur.
EventSource
The browser API that opens an SSE connection, parses the stream, and reconnects automatically when it drops.
text/event-stream
The content type that marks a response as an SSE stream rather than a fixed-length HTTP body.
Last-Event-ID
A request header the browser sends on reconnect carrying the last event ID it received, so the server can resume the stream.
retry field
A server-suggested reconnect delay in milliseconds that overrides the browser's default backoff.
Heartbeat
A periodic comment line starting with : that keeps idle proxies from closing the stream and reveals dead connections.

Retiring a server by stopping new connections while existing ones finish, avoiding a mass simultaneous reconnect.
Backpressure
The policy for what to do when the server produces events faster than one client can consume them.

01Why SSE exists

A live dashboard needs to update whenever the server has new data. You want the browser to connect once and let the server talk whenever something changes.

  • Polling makes the browser ask repeatedly, so frequent polling wastes requests that return nothing.
  • Infrequent polling reduces traffic but adds delay before updates are seen.
  • Long polling improves on that, yet every response still closes the request and forces the browser to ask again.
  • SSE removes the trade-off: one connection, and the server pushes each update the moment it exists.
  • The cost is that the connection is now long-lived, which changes how you scale, deploy, and monitor.

02What SSE is

  • The client sends a normal HTTP request; the server replies with a response that never completes while the stream is open.
  • New data is written as individual events on that same response, and the client receives each event immediately.
  • SSE is strictly one-way: server to client. The client cannot send messages back over the stream.
  • Anything the client must send uses a separate ordinary request, such as a POST.
  • That asymmetry is a feature for feeds, dashboards, and progress bars where the server talks and the browser listens.
  • It is plain HTTP, so existing auth, TLS, and cookie handling apply, and it works through most corporate proxies.

03How a connection works

  • The browser uses the EventSource API against a server endpoint.
  • The server responds with Content-Type: text/event-stream and keeps the response open.
  • The server writes events incrementally and must flush after each one; buffering hides the update.
  • EventSource exposes a connection state so the client can render connecting, open, and closed behavior.
  • Closing the endpoint or ending the response moves the client to a closed state that will not reconnect on its own.

04The SSE event format

An event is a few text lines followed by a blank line. The format is deliberately simple, which is why it is easy to implement on any server.

  • data carries the payload, either plain text or JSON; multiple data lines are joined with newlines.
  • event sets the event type so the client can attach a separate listener per kind of update.
  • id marks the event's position and becomes the Last-Event-ID value on reconnect.
  • retry suggests a reconnect delay in milliseconds for the browser to use.
  • A line starting with : is a comment and is ignored by the client, which makes it a natural heartbeat.
  • One stream can legitimately carry mixed types — notifications, order status, progress — on the same connection.
event: order-status
id: 1042
data: {"orderId":"A-77","state":"shipped"}

: heartbeat
The blank line terminates an event. Forgetting it means the client buffers the event indefinitely.

05Automatic reconnection

  • If the connection drops, the browser reconnects by itself, so basic retry logic does not need to be written.
  • The default reconnect delay is short — on the order of a few seconds — and the server can override it with retry.
  • Automatic reconnection is why SSE survives flaky mobile networks and rolling restarts without client code.
  • The client should still observe errors and surface a degraded state; silent reconnection can hide a server problem.
  • A server that intentionally ends the stream should signal it clearly, otherwise the browser reconnects into a loop.

06Recovering missed events

  • The server stamps each event with an ID and the browser remembers the most recent one.
  • On reconnect the browser sends Last-Event-ID, and the server resumes from there — for example replaying everything after event 100.
  • SSE does not store events for you; the protocol only carries the marker.
  • Reliable replay needs durable storage: a database, cache, event log, or message broker the server can query.
  • If the gap is too large or storage has expired, the server should tell the client to resynchronize rather than silently skipping events.
  • Without a durable backing store, Last-Event-ID gives the illusion of resume while events are still lost.

07Scaling SSE

  • Behind a load balancer, each connection is pinned to one server for its lifetime, so users end up spread across servers.
  • A backend service that produces an event for a user has no idea which SSE server holds that user's connection.
  • The fix is a shared messaging layer: publishers emit events, every SSE server subscribes, and the server with the matching connection pushes it.
  • This keeps business services decoupled from the servers that manage long-lived connections.
  • Adding SSE servers then scales by connection count without touching producers.
  • Track connections per server, memory per connection, and event fan-out cost as the primary capacity signals.
Backend service publishes an event→Messaging layer fans out to all SSE servers→Only the server holding that client's stream writes the event→Client receives it on the existing connection→Durable store covers any gap after a reconnect

08Pub/sub behind SSE

  • Redis Pub/Sub suits fast, transient events where replay does not matter: a server not subscribed at publish time never sees the message.
  • Kafka suits durability, replay, and large-scale processing; retention lets a reconnecting client's Last-Event-ID be served from the log.
  • Either way the roles stay fixed: producers emit, the messaging layer distributes, SSE servers own connections.
  • Mixing both is common — pub/sub for live fan-out, a log or table for replay.
  • The messaging choice is a durability decision, not a protocol decision; SSE looks identical to the client either way.

09Slow clients and backpressure

  • If a server produces events faster than one client consumes them, that client's buffer keeps growing.
  • Unbounded buffering per connection turns a few slow clients into a memory problem for the whole server.
  • Explicit options: buffer temporarily up to a limit, drop oldest events, keep only latest state, or disconnect and let the client resume.
  • Latest-state-only is right for prices and progress percentages where intermediate values are useless.
  • Disconnect-and-resume is right when every event matters and the cursor can replay the gap.
  • Whatever the policy, it should be chosen per stream type rather than left implicit.

10Heartbeats and infrastructure

  • Quiet streams look idle to proxies and load balancers, which may close them.
  • Send periodic comment lines (:) as heartbeats; the client ignores them but the connection stays warm.
  • Heartbeats should be more frequent than the shortest idle timeout anywhere in the path.
  • They also detect half-open connections, since a write failure surfaces faster than waiting for a timeout.
  • Response buffering is the other silent killer: proxies, CDNs, and middleware may hold written bytes before forwarding.
  • Disable buffering along the whole path — in Nginx this is commonly done with X-Accel-Buffering: no.

11Deployments and connection draining

  • Shutting down an SSE server instantly disconnects thousands of clients that may then reconnect simultaneously.
  • That spike hits the remaining servers exactly while capacity is reduced.
  • Drain instead: the load balancer stops sending new connections to the retiring server.
  • Existing streams stay until they close naturally or the client reconnects elsewhere.
  • The server shuts down only when it holds no active connections.
  • Because clients resume with Last-Event-ID, moving servers does not lose events.
Mark server as draining→Load balancer stops new connections→Existing streams finish or the client reconnects elsewhere→Wait for connection count to reach zero→Terminate the instance safely

12When to use SSE

  • Strong fit when you need frequent server-to-client updates and no bidirectional messaging on the same connection.
  • Common uses: notifications, live dashboards and monitoring, job progress, sports scores, social feeds.
  • If both directions need frequent messages on one connection, WebSockets are the better fit.
  • If updates are rare and the client is already request-driven, long polling may be simpler to operate.
  • SSE is the natural transport for streaming LLM responses: one request in, progressive tokens out.
  • Because it is HTTP, it is easier to route through firewalls and proxies than a custom upgrade protocol.

13SSE for streaming AI responses

  • Generating a full LLM answer can take many seconds, which feels broken if the user sees nothing.
  • The server streams tokens as they are produced, so the answer starts appearing almost immediately.
  • The client sends one request and the server progressively writes the response back on that stream.
  • It is a textbook server-to-client pattern, not a bidirectional one, which is why SSE fits better than WebSockets here.
  • End-of-stream must be explicit so the client stops waiting and enables follow-up actions.
  • Because tokens arrive incrementally, the client should render partial text and handle mid-stream failures gracefully.

↔Trade-offs to say out loud

  • One connection replaces many polls, but that connection must stay open and healthy for a long time.
  • Automatic reconnection removes retry code, but hides transient failures unless the client also observes errors.
  • Last-Event-ID enables resume, but only if the server keeps events in durable storage with enough retention.
  • Plain HTTP compatibility eases proxying and auth, but the client cannot send messages back over the stream.
  • Server push cuts latency, but adds per-connection memory and file descriptor cost at scale.
  • Buffering disabled end to end gives immediate delivery, but requires coordinated proxy and CDN configuration.
  • Heartbeats keep idle connections alive and detect dead ones, at the cost of constant background traffic.
  • Connection draining makes deploys safe, but slows rollouts because old instances wait for clients to leave.
  • Latest-state-only backpressure protects memory, but silently discards intermediate events.

?Interview questions

Answer aloud before opening the outline.

1. What is SSE and how does it differ from polling?

SSE is a one-way stream where the server keeps an HTTP response open and writes events as they occur. Polling makes the client ask repeatedly; SSE has the client connect once and receive updates immediately. That removes the latency-versus-wasted-requests trade-off polling forces.

2. Why is SSE described as one-way?

The protocol only defines server-to-client messages on the open response. The client sends data through separate normal HTTP requests. If an application needs frequent messages in both directions on one connection, WebSockets are the appropriate tool.

3. How does an SSE event look on the wire?

Each event is a few field lines followed by a blank line. Supported fields are data, event, id, and retry. Lines beginning with a colon are comments and are commonly used as heartbeats.

4. What does Last-Event-ID actually solve?

It tells the server where the client's stream left off, so the server can replay events after that ID. It only solves positioning: the server must still store events durably for replay to be possible.

5. Does the browser store events for replay?

No. The browser only remembers the last event ID it saw. Durable storage such as a database, log, cache, or broker is the application's responsibility, and retention limits determine how far back a reconnect can resume.

6. How do you scale SSE to many connections?

Run multiple SSE servers behind a load balancer and put a shared messaging layer in front of them. Producers publish events, every SSE server subscribes, and the server holding the client's connection writes it. Capacity then scales with connection count, not with producer logic.

7. Redis Pub/Sub or Kafka behind SSE?

Redis Pub/Sub is a good fit for fast transient events where a missed message is tolerable. Kafka is better when you need retention, replay, or large-scale processing, because a reconnecting client's cursor can be served from the log.

8. What happens when a client cannot keep up?

Its per-connection buffer grows. The server needs an explicit policy: bounded buffering, dropping old events, sending only latest state, or disconnecting the client so it resumes from its last event ID.

9. Why do SSE streams need heartbeats?

Idle proxies and load balancers close connections that look inactive. Comment heartbeats keep the stream warm and expose dead connections quickly. They should be more frequent than the shortest idle timeout in the path.

10. Events arrive several seconds late even though the server writes them immediately. Why?

Something in the path is buffering the response — a proxy, CDN, or middleware that collects bytes before forwarding. Disable response buffering end to end and verify the content type is text/event-stream.

11. How do you deploy without a reconnect stampede?

Drain connections. Stop routing new connections to the retiring server, let existing streams finish or move on reconnect, and terminate only when the connection count reaches zero. Clients resume with Last-Event-ID, so no events are lost.

12. Why is SSE popular for streaming LLM output?

LLM responses take seconds to generate and are strictly server-to-client, which matches SSE exactly. Streaming tokens as they are produced makes the interface feel responsive, and one HTTP request starts the whole stream.

!Traps

  • Forgetting to flush the response, so events sit in a server or proxy buffer and arrive late in batches.
  • Assuming Last-Event-ID gives replay without a durable event store behind it.
  • Using SSE when the client must push frequent messages on the same connection instead of choosing WebSockets.
  • Ignoring per-connection buffering, letting a few slow clients exhaust server memory.
  • Omitting heartbeats so idle connections are closed by proxies and treated as mysterious disconnects.
  • Shutting down SSE servers abruptly and causing a reconnect stampede on the remaining capacity.
  • Treating automatic browser reconnection as proof the stream is healthy rather than monitoring errors and gaps.
