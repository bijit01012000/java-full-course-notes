Metric
A named numeric measurement recorded over time, with labels that identify which service, endpoint, or resource it describes.
Time series
The sequence of values for one metric name plus one specific combination of label values.
Counter
A cumulative metric that only increases, from which rates and totals are derived by differencing over a window.
Gauge
A metric representing a value at a point in time that can rise or fall, such as connection pool usage or queue depth.
Histogram
A metric that counts observations into buckets, allowing percentiles to be estimated and aggregated across instances.
Label
A key-value dimension attached to a metric, such as status code or region, that makes the series queryable from many angles.
Cardinality
The number of distinct time series produced by a metric; driven by the product of distinct label values.
Golden signals
Latency, traffic, errors, and saturation — the four default signals for judging a service's health.
Scrape
A pull-based collection in which the monitoring system periodically fetches the current metric values from each target.
Downsampling
Progressively reducing the resolution of older metric data so long retention stays affordable.

01Why metrics exist

Without metrics, the first sign of a problem is often a wave of customer complaints. With metrics, the same problem appears as a trend that can be alerted on before most users notice.

  • Metrics give a continuous numeric view: latency, error rate, throughput, and resource saturation at every point in time.
  • They show whether the system is normal, when it stopped being normal, and which part changed.
  • Because they are cheap, they can be collected from every service and instance all the time.
  • They are the natural input to alerts, dashboards, capacity planning, and autoscaling decisions.
  • They are also comparable over time, so a deploy can be judged by what happened to the curves after it.
  • Metrics are a summary, not a record: they tell you that something is wrong, not which specific request failed.

02Anatomy of a metric

  • A metric has a name describing what is measured, such as http_requests_total.
  • It has a type that defines valid operations — counters can be rate-d, gauges cannot.
  • It has labels identifying the dimensions: service, endpoint, method, status code.
  • Each observation carries a timestamp and a value.
  • Name plus a unique label set defines one time series; changing one label value creates a different series.
  • The unit belongs in the name or metadata (seconds, bytes), because a latency in milliseconds and one in seconds look identical numerically.
  • Instrumentation should expose low-level, composable metrics rather than pre-computed business judgments, so queries can combine them later.

03Metric types and when to use them

  • Counter — cumulative totals such as requests, errors, bytes. Query with a rate over a window; never graph raw totals for traffic shape.
  • Gauge — a snapshot such as active connections, queue depth, memory in use. Query the current value, min, max, or average.
  • Histogram — bucket counts for latency or payload size, from which percentiles are estimated.
  • Summary — client-side computed quantiles; accurate per instance but impossible to merge across instances.
  • Use counters for anything that logically accumulates, even if you only ever query the rate.
  • Use a histogram when the distribution matters; use a gauge when only the level matters.
  • Avoid deriving a counter from a gauge by subtraction — restarts and resets will corrupt the series.

04Labels and the cardinality budget

  • Labels are what turn a single number into an answerable dataset: without status_code you cannot separate errors from success.
  • Cardinality multiplies: five endpoints times four methods times six status codes is already one hundred and twenty series for one counter.
  • Adding a label whose values grow with traffic — user ID, request ID, full URL path — makes cardinality unbounded.
  • Each series costs memory, index space, and query time, and the bill is paid by every team sharing the backend.
  • Prefer bounded dimensions: service, region, environment, version, status class, route template.
  • Normalize paths before labeling (/orders/{id}, not /orders/12345).
  • When you need per-request detail, use a trace or log, or attach an exemplar rather than a label.
A useful test before adding a label: can you list every possible value, and will that list stay small a year from now?

05What to measure

  • The four golden signals — latency, traffic, errors, saturation — are the default per-service set.
  • RED (rate, errors, duration) fits request-driven services and maps cleanly to those signals.
  • USE (utilization, saturation, errors) fits resources such as CPU, disks, and queues.
  • Latency must be split by outcome: a fast error response and a slow success mean very different things, so never merge them into one latency series.
  • Measure saturation directly where possible — pool in use versus pool size, queue depth, thread count — because it moves before latency degrades.
  • Add business metrics that reflect user outcomes: orders placed, payments declined, signups completed.
  • Instrument dependencies as well as your own service, so you can tell whether the fault is yours or downstream.

06Percentiles, buckets, and why averages lie

Latency distributions are skewed. A small fraction of slow requests can be invisible in the mean while dominating user complaints.

  • If most requests take tens of milliseconds and a few take seconds, the average sits near the fast majority and looks healthy.
  • p95 and p99 describe the experience of the slowest users, which is where timeouts and abandonment live.
  • A histogram stores bucket counts, so percentiles are estimated from the bucket boundaries — coarse buckets give coarse answers.
  • Percentiles cannot be averaged: the average of two p99 values is not the p99 of the combined traffic.
  • To aggregate across instances, sum the histogram buckets and then compute the percentile on the merged distribution.
  • Client-side summaries cannot be merged at all, which is why they are a poor fit for fleet-wide latency dashboards.
  • Pick bucket boundaries around the thresholds that matter, such as the timeout or SLO target.

07Instrumentation approaches

  • Client library: the application records metrics in-process and exposes or pushes them; full control, but code changes per language.
  • Auto-instrumentation: agents or framework integrations wrap HTTP handlers, database clients, and queues with no business logic changes.
  • Sidecar or proxy: a local process observes traffic and exports network-level metrics; no application changes, less semantic detail.
  • Host and platform agents: collect CPU, memory, disk, and container metrics that the application cannot see.
  • Auto-instrumentation covers the standard request path well; you still hand-write business counters and gauges.
  • Keep metric emission non-blocking and cheap — an instrumentation call on the hot path must not allocate heavily or take locks.
  • Use a vendor-neutral SDK such as OpenTelemetry so the export target can change without re-instrumenting.

08Push versus pull collection

  • In pull, the monitoring system scrapes each target on an interval; targets expose a current snapshot.
  • Pull makes it obvious when a target is down, because the scrape fails, and keeps the target free of delivery logic.
  • In push, the application sends observations to a collector or gateway; useful for short-lived jobs and for crossing network boundaries.
  • Push hides target health: a missing series looks the same as a target that never existed.
  • Scrape interval bounds resolution — a spike shorter than the interval can be missed entirely.
  • Short-lived jobs need a gateway or an export on shutdown, because they may not exist when the next scrape arrives.
  • Whichever model you choose, align the collection interval with the shortest alerting window you intend to use.

09Query semantics that trip people up

  • Counters reset when a process restarts; rate calculations must handle the reset rather than reporting a negative spike.
  • A rate over a window shorter than the scrape interval produces noisy or empty results.
  • Window alignment matters: comparing a value at 09:00 with an average over a trailing window can suggest a trend that is not there.
  • Aggregating before versus after a ratio changes the answer — compute ratios from summed components, not from averaged ratios.
  • Recording rules precompute expensive queries so dashboards and alerts stay fast and consistent.
  • Staleness handling matters during deploys: an old value can look like a current one unless the system marks missing series.
  • Label matchers are the main cost lever; broad selectors over many series are what make queries slow.

10Storage, resolution, and retention

  • Metric stores compress well because values change slowly relative to their volume, but volume is still driven by series count times sample rate.
  • Higher resolution means more samples and higher cost; most systems keep recent data at full resolution and thin older data.
  • Downsampling preserves trends for dashboards over long ranges while losing short spikes.
  • Retention should match the question: weeks for operational debugging, months or years for capacity trends and SLO reporting.
  • Series churn — short-lived series from ephemeral pods or unbounded labels — is a hidden cost multiplier.
  • Capacity planning needs enough history to see weekly and seasonal patterns, not just the last few days.

11From metrics to alerts

  • Alert on symptoms users feel — error rate, latency, availability — rather than on every internal cause metric.
  • Cause metrics such as CPU or queue depth are better used for diagnosis and early warning than for paging.
  • Require a sustained breach (for duration) so a single scrape spike does not page anyone.
  • Alert on missing data too, because a service that stops reporting looks healthy on a graph with no gaps drawn.
  • Every alert should link to a dashboard and a runbook that explains what to check and what to do.
  • Keep thresholds tied to an SLO or a capacity limit, not to a number that felt right once.
  • Review alerts after each incident: an alert that never leads to action is noise that erodes trust in the pager.

12Common instrumentation failure modes

  • A cardinality explosion from one unbounded label can degrade the whole metrics backend, not just one dashboard.
  • Instrumenting only successes hides the failure path, which is usually the one that matters during an incident.
  • Measuring at the wrong layer — proxy latency only — hides slow application code behind a fast network hop.
  • Emitting high-frequency metrics from inside hot loops adds measurable CPU and allocation overhead.
  • Inconsistent metric names and units across services make fleet-wide queries impossible.
  • Gauges sampled too coarsely miss short saturation events, such as a pool briefly exhausting under a burst.
  • Assuming a metric exists because a dashboard shows a line: the panel may be graphing a stale or defaulted series.

↔Trade-offs to say out loud

  • Rich labels make metrics sliceable but multiply series count and can overwhelm the backend.
  • High-resolution scraping catches short spikes but multiplies storage and ingestion cost.
  • Histograms enable fleet-wide percentiles but cost more per series than a simple counter.
  • Client-computed summaries give accurate local quantiles but cannot be merged across instances.
  • Auto-instrumentation is fast to adopt but produces generic metrics that may miss business meaning.
  • Pull collection reveals target health but requires discoverable targets and a working scrape path.
  • Long retention and downsampling support capacity planning but lose detail on old incidents.
  • Alerting on cause metrics catches problems early but generates pages for conditions users never felt.

?Interview questions

Answer aloud before opening the outline.

1. What is a metric, precisely?

A named numeric measurement recorded at points in time, identified by a name, a type, and a set of labels. One metric name with one unique label combination forms a time series. Metrics summarize many events into a small number of numbers, which is what makes them cheap to store and query.

2. Counter, gauge, or histogram — how do you choose?

Use a counter for anything that only accumulates, such as requests or errors, and query its rate. Use a gauge for a level that rises and falls, such as connections in use. Use a histogram when the distribution matters, typically latency or payload size, because it lets you compute percentiles after the fact.

3. Why are percentiles better than averages for latency?

Latency distributions are heavily skewed, so the mean tracks the fast majority and hides the slow tail. p95 and p99 reflect the users most likely to time out or abandon, which is usually what triggers complaints. Report both a percentile and a count so the reader knows how much traffic the tail represents.

4. Why can't you average percentiles across instances?

A percentile is a position in a distribution, not an additive quantity, so the average of two p99 values says nothing about the combined p99. The correct approach is to aggregate the underlying histogram buckets and compute the percentile on the merged distribution. Client-side summaries make this impossible, which is a reason to prefer histograms for fleet-wide latency.

5. What is the high cardinality problem in metrics?

Every distinct label combination is its own time series, so an unbounded label such as user ID or raw URL can create millions of series. That consumes memory and index space, slows queries, and can destabilize the metrics backend for everyone. Keep labels bounded and put unbounded identifiers in logs or traces.

6. Push or pull — which do you prefer and why?

Pull suits long-running services: failed scrapes reveal target health and the application needs no delivery logic. Push suits short-lived jobs, edge sites, and networks where the collector cannot reach the target. Push hides target liveness, so you need explicit heartbeats or a gateway that tracks expected senders.

7. What are the four golden signals and why those four?

Latency, traffic, errors, and saturation. Together they answer how slow requests are, how much demand exists, how often requests fail, and how close resources are to their limits. They cover both user-visible symptoms and the leading indicator — saturation — that predicts degradation.

8. How would you instrument a new HTTP service?

Auto-instrument inbound and outbound calls, then add a request counter by route, method, and status class, a latency histogram, an in-flight request gauge, and saturation metrics for pools and queues. Add business counters for outcomes that matter to users. Keep every label bounded and route metric names consistently with other services.

9. Why do counters reset, and how does that affect queries?

A counter lives in process memory, so a restart starts it from zero. Rate calculations must detect the reset and treat the drop as a new accumulation rather than a negative rate. This is why you query rate or increase over a window instead of subtracting raw samples yourself.

10. What makes a good alerting metric?

It should reflect something users experience, such as error rate or latency above an SLO, and be stable enough that a short spike does not page anyone. It should have a clear owner, a link to a dashboard, and a runbook. Cause metrics like CPU are better for diagnosis and warning than for waking people up.

11. How do you keep long-term metric storage affordable?

Keep recent data at full resolution, downsample older data to coarser intervals, and set retention by question type — short for debugging, long for capacity trends. Also control series count, because churn from ephemeral pods or unbounded labels costs more than sample rate in many systems.

12. What are the risks of auto-instrumentation?

It is generic: it measures transport-level facts but not business outcomes, and it can create high-cardinality series if it labels by raw paths. It also hides which metrics are actually maintained. Use it for the standard request path, then add deliberate domain metrics and prune noisy defaults.

!Traps

  • Labeling by raw URL path or user ID and collapsing the metrics backend with unbounded cardinality.
  • Graphing average latency and concluding the service is healthy while the p99 is timing out.
  • Averaging per-instance percentiles instead of merging histogram buckets.
  • Measuring only successful requests, so the failure path is invisible exactly when it matters.
  • Alerting on CPU or memory as a page while ignoring user-facing error rate and latency.
  • Treating a missing series as healthy instead of alerting on absent data.
  • Emitting metrics from hot loops with expensive label computations and adding real request latency.
