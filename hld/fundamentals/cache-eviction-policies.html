01Why cache eviction is necessary

Caches have limited memory. Once full, something must give when a new object arrives.

  • As requests arrive, more objects are added until the cache reaches its memory limit.
  • At that point there are two options: reject the new object, or remove an existing entry to make room.
  • Most caching systems choose to remove an existing entry.
  • The real question is which entry to remove: ideally one unlikely to be needed again.
  • A good policy keeps the data users are most likely to request next and discards the rest.
  • The choice shows up directly in latency and database load: evicting useful entries lowers the hit rate.
  • Keeping the wrong entries fills memory with data nobody asks for and still starves useful keys.

02Eviction versus expiration

These are often conflated, but they answer different questions.

  • Expiration happens because an entry is no longer valid — for example, its five-minute TTL has ended.
  • Eviction happens because memory is needed, even though the entry may still be perfectly correct.
  • Expiration is triggered by time; eviction is triggered by memory pressure.
  • Expiration's main concern is freshness; eviction's main concern is memory management.
  • An expired entry may be stale; an evicted entry may still be valid.
  • Real caches use both: entries expire by TTL, and valid entries are evicted when the cache fills.
  • Confusing the two leads to the false belief that TTLs alone solve memory pressure.

03What makes a good eviction policy

  • The goal is to maximize the usefulness of limited memory, not to be theoretically elegant.
  • If one value is requested thousands of times a minute and another was requested once hours ago, the second is the better victim.
  • A policy is a prediction about which entries belong in the working set — the data likely to be requested soon.
  • Different policies use different signals: recency (LRU), frequency (LFU), insertion order (FIFO), or nothing (random).
  • Each signal costs metadata and processing, so the policy must earn its overhead in hit rate.
  • No policy predicts perfectly; the right choice depends on whether popularity is stable, whether scans occur, and how much memory is available.
  • Object size is a separate dimension: evicting one large entry may free far more space than evicting many small ones.

04Least Recently Used (LRU)

LRU evicts the entry that has not been accessed for the longest time.

  • The assumption is temporal locality: data accessed recently is likely to be accessed again soon.
  • With a cache holding A, B, and C, accessing A then C makes B the least recently used entry; inserting D evicts B.
  • A classic implementation pairs a hash map for O(1) lookup with a doubly linked list for recency order.
  • On access, the entry moves to the front; on eviction, the tail is removed — both O(1).
  • Large production caches often approximate this to save memory; Redis samples a handful of keys and evicts the least recent among them.
  • LRU is intuitive and a strong general-purpose default for read-heavy systems.
  • Its weakness is that it considers only recency, never how often an entry was used before.
Access A→Access C→Insert D→B is least recent→Evict B

05LRU and one-time scans

  • A background job that scans millions of unique records once is the classic LRU failure case.
  • Every scanned record enters the cache and becomes more recent than the existing entries.
  • A large enough scan pushes genuinely useful data out of the cache.
  • After the scan, most newly cached records are never requested again, so the cache is full of dead entries.
  • This is cache pollution: one-time accesses treated as important merely because they happened recently.
  • Scan-resistant LRU variants make a new entry prove itself with a second access before treating it as hot.
  • This weakness is a main reason LFU and frequency-based admission exist.

06Least Frequently Used (LFU)

LFU evicts the entry with the fewest accesses rather than the oldest access.

  • If A has 100 requests, B has 50, and C has 2, LFU evicts C first.
  • The assumption is that frequently accessed values are more valuable and should survive.
  • When counts tie, implementations usually break the tie by removing the less recently used entry.
  • LFU handles stable popularity well: a small set of consistently hot products stays cached.
  • A single scan is less damaging because scanned entries have low counts, so hot data survives.
  • Its weakness is stale popularity: an item that was briefly viral can keep a huge count long after anyone cares.
  • Real implementations add aging or decay; Redis's LFU mode uses a small logarithmic counter that decays when a key is not accessed.
  • LFU needs more metadata per entry because it must track access frequency.

07LRU versus LFU

  • LRU prioritizes recent activity; LFU prioritizes repeated activity.
  • An item requested 1,000 times yesterday but untouched today favors LFU; an item requested 10 times in the last minute favors LRU.
  • LRU adapts quickly when popularity changes; LFU adapts slowly unless counts decay.
  • One-time scans can push hot data out of LRU, while scanned entries have low counts and leave LFU's hot data intact.
  • LRU needs recency ordering; LFU needs an access count, often with decay.
  • If popularity shifts fast, recency is more useful; if the same small set stays hot for long periods, frequency wins.
  • Modern caches blend both: Caffeine's W-TinyLFU uses a small LRU window for new entries plus a frequency estimate for admission.

08First In, First Out (FIFO)

  • FIFO evicts the oldest inserted entry, regardless of how it was used.
  • If A enters first, then B, then C, inserting D when full removes A.
  • A read does not change anything, so a FIFO cache can be a plain queue.
  • Its advantage is simplicity and low metadata: far less tracking than LRU or LFU.
  • Its cost is that a heavily used entry can be evicted simply because it is old.
  • It works when insertion order roughly matches usefulness, which is uncommon for general web traffic.
  • It is a reasonable choice when the tracking budget is very low and the workload is not strongly skewed.

09Random eviction

  • When the cache is full, pick an entry at random and remove it.
  • It requires almost no access tracking: no recency list and no frequency counter.
  • That lowers implementation overhead and memory cost per entry.
  • Under some workloads the hit-rate difference from sophisticated policies is smaller than expected.
  • The obvious risk is evicting a very hot entry purely by chance.
  • It is therefore used when simplicity and low overhead matter more than maximizing hit ratio.
  • It is also a useful baseline: if LRU beats random only slightly on your workload, the bookkeeping may not be worth it.

10Most Recently Used (MRU)

  • MRU evicts the entry that was used most recently — the opposite of LRU.
  • That sounds backwards because most workloads want to keep recently used data.
  • It fits narrow cases where the most recent item is least likely to be needed again.
  • The classic example is a job that loops over the same large set of records in order.
  • For normal web traffic, recently used data is exactly what should stay cached, so MRU is a poor default.
  • Knowing it is useful mainly to recognize when a non-standard access pattern might justify it.

11TTL-based expiration

Caches can also remove entries because their time-to-live has elapsed.

  • Every object might expire ten minutes after being cached, after which it becomes eligible for removal.
  • Expired entries are no longer useful, so removing them improves freshness as well as freeing memory.
  • Removal can happen in a background cleanup process or lazily when someone next reads the key.
  • TTL alone does not solve memory pressure: if the cache fills after two minutes, no entry has reached its ten-minute TTL.
  • So TTL is usually combined with an eviction policy that handles the still-valid entries.
  • A synchronized TTL is a trap: many keys cached together expire together, and the database receives all their misses at once.
  • Adding random jitter spreads expirations into a steadier stream of refreshes the database can absorb.

12Evicting only entries with TTLs

Some systems let eviction target only keys that already have an expiration time.

  • This is useful when one cache holds different categories of data, some temporary and some persistent.
  • When memory tightens, only temporary entries are evicted and persistent application state is left untouched.
  • It gives more control over which data is allowed to disappear, but introduces risk.
  • If too much non-evictable data fills the cache, there may eventually be no safe entry left to remove and new writes fail.
  • Redis exposes this through maxmemory-policy: allkeys-* policies may evict any key, while volatile-* policies only evict keys with a TTL.
  • With any volatile-* policy, if no key has a TTL left, Redis behaves like noeviction and rejects writes that need more memory.
  • The eviction policy therefore has to match how the cache is actually used, not just how it is configured.

13Object size also matters

  • Frequency is not the only measure of value; the memory an entry occupies matters too.
  • Evicting one 100 MB object may free enough room for thousands of small entries.
  • A standard LRU or LFU policy treats both as a single key, ignoring the size difference.
  • A large object may be popular enough to keep, or may consume huge memory for very little benefit.
  • Some advanced caches weigh both object size and reuse when deciding what to keep.
  • Limit the cache by memory, not by item count: a cache capped at 10,000 items can still exhaust memory if a few are huge.
  • Watch oversized values; compressing, splitting, or simply not caching them is often the cheapest fix.
A byte-bounded cache with size-aware accounting avoids the surprise of an item-count limit that still runs out of memory.

14Cache pollution, admission control, and measuring the policy

  • Cache pollution is low-value data pushing useful data out, caused by scans or floods of unique requests.
  • Thousands of slightly different search queries can each be cached once and never requested again, lowering the hit ratio.
  • Admission control separates two decisions: should this object enter the cache, and which existing object should leave?
  • Simple admission skips caching known one-time work such as report exports, backfills, migrations, and full table scans.
  • TinyLFU admits a new entry only if its estimated frequency is higher than that of the entry it would replace.
  • Measure the policy on the real workload: hit ratio per key pattern, eviction rate, memory usage, backend request rate, latency, and expired entries.
  • Alert when the eviction rate spikes, the hit ratio drops on a critical pattern, memory stays pinned, or backend load rises after evictions.
  • Sometimes the policy is not the problem: the cache may be undersized, the TTL too long, or the application caching too much low-value data.

↔Trade-offs to say out loud

  • LRU adapts quickly to changing popularity and is a strong default, but one-time scans can flush the working set.
  • LFU protects stable hot keys from scans, but stale popularity lingers unless counters decay.
  • FIFO needs little metadata and is easy to implement, but evicts heavily used entries just because they are old.
  • Random eviction is cheapest to track and a useful baseline, but can discard a hot entry by chance.
  • MRU suits looping scans over a large set, but is wrong for normal web workloads where recent data is reused.
  • TTL improves freshness automatically, but does not handle memory pressure and can create synchronized expiry waves.
  • Volatile-only eviction protects persistent keys, but can leave no evictable entry and cause writes to fail.
  • Size-aware eviction frees memory efficiently, but adds accounting overhead and can evict a popular large object.
  • Admission control keeps low-value data out, but rejects new entries that might have become hot.

?Interview questions

Answer aloud before opening the outline.

1. Why do caches need an eviction policy?

Cache memory is finite. Once full, a new object cannot be stored without removing something or rejecting the write. The policy decides which existing entry is least valuable to keep, directly affecting hit ratio, latency, and database load.

2. Eviction vs expiration — what is the difference?

Expiration removes an entry because its TTL ended and it is no longer valid; it is about freshness. Eviction removes a still-valid entry because memory is needed; it is about memory management. Caches normally use both, since TTLs alone cannot handle a cache that fills before entries expire.

3. How does LRU work?

It evicts the entry that has gone longest without being accessed, on the assumption that recently used data will be reused soon. A classic implementation uses a hash map for lookup plus a doubly linked list for recency, giving O(1) access and eviction. Production systems often approximate it by sampling a few keys rather than maintaining an exact list.

4. What is LRU's main weakness?

It ignores frequency, so a large one-time scan can make every scanned record look recently used and push out genuinely hot data. This is cache pollution. Scan-resistant variants require a second access before treating a new entry as hot, and LFU or frequency-based admission can also protect the working set.

5. How does LFU differ from LRU?

LRU uses time since last access; LFU uses the number of accesses. LFU protects a stable set of hot keys and resists scans, but adapts slowly when popularity changes, so an item that was briefly viral can stay cached too long. Implementations add aging or decay, and often break ties by recency.

6. When would you choose FIFO?

When simplicity and low metadata matter and insertion order is a reasonable proxy for usefulness. FIFO needs no recency list or frequency counters, so it is cheap. The cost is that a frequently used entry can be evicted simply because it is old, which is usually a poor fit for general web traffic.

7. Why would anyone use random eviction?

It requires almost no tracking, which reduces overhead and memory per entry. On some workloads its hit rate is close enough to LRU or LFU that the extra bookkeeping is not justified. It is also a good baseline for benchmarking: if a smarter policy barely beats random, it may not be worth the complexity.

8. When is MRU appropriate?

Only when the most recently used item is the least likely to be needed again, such as a job that loops over the same large set of records in order. For normal web workloads, recently used data is exactly what should remain cached, so MRU is a poor default.

9. Does TTL replace an eviction policy?

No. TTL handles freshness by removing entries after a fixed time, but if the cache fills before those TTLs expire, it still needs a policy to choose a valid victim. Most systems combine expiration with LRU, LFU, or another policy. TTLs also need jitter so many keys do not expire simultaneously and stampede the database.

10. What does volatile-lru mean in Redis?

It evicts the least recently used key, but only among keys that have a TTL set. Persistent keys without a TTL are never evicted. If memory is full and no volatile key remains, Redis behaves like noeviction and rejects writes that need more memory, so the policy must match how the cache is used.

11. Why does object size matter for eviction?

Evicting one large object may free as much memory as evicting thousands of small ones, but LRU and LFU count both as a single entry. A cache limited by item count can still run out of memory because of a few huge values. Limit by bytes, monitor item sizes, and consider compressing, splitting, or not caching oversized objects.

12. What is cache pollution, and how do you prevent it?

It is low-value data displacing useful data — for example, a full table scan or thousands of unique search queries filling the cache. Prevent it with admission control, which decides whether a new object should enter at all, plus scan-resistant policies or frequency-based admission such as TinyLFU. Skipping cache writes for known one-time jobs is the simplest defense.

13. How do you measure whether an eviction policy is working?

Track hit ratio per key pattern or route, eviction rate, memory usage, backend request rate, latency, and expired entries. A high aggregate hit ratio can hide a critical route that always misses. If evictions spike and backend load rises, the cache may be undersized or holding too much low-value data rather than using the wrong algorithm.

14. Which eviction policy should you start with?

LRU or an LRU-like policy is a reasonable default when recently accessed data tends to be reused. If a stable set of keys stays hot, LFU can do better; for very low tracking budgets, FIFO or random; for strict freshness, TTL combined with LRU or LFU. Measure on your own workload rather than choosing by reputation.

!Traps

  • Treating TTL as a complete eviction policy and ignoring what happens when the cache fills before entries expire.
  • Using pure LRU behind a periodic full scan and letting the scan flush the working set.
  • Using pure LFU without decay, so a briefly viral key stays cached long after it stops being requested.
  • Capping the cache by item count while storing a few very large objects.
  • Configuring volatile-* eviction while most keys have no TTL, then being surprised when writes fail.
  • Adding the same TTL to a large batch of keys and creating a synchronized expiry stampede.
  • Choosing a policy by reputation without measuring hit ratio and eviction rate on the real access pattern.
  • Blaming the eviction algorithm when the cache is simply undersized or is caching low-value data.
