Geohash
A short Base32 string that encodes a rectangular cell on the Earth's surface; longer strings mean smaller cells.
Cell
The rectangle represented by one geohash prefix at a given length; every point inside it shares that prefix.
Prefix property
Locations in the same cell share the leading characters of their geohash, which is what makes a range scan on a string index work.
Morton code (Z-order curve)
The interleaving of longitude and latitude bits so that a two-dimensional point becomes one ordered value.
Base32 alphabet
The 32-character set used to write five bits per character; a, i, l, and o are omitted to avoid misreading.
Neighbor cell
One of the eight cells surrounding a given cell; together with the cell itself they form the 3×3 grid used for radius search.
Covering set
The collection of cells whose union contains the search area, used when the radius is much larger than one cell.
Two-phase filter
Cheap index lookup to get candidate rows by cell, followed by an exact distance computation on only those candidates.

01Why one index is not enough

A food-delivery app wants every restaurant within 500 meters of the user. Restaurants already have a latitude and a longitude, so it looks like a solved problem.

  • A separate index on latitude and on longitude still leaves the database to combine two independent ranges.
  • A B-tree organizes values in one dimension: it can seek to a latitude band quickly, but it cannot also narrow by longitude in the same descent.
  • Driving the query from the latitude index produces a strip that wraps around the entire globe, and every row in that strip must be filtered by longitude.
  • With millions of rows the strip is enormous relative to the handful of results, so most of the I/O is wasted.
  • The fix is to represent the 2D location as one value that sorts meaningfully, so a single index range scan returns a compact candidate set.
The strip is worse the closer the query is to the poles, because a degree of longitude covers less ground there.

02What a geohash is

  • A geohash converts a coordinate pair into a short string of letters and digits, for example 9q8yyk8.
  • Each string identifies a rectangle, not a point: every coordinate inside that rectangle encodes to the same string.
  • The string length sets the precision, and each extra character subdivides the previous rectangle into 32 smaller ones.
  • Shorter strings cover continents and regions; longer strings narrow down to a neighborhood, a block, or a building.
  • Because nearby points usually land in the same or adjacent cells, they usually share a leading substring.
  • This turns a two-dimensional proximity question into a string prefix search, which any ordered index already supports.
  • The encoding is deterministic, so the same coordinates always produce the same key — a requirement for using it as a stored index value.

03Encoding step one: bisecting the ranges

  • Longitude spans [-180, 180] and latitude spans [-90, 90]; each dimension is bisected independently.
  • At each step, compare the value with the midpoint of the current interval and emit 0 for the lower half, 1 for the upper half.
  • Then keep the half that contains the value and repeat, halving the interval every time.
  • Each bisection adds one bit of precision, so after n steps the coordinate is pinned to an interval of width range / 2^n.
  • Longitude and latitude are processed as two separate bit sequences of the same length.
  • The process is equivalent to writing the coordinate in binary and keeping the leading fractional bits.

04Interleaving the bits and Base32

  • The two bit sequences are merged by taking longitude first, then latitude, then the next longitude bit, and so on.
  • Interleaving keeps both dimensions balanced: every extra pair of bits shrinks the rectangle horizontally and vertically.
  • This interleaving is a Morton code, also called a Z-order curve, because the order traces a Z-shaped path through the grid.
  • The combined bit stream is then cut into groups of five bits, and each group becomes one character.
  • A five-bit group has 32 possible values, so the alphabet is Base32: digits plus lowercase letters, minus the easily confused a, i, l, and o.
  • San Francisco's first ten bits produce 9 then q, which is why every geohash in the city begins 9q.

05Precision levels

  • Every added character contributes five more bits, dividing the current cell by 32.
  • Cell height is roughly constant for a given length; cell width shrinks toward the poles because lines of longitude converge.
  • The table below gives the usual approximate sizes near the equator — treat them as magnitudes, not exact constants.
  • Pick a length from the search radius, not from a habit: a radius search needs cells at least as large as the radius.
  • The same length therefore means different ground distances in Nairobi and in Reykjavik.

06Prefixes, storage, and prefix queries

  • Cells nest: the cell for 9q8 strictly contains every cell whose string starts with 9q8.
  • So a common prefix of length k guarantees both points are inside the same cell of precision k.
  • Store the geohash in an ordinary string column and keep the raw latitude and longitude too, because exact distance needs the original numbers.
  • Create a normal B-tree index on the geohash column; no spatial extension is required.
  • A prefix query becomes WHERE geohash LIKE '9q8yyk%', which the index answers as a range scan: seek to the first match and stop when the prefix no longer matches.
  • Some databases need an explicit operator class (PostgreSQL's text_pattern_ops) before a LIKE prefix can use the index at all.
  • The same scan can be written as a string range, for example geohash >= '9q8yyk' AND geohash < '9q8yyl', because l is the next character after k in the alphabet.

07The boundary problem

  • A user standing just inside one cell can be meters away from a restaurant just inside the next cell.
  • Those two locations may share a very short prefix, or in the worst case no prefix at all.
  • Two points a couple of meters apart on opposite sides of the equator or the prime meridian can have geohashes with completely different first characters.
  • So the implication runs one way only: shared prefix implies close, but close does not imply shared prefix.
  • Searching a single cell therefore silently drops true neighbors, which is the classic geohash bug: flawless in a demo, lossy near cell edges in production.
  • The bug is invisible in metrics unless you specifically test points near boundaries.

08Neighbor search and choosing precision

  • Every cell has eight neighbors — north, south, east, west, and four diagonals — forming a 3×3 block with the user's cell.
  • Querying all nine cells covers everything within one cell width and height of the user, whichever side of a boundary they are on.
  • The nine prefix scans can be issued as one IN query or nine range scans; either way they are small index seeks.
  • Nine lookups are far cheaper than scanning a latitude strip that circles the planet.
  • Most geohash libraries provide a neighbor function; hand-rolling it is where date-line and pole bugs enter.
  • For the 3×3 rule to be correct, the cell must be at least as wide and tall as the search radius.

09Filtering by actual distance

  • The nine cells form a rectangle, but the requirement is a circle, so corner candidates can be too far away.
  • Run an exact distance calculation on each candidate, typically the Haversine formula or the database's distance function.
  • Drop candidates beyond the radius, then sort the rest by distance before returning them.
  • This two-phase pattern — cheap index narrowing, then exact geometry — is standard in spatial queries.
  • The index is allowed to be approximate because the final filter is exact.
  • In a real app the spatial filter is combined with other predicates such as open-now or delivers-to-this-area, and those can be applied in the same query.

10End-to-end flow and moving objects

  • On write, compute the geohash for the restaurant's coordinates and store it alongside latitude and longitude.
  • On read, encode the user's position, compute the eight neighbors, run nine prefix scans, distance-filter, and sort.
  • Location updates for moving objects follow the same path: recompute the geohash and update the stored row or key.
  • GPS pings arrive every few seconds, so writing a relational row per ping is usually the wrong shape.
  • Keep the latest driver position in a fast in-memory store and let TTLs or heartbeats remove drivers who go offline.
  • Keep live position state separate from the append-only history of location events, because they have different write rates and retention needs.
Encode user location to a 6-character geohash→Compute the 8 neighboring cells→Prefix-scan all 9 cells for candidates→Compute exact Haversine distance→Filter by radius and sort

11Limitations

  • Uneven cell sizes: the grid splits degrees evenly, but a degree of longitude is widest at the equator and shrinks to nothing at the poles.
  • Fixed grid: the cell size cannot adapt to density, so a downtown cell may hold thousands of rows while a rural cell of the same size holds none.
  • Dense cells return large candidate sets that all need distance filtering, which erodes the benefit of the index.
  • Date line: points just east and west of 180° are physically close but sit at opposite ends of the string range, so neighbor logic needs wraparound.
  • Poles: cells become extremely thin and the 3×3 coverage argument becomes unreliable.
  • The structure indexes points only; polygons, routes, and delivery zones do not fit one key without duplication.

12Beyond nearby search

  • Because a cell is a grouping key, geohashes aggregate data by area: count ride requests per 6-character cell to build a heat map.
  • Shortening the prefix rolls smaller cells up into larger ones, so one dataset supports several zoom levels.
  • Prefixes also work as partition keys: send every driver whose geohash starts 9q to the same shard.
  • The same density skew reappears here — a partition covering a busy city receives far more traffic than a rural one.
  • Fix hot partitions by splitting busy prefixes into longer prefixes or by giving them more capacity.
  • Prefix-based partitioning keeps related locations together, which helps local queries but concentrates load.

13Real systems and when to use it

  • Redis stores locations in sorted sets using a geohash-derived score, so a score range narrows candidates before exact distance filtering; prefer GEOSEARCH over the older GEORADIUS.
  • Redis fits live, in-memory data such as driver positions, but the working set must fit in memory.
  • Elasticsearch offers geohash grid aggregations for grouping documents by area, plus distance queries on geo_point fields.
  • A plain indexed column is often enough, and its portability is the main attraction: no spatial database required.
  • If the database already has strong spatial support — PostGIS, MongoDB 2dsphere — use it for proximity and keep geohash for sharding, caching, or grouping.
  • Write the encoder yourself only to learn it: pole handling, date-line wrapping, precision choice, and covering generation are all easy to get subtly wrong, so production code should use a maintained library.
  • Choose a quadtree when data is very uneven, S2 or H3 at global scale, and an R-tree when the objects are shapes rather than points.

↔Trade-offs to say out loud

  • One string key makes geohash portable to any ordered index, but it flattens a sphere onto a grid and inherits the distortion.
  • Longer geohashes shrink candidate sets but risk missing neighbors unless the 3×3 search still covers the radius.
  • Shorter geohashes guarantee coverage but return many candidates that must be distance-filtered.
  • Nine prefix scans fix the boundary bug at the cost of roughly nine index seeks instead of one.
  • Fixed cell sizes keep encoding trivial but waste work in dense areas and waste cells in empty ones.
  • Prefix partitioning keeps nearby data co-located but concentrates traffic on popular regions.
  • Storing raw coordinates alongside duplicates data but is mandatory for exact distance and for re-encoding at other precisions.
  • Geohash over native spatial indexes maximizes portability but gives up polygon support and globe-correct geometry.

?Interview questions

Answer aloud before opening the outline.

1. Why is a normal B-tree index on latitude and longitude not enough?

A B-tree orders values along one dimension, so it can seek a latitude band or a longitude band but not intersect both cheaply. Driving from one column leaves a strip that spans the other dimension entirely, and every row in it must be filtered. A geohash collapses both coordinates into one sortable value so a single range scan returns a small candidate set.

2. How is a geohash actually computed?

Bisect the longitude range and the latitude range independently, emitting a 0 or 1 at each step depending on which half contains the value. Interleave the two bit streams starting with longitude — a Morton code — then cut the result into five-bit groups and map each group to a Base32 character.

3. What does a geohash represent: a point or an area?

An area. Every coordinate inside the rectangle encodes to the same string, and the string length determines the rectangle's size. This is why geohash is an index key rather than a precise location: the raw latitude and longitude are still needed for exact distance.

4. Why do nearby points sometimes share no prefix?

Because cell boundaries are arbitrary with respect to the data. Two points a few meters apart can sit in different cells, and near the equator, the prime meridian, or the date line their strings can differ from the first character. Proximity implies a shared prefix only in the other direction.

5. How do you fix the boundary problem?

Search the eight neighboring cells as well, so the 3×3 block covers everything within one cell width and height. For this to be correct, the chosen cell must be at least as large as the search radius, or you must generate a covering set of cells instead.

6. How do you pick the geohash precision for a radius search?

Pick the longest length whose cell is still at least as wide and tall as the radius, so the 3×3 grid reaches the full circle. Then measure candidate counts in both dense and sparse areas, because the same length behaves differently at different latitudes and densities.

7. Why is a distance filter still needed after the prefix scan?

The nine cells form a rectangle while the requirement is a circle, so corner candidates can lie outside the radius. Haversine or a database distance function removes them, and the result is sorted by distance. The index narrows, the geometry decides.

8. What happens to geohash accuracy near the poles?

Cells keep roughly the same height but become very narrow in ground distance, because lines of longitude converge. Coverage arguments based on cell width break down, and neighbor logic becomes unreliable. A spherical index such as S2 handles polar and date-line geometry properly.

9. How would you find all drivers within 2 km of a rider?

Encode the rider's position, choose a precision whose cells cover 2 km, and scan the 3×3 block of cells holding live driver positions — typically in memory with TTLs. Then compute exact distance, filter, and sort. History belongs in a separate store, not in the live position table.

10. How can geohash be used for sharding?

Use a geohash prefix as the partition key so nearby locations land on the same shard, which keeps local queries single-shard. The cost is skew: a prefix covering a dense city handles far more traffic than a rural one, so busy prefixes need splitting or extra capacity.

11. When would you not choose geohash?

When the data is highly uneven (a quadtree adapts), when the system is global and polar or date-line correctness matters (S2 or H3), or when the objects are polygons and lines rather than points (an R-tree). Geohash indexes points well and shapes poorly.

12. Why keep latitude and longitude if the geohash is already stored?

The geohash identifies a cell, not a position, so exact distance and sorting need the original coordinates. The coordinates also let you re-encode at a different precision later without going back to the source data.

!Traps

  • Querying only the user's own cell and calling the feature done — results vanish near boundaries in production.
  • Choosing a geohash length without checking that the 3×3 block still reaches the search radius.
  • Forgetting text_pattern_ops or the equivalent, so the prefix query silently falls back to a full scan.
  • Assuming a shared prefix is required for proximity; the implication only holds in one direction.
  • Applying exact-distance filtering to millions of rows instead of to the small candidate set.
  • Sharding by geohash prefix and ignoring that dense regions become hot partitions.
  • Expecting one geohash key to index a delivery polygon without duplicating it into every overlapping cell.
