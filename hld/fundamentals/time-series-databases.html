01The problem time-series databases solve

Monitoring and metering produce a very particular workload: many sources each emit one number every few seconds, forever, and almost every query asks about a time range.

  • The write rate is high and constant, and writes are nearly all appends of new timestamps.
  • Rows are rarely updated or deleted individually; they simply age out.
  • Queries ask for a range — last hour, last day — grouped by host, endpoint, or region.
  • A general-purpose table accumulates enormous numbers of rows, and its indexes grow with them.
  • Storing each sample with full row overhead wastes space, because timestamps and label sets repeat constantly.
  • Deleting old data through row-by-row deletes is slow and leaves bloat.
  • Every property points to a specialized layout: append-only, time-ordered, columnar, and easy to expire.

02What a time-series database is

  • It stores samples: a metric name, a label set, a timestamp, and a value.
  • A series is the identity formed by the metric plus its exact label set; all its samples share that identity.
  • Writes are appends keyed by series and time, with no read-modify-write and no cross-row relationships.
  • The engine indexes series by labels, and stores samples ordered by time inside each series.
  • Queries select series by label matchers and a time range, then aggregate the values.
  • The design assumes data is immutable once written, which unlocks compression and cheap retention.
  • Engines differ in interface — some pull from scrape targets, others accept pushed writes — but the model is the same.

03Data model and cardinality

  • Labels are the dimensions you filter and group by, such as host, region, or endpoint.
  • Every distinct label combination creates a new series, with its own index entry and storage stream.
  • Cardinality is the number of distinct series, and it is the dominant cost driver.
  • A label like user id or request id turns one metric into millions of series and overwhelms the index.
  • A label like region or status code stays small and is safe to group by.
  • So label design is the schema design of a time-series database, and it must be decided before ingest.
  • The usual failure is invisible at first: cardinality explodes when a new high-cardinality label is deployed.

04The write path

  • Samples are batched, because one write per sample would waste most of the effort on overhead.
  • The batch is appended to a write-ahead log so it survives a crash before being stored.
  • Samples are added to the in-memory head block, indexed by series and sorted by time.
  • When the head block reaches its size or time limit, it is written out as an immutable block.
  • Blocks are never edited, so later writes create new blocks rather than modifying old ones.
  • Compaction merges small blocks into larger ones, which reduces query fan-out over time.
  • Writes are cheap because the engine appends rather than searching for an existing row.

05Storage layout and compression

  • Within a series, timestamps are usually regular, and values change slowly or repeat.
  • The engine stores samples column by column — all timestamps together, all values together — rather than as rows.
  • Timestamps are stored as deltas, and then deltas of deltas, so a constant scrape interval encodes as near-zero.
  • Floating-point values are stored by their bit patterns with XOR compression, which makes repeated values very cheap.
  • Labels are stored once per series rather than repeated on every sample.
  • The result is that storage grows with the number of changes, not with the number of samples times a row size.
  • That compression is what makes retaining fine-grained data for weeks or months practical.

06Indexing time and labels

  • The label index maps each label pair to the series that contain it, which makes matcher-based selection fast.
  • Time is handled by partitioning storage into blocks with bounded time ranges, so a range query touches only the relevant blocks.
  • Recent data lives in memory, so dashboards over the last minutes read from the head block.
  • Older blocks carry a sparse index of series and time inside the block, so a query can seek instead of scanning.
  • Queries combine a label match with a time range; both filters prune before any sample is decoded.
  • Block metadata lets the engine skip blocks entirely when their time range or label set cannot match.
  • The cost of a query grows with the number of matched series and the range width, which is why cardinality matters so much.

07Query patterns

  • The canonical query is: select series by labels, take a time range, aggregate the values.
  • Common aggregations are sum, average, minimum, maximum, count, and rate over a window.
  • Percentiles are computed from histograms or approximated from compressed sketches, because exact percentiles over raw samples are expensive.
  • Grouping by a label produces one result series per label value, which is how per-host or per-region charts are built.
  • A rate query converts a monotonically increasing counter into a per-second value by differencing over the window.
  • Long ranges over raw samples are costly, which is why rollups exist for historical views.
  • Query cost is dominated by matched series count and window size, not by total table size.

08Retention and tiered storage

  • Time-series data loses value with age, so retention is a first-class feature rather than an afterthought.
  • Because storage is organized in immutable time-bounded blocks, expiry is just dropping whole blocks.
  • Policies can differ per series or per table: keep raw data briefly, keep rollups much longer.
  • Older blocks can move to cheaper object storage while remaining queryable, at higher latency.
  • Deleting a whole block is far cheaper than deleting rows and leaves no bloat.
  • Retention must be planned against query needs: if a dashboard needs a year of data, keep a rollup for it.
  • This is a large operational advantage over general-purpose databases, where aging data out is a maintenance burden.

09Downsampling and continuous aggregates

  • Downsampling replaces many fine-grained samples with a smaller number of aggregates.
  • A one-minute rollup keeps count, sum, min, max, and sometimes a histogram, so averages remain computable later.
  • Keeping count and sum rather than only the average is essential, or later re-aggregation is wrong.
  • Rollups are computed continuously as new blocks arrive, so historical queries never rescan raw samples.
  • The cost is resolution: a yearly chart cannot show second-level spikes that were averaged away.
  • Late-arriving samples can invalidate a rollup window, so recomputation or a lateness window is needed.
  • Choosing granularities — raw, minute, hour — is choosing between query cost and the detail users can still see.

10Late and out-of-order samples

  • Sensors buffer, retry, and report late, so samples do not always arrive in timestamp order.
  • Many engines accept out-of-order writes only within a bounded window, then reject or drop them.
  • Handling them requires rewriting the affected block, which is why it is treated as an exception rather than the norm.
  • The same sample may be delivered twice; the engine must deduplicate by series and timestamp to keep sums correct.
  • Idempotent writes — same timestamp replacing the same value — make retries safe.
  • A lateness window should be documented, because it defines when a dashboard's past values stop changing.
  • Aggregations that already ran over an incomplete window will be wrong unless they are recomputed.

11Scaling

  • Sharding is usually by series, so one series lands on one node and queries can be routed.
  • Some designs also shard by time, which helps retention and parallel range scans.
  • Replication provides availability and read capacity, with the usual staleness trade-off.
  • A query spanning many series fans out to the owning nodes and merges partial aggregates.
  • Merging partial results requires combinable aggregates: counts and sums combine, distinct counts need sketches.
  • Very long ranges over many series are the hardest query shape, and rollups are the standard mitigation.
  • Ingest scale and query scale are separate dimensions, so they are sized independently.

12Alternatives and comparisons

  • A relational table with an index on (series_id, timestamp) handles modest volumes and keeps SQL and transactions.
  • It becomes expensive at scale because each row carries overhead and retention means bulk deletes.
  • A wide-column store can hold high-volume time-ordered rows partitioned by series, but lacks the compression and rollups.
  • A search or columnar analytics engine can answer time-range aggregates, but usually at higher ingest cost.
  • Prometheus-style systems pull metrics from targets, while other engines accept pushed writes; the choice affects how targets are discovered and how gaps appear.
  • The specialized engine wins when ingest rate, retention, and range queries dominate and rows are never updated.
  • If you need relational relationships or transactions, a time-series store is the wrong tool.

13When to use one

  • Infrastructure and application monitoring: metrics per host, service, and endpoint.
  • IoT and sensor telemetry, where devices emit readings continuously.
  • Financial or trading ticks, where ordered timestamps and range aggregation dominate.
  • Any workload that is append-only, time-ordered, and queried by range and label.
  • Not for records that are updated by attributes, joined across entities, or need multi-row transactions.
  • Not for sparse, irregular events that are read one at a time; a document or relational store fits better.
  • The decisive question is whether the value of the data decays with age — if yes, retention and rollups are the core features.

↔Trade-offs to say out loud

  • Compression makes long retention affordable but works because data is append-only, so updates become rewrites.
  • High-cardinality labels allow precise filtering but multiply series and can overwhelm the index.
  • Small head blocks limit memory use and data loss on crash but create many blocks for compaction to merge.
  • Downsampling cuts query cost for old data but permanently removes fine-grained detail.
  • Rollups make long-range queries fast but must store combinable aggregates and handle late data.
  • Bounded lateness windows keep blocks immutable but reject genuinely late samples.
  • Sharding by series spreads ingest and routes queries but makes cross-series comparisons a fan-out.
  • Tiered storage lowers cost per byte but makes historical queries slower.
  • Deduplication keeps aggregates correct but adds index and write overhead per sample.

?Interview questions

Answer aloud before opening the outline.

1. What distinguishes a time-series database from a normal one?

It assumes every row is an append-only sample identified by a metric, labels, and a timestamp. That assumption lets it store data in time-ordered columnar blocks, compress timestamps and values heavily, and expire data by dropping whole blocks instead of deleting rows.

2. What is a series and why does cardinality matter?

A series is one metric plus one exact label set, and each one gets its own index entry and storage stream. Cardinality is how many series exist, so a high-cardinality label such as user id or request id multiplies both index size and query fan-out. It is the main scaling limit of the model.

3. Why is time-series data so compressible?

Timestamps usually arrive at a regular interval, so deltas are constant and deltas of deltas are near zero. Values often change slowly or repeat, which XOR encoding captures cheaply. Labels are stored once per series rather than on every sample. Together that removes most per-row overhead.

4. Walk through a write.

Samples are batched, appended to a write-ahead log for durability, and inserted into the in-memory head block sorted by series and time. When the head block fills, it is flushed as an immutable block, and compaction later merges small blocks into larger ones.

5. How does a range query execute?

The engine uses the label index to select matching series, then uses block metadata to skip blocks whose time range cannot match. Within the remaining blocks it decodes only the needed columns and aggregates per series and window. Cost follows matched series count and range width.

6. What is downsampling and what must it preserve?

Downsampling replaces many samples with fewer aggregates over a window. It must keep combinable values — count, sum, min, max — rather than only the average, or later re-aggregation over a longer range becomes wrong. The cost is losing fine detail permanently.

7. Why is retention cheap here?

Because storage is organized into immutable, time-bounded blocks, expiring old data means deleting whole blocks. That is a metadata operation plus a file removal, with no row-level deletes, no index churn, and no bloat left behind.

8. How should out-of-order samples be handled?

Accept them only within a documented lateness window, write them idempotently so retries cannot double-count, and recompute affected rollups. Frequent out-of-order data means rewriting blocks, so it should be treated as an exception rather than a normal path.

9. What happens if a metric gains a high-cardinality label?

Each distinct value creates a new series, so index memory, storage streams, and query fan-out all grow with the value count. A single deployment can multiply series count dramatically. Guard against it by reviewing label choices and monitoring series count as a first-class metric.

10. Why are percentiles harder than averages?

An average is one number that combines across series, but a percentile describes a distribution and cannot be averaged. Accurate percentiles need the underlying samples or a histogram or sketch that preserves the distribution, which is also why rollups must keep that sketch.

11. When is a relational database good enough?

When ingest volume is modest, retention is short or unimportant, and you value SQL, joins, and transactions over compression. An index on series and timestamp handles range queries well at small scale, and one store is simpler to operate than two.

12. How do you decide between pushing and pulling metrics?

Pulling lets the collector discover targets and detect absence as a failed scrape, which suits service discovery. Pushing suits short-lived jobs, devices behind NAT, and high-volume producers. The decision affects gap handling and how you instrument targets, not the storage model.

!Traps

  • Adding a per-user or per-request label and destroying the index with cardinality.
  • Storing only the average in a rollup, then being unable to compute an honest longer-range average.
  • Assuming a time-series store can answer joins or transactions across entities.
  • Deleting individual samples and expecting space to be reclaimed like block expiry.
  • Sending one write per sample and paying connection and batching overhead on every point.
  • Ignoring out-of-order writes until dashboards start disagreeing with each other.
  • Retaining raw data forever because compression is cheap, without planning query cost growth.
