In one lineA B-tree is a wide, shallow, self-balancing search tree whose nodes are disk pages, so a lookup needs only a few page reads instead of a table scan — and its sorted order also makes range queries cheap, at the price of write amplification on splits.
Page
The fixed-size block a database reads from and writes to disk; a B-tree node is sized to fit one page.
Fanout
The number of child pointers a node holds; large fanout is what keeps the tree shallow.
Balanced tree
A tree in which every root-to-leaf path has the same length, so lookup cost is predictable.
Internal node
A node holding separator keys and child pointers; it routes the search but stores no rows.
Leaf node
The bottom-level node that holds the actual index entries — keys plus row references or rows.
Node split
Dividing an overfull node into two and promoting a separator key to the parent, which increases the tree's width, not its order.
B+ tree
A B-tree variant where all entries live in leaves and leaves are linked, so internal nodes hold only separators.
Clustered index
An index whose leaf level is the table rows, physically ordered by the index key.
Covering index
An index containing every column a query reads, so the engine never fetches the base row.
Range scan
Reading a contiguous run of index entries in key order, such as all orders in a date interval.

01Why a full table scan is not acceptable

A query such as SELECT * FROM users WHERE id = 5000000 must not examine every row. Without an index the engine has no idea where that id lives, so it reads the table page by page.

  • A scan costs time proportional to table size, so it gets slower every month as data grows.
  • It also reads pages it does not need into the buffer pool, evicting useful pages and hurting other queries.
  • An index adds a small, sorted structure that maps key values to row locations.
  • With an index the engine can navigate to the key in a few page reads instead of touching the whole table.
  • Most relational engines build these indexes with a B-tree or the closely related B+ tree.
  • The same structure keeps keys sorted, so it also answers range and ordering queries, not just equality lookups.

02What a B-tree is

  • A B-tree is a balanced, multiway search tree: each node holds many sorted keys and many child pointers, not just two.
  • Keys inside a node are sorted, and a child between two keys contains only values in that interval.
  • Every root-to-leaf path has the same length, so the worst case equals the average case — no degenerate tree.
  • The tree stays balanced by construction: inserts and deletes rebalance locally rather than rebuilding the index.
  • Each node is sized to fill one disk page, so reading a node is one I/O operation.
  • Because one node can hold many keys, the tree stays shallow even for very large tables.
  • The index is much smaller than the table, so its upper levels usually stay cached in memory.

03Why disks favor wide, shallow trees

  • Disk and SSD reads happen in pages; fetching one byte costs the same as fetching a whole page.
  • So the goal is to minimize the number of pages touched, not the number of comparisons.
  • A binary search tree has fanout two, so its height grows with the logarithm of the row count in base two — far too many levels for a large table.
  • A B-tree with large fanout reduces height to a logarithm in a much larger base, so a handful of levels covers a huge key space.
  • This is why fanout, not comparison count, is the design variable of an on-disk index.
  • The top levels are tiny and almost always in the buffer pool, so a lookup typically costs one or two real I/Os at the leaf.
  • The same reasoning explains why in-memory indexes can afford different structures: there is no page-fetch penalty to amortize.

04Anatomy of a node

  • A node stores an ordered array of keys and an ordered array of child pointers, with the pointers interleaved between keys.
  • With k keys a node has k+1 children: one before the first key, one between each pair, one after the last.
  • Internal nodes hold separator keys only — copies of keys used for routing, not the data itself.
  • Leaf nodes hold the index entries: the key plus either the row itself or a pointer to it.
  • Leaves also carry sibling pointers in a B+ tree, which turns range reads into a sequential walk.
  • Nodes are kept at least half full (except the root), which bounds height and wasted space.
  • Slot arrays and free space inside the page make inserts and deletes possible without rewriting the whole page.

05Search

  • Start at the root and binary search the node's keys to choose the child whose interval contains the target.
  • Descend one level and repeat until a leaf is reached.
  • At the leaf, binary search finds the entry; then follow its row reference if the query needs columns the index lacks.
  • The number of page reads is the tree height, not the number of rows.
  • Equality lookups, IN lists, and prefix lookups on the leading column all use the same descent.
  • An unsuccessful lookup is just as cheap: it stops at the leaf position where the key would be.
  • Because the top levels are cached, the dominant cost is usually the leaf page plus the row fetch.
Read root page→Binary search keys, choose child→Descend to next level→Reach leaf, locate entry→Follow row pointer if needed

06Insert and node split

  • Locate the target leaf by the same descent as a search.
  • Insert the key in sorted position if the page has free space.
  • If the page is full, split it into two roughly half-full pages and promote the middle key to the parent.
  • The parent now needs one more child pointer; if it overflows too, it splits as well, and the effect propagates upward.
  • If the root splits, a new root is created and the tree grows one level taller — the only way height increases.
  • Splits are local, so an insert touches a bounded number of pages rather than rewriting the index.
  • Random insert order scatters writes across the tree; monotonic keys such as timestamps concentrate them at the right edge.

07Delete and rebalance

  • Find the entry and remove it from its leaf.
  • If the leaf falls below the minimum occupancy, the tree repairs it by borrowing an entry from a sibling or merging with one.
  • Merging removes a separator from the parent, which can cascade upward; if the root empties, the tree shrinks a level.
  • Deletes therefore cost more than a simple removal and can touch sibling pages.
  • Many engines defer the physical work: they mark the entry deleted and reclaim space later, which keeps deletes fast.
  • Frequent delete-and-insert churn leaves pages underfilled, so indexes need maintenance to stay compact.
  • A shrinking tree is a sign of healthy rebalancing, not of data loss.

08B+ trees versus classic B-trees

  • In a classic B-tree, an entry can live in an internal node as well as a leaf.
  • In a B+ tree, all entries live in the leaves; internal nodes hold only separator keys for routing.
  • Because internal nodes carry no row pointers, they pack in more keys per page, which raises fanout and lowers height.
  • Leaves are linked in key order, so a range query finds the start and then walks sequentially instead of re-descending.
  • Every lookup reaches a leaf, so search cost is uniform, which makes performance easier to predict.
  • The price is that a key may be stored twice — once as a separator, once in a leaf — and that internal nodes cannot answer a lookup alone.
  • Most relational indexes — and most key-value engines built on B-trees — use the B+ layout for exactly these reasons.

09Range scans and ordered access

  • A range predicate such as WHERE created_at BETWEEN a AND b descends to the first matching key.
  • From there the engine walks the leaf level in order until the range ends, using sibling pointers.
  • That turns a scattered set of rows into one sequential read pattern, which storage handles well.
  • The same mechanism satisfies ORDER BY on the index's leading columns without a sort step.
  • Prefix queries on strings work because the index is ordered lexicographically.
  • Ordering only helps if the query's sort order matches the index definition, including direction.
  • A range that matches most of the table is cheaper as a scan, which is why the planner compares costs.

10Clustered and secondary indexes

  • A clustered index stores the table rows in leaf pages, ordered by the index key — the index and the table are the same structure.
  • Because rows can be physically ordered only one way, a table has at most one clustered index.
  • A secondary index stores the key plus a row locator — the primary key or a physical address — and needs a second lookup to fetch the row.
  • If the clustered key is wide or changes, every secondary index must carry it, which makes them larger.
  • A covering index includes all columns a query needs, so the second lookup disappears.
  • Secondary lookups that return many rows cause many random row fetches, sometimes slower than a sequential scan.
  • The choice of clustered key therefore affects every query and every other index, not just one access path.

11What a B-tree costs on writes

  • Every insert, update, and delete must also update every index on the table.
  • A split writes two pages and updates a parent, so one logical insert can become several physical writes — write amplification.
  • Updates that change an indexed column relocate the entry, which may split a different leaf.
  • Random key order scatters these writes across the file, causing more I/O than an append-only structure would.
  • The write-ahead log must record page changes, so index maintenance also adds log volume and replication traffic.
  • Leaving a fill factor below full trades disk space for fewer future splits.
  • Indexes left unmaintained accumulate bloat and fragmentation, which raises read cost as well.

12Variants and tuning

  • Prefix compression and suffix truncation shrink keys in internal nodes, raising fanout.
  • Copy-on-write B-trees never modify a page in place; they write a new page and switch a pointer, which gives cheap snapshots.
  • Some engines use a B-epsilon tree that buffers small updates in internal nodes to reduce write amplification.
  • Hash indexes beat B-trees for pure equality lookups but cannot serve ranges or ordering.
  • For very low-cardinality columns, a bitmap index can be far more compact than a B-tree.
  • Buffer pool size decides how much of the upper tree stays in memory, which dominates lookup latency.
  • Measure with EXPLAIN and index statistics; guessing which index the planner will use is unreliable.

13When a B-tree is the wrong choice

  • Write-heavy append workloads — event logs, sensor streams — fit an LSM tree better because sequential writes beat scattered page updates.
  • Full-text and similarity search need inverted indexes or vector indexes, not ordered key lookup.
  • Analytical scans over most of a table prefer columnar storage and zone maps over row-by-row index fetches.
  • A query returning a large fraction of the table is cheaper as a sequential scan; the index only adds random I/O.
  • Too many indexes turn a fast write path into a slow one, so index only columns that queries actually filter or sort on.
  • Low-selectivity predicates — a status column with three values — rarely benefit, because the index still matches most rows.
  • Ordering a clustered index badly makes every insert land on the same page, creating a contention hotspot.

↔Trade-offs to say out loud

  • High fanout keeps the tree shallow and lookups cheap but makes each page split merge more keys, so splits cost more work.
  • Sorted keys enable range scans and ordering but make random inserts scatter page writes across the file.
  • B+ tree leaves linked in order make ranges sequential reads but duplicate separator keys and force every lookup to reach a leaf.
  • Clustered indexes make primary-key range reads fast but allow only one per table and make non-key updates expensive.
  • Secondary indexes speed up more queries but add a row lookup per match and enlarge every write.
  • Covering indexes remove row fetches but duplicate data into the index and must be updated on every column change.
  • Low fill factor reduces future splits but wastes space and lengthens scans.
  • More indexes improve read coverage but multiply write amplification, log volume, and storage.
  • Keeping the upper levels cached makes lookups fast but competes with data pages for buffer pool memory.

?Interview questions

Answer aloud before opening the outline.

1. Why do databases use B-trees instead of binary search trees?

Disk reads happen in pages, so cost is measured in pages touched. A binary tree has one key per node, so its height is large. A B-tree packs hundreds of keys into one page, which makes the tree very shallow and keeps the upper levels in memory, so a lookup needs only a few page reads.

2. What does the fanout of a node control?

Fanout is the number of children per node, set by how many keys fit in a page. Higher fanout reduces tree height logarithmically, so fewer pages are read per lookup. It is bounded by page size, key size, and the space taken by child pointers.

3. Walk through what happens on insert.

The engine descends to the correct leaf, inserts the key in sorted order, and splits the page if it is full. The split promotes a separator key to the parent, which may split too, cascading upward. If the root splits, a new root is created and the tree gains one level.

4. Why is a B+ tree usually preferred for indexes?

Because internal nodes hold only separators, they pack more keys per page, raising fanout and lowering height. All entries live in linked leaves, so range scans find the start once and then walk sequentially. The cost is that keys may be stored twice and every lookup reaches a leaf.

5. What is the difference between a clustered and a secondary index?

A clustered index stores the rows themselves in its leaves in key order, so it is the table. A secondary index stores the key plus a row locator and needs a second lookup to fetch the row. A table can have only one clustered index but many secondary ones.

6. How does an index serve a range query?

It descends to the first key in the range, then follows leaf sibling pointers in key order until the range ends. That produces a sequential read pattern and also satisfies matching ORDER BY clauses without a sort. If the range is most of the table, a scan is usually cheaper.

7. What is write amplification in a B-tree?

One logical row change can force several page writes: the leaf, a sibling if it splits, a parent, plus log records for each. Indexes multiply this, since every index must be maintained. That is why write-heavy workloads often prefer append-oriented structures like LSM trees.

8. Why does random insert order hurt?

Random keys land on random leaves, so each insert dirties a different page and defeats sequential write patterns, and the buffer pool cannot hold all the touched pages. Monotonic keys concentrate inserts at one edge, which is friendlier for writes but can create a hot rightmost page.

9. When would the optimizer ignore your index?

When the predicate matches a large fraction of rows, when statistics say the index is not selective, or when the query needs columns the index does not cover. A sequential scan then reads fewer pages than many random index-plus-row lookups. EXPLAIN shows which plan was chosen.

10. What is a covering index and its cost?

It contains every column the query reads, so the engine answers from the index alone and skips the row fetch. The cost is duplicated data and extra write work whenever any covered column changes, plus more storage and memory pressure.

11. How does deletion keep the tree balanced?

If a leaf drops below minimum occupancy, the engine borrows an entry from a sibling or merges the two pages, removing a separator from the parent. That can cascade upward, and an emptied root is dropped so the tree shrinks a level. Many engines defer the physical work and reclaim space later.

12. When is a B-tree the wrong index?

For append-heavy write streams, full-text search, and similarity search, other structures dominate. For analytical queries scanning most of a table, columnar storage without per-row lookups wins. And for pure equality lookups on small keys, a hash index is simpler and faster.

!Traps

  • Saying a B-tree is fast because it uses binary search, instead of because it minimizes page reads.
  • Forgetting that an index must be maintained on every write, and adding one for each column that appears in a query.
  • Assuming a secondary index lookup is free, when each match costs an extra row fetch.
  • Confusing a B-tree with a B+ tree when asked where the entries actually live.
  • Choosing a random UUID as a clustered key and then wondering why inserts scatter across the index.
  • Expecting a low-selectivity index on a status column to speed up a query that matches most rows.
  • Leaving every page completely full, so the next insert forces a split.
