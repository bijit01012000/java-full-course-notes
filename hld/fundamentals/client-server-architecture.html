In one lineClient-server architecture splits responsibilities between clients that handle interaction and servers that own shared data, business rules, and permissions — communicating over a network through a request-response contract.
Client
The program that starts a request: a browser, mobile app, desktop app, or another backend service.
Server
The program that accepts requests, enforces business rules, and returns responses; in production usually many instances behind a load balancer.
Request-response cycle
The client sends a request, the server processes it, and the server returns a response that the client renders or acts on.
Thin client
A client that performs little local processing and relies on the server for most logic, such as a server-rendered website.
Thick client
A client that performs substantial processing locally, such as a single-page app or a video editor.
Polling
The client repeatedly asks the server for updates at an interval, wasting requests when nothing has changed.
WebSocket
A persistent bidirectional connection that lets either side send messages after the initial client-initiated handshake.
Stateless server
A server that keeps no client-specific state between requests, so any instance can handle any request.
Tier
A layer with a distinct responsibility, such as presentation, application, or data; tiers may be separate deployable services.
Trust boundary
The line between code the user controls and infrastructure you control; everything across it must be treated as untrusted.

01What client-server architecture is

A local to-do app can keep its interface, logic, and data on one machine. The moment the same list must appear on a phone, a laptop, and a teammate's computer, a shared source of truth is needed.

  • Responsibilities are divided between two roles: the client starts a request, and the server processes it and responds.
  • The client handles user interaction and presentation; the server owns shared data and enforces business rules.
  • The network is part of the architecture, including DNS, routers, firewalls, proxies, and the protocols between them.
  • A protocol defines the message format and rules — HTTP, gRPC, WebSocket, SMTP, or a database protocol.
  • Client and server are roles, not machine types: a payment service can be a server to checkout and a client to fraud detection.
  • In production the server is usually a fleet of processes behind a load balancer, not one physical machine.

02The request-response cycle

Opening a website shows the full cycle in a few hundred milliseconds.

  • The browser resolves the domain to an IP address using DNS.
  • It establishes a connection, usually TCP plus TLS, to the server on a port such as 443.
  • It sends an HTTP request with a method, path, headers, and optionally a body.
  • The server authenticates the request, runs business logic, and queries a database or cache.
  • The server returns a status code and body — for example 200 OK with HTML, or 404 for a missing resource.
  • The client parses the response and renders the result or updates its local state.
  • Every step can fail independently, so timeouts, retries, and error handling are part of the contract.
DNS lookup→Connect (TCP/TLS)→Send request→Authenticate and process→Query data→Return response→Render or update state
A request is not free: DNS, connection setup, TLS, server processing, and data access all add latency before the first byte of content arrives.

03What the client does

  • Renders the interface and collects user input.
  • Sends requests that describe the user's intent, such as the product chosen and quantity, not the final price.
  • Displays responses and maintains temporary UI state such as an open dialog or a draft form.
  • Performs optimistic updates and local validation for responsiveness, while accepting that the server may reject the result.
  • Caches previously loaded data so some screens still work offline or on a slow connection.
  • Can be a browser, mobile app, desktop app, or another backend service — a client does not need a user interface.

04What the server does

  • Listens on a port and accepts requests from many clients concurrently.
  • Authenticates the caller and authorizes the specific action on the specific resource.
  • Executes business logic such as pricing, inventory checks, and payment capture.
  • Reads and writes shared data in databases, caches, and object storage.
  • Validates input independently of any client-side checks.
  • Returns a response with a meaningful status code, and records logs and metrics for the request.
  • Coordinates with other services, where it becomes a client itself.

Never trust the client

  • Anything running on a user's device can be inspected, modified, or replayed by the user.
  • If the client sends a price, a malicious user can change a laptop's price to one dollar; the server must look up the price itself.
  • A safe checkout request sends the product ID and quantity; the server applies valid discounts and computes the total.
  • Client-side validation is a UX feature — immediate feedback — not a security control.
  • The server must enforce input validation, price and permission rules, rate limits, and idempotency.
  • Hiding a button in the UI prevents accidents, not attacks; only the server can reliably deny the action.

05Why centralize on the server

  • One source of truth: every device reads and writes the same data, so a task completed on a phone is not still pending on a laptop.
  • Security control: sensitive data and operations stay on infrastructure you manage; a shipped app must never contain database credentials or private API keys.
  • Easier maintenance: fix pricing logic once on the server and every client benefits, without shipping a new version.
  • Consistent rules: permissions, fraud checks, and validation are applied uniformly instead of being reimplemented per client.
  • Central audit and backup: access logs, retention, and recovery are possible when data lives in one governed place.
  • Backward compatibility: old clients keep working as long as the API contract remains compatible.

06Thin clients and thick clients

  • A thin client does little local processing: it displays server output and forwards user actions.
  • A server-rendered website is thin — each click asks the server for a new page.
  • A thick client handles substantial logic locally, such as a single-page app or a video editor.
  • Thin clients are easier to maintain centrally and keep rules consistent, but many actions need a network round trip.
  • Thick clients feel faster and can work offline, but logic ships to every device and must stay in sync with the server.
  • Most applications mix both: local interaction and caching, with final authority on prices and permissions left to the server.

07Who starts the conversation: polling and WebSockets

In the basic model the client always initiates. That breaks down when the server has new information the client needs immediately, such as an incoming message.

  • Polling has the client ask periodically, for example every few seconds.
  • Most polls return nothing, wasting bandwidth and server capacity, and updates wait up to one interval.
  • Long polling holds the request open until data arrives or a timeout expires, reducing empty responses.
  • WebSockets open a persistent bidirectional connection after a client handshake, so either side can send at any time.
  • Server-sent events are a one-way alternative for streams the client only needs to receive.
  • The client still initiates a WebSocket connection; the model remains client-server, but the server no longer waits for a request to push data.
  • Choose polling for infrequent updates and simple infrastructure; choose WebSockets for chat, presence, collaboration, and live dashboards.

08Stateless and stateful servers

  • A stateless server processes each request independently; the request carries the credentials and parameters needed.
  • A stateful server stores client-specific information between requests, such as a session or shopping cart in memory.
  • With multiple servers, local state forces subsequent requests to reach the same instance, which complicates routing.
  • If that instance crashes, the session is lost and the user may be logged out or lose a cart.
  • Stateless application servers let any instance serve any request, which makes load balancing, autoscaling, and rolling deploys simple.
  • Shared state belongs in an external database, cache such as Redis, or a signed token, not in process memory.
  • Stateless does not mean no state exists; it means state is not tied to a particular server instance.
Client→Load balancer→Any app instance→Shared session store→Response
Sticky sessions are a middle ground: simple, but they create uneven load and break when the pinned server dies.

09Tiers: one-tier and two-tier

  • A tier is a layer with a clear job; tiers can be separate services or logical layers in one deployment.
  • 1-tier keeps interface, logic, and data on one machine, like a local spreadsheet or single-user desktop tool.
  • One-tier is simple, has no network dependency, and is easy to run, but cannot share data or scale to many users.
  • 2-tier has the client talk directly to a server, often a database server.
  • Two-tier is common for small internal tools on a trusted network and has few moving parts.
  • Every client needs database credentials, business logic is duplicated in each client, and a schema change breaks installed clients.
  • Two-tier is usually a poor fit for public internet-facing systems.

10Tiers: three-tier and n-tier

  • 3-tier separates presentation (browser or app), application (business logic and auth), and data (database, cache, object storage).
  • The client never touches the database directly; it calls the application tier, which enforces permissions.
  • Each tier can be secured, scaled, tested, and deployed independently.
  • The cost is more moving parts, network latency, and the risk of chatty APIs that require many round trips.
  • N-tier adds layers such as a CDN or WAF at the edge, an API gateway, separate domain services, and background workers.
  • Extra tiers let teams scale and own high-traffic components independently and isolate failures.
  • They also make tracing, debugging, and backward-compatible API contracts harder; add a tier only for a real requirement.

11The server as a single point of failure

  • A central server is also a central failure: if the only instance crashes, every client is blocked.
  • Run multiple application instances behind a load balancer that routes only to healthy targets.
  • Use database replicas and failover so a primary failure does not stop writes indefinitely.
  • Replicate caches, load balancers, and queues too, or they become the new single point of failure.
  • Health checks and automated failover reduce recovery time, but they must be tested rather than assumed.
  • The architecture is still client-server; the server side becomes a group of machines presenting one logical service.
  • Redundancy costs money and adds consistency challenges, so apply it according to the availability target.

12Network latency and dependency

  • Every request takes time to travel to the server, be processed, and return.
  • Geography matters: a user far from the server sees a larger round-trip time.
  • Sequential requests add up; five round trips of 250 ms each delay the screen by more than a second.
  • Losing connectivity can stop a client that depends entirely on the server.
  • Reduce round trips with a well-designed API that returns what a screen needs in one or two calls.
  • Use client caching for previously loaded data and a CDN for static assets closer to users.
  • Design offline and error states explicitly rather than assuming the network is always available.

13Security and the trust boundary

  • The client runs on a device the user controls, so the server must treat every request as potentially hostile.
  • Authentication identifies the user, using a session cookie or token.
  • Authorization checks that this user may perform this action on this resource; being signed in does not grant access to someone else's orders.
  • Input validation on the server is mandatory even when the client already validated.
  • Encryption in transit with HTTPS protects credentials and data from interception and tampering.
  • Apply rate limits and idempotency keys to limit abuse and accidental duplicate actions.
  • Never ship secrets, database credentials, or privileged API keys inside a client application.

14Where you see it, and when it fits

  • Websites are client-server: the browser requests, the web server responds.
  • Database access is client-server: the application is the client and the database is the server.
  • Email apps connect to mail servers to send and sync messages.
  • Backend services form chains: order calls payment, which calls fraud detection; each is a server for one call and a client for the next.
  • It fits when you need centralized data, shared business rules, and consistent access control across users and devices.
  • Its main costs are scaling the server side, central points of failure, and dependence on network latency and connectivity.
  • Monoliths, microservices, and serverless all build on this model; they differ mainly in how server-side responsibilities are organized and scaled.
Client interaction→Request over network→Server enforces rules→Shared data access→Response→Client renders

↔Trade-offs to say out loud

  • Centralization gives one source of truth and consistent rules but concentrates load, cost, and failure risk.
  • Thin clients are easy to update centrally but depend on the network for nearly every action.
  • Thick clients feel fast and work offline but duplicate logic and risk drifting from server rules.
  • Stateless servers scale and deploy easily but require external state and an extra lookup per request.
  • Stateful servers can be simpler and faster for a single instance but make routing, scaling, and failover harder.
  • Polling is simple and stateless but wastes requests and adds update latency.
  • WebSockets deliver real-time push but add connection management, scaling, and reconnect complexity.
  • More tiers improve isolation and independent scaling but increase latency, cost, and debugging difficulty.

?Interview questions

Answer aloud before opening the outline.

1. What is client-server architecture?

A model that divides responsibilities between clients, which handle interaction and send requests, and servers, which own shared data, enforce business rules, and return responses. The two communicate over a network using an agreed protocol.

2. Walk through a request from browser to response.

DNS resolves the host, the client opens a TCP and TLS connection, sends an HTTP request, and the server authenticates, runs logic, and queries data. The server returns a status code and body, and the client renders or updates state.

3. What is the difference between a client and a server?

They are roles in a conversation, not fixed machine types. The client initiates a request; the server handles it. A payment service can be a server to checkout and a client when it calls fraud detection.

4. Why should the server never trust the client?

Because the client runs on a device the user controls, where code, requests, and stored values can be modified. The server must independently verify prices, validate input, and enforce permissions; client-side validation is only for UX.

5. How would you prevent a client from changing a product price?

Accept only the product ID and quantity, then look up the current price, apply server-side discounts, and compute the total on the server. Ignore any price supplied by the client and log the discrepancy.

6. Why centralize data and logic on a server?

It gives every device one source of truth, keeps sensitive data and credentials off user devices, and lets you fix or update rules once. It also makes permissions, auditing, and backup consistent.

7. Thin client versus thick client?

A thin client keeps most logic on the server and is easier to maintain, but needs round trips. A thick client processes locally for responsiveness and offline use, but ships logic to every device and must stay in sync with server rules.

8. How can the server push updates to a client?

Polling has the client ask repeatedly, which is simple but wasteful. Long polling holds a request open. WebSockets keep a persistent bidirectional connection so the server can push immediately. Server-sent events cover one-way streams.

9. Stateless versus stateful server?

A stateless server keeps no client state between requests, so any instance can serve any request. A stateful server keeps session data locally, which forces sticky routing and loses the session if that instance dies. Most systems externalize state and keep app servers stateless.

10. What are tiers, and what does 3-tier mean?

Tiers are layers with distinct responsibilities. Three-tier separates presentation, application logic and auth, and data storage. The client talks only to the application tier, so each tier can be secured, scaled, and deployed independently.

11. When would you use n-tier over 3-tier?

When scale, security, or team ownership justifies extra layers such as a CDN or WAF, API gateway, separate domain services, and background workers. Each layer adds operational and debugging cost, so add one only for a concrete requirement.

12. How do you remove the server as a single point of failure?

Run multiple application instances behind a health-checked load balancer, add database replicas with tested failover, and replicate caches, queues, and load balancers. The client still sees one logical service.

13. What are the main limitations of client-server?

Server-side scaling cost, centralized components becoming single points of failure, and dependence on network latency and connectivity. Redundancy, caching, CDNs, fewer round trips, and server-side security checks address them.

!Traps

  • Treating client-side validation as a security control.
  • Shipping API keys or database credentials inside a mobile or web client.
  • Keeping sessions in process memory and then wondering why sticky routing is needed.
  • Assuming the server is one machine rather than a load-balanced fleet.
  • Using polling for real-time interaction and ignoring the wasted requests.
  • Adding tiers for their own sake and increasing latency without a requirement.
  • Forgetting that a WebSocket connection still begins with a client request.
