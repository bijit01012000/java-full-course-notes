01Why there is more than one type of database

One e-commerce application already contains four very different data problems, and each one stresses a different part of the storage engine.

  • Payments and orders need correctness: a partial write must never leave money taken without an order.
  • Shopping carts and login sessions need lookup by a single key with very low latency.
  • The search bar needs to rank products by how well they match free text, tolerate typos, and match word variants.
  • Metrics arrive continuously and are almost always read as a time window aggregate, not as individual rows.
  • A database tuned for one of these jobs is usually mediocre at the others, which is why the categories exist.
  • The categories are not strict boxes: PostgreSQL stores JSON, runs full-text search, and supports vector indexes through extensions.
  • Choosing a database is one of the hardest decisions to undo, because the data model, queries, and operational tooling all grow around it.

Start from the access pattern, not from the product name. The same table can be a good fit for one query and a bad fit for the next.

02Relational databases

A relational database stores data in tables of rows and columns. The schema is fixed: every row in a table has the same columns and types, and the database rejects writes that violate them.

  • A users table holds id, name, email; an orders table holds id, user_id, amount, status.
  • The orders.user_id column is a foreign key pointing at users.id, which is how relationships are modeled.
  • SQL is declarative: you state the result you want and the planner decides which indexes, join order, and algorithms to use.
  • Joins let the same normalized data answer questions that were never anticipated when the schema was written.
  • Indexes on primary keys, foreign keys, and filter columns are what keep lookups fast as tables grow.
  • The table itself has no guaranteed row order; only indexes are sorted, and that distinction explains most performance behavior.
CREATE TABLE users (
  id     BIGINT PRIMARY KEY,
  name   TEXT NOT NULL,
  email  TEXT UNIQUE NOT NULL
);

CREATE TABLE orders (
  id       BIGINT PRIMARY KEY,
  user_id  BIGINT NOT NULL REFERENCES users(id),
  amount   NUMERIC NOT NULL,
  status   TEXT NOT NULL
);
Normalization removes duplication and puts each fact in one place; the cost is that reading a whole object may require a join.

03Why relational databases are the default choice

Relational databases are the starting point for most applications because they solve the problems that are expensive to fix later: correctness, integrity, and unplanned queries.

  • Transactions: creating an order, decrementing inventory, and recording payment commit together or not at all.
  • Flexible querying: joins, filters, grouping, and aggregates answer new questions without a new data model.
  • Data integrity: types, NOT NULL, UNIQUE, check constraints, and foreign keys keep invalid rows out.
  • Mature operations: backup, point-in-time recovery, replication, monitoring, and tuning are well understood.
  • Ecosystem: drivers, migration tools, ORMs, and experienced engineers are widely available.
  • The guarantee is local to one database: a transaction is atomic inside it, not across services.
  • Isolation levels trade concurrency against anomalies, so even ACID systems need thought about read phenomena.
BEGIN→Create order→Reduce inventory→Record payment→COMMIT (all saved)
If any statement fails before COMMIT, the transaction rolls back and none of the three changes are visible.

04Where relational databases struggle

  • A traditional deployment is designed around a single primary; read replicas scale reads but not writes.
  • Scaling writes beyond one machine usually means sharding, which brings routing, cross-shard joins, and resharding.
  • A fixed schema makes frequent shape changes expensive; large migrations need planning, backfills, and lock awareness.
  • Deeply connected data turns into repeated self-joins whose cost grows with each additional hop.
  • Full-text relevance, high-volume timestamped data, and very wide sparse records do not map cleanly onto normalized tables.
  • Wide rows with many nullable columns often signal that the data wants a document or key-value model instead.

05Key-value stores

A key-value store is a hash map at cluster scale: every value is stored under a unique key, and reads happen only by that key.

  • Keys are independent, so the store can hash each key to a node and scale horizontally without coordination.
  • Lookups avoid query planning entirely: hash or tree lookup, then return the value.
  • Values are opaque; the database cannot filter on fields inside a serialized blob.
  • Many stores support TTL, which makes them natural for sessions, carts, and caches.
  • Common uses: session state, rate-limit counters, feature flags, and hot-object caching.
  • Without the key the database usually cannot help, so access paths must be designed by the application.
  • A single very popular key lands on one node and can create a hot key that no amount of sharding fixes.
  • Key-value stores usually sit beside a primary database, not in place of the durable source of truth.

06Document databases

Document databases extend the key-value idea: the value is a structured document, usually JSON-like, with nested objects and arrays.

  • Related data is stored together, so a product page with variants and shipping details can load in one read instead of several joins.
  • Unlike a key-value store, the engine understands the document shape and can index and query nested fields.
  • The schema is flexible: two documents in one collection may have different fields.
  • Documents map closely to the objects the application already uses, reducing mapping code.
  • The weakness is relationships: heavily connected data forces either duplication or application-side joins.
  • Duplicated facts embedded in many documents must be updated everywhere, which invites drift.
  • A flexible schema still needs conventions and validation, or the collection becomes impossible to reason about.
  • Good fits: catalogs, content management, user profiles, and event payloads that are read as a whole object.

07Wide-column databases

Wide-column stores keep rows and columns but organize them by partition key, with rows inside a partition sorted by a clustering key.

  • All rows for one partition live on the same node set, so a partition read is local and predictable.
  • Within a partition, rows are already sorted by the clustering key, making ORDER BY time DESC LIMIT 50 a sequential read.
  • Log-structured storage turns writes into sequential appends, which is why these systems absorb very high write throughput.
  • Tables are designed query-first: you write down the exact queries, then model a table for each one.
  • A second access path usually means a second table with the same data keyed differently, not a new index.
  • Ad hoc filters and joins are not the optimization target; expecting them leads to full partition scans.
  • Operations matter: compaction, repair, partition sizing, and hot partitions all need active attention.
  • Good fits: messaging, activity feeds, IoT telemetry, and write-heavy workloads spread across many machines.
Partition key = conversation id→Clustering key = message timestamp→Messages co-located and time-sorted→Latest 50 read sequentially
To fetch messages by sender you would typically maintain a second table partitioned by sender, because the original partition layout cannot serve that query.

08Graph databases

Some data is mostly relationships. A graph database stores entities as nodes and relationships as edges with their own types and properties.

  • Alice FOLLOWS Bob and WORKS_AT Acme; both the nodes and the edges are stored explicitly.
  • Multi-hop questions follow pointers from node to node instead of joining a table to itself once per hop.
  • In a relational database, each extra hop adds another join and the cost compounds; a graph index makes each hop a local lookup.
  • Traversal languages such as Cypher express the question directly: friends of friends who work at the same company.
  • Relationships are first-class, so edge properties (since, weight, role) are natural to store.
  • Strong fits: social networks, recommendations, fraud rings, dependency chains, and knowledge graphs.
  • Weak fits: bulk scans and aggregations where relationships are incidental — a column store or relational engine is cheaper.
  • Relationships cross machine boundaries, so partitioning a graph well is genuinely hard and limits horizontal scale.
Node / EdgeMeaning
Alice, Bob, Carol, AcmeNodes: people and a company
Alice → Bob (FOLLOWS)Edge: a directed social relationship
Carol → Acme (WORKS_AT)Edge: employment
Alice → Acme (WORKS_AT)Edge: employment, enabling the shared-employer query

09Time-series databases

Time-series data is a sequence of measurements, each tagged with a timestamp. Its access pattern is unusually predictable, and the storage engine is built around that.

  • New points are almost always appended at the current time; old points are rarely updated.
  • Queries usually ask for a time window and a summary: average CPU over the last hour, p99 latency today.
  • Points are stored in time order, so consecutive values compress very well and range scans read contiguous blocks.
  • Retention policies drop or downsample old data automatically, which keeps the working set bounded.
  • Common pattern: keep raw points briefly, then keep hourly rollups for much longer.
  • Tags or labels identify the series; grouping by a label is how dashboards aggregate across hosts.
  • High-cardinality labels — such as a user id on every metric — blow up the index and degrade the whole database.
  • Good fits: monitoring, sensor data, application metrics, and financial tick data.
Servers report CPU every 10s→Raw points retained briefly→Downsample to hourly averages→Raw points expire
Downsampling is a design decision: you trade the ability to answer fine-grained historical questions for bounded storage and fast long-range queries.

10Search engines

A search engine answers the query a relational LIKE '%shoes%' cannot: rank documents by how well they match free text.

  • An inverted index maps each term to the list of documents containing it, so the engine jumps straight to candidates.
  • Matches for each term are combined and scored by relevance; a document matching all three query words outranks one matching a single word.
  • Text is analyzed before indexing: lowercasing, tokenization, and stemming make running match run.
  • Fuzzy matching tolerates typos, and prefix structures support autocomplete.
  • Faceted filters (category, price, brand) are applied alongside relevance scoring, not instead of it.
  • A LIKE '%term%' predicate cannot use a normal B-tree index and cannot produce a relevance score.
  • The search index is usually not the source of truth; the primary database stays authoritative and changes are copied over.
  • That copy is asynchronous, so search results can lag behind writes — an accepted staleness window, not a bug to hide.
Documents written to primary DB→Change stream or pipeline indexes them→Inverted index updated→Query scored and returned
Because the index lags, a just-created product may not be searchable yet. Design the UX for that window instead of pretending it does not exist.

11Vector databases

A model converts text, images, or audio into an embedding: a vector where items with similar meaning are close together.

  • cheap flights and budget airfare share almost no words but land near each other in vector space.
  • The core query is: given a vector, which stored vectors are most similar, usually by cosine or dot-product distance.
  • Comparing against every stored vector is too slow at millions of items, so engines build ANN indexes such as HNSW.
  • ANN trades exactness for speed: recall is high but not guaranteed, which is a product decision, not just a benchmark number.
  • Metadata filters (tenant, language, date) are applied with or around the vector search and can change recall behavior.
  • Embeddings are tied to the model that produced them; changing the model means re-embedding the corpus.
  • As with search, the vector store holds a derived representation, not the authoritative record.
  • Good fits: semantic search, recommendation candidates, deduplication, and retrieval-augmented generation.
Query text→Embedding model→Query vector→ANN index search→Nearest neighbors + metadata filter
Vector search finds semantically similar items. It does not replace exact filters, permissions checks, or transactional reads.

12How to choose a database

Work through the data and the queries before comparing products. Five questions eliminate most of the option space.

  • What do the queries look like? Single-key fetches, ad hoc joins, text ranking, or time windows each point somewhere different.
  • How important are transactions? If a partial update causes real damage, start with a system that gives atomic multi-row writes.
  • What is the read and write volume? Very write-heavy workloads need an engine designed to spread writes across machines.
  • How often does the shape change? Frequent evolution favors a flexible document model or JSON columns.
  • What can the team operate? A familiar database run well beats a theoretically perfect one nobody can tune at 3 a.m.
  • Prefer the simplest engine that satisfies the hardest requirement; every extra system adds backup and upgrade work.

13Polyglot persistence and a practical starting point

Large systems often use several databases, each for the workload it handles best. That is polyglot persistence, and it is a cost as much as a capability.

  • PostgreSQL holds users, orders, and payments because they need transactions and constraints.
  • Redis holds sessions and carts because they need very fast lookup by a known key.
  • The catalog is copied into a search engine so the search bar can rank results.
  • Request metrics go to a time-series store so dashboards do not slow the transactional database.
  • Each additional database must be deployed, monitored, backed up, upgraded, and secured.
  • Copied data needs a reliable synchronization path; without one, the systems silently disagree.
  • Start with one well-tuned relational database; JSON columns, full-text search, and vector extensions cover many early needs.
  • Add a specialized engine when a specific workload clearly outgrows the primary — not in anticipation of scale you do not have.
DataStoreReason
Users, orders, paymentsPostgreSQLTransactions, joins, integrity
Sessions, cartsRedisFast key lookup, TTL
Product searchElasticsearchRelevance ranking, facets
Request metricsTime-series DBRange queries, retention
Every copy of the data is a consistency problem. Keep the number of copies as small as the workload allows.

↔Trade-offs to say out loud

  • Relational gives transactions, integrity, and ad hoc joins but makes write scaling past one primary and frequent schema changes expensive.
  • Key-value gives the fastest and simplest key lookups but cannot answer questions about fields inside the value.
  • Document gives one-read object fetches and schema flexibility but pushes relationship handling and duplication into the application.
  • Wide-column gives very high write throughput and partition-local range reads but requires one table per query pattern.
  • Graph makes multi-hop traversal cheap but partitions poorly and suits fewer engineers and tools.
  • Time-series gives compression and fast window aggregates but punishes high-cardinality labels and non-time access patterns.
  • Search engines give relevance, stemming, and facets but are a derived copy that can lag and must be rebuilt.
  • Vector databases give semantic matching but return approximate results and couple the index to one embedding model.
  • Polyglot persistence gives each workload its best engine but multiplies operational cost and data-sync risk.

?Interview questions

Answer aloud before opening the outline.

1. Why does more than one type of database exist?

Because workloads have incompatible access patterns. Payments need atomic multi-row writes, sessions need single-key lookups, search needs relevance ranking, and metrics need time-window scans. An engine optimizes its storage and index layout for one shape of query, so it is usually mediocre at the others.

2. When is a relational database the right default?

When the data is structured, invariants matter, and you do not yet know every query. ACID transactions, constraints, foreign keys, and SQL joins cover a wide range of unplanned questions. Start there and specialize only when a measured workload outgrows it.

3. How does a relational database enforce correctness across multiple tables?

With transactions. All statements inside a transaction commit together or roll back together, and constraints such as UNIQUE and foreign keys are checked inside that boundary. This is why an order, an inventory decrement, and a payment record can be treated as one unit.

4. What is the main scaling limitation of a relational database?

Writes are bound to a single primary. Read replicas add read capacity, but write throughput beyond one machine usually requires sharding, which introduces routing, cross-shard joins, distributed transactions, and resharding.

5. When would you choose a key-value store?

When the application already knows the key and only needs to fetch or update the value: sessions, carts, counters, rate limits, feature flags. The trade-off is that you cannot query by fields inside the value, and a single hot key can overload one node.

6. Document database versus key-value store — what actually changes?

A document store understands the value's structure, so it can index and filter nested fields and return a whole object in one read. A key-value store treats the value as opaque and only helps when you have the key.

7. Why do wide-column databases require query-first modeling?

Rows are distributed by partition key and sorted by clustering key, so the physical layout only supports the access paths it was built for. A new query pattern such as 'messages by sender' usually needs a new table with a different partition key rather than an ad hoc index.

8. When does a graph database beat recursive SQL?

When relationship depth is variable and central to the query, such as friends-of-friends, fraud rings, or dependency chains. Each extra hop in SQL adds another join, while a graph follows pointers locally. If you mostly do bulk scans or one-hop lookups, a relational store is simpler.

9. What makes time-series data different from ordinary event data?

The write pattern is append-only at the current time, and reads are time-range aggregates. That allows time-ordered storage, strong compression of consecutive values, and retention policies that downsample old data. It also means non-time predicates and high-cardinality labels are the weak spots.

10. Why is a search engine not the source of truth?

It is a derived, denormalized index optimized for ranking rather than durable transactional storage. Changes are copied asynchronously, so results can lag, and the index can be rebuilt from the primary database if it is lost or its mapping changes.

11. What does an inverted index do that a B-tree cannot?

It maps each analyzed term to the documents containing it, so the engine can find candidates and score them by relevance. A B-tree compares whole column values and cannot rank free text, stem words, or support LIKE '%term%' efficiently.

12. How does a vector database find similar items?

An embedding model converts items and the query into vectors; items with similar meaning are close in that space. The database uses an approximate nearest neighbor index such as HNSW to avoid comparing against every vector, trading a small amount of recall for speed.

13. What is polyglot persistence, and when is it a mistake?

Using several database types, each for the workload it handles best. It becomes a mistake when adopted before a workload actually needs it: every extra engine adds deployment, monitoring, backup, upgrade, and synchronization work, plus a new way for copies of the data to disagree.

14. How would you choose a database in an interview?

State the access patterns, consistency requirements, write volume, schema churn, and team constraints, then map them to candidates. Pick the simplest engine that satisfies the hardest requirement, and note the migration path if that assumption changes.

!Traps

  • Choosing a database from its reputation instead of from the query patterns it must serve.
  • Assuming NoSQL automatically scales writes — some document and graph systems still have a single primary or a hard partitioning limit.
  • Storing connected data in documents and duplicating the same fact until updates drift.
  • Using a search engine or vector index as the authoritative store rather than a derived copy.
  • Putting high-cardinality labels such as user id on every time-series metric and destroying index performance.
  • Adopting polyglot persistence before a workload needs it, then paying for four systems nobody operates well.
  • Forgetting that every copy of data needs a synchronization path and a way to detect divergence.
