01The problem: concurrent writes on multiple replicas

  • With multiple replicas accepting writes, two users can update the same item before either sees the other's change.
  • A last-write-wins rule silently discards one update, which is unacceptable for counters, sets, and shared documents.
  • Serialising every write through a leader or quorum adds a round trip and makes the system unavailable without a majority.
  • Offline and multi-region clients need to write locally and reconcile later, not block on the network.
  • The requirement is a merge that is deterministic: every replica computes the same result from the same updates, in any order.
  • CRDTs satisfy that by constraining the data type itself rather than the network or the coordination protocol.

02What a CRDT is

  • A CRDT is a data structure with a merge function that always produces the same state regardless of order or duplication.
  • Each replica applies updates locally and immediately; no lock, quorum, or leader is consulted.
  • Replicas exchange updates asynchronously, and any two that have seen the same updates are identical.
  • The guarantee is strong eventual consistency: convergence is deterministic, not merely likely.
  • Conflicts are not resolved by a human or a timestamp alone; the data type encodes the resolution rule.
  • This gives availability during partitions and low-latency local writes, at the cost of richer metadata and constrained operations.
  • CRDTs solve data convergence, not business invariants; those still need coordination.

03State-based versus operation-based

  • State-based (CvRDT): a replica sends its state, or a delta, and the receiver merges with join.
  • State-based designs tolerate loss, duplication, and reordering because merging is idempotent and order-independent.
  • Their cost is state size: merging requires sending something at least as large as the difference.
  • Delta-state CRDTs send only the changed portion, keeping the tolerance while cutting bandwidth.
  • Operation-based (CmRDT): a replica broadcasts operations, which are usually much smaller.
  • Op-based designs require causal, exactly-once delivery, which a reliable broadcast layer must provide.
  • In practice: state-based is simpler to make correct, op-based is cheaper on the wire.

04The merge algebra

  • Merging must be commutative: merging A with B equals merging B with A.
  • It must be associative: grouping of merges does not change the result, so gossip paths do not matter.
  • It must be idempotent: merging the same state twice changes nothing, which makes duplicate delivery harmless.
  • Formally the states form a join-semilattice and merge is the least upper bound.
  • A monotonic growth rule — states only move up the lattice — guarantees that information is never lost by merging.
  • These properties are what let CRDTs ride on unreliable, unordered gossip instead of a reliable ordered log.
  • If a merge function lacks one property, replicas can diverge permanently and silently.
Idempotence is the property most often broken by hand-rolled merges — for example, a counter that adds instead of taking a maximum.

05Counters

  • A G-Counter keeps one count per replica and merges by taking the maximum per replica; the value is their sum.
  • Taking the maximum makes duplicate increments harmless, because each replica's contribution is remembered once.
  • A PN-Counter pairs two G-Counters, one for increments and one for decrements, and the value is their difference.
  • PN-Counters cannot enforce a floor: concurrent decrements can drive the result negative even when every individual operation was valid.
  • Counters track totals, not identities, so they cannot answer questions like did user 42 like this.
  • Per-replica components mean metadata grows with the number of replicas, not with the number of increments.
  • Removing a departed replica's component requires knowing its updates are causally stable.

06Sets

  • G-Set is grow-only: merge is union, so it can never remove an element.
  • 2P-Set uses an add set and a remove set; an element disappears when it is in both, and can never be re-added.
  • LWW-Element-Set timestamps adds and removes and keeps the latest, which needs a tie-break rule for equal timestamps.
  • OR-Set tags each add with a unique identifier, so a remove only deletes the adds it observed.
  • In an OR-Set, a concurrent add and remove resolves in favour of add, matching most user expectations.
  • Set variants differ in how badly they handle the re-add case, which is common in real workloads.
  • Choose based on semantics, not convenience: remove wins versus add wins is a product decision.

07Registers and maps

  • A LWW-Register holds one value with a timestamp and keeps the newest, which is simple but silently loses the loser.
  • Clock skew makes LWW unsafe where the ordering must reflect causality; a hybrid logical clock reduces but does not remove the risk.
  • An MV-Register keeps all concurrent values and surfaces them to the application, which resolves the conflict explicitly.
  • This is the honest option when silent loss is unacceptable: show both, let the user or a rule choose.
  • A map is a CRDT of CRDTs: the keys are themselves a replicated structure and each value carries its own merge rule.
  • Nested types are what make CRDTs usable for documents — a task board with per-field types, for example.
  • Mixing types is legal but beware: a nested LWW inside an OR-Map inherits LWW's silent-loss behaviour.

08Sequences and text

  • Collaborative text is a sequence CRDT: characters have stable identifiers and are ordered by those identifiers, not by array index.
  • Insertions carry a reference to the identifier they follow, so a concurrent insert stays in the intended place.
  • RGA orders concurrent inserts by identifier to break ties deterministically.
  • Logoot and LSEQ allocate position identifiers between neighbours, which avoids renumbering entirely.
  • YATA, used by Yjs, adds origin-left and origin-right references to keep interleaving natural.
  • Sequence CRDTs preserve intention: an insert meant for a spot stays near that spot after remote edits.
  • The cost is per-character metadata, which is why implementations compress and run-length encode aggressively.

09Causality and metadata

  • CRDTs need to know which updates a replica has already seen, or a merge cannot tell old from new.
  • Lamport timestamps give a total order consistent with causality, sufficient for LWW types.
  • Version vectors capture partial order and detect concurrency, but grow with replica count.
  • Dotted version vectors keep the size manageable while preserving precise causality.
  • Op-based CRDTs rely on a causal broadcast layer; without it, an operation can be applied before its prerequisite.
  • Metadata is the real cost of CRDTs and the main thing to design deliberately.
  • Pruning old entries is only safe once causal stability is reached and no future update can reference them.

10Deletes, tombstones, and garbage collection

  • A delete must be remembered as a tombstone, otherwise a delayed add would resurrect the element.
  • Tombstones accumulate forever unless the system can prove no older update will arrive.
  • Causal stability is that proof: once all replicas have seen an update, its metadata can be discarded.
  • Practical systems use coordinator acknowledgements, session tracking, or periodic snapshots to establish stability.
  • Snapshotting a document and discarding history is a common compromise, at the cost of losing late-merge ability.
  • Unbounded tombstones are the most common cause of CRDT memory and sync problems in production.
  • Design the GC strategy before shipping; retrofitting it often requires changing the wire format.

11Choosing between CRDT, OT, and consensus

  • CRDTs need no coordination and survive partitions, so they excel for offline editing, counters, presence, and carts.
  • Operational transformation needs a central server to order and transform operations, giving tighter control of intention at the cost of a coordinator.
  • Consensus gives a single agreed order and supports invariants, but blocks without a majority.
  • LWW is simplest but silently drops concurrent writes, so use it only where loss is acceptable.
  • CRDTs cannot enforce global rules such as uniqueness or non-negative balances without extra coordination.
  • Hybrid designs are common: CRDT state for local editing, a quorum-based check for the invariant that matters.
  • Decision rule: does the data need convergence only, or a global truth? Convergence → CRDT, truth → coordination.

12Where CRDTs are used in practice

  • Collaborative editors use sequence CRDTs such as Yjs and Automerge to merge offline edits.
  • Distributed databases expose counters, sets, maps, and registers as replicated types in multi-region modes.
  • Shopping carts and to-do lists often use add-wins sets so concurrent edits never lose items.
  • Presence and analytics counters use grow-only or PN counters for cheap, partition-tolerant aggregation.
  • CRDTs also appear in local-first apps where the device holds the primary copy and sync is opportunistic.
  • Some systems use CRDTs internally for cluster state, combining them with gossip for dissemination.
  • The pattern is consistent: user-visible state that can tolerate merge, not money or inventory.

13Limits and a practical checklist

  • No global invariants: uniqueness, referential integrity, and balance floors need coordination.
  • Metadata can outgrow the payload, especially for text and sets with many deletes.
  • Semantic conflicts remain: two people can concurrently rename and delete the same document, and the merge is legal but wrong for the user.
  • Authorization is tricky because any replica can produce a valid update; verify at the boundary.
  • Schema evolution must be compatible across replicas that may be offline for a long time.
  • Pick the weakest type that matches the semantics, define the tie-break rule up front, and plan tombstone GC early.
  • Test convergence explicitly: apply the same operation set in many orders and assert identical final states.

↔Trade-offs to say out loud

  • Coordination-free writes give availability and low latency but make global invariants impossible to enforce.
  • State-based merging is robust to any delivery pattern but costs bandwidth proportional to state size.
  • Op-based merging is compact but depends on causal, exactly-once broadcast.
  • Rich metadata preserves intent and enables merges at the cost of storage that grows with history.
  • OR-Set semantics prevent lost additions but keep a tag per add, which is expensive for large sets.
  • LWW types are small and simple but silently discard concurrent writes.
  • Tombstone retention preserves correctness but consumes memory until causal stability is provable.
  • Offline-first design improves user experience but pushes conflict handling onto the data model.

?Interview questions

Answer aloud before opening the outline.

1. What is a CRDT?

A replicated data type whose merge function always converges, so replicas can accept writes locally and reconcile later. The guarantee is strong eventual consistency: same updates in, same state out, regardless of order.

2. Why do CRDT merges need commutativity, associativity, and idempotence?

Updates arrive in arbitrary order and may be duplicated. Commutativity makes order irrelevant, associativity makes grouping irrelevant, and idempotence makes duplicates harmless. Together they guarantee convergence over an unreliable network.

3. State-based or operation-based: how do you choose?

State-based is easier to make correct because it survives any delivery pattern, but messages are larger. Operation-based is compact but requires causal, exactly-once delivery. Delta-state CRDTs are the usual compromise.

4. How does a G-Counter work?

Each replica keeps its own counter and increments only its own slot. Merge takes the maximum per slot, and the value is the sum of all slots. Duplicate delivery is harmless because max is idempotent.

5. Why can a PN-Counter go negative?

It is two G-Counters whose difference is the value. Concurrent decrements on different replicas are each locally valid but sum to more than the increments, so the merged value can drop below zero. Enforcing a floor needs coordination.

6. What does an OR-Set solve?

It stops a remove from deleting an addition it never saw. Each add carries a unique tag, and a remove deletes only the tags it observed, so a concurrent add survives — the usual add-wins behaviour users expect.

7. What is a tombstone and why is it a problem?

A marker that records a deletion so a delayed add cannot resurrect the element. Tombstones accumulate indefinitely because the system cannot know when all replicas have seen them, which drives memory growth and slow syncs.

8. How do you garbage-collect CRDT metadata?

Wait for causal stability: once every replica has acknowledged an update, nothing can still reference its metadata. Systems establish this with session tracking, coordinator acknowledgements, or periodic snapshots, then prune tombstones and version entries.

9. CRDTs versus operational transformation?

OT routes operations through a central server that transforms them against concurrent edits, which keeps intention tight but requires a coordinator. CRDTs are peer-to-peer and partition-tolerant but carry more metadata and resolve conflicts by data-type rules.

10. What can a CRDT not do?

It cannot enforce a global invariant such as uniqueness, a non-negative balance, or inventory limits, because no replica has a current global view. Those need quorum coordination or a single authority.

11. Why is text hard for CRDTs?

Positions shift on every edit, so characters need stable identifiers and ordering rules to keep concurrent insertions in the intended place. Per-character metadata is large, and naive designs cause interleaving that looks wrong to users.

12. How would you test a CRDT implementation?

Generate random operation sets and apply them to replicas in many orders with duplication, then assert all replicas converge to the same state. Also test specific conflict cases such as concurrent add and remove, and measure metadata growth over time.

!Traps

  • Using a last-write-wins register where losing a write is unacceptable.
  • Assuming convergence also preserves business invariants like uniqueness or non-negative balances.
  • Forgetting idempotence, so duplicate delivery double-counts.
  • Shipping a CRDT with no tombstone GC plan and watching metadata grow without bound.
  • Relying on wall-clock timestamps for ordering when clocks can drift.
  • Choosing add-wins or remove-wins semantics without deciding what users expect.
  • Testing only happy-path merges and never reordering or duplicating operations.
