In one lineA skip list is a sorted linked list with probabilistic express lanes above it, giving expected logarithmic search, insertion, and deletion without the rotations that make balanced trees hard to implement and hard to update concurrently.
Skip list
A layered sorted linked list where each higher level skips over more nodes, so a search descends instead of walking every element.
Level (lane)
One of the stacked linked lists; level zero contains every element, higher levels contain progressively sparser samples.
Tower
The stack of forward pointers belonging to one element, whose height is chosen randomly at insertion.
Promotion probability (p)
The chance that a new node also appears at the next level up; it controls the balance between search speed and pointer overhead.
Header node
A sentinel that owns the forward pointers for the start of every level, so no level needs a special case.
Span
The number of bottom-level nodes a forward pointer skips, which lets the list compute ranks without walking.
Expected O(log n)
The average cost over the random level choices; the worst case is linear but vanishingly unlikely.
Lock-free insertion
Inserting with atomic compare-and-swap on forward pointers, which avoids the global restructuring of a balanced tree.

01The problem: sorted data under constant change

An online game needs a leaderboard over millions of players whose scores change every second.

  • The leaderboard must support updating a player's score.
  • It must return the top players quickly.
  • It must find a specific player's current rank.
  • It must list players whose scores fall inside a range.
  • All of these need the data kept in sorted order at all times.
  • With constant updates, the structure must insert and delete fast and search and scan fast — a combination the simple options do not provide.

02Sorted array

  • Searching is excellent: binary search finds a key in logarithmic time with predictable memory access.
  • Insertion and deletion are expensive: everything after the position must shift to close or open a gap.
  • A single insertion near the front can move a very large number of elements.
  • The cost is inherent to contiguous storage, not to the algorithm.
  • Bulk rebuilds are fine; steady churn is not.
  • A sorted array works when the data is mostly static or rebuilt in batches.

03Sorted linked list

  • Insertion is cheap once the position is known: a few pointer updates, no shifting.
  • Search is the problem: a linked list cannot jump to the middle, so it must walk node by node.
  • Finding the insertion position therefore costs a full scan, which cancels the cheap insert.
  • Range scans are natural once you are at the start of the range.
  • Memory is fragmented across nodes, so pointer chasing replaces cache-friendly scans.
  • Neither array nor linked list delivers fast search and fast update at the same time.

04Why not a balanced tree

  • Balanced search trees such as red-black and AVL trees do provide logarithmic search, insert, and delete.
  • They maintain balance with rotations after updates, and the rotation cases are easy to get wrong.
  • An insertion can require updating nodes all the way to the root.
  • Under concurrency, threads modifying nodes near the root must coordinate, which limits parallelism.
  • A single structural change can invalidate work other threads are doing.
  • Skip lists achieve similar expected performance with a simpler, more local update pattern.
  • That simplicity is why some systems pick them even when a tree would be asymptotically equivalent.

05The express lane idea

  • Imagine a highway with local lanes and express lanes: the express lanes stop at fewer exits.
  • A skip list stacks sorted linked lists, where each higher level contains a random subset of the nodes below.
  • A search starts at the top level, travels as far as it can, then drops down a level and continues.
  • Each level removes roughly the same fraction of nodes, so the number of levels needed grows logarithmically with the element count.
  • The top levels skip large stretches; the bottom level contains everything.
  • No rotation or global restructuring is required: balance comes from randomness, not invariant maintenance.
  • The structure is a probabilistic alternative to a balanced tree, not an approximation of one.

06Structure

  • Level 0 is an ordinary sorted linked list containing every element.
  • Level i+1 contains a random subset of the nodes at level i, each promoted with probability p.
  • Each node owns a tower of forward pointers, one per level it participates in.
  • A header node holds the entry pointer for every level, so descent never needs a special case.
  • The number of levels is bounded by a small maximum derived from the expected element count.
  • Total pointer overhead stays linear in the element count, since few nodes reach the high levels.
  • Ordering is by key, so duplicates need a tie-break such as insertion sequence or a composite key.

07Search

  • Start at the highest level of the header node.
  • While the next node's key is less than the target, move forward at the current level.
  • When the next key is greater (or the level ends), drop down one level and continue.
  • Repeat until level 0, where the next node is either the target or the insertion point.
  • Each level costs a few comparisons, and the number of levels is logarithmic in expectation.
  • The path is a staircase from the sparse top to the dense bottom.
  • Searching for a range is the same descent, followed by a linear walk along level 0.
Start at top level→Advance while next key is smaller→Drop one level→Repeat until level 0→Compare next node with target

08Insertion with random levels

  • Search first to find the position at every level, keeping the predecessor at each level.
  • Choose the new node's height randomly: keep promoting while a random draw succeeds, up to the maximum level.
  • Link the node into each level up to its height by updating the predecessors' forward pointers.
  • No rotations, no rebalancing, no ancestor updates beyond the predecessors just recorded.
  • The geometric distribution of heights is what keeps the structure balanced on average.
  • A common p is one half or one quarter; a smaller p means fewer levels and more forward steps per level.
  • Because the height is random, two runs over the same data can produce different shapes with the same expected cost.

09Deletion

  • Search for the node while recording its predecessor at each level.
  • Unlink it from every level where it appears by pointing each predecessor at the node's next pointer.
  • Deletion is local: only the tower's own levels are touched.
  • No rebalancing follows, because removing a node cannot violate any balance invariant.
  • Freeing the node is a memory-management concern, especially under concurrency.
  • Repeated insert and delete churn leaves the height distribution slightly different from a fresh build, which is acceptable in expectation.
  • If exact reproducibility matters, rebuild rather than relying on the evolved shape.

10Ranks and range scans

  • Store a span on each forward pointer: how many level-0 nodes it jumps over.
  • To compute a rank, accumulate spans while descending and advancing.
  • A rank lookup is then a search with an extra accumulator, not a separate traversal.
  • Range queries start with a descent to the lower bound, then walk level 0 while keys stay in range.
  • The walk touches only matching nodes plus one stop, which is optimal for a linked structure.
  • Leaderboard queries such as "top 100" and "players between two scores" map directly onto these operations.
  • Without spans, rank requires walking from the head and the structure loses an important capability.

11Concurrency

  • An insertion only changes the forward pointers of the nodes it links, so updates are naturally local.
  • Forward pointers can be installed with atomic compare-and-swap, which enables lock-free insertion.
  • Deletion is harder: a node removed while another thread is reading it needs a mark-and-reclaim scheme.
  • Balanced trees need coordination across rotations near the root, which serializes writers.
  • This locality is a major reason Java ships ConcurrentSkipListMap and concurrent indexes favor skip lists.
  • Correct lock-free memory reclamation is still subtle; most production code uses a tested library.
  • In single-threaded engines such as Redis, the win is implementation simplicity rather than concurrency.

12Where it is used, and its limits

  • Redis sorted sets are skip lists with spans, which is how ZRANGE, ZRANK, and score ranges work.
  • LSM memtables in LevelDB and RocksDB use skip lists because they take concurrent inserts and support ordered iteration for flush.
  • Java's concurrent collections use them for ordered maps and sets.
  • Some in-memory databases and search structures use them where ordered iteration plus concurrent writes matter.
  • Limits: pointer overhead, poor cache locality, randomized worst case, and no native disk layout.
  • Choose a skip list when ordered iteration and concurrent updates matter more than raw cache efficiency.
  • Choose a B-tree or sorted array when the data is disk-resident and page locality dominates.

↔Trade-offs to say out loud

  • Random levels remove rotation logic but make the worst case linear instead of guaranteed logarithmic.
  • More levels shorten searches but add pointers and memory per node.
  • Smaller promotion probability reduces pointer overhead but increases forward steps within a level.
  • Local pointer updates make concurrency easier but leave the structure sensitive to memory reclamation bugs.
  • Spans enable rank queries but must be maintained on every insert and delete.
  • Ordered iteration is natural and cheap, unlike a hash table, but cache locality is worse than an array or B-tree.
  • In-memory design suits memtables and leaderboards but not page-oriented disk storage.
  • Simpler code reduces maintenance risk but gives up the deterministic balance guarantees a tree provides.

?Interview questions

Answer aloud before opening the outline.

1. What is a skip list?

A sorted linked list with several layers of express pointers. Level zero holds every element, and each higher level holds a random sample of the level below. A search moves forward at high levels and drops down when it overshoots, which yields expected logarithmic cost.

2. Why does a sorted array fail for a leaderboard?

Binary search is fast, but every score update shifts the elements after the insertion point. With millions of players and constant updates, that shifting dominates. A skip list inserts by relinking a few pointers instead of moving data.

3. Why does a sorted linked list fail?

Insertion is cheap only after you know the position, and finding the position requires walking from the head node by node. Search is linear, so the cheap insert never pays off. The express lanes exist to make that search logarithmic.

4. How is a skip list balanced without rotations?

Balance comes from random promotion: each node is promoted to the next level with probability p, producing a geometric height distribution. That keeps the expected number of nodes per level shrinking geometrically, which bounds the expected search path. No invariant needs repair after an update.

5. What is the expected complexity and what is the worst case?

Search, insert, and delete are expected O(log n), and space is expected O(n). The worst case is O(n) if the random heights happen to degenerate, but that probability falls off extremely fast, so it does not drive design decisions.

6. How does a search actually descend?

It starts at the highest level of the header and advances while the next key is smaller than the target. When the next key is larger, it drops one level and repeats. At level zero the next node is the target or the insertion point.

7. What is p and how does it affect the structure?

It is the probability that a node is promoted to the next level. A larger p means more nodes per level and fewer levels; a smaller p means sparser levels and more pointer steps per level. Both keep expected search logarithmic; the choice trades memory against comparisons.

8. How do you get a player's rank?

Store a span on each forward pointer counting how many bottom-level nodes it skips. During the search, accumulate spans while advancing and descending, which yields the rank in the same pass. Without spans, rank would require a linear walk from the head.

9. How do range queries work?

Descend to the lower bound using the normal search, then walk level zero while keys remain within the range. The traversal touches only matching nodes and one terminating node, so it is proportional to the output size.

10. Why are skip lists considered concurrency-friendly?

An insert changes only the forward pointers of the nodes it links, so it can be done with atomic compare-and-swap instead of locks. Balanced trees may rotate nodes near the root and touch a shared path. Deletion still needs careful reclamation, so production code relies on proven implementations.

11. Where are skip lists actually used?

Redis sorted sets use a skip list with spans to support ranking and score ranges. LSM memtables in LevelDB and RocksDB use one for concurrent ordered inserts and iteration during flush. Java's concurrent ordered collections use them as well.

12. Skip list or balanced tree?

Use a skip list when ordered iteration, concurrent updates, and simple code matter, and expected rather than worst-case bounds are acceptable. Use a balanced tree or B-tree when you need deterministic bounds or disk-friendly page layout.

!Traps

  • Confusing expected O(log n) with a guaranteed worst case.
  • Forgetting spans and then discovering rank queries require a full scan.
  • Choosing p without considering the memory cost of tall towers versus the comparison cost of sparse levels.
  • Assuming lock-free insertion solves deletion and memory reclamation too.
  • Using a skip list for disk-resident data where page locality matters more than pointer simplicity.
  • Letting duplicate keys in without a tie-break rule, which breaks deterministic ordering and rank.
