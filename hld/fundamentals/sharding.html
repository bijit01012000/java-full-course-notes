01The single-database limit

A single relational database is the simplest correct design. Growth eventually makes it the constraint.

  • Vertical scaling — more CPU, memory, faster storage, a bigger machine — is the first response, and it works for a long time.
  • Read replicas absorb read traffic, but they do not reduce the primary's write load or total dataset size.
  • The dataset can outgrow what one machine can store, back up, or index efficiently.
  • Write traffic can exceed what one primary can absorb, even when reads are already offloaded.
  • Each successive machine upgrade costs more than the last, so vertical scaling has an economic ceiling as well as a hardware one.
  • When storage and write capacity both run out, the remaining move is to divide the data across multiple servers.
Sharding addresses dataset size and write throughput. If the problem is read latency, caching and replicas are cheaper answers.

02What database sharding is

Sharding splits a large dataset across multiple independent database instances. Each instance is a shard and holds only a portion of the data.

  • With 100 million users spread over four shards, each shard holds roughly 25 million users and serves roughly a quarter of the queries.
  • Together the shards hold the complete dataset; no single database stores or processes all of it.
  • It is horizontal scaling for the data tier: add more database servers rather than a bigger one.
  • Each shard is typically a full database in its own right, with its own storage, indexes, connections, and backups.
  • The application or a routing layer must know how data is distributed; the shards themselves do not coordinate placement.
  • Sharding is a partition of data, not of traffic: the same row always lives on one shard unless it is migrated.
One primary at capacity→Choose a shard key→Split rows into shards→Route queries by key→Scale by adding shards

03Sharding vs replication

The two are often confused because both put data on multiple servers, but they divide different things.

  • Replication copies the same data onto multiple servers; sharding divides different data across servers.
  • Replication's main benefit is availability and read scaling; sharding's main benefit is storage and write scaling.
  • With replication, every server holds all 100 million users; with sharding, every server holds a slice.
  • Large systems usually combine them: data is split into shards, and each shard has its own primary and replicas.
  • A shard's replicas copy that shard only, never the other shards' data.
  • Replication keeps one logical dataset identical everywhere; sharding makes each node authoritative for a subset.

04The shard key

The shard key is the most important decision in a sharded design. It decides where every row lives and which queries stay cheap.

  • The shard key is the field whose value is fed into the placement rule — for example, shard the users table by user_id.
  • On insert, the system reads the key and computes or looks up the target shard; on read, the same key routes the query.
  • A good key spreads data and traffic evenly, so no shard stores far more rows or serves far more requests.
  • A good key appears in common queries, so the hottest access paths resolve to a single shard.
  • A poor key concentrates traffic on one shard, or forces most queries to visit every shard.
  • Key choice follows access patterns, not just the shape of the data model.
  • Changing the shard key later is effectively a full data migration, so treat it as a long-lived commitment.
Test candidate keys against real queries: what fraction of requests include the key, and how evenly does the key's value distribution split?

05Range-based sharding

Range sharding divides the key space into contiguous ranges and assigns each range to a shard.

  • Users 1–1,000,000 go to Shard 1, 1,000,001–2,000,000 to Shard 2, and so on.
  • It is simple to implement and reason about: a range lookup identifies the shard.
  • Range queries are efficient because related values sit together; a query for users 1,200,000–1,300,000 visits only Shard 2.
  • Locality helps scans and ordered access, which makes this a natural fit for time-series or sequential ID data.
  • The weakness is uneven load: if IDs increase over time, every new signup lands on the shard holding the newest range.
  • New users are often the most active, so the newest shard can become a hot shard while older shards idle.
  • Preserving locality therefore buys range efficiency at the risk of skewed writes.

06Hash-based sharding

Hash sharding applies a hash function to the shard key and maps the result onto a shard.

  • Conceptually the rule is shard = hash(user_id) % number_of_shards, so the key itself is never interpreted as a range.
  • Hashing spreads keys more evenly than ranges because consecutive IDs produce unrelated hash values.
  • New signups no longer pile onto one shard, which distributes both storage and write traffic.
  • The cost is lost locality: users with nearby IDs can land on completely different shards.
  • A range query must now visit every shard, because matching rows are scattered across all of them.
  • Plain modulo is fragile when the shard count changes: from 4 to 5 shards, most keys map to a different shard and roughly 80% of data moves.
  • Consistent hashing is often used instead so that adding a shard moves only the share of data the new shard should own.

07Directory-based sharding

Range and hash sharding compute the shard from the key. Directory sharding looks the shard up in a table instead.

  • A lookup service records which shard holds each customer, tenant, or user — for example Customer A → Shard 3, Customer B → Shard 7.
  • This gives the most flexibility: a large tenant can be moved to its own shard by changing one directory entry.
  • The shard key does not change when data moves, and no other tenant is affected.
  • The directory becomes critical infrastructure: every routed request depends on it.
  • If the directory is slow, every request is slow; if it is wrong or unavailable, routing breaks.
  • It therefore needs to be fast, highly available, and cached carefully, with a plan for what happens when it cannot be reached.
  • Directory sharding trades simplicity for flexibility and an extra always-on dependency.

08Query routing

Once data is split, something must decide where each query goes. That is the routing layer.

  • Routing can live in application code, a data-access library, a proxy, or the database system itself.
  • For a query containing the shard key, the router computes the shard and sends the request to exactly one database — the ideal case.
  • For a query without the shard key, the router has no way to prune; it must broadcast to all shards.
  • A broadcast read is a scatter-gather query: send to every shard, wait for all responses, merge the results.
  • Scatter-gather cost grows with shard count: 4 shards means 4 times the work, 100 shards means 100 times the work.
  • Its latency is set by the slowest shard, so one slow shard degrades the whole query.
  • Shard key design should therefore be driven by the application's access patterns, not only by entity relationships.

09Cross-shard queries

Scatter-gather is the simplest case of a broader problem: any query needing data from multiple shards becomes an application-level distributed query.

  • A global count of active users requires every shard to return a partial count, which the application then sums.
  • Global sorting is harder: for the 100 most recent orders, each shard returns its own top 100, and the application merges and re-sorts them.
  • Pagination is harder still: the system cannot ask each shard for global rows 101–200, because it does not know how many global rows each shard holds.
  • The usual workaround is to fetch the top 200 from every shard and discard most of the result, which wastes work as depth increases.
  • Aggregations such as averages need care: averaging per-shard averages is wrong unless the shards also return their counts.
  • Cross-shard reads add network round trips, merge logic, and tail latency, and they scale with the number of shards.
  • Keeping a separate read model or summary table is often cheaper than repeatedly scattering across shards.
Send query to all shards→Each shard computes a partial result→Collect responses→Merge, sort, or aggregate→Apply global limit or page window

10Cross-shard transactions

A transaction that spans two shards becomes a distributed transaction, because neither database can guarantee the other's commit.

  • If both accounts live on one shard, the local database transaction gives atomicity for free.
  • If account A is on Shard 2 and account B on Shard 6, a transfer spans two independent databases with no shared commit.
  • One option is a distributed commit protocol such as two-phase commit, where a coordinator asks every participant to prepare and then commit.
  • Another is an application-level Saga, where each step has a compensating action that undoes it if a later step fails.
  • Both add coordination latency, new failure states, and the need to handle partial success, retries, and idempotency.
  • The best fix is design-level: keep data that is updated together on the same shard, which is called data locality.
  • For example, shard both orders and order_items by user_id, storing user_id on items too, so creating an order and its items is a single-shard transaction.
Denormalizing the shard key onto child tables is a common price for single-shard transactions.

11Hot shards

Even distribution of rows does not guarantee even distribution of work. A hot shard is one that receives far more traffic than its peers.

  • In a social system sharded by user_id, a few celebrity accounts may receive millions of requests while most users receive very little.
  • If a celebrity lands on one shard, that shard saturates while the others have spare capacity; the whole system is limited by the hottest shard.
  • A poor key creates the same effect: sharding by region puts most traffic on one shard when most users come from one country.
  • Low-cardinality keys such as status or plan_type concentrate values into few shards and cannot balance load.
  • Skew can be in read traffic, write traffic, or storage; each needs a different mitigation.
  • Mitigations include choosing a higher-cardinality key, splitting a hot key across sub-shards, isolating large tenants, or caching the hot record.
  • Monitoring must track per-shard load, not just the cluster average, or a hot shard hides inside healthy-looking numbers.

12Resharding

Growing from four shards to eight does not spread load by itself. Existing data must move, and that process is resharding.

  • Adding empty databases changes nothing until some rows are migrated onto them.
  • Resharding usually runs while the system serves live traffic, so a row may temporarily exist in both its old and new location.
  • The system must route reads and writes correctly during the move, avoid losing writes that arrive mid-copy, and avoid inconsistent results.
  • Some databases rebalance automatically; in others the application team owns the migration.
  • The mapping strategy determines how much data moves: with plain modulo hashing, 4 → 5 shards remaps most keys even though the new shard needs only about 20% of the data.
  • Consistent hashing limits movement to roughly the share the new shard should own.
  • Plan for a reversible, observable migration: copy, dual-write or change-data-capture, verify, switch reads, then remove old copies.
Add new shard→Copy affected ranges→Dual-write or stream changes→Verify counts and checksums→Switch routing→Remove old copies

13Failure isolation and operational complexity

Sharding changes both the blast radius of failure and the day-to-day cost of running the system.

  • Failure isolation improves: if one of ten shards fails, only the users on that shard are affected while the other nine keep serving.
  • That isolation is not automatic availability: a shard on a single machine is unavailable until that machine recovers.
  • Production shards therefore combine sharding with replication, promoting a replica when a shard's primary fails.
  • Schema migrations must run across every shard; a half-finished migration leaves mixed schema versions.
  • Monitoring, backups, and point-in-time restores must be per shard, and a consistent restore across all shards is harder than restoring one database.
  • Rebalancing becomes an ongoing operational task rather than a one-time setup step.
  • Debugging is harder because two users making the same request may hit different databases with different schema or configuration versions.

14When should you shard?

Sharding is a late-stage technique. Exhaust the cheaper options first, then confirm the application has a natural shard key.

  • Optimize slow queries and add the right indexes; these are far cheaper than distributing data.
  • Introduce caching and scale the database vertically before partitioning.
  • Move read traffic to replicas and archive old data out of the hot tables.
  • Partition large tables inside one database, which gives some locality and maintenance benefits without cross-node routing.
  • Shard when one database can no longer handle the dataset or write workload efficiently and the application must scale horizontally.
  • Confirm a natural shard key exists: if most operations route to a single shard, sharding works well.
  • Multi-tenant SaaS is a good fit because almost every request belongs to one customer; a system that joins across everything is a poor fit.
Optimize queries and indexes→Cache→Scale vertically→Add read replicas→Archive old data→Partition tables→Shard

↔Trade-offs to say out loud

  • Sharding raises storage and write capacity, but turns every query without the shard key into a scatter-gather operation.
  • Range sharding keeps related keys together and makes range scans cheap, but sequential keys concentrate new writes on one shard.
  • Hash sharding spreads data and traffic evenly, but destroys key locality and makes range queries visit every shard.
  • Directory sharding allows per-tenant placement and easy moves, but adds a lookup service that must be fast and always available.
  • Data locality keeps common transactions single-shard, but often requires denormalizing the shard key onto child tables.
  • Cross-shard transactions preserve global atomicity, but add coordination latency, failure states, and retry complexity.
  • Failure isolation limits the blast radius of one shard, but only if each shard also has its own replication and failover.
  • More shards increase aggregate capacity, but multiply migrations, backups, monitoring surfaces, and scatter-gather cost.

?Interview questions

Answer aloud before opening the outline.

1. What is sharding, and how is it different from partitioning?

Sharding splits a dataset across multiple independent database instances, each holding a portion and each capable of running on its own server. Partitioning is the broader idea of dividing a table; a partition can live inside one database. Sharding specifically implies distribution across nodes, so it brings routing, cross-shard queries, and distributed operations.

2. Sharding vs replication — what problem does each solve?

Replication copies the same data for availability and read scaling; sharding divides different data for storage and write scaling. Replication leaves one primary accepting all writes. Large systems use both: each shard has a primary and replicas, so writes spread across shards and each shard survives a node failure.

3. How do you choose a shard key?

Pick a high-cardinality field that spreads data and traffic evenly and appears in the most common queries, so those queries route to a single shard. Check the real access pattern: what fraction of requests include the key, and how skewed is its value distribution. Avoid low-cardinality fields like status and monotonically increasing fields that concentrate new writes.

4. Compare range, hash, and directory sharding.

Range sharding assigns contiguous key ranges: great for range queries, but sequential keys create hot shards. Hash sharding computes a hash and maps it to a shard: even distribution, but range queries hit every shard and modulo remaps most data when the shard count changes. Directory sharding looks up placement in a table: maximum flexibility, but the directory must be fast and highly available.

5. What happens to a query that does not include the shard key?

The router cannot prune shards, so it broadcasts the query to all of them and merges the results — a scatter-gather query. Work and tail latency grow with shard count, since the response waits for the slowest shard. Common non-key queries are better served by a secondary index, a read model, or a redesign of the shard key.

6. Why is global pagination hard in a sharded system?

Each shard only knows its own rows, so it cannot identify which of its rows correspond to global positions 101–200. A typical approach fetches the top N from every shard, merges and sorts them, then discards the earlier pages. Deep pagination therefore multiplies work across shards and gets worse as the page depth increases.

7. How do you handle a transaction that spans two shards?

Use a distributed commit protocol such as two-phase commit, or an application-level Saga with compensating actions for each step. Both add latency and new partial-failure states, so the better answer is usually to avoid the situation: shard related tables by the same key so the operation stays on one shard. For example, store user_id on order_items so orders and items are co-located.

8. What is a hot shard and how do you fix it?

A hot shard receives disproportionate traffic even when row counts are even — a celebrity account, a dominant region, or a low-cardinality key. Fixes include choosing a higher-cardinality key, isolating large tenants on dedicated shards, splitting a single hot key into sub-shards, or caching the hot value so reads never reach the database. Detect it with per-shard metrics, not cluster averages.

9. Why is resharding risky?

Data must move while live traffic continues, so a row can exist in two places and writes arriving mid-copy can be lost or applied out of order. The system must route correctly throughout, verify the copy, and switch reads safely. Plain modulo hashing makes it worse by remapping most keys; consistent hashing limits movement to roughly the new shard's share.

10. Does sharding improve availability?

It improves failure isolation: one failed shard affects only its keys, while the others keep serving. But it does not by itself make a shard available — a shard on one machine is still a single point of failure for its data. Each shard needs its own replicas and failover to turn isolation into availability.

11. What operational costs does sharding add?

Schema migrations must run on every shard and can end half-applied; monitoring, backups, and restores become per-shard; rebalancing becomes routine work; and debugging spans multiple databases that may drift in schema or configuration. These costs are why sharding should come after caching, replicas, archiving, and in-database partitioning.

12. When would you decide not to shard?

When queries routinely join across many entities, when no natural shard key exists, or when simpler options still have headroom. If most requests would need data from several shards, the design adds latency and complexity without relieving the real bottleneck. A multi-tenant SaaS app with per-customer routing is a good fit; an analytics system joining everything is not.

13. How would you migrate a single database to shards?

Start by identifying the shard key and validating its distribution against real queries. Add a routing layer that can direct reads and writes per key, backfill data into shards, dual-write or stream changes, verify counts and checksums, then move read traffic and finally writes. Keep the old database available for rollback until the new topology is proven.

!Traps

  • Sharding before trying indexes, caching, vertical scaling, replicas, archiving, or in-database partitioning.
  • Choosing a shard key that is not present in the most common queries, turning normal reads into scatter-gather.
  • Sharding by a low-cardinality field such as status or plan type and expecting balanced load.
  • Assuming even row counts mean even traffic; a single popular key can saturate one shard.
  • Using plain modulo hashing and then discovering that doubling the shard count remaps most keys.
  • Forgetting that each shard still needs replication and failover to be highly available.
  • Underestimating operational work: per-shard migrations, backups, monitoring, and configuration drift.
