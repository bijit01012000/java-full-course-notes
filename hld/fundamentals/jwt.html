JWT
JSON Web Token: a compact, URL-safe token format carrying claims, defined by RFC 7519. It is a format, not an authentication protocol.
Claim
A piece of information inside the payload, such as subject, issuer, audience, expiry, role, or tenant.
JWS
JSON Web Signature: a signed JWT. This is what almost all access tokens are.
JWE
JSON Web Encryption: an encrypted JWT, where the payload is unreadable without the decryption key.
kid
Key ID in the header that tells the verifier which key in the issuer's key set signed this token.
JWKS
JSON Web Key Set: an endpoint publishing the issuer's current public keys so services can verify tokens and rotate keys.
Bearer token
A credential where possession alone grants access; anyone who holds it can use it until it expires.
Access token
Short-lived credential sent to APIs that grants access to specific resources or scopes.
Refresh token
Longer-lived credential sent only to the auth server to obtain new access tokens; usually opaque and server-tracked.
Algorithm confusion
An attack where a verifier trusts the token's alg header and accepts a token signed with the wrong algorithm or a public key used as an HMAC secret.

01The problem: HTTP has no memory

HTTP is stateless: every request must carry proof of who is calling. The classic answer is a server-side session.

  • On login, the server verifies credentials, creates a session, and stores it in a database or in Redis.
  • The client receives an opaque session ID — usually in a cookie — and sends it with every request.
  • The server looks up the session, resolves the user, and processes the request.
  • This is simple, centrally revocable, and still the right default for many applications.
  • In a distributed system, every service must either query the session store or call the auth service, adding latency and a shared dependency on the critical path.
  • Caching session data locally helps latency but reintroduces staleness and cache invalidation.
  • The alternative is to put signed claims in the credential itself so each service can verify locally.

02Why JWTs are useful — and what they are not

  • A signed JWT lets a service verify that the token came from a trusted issuer and was not modified, without contacting the issuer.
  • That removes the session lookup from every request and keeps the auth service off the hot path.
  • A JWT is a token format, not an authentication protocol. OAuth 2.0 and OpenID Connect decide when tokens are issued, to whom, with which scopes, and how refresh works.
  • A signed JWT is formally a JWS. Encrypted JWTs exist (JWE) but are less common for API access tokens because they add key-management work.
  • JWTs are also used for service-to-service auth, short-lived signed URLs, and passing verified identity between internal services.
  • They do not automatically make a system faster, more secure, or more scalable; they move trust into a signing key and a claims contract.
  • Statelessness is partial: revocation, refresh tracking, and high-risk checks still need server-side state.

03The structure of a JWT

A JWT is three Base64URL-encoded sections joined by dots: header.payload.signature.

  • The header describes how the token was signed: algorithm, type, and key ID.
  • The payload carries the claims: who the subject is, who issued it, when it expires, and application data such as roles or tenant.
  • The signature is computed over the encoded header and payload and lets the receiver detect tampering.
  • Base64URL is an encoding, not encryption. Anyone holding the token can decode the first two parts.
  • The signature covers base64url(header) + '.' + base64url(payload), so changing either part invalidates it.
  • Tokens are compact enough to travel in an Authorization header, which is why the format spread.
  • Decoding without verifying is always possible and often useful for debugging — never for trust decisions.

04The header

  • alg names the signing algorithm: HS256 (HMAC-SHA256), RS256 (RSA + SHA-256), or ES256 (ECDSA + SHA-256).
  • typ is normally JWT and identifies the token type.
  • kid is the key ID; it tells the verifier which key in a set to use, which is what makes rotation possible.
  • The header is attacker-controlled until verification succeeds. It is a hint, not an instruction.
  • The server must enforce its own allowlist of algorithms and its own trusted key set; it must never let alg decide how to verify.
  • kid is also attacker-controlled: never use it to build a file path or database query directly (path traversal and injection risks).
  • During rotation, old and new keys coexist, and kid selects the right one for each token.
{
  'alg': 'RS256',
  'typ': 'JWT',
  'kid': 'key-2026-10'
}
The header carries no user information. It describes how the signature should be checked, and the verifier decides which of those descriptions it accepts.

05The payload and its claims

  • Registered claims are standardized and understood by libraries: sub, iss, aud, iat, exp, nbf, jti.
  • sub identifies the subject; iss the issuer; aud the intended audience; exp and nbf bound validity in time.
  • jti is a unique token ID, useful for replay detection and deny lists.
  • Custom claims carry roles, permissions, tenant ID, plan, or scopes — whatever the API needs to make a decision.
  • The payload is not encrypted by default. Never put passwords, API keys, secrets, or sensitive personal data in it.
  • Claims are a snapshot taken at issuance: changing a user's role does not change tokens already issued until they expire.
  • Keep claims small and stable. They travel on every request and oversized tokens hit gateway header limits.
ClaimMeaning

06The signature

The signature is what turns readable JSON into a trustworthy credential. It proves integrity and origin — not secrecy.

  • The issuer computes a MAC or digital signature over the encoded header and payload using its signing key.
  • The verifier recomputes or checks it with the corresponding key; a mismatch means the token was altered or signed by someone else.
  • If an attacker flips a role from user to admin, the encoded payload changes and the old signature no longer matches.
  • Without the signing key, the attacker cannot produce a valid signature for the modified payload.
  • HS256 uses one shared secret to sign and verify, so every verifier can also mint tokens.
  • RS256/ES256 use a private key to sign and a public key to verify, so verifiers can check but not create tokens.
  • Use constant-time comparison (libraries do this) and never implement signature checks by hand.

07The authentication flow

  • The client sends credentials to the authentication server, which verifies them.
  • The server builds a payload with subject, issuer, audience, expiry, and needed claims, then signs it.
  • The client stores the token and sends it as Authorization: Bearer <token>.
  • The API verifies the signature, then checks exp, iss, aud, and required scopes or permissions.
  • Return 401 Unauthorized when authentication fails; return 403 Forbidden when the token is valid but lacks permission.
  • A JWT is a bearer credential: whoever holds it can use it. HTTPS is mandatory, and tokens must never appear in URLs.
  • With OAuth 2.0 and OIDC, the app redirects to an identity provider and never handles the user's password; the API-side verification is the same.

08JWTs across services, JWKS, and key rotation

  • The auth service signs with its private key; each downstream service verifies with the matching public key.
  • Public keys are published at a JWKS endpoint — a URL returning a JSON Web Key Set.
  • Services fetch and cache the key set, then use kid from the header to pick the right key.
  • The JWKS URL and expected issuer must come from the service's own configuration, never from the token.
  • Rotation: publish the new public key, start signing with the new private key, keep the old public key until all tokens signed with it expire, then remove it.
  • Emergency rotation after a key compromise needs a shorter overlap and usually forced re-authentication, because old tokens cannot be trusted.
  • Cache refresh needs care: an unknown kid should trigger a rate-limited JWKS refresh, not an unbounded fetch per request.
Publish new public key in JWKS→Sign new tokens with the new key→Verifiers pick keys by kid→Keep old key until old tokens expire→Remove the old key

09Access, refresh, and ID tokens

  • The access token is short-lived and sent to APIs; if it is a JWT, APIs verify it locally and read its scopes.
  • The refresh token is longer-lived, sent only to the auth server, and is often an opaque random value rather than a JWT.
  • Splitting them limits blast radius: a stolen access token dies quickly, while the user stays signed in via refresh.
  • Refresh token rotation issues a new refresh token on each use and invalidates the old one; reuse of an old token signals theft and can revoke the whole family.
  • The ID token in OIDC tells the client who signed in. It is not an API credential, and APIs should reject it as an access token.
  • Scope tokens to an audience: a token minted for billing-api must not be accepted by orders-api.
  • Refresh tokens are typically tracked server-side so they can be revoked, rotated, or bound to a device.

10Storing tokens in browsers and elsewhere

  • Local storage is easy to use with an Authorization header, but JavaScript can read it, so any XSS bug becomes token theft.
  • HTTP-only cookies are unreadable from JavaScript, reducing XSS impact, but the browser sends them automatically, which creates CSRF exposure.
  • Mitigate cookie risk with SameSite, CSRF tokens, the Secure flag, and narrowly scoped Path and Domain.
  • A common pattern is a short-lived access token in memory plus a refresh token in an HTTP-only, SameSite cookie.
  • Mobile apps should use the iOS Keychain or Android Keystore; backend services should use a secrets manager or workload identity.
  • Public clients (SPAs, mobile apps) cannot keep a client secret; use PKCE in the authorization code flow.
  • Never store tokens in URLs, analytics events, crash reports, or logs — all of them leak.

11Revocation

Revocation is the hardest operational problem with JWTs: a self-contained token can be verified without the issuer, so the issuer cannot pull it back.

  • Logout, password change, lost device, role change, and suspected compromise all require some form of invalidation.
  • Strategy 1 — short access-token lifetime: stolen tokens stop working soon, but they still work until they expire.
  • Strategy 2 — refresh token rotation: routine logout revokes the refresh token, and the access token dies shortly after.
  • Strategy 3 — deny list: store revoked jti values until natural expiry and check them on each request, which adds a lookup.
  • Strategy 4 — token version: embed a version and compare it with the user's current version; bumping it invalidates all their tokens at once.
  • High-risk actions (payout changes, API key creation, permission grants) should re-check current server-side state even when the JWT is valid.
  • The revocation store must be highly available; for high-risk operations, a failed check should fail closed.

12Trade-offs and when not to use JWTs

  • For a simple monolith or first-party web app, server-side sessions are often easier to implement, reason about, and revoke.
  • JWTs earn their complexity when many services or parties must verify the same identity without a shared lookup.
  • They are a poor fit when immediate revocation is a hard requirement, because you end up rebuilding session state through deny lists or version checks.
  • Other costs: key management and rotation, claim staleness, token size on every request, and a larger validation attack surface.
  • Do not adopt JWTs because they sound modern or scalable; adopt them because portable verification solves a real problem you have.
  • A hybrid is common and sensible: opaque session or refresh token server-side, short-lived JWT access token at the edge.
  • Whichever you choose, the security properties come from correct validation and key handling, not from the format itself.

13Security checklist and common mistakes

  • Validate more than the signature: check exp, nbf, iss, aud, and then enforce the required permissions.
  • Allowlist algorithms server-side. Reject alg: none, and never let the token choose the verification method.
  • Prevent RS256-to-HS256 confusion: an attacker signs a forged token with HMAC using the issuer's public key as the secret, so never use a public key as an HMAC secret.
  • Allow a small clock skew (tens of seconds) on exp and nbf; do not stretch it into minutes.
  • Keep access tokens short-lived, rotate refresh tokens, and store refresh tokens server-side.
  • Put nothing sensitive in the payload and no frequently changing values you need to be instantly accurate.
  • Redact Authorization headers in proxy logs, error logs, traces, analytics, and crash reports.
  • Use separate issuers, audiences, and signing keys per environment so a staging token can never work in production.
verify(token, key):
  header = decode(token.header)
  if header.alg not in ALLOWED_ALGS: reject
  key = keyset.get(header.kid) or refresh_jwks_once()
  if not signature_valid(token, key): reject
  if now > exp + leeway: reject
  if nbf and now < nbf - leeway: reject
  if iss != EXPECTED_ISS: reject
  if aud not in EXPECTED_AUDS: reject
  return claims
A JWT is a signed token format, not a complete authentication system. Keep access tokens short-lived, pair them with refresh tokens, validate issuer/audience/expiry, and store them carefully.

↔Trade-offs to say out loud

  • Stateless verification removes a session lookup from every request but makes revocation expensive, because the issuer cannot reach tokens already issued.
  • Short access-token lifetimes limit the damage of theft but increase refresh traffic and add a dependency on the auth server for renewal.
  • Asymmetric signing (RS256/ES256) lets many services verify without being able to mint tokens, but costs more CPU and requires JWKS and key-rotation machinery.
  • Symmetric signing (HS256) is simple and fast but every verifier holds the signing secret, so one compromised service can forge tokens for all.
  • Rich claims let services authorize locally but make tokens large and stale; minimal claims stay small but force extra lookups.
  • HTTP-only cookies resist XSS token theft but reopen CSRF risk; local storage avoids CSRF but turns any XSS into full account takeover.
  • Deny lists and token version checks restore revocation but reintroduce the per-request state lookup that JWTs were meant to remove.
  • Self-contained tokens improve availability and latency across services but mean a signing-key compromise has a blast radius measured in token lifetimes.

?Interview questions

Answer aloud before opening the outline.

1. What is a JWT and what problem does it solve?

A compact, signed token format carrying claims about a subject. It solves distributed authentication: any service with the issuer's public key can verify the token locally instead of looking up a central session on every request. It is a format, not a protocol.

2. What are the three parts of a JWT?

header.payload.signature, each Base64URL-encoded and joined by dots. The header describes the signing algorithm and key ID, the payload carries claims, and the signature proves the first two parts were not modified.

3. Is a JWT encrypted?

Normally no. A signed JWT (JWS) is only encoded, so anyone holding it can read the header and payload. Encrypted JWTs (JWE) exist but are uncommon for API access tokens. Never put secrets or sensitive personal data in a normal JWT payload.

4. What does the signature actually guarantee?

Integrity and origin — that the header and payload have not changed since signing and that whoever signed held the key. It does not hide the contents, and it only proves origin if the verifier trusts the right key and issuer.

5. When would you use HS256 versus RS256?

HS256 when one issuer and a small set of fully trusted verifiers share a secret and you want simplicity. RS256/ES256 when many services must verify tokens from one issuer: they get the public key and cannot mint tokens, which is the usual microservice and third-party pattern.

6. How does a service verify a token from another service?

It fetches the issuer's JWKS, caches it, reads kid from the token header, and verifies the signature with the matching public key. It then validates exp, iss, and aud. The JWKS URL and expected issuer come from local configuration, not the token.

7. How does key rotation work without breaking clients?

Publish the new public key in JWKS first, start signing new tokens with the new private key, keep the old public key available until every token signed with it has expired, then remove it. The kid header lets verifiers select the correct key during the overlap.

8. Why split access and refresh tokens?

The access token is short-lived and widely exposed, so theft has a small window. The refresh token is long-lived but sent only to the auth server and can be tracked, rotated, and revoked. Together they balance security with not forcing users to log in constantly.

9. Where should a browser store a JWT?

There is no universally correct answer. Local storage is exposed to XSS; HTTP-only cookies resist XSS but need SameSite and CSRF protection. A common pattern is a short-lived access token in memory plus a refresh token in a Secure, HTTP-only, SameSite cookie.

10. How do you revoke a JWT before it expires?

You cannot reach a token already issued. Use short lifetimes plus refresh-token revocation for routine logout, and add a deny list of jti values or a per-user token version for immediate cases. High-risk actions should re-check current server state anyway.

11. What claims must an API validate?

Signature first, then exp (and nbf if present) with a small clock skew, iss against the expected issuer, and aud against this API. Then enforce the scopes or permissions the operation needs. Signature validation alone is not authentication.

12. What is the algorithm-confusion attack?

The attacker sets alg to HS256 and signs a forged token using the issuer's RSA public key as the HMAC secret. If the verifier trusts the header and uses that public key as a secret, the forgery passes. The fix is to allowlist algorithms server-side and never use a public key as an HMAC key. Rejecting alg: none is the same class of fix.

13. When would you choose sessions over JWTs?

For a single application or first-party web app where immediate revocation matters and there is no need for third parties to verify tokens. Sessions are simpler to reason about and revoke. JWTs pay off when many services need portable, locally verifiable identity.

14. A user's role changed but their token still says admin. What do you do?

Accept that claims are a snapshot, keep access-token lifetimes short, and bump a token version or revoke refresh tokens on role change. For privileged actions, check current authorization server-side rather than trusting the claim. Long-lived tokens with authorization claims are the underlying design error.

!Traps

  • Treating a signed JWT as encrypted and putting secrets or sensitive personal data in the payload.
  • Validating only the signature and skipping iss, aud, and expiry checks.
  • Trusting the alg header, or accepting alg: none and RS256-to-HS256 confusion.
  • Issuing long-lived access tokens, so a stolen token stays usable for days.
  • Accepting an OIDC ID token as an API access token.
  • Logging or tracing full Authorization headers and leaking tokens into observability systems.
  • Putting roles in the token and expecting permission changes to take effect immediately.
  • Claiming JWTs are fully stateless while relying on deny lists, refresh tracking, and session-like checks.
