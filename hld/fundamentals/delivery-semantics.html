In one lineDelivery semantics describe what a messaging system promises about loss and duplication — and every promise is really a choice about when to retry and when to acknowledge.
Delivery semantics
The guarantee a messaging path makes about whether a message can be lost, duplicated, or processed exactly one time.
At-most-once
A message is delivered zero or one time: it may be lost, but it is never duplicated.
At-least-once
A message is never lost, but it may be delivered more than once, so consumers must tolerate duplicates.
Exactly-once
Every message affects the system one time, with no loss and no duplicates, usually implemented as at-least-once plus deduplication.
Acknowledgment
The signal that tells the broker a message was processed, which is what allows it to stop redelivering.
Idempotency
The property that repeating an operation produces the same final state as doing it once.
Idempotency key
A unique identifier carried with a message so the consumer can detect and discard a repeat.
Deduplication
Storing recently seen message identifiers so duplicate deliveries are ignored instead of reprocessed.
Effectively-once
An end-to-end design where duplicates may exist in transport but produce only one observable effect.

01The uncertainty problem

An order service sends 'charge this customer $50' to a payment service and waits. Nothing comes back. The silence is ambiguous, and the ambiguity is the entire subject of delivery semantics.

  • The message may have been lost before delivery, so nothing happened.
  • The message may have been processed and the response lost, so the charge already happened.
  • The service may simply be slow and the response is still in flight.
  • From the sender's view these three cases are indistinguishable — all it observes is silence.
  • Not retrying risks a payment that never happens; retrying risks charging the customer twice.
  • Every messaging system therefore has to pick a behavior for this exact moment.

02The three guarantees

  • At-most-once: delivered once or not at all — possible loss, never duplication.
  • At-least-once: never lost, but possibly delivered more than once.
  • Exactly-once: each message affects the system one time, with neither loss nor duplication.
  • The guarantees are not abstract promises; each follows from concrete choices about retrying and acknowledging.
  • In practice exactly-once is delivered as at-least-once transport plus deduplication at the effect boundary.
  • The choice should be made per message type, because not every message deserves the same cost.

03At-most-once

  • The consumer acknowledges, or the broker deletes, the message before the work is done.
  • Because the message is already gone, a crash during processing leaves nothing to redeliver.
  • The failure mode is silent loss, which is acceptable when the data is replaceable or superseded.
  • Good fits: metrics samples, telemetry, log shipping, live position updates where the next value overwrites the last.
  • Bad fits: payments, order placement, anything a user expects to happen.
  • It is cheap and simple because no retry, tracking, or deduplication state is required.

04At-least-once

  • The consumer acknowledges only after successfully processing, so an unacknowledged message is redelivered.
  • This guarantees no loss as long as retention outlives the consumer's downtime — a real constraint, not a free property.
  • The cost is duplicates: a crash after the effect but before the acknowledgment replays the message.
  • Duplicate delivery can also come from retries after a timeout, from failover, or from a consumer being reassigned.
  • Consumers must therefore be idempotent or deduplicated, otherwise the guarantee becomes 'at least one bad outcome'.
  • It is the most common production default because it fails safe: nothing disappears.

05Exactly-once

  • Exactly-once means one effect, not one network transmission; the network may still carry a message twice.
  • Typical construction: at-least-once delivery, a stable message ID, and a deduplication store the consumer checks before acting.
  • The effect and the record of 'already processed' must commit together, usually in one local transaction.
  • If the effect is an external side effect (an email, a card charge), you need that system's own idempotency mechanism.
  • Scope matters: exactly-once inside one broker and one database is tractable; across arbitrary external systems it is a design effort, not a switch.
  • It costs latency, extra storage, and coordination, so applying it everywhere is usually over-engineering.

06Where the choice lives: retry and acknowledge timing

  • Move the acknowledgment earlier and you reduce duplicate risk while increasing loss risk.
  • Move the acknowledgment later and you eliminate loss while accepting duplicates.
  • A retry is what turns an unacknowledged message into a possible duplicate.
  • The ack boundary must match the transaction boundary of the work being done, not an arbitrary point in the handler.
  • Batching acknowledgments trades throughput for a wider duplicate window on partial failure.
  • Explicitly document which guarantee each consumer path provides; implicit semantics drift during refactors.
Ack pointLoss riskDuplicate risk
Before processingHigh — crash loses the workNone
After processing, before commitLowModerate — effect may have applied
After commitNonePossible on ack failure

07Producer-side duplicates

  • A producer that retries after a timeout may send the same message twice even if the first was stored.
  • An idempotent producer attaches a producer identity and a per-message sequence number so the broker discards a repeat.
  • This protects the write path only — it does nothing about a consumer that reapplies an effect.
  • Some brokers also offer transactions that group writes and offsets into one atomic unit for stream processing.
  • Producer retries need a bounded policy and a cap, otherwise a stuck producer turns into a retry storm.
  • Retries should never be unbounded loops without backoff and a terminal outcome.

08Consumer-side idempotency

  • Make the handler naturally idempotent where possible: SET status = 'shipped' instead of increment count.
  • Use a unique message ID plus a processed-messages table, ideally in the same store as the effect.
  • For inserts, rely on a unique constraint on the business key so a duplicate fails harmlessly.
  • For external calls, pass an idempotency key the downstream service honors.
  • Deduplication windows are finite, so decide how long an ID is remembered and what happens after it expires.
  • Idempotency is the real requirement; exactly-once is one way to satisfy it.

09Ordering, partitions, and duplicates

  • Retries and redelivery can reorder messages unless the system preserves a sequence per key.
  • Many brokers guarantee order only within a partition or message group, so ordering scope must match the business key.
  • A retry that lands later than a subsequent message can apply an older state over a newer one.
  • Consumers can guard with a version or timestamp and reject stale updates.
  • Preserving strict order usually forces a single consumer lane, which caps throughput.
  • State the ordering requirement first; it constrains which semantics are even achievable.

10Failure modes that break the guarantee

  • Poison messages redelivered forever under at-least-once, consuming capacity — route them to a dead-letter queue.
  • Retention expiry silently converts at-least-once into at-most-once for a consumer that fell too far behind.
  • Ack after external side effect leaves an unrecorded effect when the ack fails, producing duplicates.
  • Deduplication store unavailable forces a choice between blocking and risking duplicates.
  • Non-transactional dedup allows the effect to apply and the ID record to fail, defeating exactly-once.
  • Unbounded retry hides a permanent error as a slow one and inflates load.

11Choosing a guarantee

  • Ask what a lost message costs versus what a duplicate costs.
  • Loss is worse for money, inventory, and fulfilment; duplicates are worse for notifications, emails, and counters.
  • If duplicates are cheaper, choose at-least-once and invest in idempotency.
  • If loss is cheap and volume is high, at-most-once can be the pragmatic choice.
  • Reserve exactly-once machinery for flows where both loss and duplication are unacceptable.
  • Match the guarantee to the message type rather than standardizing on the strongest one everywhere.

12Verifying it in production

  • Track redelivery counts and duplicate rejections; a rising rate means duplicate handling is doing real work.
  • Alert on consumer lag and retention risk, since falling behind quietly degrades at-least-once.
  • Log the message ID and a trace ID so a duplicate can be traced to the exact retry.
  • Test by injecting failures: kill the consumer between effect and ack, and confirm the outcome is still correct.
  • Review every new consumer for idempotency rather than assuming the framework provides it.
  • Document the chosen semantics next to the topic or queue configuration.

↔Trade-offs to say out loud

  • Acknowledge early removes duplicates but risks losing work on a crash.
  • Acknowledge late removes loss but guarantees occasional duplicates on retry.
  • Exactly-once removes both risks in its scope, at the cost of coordination, storage, and latency.
  • Deduplication tables suppress repeats, but add a write per message and a retention decision on IDs.
  • Idempotent producers protect the write path, but do nothing for consumer-side reapplies.
  • Strict ordering preserves intent across retries, but limits parallelism to a single lane.
  • Batching raises throughput, but widens the window where a partial failure forces a redelivery.
  • Unbounded retries maximize delivery attempts, but hide permanent failures and amplify load.
  • Strongest-everywhere simplifies reasoning, but pays coordination cost on messages that never needed it.

?Interview questions

Answer aloud before opening the outline.

1. Why is a lost acknowledgment ambiguous?

The sender cannot tell whether the message was dropped before delivery, processed with the response lost, or is still in flight. Since all three look identical, any decision — retry or not — risks either loss or duplication.

2. Define the three delivery guarantees.

At-most-once delivers zero or one time and may lose messages. At-least-once never loses but may duplicate. Exactly-once means each message takes effect once, with neither loss nor duplication, and is normally implemented as at-least-once plus deduplication.

3. How is at-most-once implemented?

The consumer acknowledges before doing the work, so the broker has nothing to redeliver if processing fails. It is simple and duplicate-free but silently loses messages, which suits telemetry and superseded state updates.

4. When do duplicates appear under at-least-once?

Whenever the work succeeded but the acknowledgment did not reach the broker. That happens on a consumer crash, an ack timeout, a network partition, or a failover that reassigns the message to another consumer.

5. Does exactly-once mean the message crosses the network once?

No. Transport can still carry duplicates. Exactly-once is a statement about effects: the system reaches the same state as if each message were applied once. Deduplication and atomic commit are what make that true.

6. How do you implement idempotent consumption?

Prefer naturally idempotent writes such as setting a value. Otherwise record processed message IDs in the same transaction as the effect, use unique constraints on business keys, or pass an idempotency key to downstream services.

7. What breaks exactly-once most often?

Doing the dedup check and the effect in separate transactions, or calling an external system that has no idempotency support. Either way, a failure between the two steps leaves the state inconsistent with what the system believes.

8. How does consumer lag threaten at-least-once?

If a consumer falls behind longer than the retention window, unprocessed messages are deleted. At that point the system behaves like at-most-once for that consumer, without any configuration change or warning unless lag is monitored.

9. Why does ordering interact with delivery semantics?

A retry can deliver an older message after a newer one, so the effect order differs from the send order. Systems therefore guarantee order only within a partition or message group, and consumers often reject stale updates using a version or timestamp.

10. Which guarantee would you pick for a payment?

Exactly-once behavior with an idempotency key the payment provider honors, because both a lost charge and a double charge are unacceptable. In practice this means at-least-once transport plus a durable record of processed keys.

11. When is at-most-once the right call?

When messages carry replaceable data that is superseded quickly, such as metrics samples, live position updates, or cache warm hints. Losing one is harmless and the duplicate-suppression machinery would cost more than it saves.

12. How would you test that a consumer is idempotent?

Deliver the same message twice and compare state, then kill the consumer between the effect and the acknowledgment and confirm recovery produces one effect. Both tests exercise the failure paths that production actually hits.

!Traps

  • Claiming exactly-once because the broker supports it, while the consumer calls a non-idempotent external API.
  • Acknowledging before processing and calling the result reliable.
  • Checking a deduplication table in a different transaction from the effect.
  • Ignoring that retention expiry silently downgrades at-least-once to at-most-once.
  • Retrying forever without a terminal outcome or dead-letter path.
  • Assuming a topic-wide ordering guarantee when the broker only orders within a partition.
  • Applying the strongest guarantee to high-volume telemetry and paying coordination cost for nothing.
