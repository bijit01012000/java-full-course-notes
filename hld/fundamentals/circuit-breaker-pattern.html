Cascading failure
A failure that spreads because callers hold threads and connections waiting on a degraded dependency, so healthy endpoints also stop serving.
Circuit breaker
A state machine around calls to one dependency that passes, rejects, or probes traffic based on recent outcomes.
Closed state
Normal operation: calls flow through and the breaker records successes, failures, and slow calls.
Open state
The breaker rejects calls immediately — or routes them to a fallback — for a cool-down period instead of waiting on a failing dependency.
Half-open state
A limited number of trial calls are allowed after the cool-down; success closes the breaker and failure reopens it.
Failure-rate threshold
The proportion of failed calls in a sliding window that trips the breaker from closed to open.
Slow-call threshold
A latency above which a call counts as a failure even if it eventually succeeds, catching degradation before hard errors.
Minimum request volume
The number of calls required in the window before the breaker is allowed to trip, preventing noise on low-traffic dependencies.
Fallback
The response used when a call is rejected or fails: a cached value, a safe default, a queued retry, or an explicit fast error.
Retry budget
A cap on retries as a fraction of successful traffic, so retry amplification cannot exceed a small multiple of normal load.

01How one slow dependency takes down the caller

Remote calls fail differently from local calls. A dependency can stay up, accept connections, and simply take far too long to answer.

  • The order service calls payment on every checkout; normally payment responds quickly.
  • If payment's database saturates, calls do not fail fast — they hang for many seconds each.
  • Every waiting request holds a thread, a connection, and memory in the order service.
  • Thread and connection pools are finite, so once they fill, unrelated endpoints on the same service also stop responding.
  • Callers of the order service then queue behind it, and the slowdown propagates upstream as a cascading failure.
  • The dependency may be only partially degraded while the caller becomes completely unavailable.
The dangerous failure is not the one that returns an error immediately. It is the one that makes every caller wait.

02Why timeouts and retries are not enough

A timeout is necessary but not sufficient. It bounds a single call; it does not stop the aggregate damage of many doomed calls.

  • A timeout still spends its full duration on every failing call, so under load the pool still fills with waiters.
  • Retries add load exactly when the dependency is weakest: 1 attempt plus 3 retries can turn 100 requests/s into up to 400 calls/s.
  • Retries also extend how long the caller holds a thread, making exhaustion faster.
  • Layered retries are worse — gateway, sidecar, and application each retrying can multiply attempts again.
  • Timeouts must be shorter than the caller's own deadline and should propagate as a remaining-time budget.
  • What is missing is memory of failure: the caller keeps paying the timeout even after it knows the dependency is down.
Retries help with transient, isolated faults. They make sustained overload worse.

03What a circuit breaker is

  • A circuit breaker wraps calls to one dependency and records the outcome of each call.
  • When the failure or slow-call rate crosses a threshold, it stops forwarding calls and fails them fast.
  • After a cool-down it admits a small number of probe calls to test recovery.
  • It is named after the electrical breaker: it trips to protect the wider system rather than trying harder.
  • It is a state machine, not a retry policy; its job is to shed load, not to make a failing call succeed.
  • It converts an unpredictable slow failure into a fast, bounded, observable one.

04The three states

  • Closed is normal operation; the breaker is invisible except for its metrics.
  • Open protects the caller and gives the dependency room to recover, but every rejected call needs a defined behavior.
  • Half-open answers the question the timer cannot: has the dependency actually recovered?
  • The probe count should be small; a large half-open allowance floods a service that is still broken.
  • Each instance usually keeps its own breaker state, so a fleet has many independent breakers.
  • Operational controls often include a forced-open mode for draining a dependency during maintenance.

05Thresholds that actually work

  • Use a failure rate over a sliding window, not a lifetime average that takes hours to react.
  • Track a slow-call rate as well as errors; a call that takes many seconds is a failure for capacity purposes.
  • Set a minimum request volume so two failures out of two calls do not trip a low-traffic dependency.
  • Choose the open duration long enough for recovery and short enough to restore service when the dependency returns.
  • Limit permitted calls in half-open so the probe itself cannot become a load spike.
  • On very low-traffic dependencies, a consecutive-failure count is often more stable than a percentage.
  • Tune from observed latency and error budgets, not from copied defaults; thresholds depend on the dependency's normal behavior.
A breaker that trips on every single error flaps. One tuned too loosely never protects. Both are configuration bugs.

06Fallbacks and degraded behavior

  • Failing fast with a clear error is a valid fallback and is far better than making the user wait.
  • Return a cached or last-known value when slight staleness is acceptable, such as recommendations or a shipping estimate.
  • Use a safe default for non-critical sections: an empty list, a generic message, or a hidden widget.
  • Queue the operation for later when it is deferrable, such as sending a confirmation email.
  • Return a partial response: serve the page without the recommendations that are currently unavailable.
  • The fallback must not call the same failing dependency or another one likely to fail at the same moment.
  • Never fake a critical success — a payment must not be reported as captured because the breaker opened.
  • Make degradation explicit in the product and in metrics so nobody mistakes a fallback for a healthy path.

07Scope: one breaker per dependency

  • Scope a breaker to the dependency it protects, usually per callee and per caller instance.
  • A single global breaker would let a failing recommendation service block checkout.
  • If one dependency has very different endpoints or clusters, separate breakers prevent one bad route from disabling the rest.
  • Per-tenant or per-shard breakers stop one noisy tenant from tripping protection for everyone.
  • Breakers do not limit concurrency; pair them with bulkheads so a slow dependency cannot consume all threads or connections.
  • In a service mesh, breakers are often per proxy and per route, which is coarser than application-level business semantics.
  • Track breaker state per dependency; an aggregate health number hides which dependency is actually failing.

08Retries and retry budgets

  • Retry only transient, retryable failures, and only operations that are safe or idempotent to repeat.
  • Use exponential backoff with jitter so retries do not synchronize into waves.
  • A retry budget caps retries as a small fraction of successful traffic, so total attempts stay bounded even during an incident.
  • Retry at exactly one layer; gateway, sidecar, and application retries otherwise multiply into a retry storm.
  • An open breaker should suppress retries rather than queue them for after the cool-down.
  • Respect an overall deadline: a retry that will finish after the caller's deadline is wasted capacity.
  • Hedged requests — sending a second copy after a latency threshold — reduce tail latency but add load; use them selectively.

09Where to implement it

  • An in-process library can distinguish a business failure from a transport failure; a proxy usually cannot.
  • A mesh applies the same policy to every service without code changes, which is valuable in a polyglot estate.
  • An API gateway protects the system from client traffic but not from internal service-to-service failures.
  • Pick one owner per hop for timeouts, retries, and breakers, and document the division.
  • Duplicating protection at several layers makes behavior hard to predict and can amplify retries.
  • Whichever layer you choose, expose its state and transitions to the people on call.

10Observability and tuning

  • Expose the current state as a gauge and every transition as an event with a reason.
  • Track rejected calls, fallback rate, half-open probe results, and time spent open.
  • Alert on breakers that stay open for a long time and on breakers that flap repeatedly.
  • Correlate breaker state with dependency latency and error rate to distinguish a real outage from a misconfigured threshold.
  • A breaker that never opens during real incidents is too loose; one that opens every day is hiding an unresolved problem.
  • Fault-inject latency and errors in staging to verify that the breaker trips and the fallback behaves.
  • Revisit thresholds after major traffic, deployment, or dependency changes.

11Failure modes and design rules

  • Without timeouts, the breaker has no bounded outcome to count; slow calls must be classified, not waited on forever.
  • All instances opening at once can create a thundering herd when they all probe in half-open; add jitter to the open timer.
  • A cached fallback with no expiry can serve stale data indefinitely and hide a permanent failure.
  • A breaker cannot fix a deterministic bug; if every call fails the same way, fix the dependency instead of tuning thresholds.
  • Per-instance state can oscillate: some instances open while others keep sending traffic; aggregate health before declaring recovery.
  • Retries on top of an open breaker turn rejection into a delay loop unless retries are suppressed.
  • Design rule: timeout < caller deadline, bounded retries, one retry layer, a safe fallback, and a per-dependency bulkhead.

↔Trade-offs to say out loud

  • Fast failure protects the caller's capacity but turns a slow dependency into an immediate user-visible error.
  • Aggressive thresholds trip early and preserve availability but cause false positives during normal variance.
  • Lenient thresholds avoid false positives but let a degraded dependency exhaust the caller before protection engages.
  • Per-instance breakers are simple and local but give an inconsistent fleet view and can oscillate.
  • Mesh-level breakers are uniform and language-agnostic but cannot distinguish business-level failures.
  • Cached fallbacks preserve the user experience but risk serving stale or incorrect data.
  • Retry budgets bound amplification but can reject otherwise recoverable requests during a partial outage.
  • Short open windows recover quickly but hammer a dependency that is still down; long windows are safer but slower to restore.

?Interview questions

Answer aloud before opening the outline.

1. What problem does a circuit breaker solve?

It prevents a caller from repeatedly waiting on a failing or slow dependency. By failing fast once failures cross a threshold, it preserves threads, connections, and capacity so the failure does not cascade to other services.

2. Why isn't a timeout enough?

A timeout bounds one call but every doomed call still consumes its full duration. At high volume the pool still fills. A breaker stops issuing calls entirely for a cool-down, which is the part a timeout cannot do.

3. Explain the three states.

Closed: calls pass and outcomes are recorded. Open: calls are rejected immediately for a cool-down. Half-open: a few probe calls are allowed; success closes the breaker, failure reopens it.

4. What thresholds matter when configuring a breaker?

Failure rate and slow-call rate over a sliding window, a minimum request volume so low-traffic services do not trip on noise, the open duration, and the number of permitted half-open probes.

5. Why count slow calls as failures?

A dependency can return successful responses too slowly to be usable. Counting calls above a latency threshold as failures lets the breaker trip on degradation before the caller's pools are exhausted.

6. What is a good fallback?

A response that is safe, cheap, and does not depend on the failing service: a cached value, a default, a partial page, a queued retry, or an explicit error. It must never report a critical action as successful when it did not happen.

7. Why scope breakers per dependency?

Protection should apply to the failing dependency only. A global breaker would let a broken recommendation service block checkout, turning a partial degradation into a full outage.

8. How do circuit breakers and retries interact?

Retries increase load on a struggling dependency and can turn a blip into an outage. Bound them with a retry budget, backoff, and jitter, retry at one layer, and suppress retries when the breaker is open.

9. What is a retry budget?

A cap on retries relative to successful traffic, for example a small percentage of normal request volume. It keeps amplification bounded during an incident instead of letting every caller multiply its attempts.

10. Where should the breaker live?

In-process when it needs business semantics, in a sidecar or mesh when uniformity across languages matters, or at the gateway for north-south traffic. Choose one owner per hop to avoid duplicated protection.

11. What can go wrong when the breaker opens on every instance at once?

When the cool-down expires, all instances may probe simultaneously and create a load spike. Jitter the open timer and keep the half-open probe count small.

12. How do you know the breaker is configured correctly?

It trips during injected faults, recovers cleanly when the dependency returns, does not flap during normal variance, and its state correlates with dependency latency and errors. Test it with fault injection rather than assuming.

13. Is a circuit breaker a substitute for a bulkhead?

No. A breaker stops calls after failure is detected; a bulkhead limits how many resources one dependency can consume in the first place. They are complementary, along with timeouts and bounded retries.

14. When would you not add a circuit breaker?

When the dependency is local and fast, when failures are deterministic and must be surfaced, or when the caller has no fallback and no capacity risk. Adding one without a fallback plan mainly changes the error message.

!Traps

  • Adding a breaker without timeouts, so slow calls never produce a bounded outcome to count.
  • Retrying at the gateway, the sidecar, and the application, multiplying attempts during an outage.
  • Tripping on a single failure with no minimum request volume, causing constant flapping.
  • Using one global breaker for all dependencies, so one failure disables unrelated calls.
  • Treating an open breaker as a success path and silently returning fake data for critical operations.
  • Forgetting that breaker state is usually per instance and assuming the whole fleet is protected at once.
  • Tuning thresholds once and never revisiting them after traffic or dependency changes.
