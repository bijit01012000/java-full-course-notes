View
A saved query definition that runs against base tables every time it is referenced; it stores no rows of its own.

A database object that stores the computed result of a query physically, so later reads do not recompute it.
Refresh
The operation that recomputes a materialized view and replaces or updates its stored rows.
Full refresh
Recomputing the entire query result and rewriting the view's contents.
Incremental refresh
Applying only the deltas produced by base-table changes, avoiding a full recomputation.

How far a materialized view lags behind the base tables it was derived from.

The optimizer transparently answering a query from a matching materialized view instead of the base tables.

The schedule or trigger that decides when a materialized view is brought up to date.
Base table
A source table whose changes must eventually be reflected in the materialized view.

01The problem: expensive work repeated on every request

Some queries are cheap to write and expensive to run: multi-table joins, wide aggregations, ranking, and rollups over large fact tables. When a dashboard or API endpoint runs that query on every page load, the database pays the same cost again and again for the same answer.

  • A join across several large tables can take far longer than the surrounding request logic.
  • Aggregations must scan or index-scan large ranges to produce a small result.
  • Repeated identical queries waste CPU and I/O that could serve other traffic.
  • Caching in the application helps, but the cache still has to be filled by a slow first query.
  • Business users often want the same rollup refreshed on a predictable schedule, not per request.
  • If the underlying data barely changes relative to how often it is read, recomputing is pure waste.

02What a materialized view is

  • A regular view is only a stored query: referencing it re-executes the SQL against base tables.
  • A materialized view executes the query and stores the rows, so reads fetch a result set instead of computing one.
  • It behaves like a table for reads: it can be indexed, queried, and joined like any other relation.
  • It is derived data, so it must be refreshed when the base tables change.
  • The stored result is often far smaller than the inputs — a daily rollup over millions of events may be a few thousand rows.
  • It is the database-native form of a precomputed result, separate from an application cache.

03How refresh works

  • Full refresh recomputes the whole query and replaces the contents; simple and correct, but cost scales with the data.
  • Incremental refresh applies only changes since the last refresh, often derived from logs or change tracking.
  • Incremental refresh is cheaper but requires the database to prove the delta is computable — not every query shape qualifies.
  • Refresh can run on a schedule, on demand, after a commit, or when the view is next queried.
  • Some engines refresh lazily: a read triggers the update if the view is marked stale.
  • Refresh usually takes a lock or swaps the result, so concurrent readers may briefly block or see a mix of old and new data.
Base tables receive inserts, updates, and deletes→Changes are captured in a log, trigger, or tracked delta→Refresh job is triggered by schedule or explicitly→View result is recomputed or patched incrementally→New result is swapped in and indexes are updated

04Staleness is the central design decision

  • A materialized view is a snapshot; between refreshes it reports the past.
  • Staleness must be bounded by business need, not by refresh speed alone.
  • A daily revenue rollup can tolerate hours of lag; an inventory count cannot.
  • Choose the refresh cadence from how quickly the answer becomes wrong, not from how cheap the refresh is.
  • State the freshness contract in the design: at most N minutes behind is a testable requirement.
  • If no staleness is acceptable, a materialized view is the wrong tool for that read.
The question to ask is not how often can we refresh but how old may this answer be before it misleads someone.

05Where materialized views pay off

  • Dashboards and reporting over large fact tables with a small set of fixed metrics.
  • Rollups: counts, sums, averages, and percentiles precomputed per hour, day, or tenant.
  • Expensive joins that flatten normalized data into a wide read model.
  • Search or feed pages that need a pre-sorted, pre-filtered candidate set.
  • Read-heavy endpoints where the same aggregate is requested by many users.
  • Analytical workloads on a replica, keeping the primary free for transactions.

06Choosing what to materialize

  • Materialize queries that are both frequent and expensive; ignore one-off analytics.
  • Prefer results that are small relative to their inputs, so storage cost stays modest.
  • Prefer queries whose underlying data changes slowly relative to read volume.
  • Group related metrics into one view rather than many overlapping ones that each rescan the same data.
  • Keep the definition stable: every change to the query means a rebuild or a new object.
  • Design the view around the access pattern — the filter and sort columns users actually query.

07Indexing and storage cost

  • A materialized view is a physical relation, so it can and usually should have indexes.
  • Index the columns used in the view's own WHERE, JOIN, and ORDER BY clauses.
  • Without an index, reading the view may still scan a large stored result.
  • Storage cost is the result size plus indexes plus any change-tracking structures.
  • Refresh rewrites or patches rows, which consumes I/O and generates its own log volume.
  • Over many views, storage and refresh load can rival the cost of the queries they replaced.

08Keeping the view trustworthy

  • Refresh must be idempotent: a retried or failed run should not double-count rows.
  • Incremental refresh needs a reliable ordering or watermark so a change is applied exactly once.
  • Readers should see either the previous complete result or the new one, not a half-applied state.
  • Long-running reads on a view being refreshed can block the swap or read stale pages.
  • Track and expose the last successful refresh time; silent refresh failures are the worst failure mode.
  • A view that has been failing for days looks healthy to the application while returning old numbers.

09Alternatives and how they compare

  • Application cache avoids database work entirely, but you own invalidation and cold-start cost.
  • Denormalization stores duplicate columns in base tables, keeping writes responsible for consistency.
  • Plain summary table written by a job gives full control, at the cost of maintaining the write path yourself.
  • Stream processing maintains aggregates continuously with low latency, but adds a whole pipeline to operate.
  • Materialized view keeps the logic in the database and reuses its optimizer, at the cost of refresh control.
  • All of these trade freshness for read speed; the choice is about where the staleness and the maintenance live.

10Operational failure modes

  • Refresh jobs that overlap because one run takes longer than the interval.
  • Refresh timelines drifting later and later until the view is hours or days stale.
  • Full refreshes on a large base table causing I/O spikes that hurt production traffic.
  • Refresh and heavy reads contending for the same locks and buffer pool.
  • Unbounded growth when the view is never pruned and accumulates old partitions.
  • Schema changes to base tables silently breaking the view definition.
  • Dashboards that never show the last refreshed timestamp, so nobody notices the staleness.

11Decision rules

  • Use a materialized view when reads greatly outnumber writes to the underlying data.
  • Use it when the query is expensive but its result is compact.
  • Skip it when the answer must always be exact and current.
  • Skip it for queries that run rarely or vary per request.
  • Always define the freshness budget, the refresh trigger, and who is alerted when refresh fails.
  • Start with one high-value view, measure the win, and only then add more.
  • If writes are frequent and the view must be fresh, prefer incremental maintenance or a streaming pipeline.

↔Trade-offs to say out loud

  • Precomputing a result turns a repeated expensive query into a cheap read, but adds storage and a refresh path that can fail.
  • Full refresh is simple and always correct, but its cost scales with the source data and it can spike I/O during business hours.
  • Incremental refresh is cheap per run, but requires change tracking and only works for query shapes whose deltas can be computed.
  • Shorter refresh intervals reduce staleness, but increase compute, lock contention, and the chance that runs overlap.
  • Query rewrite lets existing SQL benefit transparently, but makes it harder to reason about which queries actually hit the base tables.
  • Database-native views keep logic near the data, but tie the refresh model to one engine's feature set.
  • Materialized views reduce read latency, but they duplicate data that must be rebuilt during migrations and reindexing.
  • Many small views are easier to refresh, but overlapping definitions multiply storage and rescan the same base data.

?Interview questions

Answer aloud before opening the outline.

1. What is a materialized view?

A database object that runs a query once and stores the result rows on disk. Reads then fetch the stored result instead of recomputing the join or aggregation. It must be refreshed to reflect changes in the base tables, so it is always somewhat stale.

2. How is it different from a normal view?

A normal view is only a saved query and re-executes against base tables on every reference, so it is always current but never faster than the underlying query. A materialized view stores the computed result, making reads fast but introducing storage cost and a refresh requirement.

3. When would you use a materialized view?

When a query is expensive, runs often, returns a comparatively small result, and the business can tolerate bounded staleness. Dashboards, rollups, and flattened read models are typical. Rare or always-exact queries should read the base tables directly.

4. How do you decide the refresh strategy?

Start from the freshness requirement: how old may the answer be before it misleads someone? Then pick the cheapest mechanism that meets it — scheduled full refresh for small results, incremental for large fact tables, or on-commit for tiny views. Always make the last successful refresh time visible.

5. What is the risk of a full refresh?

It recomputes the entire result, so its cost grows with the source data and it can generate large I/O and log volume. Run during a quiet window, or refresh into a shadow copy and swap, so readers are not blocked. If runs take longer than the interval, they overlap and compound the load.

6. How do you keep a materialized view from silently going stale?

Record and expose the last successful refresh timestamp, alert when it exceeds the freshness budget, and fail loudly rather than partially. Make refreshes idempotent and retryable. A dashboard that shows its own data age makes staleness visible to the people relying on it.

7. Do materialized views need indexes?

Usually yes. The view is a physical relation, and without an index a read may scan the whole stored result. Index the columns the consuming queries filter, join, and sort on. The indexes add storage and make each refresh more expensive to apply.

8. Materialized view vs application cache — which do you choose?

Use a materialized view when the computation belongs in the database, the result is queryable and joinable, and you want the optimizer involved. Use an application cache when you need per-key caching of API responses and can accept TTL invalidation. Both accept staleness; they differ in where the refresh logic lives.

9. What happens to consistency during a refresh?

Depending on the engine, readers may block briefly, or see the old result until a swap completes. The safe pattern is to compute into a shadow relation and swap atomically, so no reader observes a half-applied state. Incremental refresh must also guarantee each change is applied exactly once.

10. Can a materialized view replace a read replica?

No. A replica copies the whole database and serves arbitrary read queries; a materialized view stores one specific result. Replicas give read capacity and failover, views give latency reduction for a known query. They are often combined: views maintained on a replica for reporting.

11. What is the operational cost of adding many views?

Each view adds storage, index maintenance, and a refresh job that can fail or overrun. Overlapping views rescan the same base tables repeatedly. Refresh load can end up competing with production traffic, so views should be few, purposeful, and monitored like any other batch job.

!Traps

  • Materializing a query whose result is nearly as large as the base table, gaining little and paying full storage.
  • Assuming a materialized view is always current because it is defined in the database.
  • Scheduling refreshes so tightly that runs overlap and pile load onto the primary.
  • Never surfacing the last refresh time, so a broken job goes unnoticed for days.
  • Forgetting indexes on the view and then scanning the whole stored result.
  • Using views as a substitute for fixing a missing index or a badly shaped query.
