In one lineA key-value store is the simplest useful database: a value under a unique key, with get, put, and delete — extremely fast and easy to partition, but blind to what is inside the value.
Key
The unique identifier used to store and retrieve one value, usually a string built by the application.
Value
An opaque blob of bytes from the store's point of view — JSON, a serialized object, or just a number.
Cache-aside
A pattern where the application reads the cache first, loads from the database on a miss, then writes the result back with a TTL.
TTL
Time-to-live: an expiry attached to a key so the store removes it automatically after a period.
Eviction
The policy that decides which keys to drop when an in-memory store runs out of memory.
Consistent hashing
Placing nodes and keys on a ring so adding or removing a node moves only the keys in its section.
Hash slot
A fixed partition of the key space, assigned in groups to nodes, so capacity moves by moving slots rather than rehashing every key.
Quorum (N, W, R)
N replicas, W acknowledgments required for a write, R responses required for a read; if R + W > N, reads overlap the newest write.
Leaderless replication
A model where a write goes to several replicas at once instead of to one primary.
Hot key
A single key whose traffic overloads its node even though the rest of the cluster is idle.

01The problem key-value stores solve

A web application with millions of logged-in users loads a session on every request: who the user is, their permissions, and their cart.

  • The lookup is always identical: fetch one record by its session id.
  • There is no join, no search by content, no aggregation — just a fetch that must be fast, thousands of times per second.
  • A relational database can store it, but each fetch pays for parsing, planning, and possibly disk reads to answer a trivial question.
  • The work is pure overhead because the access pattern is already known exactly.
  • What is wanted is a shared hash map that many application servers can use.
  • That is exactly the shape of a key-value store.

02What a key-value store is

  • Data is stored as pairs: a unique key and the value associated with it.
  • The interface is tiny — put stores, get returns, delete removes.
  • A key like session:abc123 maps to a value holding the session details.
  • The store usually does not interpret the value; to it, the value is a blob of bytes.
  • Some stores add structure: Redis supports lists, sets, sorted sets, and hashes with operations on each element.
  • A sorted set, for example, makes a leaderboard a single command instead of an application-side sort.
  • The core contract stays the same: you must know the key to reach the data.

03Common use cases

  • The common thread is that the application already knows the exact key it needs and needs the answer immediately.
  • Caching, sessions, carts, rate limits, feature flags, leaderboards, tokens, and one-time codes all fit that shape.
  • Each use case stresses a different feature: expiry for sessions, atomicity for counters, ordering for leaderboards.
  • What they share is a value that is small, self-contained, and meaningful only when paired with its key.
  • None of them needs a join or a scan, which is exactly why the store can stay minimal.
  • A workload that needs to answer questions across many keys does not belong here.

Caching

  • Store the result of an expensive query or API call under a key derived from the request.
  • The cache-aside flow: read the cache; on a hit return; on a miss read the database, store the result with a TTL, then return it.
  • The benefit is skipped work on every subsequent request.
  • The cost is freshness: the cached value can be older than the database until it expires or is deleted.
  • Decide explicitly whether expiry or explicit invalidation owns correctness.
Read cache→Hit: return value→Miss: read database→Store result with TTL→Return value

Sessions, carts, and rate limits

  • Session storage uses the session id as key and the session data as value, which lets any app server serve any user.
  • Shopping carts work the same way with the user id as key.
  • A rate limiter keys on user plus time window and stores a counter incremented per request.
  • That increment must be atomic: a read-then-write in the application lets two requests race and both pass.
  • Windows are usually fixed or sliding; the key design decides which is easy.

04In-memory versus persistent stores

  • In-memory stores such as Redis and Memcached keep data in RAM, so reads and writes are extremely fast.
  • The trade-off is cost per gigabyte and volatility: memory is more expensive than disk and disappears on restart.
  • Memcached is purely a cache, so a restart or eviction simply loses entries.
  • Redis can persist to disk, with different guarantees per mode.
  • Persistent stores — DynamoDB, RocksDB, etcd — are designed to be the permanent home of data and to survive restarts and node loss.
  • They are slightly slower but durable and horizontally scalable.
  • The first design question is therefore: is this a cache that can be rebuilt, or a source of truth that must never lose data?

05How it works internally

  • On one machine, an in-memory store is usually a hash table: hash the key to find a slot.
  • That gives constant-time average lookup regardless of how many keys are stored.
  • Disk-based stores need a structure suited to pages: many use an LSM tree, where writes are buffered and flushed as sorted files.
  • Others use a B-tree, which keeps keys sorted in pages on disk.
  • A useful side effect of sorted structures is range scans, such as all keys starting with user:42:.
  • A pure hash table cannot do that efficiently, because hashing scatters related keys.
  • So the choice of structure decides whether prefix scans are possible, not just how fast a single get is.

06Designing good keys

  • The key is the only way to find data, so key design is the schema of a key-value store.
  • Use a structured naming pattern such as user:42:profile to group related data and avoid collisions between types.
  • Make keys predictable: if the application can build the key from data it has, one lookup suffices.
  • Composite keys add ordering: DynamoDB's partition key plus sort key lets you fetch all orders for a user sorted by date.
  • The partition key decides placement; the sort key decides order inside the partition.
  • Keep keys and values small — large values cost network time and replication bandwidth, and long keys cost memory across millions of entries.
  • Prefer user:42:profile over a name that repeats the whole application hierarchy.

07Expiration and eviction

  • Much of the data is temporary: sessions expire, caches go stale, rate windows pass.
  • TTL lets the store delete a key automatically, so the application does not need a cleanup job.
  • Eviction is what happens when memory fills and something must go.
  • LRU evicts the least recently used keys, which suits general caches.
  • LFU evicts the least frequently used, which suits a stable set of popular keys.
  • volatile-* policies evict only keys that have a TTL, so permanent keys survive.
  • noeviction rejects new writes instead, which is what a primary store should do rather than silently lose data.
  • Policy choice follows directly from the cache-versus-source-of-truth question.

08Scaling with partitioning

  • One machine eventually cannot hold all keys or serve all requests, and keys are independent, so they partition naturally.
  • Hash modulo N is the simplest scheme: node = hash(key) % N.
  • Its flaw is resharding: changing N remaps most keys, so adding one node moves a large share of the data.
  • Consistent hashing places nodes and keys on a ring; a key belongs to the next node clockwise.
  • Adding a node then moves only the keys in its arc, not the whole key space.
  • Hash slots take a related approach: divide the key space into fixed slots and assign groups of slots to nodes.
  • Redis Cluster uses this idea with a fixed slot count, so rebalancing moves slots rather than rehashing every key.
  • Keys that must be operated on together can be forced into one slot with a hash tag: only the part inside braces is hashed.

09Replication and consistency

  • Partitioning spreads load, but a failed node makes its keys unavailable, so each partition is replicated.
  • Primary-replica replication sends writes to one primary that copies to followers; on failure a replica is promoted.
  • Reads from replicas may lag, so a read can return an older value.
  • Leaderless replication sends a write to several replicas at once and uses quorums.
  • With N replicas, W write acknowledgments, and R read responses, R + W > N guarantees the read set overlaps the newest write.
  • Lower W and R give faster responses and weaker consistency; with both at one, a read can easily miss the write.
  • Consensus systems such as etcd run Raft, where a majority must agree before a write commits, so reads see the latest committed value.
  • The right model depends on the data: a stale product page is harmless, a stale lock owner or permission check is not.

10Limitations

  • You can look data up efficiently only by its key.
  • A store holding profiles keyed by user id cannot answer all users in India; it has no idea what is inside the values.
  • The workaround is a second key you maintain yourself, such as country:India pointing at a list of user ids.
  • That index is now application-owned: a user moving countries must update both keys in one logical step.
  • There are no joins: data from two keys is fetched separately and combined in the application.
  • Transactions are limited: often only single-key atomic operations, sometimes limited multi-key transactions, and rarely anything like relational semantics.
  • So a key-value store is excellent at one access pattern and poor at everything else.
Good fitPoor fit
Get a session by session idFind sessions by browser or city

11Hot keys

  • Partitioning balances traffic across keys, not within one key.
  • If a celebrity posts and millions of users request that data, every request maps to the same partition and one node saturates.
  • The rest of the cluster can be idle while that node is overloaded.
  • Local cache: keep extremely popular values in a small in-process cache so most requests never reach the store.
  • Key splitting: replicate a hot key across several keys and pick one at random per read.
  • Hot counters can be split into bucket keys and summed when the total is needed.
  • Read replicas spread read traffic for that partition across machines.
  • The design lesson is explicit: sharding does not fix a single hot key; it needs its own strategy.

12The landscape, and when to use one

  • Redis and Memcached are the classic in-memory choices, the first with rich data structures and optional persistence.
  • DynamoDB is a managed, durable key-value and document store built for predictable performance at scale.
  • RocksDB is an embeddable storage engine used inside other databases rather than as a standalone server.
  • etcd is a strongly consistent store used for configuration, service discovery, and coordination.
  • They share one model but differ sharply on memory, durability, and consistency — so compare those properties, not the label.
  • Choose one when you always know the key, need very low latency, and need to scale many simple reads and writes.
  • Do not choose one when you must filter by value, join related records, or run ad hoc reports.
  • Most production systems combine it with a relational source of truth, using the key-value store for the hottest paths.

↔Trade-offs to say out loud

  • In-memory storage gives the lowest latency but costs more per gigabyte and loses data on restart unless persisted.
  • Snapshots restart quickly but can lose recent writes; append-only logging is safer but slower to recover.
  • Opaque values keep the store simple and fast but make value-based queries impossible.
  • TTL removes stale data automatically but means the application must tolerate a cache miss at any time.
  • LRU eviction keeps recent keys but can drop a rarely read key that is expensive to recompute.
  • Consistent hashing minimizes data movement on resharding but adds ring management and virtual nodes.
  • Quorum reads and writes are tunable per request but you must reason about R, W, and N for each use case.
  • Leaderless replication keeps writes available during node loss but can produce conflicting versions that need resolution.
  • Consensus replication gives strong consistency but needs a majority, so it is unavailable when quorum is lost.
  • Key duplication for secondary indexes enables lookups by another attribute but moves index maintenance into the application.

?Interview questions

Answer aloud before opening the outline.

1. What is a key-value store?

A database that stores a value under a unique key and exposes a minimal interface: put, get, delete. The store usually treats the value as an opaque blob, so lookups are fast and simple but limited to exact key access.

2. Why is it a good fit for sessions?

Session access is always the same lookup by session id, with no joins, filters, or reports. A key-value store answers that in one hop, scales horizontally by key, and lets any application server serve any user, which is exactly what stateless app tiers need.

3. Walk through cache-aside.

Read the cache; on a hit return the value. On a miss, read the source of truth, write the result back with a TTL, and return it. The trade-off is freshness: until expiry or invalidation, the cached value can be older than the database.

4. In-memory or persistent: how do you decide?

Ask whether the data can be rebuilt. A cache can live purely in memory because losing it only costs a miss. If the data is the source of truth — configuration, sessions that must survive, counters that matter — choose a durable store or enable persistence with an explicit durability setting.

5. Why must a rate-limit counter increment atomically?

If the application reads the counter, decides, then writes it back, two concurrent requests can both read the same value and both be allowed. An atomic increment at the store closes that window, so the limit holds under concurrency.

6. What does the internal data structure change?

A hash table gives constant-time point lookups but cannot serve range or prefix queries. An LSM tree or B-tree keeps keys sorted, so it supports range scans at the cost of slightly more work per lookup or per write. That decides whether user:42: prefix scans are even possible.

7. How should keys be designed?

Use a structured, predictable pattern like entity:id:field so the application can construct the key without a lookup, collisions between data types are impossible, and related keys group together. Keep keys and values small, and add a sort key where ordered access inside a partition is needed.

8. What is the difference between TTL and eviction?

TTL is a per-key expiry the application sets deliberately, so the data disappears on schedule. Eviction is the store's reaction to memory pressure, governed by a policy such as LRU or LFU. One models data lifetime; the other models running out of room.

9. Why does hash modulo N fail when you add a node?

Because N changes, so almost every key's hash % N points somewhere new. Going from four nodes to five remaps the large majority of keys, forcing a mass migration. Consistent hashing and hash slots move only a fraction of the data instead.

10. Explain R + W > N.

With N replicas, a write waits for W acknowledgments and a read waits for R responses. If R + W exceeds N, the read set and the newest write set must overlap in at least one replica, so the reader can see the latest version. Smaller W and R are faster but can miss the write.

11. What is a hot key and how do you fix it?

It is one key receiving so much traffic that its owning node saturates while the cluster is idle. Fixes include caching the value locally in the application, splitting the key into several copies or buckets and choosing one per read, and adding read replicas for that partition.

12. When is a key-value store the wrong choice?

When you need to filter or search by values, join related records, or run ad hoc reports. The key is the only efficient access path, so any other question means a full scan or an application-maintained index. A relational or document store fits those needs better.

!Traps

  • Using a cache-only store as the source of truth and discovering the data loss on the first restart.
  • Filtering by value and assuming the store will do it efficiently, when it can only scan.
  • Leaving a large key-value pair unpaginated, then paying network and replication cost on every read.
  • Choosing noeviction for a cache and then rejecting writes when memory fills.
  • Adding a node under hash-modulo partitioning and triggering a near-total remap.
  • Sharding a hot key and expecting partitioning to spread one key's load.
  • Reading from a replica for a flow that must reflect the user's own last write.
