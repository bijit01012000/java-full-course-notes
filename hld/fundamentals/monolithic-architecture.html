In one lineA monolith builds, deploys, and runs every feature as one unit — the simplest way to start, but its coupling, shared releases, and shared process become the constraints as the system and the team grow.
Monolith
An application whose features are built, packaged, and deployed as a single artifact and run inside one process.
Deployment unit
The boundary that defines a monolith: everything that must be rebuilt and released together, regardless of how the code is organized internally.
Modular monolith
A single deployable application whose code is split into business-domain modules with explicit public interfaces and owned tables.
Big ball of mud
A codebase where modules reach into each other's internals so freely that no one can predict what a change will break.
Tight coupling
A dependency on another module's internal methods, tables, or data shapes rather than on a stable public contract.
All-or-nothing scaling
Scaling the entire application because one workload inside it is under heavy load, wasting capacity on the parts that are idle.
Fault isolation
The degree to which a failure in one component can be contained so that other components keep serving requests.
Strangler fig pattern
Incrementally routing pieces of functionality to new services until the old system can be switched off, instead of rewriting everything at once.
In-process call
A direct function or method invocation inside one runtime, with no network hop, serialization, or remote failure mode.

01Where most applications begin

A new e-commerce product needs accounts, a catalog, a cart, orders, and payments. The obvious first version puts all of it in one application.

  • One codebase, one build, one deployment, and one database behind it is the natural starting shape.
  • Sign-up is handled by the user module, checkout by the order module, but both live in the same program.
  • This is how many applications start, including some that later serve very large user bases.
  • Starting with services forces you to commit to boundaries before you understand the domain.
  • The real question is not whether to start monolithic, but how long the simplicity holds.
  • Growth in traffic, code size, and headcount each attack a different monolith advantage.

02What makes an application monolithic

The defining trait is deployment, not code quality: a monolith is one deployable unit even when its code is neatly modular.

  • Modules may exist — users, catalog, orders, payments — but they are compiled or packaged into one artifact.
  • They run in the same process and call each other with ordinary function calls.
  • They usually share one database, which is what enables simple transactions later.
  • Changing a single line in payments forces a rebuild and redeploy of the entire application.
  • A well-designed monolith can have clear modules and clear ownership; a badly designed one is tangled code in one process.
  • Because the code can be clean or messy, monolith alone says nothing about maintainability.

03How a request flows through a monolith

  • A user clicks Place Order; the request reaches the order handler in the application.
  • The order code calls the inventory module to verify stock, then the payments module to charge the card.
  • The order row is written to the shared database and inventory is decremented in the same transaction.
  • Every step is a function call in one process: no network hop, no serialization, no partial remote failure.
  • If saving the order fails, the stock change rolls back with it — atomicity comes for free.
  • A distributed version of the same workflow needs sagas, compensations, and idempotent retries.
  • This transactional simplicity is the strongest technical argument for a monolith.
Client sends Place Order→Order handler validates request→Inventory module checks and reserves stock→Payments module charges the card→Order and stock written in one transaction→Commit and return confirmation
The whole flow succeeds or fails as one database transaction — a guarantee that is expensive to reproduce across services.

04The layered structure

Most monoliths organize code into technical layers, with requests flowing down and responses flowing back up.

  • The presentation layer accepts HTTP requests and renders responses through controllers or views.
  • The business logic layer holds rules such as discount calculation and cancellation eligibility.
  • The data access layer reads and writes the database.
  • Larger systems split business logic into an application layer (use-case coordination) and a domain layer (rules).
  • The data access layer often becomes an infrastructure layer that also talks to queues and external APIs.
  • Layering separates technical roles, not business capabilities — order and payment logic can still share one layer.
LayerResponsibilityExamples
PresentationAccept requests and return responsesControllers, REST endpoints, views
ApplicationCoordinate use cases and workflowsCheckout flow, refund workflow

InfrastructureTalk to databases and external systemsRepositories, queue clients, payment clients

05Why monoliths work well

  • Simple development: one repository to clone, one application to run locally, one place to search while debugging.
  • Simple deployment: build one JAR or container image and release it; no cross-service version coordination.
  • Easier testing: an end-to-end test can start the whole app and exercise a complete user journey.
  • Performance: in-memory calls avoid network round trips, serialization, and remote failure handling.
  • Data consistency: one database gives transactions, joins, and foreign keys without distributed coordination.
  • Cheap refactoring: renaming a method or moving a class is one commit verified by the compiler and tests.
  • For a small team building a new product, these benefits usually outweigh the drawbacks.

06Scaling a monolith

A monolith can scale with the same techniques as any web application; the constraint is that every copy carries every feature.

  • Vertical scaling: move to a bigger machine with more CPU and memory.
  • Horizontal scaling: run several identical copies behind a load balancer; any copy can serve any request.
  • Horizontal scaling only works if the app is stateless, with sessions and shared data in a database or cache.
  • On the data side, add read replicas, caching, and proper indexing.
  • Move slow work such as email or report generation to background workers so it does not hold request threads.
  • A well-built monolith can serve a very large number of users before architecture becomes the limit.
  • The first real limits are usually team coordination and release risk, not raw server capacity.

07The codebase keeps growing

  • A successful product can grow from a small codebase to over a million lines and from a handful of engineers to dozens.
  • Builds take longer, so the feedback loop between commit and test result stretches.
  • The full test suite may take tens of minutes, so developers stop running it locally.
  • New engineers need weeks to understand how the pieces fit together.
  • None of this breaks the application, but it steadily reduces how fast the team ships.
  • Slow feedback encourages batching changes into larger pull requests, which makes each change riskier.
  • Codebase size is a coordination cost, not a runtime problem.

08Tight coupling and the big ball of mud

The bigger long-term problem is coupling: nothing in a single process stops one module from reaching directly into another.

  • A marketing report needs order data, so it queries the orders table directly or calls an internal orders method.
  • The feature ships fast, but marketing code now depends on the internal details of the orders system.
  • Repeated across hundreds of features, these shortcuts form a dense web of hidden dependencies.
  • Changing the shape of the orders table can then break reporting, shipping, and invoicing at once.
  • This is the classic big ball of mud: small changes feel risky because the blast radius is unknown.
  • Coupling is not caused by having one codebase; it is caused by shortcuts nobody blocked.
  • The usual fix is the modular monolith, not necessarily microservices.

09Shared releases and all-or-nothing scaling

Two costs come directly from shipping one unit: releases carry everyone's changes, and scaling applies to the whole application.

  • A one-line search fix still requires rebuilding, testing, and redeploying the whole application.
  • That release also contains whatever payments, orders, and catalog merged that week.
  • If any included change is faulty, the entire release may need to be rolled back.
  • Teams respond by coordinating release trains, which makes releases rarer and each one larger.
  • Larger releases are riskier because more independent changes fail together.
  • Feature flags, canaries, and fast rollbacks reduce the risk but do not change the shared unit.
  • On the scaling side, a CPU-heavy workload such as image resizing forces you to duplicate the entire app.
  • Each copy still needs memory for catalog, cart, and checkout even though only image processing is busy.

The worker-pool middle ground

  • Push heavy jobs onto a queue and run a separate pool of worker processes from the same codebase.
  • Only the workers scale, so the cost tracks the workload that is actually hot.
  • This keeps one deployment while removing the worst all-or-nothing scaling effect.
  • It does not fix release coupling, shared process failure, or language lock-in.

10Weak fault isolation

  • All modules share one process, so a fault in one module can take down the rest.
  • A memory leak in recommendations slowly consumes the heap until the process crashes.
  • The crash also removes login, checkout, and payments, which were healthy the whole time.
  • A slow query can exhaust the shared database connection pool for every module.
  • A slow external API can tie up all request threads, so unrelated endpoints stop responding.
  • Timeouts, bulkheads, and resource limits help, but the modules are never fully isolated.
  • The blast radius of any defect is effectively the whole application.

11Technology lock-in

  • A monolith is usually built with a single language and framework, which keeps conventions consistent early on.
  • A machine-learning feature may need Python libraries while the core is Java, which is awkward inside one process.
  • Framework major upgrades may require testing and updating a million lines together, taking months.
  • Shared runtime and dependency versions force unrelated teams onto the same upgrade schedule.
  • A full rewrite is rarely the answer; extract only the specialized workload as a separate service.
  • This keeps the stable core in place while letting the new workload pick its own stack.

12The modular monolith

The modular monolith keeps one application and one deployment but organizes code around business domains.

  • Modules are business capabilities such as users, catalog, orders, and payments, not technical layers.
  • Each module exposes a small public interface; other modules must not import its internals.
  • Modules own their own tables, so shipping asks orders for data instead of querying the orders table.
  • Folder structure follows business areas first, with layers inside each module.
  • Build rules or architecture tests enforce boundaries, for example failing a build if anything outside orders imports orders internals.
  • Tools such as ArchUnit for Java and Packwerk for Ruby automate these checks.
  • A clean boundary makes later extraction into a service a small step instead of a data-migration project.
You get most monolith benefits while preventing the gradual slide into a big ball of mud.

13Monolith vs microservices, and when to split

  • Microservices run each business capability as its own service with its own deployment and usually its own database.
  • They enable independent deploys, per-service scaling, and stronger fault isolation.
  • They also add network calls that can fail, sagas for cross-service transactions, service discovery, and distributed tracing.
  • A monolith trades independent scaling and deployment for simplicity; microservices trade simplicity for independence.
  • Neither is better in general, and large successful monoliths exist — Shopify runs a large modular Rails monolith.
  • Split when multiple teams are blocked by shared releases, one part needs very different scaling, or failures keep spreading.
  • Even then, a modular monolith or extracting a few hot parts is often enough.

Leaving safely with the strangler fig

  • Avoid a full rewrite: it takes years while the business keeps changing the old system.
  • Extract one capability, such as notifications, as a new service and route those requests to it.
  • Once stable, delete the old code path and repeat with the next capability.
  • Extraction is far cheaper when the module already has a clean boundary and owns its tables.
Pick one capability with a clean seam→Build the new service beside the monolith→Route that traffic to the new service→Verify behaviour and remove the old code→Repeat for the next capability

↔Trade-offs to say out loud

  • Single deployment makes releases and testing simple but couples every team to one release train and one rollback decision.
  • In-process calls are fast and reliable but cannot be scaled or deployed independently per module.
  • One shared database gives ACID transactions and joins but lets any module couple to any table.
  • Horizontal app scaling adds capacity but duplicates every feature in every copy, including idle ones.
  • Modular monolith keeps operational simplicity and clean boundaries but requires tooling and discipline to enforce them.
  • Microservices improve independent scaling and fault isolation but add network failures, sagas, discovery, and tracing.
  • Delaying the split avoids premature boundaries but accumulates coupling that makes later extraction expensive.
  • Extracting one workload fixes the hot spot cheaply but leaves the rest of the shared release and failure domain intact.

?Interview questions

Answer aloud before opening the outline.

1. What actually makes an application a monolith?

It is built, packaged, and deployed as one artifact and runs in one process, usually against one database. Code organization does not decide it: a clean modular codebase and a tangled one are both monoliths if they ship as a single unit.

2. Why do so many systems start as monoliths?

Because the first version has one team, an unclear domain, and a need to ship quickly. One repo, one deploy, in-process calls, and real database transactions remove a large amount of coordination and infrastructure work that would otherwise slow the team down.

3. Walk through a request inside a monolith.

The order handler receives Place Order, calls the inventory module to reserve stock, calls payments to charge the card, and writes the order. All of it is function calls in one process, and the order write plus stock decrement commit in a single database transaction, so a failure rolls both back.

4. How does a monolith scale?

Vertically with a bigger machine, and horizontally by running identical stateless copies behind a load balancer. Data-side techniques are the same as elsewhere: caching, read replicas, indexes, and background workers for slow jobs. The limitation is that every copy contains every feature.

5. What is all-or-nothing scaling?

When one workload, such as image processing, is CPU-heavy while the rest is light, you cannot scale only that workload. You run more copies of the entire application, each sized for the full feature set, so you pay for capacity most of the system does not use. A queue plus a worker pool from the same codebase is the usual middle ground.

6. Why is deployment risk higher in a monolith?

Every change ships together with every other team's merged work, so one faulty change can force a rollback of the whole release. Teams then coordinate release schedules, which makes releases rarer and larger, and larger releases are riskier still. Canaries and flags reduce but do not remove the coupling.

7. How does a monolith fail?

Because modules share a process and resource pools, one memory leak, slow query, or slow downstream API can consume all threads or connections. Healthy modules such as login and payments then fail too. Timeouts and limits reduce the damage but cannot isolate modules the way separate processes can.

8. Is a monolith always a big ball of mud?

No. Coupling comes from unblocked shortcuts such as one module querying another's tables, not from having a single codebase. A modular monolith with public interfaces, owned tables, and architecture tests keeps boundaries intact and stays maintainable for years.

9. What is a modular monolith and what does it cost?

One deployable application organized by business domain, where each module exposes a narrow interface and owns its tables. It keeps simple development and deployment, but the boundaries are conventions that must be enforced with build rules or architecture tests, and a single process still limits fault isolation.

10. When should you move from a monolith to microservices?

When real pain appears: teams are blocked by shared releases, one capability needs very different scaling, failures in one area keep affecting everything, or a workload needs another runtime. Clear, stable module boundaries are the precondition, not the reward.

11. How do you migrate safely?

Use the strangler fig pattern: choose one capability with a clean seam, build it as a service, route that traffic to it, verify, delete the old path, then repeat. The application keeps serving users throughout, and you can stop after extracting the few parts that actually hurt.

12. Why extract modules before extracting services?

If every module reads every table, pulling one out becomes a long data migration with unclear ownership. Once a module owns its tables and exposes an interface, the extraction is mostly wiring and traffic switching.

!Traps

  • Judging a monolith by code style instead of by its deployment unit.
  • Starting with microservices before the domain boundaries are understood.
  • Calling a system modular while every module still reads every table.
  • Assuming a monolith cannot scale, when the real limit is team coordination and release risk.
  • Scaling the whole application to fix one hot workload instead of isolating it.
  • Planning a big-bang rewrite instead of incremental extraction.
  • Extracting services without first establishing clean module boundaries and table ownership.
