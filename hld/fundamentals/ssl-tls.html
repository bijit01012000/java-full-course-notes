In one lineTLS turns an untrusted network into a channel that is private, tamper-evident, and bound to a verified server identity — confidentiality, integrity, and authentication for data in transit.
TLS
Transport Layer Security: the protocol behind HTTPS that encrypts and authenticates traffic between two endpoints. SSL is its obsolete predecessor.
Handshake
The negotiation at the start of a connection where both sides agree on versions and algorithms, authenticate, and derive shared session keys.
Cipher suite
The named combination of key exchange, authentication, bulk encryption, and hashing algorithms used by a connection.
Certificate
A signed X.509 document binding a public key to an identity such as a hostname, valid for a defined period.
Certificate authority (CA)
An entity whose certificate is trusted by clients and who signs the certificates of servers.
Chain of trust
The path from a server's leaf certificate through intermediates to a root CA that the client already trusts.
SAN
Subject Alternative Name: the certificate field listing the hostnames and IPs the certificate is valid for.
Forward secrecy
A property of ephemeral key exchange where compromise of the server's long-term key does not decrypt past sessions.
mTLS
Mutual TLS: both client and server present certificates, so each side authenticates the other.
HSTS
HTTP Strict Transport Security: a response header that tells browsers to use HTTPS only for a host for a period of time.

01The problem with plain HTTP

Connect to café Wi-Fi and log in to a website over HTTP. The request passes through the router, the ISP, and several other networks before it reaches the server.

  • Every machine on that path can read the request, including credentials, session cookies, and personal data.
  • Reading is not the only risk: an attacker in the middle can modify the response — injecting scripts, changing a payment amount, altering content.
  • An attacker can also impersonate the site entirely with their own server and collect the credentials directly.
  • Plain HTTP gives the client no way to detect any of these attacks; there is no integrity check and no identity proof.
  • TLS addresses all three at the transport layer, so the application protocol does not have to solve them itself.
  • The threat model includes passive eavesdropping and active man-in-the-middle attacks, not just curious network operators.
Client→Coffee-shop Wi-Fi→ISP and transit networks→Server
A padlock means the connection is encrypted to a certificate-validated host — not that the site is honest, and not that data is safe at rest.

02The three guarantees

  • Confidentiality: nobody on the path can read the payload; it is encrypted with keys only the endpoints know.
  • Integrity: nobody can change data without detection; each record is authenticated, and a modified record is discarded.
  • Authentication: the client is sure it is talking to the real server, proven by a certificate chaining to a trusted CA.
  • Confidentiality without authentication is useless: you could be encrypting your password to the attacker.
  • Integrity is checked per record, so tampering or reordering breaks the connection rather than silently corrupting data.
  • By default authentication is one-sided — the client verifies the server. mTLS adds verification in the other direction.
  • TLS also provides replay protection through sequence numbers and fresh per-session keys.

03Where TLS sits

  • TLS runs above TCP and below the application protocol: HTTP, SMTP, the PostgreSQL wire protocol, gRPC, and others.
  • HTTPS is simply HTTP over TLS; HTTP/2 and HTTP/3 assume TLS, and QUIC builds TLS into the transport.
  • Databases, message brokers, caches, and internal APIs all support TLS, and internal traffic deserves the same protection as public traffic.
  • A service mesh terminates and originates TLS in a sidecar, so applications get encryption and identity without code changes.
  • The old name SSL persists, but SSLv2 and SSLv3 are broken and must be disabled; TLS 1.2 and 1.3 are the usable versions.
  • TLS adds handshake round trips, CPU for cryptography, and certificate operations; resumption and connection reuse amortize that cost.
  • It protects data in transit only — not data at rest, not data in logs, and not a compromised endpoint.

04The handshake, conceptually

The handshake is where the two sides agree on parameters, authenticate, and create the keys used for the rest of the connection.

  • The client sends a ClientHello: supported TLS versions, cipher suites, a random value, the SNI hostname, and a key share.
  • The server replies with ServerHello, its chosen parameters, its key share, and its certificate chain.
  • The client validates the chain, the hostname, the validity dates, and the certificate's intended usage before trusting anything.
  • Both sides derive the same session keys from the key exchange; the certificate is what binds those keys to the server's identity.
  • Finished messages prove each side derived the same keys and saw the same handshake transcript, catching tampering.
  • Only after the handshake does application data flow, encrypted with fast symmetric ciphers.
  • Session resumption skips most of the handshake using a pre-shared key from an earlier session.
ClientHello→ServerHello + certificate + key share→Verify certificate chain→Derive session keys→Finished→Encrypted application data
A full TLS 1.3 handshake takes one round trip; TLS 1.2 takes two. Resumption can make it zero round trips for repeat visitors.

05Key exchange and forward secrecy

  • The two sides must agree on a shared secret without ever sending it over the network.
  • With ephemeral Diffie-Hellman (DHE/ECDHE), each session generates fresh key pairs; the shared secret is derived, not transmitted.
  • Forward secrecy means that stealing the server's long-term private key later does not decrypt sessions recorded earlier.
  • Static RSA key transport — the client encrypts a secret with the server's public key — has no forward secrecy and is removed from TLS 1.3.
  • Asymmetric cryptography is used only for authentication and key agreement; bulk data uses fast symmetric ciphers such as AES-GCM or ChaCha20-Poly1305.
  • Weak parameters (small DH groups, legacy curves) undermine the exchange even when the protocol version is current.
  • Session keys are per-connection, so one compromised session does not expose others.
Key exchangeForward secrecyStatus
ECDHE (ephemeral)YesPreferred in TLS 1.2 and required in TLS 1.3
DHE (ephemeral)YesAcceptable, but slower; needs strong parameters
Static RSA transportNoDeprecated and removed in TLS 1.3

06Certificates and the chain of trust

  • A certificate binds a public key to an identity and is itself signed by a CA.
  • Key fields: subject, SAN (the hostnames it is valid for), issuer, validity window, public key, key usage, and the CA's signature.
  • Browsers and operating systems ship a trust store of root CAs; the server sends its leaf plus intermediates, and the client builds a path to a trusted root.
  • The leaf certificate must match the hostname the client requested — in practice via SAN, not the legacy Common Name field.
  • The current time must fall inside the validity window; expiry is one of the most common causes of self-inflicted outages.
  • Revocation is handled with CRLs and OCSP, and increasingly by issuing short-lived certificates so exposure windows stay small.
  • The private key must stay on the server or in an HSM; a leaked key plus a valid certificate allows undetectable impersonation.
Chain elementRoleWho holds it
Root CAAnchor of trust, pre-installed in clientsBrowser and OS trust stores
Intermediate CAIssues leaf certificates, isolates the rootSent by the server as part of the chain
Leaf certificateIdentifies this specific serverThe server
Private keyProves ownership of the certificateThe server or an HSM, never shared

07TLS 1.2 vs TLS 1.3

  • TLS 1.3 cuts a round trip from the full handshake and encrypts more of the handshake, including the certificate.
  • It permits only AEAD ciphers and ephemeral key exchange, so forward secrecy is mandatory rather than optional.
  • Legacy building blocks — static RSA, CBC-mode ciphers, RC4, 3DES, custom DH groups — are removed rather than disabled by configuration.
  • TLS 1.2 still works but needs deliberate configuration: modern ECDHE suites, AEAD ciphers, and weak options turned off.
  • TLS 1.3 has built-in downgrade protection; with 1.2, version negotiation needs care and old versions must be disabled.
  • 0-RTT early data in TLS 1.3 reduces latency but is replayable, so it should be limited to idempotent requests.
  • Both versions are acceptable in production; the real risk is old versions, weak ciphers, and stale certificates.

08Termination, re-encryption, and where trust ends

Where TLS terminates determines who can read the traffic and which controls can inspect it.

  • Edge termination at a CDN or load balancer centralizes certificates, offloads crypto, and enables L7 routing, WAF, and caching.
  • After termination, traffic to the backend is plaintext unless it is encrypted again.
  • Re-encryption establishes a second TLS connection from the edge to the service, protecting traffic inside the network or cloud boundary.
  • Passthrough forwards encrypted bytes to the backend, preserving end-to-end encryption but preventing L7 inspection and host-based routing.
  • mTLS adds client certificates so both ends authenticate, which is the basis of zero-trust service identity.
  • Termination plus re-encryption is a common compromise: edge controls stay, and the internal hop is protected.
  • Whatever the mode, the application still needs to know the original scheme and client IP from trusted proxy headers.

Edge terminationCDN or load balancerSimple cert management, L7 controlsPlaintext inside the network
Termination + re-encryptionEdge and serviceEnd-to-end coverage with edge controlsDouble crypto, more certs to manage
PassthroughBackend onlyTrue end-to-end encryptionNo L7 routing, WAF, or caching

09Designing mTLS

  • Each workload receives a certificate whose identity is the service or workload, not a shared hostname.
  • The server verifies the client's chain and its identity; trusting any certificate from the CA is not enough.
  • Certificates should be short-lived and rotated automatically by the platform or service mesh.
  • mTLS authenticates the connection; it does not grant permissions by itself — pair it with RBAC or policy.
  • Workload identity standards such as SPIFFE give certificates a stable, verifiable name independent of IP addresses.
  • Certificate issuance must be tied to workload attestation; otherwise any process can request an identity.
  • Common failure: accepting any client cert signed by the internal CA, which turns mTLS into a formality.
Workload requests identity→Platform attests and issues short-lived cert→Client connects with cert→Server verifies chain and identity→Policy decision→Connection allowed
mTLS replaces network-location trust with cryptographic identity, which is why it is central to zero-trust designs.

10HSTS and browser-side hardening

  • HSTS tells the browser to use HTTPS only for a host for a given period, preventing downgrade attacks after the first visit.
  • The header is Strict-Transport-Security: max-age=...; includeSubDomains; preload; preload requires meeting browser list criteria.
  • Start with a short max-age, confirm every subdomain supports HTTPS, then raise it; removing HSTS is deliberately slow.
  • Always redirect HTTP to HTTPS, but remember the first redirect can itself be intercepted before HSTS is known.
  • Set cookies with Secure, and prefer the __Host- prefix so a cookie cannot be set over plaintext or for a parent domain.
  • Block or upgrade mixed content; one HTTP asset on an HTTPS page weakens the whole page.
  • HSTS does not replace a valid certificate or fix an application-level vulnerability; it only forces the secure transport.
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax; Path=/

11Certificate lifecycle and operations

  • Automate issuance and renewal, typically with ACME, and monitor expiry independently of the application.
  • Alert on expiry with enough lead time for a human to act; renewal failure is a classic avoidable outage.
  • Serve the complete chain, including intermediates — some clients fail where browsers quietly repair the path.
  • Deploy certificate and key atomically and reload without dropping live connections where the server supports it.
  • Keep an inventory with an owner for every certificate, including internal services and non-HTTP protocols.
  • After renewal, test with a real client and the actual hostname, not only by inspecting the load balancer configuration.
  • Have an emergency path for compromise: revoke, reissue, redeploy, and invalidate anything that trusted the old key.
Request certificate→Validate domain control→Deploy cert + key→Reload listeners→Verify with a real client→Monitor expiry
Short-lived certificates reduce exposure but only work if issuance and rotation are fully automated.

12Failure modes and diagnosis

  • Expired certificate: browsers show an interstitial and API clients reject the connection; check notAfter first.
  • Hostname mismatch: the SAN does not cover the requested name, often because SNI and the Host header disagree.
  • Incomplete chain: works in browsers but fails in Java, Go, or curl clients that do not fetch missing intermediates.
  • Unknown CA: the client trust store lacks the internal root, common with private CAs and pinned environments.
  • Protocol or cipher mismatch: an old client meets a modern-only server policy, or the reverse after a hardening change.
  • TLS inspection proxies break pinning and mTLS and produce certificate errors inside corporate networks.
  • Clock skew invalidates validity checks; correct time synchronization matters on servers and clients.
  • Debug with openssl s_client -connect host:443 -servername host and compare the presented chain with what the client trusts.
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts
openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName

↔Trade-offs to say out loud

  • TLS everywhere gives confidentiality, integrity, and authentication but adds handshake latency, CPU cost, and a certificate lifecycle to operate.
  • Edge termination simplifies certificate management and enables L7 inspection but leaves traffic plaintext inside the network unless it is re-encrypted.
  • Re-encryption closes that internal gap but doubles cryptographic work and complicates debugging and latency analysis.
  • TLS 1.3 improves latency and handshake privacy but drops compatibility with old clients and makes some passive inspection harder.
  • mTLS gives strong workload identity but requires a CA, attestation, automatic rotation, and separate authorization logic.
  • HSTS with preload prevents downgrade attacks but is slow to undo and can lock users out of a misconfigured subdomain.
  • Passthrough preserves true end-to-end encryption but blocks WAF, caching, and host-based routing at the edge.
  • Short-lived certificates shrink compromise windows but turn an automation outage into a site-wide outage.

?Interview questions

Answer aloud before opening the outline.

1. What three problems does TLS solve?

Confidentiality (nobody on the path can read the data), integrity (tampering is detected), and authentication (the client knows it is talking to the real server). Confidentiality alone is useless without authentication, because you could be encrypting to an attacker.

2. Walk me through the TLS handshake.

The client sends a ClientHello with supported versions, cipher suites, SNI, and a key share. The server selects parameters, returns its key share and certificate chain. The client validates the chain, hostname, and dates, both sides derive session keys from the key exchange, and Finished messages confirm the transcript. Then application data flows encrypted. TLS 1.3 does this in one round trip.

3. How does a certificate prove a server's identity?

A certificate binds a public key to a hostname and is signed by a CA. The client builds a chain from the leaf through intermediates to a root in its trust store, then checks the hostname in the SAN and the validity window. If all checks pass, the key exchange is bound to that identity.

4. What is the chain of trust?

The path from the server's leaf certificate, through one or more intermediates, to a root CA the client already trusts. The server sends the leaf and intermediates; the client supplies the root from its trust store. A missing intermediate breaks clients that do not fetch it themselves.

5. What is forward secrecy and why does it matter?

It means each session uses an ephemeral key exchange, so a later compromise of the server's long-term private key cannot decrypt previously recorded traffic. It protects against retrospective decryption of captured data. TLS 1.3 mandates it; TLS 1.2 provides it only when ECDHE or DHE is used.

6. TLS 1.2 vs TLS 1.3?

TLS 1.3 removes legacy ciphers, requires forward secrecy, encrypts more of the handshake, and saves a round trip. TLS 1.2 can be secure but depends on correct configuration. The practical difference is fewer ways to misconfigure 1.3 — but old clients may force you to keep 1.2 enabled.

7. Where should TLS terminate in a system design?

Commonly at the edge (CDN or load balancer) to centralize certificates and enable L7 routing, WAF, and caching — then re-encrypt to the backend to avoid plaintext inside the network. Passthrough is right when end-to-end encryption is required and edge L7 features are not.

8. What is the difference between TLS termination and re-encryption?

Termination decrypts at the edge and forwards plaintext. Re-encryption decrypts at the edge and immediately opens a new TLS connection to the service. Re-encryption protects the internal hop; termination alone trusts the internal network.

9. What is mTLS and when would you use it?

Mutual TLS: both client and server present certificates and verify each other. Use it for service-to-service authentication in zero-trust networks, internal APIs, and device identity. It authenticates the connection only, so authorization still needs RBAC or policy.

10. What does HSTS do?

It tells the browser to use HTTPS only for a host for a period, preventing downgrade and stripping attacks after the first visit. With includeSubDomains and preload it covers the whole domain. It is hard to undo, so roll it out carefully.

11. A service works in the browser but fails from a Java client. Why?

Most likely an incomplete certificate chain: the server is not sending the intermediate, and browsers fetch or cache it while the Java trust store does not. Check the presented chain with openssl s_client. Other candidates are an untrusted private root or a hostname mismatch.

12. Why is a certificate expiry such a common outage?

Renewal is manual or monitored only by the team that owns the load balancer, so it fails silently until clients reject the connection. The fix is automated issuance, expiry alerts independent of the application, and an inventory that includes internal services.

13. What is 0-RTT and what is the risk?

TLS 1.3 early data lets a returning client send application data with the first flight, saving a round trip. That data is replayable by an attacker, so it should be limited to idempotent requests and never used for state-changing operations.

14. Does HTTPS protect data at rest or in logs?

No. TLS protects data in transit between two endpoints. Once it is decrypted, stored in a database, written to a log, or captured by an inspection proxy, TLS provides no protection — those need encryption at rest, redaction, and access control.

!Traps

  • Saying TLS provides confidentiality and forgetting authentication — encryption to an impersonator is worthless.
  • Treating the padlock as proof the site is trustworthy rather than proof of a validated certificate for that hostname.
  • Terminating TLS at the edge and calling the system end-to-end encrypted while the backend hop is plaintext.
  • Forgetting that TLS protects data in transit only, not data at rest, in logs, or in a compromised process.
  • Deploying a leaf certificate without the intermediate chain.
  • Assuming mTLS authorizes an action rather than only authenticating the connection.
  • Enabling HSTS preload before every subdomain supports HTTPS.
  • Keeping TLS 1.0/1.1 or CBC cipher suites enabled for compatibility and calling the deployment secure.
