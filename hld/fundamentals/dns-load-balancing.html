01Why DNS load balancing exists

A regional load balancer distributes requests among the servers behind it, but it cannot decide which region a user should reach, because that decision has to happen before the connection is made.

  • A single-region load balancer gives you no answer when the whole region fails.
  • Sending a user in Singapore to a data centre in Virginia adds round-trip latency to every request, including the TLS handshakes.
  • DNS is the first step of every connection: the client must resolve api.example.com to an address before it can connect.
  • Returning different addresses per user lets you steer traffic to the nearest or healthiest region.
  • Because it works at resolution time, DNS can express regional policy that no HTTP-layer device can apply.
  • It is also the cheapest global control plane available: no additional hop in the data path.
  • The trade-off is coarse control: you are choosing an address, not a server, and you cannot see the request.

02How a DNS lookup works

  • The client asks its configured recursive resolver for the name; the resolver does the walking.
  • The resolver checks its cache first, which is why a previously resolved name returns instantly.
  • On a miss it queries a root server, which points to the TLD servers, which point to the zone's authoritative nameservers.
  • The authoritative server returns the record, such as an A record for IPv4 or an AAAA record for IPv6.
  • The resolver caches the answer for the record's TTL and returns it to the client.
  • The client may cache it again, so several layers can hold a stale answer independently.
  • Every answer in this chain is a routing decision when the zone is configured for traffic management.
Client asks recursive resolver→Resolver cache miss→Root server referral→TLD server referral→Authoritative nameserver answers→Resolver caches for TTL→Client connects to the returned address

03Round-robin DNS

  • Publish several A records for one name and rotate the order in which they are returned.
  • Most clients try the first address, so rotation spreads connections across the pool over many lookups.
  • There is no state to maintain beyond the record list, and no extra infrastructure in the request path.
  • It balances lookups, not requests: one client that caches an answer sends all its traffic to one address.
  • Distribution is uneven whenever resolvers cache aggressively or client volumes differ wildly.
  • Removing an address does not take effect until caches expire, so failed endpoints keep receiving traffic.
  • It ignores capacity: every address gets an equal share regardless of how big the region behind it is.
Round-robin DNS is best treated as a coarse spread across equivalent endpoints, never as the only mechanism protecting a pool.

04Health checks and failover

  • A health-checked DNS service probes each endpoint and withdraws the address when the probe fails.
  • Withdrawal only helps once caches expire, so failover time is bounded by the TTL, not by the probe interval.
  • Probes must test the dependency path, not just whether a host answers on a port.
  • Flapping endpoints create flapping answers; require several consecutive failures and successes before changing state.
  • Keep a manual override so an operator can drain a region even when automated checks look healthy.
  • The check itself is a single point of failure: if the health service cannot reach endpoints, it may withdraw everything.
  • Never let DNS health checks be the only failover mechanism; the regional load balancer still needs its own.

05TTL is the real control knob

  • TTL decides how long resolvers and clients may reuse an answer, so it directly controls how fast changes propagate.
  • Long TTLs reduce query volume and improve resolution latency but slow failover and migrations.
  • Short TTLs make changes fast but increase resolver traffic and give caches less benefit.
  • Some resolvers enforce a minimum TTL, so a very low value may be ignored in practice.
  • Lower the TTL before a planned migration, wait at least the old TTL, then change the records.
  • Keep the old endpoint serving until the new TTL window has passed, otherwise in-flight cached clients break.
  • TTL is advisory: clients, proxies, and some ISPs may cache longer than you asked.

06Weighted and geographic routing

  • Weighted answers send a configured share of resolutions to each endpoint, which supports canaries and gradual regional ramps.
  • Weights are enforced per lookup, so a client that caches gets no re-weighting until its TTL expires.
  • Geographic routing maps a query's location to the nearest or designated region.
  • Location is usually inferred from the resolver's address, which may be far from the actual user.
  • EDNS Client Subnet can pass a truncated client subnet to the authoritative server for better accuracy, at some privacy cost.
  • Geographic routing also expresses policy: data residency, market-specific endpoints, and legally required local termination.
  • Defaults matter: always configure a fallback region for queries that match no rule.

07Latency- and proximity-based answers

  • Instead of static geography, some services measure which region actually responds fastest for a given resolver network.
  • The measurement is periodic and coarse, so it reacts to persistent differences rather than momentary jitter.
  • This handles asymmetric internet paths where the geographically nearest region is not the network-nearest one.
  • It still cannot see the individual request, so a slow request-type mix inside a region is invisible to DNS.
  • Combining latency data with health and capacity weights gives better results than any single signal.
  • Any latency-based policy needs a fallback for regions with too little measurement data.
  • Beware of using these controls during incidents: stale measurements can keep sending users to a degraded region.

08DNS alongside regional load balancers

DNS and load balancers solve different halves of the problem, and production systems use both.

  • DNS picks the region or entry point; the load balancer picks the server inside it.
  • The name typically points at a load balancer address, so backends can change without touching DNS.
  • The load balancer has per-request visibility, immediate health knowledge, and sub-second failover.
  • DNS has global reach, no data-path cost, and the only pre-connection view of the client.
  • Layering them means a regional failure is handled by DNS and an instance failure is handled by the balancer.
  • Using DNS for per-request balancing is a category error: it is too coarse and too cached.
  • A common pattern is DNS to a global anycast entry point, then a regional balancer behind it.
Client resolves api.example.com→DNS returns the nearest healthy region→Client connects to that region's load balancer→Load balancer chooses a healthy backend→Backend serves the request

09Limitations and failure modes

  • Caching defeats control: clients keep using withdrawn addresses until their TTLs expire.
  • The resolver's location is a proxy for the user's location, and it is often wrong.
  • Clients may ignore the returned order and always pick the first or a random address.
  • There is no per-request signal, so DNS cannot react to a single slow backend or a hot tenant.
  • Long-lived connections never re-resolve, so a client may hold a dead region for hours.
  • Misconfigured health checks can withdraw a healthy region and cause a self-inflicted global outage.
  • DNS itself is a dependency: if resolution fails or is slow, nothing else can start.

10When to use DNS load balancing

  • Use it for multi-region entry: choosing which region a user connects to, and failing over between regions.
  • Use it for coarse traffic shaping such as canaries, blue-green cutovers, and gradual regional ramps.
  • Use it when you need no extra hop, no extra TLS termination, and no per-request state.
  • Do not use it as the only balancer for a pool of equivalent servers; a real balancer does that better.
  • Do not expect sub-second failover; treat DNS failover as a minutes-scale mechanism.
  • Always pair it with health checks, a low-but-not-zero TTL, and a client that retries on connection failure.
  • Document the fallback region and test the failover path on a schedule, because it is rarely exercised.

↔Trade-offs to say out loud

  • DNS balancing adds no data-path hop but cannot see requests or react per request.
  • Round-robin DNS is free and simple but balances lookups rather than load and ignores capacity.
  • Long TTLs reduce query volume and improve resolution speed but stretch failover to hours.
  • Short TTLs speed up changes but multiply resolver traffic and are often clamped anyway.
  • Geographic routing improves locality but depends on resolver location, which can be far from the user.
  • Health-checked DNS automates regional failover but adds a control plane that can withdraw a healthy region.
  • DNS plus a regional balancer gives global and per-request control at the cost of two systems to operate.
  • EDNS Client Subnet improves location accuracy but leaks part of the client's address to more parties.

?Interview questions

Answer aloud before opening the outline.

1. Why is DNS needed for load balancing at all?

Because a load balancer can only choose among servers behind it, and it cannot choose a region before the client connects. DNS is the only step where a different destination can be selected per user, which is what makes multi-region routing possible.

2. How does round-robin DNS work?

You publish multiple A or AAAA records for one name and rotate the order in each answer. Clients typically try the first address, so lookups spread connections across the endpoints without any extra infrastructure.

3. Why is round-robin DNS not real load balancing?

It distributes lookups, not requests or work. A client that caches an answer sends all its traffic to one address, and every address receives an equal share regardless of capacity or current load.

4. What determines how fast DNS failover happens?

The TTL on the record and the behaviour of downstream caches. Even after a health check withdraws an address, clients keep using it until their cached answer expires, so failover is a minutes-scale mechanism unless TTLs are short.

5. How would you plan a migration between two addresses?

Lower the TTL well before the change, wait for the old TTL to elapse so caches hold the short value, then switch the record. Keep the old endpoint serving until the new short-TTL window has passed, then retire it.

6. What is wrong with using the resolver's IP to locate a user?

Recursive resolvers are often shared and centrally located, so many users appear to come from one place. A user in one country may be routed to a region near the resolver rather than near themselves.

7. How do DNS and a regional load balancer divide responsibilities?

DNS chooses the region or global entry point; the load balancer chooses the server inside that region. DNS handles region-level failure, and the balancer handles instance-level health with sub-second reaction.

8. What is EDNS Client Subnet and what does it cost?

It forwards a truncated client subnet in the DNS query so the authoritative server can answer more accurately than by resolver location. The cost is additional exposure of client addressing information to parties in the resolution path.

9. Why can long-lived connections break DNS failover?

A client only resolves the name when it opens a connection. An established connection or a pooled channel can stay pinned to a region that has since failed, so it never sees the updated DNS answer.

10. What health-check mistakes make DNS dangerous?

Probing only a port instead of the dependency path, flapping without consecutive-failure thresholds, and having no manual override. A false negative can withdraw a whole healthy region and turn a small fault into a global outage.

11. When would you choose DNS balancing over anycast?

When you need explicit per-region control, weighted ramps, or residency-based routing that you can express as policy. Anycast gives faster, automatic failover but gives you less control over which location a user reaches.

12. How do you make DNS-based failover testable?

Schedule regular game days that withdraw a region and verify that clients re-resolve and reconnect within the expected window. Also monitor resolution latency and answer correctness, since the failure path is otherwise never exercised.

!Traps

  • Calling round-robin DNS a load balancer when it only rotates lookups.
  • Relying on DNS for sub-second failover while using hour-long TTLs.
  • Forgetting that clients and resolvers may cache longer than the TTL you set.
  • Lowering the TTL at the same moment you change the record, so old caches still point at the old address.
  • Routing by resolver location and assuming it matches the user's location.
  • Adding geographic rules with no default fallback, so unmatched queries fail to resolve.
  • Trusting DNS health checks as the only failover mechanism for a region.
