API
Application Programming Interface: the defined way for one piece of software to communicate with another.
API contract
The agreed set of operations, input shapes, response shapes, and error behavior that clients can depend on.
Endpoint
A specific URL path plus HTTP method that a client calls to interact with a resource or trigger an operation.
HTTP method
The verb on a request (GET, POST, PUT, PATCH, DELETE) that tells the server what action is intended.
Header
Metadata sent with a request or response, such as Authorization, Content-Type, or Cache-Control.
Query parameter
Extra input appended to the URL after ?, typically used for filtering, paging, or sorting.
Request body
The payload carrying the actual data for methods like POST, PUT, and PATCH, usually JSON.
Status code
A three-digit number in the response that classifies the outcome as success, client error, or server error.
Public API
An API exposed to external developers, which needs documentation, authentication, rate limits, and a compatibility plan.
Partner API
An API exposed only to selected external companies or business partners under a specific agreement.

01Why APIs exist

Almost every system is made of pieces of software that need to talk to each other. APIs are how they do it.

  • A food delivery app calls one API for nearby restaurants, another to place an order, another to take payment, and another to track delivery.
  • Each of those capabilities is owned by a different system, often a different team, with its own database and deployment.
  • The app does not need to know how any of those systems work internally; it only needs to know how to talk to them.
  • APIs are the seams of a system: they define where one component ends and the next begins.
  • As a product grows, the number of API calls per user action grows faster than the number of features.
  • Even a monolith benefits from internal APIs because they force explicit boundaries between modules.

02What an API is

  • An API defines how one piece of software can communicate with another; it is an interface, not an implementation.
  • It is not the same as a UI: a UI is for humans, an API is for other software, even when both sit on top of the same backend.
  • It is also not the same as a protocol. HTTP is a transport; an API is the contract carried over it.
  • The same contract can be exposed over different transports, such as HTTP for browsers and gRPC for internal services.
  • APIs are consumed by web apps, mobile apps, command-line tools, and other backend services alike.
  • The API is the product boundary: what callers can rely on, and what the owner promises to keep stable.
A useful test: if you can replace the entire backend without changing a single client, the API boundary was real.

03The API contract

At a high level, an API is a contract between two pieces of software. It tells the client what operations exist, what data to send, and what response to expect.

  • The contract names the operations: which actions a client is allowed to request.
  • It defines the input: required fields, types, formats, and which parts are optional.
  • It defines the output: the shape of the response and the meaning of each field.
  • It defines error behavior: which status codes and error bodies a client must handle.
  • A request such as GET /users/123 might return {"id": 123, "name": "Alice"}, and the client may rely on exactly those field names.
  • The client does not know or care whether that user came from a database, a cache, or another service.
  • If the contract changes, every client that depended on it is at risk, which is why contracts are versioned and documented.
GET /users/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"id": 123, "name": "Alice"}

04Clients and servers

  • The client is the application that sends the request: a web app, mobile app, CLI, or another backend service.
  • The server receives the request, performs work, and sends back a response.
  • The client always initiates in a request-response API; the server cannot push uninvited (that needs WebSockets, SSE, or webhooks).
  • Roles are per interaction, not per process: a service is a server to its callers and a client to its own dependencies.
  • One user action can fan out into many internal calls, so the user-visible latency is the sum along the slowest chain.
  • Every network hop can fail independently, so the client needs timeouts and error handling for each call it makes.
Client builds the request→Request crosses the network→Server authenticates and routes it→Server reads or writes data sources→Server returns a response→Client parses it or handles the error

05Anatomy of an API request

An HTTP API request has up to five parts. Not every request uses all of them, but they are the building blocks you will see repeatedly.

  • The HTTP method states the action: POST here means create or trigger processing.
  • The endpoint identifies the resource or operation, such as /orders.
  • The headers carry metadata: authentication, the format being sent, and the format expected back.
  • The query parameters add input to the URL, such as ?category=books&limit=20, and are typically used for filtering and paging.
  • The request body carries the actual payload for POST, PUT, and PATCH; a GET normally has none.
  • The same information can arrive in different places, so the contract must be explicit about where each field belongs.

06API endpoints

  • An endpoint is a specific URL a client can call to interact with a resource or perform an operation.
  • The path usually identifies the resource; the method says what to do with it.
  • GET /users/123, PATCH /users/123, and DELETE /users/123 share a path but are different operations.
  • Endpoints are the entry points into a service; a real backend may expose dozens or hundreds of them.
  • Good endpoint naming is consistent and resource-oriented, so learning one part of the API teaches you the rest.
  • An endpoint is a public promise: renaming one is a breaking change for every client that calls it.
EndpointWhat it means
GET /users/123Fetch user 123
POST /usersCreate a new user
PATCH /users/123Update part of user 123
DELETE /users/123Remove that user

07Anatomy of an API response

  • A response has a status code, headers, and optionally a body.
  • The status code is the machine-readable outcome; clients branch on it rather than parsing prose.
  • 2xx means the request worked, 4xx means the client sent something the server could not accept, and 5xx means the server failed.
  • Headers add metadata such as Content-Type and caching directives like Cache-Control.
  • The body is optional: a successful DELETE may return only a status code with no body.
  • A success status with an ambiguous body is a bug; the code and body must agree.
Status codeMeaning
200 OKThe request succeeded
201 CreatedA resource was created
400 Bad RequestThe request was invalid
401 UnauthorizedAuthentication is required
404 Not FoundThe resource was not found
500 Internal Server ErrorSomething went wrong on the server

08APIs hide implementation details

One client request can hide a cache lookup, a database query, a call to another service, and a machine learning model.

  • The client sees GET /recommendations; the backend may consult a cache, a database, a service, and a model.
  • Because none of that is in the contract, the backend can change storage, add caching, or split a service without touching clients.
  • This boundary reduces coupling and lets teams evolve and deploy independently.
  • The boundary is not absolute: latency, rate limits, and error modes still leak through and must be designed for.
  • Hiding internals does not mean hiding failure; the contract must still state what a timeout or partial failure looks like.
  • A leaky API exposes internal IDs, table names, or stack traces, which then become de facto contract.

09Public, private, and partner APIs

  • Public APIs are exposed to external developers, such as a payments or maps provider.
  • Public APIs need clear documentation, authentication, rate limits, and a careful plan for non-breaking change.
  • Private APIs, or internal APIs, are used only inside an organization, such as Order Service calling Inventory Service.
  • Internal does not mean informal: internal APIs still need owners, timeouts, stable shapes, and defined failure behavior.
  • Partner APIs are exposed only to selected external companies or business partners.
  • The difference is about who may call it, not about the underlying technology.
  • In large systems most APIs are internal, because services constantly talk to other services behind the scenes.

10What makes a good API

  • It is easy to understand: consistent naming and structure make one part predict the next.
  • It is predictable: the same input produces the same shape of output and the same class of errors.
  • It is hard to misuse: required fields are explicit, invalid combinations are rejected, and defaults are safe.
  • It gives clear errors: the response says what was wrong and what to do, instead of leaving the client guessing.
  • It handles growth: pagination, filtering, and rate limits exist before the dataset is large.
  • It is documented, often with a machine-readable spec such as OpenAPI, so clients can generate code and tests.
  • It changes carefully: backward compatibility is treated as a promise, not an afterthought.
A good API is a product with users. Its documentation, error messages, and deprecation policy are part of the interface.

11Evolving an API without breaking clients

  • Additive changes are usually safe: new optional fields, new endpoints, new enum values that clients tolerate.
  • Breaking changes include removing or renaming fields, changing types, tightening validation, and changing status-code semantics.
  • Version explicitly, either in the path (/v2/users) or in a header, so old and new clients can coexist.
  • Run an expand, migrate, contract sequence: add the new shape, move clients over, then remove the old one.
  • Announce deprecation with a timeline, emit warnings in responses, and monitor which clients still call the old surface.
  • Contract tests and a published schema catch accidental breakage before it reaches production.
  • Every version you keep alive is a maintenance cost, so version only when a compatible path is not possible.

↔Trade-offs to say out loud

  • Thin APIs are simple to learn but force clients into many round trips; rich APIs reduce calls but return data clients may not need.
  • Fine-grained endpoints are reusable and cacheable but multiply network calls; coarse-grained endpoints cut latency but couple the response to one screen.
  • Strict contracts make clients safe but slow the backend down; loose contracts move faster but break callers silently.
  • Public APIs create an ecosystem but every change becomes a compatibility negotiation with strangers.
  • Hiding implementation enables independent evolution but can hide latency and failure modes the client must still handle.
  • Versioning protects existing clients but doubles the surface to test, document, and operate.
  • Machine-readable specs improve tooling and validation but must be kept in sync with the real implementation.
  • Detailed error bodies speed up debugging but can leak internal structure or sensitive data if not sanitized.

?Interview questions

Answer aloud before opening the outline.

1. What is an API in one sentence?

A defined interface that lets one piece of software communicate with another, specifying the available operations, the data to send, and the response to expect. It hides the implementation behind the boundary.

2. What is an API contract and why does it matter?

The contract is the set of operations, input shapes, output shapes, and error behavior clients can depend on. It matters because clients are written against it, so any change to it is a change to every caller.

3. What are the parts of an HTTP request?

Method, endpoint, headers, query parameters, and an optional body. The method is the action, the endpoint identifies the resource, headers carry metadata, and the body carries data for POST, PUT, or PATCH.

4. What is the difference between an endpoint and a resource?

A resource is the thing being manipulated, such as a user; an endpoint is a URL plus method through which you manipulate it. GET /users/123 and DELETE /users/123 target the same resource through different operations.

5. Why are status codes important?

They give the client a machine-readable outcome without parsing the body. 2xx means success, 4xx means the client must fix the request, and 5xx means the server failed and a retry may be reasonable.

6. How does an API hide implementation details?

The client only sees the request and response shape. Behind the boundary the server can query a database, check a cache, call another service, or run a model, and can change all of that without breaking callers as long as the contract holds.

7. What is the difference between public, private, and partner APIs?

The difference is the audience, not the technology. Public APIs are open to external developers, partner APIs to selected companies, and private APIs to teams inside the organization. Each audience implies different documentation, auth, and compatibility obligations.

8. Why do internal APIs still need to be well designed?

They are called by other teams and services that cannot see the implementation, so they need stable shapes, owners, timeouts, and defined failure behavior. Sloppy internal APIs create the same outages as sloppy public ones, with less documentation.

9. What makes an API hard to misuse?

Explicit required fields, safe defaults, validation that rejects contradictory input, clear errors, and idempotent operations where retries are likely. A caller should not be able to cause silent corruption with a plausible request.

10. What is a breaking change, and how do you avoid one?

Removing or renaming a field, changing a type, tightening validation, or changing status-code meaning breaks existing clients. Avoid it by making additive changes, versioning when necessary, and running expand-migrate-contract with a deprecation window.

11. How would you design an API for a mobile screen that needs user, profile, and recent orders?

Either provide a coarse endpoint for that screen, or expose separate resources and let the client compose them. A coarse endpoint cuts round trips on mobile but couples the API to one screen; separate resources are more reusable but add latency.

12. What is the difference between an API and a protocol?

A protocol defines how bytes move and how a conversation is framed, such as HTTP or TCP. An API defines what operations exist and what the data means. The same API contract can be served over HTTP, gRPC, or a message bus.

13. How do you know your API design is good?

New developers can predict the next endpoint, clients need few round trips, errors are self-explanatory, retries are safe, and the backend can change internals without client releases. Usage metrics and support tickets confirm it.

!Traps

  • Treating the API as a thin wrapper over database tables, so internal schema changes leak into the public contract.
  • Using 200 OK for failures and putting the error only in the body, which breaks every standard client and monitor.
  • Returning internal identifiers, stack traces, or table names in error responses.
  • Adding required fields or tightening validation and calling it a compatible change.
  • Designing endpoints per screen so the API becomes a set of one-off RPC calls with no reusable resources.
  • Documenting the API only in prose, so the spec and the implementation drift apart.
  • Assuming an internal API needs no timeouts or failure contract because the caller is inside the company.
