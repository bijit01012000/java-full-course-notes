Forward proxy
An intermediary that acts on behalf of clients, forwarding their outbound requests to the internet and returning responses.
Reverse proxy
An intermediary that acts on behalf of backend servers, accepting client requests and forwarding them to the right internal service.

TLS termination
Ending the client's HTTPS connection at the proxy and forwarding the request to backends, centralizing certificates.
Request routing
Sending requests to different backends based on path, host, or headers, for example /users to the user service.

A reverse proxy specialized for APIs, adding authentication, rate limiting, and per-route policy.

A Kubernetes component that programs a reverse proxy to expose cluster services to external traffic.

Forwards TCP or UDP connections without reading the application payload.
Layer 7 proxy
Parses the application protocol, usually HTTP, and can decide using paths, headers, or hostnames.

Pinning a client to one backend, often implemented by a proxy cookie; useful for local state but harmful to balance.

01Two proxies, one question

When you open a website, the request does not always travel straight from browser to application server. Sometimes another server sits in the middle.

  • If the middle server acts on behalf of the client, it is a forward proxy.
  • If it acts on behalf of the backend servers, it is a reverse proxy.
  • Both forward traffic and both hide one side from the other; only the direction and intent differ.
  • The distinguishing question is not where the box sits but whose interests it represents.
  • A forward proxy sees outbound traffic leaving a client network.
  • A reverse proxy sees inbound traffic entering a service.
  • The same software, such as NGINX, can play either role depending on configuration.

02How a forward proxy works

  • The client is configured to send requests to the proxy rather than directly to the destination.
  • The proxy forwards the request to the destination server on the client's behalf.
  • The destination responds to the proxy, which relays the response to the client.
  • From the destination's point of view, the request appears to come from the proxy's address, not the client's.
  • The client's browser or OS must know about the proxy, usually through explicit configuration or a proxy auto-config file.
  • Because the proxy sits in the path, it can log, block, cache, or modify requests — which is both the feature and the risk.
  • HTTPS complicates inspection: without a trusted interception certificate, the proxy can see the destination but not the content.

Proxy vs VPN

  • Both can hide the client's IP address from the destination, which is why they get confused.
  • A proxy usually forwards traffic for specific applications or protocols.
  • A VPN typically creates an encrypted tunnel that carries broader network traffic from the device.
  • A proxy can be per-application; a VPN is usually system-wide.
  • Hiding an IP is not anonymity: the proxy operator can log connections, and sites can still recognize you via cookies, logins, or fingerprints.
Client sends request to the proxy→Proxy forwards to the destination server→Server responds to the proxy→Proxy returns the response to the client

03Why use a forward proxy

  • Privacy: the destination sees the proxy's address instead of the client's network address.
  • Access control: organizations block sites or restrict which external services employees can reach.
  • Monitoring and logging: outbound traffic passes one point, so requests and policy violations can be tracked.
  • Caching: repeated requests for the same resource can be served from the proxy, reducing bandwidth and latency.
  • Access through another network: a proxy can reach resources that are unavailable or restricted from the client's location.
  • Protocol bridging and header control: rewrite headers, add authentication, or normalize traffic before it leaves.
  • The common thread is control over outbound traffic from clients.
  • The cost is a central choke point, added latency, and a component that must be trusted with all that traffic.

04How a reverse proxy works

  • The reverse proxy sits in front of backend servers and accepts requests on their behalf.
  • The client talks to the proxy, often without knowing a proxy exists.
  • The proxy decides which backend should handle the request and forwards it.
  • The backend sends its response to the proxy, which returns it to the client.
  • From the client's perspective there is a single endpoint; the internal topology stays hidden.
  • Because it terminates the client connection, it can apply policy before any backend sees the request.
  • This is the shape used by web servers in front of app servers, API gateways, ingress controllers, and CDNs.
Client sends request to the proxy→Proxy chooses a backend→Proxy forwards the request→Backend responds to the proxy→Proxy returns the response

05Why use a reverse proxy

  • Traffic management: distribute requests across backends so no single server is overloaded.
  • TLS termination: handle certificates and encryption in one place instead of on every backend.
  • Caching: serve repeated responses without touching the backend, reducing load and latency.
  • Security and access control: hide backends from direct public access, enforce rate limits, filter requests, and require authentication.
  • Request routing: send /users to the user service and /payments to the payment service.
  • Connection management: absorb slow clients, buffer responses, and keep backend connections pooled.
  • Observability: one place for access logs, request ids, metrics, and tracing headers.
  • Caching personalized responses is dangerous: a cached copy of one user's data must never be served to another.

06Forward vs reverse proxy

The two roles share mechanics but differ in direction, trust boundary, and who operates them. This table is the one to reproduce in an interview.

  • A forward proxy is usually deployed at the edge of a client network; a reverse proxy at the edge of a service.
  • A forward proxy protects and controls clients; a reverse proxy protects and controls servers.
  • A forward proxy must be known to the client; a reverse proxy is usually transparent to the client.
  • A reverse proxy is where TLS termination, routing, and load balancing normally live.
  • A forward proxy is where egress filtering, outbound logging, and shared caching normally live.
  • Either can cache, but the cache serves different populations and has different privacy rules.

07Reverse proxy vs load balancer

They are closely related and often the same process, but they are not the same concept.

  • A load balancer has one primary job: distribute incoming traffic across multiple backend servers.
  • A reverse proxy is a broader role: it also sits in front of backends but can do much more than distribute.
  • Load balancing is one capability a reverse proxy may provide, not its definition.
  • A reverse proxy can terminate TLS, cache, compress, authenticate, rate limit, and route by path without balancing at all.
  • A load balancer can be a dedicated Layer 4 appliance that does nothing else.
  • Products such as NGINX, HAProxy, and Envoy blur the line because they do both.
  • The same behaviour may also arrive as an API gateway, an ingress controller, or a CDN edge — the label changes, the function does not.
  • In an interview, say the reverse proxy is the position in the architecture and load balancing is one of its jobs.

08Layer 4 vs Layer 7 proxying

  • A Layer 4 proxy forwards TCP or UDP connections without reading what is inside them.
  • It is fast, protocol-agnostic, and can handle databases, message brokers, and custom protocols.
  • It cannot route on URL or header because it never parses them; it sees addresses and ports.
  • A Layer 7 proxy understands the application protocol, usually HTTP.
  • That lets it route by path, host, header, or cookie, and rewrite or reject requests intelligently.
  • It can also cache responses, compress bodies, and apply per-route authentication.
  • The cost is parsing and buffering every request, which uses more CPU and memory.
  • Choose the lowest layer that satisfies the routing requirement; use Layer 7 when content matters.

09Common reverse proxy technologies

  • NGINX is one of the most widely used: reverse proxying, load balancing, caching, TLS termination, and static content.
  • HAProxy is known for high-performance Layer 4 and Layer 7 proxying and load balancing.
  • Envoy targets cloud-native and microservice architectures with advanced routing, observability, retries, and circuit breaking.
  • Managed cloud services provide load balancers and gateways that perform similar roles without you running the software.
  • CDN edges act as reverse proxies for cacheable content close to users.
  • Envoy often runs next to every service in a mesh, handling service-to-service traffic rather than only north-south ingress.
  • You may never deploy something literally named a reverse proxy; an ingress controller or gateway may already be doing it.

10NGINX reverse proxy example

A minimal HTTP reverse proxy forwards every request to one backend and passes along the headers the backend needs to understand the original request.

  • Install NGINX, validate the configuration with nginx -t, then reload rather than restart for zero-downtime changes.
  • proxy_pass names the backend the request is forwarded to.
  • Host preserves the original hostname so the backend generates correct links and redirects.
  • X-Real-IP and X-Forwarded-For tell the backend who the client really is behind the proxy.
  • X-Forwarded-Proto preserves the original scheme so HTTPS redirects do not loop.
  • Only trust these headers from a proxy you control; otherwise clients can spoof their address.
  • This block alone gives you a single entry point, but not TLS, caching, or balancing.
# validate and reload
sudo nginx -t
sudo systemctl reload nginx

# /etc/nginx/conf.d/app.conf
server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

11Load balancing across backends

Adding an upstream block turns the same proxy into a load balancer across several backends.

  • NGINX uses round robin by default, cycling through the listed servers.
  • least_conn sends new requests to the backend with the fewest active connections, which helps when request durations vary.
  • max_fails and fail_timeout stop sending traffic to a server that keeps failing.
  • A backup server receives traffic only when the primary servers are unavailable.
  • Health checks or passive failure detection are not optional in production; without them the proxy keeps hitting a dead node.
  • Sticky routing is possible with a cookie, but use it carefully because it hides a dependency on local server state.
  • This configuration is deliberately small; it needs timeouts, limits, and logs before it is production-ready.
upstream app_backend {
    least_conn;
    server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.13:3000 backup;
}

server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://app_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

12Production hardening

  • Timeouts: set connect, send, and read timeouts so a stalled backend cannot hold client connections indefinitely.
  • Request limits: cap body size and header size to blunt accidental or malicious large requests.
  • TLS: terminate HTTPS with managed certificates, modern protocol versions, and automated renewal.
  • Buffering: decide whether to buffer request and response bodies; buffering protects slow backends but costs memory.
  • Compression and caching: compress text responses and cache only content that is safe to share.
  • Security headers and filtering: apply HSTS, frame and content-type protections, and request filtering at the edge.
  • Logging and tracing: log upstream status and latency, and propagate request ids to backends.
  • Capacity and redundancy: the proxy sees all traffic, so run more than one instance and monitor its saturation.

13Placing proxies in an architecture

  • Put a reverse proxy at the public edge to terminate TLS, absorb abusive traffic, and hide internal topology.
  • Use Layer 7 routing to split traffic by path or host across services.
  • Add load balancing at each tier that has more than one instance, including internal service-to-service calls.
  • Put a forward proxy on egress paths where outbound traffic must be filtered, logged, or routed through an allowed network.
  • Keep cache rules explicit: shared caches must never store authenticated, per-user responses.
  • Make the proxy tier redundant, since every request depends on it.
  • Choose one primary place for policy — edge proxy or API gateway — to avoid conflicting rules at multiple layers.
  • The mental model to state: the proxy is the position, and proxying, balancing, TLS, caching, and routing are jobs it can take on.
Client→Edge reverse proxy (TLS termination)→Route by host or path→Load balance to service instances→Backend services→Shared data stores

↔Trade-offs to say out loud

  • A forward proxy centralizes outbound control and caching, but adds a choke point, extra latency, and a component that sees all client traffic.
  • A reverse proxy gives one hardened entry point and central policy, but becomes a critical dependency and a potential single point of failure.
  • TLS termination at the proxy simplifies certificates and saves backend CPU, but leaves internal traffic in plaintext unless re-encrypted.
  • Layer 7 proxying enables content-aware routing and per-route policy, but costs more CPU per request and limits protocol support to HTTP-like traffic.
  • Proxy caching cuts latency and origin load, but risks serving stale or private data if cache keys and headers are wrong.
  • Path-based routing keeps one public endpoint for many services, but couples the proxy configuration to service topology and deploy order.
  • Sticky routing through a proxy supports local state and cache locality, but produces uneven load and complicates failure handling.
  • Adding another proxy layer improves isolation and policy separation, but adds hops, latency, and more configuration to keep consistent.

?Interview questions

Answer aloud before opening the outline.

1. What is the difference between a forward and a reverse proxy?

A forward proxy acts on behalf of the client and handles outbound traffic, hiding the client from destinations. A reverse proxy acts on behalf of the servers and handles inbound traffic, hiding the backend topology from clients. The direction and whose interests are served define the role.

2. Walk me through a request through a forward proxy.

The client sends the request to the proxy instead of the destination. The proxy forwards it to the destination, receives the response, and returns it to the client. The destination sees the proxy's address as the source.

3. Walk me through a request through a reverse proxy.

The client connects to the proxy, which selects a backend, forwards the request, receives the backend's response, and relays it. The client believes it is talking to one server and never learns which backend handled it.

4. Is a proxy the same as a VPN?

No. Both can hide the client's IP, but a proxy typically forwards traffic for specific applications or protocols, while a VPN usually creates an encrypted tunnel carrying broader device traffic. Neither guarantees anonymity.

5. Why would an enterprise deploy a forward proxy?

To control and observe outbound traffic: blocking disallowed sites, enforcing policy, logging requests, caching repeated downloads, and providing egress through an approved network. It is a management and security control point for clients.

6. Why put a reverse proxy in front of an application?

To get one hardened entry point that terminates TLS, hides internal servers, caches responses, enforces rate limits and authentication, and routes requests to the right service. Load balancing is often one of those jobs rather than the only one.

7. Reverse proxy vs load balancer?

A load balancer distributes traffic across backends; that is its primary job. A reverse proxy is the broader role of representing backend servers and may also balance, terminate TLS, cache, compress, and route by content. Many products do both.

8. When do you need Layer 7 rather than Layer 4?

When routing depends on the request itself: path, host, headers, or method. Layer 4 only sees addresses, ports, and protocol, so use it when you need speed and protocol independence. Layer 7 costs more per request but enables content-aware policy.

9. What does TLS termination mean and where should it happen?

The proxy completes the TLS handshake and forwards the decrypted request to the backend. Usually this happens at the edge proxy or load balancer, centralizing certificate management and saving backend CPU. Re-encrypt internally if the network is not trusted.

10. What is dangerous about caching in a reverse proxy?

Serving a response that was generated for one user to another. Shared caches must key on the right dimensions and respect Cache-Control, Vary, and authentication. Personalized responses should generally bypass the shared cache.

11. How does an API gateway relate to a reverse proxy?

An API gateway is a reverse proxy specialized for APIs, adding authentication, rate limiting, request validation, and per-route policy. The traffic position is the same; the feature set and the audience are different.

12. How would you avoid the proxy becoming a single point of failure?

Run multiple proxy instances behind a shared address or a managed service, keep configuration identical across them, health-check the proxies themselves, and monitor their saturation. Every added central component needs its own redundancy plan.

!Traps

  • Defining the two by where the box sits instead of whose traffic it represents.
  • Saying a load balancer and a reverse proxy are the same thing; balancing is one capability, not the definition.
  • Caching authenticated or personalized responses in a shared proxy cache.
  • Terminating TLS at the proxy and then sending sensitive traffic as plain HTTP across an untrusted network.
  • Trusting X-Forwarded-For from arbitrary clients, which lets them spoof their source address.
  • Adding a second proxy layer without consolidating policy, producing contradictory rules at different hops.
  • Forgetting that the proxy itself needs redundancy, health checks, and capacity planning.
  • Assuming a proxy hides a user's identity completely; cookies, logins, and fingerprints still identify them.
