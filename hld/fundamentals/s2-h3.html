01The problem with a flat grid

  • Latitude/longitude grids such as geohash divide degrees, not ground distance.
  • Lines of longitude converge toward the poles, so a cell near the equator covers far more area than a cell of the same resolution near the Arctic.
  • The flat map also has edges the Earth does not have: two ships on opposite sides of 180° longitude can be kilometers apart yet appear at opposite ends of the map.
  • Neighbor logic near the date line needs special wraparound cases that are easy to get wrong.
  • For ride-hailing, shipping, and mapping platforms, these artifacts make distance and neighbor queries inconsistent across the globe.
  • The requirement is a cell system that covers the sphere without seams and keeps cells comparable in size everywhere.

02Two global cell systems

  • S2 and H3 both tile the whole globe and give every cell a compact numeric ID.
  • Both support many resolutions, so the same system can represent a country or a street corner.
  • The ID works as an index key, a grouping key for analytics, or a shard key for partitioning.
  • They differ in cell shape, hierarchy, and the questions they answer best.
  • Neither is a database: they are geometry libraries that produce keys your storage layer can index.
  • Choosing between them is really choosing between exact containment and uniform neighborhoods.

03S2: mapping the Earth onto a cube

  • S2 starts from a cube and projects each of its six faces onto the sphere, which removes the single seam a flat map has.
  • Every point on Earth maps to one point on one face, so the whole surface is covered with six equal regions.
  • Each face is then recursively divided into four quadrants, level by level.
  • Level 0 holds the six face cells; deeper levels multiply the cell count by four each time.
  • Because the subdivision is exact, every cell is fully contained in its parent — a true hierarchy rather than an approximation.
  • The projection distorts shape and area somewhat, so cells are not perfectly uniform, but there are no polar or date-line discontinuities.
  • That structure is what allows an S2 cell to be treated as an interval of IDs in a normal index.

04S2: Hilbert ordering and cell IDs

  • Within a face, S2 orders cell positions along a Hilbert curve, a space-filling curve that keeps nearby 2D positions close in 1D order.
  • A cell's position on the curve plus its face and level becomes a 64-bit cell ID.
  • The ID is hierarchical: the prefix bits identify the ancestors, so the children of a cell occupy a contiguous ID range.
  • Hilbert ordering gives better locality than a naive row-major or Z-order traversal, because it avoids large jumps between adjacent regions.
  • Contiguous IDs are the whole point: a database can store one integer column and answer region queries with range scans.
  • Leaf-level cells are much finer than any application needs, so production code works at a chosen level rather than at maximum precision.
  • The 64-bit representation keeps keys compact and sortable without strings.

05S2: region coverings

  • A query is usually a shape — a circle around the user, a delivery polygon, a city boundary.
  • S2 computes a covering: the set of cells at chosen levels whose union contains the shape.
  • The covering is tuned by a maximum cell count, a minimum level, and a maximum level.
  • A tighter budget yields fewer, larger cells; a looser budget yields a closer fit with more cells.
  • Because cell IDs are ordered, a covering can be compressed into a small number of ID ranges.
  • The database then runs a handful of range scans instead of a spatial join.
  • The result is approximate: cells extend beyond the shape, so an exact distance or containment test still filters the candidates.

06S2 strengths and costs

  • Exact hierarchy: a child is entirely inside its parent, so aggregation and drill-down are consistent.
  • ID ranges make region queries work on ordinary indexes, including key-value stores and columnar warehouses.
  • No special case for the poles or the date line, because the sphere is covered uniformly by construction.
  • The cost is conceptual weight: cube projection, Hilbert ordering, and covering heuristics are more machinery than a geohash string.
  • Cells are only roughly square and only roughly equal in area, so distance math must use the geometry library, not the ID.
  • Choosing levels and covering budgets is a tuning exercise that changes with the query radius.
  • Teams usually adopt a client library rather than implementing the projection themselves.

07H3: hexagons on an icosahedron

  • H3 projects an icosahedron onto the sphere; its twenty triangular faces are filled with hexagonal cells.
  • Hexagons are the reason H3 exists: on a hexagonal grid every neighbor shares an edge and sits the same distance from the center.
  • A square grid has edge neighbors and diagonal neighbors at different distances, which complicates smoothing, distance, and neighborhood logic.
  • Twelve pentagons are unavoidable when covering a sphere with hexagons, and they appear as distortion points in the grid.
  • H3 subdivides with aperture 7: each cell becomes one center child plus six surrounding children.
  • The system offers many resolutions, from continental cells down to street-scale cells.
  • Cells at one resolution are close to equal in area, though not exactly equal.

08H3: neighbors and analytics

  • Neighbor queries are expressed as a k-ring: all cells within k steps of the origin cell.
  • Because every hexagon has six equidistant neighbors, ring shapes are regular and distances are comparable.
  • This makes H3 natural for demand smoothing, surge pricing, supply/demand balancing, and heat maps.
  • Aggregating counts per cell and rolling up to a parent gives multi-resolution dashboards from one dataset.
  • Grid distance (number of steps) is a cheap proxy for travel distance, which is useful for coarse matching.
  • The regular neighborhood also helps when comparing a cell with its surroundings, since all six neighbors are the same shape.
  • Analytics pipelines often store the H3 cell ID as a partition or grouping column next to the raw coordinates.

09H3's hierarchy caveat

  • Children only roughly fit inside their parent, so containment is approximate across resolutions.
  • A point may fall near a child boundary and be assigned to a cell whose parent relationship is not geometrically exact.
  • Consequently, a parent's aggregate is not a perfect sum over its children, which matters for strict accounting.
  • The twelve pentagons have five neighbors instead of six and distort subdivision around them.
  • Cell area varies somewhat within a resolution, so counts per cell are not perfectly comparable without normalization.
  • For exact region math, compute the geometry rather than relying on parent-child containment.
  • This is the main reason S2 is preferred when exact nesting and region ranges drive the design.

10Choosing between them

  • Choose S2 when the workload is indexing and search: point lookups, region coverings, range scans on an ID column, and exact parent-child rollups.
  • Choose H3 when the workload is analysis: neighborhood comparisons, ring queries, demand smoothing, and heat maps.
  • Choose S2 when a region must be expressed as a small set of ID intervals for a storage engine.
  • Choose H3 when six equally distant neighbors make the model simpler than eight uneven ones.
  • Both are preferable to geohash at global scale, where pole and date-line artifacts appear.
  • Neither replaces an R-tree when the indexed objects are arbitrary shapes rather than points or cells.

11Using cell IDs in a system

  • Store the cell ID as a 64-bit integer alongside the raw latitude and longitude; the ID is a key, not a position.
  • Always store the resolution with the ID, because the same integer space means different sizes at different levels.
  • Use the ID as an index key for nearby lookups, and as a grouping key for counts and rollups.
  • As a shard key, cell IDs concentrate a city on one shard — convenient for local queries, dangerous for hot spots.
  • Sharding by cell therefore needs a salt or a split of dense cells, exactly like geohash prefix sharding.
  • For live position updates, keep the current cell in memory and let the durable store hold history.
  • Recompute the cell when the resolution changes; never mix levels in one column without recording which is which.

12Practical adoption notes

  • Use a maintained library: the projection, covering, and edge-case geometry are not worth reimplementing.
  • Pick the resolution from the query radius and the expected rows per cell, then test in both dense and sparse regions.
  • Budget coverings by cell count, not by guesswork; a covering that is too fine explodes the number of ranges.
  • Expect approximate answers from cell-based filtering and keep an exact distance step for correctness.
  • Watch cell cardinality in dashboards: a handful of very hot cells usually means the resolution is too coarse for that city.
  • Keep the raw coordinates for re-indexing, because changing resolution or switching systems requires recomputation.
  • Document the resolution everywhere, since a cell ID without its level is ambiguous.

↔Trade-offs to say out loud

  • Spherical cells remove pole and date-line artifacts but add projection and covering complexity.
  • S2's exact hierarchy makes rollups and range queries reliable but its cells are only roughly square.
  • H3's hexagons give equidistant neighbors but break exact parent-child containment.
  • Fine resolutions reduce candidate counts but multiply index entries and covering ranges.
  • Coarse resolutions keep keys few and cheap but blur dense areas into hot cells.
  • ID ranges on a normal index avoid a spatial database dependency but return approximate candidates.
  • Cell-ID sharding co-locates local data but concentrates traffic on popular regions.
  • Adopting a global cell system fixes worldwide geometry but costs more conceptual and library overhead than a geohash string.

?Interview questions

Answer aloud before opening the outline.

1. Why is a geohash not ideal at global scale?

A geohash splits degrees evenly, so cells shrink in ground area toward the poles where longitude lines converge. It also treats the 180° meridian as an edge, so neighboring points can land at opposite ends of the index. S2 and H3 define cells on the sphere itself, so both artifacts disappear.

2. How does S2 turn the Earth into cell IDs?

It projects a cube onto the sphere, recursively divides each face into four quadrants, and orders positions within a face along a Hilbert curve. That ordering plus the face and level produces a 64-bit ID whose prefix identifies its ancestors, so a subtree is a contiguous ID range.

3. What is a region covering and why does it matter?

It is the set of cells whose union approximates a query shape such as a circle or polygon. Because S2 IDs are ordered, the covering compresses into a few ID ranges that a normal index can scan. The covering is approximate, so candidates are still filtered by exact geometry.

4. Why is a Hilbert curve used instead of a simple Z-order?

Both map 2D positions to 1D order, but a Z-order curve makes large jumps between some adjacent regions, which splits a compact area into distant ID ranges. Hilbert ordering keeps neighbors closer in the ordering, so a region becomes fewer, tighter intervals.

5. What makes H3's hexagons attractive?

Every hexagon has six neighbors that share an edge and sit at the same distance, so ring queries and neighborhood comparisons are regular. A square grid mixes edge and diagonal neighbors at different distances, which complicates smoothing and distance estimates. That regularity is why H3 is popular for demand and mobility analytics.

6. What is aperture 7 in H3?

It is the subdivision rule: each cell is replaced by seven children, one in the center and six around it. That keeps the hexagonal shape and neighbor structure at every resolution, at the cost of children only roughly fitting inside the parent.

7. Why do H3 parent aggregates not equal the sum of children?

Because child cells only approximately tile their parent, some area is shared or missed at boundaries. Assigning each point to its own cell at each resolution avoids double counting within a level, but the geometric containment is not exact, so rollups are approximate by construction.

8. What are the pentagons in H3 and why do they matter?

A sphere cannot be tiled entirely by hexagons, so twelve pentagons fill the gaps. They have five neighbors instead of six and distort subdivision nearby, which shows up as irregular rings and slightly different cell behavior around those points.

9. How would you find all drivers within 2 km using H3?

Choose a resolution whose cells are roughly the size of the search area, take the k-ring around the rider's cell, and look up drivers indexed by cell ID. Then compute exact great-circle distance and filter. The ring gives candidates; geometry gives the answer.

10. How would you query a city polygon stored in an ordinary database using S2?

Compute an S2 covering of the polygon within a cell budget, compress it into ID ranges, and run range scans on the cell ID column. The covering returns a superset, so apply exact containment to finish. This gives spatial queries without a spatial index extension.

11. Can either system replace an R-tree?

No. S2 and H3 organize space, so arbitrary shapes must be approximated by coverings. An R-tree organizes objects by their bounding rectangles, which handles large, overlapping shapes with one entry each. Use cells for points and regions, R-trees for shape-heavy geometry.

12. What is the operational risk of sharding by cell ID?

Dense cities collapse into a few hot cells, so one shard takes most of the traffic while others idle. Mitigations are to split hot cells at a finer resolution, add a salt, or route by a composite key. The same skew exists with geohash prefixes.

!Traps

  • Storing a cell ID without its resolution, which makes the same integer mean different areas.
  • Treating H3 parent-child containment as exact and using it for strict accounting.
  • Assuming cell IDs give exact distance; they give candidates that still need geometry.
  • Choosing the finest resolution and exploding the number of index entries and covering ranges.
  • Sharding by cell ID and creating a single hot shard for a dense city.
  • Mixing S2 and H3 IDs, or different resolutions, in one index column.
  • Reimplementing the projection and covering logic instead of using a maintained library.
