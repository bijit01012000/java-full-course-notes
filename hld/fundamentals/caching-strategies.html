In one lineCaching strategies answer one question: who moves data between cache and database, and when — with cache-aside as the default read pattern and write-through, write-behind, or write-around chosen to fit the write path.
Cache-aside (lazy loading)
The application checks the cache itself, loads from the database on a miss, and populates the cache.
Read-through
The cache layer loads missing data from the database, so the application only talks to the cache.
Write-through
Every write goes through the cache, which writes to the database before acknowledging success.
Write-behind (write-back)
The cache acknowledges the write immediately and persists it to the database asynchronously later.
Write-around
Writes go directly to the database and bypass the cache, which is populated only when data is later read.
Cache invalidation
Removing or updating a cached entry when the underlying data changes so stale values are not served.
Loader function
The function registered with a read-through cache that knows how to fetch a missing value from the source.
Durability
The guarantee that an acknowledged write survives a crash; write-behind weakens this until the flush completes.
Cache pollution
Filling the cache with entries that are written but rarely read, displacing more useful data.

01Why one strategy is not enough

A cache sits between the application and the source of truth. There are several ways requests can move through those components.

  • For reads, either the application checks the cache itself or the cache automatically fetches missing data.
  • For writes, the system can update the database first, update cache and database together, or write the cache and persist later.
  • Each arrangement produces a different strategy with different latency, consistency, and durability.
  • The right choice depends on what matters most: read performance, write performance, consistency, simplicity, or durability.
  • Read strategies and write strategies are separate decisions and are often combined.
  • Naming the data flow explicitly prevents accidental mixes that quietly break consistency.

02Cache-aside: the read path

Cache-aside, also called lazy loading, is the most common strategy. The application manages the cache explicitly.

  • The application checks the cache first and returns the value immediately on a hit.
  • On a miss, the application queries the database, stores the result in the cache, then returns it.
  • The cache never talks to the database on its own; the application owns both the lookup and the population.
  • It is called lazy because data enters the cache only when somebody actually requests it.
  • Only requested data is cached, so memory is not wasted on rows nobody reads.
  • The first request for a key is slower because it must reach the database.
  • The application must handle hits, misses, database reads, and invalidation — more code than a transparent cache.
value = cache.get(key)
if value is None:
    value = db.query(key)
    cache.set(key, value, ttl)
return value

03Cache-aside: writes and invalidation

  • If a value is cached and the database changes, updating only the database leaves the cache stale.
  • The common pattern is to update the database, then delete the cache entry.
  • The next read then misses, fetches the latest value, and repopulates the cache.
  • You could update both database and cache, but keeping two copies synchronized is harder.
  • Two concurrent writers can reach the database and the cache in different orders, leaving the cache with the older value.
  • Deleting rather than updating avoids that ordering race in most cases, which is why it is the usual choice.
  • A delete can still fail or race with a concurrent read that repopulates an old value, so TTLs act as a backstop.
Write database→Delete cache entry→Next read misses→Load fresh value→Repopulate cache→Serve fresh value

04Read-through

Read-through looks similar to cache-aside from outside, but the cache owns the miss handling.

  • The application asks the cache for the data as if the cache were the main data access layer.
  • On a hit, the cache returns the value directly.
  • On a miss, the cache itself retrieves the value from the database, stores it, and returns it.
  • The loading logic lives in the cache layer, usually as a loader function registered once.
  • Application code becomes cleaner because it does not implement cache-miss logic.
  • It requires a cache or library that knows how to load from the source; a plain key-value store is not enough.
  • If the loader breaks or is misconfigured, reads through the cache fail too.
cache = LoadingCache(loader = key -> db.query(key), ttl = 300)
value = cache.get(key)   # cache loads on miss

05Cache-aside versus read-through

  • Both end up caching frequently accessed data, and both may send the first request to the database.
  • The difference is who handles the miss: the application or the cache layer.
  • Cache-aside needs only a general-purpose key-value store such as Redis or Memcached.
  • Read-through needs a cache or library that supports a loader, such as a local caching library with refresh semantics.
  • Read-through centralizes loading, which helps when many services share the same read pattern.
  • Cache-aside keeps loading logic visible in application code, which some teams prefer for flexibility and debugging.
  • Cache-aside is the easier default with Redis; read-through is attractive when the cache abstraction is already strong.

06Write-through

With write-through, every write goes through the cache, and the cache writes to the database before the operation is acknowledged.

  • The application writes the new value to the cache.
  • The cache writes that value to the database as part of the same operation.
  • The write is successful only after the database has also been updated.
  • Cache and database stay closely synchronized, so an immediate read sees the latest value.
  • It does not normally make writes faster: every write still reaches the database, plus cache overhead.
  • Its main benefit is keeping frequently accessed data warm and consistent after writes.
  • All writers must use the same cache path; a service writing directly to the database bypasses the cache and leaves it stale.
Application writes cache→Cache writes database→Database commit succeeds→Acknowledge write→Cache and DB agree

07Write-behind

Write-behind, or write-back, acknowledges the cache write immediately and persists to the database asynchronously.

  • The application writes to the cache, and the cache returns success quickly.
  • The database update happens later, often batched with other changes.
  • Writes become much faster because the request no longer waits for the database.
  • Batching reduces database load: many rapid updates can collapse into fewer database writes.
  • A page-view counter updated constantly might become a single periodic database write.
  • The cache temporarily holds data that has not reached the durable source of truth.
  • Readers of the cache see the newest value while anything reading the database directly sees an older one until the flush.
Write-behind is usually reserved for a narrow, high-volume, low-risk path rather than used across the whole system.

08Write-behind: durability and ordering risks

  • If the cache acknowledges a write and then fails before flushing, data held only in volatile memory can be lost.
  • Replication, persistent logs, or durable queues narrow that window but do not close it for free.
  • Redis AOF depends on fsync frequency: the common everysec setting can still lose about a second of writes.
  • With always, writes are safer but much slower, removing much of the reason to use write-behind.
  • The background writer must handle ordering, retries, and duplicate writes.
  • A retried batch must not apply the same update twice, and an old value must not overwrite a newer one.
  • Anything reading the database directly — reports, analytics, other services — sees stale data until the flush completes.

09Write-around

Write-around takes almost the opposite approach from write-through: writes go straight to the database and skip the cache.

  • A new product is written directly to the database and is not immediately placed in the cache.
  • If someone later requests it, the first read misses, loads from the database, and caches the result.
  • That read path is usually cache-aside.
  • The cache only holds values that somebody actually read, so it is not filled by writes alone.
  • This suits write-heavy workloads where much written data may never be read again: bulk imports, event ingestion, append-only logs.
  • The downside is that recently written data is not immediately cached, so read-after-write pays a database round trip.
  • If the key was already cached before the write, the cached copy is stale, so write-around is usually paired with deleting the entry on write.

10Combining read and write strategies

  • Read strategies decide what happens on a miss; write strategies decide what happens when data changes.
  • A system usually picks one of each rather than adopting a single named pattern everywhere.
  • The most common combination is cache-aside reads with database update plus cache delete on writes.
  • Read-through plus write-through makes the cache the main interface for both reads and writes.
  • Write-behind can reduce database pressure for a high-volume path while normal paths stay strictly consistent.
  • Write-around plus cache-aside fits write-heavy data that is rarely read back.
  • Mixing strategies across different data types is normal, as long as each key family has one clear owner.

11Choosing the right strategy

Start with the access pattern, then check consistency, durability, and failure behaviour.

  • Mostly reads, want simplicity: cache-aside.
  • Cache should hide database access from the application: read-through.
  • Recently written values are read immediately and freshness matters: write-through.
  • Write latency and throughput are the main concern: write-behind, with a durable buffer for pending writes.
  • Lots of written data may never be read: write-around, to avoid cache pollution.
  • Ask what the read pattern is, what the write pattern is, how much staleness is tolerable, how important write latency is, and what happens if the cache fails.
  • If losing an acknowledged write is unacceptable — payments, orders, audit logs — do not use write-behind for that path.

12Failure modes and operating rules

  • Define one write path per key family; a second path that bypasses the cache silently invalidates the strategy.
  • Prefer deleting a cache entry over updating it in place to avoid write-order races.
  • Always keep a TTL as a backstop, even when explicit invalidation exists.
  • Make cache failures non-fatal: fall back to the database with timeouts and load protection.
  • For write-behind, log pending writes durably and make replay idempotent.
  • Monitor hit ratio, cache latency, eviction rate, and the backend request rate that slips through.
  • Load-test the full-miss path, because that is what runs when the cache is cold or down.

↔Trade-offs to say out loud

  • Cache-aside is simple and caches only what is read, but every miss and every invalidation lives in application code.
  • Read-through centralizes loading and simplifies callers, but depends on a loader-capable cache and fails reads if the loader fails.
  • Write-through keeps cache and database consistent after writes, but does not speed writes up and can pollute the cache with rarely read data.
  • Write-behind delivers the fastest writes and absorbs bursts, but acknowledged writes can be lost and the database lags.
  • Write-around avoids filling the cache with unread writes, but read-after-write always pays a database miss.
  • Deleting on write avoids cache/database ordering races, but leaves the next read to repopulate and may briefly serve a miss.
  • Updating the cache on write keeps hot data warm, but concurrent writers can finish in the opposite order and leave stale data.
  • One shared cache path makes consistency tractable, but couples every writer to the cache layer's availability and latency.

?Interview questions

Answer aloud before opening the outline.

1. What is cache-aside, and why is it so common?

The application checks the cache, loads from the database on a miss, and populates the cache itself. It is common because it needs only a general-purpose key-value store, caches only data that is actually read, and degrades to direct database reads if the cache is unavailable. It suits read-heavy workloads such as product catalogs and user profiles.

2. How do you handle writes with cache-aside?

Update the database first, then delete the cache entry. The next read misses and repopulates with fresh data. Deleting rather than updating avoids the race where two concurrent writers update cache and database in opposite orders. A TTL is still kept as a backstop for failed deletes.

3. Cache-aside vs read-through?

Both cache data lazily, but cache-aside puts miss handling in the application while read-through puts it in the cache layer via a loader. Read-through gives cleaner application code and one shared loading path; cache-aside works with any key-value store and keeps the logic visible. Redis is typically used with cache-aside; a local caching library supports read-through.

4. How does write-through work?

The application writes to the cache, the cache writes to the database, and success is returned only after the database write succeeds. The cache and database stay synchronized, so a subsequent read sees the new value immediately. It does not make writes faster, since every write still reaches the database.

5. What is the main risk of write-through?

The cache can fill with data that is written once and never read, wasting memory and evicting more useful entries. It also requires every writer to go through the cache; a service that writes directly to the database leaves the cache stale. It is most useful when recently written data is likely to be read again soon.

6. How does write-behind improve write performance?

The cache acknowledges the write immediately and persists to the database asynchronously, often batching many updates into fewer database writes. The application no longer waits for the database on every request, which raises throughput and reduces database load. The cost is durability and consistency lag.

7. What can go wrong with write-behind?

An acknowledged write can be lost if the cache fails before flushing, so the cache temporarily owns data that has not reached durable storage. Background writes must handle ordering, retries, and duplicates so an old value does not overwrite a newer one. Anything reading the database directly sees stale data until the flush. It is unsuitable for payments, orders, or audit logs.

8. When would you use write-around?

When most written data is unlikely to be read soon, such as bulk imports, event ingestion, or append-only logs. Writing directly to the database avoids filling the cache with values nobody requests. The cost is that read-after-write always misses and pays a database round trip, so it is a poor fit for read-your-writes workflows.

9. Why delete the cache entry instead of updating it on write?

Two concurrent writers can update the database and the cache in different orders, leaving the cache holding an older value. Deleting makes the next read fetch the authoritative value, sidestepping that race in most cases. Updating in place can keep hot data warmer, but only with careful ordering or versioning.

10. Can you combine caching strategies?

Yes, and most systems do. Read and write strategies answer different questions, so a common combination is cache-aside reads with database-update-plus-cache-delete writes. Another is read-through with write-through when the cache is the main data interface. Write-behind is usually limited to a specific high-volume path rather than applied system-wide.

11. How do you choose a caching strategy?

Start from the access pattern: read-heavy and simple points to cache-aside; hide-the-database abstraction points to read-through; read-after-write freshness points to write-through; write throughput with tolerable delay points to write-behind; writes rarely read back point to write-around. Then check staleness tolerance, durability requirements, and what happens if the cache fails.

12. What happens if the cache is unavailable in each strategy?

With cache-aside, the application can usually fall back to the database, so reads still succeed more slowly. With read-through, reads through the cache can fail if the cache is the only path to the loader. With write-through, writes may fail because the write must pass through the cache. With write-behind, pending writes must survive in a durable buffer or they are lost.

13. Which strategies are safe for payments?

Payments need durable, ordered writes and strong consistency, so write-behind is inappropriate because an acknowledged write can be lost. A database-first write with cache invalidation, or write-through with a reliable database commit, is safer. Many systems skip caching the authoritative balance entirely and cache only derived, non-critical views.

!Traps

  • Using write-behind for payments, orders, or audit logs where an acknowledged write must never be lost.
  • Updating the cache and database separately and assuming the two copies will stay in the same order.
  • Letting one service write directly to the database while others use write-through, leaving the cache stale.
  • Assuming write-through makes writes faster when every write still waits for the database.
  • Using write-around and then expecting the first read after a write to be fast.
  • Forgetting to invalidate an existing cache entry when using write-around for an update.
  • Treating write-behind as durable because the cache is replicated, without checking fsync and replay guarantees.
