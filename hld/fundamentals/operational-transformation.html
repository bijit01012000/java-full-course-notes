In one lineOperational transformation lets several people edit one document at once: each edit applies instantly on its author's screen, and remote edits are rewritten to still mean the same thing once they arrive.
Operational transformation
A technique that transforms concurrent edits against each other so all replicas converge on the same document.
Operation
A minimal edit such as insert characters at a position or delete a range, addressed by index.
Transform function
The routine that rewrites operation B so it keeps its intent after operation A has already been applied.
Tie-break rule
A deterministic ordering, such as client ID, that decides which of two concurrent inserts goes first.
Inclusion transformation
Rewriting an operation against one already applied at the same site.
Exclusion transformation
Rewriting an operation as if a given operation had not been applied, used to invert or reorder history.
TP1
The convergence property that transforming each of two concurrent operations against the other yields the same document.
TP2
The stronger property required when three or more operations are concurrent, ensuring transform composition is consistent.
Revision
A server-assigned version number identifying a document state; operations are expressed against a revision.
Pending buffer
A client-side queue of local operations not yet acknowledged, kept so remote operations can be transformed against them.

01The problem: editing the same document at once

  • Two users can insert, delete, and replace in the same region before either sees the other's change.
  • Applying both edits literally can produce duplicated text, lost text, or text in the wrong place.
  • Serialising all edits through a lock destroys the interactive feel and blocks users behind each other.
  • Last-write-wins on whole documents throws away one person's work entirely.
  • The system must keep every replica identical while letting each user see their own keystroke immediately.
  • It must also preserve intent: an edit that meant add a comma here must still land there after remote edits shift the text.

02The core idea

  • Every edit is expressed as an operation against a known document state, not as a whole new document.
  • The local edit is applied immediately, so typing never waits for the network.
  • When a concurrent remote operation arrives, it is transformed against the operations already applied locally.
  • Transformation adjusts positions so the remote edit still targets the same logical text after local changes moved it.
  • Each site converges because every site eventually applies the same set of transformed operations in a consistent order.
  • The technique needs either a central server to order operations, or a peer-to-peer protocol with a total order and correct transformation.
  • The hard part is not the simple case; it is guaranteeing convergence when three or more edits overlap.

03Operations and the document model

  • A minimal operation set is insert(position, text) and delete(position, length).
  • Richer editors add replace, attribute changes, and structural operations for lists or tables.
  • Positions are indexes into the current document, which is exactly why they become invalid after concurrent edits.
  • An operation is only meaningful relative to the state it was created against, usually tagged with a revision.
  • Character-level operations converge more precisely but produce many more messages than line-level ones.
  • Some systems batch keystrokes into a single operation to cut traffic, at the cost of coarser transformation.
  • The operation model dictates the transformation matrix, so keep the set small and well-defined.

04Transforming a concurrent pair

  • Two inserts at the same position: apply both, but order them by a deterministic tie-break so every site agrees.
  • An insert before a deletion's range: the insert's index is unaffected, and the remote deletion proceeds as-is.
  • An insert inside a deletion's range: the deletion must extend to cover the inserted text, or the insert must be shifted out.
  • A deletion overlapping a deletion: the second delete must be shrunk or shifted to avoid removing text twice.
  • A deletion covering text that a remote insert already deleted: the remote operation becomes a no-op rather than an error.
  • Transformation is a function of both operations, not of the document alone, which is why it is easy to get subtly wrong.
  • Every case must have a defined result; undefined cases become divergence bugs that appear only under racing edits.
Concurrent pairWhat transformation must do
Insert / insert, same positionOrder by tie-break so both sites agree
Insert / delete, before rangeShift the delete by the inserted length
Insert / delete, inside rangeDecide whether the insert survives the delete
Delete / delete, overlapShrink the later delete to avoid double removal

05Inclusion and exclusion transformation

  • Inclusion transformation rewrites an operation so it can be applied after another one at the same site.
  • It is the common path: a remote edit is included on top of local edits already applied.
  • Exclusion transformation rewrites an operation as if another had not been applied.
  • Exclusion is needed for undo, for restoring a checkpoint, and for certain multi-way transformation paths.
  • Together they let a site move an operation across the history it has already applied.
  • Formal correctness is stated as transformation properties TP1 and TP2 rather than as ad-hoc case checks.
  • Having both directions available is what separates a real OT library from a naive insert/delete shifter.

06Convergence and intention preservation

  • TP1 requires that two concurrent operations, each transformed against the other, produce the same document.
  • TP1 alone is enough for two concurrent edits and is the property most simple implementations check.
  • TP2 extends this to three or more concurrent operations and constrains how transforms compose.
  • Classic counterexamples exist: three concurrent inserts at the same spot can diverge if the tie-break is not consistent across transformation orders.
  • Satisfying TP2 for all operation pairs is difficult, which is why many production systems rely on a central server to serialise.
  • Intention preservation is the separate goal that the user's edit still lands where they meant it.
  • Convergence and intention are different properties; a system can agree on a document nobody wanted.

07The central-server model

The dominant architecture, often called the Jupiter model, uses one server as the serialisation point for all operations.

  • The server holds the authoritative document and assigns a monotonically increasing revision to each accepted operation.
  • Clients send operations tagged with the revision they were created against.
  • The server transforms incoming operations against everything committed since that revision, then broadcasts the result.
  • Because the server orders operations, each client only needs to transform against its own unacknowledged edits.
  • This removes the need for full N-way transformation on clients and is far easier to reason about.
  • The cost is a coordinator: latency depends on the server, and the server must retain history for transformations.
  • Google Docs and Etherpad-style editors use this shape because it keeps client logic tractable.
Client applies its edit locally, buffers it→Sends operation with its base revision→Server transforms against newer operations→Server assigns a new revision and broadcasts→Clients transform remote operations against pending locals→All sites converge on the same text

08The client loop

  • The client keeps a pending buffer of operations sent but not yet acknowledged by the server.
  • Local edits apply immediately and enter the buffer, giving instant feedback.
  • When a remote operation arrives, the client transforms it against every buffered local operation before applying it.
  • When the server acknowledges an operation, the client removes it from the buffer.
  • Acknowledgements must be matched by identifier; assuming order lets a lost ack corrupt the buffer.
  • If the client's revision is far behind, it may need to resync the whole document rather than transform a long history.
  • A reconnect must resend unacknowledged operations idempotently so retries do not duplicate text.

09Cursors, selections, and presence

  • A remote cursor is just a position, so it must be transformed by the same rules as edits.
  • Without transformation, cursors drift and appear to point at the wrong word.
  • Cursor affinity decides behaviour at boundaries: does the caret stick to the character before or after an insertion?
  • Selections are ranges and need both endpoints transformed plus overlap handling.
  • Presence updates are frequent and disposable, so they usually take a lossy path separate from document operations.
  • Comment anchors and highlights are positions too, so they need the same treatment as cursors.
  • Users notice cursor jumps immediately, making this a visible correctness signal rather than a cosmetic detail.

10Why OT is difficult in practice

  • The transformation function must handle every pair of operation types, and the matrix grows with each new operation.
  • Three-way concurrency exposes composition bugs that two-way tests never reach.
  • Undo is not the inverse of the original operation: it must be transformed against everything applied since.
  • Redo, history navigation, and branching undo stacks multiply the cases further.
  • Attribute and rich-text operations add a second dimension, because formatting ranges also shift.
  • The server must keep enough history to transform late operations, which conflicts with memory limits.
  • Correctness is hard to test: divergence may need a specific interleaving of three clients to appear.

11Failure modes

  • Divergence: replicas silently hold different text because one transformation case was wrong.
  • A stuck client waits forever for an acknowledgement or revision that never arrives.
  • A duplicate operation from a retry inserts the same text twice without idempotency keys.
  • Long offline edits force transformation against a large history, which is slow and error-prone.
  • History truncation makes an old revision untransformable, so the client must be resynced.
  • A client that reconnects with a stale buffer can reintroduce edits the server already committed.
  • Divergence is the worst case because it is invisible until a user notices the document does not match.

12OT versus CRDTs

  • OT needs a total order of operations; CRDTs encode ordering in the data itself.
  • OT keeps documents compact because it does not store per-character identifiers or tombstones.
  • CRDTs tolerate offline and peer-to-peer editing more naturally, at the cost of metadata growth.
  • OT server logic is harder to write correctly, while CRDT libraries are harder to bound in memory.
  • OT gives a central place to enforce permissions and validation; CRDTs accept any valid update.
  • Modern collaborative editors increasingly choose CRDTs for offline and multi-device support, while OT remains proven for server-centric editing.
  • The decision usually comes down to whether you can accept a central coordinator and whether offline editing is a first-class requirement.

13Implementation checklist

  • Define the smallest operation set that covers the product and keep it closed under transformation.
  • Write the transformation matrix explicitly and test every pair, including no-ops and overlapping deletes.
  • Fix a deterministic tie-break rule and apply it identically on server and client.
  • Tag operations with a client identifier, a sequence number, and a base revision.
  • Make operation application idempotent so retries and reconnects cannot duplicate edits.
  • Test with three or more simulated clients and randomised interleavings, not just two.
  • Bound server history with snapshots and force a resync when a client is too far behind.
Model operations→Define transform for every pair→Pick a tie-break rule→Add revision and client IDs→Simulate N-way concurrency→Snapshot history and resync stragglers

↔Trade-offs to say out loud

  • Central ordering simplifies correctness but adds a coordinator, latency, and a single point of failure.
  • Character-level operations merge precisely but generate far more messages than line-level ones.
  • Local echo makes typing feel instant but forces pending buffers and transformation on every remote edit.
  • Rich operation sets support better editing features but explode the transformation matrix.
  • Long server history allows late operations to be transformed but costs memory and slows startup.
  • Batching keystrokes reduces traffic but makes conflicts coarser and intention harder to preserve.
  • OT over CRDTs keeps documents compact and server-controlled but handles offline editing poorly.
  • Aggressive history truncation caps memory but forces expensive full resyncs.

?Interview questions

Answer aloud before opening the outline.

1. What is operational transformation?

A technique for collaborative editing where each edit is an operation that is applied locally at once and transformed against concurrent remote operations when they arrive. Transformation adjusts positions so every replica converges on the same document while each edit keeps its intent.

2. Why not just apply operations in arrival order?

Positions are indexes into a specific document state. A remote insert computed against an older state points at the wrong offset once local edits have shifted the text, so applying it directly duplicates or misplaces content.

3. What does the transform function actually do?

Given two concurrent operations, it rewrites one so it can be applied after the other while preserving intent. For example, a delete must be shifted by the length of an insert that landed before it, and overlapping deletes must be shrunk to avoid removing text twice.

4. What are TP1 and TP2?

TP1 says two concurrent operations, each transformed against the other, produce the same document. TP2 extends this to three or more concurrent operations and constrains how transformations compose, which is where naive implementations diverge.

5. Why is TP2 so hard?

It must hold for every combination of operation types and transformation paths, including cases only reachable with three concurrent editors. Classic counterexamples show that a locally consistent tie-break can still yield different documents depending on the order transforms are composed.

6. How does the central-server model work?

The server serialises operations and assigns each a revision. Clients send operations against the revision they saw; the server transforms them against newer operations and broadcasts the result. Clients only transform remote operations against their own unacknowledged edits.

7. What is a pending buffer for?

It holds local operations that have been applied and sent but not yet acknowledged. When a remote operation arrives, the client transforms it against everything in the buffer so the local edits are not overwritten or duplicated.

8. How do you handle two users inserting at the same position?

Apply both and order them with a deterministic tie-break such as client ID so every replica picks the same order. Without a shared rule, different sites could interleave the inserts differently and diverge.

9. Why is undo difficult in OT?

An undo cannot simply invert the original operation, because the document has changed since. The inverse must be transformed against every operation applied after it, and the undo stack itself may need transformation when remote edits arrive.

10. How do remote cursors stay correct?

Cursor positions are transformed like edits, with an affinity rule deciding whether the caret sticks to the character before or after an insertion at the boundary. Selections transform both endpoints and handle overlap.

11. What breaks when a client edits offline for a long time?

Its operations must be transformed against a long history, which is slow and exposes rare transformation cases. If the server has truncated that history, the client cannot be transformed at all and must resync the document.

12. OT or CRDT for a new collaborative editor?

OT is a good fit for server-centric editing where documents must stay compact and a coordinator is acceptable. CRDTs are better when offline, peer-to-peer, or multi-device editing is a first-class requirement, at the cost of metadata growth.

!Traps

  • Handling only insert/insert and insert/delete, then diverging on overlapping deletes.
  • Using document position as identity instead of transforming positions.
  • Forgetting a deterministic tie-break for concurrent inserts at the same index.
  • Testing with two clients only, so TP2 failures never appear.
  • Assuming undo is the inverse of the original operation.
  • Letting server history grow unbounded, then running out of memory.
  • Retrying operations without idempotency keys, so a lost acknowledgement duplicates text.
