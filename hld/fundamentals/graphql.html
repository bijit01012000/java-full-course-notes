Schema
The typed contract of a GraphQL API: the types, fields, arguments, and operations clients may use.
Query
A read operation whose selection set describes exactly which fields the response should contain.
Mutation
A write operation defined in the schema, executed in order and usually returning the changed fields.
Resolver
The function that supplies the data for one field, called as the server walks the selection set.
Selection set
The nested list of fields a client requests inside a query or mutation.
Over-fetching
Receiving more data than the client needs, a common cost of fixed REST response shapes.
Under-fetching
Needing several round trips because one endpoint does not return everything a screen requires.
N+1 problem
Issuing one query per parent item in a list, turning a single request into many backend calls.
DataLoader
A batching and caching utility that collects per-item lookups within a tick and issues one batched call.
Persisted query
A pre-registered query identified by a hash so clients send a small identifier instead of the full document.

01The problem with fixed responses

In a REST API the server decides the response shape for each endpoint, so the client must fit its needs to that shape.

  • A mobile screen needs a name and avatar but the endpoint returns the full profile, so bandwidth and parsing work are wasted: over-fetching.
  • A screen needs an order plus its customer plus line items, but no single endpoint returns all three, so the client makes several calls: under-fetching.
  • Each new screen shape encourages either a new bespoke endpoint or a bloated general one.
  • Versioning accelerates because every client-specific shape becomes part of the contract.
  • BFF layers and response-shaping parameters are common workarounds, and they add servers to maintain.
  • GraphQL's answer is to let the client declare the shape it needs from one typed graph.
  • The trade is explicit: flexibility for clients, more variability and cost on the server.

02How GraphQL works

  • The client sends a document containing an operation and a nested selection of fields.
  • The server validates the document against the schema before executing anything.
  • Execution walks the selection set and calls a resolver for each field, assembling the response shape.
  • The response mirrors the query's shape, so the client knows exactly what it will receive.
  • A single endpoint, usually POST /graphql, serves all reads and writes.
  • The transport is usually HTTP with JSON, but GraphQL itself specifies no transport.
  • Errors can appear per field alongside partial data, so one failed field does not necessarily fail the request.
query OrderSummary($id: ID!) {
  order(id: $id) {
    id
    total { amount currency }
    customer { name avatarUrl }
    items { sku quantity }
  }
}

03The schema and type system

  • The schema is the contract, written in the schema definition language and served for introspection.
  • Types are object, scalar, enum, interface, union, and input types; fields may take arguments.
  • Nullability is explicit: String! means non-null, and it is a promise the resolvers must keep.
  • Interfaces and unions let one field return several concrete types, which clients handle with fragments.
  • Enums constrain values so clients get validation instead of free-form strings.
  • Schema-first design makes the API reviewable before implementation and enables code generation.
  • Evolving the schema means adding fields and deprecating old ones with @deprecated, not deleting them abruptly.
  • Introspection is powerful for tooling and also a disclosure surface you may need to restrict in production.

04Queries and field selection

  • A query names an operation, optionally takes variables, and lists the fields to return.
  • Variables keep documents static so clients can cache and servers can persist them.
  • Fragments reuse selection sets across queries and across union or interface types.
  • Aliases let one query fetch the same field with different arguments, such as two products by ID.
  • Directives such as @include and @skip make parts of a selection conditional.
  • The response shape follows the query exactly, which is why clients can rely on it without defensive mapping.
  • Deeply nested selections are legal, which is precisely why depth limits exist.

05Resolvers and execution

  • Each field has a resolver: a function receiving the parent value, arguments, and context.
  • Execution is breadth-first over the selection tree, and sibling fields may resolve concurrently.
  • A trivial resolver reads a property from the parent object; a complex one calls a service or database.
  • The context object carries per-request state such as the authenticated user and data loaders.
  • Resolvers are where authorisation belongs, per field, because the client chooses which fields to request.
  • Errors thrown in a resolver surface on that field, with data for the rest of the tree when possible.
  • Because the client controls the traversal, resolver cost is not fixed by the endpoint design.

06Mutations and subscriptions

  • Mutations are writes declared in the schema, and their top-level fields execute serially in document order.
  • They return a selection set, usually the changed object, so the client can update its cache without a second read.
  • Input types group mutation arguments into one object, which keeps signatures stable as fields are added.
  • Mutations are not automatically idempotent; a retried create behaves like a retried POST.
  • Subscriptions push updates over a long-lived connection such as WebSocket, driven by server-side events.
  • Subscriptions need authorisation per topic and backpressure handling, or they become an unbounded fan-out.
  • Many teams skip subscriptions and use webhooks or polling, which are simpler to operate.

07The N+1 problem

The most common performance failure in GraphQL is a list field whose child field resolves once per item.

  • A query for 50 orders, each with a customer, can trigger 50 separate customer lookups after the initial list query.
  • The client sees one HTTP request, but the server issues dozens or hundreds of backend calls.
  • The fix is batching: collect the keys needed within one execution tick and fetch them in a single call.
  • DataLoader is the standard pattern, giving per-key batching plus per-request caching.
  • Batch loaders must be per request, not global, or users can see each other's cached data.
  • Join or prefetch at the data layer where possible, so the batch is one query rather than many.
  • Monitor resolver-level timing and backend call counts, because HTTP-level metrics hide this cost.

08Caching and performance

  • HTTP caching assumes one URL per resource; GraphQL uses one URL for everything, so CDN caching mostly disappears.
  • Clients still cache normalised objects by type and ID, which is why Apollo-style clients feel fast on repeat navigation.
  • Persisted queries restore some CDN-ability: the client sends a hash and the server maps it to a query.
  • Server-side response caching must be keyed on the operation plus variables plus user scope.
  • Field-level caching inside resolvers can help, but invalidation becomes the hard part.
  • Depth and complexity limits are performance controls, not just security controls.
  • Because one query can touch many services, tracing per resolver is essential for finding the slow part.

09Query cost, abuse, and security

  • A client can request a very expensive graph traversal in a single legal query, so rate limiting by request count is not enough.
  • Enforce depth limits, complexity budgets, and pagination requirements on list fields.
  • Use persisted or allowlisted queries in production so only known documents can execute.
  • Disable or restrict introspection outside development to reduce schema disclosure.
  • Authorise at the field level: hiding a field in the UI is not access control.
  • Timeout and cancel long executions, and cap the total resolvers a single request may invoke.
  • Aliases can multiply the same expensive field, so cost calculation must account for repetition.

10GraphQL vs REST, and when to use it

  • Choose GraphQL when many clients need different shapes of the same data, especially mobile plus web plus partners.
  • Choose it when the domain is a highly connected graph that would otherwise need many bespoke endpoints.
  • Prefer REST for simple public APIs, for file uploads and downloads, and where HTTP caching is central.
  • Prefer gRPC for internal service-to-service calls where schema and performance matter more than client flexibility.
  • GraphQL shifts complexity: simpler clients, harder server operations, caching, and rate limiting.
  • A BFF with REST is often enough when only one or two clients need shaping.
  • You can mix styles: GraphQL at the edge, REST or gRPC behind it.

↔Trade-offs to say out loud

  • Client-selected fields remove over-fetching but make response size and cost unpredictable to the server.
  • Single endpoint simplifies the surface but removes URL-based CDN caching.
  • One query per screen cuts round trips but can hide N+1 work behind a single HTTP call.
  • Strong typing enables code generation and validation but requires schema discipline and review.
  • Introspection helps tooling but exposes your data model unless restricted.
  • Subscriptions give real-time updates but add connection state, authorisation, and backpressure work.
  • Persisted queries restore caching and reduce abuse but require a build-time registration step.
  • Field-level resolvers keep concerns separated but multiply backend calls if not batched.
  • Flexible queries serve diverse clients but make cost limits and capacity planning harder.

?Interview questions

Answer aloud before opening the outline.

1. What problem does GraphQL solve?

It removes fixed response shapes by letting the client request exactly the fields it needs from one typed graph. That eliminates over-fetching and reduces the multiple round trips typical of composing a screen from several REST endpoints.

2. How does a GraphQL request actually execute?

The server parses and validates the document against the schema, then walks the selection set calling a resolver per field. The response mirrors the query shape, and field errors can coexist with partial data.

3. What is the N+1 problem in GraphQL?

A list field's child resolver runs once per item, so one client request can trigger dozens of backend queries. Batching keys within an execution tick, usually with a per-request DataLoader, collapses those into a single call.

4. Why is caching harder in GraphQL than in REST?

REST gives each resource its own URL, which HTTP caches and CDNs understand. GraphQL sends everything to one URL with different bodies, so shared caching needs persisted queries or server-side caching keyed on operation, variables, and user.

5. How do you protect a GraphQL endpoint from expensive queries?

Enforce depth limits, complexity budgets, required pagination, and timeouts, and consider allowlisting persisted queries in production. Rate limiting by request count alone fails because one legal query can be arbitrarily expensive.

6. Where should authorisation live in GraphQL?

In the field resolvers, because the client chooses which fields to request and the same object may expose fields with different permissions. Hiding fields in the client or relying on query-level checks leaves holes.

7. Are mutations idempotent?

No, not automatically. A retried create mutation behaves like a retried POST and can duplicate the resource, so idempotency keys or explicit deduplication are still needed.

8. What is the difference between a query and a mutation in execution terms?

Query fields may resolve concurrently. Mutation top-level fields execute serially in document order, which lets a client rely on one write completing before the next begins.

9. Would you use GraphQL for internal service-to-service calls?

Usually not. Internal calls benefit more from a compact, strongly typed RPC protocol such as gRPC with predictable performance, while GraphQL's flexibility pays off mainly when diverse clients shape their own responses.

10. How do you evolve a GraphQL schema without breaking clients?

Add fields and types rather than removing or renaming them, mark retiring fields with @deprecated, and monitor field usage to know when removal is safe. Because clients select fields explicitly, unused fields can often be removed after telemetry confirms they are unused.

11. When is REST the better choice?

When the API is simple and public, when endpoints map cleanly to resources, when file transfer or HTTP caching dominates, or when you want the lowest operational complexity. GraphQL repays its cost only when client flexibility is a real requirement.

!Traps

  • Assuming one GraphQL request means one backend query; N+1 resolver calls hide behind a single HTTP call.
  • Sharing a DataLoader cache across requests, which leaks one user's data into another's response.
  • Rate limiting by request count on a single endpoint, where one query can be arbitrarily expensive.
  • Treating introspection as harmless in production and exposing the entire schema.
  • Enforcing access control at the query level while fields have different permissions.
  • Deleting schema fields instead of deprecating them, breaking clients that still select them.
  • Expecting CDN caching to work as it does for REST URLs.
