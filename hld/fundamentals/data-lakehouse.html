In one lineA data lakehouse keeps analytical data as open columnar files on cheap object storage and adds a table format on top, so one copy of the data supports both reliable SQL reporting and machine learning without a second warehouse copy.
Open table format
A metadata layer such as Apache Iceberg, Delta Lake, or Apache Hudi that makes a set of files behave like a transactional table.
Snapshot
An immutable view of the table at one commit, listing exactly which data files and delete files belong to that version.
Manifest
A metadata file that lists data files together with per-file statistics such as row counts and column min/max values.
Catalog
The service that stores the pointer to the current table metadata, so readers do not have to list the object store to find files.
Copy-on-write
An update strategy that rewrites whole data files containing changed rows; reads stay simple and fast.
Merge-on-read
An update strategy that writes new data files plus delete files, and reconciles them when the table is read.
Time travel
Querying a table as of an older snapshot or timestamp for audit, debugging, or reproducible model training.
Schema evolution
Changing columns of a table, such as adding or renaming one, without rewriting existing data files.
Compaction
A maintenance job that merges small files and applies pending deletes so reads do not degrade over time.
Separation of storage and compute
Keeping data in object storage while independent engines read it, so each can scale and be priced on its own.

01Why companies ran two systems

The lake and the warehouse solved different halves of the analytical problem, so most companies paid for both.

  • A data lake stores raw files cheaply on object storage and applies schema on read, which suits exploration and machine learning.
  • A data warehouse enforces schema on write, offers ACID transactions, indexes, and tuned SQL, which suits governed business reporting.
  • Feeding the warehouse means copying data out of the lake on a schedule, so the same rows exist twice and are paid for twice.
  • The copies drift: late fixes, changed transformations, and partial loads leave the two systems disagreeing about basic numbers.
  • Teams then argue about which copy is correct while machine learning uses one and dashboards use the other.
  • The root cause is that cheap open storage historically lacked table guarantees, and reliable tables historically required a closed, expensive store.
The lakehouse is an attempt to move the warehouse guarantees onto the lake instead of moving the data into the warehouse.

02What a lakehouse is

  • Data lives in open columnar files such as Parquet or ORC in object storage, not in a proprietary internal format.
  • A table format adds the database behaviours on top: transactions, updates and deletes, snapshots, schema checks, and partition management.
  • Any compatible engine can read the same table: Spark for batch, Flink for streaming, Trino or a warehouse-style engine for SQL, Python for ML.
  • Storage and compute stay separate, so you scale readers without copying data and pay for storage at object-store prices.
  • It is an architecture pattern, not a single product: the files plus the table format plus a catalog plus engines.
  • The lake keeps its flexibility because files remain readable by ordinary tools; nothing is hidden inside a storage engine.

03The table format: turning files into a table

A directory of Parquet files is not a table. The table format supplies the missing structure.

  • Metadata records the schema, the partition specification, the sort order, and the list of files that currently make up the table.
  • Each data file is registered with statistics: row count, size, and per-column minimum, maximum, and null count.
  • A read resolves one snapshot, prunes files using those statistics, and only then opens the surviving files.
  • Readers never list the bucket; listing is slow, request-expensive, and not reliably consistent, so metadata is the source of truth.
  • Because old metadata is retained, a reader can pin a snapshot and get a stable answer while writers keep committing.
  • The format also owns table-level rules such as which partition layout is valid and how new columns are identified.
Writer creates new data files in object storage→Writer writes manifest entries with file statistics→Writer commits a new metadata version→Catalog atomically points to the new version→Reader resolves the snapshot and prunes files→Reader scans only the surviving files

04ACID on top of object storage

  • Object stores expose simple put and get operations and no atomic multi-file rename, so a multi-file commit cannot be made atomic by moving a directory.
  • The standard trick is to write the data files first, then commit one small metadata file atomically, so the visible change is a single pointer swap.
  • A reader sees either the old snapshot or the new one, never a half-written table, which is what makes the table transactional.
  • Writers use optimistic concurrency: two writers can prepare commits, but the second one detects the conflict and retries or fails.
  • Conflict checks compare which files each transaction read and wrote, which is why the metadata tracks the file set and not just row counts.
  • A writer that crashes after writing data but before committing leaves orphan files that no snapshot references; a garbage-collection job removes them later.
The commit protocol is the whole product. Everything else, such as SQL and time travel, is a consequence of having atomic commits.

05Updates, deletes, and row-level changes

  • Analytical stores were append-only for years, but privacy deletes, corrections, and change-data-capture upserts require row-level change.
  • Copy-on-write rewrites every file that contains an affected row; the read path stays a plain file scan, but writes are amplified.
  • Merge-on-read writes new data files plus small delete files, and the reader applies those deletes while scanning.
  • Delete files are recorded as positions in a file or as predicates, so a delete can target specific rows without rewriting history.
  • Merge-on-read favours frequent updates and streaming ingest; copy-on-write favours read-heavy tables with occasional corrections.
  • Compaction later rewrites affected files, applies the deletes, and restores a clean read path, at the cost of extra writes.
  • A table that never compacts accumulates delete files until read latency and planning time become the visible problem.

06Time travel and snapshots

  • Every commit produces a snapshot, so the table has a readable history rather than a single mutable state.
  • A query can read AS OF a timestamp or a version number, which is useful for audits and for reproducing a model's training data.
  • A bad load can be rolled back by pointing the table at the previous snapshot instead of restoring from a backup.
  • Incremental reads between two snapshots expose the rows that changed, which is how downstream jobs avoid full rescans.
  • Snapshots cost storage, so retention policies expire old metadata and let garbage collection remove files that no live snapshot references.
  • Expiring snapshots is a real decision: expire too aggressively and you lose audit and rollback ability, too slowly and storage and metadata grow.

07Schema enforcement and evolution

  • The table enforces a schema when a writer commits, so a malformed batch is rejected instead of silently polluting the table.
  • Columns are tracked by stable identifiers, so renaming a column does not make old files unreadable or mis-map data.
  • Adding a nullable column is cheap because old files simply have no value for it; dropping or reordering is handled by the metadata mapping.
  • Partition layouts can evolve, so a table can switch from daily to hourly partitioning without rewriting everything written so far.
  • Compatibility rules still matter for consumers: a widened type or a renamed column can break dashboards even when the table itself accepts the change.
  • Use a schema registry or a contract with producers so upstream teams cannot surprise every reader with an incompatible field.

08One copy for BI and machine learning

  • The same tables serve SQL dashboards, ad-hoc analysis, feature engineering, and model training, so there is one definition of each entity.
  • Removing the lake-to-warehouse copy removes a scheduled job, its lag, and a class of reconciliation bugs.
  • Training on the same tables that feed reporting reduces train/serve skew, because features come from the governed source.
  • Open formats avoid lock-in: the data outlives any one vendor's engine or pricing change.
  • Governance is centralised in the catalog, so access control, lineage, and audit apply to every engine that reads the table.
  • The caveat is that a lakehouse does not automatically match a mature warehouse on high-concurrency BI, workload isolation, or optimiser maturity.

09Performance: how lakehouses stay fast

  • Columnar files plus compression mean a query reads only the columns it projects.
  • Partition pruning removes whole directories when the filter matches the partition key.
  • File statistics skip files whose minimum and maximum values cannot satisfy the predicate; some formats also keep bloom filters for equality lookups.
  • Clustering or sorting data on common filter columns co-locates related values, so pruning skips more files.
  • Local disk caches and engine-side caches hide repeated object-store latency for hot tables.
  • Compaction keeps file sizes in a healthy range; many tiny files make planning and per-file overhead dominate the actual scan.
  • There is no B-tree index to seek a single row, so skipping files with metadata is the main performance lever.

10Metadata, catalogs, and the small-file problem

  • Every commit writes metadata, so thousands of tiny commits create thousands of tiny metadata files and slow query planning.
  • Formats periodically collapse metadata into checkpoints so a reader does not replay the entire commit history.
  • Streaming ingest is the usual source of small files: a short micro-batch or checkpoint interval writes a new file each time.
  • A scheduled compaction job groups small files, and a manifest-rewrite job keeps planning cost bounded.
  • The catalog holds the current pointer and enforces naming and access; options range from a Hive metastore to a REST catalog to vendor catalogs.
  • Catalog features such as branching and tagging let teams stage a table version before promoting it, similar to a code branch.
  • Table maintenance is production work: it needs owners, schedules, monitoring, and a rollback plan, not a one-off script.

11Failure modes to design for

  • Concurrent writers to the same partition can conflict repeatedly; partition the writes or serialise them through one job.
  • A compaction job racing with readers can cause stale reads or wasted work if snapshot isolation and retention are not respected.
  • A schema change that the table accepts can still break every downstream consumer, so contracts and tests are required.
  • Snapshot expiry can silently destroy the audit trail or the ability to reproduce an old model.
  • An engine that lists the bucket instead of reading metadata can return wrong results, especially with merge-on-read deletes.
  • Many small GET requests to an object store can hit request throttling and cost more than the data scanned.
  • Orphaned files from failed writes waste storage until garbage collection runs, and aggressive GC can delete files a slow reader still needs.

12Trade-offs and when not to use one

  • Against a warehouse, a lakehouse wins on storage cost, open formats, and multi-engine access, but usually loses on concurrency, workload isolation, and SQL maturity.
  • Against a raw lake, it wins on correctness and manageability, but adds a table format, a catalog, and ongoing maintenance jobs.
  • For a small dataset with one BI tool and one team, a managed warehouse is simpler and may be cheaper than operating a lakehouse.
  • For large volumes read by several engines, including ML, the avoided copy and avoided lock-in usually justify the operational work.
  • The table format is a long-lived commitment: migrating snapshots, deletes, and catalogs later is possible but expensive.
  • A hybrid is common: lakehouse as the system of record, plus a warehouse or serving layer for the highest-concurrency dashboards.

13Designing a lakehouse in an interview

  • State the freshness requirement per layer: raw landing in minutes, curated tables in tens of minutes, or near real time.
  • Pick partition keys from the dominant filters, and avoid over-partitioning small tables because metadata and file counts grow.
  • Choose copy-on-write or merge-on-read based on update frequency versus read latency, and say who runs compaction.
  • Define retention for snapshots and raw files explicitly, because it determines both audit ability and storage cost.
  • Say which consumers still need a warehouse or serving store, rather than claiming one system fits every workload.
  • Mention cost drivers honestly: storage volume, request counts, compute hours, and maintenance jobs.
Sources: databases, events, files→Ingest: batch loads and streaming writes→Raw zone: immutable landing files→Curated zone: table format with schema and partitions→Catalog and governance: access, lineage, audit→Consumers: SQL engines, dashboards, ML training→Maintenance: compaction, snapshot expiry, garbage collection

↔Trade-offs to say out loud

  • One copy instead of two removes sync jobs and drift, but makes the lakehouse a single system whose outages and mistakes affect both BI and ML.
  • Open files on object storage cut storage cost and lock-in, but object stores lack atomic renames, so every guarantee must be built in the metadata commit protocol.
  • Copy-on-write gives fast, simple reads but multiplies write cost and rewrite volume on update-heavy tables.
  • Merge-on-read makes updates cheap but pushes work to readers and requires disciplined compaction.
  • Time travel improves audit, rollback, and reproducibility but retains files and metadata that must eventually be expired.
  • Schema evolution lets the table change without rewrites but can still break downstream consumers that assumed the old shape.
  • A single governed catalog simplifies access control and lineage but concentrates risk and can become a cross-team bottleneck.
  • Lakehouse over warehouse favours large, multi-engine, ML-heavy workloads; a warehouse still wins on concurrency, isolation, and operational simplicity.

?Interview questions

Answer aloud before opening the outline.

1. What problem does a data lakehouse solve?

It removes the need to keep one copy of analytical data in a lake and another in a warehouse. The lakehouse keeps data in open files on object storage and adds a table format for transactions, schema, and snapshots, so SQL reporting and machine learning can share one governed copy.

2. What does the table format actually add on top of Parquet files?

It adds a metadata layer: the schema, partition specification, the list of files in each snapshot, and per-file statistics. That enables atomic commits, file pruning, time travel, row-level deletes, and schema evolution, none of which plain files provide.

3. How do you get ACID transactions when object storage has no atomic rename?

Write the new data files first, then commit one small metadata file atomically and let the catalog pointer move to it. Readers resolve a snapshot, so they see the old version or the new one, never a partial table. Writers use optimistic concurrency and retry on conflict.

4. Copy-on-write or merge-on-read: how do you choose?

Choose copy-on-write for read-heavy tables with occasional corrections, because reads stay a plain scan. Choose merge-on-read for frequent updates or streaming ingest, because writes are cheap, but commit to running compaction so delete files do not accumulate.

5. What is time travel useful for in practice?

Auditing what a report showed on a given date, debugging a bad pipeline run, rolling back an incorrect load, and reproducing the exact training set behind a model. It depends on snapshot retention, so expiry policy is part of the design.

6. How does a lakehouse avoid the small-file problem?

Batch or micro-batch writes produce files sized to a target, and a scheduled compaction job merges the small ones. Metadata checkpoints and manifest rewrites keep planning cost bounded. Without maintenance, file count grows and query planning dominates.

7. Where does a lakehouse still lose to a warehouse?

High-concurrency BI with many simultaneous short queries, strict workload isolation, mature cost-based optimisation, and hands-off operations. A warehouse is a tuned appliance; a lakehouse is a collection of engines and maintenance jobs you operate.

8. How would you design zones in a lakehouse?

Land raw immutable files first, then curate them into conformed tables with enforced schema and sensible partitions, then build aggregated or serving tables for specific consumers. Each zone has an owner, a freshness target, and a quality check.

9. What breaks if you skip compaction?

Reads must open more files, apply more delete files, and plan over more metadata, so latency and cost climb steadily. Streaming tables are the worst case because every checkpoint can create a new file.

10. How do you handle deletes for privacy requirements?

Use row-level deletes supported by the table format, then run compaction so the deleted rows are physically removed from rewritten files. Expire old snapshots and garbage-collect unreferenced files, otherwise the deleted data still exists in history.

11. When would you not use a lakehouse?

When the data is small, one team owns it, and one managed warehouse already meets latency and concurrency needs. The table format, catalog, and maintenance jobs are overhead that only pays off with scale, multiple engines, or a real ML workload.

12. How do you keep BI and ML from disagreeing in a lakehouse?

Publish one governed table per entity, document its grain, and make both consumers read that table rather than private extracts. Add tests and lineage so a transformation change is visible to every downstream owner before it ships.

!Traps

  • Calling a directory of Parquet files a lakehouse when there is no table format, catalog, or commit protocol.
  • Assuming object storage gives you atomic multi-file commits for free.
  • Choosing merge-on-read for a read-heavy table and never scheduling compaction.
  • Forgetting snapshot expiry, so storage grows forever or audit history disappears unexpectedly.
  • Over-partitioning on a high-cardinality column and creating millions of tiny files.
  • Letting a schema change through because the table accepts it, without checking downstream consumers.
  • Running garbage collection while long readers still depend on older snapshots.
