In one lineBatch processing runs finite jobs over bounded data for throughput and exact reprocessing; stream processing runs forever over unbounded events for low latency, at the cost of windows, watermarks, state, and delivery guarantees.
Bounded data
A dataset with a clear beginning and end, such as one day of orders or a table snapshot; batch jobs process it as a finite input.
Unbounded data
A continuous flow of events with no final record, such as clicks, transactions, or sensor readings; stream processors handle it as it arrives.
Batch processing
Collecting data over a period and processing it together in a scheduled job that finishes when the input is consumed.
Stream processing
Processing each event shortly after it is produced, in a job that runs continuously.
Windowing
Splitting an endless stream into finite groups — tumbling, sliding, or session — so aggregations can produce a result.
Event time
The timestamp when an event actually happened, which determines the correct analytical window.
Processing time
The timestamp when the processor handles an event; simpler and fresher, but it misplaces delayed events.
Watermark
An estimate of how far event time has progressed, used to decide when a window is complete enough to emit.
Checkpoint
A durable snapshot of processor state plus the corresponding stream position, used to recover without losing or double-counting events.
Lambda / Kappa
Two ways to combine fast and historical results: Lambda runs separate batch and speed layers, while Kappa replays one streaming pipeline over a retained log.

01Two teams, same data, different latency

An e-commerce platform records an event for every order. Finance and fraud both use those events, but they need answers on very different clocks.

  • Finance wants yesterday's revenue by product category; an hour of processing overnight is acceptable.
  • Fraud wants to flag a suspicious order before payment is approved; an hour later, the payment has cleared and the order may have shipped.
  • The data is the same; the requirement that differs is how fresh the result must be.
  • Latency requirements drive the architecture more than data volume does.
  • Neither approach is universally better; each fits a different class of question.
  • Most large systems end up using both rather than choosing one forever.

02Batch processing: bounded data

  • Batch processing collects data over a period and processes it together as one job.
  • It works on bounded data: the input has a known beginning and end, such as one day of orders.
  • A nightly job reads the previous day's orders, groups them by category, and writes totals to a reporting table.
  • When the input is consumed, the job finishes; the next run handles the next period.
  • Because the full dataset is available, the job can sort, join large tables, scan repeatedly, and compute exact totals.
  • It can also validate output before publishing, which is hard when results are emitted continuously.
  • Common tools include Apache Spark, SQL engines such as Hive, Trino, and Presto, dbt, and managed data warehouses.

03Inside a batch job

  • Collection happens beforehand: the application writes events to object storage or a warehouse table throughout the day.
  • A scheduler starts the job at a fixed time, or an orchestrator starts it when upstream data is ready.
  • The job reads the input and splits it across machines, each processing a portion in parallel.
  • Partial results are combined — shuffled and reduced — into the final aggregate.
  • The output is written to a reporting table or another destination, and the job ends.
  • The startup cost of the cluster is spread across the whole dataset, which is why throughput is high.
  • A common safe-write pattern is to replace an entire output partition rather than append rows, so a rerun cannot duplicate data.
Collect events into storage→Scheduler starts the job→Read and split the input→Process partitions in parallel→Combine partial results→Write output and finish

04Why batch works, and where it stops

  • High throughput: sequential reads and distributed processing use resources efficiently over large inputs.
  • Simplicity: a fixed input is easier to write, test, and reason about than an endless stream.
  • Easy recovery: if a job fails, fix it and rerun on the same input; deterministic output makes this safe.
  • Reprocessing: a bug in last month's revenue can be fixed by rerunning last month's job.
  • Bursty resources: the cluster can start for the job and shut down afterward.
  • The limitation is latency: results are only as fresh as the last completed run.
  • Running the job more often helps, but each run pays scheduling, startup, read, and write overhead; tiny frequent jobs are inefficient.
  • Once the requirement is seconds, traditional batch stops being practical and streaming takes over.
Batch freshness equals the job interval plus the job duration. A daily job can be nearly a day behind.

05Stream processing: unbounded data

  • Stream processing handles events continuously, shortly after they are produced.
  • It works on unbounded data: there is no final record, and new events can arrive indefinitely.
  • The job runs continuously rather than finishing after a fixed dataset.
  • Fraud checks can run as each order arrives, before payment is approved.
  • Latency is typically milliseconds to seconds, which is the main reason to accept the extra complexity.
  • State is often required for counts, windows, joins, deduplication, and pattern detection.
  • Recovery is harder than batch: the processor must restore state and resume from the right stream position.
  • Common workloads include fraud detection, monitoring and alerting, live dashboards, recommendations, tracking, and change data capture.

06The streaming pipeline

  • Producers create events: application servers, mobile apps, and IoT devices.
  • A durable event log or broker such as Kafka receives and retains events in partitions.
  • Consumers read at their own pace; a restart or lag does not destroy the events.
  • A stream processor continuously reads, filters, enriches, aggregates, and detects conditions.
  • Results go to another topic, a database, a cache, or a notification service.
  • Flink suits low-latency stateful pipelines that depend on event time.
  • Kafka Streams suits services already close to Kafka, especially Kafka-to-Kafka transformations.
  • Spark Structured Streaming suits teams already using Spark that want to share logic between batch and streaming.

07Windowing

An endless stream has no point at which every event has arrived, so an aggregation must be given finite boundaries. A window is that boundary.

  • In batch, the input boundary is implicit; in streaming, the query must state how to split the stream.
  • The window choice changes the meaning of the result: a five-minute error rate and an hourly error count answer different questions.
  • Derive the window from the requirement, not from what is convenient to implement.
  • Small windows give fresher results but more output volume and more partial state.
  • Large windows are cheaper per event but delay every result.
  • Session windows need a timeout and per-key state, so they are usually the most expensive.
  • Windows are the foundation for joins and alerts that compare recent behavior to a baseline.
WindowShapeExample use
TumblingFixed, non-overlapping intervals; each event belongs to oneOrders per minute
SlidingOverlapping intervals evaluated on a schedule; an event can appear in manyFive-minute order count, updated every 10 seconds
SessionGrouped by activity with a gap; no fixed lengthA user session ending after 30 minutes idle

08Event time, processing time, and late data

  • Event time is when the event actually happened; processing time is when the processor handles it.
  • Ingestion time, when the event entered the platform, is a third option some systems track.
  • Usually they are close, but network delay can separate them significantly.
  • A phone in a tunnel can produce an order at 12:01 that reaches the processor at 12:06.
  • Processing time would count it in the 12:06 window; event time puts it in the 12:01 window.
  • Analytics and billing usually want event time, because the event belongs to the period when it happened.
  • Operational alerts may accept processing time, because freshness matters more than exact placement.
  • The cost of event time is late-arriving data: the target window may already have emitted its result.

09Watermarks and late-event strategies

  • A watermark estimates how far event time has progressed; it says most events before that point have arrived.
  • When the watermark passes a window's end, the processor can emit that window's result.
  • A watermark is an estimate, not a guarantee; some events can still arrive after it.
  • Aggressive watermarks emit faster but leave more events late; conservative watermarks wait longer for more complete results.
  • Late events can be dropped when the window state is gone — cheap and simple, but the published result stays wrong.
  • They can update the result if the engine keeps state for an allowed lateness period; downstream must accept corrections.
  • A more conservative watermark can wait longer and include the event the first time, at the cost of latency for every window.
  • The event can be sent to a side output and handled by a separate correction path, keeping the main pipeline simple.
Dropping late data is a correctness decision, not just an implementation detail. Decide it with the consumer of the result.

10State, checkpoints, and recovery

  • Stateless work such as filtering needs only the current event; most interesting streaming work needs memory of the past.
  • Running counters, active windows, and recent transaction histories are all state.
  • A fraud rule that detects a card used in three countries within ten minutes must remember that card's recent events.
  • Streaming jobs run for months, so a crash cannot mean starting the count from zero.
  • Engines periodically snapshot state to durable storage; each checkpoint also records the matching stream position, such as a Kafka offset.
  • After a failure, the processor restores the latest checkpoint and resumes from the recorded position.
  • State and position must be saved together; mismatching them causes skipped or double-counted events.
  • State must be partitioned to scale and expired so it does not grow forever — a ten-minute rule needs ten minutes of history.

11Processing guarantees and idempotency

  • Events read after the last checkpoint are read again after recovery, which creates duplicates unless handled.
  • At-least-once plus idempotent writes is the usual practical design.
  • Exactly-once usually covers state inside the engine and sometimes supported sinks; it cannot make every external API exactly-once.
  • A job that calls a payment gateway or sends email still needs idempotency keys, deduplication, or compensation.
  • Ask what a downstream system can observe if the job crashes after processing but before writing output.
  • Transactional sinks or two-phase writes help, but they narrow the set of supported destinations.
  • Guarantees should be stated per input and output, not as a blanket property of the platform.

12Micro-batching

  • Micro-batching collects events for a short interval, such as one second, and processes each group as a small batch.
  • It sits between traditional batch and continuous event-by-event processing.
  • Spark Structured Streaming uses this model by default.
  • It can reuse batch-style execution and recovery, so the engine is simpler to build and operate.
  • Many transformations look the same as their batch equivalents, which helps code reuse.
  • The cost is added latency: every event waits for its batch to be processed.
  • Engines such as Flink support continuous processing for lower latency.
  • Dashboards refreshing every few seconds or tables updating every minute are good fits for micro-batching.

13Side-by-side comparison

  • Modern engines blur the API line: Spark Structured Streaming shares the DataFrame model, and Flink handles bounded and unbounded inputs.
  • Sharing an API does not remove the design questions; a streaming job still needs windows, watermarks, state, and duplicate handling.
  • A batch job still needs scheduling, partitioning, and backfill decisions.
  • Resource shape differs: batch is bursty and can be cheaper when the latency requirement allows it.
  • Choose based on the requirement, not on which engine the team finds more interesting.

14Lambda, Kappa, and how to choose

Large systems often need fast reactions and accurate history at the same time. Lambda and Kappa are two ways to provide both.

  • Lambda runs a batch layer for accurate historical results, a speed layer for recent low-latency results, and a serving layer that combines them.
  • In Lambda, the next batch run replaces what the speed layer computed for that period.
  • Lambda's drawback is maintaining similar logic in two systems and keeping their outputs consistent.
  • Kappa uses one streaming pipeline for both live and historical processing.
  • Reprocessing in Kappa means replaying stored events through a new version of the pipeline.
  • Kappa requires the log to retain events long enough to cover the history you may need to rebuild.
  • Replaying a large history can be expensive even though there is only one implementation.
  • Start with the simplest option that meets the latency requirement: batch for hours, streaming for seconds, micro-batching for a few seconds to minutes.
What latency is required?→How complex is the computation?→How much operational complexity can we staff?→Choose batch, stream, micro-batch, or both

↔Trade-offs to say out loud

  • Batch gives high throughput and easy reprocessing but results are only as fresh as the last job.
  • Streaming gives low latency but adds windows, watermarks, state, recovery, and duplicate handling.
  • Event time produces correct period assignment but waits for watermarks and must handle late data.
  • Processing time is simpler and fresher but places delayed events in the wrong window.
  • Aggressive watermarks emit quickly but drop or correct more late events; conservative watermarks are accurate but slower.
  • Longer state retention enables corrections and richer rules but increases memory, checkpoint size, and recovery time.
  • Micro-batching reuses batch execution and recovery but adds latency compared with continuous processing.
  • Lambda gives fast and accurate results but duplicates logic; Kappa removes duplication but relies on long log retention and replay cost.

?Interview questions

Answer aloud before opening the outline.

1. What is the core difference between batch and stream processing?

Batch processes bounded data in scheduled jobs that finish; stream processing handles unbounded events continuously as they arrive. The practical difference is latency, and the cost is the extra machinery streaming needs for windows, state, and late data.

2. What does bounded versus unbounded data mean?

Bounded data has a known beginning and end, such as one day of orders. Unbounded data is a continuous flow with no final record, such as clicks or sensor readings. The input shape determines whether a job can finish.

3. Why is batch processing easier to operate?

The input is fixed, so logic is easier to test and output can be compared with input. A failed job can be fixed and rerun on the same data, often replacing an output partition so a rerun does not duplicate rows.

4. What is the main limitation of batch processing?

Latency: results are only as fresh as the last completed job. Running jobs more frequently helps, but each run has scheduling and startup overhead, so traditional batch becomes inefficient at very low latency.

5. Why does streaming need windowing?

A stream never ends, so there is no point at which all events have arrived. A window creates a finite set — tumbling, sliding, or session — over which an aggregation can produce a result.

6. Compare tumbling, sliding, and session windows.

Tumbling windows are fixed and non-overlapping. Sliding windows overlap and are evaluated on a schedule, so an event can appear in several results. Session windows group activity with a gap and have no fixed length.

7. What is the difference between event time and processing time?

Event time is when the event occurred; processing time is when the processor handled it. Event time gives correct period assignment for billing and analytics; processing time is simpler and may be fine for fresh operational alerts.

8. What is a watermark?

An estimate of how far event time has progressed. When it passes a window's end, the processor emits that window's result. It is a heuristic, not a guarantee, so some late events can still arrive.

9. How can you handle late events?

Drop them for simplicity, update the result during an allowed-lateness period, wait longer with a conservative watermark, or route them to a side output for later correction. Each choice trades latency, completeness, and complexity.

10. Why is state needed in stream processing?

Many computations depend on previous events: running counts, active windows, joins, deduplication, and pattern detection. The processor must remember recent history per key, which is state.

11. What is a checkpoint, and why must it include the offset?

A checkpoint is a durable snapshot of processor state. It must record the matching stream position, such as a Kafka offset, so recovery restores state and resumes at the same point. Otherwise events are skipped or counted twice.

12. Explain at-most-once, at-least-once, and exactly-once.

At-most-once can lose events. At-least-once loses none but may duplicate. Exactly-once means each event affects the result once for a defined set of inputs and outputs, which usually requires coordination and rarely covers arbitrary external APIs.

13. What is micro-batching, and when is it a good fit?

Collecting events for a short interval and processing each group as a small batch. It reuses batch execution and recovery, at the cost of some latency. It fits dashboards or tables that tolerate a delay of a second or a few seconds.

14. Compare Lambda and Kappa architectures.

Lambda keeps a batch layer for accurate history and a speed layer for low latency, so logic is duplicated. Kappa uses one streaming pipeline and replays a retained log to reprocess history, avoiding duplication but requiring long retention and paying replay cost.

!Traps

  • Choosing streaming for a daily report where batch would be simpler and cheaper.
  • Using processing time for billing, then misplacing events delayed by the network.
  • Assuming a watermark guarantees no more late events will arrive.
  • Dropping late events without agreeing with the consumer that approximate results are acceptable.
  • Saving state and the stream offset separately, causing skipped or double-counted events after recovery.
  • Claiming exactly-once end to end when the job calls an external API with side effects.
  • Maintaining two implementations in Lambda and letting their results diverge.
  • Selecting an engine by preference instead of by the required latency and the team's operational capacity.
