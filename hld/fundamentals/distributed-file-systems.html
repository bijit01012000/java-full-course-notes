In one lineA distributed file system (DFS) presents one familiar namespace — /logs/2026/05/24/app.log — while the bytes behind that path are chunked and replicated across many machines.
Distributed file system
A file system whose data and metadata are spread across multiple machines but exposed through one namespace.
Namespace
The logical directory and file tree that clients see, independent of where the data physically lives.
Metadata server
The component that holds the namespace, file-to-chunk mappings, and chunk locations; the namenode in HDFS.
Data node
A worker machine that stores chunks and serves reads and writes for them.
Chunk
A large fixed-size slice of a file, stored and replicated independently across data nodes.
Replication factor
How many copies of each chunk the system keeps, usually three in HDFS-style designs.
Data locality
Scheduling computation on nodes that already hold the needed chunks, so data does not cross the network.
Block report
A periodic message from a data node listing the chunks it holds, which the metadata server uses to track placement.
Rebalancing
Moving chunks between nodes to even out utilization or restore the replication factor after a failure.

01The problem with a single file system

  • A local file system is bounded by one machine's disks, CPU, and network interfaces.
  • A file larger than any single disk cannot be stored at all.
  • Aggregate throughput is capped by one server's I/O path.
  • Losing that machine loses the data unless something else copies it.
  • Adding capacity means replacing disks or migrating to a bigger machine.
  • Analytics jobs that read the same large dataset from many machines create a hot spot on one server.

02What a distributed file system is

  • A DFS manages files across many machines while presenting one logical namespace.
  • Applications keep using ordinary paths; the split into pieces is invisible.
  • A single path may map to pieces stored on dozens of servers.
  • The DFS tracks where pieces live, reassembles them on read, and checks them for corruption.
  • It also keeps data available when machines fail, typically by replicating pieces.
  • The design goal is capacity and throughput at scale, not low per-operation latency.

03Architecture: metadata plane and data plane

  • A metadata server owns the namespace: directories, file names, permissions, and the mapping from file to chunks.
  • It also tracks which data nodes hold each chunk, built from node registrations and block reports.
  • Clients ask the metadata server where a file's chunks live, then talk to data nodes directly.
  • Data nodes store chunks on local disks and serve read and write requests.
  • The metadata server is not in the data path, so bulk traffic bypasses it.
  • That separation is what lets a modest metadata service coordinate enormous data throughput.
  • It also makes the metadata server the coordination point that must be made highly available.

04How a large file is stored

  • Files are split into large fixed-size chunks rather than whole-file objects or tiny blocks.
  • Large chunks keep the metadata small: one entry per chunk instead of per small block.
  • Each chunk is placed on a data node and replicated to several others.
  • The default placement spreads replicas across machines and racks so one rack failure is survivable.
  • A file's chunk order is recorded in metadata, so reads can reconstruct the byte stream.
  • Chunk size is a trade-off: bigger chunks mean less metadata but coarser load balancing and more wasted space for small files.
Client asks the metadata server to create a file→Metadata server allocates a new chunk and chooses data nodes→Client streams data to the first node→That node forwards the pipeline to the next replica→Acknowledgements flow back once replicas are written

05Read and write paths

  • Read: the client asks for chunk locations, then reads the nearest replica directly.
  • If a read fails or a checksum mismatches, the client retries another replica and reports the bad one.
  • Writes normally flow through a pipeline of data nodes so each replica is written in order.
  • Replication happens during the write, not as a later background copy, for newly written chunks.
  • A client that fails mid-write leaves an incomplete chunk that must be cleaned up.
  • Files are typically append-oriented; random in-place overwrite is not the design centre.

06Fault tolerance

  • Hardware failure is treated as normal, not exceptional: disks and nodes fail continuously at scale.
  • Replication is the primary defense; losing one node does not lose a chunk.
  • Data nodes send periodic heartbeats; missing heartbeats mark a node dead.
  • The metadata server then re-replicates the missing chunks onto healthy nodes.
  • Checksums detect silent corruption, and a corrupt replica is replaced from a good one.
  • Detecting and repairing is continuous background work, which is why cluster health needs monitoring.
  • The metadata server itself must be replicated or backed by a standby, or it becomes the single point of failure.
Data node stops sending heartbeats→Metadata server marks it dead after a timeout→Chunks that were only on that node drop below the replication factor→New replicas are copied from surviving copies→Cluster returns to full replication

07Metadata and coordination limits

  • All namespace operations go through the metadata server, so it caps file and directory operation rates.
  • Chunk location state is held in memory, which bounds how many chunks a single metadata server can track.
  • A single metadata server is a single point of failure unless a standby or replicated design is used.
  • Failover to a standby requires shared or replicated edit logs so the namespace is not lost.
  • Client-side caching of chunk locations reduces metadata round trips but can go stale.
  • Very large clusters often shard the namespace across multiple metadata services.
  • This is the classic tension in DFS design: simple central metadata versus scale and availability.

08Consistency model

  • A DFS usually gives strong consistency for namespace operations such as create, rename, and delete.
  • File content consistency is weaker for concurrent writers to the same file.
  • The common model guarantees that once a write is acknowledged, readers see those bytes, but not a global ordering across independent writers.
  • Append-oriented workloads with one writer per file avoid most conflicts.
  • Many analytics systems assume immutable or append-only files, which sidesteps concurrency entirely.
  • Leases coordinate who may write a chunk and expire if the writer stalls.
  • Design questions should ask who writes a file and whether concurrent mutation is needed at all.

09Performance characteristics

  • A DFS optimizes for high aggregate throughput on large sequential reads, not low latency per operation.
  • Reading many chunks in parallel from many nodes multiplies bandwidth.
  • Data locality lets computation run where the data already is, avoiding network transfer.
  • Small random I/O is a poor fit because each operation pays metadata and network overhead.
  • Many small files stress the metadata server far more than a few large files holding the same bytes.
  • Network topology awareness matters: rack-local reads are cheaper than cross-rack reads.
  • Caching and short-circuit reads help, but the design still favours streaming access.

10Scaling and rebalancing

  • Capacity grows by adding data nodes; the system rebalances chunks onto them.
  • Throughput grows with node count because reads are served in parallel.
  • Decommissioning a node drains its chunks to other nodes before removal.
  • Rebalancing consumes network and disk bandwidth, so it is throttled and scheduled.
  • Skewed placement or hot files create hot nodes even when total capacity is fine.
  • The metadata tier does not scale as easily as the data tier, so it usually needs attention first.
  • Cluster growth is an operational process, not just a hardware purchase.

11Limitations and failure modes

  • The small-file problem: millions of tiny files bloat metadata and overwhelm the namespace server.
  • Low-latency random updates are slow compared with a local disk or block volume.
  • A metadata server outage blocks all namespace operations even if data nodes are healthy.
  • Under-replication after a large failure creates a window where another failure loses data.
  • Slow or flapping nodes cause repeated re-replication and constant background traffic.
  • Misconfigured replication across racks can put all copies in one failure domain.
  • Clients that cache stale chunk locations retry unnecessarily and add load.

12DFS vs block and object storage

  • Block storage gives one server a fast disk; a DFS gives many servers one shared namespace.
  • Object storage offers a flat key space with high durability and HTTP access, without a real directory tree or in-place writes.
  • A DFS supports hierarchical paths, permissions, and append semantics that object stores do not natively provide.
  • Object storage usually wins for cheap archival and serving media over HTTP.
  • A DFS wins when analytics jobs need to read huge files in parallel with locality.
  • A shared file system is also the practical answer when several servers must read and write the same files.
  • Choose by access pattern: random low-latency, shared hierarchical files, or cheap durable objects.

↔Trade-offs to say out loud

  • Centralized metadata keeps the namespace simple and consistent, but caps namespace throughput and needs its own failover.
  • Large chunks shrink metadata and improve streaming, but waste space on small files and make balancing coarser.
  • Replication factor 3 survives multiple failures, but triples raw storage cost.
  • Data locality avoids network transfer for analytics, but ties computation to placement and complicates scheduling.
  • High aggregate throughput comes from parallel chunk reads, at the cost of poor small-random latency.
  • Append-oriented semantics simplify consistency, but make in-place updates and random writes awkward.
  • Lazy re-replication avoids overreacting to transient failures, but leaves a window of reduced redundancy.
  • Growing the data tier is straightforward, but the metadata tier remains the harder scaling problem.

?Interview questions

Answer aloud before opening the outline.

1. What is a distributed file system?

A file system that stores data across many machines while presenting a single hierarchical namespace to applications. Files are split into chunks, placed on data nodes, and usually replicated. The system tracks placement, reassembles reads, verifies checksums, and repairs lost copies.

2. Why not just use one big server with many disks?

A single server caps capacity and throughput at its own hardware and is a single failure domain. A DFS adds nodes to increase both capacity and parallel read bandwidth, and tolerates node loss through replication. It also lets computation run next to the data.

3. How does the metadata server stay out of the data path?

Clients ask it only where chunks live, then read and write directly to data nodes. Bulk bytes therefore never flow through the metadata server, which keeps it from becoming a throughput bottleneck. It handles namespace operations and placement decisions instead.

4. How is a large file stored?

It is split into large fixed-size chunks, each stored on a data node and replicated to others. Metadata records the ordered list of chunks and their locations. On read, the client fetches chunks in parallel and assembles the byte stream.

5. What happens when a data node fails?

The metadata server notices missing heartbeats and marks the node dead. Chunks that were only on that node fall below the replication factor, so new copies are made from surviving replicas. Reads continue from other replicas in the meantime, possibly with higher latency.

6. What consistency does a DFS provide?

Namespace operations such as create and rename are strongly consistent because they go through one metadata authority. File content guarantees are usually weaker for concurrent writers, often only promising that acknowledged bytes are visible. Append-oriented, single-writer workloads avoid most of the problem.

7. Why are many small files a problem?

Each file and chunk consumes metadata entries in the namespace server's memory. Millions of tiny files exhaust that capacity and drive far more metadata operations than a few large files with the same total bytes. Small files also make chunk-level placement and balancing inefficient.

8. What is data locality and why does it matter?

It means running computation on nodes that already store the needed chunks, so the data does not cross the network. For analytics scanning huge datasets, moving computation is far cheaper than moving bytes. This is why DFS designs are paired with schedulers that respect placement.

9. How does a DFS scale?

Capacity and read throughput scale by adding data nodes, with background rebalancing to spread chunks. The metadata tier does not scale as easily, since it holds namespace state and coordinates placement. Large clusters may shard the namespace or use replicated metadata services.

10. DFS vs object storage — when do you pick which?

Pick a DFS when you need a shared hierarchical namespace, append semantics, and parallel reads for analytics with locality. Pick object storage for cheap, durable storage of large immutable objects served over HTTP, such as media and backups. A DFS is not a low-latency random-access store for a database.

11. What is the single point of failure in a DFS?

The metadata server. If it is unavailable, clients cannot resolve paths or learn chunk locations even though data nodes are healthy. Designs address this with a standby, replicated edit logs, and fast failover, or by sharding the namespace.

12. Would you run a database on a distributed file system?

Usually not. Databases need low-latency random writes and fsync semantics, which a network DFS serves poorly. They run better on local or network-attached block storage, with the database's own replication providing durability. A DFS suits large append-heavy files and analytics workloads.

!Traps

  • Using a DFS as a low-latency database volume and blaming the database for slow commits.
  • Storing millions of tiny files and exhausting metadata memory.
  • Assuming replication replaces backups, when a deleted file is deleted from every replica.
  • Forgetting that the metadata server is a single point of failure.
  • Declaring the cluster healthy while chunks sit under-replicated after a node loss.
  • Placing all replicas in one rack and losing them together.
