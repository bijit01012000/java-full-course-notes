01The problem with DNS-based routing

Running a service in Tokyo, Frankfurt, and Virginia means you need to decide which location each user reaches.

  • A DNS provider can return the address of a nearby region based on the query location, and that works for the steady state.
  • The first problem is caching: if Tokyo fails, users keep connecting to its old address until their cached answer expires.
  • The second problem is location accuracy: DNS often sees the user's recursive resolver, not the user.
  • A resolver in another country can send a user to a region that is not actually closest.
  • DNS also cannot react to the path between the user and the region, only to coarse geography.
  • Anycast removes the choice from DNS: every location advertises the same address and the network decides.

02IP routing models

  • Unicast is the default: one address maps to one endpoint, and packets route toward it. Web, APIs, and databases all use it.
  • Broadcast sends to every device on a local network, for example DHCP discovery.
  • Multicast delivers to receivers that joined a group, used in some video distribution and market-data networks.
  • Anycast shares one address across many locations, and each packet reaches exactly one of them.
  • The difference between anycast and unicast is not the packet format but how many places advertise the prefix.
  • Broadcast does not cross routers, which is why it stays a local-network tool.
  • Multicast requires network support end to end, so it is rarely available across the public internet.

03BGP and autonomous systems

  • The internet is a network of networks, each an autonomous system with its own routing policy and AS number.
  • BGP is how those systems tell each other which address prefixes they can reach.
  • Each announcement carries attributes such as the AS path, which routers use to compare candidate routes.
  • Routers normally prefer the shortest AS path, so a location that is fewer hops away tends to win.
  • BGP is a policy protocol as much as a shortest-path protocol: operators can prefer, prepend, or filter routes.
  • Anycast works because the same prefix can be announced from several AS locations, and each network picks its own best route.
  • Convergence is not instant: withdrawals and new announcements take time to propagate across the internet.

04How a packet reaches an anycast location

  • Every location advertises the same prefix, so routers worldwide hold several candidate paths to that address.
  • A given network selects one best path based on BGP attributes and local policy, typically the nearest in AS-hop terms.
  • Packets from that network then consistently reach that location, which keeps a connection stable.
  • Different networks may select different locations, which is exactly how the load is spread geographically.
  • Because routing is per network rather than per user, all users behind one provider often hit the same site.
  • Within a location, ordinary load balancers still distribute requests across servers.
  • The address is shared, but a TCP connection still terminates at one specific machine.
Every region announces the same prefix→Routers compute their best path→Client packets follow the chosen path→Packets arrive at one region→Regional load balancer picks a server

05Failover and withdrawal

  • When a location fails, it stops announcing the prefix, or its upstream stops accepting the announcement.
  • Routers then recompute and send traffic to the next-best location for that prefix.
  • Failover is driven by routing convergence, so it is usually much faster than waiting for DNS TTLs.
  • Anycast also absorbs some attacks for free: traffic is spread across many locations instead of concentrating on one.
  • The catch is connection state: existing TCP sessions to a failed site break and must be re-established.
  • Convergence time varies by network, so some clients recover sooner than others.
  • A common failure is a partial withdrawal, where some networks still route to a degraded site.
Anycast failover is often described as “the routing table heals”, but the application must still tolerate broken connections and retries.

06Where anycast is used

  • DNS is the classic case: root and public resolvers share addresses so queries reach a nearby instance.
  • CDN edges announce shared addresses so users terminate at a nearby point of presence.
  • DDoS mitigation uses anycast to spread attack traffic across many scrubbing locations.
  • Global entry points for APIs and load balancers give users one address with regional delivery.
  • Public time services and some gaming and voice platforms use it for latency.
  • In private networks, anycast is used for resilient DNS and NTP servers inside a data centre.
  • The pattern is always the same: stateless or connection-local service, replicated widely, reachable at one address.

07Limitations

  • Routing is coarse and network-based, not per user, so load distribution follows provider topology rather than population.
  • A large ISP can send all of its users to one site, creating imbalance that is hard to correct.
  • Existing connections cannot migrate: when a site fails, sessions break rather than move.
  • Long-lived TCP sessions are pinned to a location for their entire lifetime.
  • BGP convergence is measured in seconds to minutes and is not uniform across the internet.
  • Operating anycast means running BGP, which brings prefix hijack and route-leak risk plus a new operational skill set.
  • Debugging is harder because the path a user takes depends on their provider's routing decisions.
  • Application state, caches, and sessions must tolerate users moving between sites between connections.

08Anycast vs DNS load balancing

  • DNS chooses a location before the connection and can be overridden by caching.
  • Anycast chooses a location per packet path, so caches cannot override it and failover is not gated by TTL.
  • DNS gives explicit control: weights, region rules, and residency policy.
  • Anycast gives automatic proximity and resilience, but you surrender fine-grained control.
  • DNS can express application meaning such as tenant or canary; anycast can only express network reachability.
  • Many systems combine them: anycast addresses for the entry point, with DNS or a global balancer for policy above it.
  • For a new global service, anycast is usually the better default for the front door, with DNS as the control plane.

09Operating an anycast service

  • Keep sites stateless or locality-aware; never assume a user stays on one site between connections.
  • Replicate data close enough that a user routed to a different site still finds their session or cache.
  • Monitor per site: traffic share, health, and latency, because a silent site is invisible in aggregate metrics.
  • Watch for traffic shifting unexpectedly after a routing change, which often signals a leak or a bad announcement.
  • Test failover by withdrawing a site deliberately and observing real client recovery.
  • Guard against prefix hijacks and route leaks with strict filters and RPKI validation where available.
  • Use consistent TLS certificates and configuration across sites so a failover does not also become a certificate error.

↔Trade-offs to say out loud

  • Anycast gives automatic proximity and fast failover but removes control over which site a client reaches.
  • DNS routing gives policy control but failover is bounded by caching and TTLs.
  • Shared prefixes spread load and absorb attacks but make traffic distribution depend on ISP topology.
  • Connection pinning keeps TCP stable within a session but guarantees broken connections on failover.
  • Running BGP unlocks global anycast but adds hijack, leak, and operational complexity risk.
  • Wide replication improves locality but multiplies data consistency and cost problems.
  • Per-site monitoring catches silent failures but is more expensive than aggregate dashboards.
  • Combining anycast with DNS gives resilience and control but means operating two control planes.

?Interview questions

Answer aloud before opening the outline.

1. What is anycast in one sentence?

Several locations advertise the same IP address, and the routing system delivers each packet to just one of them, usually the nearest according to BGP. Users see a single address while traffic is served from many sites.

2. How does anycast differ from unicast and multicast?

Unicast has one address per endpoint, multicast delivers to a group that joined, and anycast shares one address across many locations with delivery to exactly one. Anycast reuses ordinary unicast packets; the difference is how many places announce the prefix.

3. Why is anycast often better than DNS for failover?

DNS failover waits for cached answers to expire, which can take minutes. Anycast failover waits for BGP convergence, which is also imperfect but is not gated by client or resolver caching, so traffic shifts once routes are withdrawn.

4. What role does BGP play?

BGP is how autonomous systems tell each other which prefixes they can reach. Anycast works because the same prefix is announced from multiple sites, and each network selects its own best path based on BGP attributes and policy.

5. What happens to open connections when an anycast site fails?

They break. Routing changes affect new packets, but an established TCP connection is tied to the failed site's state, so the client must reconnect and may land on a different site. Applications need retries and reconnect logic.

6. Why can anycast produce very uneven load?

Routing decisions are made per network, not per user, so a large ISP may send all of its subscribers to one site. Traffic distribution follows internet topology, which rarely matches population or capacity.

7. Where is anycast commonly used?

DNS resolvers and root servers, CDN edges, DDoS scrubbing networks, global API entry points, and internal DNS or NTP inside data centres. The common trait is a service that is replicated and does not depend on per-user server state.

8. What does anycast cost you operationally?

You need BGP expertise, peering or provider support, prefix filtering, and per-site monitoring. You also accept hijack and route-leak risk, plus a debugging model where the path depends on someone else's routing policy.

9. How do you handle sessions with anycast?

Keep them out of local server memory: use signed tokens or a replicated session store so a reconnect to another site still works. Design for the assumption that a user can change sites between connections.

10. Would you use anycast for a database?

Not for the primary. Anycast suits stateless or read-mostly services where any site can serve any request; a writable primary needs consistent routing to one location. Read-only replicas can sit behind anycast if staleness is acceptable.

11. How does anycast help against DDoS?

Attack traffic is spread across many announcing sites instead of concentrating on one address, and scrubbing capacity is distributed too. It does not remove the attack, but it raises the capacity required to saturate you and shortens the path to mitigation.

12. How would you combine anycast and DNS?

Use anycast for the global entry address so users reach a nearby point of presence automatically, and keep DNS or a global traffic manager above it for policy, weights, canaries, and residency rules.

!Traps

  • Assuming anycast migrates live connections; it only changes where new packets are routed.
  • Expecting anycast to distribute load evenly across sites regardless of ISP topology.
  • Running anycast without per-site monitoring, so a silent site keeps attracting traffic.
  • Forgetting that BGP convergence is not instant or uniform across the internet.
  • Putting a stateful primary behind anycast and expecting consistent writes.
  • Announcing prefixes without route filters, exposing yourself to hijacks and leaks.
  • Treating anycast as a replacement for a load balancer inside a region; it only chooses the site.
