In one lineAn API gateway is the single stable front door for outside clients: it routes each request to the right service and centralizes authentication, rate limiting, TLS, and response shaping.
API gateway
A server that sits between external clients and internal services, routing requests and centralizing cross-cutting edge concerns.
North-south traffic
Traffic entering or leaving the system from outside clients, which the gateway handles.
East-west traffic
Service-to-service traffic inside the system, usually handled by discovery, load balancing, or a mesh rather than the gateway.
Request aggregation
Calling several backend services for one client request and merging the results into a single response.
TLS termination
Ending encryption at the gateway so backend services receive plain traffic inside a trusted network.
Rate limiting
Restricting request volume per client, key, or route to protect services and enforce quotas.
Backend for frontend
A gateway variant dedicated to one client type, with an API shaped for that client's experience.
Service discovery
The mechanism that lets the gateway find healthy instances of each backend service.
Single point of failure
A component whose outage takes down the whole request path, which the gateway becomes if it is not made redundant.

01The problem with calling services directly

An e-commerce system split into user, product, order, payment, and review services exposes a separate API for each.

  • A mobile product page needs product details, reviews, and the user's saved addresses.
  • Without a gateway, the client calls each service directly over the public network.
  • The client must know every service address and keep that list current.
  • The client must implement retries, timeouts, and partial-failure handling for each dependency.
  • Every service independently re-implements authentication, quotas, and logging.
  • Internal refactoring becomes a client-visible breaking change.
  • The result is a chatty, brittle client coupled to backend topology.

02The client knows too much and calls too often

  • The client holds a hard-coded map of services, which must change whenever the backend is split or renamed.
  • Multiple round trips over a mobile connection multiply latency and failure probability.
  • Sequential calls add up; parallel calls still wait for the slowest dependency.
  • The client needs per-call retry, timeout, and fallback logic, duplicated on every platform.
  • Partial failure is hard: one service failing should degrade a section, not blank the page.
  • Caching and compression decisions are pushed into every client.
  • Each new client re-solves the same orchestration problem.

03Every service repeats the same work

  • Each exposed service validates external tokens, so auth logic is copied and can drift.
  • Rate limits are configured per service, producing inconsistent protection.
  • Every service manages its own public certificates and TLS settings.
  • CORS policy is configured in many places and easily misconfigured.
  • Request logging uses different fields and formats, so correlation across services breaks.
  • Duplication raises the chance that one service gets a security check wrong.
  • The public boundary is the first security boundary, so one gap is enough.

04The backend structure leaks to clients

  • Splitting the product service into catalog and pricing would break every direct client.
  • Service names and routes become a public contract that is expensive to change.
  • Mobile apps make this worse: old versions stay installed for months.
  • The backend cannot reorganize without coordinating with client releases.
  • Internal APIs get shaped by external client quirks instead of domain design.
  • Versioning becomes a per-service negotiation rather than one edge policy.
  • This coupling is the organizational reason gateways appear.

05What an API gateway is

  • A single entry point in front of many backend services.
  • Clients send every request to the gateway and never address services directly.
  • The gateway decides which service or services should handle the request.
  • It can translate protocols, for example exposing REST while calling gRPC internally.
  • It hides internal topology, so services can split, merge, or move.
  • It concentrates edge concerns in one deployable component with one policy.
  • It is a north-south component: it handles external traffic, not service-to-service calls.

06Core responsibilities

  • Routing by path, host, header, or method to the correct service and version.
  • Authentication and authorization: validate tokens once, forward trusted identity claims.
  • Rate limiting and quotas per client, API key, or route.
  • TLS termination and certificate management at the edge.
  • Request and response shaping, including aggregation for chatty screens.
  • Observability: one request ID, consistent access logs, and edge metrics.
  • Resilience: timeouts, retries with budgets, circuit breaking, and payload limits.
  • Not every gateway does all of this; choose the set the system actually needs.

07How a request flows

  • The client connects to one hostname and presents a token.
  • The gateway terminates TLS and authenticates the caller.
  • It applies rate limits, request size limits, and route matching.
  • It resolves the target service through discovery and picks a healthy instance.
  • For composite screens it fans out to several services with per-call timeouts.
  • It merges, filters, and caches responses before returning one payload.
  • It records latency, status, and a correlation ID for every hop.
Client calls gateway→TLS termination and authentication→Rate limit and route match→Discover target instance→Call backend services→Aggregate and shape response→Log, meter, and return

08Gateway versus neighbouring components

  • A load balancer distributes connections across instances but does not understand APIs.
  • A reverse proxy forwards traffic and can cache, but usually lacks API-aware auth and aggregation.
  • An API gateway adds routing by API semantics, auth, quotas, and composition.
  • A service mesh handles east-west traffic between services, with mTLS, retries, and telemetry.
  • A BFF is a gateway per client type, shaped for one experience.
  • These roles overlap in products, so separate the responsibilities conceptually before buying a tool.
  • Many systems use a gateway at the edge and a mesh inside.

09The gateway as a new single point of failure

  • Every request now passes through one component, so its outage is a total outage.
  • Run multiple gateway instances behind a load balancer across availability zones.
  • Keep the gateway stateless so instances can be replaced freely.
  • Avoid per-instance configuration drift by treating routes as versioned configuration.
  • Protect against cascading failure with connection limits to each backend.
  • Plan capacity for peak traffic plus failover headroom, not average load.
  • Test gateway failure and failover explicitly; it sits on the critical path.

10Performance and the latency budget

  • The gateway adds at least one network hop and some processing time to every request.
  • Keep the hot path lean: avoid heavy transformation and unnecessary body parsing.
  • Reuse upstream connections with pooling instead of opening one per request.
  • Cache safe, cacheable responses at the edge where correctness allows.
  • Set explicit per-route timeouts so one slow service cannot hold edge capacity.
  • Aggregation in parallel reduces total time only to the slowest included call.
  • Measure gateway latency separately from backend latency to attribute regressions.
A gateway that saves client round trips usually wins overall, but only if its own overhead stays small and predictable.

11Failure modes and resilience

  • Retries at the gateway multiply load during an outage; use budgets and jitter.
  • Aggressive aggregation turns one backend slowdown into a fully failed screen.
  • A shared connection pool to a hot service can saturate and stall unrelated routes.
  • Large request bodies can exhaust memory if limits are absent.
  • A bad route configuration deploy can misroute all traffic at once.
  • Auth token caches that are too long-lived delay revocation.
  • Missing fallbacks turn partial degradation into blank pages.

12Operating and evolving the gateway

  • Treat routes, policies, and limits as code with review and rollback.
  • Version the external API at the edge, not inside every service.
  • Roll out configuration changes gradually and watch error and latency metrics.
  • Keep business logic out: the gateway routes and enforces policy, it does not price orders.
  • Document which concerns live at the edge versus inside services.
  • Give the platform team ownership, with client teams proposing routes through review.
  • Revisit the gateway when it becomes a deployment bottleneck for every team.

13Anti-patterns and decision rules

  • God gateway: every feature adds logic until it is an unmaintainable monolith at the edge.
  • Chatty aggregation: fanning out to many services per request with no caching or batching.
  • Putting domain rules in the gateway duplicates logic and drifts from the services.
  • Using a gateway to hide a broken service design instead of fixing the API.
  • Adopting one too early for a single-service system adds a hop with no benefit.
  • Adopt it when clients are many, services are many, or edge concerns are duplicated.
  • If only one client type needs shaping, a BFF is the better fit.

↔Trade-offs to say out loud

  • Single entry point simplifies clients but concentrates availability risk in one tier.
  • Centralized auth removes duplication but makes the gateway a security-critical component.
  • Aggregation reduces client round trips but couples the gateway to multiple service contracts.
  • Edge caching cuts latency and backend load but risks serving data that is stale or user-specific.
  • Protocol translation decouples clients from internals but adds transformation cost and mapping bugs.
  • One policy layer gives consistent limits but can become a release bottleneck for all teams.
  • Hiding topology lets the backend evolve but makes debugging require correlation across the gateway.
  • Extra hop buys control and observability at the cost of latency and another component to operate.

?Interview questions

Answer aloud before opening the outline.

1. What problem does an API gateway solve?

It gives external clients one stable entry point instead of direct access to every service. That removes client-side service discovery and orchestration, centralizes authentication and rate limiting, and hides internal topology so services can change without breaking clients.

2. What does a gateway typically do?

Routes requests by path or host, terminates TLS, authenticates callers, enforces quotas, aggregates several backend calls, translates protocols, and emits consistent logs and metrics. It should not hold business rules.

3. How is a gateway different from a load balancer?

A load balancer distributes connections across instances and knows nothing about API semantics. A gateway understands routes, tokens, quotas, and response composition, and it usually sits behind or alongside a load balancer that spreads traffic across gateway instances.

4. How is it different from a service mesh?

The gateway handles north-south traffic from outside clients. A mesh handles east-west traffic between services, providing mTLS, retries, and telemetry. Many systems run both, each with a distinct responsibility.

5. How is it different from a BFF?

A BFF is a gateway dedicated to one client type and shaped for that experience; a general gateway serves all clients with one API. Start with a gateway, and split out a BFF when client needs diverge sharply.

6. Does a gateway become a single point of failure?

Yes, because all traffic passes through it. Mitigate with multiple stateless instances across zones, a load balancer in front, versioned configuration, connection limits per backend, and tested failover.

7. How does aggregation work and what does it cost?

The gateway calls several services, applies per-call timeouts, and merges the results into one response. It saves client round trips but couples the gateway to several contracts, and total latency is bounded by the slowest included call.

8. Where should authentication happen?

At the edge: the gateway validates the external token once, rejects unauthenticated calls, and forwards trusted identity claims to services. Services still enforce authorization on their own resources, because the gateway cannot know every domain rule.

9. What are common gateway failure modes?

Retry storms during outages, aggregation turning one slow service into a failed screen, connection pool saturation, missing payload limits, and a bad configuration deploy misrouting everything. Timeouts, budgets, limits, and staged rollouts address them.

10. Should the gateway contain business logic?

No. Business rules in the gateway duplicate service logic, drift, and make the edge a deployment bottleneck. Keep it to routing, policy, and light shaping; push domain decisions into services.

11. When is a gateway unnecessary?

For a single service, a small number of trusted clients, or when edge concerns are not duplicated. Adding a gateway there adds a hop and an operational component with little benefit.

12. How do you version APIs at the edge?

Expose stable, versioned external routes at the gateway and map them to current internal services. That lets services split or change while old client versions keep working, which matters most for mobile apps that upgrade slowly.

!Traps

  • Letting the gateway accumulate business logic until it becomes a monolith at the edge.
  • Running a single gateway instance and discovering it is a single point of failure during an incident.
  • Adding retries at the gateway without budgets, turning a backend slowdown into a retry storm.
  • Aggregating many services per request with no per-call timeout, so the slowest dependency fails the page.
  • Treating the gateway as a replacement for service-to-service discovery or a mesh.
  • Exposing internal service routes as a permanent public contract and then being unable to split them.
  • Skipping payload size limits and letting large uploads exhaust gateway memory.
