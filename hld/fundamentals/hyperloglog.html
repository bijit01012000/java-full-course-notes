HyperLogLog
A probabilistic structure that estimates the number of distinct items in a multiset using a fixed, small array of registers.
Register
One small counter in the sketch that stores the maximum rank observed for the items hashed into it.
Precision (p)
The number of hash bits used to choose a register, giving m = 2^p registers and setting both memory and accuracy.
Rank
The position of the leftmost 1 bit in the remaining hash bits, equivalent to one plus the count of leading zeros.
Stochastic averaging
Splitting the stream across many registers and combining their estimates, which reduces variance compared with one counter.
Relative standard error
The typical relative error of the estimate, approximately 1.04 / sqrt(m).
Linear counting
The small-cardinality correction that behaves like counting occupied registers when few are set.
Sparse representation
A compact encoding used while few registers are non-zero, which is promoted to a full register array as cardinality grows.
Merge by maximum
Combining two sketches register by register with max, which yields the estimate for the union of both streams.

01The problem: how many distinct items?

A content platform wants to show how many unique readers each article received today.

  • The metric is distinct users, not total views: one person reading ten times counts once.
  • The exact approach keeps a set of user IDs per article and adds each viewer's ID.
  • Set semantics handle the deduplication automatically, and the final size is the answer.
  • This is correct and simple, and it works perfectly at small scale.
  • The trouble starts when the cardinality of each set becomes very large and the number of sets multiplies.
  • The question is whether the exact identity of each reader is actually needed, or only the count.

02Why exact counting gets expensive

  • A popular article with tens of millions of unique readers needs hundreds of megabytes just for the IDs, before hash-set overhead.
  • That cost is per article per day, and platforms have enormous numbers of articles.
  • Every additional slice — week, month, country, device — needs its own set.
  • Combining exact counts across servers means shipping every ID to one place to deduplicate.
  • Retention multiplies the problem: keeping daily sets for a year multiplies memory by the number of days.
  • So exact distinct counts scale with cardinality times the number of slices, which is the wrong shape for analytics.
  • A fixed-size summary per slice would make cost independent of traffic volume.

03What HyperLogLog is

  • It estimates cardinality from a fixed array of m registers, without storing any item.
  • Each item is hashed to a large integer; part of the hash picks a register, the rest determines a rank.
  • The register keeps the maximum rank it has seen, so each register summarizes a subset of the stream.
  • The estimate combines all registers, corrected for the expected statistical behavior of random hashes.
  • Accuracy depends on m, not on how many items were seen.
  • The structure is mergeable, which makes it a natural fit for distributed and time-bucketed analytics.
  • It answers "how many distinct" and nothing else: not which items, not how often.

04The core observation: leading zeros are rare

  • For a uniformly random hash, the probability of the first bit being 1 is one half.
  • The probability of starting with two zeros and then a one is one quarter, and so on, halving each time.
  • So observing r leading zeros before the first 1 is roughly as rare as one event in 2^r.
  • If the rarest pattern you have seen requires r zeros, you have probably seen on the order of 2^r distinct items.
  • A single maximum is far too noisy: one lucky hash would dominate the estimate.
  • The fix is to average many independent observations, which is exactly what splitting the hash space into registers does.
  • This is the entire intuition: cardinality is inferred from how rare the rarest hashes look.

05Registers and stochastic averaging

  • Use the first p bits of the hash to select one of m = 2^p registers.
  • Use the remaining bits to compute the rank: one plus the number of leading zeros, or the position of the first 1.
  • Store the maximum rank per register, since duplicates and ordering do not affect a maximum.
  • Each register therefore tracks the rarest hash among roughly n/m items.
  • Averaging across registers reduces variance by a factor of roughly m, which is the point of the split.
  • Averaging is done on 2^-rank values, a harmonic mean, because that is the quantity with the right expectation.
  • Adding the same item twice changes nothing, which is why the structure estimates distinct counts rather than totals.

06The estimator

  • The classic estimator is E = alpha * m^2 / sum(2^-M[j]) over all registers.
  • The denominator is a harmonic-style sum: registers with high ranks contribute tiny values, so they raise the estimate strongly.
  • The constant alpha corrects for the bias of the harmonic mean at a given m.
  • The estimate is then adjusted for small and large cardinalities, where the raw formula is biased.
  • The arithmetic is cheap: one pass over the registers, no data scan.
  • Estimates are not exact integers and should be rounded only at presentation time.
  • Implementations sometimes smooth small values with a different estimator entirely, because the raw formula is poor when few registers are set.

07Accuracy and the precision knob

  • The relative standard error is approximately 1.04 / sqrt(m), so accuracy improves with the square root of memory.
  • Doubling m multiplies memory by two and reduces error by about 1.4.
  • Each register needs only a handful of bits because ranks are small, which is why the whole sketch is tiny.
  • p is usually chosen to give an error appropriate to the metric: dashboards tolerate more error than billing.
  • The error is statistical, not adversarial: it is a typical deviation, and individual results can fall outside it.
  • The same precision must be used for sketches that will be merged.
  • A larger sketch also reduces the chance that the hash space itself limits the maximum observable rank.

08Small and large range corrections

  • At small cardinalities most registers are still zero, and the raw estimator overestimates badly.
  • Linear counting handles this by treating the number of occupied registers as a sample of a coupon-collector process.
  • Implementations switch to that estimate below a threshold related to m.
  • At extremely large cardinalities, hash collisions and the finite hash width make the estimate saturate.
  • A large-range correction compensates, and wider hashes reduce the problem.
  • A practical implementation therefore has three regimes: linear counting, the main estimator, and the large-range correction.
  • Skipping the corrections is the usual reason a home-grown sketch is wrong at both ends of the range.

09Merging and distributed analytics

  • Two sketches with the same precision merge by taking the register-wise maximum.
  • That is correct because each register's maximum is a summary of the union of the underlying streams.
  • Union is exact; intersection and difference are not directly computable from sketches.
  • Merging is associative and commutative, so aggregation order does not matter.
  • This allows per-server sketches to be shipped and combined at a fraction of the cost of shipping IDs.
  • Daily sketches can be merged into weekly and monthly views without storing raw events.
  • Sketches with different precisions cannot merge, so the parameter is part of the data contract.

10Implementations and variants

  • Redis exposes PFADD, PFCOUNT, and PFMERGE, keeping each key to a small fixed footprint.
  • Redis uses a sparse encoding while cardinality is low and promotes to a dense register array as it grows.
  • HyperLogLog++ improves small-range accuracy with bias correction and a sparse representation.
  • Database and analytics engines embed sketches as aggregate types so dashboards can merge partial results.
  • Some systems ship a sketch per time bucket and merge at query time, avoiding pre-aggregation of every slice.
  • Variant differences matter mostly at low cardinality and at extreme scale.
  • Treat the sketch as an opaque serialized value with a version and precision, not as a portable raw array.

11Limitations

  • No membership test: you cannot ask whether a specific user was counted.
  • No per-item counts: it estimates distinct cardinality only.
  • No direct intersection or set difference; only union via merging.
  • Error is inherent and statistical, so two runs over the same data with different hash seeds can disagree slightly.
  • Small cardinalities need the correction path, and home-grown code usually gets this wrong.
  • Extremely large cardinalities approach the limits of the hash width.
  • Cost is per sketch: many slices mean many sketches, and cardinality per slice still multiplies storage.

12When to use it

  • Unique visitors, unique viewers, unique search queries, and any distinct-count metric over large streams.
  • Cardinality estimation for query planners and for capacity planning.
  • Distributed aggregation where shipping raw IDs is impossible or too expensive.
  • Real-time dashboards that need approximate counts within seconds of ingestion.
  • Do not use it when the exact count is contractual, when you must identify members, or when the set is small enough for a hash set.
  • Pair it with exact counting for the few dimensions that must be precise, and use sketches for the long tail of slices.
  • Choose it over a Bloom filter when the question is "how many" rather than "is this one present".

↔Trade-offs to say out loud

  • Fixed memory makes cost independent of cardinality but gives up exactness and membership.
  • More registers improve accuracy but increase memory and serialization size.
  • Fewer registers shrink the sketch but widen the error band on every reported number.
  • Merging by max makes union cheap but offers no way to compute intersection or difference.
  • Sparse encoding saves memory at low cardinality but adds conversion complexity.
  • Bias correction improves small-range accuracy but ties the data to a specific implementation version.
  • Per-slice sketches keep dashboards flexible but multiply the number of sketches stored.
  • Approximate counts reduce infrastructure cost but cannot support exact billing or audit.

?Interview questions

Answer aloud before opening the outline.

1. What does HyperLogLog actually measure?

It estimates the number of distinct items in a multiset — the cardinality — using a fixed-size array of registers. Repeats contribute nothing because registers only keep a maximum. It cannot tell you which items were seen or how often each appeared.

2. Why does counting leading zeros estimate cardinality?

For a uniform hash, r leading zeros before the first one occurs with probability about 2^-r. So the rarest pattern observed suggests a set size on the order of 2^r. A single maximum is too noisy, so the hash space is split into many registers whose observations are averaged.

3. Why split into registers instead of one counter?

One maximum has enormous variance: a single lucky hash dominates the estimate. Using m registers means each summarizes a smaller slice of the stream, and combining them reduces variance by roughly a factor of m. That is stochastic averaging.

4. How accurate is it?

The relative standard error is about 1.04 / sqrt(m), so accuracy improves with the square root of register count. That is a typical deviation, not a hard bound. Doubling registers cuts error by about 1.4, which is why the sketch stays small.

5. What does the precision parameter control?

It sets how many hash bits select a register, so it fixes m = 2^p. That determines both memory and error. All sketches that will be merged must use the same precision, so it is part of the schema.

6. Why are there special cases for small and large counts?

When few registers are set, the raw harmonic estimator overestimates, so implementations use linear counting based on occupied registers. At extreme cardinalities the finite hash width causes saturation, so a large-range correction applies. Both corrections are needed for the estimate to be usable across the whole range.

7. How do you merge two sketches?

Take the register-wise maximum, because each register's maximum summarizes the union of the streams. Merging is associative, so partial results can be combined in any order. This is what makes distributed distinct counts practical.

8. Can you compute the intersection of two audiences?

Not directly. Union is available through merging, but intersection and difference cannot be derived from cardinality sketches alone, because they lose the identities that overlap detection needs. Inclusion-exclusion over union and individual counts only works if you also know the intersection, which you do not.

9. How would you count unique readers per article per day?

Keep one sketch per article per day, updated on each view, and merge them for weekly or monthly totals. Sketches stay tiny, so many slices fit in memory or a small store. If a specific reader must be verified, keep a separate exact source for that case.

10. HyperLogLog or an exact set?

Use an exact set when the cardinality is modest, when you need membership, or when the number is contractual. Use HyperLogLog when cardinality is huge, many slices are tracked, and a small relative error is acceptable. The decision is about whether identity matters, not just size.

11. HyperLogLog or Count-Min Sketch?

HyperLogLog answers "how many distinct items" and ignores repetition. Count-Min Sketch answers "how often did this item appear" and overestimates. Both are tiny fixed-size summaries, but they answer different questions and are not interchangeable.

12. What breaks if two teams use different precisions?

Their sketches cannot be merged, and forcing a merge by padding or truncating produces a biased estimate. Precision, hash seed, and implementation version form a contract. The safe approach is to fix them centrally and version the serialized format.

!Traps

  • Using HyperLogLog to answer membership or per-item frequency questions.
  • Skipping small-range correction and reporting badly inflated counts for low-cardinality slices.
  • Merging sketches built with different precisions or hash seeds.
  • Treating the error bound as a hard guarantee rather than a standard deviation.
  • Assuming intersections can be derived from merged cardinalities.
  • Keeping one sketch per tiny slice without bounding the number of slices, so storage still explodes.
