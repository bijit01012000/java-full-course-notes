01The problem: transactional and analytical work pull in opposite directions

Production databases are built for small, fast reads and writes. Business questions scan months of history and group it in many ways.

  • An OLTP database serves point lookups and short transactions, with indexes tuned for finding a few rows.
  • An analytical query may scan most of a large table and aggregate it, which is the opposite access pattern.
  • Running those scans on the production primary competes for CPU, I/O, and buffer cache with user traffic.
  • The data needed often spans several systems, and the production schema does not contain the history or conformed dimensions required.
  • Operational schemas change for application reasons, which makes them a poor contract for reporting.
  • A warehouse is a separate store built for analysis, loaded from sources on a schedule.

02Schema-on-write: model before you load

  • The warehouse declares tables, columns, types, and keys before data is queryable.
  • Loads validate and transform data to match that contract, rejecting or quarantining violations.
  • Because the schema is enforced once, every reader can trust column names and types.
  • Query optimizers rely on declared types, statistics, and constraints, which schema-on-read cannot guarantee.
  • The cost is rigidity: a new source field requires a schema change and a reload or migration.
  • Modeling is deliberate: the warehouse usually stores conformed dimensions and facts rather than raw source tables.
  • This is the key contrast with a lake, where structure is applied by the reader.

03Columnar storage

  • Columnar files store all values of one column together rather than all columns of one row.
  • An analytical query that touches three of fifty columns reads only those three, cutting I/O drastically.
  • Values in a column share a type and often repeat, so compression — dictionary, run-length, delta — works well.
  • Compression means less data to read from disk and less memory needed for the working set.
  • Column statistics and min/max metadata allow the engine to skip whole blocks that cannot match a filter.
  • Vectorized execution processes batches of column values, using CPU caches and SIMD-style operations efficiently.
  • The trade-off appears on single-row writes and point reads, where columnar layout is inefficient; that is why warehouses batch loads.

04MPP execution

  • A coordinating node parses the query, plans it, and distributes work to worker nodes.
  • Data is distributed across workers by distribution key or hash, and each worker scans its local portion.
  • Shared-nothing workers have their own CPU, memory, and storage, so they scale by adding nodes.
  • Aggregations run partially on each worker and are combined by the coordinator or a second stage.
  • Joins require matching rows to be co-located; otherwise the engine shuffles or broadcasts one side across the network.
  • The planner chooses join order, join strategy, and distribution based on table statistics and sizes.
  • Skew in a distribution key sends disproportionate rows to one worker and dominates query time.
MPP performance is a planning problem as much as a hardware problem. A bad distribution key or stale statistics can make a fast cluster look slow.

05Dimensional modeling: facts and grain

  • A fact table stores business events or snapshots with numeric measures and foreign keys to dimensions.
  • Define the grain first: one row per order line, per shipment, or per account per day.
  • Measures are additive, semi-additive, or non-additive; summing a balance across days is usually wrong.
  • Keep facts narrow and numerous; descriptive attributes belong in dimensions.
  • Surrogate integer keys isolate the warehouse from source-system key changes.
  • A fact table should be loaded at a consistent grain so one query can combine metrics without double counting.

06Dimensions and the star schema

  • Dimensions provide the who, what, where, and when used to filter and group facts.
  • A star schema keeps dimensions denormalized, so a query joins the fact to each dimension once.
  • Conformed dimensions — the same customer and date definitions across fact tables — let separate processes be compared.
  • A date dimension is pre-built with fiscal periods, holidays, and week numbers so reports do not recompute them.
  • Star schemas favor simplicity and query performance over storage normalization.
  • Dimension attributes should use consistent names and values across sources, or drill-across breaks.
  • The model is optimized for how analysts ask questions, not for how the source application stores data.

07Snowflake schema and normalization

  • A snowflake schema normalizes dimensions into hierarchies, such as product to category to department.
  • It reduces redundancy when dimension attributes are large or change independently.
  • The cost is more joins, more complex SQL, and often slower BI queries.
  • Modern columnar warehouses handle joins well, so the performance gap is smaller than on older systems.
  • Normalization helps when a dimension is shared by many facts or maintained by a separate team.
  • Most warehouses use a star for common marts and normalize only where the dimension is genuinely large.
  • The modeling choice should follow query patterns and maintenance ownership, not dogma.

08Slowly changing dimensions

  • A slowly changing dimension handles attributes that change, such as a customer's region or a product's price band.
  • Type 1 overwrites the old value; simple, but history is lost and past reports change retroactively.
  • Type 2 adds a new row with valid-from and valid-to dates and a current flag, preserving history.
  • Type 3 keeps a previous-value column for a limited number of changes.
  • Type 2 requires an effective-date join so a fact is attributed to the dimension version valid at event time.
  • Late-arriving dimension records must be handled without dropping or misattributing facts.
  • Choose based on whether analysts need to reproduce history or only the current state.

09OLAP versus OLTP

  • OLTP supports day-to-day operations: short transactions, high concurrency, row-level access, strict consistency.
  • OLAP supports analysis: large scans, few concurrent users relative to transactions, aggregations, and history.
  • OLTP schemas are normalized to avoid update anomalies; OLAP schemas are denormalized for query simplicity.
  • OLTP indexes serve point lookups; OLAP relies on column pruning, partitioning, and zone maps.
  • Warehouses batch-load from OLTP rather than serving transactions directly.
  • Keeping the two workloads separate protects application latency and lets each be tuned independently.

10Loading the warehouse: ETL and ELT

  • Extract from sources into a staging area, then validate and conform before publishing to marts.
  • ETL transforms outside the warehouse and loads curated tables; ELT loads raw and transforms with warehouse SQL.
  • Incremental loads use change capture or a watermark so the warehouse does not reprocess all history nightly.
  • Loads should be idempotent: a rerun replaces the affected partition or merges on a key rather than appending duplicates.
  • Stage tables allow validation and reconciliation before swapping data into production tables.
  • Dimension loads must run before fact loads so foreign keys resolve, and late facts may need a default member.
  • The transformation layer — SQL models, tests, and documentation — is part of the warehouse product.
Extract to staging→Validate and conform→Load dimensions→Load facts→Run quality tests→Publish marts
A nightly full rebuild is simple and self-correcting, but it stops scaling once history and concurrency grow. Incremental loads need the same idempotency discipline as any pipeline.

11Performance, concurrency, and cost

  • Partition large fact tables by date so queries scan only relevant history.
  • Cluster or sort within partitions by common filter columns such as customer or region.
  • Keep statistics current; stale statistics produce bad join orders and distribution choices.
  • Pre-aggregate expensive repeated metrics into summary tables or materialized views.
  • Use workload management to stop one runaway query from consuming the whole cluster.
  • Result caching and concurrency scaling help dashboards but do not fix a bad data model.
  • Cost is driven by bytes scanned and compute time, so column pruning and partitioning are financial controls as well as performance ones.

12Warehouse, lake, or lakehouse

  • A warehouse gives the strongest governed SQL performance and concurrency for structured data.
  • A lake is cheaper for raw, varied, and unstructured data and supports emerging use cases.
  • A lakehouse adds transactions and schema to lake storage, narrowing the gap for open-format analytics.
  • Many organizations keep raw data in a lake and publish modeled marts in a warehouse or lakehouse.
  • The warehouse is still the better default when BI concurrency and a mature optimizer matter most.
  • Data movement between them should be deliberate; copying everything both ways creates inconsistency.

13Designing a warehouse in an interview

  • Clarify the business questions, the metrics, and the freshness required before choosing tables.
  • Identify source systems and the keys that let them be conformed.
  • Declare the grain of each fact table and the dimensions it references.
  • Choose star schemas for common marts and normalize only where dimensions justify it.
  • Decide how changes to dimensions are tracked — overwrite or full history.
  • Plan partitioning, incremental loads, quality tests, and backfills.
  • State the trade-off between freshness, cost, and concurrency instead of assuming all three are free.
Questions and metrics→Sources and keys→Grain and facts→Conformed dimensions→Load strategy→Performance and governance

↔Trade-offs to say out loud

  • Schema-on-write gives trustworthy, optimizable tables but slows onboarding of new sources.
  • Denormalized star schemas simplify queries and speed BI but duplicate dimension attributes.
  • Snowflake schemas reduce redundancy and ease maintenance but add joins and complexity.
  • Columnar storage accelerates scans and compression but makes point updates and single-row writes expensive.
  • MPP scale-out increases throughput but adds shuffle cost, skew sensitivity, and cluster management.
  • Pre-aggregation makes dashboards fast but multiplies storage and creates refresh lag.
  • Type 2 history preserves accurate past reporting but grows dimensions and complicates every join.
  • Batch loading is simple and cheap but delivers stale data; streaming ingestion adds cost and late-data handling.

?Interview questions

Answer aloud before opening the outline.

1. What is a data warehouse?

A separate analytical database loaded from operational systems, with an enforced schema and a model designed for large scans and aggregations. It protects production systems and gives business users one governed place to query history.

2. Why not run analytics on the production database?

Analytical scans consume CPU, I/O, and cache that user traffic needs, and the operational schema often lacks the history and conformed dimensions required. A warehouse isolates the workloads and models data for analysis.

3. What is schema-on-write?

The warehouse defines and enforces tables, types, and keys before data becomes queryable. Loads conform to that contract, so readers and the optimizer can trust the structure. The cost is that new sources and fields need explicit schema changes.

4. Why is columnar storage good for analytics?

Queries usually touch a few columns over many rows. Columnar layout reads only those columns, compresses similar values well, and uses metadata to skip blocks. It is poor for single-row updates, which is acceptable because warehouses load in batches.

5. How does an MPP warehouse execute a query?

A coordinator plans the query and distributes fragments to workers that scan local partitions in parallel. Aggregations are partially computed and merged, and joins either co-locate, shuffle, or broadcast data. The planner uses statistics to choose the strategy.

6. What is the grain of a fact table and why define it first?

The grain is what one row represents, such as one order line or one account-day. Defining it first prevents mixed grains and double counting, and it determines which dimensions and measures are valid.

7. Star versus snowflake schema?

A star keeps dimensions denormalized for fewer joins and simpler queries. A snowflake normalizes dimensions into hierarchies, saving storage and easing maintenance at the cost of more joins. Stars are the usual default for BI marts.

8. What is a conformed dimension?

A dimension with consistent keys, attributes, and values shared across fact tables or data marts. It is what makes drill-across analysis possible, for example comparing sales and returns by the same customer definition.

9. How do you handle a changing customer region?

Decide whether history matters. Type 1 overwrites the value. Type 2 inserts a new version with valid-from and valid-to dates and joins facts to the version valid at event time. Type 3 keeps a limited previous value.

10. OLTP versus OLAP?

OLTP handles short, concurrent transactions and point reads on a normalized row store. OLAP handles large scans and aggregations on a columnar, often denormalized model. They have different schemas, storage layouts, and performance goals.

11. How do you keep warehouse loads correct on retry?

Make loads idempotent with partition replacement or key-based merges, stage and validate before publishing, and record batch metadata. Load dimensions before facts and reconcile row counts against the source.

12. How would you make a slow dashboard query faster?

Check the scanned bytes first: partition pruning and column pruning usually matter most. Then review join order and statistics, consider a summary table or materialized view, and only then add compute. A bad grain or missing partition will not be fixed by a bigger cluster.

!Traps

  • Loading facts before dimensions and silently dropping rows that fail foreign keys.
  • Mixing grains in one fact table and double counting revenue.
  • Using a Type 1 overwrite when analysts need historical accuracy.
  • Denormalizing everything without measuring query patterns.
  • Assuming a columnar warehouse is good for single-row updates.
  • Partitioning on a high-cardinality column and creating metadata overhead.
  • Treating the warehouse as a raw dump instead of a modeled, governed product.
