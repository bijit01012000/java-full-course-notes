01The problem: latency without a location

A checkout click can pass through a gateway, order service, inventory service, payment service, fraud check, database, and message queue. When the whole flow takes six seconds, per-service dashboards often show several services slightly elevated and none obviously guilty.

  • Metrics aggregate thousands of requests, so they show that a service is slower on average, not which call inside it waited.
  • Logs describe events inside one service; nothing in them identifies the same request in the next service's log.
  • Correlating logs by timestamp across services fails when clocks differ and requests overlap.
  • The question that matters is causal: for this request, which hop consumed the time, and was it waiting on a child call?
  • Without a per-request path you end up guessing, restarting services, or adding temporary logging and redeploying.
  • Tracing exists to answer that question from data collected before the incident.

02What distributed tracing is

  • Tracing instruments each unit of work as a span and links spans that belong to the same request into a trace.
  • It captures causality, not just timing: the order service's span is a child of the gateway's span because the gateway called it.
  • The result is a per-request tree, which can be rendered as a timeline and analyzed programmatically.
  • Traces are sampled, so they are a statistical view of traffic rather than a complete ledger.
  • Tracing is the only pillar that shows cross-service structure: fan-out, sequential dependencies, retries, and queue waits.
  • It is also the cheapest way to discover that a call graph is not what the architecture diagram claims.

03Spans: the unit of work

  • Every span carries a trace ID, its own span ID, and the parent span ID that placed it in the tree.
  • It records an operation name such as POST /checkout or SELECT orders, plus start and end timestamps.
  • A status field separates success from error, and often carries an error message or exception type.
  • Attributes hold the useful dimensions: route, method, status code, database system, queue name, retry count, tenant.
  • Events inside a span mark notable moments — cache miss, retry, exception — without needing a new span.
  • A span's duration includes time waiting on its children; self time subtracts children to show where the service actually worked.
  • Span names should be low-cardinality templates, because the span name is also an index dimension in most backends.

04Reading the waterfall

Tracing UIs render a trace as a waterfall: nested bars on a shared time axis, each bar one span.

  • The root span is the user-visible duration; children partition it into dependencies and local work.
  • Long bars with no children indicate work inside that service — slow queries, serialization, CPU contention.
  • Long bars with long children indicate waiting on a dependency, so you follow the tree downward.
  • Sequential sibling calls that could be parallel show up as adjacent blocks that do not overlap.
  • Gaps between a parent and its children are overhead: connection setup, queueing in a pool, scheduling delay, or clock skew.
  • Repeated identical short spans in a row reveal retry loops or N+1 query patterns.
  • The critical path is the chain of spans that determines total duration; optimizing off-path work changes nothing.

05Propagating context across boundaries

  • The entry service creates the trace ID; every downstream service must receive it and create its spans under it.
  • The W3C Trace Context standard defines traceparent, carrying trace ID, parent span ID, and sampling flags.
  • HTTP and gRPC propagate via headers or metadata; message queues must copy context into message attributes, since there is no live call stack.
  • Background jobs and scheduled tasks need explicit context handoff, or the trace stops at the enqueue.
  • If any single hop drops the header, the trace splits into disconnected fragments and causality is lost.
  • Asynchronous fan-out creates sibling spans with the same parent, which is why consumer spans often record a link to the producer.
  • Context from untrusted callers is a spoofing risk; validate or regenerate at the edge if trace data drives security decisions.

# gateway
span = start_span("GET /checkout")

# downstream reads it

span = start_span("POST /charge", parent=ctx)

06Instrumentation: automatic and manual

  • Auto-instrumentation wraps HTTP servers and clients, database drivers, caches, and messaging libraries, creating spans without code changes.
  • Manual spans cover business operations that no library understands: pricing, fraud rules, allocation, settlement.
  • A hybrid is normal: automatic spans for the transport path, manual spans around the domain logic that dominates latency.
  • Service meshes can emit spans at the network layer without application changes, but they see hops, not internal semantics.
  • OpenTelemetry provides the vendor-neutral API, SDK, and propagation format used by most modern tracing setups.
  • Instrumentation must be cheap: creating a span allocates, and a span per loop iteration can measurably slow a hot path.
  • Attribute values should avoid secrets and unbounded identifiers; they are stored per span and indexed.

07Sampling: making tracing affordable

  • Recording every span of every request is usually too expensive at high traffic, so traces are sampled.
  • Head-based sampling decides at the root, keeps a fixed fraction, and is trivially cheap but statistically blind.
  • Tail-based sampling buffers complete traces and keeps all errors and outliers plus a small sample of normal traffic.
  • Tail sampling needs a collector tier that groups spans by trace ID and holds them until the trace is complete or times out.
  • Adaptive sampling adjusts the rate per service or route so noisy endpoints do not dominate the sampled set.
  • The sampling decision is propagated in the trace context; otherwise one service records spans that another discards.
  • Sampling biases every trace-based statistic — a rate computed from sampled traces must be scaled by the sampling rate.

08Collection and storage

  • Applications export spans to a local collector, which batches, samples, and forwards them to the tracing backend.
  • The collector is the right place for redaction, attribute scrubbing, and fan-out to multiple backends.
  • Backends index traces by trace ID and usually by service, operation, duration, and status for search.
  • Search by attributes is more expensive than search by indexed fields, so most tools limit arbitrary filtering.
  • Span volume is the cost driver: requests times spans per request, multiplied by attribute size.
  • Retention is typically short because traces answer what happened questions for recent incidents, not long-term trends.
  • Waterfall queries are point lookups by trace ID; aggregate queries over traces are much heavier and often offloaded.

09Correlating traces with logs and metrics

  • Put the trace ID in every log line, so a slow trace leads directly to the entries that explain it.
  • Attach exemplars to metric buckets so a latency spike links to a sampled trace from that bucket.
  • Record the trace ID in error responses and support tickets, so a user report can be traced without guesswork.
  • Tag spans with the deployment version, so a bad release is one filter away from a suspect.
  • Include the span ID in logs when one request produces many log lines, to distinguish concurrent operations inside a service.
  • Correlation is what turns three tools into one investigation; without it tracing becomes another silo.

10What tracing reveals that nothing else does

  • Latency attribution: how much time was local work, how much was waiting on each dependency.
  • Hidden serialization: calls that could run in parallel but are executed one after another.
  • Retry amplification: a failing dependency retried at several layers multiplies load and latency.
  • Queue delay versus processing time, by comparing the producer span's end with the consumer span's start.
  • Fan-out width: how many services one request touches, which predicts blast radius and cost.
  • Version skew: a trace can show requests served by mismatched service versions during a rollout.
  • The real call graph, including calls that are invisible in the architecture diagram.

11Failure modes and overhead

  • Broken propagation is the classic failure: traces appear as disconnected single-span fragments, and nobody notices until an incident.
  • Clock skew between hosts warps the waterfall and can make a child appear to start before its parent.
  • Span explosion — a span per loop iteration or per item in a batch — inflates cost and makes the waterfall unreadable.
  • High-cardinality attributes such as raw URLs, user IDs, or SQL text bloat storage and slow attribute search.
  • Instrumentation overhead shows up as CPU and allocation cost on the hot path, and as network egress from span export.
  • Sampling bias makes traces look healthier than reality if head sampling drops precisely the failing requests.
  • Collector outages silently drop spans; export failures must be monitored, not assumed away.
A trace that stops at a service boundary is a data bug, not a property of the request. Alert on propagation gaps the same way you alert on missing metrics.

12When tracing is worth the cost

  • Tracing pays off when requests cross many services, when latency is hard to attribute, or when incidents are diagnosed by guesswork.
  • It is less valuable in a single-process monolith, where a profiler and logs already show the call path.
  • Start with auto-instrumentation at the edges, tail sampling for errors and slow requests, and trace IDs in logs.
  • Add manual spans only where the waterfall shows unexplained self time.
  • Set a span budget per request by instrumenting meaningful operations, not every function call.
  • Review traces during design reviews: the trace of a normal request is a fast way to see coupling and fan-out.
  • Measure tracing's own cost and value: export volume, collector load, and how often traces shorten an investigation.

↔Trade-offs to say out loud

  • Full-fidelity tracing answers any latency question but multiplies storage, network, and instrumentation cost.
  • Head-based sampling is cheap and simple but can discard the rare failure you need to diagnose.
  • Tail-based sampling keeps errors and outliers but requires buffering collectors and more operational complexity.
  • Automatic instrumentation is quick to adopt but produces transport-level spans that miss business logic.
  • Manual spans capture domain detail but add code, maintenance, and hot-path overhead.
  • Rich span attributes make traces searchable but increase span size and cardinality cost.
  • Service-mesh tracing requires no app changes but only shows hops, not what happened inside them.
  • Long trace retention helps post-incident review but retains mostly ordinary traffic at full cost.

?Interview questions

Answer aloud before opening the outline.

1. What is distributed tracing?

It is the practice of recording each request's path through a distributed system as a tree of timed spans sharing one trace ID. It preserves causality — which span called which — so you can attribute latency and errors to a specific hop. It complements metrics, which aggregate, and logs, which stay inside one service.

2. What is in a span?

A trace ID, its own span ID, a parent span ID, an operation name, start and end timestamps, a status, and key-value attributes. It may also contain timed events such as retries or exceptions. The parent reference is what lets a backend rebuild the call tree from otherwise independent records.

3. How does context propagation work?

The first service creates a trace ID and sends it downstream in a header or message attribute, following a standard such as W3C Trace Context's traceparent. Each service extracts the context, creates a child span, and forwards it on its own outbound calls. If any hop fails to forward it, the trace splits into disconnected fragments.

4. Why do traces sometimes appear as isolated single spans?

Because context propagation broke somewhere: a library was not instrumented, a queue message did not carry the header, or a background job started fresh context. The trace tree depends entirely on the parent reference arriving intact. Fixing it usually means using standard auto-instrumentation rather than hand-rolled propagation.

5. Head-based versus tail-based sampling?

Head-based sampling decides at request start and keeps a fixed fraction; it is cheap and needs no buffering, but it can throw away the rare error. Tail-based sampling waits for the trace to finish and can keep every error and slow trace while sampling normal traffic lightly. The cost is a collector tier that buffers spans per trace and more infrastructure to operate.

6. Why can't you just use per-service latency metrics to find the slow hop?

Metrics aggregate across requests, so a service can look mildly slow while a specific call path is pathological. They also cannot distinguish waiting on a downstream dependency from doing local work. Tracing preserves the per-request structure, which is what attributes the delay to a specific edge in the call graph.

7. What is self time and why does it matter?

Self time is a span's duration minus the time spent in its children. It separates this service is slow from this service is waiting on something slow. Without it, a parent span at the top of the tree always looks like the culprit because it contains everything below it.

8. How do traces reveal problems that metrics hide?

They show structure: sequential calls that could be parallel, retry amplification across layers, queue waiting time, and unexpected fan-out. Metrics show that latency rose but not that the same dependency was called four times serially. This structural view is usually what turns a vague slowdown into a specific fix.

9. How do you connect a trace to its logs?

Every log line includes the trace ID, and ideally the span ID, of the work that produced it. Then a slow trace gives you a filter that returns exactly the relevant entries instead of a time window full of unrelated traffic. This requires consistent propagation, including through asynchronous work.

10. What are the main costs of running tracing?

Span volume drives storage and network cost, instrumentation adds CPU and allocation overhead, and tail sampling adds a buffering collector tier. There is also human cost: too many spans make a waterfall unreadable. Control it with deliberate span budgets, sampling, attribute hygiene, and short retention.

11. When is tracing not worth it?

In a single-process application where a profiler and structured logs already show the call path, tracing adds infrastructure without new insight. It is also poor value if nobody propagates context or looks at the data. Tracing earns its cost when requests cross many services and latency attribution is otherwise guesswork.

12. How would you design tracing for an asynchronous order pipeline?

Propagate context into the message attributes at publish time, and have the consumer start a span linked to the producer's span rather than pretending it is a direct child. That preserves the causal chain without implying a synchronous call. Include queue wait time in the analysis, since that delay is invisible in service latency metrics.

!Traps

  • Instrumenting services but never validating that traces are complete end to end, so broken propagation goes unnoticed.
  • Sampling at a low head-based rate and then having no slow trace to inspect during the incident.
  • Creating a span per item in a batch loop, producing thousands of spans and an unreadable waterfall.
  • Putting raw SQL, URLs, or user IDs into span attributes and blowing up storage and cardinality.
  • Assuming the longest span is the culprit without subtracting time spent in children.
  • Ignoring clock skew when reading a waterfall and blaming the wrong service.
  • Treating trace data as complete when sampling means it is only a statistical sample.
