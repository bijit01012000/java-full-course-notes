01What HTTP is

HTTP is the application-layer protocol that browsers, mobile apps, and backend services use to talk to web servers and APIs.

  • It follows a simple request-response model: the client asks for something, the server answers.
  • A page load is many requests: HTML first, then images, scripts, and stylesheets discovered in it.
  • HTTP does not move bytes itself; it relies on a transport underneath.
  • HTTP/1.1 and HTTP/2 run over TCP; HTTP/3 runs over QUIC, which is built on UDP.
  • Plain HTTP defaults to port 80; HTTPS defaults to port 443.
  • Before the first request, the client usually resolves the name with DNS, opens a connection, and for HTTPS performs a TLS handshake.
  • The same connection can be reused for later requests, which is why connection setup cost is amortized rather than paid per call.
Resolve the hostname with DNS→Open a transport connection (TCP, or QUIC over UDP)→Perform the TLS handshake for HTTPS→Send the HTTP request→Route to the application and produce a response→Return the response; keep the connection for reuse

02Anatomy of an HTTP request

  • The request line carries three things: the method, the path (with query string), and the HTTP version.
  • Headers follow as Name: value pairs, each describing some aspect of the request.
  • Host names the domain the client wants, which lets one server or IP host many sites.
  • Content-Type tells the server how to parse the body, for example JSON.
  • Authorization carries credentials such as a bearer token; Cookie carries session state.
  • Accept, Accept-Language, and similar headers state what representations the client can handle.
  • A blank line separates headers from an optional body; GET requests typically have no body.
  • HTTP/2 and HTTP/3 do not send this text on the wire; they use binary frames with pseudo-headers such as :method and :path, but the same parts exist.
POST /api/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 42

{"sku":"A-1","quantity":2}
Content-Length or chunked transfer encoding tells the receiver where the body ends. Without a framing rule, the server cannot know when the request is complete.

03Anatomy of an HTTP response

  • The status line contains the version and a three-digit status code, followed by headers and a body.
  • Status codes are grouped into five classes: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error.
  • Response headers describe the result: content type, length, caching policy, cookies, and request IDs.
  • The body carries the content, or is empty for responses such as 304 and 204.
  • A 4xx says the client sent something wrong; repeating the same request will usually fail again.
  • A 5xx says the server or a dependency failed; retrying later may succeed.
  • 429 Too Many Requests is a client error that is still retryable, usually after the delay in Retry-After.
RangeMeaningExamples
1xxInformational100 Continue

Returning 200 OK with an error object in the body breaks caches, metrics, SDKs, and retry logic, because all of them read the status code first.

04Caching headers

  • Cache-Control: max-age lets the client reuse a response for a number of seconds without asking again.
  • ETag is a version tag for the response; the client sends it back as If-None-Match to ask whether it changed.
  • 304 Not Modified answers that question with no body, saving the download but still costing a round trip.
  • Last-Modified and If-Modified-Since do the same with timestamps, at coarser resolution.
  • Vary names the request headers a response depends on, so caches store a separate copy per value.
  • private allows only the browser to cache; no-store forbids caching entirely for sensitive responses.
  • s-maxage lets shared caches such as CDNs use a different lifetime from browser caches.
Without Vary: Accept-Language, a shared cache can serve a French page to an English reader because it keyed only on the URL.

05Methods, safety, and idempotency

  • A method is safe if it does not modify server state; GET and HEAD are safe.
  • A method is idempotent if repeating the same request has the same effect as sending it once.
  • GET, PUT, and DELETE are idempotent; PUT replaces a resource, so applying it twice leaves the same value.
  • POST is neither safe nor idempotent by default: sending it twice can create two orders or charge a card twice.
  • PATCH is not guaranteed idempotent, because a patch can be a relative operation such as "increment".
  • The distinction matters most on timeout: the client cannot tell whether the server processed the request.
  • Retrying an idempotent request is generally safe; retrying a POST requires an idempotency key.
  • With an idempotency key, the server stores the key and the original result, then returns that result when the same key arrives again.

06Statelessness

  • HTTP is stateless: each request is handled independently and the protocol remembers nothing about the previous one.
  • That makes horizontal scaling easy, because any server can handle any request.
  • Applications still need identity, so the client sends a cookie or token on every request.
  • Additional session data lives in a shared store such as Redis or a database, not in one server's memory.
  • The protocol is stateless; the system around it is stateful, and the design decision is where that state lives.
  • State in a shared store keeps any instance able to serve any request and makes rolling deploys trivial.
  • State pinned to one instance forces sticky routing and breaks when that instance dies.
Ask two questions of every design: where does state live, and what happens when a request is retried or lands on a different server?

07The problem with plain HTTP

A request does not go straight to the server; it crosses a home router, an ISP, and several other networks.

  • Plain HTTP sends requests and responses without encryption, so anyone on the path can read them.
  • Eavesdropping: someone on public Wi-Fi can capture passwords, session cookies, or card details.
  • Tampering: an attacker can modify the response, injecting ads or malicious scripts into a page.
  • Impersonation: traffic can be redirected to a lookalike site that captures credentials.
  • Any middlebox on the path can also read or rewrite headers, which may leak internal identifiers.
  • These risks are not theoretical on shared networks, which is why browsers mark plain HTTP as not secure.

08What HTTPS adds — and what it does not

HTTPS is not a different protocol. It is HTTP carried over a connection secured by TLS.

  • Encryption stops eavesdropping: an observer sees ciphertext, not credentials or content.
  • Integrity stops tampering: a modified record fails its authentication check and is rejected.
  • Authentication stops impersonation: the server presents a certificate the client can validate.
  • The methods, headers, status codes, and bodies are unchanged; TLS only protects their transmission.
  • HTTPS does not authenticate the user; the application still needs logins, tokens, or other checks.
  • HTTPS does not make a vulnerable API safe, and it does not protect data once it reaches a compromised endpoint.
  • HTTPS does not fully hide which server you contact: the destination IP is visible, and the hostname often leaks through DNS and SNI.

EncryptionEavesdroppingSymmetric encryption of the record payload

09The TLS 1.3 handshake

  • The client first establishes a transport connection, normally TCP for HTTPS over HTTP/1.1 or HTTP/2.
  • It sends a ClientHello listing supported cipher suites, a public key share, the SNI hostname, and ALPN protocol preferences.
  • The server replies with a ServerHello, choosing the parameters and providing its own key share.
  • Both sides derive the same shared secret from the exchanged key shares; the secret itself is never sent.
  • The server sends its certificate chain and a signature made with its private key, proving it controls the matching key.
  • Finished messages from both sides verify that the handshake transcript was not altered.
  • Application data is then encrypted with symmetric keys derived from the shared secret, which is far cheaper than public-key operations.
TCP connection established→ClientHello: cipher suites, key share, SNI, ALPN→ServerHello: chosen parameters, server key share→Both sides derive the shared secret→Server sends certificate + signature→Both sides send Finished and verify the transcript→Encrypted HTTP request and response
Because key shares are fresh per connection, TLS 1.3 provides forward secrecy: stealing the server's private key later does not decrypt previously recorded traffic.

10Certificates and trust

  • A certificate binds a domain name to a public key and is signed by a Certificate Authority.
  • The client checks that the certificate matches the requested hostname, such as shop.example.com.
  • It checks the validity period; an expired certificate causes connection failures.
  • It checks that the chain leads to a trusted root CA, possibly through intermediate certificates.
  • The handshake signature proves the server holds the matching private key, so a stolen certificate file alone cannot impersonate it.
  • Revocation checking (OCSP or CRLs) attempts to catch certificates that were compromised before expiry.
  • The client's trust store is the root of the whole model: an unknown or misconfigured CA breaks every connection.

11HTTP/1.1, HTTP/2, and HTTP/3

  • HTTP/1.1 added persistent connections (keep-alive), so one connection serves multiple requests.
  • Requests on an HTTP/1.1 connection are handled one at a time, so a slow response blocks those behind it — head-of-line blocking.
  • Browsers work around this by opening several connections per domain, which multiplies handshakes and server state.
  • HTTP/2 uses a binary framing layer and multiplexing, interleaving many requests on one connection.
  • HTTP/2 adds HPACK header compression, which matters when every request repeats large cookies and tokens.
  • HTTP/2 still runs over TCP, so a lost packet stalls every stream until it is retransmitted — TCP-level head-of-line blocking remains.
  • HTTP/3 replaces TCP with QUIC over UDP, giving each stream independent reliability so one loss blocks only its own stream.
  • QUIC integrates TLS 1.3, so a new secure connection needs one round trip, and connection IDs let a session survive a network change.

0-RTT resumption lets a returning client send data immediately, but that early data can be replayed, so it should only carry requests that are safe to repeat, such as GET.

12HTTPS in system design

  • TLS termination at a load balancer, reverse proxy, or CDN centralizes certificates and removes encryption work from application servers.
  • Termination also lets the edge route on HTTP paths and headers, which it could not inspect on an encrypted connection.
  • Backends may receive plain HTTP on a private network, or a new TLS connection, or mTLS in a service mesh.
  • The edge must forward client details in trusted headers: X-Forwarded-For for the client IP and X-Forwarded-Proto for the original scheme.
  • Only trust those headers when your own infrastructure sets them; a client can send fake values otherwise.
  • Connection reuse and pooling avoid paying TCP and TLS setup on every call, which is significant on long-haul paths.
  • CDNs terminate TLS close to users, shortening the network path for the handshake.
  • Certificates must be automated (ACME / managed services) and expiry must be monitored, because an expired certificate is a self-inflicted outage.

Timeouts and retries

  • Every outbound call needs a timeout; without one, a slow dependency ties up threads and connections until the caller fails too.
  • Retry only idempotent requests, or POSTs protected by an idempotency key.
  • Add exponential backoff with jitter so many clients do not retry in the same instant.
  • Cap retries and use a circuit breaker so a failing dependency is not hammered.

13What to remember

  • HTTP is a stateless request-response protocol: method, path, headers, optional body in; status, headers, body out.
  • Status codes drive retry and caching behavior: 4xx for client mistakes, 5xx for server failures, 429 with Retry-After.
  • Idempotency decides what is safe to retry: GET, PUT, and DELETE yes; POST only with an idempotency key.
  • Plain HTTP is readable and modifiable by anyone on the path; HTTPS adds encryption, integrity, and server authentication.
  • TLS 1.3 completes in one round trip and gives forward secrecy through per-connection key shares.
  • HTTP/1.1 added keep-alive, HTTP/2 added multiplexing over TCP, HTTP/3 moved to QUIC to remove TCP head-of-line blocking.
  • In production, the key decisions are where TLS terminates, how internal traffic is protected, and how connections are reused.

↔Trade-offs to say out loud

  • TLS termination at the edge centralizes certificates and offloads crypto but means traffic inside the network may be plaintext unless you re-encrypt.
  • End-to-end TLS or mTLS protects service-to-service traffic but adds certificate distribution, rotation, and CPU cost.
  • Long-lived cached responses cut bandwidth and latency but risk serving stale content after a deploy or data change.
  • Short cache lifetimes keep content fresh but increase origin traffic and user-visible latency.
  • Aggressive retries improve success rates on transient failures but amplify load and can turn a blip into an outage.
  • HTTP/2 multiplexing reduces connection count and handshakes but concentrates all streams on one TCP connection where a lost packet stalls everything.
  • HTTP/3 over QUIC removes TCP head-of-line blocking and speeds up setup but depends on UDP being allowed and adds operational complexity.
  • 0-RTT resumption lowers latency for returning clients but exposes the server to replayed requests, so it must be limited to safe methods.
  • Fine-grained status codes make APIs predictable for caches and retries but require discipline to keep error semantics consistent.

?Interview questions

Answer aloud before opening the outline.

1. What is HTTP and what layer does it run at?

A stateless application-layer request-response protocol used by browsers, apps, and services. It defines the message format and semantics but relies on a transport: TCP for HTTP/1.1 and HTTP/2, QUIC over UDP for HTTP/3.

2. What are the parts of an HTTP request and response?

A request is a method, path, version, headers, and an optional body. A response is a status code, headers, and an optional body. In HTTP/2 and HTTP/3 the same parts travel as binary frames rather than text.

3. Why does the difference between 4xx and 5xx matter for retries?

A 4xx means the client's request is wrong, so an identical retry will fail again. A 5xx means a server or dependency failed, so retrying later may succeed. 429 is the exception: a client error that should be retried after the Retry-After delay.

4. What is idempotency and why does it matter?

An idempotent request has the same effect whether sent once or many times. That matters on timeouts, when the client cannot tell whether the server processed the request. GET, PUT, and DELETE are idempotent; POST is not, so retrying it can create duplicates or double-charge a customer.

5. How do idempotency keys work?

The client sends a unique key with each POST. The server stores the key alongside the result of the first attempt. If the same key arrives again, the server returns the stored result instead of repeating the operation.

6. HTTP is stateless — how do applications track users?

The client sends a cookie or a token on every request, and the server looks up any extra session data in a shared store such as Redis. The protocol stays stateless, which lets any server handle any request.

7. What three risks does plain HTTP expose?

Eavesdropping, because anyone on the path can read the traffic; tampering, because they can modify responses; and impersonation, because traffic can be redirected to a fake server. TLS addresses all three with encryption, integrity checks, and certificates.

8. Does HTTPS make an API secure?

No. It protects data in transit and authenticates the server, but it does not authenticate the user, fix authorization bugs, or protect data at rest or on a compromised endpoint.

9. Walk through the TLS 1.3 handshake.

The client sends a ClientHello with cipher suites, a key share, SNI, and ALPN. The server responds with ServerHello and its key share, then sends its certificate and a signature. Both sides derive the same shared secret and exchange Finished messages to verify the transcript. Application data then flows under symmetric keys.

10. What does the client check in a certificate?

That the certificate matches the requested hostname, that it is within its validity period, and that it chains to a trusted root CA. The handshake signature then proves the server holds the matching private key.

11. What is forward secrecy and why does it matter?

Because TLS 1.3 derives keys from ephemeral key shares, recorded traffic cannot be decrypted later even if the server's long-term private key is stolen. It limits the damage of a future key compromise.

12. Compare HTTP/1.1, HTTP/2, and HTTP/3.

HTTP/1.1 added persistent connections but handles one request at a time per connection. HTTP/2 multiplexes many streams over one TCP connection with binary framing and header compression, but a lost TCP packet still blocks all streams. HTTP/3 runs over QUIC, so streams are independent and setup takes one round trip.

13. What is TLS termination and what are the trade-offs?

The edge — load balancer, proxy, or CDN — decrypts the connection, then routes the request to backends. It centralizes certificate management and enables HTTP-aware routing, but backend traffic may be plaintext unless you re-encrypt or use mTLS.

14. How do you design retries safely?

Set timeouts on every call, retry only idempotent operations or POSTs with idempotency keys, use exponential backoff with jitter, cap attempts, and add a circuit breaker so a failing dependency is not overwhelmed.

!Traps

  • Treating POST as retryable and creating duplicate orders or double charges.
  • Returning 200 OK with an error payload, which hides failures from caches, metrics, and retry logic.
  • Forgetting Vary on a response that depends on Accept-Language or another request header.
  • Assuming HTTPS authenticates the user rather than only the server.
  • Saying TLS 1.3 removes all head-of-line blocking while HTTP/2 still runs over TCP.
  • Trusting X-Forwarded-For from the public internet without stripping client-supplied values at the edge.
  • Shipping without certificate expiry monitoring or automated renewal.
  • Claiming HTTP/3 is always faster when some networks block or throttle UDP.
