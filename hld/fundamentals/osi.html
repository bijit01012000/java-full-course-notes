In one lineThe OSI model divides network communication into seven layers, each providing a service to the layer above and relying on the layer below, so you can reason about what is built where and where a request breaks.
Layer
A level of the networking stack with one narrow responsibility, exposing a service upward and consuming a service downward.
Encapsulation
The process of each layer wrapping the data from the layer above with its own header before handing it down the stack.
Frame
The Layer 2 unit of data, addressed with MAC addresses and valid only within one local network segment.
Packet
The Layer 3 unit of data, addressed with source and destination IP addresses and routable across networks.
Segment
The Layer 4 unit of data, carrying source and destination ports so the receiving host can pick the right application.
MAC address
A hardware-level address used to deliver a frame to a specific device on the same local network.
Port
A 16-bit number that identifies which application or service on a machine should receive the data.
TCP/IP model
A four-layer model that collapses OSI layers and matches how the internet is actually implemented.
PDU
Protocol Data Unit: the name of the data chunk at a given layer, such as frame, packet, or segment.

01Why the OSI model matters

One request touches many technologies before it reaches your code: Wi-Fi or Ethernet, IP routing, a TCP connection, TLS, and finally HTTP.

  • The OSI model is a mental map of that journey, not a protocol you implement.
  • It separates concerns so each layer can change without rewriting the others: Wi-Fi became 5G, Ethernet became fiber, and HTTP still worked.
  • It gives a shared vocabulary for debugging: “is this a Layer 3 problem or a Layer 7 problem?” is a faster question than “is the network broken?”.
  • Each layer provides a service to the layer above it and relies on the layer below it.
  • As a system designer you mostly live at Layer 4 and Layer 7, but failures propagate from every layer.
  • Knowing the layer tells you what information is available: MAC addresses at Layer 2, IP addresses at Layer 3, ports at Layer 4, HTTP headers at Layer 7.

02The seven layers and encapsulation

Sending data means walking down the stack; receiving it means walking back up. Each step down adds a header, and each step up removes one.

  • Layer 7 Application — what the request means: HTTP, HTTPS, DNS, WebSocket, gRPC.
  • Layer 6 Presentation — representation: serialization, compression, encoding, encryption.
  • Layer 5 Session — creating, maintaining, and closing communication sessions.
  • Layer 4 Transport — end-to-end delivery between applications: TCP, UDP, ports.
  • Layer 3 Network — delivery between networks: IP addresses, packets, routers.
  • Layer 2 Data Link — delivery on one local network: MAC addresses, frames, switches.
  • Layer 1 Physical — moving raw bits over copper, fiber, or radio.
  • Encapsulation turns one HTTP request into a TCP segment, then an IP packet, then an Ethernet frame, then bits on the wire; the receiver reverses the process.
HTTP request (Layer 7)→TLS / encoding (Layers 6)→TCP segment with ports (Layer 4)→IP packet with addresses (Layer 3)→Frame with MAC addresses (Layer 2)→Bits on the medium (Layer 1)
The layer names matter less than the ordering: each header answers a narrower question than the one above it.

03Layer 1: Physical

  • Moves raw bits from one device to another over a physical medium: copper cable, fiber, or radio such as Wi-Fi.
  • Defines electrical, optical, and radio characteristics, plus connectors and signalling rates.
  • In system design you rarely touch it directly; cloud providers and hardware vendors own it.
  • Physical failures look like packet loss, link flapping, or reduced throughput rather than application errors.
  • Redundancy at this layer means multiple links, diverse paths, and separate providers so one cut cable does not take you down.
  • Because everything above depends on it, a physical problem is invisible to application-level retries that keep hitting the same dead link.

04Layer 2: Data Link

  • Moves data between devices on the same local network, packaged into frames and addressed with MAC addresses.
  • Switches operate here: they learn which MAC address sits on which port and forward frames only out of the relevant port.
  • The destination MAC changes at every hop, because each hop is a new local delivery.
  • Broadcast and link-local discovery (such as DHCP discovery) live at this layer.
  • Cloud networks hide most Layer 2 detail, but overlay networks and MAC-based routing still appear in some designs.
  • ARP, which maps an IP address to a MAC address on the local segment, is the glue between Layer 3 and Layer 2.
  • Layer 2 domains are a failure domain: a broadcast storm or looping topology can take out a whole segment.

05Layer 3: Network

  • Moves packets between different networks, addressed by IP addresses.
  • Routers operate here: they read the destination IP and choose the next hop, with no need to know the full path.
  • Longest-prefix match decides which route wins when several prefixes match a destination.
  • The destination IP normally stays the same end to end, unless NAT or a proxy rewrites it.
  • Layer 3 is where you express topology: subnets, VPCs, peering, VPNs, and route tables.
  • A Layer 3 failure is reachability: timeouts, “no route to host”, or asymmetric paths, not HTTP error codes.
  • Reaching the machine is not enough — you still need the right process on it, which is Layer 4's job.

06Layer 4: Transport

The Transport Layer provides end-to-end communication between applications running on different machines.

  • The dominant protocols are TCP and UDP.
  • It introduces ports: the IP address finds the machine, the port finds the application on it.
  • A connection is identified by the four-tuple of source IP, source port, destination IP, and destination port.
  • It decides reliability: ordering, retransmission, and flow control are TCP features, not IP features.
  • Layer 4 load balancers route on IP and port only, so they are fast but blind to URLs and headers.
  • Firewalls and security groups commonly operate here, allowing or denying specific ports.
  • Ephemeral source ports are a finite resource, which is why a NAT gateway or client can run out under heavy connection churn.

TCP

  • Connection-oriented: a handshake establishes state on both sides before data flows.
  • Reliable and ordered: missing segments are detected and retransmitted.
  • Adds head-of-line blocking, because a lost segment stalls everything behind it on that connection.
  • Its connection state is what makes least-connections load balancing meaningful.

UDP

  • Connectionless and unreliable: no handshake, no ordering guarantee, no retransmission.
  • Lower overhead and no head-of-line blocking, which suits latency-sensitive traffic such as voice, games, and DNS queries.
  • Any reliability must be built in the application when it is needed.
  • HTTP/3 runs over QUIC, which is UDP-based and adds reliability in user space.

Ports

  • Well-known ports signal intent: 80 for HTTP, 443 for HTTPS, 53 for DNS, 22 for SSH.
  • Servers listen on a fixed port; clients use a random ephemeral port.
  • Two services cannot bind the same IP and port on the same host, which is a common deployment conflict.

07Layers 5 and 6: Session and Presentation

These two layers are less visible in modern internet systems because application frameworks and libraries absorb their responsibilities.

  • Layer 5, Session, creates, maintains, and closes communication sessions between applications.
  • Session concerns now appear as cookies, session stores, TLS session resumption, and WebSocket connection lifetime.
  • Layer 6, Presentation, decides how data is represented: serialization format, compression, character encoding, and encryption.
  • JSON versus Protobuf is a presentation-layer decision; so is gzip or TLS.
  • Because these concerns moved into libraries, a bug here looks like an application bug: wrong charset, broken decompression, or failed certificate validation.
  • The practical lesson is that “the network” includes serialization and encryption, and both cost CPU and latency.

08Layer 7: Application

  • The layer closest to your code, defining how applications communicate: HTTP, HTTPS, DNS, WebSocket, gRPC.
  • At this layer you care about meaning: method, path, headers, status code, and body.
  • It is where most system design components live: reverse proxies, API gateways, CDNs, and caches.
  • A Layer 7 load balancer can route on hostname, path, headers, or cookies, which Layer 4 cannot.
  • It is also the most expensive layer to inspect, because parsing requests costs CPU and memory.
  • Most user-visible failures are reported at Layer 7 even when the cause is lower: a 502 usually means the upstream connection failed.

System design components at Layer 7

  • Reverse proxy — terminates client connections and forwards requests to backends.
  • Layer 7 load balancer — chooses a backend using path, header, or cookie rules.
  • API gateway — adds authentication, rate limiting, and routing per route.
  • CDN — caches responses close to users using HTTP cache semantics.

09Following a request through the layers

Opening a page exercises the whole stack twice: down on the client, then up on the server.

  • The browser builds an HTTP request at Layer 7, and uses DNS to resolve the hostname to an IP address.
  • For HTTPS it establishes a TCP connection to port 443 and then negotiates TLS.
  • Layer 4 carries the bytes in TCP segments; Layer 3 places them in IP packets with source and destination addresses.
  • Layer 2 wraps each packet in a frame for the current link, for example laptop to Wi-Fi router.
  • Layer 1 transmits the frame as electrical, optical, or radio signals.
  • Across the internet, routers forward packets and each link re-frames them; the IP addresses stay the same.
  • The server reverses the process: signals, frames, packets, TCP, TLS, then the HTTP request handed to the application.
DNS resolves hostname to IP→TCP handshake to port 443→TLS handshake→HTTP request travels down the stack→Routers forward packets hop by hop→Server walks back up the stack→Application handles the request

10OSI vs TCP/IP

  • The internet does not implement seven strict layers; the TCP/IP model is what actually runs.
  • TCP/IP collapses OSI into four layers: link, internet, transport, and application.
  • OSI's session and presentation layers are absorbed into the TCP/IP application layer.
  • OSI is better for teaching and debugging because it is more granular.
  • TCP/IP is better for describing real deployments and real protocol boundaries.
  • Interview answers should use OSI vocabulary for diagnosis but acknowledge that implementations follow TCP/IP.

11Using the OSI model to debug

The model earns its place when something is broken and you need to localise the fault quickly.

  • Hostname does not resolve — suspect Layer 7 / DNS first.
  • Packets never arrive — suspect Layer 3: IP addresses, routes, subnets, security groups.
  • Host reachable but connection refused or times out — suspect Layer 4: port, listener, firewall, connection limits.
  • Connection works but HTTPS fails — suspect Layer 6: certificates, TLS versions, cipher mismatch.
  • Requests reach the system but land on the wrong backend — suspect Layer 7: reverse proxy, gateway, or load balancer rules.
  • Slow but correct responses — look above the network at queueing, database latency, and application work.
  • Walk bottom-up when nothing works and top-down when the symptom is already specific.

↔Trade-offs to say out loud

  • Layer 7 inspection enables routing and caching decisions on URL and headers but costs CPU and adds a hop that can fail.
  • Layer 4 load balancing is fast and protocol-agnostic but cannot route on path, tenant, or content type.
  • Encapsulation gives clean separation of concerns but adds header overhead at every layer.
  • TCP buys reliability and ordering but pays with handshake latency and head-of-line blocking.
  • UDP avoids connection overhead but pushes reliability, ordering, and congestion handling into your application.
  • Strict layering keeps the model teachable but hides cross-layer effects such as TLS on latency or MTU on throughput.
  • Extra proxy layers add observability and control but lengthen the request path and create more failure domains.
  • Debugging top-down is fast for specific symptoms but can miss a lower-layer cause that only appears under load.

?Interview questions

Answer aloud before opening the outline.

1. What problem does the OSI model solve?

It gives a shared, layered vocabulary for network communication so each responsibility can be designed, replaced, and debugged independently. In practice it helps you decide whether a failure is about naming, routing, connection, encryption, or application logic.

2. What is encapsulation and why does it matter?

Each layer wraps the data from the layer above in its own header before passing it down, and the receiver removes headers on the way up. It matters because it explains why a single request carries nested addressing: ports for the process, IP for the host, MAC for the local link.

3. How do Layer 2 and Layer 3 differ?

Layer 2 delivers a frame within one local network using MAC addresses; Layer 3 delivers a packet across networks using IP addresses. The destination MAC changes at every hop, while the destination IP normally survives to the end unless NAT or a proxy rewrites it.

4. What does Layer 4 add that Layer 3 does not?

Layer 3 gets the packet to the right machine; Layer 4 gets the bytes to the right process on that machine using ports, and optionally adds reliability, ordering, and flow control through TCP.

5. When would you use UDP instead of TCP?

When low latency matters more than guaranteed delivery and the application can tolerate or handle loss, such as voice, games, or telemetry. DNS queries also use UDP for small responses because the round-trip savings outweigh the rare retry.

6. Why does a Layer 7 load balancer need more resources than a Layer 4 one?

It must parse the application protocol, buffer requests, and possibly terminate TLS before it can route on path or headers. A Layer 4 balancer only reads address and port fields, so it can forward packets with far less state and CPU per connection.

7. What actually happens when you type a URL and press Enter?

The browser resolves the hostname via DNS, opens a TCP connection to port 443, negotiates TLS, and sends an HTTP request. That request is encapsulated into segments, packets, and frames, crosses multiple networks, and is unwrapped by the server before your application sees it.

8. Connection succeeds but HTTPS fails. Where do you look?

Layer 6: certificate validity and chain, SNI and hostname mismatch, TLS version or cipher support, and expiry. A working TCP connection proves routing and the listener are fine, so the fault is in the encryption negotiation, not the network path.

9. How does the OSI model help during an incident?

It narrows the search space. Resolve failures point at DNS, unreachable hosts at routing, refused connections at ports and firewalls, TLS errors at certificates, and wrong-backend responses at proxy or gateway configuration.

10. Is the internet actually built on seven layers?

No. Real deployments follow the four-layer TCP/IP model, and OSI's session and presentation responsibilities are handled by application libraries and protocols. OSI remains useful as an analytical framework rather than an implementation blueprint.

11. Where do reverse proxies and API gateways sit, and why?

At Layer 7, because they need to understand HTTP: method, path, headers, and body. That lets them do path-based routing, authentication, rate limiting, and response caching, which a packet-level device cannot do.

12. What breaks if you forget the lower layers when designing?

You get designs that ignore connection limits, ephemeral port exhaustion, cross-zone latency, or TLS overhead. Application-level retries also cannot fix a routing failure, so you build resilience in the wrong place and still go down.

!Traps

  • Saying “the network is slow” without naming a layer — it hides whether the cause is DNS, routing, TLS, or the application.
  • Assuming a Layer 4 load balancer can route on URL path or headers; it cannot see them.
  • Forgetting that the destination MAC changes at every hop while the IP usually does not.
  • Treating OSI as a literal implementation and then being confused that session and presentation are missing from real stacks.
  • Blaming the network for latency that is actually queueing, database time, or serialization cost.
  • Ignoring that TLS and compression live in the request path and therefore cost CPU and latency.
  • Diagnosing a 502 as a client problem when it usually indicates an upstream connection or health failure.
