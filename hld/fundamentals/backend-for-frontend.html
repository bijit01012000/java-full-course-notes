Backend for Frontend
A backend layer dedicated to one client type, exposing an API designed for that client's screens and constraints.
Over-fetching
Returning more data than a client needs, so it downloads and parses fields it never displays.
Under-fetching
Returning too little for a screen, forcing the client to make several extra calls.
Aggregation
Calling multiple backend services for one client request and merging the results into a single response.
Client-specific API
An API contract shaped around one user experience rather than a general-purpose resource model.
Release cadence
How often a client can ship; app-store review and slow user upgrades make mobile and TV far slower than web.
Experience layer
The part of the backend that composes and shapes data for presentation, without owning domain rules.
Code sharing
Reusing aggregation or authentication libraries across BFFs while keeping each API contract independent.
Field selection
A GraphQL-style mechanism where the client declares exactly which fields it needs, reducing the need for separate BFFs.

01One API, many clients

A video streaming product runs a web app, an iOS app, an Android app, and a smart TV app over the same services.

  • Behind the clients sit user, catalog, recommendation, and watch-history services.
  • The simplest first move is one general-purpose API that every client calls.
  • That works while the clients are similar and the product is young.
  • Over time the clients diverge in screen size, network quality, and interaction model.
  • Each client starts asking the shared API to be something slightly different.
  • The shared API becomes a negotiation rather than a design.
ClientEnvironmentWhat it needs
Web appLarge screen, usually fast connectionRich pages with lots of detail
Mobile appSmall screen, often slower networkSmaller responses and fewer requests
TV appLarge screen, remote controlLarge thumbnails, its own layout and navigation

02Over-fetching

  • A movie details endpoint returns cast, reviews, and technical metadata because the web app uses all of it.
  • The mobile app may display only title, poster, and rating but still downloads everything.
  • On a constrained network that wastes bandwidth and increases time to render.
  • The client pays parsing and memory costs for data it discards.
  • Removing fields for mobile breaks the web app if there is only one response shape.
  • Adding a sparse-fields parameter pushes response shaping into every client.
  • Over-fetching is a symptom of one contract serving incompatible screens.

03Under-fetching and chatty clients

  • A mobile home screen needs data from user, recommendation, and watch-history services.
  • Without composition, the client calls each service separately.
  • Each call adds a round trip, and on mobile each round trip is expensive.
  • The client must handle partial failure and decide what to render when one call fails.
  • Parallel calls help but the screen still waits for the slowest dependency.
  • Retry and timeout logic gets duplicated per platform.
  • Under-fetching is the mirror problem: the API is too granular for the screen.

04One team, many release cycles

  • Every client team depends on the same backend team to change the shared API.
  • Mobile asks for smaller responses; web asks for more fields; TV asks for a different layout.
  • Every change must be checked against all other clients before shipping.
  • A shared API must keep working for the oldest version of the slowest client.
  • Web can deploy many times a day while TV apps wait on platform review and slow device upgrades.
  • Backend releases get gated by the slowest consumer, so velocity drops for everyone.
  • The organizational bottleneck appears before the technical one.
ClientTypical release constraint
Web appCan deploy many times per day
iOS appApp Store review, and users upgrade slowly
Android appOften faster than iOS, but still tied to app versions
TV appPlatform review and very slow upgrade cycles on older devices

05What a Backend for Frontend is

  • One backend per client type: a web BFF, an iOS BFF, an Android BFF, a TV BFF.
  • Each BFF exposes an API designed for one experience, not a general resource model.
  • The services behind it stay shared and unchanged.
  • The BFF aggregates calls, trims payloads, and maps data into screen-ready shapes.
  • It absorbs client-specific concerns such as session handling and response caching.
  • Clients get fewer, purpose-built endpoints and no knowledge of internal topology.
  • The pattern is often summarized as one experience, one backend.

06BFF versus API gateway

  • An API gateway is one entry point for all clients with shared cross-cutting policy.
  • A BFF is one entry point per client type with a client-shaped contract.
  • Gateways centralize auth, quotas, TLS, and routing; BFFs concentrate on composition and response shape.
  • A BFF often sits behind or alongside the gateway, which still terminates TLS and authenticates.
  • A single general gateway starts to behave like a BFF when it accumulates client-specific endpoints.
  • Many systems keep the gateway thin and put experience logic in BFFs.
  • Both hide services; only the BFF tailors the API per experience.

07What a BFF should own

  • Request composition: fan out to services, apply timeouts, merge results.
  • Response shaping: drop unused fields, rename for the UI, precompute display values.
  • Client session and token exchange, mapping the client's credential to downstream calls.
  • Per-client caching and compression tuned to that client's network.
  • Protocol adaptation, for example exposing simple JSON over internal gRPC.
  • Graceful degradation rules: which sections to omit when a dependency fails.
  • Client-specific versioning so one app can lag without blocking others.

08What a BFF must not own

  • Domain rules such as pricing, eligibility, or inventory reservations.
  • Direct writes to service databases, which breaks ownership and invariants.
  • Business validation that services must also perform, creating two sources of truth.
  • Long-running workflows that should be durable and service-owned.
  • Authorization decisions about resources the service is responsible for.
  • Cross-client policy that belongs in the gateway.
  • Anything that would force all BFFs to change together.
A BFF is an experience layer. If a rule must hold regardless of client, it belongs in the service.

09How a request flows through a BFF

  • The client calls one BFF endpoint for a screen, not five service endpoints.
  • The BFF authenticates or forwards the token through the gateway.
  • It fans out to the required services in parallel with per-call timeouts.
  • It handles partial failure, for example showing the page without recommendations.
  • It trims, renames, and merges fields into the exact shape the screen renders.
  • It caches what is safe to cache for that client and sets appropriate headers.
  • It returns one payload and logs the fan-out for tracing.
Client calls screen endpoint on its BFF→BFF validates session and token→BFF fans out to services in parallel→Partial failures handled per section→Responses merged and trimmed→Single screen-shaped payload returned

10Ownership and team topology

  • The team that builds the client usually owns its BFF, so API changes ship with the app.
  • This removes the shared-backend review queue that blocked every client.
  • Each team can deploy independently, at its own cadence.
  • The shared services keep one owner and one contract for all BFFs.
  • Ownership must be explicit or BFFs become unowned glue code.
  • Small teams can start with one BFF and split when divergence justifies it.
  • Conway's law applies: per-client backends mirror per-client teams.

11Sharing code without merging the APIs

  • Extract common aggregation, auth, and telemetry helpers into a shared library.
  • Share infrastructure and conventions, not endpoint contracts.
  • Keep each BFF's routes independent so one client can evolve alone.
  • Duplication of small mapping code is often cheaper than a shared abstraction.
  • Watch for the shared library becoming a distributed monolith that forces lockstep releases.
  • Generated clients from service schemas reduce drift in downstream calls.
  • Contract tests against services catch breakage before a client ships.

12Failure modes

  • A BFF grows into a mini-monolith with business logic and its own database.
  • Fan-out without timeouts lets one slow service stall every screen.
  • Inconsistent fallbacks produce blank sections that look like data loss.
  • Caching per BFF fragments caches and multiplies origin load.
  • Divergent BFFs implement the same rule differently, producing inconsistent behaviour.
  • Adding a client means a new BFF plus a new deployment and on-call surface.
  • Unversioned BFF contracts break old app versions still in the wild.

13Alternatives and decision rules

  • A single well-designed API with sparse field selection can cover similar clients.
  • GraphQL lets clients declare fields, reducing over-fetching but not the team bottleneck.
  • A general API gateway with a few client-specific routes is lighter than several BFFs.
  • Adopt a BFF when clients differ materially in shape, network, or release cadence.
  • Adopt it when one team's changes are blocked by other clients' compatibility needs.
  • Avoid it when there is one client, or when the divergence is only cosmetic.
  • Start with one BFF for the most constrained client, then split by evidence.

↔Trade-offs to say out loud

  • Client-shaped APIs cut payloads and round trips but duplicate aggregation logic across BFFs.
  • Team ownership unblocks independent releases but multiplies deployables and on-call surface.
  • Shared services keep one domain model but require stable contracts for several consumers.
  • Per-client caching improves hit locality but fragments caches and increases origin traffic.
  • Fast client iteration is possible but old app versions still need compatible BFF routes.
  • GraphQL field selection reduces over-fetching with one API but does not fix release-cadence conflicts.
  • Shared helper libraries reduce duplication but risk coupling BFF releases together.
  • Graceful partial responses keep screens usable but hide dependency failures from users.

?Interview questions

Answer aloud before opening the outline.

1. What is the Backend for Frontend pattern?

It gives each client type its own backend that exposes an API designed for that client's screens. The BFF aggregates service calls and shapes responses, while the underlying services stay shared.

2. Why does one shared API stop working?

Clients diverge in screen size, network quality, and release cadence. A single contract either over-fetches for small clients or under-fetches for rich ones, and every change must be validated against all clients, including old app versions that cannot upgrade quickly.

3. What is over-fetching?

Returning more data than a client needs, such as full cast and reviews when mobile shows only a title and rating. The client pays bandwidth, parsing, and memory costs for fields it never displays.

4. What is under-fetching?

Returning too little for one screen, so the client must call several services. That adds round trips, latency, and per-platform failure handling. A BFF fixes it by composing the calls server-side.

5. How is a BFF different from an API gateway?

A gateway is one entry point for all clients and focuses on routing, auth, quotas, and TLS. A BFF is one entry point per client type and focuses on aggregation and response shape. In practice the BFF sits behind the gateway.

6. Should a BFF contain business logic?

No. It may format, filter, and compose, but rules such as pricing, eligibility, and inventory belong in services. Otherwise each BFF reimplements the rule differently and they drift.

7. Who should own a BFF?

The team that owns the client experience, so API changes can ship alongside the app without waiting on a shared backend team. The underlying services keep their own owners and contracts.

8. How do you avoid duplicating code across BFFs?

Share libraries for aggregation, auth, and telemetry, and keep endpoint contracts separate. Accept small duplication of mapping code where a shared abstraction would force lockstep releases.

9. What happens when a service behind a BFF is slow?

The BFF needs per-call timeouts and a defined degradation policy, such as omitting recommendations while still rendering the catalog. Without that, one slow dependency can stall or fail the entire screen.

10. Does a BFF solve the mobile release problem?

Partly. It lets the mobile backend evolve without breaking web, and it can keep old routes for old app versions. It does not remove app-store review or slow user upgrades, so backwards compatibility is still required.

11. When is GraphQL a better choice than several BFFs?

When clients mostly need different field selections over the same graph rather than genuinely different experiences and release cycles. GraphQL reduces over-fetching with one API but does not resolve team ownership or cadence conflicts.

12. When should you not use a BFF?

When there is only one client, clients differ only cosmetically, or a thin gateway with a couple of tailored routes is enough. Each BFF adds a deployment, an on-call surface, and a place for logic to drift.

!Traps

  • Turning a BFF into a mini-monolith with domain rules and its own database.
  • Fanning out to services with no per-call timeout, so one slow dependency fails the whole screen.
  • Assuming a BFF removes the need to support old mobile app versions.
  • Letting all BFFs share one endpoint contract, which recreates the shared-API bottleneck.
  • Duplicating pricing or eligibility rules in each BFF so clients behave inconsistently.
  • Adding a BFF per platform before the clients actually diverge.
  • Caching the same data independently in every BFF and multiplying origin load.
