In one lineFeature flags put behavior behind a runtime switch, so code can be deployed without being released and a risky feature can be turned off in seconds without a redeploy.
Feature flag
A runtime decision point that enables, disables, or varies a code path for a defined population without shipping new code.
Deploy vs release
Deploying puts code into production; releasing exposes behavior to users. Flags separate the two events.
Targeting rule
The condition that decides whether a user or request evaluates a flag as on, such as user ID, tenant, region, or percentage.
Bucketing
Deterministically mapping an identifier into a group so the same user consistently gets the same flag value.
Kill switch
An operational flag whose only job is to disable a feature quickly during an incident.
Flag evaluation
The act of resolving a flag to a value for a specific context, either locally in the SDK or remotely.
Flag debt
The accumulation of stale flags that no one removes, multiplying code paths and test combinations.
Default value
The value used when the flag service is unreachable or the flag is undefined, which decides behavior during an outage.

01The problem: unfinished work and uncontrollable releases

A large feature can take weeks. Keeping it on a side branch means constant merge conflicts, and merging it later exposes it to every user at once.

  • Long-lived branches drift from the mainline, so the eventual merge is a large, risky, poorly tested event.
  • Shipping the finished feature makes it visible to everyone the moment it deploys, with no gradual exposure.
  • Turning a bad feature off then requires another deployment, which is exactly what you cannot rely on during an incident.
  • Both problems share a root cause: code availability and user exposure are treated as the same event.
  • Flags break that coupling: the code can be in production, merged, and tested long before users see it.
  • The result is smaller, continuous integration and a separate, controllable release decision.

02Deploy is not release

  • Deploy means getting code into the production environment and running it.
  • Release means making the behavior visible to users. A flag makes this a separate, reversible action.
  • Code can run dark for weeks, exercised by tests and internal users, while customers see the old path.
  • Release can be ramped: internal accounts, then a small population, then everyone.
  • Turning a flag off does not require a build, a rollout, or a rollback, so the kill switch is instant.
  • This separation is the reason flags work alongside every deployment strategy rather than replacing one.

03How a flag is evaluated

  • The application asks a flag provider for a value, passing a context such as user ID, tenant, region, and plan.
  • The provider applies targeting rules in order and returns the first matching variation.
  • Common rule shapes: explicit allowlists, attribute match, percentage rollout, and a scheduled enable time.
  • Percentage rollouts hash a stable identifier so the same user always lands in the same bucket.
  • Evaluation usually happens in a local SDK using a cached ruleset, so a request does not depend on a network call.
  • The decision, and ideally the reason for it, should be logged so later analysis can attribute behavior to a variation.
Request arrives with user context→SDK evaluates the flag locally→Targeting rules produce a variation→Application runs the matching code path→Exposure event is logged

04Kinds of flags

  • Release flags hide incomplete or risky features and are removed once the feature is fully launched.
  • Experiment flags split traffic into variants for measurement and are removed when the experiment concludes.
  • Operational flags (kill switches) disable a dependency-heavy feature during an incident and may be long-lived.
  • Permission flags gate features by plan or entitlement and are effectively product configuration, not deployment debt.
  • Each kind has a different expected lifetime, which determines whether keeping it is debt or intent.
  • Confusing the categories is why teams either delete flags they still need or keep dead release flags forever.

05The flag lifecycle

  • Create the flag disabled by default, so the old behavior is the safe default when anything goes wrong.
  • Deploy the code and enable it for internal users or a test tenant first.
  • Ramp exposure in stages while watching error, latency, and business metrics.
  • Reach full exposure and keep the flag for an observation period before removing the old code path.
  • Delete the flag and the dead branch together; a flag without its removal is half a change.
  • Track every flag with an owner and an expiry date, because unused flags are indistinguishable from used ones without records.

06Architecture and availability

  • A flag service stores definitions and serves them to SDKs, which evaluate locally to avoid per-request latency.
  • SDKs cache the ruleset and refresh it periodically or on change notification.
  • If the service is unreachable, evaluation falls back to the last known ruleset or to the code default.
  • Defaults must be safe: a fallback that enables an unproven feature turns a flag outage into a product incident.
  • Server-side evaluation suits shared services; client-side SDKs need the ruleset to be publishable to browsers or apps.
  • Expose the flag state and the SDK's last refresh time as metrics, or you cannot tell stale from correct.
Flags should be a data dependency with a graceful fallback, never a hard request-time dependency on a control plane.

07Consistency and stickiness

  • Hashing a stable identifier gives deterministic bucketing, so a user does not flip variations between requests.
  • Hashing the request ID instead produces flicker and invalidates both user experience and experiment results.
  • When several services read the same flag, they must share the same evaluation context or they will disagree.
  • Changing the bucketing salt or ramp percentage reshuffles users, which can be visible as a sudden shift in behavior.
  • Propagating the evaluated variation downstream is safer than letting each service re-evaluate independently.
  • Cached rulesets mean a flag change is eventually consistent; the propagation delay must be acceptable for the use case.

08Flag debt and combinatorial growth

  • Every flag doubles the number of possible behavior combinations, so testing cannot cover the full matrix.
  • Stale flags hide dead code, confuse new engineers, and make incidents harder to reason about.
  • Interactive flags that depend on each other create order-dependent behavior that is nearly impossible to test.
  • Old experiment flags keep serving variant code long after the experiment ended, silently changing behavior.
  • Removal is part of the flag's definition of done, not a cleanup task for later.
  • Some organizations cap the number of live flags per service or require an expiry date at creation.

09Failure modes

  • Unsafe default: service outage falls back to enabling the feature, so availability of the flag service becomes a release gate.
  • Stale ruleset: an instance keeps a cached value long after the kill switch was flipped.
  • Split-brain evaluation: two services evaluate the same flag differently and disagree on data shape.
  • Orphaned flag: nobody remembers what the flag does or who owns it, so nobody dares remove it.
  • Kill switch rot: the switch was never tested, so flipping it throws an exception instead of disabling the feature.
  • Unaudited change: someone flips a flag in production without review, producing an unexplained behavior change.

10Governance, safety, and auditing

  • Restrict who can change flags in production and record who changed what, when, and why.
  • Require review for changes that affect a large population, treating them like deployments.
  • Test kill switches periodically in production-like conditions, because an untested fallback is a guess.
  • Separate flag administration from application credentials so a compromised service cannot rewrite its own behavior.
  • Alert on unexpected flag changes, especially flips of high-impact operational flags.
  • Keep an inventory with owner, purpose, and expiry so audits do not become archaeology.

11Testing flagged code

  • Test both the on and off branches of every release flag, not just the new path.
  • Avoid testing all combinations; test the two meaningful states and any explicitly interacting pairs.
  • Use contract tests to confirm both branches produce compatible responses for downstream consumers.
  • Add a test that fails when a flag has passed its expiry date, so debt becomes visible in CI.
  • Cover the fallback path: simulate an unreachable flag service and assert safe defaults.
  • Keep flag evaluation behind a thin abstraction so tests can set values without a live provider.

12When flags are the right tool

  • Use flags when a feature must be dark-launched before it is finished or proven.
  • Use flags when exposure must be ramped by population rather than by infrastructure.
  • Use a kill switch when a dependency or feature is likely to need instant disabling.
  • Avoid flags for permanent business rules that never change at runtime; that is configuration, not a feature toggle.
  • Avoid adding a flag when a deployment strategy already gives the same control; redundant switches multiply the state space.
  • Keep the number of live flags small enough that a single engineer can reason about the current behavior.

↔Trade-offs to say out loud

  • Feature flags decouple release from deploy and enable instant disablement, but add a runtime dependency and configuration surface.
  • Long-lived flags support gradual rollouts and kill switches, but accumulate into debt that multiplies code paths.
  • Local SDK evaluation keeps latency low and avoids a network hop, but introduces eventual consistency and stale rulesets.
  • Remote evaluation guarantees fresh values but makes every request depend on a control plane.
  • Many small flags give fine-grained control but make the possible behavior space untestable.
  • Strict flag governance reduces accidental changes but slows down the emergency changes flags exist to enable.
  • Aggressive flag cleanup keeps the codebase honest but can remove a switch that operations still relies on.
  • Separate experiment and release flags improves clarity but requires teams to understand and respect the distinction.

?Interview questions

Answer aloud before opening the outline.

1. What is a feature flag?

A runtime switch that decides whether a code path is active for a given user or request, based on rules stored outside the application binary. It lets code be deployed without being released. Flipping it changes behavior without a build or a deployment.

2. Explain the difference between deploy and release.

Deploying puts code into production and makes it runnable; releasing exposes its behavior to users. Without flags these happen together, so every deployment is also a product launch. Flags let a team ship code early, test it dark, and decide exposure separately and reversibly.

3. Why are long-lived feature branches a problem?

While a branch lives, the mainline keeps changing, so the eventual merge is large and full of conflicts. The merged result is also untested against everything that landed meanwhile. Shipping behind a flag keeps the work on the mainline in small increments and avoids the big-bang merge.

4. How does percentage rollout stay consistent for a user?

By hashing a stable identifier such as user ID and mapping the hash into a bucket range. Because the same input always produces the same bucket, a user keeps the same variation as the percentage grows. Hashing a request ID instead would make users flip between variations.

5. What kinds of flags exist?

Release flags hide unfinished features, experiment flags split traffic for measurement, kill switches disable features during incidents, and permission flags gate features by entitlement. Their lifetimes differ, which is why the category determines whether keeping a flag is intentional or debt.

6. What should happen when the flag service is down?

Evaluation should fall back to the last known ruleset or to a hard-coded default that preserves the safe, previously shipped behavior. The control plane must never be a hard dependency of the request path. If the fallback enables an unproven feature, a flag outage becomes a product outage.

7. Why is flag debt dangerous?

Each flag doubles the number of behavior combinations, so tests cover a shrinking fraction of reality. Stale flags hide dead code, confuse debugging, and keep old experiment variants alive. The codebase becomes something nobody can fully reason about.

8. How do you prevent flag debt?

Give every flag an owner and an expiry date at creation, and treat removal as part of the feature's definition of done. Track live flags per service and fail CI or flag reviews when a flag passes its expiry. Keep only the flags whose lifetime is genuinely long, such as kill switches and entitlements.

9. How should flagged code be tested?

Test both branches rather than the full combinatorial matrix, plus any pairs that genuinely interact. Include contract tests so both branches stay compatible with consumers. Also test the fallback path by simulating an unreachable flag service.

10. What is a kill switch and what makes it reliable?

An operational flag whose purpose is to disable a feature instantly during an incident. It is reliable only if it is exercised regularly, has a safe default, and does not itself depend on the failing code path. A kill switch that has never been flipped is an untested hypothesis.

11. Can feature flags replace deployment strategies?

No. Flags control behavior inside a running version; deployment strategies control how code is distributed across instances. A flag cannot protect you from a bad binary that crashes on startup, and a deployment strategy cannot disable one risky feature. They solve different problems and compose well.

12. What are the operational risks of flags?

Unsafe defaults during a flag-service outage, stale cached rulesets, inconsistent evaluation across services, and unaudited production changes. Each is mitigated by safe defaults, freshness metrics, shared evaluation context, and change auditing with least privilege.

!Traps

  • Making the flag service a synchronous dependency of the request path so a control-plane incident becomes an outage.
  • Defaulting to enabled during a fallback, turning a flag outage into an unproven feature launch.
  • Hashing request IDs for percentage rollouts, so users flip between variations.
  • Leaving experiment flags in place long after the experiment ended.
  • Never testing the off branch, so the kill switch throws when it is finally needed.
  • Letting each service evaluate the same flag independently with different context.
  • Allowing production flag changes with no review, audit trail, or alerting.
