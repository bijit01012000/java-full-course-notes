01Networking Foundations

Every request crosses a network before any business logic runs. These six concepts describe the path from a name to a reachable machine and the delay incurred along the way.

  • Learn the order: name resolution → IP routing → transport connection → HTTP exchange.
  • The same primitives reappear at every scale: a load balancer is a server to its clients and a client to its backends.
  • Networking problems — DNS errors, packet loss, added round trips — surface as application failures, so they belong in the design.
  • Names and addresses are separate concerns: DNS maps stable names to changing IPs, which is what makes autoscaling and failover possible.
  • Every network hop adds latency and a failure mode, so the shortest correct path is usually the most available one.

1. Client-Server Model

  • The client initiates a request; the server listens, processes, and responds.
  • The split lets each side evolve independently: a mobile app can be added without changing the server, and servers can scale without changing clients.
  • The server is a shared, centralized resource, so it needs replication and load balancing once demand exceeds one machine.
  • A server can itself be a client of a database or another service; the roles describe who initiates, not a fixed tier.

2. IP Address

  • An IP address identifies an interface on a network so routers know where to deliver packets.
  • IPv4 provides roughly 4.3 billion addresses; IPv6 removes that practical scarcity with a vastly larger address space.
  • Servers, load balancers, and database nodes are all addressed by IP, but clients normally reach them through DNS names.
  • Addresses change when instances restart or autoscale, so hardcoding IPs is fragile; use DNS or service discovery.

3. DNS (Domain Name System)

  • DNS is the internet's phone book: it maps example.com to an IP address the machine can route to.
  • Resolution walks from local cache to a resolver, then root servers, TLD servers, and the domain's authoritative name server; answers are cached with a TTL.
  • DNS can steer traffic by returning different addresses for the same name, which supports load balancing, geo-routing, and failover.
  • A short TTL makes failover faster but increases query volume; a long TTL reduces queries but leaves stale answers cached longer.

4. Proxy vs Reverse Proxy

  • A forward proxy sits in front of clients and hides the client's identity from servers; VPNs and corporate egress filters are examples.
  • A reverse proxy sits in front of servers and hides the backend topology from clients; Nginx and HAProxy are common.
  • Reverse proxies handle TLS termination, caching, compression, and load balancing, so every backend does not repeat that work.
  • Decide by whose identity is being protected and where the trust boundary sits, not by the word proxy.

5. Latency

  • Latency is the time for data to move from point A to point B, usually reported as a round-trip time in milliseconds.
  • Its sources are propagation distance, serialization, server processing, and queuing when the server is busy.
  • Physics sets a floor: a request between distant continents cannot beat the speed of light in fiber.
  • Reduce perceived latency with CDNs, caching, regional deployment, batching, and fewer sequential round trips; measure p95/p99 rather than only the average.

6. HTTP / HTTPS

  • HTTP defines the request/response format: method, path, headers, optional body, and a status code in the response.
  • It is stateless — each request stands alone — which makes horizontal scaling easy but requires cookies, tokens, or sessions for continuity.
  • Know the methods and semantics: GET reads, POST creates, PUT replaces, PATCH updates, DELETE removes; GET, PUT, and DELETE are idempotent.
  • HTTPS is HTTP over TLS: the handshake authenticates the server and negotiates keys, adding a round trip but providing confidentiality and integrity.
Client sends ClientHello with TLS versions and ciphers→Server responds with ServerHello and certificate→Both sides complete key exchange→Encrypted HTTP requests and responses flow→Connection is reused for subsequent requests

02APIs and Communication

An API is a contract: what you may ask for, how to ask, and what comes back. The style should follow the interaction pattern — request-response, client-shaped queries, server push, or event notification.

  • Synchronous request-response suits immediate answers; asynchronous events suit work that can happen later.
  • The contract, not the implementation, is what other teams depend on, so versioning and error semantics matter.
  • Choose the simplest style that fits the interaction; every richer style adds server and operational complexity.
  • Pull-and-poll, server push, and event callbacks solve different problems; mixing them without a reason creates duplicate paths.
  • Whatever the style, define timeouts, retries, idempotency, and error semantics so callers know how to behave when a response is missing.

7. APIs (Application Programming Interfaces)

  • An API hides implementation behind a stable contract, much like a menu hides the kitchen.
  • A typical HTTP API defines an endpoint, method, request schema, response schema, status codes, and error format.
  • Because callers depend on the contract, breaking changes require versioning or a deprecation window.
  • Good APIs are predictable, documented, and explicit about authentication, pagination, and failure behavior.

8. REST API

  • REST models everything as a resource with its own URL and uses HTTP methods for CRUD operations.
  • Key constraints: statelessness, cacheability, a uniform interface, and consistent resource naming.
  • Example mapping: GET /users/123 reads, POST /users creates, PUT /users/123 replaces, DELETE /users/123 removes.
  • Its weakness is fixed response shapes: clients may get too much data or need several round trips for related resources.

9. GraphQL

  • GraphQL exposes a single endpoint where the client sends a query describing the exact fields it wants.
  • The server resolves each field, potentially calling several downstream services, and returns one combined result.
  • It removes over-fetching and under-fetching, which is valuable for mobile clients and varied UIs.
  • The costs are server-side resolver complexity, harder HTTP caching because queries differ, and expensive deeply nested queries that need depth and complexity limits.

10. WebSockets

  • A WebSocket starts as an HTTP request, receives 101 Switching Protocols, and becomes a persistent bidirectional connection.
  • Either side can send messages at any time without a new HTTP request, which suits chat, live scores, and collaborative editing.
  • Connections are stateful: the server tracks every open socket, so scaling requires connection-aware routing or a shared pub/sub layer.
  • Design for reconnect, backoff, heartbeats, backpressure, and the loss of all connections when one server dies.
Client sends an HTTP Upgrade request→Server responds 101 Switching Protocols→Connection stays open→Client and server exchange messages in both directions→Connection closes or is re-established after failure

11. Webhooks

  • Webhooks invert polling: the client registers a callback URL and the provider POSTs an event when something happens.
  • They are the standard integration mechanism for payment events, code pushes, and delivery status changes.
  • Delivery is typically at-least-once, so receivers must verify signatures, tolerate duplicates, and be idempotent.
  • The receiver should acknowledge quickly, enqueue the event, and process it asynchronously; providers usually retry failed deliveries.

03Data Storage

Choosing storage is one of the highest-leverage decisions in a design. Match the data model, access pattern, consistency requirement, and growth path rather than picking a familiar database.

  • There is no best database in general, only a best fit for a dataset and its queries.
  • Reads and writes have different optimization paths: indexes and caches help reads, partitioning and batching help writes.
  • Most production systems use more than one storage type, each for the data it handles best.
  • Every dataset needs one declared source of truth; caches and denormalized copies must be rebuildable from it.
  • Storage choices are hard to reverse later, because changing the data model also changes every query and migration path.

12. Databases

  • A database provides organized storage with efficient create, read, update, and delete operations plus durability and concurrency control.
  • Relational databases use tables and relationships; document stores use flexible JSON-like documents; key-value stores act like distributed hash maps; graph databases make relationships first-class.
  • The choice depends on the shape of the data, the queries you need, consistency requirements, and expected scale.
  • Using several database types in one system is normal, but each adds an operational and consistency boundary.

13. SQL vs NoSQL

  • SQL enforces a schema, supports ACID transactions and joins, and is strong for money, inventory, and well-defined relational data.
  • NoSQL trades rigid schema and joins for flexible documents or keys, horizontal partitioning, and tunable consistency.
  • Choose SQL when correctness and complex queries dominate; choose NoSQL when schema evolves quickly, write volume is high, or data is naturally unstructured.
  • The realistic answer is often both: orders in a relational store, product catalog or activity feed in a document or wide-column store.

14. Database Indexing

  • Without an index, finding a row means scanning every row — fine for hundreds, disastrous for hundreds of millions.
  • Most databases use a B-tree, a sorted balanced structure that gives O(log n) lookups.
  • Index columns used in WHERE and JOIN conditions; composite index order matters, and a covering index can avoid table lookups.
  • Every index slows inserts and updates and consumes storage, so index deliberately rather than indexing every column.

15. Vertical Partitioning

  • Vertical partitioning splits a wide table into narrower tables by column, joined by a shared key.
  • Group columns by access pattern: profile data, authentication data, and billing data rarely need to be read together.
  • Each query reads fewer bytes, and sensitive columns can get stricter access controls and independent tuning.
  • The cost is more tables and joins when a request genuinely needs columns from several partitions.

16. Caching

  • A cache stores frequently accessed data in a faster layer, usually memory, to avoid repeated database work.
  • The common cache-aside pattern checks the cache first, reads the database on a miss, then populates the cache.
  • Invalidation is the hard part: use a TTL, write-through updates, or write-behind with an explicit durability trade-off.
  • Watch hit ratio, stampedes on popular keys, and staleness; a low hit ratio adds complexity for little benefit.
Application checks the cache→Hit: return the cached value→Miss: read from the database→Store the result in the cache→Return the value to the client

17. Denormalization

  • Normalization removes duplication; denormalization deliberately adds it to avoid expensive joins.
  • Storing a user's name and a product title directly in an orders row turns a three-table join into a single read.
  • It is a read optimization for read-heavy, join-heavy paths, and it is common where the database does not support joins.
  • The price is update amplification: a changed name or title must be propagated to every copy, so pair it with a consistency strategy.

18. Blob Storage

  • Blob storage holds large, usually immutable binary objects such as images, videos, PDFs, and backups.
  • Store the bytes in object storage and keep only the URL or key in the database, so the database stays lean.
  • Blob stores provide durability, replication, cheap capacity, and CDN integration for delivery.
  • Use pre-signed URLs for controlled uploads and downloads, and lifecycle rules for retention; do not use blob storage for transactional records.

04Scaling

Scaling is about handling more traffic, data, and users without collapse. The two fundamental approaches — bigger machines and more machines — are complementary, and both eventually push pressure onto the database.

  • Measure the bottleneck before choosing a technique; adding servers to a database-bound system changes nothing.
  • Application servers scale horizontally when they are stateless; databases need replication or partitioning.
  • Each added layer improves capacity but also adds a failure mode and operational work.
  • Scaling the application tier does not scale the database; reads and writes need their own plan.
  • Capacity has a cost curve: the goal is the cheapest design that survives peak load and a single failure.

19. Vertical Scaling (Scale Up)

  • Vertical scaling gives one machine more CPU, RAM, or faster disks; no code changes are required.
  • It is simple and often the right first move for a small system or a database primary.
  • There is a hard hardware ceiling, larger instances cost disproportionately more, and the machine remains a single failure domain.

20. Horizontal Scaling (Scale Out)

  • Horizontal scaling adds more machines and spreads load across them, removing the single-machine ceiling.
  • Application servers must be stateless, with sessions and carts in a shared store such as Redis.
  • A load balancer distributes traffic, and failed instances are replaced rather than repaired in place.
  • The database still needs its own strategy — replicas for reads, sharding for writes — and distributed coordination adds complexity.

21. Load Balancers

  • A load balancer sits between clients and a server pool and distributes requests so no single server is overwhelmed.
  • Common algorithms: round robin, least connections, and weighted routing for machines with different capacity.
  • Health checks remove unhealthy servers from rotation, which turns redundancy into actual availability.
  • The load balancer itself must be redundant; otherwise it becomes the single point of failure for every healthy backend.

22. Replication

  • Replication copies data across database servers; the usual pattern sends all writes to a primary and reads to replicas.
  • It scales read throughput, provides failover capacity, and lets a replica be promoted if the primary fails.
  • Replication is often asynchronous, so replicas can be stale; read-after-write operations may need the primary.
  • Replication does not increase write capacity, because every replica still applies the same writes.

23. Sharding

  • Sharding splits data across nodes so each holds a different subset, distributing both storage and write load.
  • Choose a shard key for even distribution and common query access; a poor key creates hot shards.
  • Hash-based sharding spreads keys evenly but makes range queries harder; range-based sharding supports ranges but risks hotspots.
  • Cross-shard joins, transactions, and rebalancing are expensive, so sharding is a late-stage tool.

05Distributed Systems

Once data and computation span multiple machines, failures become independent and the network becomes an unreliable participant. Coordination, not raw capacity, becomes the hard problem.

  • A node can be healthy while the path to it is broken; the system must define behavior for that case.
  • Retries are necessary but dangerous: without idempotency they duplicate side effects.
  • Caching content near users is often cheaper than making every request travel to the origin.
  • Coordination is expensive: consensus, locks, and cross-node transactions add latency and new failure modes.
  • Design for partial failure — timeouts, retries, idempotency, and reconciliation — rather than assuming all nodes see the same state.

24. CAP Theorem

  • CAP says that during a network partition, a replicated system cannot guarantee both strong consistency and availability for affected requests.
  • Partition tolerance is not optional in a distributed system, so the real choice is CP or AP.
  • CP systems reject or wait rather than return stale data; AP systems serve local data and reconcile later.
  • The choice belongs to each operation, not to an entire database: browsing a catalog can be AP while reserving the last item must be CP.

CPReject or wait rather than serve stale dataInventory, payments, locks
APServe local data and merge laterFeeds, carts, catalogs, analytics
CAOnly meaningful when no partition existsSingle-node or partition-free systems

25. CDN (Content Delivery Network)

  • A CDN is a globally distributed set of edge servers that cache and serve content close to users.
  • The first request in a region misses and goes to the origin; later requests hit the edge, cutting latency and origin load.
  • CDNs primarily serve static assets — images, CSS, JavaScript, video — and some also cache dynamic content or run edge functions.
  • Cached content can still be served when the origin is down, which improves availability as well as speed.

26. Idempotency

  • An idempotent operation produces the same result whether executed once or many times; GET and DELETE are naturally idempotent.
  • POST is not, so payment and order APIs accept an idempotency key that uniquely identifies the attempt.
  • The server records the key and the result; a retry with the same key returns the stored result instead of charging again.
  • This matters because a timeout does not prove failure: the server may have succeeded while the response was lost.
Client sends a request with an idempotency key→Server checks whether the key was already processed→New key: execute, store the key and result→Duplicate key: return the stored result→No duplicate side effect occurs

06Architecture Patterns

With networking, storage, and scaling primitives in place, architecture patterns decide how to organize them into a coherent system that teams can build and operate.

  • Patterns are trade-off bundles, not maturity badges; each solves one problem while creating another.
  • Centralize cross-cutting concerns so individual services do not each reinvent authentication, limits, and routing.
  • Prefer the simplest structure that supports independent team ownership and the required scale.
  • Boundaries should follow business capabilities and data ownership, not the org chart of the moment.
  • Every pattern here changes the failure model, so pair it with observability, retries, and a rollback plan.

27. Microservices

  • Microservices split an application into small services aligned to business capabilities, each independently deployable and owning its data.
  • They allow independent scaling, deployment, and team ownership, and permit different languages or runtimes per service.
  • The costs are network calls instead of function calls, partial failure, cross-service data consistency, and heavy observability needs.
  • A monolith is often the better starting point; split services when team scale or independent deployment justifies the coordination cost.

28. Message Queues

  • A queue sits between producers and consumers, storing messages until a consumer is ready to process them.
  • It decouples services, absorbs bursts, persists work when a consumer is down, and lets consumers scale independently.
  • Delivery is usually at-least-once, so consumers must be idempotent; ordering and poison messages need explicit handling.
  • Kafka is a high-throughput event log, RabbitMQ a traditional broker, and SQS a managed queue; the right choice depends on replay, ordering, and operations.

29. Rate Limiting

  • Rate limiting caps how many requests a client may make in a time window, protecting backends and enforcing fairness.
  • Common algorithms: token bucket for bursts with a refill rate, sliding window for smoother accuracy, fixed window for simplicity.
  • Limiters usually run at the API gateway and keep counters in a fast shared store such as Redis.
  • Return 429 Too Many Requests with retry guidance, and choose limits per user, API key, IP, or endpoint.

30. API Gateway

  • An API gateway is a single entry point that routes client requests to the appropriate backend service.
  • It centralizes authentication, rate limiting, logging, and request/response transformation instead of duplicating them in every service.
  • It can aggregate responses from several services, cache results, and apply circuit breaking for failing backends.
  • Keep business logic out of the gateway, and deploy it redundantly so it does not become the bottleneck or single point of failure.

↔Trade-offs to say out loud

  • Reverse proxies simplify TLS, caching, and routing for backends but add a hop and another component that must be highly available.
  • GraphQL eliminates over-fetching and multiple round trips but complicates caching and exposes the server to expensive nested queries.
  • WebSockets enable instant server push but hold stateful connections that are harder to scale and reconnect.
  • NoSQL offers flexible schemas and horizontal scale but often gives up joins and multi-record transactions.
  • Indexes accelerate reads but slow writes and consume storage.
  • Denormalization removes joins from reads but multiplies update work and risks inconsistent copies.
  • Sharding unlocks write and storage scale but makes cross-shard queries, transactions, and rebalancing expensive.
  • Microservices improve independent deployment and ownership but turn function calls into failure-prone network calls.
  • Message queues decouple and buffer but introduce eventual completion, duplicates, and ordering concerns.
  • API gateways centralize cross-cutting concerns but add latency and a shared dependency in front of every service.

?Interview questions

Answer aloud before opening the outline.

1. What happens between typing a domain and receiving a response?

DNS resolves the name to an IP, the client opens a transport connection and performs a TLS handshake for HTTPS, then sends an HTTP request. A reverse proxy or load balancer may terminate TLS and route the request to an application server, which queries storage and returns a response. Each step adds latency and a possible failure point.

2. What is the difference between a forward and a reverse proxy?

A forward proxy represents clients to servers and hides client identity; a VPN or corporate filter is typical. A reverse proxy represents servers to clients and hides backend topology, handling TLS, caching, and routing. The direction of protection, not the software, defines the type.

3. Where does latency come from, and how do you reduce it?

Latency comes from propagation distance, serialization, server processing, and queuing. You cannot beat physics, so reduce round trips with caching and CDNs, place servers near users, batch or parallelize calls, and keep servers from saturating. Measure percentiles because averages hide the slow tail.

4. Why does HTTP being stateless matter for scaling?

If each request carries everything needed to process it, any server can handle it, so a load balancer can distribute freely and failed instances can be replaced. State moves to cookies, tokens, or a shared session store. That is what makes horizontal scaling and rolling deploys practical.

5. When would you choose GraphQL over REST?

Choose GraphQL when clients need varied or nested data shapes and REST would require many round trips or return excess fields, such as a mobile feed with user, post, and comment data. Stay with REST when simple resource CRUD, HTTP caching, and predictable per-endpoint limits matter more, since GraphQL adds resolver and query-cost complexity.

6. WebSockets, webhooks, or polling: how do you choose?

Use WebSockets when a client needs low-latency bidirectional updates, such as chat or live collaboration. Use webhooks when a third-party service must notify your server about an event, such as a completed payment. Use polling when updates are infrequent and simplicity matters more than immediacy.

7. How do you choose between SQL and NoSQL?

Choose SQL when the data is relational, transactions must be atomic, and queries need joins or aggregations — orders, payments, inventory. Choose NoSQL when the schema changes often, writes are high volume, or access is primarily by key — feeds, logs, catalogs. Most systems can use both for different datasets.

8. Why does an index speed up reads but slow writes?

An index is a separate sorted structure, usually a B-tree, that maps values to row locations and allows O(log n) lookup instead of a full scan. Every insert, update, or delete must also update every affected index and write additional pages, and the index consumes storage. Index the columns your queries actually filter and join on.

9. What is vertical partitioning, and when do you use it?

It splits a wide table into narrower tables by column, grouped by access pattern — profile, authentication, and billing data, for example. Queries read fewer bytes, and sensitive columns can be secured separately. Use it when a table has many columns that are rarely read together; the cost is additional joins when data from several partitions is needed.

10. Explain cache-aside and its main risk.

The application checks the cache, returns on a hit, and on a miss reads the database, writes the result to the cache, and returns it. The main risk is staleness: the database may change while the cache still holds an old value. TTLs, explicit invalidation, and careful handling of hot-key stampedes are the usual mitigations.

11. Why store media in blob storage instead of the database?

Images and videos are large immutable objects that would bloat database rows, backups, and memory. Blob storage provides cheap durable capacity, replication, and CDN integration. The database keeps only a URL or object key, and pre-signed URLs control direct upload and download.

12. When do you scale vertically versus horizontally, and where does a load balancer fit?

Scale vertically when the system is small or the database is hard to distribute; it is simple but has a ceiling and one failure domain. Scale horizontally for application servers when you need capacity and fault isolation; it requires stateless servers and a load balancer to distribute traffic and remove unhealthy instances. The database then needs its own read or write scaling plan.

13. Replication versus sharding — what is the difference?

Replication copies the same data to multiple nodes, scaling reads and providing failover. Sharding partitions different data across nodes, scaling storage and writes. They solve different problems and are often combined: each shard can have its own replicas.

14. How do CAP, queues, rate limiting, and an API gateway fit into a microservices design?

CAP forces a per-operation choice between consistency and availability when services cannot communicate. Queues decouple services and absorb bursts, but require idempotent consumers. Rate limiting protects services from overload, and an API gateway centralizes routing, authentication, and limits so each service does not reimplement them. Together they trade simplicity for resilience and independent ownership.

!Traps

  • Confusing a forward proxy with a reverse proxy and describing the wrong side of the connection.
  • Saying CAP means choosing any two of three; partition tolerance is mandatory, so the real choice is CP versus AP per operation.
  • Reaching for sharding before caching, replication, or query optimization has been measured.
  • Calling application servers stateless while sessions or carts still live in local memory.
  • Assuming WebSocket connections scale like stateless HTTP requests.
  • Treating webhook delivery as exactly-once and processing duplicates without idempotency.
  • Indexing every column and then wondering why write throughput dropped.
  • Choosing microservices for a small team or early product before the coordination cost is justified.
