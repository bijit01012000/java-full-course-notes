01The problem vector databases solve

Users search for how do I stop my laptop battery draining, and the best document says reduce power consumption on portable computers. Keyword matching sees almost no overlap.

  • Keyword search matches tokens, so it misses paraphrase, synonyms, and language differences.
  • The meaning of a piece of text can be represented as a numeric vector, and similar meanings produce nearby vectors.
  • Finding the nearest vectors answers what is semantically closest to this? rather than what contains this word?
  • Comparing a query against every stored vector is exact but scales linearly with corpus size and dimension.
  • At millions of vectors, exact comparison per query becomes too slow and too expensive.
  • The answer is an index that returns almost the same neighbors much faster.
  • That is the job of a vector database: store vectors, index them, and filter by metadata.

02What a vector database is

  • It stores records consisting of an id, an embedding, and optional structured metadata or payload.
  • Queries supply a query vector and ask for the k most similar stored vectors.
  • It maintains an approximate nearest-neighbor index rather than scanning every vector.
  • It supports metadata filters, updates, deletes, and usually persistence, replication, and sharding.
  • Many engines also store the original text or a pointer to it, so results can be returned without a second lookup.
  • The database does not understand meaning; the embedding model does, and the database only compares numbers.
  • So the quality of results depends on the model, the chunking, and the metric — not only on the index.

03Embeddings

  • An embedding model maps content into a vector so that semantically similar content lands nearby.
  • The same model must embed both the stored content and the query, and both must use the same preprocessing.
  • Vectors are often normalized to unit length so that ranking depends only on direction.
  • The dimension is fixed by the model and directly multiplies storage and distance-computation cost.
  • Different models capture different notions of similarity, so a model trained for code will behave poorly on prose.
  • Changing the model invalidates existing vectors: the whole corpus must be re-embedded and reindexed.
  • Store the model name and version beside each vector so a mixed index is detectable rather than silently wrong.

04Distance metrics

  • Cosine similarity compares direction and ignores magnitude, which suits text embeddings.
  • Dot product also rewards larger magnitude, which some models are trained to use deliberately.
  • Euclidean distance compares absolute positions, which suits embeddings trained with that objective.
  • For unit-normalized vectors, cosine, dot product, and Euclidean ranking become equivalent, so normalization is a common simplification.
  • The metric must match how the model was trained; a mismatch degrades quality without any error.
  • Distance functions are the inner loop of search, so cheaper metrics directly buy throughput.
  • Document the metric per collection, because changing it later requires rebuilding the index.

05Approximate nearest-neighbor indexes

  • HNSW builds a multi-layer proximity graph and searches by moving toward closer neighbors; it gives high recall and low latency but costs memory.
  • IVF clusters vectors and probes only the nearest clusters, which is cheap to build but sensitive to how many clusters are probed.
  • Product quantization compresses vectors into short codes so billions fit in memory, trading distance accuracy for footprint.
  • LSH hashes similar vectors into shared buckets, which is simple and streaming-friendly but often needs many tables.
  • Graph indexes favor query speed; cluster indexes favor build speed and memory; quantized indexes favor scale.
  • Indexes are built in memory and persisted, so build time and memory are first-class capacity concerns.
  • A single engine may combine them — an IVF or quantized coarse stage followed by a graph or exact refinement.

06Recall versus latency

  • Approximate search may miss a true nearest neighbor, and recall@k measures how often it finds the real top k.
  • Every tuning knob trades recall for speed: graph breadth, number of probes, or candidate list size.
  • Raising recall means visiting more candidates, which increases latency and CPU per query.
  • The honest way to tune is to compute exact neighbors on a sample and measure what the index returns.
  • Recall also depends on the data: clustered, high-dimensional, or heavily filtered sets are harder.
  • A fast index with poor recall produces plausible but wrong answers, which is worse than an obvious error.
  • So recall is a product requirement, not an implementation detail, and it belongs in monitoring.

07Metadata filtering

  • Real queries combine similarity with constraints: this tenant, this language, this date range.
  • A post-filter searches first and discards non-matching results, which can return fewer than k items.
  • A pre-filter restricts the candidate set first, which is correct but can shrink the graph search into a scan.
  • Filtered graph search often loses recall because the filtered subgraph is poorly connected.
  • Partitioning by a dominant filter — tenant or namespace — keeps each index small and avoids the problem.
  • Payload indexes on filter fields make the selection step cheap.
  • Filtering strategy is a design decision; the same query can be fast or unusable depending on it.

08Updates, deletes, and index maintenance

  • Graph indexes are expensive to mutate, so many engines write immutable segments and merge them in the background.
  • An update is usually a new vector plus a tombstone for the old one, not an in-place edit.
  • Deletes are logical until a merge or rebuild reclaims the space, so the index can be larger than the live data.
  • Frequent re-embedding of the same ids creates version churn and needs a stable deduplication key.
  • Rebuilding is required after a model change, a metric change, or a major index-parameter change.
  • Plan for a shadow index and an alias switch so a rebuild does not take search offline.
  • Write-heavy workloads therefore suit engines with segment-based merges, while read-heavy static corpora can use compact immutable builds.

09Hybrid search and reranking

  • Vector search handles meaning; keyword search handles exact names, codes, and rare tokens that embeddings blur.
  • Hybrid search runs both and merges the ranked lists, often with reciprocal rank fusion so scores need not be comparable.
  • A weighted blend is simpler but requires normalizing scores that mean different things.
  • Reranking takes the top candidates from the fast stage and rescores them with a slower, more accurate model.
  • Two-stage retrieval is standard because an expensive model cannot run over the whole corpus per query.
  • Reranking improves precision noticeably when the first stage is broad enough to include the right answer.
  • Hybrid plus rerank is usually the strongest quality configuration, at the cost of more moving parts.
Query→Vector search top N→Keyword search top N→Merge and deduplicate→Rerank shortlist→Return top k

10Scaling

  • Raw vectors dominate memory: size grows with vector count times dimension times bytes per component.
  • Quantization trades a little accuracy for a large reduction in memory.
  • Sharding by tenant or namespace keeps each index small and makes filters unnecessary.
  • Sharding by vector count requires scatter-gather across shards and a merge of partial top-k results.
  • Replication adds query throughput and availability; the index is read-mostly, so replicas are effective.
  • Index build and merge consume CPU and memory, so ingest bursts can starve query latency.
  • Query throughput and index size are separate capacity dimensions, and both need their own headroom.

11Architecture choices

  • A dedicated vector database offers mature indexes, filtering, and scaling, at the cost of another system.
  • Extensions inside a relational database keep vectors beside the source of truth, which removes a sync problem entirely.
  • A search engine with vector support gives hybrid search in one place, which is attractive when keyword search already exists.
  • An in-process library suits small, static corpora where the index fits in the application's memory.
  • The two-store design has the usual consequence: the vector index is derived, and it must be rebuilt from the source of truth.
  • For retrieval-augmented generation, the store also needs the source text or a pointer, so results can be assembled.
  • Start with the smallest option that meets recall and scale targets, and move only when a measured limit appears.

12Evaluating quality

  • Build a golden set of queries with known relevant results, then measure recall and ranking quality.
  • Retrieval quality depends on chunking: chunks too large blur meaning, chunks too small lose context.
  • Overlapping chunks preserve context across boundaries at the cost of duplicate hits.
  • Include the document title or section heading in the chunk text so the embedding carries context.
  • Evaluate end-to-end behavior, because a correct retrieval can still be presented badly.
  • Track embedding model drift: a model upgrade changes every vector and every ranking.
  • Measure latency at the percentile users feel, not the average, since tail latency defines perceived speed.

13When to use one, and how it fails

  • Good fits: semantic search, retrieval-augmented generation, similar-item recommendations, near-duplicate detection, and image or audio similarity.
  • Poor fits: exact lookups, transactional records, aggregations, and anything needing joins.
  • Weak fits: small corpora where exact search is fast enough and simpler to reason about.
  • A stale index is the main failure mode: new content is invisible and deleted content still surfaces.
  • A model or chunking change silently degrades quality unless vectors are regenerated together.
  • Returning plausible but irrelevant results erodes trust faster than returning nothing, so recall and relevance need monitoring.
  • The system needs both halves: retrieval quality from the model and pipeline, and operational quality from the index.

↔Trade-offs to say out loud

  • Approximate indexes make large-scale search fast but can miss true neighbors, so recall becomes a tunable product decision.
  • Higher recall means visiting more candidates, which costs latency and CPU on every query.
  • Quantization cuts memory dramatically but makes distance comparisons approximate and can need a refinement pass.
  • Larger chunks preserve context but blur meaning; smaller chunks sharpen meaning but lose surrounding detail.
  • Pre-filtering respects constraints exactly but can shrink a graph search into a scan; post-filtering stays fast but returns fewer than k results.
  • Hybrid search improves quality on names and rare terms but doubles the retrieval work and needs score fusion.
  • Reranking raises precision but adds a second, slower model in the query path.
  • A dedicated vector store offers better indexes but adds sync lag and another system to operate.
  • Keeping the index beside the source of truth avoids sync but limits index choice and scale.
  • Frequent re-embedding keeps quality current but multiplies index build cost and churn.

?Interview questions

Answer aloud before opening the outline.

1. What problem does a vector database solve?

It finds items whose meaning is similar to a query rather than items sharing exact words. Content is embedded into vectors, and the database indexes them so a nearest-neighbor query returns semantically close results quickly, even when the wording differs.

2. Why not compare the query against every vector?

Exact comparison is correct but costs one distance computation per stored vector per query, multiplied by dimension. At millions of vectors and high query rates that is too slow. An approximate index returns nearly the same neighbors while touching only a small fraction of the data.

3. What is an embedding and what fixes its dimension?

An embedding is a vector produced by a model to represent the content's meaning. The model architecture fixes the dimension, which then fixes storage per vector and the cost of each distance computation. Using a different model changes the dimension and the geometry, so old vectors cannot be mixed in.

4. How do you choose a distance metric?

Match the metric the embedding model was trained with: cosine for direction-only similarity, dot product when magnitude is meaningful, Euclidean for position-based models. With unit-normalized vectors the three rank identically, so normalization removes the choice — but only if the model tolerates it.

5. Compare HNSW, IVF, and product quantization.

HNSW is a layered proximity graph giving high recall at low latency but costing memory and build time. IVF clusters vectors and probes only nearby clusters, which builds cheaply but misses unprobed ones. Product quantization compresses vectors into short codes so enormous indexes fit in memory, at the price of approximate distances.

6. What does recall@k mean and why does it matter?

It is the fraction of the true k nearest neighbors that the approximate search actually returned. Because the index is approximate, a fast setting can silently miss the best answer. Measuring recall against exact search on a sample is the only reliable way to tune the speed-accuracy trade-off.

7. How should metadata filters be applied?

Prefer partitioning by the dominant filter, such as tenant, so each index is already scoped. Otherwise pre-filter carefully, because restricting a graph search to a small subset can break its connectivity and lose recall, while post-filtering can return fewer than k results.

8. Why are deletes and updates expensive?

Graph indexes are hard to mutate in place, so engines write new segments and mark old vectors deleted. Space is reclaimed only when segments merge or the index is rebuilt. Heavy churn therefore produces tombstones, extra memory, and periodic rebuild cost.

9. What is hybrid search and when is it worth it?

It runs keyword and vector retrieval and merges the ranked lists, often with reciprocal rank fusion. It is worth it when queries mix concepts with exact tokens — product codes, names, error strings — that embeddings blur. The cost is double retrieval work and a fusion step.

10. Why is chunking a retrieval decision?

Each chunk is embedded as one unit, so its size decides what counts as one meaning. Large chunks blur distinct topics together, while small chunks lose the context that makes them interpretable. Overlap and including headings are the usual ways to keep context across boundaries.

11. Dedicated vector database or an extension in the existing database?

An extension keeps vectors beside the source of truth, removes sync work, and is usually enough at moderate scale. A dedicated store offers more index choices, filtering strategies, and horizontal scale, but it is a derived copy that must be kept current and operated separately.

12. What is the most common production failure?

A stale or mismatched index: new content is never embedded, deleted content keeps surfacing, or a new model version is mixed with old vectors. Because results still look plausible, nobody notices. The fix is versioning embeddings, an explicit ingestion pipeline, and monitoring for drift.

!Traps

  • Embedding documents with one model and queries with another, then blaming the index for bad results.
  • Mixing vectors from different model versions in one collection and comparing them as if they were compatible.
  • Tuning for latency without measuring recall, so the system confidently returns the wrong neighbors.
  • Post-filtering by tenant and returning fewer results than requested, or pre-filtering into a near-scan.
  • Re-embedding on every edit without a stable id, leaving duplicate and stale vectors in the index.
  • Assuming an approximate index gives exact nearest neighbors, then debugging a ranking bug that is really recall.
  • Changing chunking or the embedding model in place without rebuilding the whole corpus.
