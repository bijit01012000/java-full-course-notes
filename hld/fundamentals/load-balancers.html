01The limit of a single server

  • One server works fine until traffic exceeds its CPU, memory, connection, or disk capacity.
  • Past that point requests queue, latency climbs, and the server may fail under load.
  • If that server is the only one, its failure takes the entire application down with it.
  • The obvious fix is more servers, which immediately raises three new questions.
  • Routing: when a request arrives, which server should handle it?
  • Balance: how do you distribute traffic evenly rather than letting one server absorb everything?
  • Failure: what happens when one of those servers becomes unhealthy or goes offline?
  • A load balancer exists to answer all three in one place, outside the application code.
Traffic grows→Single server saturates→Add more servers→Need routing, balance, and failure handling

02How a load balancer works

The load balancer sits between clients and a group of backend servers. Clients send requests to it instead of to a specific machine, and it decides where each request goes.

  • Clients resolve one stable address, for example lb.example.com, and never learn backend IPs.
  • The load balancer selects a backend using its configured algorithm and forwards the request.
  • It returns the backend's response to the client, optionally rewriting headers along the way.
  • To the client the system still looks like a single service, which is the whole point.
  • Behind that endpoint the pool can grow, shrink, or lose members without any client change.
  • Because the balancer sees every request, it is also a natural place for TLS, rate limits, and observability.

03Why use load balancers

  • Scalability: instead of buying a bigger machine forever, add more servers and let the balancer spread requests across them.
  • High availability: with several servers, a failed instance is removed and traffic continues on the rest, removing the single point of failure.
  • Better resource utilization: without balancing, one server can be overloaded while another idles; the balancer spreads work across available capacity.
  • Elastic membership: add servers when traffic rises and remove them when it falls, with no client-visible change.
  • Deployment safety: drain and replace instances one at a time instead of taking the service down.
  • Operational leverage: one place to enforce TLS, timeouts, and access rules for every service behind it.
  • The trade is a new hop, a new component to keep available, and a place where misconfiguration affects everything.

04Choosing a backend server

  • The balancing algorithm decides which healthy instance receives the next request.
  • Round robin cycles through the pool; simple, but blind to how long each request takes.
  • Weighted round robin gives stronger machines a larger share of requests.
  • Least connections sends work to the server with the fewest active connections, which suits long or uneven requests.
  • Least response time favours the fastest-responding backend but can amplify a temporary blip if not damped.
  • IP or cookie hash pins a client to a backend, useful for cache locality and stateful sessions.
  • Random choice is surprisingly effective at scale and avoids herd synchronization.
  • No algorithm fixes a pool where one backend is simply slower; health checks and capacity planning still matter.

05Stateless servers

  • In a stateless system any request can be handled by any server; nothing from a previous request is required locally.
  • The load balancer is then free to choose any healthy instance for every request.
  • Scaling becomes trivial: add or remove servers without tracking which user is connected where.
  • Failure recovery is simpler because no user's session is trapped on the lost machine.
  • Implement it by moving sessions into a shared store, a database, or a signed token such as a JWT.
  • Keep uploads and generated files in object storage rather than local disk, or the server is stateful in practice.
  • Stateless application servers are the default assumption behind autoscaling and rolling deploys.
A server can be stateless for sessions yet still hold local caches; that is acceptable as long as correctness never depends on them.

06Stateful servers and sticky sessions

  • A stateful server keeps information about a user's session in local memory or local disk.
  • If the next request lands on a different server, that server does not know the session and may treat the user as logged out.
  • Session affinity, or sticky sessions, pins a user's requests to one backend to avoid this.
  • The balancer typically implements it with a cookie or a hash of the client IP.
  • It works, but it creates uneven load: popular users or long sessions concentrate on particular servers.
  • When a pinned server dies, its users lose session state unless it was replicated elsewhere.
  • Sticky routing also complicates deploys, because draining a server logs out or interrupts everyone pinned to it.
  • The usual answer is to move shared state into a database, cache, or distributed store and keep the app tier stateless.

07Health checks

  • A load balancer must never send traffic to a server that cannot handle it.
  • It probes each backend periodically, for example GET /health, and expects a successful response within a timeout.
  • After several consecutive failures the server is marked unhealthy and removed from the pool.
  • Checks continue in the background, and the server is returned to rotation once it passes again.
  • A shallow check only proves the process answers HTTP; it can pass while the database connection is dead.
  • A deep check verifies critical dependencies, but a shared dependency outage can then mark every instance unhealthy at once.
  • Tune interval, timeout, and failure threshold together: aggressive checks flap, lenient checks keep routing to broken servers.
  • Use a separate readiness signal from liveness so a starting server is not sent traffic before it can serve it.
CheckWhat it verifiesExample
SimpleThe server responds to an HTTP requestGET /health returns 200
DetailedThe app can also reach critical dependencies/health returns 200 only if the database query succeeds
Health checks detect the failure; they do not fix it. A flapping instance should be investigated, not just rotated out.

08Layer 4 vs Layer 7 load balancing

Load balancers operate at different layers of the network stack. The two common choices trade speed and protocol flexibility against application awareness.

  • Layer 4 works at the transport layer using source and destination IP, TCP or UDP, and port numbers.
  • It does not parse the request body, so it is fast and works for protocols beyond HTTP.
  • It can forward a connection without terminating it, which suits databases, message brokers, and raw TCP services.
  • Layer 7 understands HTTP and HTTPS and can inspect URL path, hostname, headers, cookies, and method.
  • That enables content-based routing: /images to an image service, /payments to a payment service.
  • It also enables per-route policies, header rewrites, and smarter retries or timeouts.
  • The cost is more processing per request and HTTP-specific scope.
  • A common pattern is a Layer 4 balancer at the edge for raw throughput and Layer 7 inside for routing.

09TLS termination

When clients connect over HTTPS, the load balancer can be the point where encryption ends instead of making every backend do it.

  • The client performs the TLS handshake with the load balancer, not with the application server.
  • The balancer decrypts the request, forwards it to a backend, then encrypts the response back to the client.
  • Certificates are managed in one place rather than on every server.
  • Backends spend no CPU on handshakes and encryption for each connection.
  • TLS policy, cipher suites, and protocol versions can be updated centrally and applied consistently.
  • After termination the balancer may talk plain HTTP to backends on a trusted network.
  • Many production systems re-encrypt between the balancer and the backend, so termination does not mean encryption stops there.
  • Forwarding the original scheme and client IP in headers keeps redirects, logs, and rate limits correct.
Client TLS handshake with balancer→Client sends encrypted request→Balancer decrypts→Request forwarded to backend→Response returned and encrypted

10Connection draining

  • Servers are removed during deploys, scale-down, and maintenance, not only when they fail.
  • Removing a server abruptly interrupts requests it is already processing and kills open connections.
  • In draining mode the balancer stops sending new requests but lets in-flight work finish.
  • New traffic goes to the remaining servers while the draining node completes what it started.
  • Once requests complete, the process can exit cleanly and be replaced.
  • This matters most for long-running requests and long-lived connections such as WebSockets and streaming responses.
  • Draining needs a timeout: a stuck request must not keep a node alive forever.
  • Kubernetes expresses the same idea through pod termination and preStop hooks, but the principle is identical.
Mark server draining→Stop new requests→Finish in-flight requests→Close connections→Remove from pool

11High availability for load balancers

If the load balancer is what keeps the backend available, the balancer itself cannot be a single point of failure.

  • One load balancer merely moves the single point of failure one hop closer to the client.
  • Production systems run multiple balancer instances behind a shared address or DNS name.
  • Active-active: several instances serve traffic simultaneously; losing one leaves the others serving.
  • Active-passive: one instance serves while a standby monitors it and takes over on failure.
  • Active-active uses capacity better; active-passive is simpler but wastes the standby and requires reliable failover detection.
  • Clients still see one logical endpoint even when many instances are running.
  • Managed cloud load balancers handle this redundancy for you, which is a major reason to use them.
  • Whichever model you pick, the balancer tier needs its own health checks, monitoring, and capacity headroom.
ModelTrafficFailoverTrade-off
Active-activeAll instances serve at onceRemaining instances continueBetter utilization, more coordination
Active-passiveOne serves, one stands byStandby takes overSimpler, but idle capacity and detection delay

DNS-based failover is slower than an address that moves within the network, so consider how fast failover must be.

12Common load balancing technologies

  • NGINX is widely used as a reverse proxy and Layer 7 load balancer for HTTP and HTTPS.
  • HAProxy is known for high-performance Layer 4 and Layer 7 balancing with rich health-check options.
  • Envoy targets microservices and service meshes, handling both north-south and east-west traffic.
  • Cloud load balancers offer managed options such as an application (Layer 7) balancer and a network (Layer 4) balancer.
  • Kubernetes distributes traffic through Services, Ingress controllers, and gateways.
  • The right choice depends on protocol, scale, operational model, and whether you need advanced routing.
  • Whatever the product, the responsibilities are identical: accept traffic, pick a healthy backend, and spread load.

13Putting it together

  • Typical flow: DNS resolves to the balancer, the balancer terminates TLS, selects a healthy backend, and forwards the request.
  • Keep application servers stateless so the balancer can route freely and failures are cheap.
  • Use health checks with sensible thresholds, and separate readiness from liveness.
  • Drain connections during every planned removal, including deploys and scale-down.
  • Make the balancer tier redundant, or use a managed service that already is.
  • Set timeouts and retry policy at the balancer; an infinite wait there turns a slow backend into a stuck frontend.
  • Instrument per-backend request counts, error rates, and latency so imbalance is visible before users report it.
  • Watch the balancer itself: it sees all traffic and can become the bottleneck it was meant to remove.
DNS→Load balancer (TLS termination)→Health-checked backend pool→Stateless app servers→Shared cache and database

↔Trade-offs to say out loud

  • Adding a load balancer enables horizontal scaling and failover, but introduces another hop, another component to operate, and a potential bottleneck.
  • Layer 4 balancing is fast and protocol-agnostic, but cannot route on paths or headers and cannot apply HTTP-level policy.
  • Layer 7 balancing enables content-based routing and per-route policy, but costs more processing per request and only understands HTTP-like protocols.
  • Least-connections routing adapts to uneven request cost, but requires connection tracking and can still pile work onto a struggling node.
  • Sticky sessions preserve in-memory state with no shared store, but produce uneven load and lose sessions when a server dies.
  • Deep health checks catch dependency failures, but can mark the entire pool unhealthy when a shared dependency goes down.
  • Aggressive health checks remove bad nodes quickly, but flap on transient errors and cause unnecessary churn.
  • Active-active balancers use capacity well, but need coordination and careful configuration sync; active-passive is simpler but leaves capacity idle.
  • TLS termination centralizes certificate management and saves backend CPU, but puts plaintext on the internal network unless you re-encrypt.

?Interview questions

Answer aloud before opening the outline.

1. What does a load balancer actually do?

It presents one stable endpoint in front of a pool of backend servers, chooses a healthy backend for each request, forwards the request, and relays the response. Clients never need to know how many servers exist or which one served them.

2. What problems appear as soon as you add a second server?

Three: which server should handle a given request, how to keep distribution even, and what to do when one server is unhealthy or offline. A load balancer is the component that answers all three outside application code.

3. Layer 4 vs Layer 7 — how do you choose?

Choose Layer 4 for raw throughput, non-HTTP protocols, or when you only need to spread connections by IP and port. Choose Layer 7 when you need routing by path, host, header, or cookie, or per-route TLS and policy. Many architectures use both, L4 at the edge and L7 inside.

4. What is TLS termination and what does it cost?

The balancer completes the TLS handshake with the client, decrypts the request, and forwards it to the backend. Certificates and cipher policy are managed in one place and backends save CPU, but traffic is plaintext inside the network unless you re-encrypt.

5. Why are stateless servers easier to load balance?

Any instance can serve any request, so the balancer can choose freely, failed instances can be replaced, and new instances can be added without migrating users. Stateful servers force affinity, which creates uneven load and session loss on failure.

6. When would you accept sticky sessions?

When session state is expensive to externalize, or when per-user cache locality matters more than perfect balance. Accept it knowingly: it concentrates load, complicates deploys, and loses sessions when the pinned server dies.

7. How should health checks be designed?

Probe a dedicated endpoint with a defined interval, timeout, and failure threshold, and require several consecutive failures before removal. Use a shallow check for liveness and a dependency-aware check for readiness, but be careful that a shared dependency outage does not empty the pool.

8. What is connection draining and why does it matter?

Before removing a server, the balancer stops sending it new requests but lets in-flight requests and open connections finish. Without it, deploys and scale-down interrupt active users, especially on long-lived connections like WebSockets.

9. How do you keep the load balancer from becoming a single point of failure?

Run multiple instances in an active-active or active-passive configuration behind a shared address, or use a managed load balancer that provides redundancy. The balancer tier needs its own health checks, monitoring, and spare capacity.

10. Round robin or least connections?

Round robin is fine when requests cost about the same. Least connections adapts when request durations vary widely or some backends are slower, because it accounts for work already in progress rather than just counting arrivals.

11. A healthy-looking server is returning errors. What is happening?

The health check is probably too shallow — it proves the process answers, not that it can serve. A dependency-aware readiness check, plus error-rate and latency metrics per backend, exposes the problem the health check missed.

12. Where else does load balancing appear besides a dedicated appliance?

DNS round robin, reverse proxies, API gateways, service meshes, Kubernetes Services and Ingress, and client-side balancing in RPC libraries. The mechanism differs, but each picks a backend from a known healthy set.

!Traps

  • Adding servers behind a balancer while the database remains the real bottleneck.
  • Calling the app tier stateless while sessions or uploaded files still live on local disk.
  • Using sticky sessions by default instead of externalizing shared state.
  • Relying on a shallow health check that passes while the application cannot reach its database.
  • Setting health-check thresholds so aggressively that transient errors flap the whole pool.
  • Removing instances without connection draining and cutting off in-flight requests.
  • Deploying a single load balancer and recreating the single point of failure one layer up.
  • Forgetting that a Layer 7 balancer adds per-request processing and can itself saturate under load.
