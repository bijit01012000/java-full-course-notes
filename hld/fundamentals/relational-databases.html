In one lineA relational database stores each fact once in typed tables, links tables with keys, and rebuilds answers at query time with SQL and joins — giving strong correctness and flexible querying in exchange for join cost and a single write primary.
Schema
The declared structure of tables — columns, types, constraints — enforced by the database on every write.
Primary key
The column or columns that uniquely identify a row; it cannot be duplicated or null.
Surrogate key
A generated identifier with no business meaning, such as an auto-increment integer or a UUID.
Foreign key
A column whose values must match a primary key in another table, enforcing that the reference exists.
Referential integrity
The guarantee that no relationship points at a row that does not exist.
Normalization
Organizing tables so each fact is stored once, removing update, insert, and delete anomalies.
Junction table
A table whose rows pair two foreign keys, used to model many-to-many relationships and to hold attributes of the pairing.
Query planner
The optimizer that estimates the cost of alternative execution plans and picks the cheapest one.
Denormalization
Deliberately duplicating data into a table to avoid a join or an aggregate on a hot read path.
ACID
Atomicity, consistency, isolation, and durability — the transactional guarantees relational engines are known for.

01The problem relational databases solve

Imagine running an online store from one spreadsheet: every order row repeats the customer's name, email, and address.

  • A customer with twenty orders has their address copied twenty times.
  • When they move, every one of those rows must be found and updated, or the data disagrees with itself.
  • Deleting a customer's only order erases the customer entirely, because the contact details lived in that row.
  • Answering how much did each customer spend last month means writing custom scan-and-group code.
  • In 1970 Edgar Codd proposed the relational model: describe data as tables, rows, columns, and relationships, and let the database handle storage.
  • That model became the foundation of almost every major database since, and it is still the default choice for application data.

02Tables, rows, columns, and the schema

  • A table represents one kind of thing: customers, products, orders.
  • Each column has a name and a data type, such as integer, text, or timestamp.
  • Each row is one instance of that thing — one customer, one order.
  • The declared set of tables, columns, types, and constraints is the schema, and the engine enforces it on every write.
  • This is schema-on-write: a value of the wrong type is rejected instead of silently stored.
  • Rows have no guaranteed order; without ORDER BY the engine may return them any way it likes.
  • A rigid schema costs migrations, but it stops different application versions from slowly filling the table with incompatible rows.

03Keys and referential integrity

  • Every table needs a way to identify a row: the primary key, unique and never null.
  • A natural key comes from the business, such as an email or SKU; it is meaningful but can change.
  • A surrogate key is generated, such as an auto-increment integer or UUID, and never needs to change when business data does.
  • Other tables point at that key with a foreign key, such as orders.customer_id referencing customers.id.
  • The engine can then refuse an order whose customer does not exist — that is referential integrity.
  • Key choice affects index size and write distribution: random UUIDs scatter inserts, sequential integers cluster them.
  • Composite keys, such as (order_id, product_id), fit relationship tables cleanly but make references wider.

What happens when a referenced row is deleted

  • RESTRICT or NO ACTION blocks the delete while dependents exist.
  • CASCADE deletes or updates the dependent rows automatically.
  • SET NULL keeps the dependent row and clears its reference.
  • SET DEFAULT keeps the row and substitutes the column default.
  • These are business rules, not just settings: deleting a customer should not delete their completed financial records.

Key types at a glance

  • Sequential integers are compact and cluster index writes, which makes them efficient but predictable.
  • Random UUIDs can be generated anywhere without coordination, but they scatter writes and enlarge every index that carries them.
  • Time-ordered IDs sit between the two: they can be generated independently and still keep recent inserts close in the index.

04Types of relationships

  • One-to-many: one customer places many orders; the foreign key lives on the many side, in orders.
  • One-to-one: a user has one profile; model it with a foreign key that is also unique, so a user cannot appear twice.
  • Many-to-many: an order contains many products and a product appears in many orders, which a single foreign key cannot express.
  • Many-to-many needs a junction table, here order_items, with one row per (order, product) pair.
  • The junction table can carry facts about the relationship itself, such as quantity or the unit price at purchase time.
  • Storing the historical price there is what makes old orders correct after a product's price changes.
  • These three patterns cover most real-world data models, which is why the relational model generalizes so well.

05Normalization

  • Normalization removes duplication by storing each fact in exactly one place.
  • It eliminates three anomalies: update (only some copies change), insert (cannot record one fact without another), and delete (removing one fact destroys another).
  • 1NF: each column holds a single value, not a list — Keyboard, Mouse in one cell breaks it.
  • 2NF and 3NF: every column depends on the whole primary key, and only on the key — a customer's email does not belong in orders.
  • Most application schemas aim for about third normal form, which removes the common anomalies without over-splitting.
  • Normalization is not purity for its own sake: it is what makes each fact have exactly one authoritative copy.
  • The cost is that reads must recombine tables, which is what joins are for.

06Querying with SQL

  • SQL is declarative: you state the result you want, not the algorithm to produce it.
  • The query names tables, filters, groupings, and ordering; the engine decides how to execute it.
  • The same data can answer questions nobody anticipated when the schema was designed — the key advantage over pre-built access paths.
  • Expressions, aggregates, subqueries, and common table expressions compose, so complex questions stay one statement.
  • Window functions compute values across related rows without collapsing them — a running total or a rank per group.
  • SQL is standardized enough that skills and most queries transfer across engines.
  • The limitation is that deep object graphs and very large analytical scans can still be slow, which is why caches and specialized stores appear around it.

07Joins

  • A join recombines rows from related tables at read time using key equality.
  • An inner join returns only rows with a match on both sides, so a customer with no orders disappears.
  • A left join keeps every row from the left table and fills unmatched columns with NULL, which is how you find customers who never ordered.
  • Joins are what make normalization practical: store once, combine on demand.
  • Their cost depends on whether the engine can use an index for the matching side, or must hash or sort large inputs.
  • Joining many large tables multiplies that cost, and a chain of joins is often where a slow query actually spends its time.
  • Join order matters, which is why the planner, not the query author, chooses it.

08How a query is executed

  • The parser checks syntax and turns the statement into an internal tree.
  • The planner (optimizer) enumerates alternatives: scan or index, which join algorithm, which join order.
  • It estimates each plan's cost using statistics — table sizes, distinct values, and value distribution.
  • It picks the cheapest estimated plan and hands it to the executor, which produces the rows.
  • EXPLAIN shows the chosen plan; EXPLAIN ANALYZE also runs it and reports real timings.
  • Stale statistics are a classic cause of a suddenly bad plan after a data change.
  • When a query is slow, the plan is the first thing to read, not the SQL text.
Parse→Rewrite and validate→Estimate plans from statistics→Choose cheapest plan→Execute and return rows

09Indexes

  • Without an index, finding rows means a full table scan proportional to table size.
  • An index is a separate structure keeping one or more columns in sorted order with pointers to rows.
  • Relational engines typically use a B-tree, which supports equality and range lookups with a few page reads.
  • The primary key is indexed automatically; indexes on foreign keys and frequent filters are added deliberately.
  • Indexes are not free: every insert, update, and delete must maintain each one, and each consumes disk and cache.
  • Index the columns queries actually filter on, sort by, or join on — not every column.
  • Composite indexes serve a leading-column prefix, which is why column order inside the index matters.

10Transactions and constraints

  • A transaction groups changes so they succeed or fail together — insert the order, insert its items, decrement stock.
  • Relational engines provide ACID: atomicity, consistency, isolation, and durability.
  • Isolation levels trade anomaly prevention for concurrency, from read uncommitted up to serializable.
  • Durability comes from a write-ahead log: changes are logged before the commit is acknowledged and replayed after a crash.
  • Constraints enforce rules inside the engine: NOT NULL, UNIQUE, CHECK, and foreign keys.
  • Because the rules live in the database, a buggy service cannot write data that violates them.
  • A constraint failure aborts the transaction, which is exactly what makes CHECK (stock >= 0) a reliable guard against overselling.

11Denormalization

  • Normalization means more joins, and on a read-heavy page those joins become the bottleneck.
  • A product listing that shows an average rating would otherwise aggregate millions of review rows on every page load.
  • So store the average rating and review count in the products table and update them when a review is written.
  • That is denormalization: deliberate duplication to make a proven read path fast.
  • The cost moves to writes — the application or a trigger must keep every copy in sync, and a missed update silently corrupts the number.
  • Start normalized and denormalize only paths measured to be slow; premature duplication is just a future inconsistency.
  • Cached aggregates and materialized views are the same trade made in a different place.

12Scaling relational databases

  • A traditional deployment has one primary that accepts all writes, and that is the first limit to hit.
  • Vertical scaling buys CPU, memory, and faster storage and keeps every guarantee intact, but has a ceiling and stays one write node.
  • Read replicas spread read traffic but lag, so a user may not see their own write immediately.
  • Caching removes load but introduces staleness and invalidation work.
  • Partitioning splits one large table into pieces on the same server, which makes old data cheap to drop and keeps queries to one partition.
  • Sharding spreads data across independent servers and raises write capacity, but cross-shard joins, transactions, and unique constraints become hard.
  • Distributed SQL engines keep the relational model and SQL while partitioning automatically, at the cost of more latency per write and operational complexity.
  • A good shard key spreads load evenly and keeps data that is queried together on the same shard.

13When to use one, and the common engines

  • Strong fit when data is structured with clear relationships and correctness matters — payments, orders, bookings, inventory.
  • Strong fit when you need many different queries and reports over the same data.
  • Weaker fit for very high write volumes across many machines, constantly changing record shapes, or specialized search and similarity workloads.
  • Those needs are usually served by adding a specialized system beside the relational database, not replacing it.
  • PostgreSQL is known for extensions such as JSONB, full-text search, PostGIS, and pgvector; MySQL for web workloads; SQL Server and Oracle for large enterprises; SQLite for embedded use.
  • Managed services handle backups, patching, replicas, and failover, which removes much of the operational burden.
  • A database your team can operate well beats a more impressive one nobody understands.

↔Trade-offs to say out loud

  • Normalization gives one authoritative copy of each fact but forces reads to pay for joins.
  • Denormalization makes hot reads cheap but adds write work and a real risk of copies drifting apart.
  • Strict schema-on-write keeps data clean but makes structural change a planned migration, which is costly on large tables.
  • Surrogate keys never change and keep indexes compact but add a column users must map back to business identity.
  • Random UUID keys are generatable anywhere but scatter index writes; sequential keys cluster writes but are predictable.
  • Strong isolation prevents anomalies but reduces concurrency through waiting and retries.
  • Read replicas raise read capacity and availability but introduce lag and read-after-write anomalies.
  • Sharding raises write capacity but makes cross-shard joins, transactions, and uniqueness constraints expensive.
  • Extra indexes speed reads but slow every write and consume disk and cache.
  • Distributed SQL keeps SQL and ACID at scale but adds per-write coordination latency and more moving parts.

?Interview questions

Answer aloud before opening the outline.

1. What problem does the relational model solve?

It removes duplication and its consequences by storing each fact once in a typed table and linking tables by keys. That eliminates update, insert, and delete anomalies, and it lets any question be answered at query time with SQL rather than with pre-built access paths.

2. Why is a primary key required?

It gives every row a stable, unique identity, which is what other tables reference and what indexes are built on. Without one, updates and deletes cannot target a specific row reliably, and duplicates become undetectable.

3. Natural versus surrogate key?

A natural key comes from the business, such as an email or SKU: meaningful, but it can change and may expose sensitive data. A surrogate key is generated and meaningless, so it never changes when business data does; the usual cost is one extra column and a lookup to reach the natural value.

4. What does a foreign key actually enforce?

That the referencing value matches an existing primary key, which prevents orphaned rows. It also defines what happens on delete or update of the referenced row: restrict, cascade, set null, or set default. Those choices are business rules, not merely database configuration.

5. How do you model many-to-many?

With a junction table holding one foreign key per side, such as order_items(order_id, product_id). It can also store facts about the pairing itself, like quantity or the unit price at the time of purchase, which the two main tables cannot represent.

6. What are the three normalization anomalies?

Update anomaly: a duplicated fact is updated in some rows but not all. Insert anomaly: a fact cannot be recorded without an unrelated fact. Delete anomaly: removing one record destroys another fact that happened to share its row. Normalization removes the duplication that causes them.

7. Inner join versus left join?

An inner join returns only rows with matches on both sides. A left join returns every row from the left table and fills unmatched right-side columns with NULL, which is how you list customers with no orders. The two differ precisely in whether unmatched rows survive.

8. What does the query planner do?

It enumerates execution alternatives — scan versus index, join algorithm, join order — estimates each one's cost from statistics, and picks the cheapest. EXPLAIN shows the chosen plan, and EXPLAIN ANALYZE shows real timings, which is where slow-query debugging starts.

9. Why not index every column?

Because each index must be updated on every insert, update, and delete, and it consumes disk and buffer pool memory. Indexes on low-selectivity columns rarely help, and a wide set of indexes turns a fast write path into a slow one.

10. When would you denormalize?

Only on a proven hot path where joins or aggregates dominate the cost — a product page that would otherwise recompute an average from many review rows. Store the derived value next to the entity and accept the job of updating it, ideally through one code path or a trigger.

11. How do relational databases scale beyond one server?

First with a bigger machine, then read replicas for read traffic, caching, and table partitioning. Beyond one primary's write capacity, shard by a key and accept cross-shard join and transaction limits, or move to distributed SQL that partitions automatically while keeping SQL semantics.

12. When is a relational database the wrong choice?

For very high write volumes spread across many machines, rapidly changing record shapes, or specialized search and similarity work. Even then the usual architecture is a relational source of truth with a specialized store beside it, rather than replacing it outright.

!Traps

  • Saying normalization is about saving disk space, when the real goal is eliminating update, insert, and delete anomalies.
  • Choosing a random UUID as the clustered primary key without considering scattered writes and index bloat.
  • Expecting rows to come back in insertion order without an ORDER BY clause.
  • Adding an index for every column in a WHERE clause and then wondering why writes slowed down.
  • Denormalizing before measuring, and then having no single place that updates the duplicated value.
  • Sharding before exhausting indexes, caching, and read replicas.
  • Reading EXPLAIN output as a verdict rather than checking whether the planner's statistics are current.
