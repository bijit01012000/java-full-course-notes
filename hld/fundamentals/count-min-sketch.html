Count-Min Sketch
A fixed-size matrix of counters with one hash function per row that estimates item frequencies from a stream.
Width (w)
The number of counters per row; wider rows mean fewer collisions and better accuracy.
Depth (d)
The number of rows, and therefore the number of independent estimates combined by taking the minimum.
Point estimate
The minimum counter value across all rows for an item, used as its estimated frequency.
Overestimate guarantee
Estimates never fall below the true count, because every update only adds to the counters an item hashes to.
Heavy hitter
An item whose true frequency is a significant fraction of total traffic, identified from sketch estimates.
Conservative update
A variant that increments only the smallest counters in a row, which reduces collision inflation.
Mergeability
The property that two sketches with identical dimensions can be combined by adding counters cell by cell.

01The problem: counting items in a stream

A social platform wants a trending-hashtags feature. Every minute, millions of posts arrive, each carrying one or more hashtags.

  • Trending means comparing how often each hashtag appears, so the system needs per-item counts.
  • The straightforward structure is a hash map from hashtag to counter, incremented on every appearance.
  • That works while the vocabulary is small and the key space is bounded.
  • As the platform grows, unique hashtags multiply — many are typos, jokes, or one-off events.
  • Each distinct key still needs its own entry even if it was seen once and never again.
  • Memory grows with the number of distinct items, which is exactly the quantity that streaming systems cannot bound.

02Why exact counting gets expensive

  • A hash map stores every distinct key plus a counter, so cost scales with distinct items rather than traffic.
  • The distribution is heavily skewed: most keys are rare and a few are extremely common.
  • Memory is therefore spent almost entirely on keys that will never trend.
  • Exact counts also resist sharding: merging per-shard maps means shipping every key.
  • But the product decision does not need exact counts — it needs to rank items by relative frequency.
  • Relaxing exactness buys a structure whose size depends on the desired accuracy, not on the data.

03What a Count-Min Sketch is

  • It is a two-dimensional array of counters with d rows and w columns.
  • Each row has its own hash function that maps an item to one column in that row.
  • Memory is fixed when the sketch is created, regardless of how many distinct items stream through.
  • Every update touches exactly one counter per row, so cost is d increments.
  • Every query reads exactly one counter per row and takes the minimum.
  • The structure never stores keys, so it cannot list what it has seen or return exact counts.
  • It is a frequency estimator, the counterpart to a Bloom filter's membership test.

04Update

  • Hash the item once per row to find that row's column.
  • Increment each of those d counters by one.
  • All counters start at zero, so the sketch is empty and immediately usable.
  • The update never reads the item's previous count, which is what keeps it cheap and streaming-friendly.
  • Collisions are expected: two items can share a column in some rows and inflate each other's counters.
  • Because increments only ever add, an item's counters never decrease, which is the source of the one-sided error.
  • Some variants allow negative updates so that counts can be decremented, but that breaks the one-sided guarantee.

05Query: take the minimum

  • Hash the item into every row and read the d counters.
  • Return the smallest of them as the estimated count.
  • Every counter an item hashes to was incremented at least once per real occurrence, so each is at least the true count.
  • Collisions only add extra increments, so counters can be too high but never too low.
  • Taking the minimum picks the least polluted of the d observations.
  • The estimate is therefore an upper bound on the truth, with error that shrinks as rows are added.
  • An item never seen can still return a nonzero estimate, which is a false positive in count form.

06Error and sizing

  • Error comes from collisions: other items sharing a column add to the counter.
  • Widening rows reduces collisions; adding rows reduces the chance that every row is polluted for a given item.
  • The standard sizing rules are w ≈ e / ε and d ≈ ln(1/δ) for error ε with probability 1 - δ.
  • In words: width controls the size of the error relative to total stream volume, depth controls how often the guarantee fails.
  • The error bound is relative to the total count, so a high-volume stream needs a proportionally wider sketch for the same absolute error.
  • A common practical setup uses a modest number of rows, because each extra row multiplies memory by the same factor.
  • Always state the guarantee you sized for; "approximate counts" without an error bound is not a design.

07Reducing overestimation

  • Conservative update: increment only the counters that are currently at the row minimum, leaving already-high counters alone.
  • This reduces the inflation caused by collisions and improves accuracy at no extra memory cost.
  • It adds a read-before-write step, which matters for high-throughput ingestion.
  • Count sketch is a related structure that estimates the median of signed counters instead of the minimum.
  • Sketch variants can also track the maximum or the sum, depending on the question.
  • The choice depends on whether overestimation or underestimation is safer for the application.
  • For ranking heavy hitters, a small overestimate rarely changes the top of the list.

08Finding heavy hitters

  • A heavy hitter is an item whose frequency exceeds a threshold, often expressed as a fraction of total volume.
  • A sketch alone cannot enumerate candidates, because it never stores keys.
  • Pair it with a bounded candidate set: a small heap or map of the current top items.
  • On each update, query the sketch for the item's estimate and compare it with the weakest candidate.
  • Estimates are upper bounds, so an item can be promoted early but should not be dropped based on a single noisy reading.
  • This is the classic space-saving pattern: exact counts for a few candidates, approximate counts for everything else.
  • Thresholds should be derived from the query — "top k" or "more than a fraction of traffic" — not from an arbitrary number.

09Merging and distributed streams

  • Two sketches with the same width, depth, and hash functions can be merged by adding counters cell by cell.
  • The result estimates the union of both streams, including items seen on both sides.
  • This makes the sketch natural for per-shard or per-region aggregation.
  • Only the counter matrix crosses the network, never the keys.
  • Merging is associative, so aggregation order does not matter.
  • Sketches built with different dimensions or hash seeds cannot be merged, so parameters must be fixed in advance.
  • The same property supports rollups: minute sketches merge into hourly and daily views.

10Limits and failure modes

  • Estimates can be far too high for rare items, because a popular item sharing a column dominates the counter.
  • There is no way to enumerate items or recover the exact set of keys.
  • Decrements break the never-underestimate guarantee, so sliding windows need a different treatment.
  • Very heavy skew concentrates collisions on popular cells, which raises error for everyone hashing there.
  • Fixed sizing means accuracy degrades if traffic grows far beyond the design point.
  • Counters must be sized for the maximum count; overflow silently wraps or saturates.
  • The structure answers frequency, not identity, so it must be paired with something that stores candidates.

11Where it is used

  • Trending topics and most-viewed content, where ranking matters more than exact counts.
  • Rate limiting and abuse detection, where approximate request counts per key are sufficient.
  • Network monitoring for heavy flows and potential denial-of-service sources.
  • Telemetry: counting error types, endpoints, or user agents across a firehose.
  • Query planners and optimizers that need quick row-count estimates for join ordering.
  • Any pipeline that needs per-key frequency with a fixed memory budget and can tolerate overestimation.
  • Pair it with a candidate set for top-k, and with exact counts for the items that matter most.

12Decision rules

  • Use a sketch when the key space is unbounded and exact counts would not fit in memory.
  • Use exact counters when the key set is small, when counts drive billing, or when you must list items.
  • Size for peak traffic because the error bound is relative to total volume.
  • Pick conservative update when ingestion can afford the extra read and accuracy matters.
  • Keep the hash seed and dimensions fixed, or merges and comparisons silently become invalid.
  • Combine with a candidate structure whenever the product asks "which items" rather than "how many".
  • Monitor saturation and error on a sample of known keys; a sketch drifts silently otherwise.

↔Trade-offs to say out loud

  • Fixed memory bounds cost regardless of distinct keys but makes accuracy depend on total volume.
  • Wider rows reduce collision error but increase memory linearly.
  • More rows make the guarantee more reliable but multiply update and query cost.
  • Conservative update improves accuracy but adds a read-modify-write to every increment.
  • Minimum across rows never underestimates but can badly overestimate rare items.
  • Mergeability makes distributed aggregation cheap but requires identical parameters everywhere.
  • Allowing decrements enables sliding windows but destroys the one-sided error guarantee.
  • Pairing with a candidate set answers top-k but reintroduces state proportional to the number of candidates.

?Interview questions

Answer aloud before opening the outline.

1. What problem does a Count-Min Sketch solve?

It estimates how often each item appears in a stream using a fixed amount of memory, independent of how many distinct items arrive. A hash map would need an entry per distinct key, which is unbounded. The sketch trades exactness for a bounded, one-sided error.

2. How is the structure organized?

It is a matrix of d rows and w columns of counters, with one hash function per row. An update increments one counter in each row. A query reads one counter per row and returns the minimum.

3. Why take the minimum instead of an average?

Every counter an item hashes to is at least its true count, because updates only add. Collisions only inflate counters further. The minimum is therefore the least contaminated reading and remains an upper bound, whereas an average could be pushed far above by one very hot colliding item.

4. Can the estimate ever be too low?

No, in the standard additive model. Each occurrence increments all of the item's counters, and nothing decrements them, so every counter is at least the true count. Introducing decrements breaks that guarantee and makes underestimation possible.

5. How do you size a sketch?

Width controls error magnitude and depth controls failure probability: roughly w ≈ e/ε and d ≈ ln(1/δ). Because the error is relative to total stream volume, size against peak traffic. Round up in both dimensions rather than assuming the formula's exact precision.

6. Why is a sketch bad for rare items?

A rare item's counters may be dominated by a popular item that collides with it in every row. The minimum is then far above its true count. This is tolerable for ranking hot items but misleading if you query individual low-frequency keys.

7. How do you find the top-k items with a sketch?

Keep a small candidate set, such as a heap of the current top items, and update it using sketch estimates. The sketch provides approximate counts for everything, while the candidate set stores the identities the sketch cannot. Exact counts for the few candidates finish the job.

8. What is conservative update?

Instead of incrementing every row counter, it increments only those currently at the row minimum. Counters already inflated by collisions stay put, so the overestimate grows more slowly. It costs an extra read per update and does not change memory usage.

9. Can sketches from different servers be combined?

Yes, if they share width, depth, and hash functions: add the matrices cell by cell and the result estimates the combined stream. This is why sketches fit sharded ingestion and time-bucket rollups. Mismatched parameters produce meaningless numbers.

10. Count-Min Sketch or hash map?

Use a sketch when the key space is unbounded, memory is capped, and approximate frequency is enough. Use a hash map when counts must be exact, when you must enumerate keys, or when the distinct key count is genuinely small.

11. How does it differ from a Bloom filter?

A Bloom filter answers membership with possible false positives and no false negatives. A Count-Min Sketch answers frequency and always overestimates. Both are fixed-size summaries that never store their input, but they answer different questions and pair with different downstream logic.

12. What happens if traffic grows well beyond the design point?

Counters grow and collisions inflate estimates, so error increases and the promised bound no longer holds. Popular items blur together and rare items look artificially frequent. The fix is to resize from the start for peak volume or to shard the sketch by key range.

!Traps

  • Reporting sketch output as exact counts, especially for rare or newly seen keys.
  • Sizing for average traffic when the error bound is relative to total volume.
  • Trying to enumerate items from the sketch, which stores no keys.
  • Merging sketches with different dimensions or hash seeds.
  • Introducing decrements and still claiming the never-underestimate guarantee.
  • Ignoring counter width, so a long-running sketch overflows and silently wraps.
