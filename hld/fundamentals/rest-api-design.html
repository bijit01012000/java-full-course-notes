In one lineA good REST API is predictable: the same conventions for resources, methods, status codes, errors, pagination, and versioning everywhere, so learning one endpoint teaches you the rest.
Resource
A named thing the API exposes, such as a customer or an order, addressed by a URI.
Representation
The serialised form of a resource returned or accepted by the API, usually JSON.
Statelessness
Each request carries everything needed to process it, so no per-client session state lives on the server between calls.
Idempotent method
A method whose repeated application leaves the resource in the same state, such as PUT or DELETE.
Safe method
A method that does not change server state, such as GET or HEAD.
Pagination
Splitting a large collection into pages, usually with offset/limit or an opaque cursor.
Cursor pagination
Paging from a stable marker such as an ID or timestamp rather than a numeric offset.
Versioning
A scheme for evolving an API without breaking existing clients, in the path, header, or media type.
Conditional request
A request carrying ETag or Last-Modified validators so the server can answer 304 Not Modified or reject a stale write.
HATEOAS
Returning links to related actions and resources so clients discover transitions instead of hardcoding URLs.

01Why API design conventions matter

Making an API that works is easy: a few endpoints, some JSON, and a client. Keeping it usable as it grows is the hard part.

  • Once other teams, mobile apps, or external customers depend on it, every rename is a potential outage for someone else.
  • Inconsistent conventions force developers to relearn each endpoint instead of generalising from one example.
  • Inconsistent error handling pushes bespoke branching logic into every client.
  • A predictable API reduces support load, because behaviour can be inferred rather than looked up.
  • REST is an architectural style, not a protocol: it describes constraints such as resources, statelessness, and a uniform interface.
  • Most “REST” APIs are pragmatically REST-ish: resource-oriented URLs, HTTP semantics, JSON bodies.
  • The goal is not purity, it is predictability and evolvability.
A useful test: a developer who has used one endpoint should be able to guess the shape of the next one.

02Resources and URIs

  • Model nouns, not verbs: /customers, /orders, /orders/1001.
  • Use plural collection names and a stable identifier for each item: /orders/{orderId}.
  • Express containment with nesting only one or two levels deep: /customers/{id}/orders.
  • Actions that do not fit CRUD can be sub-resources, such as /orders/{id}/cancellation.
  • Keep identifiers opaque; clients should treat them as strings, not as database keys with meaning.
  • Lowercase, hyphen-separated path segments avoid case and encoding ambiguity.
  • Query strings carry filters, sorting, and pagination, not resource identity.
  • Deeply nested or verb-based URLs (/getOrderById) make the surface harder to reason about.

03HTTP methods and semantics

  • GET reads a resource, is safe, and must have no side effects.
  • POST creates a subordinate resource or triggers processing, and is not idempotent by default.
  • PUT replaces a resource with the supplied representation and is idempotent.
  • PATCH applies a partial modification; idempotency depends on the patch format.
  • DELETE removes a resource and is idempotent, even if later calls return 404.
  • Method semantics are a contract: caches, proxies, and clients rely on them being honest.
  • A GET that mutates state breaks retries, prefetching, and caching in ways that are hard to trace.
  • Use the method that matches the semantics rather than tunnelling everything through POST.

04Status codes

  • Use the class of the code, not a blanket 200: 2xx success, 3xx redirect, 4xx client error, 5xx server error.
  • 201 Created for a successful create, ideally with a Location header pointing at the new resource.
  • 204 No Content when an operation succeeds and there is no body to return.
  • 400 for malformed input, 401 for missing or invalid credentials, 403 for a denied but authenticated action.
  • 404 for a missing resource, 409 for a state conflict, 422 for semantically invalid input.
  • 429 for rate limiting with Retry-After, and 5xx only when the server is genuinely at fault.
  • Do not return 200 with an error body: clients, dashboards, and retry logic all key off the status.
  • Document the codes each endpoint can return so clients do not guess.

05Representations and content negotiation

  • JSON is the default representation; the resource is the concept, JSON is only one encoding of it.
  • Clients declare format and expectations with Accept and Content-Type.
  • Return consistent field naming, such as snake_case or camelCase, across every endpoint.
  • Use ISO-formatted timestamps in UTC and state the timezone convention explicitly.
  • Money should carry an amount plus a currency, never a bare float.
  • Prefer explicit nulls over omitted fields when absence is meaningful, and document which it is.
  • Keep representations stable: a field's type changing from number to string breaks strongly typed clients.

06Request and error design

  • Validate input at the edge and return all field-level failures in one response, not one at a time.
  • Use a single, documented error envelope with a machine-readable code, a human message, and optional field details.
  • Never leak stack traces, SQL, or internal identifiers in error bodies.
  • Include a correlation or request ID so support can trace a specific failure.
  • Accept an idempotency key on create-like endpoints so clients can retry safely.
  • Bound request sizes and payload depth to protect parsing and memory.
  • Make error codes part of the contract, because clients branch on them.

07Pagination, filtering, and sorting

  • Never return an unbounded collection; always paginate with an explicit limit and a maximum.
  • Offset pagination is simple and supports jumping to a page, but drifts when items are inserted or deleted mid-traversal.
  • Cursor pagination uses an opaque marker from the last item, giving stable results and better index performance.
  • Return a next cursor rather than letting clients construct one, so the encoding can change later.
  • Include an approximate total only when the UI needs it, because counting large collections is expensive.
  • Define a small, documented set of filter and sort parameters instead of accepting arbitrary field names.
  • Sort order must be deterministic and tie-broken, or pagination can repeat or skip items.

08Versioning and evolution

  • Assume every published field is depended on by someone, including ones you consider internal.
  • Prefer additive change: new optional fields and new endpoints rarely break clients.
  • Adding a required field to a request, renaming a field, or tightening validation are breaking changes.
  • Common versioning schemes are a path segment (/v1/orders), a custom header, or a media type.
  • Path versioning is the most visible and easiest to route; header versioning keeps URLs clean but is easy to overlook.
  • Support a small number of versions and publish a deprecation timeline with sunset dates.
  • Emit deprecation signals in response headers so clients can discover them before removal.
  • Change behaviour behind a feature flag first and measure, rather than shipping a breaking change directly.

09Caching and conditional requests

  • Mark safe, cacheable responses with Cache-Control, and use no-store for anything user-specific or sensitive.
  • Serve shared responses through a CDN or reverse proxy when the data is not per-user.
  • Return an ETag and support If-None-Match so clients can revalidate cheaply with 304 Not Modified.
  • Support If-Match on writes to prevent lost updates when two clients edit the same resource.
  • Use Last-Modified when a reliable modification timestamp exists; ETags are more precise.
  • Vary caches correctly by authorization or tenant, or one user's response can be served to another.
  • Caching is only safe when the method is safe and the response is not personalised without a key.

10Statelessness and horizontal scale

  • Each request must carry its own credentials and parameters so any server instance can handle it.
  • Statelessness is what lets you add instances behind a load balancer without sticky sessions.
  • Put session or conversation state in a token or a shared store, not in process memory.
  • Stateless APIs restart, redeploy, and autoscale cleanly because no instance is special.
  • Long-running work belongs in a job with a status resource: submit, return a handle, poll or receive a webhook.
  • Statelessness does not forbid server-side state; it forbids depending on this server's memory.
  • Idempotency is still required, because stateless retries can duplicate side effects.

11Idempotency, concurrency, and retries

  • Clients must retry on timeouts and 5xx, so non-idempotent operations need an explicit key.
  • Accept an Idempotency-Key header on create and payment endpoints and store the outcome.
  • Use optimistic concurrency with ETags or version numbers to avoid lost updates.
  • Return 409 when a state transition conflicts with the current resource state.
  • Document which errors are retryable and which are permanent, and back that up with status codes.
  • Retries need backoff with jitter, plus a cap, or a struggling service gets hammered.
  • A timeout is an unknown outcome, not a failure: design the endpoint so a retry is harmless.

12Design checklist

  • Are resources nouns, plural, and addressed by opaque identifiers?
  • Does every endpoint use HTTP methods and status codes with their standard meaning?
  • Is there one error envelope with stable machine-readable codes?
  • Is every collection paginated, bounded, and deterministically sorted?
  • Are breaking changes versioned, deprecated on a schedule, and announced in headers?
  • Are cacheable responses marked, and are personalised ones excluded from shared caches?
  • Can a create or payment request be retried safely with an idempotency key?
  • Is the API documented with examples, codes, and rate limits, and is that documentation generated from the contract?

↔Trade-offs to say out loud

  • Strict REST purity gives a uniform, discoverable interface but can be awkward for action-style operations.
  • Path versioning is obvious and easy to route but duplicates the surface and fragments clients across versions.
  • Header versioning keeps URLs stable but is invisible in logs and easy for clients to forget.
  • Offset pagination is simple and allows page jumps but drifts and slows down at deep offsets.
  • Cursor pagination is stable and fast but prevents random page access and complicates UI.
  • Verbose error details speed up integration but risk leaking internal structure and enlarge payloads.
  • Aggressive caching cuts latency and load but risks serving stale or wrongly scoped data.
  • Additive-only evolution avoids breakage but accumulates fields and inconsistent shapes over time.
  • Fine-grained endpoints are simple individually but force chatty clients and more round trips.

?Interview questions

Answer aloud before opening the outline.

1. What makes an API RESTful?

Resource-oriented design with a uniform interface: nouns in URIs, standard HTTP methods and status codes, representations such as JSON, and stateless requests. Purity matters less than consistency and predictability for clients.

2. Why model resources as nouns instead of verbs?

Nouns map cleanly onto HTTP methods and identifiers, so the same URL supports read, replace, and delete with different methods. Verb URLs collapse all intent into POST and lose the semantics that caches and clients rely on.

3. What is the difference between PUT and PATCH?

PUT replaces the resource with the complete representation you send, so repeating it is idempotent. PATCH applies a partial change, and whether that is idempotent depends on the patch format you use.

4. Which status code should a create endpoint return?

201 Created, ideally with a Location header pointing to the new resource and the created representation in the body. Returning a bare 200 loses the information that something was created.

5. Why is returning 200 with an error body a bad pattern?

Clients, monitoring, gateways, and retry logic all branch on the status code. A 200 signals success, so failures get logged as successes and retried incorrectly.

6. When would you choose cursor pagination over offset?

When the collection changes frequently or is large. Cursor pagination stays stable across inserts and deletes and performs well with an indexed sort key, while offset drifts and slows at deep offsets.

7. How do you version a REST API?

Pick one scheme and apply it consistently: a path segment, a custom header, or a media type. Prefer additive change so most releases need no new version, and publish deprecation and sunset policy for the versions you retire.

8. What kinds of changes are breaking?

Renaming or removing a field, changing a field's type, making an optional request field required, tightening validation, and changing status-code behaviour. Adding an optional response field or a new endpoint is normally safe.

9. Why does statelessness matter for scaling?

If any instance can serve any request, you can add instances behind a load balancer, deploy without draining sticky sessions, and replace failed nodes freely. Per-instance memory makes all of that harder.

10. How do you prevent lost updates?

Use optimistic concurrency: return an ETag or version on read, require it on write through If-Match or a version field, and reject stale writes with 409 or 412.

11. How do you make a create endpoint retry-safe?

Accept an idempotency key, store the outcome with the key, and return the stored result on a repeat. That way a client that times out can retry without creating a duplicate order.

12. How would you design a long-running operation in REST?

Accept the request, return 202 Accepted with a job resource URL, and let the client poll that resource or receive a webhook. This keeps requests short and avoids tying a connection to the work.

!Traps

  • Returning 200 for every outcome, including errors and validation failures.
  • Using GET for state-changing operations so retries and prefetches mutate data.
  • Returning unbounded collections and calling the endpoint “done”.
  • Paging with an offset on a fast-changing feed and silently skipping or repeating rows.
  • Breaking clients by renaming a field and shipping it as a minor change.
  • Caching a personalised response in a shared cache without varying on the caller.
  • Documenting errors only as free-text messages with no stable machine-readable code.
