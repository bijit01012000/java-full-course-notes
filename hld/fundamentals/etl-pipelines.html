In one lineAn ETL pipeline moves data from many source systems into one trusted analytical store by extracting changes, transforming them into agreed shapes, and loading them in a repeatable, monitored, and replayable way.
ETL
Extract, Transform, Load — data is cleaned and shaped before it reaches the target analytical store.
ELT
Extract, Load, Transform — raw data lands first and transformations run inside the target warehouse or lakehouse.
Change data capture (CDC)
Reading a database's change log to capture inserts, updates, and deletes without repeatedly scanning the whole table.
Watermark
A stored marker, such as a timestamp or offset, that records how far a pipeline has successfully processed a source.
DAG
A directed acyclic graph of tasks with explicit dependencies, used by orchestrators to schedule and retry pipeline steps.
Idempotency
The property that rerunning the same task with the same input leaves the target in the same final state.
Backfill
Reprocessing historical partitions after a bug fix, schema change, or new metric is introduced.
Data quality gate
An automated check on schema, volume, freshness, or business rules that blocks publication of bad data.
Schema drift
An unannounced change in a source's columns, types, or semantics that breaks downstream assumptions.
Lineage
The recorded path from a source column through transformations to the reports and models that depend on it.

01The problem: data is scattered

The data a business needs is rarely in one place. Each source has its own format, identifiers, and definitions, and someone has to make them agree.

  • Orders live in an OLTP database, payments at a provider, tickets in a helpdesk, and clicks in an analytics tool.
  • Analysts cannot join across those systems by hand; exports are stale, inconsistent, and ungoverned.
  • Source systems are tuned for small transactional reads and writes, so heavy analytical scans must not run against them.
  • The same customer may appear as an internal ID in one system and an email or account number in another, so identity resolution is part of the job.
  • A pipeline is a product with an owner, a freshness SLA, tests, and documentation — not a one-off script.
  • The hard part is usually agreeing on definitions and handling change, not moving bytes.

02Extract: get the data out without hurting the source

Extraction reads from sources and lands the result in a staging area. Incremental extraction is preferred once a source is large.

  • A full extract reads the entire table; it is simple but cost grows with all history, not with new changes.
  • An incremental extract reads rows changed since a watermark using updated_at, a monotonic ID, or a stored offset.
  • CDC reads the database log to capture inserts, updates, and deletes with far less query load than repeated scans.
  • API sources need pagination, rate-limit backoff, retries, and a checkpoint of the last page or cursor.
  • File drops should be landed untouched in a raw zone first, then parsed, so a bad parse never destroys the original.
  • Record extraction metadata — source, extraction time, cursor, and row count — so any run can be audited or repeated.
  • Late-arriving and out-of-order records are normal; extraction must not assume a complete, ordered stream.
Deletes are the classic gap. A timestamp-based extract sees updates but not rows that vanished, so CDC or a periodic reconciliation is needed.

03Transform: turn source rows into agreed business entities

  • Parse and cast types, normalize timestamps to UTC, and standardize currencies, units, and encodings.
  • Clean: quarantine malformed rows, handle nulls explicitly, and deduplicate on a defined business key.
  • Conform: rename to standard columns, map source codes to shared dimensions, and resolve entities across systems.
  • Enrich with reference data, geographic lookups, or derived measures such as margin, duration, or session count.
  • Aggregate to the grain the consumer needs — for example order level for finance and daily-per-region for a dashboard.
  • Keep business rules in one versioned place so every report uses the same definition of active customer or revenue.
  • Transformations should be deterministic and unit-tested: identical input must produce identical output.

04Load: publish atomically and know what was written

  • A full refresh replaces the target table; it is easy to reason about but expensive and briefly inconsistent.
  • An incremental load appends new rows or merges changes by key, which is cheaper but requires a trustworthy key.
  • Upsert or MERGE matches on a key and updates or inserts; deduplicate the batch first or the merge becomes ambiguous.
  • Partition the target by date or tenant and replace only the affected partitions to make reruns cheap.
  • Load inside a transaction or swap a partition atomically so consumers never see half a batch.
  • Publish only after quality checks pass; on failure keep the previous good version and mark the new partition failed.
  • Write an audit row per batch with batch ID, row counts, and timestamps so source and target can be reconciled.

05ETL versus ELT

The difference is where the transformation compute runs and whether raw data is preserved in the target.

  • ETL transforms in a separate engine before loading, so the warehouse receives only curated data.
  • ELT loads raw data into a scalable warehouse or lakehouse, then transforms it with SQL in place.
  • ETL fits strict target schemas, limited target compute, legacy warehouses, and data that must be masked before landing.
  • ELT fits cheap scalable storage and compute, fast iteration, and teams that want raw history available for reprocessing.
  • ELT keeps the ability to derive new metrics from history; ETL may discard the intermediate detail that would enable it.
  • Real pipelines often blend the two: extract to staging, transform in the warehouse, then publish curated marts.

06Batch versus streaming pipelines

  • Batch processes bounded chunks on a schedule: high throughput, simple recovery, latency in minutes or hours.
  • Streaming processes unbounded events continuously: low latency, but needs watermarks, state, and careful delivery semantics.
  • Micro-batch is the compromise — small, frequent batches with batch-style recovery and near-real-time latency.
  • Choose batch when the consumer makes daily or hourly decisions; choose streaming when a decision expires in seconds.
  • Every streaming pipeline still needs a batch or replay path for backfills; reprocessing a whole event log is expensive.
  • A Lambda design keeps batch and speed paths; a Kappa design keeps one stream path and relies on replayable storage.

Do not choose streaming because it sounds modern. If the dashboard is read every morning, a nightly batch is cheaper and easier to operate.

07Orchestration: who runs what, when, and what happens on failure

  • Model the pipeline as a DAG with explicit dependencies instead of a chain of cron jobs.
  • The orchestrator handles scheduling, retries, alerts, concurrency limits, and run history.
  • Trigger on time, on upstream data arrival, or on an event; time-only triggers silently process missing data.
  • Keep tasks small and restartable so a failure reruns one step rather than the whole pipeline.
  • Use bounded retries with backoff; endless retries hide a broken source and burn capacity.
  • Define SLAs and alert on duration, freshness, and row counts — not just on task failure.
  • Pass run metadata such as batch ID and partition through tasks so every output is traceable.

Backpressure and dependencies

  • If a source is late, wait on a data sensor rather than running on an empty partition.
  • Cap concurrent backfills so they do not starve the daily run of source or warehouse capacity.
  • A downstream task should fail fast when its upstream partition is missing or failed.

08Idempotency: reruns must not corrupt the target

Networks time out, workers die, and orchestrators retry. A pipeline that appends on every attempt will duplicate data.

  • A task is idempotent if rerunning it with the same input leaves the same final state.
  • Append-only loads duplicate rows on retry; use a merge key or delete-and-reinsert for the affected partition.
  • Write to a temporary location and atomically rename or swap the partition only after success.
  • Carry a deterministic batch ID and deduplicate on an event ID or on (source, key, event_time).
  • Use transactional table formats that support MERGE, snapshot isolation, and safe concurrent writes.
  • Store processed offsets or watermarks in the same transaction as the output when the store allows it.
  • End-to-end exactly-once is rare; at-least-once delivery plus idempotent writes is the practical target.
-- Idempotent upsert keyed by order_id
MERGE INTO curated.orders AS t
USING staged.orders_batch AS s
  ON t.order_id = s.order_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
Deleting and reloading a whole partition is also idempotent and often simpler than a complex merge — if the partition is small enough.

09Data quality: define what correct means and enforce it

  • Check schema: required columns exist, types match, and unexpected columns are flagged.
  • Check business rules: amounts are non-negative, statuses are in the allowed set, dates are plausible.
  • Check volume: row counts fall within an expected band relative to previous runs and source counts.
  • Check freshness: the latest event timestamp is recent enough for the promised SLA.
  • Check uniqueness and referential integrity on keys before any merge or join.
  • Quarantine bad rows with a reason and a link back to the source instead of dropping them silently.
  • Fail the publish step on critical checks and warn on non-critical ones; review expectations when a source changes.

10Backfills: repairing history without breaking trust

  • A backfill reprocesses historical partitions after a bug fix, schema change, or new metric.
  • Design the pipeline to be partition-addressable so a date range can be rerun independently of today's run.
  • Bound concurrency and run backfills off-peak; they compete for source, network, and warehouse capacity.
  • Replace affected partitions rather than appending, or the backfill doubles the history.
  • Version transformation logic so old and new outputs are distinguishable during the transition.
  • Reconcile row counts and spot-check results before swapping backfilled data into production.
  • Record the backfill in the audit log; silent historical rewrites destroy confidence in every dashboard.

11Observability and operations

  • Monitor at three levels: infrastructure, task execution, and the data itself.
  • Log rows in and out per stage; a sudden drop is often the first sign of a broken source or filter.
  • Track lineage from source column to report so impact analysis is possible when a source changes.
  • Alert a named owner with a runbook; alerts without an owner are eventually ignored.
  • Route repeatedly failing records to a dead-letter table or quarantine for inspection and replay.
  • Run reconciliation jobs that compare source and target totals for critical entities such as payments.
  • Treat runtime and cost as operational metrics; a pipeline that finishes after its SLA has failed.

12Designing a pipeline in an interview

  • Start from the consumer: what question, what freshness, what grain, and how much history is needed.
  • Inventory sources by volume, change rate, access method, and whether deletes matter.
  • Choose ingestion per source — CDC, API, or file drop — instead of forcing one pattern everywhere.
  • Decide ETL versus ELT based on where compute and governance already live.
  • Define the output contract: schema, keys, partitioning, freshness SLA, and quality thresholds.
  • Build idempotency, backfill, and quality gates into the first version; they are not later polish.

State the freshness requirement early. It determines batch versus streaming, cost, and most of the operational complexity.

↔Trade-offs to say out loud

  • Incremental extraction lowers source load and runtime but depends on reliable watermarks and must handle late or deleted rows.
  • CDC captures deletes and near-real-time changes but adds log access, connector operations, and schema-evolution work.
  • ELT preserves raw history and speeds iteration but can create raw sprawl and uncontrolled warehouse compute cost.
  • ETL gives tight control and pre-load masking but adds a separate engine and delays feedback from the target.
  • Streaming reduces latency but multiplies complexity through state, watermarks, ordering, and replay.
  • Full refresh is simple and self-correcting but becomes expensive and slow as history grows.
  • MERGE-based loads avoid duplicates but need a stable key and can be costly on large targets.
  • Strict quality gates protect consumers but can block a business-critical report when the source is late.

?Interview questions

Answer aloud before opening the outline.

1. What is an ETL pipeline?

A pipeline that extracts data from source systems, transforms it into a consistent modeled form, and loads it into a target such as a warehouse or mart. It exists so analytical consumers get one trustworthy, queryable view instead of stitching together exports.

2. Walk me through the three stages.

Extract reads source data, preferably incrementally, and lands it in staging. Transform cleans, conforms, enriches, and aggregates it to the required grain. Load writes it to the target atomically and records audit metadata. Orchestration, quality checks, and monitoring wrap all three.

3. ETL versus ELT — how do you choose?

Choose based on where compute and governance live. ETL when the target is expensive or constrained, the schema is strict, or sensitive data must be masked before landing. ELT when storage and compute scale cheaply, raw history is valuable, and the team iterates in SQL.

4. How do you extract only changes?

Use an updated_at watermark, a monotonic ID, or CDC from the database log. APIs need cursor-based pagination and checkpointing. Whatever the method, handle late-arriving rows and deletes, and store the watermark durably.

5. Why is CDC better than polling a table?

CDC reads the log rather than scanning the table, so it adds little query load, captures deletes, and sees changes close to real time. The cost is connector infrastructure and careful handling of schema changes and log retention.

6. What does idempotent mean for a pipeline and why does it matter?

Rerunning a task with the same input produces the same final state. It matters because retries, timeouts, and worker crashes are normal; without idempotency, every retry risks duplicate or partially written data.

7. How do you make a load idempotent?

Use a deterministic batch key and deduplicate before writing, then MERGE on a stable key or delete and replace the affected partition. Write to a temp location and swap atomically, and store the processed offset in the same transaction when possible.

8. Batch or streaming — what decides it?

The freshness the consumer actually needs. Daily decisions fit batch. If a fraud block or live dashboard must react in seconds, stream. Streaming brings state, watermark, ordering, and replay complexity, so do not pay for it without a latency requirement.

9. How do you handle a bad batch?

Fail the quality gate before publishing, keep the previous good partition live, quarantine bad rows with reasons, and alert the owner. Fix the cause, then rerun only the affected partition idempotently and reconcile counts.

10. What is a backfill and how do you run one safely?

Reprocessing historical partitions after a logic or schema change. Make partitions addressable, limit concurrency, replace rather than append, reconcile against source totals, and record the operation in the audit log.

11. How do you detect schema drift?

Validate incoming schema against a registered contract, compare column sets and types run over run, and fail or quarantine unexpected changes. Alert on new nullable columns and on type widening before downstream models break.

12. What would you monitor for a pipeline?

Task success and duration, freshness, row counts in and out, duplicate rates, quality-check results, queue or lag depth, and cost. Alert on data anomalies, not only on job failures.

13. Design a pipeline that loads orders from three systems into one revenue report.

Extract with CDC or incremental API pulls into a raw zone, standardize currency and timestamps, resolve customer and order identity, deduplicate on order ID, then build a fact table at order grain with conformed date and customer dimensions. Gate on completeness and reconciliation, publish atomically, and keep a replayable raw layer for backfills.

!Traps

  • Appending on every retry and calling the pipeline reliable.
  • Using a timestamp watermark without handling late-arriving rows or deletes.
  • Choosing streaming when the consumer only needs a daily refresh.
  • Transforming only in a script with no version control, tests, or lineage.
  • Skipping quality gates so bad data reaches dashboards and looks authoritative.
  • Running a backfill at full concurrency against a production source.
  • Assuming the source schema will never change, then silently dropping new columns.
