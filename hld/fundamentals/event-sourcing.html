Event
An immutable record of something that already happened, named in the past tense and carrying the data needed to explain it.
Event store
An append-only store of events, ordered within each stream, that acts as the system of record.
Stream
The ordered sequence of events for one entity, such as a single order or account.
Aggregate
A consistency boundary whose state is rebuilt from its stream and which validates new commands against that state.
Replay
Rebuilding state by applying events in order from the beginning of a stream or from a snapshot.
Snapshot
A periodically saved copy of aggregate state that lets replay start from a recent point instead of the first event.
Projection
A derived read model built by consuming events, queryable without replaying a stream.
Optimistic concurrency
Appending only if the stream is still at the expected version, preventing two commands from overwriting each other.
Upcasting
Transforming an older event schema into the current one while reading, so history does not need rewriting.
Temporal query
A read that reconstructs state as of a past point in time by replaying only events up to that point.

01The problem with storing only current state

Most systems keep only the latest value. A new email replaces the old one; a withdrawal overwrites the balance.

  • That is simple and often exactly right for the product.
  • History disappears: you cannot answer why a value is what it is.
  • You cannot reconstruct what the account looked like last week.
  • Audit needs are usually solved later with a separate trail that drifts from the real data.
  • Bugs that corrupted state in the past cannot be replayed to see how it happened.
  • Denormalized derived fields cannot be rebuilt if the derivation logic changes.
  • The alternative is to treat history itself as the primary record.

02What event sourcing is

  • Every state change is stored as an immutable event describing what happened.
  • Current state is not stored as the source of truth; it is calculated by applying events in order.
  • The event log becomes the system of record for that bounded context.
  • Events are facts: they are appended, never updated or deleted in normal operation.
  • A new event is the only way to express change, including corrections (for example, a reversal event).
  • The design is common in finance, logistics, and audit-heavy domains.
  • It is a persistence model, not a UI or messaging pattern.

03Events, commands, and state

  • A command is a request that may be rejected: WithdrawMoney.
  • An event is the recorded outcome in the past tense: MoneyWithdrawn.
  • Events describe facts; commands describe intent. Mixing the names corrupts the model.
  • State is a fold over events: state = reduce(apply, events, initialState).
  • Events should carry enough data to be understood without the current schema.
  • Events must not contain decisions or references that only made sense at write time.
  • A rejected command produces no event, which is why validation happens before append.

04Streams, aggregates, and versions

  • Events are grouped into streams, one per entity such as an order or a bank account.
  • A stream is ordered; order across streams is not guaranteed unless the store provides a global position.
  • The aggregate loads its stream, replays it, and validates a new command against the resulting state.
  • Each append includes the expected version, so concurrent writes fail instead of silently overwriting.
  • The store assigns a monotonically increasing version per stream.
  • Cross-entity invariants need a different boundary or a process manager, not a bigger stream.
  • Stream design is the hardest part: too large and writes contend; too small and invariants fragment.

05Rebuilding state by replay

  • To handle a command, load the events for that stream from the store.
  • Apply them in version order through the aggregate's apply function.
  • The result is the current state, which is then validated and used to decide the next event.
  • The same mechanism answers questions about the past by replaying only up to a timestamp.
  • Replay is deterministic only if apply logic is pure and does not call external systems.
  • Long streams make replay slow, which is what snapshots solve.
  • Replay is also the recovery tool when a projection or cache is wrong.
Receive command→Load stream events→Apply events to rebuild state→Validate command against state→Append new event with expected version→Publish event for projections

06Snapshots

  • A snapshot stores aggregate state at a specific stream version.
  • Loading then reads the latest snapshot and replays only events after it.
  • Snapshots are an optimization, not the source of truth; they can be deleted and rebuilt.
  • Snapshot frequency trades write and storage cost against replay length.
  • Snapshots must be versioned with the code that produced them, or schema changes make them unreadable.
  • A corrupt snapshot must never be trusted over the events.
  • Slow-changing entities may never need snapshots at all.

07Projections and read models

  • Reading a stream and replaying it is too slow for queries and lists.
  • Projections consume events and maintain denormalized read models for specific screens.
  • They are usually eventually consistent and must be idempotent under at-least-once delivery.
  • Projections can be rebuilt from zero, which makes schema and logic changes safe.
  • Multiple projections can serve different views over the same events.
  • A checkpoint per projection tracks how far it has consumed.
  • Event sourcing is often paired with CQRS, but each is an independent decision.

08The event store

  • Append-only writes with no in-place updates; correction means appending another event.
  • Ordering within a stream is guaranteed; global ordering enables subscriptions.
  • Optimistic concurrency is enforced with expected version numbers.
  • Durability and fsync policy decide whether an acknowledged event can be lost.
  • A global position or subscription feed lets projections and other consumers tail the log.
  • Retention is permanent for the business-meaningful history, which drives storage planning.
  • Some systems implement the store on relational tables; others use purpose-built event databases or log systems.

09Schema evolution and event versioning

  • Events are contracts that live for years, so changing them is a migration problem, not a refactor.
  • Prefer additive changes: new optional fields with safe defaults.
  • Version event types and use upcasting to convert old shapes on read.
  • Never reinterpret an existing field's meaning; write a new event type instead.
  • Unreadable old events break replay, which breaks rebuilds and audits.
  • Keep a schema registry or documented contract tests for event payloads.
  • Serialization format choice matters: text formats are easier to evolve and debug than opaque binary blobs.

10Benefits

  • Complete audit trail by construction, not as a bolted-on side table.
  • Temporal queries answer what the state was at any point.
  • Debugging can replay the exact sequence that produced a bad state.
  • Rebuildable views let you change read models or fix bugs and reprocess history.
  • Loose coupling because consumers subscribe to facts instead of being called synchronously.
  • No lost intent: every change is explained by the event that caused it.
  • New features can often be added by building a new projection over existing history.

11Costs and constraints

  • Simple reads now require projections, which is extra infrastructure and lag.
  • Storage grows without bound, and rebuilding takes real time and compute.
  • Deleting data conflicts with immutability; privacy requests need crypto-shredding or redaction strategies.
  • Queries across aggregates are awkward without projections or a separate store.
  • The team must understand versioning, concurrency, replay, and idempotency.
  • Existing reporting, BI, and ad-hoc SQL tools expect tables, not streams.
  • Operationally, you now run an event store plus projections plus snapshotting.

12Failure modes

  • A non-deterministic apply function makes replay produce different state over time.
  • External calls inside apply turn replay into a side-effecting operation.
  • Duplicate event delivery double-applies changes in a projection without idempotency.
  • Out-of-order projection consumption overwrites newer data with older values.
  • Unversioned event schemas break replay after a deploy.
  • A missing subscription checkpoint forces a full rebuild or loses events.
  • Unbounded streams without snapshots make command handling progressively slower.

13When to use it, and what it is not

  • Use it when history, audit, or temporal reconstruction is a core requirement.
  • Use it when multiple derived views must be rebuilt as logic changes.
  • Avoid it for simple CRUD where current state is all anyone needs.
  • Event sourcing is not event-driven architecture: the latter is about messaging between components.
  • It is not change data capture: CDC records database row changes, not domain intent.
  • It is not an audit log bolted onto mutable tables; the log is the source of truth.
  • Start with one bounded context with clear value, and keep the rest of the system conventional.

↔Trade-offs to say out loud

  • Full history enables audit and temporal queries but grows storage forever.
  • Replay rebuilds any view or fixes bad state but costs time and compute as streams lengthen.
  • Snapshots keep command latency flat but add write amplification and versioning concerns.
  • Projections make reads fast and flexible but introduce lag and rebuild infrastructure.
  • Immutability preserves truth but makes deletion and privacy compliance harder.
  • Event contracts decouple consumers but require long-term schema evolution discipline.
  • Intent-rich events explain changes but couple the model to the domain language at write time.
  • Specialized store fits append-heavy workloads but leaves the team without familiar SQL tooling.

?Interview questions

Answer aloud before opening the outline.

1. What is event sourcing in one sentence?

It is a persistence model where every state change is stored as an immutable event and current state is derived by replaying those events. The event log, not a mutable row, is the source of truth.

2. How is current state obtained?

By loading the entity's stream and applying each event in order from the start or from the latest snapshot. The same apply logic always produces the same state, so replay is deterministic.

3. Why are snapshots needed?

Long streams make full replay slow, and command handling pays that cost on every load. A snapshot stores state at a version so only newer events must be applied. It is a cache that can be discarded and rebuilt.

4. What is the difference between a command and an event?

A command is an intent that may be rejected, such as WithdrawMoney. An event is a recorded fact that already happened, such as MoneyWithdrawn. Only accepted commands produce events.

5. How do you handle a correction or reversal?

Append a compensating event rather than editing history. For example, append a reversal or adjustment event so the log still explains what happened and why the current state changed.

6. How do you prevent two concurrent commands from conflicting?

Use optimistic concurrency: the append includes the expected stream version, and the store rejects it if another event landed first. The command can then reload and retry or fail.

7. How do you query event-sourced data?

Through projections that maintain denormalized read models, or by replaying a stream for a single entity. Ad-hoc queries across many entities need projections or an exported analytical store.

8. How do you evolve event schemas?

Prefer additive changes with defaults, version event types, and upcast older shapes when reading. Avoid changing the meaning of an existing field, and test that old events still replay correctly.

9. How does event sourcing handle deletion and privacy?

Immutability conflicts with delete requests, so designs use crypto-shredding (discarding the key that decrypts a person's data), redaction of payload fields, or a separate personal-data store referenced by events. The approach must be decided before launch, not after.

10. Is event sourcing the same as event-driven architecture?

No. Event-driven architecture is about components communicating through events. Event sourcing is about how one component persists state. You can use events for messaging while storing plain rows, or source events without publishing them anywhere.

11. What makes replay go wrong?

Non-deterministic apply logic, external calls or clock reads inside apply, and schema changes that alter interpretation. Replay must be a pure function of events and code, with versions pinned so history is reproducible.

12. When should you avoid event sourcing?

When nobody needs history, temporal queries, or rebuildable views, and the domain is simple CRUD. The event store, projections, snapshots, and versioning only pay off when the history is genuinely valuable.

!Traps

  • Naming events in the imperative or present tense, which blurs commands and facts.
  • Putting external calls, randomness, or current time inside the apply function, breaking replay determinism.
  • Skipping event schema versioning until the first breaking change.
  • Building projections without idempotency and then meeting at-least-once delivery.
  • Replaying unbounded streams on every command because snapshots were never added.
  • Treating the event store as an audit side-log while mutable tables remain the source of truth.
  • Ignoring privacy deletion requirements until a user requests erasure from an immutable log.
