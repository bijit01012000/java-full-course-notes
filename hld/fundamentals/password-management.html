In one lineDesign password storage around one assumption — the database will be stolen — and make the stolen data as useless as possible with per-user salts, a deliberately slow hash, and a reset flow that does not become the weakest link.
Password hashing
Running a password through a one-way function so the stored value cannot be turned back into the password, only compared against a new attempt.
Salt
A unique random value per user, stored with the hash, that ensures identical passwords produce different stored values.
Pepper
A secret value applied to passwords and kept outside the database, so a database-only leak still cannot be attacked offline without it.
Work factor
The tunable cost of a password hash — iterations, memory, or parallelism — set high enough to slow attackers but low enough for login latency.
Key derivation function
A deliberately slow, memory-hard function such as bcrypt, scrypt, or Argon2id designed for password storage.
Rainbow table
A precomputed lookup of hashes to passwords, defeated by per-user salts that force attackers to attack each hash separately.
Credential stuffing
Trying username-password pairs leaked from one site against other sites, which works because people reuse passwords.
Rehash on login
Upgrading a stored hash to a stronger algorithm or higher cost when the user next authenticates successfully.
Constant-time comparison
Comparing secrets in a way that does not leak how many leading bytes matched through response timing.
Password reset token
A single-use, expiring, high-entropy value sent out of band that authorizes setting a new password.

01The assumption that shapes the design

The simplest login system stores the password exactly as typed and compares on login. It works, until the database leaks.

  • Leaks happen through SQL injection, a misconfigured backup, a stolen admin credential, or a compromised vendor.
  • The attacker then holds every user's password in plain text, with no work required.
  • Damage does not stop at your system: password reuse lets the same email-password pairs be tried against email, banking, and shopping sites.
  • So the design goal is not prevent the breach alone, but make the stolen data as useless as possible.
  • Everything else — salting, slow hashing, peppers, reset flows — follows from that single assumption.
  • This is a data-at-rest problem with a twist: the stored value must be verifiable but never reversible.

02Why plaintext and reversible encryption both fail

  • Plaintext storage means the leak is a credential dump, not a data breach only.
  • Encrypting passwords is better than plaintext but still reversible: whoever holds the key can recover every password.
  • The key usually sits in the same infrastructure as the database, so a full compromise recovers both.
  • Insiders and support staff with database or key access can read user passwords, which is both a security and privacy failure.
  • Backups, replicas, and analytics copies multiply every stored plaintext or decryptable password.
  • A one-way function removes the key-management problem entirely: there is nothing to decrypt.
  • The system only ever needs to answer does this input match, never what was the password.

03Hashing: verification without storage

  • Store hash(password); on login, hash the submitted password and compare.
  • A cryptographic hash is deterministic, so the same input always produces the same output and comparison works.
  • It is one-way in practice: recovering the input from the digest is infeasible for a strong hash.
  • The stored digest is not secret in the same sense as a password, but it must still be protected, because offline guessing is possible.
  • A hash also fixes length and format issues: any password becomes a fixed-size stored value.
  • The system must never log the plaintext password or include it in error reports, traces, or analytics.
  • Hashing alone is not enough — the choice of hash and the addition of salt determine how much a leak actually costs the attacker.

04Why general-purpose fast hashes are the wrong tool

  • Hashes such as MD5 and SHA-family digests are designed to be fast, which is exactly wrong for passwords.
  • Fast hashes let an attacker test an enormous number of guesses per second on commodity hardware.
  • Unsalted hashes are also precomputable: an attacker builds a table of common passwords and their digests once, then looks up matches.
  • Identical passwords produce identical digests, so one cracked value reveals every user who chose it.
  • The attacker's cost is the whole game; a fast hash makes guessing cheap, a slow hash makes it expensive.
  • Password storage therefore needs a deliberately expensive function, not the fastest available primitive.

05Salts

  • A salt is a unique random value generated per user and stored alongside the hash, usually in plaintext.
  • The hash input becomes salt + password, so two users with the same password get different stored values.
  • Salts defeat precomputed rainbow tables, because a table would have to be rebuilt for every possible salt.
  • They also prevent an attacker from spotting shared passwords or cracking many accounts with one guess.
  • The salt does not need to be secret; its job is uniqueness, not confidentiality.
  • Use a cryptographically secure random source and a salt long enough to make collisions negligible.
  • A single global salt is a common mistake: it restores the shared-hash problem and makes precomputation worthwhile again.

06Slow, memory-hard hashing

  • Password hashing functions are intentionally expensive: they require many iterations, large memory, or both.
  • bcrypt is widely available and includes the salt and cost in the stored string.
  • scrypt adds memory hardness, which reduces the advantage of specialized parallel hardware.
  • Argon2id is a modern design with tunable time, memory, and parallelism, and is a strong default for new systems.
  • Memory hardness matters because attackers use GPUs and dedicated hardware that excel at cheap, parallel computation.
  • The stored format should include the algorithm, parameters, and salt, so verification can evolve without a schema change.
  • Never invent a custom construction by composing primitives yourself; use a standard password hashing function.

07Peppering

  • A pepper is a secret value, not stored in the database, mixed into the password before hashing.
  • It is usually held in a secrets manager or HSM, so a database-only leak does not give the attacker everything needed to start guessing.
  • Unlike a salt, a pepper is shared across users and must remain secret.
  • Rotating a pepper requires rehashing every password, which is only possible at login or through a forced reset.
  • A pepper is defense in depth, not a replacement for salting and slow hashing.
  • If the application server is also compromised, the pepper is available and the protection disappears.
  • Use it when the threat model specifically worries about a database dump without application compromise.

08Choosing and tuning the cost

  • Set the work factor as high as the login latency budget allows, then verify on the hardware you actually run.
  • The cost must be paid once per login by you and once per guess by the attacker — that asymmetry is the whole point.
  • Measure under concurrency: a cost that is fine for one login can saturate CPU during a traffic spike.
  • Plan to increase the cost over time as hardware gets faster; parameters must be revisitable, not fixed forever.
  • Store the parameters with each hash so old and new values can coexist during migration.
  • Do not lower the cost to make a slow login endpoint feel faster; fix the endpoint or add capacity instead.
  • Document the chosen parameters and the date they were reviewed, so the next engineer knows the baseline.

09The login path and side channels

  • Compare derived values in constant time to avoid leaking information through timing differences.
  • Return the same error for unknown user and wrong password, so the endpoint does not confirm which accounts exist.
  • Perform a dummy hash for unknown users so response time does not reveal account existence either.
  • Rate limit by account and by source, because online guessing is cheap when nothing throttles it.
  • Log authentication failures without logging the submitted password, and alert on distributed guessing patterns.
  • Invalidate or rotate the session identifier on successful login to prevent session fixation.
  • Keep the password out of URLs, referrers, and client-side analytics.

10Reset flows

  • Reset is often the weakest link: a predictable token or a leaky email flow bypasses all the hashing work.
  • Generate a high-entropy token, store only its hash, and bind it to the user and a short expiry.
  • Make tokens single-use: invalidate on use, on a new reset request, and on password change.
  • Serve reset links over HTTPS and avoid putting tokens in referrers or third-party analytics.
  • On completion, invalidate existing sessions and notify the user out of band, so a hijacked reset is visible.
  • Do not reveal whether an email address exists when a reset is requested.
  • Support staff should never be able to read or set a password directly; they can only trigger the same reset flow.

11Surrounding controls: reuse, MFA, and breach checks

  • Block known-breached passwords at signup and reset by checking against a breach corpus, ideally without sending the password anywhere.
  • Reject the most common passwords and the user's own email or service name.
  • Offer multi-factor authentication, which limits the value of a cracked password even after a breach.
  • Encourage or require a password manager, which makes unique passwords practical and reduces reuse.
  • Monitor for credential stuffing patterns: many accounts, few source networks, high failure rates.
  • Notify users when their password changes, from a new device, or after a breach affecting your service.
  • Password rotation on a fixed schedule is generally less useful than rotation on evidence of compromise.

12Migration and breach response

  • Identify legacy hashes by their stored format — for example unsalted or fast-hash values — and mark them for upgrade.
  • Rehash transparently at successful login: verify with the old scheme, then store with the new one.
  • For users who never log in, force a reset when the account is next touched or after a deadline.
  • A breach response starts with forced resets and session invalidation, not with an email explaining it later.
  • After a leak, assume offline cracking has begun; raise the work factor and invalidate anything derived from the passwords.
  • Keep an audit trail of algorithm migrations so you can prove coverage.
  • Test the whole flow: signup, login, reset, rehash, and lockout, because migration bugs lock users out at scale.

↔Trade-offs to say out loud

  • Higher work factors make offline cracking expensive but raise login latency and CPU cost under load.
  • Memory-hard hashing blunts GPU attacks but increases memory pressure on authentication servers.
  • Peppering protects against a database-only leak but complicates rotation and depends on secret storage.
  • Aggressive breach checks block weak passwords but add a dependency and can leak partial password data if implemented carelessly.
  • Strict lockout slows guessing but enables denial of service against known accounts.
  • Transparent rehash on login avoids mass resets but leaves dormant accounts on old hashes indefinitely.
  • Long-lived sessions improve usability but widen the window after a password compromise.
  • Forced periodic rotation satisfies policy but tends to produce weaker, predictable passwords.

?Interview questions

Answer aloud before opening the outline.

1. Why should passwords never be stored in plain text?

Because any database leak then hands attackers every credential directly, with no work required. Password reuse spreads the damage to other services, and insiders or support staff can read the values. The design assumption should be that the database will eventually be stolen.

2. Why is encrypting passwords not good enough?

Encryption is reversible, so whoever obtains the key recovers every password. The key usually lives in the same infrastructure as the data, so a full compromise yields both. A one-way hash removes the key entirely, which is why password storage uses hashing rather than encryption.

3. Why are SHA-256 or MD5 unsuitable for passwords?

They are designed to be fast, so an attacker can test an enormous number of guesses per second. Unsalted fast hashes are also precomputable and reveal users who share a password. Password storage needs a deliberately slow, salted function whose cost can be tuned.

4. What does a salt protect against?

It makes precomputed rainbow tables useless, because a table would have to be rebuilt per salt. It also ensures identical passwords hash differently, so cracking one account does not reveal others. The salt is stored with the hash and does not need to be secret.

5. What is the difference between a salt and a pepper?

A salt is unique per user and stored alongside the hash, defeating precomputation. A pepper is a shared secret kept outside the database, so a database-only leak still leaves the attacker unable to guess efficiently. Peppers add defense in depth but complicate rotation.

6. Which password hashing algorithm would you choose?

A memory-hard, tunable function such as Argon2id for new systems, or bcrypt or scrypt where library support favors them. All of them are acceptable when the cost is tuned and the salt is unique. Avoid fast general-purpose hashes and any home-grown construction.

7. How do you choose the work factor?

Set it as high as your login latency budget allows while remaining acceptable under concurrent load, and measure on production-class hardware. Store the parameters with each hash so they can be raised later, and rehash at login when a user presents a valid password under an outdated setting.

8. How do you migrate users from an old hashing scheme?

Verify with the old scheme at login, then immediately store a hash using the new algorithm and parameters. Keep both verification paths until coverage is complete, and force a reset for dormant accounts after a deadline. The login path must tolerate mixed formats during the whole migration.

9. What makes a password reset flow secure?

A high-entropy token that is stored hashed, bound to the user, short-lived, and single-use. It travels over HTTPS only, and completing the reset invalidates other sessions and notifies the user. The endpoint should not reveal whether an email address exists.

10. How do you prevent username enumeration?

Return the same message and comparable timing for unknown users and wrong passwords, including a dummy hash computation for missing accounts. Also apply the same rate limiting and lockout behavior. Seemingly harmless variations in error text or latency are enough to enumerate.

11. Does a slow hash make rate limiting unnecessary?

No. A slow hash raises the cost per guess, but online guessing against a single account is still cheap without throttling. Rate limiting limits attempts per account and per source, while the slow hash protects the data if it is stolen and attacked offline. They defend different phases.

12. What should happen after a password database leak?

Invalidate sessions, force resets, and notify affected users without waiting for the full investigation. Assume offline cracking has started, so raise the work factor and treat the leaked hashes as compromised. Also review how the leak occurred, since the fix has to address the access path, not just the storage format.

!Traps

  • Hashing with a fast general-purpose digest and considering the password problem solved.
  • Using one global salt or no salt, which restores precomputation and reveals shared passwords.
  • Storing the pepper in the same database or configuration file as the hashes.
  • Logging the submitted password or including it in error reports and traces.
  • Returning a distinct error for unknown users, enabling account enumeration.
  • Making reset tokens predictable, long-lived, or reusable.
  • Lowering the hashing cost because the login endpoint feels slow under load instead of adding capacity.
