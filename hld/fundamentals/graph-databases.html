01The problem graph databases solve

Many questions are about connections rather than records: who is connected to whom, how far apart two entities are, and which accounts form a ring.

  • A relational database answers these with joins, and each additional hop adds another join.
  • At two or three hops the query is still manageable; at five or more it becomes a chain of joins whose intermediate result sets explode.
  • The database also does index lookups per hop, so cost grows with depth and with the size of intermediate sets.
  • Recursive queries exist, but they are awkward to write and still build large intermediate tables.
  • The relationships themselves are often the data — their type, direction, and properties carry meaning.
  • In a relational schema, a many-to-many relationship collapses into a junction table that hides direction and attributes.
  • Graph databases make the connections the primary structure instead of a derived join.

02What a graph database is

  • Data is stored as nodes and edges, not tables and rows.
  • Nodes and edges can both carry properties, so an edge can record when a relationship started or how strong it is.
  • Edges have a type and a direction, such as (alice)-[:FOLLOWS]->(bob).
  • Labels classify nodes and edges, which lets a query match only the relevant subset.
  • The graph is queried by pattern matching: describe the shape you want and let the engine find it.
  • Because edges are stored with their endpoints, a traversal follows pointers rather than recomputing joins.
  • The model suits connected data; it is a poor fit for bulk tabular reporting.

03Index-free adjacency

  • Each node stores direct references to its incident edges, and each edge stores references to its two endpoints.
  • Traversing one hop therefore means following a pointer, with no global index lookup.
  • Cost scales with the size of the touched subgraph, not with the total number of nodes in the database.
  • This is what keeps deep traversals practical: hop ten costs about as much as hop two.
  • In a relational engine, each hop is an index probe plus a join, so latency grows with depth.
  • The trade-off is that edges are physical: moving or repartitioning data means moving relationship pointers too.
  • It also means writes touch several records, since the edge and both endpoints must be updated consistently.

04Modeling: property graphs and RDF

  • The property graph model gives nodes and edges labels and arbitrary properties, which is the common application-facing choice.
  • The RDF model expresses everything as subject-predicate-object triples, which favors interchange and shared vocabularies.
  • RDF suits publishing and integrating data across organizations; property graphs suit application queries over one domain.
  • Directions matter: FOLLOWS is not symmetric, while a FRIEND_OF edge usually is.
  • Relationships can be reified — turned into nodes — when they need their own relationships, such as a transaction between two accounts.
  • Model entities as nodes and facts about a connection as edge properties, not as extra nodes, unless the fact itself connects to other things.
  • A common mistake is to model every attribute as a node, which turns a clean graph into a tangle of lookups.

05Querying

  • Queries describe a pattern: a start node, a sequence of edges, and the properties to match.
  • Cypher, Gremlin, SPARQL, and the emerging GQL standard cover the common graph query styles.
  • A variable-length path matches an unknown number of hops, which is how friends of friends is expressed in one clause.
  • Filters can apply to nodes, to edges, or to the path as a whole, such as a maximum depth.
  • Results are usually the matched nodes, the edges, or aggregates such as a shortest-path length.
  • The engine chooses a traversal order, and a bad starting point can turn a fast query into a scan.
  • Unlike SQL, the query is naturally recursive, which is why path questions are far shorter to express.
MATCH (a:Person {name: 'Alice'})-[:FOLLOWS*1..3]->(b:Person)
RETURN b.name, count(*) AS reach

06Why traversals stay fast, and where they do not

  • A traversal begins at a small number of start nodes found through an index.
  • From there it follows edge references, expanding one hop at a time and keeping only the frontier.
  • Cost is roughly proportional to the number of nodes and edges actually visited.
  • It degrades when the frontier explodes — high-degree nodes, dense regions, or unbounded depth.
  • A supernode with an enormous number of edges is the classic failure: every traversal through it touches everything.
  • Dense graphs also blow up combinatorially, because paths multiply faster than nodes.
  • So the practical limits are degree and depth, not total data size.

07Indexes and constraints

  • Even with pointer-based traversal, you need an entry point, so indexes exist on node properties.
  • A lookup like the person with this email uses a property index to find the start node.
  • Uniqueness constraints on a property prevent duplicate entities, which matters when data arrives from several sources.
  • Edge properties can also be indexed when they are used to filter during a traversal.
  • An index lookup followed by a short traversal is the normal fast path.
  • A query that must scan all nodes of a label, or traverse from thousands of starting points, loses the advantage.
  • So indexes decide where a traversal starts; adjacency decides how cheaply it continues.

08Traversal algorithms

  • Breadth-first search finds the closest matches first, which suits shortest-path and recommendation queries.
  • Depth-first search explores a branch fully, which suits path existence and cycle detection.
  • Shortest path, with or without edge weights, answers distance and routing questions.
  • PageRank and centrality measures rank nodes by influence in the graph.
  • Community detection and connected components find clusters and isolated islands.
  • Algorithms can run inside the database for local queries, or in a batch framework for whole-graph computation.
  • Global analytics over a huge graph is usually a batch job that writes results back as properties, not an interactive query.

09Scaling a graph

  • Read scaling is straightforward: replicate the graph and serve traversals from replicas.
  • Write and storage scaling is hard, because edges connect arbitrary nodes and therefore cross partition boundaries.
  • If two connected nodes land on different machines, every traversal of that edge becomes a network call.
  • Partitioning strategies duplicate boundary nodes or cut edges, which adds coordination and can multiply storage.
  • Graph partitioning is a hard problem, and a bad partition makes cross-machine traffic dominate latency.
  • Supernodes concentrate load on whichever partition holds them, so they also become hotspots.
  • That is why many graph systems prefer a replicated, read-optimized deployment over aggressive sharding.
  • Some workloads avoid the problem entirely by keeping the graph in memory on one large machine.

10Transactions and consistency

  • Single-node graph databases typically offer ACID transactions over a traversal.
  • An update must keep the edge and both endpoints consistent, so a transaction may touch several records.
  • Distributed graph databases must trade some consistency or isolation to avoid coordinating every traversal.
  • For most query workloads, reads tolerate a slightly stale replica, while writes need the authoritative copy.
  • Causal consistency is often enough: a client should see its own writes and their effects in order.
  • Applications that mutate relationships heavily should plan for conflict and retry semantics.
  • The right guarantee depends on the question: fraud detection may tolerate lag, access control usually does not.

11Where graph databases fit

  • Fraud and risk: finding rings of accounts that share devices, addresses, or payment instruments.
  • Recommendations: friends-of-friends, co-purchase, and shared-interest paths.
  • Knowledge graphs: entities and typed relationships assembled from many sources.
  • Identity and access: users, groups, roles, and inherited permissions as a graph.
  • Network and infrastructure: topology, dependency, and blast-radius analysis.
  • Master data: resolving duplicate entities across systems by their connections.
  • The common thread is that the question is about the shape of connections, not about aggregating columns.

12When not to use one

  • If the question is one or two hops deep, a relational join or a recursive query is simpler and cheaper to operate.
  • If most queries are aggregations over records, a columnar or relational store is far better.
  • If the data is append-only events, a time-series or wide-column store fits the write pattern.
  • If the graph is enormous and analyzed in bulk rather than queried interactively, a batch graph framework is the right tool.
  • If the hierarchy is a simple tree, an adjacency list with a recursive CTE is enough.
  • A graph database adds a new system to operate, backup, and staff, so the traversal advantage must be real.
  • The test is whether depth and connection shape are central to the product, not whether the data can be drawn as a graph.

13Operational realities

  • Backup and restore must preserve edges and indexes together, or traversals break silently.
  • Memory sizing matters more than for row stores, because traversals benefit enormously from cached adjacency.
  • Monitoring should track traversal depth, frontier size, and the most-traversed supernodes.
  • Bulk import needs its own path, since loading edge by edge through the transaction API is slow.
  • Query reviews catch unbounded variable-length patterns before they reach production.
  • Schema constraints and naming conventions keep a graph from becoming an untyped tangle.
  • Graph projections — a purpose-built subgraph — are often better than letting every query roam the full graph.

↔Trade-offs to say out loud

  • Index-free adjacency makes deep traversals cheap but makes writes and repartitioning more expensive.
  • First-class edges capture relationship semantics but add records that must stay consistent with both endpoints.
  • Property graphs are ergonomic for applications but less standardized than RDF for interchange.
  • Variable-length paths express deep questions concisely but are easy to write unboundedly and expensively.
  • Replication scales read-heavy traversals but does not solve write scaling.
  • Sharding increases capacity but turns cut edges into network hops and complicates traversal.
  • In-memory graphs give the fastest traversals but cost the most per unit of data.
  • Global graph algorithms answer important questions but run as batch jobs, not interactive queries.
  • A dedicated graph store buys traversal performance but adds a system to operate and a second copy of data.

?Interview questions

Answer aloud before opening the outline.

1. Why do relational joins degrade on deep traversals?

Each hop requires an index lookup and a join, and each join produces an intermediate result set that the next hop must consume. As depth grows, those intermediate sets grow and the planner has more work to do. The database is also re-deriving relationships that a graph stores directly.

2. What is index-free adjacency?

Each node holds direct references to its incident edges, and each edge points at its endpoints. Traversing a hop is a pointer follow rather than an index probe, so cost depends on the subgraph touched instead of the total graph size. That is why deep traversals stay practical.

3. Property graph or RDF?

Property graphs attach labels and arbitrary properties to both nodes and edges, which suits application queries. RDF expresses everything as subject-predicate-object triples, which suits interchange, shared vocabularies, and knowledge graphs assembled from many sources. Edge attributes need reification in RDF.

4. What makes a supernode a problem?

A supernode has an enormous number of edges, so any traversal that reaches it must examine a huge frontier, and it concentrates load on one partition or cache line. Common examples are celebrity accounts, shared corporate entities, and popular products. Mitigations include excluding them from paths or precomputing their neighbors.

5. Do you still need indexes in a graph database?

Yes. Adjacency makes the traversal cheap, but something must find the starting node. Property indexes locate start nodes by email, id, or name, and uniqueness constraints prevent duplicate entities. An index lookup followed by a short traversal is the normal fast path.

6. How do you express friends-of-friends?

With a variable-length path pattern that allows one to three hops and a filter on the target, written in a single clause. The engine expands the frontier hop by hop and deduplicates results. The danger is leaving the depth unbounded on a dense graph.

7. Why is sharding a graph hard?

Edges connect arbitrary nodes, so a partition boundary cuts relationships. Traversing a cut edge becomes a remote call, and keeping the two sides consistent needs coordination. Strategies duplicate boundary nodes or accept expensive cross-partition hops, and both add cost.

8. How would you scale graph reads?

Replicate the graph and serve traversals from replicas, accepting some staleness. Keep the hot portion of the adjacency in memory, since traversal cost is dominated by cache misses. Project the graph per use case so queries touch a smaller subgraph.

9. When is a recursive SQL query good enough?

When traversal is shallow, the hierarchy is simple, and the graph is not the product's core. A recursive CTE over an adjacency list handles org charts, category trees, and a few hops well, with no new system to operate and full transactional consistency.

10. Graph database or batch graph processing?

Use a graph database for interactive, local questions — a few hops around known entities. Use batch processing for whole-graph computation such as global ranking or community detection, then write results back as properties. Trying to run global analytics interactively is the common misallocation.

11. What consistency issues arise with edges?

An edge and its two endpoints must stay consistent, so a write touches several records, and a distributed deployment cannot avoid coordinating them. Partial writes can leave a dangling edge. Transactions, or repair procedures, are needed to prevent a graph that lies about its own structure.

12. Give three strong graph use cases.

Fraud detection, where rings of accounts share devices and addresses; recommendations, where similarity flows along paths of shared interests; and identity or permission graphs, where access is inherited through nested groups. In each, the question is about connection shape rather than column aggregation.

!Traps

  • Using a graph database for data that happens to be drawable as a graph but is queried as tables.
  • Writing variable-length paths without a depth bound and scanning a dense graph by accident.
  • Modeling every attribute as a node, producing a slow and unreadable tangle.
  • Ignoring supernodes until one celebrity account or shared tenant dominates traversal cost.
  • Assuming edge traversal is free across a sharded cluster, where cut edges become network hops.
  • Loading bulk data through the transactional write API instead of a bulk import path.
  • Choosing a graph store for a two-hop question that a single join already answers.
