In one lineA load balancing algorithm is the rule that picks which backend serves a request; the right choice depends on what the balancer can actually observe and on how uneven request cost and duration are.
Static algorithm
A rule that picks a backend without looking at current server load, such as round robin or random.
Dynamic algorithm
A rule that chooses using live signals such as active connections, request counts, or response time.
Round robin
Cycling through the server list in fixed order, giving each backend an equal share of requests.
Weighted round robin
Round robin where each server has a weight and receives requests in proportion to it.
Least connections
Sending each new request to the server with the fewest active connections.
Power of two choices
Sampling two servers at random and choosing the less loaded one, which avoids herd effects.
Consistent hashing
Placing servers and keys on a ring so that adding or removing a server moves only a small fraction of keys.
Herding
Many balancer instances independently choosing the same least-loaded server and overloading it at once.
Slow start
Gradually ramping traffic to a new server so its caches and connection pools can warm up.
Virtual node
An extra position on the hash ring owned by a server, used to spread keys more evenly.

01Static and dynamic algorithms

A load balancer sits in front of a pool of servers and decides which one handles each request. The rule is the algorithm.

  • Static algorithms follow a fixed rule: fixed order, fixed weights, or random choice, with no live state.
  • Dynamic algorithms read server state first: active connections, active requests, response time, or reported load.
  • Static is cheap and predictable but blind: it keeps sending to an overloaded server because it never looks.
  • Dynamic adapts but depends on metrics that are delayed, partial, or measured by the wrong instance.
  • An algorithm is only as good as its signal: connection count helps only if connections track load.
  • No algorithm compensates for missing health checks, bad timeouts, or insufficient capacity.
  • Most real systems layer several rules: zone preference first, then a dynamic pick inside the zone.

02Round robin

With servers A, B, and C, the first request goes to A, the second to B, the third to C, and the fourth back to A.

  • The balancer only stores the index of the last pick, so the implementation is a counter plus a remainder.
  • It is the common default in NGINX and HAProxy and a sensible baseline in interviews.
  • It works when all servers have similar capacity and requests cost roughly the same.
  • It fails when request cost varies: a five-second report and a ten-millisecond lookup get equal turns.
  • It also fails with heterogeneous hardware: a 16-core server still gets one third of the traffic.
  • In production the list must contain only healthy, ready servers, so health checking is part of the algorithm.
  • Requests are balanced, but work is not, which is the distinction that matters.
pick = servers[counter % len(servers)]
counter += 1
Equal request counts do not imply equal CPU, memory, or queue depth on the backends.

03Weighted round robin

  • Assign each server a weight based on capacity: weight 4 receives four times the traffic of weight 1.
  • With weights A=4, B=1, C=1, four of every six requests go to A, and one each to B and C.
  • It handles heterogeneous instance sizes and mixed generations of hardware in one pool.
  • Weights also give deliberate control: canary releases, gradual regional ramp-up, and draining a server.
  • Smooth weighted round robin spreads each server's turns through the cycle instead of sending bursts of four to A.
  • Smooth implementations keep a running score per server, add the weight each pick, choose the highest, then subtract the total weight.
  • The limit is that weights are expected capacity, not current capacity: a server stalling on a garbage collection pause keeps its full share.
Start every server score at 0→Add each server's weight to its score→Pick the highest score→Subtract the total weight from the winner→Repeat for the next request

04Random

  • Pick a server at random for each request; no counter, no shared state, no coordination.
  • Over a small number of requests the distribution looks lumpy, but it evens out as volume grows.
  • It is attractive when many balancer instances must decide independently, because there is nothing to synchronise.
  • Like round robin it ignores load, so an overloaded server still receives new requests.
  • Randomness is also the ingredient that makes power of two choices work.
  • Weighted random exists and is useful when capacities differ but you do not want bursty cycles.
  • Variance is the cost: at low request rates, some servers get noticeably more than their share.

05Least connections

  • Track active connections per server and send each new request to the one with the fewest.
  • Slow requests hold connections open longer, so a busy server naturally stops attracting new traffic.
  • It suits workloads with very different durations: file uploads, long queries, WebSockets, and database connections.
  • A weighted variant scales the comparison by server capacity so larger servers take a bigger share.
  • The bookkeeping must be concurrency-safe, with increments on start and decrements on finish, timeout, or failure.
  • With HTTP/2 or gRPC one connection carries many concurrent requests, so connection count understates real load.
  • A brand-new server starts at zero connections and can be flooded unless slow start is enabled.
pick = min(servers, key=lambda s: s.active_connections)
pick.active_connections += 1
# decrement on completion, timeout, or failure

06Least response time

  • Connection count says how many requests are in flight, not how fast the server finishes them.
  • Two servers with ten connections each can differ tenfold in latency because of disk, GC, or a noisy neighbour.
  • The balancer measures response time per server and prefers the faster ones, often combining it with connection count.
  • Using only the last response is fragile: one slow query can make a healthy server look broken.
  • Production implementations use an exponentially weighted moving average so recent samples dominate without overreacting.
  • The average only shifts when a server is consistently slow, which is the desired damping.
  • Quiet servers need occasional probe traffic, otherwise their latency data goes stale and they are never chosen.
Response time is also a property of the request: a heavy query is slow on any server, so latency can penalise a healthy backend that happened to receive expensive work.

07Power of two choices

When many balancers share a pool, each has a partial and slightly stale view, so “pick the global minimum” causes herding.

  • Choose two servers at random, compare their load, and send the request to the lighter one.
  • Random sampling makes it unlikely that every balancer picks the same server at the same moment.
  • Comparing two is dramatically better than picking one at random, and comparing more adds little for the cost.
  • Cost per request is constant regardless of pool size, which matters at large scale.
  • It works with connections or in-flight requests, and with weights by comparing weighted scores.
  • Envoy uses power of two choices by default for its least-request policy; NGINX offers a similar random-two option.
  • It is the pragmatic default for large stateless fleets with many balancer instances.
a, b = random.sample(servers, 2)
pick = a if a.active_requests <= b.active_requests else b

08Hash-based routing

Sometimes the same client or key should keep reaching the same server, usually for local caches or in-memory sessions.

  • The balancer hashes a chosen value and maps the result onto the server pool.
  • Candidate keys include client IP, user ID, session ID, tenant ID, URL, or cache key.
  • Source IP hashing is the simplest form: hash the client IP and take it modulo the server count.
  • Problem one: many users share a public IP behind carrier or office NAT, so they all land on one server.
  • Problem two: changing the server count remaps most keys, because the modulus changes.
  • Hashing a session cookie, user ID, or tenant ID is usually more stable than hashing the IP.
  • Hash routing ignores load, so a hot key such as a popular product page can overload one server while others idle.

09Consistent hashing

  • Place servers and keys on a hash ring; a key belongs to the first server clockwise from its position.
  • Adding a server only takes over the arc between it and its predecessor, so few keys move.
  • Removing a server moves only its keys, and they go to the next server on the ring.
  • Going from four servers to five moves roughly one fifth of the keys instead of most of them.
  • Virtual nodes give each server several ring positions so ownership is spread evenly.
  • Rendezvous hashing achieves the same stability without a ring: score every server per key and pick the highest.
  • Maglev-style hashing is another variant used inside very large load balancers for stable, even distribution.
  • The remaining weakness is a hot key: stability is preserved, but that key's server can still saturate.

10Locality-aware routing

  • Servers are usually spread across availability zones and regions, and cross-zone calls add latency and transfer cost.
  • Prefer backends in the same zone as the balancer, then use round robin or least requests inside that zone.
  • Fall back to other zones when local servers are unhealthy or saturated, so capacity gaps do not become outages.
  • Envoy implements this as zone-aware routing with a configurable spillover threshold.
  • The failure mode is imbalance: if most traffic arrives in zone A but most capacity sits in zone B, strict locality overloads A.
  • Weight locality by both traffic share and capacity share, not by proximity alone.
  • Data residency rules can forbid cross-region fallback, so the fallback policy must respect legal boundaries.
Receive request in zone A→Try healthy backends in zone A→If A is saturated or unhealthy, spill to zone B→Recheck local capacity on the next request

11Adaptive and load-aware routing

  • Instead of inferring load, ask the server: it reports CPU, memory, queue depth, or request rate.
  • Metrics can come back in response headers or through a separate reporting channel.
  • The balancer continuously adjusts each server's share: a server at high CPU gets less, an idle one gets more.
  • gRPC's weighted round robin policy lets backends report utilization and lets the client compute weights.
  • It shines when identical hardware performs differently because of noisy neighbours or background jobs.
  • The danger is instability: fast-changing weights make balancers chase whichever server last reported low load.
  • Mitigate with smoothed measurements, rate-limited weight changes, hysteresis, and a safe fallback when a server stops reporting.

12Choosing an algorithm

  • Equal servers with short, uniform requests: round robin or power of two choices.
  • Different capacities or a canary rollout: weighted round robin, or weighted least requests.
  • Highly variable durations or long-lived connections: least connections, with slow start enabled.
  • HTTP/2 or gRPC multiplexing: least requests, because connections no longer represent work.
  • Many balancer instances: power of two choices to avoid herding.
  • Cache affinity or sticky sessions: consistent hash, rendezvous, or Maglev rather than modulo hashing.
  • Multi-zone deployments: locality-aware routing with spillover, and adaptive routing only if metrics are trustworthy.

↔Trade-offs to say out loud

  • Static algorithms are cheap and predictable but cannot react when a backend slows down.
  • Dynamic algorithms adapt to real load but depend on delayed or partial metrics.
  • Round robin is trivial to operate but assumes equal capacity and equal request cost.
  • Weighted round robin handles mixed hardware but its weights never react to live trouble.
  • Least connections handles variable durations but misreads multiplexed HTTP/2 and gRPC traffic.
  • Least response time follows real latency but can punish a server that merely received expensive requests.
  • Power of two choices avoids herding cheaply but can still pick a bad server if both samples are bad.
  • Consistent hashing preserves affinity during scaling but concentrates hot keys on single servers.
  • Locality-aware routing cuts latency and cross-zone cost but risks imbalance when traffic and capacity are in different zones.
  • Adaptive routing uses the truest signal but is the easiest to make oscillate.

?Interview questions

Answer aloud before opening the outline.

1. What is the difference between a static and a dynamic load balancing algorithm?

A static algorithm follows a fixed rule such as a rotation or fixed weights and ignores current load. A dynamic algorithm reads live signals such as active connections, in-flight requests, or response time, so it can steer away from a struggling server.

2. When is round robin a bad choice?

When request costs vary widely or servers have different capacities. Round robin equalises request counts, not work, so a server that receives several slow requests keeps getting new ones while its peers are idle.

3. What problem does weighted round robin solve, and what does it not solve?

It matches traffic share to capacity, so a larger instance receives proportionally more requests, and it enables canaries and gradual ramps. It does not react to live condition: a server paused on garbage collection keeps its full weight.

4. Why does least connections work well for long-lived connections?

Because slow or long requests keep their connections open, so the connection count tracks outstanding work. A server handling expensive requests accumulates connections and stops attracting new traffic without any explicit cost model.

5. Why is least connections misleading for gRPC and HTTP/2?

Both multiplex many concurrent requests over a single connection, so one connection can represent heavy load while another carries almost nothing. Counting in-flight requests instead of connections gives a truer picture.

6. What is slow start and why does least connections need it?

A new server has zero connections, so it looks like the least loaded backend and gets a burst of traffic before its caches, connection pools, and JIT are warm. Slow start ramps its share gradually over tens of seconds to avoid that cold-start overload.

7. Why does least response time need a moving average?

A single slow request, such as one expensive query, would otherwise mark a healthy server as slow. An exponentially weighted moving average damps outliers while still shifting traffic away from a server that is consistently slow.

8. What is herding and which algorithm prevents it?

Herding happens when many balancer instances independently pick the same least-loaded server, overload it, then all switch to another. Power of two choices prevents it by sampling two random servers, which makes simultaneous identical choices unlikely.

9. Why is modulo hashing dangerous when the pool changes?

Changing the number of servers changes the modulus, so most keys map to different servers. Local caches lose their data and session affinity breaks even though only one server was added.

10. How does consistent hashing reduce key movement?

Servers and keys share a ring, and each key belongs to the next server clockwise. Adding or removing a server only reassigns the arc it owns, so a small fraction of keys move instead of most of them. Virtual nodes keep that ownership evenly spread.

11. What is the risk of hash-based routing?

It ignores load, so a hot key such as a popular product page sends all of its traffic to one server and can saturate it while the rest of the pool idles. Affinity and balance are in direct tension.

12. How do you choose an algorithm in an interview?

Start from the workload: request duration variance, connection longevity, server homogeneity, protocol, and number of regions. Then name the signal available at your balancer layer and pick the simplest algorithm that uses it, with health checks and slow start as defaults.

!Traps

  • Assuming equal request counts mean equal load.
  • Using round robin with a long-tail endpoint that occasionally takes seconds.
  • Enabling least connections without slow start and melting every new instance.
  • Counting connections on a gRPC service where one connection carries thousands of requests.
  • Using modulo hashing for cache affinity and losing most of the cache on every scale event.
  • Hashing only the client IP when many users share a NAT address.
  • Building locality-aware routing that ignores how much traffic and capacity each zone actually has.
