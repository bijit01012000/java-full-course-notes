In one lineRaft keeps a replicated log identical across a group of servers by electing one leader per term, appending entries through it, and committing only what a majority has stored — consensus designed to be explainable.
Consensus
Agreement among a set of servers on a single sequence of values despite crashes and network partitions.
Replicated state machine
A deterministic service that reaches the same state on every replica by applying the same commands in the same order.
Term
A monotonically increasing logical epoch; each term has at most one leader and stale terms are rejected.
Leader election
The process where a candidate requests votes and becomes leader after winning a majority.
Election timeout
A randomised wait after which a follower that heard no leader starts an election.
Log matching property
If two logs contain an entry with the same index and term, then all preceding entries are identical.
Commit index
The highest log index known to be stored on a majority; entries up to it will never be lost.
Quorum
A majority of the cluster; any two quorums overlap, which is what makes agreement possible.
Joint consensus
A two-phase configuration change that requires majorities of both the old and new member sets.
Snapshot
A compact image of state at a log index, used to discard old entries and to bring new or lagging followers up to date.

01Why Raft exists

Replication without agreement gives you copies that disagree. Agreement without a replicated log gives you a value, not a history. Raft supplies both with a structure people can follow.

  • Raft is a consensus algorithm for a replicated log, not a general-purpose database.
  • It was designed for understandability: leader election, log replication, and safety are separated into distinct mechanisms.
  • It targets crash and partition faults, not Byzantine faults; it assumes nodes fail by stopping or going silent.
  • Paxos solves the same problem but is notoriously hard to implement and to reason about operationally.
  • The output is a single agreed order of commands, so every replica reaches the same state.
  • Correctness is guaranteed only while a majority of the cluster is reachable; a minority cannot make progress.

02The replicated log model

  • Each server stores an ordered log of commands; index 1, 2, 3 and so on.
  • Every replica applies committed commands in index order, so identical logs imply identical state.
  • The log is the source of truth; the state machine is just a fold over it.
  • Commands must be deterministic — anything random or time-dependent belongs in the command payload, not in the apply step.
  • A client submits a command to the leader, which assigns it the next index and replicates it.
  • Once a command is committed it is durable in the sense that some future leader will contain it.
  • This model underlies etcd, Consul's KV store, and the per-range replication in CockroachDB.

03Roles, terms, and authority

  • A server is a follower, a candidate, or the leader at any moment.
  • Time is divided into terms; each term begins with an election and has at most one leader.
  • Every message carries a term, and a server that sees a higher term immediately steps down to follower.
  • A server votes at most once per term, which is what prevents two leaders in the same term.
  • Only the leader accepts client writes; followers redirect clients or forward the request.
  • Terms act as a logical clock that orders leadership changes without needing synchronised wall clocks.
  • A leader that loses contact with a majority keeps believing it leads until it hears a higher term — hence the need for leases and fencing.

04Leader election

A follower that hears nothing from a leader for its election timeout becomes a candidate. Randomisation is what breaks ties.

  • The candidate increments the term, votes for itself, and sends RequestVote to all peers.
  • It wins with votes from a majority and immediately starts sending heartbeats to assert leadership.
  • Each election timeout is randomised so simultaneous candidates rarely split the vote the same way twice.
  • A split vote means no majority; everyone times out again and a different random delay resolves it.
  • A candidate must have a log at least as up to date as any voter's, so a server missing committed entries cannot win.
  • Pre-vote extensions ask peers whether they would vote before incrementing the term, preventing a partitioned node from disrupting a healthy leader.
  • Election timeouts must be long relative to network round trips, or elections trigger constantly under load.

05Log replication

  • The leader appends the client command at the next index and sends AppendEntries to followers.
  • Each request carries the previous entry's index and term, which acts as a consistency check.
  • A follower that lacks the preceding entry rejects the request; the leader decrements its next index and retries.
  • When the check passes the follower appends the entry, fsyncs it, and acknowledges.
  • Once a majority has stored an entry, the leader advances its commit index and applies it.
  • Followers learn the commit index from later AppendEntries messages, so followers commit slightly later than the leader.
  • Retries plus the consistency check repair divergent suffixes: the leader overwrites follower entries that never committed.

06The safety rules that make it correct

  • Election restriction: a candidate needs the most up-to-date log, so committed entries are never lost by electing a lagging node.
  • Log matching: same index and term implies identical prefixes, which lets the leader trust the consistency check.
  • Leader completeness: a leader holds every entry committed in previous terms.
  • Commit only current-term entries by counting replicas: older-term entries become committed indirectly once a current-term entry commits.
  • A leader never overwrites its own log; it only appends, and only followers truncate conflicting suffixes.
  • State transitions are applied to the state machine only after commit, never on append.
  • These rules are why Raft does not need the complicated recovery logic that makes Paxos implementations diverge.
The subtle rule is the current-term commit restriction. Counting replicas for an old-term entry can commit an entry that a future leader might still overwrite.

07Failures and partitions

  • A leader crash causes a timeout, an election, and a new leader that repairs any half-replicated suffix.
  • A leader isolated in a minority keeps accepting requests but cannot commit them; it must step down or clients must time out.
  • The majority side elects a new leader and continues; this is exactly the split-brain scenario quorums are designed to survive.
  • Uncommitted entries on the isolated leader are discarded when it rejoins, so clients must treat an unacknowledged write as unknown.
  • A cluster of 2f + 1 nodes tolerates f failures; even-sized clusters add cost without extra tolerance.
  • Losing a majority stops all writes and, depending on read policy, may stop reads too.
  • Slow disks and slow followers translate directly into commit latency, because the leader waits for a quorum of acknowledgements.

08Membership changes

  • You cannot simply edit a member list: different nodes would apply different quorum rules at the same time and could elect two leaders.
  • The standard solution is joint consensus: first commit a configuration requiring majorities of both old and new sets, then commit the new configuration alone.
  • Single-server changes are a simpler special case and are safe when only one change is in flight at a time.
  • The leader should step down once the new configuration no longer includes it, after committing the change.
  • New members usually join as non-voting learners and catch up before they count toward quorum.
  • Raft does not shard by itself: large datasets use many independent Raft groups, one per shard or range.
  • Membership changes are rare, slow, and risky — treat them as an operational procedure, not a routine write.

09Snapshots and log compaction

  • An unbounded log eventually exceeds disk and slows restart, so committed prefixes are discarded.
  • A snapshot captures the state machine at a specific index, and the log before that index can be removed.
  • A follower that has fallen behind the leader's retained log receives an InstallSnapshot instead of entries.
  • Snapshotting can be expensive; copy-on-write or incremental snapshots avoid stalling writes.
  • Snapshot transfer competes with replication traffic, so throttle it to protect leader latency.
  • Snapshot metadata must record the last included index and term so the log can continue consistently.
  • Keep enough log after the snapshot to serve normal follower catch-up without shipping a full image.

10Clients and read consistency

  • Writes go to the leader; a follower returns a redirect or forwards the request internally.
  • A write is only acknowledged as successful after commit, not after the local append.
  • Clients must retry with a request identifier so the state machine can deduplicate and avoid applying a command twice.
  • Reading from the leader's state machine directly can return stale data if the leader has been deposed but does not know it.
  • ReadIndex confirms leadership with a heartbeat quorum, waits for the applied index to catch up, then serves locally.
  • Leader leases skip the round trip but depend on bounded clock drift between nodes.
  • Routing reads through the log is the simplest correct option and the slowest; choose per endpoint based on staleness tolerance.

11Performance and tuning

  • Throughput is bounded by the leader and by the slowest quorum member, not by the fastest follower.
  • Batch and pipeline AppendEntries requests so one fsync covers many entries.
  • Group commit on followers matters as much as on the leader; disk fsync dominates commit latency.
  • Use fast local disks for the log; network storage adds jitter that shows up as election instability.
  • Spread the cluster across failure domains while keeping quorum latency low — geo-distributed majorities pay round-trip cost on every commit.
  • Keep the state machine apply path off the replication critical path so slow applies do not block acknowledgements.
  • Monitor leader changes, commit latency, follower match index lag, and snapshot duration as first-class metrics.

12Raft versus Paxos and other options

  • Multi-Paxos and Raft provide the same guarantee; Raft constrains the design (strong leader, ordered log) to make implementation tractable.
  • Zab, used by ZooKeeper, shares the leader-plus-log structure with different recovery details.
  • Raft is a good fit for metadata, configuration, leader election, and small strongly consistent datasets.
  • It is a poor fit for high-volume data that needs sharding; use many Raft groups or a system built on them.
  • CRDTs avoid consensus by accepting concurrent merges, but they cannot enforce global invariants such as uniqueness.
  • Gossip spreads membership and health cheaply but cannot order writes or commit transactions.
  • Choose Raft when you need a single agreed order and can afford a majority round trip per write.

13Operational pitfalls

  • Deploying an even number of voters: more machines, no additional failure tolerance.
  • Running Raft across regions and then blaming the algorithm for commit latency.
  • Using wall-clock time as the ordering mechanism instead of terms and log indexes.
  • Forgetting client-side deduplication, so retries apply a command twice.
  • Changing membership by editing configuration files on live nodes instead of using the protocol.
  • Ignoring snapshot behaviour until the log fills the disk and the node cannot restart.
  • Treating a leader as authoritative without leases or fencing, which reintroduces split-brain at the storage layer.

↔Trade-offs to say out loud

  • Strong consistency makes every write a majority round trip, so availability and latency depend on quorum health.
  • A single leader simplifies ordering but caps write throughput at one node and one disk.
  • Understandability comes from constraining the design, which makes Raft less flexible than general Paxos variants.
  • More voters increase durability but widen the quorum and slow every commit.
  • Randomised election timeouts resolve ties quickly but can produce needless elections under heavy load or slow networks.
  • Snapshots bound log growth but add CPU, I/O, and a large transfer that competes with replication.
  • Leader leases make reads fast but rely on bounded clock drift and correct lease handling.
  • Joint consensus makes membership safe but requires two commits and careful orchestration.

?Interview questions

Answer aloud before opening the outline.

1. What problem does Raft solve?

It keeps a replicated log identical across servers so every replica applies the same commands in the same order. That gives a linearizable, fault-tolerant state machine as long as a majority of the cluster is available.

2. Why is Raft easier to understand than Paxos?

Raft separates leader election, log replication, and safety into distinct mechanisms with a strong leader and an ordered log. Paxos describes agreement on single values and leaves much of the multi-value, recovery, and membership design to the implementer.

3. Walk through leader election.

A follower that hears no leader past a randomised election timeout increments the term, votes for itself, and requests votes. A majority elects it, and it starts sending heartbeats. Split votes are resolved by new random timeouts on the next attempt.

4. How does Raft repair a divergent log?

The leader sends the previous entry's index and term with each append. A follower missing that prefix rejects the request, the leader backs up its next index, and retries until it finds the match point. The follower then truncates its conflicting suffix and accepts the leader's entries.

5. When is an entry committed?

When it is stored on a majority and belongs to the leader's current term. Entries from earlier terms become committed indirectly once a current-term entry commits, because the leader only advances its commit index to that point.

6. Why can only a current-term entry be committed by counting replicas?

An old-term entry replicated on a majority may still be overwritten by a future leader that lacks it. Committing a current-term entry forces the whole prefix to be committed, so the older entries become safe through that single event.

7. What happens during a network partition?

The majority side elects a new leader and continues. A leader stranded in the minority cannot commit anything and should step down. When the partition heals, the stale leader discards uncommitted entries and follows the new leader.

8. How many failures can a five-node cluster tolerate?

Two. Quorum is three, so the cluster keeps operating while three of five nodes are reachable. A four-node cluster tolerates only one, which is why even-sized voter sets are wasteful.

9. How do you serve a consistent read without writing to the log?

Use ReadIndex: confirm leadership by getting heartbeat acknowledgements from a quorum, wait until the state machine has applied up to the commit index, then answer locally. Leader leases achieve the same with less latency but rely on bounded clock drift.

10. How are cluster membership changes made safely?

Use joint consensus: commit a configuration that requires majorities of both old and new sets, then commit the new configuration alone. Adding one voter at a time, and letting new members catch up as non-voting learners, avoids overlapping quorum changes.

11. Why are snapshots necessary?

Committed log entries accumulate indefinitely, and replaying a long log makes restarts slow. A snapshot captures state at an index so earlier entries can be discarded, and it lets a lagging follower catch up without shipping the entire history.

12. When would you not use Raft?

When you need to store high write volumes across many machines, when concurrent merges are acceptable, or when a global order is unnecessary. In those cases use sharded Raft groups, CRDTs, or gossip rather than one cluster-wide consensus group.

!Traps

  • Thinking Raft tolerates Byzantine faults or malicious nodes.
  • Assuming a leader is always right about its own leadership.
  • Committing entries from previous terms by counting replicas instead of waiting for a current-term commit.
  • Expecting writes to survive when a majority of the cluster is unreachable.
  • Adding voters by editing configuration instead of using joint consensus or single-server changes.
  • Ignoring snapshot size until the log fills the disk.
  • Leaving client retries undeduplicated, so a command is applied twice.
