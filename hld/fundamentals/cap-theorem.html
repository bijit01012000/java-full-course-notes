01The problem

An online store keeps product data in Region A and Region B. Both show a price of 50 dollars. An administrator changes it to 60 in Region A, and the update is confirmed.

  • Before the change reaches Region B, the network link between the regions fails.
  • Both regions are still running, and customers can reach both of them.
  • A customer asks Region B for the price, but Region B still has the old value and cannot contact Region A.
  • The update was confirmed, yet a healthy node would return stale data if it answered locally.
  • Region B has no way to discover an update it never received while communication stays broken.
  • No protocol can make the missing information appear; the system must choose how to behave.
  • This is the situation CAP describes: a partition exposes a conflict between freshness and successful responses.

02The two choices

Region B has exactly two options when a customer asks for the price.

  • Answer locally: return 50 dollars. The request succeeds, but the customer sees an older price after the update was confirmed.
  • Refuse or wait: do not answer until the current value can be established. The answer is not stale, but the customer gets an error or a delay.
  • The first choice keeps the request available and gives up consistency.
  • The second keeps consistency and gives up availability for that request.
  • The trade-off appears only because the replicas are separated; while the link is healthy, both properties can usually hold.
  • The choice can differ by operation: a product description can tolerate staleness, while the last unit in stock cannot.
  • An error from a healthy node that cannot coordinate does not count as available under CAP.

03Consistency

In CAP, consistency means the system behaves as if there were only one up-to-date copy of the data. It is about replicated reads, not about database constraints.

  • Once a write is confirmed, any read that starts afterward must return that value or a newer one.
  • A read must not return the old value after the new value was acknowledged.
  • One way to achieve this is to copy the write to other replicas before acknowledging the client.
  • It does not require every replica to update at the same instant; a lagging replica can coordinate or refuse to serve until it can be consistent.
  • A read from Region A after the update returns 60 and is consistent.
  • A read from Region B is consistent only once it has caught up; answering 50 before that breaks consistency.
  • Refusing to answer because freshness cannot be confirmed preserves consistency, even though the customer gets no value.

CAP consistency vs ACID consistency

  • ACID consistency is about preserving database rules and constraints inside one database.
  • CAP consistency is about replicated data across nodes behaving like a single current copy.
  • A transaction that leaves a negative price violates ACID consistency; a replica returning a value older than a confirmed write violates CAP consistency.
  • The two ideas share a word but answer different questions, so do not use them interchangeably in an interview.

04Availability

CAP availability is narrower than the everyday word. It means every request sent to a healthy node eventually gets a valid response, even if replicas cannot coordinate.

  • Returning an older local price keeps the system available but gives up strong consistency.
  • Returning service unavailable does not satisfy CAP availability for that request.
  • The response does not have to be fast; it only has to arrive eventually.
  • A stale value from a healthy node counts as available.
  • A value that arrives after a long delay also counts.
  • An error from a healthy node that could not coordinate does not count.
  • A monthly uptime figure such as 99.99% is a different measurement: CAP availability is about individual requests during a partition, not time spent online.

05Partition tolerance

A partition happens when groups of nodes can no longer communicate, even though the nodes themselves are still running.

  • Causes include a broken network link, a routing problem, a firewall misconfiguration, or an overloaded network device.
  • A broken link between data centers leaves both regions running while replication traffic stops.
  • A routing issue can send packets down a path that never arrives.
  • A firewall change can block the port replication depends on.
  • An overloaded device can drop or delay messages until timeouts fire.
  • In every case the nodes are fine; the problem is the path between them.
  • Partition tolerance means the system has defined behavior during these failures, not that every request will still succeed.

06Why “pick two” is too simple

CAP is often summarized as pick any two of three. That framing hides the part that matters.

  • A distributed system cannot prevent network partitions, so partition tolerance is not a feature you can decline.
  • While the network is healthy, a system can often provide both consistency and availability.
  • The real trade-off appears when communication breaks, and only for operations that depend on the separated replicas.
  • The choice does not have to be uniform: reading a description can use local data, while reserving the last item must stop.
  • Calling a whole database CP or AP is therefore imprecise; the label is most useful per operation.
  • CAP describes a moment of failure, not the steady-state behavior of the system.
  • The practical question is: during a partition, what should this specific operation do?

07CP: preserving consistency

A CP system preserves consistency during a partition, even at the cost of rejecting or delaying affected requests.

  • Suppose only one unit of a product is left; a reservation must check inventory and reduce it as one coordinated operation.
  • If two separated regions each see one unit and both confirm a sale, the same item is sold twice.
  • A CP design routes reservations through a leader or a group of replicas that agrees on the update.
  • If a region cannot reach that authority, it waits or rejects the reservation instead of guessing.
  • Reads follow the same rule: a replica that cannot prove freshness refuses rather than returning a stale answer.
  • Some customers may be unable to check out during the partition, but the system avoids double-selling.
  • This is the right default for inventory, payments, locks, and anything where stale data causes real harm.
Customer reserves the last unit→Request routes to the inventory leader→Leader coordinates the update with a quorum→Reservation is confirmed once the update is agreed→A region that cannot reach the leader rejects or waits
CP is about refusing to guess, not about making the partition disappear.

08AP: preserving availability

An AP system keeps accepting requests on reachable replicas and reconciles divergent copies after communication returns.

  • A customer adds a book from a phone through Region A and a notebook from a laptop through Region B.
  • The regions are disconnected, but both additions can still succeed if each replica accepts local writes.
  • During the partition, the phone may show only the book and the laptop only the notebook.
  • When the link returns, the system merges the additions so both views contain both items.
  • Combining two cart additions is usually a reasonable merge rule.
  • The same strategy would be unsafe for the last unit in stock, because two reservations cannot both succeed.
  • Other conflicts, such as two edits to the same description, need a defined winner or version rule.
  • The system trades a period of drift for uninterrupted service, and the application owns the reconciliation logic.
Phone adds a book in Region A→Laptop adds a notebook in Region B→Each replica accepts its local write→Views diverge while the partition lasts→Link returns and the cart is merged

09CA: consistency and availability

CA means consistency and availability without partition tolerance. It is meaningful only while no partition exists.

  • A single-node database can provide both while it is healthy, because there are no replicas to coordinate across a network.
  • A distributed system can also provide both while communication is working normally.
  • Once replicas can be separated, the system still has to decide what to do during the partition.
  • For replicated data, the same choice returns: preserve consistency or keep affected operations available.
  • That is why CA is not a useful label for a distributed system that can be split.
  • A design that never states its partition behavior has not escaped the trade-off; it has left the answer undefined.
  • In an interview, say CA only while there is no partition rather than presenting it as a third viable option.

10PACELC: the trade-off when the network is healthy

Even with a healthy network, coordination takes time. PACELC extends CAP to cover that normal case.

  • If there is a Partition, choose Availability or Consistency — the original CAP trade-off.
  • Else, when the network is healthy, choose Latency or Consistency.
  • Reading from a nearby replica is faster than contacting a leader in another region, but the replica may be slightly behind.
  • Waiting for multiple replicas to agree on a write improves consistency but adds latency.
  • Stronger consistency generally requires more coordination, which makes requests slower.
  • The trade-off applies most of the time, because partitions are rare compared with normal operation.
  • The right choice still depends on what each operation needs: a feed read can accept a nearby stale replica, while a balance check may wait for the leader.

11Summary and how to apply it

  • CAP describes what happens to replicated data during a network partition, not the general quality of a database.
  • When replicas cannot communicate, the system cannot guarantee both a consistent view and a successful response for every affected request.
  • Partition tolerance is unavoidable; the meaningful labels are CP and AP for the affected operation.
  • CP rejects or waits rather than returning stale data; AP serves local data and reconciles later.
  • CA is only meaningful when partitions are not part of the picture.
  • PACELC adds the everyday trade-off between latency and consistency when the network is healthy.
  • Choose per operation: catalog browsing and cart updates can continue with local data, while reserving the last unit must stop.
  • In an interview, name the user impact of each choice — a stale price, a failed checkout, or a duplicated sale — rather than only naming the label.

↔Trade-offs to say out loud

  • CP prevents stale reads and duplicate side effects but makes affected operations unavailable or slow during a partition.
  • AP keeps serving requests but returns possibly stale data and pushes conflict resolution onto the application.
  • Synchronous replication strengthens consistency but adds write latency and reduces availability when a replica is unreachable.
  • Reading from a nearby replica reduces latency but may return data that is slightly behind the leader.
  • Waiting for a quorum improves consistency but increases latency and can fail when too few replicas are reachable.
  • Per-operation CAP choices match behavior to business risk but make the system harder to reason about and test.
  • CA designs are simple while the network is healthy but leave partition behavior undefined once replicas separate.
  • Eventual consistency improves availability and latency but requires merge rules, versioning, and tolerance for temporary divergence.

?Interview questions

Answer aloud before opening the outline.

1. What does the CAP theorem state?

When a network partition separates replicas, a distributed system cannot guarantee both strong consistency and availability for the affected requests. It must choose whether to return possibly stale data or refuse/wait. Partition tolerance is not optional, so the practical choice is CP or AP.

2. Why is partition tolerance not optional?

Networks fail: links break, routes go wrong, firewalls change, and devices drop messages. A distributed system cannot prevent partitions, so it must define behavior for them. Saying a system chooses CA only means it has not specified what happens when the network splits.

3. How is CAP consistency different from ACID consistency?

ACID consistency preserves rules and constraints inside one database, such as a price never being negative. CAP consistency is about replicated data behaving like a single current copy, so a read after a confirmed write does not return an older value. They share a word but describe different guarantees.

4. What does availability mean in CAP?

Every request sent to a healthy node eventually gets a valid response, even if replicas cannot coordinate. A stale response counts, and a slow response counts, but an error from a healthy node does not. This is request-level availability during a partition, not a monthly uptime percentage.

5. What causes a network partition?

A broken link between data centers, a routing problem, a firewall blocking a replication port, or an overloaded network device dropping messages. The nodes remain healthy; only the path between them fails. That is why the failure is invisible to a simple process health check.

6. Why is “pick two” a misleading summary?

It treats partition tolerance as optional, when partitions are unavoidable. It also implies one choice for the whole system, when the trade-off appears only during a partition and can differ per operation. A catalog read can be AP while an inventory reservation is CP.

7. Give an example of a CP decision.

Reserving the last unit of stock. Two separated regions must not both confirm the sale, so the reservation goes through a leader or quorum. If a region cannot reach that authority, it rejects or waits. The cost is that some customers cannot check out during the partition.

8. Give an example of an AP decision.

Adding items to a shopping cart. A phone in one region and a laptop in another can both accept additions while disconnected, then merge them when the link returns. The cart may be temporarily incomplete, but no addition is lost. The same approach would be unsafe for inventory.

9. Why is CA not useful for a distributed system?

CA holds only while there is no partition. A single-node database can provide it, and a distributed system can provide it while the network is healthy, but once replicas separate the system must still choose. CA is a statement about the absence of partitions, not a third behavior during one.

10. What does PACELC add to CAP?

PACELC covers normal operation: if there is a partition, choose availability or consistency; else, choose latency or consistency. Reading a nearby replica is fast but may be stale, while waiting for a leader is consistent but slower. Most of the time there is no partition, so this trade-off matters more often than CAP alone suggests.

11. Can one system be CP for some operations and AP for others?

Yes, and that is usually the right design. The label applies to the operation's behavior during a partition, not to the entire database. A product description read can serve local data, while a payment or inventory reservation refuses until it can coordinate.

12. How do you choose between CP and AP?

Ask what a wrong answer costs. If stale data causes a duplicated sale, lost money, a security breach, or an irreversible action, choose CP for that operation. If availability matters more and conflicts can be merged sensibly, choose AP. Then state the user impact of each choice.

13. How do AP systems handle conflicts when the partition heals?

They reconcile divergent copies using a merge rule: union for cart additions, last-writer-wins with a timestamp or version, or application-specific resolution. The rule is part of the design, because some conflicts cannot be merged safely. Eventual consistency means convergence, not the absence of conflicts.

14. What is a common CAP mistake in interviews?

Listing databases as dogmatically CP or AP and stopping there. A database's behavior depends on its configuration, replication mode, and the operation being performed. The stronger answer names the operation, describes the partition behavior, and explains the user-visible consequence.

!Traps

  • Saying CAP means choosing any two of three, as if partition tolerance were optional.
  • Presenting CA as a viable design for a system whose replicas can be separated by a network failure.
  • Applying a single CP or AP label to an entire database instead of to specific operations.
  • Confusing CAP availability with monthly uptime or confusing CAP consistency with ACID constraints.
  • Assuming AP means the system is never consistent, rather than eventually consistent after reconciliation.
  • Ignoring the latency-versus-consistency trade-off that exists even when the network is healthy.
  • Choosing CP for every operation and making the system unnecessarily unavailable during partitions.
  • Forgetting that an AP design still needs a defined, tested merge rule for conflicting writes.
