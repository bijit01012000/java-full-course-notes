In one lineThe hard part of a schema migration is not changing the schema — it is changing it while old and new application versions both run against the same database.
Schema migration
A versioned, ordered change to database structure or data applied as part of a release process.
Expand and contract
A migration pattern that adds the new structure, keeps both versions working, then removes the old structure in a later release.
Backward-compatible change
A change the old application version can still operate against, such as adding a nullable column.
Backfill
Populating a new column or table from existing data, usually in throttled batches.
Dual write
Writing to both old and new structures for a transition period so either version can read valid data.
Dual read
Reading from the old structure and falling back to the new one (or the reverse) while both are populated.
Online DDL
A schema change performed without blocking writes for the duration of the operation.
Irreversible migration
A change whose data cannot be reconstructed, making rollback of the application version unsafe.

01The problem: a simple rename breaks a fleet

Renaming name to full_name is trivial in development: change the column, change the code, restart.

  • In production the application runs on many servers that share one database and are upgraded gradually.
  • Rename the column first and old servers fail, because the column they query no longer exists.
  • Deploy the new code first and new servers fail, because the column they expect does not exist yet.
  • The rollout guarantees a window where both versions run, so neither ordering works.
  • The real problem is mixed-version compatibility, not the DDL statement itself.
  • Every migration must therefore be safe for the version mix that exists while it is being applied.

02Expand and contract

  • Phase 1 — expand: add the new column or table without touching the old one.
  • Phase 2 — dual write: new code writes both the old and new structures.
  • Phase 3 — backfill: copy existing rows into the new structure in small, throttled batches.
  • Phase 4 — switch reads: new code reads the new structure, with a fallback while data catches up.
  • Phase 5 — deploy everywhere: after all instances run the new code, the old structure is unused.
  • Phase 6 — contract: drop the old column or table in a later, separate release.
Add new structure→Write both→Backfill in batches→Read new→Confirm old code is gone→Drop old structure
Each phase is its own deployable change, and each is safe for every version that can be running at that moment.

03Why each phase must be independently safe

  • A migration runs while the deployment is in progress, so the version mix is not under your control.
  • If a phase only works when all instances are new, it must wait for a later release.
  • If a phase only works when all instances are old, it must happen before the code that breaks it.
  • The contract phase is the dangerous one: it breaks old code, so it must be strictly after the last old instance is gone.
  • Intermediate releases may need to tolerate both shapes for longer than expected, especially with slow rollouts or long-lived workers.
  • Document which release removes each transitional tolerance, or the cleanup never happens.

04Classifying operations by safety

  • Adding a nullable column, a new table, or a new index is generally safe for old code.
  • Dropping a column or table breaks any code still referencing it.
  • Renaming is a drop plus an add from the old code's perspective, so it is never safe in one step.
  • Adding a NOT NULL constraint without a default fails on existing rows and can rewrite the table.
  • Changing a column type can break old readers and may require a full table rewrite.
  • Adding a foreign key or unique constraint validates existing data and can fail or lock while doing so.

05Backfilling data safely

  • Backfill in bounded batches with a sleep or rate limit between them to avoid saturating the database.
  • Make each batch idempotent so a retry after failure does not double-apply changes.
  • Track progress with a watermark or a processed flag so the job can resume rather than restart.
  • Backfill in the background, not inside the migration transaction, or the migration holds locks for its entire duration.
  • Watch replication lag: heavy backfills slow replicas and make read paths stale.
  • Verify completeness with a count comparison before switching reads to the new structure.

06Dual write and the switch of reads

  • Dual write keeps both structures current while old and new code coexist.
  • Write order matters: write the old structure first if the new one can be rebuilt, or the new one first if it is authoritative.
  • Wrap dual writes in the same transaction where possible, so the two structures cannot diverge.
  • Dual read with a fallback covers rows the backfill has not reached yet.
  • Log mismatches between the two reads so divergence is measured rather than assumed away.
  • Remove dual writes only after reads are fully on the new structure and the backfill is verified.

07Locking and online DDL

  • Many schema changes take an exclusive lock, which blocks writes and can queue reads behind it.
  • A blocked queue grows quickly under load, so a short lock can still cause a long outage.
  • Prefer online or concurrent DDL modes where the engine supports them.
  • Adding an index on a large table may need an online build or a shadow-table approach.
  • Some engines rewrite the entire table for a type or default change, which is effectively an outage on large tables.
  • Set a lock timeout so a migration fails fast instead of stalling traffic.

08Rollback and irreversibility

  • Application rollback and schema rollback are different operations; the schema often cannot go back.
  • Dropping a column destroys data, so rollback requires a backup or a deliberate retention window.
  • Design every migration so the previous application version still works after it is applied.
  • Keep the expanded form longer than the observation window; the cost of an extra column is small compared with an unrecoverable release.
  • Take a backup or snapshot before destructive phases, and know the restore time before you need it.
  • Record which migrations are reversible and which are one-way, and treat the one-way ones as high-risk changes.

09Migration tooling and discipline

  • Version migrations in source control and apply them in a fixed order, tracked in a migrations table.
  • Run migrations as a separate step from the application deployment, with its own logs and failure handling.
  • Never edit an applied migration; add a new one, or environments drift.
  • Test migrations against a production-like dataset, not an empty schema, because data volume drives lock duration.
  • Guard against concurrent runners with a lock so two instances cannot apply the same migration twice.
  • Require review for destructive statements as strictly as for code.

10Failure modes

  • Half-applied migration: a multi-statement migration fails midway, leaving a schema no version expects.
  • Lock storm: a DDL statement waits on a long transaction, and every subsequent query queues behind it.
  • Silent divergence: dual writes partially fail, and the new structure is missing rows with no error visible.
  • Premature contract: the old column is dropped while a slow-rolling worker still reads it.
  • Backfill saturation: an unthrottled copy consumes I/O and degrades the whole service.
  • Non-idempotent retry: a retried batch doubles a counter or appends duplicate rows.

11A safe-migration checklist

  • Ask which application versions will exist while this migration runs, and check the change against each of them.
  • Prefer additive changes; split rename and drop into separate releases.
  • Keep the migration fast; move data changes into a separate throttled job.
  • Ensure the old code path keeps working after the migration, so application rollback remains possible.
  • Verify with real traffic and per-version error rates before starting the contract phase.
  • Delete the transitional code and the old structure in a tracked follow-up, or the schema keeps permanent residue.

12Working with rolling, blue-green, and canary

  • Rolling deploys mix versions per instance, so migrations must be compatible with both for the rollout duration.
  • Blue-green keeps a full old environment alive, so the contract phase must wait until blue is retired.
  • Canary keeps a large baseline population on old code for the entire ramp, which extends the compatibility window.
  • Feature flags can gate reads of a new structure, letting you switch behavior without another schema change.
  • In all three, the migration and the deployment are separate timelines that must be reasoned about together.
  • The safest rule: never let a single release both add and remove the same structure.

↔Trade-offs to say out loud

  • Expand and contract keeps every version working but multiplies the number of releases and leaves temporary duplicate storage.
  • Dual writes keep two structures consistent but add write latency, complexity, and a new partial-failure mode.
  • Online DDL avoids blocking writes but consumes extra I/O and can still be slow or fail under load.
  • Fast contract reclaims storage and simplifies the schema but removes the ability to roll back the application safely.
  • Aggressive backfill finishes quickly but degrades the database for live traffic and replication.
  • Keeping the old structure indefinitely preserves rollback options but accumulates dead columns and confusing code.
  • Single-transaction migrations are atomic and simple but hold locks for their full duration on large tables.
  • Longer compatibility windows reduce risk but prolong the period when two code paths and two data shapes must be maintained.

?Interview questions

Answer aloud before opening the outline.

1. Why is renaming a column hard in production?

Because the fleet upgrades gradually, so old and new code run at the same time against one database. Renaming first breaks the old code, and deploying first breaks the new code. The rename has to be decomposed into add, dual write, backfill, switch reads, and drop.

2. What is expand and contract?

A migration pattern in phases: add the new structure, keep both versions working, backfill, switch reads and writes, then remove the old structure in a later release. Each phase is independently safe for the version mix that exists at that moment. It trades extra releases for zero-downtime compatibility.

3. Which schema changes are safe during a rolling deploy?

Purely additive ones: adding a nullable column, adding a table, or adding an index built online. Dropping, renaming, narrowing types, and adding constraints that validate existing rows are unsafe because old or new code can break. Safety is always relative to the versions that will be running.

4. How should a backfill be run?

As a separate, throttled, resumable job in bounded batches, outside the migration transaction. Each batch should be idempotent so retries are safe, and progress should be tracked with a watermark. Watching replication lag and query latency is part of running it, not an afterthought.

5. Why is dual write risky?

Because two writes can partially fail, leaving the structures inconsistent without an obvious error. It also adds latency and requires a deliberate write order. Mitigations include a shared transaction, mismatch logging, and a reconciliation job, but the complexity is real and should be temporary.

6. Can you always roll back a migration?

No. Dropping a column or narrowing a type destroys or truncates data, and no down-migration restores what was lost. Some changes are inherently one-way, so they need a backup, a retention window, or a staged approach that keeps the old data available until the release is proven.

7. What causes a lock storm during DDL?

A schema change requests an exclusive lock while long-running transactions hold shared locks. The DDL waits, and every subsequent query queues behind it, so a short lock becomes a full outage. Setting a lock timeout and choosing online DDL modes prevents the pile-up.

8. How does blue-green change migration planning?

It keeps a complete old environment alive as a rollback target, so the old code must remain functional until blue is retired. That means the contract phase cannot ship with the expand phase. It effectively lengthens the compatibility window compared with a quick rolling deploy.

9. How does a canary change migration planning?

The baseline keeps serving a large population on old code for the entire ramp, so both code paths and both data shapes must be supported for longer. Migrations that assume everyone moved to the new code will break the baseline. The canary also makes per-version error rates available, which helps validate the switch.

10. Should migrations run inside the application deployment?

Usually as a separate step with its own failure handling, ordered before the code that depends on it. Running them inside application startup causes races when many instances boot at once. A dedicated migration job with a lock gives deterministic ordering and clearer logs.

11. How do you verify a migration is complete?

Compare row counts and key aggregates between old and new structures, check for nulls in required fields, and confirm no mismatches in dual-read logs. Then verify with real traffic and per-version error rates. Only after that should the contract phase be scheduled.

12. What is the single most important migration rule?

Never let one release both add and remove the same structure. Addition must be proven in production with all versions running before removal is even scheduled. Almost every zero-downtime migration failure comes from collapsing those two steps.

!Traps

  • Renaming a column in one step and assuming the deployment is atomic.
  • Dropping the old column in the same release that introduces the new one.
  • Running an unthrottled backfill that saturates I/O and replication.
  • Adding a NOT NULL column with a default and triggering a full table rewrite on a large table.
  • Assuming dual writes cannot diverge because they are in the same code path.
  • Editing an already-applied migration instead of adding a new one.
  • Treating an application rollback as if it also restores the previous schema.
