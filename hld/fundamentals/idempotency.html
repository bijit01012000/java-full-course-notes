In one lineAn operation is idempotent when repeating it has the same intended effect as doing it once, which is what makes safe retries possible when the client cannot tell whether the first attempt worked.
Idempotency
The property that performing an operation multiple times has the same effect on the system as performing it once.
Retry
Re-sending a request after an unknown or failed outcome, which is safe only when the operation is idempotent.
Idempotency key
A unique identifier the client generates for one logical operation and reuses on every retry of that operation.
Request hash
A fingerprint of the original request stored with the key so a different payload under the same key can be rejected.
In-progress state
A record marking that a key is reserved and the operation is running, but no final response exists yet.
Atomic reservation
Inserting the key and checking its absence in one indivisible step, usually through a unique constraint.
Retention period
How long idempotency records are kept before the key can be treated as new again.
Duplicate suppression
Returning the stored result of the first attempt instead of executing the operation a second time.
Exactly-once effect
The practical goal: at-least-once delivery plus idempotent handling yields one real side effect.

01The problem: retrying after a failure

A user pays ₹1,000. The payment service charges the card successfully, but the response is lost before the client sees it.

  • The client cannot distinguish three cases: the payment succeeded, it failed, or the request never arrived.
  • Retrying is the standard reaction, and it is correct when the first attempt failed.
  • Retrying is destructive when the first attempt succeeded, because the user is charged twice.
  • The same problem appears for order creation, refunds, emails, and any write with an external side effect.
  • Timeouts are inherently ambiguous: a timeout is not a failure, it is an absence of information.
  • At-least-once delivery is the realistic guarantee in distributed systems, so duplicates must be handled somewhere.
  • Idempotency moves that handling to the server, where the operation's meaning is known.

02What idempotency means

  • An operation is idempotent if performing it multiple times has the same intended effect as performing it once.
  • The key word is effect, not response: the system state must end up the same, even if status codes differ.
  • set status = active is idempotent: after one or five executions the status is still active.
  • add $10 to balance is not: each execution adds another $10.
  • Idempotency is about the final state, so it tolerates intermediate repeated work if that work is overwritten.
  • It is a property of the operation's semantics, not of HTTP or of a database feature.
  • Reads are naturally idempotent because they do not change state, which is why retrying a GET is uncontroversial.
A safe method does not change state at all; an idempotent method may change state but converges to the same result.

03Naturally idempotent operations

  • Setting a field to an absolute value: UPDATE users SET email = ? WHERE id = ?.
  • Transitioning status to a fixed value, such as moving an order to SHIPPED.
  • Deleting a specific resource by ID: after the first delete, the resource is gone and stays gone.
  • Replacing an entire object with a supplied representation, which is what PUT is defined to do.
  • These operations are idempotent because they express an end state rather than a delta.
  • Design rule: prefer absolute state over increments when the client may retry.
  • Natural idempotency still needs care when side effects fire, such as sending an email after an update.

04Operations that are not idempotent

  • Creating a resource: POST /orders twice may create order 1001 and then order 1002.
  • Increments and decrements: balance changes, counters, and inventory reservations.
  • Appending: adding a message to a list or an event to a stream grows the data with every attempt.
  • Triggering external effects: charging a card, sending an email, calling a third-party API.
  • HTTP methods reflect this: POST is not idempotent by default, while PUT and DELETE are designed to be.
  • The response may look identical while the side effect duplicated, which is what makes this dangerous.
  • These are exactly the operations that need an explicit mechanism, because semantics cannot save them.

05Idempotency keys

The standard fix is a key generated by the client for one logical operation and reused on every retry of it.

  • The client generates a unique value before the first attempt, such as payment:7842 or a UUID.
  • It sends the key with the request, usually in a header such as Idempotency-Key.
  • The server stores the key together with the status and result of processing.
  • On a repeat, the server finds the key and returns the stored result instead of executing again.
  • Crucially, the client must reuse the same key on retries; a new key per attempt defeats the mechanism entirely.
  • The key should identify the operation, so it is generated once per user action, not once per HTTP call.
  • Keys must be scoped to the caller, so two different clients cannot collide on the same string.
POST /payments
Idempotency-Key: 9f1c2b7e-4a6d-4d1e-9c3a-2f0b7d5e8a11
Content-Type: application/json

{"amount": 1000, "currency": "INR", "card": "tok_visa"}

06How the server handles a key

  • Receive the request and read the idempotency key, rejecting requests that omit a required one.
  • Look up the key for this caller before doing any work.
  • If absent, reserve the key as IN_PROGRESS and start the operation.
  • Perform the business action, then store the outcome and mark the record COMPLETED.
  • Return the response to the client.
  • On a repeat, return the stored result rather than executing again.
  • If the reservation exists but is still in progress, apply the in-progress policy instead of starting a second execution.
  • A stored record typically holds the key, owner, request hash, status, created resource, and response.
Read Idempotency-Key→Look up record for this caller→Absent: reserve atomically as IN_PROGRESS→Execute the business operation→Store result and mark COMPLETED→Return response→Repeat arrives: return stored result

07Same key, same request

  • A key must only ever describe one logical request; reusing it for different parameters is a client bug.
  • If a ₹1,000 charge and a ₹2,000 charge share a key, silently returning the first result would hide a real error.
  • Store a hash of the significant request fields next to the key.
  • When a duplicate arrives, compare hashes: identical means a genuine retry, different means a conflict.
  • Reject mismatches explicitly, typically with a 4xx response, rather than executing or returning the old result.
  • Hashing selected fields rather than the raw body avoids false mismatches from irrelevant ordering or formatting.
  • This check turns accidental key reuse into a visible error instead of a silent wrong outcome.

08Concurrent requests with the same key

  • Two requests with the same key can arrive almost simultaneously, for example when a client times out and retries immediately.
  • A naive check-then-insert lets both requests see no record, so both execute.
  • The duplicate problem returns in exactly the situation idempotency was meant to solve.
  • The fix is an atomic check and reserve, such as a unique constraint on the key.
  • The first insert wins; the second detects the conflict and must not execute the operation.
  • Distributed stores need a conditional write or a compare-and-set, not a read followed by an unconditional write.
  • Locking works too, but adds contention and expiry handling; a unique constraint is simpler and more reliable.
INSERT INTO idempotency_keys (key, owner, request_hash, status)
VALUES (?, ?, ?, 'IN_PROGRESS')
ON CONFLICT (key, owner) DO NOTHING;
-- zero rows inserted means another request owns this key

09Handling in-progress requests

  • A retry can arrive while the original request is still running, so the record exists but has no final result.
  • Option one: return 202 Accepted with a way to poll for the outcome.
  • Option two: wait briefly for the original to finish, then return its stored result.
  • Option three: return 409 Conflict to signal that the operation is already in progress.
  • Any of these is acceptable; what is not acceptable is starting a second copy of the operation.
  • Waiting needs a bounded timeout, otherwise a stuck original request holds the retry open too.
  • Stale IN_PROGRESS records must eventually expire, or a crashed request blocks the key forever.

10Storing records and choosing retention

  • Records must be durable enough for the side effect they protect: a payment needs stronger guarantees than a preference update.
  • Typical fields: key, owning client, request hash, status, created resource, and optionally the full response.
  • A relational database with a unique constraint gives atomicity and durability in one place.
  • A fast store such as Redis works when losing a record cannot cause real damage.
  • A cache that can lose data must never be the only protection for a financial operation.
  • Retention should cover the window in which clients are expected to retry, for example a day for payment APIs.
  • Longer retention blocks late retries better but costs storage and lookups; shorter retention frees space but reopens the duplicate window.
Retention is a design decision about client behaviour, not a storage default: set it from the maximum retry window you promise.

11Keeping the operation and the record consistent

  • The hard part is not storing a key, it is writing the key and the business change together.
  • If the order is created and the process crashes before the record is marked complete, a retry may create a second order.
  • The fix is to write the business change and the idempotency record in the same transaction.
  • Then either both are committed or neither is, so state cannot diverge.
  • When the business write lives in another system, use an outbox, a two-phase approach, or make the downstream call idempotent too.
  • Recovery jobs should reconcile records stuck in IN_PROGRESS against the actual business state.
  • A crash between commit and response is fine: the next retry reads the completed record and returns it.

12Same effect, not always the same response

  • Idempotency is about system state, so a repeated request may legitimately return a different status code.
  • Deleting a resource returns 200 OK the first time and 404 Not Found the second, while the state stays deleted.
  • The state is identical, so the operation was idempotent even though the responses differ.
  • APIs with explicit idempotency keys usually return the original response because it simplifies client retry logic.
  • Returning the stored response also preserves the created resource identifier, which matters for create operations.
  • Do not conflate “same response” with “same effect”: only the latter is required for correctness.
  • Be explicit in API documentation about which behaviour clients should expect.

↔Trade-offs to say out loud

  • Idempotency keys make retries safe but add a store, a lookup, and a reservation step to every write.
  • Storing full responses makes retries seamless but consumes storage and can leak data if retention is careless.
  • Storing only the result reference saves space but forces the client to re-read state it may not have permission to see.
  • Long retention protects late retries but grows storage and slows lookups on the key index.
  • Short retention keeps storage small but lets a sufficiently delayed retry duplicate the operation.
  • Waiting for an in-progress request gives a clean answer but consumes a connection and needs a bounded timeout.
  • Returning 409 is honest and cheap but pushes retry logic onto the client.
  • Redis-based records are fast but offer weaker durability than a transactional database.
  • Rejecting mismatched hashes prevents silent corruption but can frustrate clients that mutate payloads between attempts.

?Interview questions

Answer aloud before opening the outline.

1. What does idempotent actually mean?

Performing the operation multiple times has the same intended effect on the system as performing it once. The state converges to the same result, even if individual responses differ.

2. Why is idempotency necessary if HTTP has retries built in?

Retries exist precisely because the client cannot know whether a failed request executed. Without idempotency, a retry of a create or a charge duplicates the side effect, so the safe retry depends on the operation being idempotent.

3. Which HTTP methods are idempotent and why?

GET, HEAD, PUT, and DELETE are defined as idempotent, and GET and HEAD are also safe. PUT describes a target state and DELETE removes a specific resource, so repeating them converges. POST creates or triggers something and is not idempotent by default.

4. How does an idempotency key work?

The client generates a unique key for one logical operation and sends it with every attempt. The server stores the key with the request hash, status, and result, and returns the stored result instead of executing again when the key repeats.

5. What happens if the client generates a new key on every retry?

Every attempt looks like a brand-new operation, so the server executes each one and the duplicate side effect reappears. The key must be created before the first attempt and reused for the whole logical operation.

6. Why store a request hash with the key?

To detect a key reused with different parameters, such as a ₹1,000 charge followed by a ₹2,000 charge. If the hash differs, the server rejects the request instead of silently returning an unrelated result.

7. Why is check-then-insert unsafe for idempotency keys?

Two concurrent requests can both see the key absent and both proceed, recreating the duplication. The check and the reservation must be one atomic operation, typically an insert guarded by a unique constraint.

8. What should happen when a retry arrives while the original is still running?

The server must not start a second execution. It can return 202 Accepted, wait briefly for the original to finish and return its result, or return 409 Conflict. Expiring stale in-progress records keeps a crash from blocking the key forever.

9. Where should idempotency records be stored?

Somewhere durable enough for the side effect being protected. A transactional database with a unique constraint is the safe default; a fast cache is acceptable only when losing the record cannot cause a duplicate charge or order.

10. How do you keep the business write and the idempotency record consistent?

Write them in the same transaction so either both commit or neither does. When the side effect lives in another service, use an outbox or make the downstream operation idempotent as well, and reconcile records left in progress.

11. Can an idempotent operation return different responses?

Yes. A second DELETE may return 404 while the resource stays deleted, so the effect is identical and the response is not. APIs with explicit keys often return the original response anyway to make client retries simpler.

12. How long should idempotency records be kept?

At least as long as clients are expected to retry the operation. Internal operations may need minutes or hours, while payment APIs typically keep records much longer because late retries are realistic and expensive.

!Traps

  • Generating a fresh idempotency key on every retry, which silently defeats the whole mechanism.
  • Doing a read-then-write check without atomic reservation, so concurrent retries both execute.
  • Storing idempotency records in a cache that can lose data while protecting a financial side effect.
  • Ignoring the request payload, so the same key with different parameters returns an unrelated result.
  • Leaving records in progress forever after a crash, permanently blocking that key.
  • Assuming identical responses are required, when only the resulting state has to match.
  • Confusing safety with idempotency: a safe method never changes state, an idempotent one may.
