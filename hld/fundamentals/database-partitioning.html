01The problem: one enormous table

A table that starts with a few thousand rows behaves well. After a few years the same table may hold hundreds of millions or billions of rows, and the problems that appear are operational as much as they are about raw query speed.

  • Indexes grow until they no longer fit comfortably in memory, so more lookups go to disk.
  • Queries may scan far more data than they used to, even when the query shape has not changed.
  • Deleting or archiving old records becomes an expensive, long-running operation.
  • Backups, index rebuilds, and vacuum-style maintenance take longer and touch more data.
  • The table can become hard to manage even when the server still has spare CPU, memory, and disk.
  • The fix is not necessarily a bigger machine: it is a smaller unit of work.

02What partitioning is

Partitioning splits one logical table into multiple smaller physical pieces called partitions. The application keeps writing to orders exactly as before.

  • The database decides which partition receives a row at insert time, based on the partition key.
  • Collectively the partitions still represent one logical table with one schema.
  • The application does not need to know how many physical pieces sit underneath.
  • Each partition can be read, indexed, backed up, and dropped independently.
  • The win comes from reading fewer partitions, not from a faster disk.
Partitioning is a physical layout decision. If queries never filter on the partition key, the layout changes nothing about how much data they read.

03Horizontal vs vertical partitioning

  • Horizontal partitioning divides rows: every partition keeps all columns but only a subset of rows.
  • Vertical partitioning divides columns: all rows stay together but a group of columns moves elsewhere.
  • Classic horizontal example: orders split by year, each year its own partition.
  • Classic vertical example: keeping name and email in one table and moving a large bio column to another.
  • When engineers say partitioning in a large-scale design, they almost always mean horizontal partitioning.
  • Vertical partitioning is closer to a schema refactor and is usually chosen to keep hot rows narrow.

04Range partitioning

  • Rows are assigned by ranges of a value, most often a timestamp such as month or year.
  • Range bounds are typically lower-inclusive and upper-exclusive, so a row at exactly midnight on February 1 lands in February.
  • Ranges work on numbers too: customer IDs 1–1,000,000 in one partition, the next million in another.
  • It keeps related values physically together, which suits range queries such as orders from last week.
  • It is the natural fit for time-series and append-heavy data where recent partitions are hot and old ones are cold.
  • The weakness is skew: a burst of traffic in one period can create a partition far larger than its neighbours.

05List partitioning

  • Rows are assigned by an explicit list of discrete values rather than a continuous range.
  • It suits low-cardinality categorical keys such as region, country, tenant tier, or status.
  • One partition can accept several values, which is how a Europe partition collects many countries.
  • A catch-all partition (often a default) keeps unlisted values from failing inserts.
  • Distribution depends entirely on the data: if most users sit in one region, that partition dominates.
  • Adding a new category later means altering the partition definitions, so plan for growth.

06Hash partitioning

  • The database hashes the partition key and uses the result to select a partition.
  • A good hash spreads rows evenly, which fixes the skew problems of range and list partitioning.
  • Nearby values land in unrelated partitions: customer 1000 and 1001 may be stored far apart.
  • Range queries lose pruning, because the optimizer cannot infer which partitions hold a value range.
  • Choose it when even write and storage distribution matters more than locality.
  • Changing the number of hash partitions later means reshuffling data, so pick the count deliberately.

07Partition pruning

Pruning is where partitioning earns its keep. With five years of orders in monthly partitions, a query for September 2026 needs exactly one of sixty partitions.

  • The optimizer knows each partition's bounds and eliminates those that cannot match.
  • The query then reads roughly one sixtieth of the table instead of all of it.
  • Pruning requires a filter on the partition key; a filter on another column rules nothing out.
  • Pruning usually needs a literal or a stable expression, not a function wrapped around the partition key.
  • The fewer partitions a query must open, the lower the I/O and the planning cost.
  • This is why the partition key — not the partitioning syntax — is the real design decision.
Client sends a query with a filter on the partition key→Planner compares the filter to each partition's bounds→Non-matching partitions are skipped entirely→Remaining partitions are scanned or index-probed→Rows are merged into one result set

08Choosing the partition key

  • Look at the WHERE clauses of the most frequent queries, not at the table's primary key.
  • For an events table queried as last 24 hours, partitioning by timestamp lets a query touch one or two partitions.
  • Partitioning the same table by user_id scatters recent events across every partition, so nothing is pruned.
  • The better key is workload-dependent: if the common query is all events for user 42, user_id wins.
  • Avoid keys with a dominant value, such as a status column where most rows are active.
  • Prefer keys that appear in joins and range filters, and that grow in a predictable direction.

09Partitioning and indexes

Partitioning does not replace indexing. They operate at different levels and are usually combined.

  • Each partition can carry its own index, for example an index on customer_id inside every monthly partition.
  • A query for one customer in September first prunes to September, then uses that partition's index.
  • Per-partition indexes are smaller, so they are more likely to stay resident in memory.
  • Index maintenance is cheaper because a rebuild touches one partition, not the whole table.
  • Some databases require the partition key in every primary key or unique constraint, since uniqueness can only be enforced inside a partition.
  • In PostgreSQL that constraint rule is explicit: a unique key on a partitioned table must include the partition columns.

10Lifecycle and maintenance benefits

  • Retention becomes a metadata operation: dropping a monthly partition removes its files instead of deleting rows one by one.
  • A large DELETE writes enormous transaction logs, burns I/O, and can leave dead space behind; dropping a partition avoids all of that.
  • A detached partition can be archived, exported to a warehouse, or kept read-only instead of being destroyed.
  • Statistics can be collected per partition, so a busy recent partition is analyzed more often than cold ones.
  • Backups can follow partition boundaries, so an unchanging old partition is backed up once.
  • Append-heavy workloads — logs, events, transactions, metrics — benefit most because active and historical data separate cleanly.
Create next month's partition ahead of time→Write new rows into the active partition→Detach the oldest partition at the retention boundary→Archive, export, or drop the detached partition

11Pitfalls: uneven partitions and too many partitions

  • Skew: one partition can hold the overwhelming majority of rows, making it nearly as large as the original table.
  • A skewed partition gives little pruning benefit and makes its index rebuilds far more expensive than its neighbours'.
  • Fix skew by re-splitting the hot partition — sub-partition by country or hash — while leaving small partitions alone.
  • Over-partitioning: minute-level partitions mean hundreds of thousands per year and over a million within two years.
  • Too many partitions add metadata to track, planning cost to consider, and a create/cleanup job that becomes its own system.
  • Each partition then holds so little data that splitting further buys nothing.
  • Sizing rule: match granularity to the most common query window, so a last 7 days query opens seven partitions, not hundreds.

12Partitioning vs sharding

  • Partitioning divides a dataset into smaller pieces that can all live on one database server.
  • Sharding distributes those pieces across multiple independent servers.
  • With partitioning the database routes queries; with sharding the application, a proxy, or a routing layer does.
  • Partitioning makes a large table easier to query and manage but adds no CPU, memory, or disk.
  • Sharding adds capacity but brings cross-server queries, distributed transactions, and rebalancing.
  • Real systems combine them: data is sharded across servers, and each shard's tables are partitioned internally.
  • If one server still has headroom, partitioning is usually the cheaper first step.

13When to use partitioning

  • Use it when a table is large enough that size itself causes query or operational pain.
  • It works best when the data has a natural grouping, with time being the most common one.
  • It is a strong fit when old data must be deleted or archived on a schedule.
  • Small tables do not need it: a few million rows with good indexes is often already fast.
  • Ask whether common queries filter on a natural partition key and whether pruning removes a meaningful share of data.
  • Ask whether partitioning will genuinely simplify maintenance or retention.
  • If most answers are no, better indexes or query tuning solve the problem with less complexity.
Is the table large enough to hurt?→Do common queries filter on a natural key?→Does pruning remove most of the data?→Does retention or maintenance get simpler?→If yes to most, partition; otherwise tune indexes first

↔Trade-offs to say out loud

  • Partition pruning cuts the data a query reads, but only for filters on the partition key; other filters pay the full cost plus planning overhead.
  • Range partitioning keeps time-ordered data together and makes retention trivial, but recent or bursty periods create hot, oversized partitions.
  • Hash partitioning spreads rows evenly, but destroys locality and forces range queries to touch every partition.
  • List partitioning maps cleanly to known categories, but a dominant category recreates the original single-big-table problem.
  • Per-partition indexes are smaller and cheaper to rebuild, but a global unique constraint may become impossible without the partition key.
  • Dropping a partition is far cheaper than a bulk delete, but it is all-or-nothing: you cannot keep a few rows from the dropped range.
  • More partitions improve pruning granularity, but add metadata, planning cost, and background create/drop work.
  • Partitioning improves manageability on one server, but it does not add CPU, memory, or disk the way sharding does.

?Interview questions

Answer aloud before opening the outline.

1. What is database partitioning?

It is splitting one logical table into multiple physical pieces called partitions while the application still sees and queries a single table. The database routes each inserted row to a partition based on the partition key. Each partition can then be indexed, scanned, backed up, or dropped independently.

2. How does partitioning actually make queries faster?

Through partition pruning: when a query filters on the partition key, the optimizer skips partitions whose bounds cannot match. A monthly-partitioned table queried for one month reads one partition instead of the whole table. Without a filter on the partition key, the query still touches every partition.

3. Horizontal vs vertical partitioning — what is the difference?

Horizontal partitioning splits rows, so each partition has all columns but a subset of rows; orders split by year is the classic case. Vertical partitioning splits columns, keeping all rows together and moving large or rarely read columns into another table. Large-scale system design almost always means horizontal partitioning.

4. When would you choose range partitioning over hash partitioning?

Choose range when queries filter on ranges and locality matters, especially time-series data where recent periods are hot and old data can be archived. Choose hash when the key has no natural ranges and you need even distribution of writes and storage. Range gives pruning for range filters; hash gives balance but scatters related rows.

5. Why does hash partitioning hurt range queries?

Because the hash destroys ordering: adjacent keys land in unrelated partitions, so the optimizer cannot infer which partitions hold a value range. A query for customer IDs 1000–2000 must open every partition. Hash partitioning trades pruning for even distribution.

6. How do you pick the partition key?

Start from the WHERE clauses of the most frequent queries and pick a column those queries filter on. The key should also distribute data reasonably evenly and avoid a single dominant value. If the common query is last 24 hours, partition by time; if it is all events for a user, partition by user ID.

7. Does partitioning remove the need for indexes?

No. Partitioning reduces how much data the database must consider, and indexes locate rows inside the chosen partition. Combined, a query prunes to one partition and then probes its local index. Per-partition indexes are also smaller and more likely to stay cached.

8. What constraint problem can partitioning create?

Unique constraints can usually only be enforced within a partition. PostgreSQL, for example, requires a primary key or unique constraint on a partitioned table to include the partition key columns. If you need global uniqueness on another column, partitioning alone cannot provide it.

9. How does partitioning help with deleting old data?

Instead of a large DELETE that finds and removes each row while writing a huge transaction log, you drop or detach the whole partition. The cost depends on the number of partitions, not the number of rows. A detached partition can also be archived or kept read-only instead of deleted.

10. What goes wrong with uneven partitions?

One partition can hold most of the data, so queries against it scan nearly as much as the original table and its index rebuilds dominate maintenance. The fix is to re-split the hot partition — by sub-region or by hash — while leaving the small partitions alone. Partition boundaries must follow the real data distribution.

11. Why can too many partitions be a problem?

Every partition adds metadata to track and work for the planner to consider, so query planning gets slower. Creating future partitions and cleaning up old ones becomes its own operational job, and each tiny partition yields almost no extra pruning. Match granularity to the dominant query window.

12. Partitioning vs sharding — how do they differ?

Partitioning splits a table into pieces that usually stay on one database server, with the database routing queries. Sharding spreads pieces across multiple servers, which adds storage and write capacity but brings cross-shard queries and distributed coordination. Systems commonly shard first and partition within each shard.

!Traps

  • Partitioning by the primary key or by an id column that queries never filter on, so pruning never fires.
  • Assuming partitioning adds capacity — it only reorganizes data inside the same server.
  • Choosing monthly or yearly partitions for data whose queries always ask for the last few hours.
  • Creating minute-level partitions and drowning the planner in metadata.
  • Forgetting that unique constraints usually must include the partition key.
  • Leaving a single dominant partition in place and expecting list partitioning to help.
  • Dropping a partition for retention when a few rows from that range were meant to be kept.
