Webhook
An HTTP callback where a provider sends a request to a consumer's endpoint whenever a particular event occurs.
Provider
The system that owns the event and sends the webhook request, such as a payment platform or source-control host.
Consumer (receiver)
The system that exposes the endpoint, verifies the request, and processes the event.
At-least-once delivery
The delivery guarantee most webhook systems provide: every event arrives, but some may arrive more than once.
Idempotency
Processing the same event twice has the same effect as processing it once, usually enforced by recording event IDs.
Event ID
A unique identifier for an event, used to detect duplicates and to correlate retries.
HMAC signature
A keyed hash over the request body, computed with a shared secret, proving the request came from the provider.
Dead-letter queue
Storage for events that exhausted retries, so they can be inspected, alerted on, or replayed manually.
Outbox pattern
Writing the event to a database table in the same transaction as the business change, then relaying it to a queue.
Exponential backoff with jitter
Retry delays that grow each attempt and add randomness, so thousands of failures do not retry in the same instant.

01What is a webhook?

Suppose your application uses a payment provider. When a payment succeeds, your backend must update the order status.

  • One option is polling: ask the provider every N seconds whether anything changed.
  • Polling wastes work when most checks return nothing, and it adds latency up to one full poll interval.
  • The other option is a webhook: the provider sends an HTTP request to your server when the event happens.
  • A webhook is an HTTP callback: one system exposes an endpoint, another posts to it on a specific event.
  • The sending system is the provider; the receiving system is the consumer or receiver.
  • This inverts initiation: the consumer no longer has to ask, and the provider decides when to notify.
  • The trade is that delivery now crosses the public internet asynchronously, so it can fail, duplicate, or arrive out of order.

02Basic webhook flow

  • The consumer registers an endpoint URL with the provider, usually per event type.
  • When the event occurs, the provider builds a payload and sends an HTTP POST to that URL.
  • The request carries the event type, a unique event ID, a timestamp, and the payload describing the object involved.
  • Security and delivery details travel in headers: signature, delivery ID, event name, content type, and user agent.
  • The consumer verifies the request, processes the event, and returns a success response.
  • The provider records the attempt and treats a non-success response or timeout as a failed delivery.
  • Sending the request is the easy part; making delivery reliable is the actual design problem.

03Retries

  • If a provider sends an event and the consumer is temporarily unavailable, the provider must not discard it.
  • It stores the event durably and retries later, usually with exponential backoff: for example 1, 2, 4, then 8 minutes.
  • Providers add jitter, a small random offset, so thousands of failed deliveries do not retry at the same moment.
  • Retries must eventually stop: most systems define a maximum attempt count or a retry window such as a few days.
  • After that, the event moves to a failed-delivery queue or dead-letter queue for inspection or manual replay.
  • Retry policy should be visible to the consumer: how many attempts, over how long, and what counts as success.
  • A retry is a new HTTP request, so it can arrive after newer events, which is why ordering cannot be assumed.
Attempt 1 fails→Wait with backoff and jitter→Attempt 2 fails→Double the delay, retry again→Retry window or attempt cap reached→Move event to dead-letter queue and alert

04Why duplicate webhooks happen

  • Your server processes an event successfully, but the network fails before the provider receives the HTTP response.
  • Your server knows the event succeeded; the provider does not.
  • From the provider's side the safest option is to retry, so your application receives the same event again.
  • Timeouts create the same ambiguity: the provider cannot know whether a slow request completed or never ran.
  • That is why most webhook systems provide at-least-once delivery, not exactly-once.
  • Exactly-once delivery over an unreliable network with independent failures is not practically achievable.
  • The consumer must therefore make processing safe to repeat rather than assume a single delivery.

05Idempotency

Idempotency means processing the same event twice has the same effect as processing it once.

  • Every event should carry a unique event ID.
  • On receipt, check whether that event ID has already been processed.
  • If not, process the event and record the ID in the same logical operation.
  • If it has, recognize the duplicate and skip the side effects.
  • Store processed IDs in reliable storage with a unique constraint, so two concurrent deliveries cannot both slip through.
  • When a duplicate arrives, still return success, because the original was already accepted; returning an error invites more retries.
  • For side effects outside the database, such as charging a card or sending email, prefer idempotency keys supported by the downstream system.
  • Pruning old event IDs needs a retention window longer than the provider's retry window.
BEGIN;
INSERT INTO processed_events (event_id, received_at)
VALUES ('evt_123', now())
ON CONFLICT (event_id) DO NOTHING;
-- if no row was inserted, this is a duplicate: skip side effects
COMMIT;

06Return quickly, process asynchronously

  • A common mistake is doing too much work inside the webhook handler.
  • Updating the database, sending email, generating an invoice, updating analytics, and calling another service can exceed the provider's timeout.
  • The provider then assumes failure and retries, possibly while the first request is still running.
  • The reliable pattern is: validate the request, store the event durably, return success quickly.
  • Background workers then perform the expensive business logic asynchronously.
  • This separates delivery from processing, so a slow downstream system cannot delay the acknowledgment.
  • Order matters: do not return 200 OK before the event is safely stored, or a crash loses the event with no retry.
  • The endpoint's only job is to accept responsibility for the event, not to finish all its consequences.

07Queue-based architecture

  • The endpoint validates the request, writes the event to a durable queue, and immediately returns success.
  • A pool of workers consumes events and performs the actual business logic.
  • Decoupling: a burst of events is absorbed by the queue instead of overwhelming the application.
  • Retry: workers can retry failed processing without asking the provider to resend.
  • Scaling: the worker fleet scales on queue backlog, independently of the webhook endpoint.
  • A dual-write hazard exists if the endpoint saves to a database and then publishes to a queue as two separate writes.
  • A crash between them drops the event, so commit both together or use an outbox table that a relay forwards to the queue.
  • Alternatively, workers can read directly from the events table, so there is only one write.
Provider POSTs event→Endpoint verifies signature→Deduplicate and store event durably→Return 200 OK→Queue or outbox feeds workers→Workers process and retry; failures go to DLQ

08Webhook ordering

  • Suppose an order is created and then cancelled; you might assume the events arrive in that order.
  • Distributed systems rarely guarantee it: the first webhook can fail and be retried while the second succeeds immediately.
  • Your application may therefore see the cancellation before the creation.
  • Solution one: sequence or version numbers on each event, describing the resource version.
  • If version 5 was already processed and version 4 arrives, ignore the stale event.
  • Solution two: fetch the latest state, treating the webhook as a notification that something changed.
  • The order of notifications then no longer matters, because each handler reconciles against the source of truth.
  • For payments, the common approach is to confirm status through the provider's API before fulfilling an order.

09Security and webhook signatures

  • Webhook endpoints are publicly reachable, so anyone who finds the URL can POST a fake payment_succeeded event.
  • The common defense is request signing with a shared secret.
  • The provider computes a cryptographic signature, usually an HMAC, over the payload and sends it in a header.
  • The consumer recomputes the expected signature with the same secret and compares them in constant time.
  • Verify the raw request body; parsing JSON and re-serializing can change bytes and break the signature.
  • Check the signed timestamp and reject requests older than a small window, which blocks replay attacks.
  • Use the provider's official library when available, because signature formats and header names differ.
  • Also enforce network-level controls and treat a verification failure as 401 or 403, never as a silent 200.

10Webhook endpoint design

  • Keep the endpoint simple: verify, validate, store durably, and return quickly.
  • Avoid running complex business logic directly in the request path.
  • HTTP status codes tell the provider whether to retry, so they are part of the contract.
  • 2xx means accepted or already handled; most 4xx codes mean retrying will not help; 5xx and 429 generally signal a retryable failure.
  • A malformed body should return 400, and a bad signature should return 401 or 403.
  • A 404 usually means the endpoint is gone, which may cause the provider to disable the subscription.
  • Return 429 when overloaded rather than accepting work you cannot store.
  • Document the retry semantics on both sides so the provider and consumer agree on what success means.

11Observability for webhook consumers

  • Webhook failures are easy to miss because the provider retries quietly and users notice only the symptom.
  • A typical symptom is an order stuck in PENDING while every dashboard looks healthy.
  • Track delivery volume per event type and per provider.
  • Track failures and retries, including signature failures, which usually indicate attack or misconfiguration.
  • Track processing latency and queue backlog, not just endpoint response time.
  • Alert on dead-letter arrivals and on age of the oldest unprocessed event.
  • Correlate logs by event ID and delivery ID so a single event can be traced end to end.
  • Record the raw event and the processing outcome so a failed event can be replayed deliberately.

12Designing a webhook provider

  • When a platform delivers webhooks to thousands of customers, the service that created the event should not send them directly.
  • Instead, write the event to a durable queue or event stream.
  • A dedicated webhook delivery service reads it, finds subscribed endpoints, and sends the requests.
  • The delivery service tracks each attempt: response status, retry count, and next retry time.
  • After repeated failures the event moves to a dead-letter queue per endpoint.
  • Separating generation from delivery means the originating service never waits on a customer's server.
  • The delivery service also enforces per-endpoint rate limits, timeouts, and concurrency limits.
  • Customers need a way to inspect deliveries, replay events, and rotate secrets without downtime.
Business event occurs→Write to durable queue or stream→Delivery service loads subscriptions→POST to each endpoint with signature→Record attempt and schedule retry→Move exhausted events to DLQ

13Handling slow or broken consumers

  • As a provider, assume some customer endpoints are slow, unreliable, or completely down.
  • One broken destination must not affect deliveries to everyone else.
  • Isolate per endpoint with its own retry state, rate limit, and timeout.
  • Apply concurrency limits so a single customer is not overwhelmed by parallel requests.
  • This matters most when replaying a backlog: a customer down for an hour should receive it at a pace it can handle, not all at once.
  • Set a short connect and read timeout; a slow endpoint should fail fast and retry rather than hold a worker.
  • Disable or quarantine endpoints that fail persistently, and notify the customer.
  • Never let one customer's backlog consume shared worker capacity that other customers depend on.

14When to use webhooks

  • Webhooks are a strong choice when one system must notify another that an event occurred.
  • They work especially well for discrete events where a permanent connection would be wasteful.
  • Common uses: payments, source-control events, order updates, email delivery, identity systems, CI pipelines, and third-party integrations.
  • They beat polling on latency and wasted requests when events are sparse and unpredictable.
  • They are a poor fit when the caller needs an immediate result from your system, since delivery is asynchronous.
  • They are also a poor fit for high-frequency streams or when many internal services must react to the same event; use a broker there.
  • For a large fan-out to your own services, publish to a message bus and let each service subscribe instead of registering webhooks.

↔Trade-offs to say out loud

  • Webhooks versus polling cut latency and wasted requests, but move complexity to delivery reliability, security, and duplicate handling.
  • Retries improve delivery success but create duplicates and can reorder events.
  • Exponential backoff with jitter protects the receiver and spreads load, but delays recovery when the receiver comes back quickly.
  • Idempotency keys make duplicates safe but require durable storage, a unique constraint, and a retention policy.
  • Returning quickly protects the provider timeout but means the user sees eventual, not immediate, completion.
  • Queue-based processing absorbs bursts and decouples workers, but adds a queue, a DLQ, and possible dual-write hazards.
  • Version-number ordering prevents stale overwrites but requires per-resource version tracking and correct event design.
  • Fetch-latest-state ordering is robust and simple but adds an API call and depends on the source being readable.
  • Strict signature and timestamp checks block forgery and replay but break on clock skew and on any body re-serialization.
  • Provider-side isolation protects other customers from one bad endpoint but multiplies per-endpoint state and limits throughput for healthy consumers.

?Interview questions

Answer aloud before opening the outline.

1. What is a webhook, and how does it differ from polling?

A webhook is an HTTP callback: the provider posts an event to the consumer's endpoint when it happens. Polling has the consumer ask repeatedly, which wastes requests and adds up to one poll interval of latency. Webhooks invert the direction and remove the waiting.

2. Walk through the basic webhook flow.

The consumer registers an endpoint URL. On an event, the provider POSTs a payload with an event type, event ID, timestamp, and signature. The consumer verifies the signature, stores the event, and returns a success response quickly, then processes it asynchronously.

3. Why do duplicate webhooks happen?

The provider cannot tell whether a request failed or its response was lost. If the consumer processed the event but the acknowledgment never arrived, the provider retries, so the same event is delivered again. That is why delivery is at-least-once.

4. How do you make a webhook handler idempotent?

Use the event ID: insert it into a processed-events table with a unique constraint, and only apply side effects if the insert succeeds. Return success for duplicates. For external side effects, also pass downstream idempotency keys.

5. Why should a webhook endpoint return quickly?

Providers impose timeouts. If processing takes too long, the provider assumes failure and retries, possibly while the first request is still running. Storing the event and returning immediately avoids duplicate concurrent processing and lost work.

6. What is the correct order: store the event or return 200 OK?

Store durably first, then return success. If you acknowledge before the event is persisted and then crash, the provider sees success and will not retry, so the event is lost.

7. What is the outbox pattern and why does it matter here?

It writes the event to a database table in the same transaction as the business change, and a relay forwards it to the queue. That avoids the dual-write gap where a crash between saving to the database and publishing to the queue drops the event.

8. How do you handle out-of-order webhook events?

Either attach version numbers and ignore events older than the last applied version, or treat the webhook as a notification and fetch the current state from the source. For payments, confirm status through the provider before fulfilling.

9. How do you verify that a webhook came from the provider?

Compute an HMAC over the raw request body with the shared secret and compare it to the signature header in constant time. Also check the signed timestamp and reject stale requests to prevent replay. Use the provider's official verification library when available.

10. Why must you verify the raw body rather than the parsed JSON?

Parsing and re-serializing can change whitespace, key order, or number formatting, producing different bytes and a different HMAC. The signature is over the exact bytes sent, so verification must use the raw body.

11. Which HTTP status codes should a webhook endpoint return?

2xx for accepted or already processed, 400 for malformed input, 401/403 for a failed signature, 404 for a dead endpoint, 429 when overloaded, and 5xx for a temporary failure that should be retried. Codes are part of the retry contract.

12. How would you design the sending side for thousands of customers?

Write events to a durable queue, let a dedicated delivery service fan them out to subscribed endpoints, and track attempts with retry counts and next retry times. Isolate per endpoint with rate and concurrency limits, and move exhausted events to a dead-letter queue.

13. How do you protect a provider from one broken consumer?

Give each endpoint its own retry state, rate limit, timeout, and concurrency limit. Fail fast on slow endpoints, replay backlogs at a controlled pace, and disable persistently failing subscriptions so they do not consume shared capacity.

14. When are webhooks the wrong choice?

When the caller needs an immediate result, when events are a high-frequency stream, or when many internal services must react to the same event. Use a synchronous API for immediate answers and a broker for large internal fan-out.

!Traps

  • Returning 200 OK before the event is durably stored, so a crash loses it with no retry.
  • Processing the event inline and hitting the provider timeout, which triggers a retry and duplicate work.
  • Deduplicating in memory or with a check-then-insert race instead of a unique constraint.
  • Verifying the signature over parsed and re-serialized JSON instead of the raw body.
  • Accepting signed requests without checking the timestamp, which leaves replay attacks open.
  • Assuming webhooks arrive in order and applying a cancellation before the creation it refers to.
  • Writing to the database and publishing to a queue as two independent operations, creating a dual-write gap.
  • Giving every customer endpoint shared retry state and worker capacity, so one dead endpoint stalls everyone else.
