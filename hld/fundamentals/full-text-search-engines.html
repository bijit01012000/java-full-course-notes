In one lineA full-text search engine replaces row scans with an inverted index from words to documents, so it can match, rank, and filter free text — at the cost of a second data store that must be kept in sync with the source of truth.
Inverted index
A mapping from each term to the list of documents that contain it, which is the reverse of scanning documents for words.
Analyzer
The pipeline that turns raw text into indexed terms: tokenization, normalization, stop-word removal, and stemming.
Token
One unit produced by the analyzer, usually a normalized word, which becomes a key in the index.
Stemming
Reducing words to a common root so that running and runs match the same term.
Postings list
The document ids and positions stored for one term, making phrase and proximity queries possible.
BM25
A ranking function that scores documents by term frequency, rarity across the corpus, and length normalization.
Fuzzy matching
Matching terms within an edit distance so small typos still find results, at the cost of more candidate terms.
Segment
An immutable index chunk written by a refresh; searches span all segments and merges remove deleted entries later.
Refresh
The step that makes recently indexed documents searchable, which is why search visibility is near-real-time rather than immediate.
Faceting
Counting documents per value of a field so a result page can show filters with counts instead of bare matches.

01The problem full-text search solves

A product table with millions of rows must answer find red running shoes. The obvious approach — a pattern match on the description column — has several problems at once.

  • A leading-wildcard pattern cannot use a normal index, so the database reads every row.
  • Pattern matching is literal: it misses run versus running, plurals, synonyms, and misspellings.
  • It produces a set, not an ordering; the best match is indistinguishable from the weakest.
  • Users expect the most relevant results first, plus filters, highlighting, and suggestions.
  • Ranking by hand in SQL means computing term counts and weights in application code for every query.
  • So the problem is not only find rows containing a word but find, rank, and summarize text quickly.
  • That is a different access pattern from key lookup, which is why a dedicated engine exists.

02What a search engine is

  • A search engine is a store built around text: it analyzes documents into terms and records where each term appears.
  • Its primary structure is an inverted index, mapping terms to the documents containing them.
  • It returns ranked results, not just matches, so relevance is part of the query result.
  • It typically runs beside the primary database rather than replacing it: the database stays the source of truth.
  • It adds language-aware behavior: stemming, synonyms, phrase queries, typo tolerance, highlighting, and faceting.
  • Documents are usually semi-structured records with fields, so a title match can outrank a description match.
  • The engine is a derived view: everything in it can be rebuilt from the primary data.

03The inverted index

  • A forward index answers which terms are in document 42; an inverted index answers which documents contain term X.
  • The term dictionary is sorted and mapped to a postings list of document ids.
  • Postings often store term frequency and token positions, which enable phrase and proximity queries.
  • A query intersects postings lists instead of scanning documents, so cost follows the number of matches, not the corpus size.
  • The dictionary is kept sorted and often compressed with prefix sharing, which makes prefix lookups cheap.
  • Postings for very common words are long, which is why stop words and thresholds exist.
  • Building the index is a one-time full pass; keeping it current is the ongoing work.

04Text analysis

  • Tokenization splits text into words, and the rules matter for hyphens, punctuation, and non-Latin scripts.
  • Normalization lowercases and folds accents so Running and running become one term.
  • Stop-word removal drops extremely common words that add noise and huge postings lists.
  • Stemming or lemmatization reduces words to a root so inflections match each other.
  • A synonym filter indexes or expands equivalent terms, such as sneaker and trainer.
  • N-grams index character or word sequences, which helps partial words and languages without spaces.
  • The query must be analyzed by the same analyzer as the field, or a term that exists will not match.
Raw text→Tokenize→Lowercase and normalize→Remove stop words→Stem or lemmatize→Write terms to the index

05Querying

  • A term query matches one analyzed term; a phrase query requires the terms in order using stored positions.
  • Boolean combinations — must, should, must-not — express AND, OR, and NOT semantics.
  • Prefix and wildcard queries walk the sorted dictionary, which is efficient for prefixes and expensive for leading wildcards.
  • Field-scoped queries let a title match weigh more than a body match.
  • Filters on structured fields — price, category, date — run alongside text matching but should not affect the score.
  • Query parsing turns user input into this tree, and a bad parse is a common cause of empty results.
  • Ranges and geo queries reuse the same index machinery, which is why search engines also serve some non-text filtering.

06Ranking and relevance

  • Classic scoring weights a term higher when it appears often in a document but rarely in the corpus.
  • BM25 refines that with saturation — the tenth occurrence adds less than the second — and length normalization.
  • Short documents are favored for the same term count, because the term is a larger share of the content.
  • Field boosts let titles and tags outrank long descriptions.
  • Business signals such as recency, popularity, or stock availability are applied as additional boosts.
  • Scores are comparable within one query, not across queries, so a raw score is a poor user-facing number.
  • Relevance is tuned against examples: gather queries with known good results, then measure whether changes improve them.

07Beyond matching: typo tolerance, suggestions, highlighting

  • Fuzzy matching finds terms within a small edit distance, which absorbs typos at the price of more candidate terms.
  • Autocomplete uses prefix queries over a compact structure, often on a dedicated suggestions field.
  • Did you mean suggestions come from term frequencies and near-miss corrections.
  • Highlighting needs stored positions so the engine can mark the matched fragments in the returned text.
  • Faceting computes counts per filter value so the UI can show how many results each option would return.
  • These features are why search is a product surface, not just a query API.
  • Each one adds index structures or query-time work, so enable the ones that users actually need.

08Index maintenance and near-real-time behavior

  • New documents are buffered and written as immutable segments rather than editing the index in place.
  • A refresh makes buffered documents searchable; until then a write is durable but invisible to queries.
  • Searches span all segments and merge results, so many small segments make queries slower.
  • A background merge combines segments and physically removes deleted documents.
  • Deletes are usually tombstones until the merge reclaims them, so disk usage lags behind logical deletions.
  • A bulk reindex rebuilds everything with a new mapping, which is the standard way to change analyzers.
  • Near-real-time visibility is the key expectation to set: searchable within seconds, not instant.

09Scaling search

  • An index is split into shards, each holding a subset of documents.
  • A query goes to every shard, each returns its top results, and the coordinating node merges them into one ranked list.
  • More shards increase parallelism but also per-query overhead and merge cost.
  • Replicas increase query throughput and availability, at the cost of storage and write amplification.
  • Deep pagination is expensive because each shard must return enough results to merge accurately; cursor-based paging is preferred.
  • Routing queries by a tenant or key to a single shard avoids scatter-gather when the access pattern allows it.
  • Capacity planning is dominated by index size and query rate, not by row count alone.
Query reaches coordinator→Fan out to all shards→Each shard scores its local matches→Coordinator merges top results→Return ranked page

10Search alongside the primary database

  • The primary database remains the source of truth; the search index is derived and disposable.
  • Writing to both places directly creates a dual-write problem: one write can succeed and the other fail, leaving them inconsistent.
  • A safer pattern publishes changes to a log or queue and lets an indexer consume them, so failures retry.
  • A transactional outbox stores the change in the same database transaction, then ships it asynchronously to the indexer.
  • Change data capture reads the database log and streams changes without application coordination.
  • Because indexing lags, users can search a document that was just deleted or miss one just created.
  • The standard fix for write-then-read flows is to read the record from the source of truth by id once search returns its ids.
  • Always keep a full reindex path: it is the recovery plan for a corrupted or schema-changed index.

11Operating and tuning relevance

  • Monitor zero-result queries: they reveal analyzer mismatches, missing synonyms, and vocabulary users expect.
  • Track click-through and conversion per query to see whether the top results are useful, not merely present.
  • Keep a small judgment set of queries with expected results, and rerun it after any analyzer or boost change.
  • Analyzer changes require a reindex, so plan for a second index and an alias switch rather than an in-place edit.
  • Query-time boosts are cheap to iterate; mapping and analyzer changes are not.
  • Excessive fuzzy matching produces noisy results; tightening edit distance often improves perceived quality.
  • Search quality is measured by users, so changes ship as experiments, not as pure refactors.

12Alternatives and when a dedicated engine is overkill

  • Many relational databases provide a built-in full-text index that is adequate for modest volumes and simple matching.
  • Trigram or pattern indexes can accelerate substring matching when ranking and language features are unnecessary.
  • Search inside the primary database avoids a second store, its sync lag, and its operational cost.
  • Vector search handles semantic similarity, and hybrid search combines it with keyword matching.
  • A dedicated engine earns its place when ranking quality, language analysis, faceting, or query volume exceeds what the primary can do.
  • Starting with the database's built-in capability and moving later is usually cheaper than operating an unused cluster.
  • Either way, the index stays derived: the source of truth keeps its own copy.

13When to use a dedicated search engine

  • Users type free text and expect the best matches first, not merely matching rows.
  • The corpus is large enough that scanning or naive indexing is too slow.
  • You need language handling: stemming, synonyms, typo tolerance, multi-language analysis.
  • You need facets, highlighting, suggestions, or per-field boosting as product features.
  • The index can tolerate a short visibility delay after a write.
  • You can operate a second system with its own backups, monitoring, and reindex procedure.
  • If those are not true, a database full-text index is usually the better engineering choice.

↔Trade-offs to say out loud

  • Inverted indexes make text matching fast but consume significant storage and must be updated on every document change.
  • Aggressive analysis increases recall through stemming and synonyms but reduces precision and can match unintended terms.
  • Fuzzy matching absorbs typos but multiplies candidate terms, raising latency and noise.
  • More shards increase parallelism but add per-query fan-out and merge overhead.
  • Replicas raise query throughput and availability but multiply storage and indexing work.
  • Near-real-time refresh makes writes visible quickly but produces many small segments that slow queries until merged.
  • A separate search index gives ranking and scale but introduces sync lag, dual-write failure modes, and a second system to operate.
  • Relevance tuning improves perceived quality but is empirical, so it needs evaluation data and repeated experiments.
  • Tombstone deletes keep writes cheap but let disk usage lag far behind logical document count.

?Interview questions

Answer aloud before opening the outline.

1. Why can't you just use LIKE '%term%'?

A leading wildcard prevents index use, so the database scans every row, and the cost grows with the corpus. It also matches literally, with no stemming, synonyms, typo tolerance, or relevance ranking, so results are a set rather than an ordered answer.

2. What is an inverted index?

A structure mapping each analyzed term to the documents that contain it, usually with positions and frequencies. Queries intersect those postings instead of reading documents, so cost scales with matches rather than with corpus size.

3. Walk through text analysis.

Text is tokenized into words, normalized to lowercase and accent-folded, stripped of stop words, and reduced to stems or lemmas; synonyms and n-grams may be added. The query runs through the same analyzer, because a term indexed as run will not match a query for running otherwise.

4. How does relevance ranking work?

Each matched term contributes based on how often it appears in the document and how rare it is in the corpus, with saturation so repetition adds diminishing weight, and length normalization so short documents are not penalized. BM25 is the standard formulation, and field boosts plus business signals adjust the order.

5. Why is search visibility delayed after a write?

New documents are buffered and become searchable only after a refresh writes a new immutable segment. That is what makes the engine near-real-time rather than transactional. Until the refresh, the write is durable but queries cannot see it.

6. What is the dual-write problem?

If the application writes to the database and the search index in sequence, one can succeed while the other fails, leaving the index wrong with no automatic repair. Consuming a change log or a transactional outbox makes indexing retryable and keeps the database as the single source of truth.

7. How does a query execute across shards?

The coordinating node sends the query to every shard, each shard scores its local matches and returns its top results, and the coordinator merges them into one ranked list. That is why deep pagination is expensive: every shard must return enough results for the merge to be correct.

8. How would you avoid a stale result after a user edits a record?

On the write path, update the source of truth first and index asynchronously. On the read path, treat search as an id finder: fetch the actual records from the source of truth by id before rendering. That makes a stale index affect ranking and discovery, not correctness.

9. Why do deletes not free disk immediately?

Deleted documents are marked in the index and skipped at query time, but the bytes remain until a segment merge rewrites that segment without them. So disk usage and segment count lag behind the number of live documents.

10. When is a database's built-in full-text search enough?

When the corpus is modest, matching is simple, ranking is not a product differentiator, and avoiding a second system matters more than search quality. It also keeps reads consistent with writes, since there is no indexing lag.

11. How do you change the analyzer safely?

Build a new index with the new analyzer, backfill it, compare results against a judgment set, then switch an alias to the new index. Editing the analyzer in place would require a full rebuild anyway, and doing it live risks inconsistent results during the transition.

12. Search engine or vector database?

Keyword search matches exact analyzed terms and ranks by term statistics, which is precise when users know the vocabulary. Vector search matches meaning through embeddings, which handles paraphrase and synonyms. Many systems combine both and merge the ranked lists, which is called hybrid search.

!Traps

  • Indexing text with one analyzer and querying with another, so terms silently fail to match.
  • Treating the search index as the source of truth and losing data when a reindex is needed.
  • Writing to the database and the index separately without retry or reconciliation.
  • Using leading wildcards or heavy fuzzy matching on a large corpus and then wondering about latency.
  • Expecting a newly written document to appear in search immediately.
  • Adding shards to fix slow queries that are actually caused by too many small segments.
  • Tuning boosts by intuition instead of measuring against a fixed set of queries.
