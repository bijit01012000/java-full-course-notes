01Where TCP and UDP sit

Applications do not put bytes on the wire directly; they hand them to a transport protocol, which hands packets to IP.

  • At the top are application protocols such as HTTP, DNS, and database wire protocols.
  • Below them is the transport layer, where TCP and UDP live.
  • Below that is IP, which moves packets between machines across networks.
  • IP gets a packet to the right machine; TCP or UDP gets the data to the right application on that machine.
  • A port identifies the application: one host can run a web server on 443, a database on 5432, and other services alongside.
  • Both protocols use ports, so the real difference is not location in the stack but the guarantees each one provides.

02TCP and the three-way handshake

TCP is connection-oriented: both sides agree on a starting point before any application bytes flow.

  • TCP (Transmission Control Protocol) provides reliable, ordered communication between two endpoints.
  • It is the right default when the application needs every byte, in order, and would rather wait than process stale or partial data.
  • SYN: the client proposes a connection and carries its initial sequence number.
  • SYN-ACK: the server acknowledges the client's sequence number and sends its own.
  • ACK: the client acknowledges the server's sequence number, and the connection is established.
  • The handshake confirms both sides can communicate and initializes the sequence numbers used for tracking.
  • The cost is a full round trip before useful data can be sent, which matters on high-latency paths.
  • Systems reduce that cost with connection reuse, TLS 1.3, TCP Fast Open in limited settings, or QUIC.
Client sends SYN with its initial sequence number→Server replies SYN-ACK with its own sequence number and an acknowledgment→Client sends ACK→Connection established; application data can flow

03Reliable delivery and retransmission

  • TCP numbers bytes, not packets, so the receiver can tell exactly what it has and what is missing.
  • The receiver acknowledges the next byte it expects, not necessarily every segment it received.
  • If an acknowledgment does not arrive, or a gap appears in the sequence, the sender retransmits the missing data.
  • Duplicate segments are detected by sequence number and discarded or acknowledged again.
  • The receiver buffers out-of-order data and reconstructs the original stream once the gap is filled.
  • Applications therefore do not implement packet-loss recovery themselves; TCP handles it underneath.
  • Retransmission costs latency: the data is correct in the end, but the receiver waits for it.
This is reliability at the byte-stream level. It says nothing about whether the server actually performed the business operation.

04Ordered delivery and head-of-line blocking

  • Packets can take different paths and arrive out of order; TCP uses sequence numbers to reassemble them.
  • The application always sees the bytes in the order they were sent, regardless of arrival order.
  • That is essential for file transfers, database results, and HTTP bodies, where the wrong order means wrong content.
  • The cost is waiting: if one segment is lost, later bytes may already sit in the buffer but cannot be delivered.
  • This is head-of-line blocking at the TCP stream level.
  • For a single logical stream, this behavior is usually exactly what you want — a partial file or half a SQL result is useless.
  • For many independent streams sharing one TCP connection, it means one loss stalls unrelated work.

05Flow control

A fast sender must not overrun a slow receiver, even when the network itself has capacity.

  • The receiver advertises a receive window: how much more data its buffer can accept.
  • The sender limits unacknowledged data in flight to that window, so it cannot outrun the application reading it.
  • A fast consumer advertises a larger window and lets the sender send more.
  • A receiver falling behind advertises a smaller window, which slows the sender down.
  • If the window reaches zero, the sender stops and probes until the receiver opens space again.
  • Flow control protects the receiver; it says nothing about congestion in the network.

06Congestion control

  • Routers have finite queues; if everyone sends at full speed, queues fill and packets are dropped.
  • TCP maintains a congestion window that limits unacknowledged data in flight, independent of the receive window.
  • When the network looks healthy, TCP increases the window to probe for more capacity.
  • When it detects congestion — typically packet loss, or signals such as ECN — it reduces the sending rate.
  • The exact behavior depends on the algorithm: Reno, CUBIC, and BBR respond differently.
  • The goal is to adapt continuously rather than overwhelm the path.
  • Flow control protects the receiver and congestion control protects the network; TCP applies the smaller of the two limits.

07A byte stream, not messages

  • TCP delivers a stream of bytes and does not remember where one application write ended and the next began.
  • If an application writes three messages, the receiver may read one chunk, three chunks, or several partial chunks.
  • The order is preserved, but message boundaries are not.
  • The application protocol must define framing: a length prefix, a delimiter, or a self-describing format.
  • Getting this wrong produces bugs that appear only under load or when messages coalesce.
  • UDP preserves boundaries by contrast: one send is one datagram.
A common bug is assuming one recv() equals one message. It equals whatever bytes happen to be available.

08What TCP does not guarantee

  • TCP does not guarantee that a business operation succeeded; it only guarantees ordered bytes while the connection is healthy.
  • If the server commits a transaction but the connection breaks before the response arrives, the client still does not know the outcome.
  • That is why real systems still need timeouts, retries, idempotency keys, and duplicate handling.
  • A graceful close uses FIN packets: each side signals it has finished sending.
  • An abrupt close uses RST, which tears the connection down immediately and can discard buffered data.
  • Neither close tells you whether the operation committed — only that the transport conversation ended.
  • Applications need explicit success responses and safe state transitions to recover.

09UDP: connectionless datagrams

  • UDP (User Datagram Protocol) is connectionless: no handshake, no connection state, no setup round trip.
  • The sender creates a datagram and sends it to the destination IP and port immediately.
  • If a packet is lost, UDP does not retransmit; if packets arrive out of order, UDP does not reorder them.
  • If the receiver cannot keep up, UDP provides no flow control and will happily let datagrams be dropped.
  • What UDP does provide: ports, datagram boundaries, length, and a checksum for corruption detection.
  • The UDP checksum is mandatory in IPv6 and optional in IPv4, though commonly used.
  • The UDP header is 8 bytes, while the base TCP header is 20 bytes before options.
  • Each datagram is independent, which keeps the protocol small and the latency low.

10Application-level reliability over UDP

  • UDP does not make reliability impossible; it makes reliability the application's job.
  • Common building blocks: sequence numbers to detect loss and reordering, and timestamps to discard stale data.
  • Important messages may get application-level acknowledgments and selective retransmission.
  • Media streams often use forward error correction so a lost packet can be reconstructed without a round trip.
  • Rate control prevents the sender from flooding a path that cannot carry the load.
  • Encryption is added separately through DTLS, SRTP, or QUIC.
  • Or the application adopts a higher-level protocol such as QUIC, which supplies these pieces for it.

11QUIC and HTTP/3

  • QUIC runs on UDP and adds reliable delivery, retransmission, congestion control, and flow control in user space.
  • It integrates TLS 1.3, so transport and security setup happen together instead of as two sequential handshakes.
  • It supports independent streams: a lost packet only blocks the stream it belonged to, not the whole connection.
  • It identifies connections by a connection ID, so a session can survive a network change such as Wi-Fi to cellular.
  • Because QUIC is implemented above UDP, it can evolve without waiting for operating-system TCP stacks to change.
  • HTTP/3 is HTTP over QUIC, with the same request semantics as HTTP/1.1 and HTTP/2.
  • Caveats: some networks block or throttle UDP, so clients and servers keep a TCP-based HTTP/2 fallback.
  • 0-RTT resumption can send data immediately but is replayable, so it should be limited to safe requests.

12Choosing between TCP, UDP, and QUIC

  • Choose TCP when every byte matters and must be processed in order, or when the protocol is already stream-based.
  • TCP is also the safer default through firewalls, proxies, and corporate networks that understand it well.
  • Typical TCP cases: HTTP/1.1 and HTTP/2, SSH, PostgreSQL, MySQL, SMTP, and standard gRPC.
  • Choose UDP when fresh data beats complete old data, or the application can repair loss itself.
  • UDP also fits when you need datagram boundaries or an existing UDP-based protocol.
  • Typical UDP cases: DNS queries, real-time voice and video, game state, WebRTC media, and local discovery.
  • Choose QUIC/HTTP/3 when you want encrypted HTTP with faster setup, independent streams, or mobile connection migration.
  • The practical requirement is that UDP on port 443 works and you can fall back to TCP-based HTTP.

13Real-world examples

  • Web and APIs: HTTP/1.1 and HTTP/2 over TCP with TLS; HTTP/3 over QUIC, with a fallback when UDP is blocked.
  • Databases: TCP, because queries, results, and replication streams need reliable ordered bytes.
  • DNS: UDP for small queries because it is simple and fast, with TCP for large answers and zone transfers; encrypted variants include DoT, DoH, and DoQ.
  • Real-time media: UDP with jitter buffers, packet-loss concealment, forward error correction, and rate control.
  • Online games: frequent UDP state updates where the next update supersedes a lost one, with a reliable channel for purchases and inventory.
  • AI systems: TCP-based HTTPS for request correctness and compatibility; streaming tokens over chunked HTTP, SSE, WebSockets, gRPC streaming, or HTTP/3.
  • The same question applies everywhere: what should this system do when data is late or lost?

14What to remember

  • TCP and UDP both sit on IP and use ports; the difference is the guarantees, not the layer.
  • TCP establishes state with a three-way handshake, then provides a reliable, ordered byte stream using sequence numbers and acknowledgments.
  • Flow control protects the receiver; congestion control protects the network.
  • TCP does not preserve message boundaries, so the application protocol must define framing.
  • TCP does not prove a business operation succeeded; timeouts, retries, and idempotency are still required.
  • UDP sends independent datagrams with no handshake, no retransmission, no ordering, and no flow control.
  • QUIC runs over UDP and adds reliability, congestion control, encryption, and independent streams, which is what powers HTTP/3.
  • Ask not which protocol is faster, but what the application should do when data is late, lost, duplicated, reordered, or processed twice.

↔Trade-offs to say out loud

  • TCP reliability guarantees correct ordered bytes but costs handshake round trips and waits for retransmissions.
  • UDP minimizes latency and overhead but pushes loss detection, ordering, and rate control onto the application.
  • TCP ordering simplifies application logic but creates head-of-line blocking when one segment is lost.
  • QUIC independent streams remove TCP-level blocking but add UDP dependency and a fallback path to operate.
  • Connection reuse amortizes handshake cost but concentrates risk: one broken connection affects many requests.
  • Large congestion windows improve throughput on a healthy path but cause sharp backoff and queue buildup when the path degrades.
  • Application-level reliability over UDP can be tuned precisely but reimplements decades of transport engineering.
  • Encrypting at the transport layer protects metadata and payload but prevents middleboxes from inspecting or optimizing traffic.
  • 0-RTT QUIC resumption reduces latency but allows replay, so it is limited to safe operations.

?Interview questions

Answer aloud before opening the outline.

1. What is the fundamental difference between TCP and UDP?

TCP is connection-oriented and guarantees reliable, ordered byte delivery using handshakes, sequence numbers, acknowledgments, and retransmission. UDP is connectionless and guarantees nothing beyond ports, datagram boundaries, length, and a checksum. TCP trades latency and overhead for correctness; UDP trades guarantees for simplicity and speed.

2. Walk through the TCP three-way handshake.

The client sends SYN with its initial sequence number. The server replies SYN-ACK, acknowledging that number and sending its own. The client sends ACK, and the connection is established. It takes one full round trip before application data can flow and initializes the sequence numbers used for reliability.

3. How does TCP detect and recover from lost data?

Every byte has a sequence number, and the receiver acknowledges the next byte it expects. A missing acknowledgment or a gap in the sequence tells the sender to retransmit. The receiver buffers out-of-order data and delivers the complete, ordered stream once the gap is filled.

4. What is TCP head-of-line blocking?

Because TCP delivers one ordered byte stream, data that arrived after a lost segment cannot be given to the application until that segment is retransmitted. Everything behind the gap waits, even if it belongs to an unrelated request sharing the connection.

5. Flow control versus congestion control?

Flow control protects the receiver: the receiver advertises a receive window and the sender limits unacknowledged data to it. Congestion control protects the network: the sender maintains a congestion window and grows or shrinks it based on loss or congestion signals. TCP sends at the smaller of the two limits.

6. Does TCP preserve message boundaries?

No. TCP is a byte stream, so three writes can arrive as one read or several partial reads. The application protocol must frame messages with a length prefix, a delimiter, or a structured format.

7. If TCP is reliable, why do we still need retries and idempotency?

TCP only guarantees bytes while the connection is healthy. If the server commits a transaction and the connection breaks before the response, the client cannot know the outcome. Retries, timeouts, and idempotency keys handle that uncertainty at the application level.

8. What does UDP actually guarantee?

Ports to reach the right process, preserved datagram boundaries, a length field, and a checksum for corruption detection. It does not guarantee delivery, ordering, or flow control.

9. When would you deliberately choose UDP?

When stale data is worse than missing data, such as live voice, video, or game state, or when the application implements its own acknowledgments, retransmission, and rate control. DNS also uses UDP for small queries because it avoids a handshake.

10. How do you build reliability on top of UDP?

Add sequence numbers, timestamps, application-level acknowledgments, selective retransmission for important messages, forward error correction for media, rate control, and encryption. Or use QUIC, which packages these mechanisms.

11. What does QUIC add on top of UDP?

Reliable delivery, retransmission, congestion and flow control, TLS 1.3 encryption, independent streams, and connection migration. It gives HTTP/3 TCP-like reliability without TCP's cross-stream head-of-line blocking.

12. Why doesn't everyone use QUIC/HTTP/3?

It needs UDP to work on the path, and some networks block or throttle UDP. It also adds operational complexity and requires a TCP fallback. Many systems therefore support HTTP/2 and HTTP/3 together and measure which performs better.

13. How does QUIC survive a network change?

QUIC identifies a connection by a connection ID rather than the IP address and port tuple, so a phone moving from Wi-Fi to cellular can continue the same session without a new handshake.

14. Which protocol would you use for a payment API and for a voice call?

A payment API uses TCP-based HTTPS because every byte and the exact result matter, and idempotency keys make retries safe. A voice call uses UDP because a late audio packet is useless, with jitter buffering and forward error correction to keep the conversation usable.

!Traps

  • Saying TCP guarantees message boundaries when it only guarantees an ordered byte stream.
  • Claiming TCP reliability means the business operation completed, ignoring the ambiguous timeout case.
  • Confusing flow control with congestion control, or naming only one when asked how TCP adapts.
  • Assuming a lost packet blocks only one HTTP/2 request, when it stalls every stream on that TCP connection.
  • Choosing UDP for convenience and then discovering the application has to rebuild ordering and retransmission badly.
  • Assuming QUIC is always faster, when UDP may be blocked or throttled on the path.
  • Forgetting that UDP datagrams can be reordered or duplicated, not just dropped.
  • Treating a graceful FIN close as proof that the request succeeded.
