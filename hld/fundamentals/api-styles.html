In one lineAn API style is the pattern a communication follows — resource-based, query-based, action-based, streaming, or event-driven — and real systems pick a different one for each communication path.
API style
The pattern of communication: how the client asks, how data is structured, who initiates, and whether the interaction is one-shot or continuous.
REST
Representational State Transfer: resources identified by URLs, manipulated with standard HTTP methods, usually stateless.
Idempotent
A request that has the same effect whether it is sent once or many times; GET, PUT, and DELETE are idempotent, POST is not by default.
GraphQL
A query language and schema where the client specifies exactly which fields it needs and gets back that shape.
RPC
Remote Procedure Call: the API is organized around actions or function calls rather than resources.
gRPC
A modern RPC framework using Protobuf contracts, generated client and server code, and HTTP/2 multiplexing and streaming.
Protocol Buffers
A compact binary serialization format where both sides know the field names from a shared contract, so only field numbers and values travel.
WebSocket
A persistent, full-duplex connection upgraded from HTTP, letting either side send messages at any time.
Webhook
An HTTP callback: a provider POSTs an event to a URL the consumer registered, reversing the usual direction of initiation.
SSE
Server-Sent Events: a one-way stream of updates from server to browser over a normal HTTP connection, consumed with EventSource.

01What is an API style?

An API defines how two pieces of software communicate. The style defines the pattern that communication follows.

  • How does the client ask? Does it request a resource, call a function, or subscribe to a stream?
  • How is data structured? Text JSON, XML, or a compact binary format?
  • What is the interaction model? One-shot request-response, or continuous two-way traffic?
  • Who initiates? Does the client always start, or can the server reach out when something happens?
  • The answers decide latency, coupling, caching, tooling, and operational cost more than any single library choice.
  • Most real systems mix styles; the design question is per communication path, not per company.
Identify the communication shape→Pick the style that matches it→Define the contract→Add auth, limits, and observability→Revisit when traffic or clients change

02REST: resources and HTTP methods

REST stands for Representational State Transfer. Instead of thinking in functions or actions, you think in resources: users, orders, products.

  • Each resource is identified by a URL, such as /users/123 or /orders.
  • Standard HTTP methods carry the meaning: GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes.
  • Safe means the request does not change server state; GET is safe.
  • Idempotent means repeating the request has the same effect as sending it once; GET, PUT, and DELETE are idempotent.
  • PATCH idempotency depends on the patch: setting a field is idempotent, incrementing a counter is not.
  • The path names the thing; the method names the action. That separation is what makes the API predictable.

03REST statelessness and why it won

  • REST APIs are typically stateless: every request carries everything needed, including the auth token.
  • The server does not rely on context from a previous request, so any instance behind a load balancer can serve any call.
  • That is what makes REST trivial to scale horizontally and to retry after a failed instance.
  • REST maps directly onto HTTP, so status codes, cache headers, proxies, and existing tooling work out of the box.
  • It is simple to understand, easy to debug with curl, and supported in every language and platform.
  • Strict REST per Roy Fielding also includes HATEOAS, where responses carry links to the next available actions.
  • Most APIs called RESTful skip HATEOAS: they use resource URLs, HTTP methods, and stateless requests, documented with OpenAPI.
Stateless does not mean no state exists; it means the server does not need per-client conversational state to process a request. State lives in the token, the database, or the cache.

04REST limitations: over-fetching and under-fetching

  • Over-fetching: a screen that shows only a name still receives the full user object.
  • Under-fetching: one screen needs several endpoints, so the client makes multiple round trips.
  • A profile page might need /users/123, /users/123/profile, and /users/123/orders?limit=5.
  • Each round trip adds latency, which hurts most on mobile and high-latency networks.
  • Clients compensate with bespoke endpoints, BFF layers, or response expansion parameters, all of which add API surface.
  • REST also has no standard way for the server to push updates, which is why WebSockets and SSE exist.

05GraphQL: the client asks for exactly what it needs

GraphQL reverses control: instead of the server deciding the response shape, the client specifies the fields it wants.

  • The client sends a query naming the fields it needs, and the server returns data in the same shape.
  • A single query can fetch a user, their profile picture, and five recent orders in one round trip.
  • This removes both over-fetching and under-fetching for screens with varied data needs.
  • The API is built around a strongly defined schema describing available types, fields, and operations.
  • Clients can introspect the schema to discover what they can request, which enables strong tooling and codegen.
  • GraphQL has queries for reads, mutations for writes, and subscriptions for live updates.
  • It shines when a mobile client wants a lightweight response and a desktop client wants much more from the same API.
query {
  user(id: 123) {
    name
    profilePicture
    orders(limit: 5) {
      id
      total
    }
  }
}

06GraphQL trade-offs

  • Arbitrary query shapes: the server must handle whatever the client sends, including deeply nested queries like friends { friends { friends { orders } } }.
  • Teams add query depth limits, complexity scoring, and timeouts to stop one query from exhausting the backend.
  • N+1 problem: a naive resolver runs one query for a list and then one per item; 100 users become 101 queries.
  • Batching tools such as DataLoader collapse those into fewer queries, at the cost of extra machinery.
  • Caching is harder: REST gets per-URL HTTP and CDN caching for free; GraphQL usually posts every query to one endpoint.
  • Persisted queries and response-level caching can recover some of that, but they are extra work.
  • Authorization becomes per-field rather than per-endpoint, which is more expressive but easier to get wrong.
  • GraphQL is still text JSON over HTTP with the client initiating each request, so it does not solve server push.

07RPC: actions instead of resources

  • RPC stands for Remote Procedure Call: calling a function on another server should look like calling a local function.
  • The API is organized around actions, not resources: createOrder rather than POST /orders.
  • The design question changes from "what resource am I working with?" to "what operation do I want performed?"
  • The client sends the function name and parameters; the server executes and returns a result.
  • RPC is not tied to one protocol or format: JSON-RPC sends JSON over HTTP, while gRPC uses Protobuf over HTTP/2.
  • RPC feels natural for internal service calls, command-style operations, and workflows that do not map cleanly to CRUD.
  • It tends to produce tighter coupling because every operation is a named method in the contract.

08gRPC: contracts, codegen, and HTTP/2

gRPC is a modern RPC framework designed for fast, efficient communication between services.

  • The API is defined in a .proto file, for example a UserService with a GetUser operation.
  • The definition acts as a contract: it names operations, request messages, and response messages.
  • gRPC generates client stubs and server interfaces in many languages, so Java can call Go or Python through the same contract.
  • It commonly uses Protocol Buffers, a compact binary format, instead of text JSON.
  • Protobuf does not repeat field names in every message; both sides know them from the contract, so only field numbers and values travel.
  • Smaller payloads and faster serialization make gRPC attractive for high-volume internal traffic.
  • gRPC runs on HTTP/2, which gives multiplexing (many calls share one connection) and streaming in both directions.
  • It also supports deadlines, so a caller can state how long it is willing to wait and the server can stop work early.
Write the .proto contract→Generate client stubs and server interfaces→Implement the server→Client calls a stub method→HTTP/2 carries binary Protobuf messages→Deadline or error returns a status

09gRPC trade-offs

  • Binary messages are harder to inspect by hand than JSON; you need tooling to decode them.
  • Browsers cannot call gRPC directly, so web clients usually need gRPC-Web plus a proxy.
  • Both sides usually need access to the same Protobuf definitions, which adds a build and release dependency.
  • Schema evolution is possible with field numbers, but removing or reusing them breaks compatibility.
  • Debugging stretches from the client through a proxy and HTTP/2 framing, which is more complex than curl against REST.
  • Load balancers and proxies must understand HTTP/2 and long-lived streams; some infrastructure does not.
  • The common pattern is REST or GraphQL for external clients and gRPC between internal services.

10WebSockets: two-way persistent connections

  • A WebSocket keeps one connection open so the client and server can send messages at any time.
  • It begins as an HTTP request with Upgrade: websocket; the server replies 101 Switching Protocols.
  • The same TCP connection then carries small WebSocket frames instead of repeated HTTP headers.
  • This is full-duplex: the server can push while the client is still sending.
  • It removes polling entirely, so updates arrive as soon as they exist.
  • The cost is operational: long-lived connections, reconnects, heartbeats, and routing messages across servers.
  • Good fits are chat, live notifications, multiplayer games, collaborative editing, and real-time dashboards.

11Webhooks: server-initiated event delivery

  • A webhook is an HTTP callback: the consumer registers a URL, and the provider POSTs an event when something happens.
  • It reverses initiation: the consumer no longer polls the provider for changes.
  • The request carries the event type, a unique event ID, a timestamp, a payload, and usually a signature header.
  • Webhooks are asynchronous; the provider does not wait for the consumer to finish business processing.
  • Delivery is typically at-least-once, so consumers must deduplicate by event ID and verify signatures.
  • Common uses are payment events, source-control updates, email delivery notices, and CI/CD triggers.
  • They suit discrete events where a permanent connection would be wasteful.

12Other styles you will see

  • SSE lets a server stream one-way updates to a browser over plain HTTP, consumed with EventSource.
  • SSE is simpler than WebSockets when only the server pushes: live notifications, progress bars, streamed LLM tokens.
  • If the client also sends frequent messages, use WebSockets instead.
  • Message-driven APIs publish events to a broker such as Kafka, and consumers process them independently.
  • They fit when the producer must not wait for every consumer, such as order events, notifications, and audit logs.
  • Their cost is harder debugging, ordering, and schema evolution across independent consumers.
  • SOAP is an older XML protocol with formal WSDL contracts; it persists in banking, insurance, healthcare, and government integrations.
  • Use SOAP only when an integration partner requires it.

13Using API styles together

In real systems these styles are not mutually exclusive. An e-commerce application typically uses several at once.

  • The frontend talks to the backend over REST or GraphQL through an API gateway.
  • Behind the gateway, internal services use gRPC for efficient, strongly typed calls.
  • A payment provider notifies the backend of a successful charge with a webhook.
  • Live chat or order tracking reaches the client over a WebSocket.
  • Fan-out events that many services must react to go through a message broker.
  • The right question is not which style the whole system should use, but which style fits each communication path.
  • Mixing styles adds gateways, contracts, and monitoring; the benefit must justify that operational surface.

↔Trade-offs to say out loud

  • REST is simple, cacheable, and universal, but it over-fetches, under-fetches, and has no built-in push.
  • GraphQL removes over- and under-fetching and gives clients one flexible endpoint, but adds query-cost control, N+1 risk, and harder caching.
  • RPC maps naturally to actions and internal workflows, but organizes the API around verbs and tends to couple client and server more tightly.
  • gRPC gives compact payloads, generated code, streaming, and deadlines, but is hard to inspect and unusable from browsers without a proxy.
  • WebSockets give the lowest-latency two-way communication, but require connection state, heartbeats, pub/sub routing, and draining on deploy.
  • Webhooks avoid polling and decouple event producers from consumers, but delivery is at-least-once, unordered, and needs signatures and retries.
  • SSE is far simpler than WebSockets for server push, but it is one-way and limited to browser-friendly HTTP semantics.
  • Message-driven APIs decouple producers from many consumers and absorb spikes, but make debugging, ordering, and schema changes harder.
  • SOAP offers rigid formal contracts and mature enterprise tooling, but is verbose, XML-heavy, and slow to evolve.
  • Using several styles matches each path well, but multiplies contracts, gateways, and skills the team must operate.

?Interview questions

Answer aloud before opening the outline.

1. What is an API style, and what does it decide?

It is the pattern communication follows: how the client asks for data, how data is structured, whether the interaction is one-shot or continuous, and who initiates. Those choices drive latency, coupling, caching, and operational cost.

2. When would you choose REST over GraphQL?

When a small set of stable endpoints covers the use case and you want simple, cacheable, universally supported APIs. REST is easier to secure, cache at the CDN, and operate. GraphQL pays off when clients need many different nested views of the same data.

3. What problems does GraphQL solve, and what does it create?

It solves over-fetching and under-fetching by letting the client choose fields in one query. It creates query-cost risk, the N+1 resolver problem, per-field authorization, and harder HTTP caching.

4. How do you protect a GraphQL server from expensive queries?

Limit query depth and complexity, set timeouts, cap page sizes, and reject introspection or arbitrary queries in production where appropriate. Persisted queries and cost scoring based on estimated work also help.

5. What does idempotent mean, and why does it matter for API design?

Repeating the request has the same effect as sending it once. It matters because networks fail and clients retry: GET, PUT, and DELETE can be retried safely, while a naive POST can create duplicate orders or charges.

6. Explain RPC versus REST.

REST models resources and uses HTTP methods on URLs; RPC models actions and calls named operations with parameters. REST is a better fit for public resource APIs, RPC for command-style internal calls and workflows.

7. Why is gRPC fast?

It uses Protobuf, a compact binary format that omits repeated field names because both sides know the contract, plus HTTP/2 multiplexing so many calls share one connection. It also supports streaming and deadlines.

8. What are the main drawbacks of gRPC?

Binary payloads are hard to inspect, browsers need gRPC-Web and a proxy, and both sides need the same Protobuf definitions. Proxies and load balancers must also handle HTTP/2 and long-lived streams.

9. When are WebSockets the wrong choice?

When normal request-response is enough, updates are infrequent enough for polling, or only the server pushes and SSE would do. WebSockets add connection state, reconnects, heartbeats, and cross-server routing.

10. How is a webhook different from a WebSocket?

A webhook is a one-shot HTTP POST from a provider to a consumer URL when an event occurs. A WebSocket is a persistent two-way connection between a client and a server. Webhooks are event notifications; WebSockets are a live channel.

11. When would you use SSE instead of WebSockets?

When only the server needs to push and the client does not send frequent messages: notifications, progress updates, or streamed tokens. SSE runs over ordinary HTTP, reconnects automatically, and is much simpler to operate.

12. Why use message-driven APIs instead of direct service calls?

They decouple the producer from every consumer, absorb traffic spikes, and let consumers scale and fail independently. The cost is eventual consistency, duplicate handling, ordering concerns, and harder tracing.

13. Design the API styles for an e-commerce system.

Use REST or GraphQL from clients to an API gateway, gRPC between internal services, webhooks from the payment provider, WebSockets for live chat or tracking, and a broker for events with many consumers. Choose per path, not one style everywhere.

14. What is the trade-off of using several API styles in one system?

Each path gets the right semantics and performance, but you now run multiple contracts, gateways, auth models, and debugging tools. That overhead is worth it when the paths genuinely differ, not when a single style would do.

!Traps

  • Choosing one API style for the entire system instead of per communication path.
  • Calling an API RESTful while using POST for every operation and putting the action in the URL.
  • Assuming GraphQL eliminates performance problems; unbounded query depth and N+1 resolvers move the cost to the server.
  • Treating POST as safe to retry, which creates duplicate orders or payments.
  • Using WebSockets for one-way notifications where SSE or plain HTTP would be simpler.
  • Building webhooks without signature verification, deduplication, or a fast acknowledgment.
  • Adopting gRPC for browser clients without planning for gRPC-Web and a proxy.
  • Forgetting that webhooks and message-driven APIs are asynchronous, then designing the UI as if the result were immediate.
