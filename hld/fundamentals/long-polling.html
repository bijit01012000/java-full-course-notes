Short polling
The client sends an HTTP request on a fixed interval and the server answers immediately, usually with an empty response.
Long polling
The client sends an HTTP request and the server defers the response until new data exists or a hold timeout expires.
Hold timeout
The maximum time the server keeps a request pending before returning an empty response so the client can reconnect.
Cursor
A monotonically increasing event ID or sequence number the client sends so the server can replay everything it missed.
Waiter
The server-side registration that ties a pending request to a user or topic until an event or timeout completes it.
Reconnect storm
A mass failure causing many clients to retry at once and overload the system while it is still recovering.
Exponential backoff with jitter
Delays that double after each consecutive failure and are randomized so retries spread out instead of clustering.
Idle timeout
An infrastructure limit (proxy, load balancer, CDN) that closes connections believed to be inactive.

01The problem with regular polling

Start from a notification system: the client wants to learn about a new notification soon after it is created. The naive design asks the server every few seconds whether anything new exists.

  • Regular polling, also called short polling, repeats an identical request on a fixed interval and gets an immediate answer, often empty.
  • Most requests can be useless: at 100,000 clients polling every 5 seconds you already run about 20,000 requests per second even when nothing happened.
  • There is always residual delay: polling every 10 seconds means an event can sit unseen for almost 10 seconds.
  • The interval forces a single knob to trade latency against request volume, and you cannot turn both down at once.
  • The server also does constant work while idle, which makes capacity planning driven by poll frequency rather than by real load.
The core tension is not the polling itself; it is that the interval is a guess about when events arrive.

02What long polling is

  • The client still sends an ordinary HTTP GET, usually carrying its cursor such as ?after=43.
  • If newer events already exist, the server answers immediately — no waiting.
  • If nothing is newer, the server does not answer yet; it keeps the request pending until an event arrives or the timeout fires.
  • On response, the client processes the payload, advances its cursor, and opens the next request right away.
  • Long polling is therefore a chain of normal requests, not one permanent connection; each link may idle before returning.
  • Because it is plain HTTP, existing auth, TLS, proxies, and caching semantics still apply.

03The three phases of one request

  • Check existing data: read reliable storage for events newer than the client's cursor before considering waiting.
  • Wait for new data: park the request and resume it on an event from an event bus, queue, database notification, or in-process signal.
  • Respond and reconnect: return the events, or an empty response on timeout, then let the client update its cursor and re-issue.
  • The wait must be event-driven, not a spin loop that polls storage over and over inside the handler.
  • Registration and deregistration of waiters must be cleaned up when the client disconnects mid-wait.
Client sends GET with cursor→Server authenticates and reads events after cursor→Events found -> respond immediately→No events -> register waiter and suspend request→Event arrives or timeout fires -> respond→Client advances cursor and reconnects

04Choosing the hold timeout

A server should never hold a request forever: proxies, load balancers, servers, and client libraries all impose limits. So the hold is a fixed, bounded period.

  • A hold in the range of 20–60 seconds is a common starting point, but the right value depends on the infrastructure in the path.
  • Too short and clients reconnect constantly, which recreates the empty-request problem long polling was meant to remove.
  • Too long and you risk infrastructure cuts, and dead connections stay undetected longer because a dead connection looks like a quiet one.
  • The hold timeout should be slightly shorter than every intermediary timeout so the server ends requests cleanly on its own terms.
  • The client-side request timeout should be longer than the server hold, otherwise the client cancels healthy requests before they can answer.

05Server-side architecture

  • 10,000 long-polling clients can mean close to 10,000 open requests parked inside the application at once.
  • Thread-per-request servers park one dedicated thread per waiting request, wasting memory and exhausting thread pools under load.
  • Async, event-driven servers keep a waiting request off the OS thread; Node.js, Go goroutines, async Python, reactive JVM or virtual threads all fit.
  • Even then each pending request costs memory, a socket, a file descriptor, and connection-management overhead.
  • Long polling replaces many empty requests with many open requests — cheaper, not free.
  • Track open-waiter counts and per-connection memory as first-class capacity metrics alongside CPU.

Handler responsibilities

  • Authenticate and authorize before parking the request.
  • Read events after the cursor from storage, not from memory that may be lost.
  • Register the waiter keyed by user or topic when nothing is available.
  • Complete the waiter when an event for that key arrives or the timeout fires.
  • Remove the waiter on client disconnect so it cannot leak into the next event broadcast.

06Scaling across multiple servers

With several application servers behind a load balancer, the pending request for a user lives on exactly one of them. A backend service that produces a new event has no idea which one.

  • This is a distributed routing problem, not a capacity problem; more servers make it worse if routing is unsolved.
  • The standard fix is shared messaging infrastructure: backend services publish to a broker such as Redis Pub/Sub or Kafka.
  • Every application server subscribes, and only the server holding that user's pending request answers it.
  • Producers stay unaware of HTTP delivery and connection placement, so app servers can be added without changing producers.
  • The event store is the source of truth for correctness; the broker is only a low-latency wake-up signal.
  • Pub/sub messages can be missed by a server that was not subscribed at that instant, so the next request must still recover from storage.
Backend service publishes event to broker→All long-poll servers receive the event→Server holding the waiter for that user responds→Client reconnects with the new cursor→Storage replays anything the broker dropped

07Avoiding missed events with cursors

  • The client is never continuously connected: there is always a small window between receiving a response and sending the next request.
  • An event that lands in that window is lost if the server only ever delivers to currently open requests.
  • Every event gets a sequence number, event ID, or timestamp; the client sends the last one it processed and asks for everything after it.
  • Because the server checks storage before waiting, events created during reconnection are still returned.
  • The same cursor doubles as crash recovery: reconnect anywhere and resume from the last known event ID.
  • Prefer a monotonic event ID over a timestamp — timestamps collide, can move backwards across machines, and create ambiguous edges.

08Aligning timeouts across the path

  • A client expecting a 30-second hold behind a 20-second idle timeout sees failures while the application is perfectly healthy.
  • Every hop matters: reverse proxies, API gateways, CDNs, TLS terminators, and the client's own HTTP library.
  • The usual rule is server hold < proxy idle timeout < client timeout, with a comfortable margin at each step.
  • Intermediaries that buffer responses can hold the reply even after the server writes it, which silently adds latency.
  • Document the timeout budget in one place so a proxy config change cannot quietly break real-time delivery.

09Failure and reconnection

  • Because transports are ordinary HTTP requests, a failed request is usually handled by simply retrying.
  • A controlled retry policy is mandatory: a cluster-wide failure can send hundreds of thousands of clients back at once.
  • Use exponential backoff with a cap, and jitter so clients that failed together do not retry together.
  • An empty timeout response is not a failure — reconnect immediately instead of backing off.
  • Important state such as the client's position belongs in reliable storage so recovery works on any server, not just the one that failed.
  • A complete client handles four outcomes: data, empty timeout, error with backoff, and cancellation on shutdown.

Reference client policy

  • Client timeout of roughly 35 seconds for a 30-second server hold.
  • Backoff starting near 1 second and doubling per consecutive failure up to a cap, often around 30 seconds.
  • Backoff resets after any successful response, including an empty timeout response.

10When long polling is the right tool

  • It fits when you need near-real-time updates but want to stay inside the standard HTTP request-response model.
  • Strong fits: notifications, job status updates, and asynchronous results such as a rendered report or video.
  • It gives lower latency and fewer wasted requests than short polling without a persistent streaming protocol.
  • It is a poor fit for a continuous high-rate feed, where one open connection carrying many events (SSE) is cheaper.
  • It is a poor fit when the client also needs to push frequently — that is a WebSocket-shaped problem.
  • It is a poor fit for very large numbers of idle clients on thread-per-request infrastructure.

↔Trade-offs to say out loud

  • Lower latency than fixed-interval polling, at the cost of holding connections open instead of answering instantly.
  • Standard HTTP semantics (auth, proxies, retries) are preserved, but each update still needs a full request/response round trip.
  • Fewer wasted requests when events are rare, but the same number of reconnects when events are frequent.
  • Async servers handle many waiters without a thread each, but every waiter still costs a socket, a file descriptor, and memory.
  • Adding app servers improves capacity, but requires a shared broker to route events to the server holding the waiter.
  • A long hold timeout reduces reconnect churn but lengthens failure detection and risks infrastructure cuts.
  • A broker for wake-ups reduces delivery latency, but correctness still depends on the durable event store behind it.
  • Backoff with jitter protects the system during recovery, but slows down users who genuinely want to reconnect.

?Interview questions

Answer aloud before opening the outline.

1. What problem does long polling solve?

Short polling forces a trade-off between update latency and wasted empty requests. Long polling breaks that link: the server parks the request and answers only when data exists or a timeout fires, so updates arrive soon after they happen without polling on a fixed interval.

2. Walk through the lifecycle of one long polling request.

The client sends a GET with its cursor. The server reads storage for newer events; if any exist it answers immediately. Otherwise it registers a waiter and suspends the request. An event or the hold timeout completes the request, and the client updates its cursor and immediately opens the next one.

3. How do you pick the hold timeout?

Set it long enough that clients are not reconnecting constantly and short enough to stay below every intermediary idle timeout. Roughly 20–60 seconds is a common range. The server should also finish before any proxy cuts the connection so it can return a clean empty response.

4. Why does long polling need a cursor?

The client is disconnected between responses, so an event created in that gap would be invisible to a server that only delivers to open requests. A cursor lets the server check storage for everything after the last processed event, which also makes recovery on a different server possible.

5. Why is an event ID better than a timestamp as the cursor?

Timestamps collide at the same granularity, can move backwards across machines with clock skew, and create ambiguous boundary cases when several events share a millisecond. A monotonically increasing sequence number gives a total order and a clean 'give me everything after X'.

6. How does the server scale beyond one machine?

Multiple app servers sit behind a load balancer, and a shared broker such as Redis Pub/Sub or Kafka fans each event out to all of them. Only the server holding that user's waiter responds. The durable event store remains the source of truth, because broker messages can be missed.

7. What breaks first on a thread-per-request server?

Each parked request consumes a thread even while doing nothing, so memory and thread limits are reached long before CPU. Async or event-loop servers with non-blocking handlers avoid this by keeping waiters off OS threads.

8. How do you prevent a reconnect storm?

Clients should retry with exponential backoff and randomized jitter, capped at some ceiling, and reset the backoff after success. Empty timeout responses are normal and should trigger an immediate reconnect rather than a backoff.

9. A client behind a load balancer sees failures although app logs look healthy. What do you check?

Compare the server hold timeout with the idle timeouts of the load balancer, reverse proxy, CDN, and client library. If an intermediary timeout is shorter than the hold, the connection is cut mid-wait and appears as a failure even though the application behaved correctly.

10. When should you choose SSE or WebSockets instead?

If updates are frequent, one long-lived connection carrying many events (SSE) is far cheaper than a reconnect per update. If the client also needs to push messages frequently, use WebSockets. Long polling wins when you want near-real-time delivery with minimal protocol change.

11. What state must not live only on one app server?

The client's position in the event stream. Storing it in durable storage keyed by cursor lets the client resume on any server after a failure, instead of being pinned to the instance that happened to hold the previous request.

12. Is long polling cheaper than short polling?

Usually yes in request volume, since idle clients generate one pending request instead of repeated empty ones. But it shifts cost to open connections, sockets, and memory per waiter, so capacity planning changes shape rather than disappearing.

!Traps

  • Implementing the wait as a loop that re-queries storage instead of suspending the request until an event arrives.
  • Holding requests longer than a proxy or load balancer idle timeout, then blaming the application for the failures.
  • Setting the client request timeout shorter than the server hold timeout, so healthy requests are cancelled.
  • Delivering events only to currently open requests without checking durable storage for the gap between requests.
  • Using timestamps as cursors and hitting collisions or clock skew.
  • Retrying instantly on failure and triggering a reconnect storm during recovery.
  • Assuming the broker is the source of truth for event delivery.
