In one lineGood logging is not more logging: it is structured events with consistent fields, honest levels, a correlation ID, and enough context to explain an incident — while keeping secrets out and volume affordable.
Structured logging
Emitting each entry as named fields, usually JSON, so machines can index, filter, and group without regex.
Log level
A severity label (DEBUG, INFO, WARN, ERROR, FATAL) that decides whether an entry is kept and how it is treated.
Log schema
The agreed set of field names and types every service uses, such as timestamp, level, service, and trace_id.
Correlation ID
An identifier generated at the edge and propagated through every service and message so one request can be reconstructed.
Trace ID
The identifier used by distributed tracing, which can double as the correlation ID and links logs to traces.
Redaction
Masking or removing sensitive fields in the logging library before an entry is written.
Asynchronous logging
Buffering entries in memory and writing them from a background thread so logging does not block requests.
Log aggregation
Shipping logs from every host into one central, searchable store with common indexing and retention.
Sampling
Keeping all errors and warnings but only a fraction of high-volume success logs to control cost.
Retention tier
A policy that keeps recent logs in fast storage and moves or deletes older logs based on age and purpose.

01What a good log entry answers

Suppose you are paged because payments are failing. You open the payment service logs and search for errors.

  • Thousands of lines say only that something went wrong, with no order, user, or downstream call identified.
  • The opposite failure is just as bad: logging every cache lookup and health check buries the one error in noise.
  • A useful entry answers what happened, where, to whom, when, and with what outcome.
  • It should let an investigator start work without opening the code or reproducing the request.
  • The practical test: if I saw only this line during an incident, would I understand what happened?
  • Logs are for events and context; counts and trends belong in metrics, and request paths belong in traces.
  • The goal is not maximum volume but maximum signal per line.
Compare Something went wrong with Payment charge failed plus order_id, amount, error_type, and duration_ms as fields.

02Structured logging

  • Unstructured logs mix values into a sentence, so extracting them requires fragile regex rules.
  • A small wording change then breaks every search, dashboard, and alert built on top of it.
  • Structured logging writes each entry as named fields, most commonly JSON.
  • The log system can index those fields directly: filter by service, error type, user, or order.
  • You can group and count errors by field value instead of guessing at message text.
  • Fields stay stable even if the human-readable message is reworded.
  • Structured does not mean verbose: the same facts, just machine-readable.
Emit named fields→Index fields centrally→Filter and group→Alert on a field value

03Consistent field names

  • Structured logs only help if every service uses the same names for the same thing.
  • If one service logs user_id, another userId, and a third uid, every search must know all variants.
  • Teams agree a shared schema for the common fields and enforce it through a shared logging library.
  • Required fields should be set automatically so developers cannot forget them.
  • Optional fields are added when relevant, not filled with placeholders.
  • A shared library also centralizes redaction and formatting, which is where most mistakes happen.
  • Document the schema; a new service should not have to reverse-engineer field names from existing logs.

04Log levels

  • DEBUG is detailed development information: variable values, branches taken, internal steps.
  • INFO is normal, meaningful events: service started, order placed, job finished.
  • WARN is something unexpected that the system handled: a retry that succeeded, a fallback to default.
  • ERROR is a failure that affected an operation: a payment could not be processed.
  • FATAL means the process cannot continue, such as required configuration missing at startup.
  • TRACE is finer than DEBUG, typically method entry and exit, and is rarely used in production.
  • Levels exist so you can keep INFO and above in production and raise one service to DEBUG temporarily.

05Choosing the right level

  • Wrong levels create alert fatigue, which is worse than missing logs.
  • A user typing the wrong password is expected behavior, not a system error; logging it at ERROR inflates the error rate.
  • Alerts built on error counts then fire for things that need no action, and the team learns to ignore them.
  • A useful rule: ask whether someone needs to act.
  • If yes, it is probably ERROR; if unusual but handled, WARN; if part of normal flow, INFO or DEBUG.
  • Log an error at the layer that handles it, not at every layer it passes through.
  • Log level should describe impact, not how surprised the developer was.
Something happened→Does someone need to act?→Yes → ERROR→No → handled but unusual? → WARN→Normal flow → INFO or DEBUG

06Context on every entry

  • A message alone is rarely enough; the surrounding context is what makes it actionable.
  • Static context is the same for every entry: service name, version, environment, host or container.
  • The version is especially useful: if errors start right after a deploy, it isolates the affected build.
  • Request context includes the request ID, user ID, and the main entity being processed, such as an order ID.
  • Static fields are attached when the logger is created; request fields are attached once per request.
  • The developer should only write the message and the few operation-specific fields.
  • Exceptions should include the error type, message, and stack trace — not just a generic database error.
A request-scoped logger context means you attach the order ID once and every subsequent line in that flow carries it automatically.

07Correlation IDs

  • In a distributed system, one request produces log entries in many services.
  • A correlation ID (request ID) is generated when the request enters, typically at the API gateway or edge.
  • Each service passes it to the next through an HTTP header or a message attribute.
  • Every service includes it in every log entry for that request.
  • Searching one ID then reconstructs the full story across services, in order.
  • If distributed tracing is in place, the trace ID can serve as the correlation ID and link logs to traces.
  • Most logging libraries store the ID in request-scoped context so it is added automatically.
Client request→Gateway generates req-8f2c1a→Header passed to each service→Every log line carries it→Search one ID across all logs

08What to log

  • Start at the boundaries of the system, where requests and external calls enter and leave.
  • Requests: arrival and completion, with status code and duration.
  • External calls: database, payment provider, and other services, especially failures and slow responses.
  • Important state changes: order moved from pending to paid, account locked, subscription cancelled.
  • Decisions the system made: retried a call, opened a circuit breaker, fell back to cached data.
  • Key configuration at startup: enabled feature flags, active region, dependency endpoints.
  • Log the outcome and identifiers, not the full payload.

09What not to log, and redaction

  • Never log passwords, API keys, access tokens, session cookies, or private keys.
  • Never log full credit card numbers or CVV values.
  • Be careful with personal data: email addresses, phone numbers, home addresses, and government identifiers.
  • Logs are often less protected than the database: they are copied, indexed, backed up, and read by many engineers.
  • A secret written once to a log can end up in far more places than the original record.
  • Regulations such as GDPR and PCI DSS cover logs too, not just primary storage.
  • Redact in the logging library: block known sensitive field names, mask values, and scan free text for token patterns.
  • Protection must not depend on every developer remembering it at every call site.
Application code→Shared logger→Redaction rules→Safe log output

10Avoiding noise

  • More logs do not mean more visibility; they dilute the signal and raise cost.
  • Tight loops: a job processing a million records must not emit a million INFO lines; log a summary instead.
  • Summaries should include how many records were processed, how many failed, and how long it took.
  • Same error at every layer: database logs and rethrows, service logs and rethrows, controller logs again — one failure becomes three.
  • Log an error once, at the place where it is actually handled.
  • Health checks and cache hits at INFO can dominate volume with almost no diagnostic value.
  • Keep messages short and constant, with changing values in separate fields, so identical events group together.

11Logging and performance

  • Every log line costs CPU to format, memory to buffer, and disk or network bandwidth to write.
  • In a high-traffic service, careless logging can measurably slow requests.
  • Asynchronous logging puts entries in a buffer and writes them from a background thread, so slow disk or network does not block the request.
  • The trade-off: buffered entries can be lost if the process crashes.
  • The buffer needs a full policy: block the caller, or drop entries — usually DEBUG and INFO first.
  • Do not build expensive messages when the level is disabled; use parameterized logging or lazy suppliers.
  • Compute the cost at peak request rate, not at one request per second.
Request→Process→Add to buffer→Response→Background writer flushes

12Centralizing logs

  • In containers, log files inside the container disappear when the container is replaced.
  • Applications should write to standard output and let the platform handle collection.
  • A log agent on each host, such as Fluent Bit or Vector, ships stdout to a central system.
  • The central store — Elasticsearch, Loki, or a managed service — indexes logs from every service in one place.
  • Writing to stdout keeps the app simple: no log files, rotation, or disk management.
  • Centralization enables one search across services and joins by correlation ID.
  • The pipeline itself needs monitoring: dropped batches and agent backlogs cause silent gaps.
Service stdout→Host log agent→Central log store→Search, dashboards, alerts

13Volume, cost, and retention

  • Log volume can grow into terabytes per day, and so does the bill.
  • Sampling: keep every error and warning, but only a fraction of successful request logs.
  • Runtime log levels: raise one service to DEBUG for a short window without redeploying, then lower it.
  • Retention tiers: recent logs in fast searchable storage, older logs in cheap object storage or deleted.
  • Metrics for counting: requests per second belongs in a metric, not in one log line per request.
  • Compress, batch, and filter at the agent instead of shipping everything and discarding later.
  • Review the highest-volume log statements periodically; a single noisy line can dominate cost.

14Logs, metrics, and traces together

  • Logs explain a specific event in detail: what happened to this order at this time.
  • Metrics are cheap aggregates: rates, error ratios, latency percentiles, saturation.
  • Traces show the path and timing of one request across services.
  • Use metrics to detect, traces to locate, and logs to explain.
  • A metric alert should link to the relevant logs and traces so investigation starts in one click.
  • Do not reconstruct rates by counting log lines; that is expensive and imprecise.
  • Instrument all three with the same service names and IDs so they can be correlated.

↔Trade-offs to say out loud

  • Structured JSON logs are searchable and stable but larger on disk and less pleasant to read raw.
  • More context speeds investigation but increases payload size and the risk of leaking sensitive data.
  • Verbose DEBUG logging helps development but inflates volume and cost in production.
  • Asynchronous logging protects request latency but can lose buffered entries on a crash.
  • Sampling success logs controls cost but reduces the ability to reconstruct rare successful flows.
  • Long retention helps audits and slow-burn investigations but dominates storage cost.
  • Central aggregation enables cross-service search but adds a pipeline that can drop or delay logs.
  • Shared logging libraries enforce consistency and redaction but add a dependency every service must upgrade.
  • Redacting aggressively protects privacy but can remove fields investigators later need.

?Interview questions

Answer aloud before opening the outline.

1. What makes a log entry useful?

It answers what happened, where, to whom, when, and with what outcome. That means a constant message plus structured fields such as service, level, timestamp, trace ID, entity ID, error type, and duration. The test is whether one line is enough to start an investigation.

2. Why structured logging instead of plain text?

Structured entries are named fields, so the log system can index and filter them without fragile regex. Searches and alerts survive message rewording. Plain text forces guessing and breaks when wording changes.

3. How do you enforce consistent field names across services?

Define a shared schema for required and optional fields, and implement it in a shared logging library so names are set automatically. Centralizing the library also standardizes redaction, formatting, and level handling. Document the schema for new services.

4. How do you choose between WARN and ERROR?

Ask whether someone needs to act. A failure that affected an operation is ERROR; something unexpected that the system handled, such as a successful retry or a fallback, is WARN. Logging expected user mistakes as errors creates alert fatigue.

5. What is a correlation ID and where is it created?

An identifier generated when a request enters the system, usually at the gateway, then propagated through headers and message attributes. Every service logs it so one search reconstructs the request across services. A trace ID can serve the same purpose and link logs to traces.

6. What should you never log?

Passwords, API keys, tokens, session cookies, full card numbers, and unnecessary personal data. Logs are copied, indexed, and broadly accessible, and regulations cover them too. Redact in the logger rather than relying on every developer.

7. How do you prevent sensitive data leaks in logs?

Apply redaction rules in the shared logging library: block sensitive field names, mask values such as all but the last four digits, and detect token patterns in free text. Add tests for the redaction rules and review new fields during code review.

8. Why is logging inside a tight loop a problem?

It produces enormous volume with little per-line value, raises cost, and buries useful entries. Log a summary with counts, failures, and elapsed time instead. If per-record detail is truly needed, gate it behind DEBUG and sample.

9. Why is logging the same error at every layer harmful?

One failure appears as several errors, so error counts and alerts overstate impact. Log once where the error is handled, and let other layers add context or rethrow without logging. This keeps counts meaningful.

10. How does asynchronous logging work and what is the risk?

Entries go into an in-memory buffer and a background thread writes them, so slow disk or network does not block requests. The risk is losing buffered entries on a crash, plus a policy decision when the buffer fills: block the caller or drop lower-severity entries.

11. How do you keep logging costs under control?

Sample high-volume success logs while keeping all errors and warnings, raise DEBUG only temporarily at runtime, tier retention from hot searchable storage to cheap object storage, filter and compress at the agent, and use metrics for counting instead of log lines.

12. How should logs be collected in containers?

Write to standard output and let a per-host agent such as Fluent Bit or Vector ship logs to a central store. Container-local files vanish with the container. The app stays simple and the platform handles rotation and delivery.

13. When should you use a metric instead of a log?

When you need counts, rates, percentiles, or saturation over time. Metrics are cheap to aggregate and alert on. Logs are for individual events and context. Counting log lines to compute request rate is slow, expensive, and imprecise.

14. How do logs, metrics, and traces complement each other?

Metrics detect that something is wrong, traces locate which hop is slow or failing, and logs explain the specific event and its context. Correlate them with shared service names and trace IDs so an alert leads directly to the relevant trace and log lines.

!Traps

  • Logging a generic message with no identifiers or error type.
  • Building messages by concatenating values, so every line is unique and impossible to group.
  • Logging everything at INFO in production and calling the resulting noise observability.
  • Logging the same exception at every layer and then alerting on the inflated error count.
  • Leaking tokens or personal data because redaction is optional and left to each developer.
  • Using synchronous logging on a hot path and adding latency to every request.
  • Computing expensive debug payloads before checking whether DEBUG is enabled.
  • Keeping every log forever in expensive searchable storage instead of tiering retention.
