In one lineA streaming engine turns a simple read from a log into a fault-tolerant distributed computation, handling parallelism, state, event time, checkpoints, and backpressure so application teams do not rebuild those mechanisms themselves.
Operator graph
The directed graph of sources, transformations, and sinks that makes up a streaming job.
Keyed state
State partitioned by a key, such as per-user counters, so each key is owned by exactly one parallel task instance.
State backend
The component that stores operator state, typically an embedded local store or an in-memory structure, with durability handled separately.
Checkpoint
A consistent snapshot of all operator state plus input positions, used to restart a job without losing or duplicating progress.
Watermark
A per-partition progress signal in event time that tells operators how far the input has advanced and when windows can close.
Event time
The timestamp carried by the event itself, which makes results reproducible when data arrives late or is replayed.
Backpressure
The mechanism by which a slow downstream operator slows its upstream sources instead of buffering without bound.
Parallelism
The number of concurrent task instances executing an operator, which must be reconciled with the source partition count.
Shuffle
Redistributing records across task instances by key, which is required for keyed aggregation and is the expensive step in a streaming graph.
Exactly-once sink
An output path that makes retried or replayed writes idempotent, often through transactions or deterministic keys.

01Why a streaming engine exists

Reading records from a topic is the easy part. Everything that makes the computation correct is harder.

  • Work must be spread across many machines without two machines counting the same key twice.
  • Machines crash mid-processing, so progress must survive the loss of any single process.
  • Events arrive out of order and late, so a result cannot be emitted the moment the first record shows up.
  • Traffic spikes, and a pipeline that buffers without limit eventually runs out of memory or disk.
  • Operators keep state, and that state must be partitioned, snapshotted, and restored consistently with input positions.
  • A streaming engine packages these mechanisms into one runtime so each team does not reinvent them incorrectly.

02Anatomy of a streaming job

  • Source connectors read from a log, files, or change streams and track offsets.
  • Transformations are operators such as map, filter, keyBy, window, join, and aggregate.
  • Sinks write results to tables, object storage, search indexes, or another topic.
  • A coordinator component plans the job, assigns work to workers, and drives checkpoints.
  • Workers execute task instances and host the local state for the keys they own.
  • The job graph is the contract: the engine decides how to place, chain, and parallelise its operators.
Source reads a partition and emits records→Map and filter operators process in place→keyBy triggers a shuffle to the owning task→Stateful operator updates keyed state→Sink writes with idempotence or a transaction→Coordinator checkpoints state and offsets

03Parallelism, partitioning, and shuffles

  • Each source partition is consumed by at most one task instance, which is what prevents duplicate processing at the source.
  • Total parallelism above the partition count leaves tasks idle at the source but still useful downstream.
  • keyBy hashes the key so all records for a key reach the same task instance, which is what makes keyed state correct.
  • A change in parallelism changes key ownership, so state must be redistributed or the job restarted from a savepoint with rescaling.
  • Operator chaining fuses narrow transformations into one task to avoid serialisation and network hops.
  • Wide operations such as joins and global aggregations require a shuffle, which is network-heavy and a common bottleneck.
  • Skewed keys overload one task while the rest idle, so hot-key detection and salting are part of operating a pipeline.

04State management

  • State is scoped: operator state is per task, while keyed state is per key and therefore co-located with the owning task.
  • State backends range from on-heap maps for small state to embedded local stores for state larger than memory.
  • Large state belongs on local disk with an in-memory cache, because recomputing it from the log is expensive.
  • Durability comes from periodic snapshots and, in some engines, a changelog topic that records every state mutation.
  • State must be bounded: TTLs, window cleanup, and explicit eviction prevent unbounded growth.
  • State schema is part of the job's compatibility surface; renaming a state field can make old checkpoints unreadable unless the engine supports migration.

05Checkpoints and recovery

  • A checkpoint captures every operator's state together with the source offsets that state corresponds to.
  • The engine injects a barrier into the stream; when every input has reached the barrier, the snapshot is consistent.
  • Snapshots are written to durable storage asynchronously so normal processing continues while they upload.
  • On failure, tasks restart and restore the last completed checkpoint, then resume from the recorded offsets.
  • Recovery time depends on state size and storage bandwidth, which is why huge state slows both checkpoints and restarts.
  • Sinks must cooperate: output written after the last checkpoint may be replayed, so the sink must be idempotent or transactional.
A checkpoint is only useful if restoring it produces the same result as never failing. That requires deterministic operators and a safe sink.

06Event time and watermarks

  • Event time uses the timestamp inside the record, so results do not depend on when the job happened to process it.
  • Processing time is cheaper and lower latency but produces different answers on replay and cannot handle late data correctly.
  • A watermark says the input is complete up to a point in event time, and windows close when the watermark passes their end.
  • Watermarks are usually derived from the maximum observed event timestamp minus an allowed-lateness bound.
  • Idle partitions can stall a watermark, so engines support idleness detection to keep windows closing.
  • Late events after the watermark either update a previously emitted result, go to a side output, or are dropped, and the policy must be explicit.
  • Watermarks are an estimate, not a guarantee: an event older than the watermark can still arrive and must not corrupt the output.

07Backpressure and flow control

  • When a downstream operator cannot keep up, it must slow the upstream rather than buffer indefinitely.
  • Engines propagate backpressure through bounded network buffers, so the source read rate drops to the slowest stage.
  • Backpressure is a symptom: the fix is usually more parallelism, a cheaper operator, or a faster sink.
  • Sustained backpressure appears as rising consumer lag, not as an error, so it is easy to miss without lag monitoring.
  • Buffering absorbs short spikes but cannot fix a capacity deficit; an unbounded queue only delays the failure.
  • A separate concern is load shedding: sometimes the right answer is to drop or sample low-value events during a spike.

08Delivery semantics

  • At-most-once commits the offset before processing; a crash loses records.
  • At-least-once commits after processing; a crash repeats records, so the sink must tolerate duplicates.
  • Exactly-once requires checkpointed offsets, a transactional or idempotent sink, and deterministic processing.
  • Two-phase commit sinks write output and offsets in one transaction so a restart cannot expose partial results.
  • Idempotent upserts keyed by event or window identifier achieve the same effect for many analytical sinks.
  • Stateful operators must also be exactly-once internally, which is why the checkpoint and the sink are designed together.

09Failure handling and upgrades

  • A failed task is restarted from the last checkpoint, usually on the same or another worker.
  • Full-job restarts are simpler but replay more work; regional or pipeline failover keeps a warm copy for critical jobs.
  • Savepoints enable planned changes: stop with a savepoint, change code or parallelism, restore from it.
  • Restoring with different parallelism requires redistributing keyed state, which costs time proportional to state size.
  • Upgrading operator logic while keeping old state needs explicit state migration, not just a new jar.
  • Some engines allow a standby or hot-swap pattern where a new version runs alongside until it is ready.

10Comparing common engines

  • Apache Flink is a cluster runtime with true event-time processing, large keyed state, distributed snapshots, and savepoints; it expects you to operate a cluster.
  • Kafka Streams is a library embedded in your application, with local state stores and changelog topics; there is no separate cluster to run, but scaling is tied to your app deployment and partitions.
  • Spark Structured Streaming runs on Spark and uses micro-batches with a checkpoint directory; it is a natural fit when batch and streaming share the same Spark codebase.
  • Apache Beam provides a portable API whose runner decides execution, which helps avoid lock-in but adds a layer to debug.
  • ksqlDB and similar SQL layers trade flexibility for declarative stream queries and are easiest for straightforward filtering and aggregation.
  • All of them solve the same core problems; the differences are deployment model, state capacity, latency profile, and operational burden.

11Choosing an engine

  • Start from the latency target: micro-batch is fine for near-real-time dashboards, while per-record processing suits tighter loops.
  • Check state size: joins and deduplication over long horizons need an engine built for large keyed state.
  • Check the operational model: a library inside an existing service is cheaper to run than a dedicated cluster.
  • Check the existing stack: reusing Spark or Kafka skills reduces risk more than a feature comparison.
  • Check the sink requirements: transactional output narrows the realistic options.
  • Check team capacity honestly; an engine that needs a platform team is the wrong choice for a team without one.

12Operating a pipeline

  • Monitor consumer lag and its trend, not just job status; a healthy job can still be hours behind.
  • Watch checkpoint duration and failures, state size, and restore time, because these set your recovery budget.
  • Watch watermark progress for stalled partitions and late-event rates for correctness drift.
  • Watch sink latency and error rates; a slow sink becomes backpressure across the whole graph.
  • Alert on skew and hot keys, which show up as one task at high load while peers idle.
  • Plan capacity for peaks and reprocessing, and test restores regularly rather than assuming checkpoints work.
  • Version the job, its state schema, and its input contracts together so an upgrade is reproducible.

13Designing a streaming pipeline in an interview

  • State the key and why it is the right partitioning unit for the aggregation.
  • Say whether the result must be exactly-once or whether idempotent upserts are sufficient.
  • Explain how late data is handled and what happens to windows that already emitted.
  • Explain how the job recovers: checkpoint interval, state size, and expected restore time.
  • Explain how the job is upgraded without losing state or double-writing output.
  • Name the bottleneck you expect first and the metric that will reveal it.
Define the output, latency target, and correctness requirement→Choose source partitions and key to preserve ordering where needed→Pick operators and windowing with event time→Choose state backend and checkpoint interval→Choose sink and delivery semantics→Size parallelism and plan for skew and backpressure→Define monitoring, replay, and upgrade runbooks

↔Trade-offs to say out loud

  • More parallelism raises throughput but adds shuffle traffic, coordination, and more state to checkpoint.
  • Larger state enables joins and long-window deduplication but slows checkpoints, restores, and rescaling.
  • Frequent checkpoints reduce replay on failure but consume bandwidth and add steady overhead.
  • Event time gives correct, reproducible results but requires watermarks and delays output until windows close.
  • Exactly-once sinks remove duplicates but require transactional support and can add commit latency.
  • Micro-batching simplifies fault tolerance and improves throughput but raises the minimum latency.
  • A dedicated cluster engine handles large state and complex event time well but needs a platform team to operate.
  • An embedded library is simple to deploy but makes scaling and state management the application team's problem.

?Interview questions

Answer aloud before opening the outline.

1. What does a streaming engine do that a message broker does not?

The broker stores and delivers events. The engine executes the computation: distributing operators across machines, partitioning state by key, tracking event time and watermarks, checkpointing for recovery, and applying delivery semantics at the sink.

2. How does the engine spread work across machines?

It splits the job graph into tasks and assigns them to workers, with source partitions consumed by single tasks. Keyed operations hash the key so all records for a key reach the same task, and wide operations insert a shuffle to redistribute records.

3. Why must keyed state be co-located with its key?

Each key's state is updated by exactly one task instance. If two instances owned the same key, they would each see a partial history and produce inconsistent aggregates. Hashing the key enforces single ownership.

4. How does checkpointing produce a consistent snapshot?

The coordinator injects barriers into the stream; an operator snapshots its state once all its inputs have reached the barrier, and the snapshot is uploaded asynchronously. The result pairs all operator state with the source offsets that produced it.

5. What happens on failure?

Tasks restart, restore the latest completed checkpoint, and resume reading from the recorded offsets. Output written after that checkpoint may be replayed, so the sink must be idempotent or transactional to keep results correct.

6. Event time versus processing time: when do you use each?

Use event time whenever results must be correct and reproducible, especially with late or out-of-order data. Processing time is simpler and lower latency but gives different answers on replay, so it suits approximate monitoring rather than billing.

7. What is a watermark and what breaks it?

A watermark is a claim that event time has advanced to a point, which lets windows close. Idle partitions, skewed progress, and very late events break it: windows may stall, or late records may arrive after their window was emitted.

8. What causes backpressure and how do you fix it?

A downstream stage cannot keep up, so buffers fill and the source slows. Fix it by increasing parallelism, reducing per-record cost, optimising the sink, or shedding low-value load. Backpressure is a capacity signal, not something to buffer away.

9. How do you achieve exactly-once end to end?

Combine checkpointed state and offsets with a sink that participates in a transaction or accepts idempotent writes keyed deterministically. Also keep operators deterministic, or a replay produces different output even with correct offsets.

10. When would you choose Kafka Streams over Flink?

When the data is already in Kafka, the logic is modest, and you want to deploy a normal application without operating a cluster. Choose Flink when you need large keyed state, complex event-time logic, or advanced savepoint-based operations.

11. When is Spark Structured Streaming the pragmatic choice?

When the organisation already runs Spark and the same transformations serve batch and streaming. Micro-batch latency is acceptable for many dashboards, and reusing existing skills and infrastructure lowers operational risk.

12. How do you upgrade a running streaming job?

Take a savepoint, stop the job, deploy the new code, and restore from the savepoint with the intended parallelism. If the state schema changed, provide a migration; otherwise the new job cannot read the old state.

!Traps

  • Assuming the engine makes the pipeline correct without thinking about state size, event time, and sink semantics.
  • Setting parallelism below the source partition count and leaving partitions unread or underused.
  • Using processing time for metrics that must reconcile with a batch recomputation.
  • Joining two streams without bounding state, so the join grows forever.
  • Claiming exactly-once while the sink is a plain at-least-once writer.
  • Setting a checkpoint interval so long that recovery replays more work than the latency budget allows.
  • Ignoring skew, so one task instance saturates while the rest of the cluster is idle.
