01The problem: expensive negative lookups

A sign-up page with a very large user base must tell a visitor whether a username is taken, ideally as they type.

  • Querying the database on every keystroke generates an enormous number of reads.
  • Holding every username in an in-memory hash set costs tens of gigabytes once the set is large, plus hash-table overhead.
  • Most attempted usernames are actually available, so most of that work confirms an absence and returns nothing.
  • The expensive case is the miss: proving that something is not there usually means touching storage.
  • If a cheap structure could prove absence, the database would only see the minority of cases that need confirmation.
  • The same shape appears in databases looking for absent keys and caches looking for absent objects.

02What a Bloom filter is

  • It is a space-efficient structure that answers "is this item in the set?" for a set it never stores.
  • It supports exactly two operations: add an item and check an item.
  • A check returns one of two answers: definitely not in the set, or might be in the set.
  • It keeps no keys, only a compact bit array, which is why it can be orders of magnitude smaller than a hash set.
  • The trade is precision: it can be wrong in one direction but never in the other.
  • It shines when a definite "no" lets the caller skip expensive work.
  • It is not a cache and not a store: you cannot retrieve the items or enumerate them.

03How it works

  • Allocate a bit array of m bits, all zero, and choose k hash functions.
  • Each hash function maps an item to a position in the array, deterministically: the same item always yields the same positions.
  • Add: hash the item with all k functions and set those bits to 1, leaving already-set bits untouched.
  • Check: hash the item the same way; if any bit is 0, the item was definitely never added.
  • If all bits are 1, the item might have been added — or other items may have set those bits.
  • Two items can share positions, which is exactly why deletion is unsafe and why false positives exist.
  • With a toy array of ten bits and three hashes, adding alice sets 1, 4, 7 and adding dave sets 2, 5, 7; checking bob at 0, 4, 8 hits a zero and is rejected immediately.
  • The mechanism is entirely local to memory: no disk, no network, no coordination.

04False positives: safe versus risky

  • A false positive happens when every probed bit was set by other items, so an absent key looks present.
  • It is safe when the only consequence is extra work, such as one unnecessary database read.
  • It is dangerous when the answer itself drives a decision, such as granting access or marking a payment as processed.
  • Safe pattern: treat "might be" as go check, never as yes.
  • Risky pattern: treat "might be" as a final answer, which silently converts an approximation into a wrong decision.
  • The design rule is simple: a Bloom filter may only skip work, never authorize an action.
  • This asymmetry is what makes the structure usable in production despite being approximate.

05Why there are no false negatives

  • Adding an item sets all of its bits to 1.
  • In a standard Bloom filter, bits only change from 0 to 1 and never back.
  • So an added item's bits are still 1 at every later check, no matter what else was inserted.
  • That guarantee is what lets the caller trust a "definitely not" answer and skip the lookup.
  • It also explains why clearing bits for deletion is forbidden: it can create a false negative for a different item.
  • The guarantee depends on using the same hash functions and the same array forever.
  • It also depends on the filter being current with the underlying data set; a stale filter can mislead in the other direction.

06Sizing: false positive rate and hash count

  • The false positive rate depends on three things: array size m, item count n, and hash count k.
  • More items means more bits set, so a filter that is too small fills up and starts answering "might be" to everything.
  • The practical unit is bits per item: roughly 10 bits per item with a good k gives about a 1% rate.
  • Every additional ~5 bits per item cuts the false positive rate by roughly a factor of ten.
  • Too few hash functions means each item sets few bits, so accidental matches are common.
  • Too many hash functions fills the array faster, which also raises the rate — there is an optimum.
  • The standard sizing formulas are m = -n ln(p) / (ln 2)^2 and k = (m/n) ln 2 for target rate p.
  • Libraries take expected items and target rate and compute both, so hand-tuning is rarely necessary.

07Hashing in practice

  • Hash functions must be fast and spread values evenly; cryptographic strength is unnecessary.
  • MurmurHash and similar non-cryptographic hashes are the usual choice.
  • Hashes must be stable across processes and restarts if the filter is serialized or shared between services.
  • A language's built-in hash may be randomized per process, which silently breaks a persisted filter.
  • You do not need k independent functions: compute two base hashes and derive the rest as h1 + i*h2, called double hashing.
  • Double hashing keeps construction cheap while preserving the distribution properties that sizing assumes.
  • Changing the hash functions invalidates an existing filter, so they are part of its schema.
A teaching implementation typically uses a small FNV-1a hash and double hashing; production should use a maintained library with serialization support and explicit sizing controls.

08What it saves in memory

  • A hash set holding a billion short keys needs tens of gigabytes before counting table overhead.
  • A Bloom filter at a 1% rate needs roughly 10 bits per item, so the same billion keys fit in a bit over a gigabyte.
  • The filter's size does not depend on item length: a long URL costs the same bits as a short username.
  • That compactness allows a copy of the filter on every application server, so checks become local memory reads.
  • Only the small fraction of lookups that are false positives reach the database.
  • The savings come with a hard constraint: the filter must be sized for the final item count, not today's.
  • Replication is trivial because the filter is small; recomputation is not, because it needs the full data set.

09Deletion and counting filters

  • A standard Bloom filter cannot remove an item: clearing its bits also clears bits shared with other items.
  • Doing so creates a false negative for those other items, which breaks the one guarantee the structure offers.
  • A counting Bloom filter stores a small counter per position instead of a bit.
  • Add increments the counters; remove decrements them; a position counts as set while its counter is above zero.
  • Counters are typically a few bits wide, which makes the filter several times larger than the bit version.
  • Removal must only be applied to items that were actually added, or counters drift and false negatives appear.
  • Cuckoo filters are the other common answer: they store short fingerprints and delete by removing a fingerprint instead of decrementing shared state.

10Fixed capacity and scalable filters

  • Size is fixed at construction, because the array size and hash count are baked into the structure.
  • If the set grows well beyond the planned count, the array saturates and the false positive rate spikes.
  • You cannot simply enlarge it: the original items are gone, so there is nothing to rehash.
  • Option one: rebuild from the source data with a bigger array, which is correct but expensive and periodically stale.
  • Option two: use a scalable filter, where a full filter is followed by a new, larger one for new items.
  • A lookup then checks every filter in the chain, so latency grows slowly with the number of sub-filters.
  • Sizing well up front is cheaper than relying on many sub-filters, so estimate growth before deploying.

11Bloom filters inside databases

  • Storage engines such as Cassandra, HBase, and RocksDB keep data in many immutable files on disk.
  • A lookup could match any file, and checking each one costs a disk read that often finds nothing.
  • Each file carries a Bloom filter of its keys, kept in memory, and the engine consults it before reading the file.
  • A "definitely not" answer skips the file entirely, replacing a random read with a memory check.
  • The benefit is largest for absent keys, which would otherwise force a read of every file.
  • Cassandra exposes the target rate per table through bloom_filter_fp_chance, where a lower rate costs more memory.
  • Filters are rebuilt when a file is written, so they always match the file's contents.

12Bloom filters in caching

  • One-hit wonders: a CDN observed that many requested objects are requested only once, so caching them evicts more popular objects.
  • The filter records recently seen objects; the first request adds the object without caching it, and a later request caches it.
  • False positives only cause a few one-time objects to be cached, which is harmless.
  • Cache penetration: repeated requests for nonexistent keys miss the cache and hit the database every time.
  • A filter of all valid keys rejects requests for keys that certainly do not exist, protecting the database.
  • The filter must be updated whenever a new valid key is created, or real items get rejected.
  • Both uses rely on the same property: a cheap negative answer protects an expensive tier.

13Combining filters and knowing when not to use one

  • Two filters with the same size and hash functions can be merged with a bitwise OR.
  • The result equals a filter built from the union of both item sets, with no need to reprocess the data.
  • That makes filters easy to ship between nodes: a compact summary instead of the keys themselves.
  • Do not use one when you need a definite yes, such as an allow-list decision, without an exact check.
  • Do not use one when you need to list, retrieve, or iterate the set; it stores nothing.
  • Do not use one when deletions are frequent, unless you accept a counting or cuckoo variant.
  • Do not use one when the whole set already fits comfortably in memory — a hash set is exact and simpler.
  • Match the structure to the question: Bloom for membership, HyperLogLog for distinct counts, Count-Min Sketch for frequencies.

↔Trade-offs to say out loud

  • Bits instead of keys saves orders of magnitude of memory but makes the answer probabilistic.
  • More bits per item lowers false positives but increases memory linearly.
  • More hash functions help up to the optimum, then saturate the array and hurt.
  • No deletion keeps the no-false-negative guarantee but forces rebuilds or a heavier variant.
  • Counting Bloom filters allow deletion but cost several times the memory of a bit array.
  • Scalable filters handle growth but add a chain of checks to every lookup.
  • Replicating the filter everywhere makes checks local but demands a rebuild strategy on every node.
  • A very low false positive rate reduces wasted lookups but can cost more memory than the lookups save.
  • Skipping work on a negative answer is safe, but any decision made on a positive answer is not.

?Interview questions

Answer aloud before opening the outline.

1. Explain a Bloom filter in one paragraph.

It is a bit array with several hash functions. Adding an item sets the bits its hashes point to; checking an item reads those bits. Any zero proves the item was never added, while all ones only mean it might have been. It never stores the keys, so it is tiny, and it never returns a false negative.

2. Why can a Bloom filter never have false negatives?

Adding an item sets all of its bits to 1, and bits never return to 0 in a standard filter. So an added item's positions remain set regardless of later insertions. A false negative can only appear if bits are cleared, which is exactly why deletion is unsupported.

3. When is a false positive acceptable?

When it only causes extra work, such as one more database read or one unnecessary cache fill. It is unacceptable when the answer itself drives a decision, like granting access or confirming a payment. The rule is that a "might be" answer must always be verified.

4. How do you size a Bloom filter?

Decide the expected item count and the target false positive rate, then use the standard formulas to compute the bit array size and hash count — about 10 bits per item and 7 hashes for roughly 1%. Libraries do this for you. Size for the eventual set, not the current one.

5. What happens if you use too many hash functions?

Each item sets more bits, so the array saturates faster and unrelated items find all their positions already set. Beyond the optimum, the false positive rate rises even though more work is done per operation. The optimum follows from the bits-per-item ratio.

6. Why is deletion unsafe, and what are the alternatives?

Clearing an item's bits also clears bits shared with other items, producing false negatives for keys that are still present. Alternatives are periodic rebuilds, a counting Bloom filter with per-position counters, or a cuckoo filter that deletes a fingerprint rather than shared bits.

7. What happens when a filter exceeds its planned capacity?

The array fills with ones and nearly every check returns "might be", so the filter stops saving work. It cannot be resized in place because the original keys are gone. Rebuild it from source, or use a scalable filter that appends a new larger filter and checks the chain.

8. How do databases use Bloom filters?

An LSM-style engine has many immutable files, and a key might be in any of them. Each file keeps a Bloom filter in memory, so the engine skips files that certainly do not contain the key. Absent-key lookups stop costing a disk read per file.

9. How does a Bloom filter prevent cache penetration?

Maintain a filter of all valid keys. A request for a key the filter rejects never reaches the cache or database, so repeated requests for nonexistent keys cannot hammer the backend. The filter must be updated as new valid keys are created.

10. Can two Bloom filters be merged?

Yes, if they use the same array size and hash functions: a bitwise OR yields exactly the filter you would get from the union of both item sets. That lets nodes exchange compact summaries instead of raw keys. Filters built with different parameters cannot be merged.

11. Bloom filter or hash set?

Use a hash set when the data fits in memory and you need exact answers, enumeration, or deletion. Use a Bloom filter when the set is far too large to store, most lookups are misses, and an exact check is available for the "might be" case.

12. Why must hashes be stable across processes?

If a filter is serialized to disk or shared between services, the same key must map to the same bit positions everywhere. A randomized per-process hash produces different positions, so the filter silently reports wrong answers. That is why implementations require an explicit stable hash such as MurmurHash.

!Traps

  • Treating a "might be present" answer as a definite yes in an authorization or payment path.
  • Sizing for today's item count and letting the filter saturate in production.
  • Trying to delete by clearing bits, which creates false negatives for other keys.
  • Using a language's randomized built-in hash for a persisted or shared filter.
  • Assuming more hash functions always means fewer false positives.
  • Merging filters that were built with different sizes or hash functions.
  • Forgetting to update the filter when new valid keys are created, so real keys get rejected.
