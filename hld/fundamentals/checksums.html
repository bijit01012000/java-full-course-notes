Checksum
A small, fixed-size value computed from a piece of data and compared later to detect changes.
Collision
When two different inputs produce the same checksum value, which is unavoidable for any fixed-size check.
Parity bit
A single bit recording whether a group has an even or odd number of 1s; it catches one flipped bit but not two.
Internet checksum
The 16-bit one's-complement add-and-flip checksum used by IPv4, TCP, and UDP.
CRC
Cyclic Redundancy Check: a checksum computed by binary polynomial division, sensitive to bit positions and fast in hardware.
Burst error
A short run of consecutive damaged bits, the error pattern a CRC is especially good at detecting.
Cryptographic hash
A hash function designed so finding two inputs with the same digest is computationally infeasible, such as SHA-256.
HMAC
A keyed message authentication code combining data with a shared secret, so only a key holder can produce a valid tag.
Digital signature
A private-key signature that anyone with the public key can verify, proving who produced the data.
Merkle tree
A tree of hashes where each parent summarizes its children, letting two replicas compare large data sets by comparing roots.

01How data gets corrupted

Data can change between being written and being read, and the change is often silent.

  • Electrical noise can flip a bit while a packet travels over a cable or radio link.
  • Faulty memory in a router or server can alter data while it waits in a buffer.
  • Bit rot: a storage device can lose or alter bits over months or years.
  • Misdirected writes: a driver or storage bug can write valid data to the wrong location.
  • Firmware bugs can return a block that is internally consistent but not the block that was requested.
  • The dangerous part is silence: the program does not crash, it simply reads the wrong bytes and continues.
  • One changed bit can turn a financial value into a different number or make a compressed file unreadable.
This is why the question is not whether corruption happens, but whether the system would notice if it did.

02What a checksum is

  • A checksum is a small, fixed-size value computed from a piece of data by an algorithm.
  • The sender or writer computes it and stores or transmits it alongside the data.
  • The receiver runs the same algorithm over what it got and compares the two values.
  • If they differ, the data changed: the system can reject it, retry, or read another replica.
  • If they match, the data is likely intact — not certainly intact.
  • The checksum is far smaller than the data, so many inputs map to the same value; some collisions are inevitable.
  • A good algorithm makes collisions rare for the error patterns it was designed to catch, not for all possible inputs.
Compute the checksum over the data→Store or send the checksum with the data→Recompute the checksum on read or receipt→Compare the two values→On mismatch: reject, retry, or read another replica

03Detection, not repair

  • A checksum detects corruption; it does not say which bits changed.
  • It does not repair anything by itself; it only produces evidence that something is wrong.
  • Error-correcting codes take a different approach: they add enough redundancy to recover certain errors.
  • ECC memory and the error correction inside SSDs are everyday examples.
  • In distributed systems, detecting a bad copy and fetching a good one is usually enough.
  • Recovery comes from elsewhere: a retransmission, another replica, or a backup.
  • How reliable the detection is depends entirely on the algorithm and how much data each checksum covers.

04The simplest checksum: adding bytes

Adding the byte values is the cheapest possible check, and it shows exactly why stronger algorithms exist.

  • Sum the bytes and send the total: bytes 10, 20, 30 produce 60.
  • If one byte changes to 21, the receiver computes 61 and detects the mismatch.
  • But reordering the same bytes to 30, 20, 10 still sums to 60, so reordering goes undetected.
  • If one byte increases by one and another decreases by one, the changes cancel out.
  • A simple sum is fast but blind to position and to compensating errors.
  • Parity is even weaker: one bit records whether a group has an even or odd number of 1s.
  • Parity catches any single flipped bit but misses two flips in the same group, so it suits memory and serial links, not files.

05The Internet checksum

  • The Internet checksum is used by IPv4, TCP, and UDP and produces a 16-bit value.
  • It splits the input into 16-bit words, adds them with one's-complement addition, and flips the final bits.
  • In IPv4, the header checksum covers only the IP header, not the payload.
  • Routers decrement the TTL on every hop, so they must recompute that header checksum each time.
  • TCP and UDP have separate checksums covering their headers and payloads, plus IP-layer fields such as source and destination addresses.
  • Covering the addresses is what makes it an end-to-end check rather than a single-link check.
  • It was designed for cheap computation on older hardware, which is why it is only 16 bits and not very strong.
  • Because it is additive, swapping two 16-bit words leaves it unchanged — the same weakness as the byte sum.
IPv6 removed the IP header checksum to save work at every router, leaving error detection to the link layer and to transport checksums.

06Cyclic redundancy checks (CRC)

  • A CRC treats the data as a sequence of bits and performs binary polynomial division, keeping the remainder as the checksum.
  • Because the result depends on both bit values and bit positions, reordering is far more likely to be caught than with a sum.
  • With a suitable polynomial, a 32-bit CRC detects every single-bit error and every burst error up to 32 bits long.
  • For random errors, CRC-32 leaves roughly a one-in-four-billion chance of an undetected mismatch.
  • CRCs are extremely fast: network hardware computes them directly, and CPUs have instructions for CRC-32C.
  • Common uses: Ethernet and Wi-Fi frame check sequences, ZIP and PNG, Kafka records, and many storage engines.
  • A CRC is not cryptographic: anyone who changes the data deliberately can compute a new CRC to match.

07Why network checksums are not enough

  • An Ethernet CRC protects a frame across a single link, not end to end.
  • A forwarding device validates the incoming frame, then generates a new check value for the next link.
  • If corruption happens inside a router's memory after the incoming check and before the outgoing frame, the router computes a valid CRC over the corrupted data.
  • The next device sees a perfectly valid frame and has no idea what happened earlier.
  • TCP adds an end-to-end check that can catch errors introduced between sender and receiver.
  • But its 16-bit checksum is weak enough that some corrupted packets have passed it in real traffic.
  • This is the end-to-end principle: lower-layer checks help, but only the final consumer can confirm what it received.
  • If correctness is critical, the application needs its own integrity check.
Modern TLS protects records with an authenticated encryption tag: if verification fails, the record is rejected and the connection is usually terminated.

08Cryptographic hashes

  • A cryptographic hash such as SHA-256 also produces a fixed-size value, here 256 bits versus 32 for a common CRC.
  • The difference is not just length: a cryptographic hash is designed so finding two inputs with the same digest is computationally infeasible.
  • That makes it a content fingerprint: same digest means same bytes, with overwhelming probability.
  • Software publishers ship SHA-256 digests so users can verify a download matches the expected content.
  • Git identifies objects by content hash, Docker images are addressed by digest, and content-addressed storage uses hashes as keys.
  • If two blobs share a digest, they can be stored once, which is the basis of deduplication.
  • MD5 and SHA-1 have known collision attacks and must not be used where collision resistance matters.
  • They still catch many accidental errors, but they are not appropriate for adversarial integrity checks.

09Authenticity: HMACs and signatures

  • A hash only proves the data matches the hash you compare it against.
  • If an attacker can replace both the data and the expected hash, the comparison still succeeds.
  • Authenticity needs a trusted expected value or a mechanism that proves who produced the data.
  • An HMAC combines the data with a shared secret, so only a key holder can produce a valid tag.
  • Webhook providers commonly use HMACs so receivers can confirm a call really came from them.
  • Because both sides hold the same key, either side could generate a valid tag — HMAC proves group membership, not unique origin.
  • A digital signature uses a key pair: the publisher signs with a private key and anyone verifies with the public key.
  • That is how package repositories, container registries, and software updates let many users verify one publisher.

10Choosing the right checksum

  • For accidental corruption in frames, disk blocks, or log records, CRC-32C is a strong default: it catches common patterns and is cheap.
  • Parity is only suitable for a very cheap single-bit check, not for files or messages.
  • For a longer fingerprint on large data without paying cryptographic cost, consider fast non-cryptographic hashes such as xxHash or a longer CRC.
  • For content identification or protection against deliberate tampering, use SHA-256 or another modern cryptographic hash.
  • A cryptographic digest is only as trustworthy as the way you obtain the expected value.
  • For proof of origin between two trusted parties, use an HMAC.
  • For proof of origin that anyone can verify, use a digital signature.
  • For very high-throughput per-packet checks, a hardware-accelerated CRC is usually the only affordable option.

11Coverage: one checksum or many?

  • How much data each checksum covers matters as much as which algorithm you pick.
  • One checksum over an entire large file tells you something is wrong but not where.
  • Repair then means transferring the whole object again.
  • Checksumming smaller chunks independently lets you identify the damaged chunk and replace only that part.
  • Smaller chunks make repair more precise but require more checksums to store and more work to verify.
  • This is a common pattern in storage systems and in replication protocols that compare ranges.
  • The granularity should follow the repair strategy: whatever you can replace independently should be verifiable independently.

12Checksums in storage systems

  • Storage devices have their own error detection, but bit rot, misdirected writes, and firmware bugs can still return wrong data.
  • That is why storage systems add checksums at a higher layer.
  • HDFS traditionally keeps a checksum for each 512-byte chunk of a block; a failed check triggers a read from another replica and a repair report.
  • ZFS stores a block's checksum in the metadata pointer that references it, so a valid but wrong block is still detected.
  • Storing the checksum next to the data would not catch a wrong block, because that block's own checksum would match.
  • PostgreSQL checksums write-ahead log records so crash recovery can reject invalid or incomplete records, and can checksum data pages.
  • Amazon S3 accepts a client-provided checksum on upload and rejects the upload if the received data does not match.
  • Databases may refuse to start on known-corrupt data, deliberately, so the damage is not spread to replicas and backups.

Scrubbing

  • Rarely read data can corrupt silently for months, and you find out when you urgently need it.
  • Scrubbing periodically reads stored blocks, verifies checksums, and repairs from healthy redundancy while it still exists.
  • ZFS and many distributed storage systems schedule scrubs.
  • The same logic applies to backups: a backup that has never been test-restored is not verified.

13Checksums in system design

  • Verify end to end: compute the check near where data originates and verify where it is ultimately used.
  • That covers the network, intermediate services, and storage, instead of trusting one layer.
  • Decide the failure policy: retry the transfer, read another replica, or mark the object unavailable.
  • Never silently accept a mismatch; emit metrics and alerts, because repeated mismatches point at failing hardware or a bad path.
  • Compare large data sets with Merkle trees: replicas exchange root hashes and descend only into ranges that differ.
  • Cassandra-style anti-entropy uses this to find divergent ranges without shipping every record.
  • Detect changes with content hashes: backup and sync tools upload only changed chunks.
  • HTTP servers can derive an ETag from content so clients can check for changes without downloading the whole response.
The three design questions are: where could corruption happen, how will we detect it, and what will we do when a check fails?

14What to remember

  • A checksum detects accidental change; it does not repair it and cannot prove the data is correct.
  • Every fixed-size checksum can collide, so a match is evidence, not proof.
  • A byte sum misses reordering and compensating changes; parity catches only a single flipped bit.
  • The 16-bit Internet checksum is cheap but weak; IPv6 dropped the IP header version entirely.
  • CRC-32C is the practical default for accidental corruption: position-sensitive, burst-error aware, and fast.
  • Link-layer checks do not cover corruption inside intermediate devices, so critical data needs end-to-end verification.
  • SHA-256 is for content identity and tamper detection; HMACs and signatures are for proving who produced the data.
  • Storage systems add checksums at a higher layer and scrub rarely read data before redundancy is lost.

↔Trade-offs to say out loud

  • Stronger checksums catch more error patterns but cost more CPU per byte, which matters at high throughput.
  • CRC-32C is fast and catches accidental corruption well but is trivial to forge, so it is useless against an attacker.
  • SHA-256 gives collision resistance and content identity but costs noticeably more than a CRC on large volumes.
  • Fine-grained chunk checksums make repair precise but multiply the number of checksums to store and verify.
  • One checksum per large object is cheap to store but can only tell you the whole object is bad, forcing a full retransfer.
  • End-to-end verification catches corruption anywhere in the path but duplicates work already done by lower layers.
  • Storing checksums beside the data is simple but cannot detect a valid block returned from the wrong location.
  • Scrubbing finds latent corruption before it is needed but consumes I/O and can degrade foreground performance.
  • HMACs prove a shared-secret holder produced the data, but any holder of the key could also forge it.

?Interview questions

Answer aloud before opening the outline.

1. What is a checksum and how is it used?

A small fixed-size value computed from data. It is stored or sent with the data, then recomputed on read or receipt and compared. A mismatch means the data changed, so the system can reject it, retry, or read another replica.

2. Why can't a checksum guarantee the data is correct?

Because the checksum is much smaller than the data, many different inputs map to the same value. A collision means a match is strong evidence but never proof. The guarantee is probabilistic and depends on the algorithm and the error pattern.

3. Why is adding bytes a weak checksum?

It ignores position and cancels out compensating changes. Reordering the same bytes gives the same sum, and one byte increasing while another decreases also gives the same sum, so both corruptions pass.

4. What does parity catch and miss?

It catches any single flipped bit in the group, because that changes the parity. It misses two flips in the same group, since they restore the original parity. It is cheap enough for memory and serial links but too weak for files.

5. How does the Internet checksum work?

It splits the data into 16-bit words, adds them with one's-complement addition, and flips the result to produce a 16-bit checksum. IPv4 applies it to the header only; TCP and UDP apply theirs to header, payload, and IP address fields for an end-to-end check.

6. Why do routers recompute the IPv4 header checksum?

Because they decrement the TTL on every hop, which changes the header. The checksum must be updated to match. IPv6 removed the header checksum specifically to avoid that per-hop work.

7. How is a CRC different from a simple sum?

A CRC treats data as bits and computes a polynomial-division remainder, so the result depends on bit positions. Reordering or burst damage is much more likely to change it. It also detects every single-bit error and every burst up to the width of the CRC.

8. If Ethernet already checks every frame, why do we need TCP or application checks?

The Ethernet CRC covers one link. A router validates the incoming frame, then builds a new frame with a new CRC, so corruption inside the router can be blessed by a valid outgoing checksum. End-to-end checks catch errors introduced anywhere along the path.

9. When would you use SHA-256 instead of a CRC?

When you need content identity or protection against deliberate modification: download verification, container image digests, Git objects, or content-addressed storage. A CRC is for accidents only, because anyone can recompute one.

10. What is the difference between a hash, an HMAC, and a digital signature?

A hash only compares content with a digest you already trust. An HMAC uses a shared secret so only key holders can produce a valid tag. A digital signature uses a private key to sign and a public key to verify, so anyone can check it and only the publisher could have created it.

11. Why does where the checksum is stored matter?

If it is stored beside the data, a valid but wrong block still matches its own checksum. ZFS stores the checksum in the parent pointer, so returning the wrong block is detected. The check must cover the identity and location of the data, not just its bytes.

12. How do you decide the chunk size for checksums?

Match it to the repair granularity. Smaller chunks let you identify and replace only the damaged part, but they cost more space and verification work. One checksum for a huge object forces a full retransfer on any mismatch.

13. What is scrubbing and why does it matter?

Periodically reading stored data, verifying its checksums, and repairing from redundancy. It finds latent corruption in data that is rarely read before all healthy copies are damaged. Backups need the same treatment through test restores.

14. How would you design integrity checking for a file upload service?

Have the client send a checksum or hash with the upload, verify it on receipt, and store per-chunk checksums for later reads. On mismatch, reject the upload and ask for a retry. Use SHA-256 if you need content identity and a CRC if you only need cheap accidental-corruption detection. Alert on repeated failures from one client or path.

!Traps

  • Claiming a matching checksum proves the data is correct, rather than making it likely.
  • Using a plain hash as proof of origin when an attacker could replace both the data and the digest.
  • Assuming a link-layer CRC protects data end to end, including inside routers and proxies.
  • Using CRC or MD5 for tamper detection against a deliberate attacker.
  • Storing a block checksum next to the block and expecting it to catch a valid block returned from the wrong location.
  • Checksumming an entire huge object and then having to retransfer all of it for one bad chunk.
  • Treating a checksum as a repair mechanism and forgetting that recovery needs a retry, replica, or backup.
  • Never verifying backups, so corruption is discovered only during a real restore.
