In one lineEvent-driven architecture replaces direct calls with facts: a producer announces that something happened, a broker stores and delivers it, and any number of consumers react on their own — trading immediate consistency and simple debugging for decoupling and resilience.
Event
An immutable statement that something happened, named in the past tense and carrying the facts needed to react.
Producer
The service that detects a state change and publishes an event without knowing who consumes it.
Broker
The middleware that receives, stores, and delivers events, decoupling producers from consumers in time and space.
Topic
A named, append-only stream of events that consumers subscribe to and that can often be replayed.
Partition
An ordered subset of a topic; ordering is guaranteed within a partition, not across the whole topic.
Consumer group
A set of consumers sharing the work of a subscription so each event is processed by one member per group.
Idempotency
The property that processing the same event twice leaves the system in the same state as processing it once.
Event sourcing
Persisting the sequence of events as the source of truth and deriving current state by replaying them.
Schema registry
A central store of event schemas and compatibility rules that producers and consumers validate against.
Eventual consistency
A guarantee that replicas converge once all events are processed, rather than agreeing at every instant.

01The problem with direct calls

When one service calls another directly, it must know where it lives, wait for a response, and handle the failure if the other side is slow or down.

  • The caller is coupled to the callee's address, availability, and latency at the moment of the request.
  • When many services need to react to the same change, the producer must know and call every one of them.
  • Adding a new consumer means changing the producer and redeploying it — a closed system.
  • Chains of synchronous calls multiply latency and the probability that at least one hop fails.
  • A consumer outage propagates back to the producer and then to the user.
  • The producer often ends up owning retry, ordering, and failure handling for work that is not its concern.
  • This is fine for simple request/response flows; it becomes awkward when many independent reactions are needed.

02What event-driven architecture is

  • A service announces a fact — order placed, payment captured, user registered — and other services react.
  • The producer does not know who consumes the event or what they do with it.
  • A broker sits between them and handles storage, delivery, and often retention and replay.
  • Consumers can be added, removed, or restarted without changing the producer.
  • The flow is inverted: instead of asking for work, services subscribe to what they care about.
  • The architecture is asynchronous by default, so results are eventually consistent rather than immediate.
  • The win is decoupling in space (no addresses), time (no simultaneous availability), and change (no producer edits).
Producer detects change→Publish event to broker→Broker stores and delivers→Consumers react independently

03Broker, topics, partitions, and consumer groups

  • A topic is an append-only log or channel; a consumer subscribes rather than polling a producer.
  • The log model keeps events for a retention period, so a new consumer can replay history.
  • A topic is split into partitions; each partition is an ordered sequence, and partitions are processed in parallel.
  • The partition key decides placement — events with the same key land in the same partition and stay ordered.
  • A consumer group shares partitions among members, giving scale-out plus one logical subscription.
  • Different consumer groups each receive the full stream, so independent services do not steal each other's events.
  • Consumer offsets record progress; committing an offset is the acknowledgement that processing succeeded.
  • A queue differs from a log: once a message is acknowledged it is gone, and there is no replay for new readers.

04Events, commands, and queries

  • An event is a past-tense fact: PaymentCaptured. It cannot be rejected, only reacted to.
  • A command is a request: CapturePayment. It has one intended recipient and can be refused.
  • A query asks for data and expects an answer synchronously.
  • Mixing commands and events in the same channel blurs ownership and makes failures ambiguous.
  • Commands are usually point-to-point through a queue; events are usually broadcast to a topic.
  • Name events for the business fact, not for the database operation that produced them.
  • If the producer needs the outcome, that is a command or a request/response flow, not an event.
A useful test: if the sender expects a reply or can be refused, it is a command. If it merely reports what happened, it is an event.

05Three styles: notification, state transfer, sourcing

  • Event notification: a thin event says only that something changed and carries an ID; consumers call back for details.
  • Notification keeps payloads small and contracts stable, but creates a callback dependency and possible read-after-write races.
  • Event-carried state transfer: the event includes the changed fields, so consumers update local copies without calling back.
  • State transfer removes runtime coupling but duplicates data and enlarges payloads and contracts.
  • Event sourcing: the event log itself is the source of truth; current state is a projection built by replaying events.
  • Event sourcing gives a full audit trail and time travel, but requires snapshots, projections, and schema migration of history.
  • Most systems mix styles: notifications for triggers, state transfer for read models, sourcing only where history is a requirement.

06Delivery semantics and duplicates

  • At-most-once: deliver and forget; fast, but events can be lost.
  • At-least-once: retry until acknowledged; the practical default, and duplicates are expected.
  • Effectively-once: at-least-once delivery plus idempotent or deduplicated processing, not a magic transport guarantee.
  • A crash after processing but before committing the offset causes redelivery of an already-handled event.
  • Make consumers idempotent with a natural key, a processed-event table, or conditional writes.
  • Deduplicate on an event ID with a bounded window; unbounded history for deduplication is a storage problem.
  • Producer-side retries can also create duplicates, so the event ID must be assigned before the first send attempt.
  • Exactly-once claims usually apply only inside one broker's ecosystem, not across an arbitrary database write.

07Ordering

  • Global ordering across a topic is expensive and rarely required; per-entity ordering usually is.
  • Order is guaranteed only within a partition, so the partition key must match the entity whose order matters.
  • Choosing a coarse key (tenant, region) preserves order but concentrates load and limits parallelism.
  • Choosing a fine key (random) spreads load but makes related events arrive out of order.
  • Consumers can reorder using a version or sequence number and reject stale updates.
  • Processing with multiple threads or parallel batches inside a consumer breaks ordering even if the broker preserved it.
  • Out-of-order events are often handled by making operations commutative or by keeping the latest version per key.
The question is never is ordering guaranteed, but ordering of what, and does the business logic actually depend on it.

08Eventual consistency and the user experience

  • Once work is asynchronous, the write is accepted before all read models reflect it.
  • Replicas and projections converge only after every event is processed, so reads can be temporarily stale.
  • Read-your-writes can be preserved by routing that read to the source, or by waiting for a version marker.
  • The UI should show pending or processing states instead of implying instant completion.
  • Idempotent operations plus retries make convergence likely; reconciliation jobs catch the rest.
  • Business rules must tolerate a window where two services disagree about the same entity.
  • Some flows genuinely need strong consistency; keep those inside one service or one transaction.
Accept write→Publish event→Projections update→Client sees updated state

09Schema evolution and contracts

  • An event schema is a public contract; once published, consumers depend on it.
  • Additive changes (new optional fields) are usually safe; renames, type changes, and removals break consumers.
  • Use a schema registry with compatibility rules to reject breaking changes at publish time.
  • Version events explicitly when semantics change, and support old and new versions during migration.
  • Consumers should ignore unknown fields and tolerate missing optional ones.
  • Include an event ID, type, version, timestamp, and correlation ID in a standard envelope.
  • Never reuse a field name with different meaning; that silently corrupts historical data and replays.

10Failure handling in the stream

  • Retry transient failures with backoff and jitter; do not retry permanent validation errors forever.
  • A poison message can block a partition, so cap retries and route failures to a dead-letter queue.
  • A DLQ without an owner and a replay procedure is just a graveyard.
  • Backpressure matters: if consumers fall behind, lag grows and data becomes stale.
  • Monitor consumer lag, processing time, retry counts, and DLQ depth as first-class signals.
  • Batch processing needs per-record error handling so one bad record does not fail the whole batch.
  • Consider the transactional outbox so the state change and the publish cannot diverge.
Consume event→Process→Failure→Retry with backoff→Dead-letter→Inspect and replay

11Debugging and observability

  • There is no single call stack, so debugging depends on identifiers and recorded history.
  • Propagate a correlation ID and the event ID through logs, and include the producer and consumer service names.
  • Distributed tracing links the producing request to the downstream consumption, even when it happens later.
  • Record what was processed, when, and by which consumer version.
  • Replay is the event-driven equivalent of rerunning a job: it is powerful, but only safe if consumers are idempotent.
  • A timeline of events for one entity is often more useful than aggregated metrics alone.
  • Without instrumentation, a missing side effect looks identical to a lost event.

12Choreography, orchestration, and fit

  • Choreography lets each service react to events with no central controller; flexible, but the end-to-end flow is emergent.
  • Orchestration uses a coordinator that issues commands and tracks progress; easier to reason about, but more coupling.
  • Choreography suits simple fan-out and independent reactions; orchestration suits multi-step workflows with compensation.
  • Event-driven design fits spiky workloads, cross-service propagation, audit requirements, and slow side effects.
  • It is a poor fit for simple CRUD, strict synchronous consistency, or teams without broker operations experience.
  • Events should not become a distributed database you query for current state; use projections for that.
  • A hybrid — synchronous reads, asynchronous writes and side effects — is often the most practical design.

13Designing an event-driven system

  • Start from the business facts that multiple services care about, and name them in the past tense.
  • Choose the style per event: notification for triggers, state transfer for read models, sourcing only when history is required.
  • Pick partition keys from the entity whose ordering matters, and accept the parallelism that follows.
  • Define the envelope once: event ID, type, version, timestamp, correlation ID, producer.
  • Decide delivery semantics and idempotency strategy before writing consumers.
  • Plan schema evolution, retention, replay, and dead-letter ownership up front.
  • Instrument lag, errors, and DLQ depth, and rehearse replaying a topic.
Identify facts→Define events and envelope→Choose broker and partitions→Implement idempotent consumers→Add schema and DLQ policy→Instrument and rehearse replay

↔Trade-offs to say out loud

  • Decoupling lets consumers be added without producer changes but makes the end-to-end flow hard to see.
  • Asynchronous delivery absorbs spikes and outages but introduces eventual consistency and stale reads.
  • At-least-once delivery avoids loss but requires idempotency and deduplication in every consumer.
  • Partitioned ordering gives scalability and per-key order but not global order, and hot keys limit parallelism.
  • Event-carried state removes callbacks but duplicates data and enlarges contracts.
  • Event sourcing provides a full audit log but demands snapshots, projections, and historical schema migration.
  • Replay enables recovery and new projections but can re-trigger side effects if consumers are not idempotent.
  • A broker adds resilience and buffering but is another stateful system to operate and secure.
  • Choreography is flexible but hides the workflow; orchestration is visible but centralizes control.

?Interview questions

Answer aloud before opening the outline.

1. What is event-driven architecture?

A style where services communicate by producing and consuming events through a broker instead of calling each other directly. The producer publishes a fact and does not know the consumers, which decouples services in time, space, and change.

2. What is the difference between an event and a command?

An event is a past-tense fact that already happened and cannot be rejected, and it can have many consumers. A command is a request with one intended recipient that can fail or be refused. Sending commands through an event channel hides ownership and error handling.

3. Explain notification versus state transfer versus event sourcing.

Notification carries only an ID and makes consumers call back. State transfer carries the changed fields so consumers update local copies. Event sourcing stores the events as the source of truth and derives state by replay. They differ in payload size, coupling, and how much history you must keep.

4. How do you guarantee ordering?

You cannot cheaply guarantee global order; guarantee it per partition by choosing a partition key that matches the entity. Ordering also requires the consumer to process a partition sequentially. If you need resilience to out-of-order delivery, add version numbers and reject stale updates.

5. How do you handle duplicate events?

Assume at-least-once delivery and make consumers idempotent: a natural key, a processed-event table, or a conditional write. Deduplicate on an event ID with a bounded retention window. Producer retries and offset-commit crashes both create duplicates, so the event ID must exist before the first send.

6. What does exactly-once delivery really mean?

Usually it means at-least-once delivery combined with idempotent or transactional processing inside one broker ecosystem. It does not generally span an arbitrary external database and a broker, so cross-system effects still need idempotency or a transactional outbox.

7. How do you deal with eventual consistency?

Accept that read models lag, make projections converge, and expose pending states in the UI. Route reads that must see the latest write to the source, or wait for a version marker. Add reconciliation for cases where retries and compensations fail.

8. How do you evolve event schemas?

Treat schemas as public contracts: additive optional fields are safe, while renames, removals, and semantic changes break consumers. Use a schema registry with compatibility checks, version events explicitly, include a version in the envelope, and support two versions during migration.

9. What happens when a consumer repeatedly fails?

Cap retries with backoff, then route the event to a dead-letter queue so it stops blocking the partition. A DLQ needs an owner, alerting, and a documented replay path. Batch consumers also need per-record failure handling so one poison record does not fail everything.

10. How do you debug an event-driven system?

Propagate a correlation ID and event ID through logs and traces, record which consumer version processed what, and keep an event timeline per entity. Distributed tracing links production to later consumption. Missing side effects are otherwise indistinguishable from lost events.

11. What is the transactional outbox and why does it matter?

It writes the database change and the outgoing event record in the same local transaction, then a relay publishes the event. This avoids the dual-write problem where the database commits but the publish fails, or the reverse, leaving state and events inconsistent.

12. Choreography or orchestration?

Choreography has services react to events with no central controller and suits simple fan-out and independent reactions. Orchestration uses a coordinator that tracks steps and is easier to reason about for multi-step workflows with compensation. Choose based on workflow complexity and how much visibility you need.

13. When would you avoid event-driven architecture?

For simple CRUD, strict synchronous consistency, or small systems where a direct call is clearer. Events add a broker to operate, eventual consistency, duplicate handling, schema management, and harder debugging. Use a hybrid: synchronous reads with asynchronous side effects.

14. How do you prevent a consumer from falling permanently behind?

Monitor consumer lag and processing rate, scale consumers up to the partition count, and reduce per-event work. Add backpressure and alert on growing lag. If lag is structural, increase partitions or split the topic — but changing partitions affects key-to-partition ordering.

!Traps

  • Using events as remote procedure calls and expecting an immediate reply.
  • Publishing events before the database transaction commits, so consumers read stale state or the event is lost.
  • Assuming ordering across a whole topic instead of within a partition.
  • Building consumers that are not idempotent on an at-least-once broker.
  • Treating a dead-letter queue as a solution without an owner or replay procedure.
  • Letting the event log become the primary query surface instead of building projections.
  • Changing an event field's meaning without versioning it, silently corrupting replays.
  • Adding a broker without monitoring lag, retries, and schema compatibility.
