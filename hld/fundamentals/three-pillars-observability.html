Observability
The ability to understand a system's internal state from the telemetry it emits, so you can ask new questions during an incident without shipping new code.
Monitoring
Watching a predefined set of signals against thresholds and alerting when they cross, which only catches failures you already anticipated.
Counter
A monotonically increasing metric, such as total requests or errors, queried as a rate or an increase over a window.
Gauge
A metric that moves both up and down, such as active connections or queue depth, read as a current value.
Histogram
A metric that counts observations into buckets so percentiles such as p95 and p99 can be computed later.
Cardinality
The number of distinct label-value combinations a metric produces; each new combination creates a separate time series.
Structured logging
Writing each log entry as named key-value fields rather than free text, so it can be filtered and aggregated precisely.
Span
One unit of work inside a trace, recording its operation name, start and end time, status, parent span, and attributes.
Trace
The tree of spans produced by a single request as it moves through services, all sharing one trace ID that acts as the join key for logs and exemplars.
Sampling
Keeping only a fraction of traces to control cost, decided either at request start (head) or after completion (tail).

01The problem: one slow checkout

A single user action can cross an API gateway, an order service, a payment service, an inventory service, a cache, and a database. When that action slows down, the interesting question is not is something broken but which hop, for which users, since when.

  • On one machine you would read the log file and check CPU. In a distributed system there is no single file and no single CPU graph.
  • The request may touch many services, each with many replicas, so the evidence is scattered across hosts and containers.
  • Short-lived containers take their filesystem logs with them when they are replaced, so evidence can disappear before you look.
  • Symptoms are often partial: slow only for one card type, one region, or one tenant, which aggregate health checks never show.
  • You need the system to describe its own internals, because you cannot attach a debugger to production traffic.
  • Observability is that capability: emit enough well-structured telemetry that new questions are answerable with queries, not code changes.

02Monitoring vs observability

The two words are often used interchangeably, but they describe different relationships between the questions and the data.

  • Monitoring starts from a known failure mode: pick signals in advance, set thresholds, alert on breach.
  • Monitoring answers is the error rate above 1%; it cannot answer why is checkout slow only for this card type in this region.
  • Observability starts from arbitrary questions and works backwards through high-dimensional data.
  • Observability requires wide events with many attributes, retained long enough and joinable across services.
  • A system is not observable because it has three tools installed; it is observable if an engineer can answer an unanticipated question quickly.
  • In practice you need both: monitoring for fast, cheap detection of known breakage; observability for diagnosis of the novel case.

03One question per pillar

Each pillar is optimized for a different shape of question. Choosing the wrong one is the most common reason an investigation stalls.

  • Metrics answer is something wrong, and when did it start: the checkout error rate jumped from a low baseline to a much higher one.
  • Logs answer what exactly happened to this one thing: this payment request failed with a connection timeout to the fraud service.
  • Traces answer where did the time go: the request spent most of its duration waiting on the fraud check call.
  • Metrics are cheap enough to keep on every service and alert on; logs are detailed enough to explain a single event; traces are the only pillar that preserves cross-service causality.
  • None is sufficient alone: a metric shows a symptom, a trace localizes it, a log explains the mechanism.
  • Start broad with metrics, narrow with traces, then confirm the mechanism with logs.
Alert on a metric (something is wrong)→Open slow traces (where the time went)→Search logs by trace ID (why it happened)→Fix, then watch the same metric recover

04Metrics and metric types

A metric is a numeric measurement recorded over time, identified by a name plus a set of labels.

  • A counter only increases — requests served, errors, bytes sent — and is queried as a rate per second or an increase over a window.
  • A gauge goes up and down — active connections, queue depth, memory in use — and is read as a current, min, or max value.
  • A histogram counts observations into buckets so the median, p95, or p99 can be computed after the fact.
  • Labels turn one metric name into many series: a request counter labeled by service, endpoint, and status code.
  • Labels are what make metrics queryable — without them you know an endpoint failed, not which endpoint.
  • Status codes, regions, and instance roles are good label dimensions; user IDs and request IDs are not.

05Why metrics are cheap, and where they mislead

  • A metric stores a summary, not every event: the request counter is one number whether the service handles a hundred or a hundred thousand requests per second.
  • That compactness is why metrics drive most dashboards and every threshold alert — storage and query cost stay flat as traffic grows.
  • Aggregation is also the weakness: an average can look healthy while a small fraction of users suffer badly.
  • If most requests take tens of milliseconds and one percent take seconds, the mean hides the tail entirely — track p95 and p99 instead.
  • The four golden signals — latency, traffic, errors, saturation — are a good default set per service.
  • Saturation matters because it is the leading indicator; latency and errors are what you see after the resource is already exhausted.
  • Metrics cannot tell you which order failed or why, because the individual record was discarded at write time.
Percentiles cannot be averaged across instances. Aggregate the underlying histogram buckets, or compute the percentile per instance and compare.

06Cardinality: the hard limit on metrics

  • Every unique combination of label values is a separate time series with its own storage and index cost.
  • Adding a high-cardinality label such as user ID or order ID can multiply one metric into millions of series.
  • This is the high cardinality problem, and it degrades the metrics backend for every team, not just the one that added the label.
  • High cardinality also slows queries and increases memory pressure on the ingestion path.
  • Keep label values bounded and predictable: service, endpoint template, region, status code, deployment version.
  • Put unbounded identifiers in logs or span attributes instead, where per-event storage is expected.
  • When you need per-request detail from a metric, use an exemplar — a sampled trace ID attached to a bucket — rather than a new label.

07Logs and structured logging

  • A log is a timestamped record of something that happened: a request received, a payment failed, a retry occurred, a job finished.
  • Logs are the most detailed pillar and the one you reach for after you already know roughly where to look.
  • Free-text lines are readable but expensive to query, because the backend must guess where each field starts and ends.
  • Structured logging writes each entry as named fields — timestamp, level, service, order ID, error type, retry count — usually as JSON.
  • Named fields enable precise filters such as errors from the payment service in the last hour where error type is timeout.
  • Emit one entry per meaningful outcome, not one per line of code; a request that produced five log lines is five times the volume to search.
  • Always include a correlation identifier — trace ID or request ID — so entries from different services can be joined.

08The limits of logs

  • Volume is the dominant cost: a busy system can emit enormous amounts of log data, and indexing all of it is expensive.
  • Log levels are the first control — debug in development, info or warning in production for hot paths.
  • Logs live on many machines and inside short-lived containers, so local files vanish when the instance is replaced.
  • Central shipping is mandatory for production, but it introduces its own failure modes: agent backpressure, dropped batches, delayed arrival.
  • Logs describe events inside one service; they do not by themselves reconstruct a request's path across six services.
  • Ordering is unreliable: clock skew between hosts makes naive timestamp sorting misleading during an incident.
  • Sensitive data creeps in easily, so redaction has to happen at emit time, not at query time.

09Traces, spans, and the request tree

A trace follows a single request through the whole system. Each unit of work inside it is a span.

  • A checkout trace might contain spans for the gateway, order service, inventory call, payment call, and fraud check, nested by who called whom.
  • A span records a trace ID, its own span ID, its parent span ID, an operation name, start and end times, a status, and attributes.
  • Parent links turn the spans into a tree, which is what lets a tool reconstruct the call path rather than just a list of timings.
  • Span attributes carry the useful dimensions — HTTP route, database statement shape, queue name, retry count — without polluting metrics cardinality.
  • The root span measures the user-visible latency; child spans partition that latency by dependency.
  • Self time (span duration minus time waiting on children) is what separates a slow service from a slow dependency.
  • Traces capture causality, which neither metrics nor logs can express: this call delayed that response.

10Propagating trace context

  • Every service in the path must know which trace a request belongs to, or the trace fragments into disconnected pieces.
  • The entry service generates a trace ID and passes it downstream, typically in an HTTP header.
  • The W3C Trace Context standard defines the traceparent header carrying the trace ID, parent span ID, and sampling flags.
  • Each downstream service reads the header, creates a child span under the same trace ID, and forwards the context on its own outbound calls.
  • Propagation must cross every boundary: HTTP clients, message queues, background jobs, and scheduled tasks that continue earlier work.
  • A single library or service that drops the header breaks the chain, so use auto-instrumentation rather than hand-rolled propagation.
  • Headers are also a trust boundary: accept context from untrusted callers only if you can tolerate spoofed trace IDs in your data.

11Reading a waterfall, and the cost of sampling

Tracing UIs render a trace as a waterfall: each span is a horizontal bar whose length is its duration, nested by parent.

  • The waterfall shows instantly whether latency sits in the service's own code, in a downstream call, or in serialization.
  • It also exposes structure that metrics hide: calls executed sequentially that could run in parallel, or a retry storm inside one dependency.
  • Recording every span of every request is usually unaffordable, so traces are sampled.
  • Head-based sampling decides at request start and keeps a fixed percentage; it is simple, cheap, and blind to outcome.
  • Tail-based sampling buffers spans until the request finishes, then keeps all errors and slow traces plus a small sample of normal ones.
  • Tail sampling needs a collector tier that can hold traces in memory and route by trace ID, which is significant infrastructure.
  • The sampling decision must be propagated, or different services will disagree about whether a trace exists.

12Working the pillars together

The pillars pay off as a sequence, not as three separate tools. The typical investigation moves from symptom to location to mechanism.

  • Detect with metrics: p99 latency for checkout crosses its threshold, and a per-service breakdown shows the payment service degrading first.
  • Localize with traces: several slow checkout traces all show the payment-to-fraud-check call consuming most of the duration.
  • Explain with logs: searching logs for that trace ID shows the fraud service exhausting its database connection pool.
  • Each step narrows the search space, so you never grep across the whole fleet.
  • The direction matters: starting with logs during a broad outage means reading millions of lines with no filter.
  • The conclusion should be a mechanism you can fix, not just a service name you can restart.
Alert fires on a metric→Break the metric down by service or endpoint→Open exemplar or slow traces for that window→Find the dominant span in the waterfall→Search logs by trace ID for the mechanism→Fix and confirm on the original metric

13Correlation, instrumentation, and OpenTelemetry

  • Correlation is what turns three datasets into one investigation; the trace ID is the primary key joining them.
  • Put the trace ID in every log line and in error responses, so support and engineering can jump straight to the trace.
  • Exemplars attach sample trace IDs to metric buckets, so a spike on a latency chart links to a real request.
  • Instrumentation is the code that produces this data; HTTP, database, and queue libraries can emit spans and metrics automatically.
  • Business metrics — orders per minute, checkout conversion — still have to be added deliberately, because no library knows your domain.
  • OpenTelemetry provides vendor-neutral APIs, SDKs, and a wire format for all three signals, so changing backends does not mean re-instrumenting.
  • A collector in front of the backends handles batching, sampling, redaction, and fan-out to different stores.
  • Instrumentation rule of thumb: if this broke during an incident, what would I need to know? Capture that by default.
Collecting all three signals does not make a system observable. The links between them — trace ID in logs, exemplars on metrics — are what reduce diagnosis time.

↔Trade-offs to say out loud

  • Metrics are cheap to store and fast to query but aggregate away the per-request detail you need to explain a failure.
  • Logs preserve full detail per event but cost the most in volume, indexing, and PII exposure.
  • Traces are the only pillar that shows cross-service causality, but they require context propagation everywhere and generate large data volumes.
  • Rich labels make metrics more queryable but multiply time series and can take down the metrics backend under high cardinality.
  • Head-based sampling is simple and cheap but can discard exactly the rare failure you are investigating.
  • Tail-based sampling keeps the interesting traces but requires buffering infrastructure and more operational capacity.
  • Verbose logging speeds diagnosis but raises cost and the chance that secrets or personal data land in the log store.
  • Full-fidelity tracing answers any question after the fact but is usually unaffordable at high request rates.

?Interview questions

Answer aloud before opening the outline.

1. What is observability, and how is it different from monitoring?

Observability is the ability to infer a system's internal state from the telemetry it emits, including questions nobody anticipated. Monitoring watches a predefined set of signals against thresholds. Monitoring tells you that a known condition is breached; observability lets you investigate a condition you never wrote an alert for.

2. Why do you need all three pillars?

They answer different questions: metrics say whether and since when something is wrong, traces say where in the request path the time or error sits, and logs say what exactly happened. Removing any one leaves a gap — metrics lose the individual request, logs lose the cross-service path, traces lose the fine-grained event detail.

3. When would you choose a counter over a gauge?

Use a counter for something that only accumulates, such as requests, errors, or bytes, because you can derive rates and totals from it without losing information. Use a gauge for a value that rises and falls, such as queue depth or active connections, where the current value is the signal and history matters less.

4. Why are percentiles preferred over averages for latency?

An average is dominated by the fast majority and hides the slow tail. If most requests are fast and a small fraction take seconds, the mean can look healthy while real users are suffering. p95 and p99 describe the experience of the slowest users, which is usually what triggers complaints and timeouts.

5. What is the high cardinality problem?

Each unique label-value combination is a separate time series, so a label like user ID or order ID can multiply a single metric into millions of series. That inflates storage and memory, slows queries, and can destabilize the metrics backend. Keep labels bounded and move unbounded identifiers into logs or span attributes.

6. Why is structured logging better than plain text?

Structured entries store each value in a named field, so the backend does not have to guess boundaries with regular expressions. That makes filtering, aggregation, and dashboarding reliable, and it lets you query by field such as error type or tenant. Plain text is readable but expensive and brittle to search at scale.

7. What is a span, and what does it contain?

A span is one unit of work inside a trace, such as an HTTP handler or a database call. It carries a trace ID, its own span ID, a parent span ID, an operation name, start and end timestamps, a status, and attributes describing the work. The parent links are what allow a tool to rebuild the request tree.

8. How does trace context propagate across services?

The first service creates a trace ID and sends it downstream, usually in the traceparent header defined by W3C Trace Context. Each service creates a child span under that trace ID and forwards the context on its outbound calls, including to message queues and background jobs. If any hop drops the header, the trace splits.

9. Head-based versus tail-based sampling — what would you pick?

Head-based sampling decides at request start and keeps a fixed fraction: trivial to implement, no buffering, but it can discard the rare error you need. Tail-based sampling buffers spans until the trace completes and can keep every error and slow trace. Start with head-based for cost control, and add tail-based when investigating rare failures matters more than infrastructure simplicity.

10. How do you connect a metric spike to the logs that explain it?

Attach exemplars to histogram buckets so a spike links to a sampled trace ID, then search the log store for that trace ID. This requires every log line to include the trace ID of the request that produced it, and every service to propagate trace context. Without those two links, you end up matching timestamps by hand across thousands of concurrent requests.

11. What would you instrument first in a new service?

Start with the four golden signals — latency percentiles, traffic, errors, and saturation — plus spans on inbound requests and outbound dependencies. Then add business-level counters that reflect user outcomes, such as orders placed. The test is whether an on-call engineer could answer what is broken and where without deploying new code.

12. Why can collecting all three signals still leave a system unobservable?

Because the value comes from the links between them. If logs carry no trace ID, if metrics have no exemplars, and if trace context breaks at one service, an engineer still has three disconnected tools. Observability is a property of the joins and the data quality, not of the number of agents installed.

!Traps

  • Installing metrics, logs, and traces but never linking them, so incidents still require manual timestamp matching.
  • Adding user ID or request ID as a metric label and creating a cardinality explosion.
  • Reporting average latency in reviews and dashboards while the p99 is timing out users.
  • Instrumenting a service with rich telemetry but letting one downstream library drop the trace header.
  • Logging everything at info level in production and then being unable to afford the log bill or find the signal.
  • Treating observability as a purchased tool rather than as data emitted deliberately by the application.
  • Confusing monitoring coverage with observability: a hundred green dashboards can coexist with an undiagnosable outage.
