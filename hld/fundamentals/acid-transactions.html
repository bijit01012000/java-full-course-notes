In one lineACID transactions let an application group several operations into one all-or-nothing unit, so a crash or a concurrent request cannot leave the data half-updated — at the cost of latency, locking, and throughput.
Transaction
A group of database operations treated as a single unit of work that commits as a whole or rolls back.
Atomicity
The guarantee that either every change in a transaction is applied or none of them is.
Consistency (ACID)
The guarantee that a transaction moves the database from one valid state to another, with all declared rules still holding.
Isolation
The guarantee that concurrent transactions do not observe or corrupt each other's half-finished work.
Durability
The guarantee that a committed change survives a crash or power loss immediately afterward.
Dirty read
Reading a value written by another transaction that has not committed and may still roll back.
Isolation level
A named setting that chooses which concurrency anomalies the engine prevents, trading correctness for throughput.
MVCC
Multi-version concurrency control: keeping several versions of a row so readers see a consistent snapshot without blocking writers.
Write-ahead log
An append-only log of changes that is flushed before commit, used to replay committed work and discard incomplete work after a crash.

01The problem

Alice transfers $100 to Bob. The application must deduct from Alice and credit Bob — two writes that only make sense together.

  • The server can crash between the two writes, leaving money deducted from Alice and never credited to Bob.
  • Two transfer requests can arrive at the same time, both read a $100 balance, and both proceed.
  • Both problems come from the same root cause: several operations that must behave as one, plus concurrency.
  • Application-level cleanup code for every partial-failure case is exactly what a database transaction replaces.
  • A transaction needs three things: group the operations, survive failures safely, and stop concurrent requests from interfering.

02What a transaction is

  • A transaction begins, performs reads and writes, and then either commits or rolls back.
  • Commit makes all changes permanent and visible; rollback undoes every change the transaction made.
  • In SQL the shape is BEGIN, then the statements, then COMMIT or ROLLBACK.
  • The boundary is a design decision: too wide and locks and conflicts grow, too narrow and related changes escape the guarantee.
  • The four properties that make this useful are summarized as ACID.
  • Each property addresses a different failure: crash, rule violation, concurrency, and lost storage.
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 100 WHERE id = 'bob';
COMMIT;

03Atomicity

  • Atomicity means all or nothing: every change in the transaction applies, or none does.
  • If the crash happens mid-transaction, recovery rolls back the partial work, so both balances return to their pre-transfer values.
  • Because no partial state is ever visible or persisted, the application can simply retry a failed transaction.
  • Atomicity covers the transaction's own writes; it says nothing about whether concurrent transactions conflict.
  • Without it, every failure path needs bespoke compensation logic, which is where subtle data corruption starts.

04Consistency

  • Consistency means a transaction takes the database from one valid state to another, where valid is defined by rules.
  • Rules the engine can check — non-negative balance, unique email, foreign key to an existing customer — are enforced as constraints.
  • A violating statement is rejected and the transaction rolls back; nothing partial survives.
  • Rules the engine cannot know, such as total money across all accounts is unchanged, remain the application's job.
  • So consistency is a joint guarantee: the schema enforces structure, the code must enforce business invariants.
  • Beware the overloaded word: ACID consistency means rules hold, while CAP consistency means every read sees the latest write.
  • A transaction can be ACID-consistent and still violate business logic if the application never encoded that logic anywhere.

05Isolation

  • A busy database runs thousands of transactions concurrently, and isolation decides how much they can see of each other.
  • The ideal is serializable behavior: the outcome equals some order of running them one at a time.
  • In the transfer example, proper isolation makes the second request see the reduced balance and fail instead of double-spending.
  • Perfect isolation costs concurrency: transactions wait on locks or get aborted and retried.
  • So engines offer a ladder of isolation levels, and the application chooses how much anomaly it can tolerate.
  • Isolation is the ACID property most often weakened in production, usually without anyone writing it down.

06Isolation anomalies

Each anomaly is a specific way an interleaving of two transactions produces a result no serial order could produce.

  • Dirty read: transaction B reads Alice's new balance, but A rolls back, so B acted on a value that never existed.
  • Non-repeatable read: B reads the same row twice and gets different values because A committed an update in between.
  • Phantom read: B runs a range query twice and a new matching row appears because A inserted one.
  • Lost update: A and B both read a value, both compute from it, and the second write erases the first.
  • Lost update is the classic double-spend: two requests read $100 and each writes a $0 balance after sending $100.
  • Dirty and non-repeatable reads concern one row; phantoms concern the set of rows a predicate matches.
  • The anomalies are not academic — each maps to an application bug such as overselling stock or overwriting a profile edit.

07Isolation levels

The SQL standard defines four levels, each preventing a different subset of anomalies.

  • Read Uncommitted allows dirty reads; it is rarely appropriate for important data.
  • Read Committed shows only committed data, preventing dirty reads, but allows non-repeatable and phantom reads. It is the common default in PostgreSQL, Oracle, and SQL Server.
  • Repeatable Read also prevents non-repeatable reads: a row read once keeps returning the same value. It is the default in MySQL's InnoDB.
  • Serializable makes concurrent transactions behave as if they ran one at a time, preventing all four anomalies.
  • Stronger levels mean more waiting, more aborts, and lower throughput, so they are chosen per workload, not per database.
  • Implementations are not identical: PostgreSQL's Repeatable Read also prevents phantoms, so the standard's table is a starting point, not a contract.
  • Always confirm the actual behavior of your engine and version before relying on a level for correctness.

08How databases provide isolation

  • Engines use two main families of technique: locking and multi-version concurrency control.
  • Both must also detect and break the conflicts they cannot resolve, or the system would stall.
  • The choice is visible to operators as waiting, aborts, and bloat, not just as a correctness setting.
  • Most production engines combine the two: MVCC for reads, locks or conflict checks for writes.
  • Granularity matters: locking a single row lets unrelated work proceed, while a table lock serializes everything that touches the table.

Locking

  • A transaction that updates a row takes a lock; another writer of that row waits until the lock is released.
  • Simple and easy to reason about, but under contention transactions spend their time queuing.
  • Deadlock: A holds row 1 and waits for row 2 while B holds row 2 and waits for row 1, so neither can proceed.
  • The engine detects the cycle and aborts one transaction, which the application must then retry.
  • Lock duration is set by transaction length, so a slow external call inside a transaction multiplies contention.

Multi-version concurrency control

  • Instead of overwriting a row in place, the engine keeps multiple versions and tags each with the transaction that created it.
  • A reader sees the snapshot that was current when its transaction or statement started.
  • So readers do not block writers and writers do not block readers, which is why MVCC dominates read-heavy workloads.
  • Writers that target the same row still conflict, so the engine uses row locks or first-updater-wins checks.
  • Old versions must be cleaned up later; if a long transaction holds an old snapshot, that cleanup is delayed.
  • PostgreSQL and InnoDB both rely heavily on MVCC alongside locks for conflicting writes.

09Durability and write-ahead logging

  • Durability means a committed transaction survives a crash or power loss immediately after the commit returns.
  • The commit must therefore be recorded on durable storage before the application is told it succeeded.
  • Writing every modified page at commit would be slow and scattered, so engines write a log first.
  • Write-ahead logging appends the change records sequentially, flushes the log at commit, and writes data pages later in the background.
  • Sequential log writes are far cheaper than updating scattered pages, which is what makes fast commits possible.
  • After a crash, the log is replayed: committed records reach the data files, incomplete transactions are discarded.
  • One mechanism therefore delivers both atomicity and durability.
  • Some engines let you relax durability — for example by acknowledging before the log is flushed — and then recently committed transactions can vanish in a crash.
Begin transaction→Write change records to the WAL→Flush WAL to disk→Acknowledge commit→Write data pages in the background→Replay the WAL after a crash

10The cost of ACID

  • Durability adds a flush before acknowledgment, so commit latency is bounded by storage, not CPU.
  • Isolation adds lock waits or version bookkeeping, and stronger levels add aborts and retries.
  • When many transactions touch the same rows — a hot inventory counter, a popular seat — contention becomes the bottleneck.
  • Keep transactions short: never hold a lock while waiting on a slow network call.
  • Use the weakest isolation level that is actually correct for the workload instead of defaulting to Serializable everywhere.
  • Prefer a single atomic statement where possible; it avoids an explicit transaction and its lock window.
  • Design hot paths to spread writes — partitioned counters or queued updates — rather than serializing on one row.
-- One statement, no read-then-write race:
UPDATE accounts
SET balance = balance - 100
WHERE id = 'alice' AND balance >= 100;
-- Zero rows updated means insufficient funds.

11Transactions across multiple databases

ACID is straightforward inside one database. Once a single business operation spans shards or services, no single engine can commit both sides for you.

  • If Alice and Bob live on different shards, the transfer needs two independent commits that must agree.
  • Each database can commit atomically on its own, but coordinating the pair is a distributed systems problem.
  • There are two standard answers with very different guarantees: two-phase commit and the saga pattern.
  • Both add failure modes that do not exist in a single-node transaction.
  • Both also need an answer to did this step happen?, which usually means an idempotency key stored with the operation so a retry cannot apply it twice.

Two-phase commit

  • A coordinator asks every participant to prepare, meaning it can commit on request.
  • If all participants vote yes, the coordinator tells them to commit; if any votes no, it tells all to abort.
  • This gives atomicity across databases, at the cost of an extra round trip and locks held during coordination.
  • If the coordinator dies after prepare, participants stay blocked holding locks until it recovers.
  • Because locks span the whole protocol, throughput suffers and availability depends on the coordinator.

Saga pattern

  • A saga splits the operation into a sequence of local transactions, each committing on its own.
  • If a later step fails, earlier steps run compensating actions that reverse their effects.
  • In the transfer, debit Alice locally, then credit Bob; if crediting fails, refund Alice.
  • No locks are held across services, so availability and throughput stay high.
  • The price is lost isolation: other readers can observe intermediate states before the saga completes.
  • Compensations must be idempotent and retryable, because the failure may itself be ambiguous.

12ACID vs BASE

  • BASE stands for Basically Available, Soft State, Eventual Consistency and is usually associated with NoSQL systems.
  • The system stays available and scalable even when replicas disagree, and updates propagate until they converge.
  • That fits view counts, likes, feeds, and analytics, where a temporarily stale number is harmless.
  • It does not fit balances, inventory, or seat reservations, where a stale read means real loss.
  • The divide is blurrier than the acronyms suggest: many NoSQL engines now offer transactions, and distributed SQL engines offer ACID across machines.
  • So the useful question is what guarantee this specific data needs, not which camp the database belongs to.

13When to use ACID transactions

  • Use them when a partial or conflicting update would cause harm that cannot be repaired later.
  • Classic fits: payments and transfers, account balances, inventory and orders, seat reservations, coupon redemption.
  • The common thread is a shared resource with a rule — money that must balance, stock that must not go negative.
  • Analytics events, application logs, activity counters, and view counts can usually tolerate weaker guarantees.
  • A practical architecture keeps critical data in a transactional store and relaxes elsewhere.
  • Choose the guarantee per data set, and write down the assumption so nobody later moves balance data into the eventually consistent path.

↔Trade-offs to say out loud

  • Atomicity removes partial-write bugs but requires the engine to keep undo information until commit, which costs space and recovery time.
  • Durability survives crashes but forces a storage flush before acknowledgment, adding commit latency.
  • Serializable isolation eliminates every anomaly but causes more waiting and aborts, cutting throughput on contended rows.
  • Weaker isolation levels raise concurrency but leave specific anomalies for the application to handle.
  • MVCC keeps readers from blocking writers but retains old row versions that must be cleaned up, and long snapshots delay that cleanup.
  • Row locking is simple to reason about but serializes hot rows and risks deadlocks.
  • Two-phase commit gives cross-database atomicity but holds locks across a network round trip and stalls if the coordinator fails.
  • Sagas avoid distributed locks but expose intermediate states and require correct, idempotent compensating actions.
  • Long transactions simplify application logic but widen lock windows and increase conflict and bloat.

?Interview questions

Answer aloud before opening the outline.

1. What is a transaction in one sentence?

A group of database operations treated as a single unit of work that either commits all of its changes or rolls all of them back. It exists so the application does not have to implement its own recovery for every partial-failure case.

2. Walk through the four ACID properties.

Atomicity makes the group all-or-nothing. Consistency keeps declared rules and constraints satisfied. Isolation stops concurrent transactions from seeing or corrupting half-finished work. Durability keeps committed changes after a crash.

3. Isn't ACID consistency the same as CAP consistency?

No. In ACID, consistency means the data still satisfies its declared rules and invariants after the transaction. In CAP, consistency means every read observes the most recent write, as if there were a single copy. The same word describes different guarantees.

4. Explain the four isolation anomalies.

A dirty read sees uncommitted data that may roll back. A non-repeatable read sees the same row change between two reads because another transaction committed. A phantom read sees a new row appear in a repeated range query. A lost update loses one of two read-modify-write cycles.

5. Which isolation level should you use?

Start from the engine's default, usually Read Committed, and raise it only for operations whose invariants require it — a balance check, an inventory decrement, a seat booking. Higher levels buy correctness with waiting and retries, so applying Serializable everywhere is usually a throughput mistake.

6. How does MVCC improve concurrency?

It keeps multiple versions of a row so a reader can use the snapshot from when its transaction started. Readers therefore never block writers and writers never block readers. Writers that touch the same row still conflict and are resolved with locks or conflict detection.

7. What causes a deadlock and how is it handled?

Two transactions each hold one lock and wait for the other's, forming a cycle. The engine detects the cycle and aborts one transaction so the other can finish, and the aborted one must be retried. Short transactions and consistent lock ordering reduce the frequency.

8. How does a write-ahead log give two ACID properties at once?

Change records are appended to the log and flushed before commit, so a committed transaction is durable even if data pages are still unwritten. On restart, committed log records are replayed and incomplete transactions are discarded, which restores atomicity.

9. Why is a long transaction dangerous?

It holds locks and an old snapshot for its whole duration, so other writers queue and old row versions cannot be reclaimed. If it includes a slow network call, every transaction touching the same rows waits on that call. Keep the transaction to the database work and do external calls outside it.

10. How would you fix the double-spend race?

Either raise isolation so the two read-modify-write cycles conflict, or collapse them into one statement — UPDATE ... SET balance = balance - 100 WHERE id = ? AND balance >= 100 — and treat zero affected rows as insufficient funds. The single statement removes the window without a long transaction.

11. Compare two-phase commit and sagas.

Two-phase commit gives atomicity across databases by preparing all participants and then committing them together, but it holds locks across the protocol and stalls if the coordinator dies. A saga runs local transactions and compensates on failure; it avoids distributed locks but exposes intermediate states and needs idempotent compensations.

12. When is BASE acceptable?

When a briefly stale or out-of-order read causes no financial or safety harm — view counts, likes, feeds, logs, recommendations. It is not acceptable for balances, inventory, reservations, or authorization decisions, where staleness can double-spend or leak access.

!Traps

  • Assuming a transaction makes concurrent requests safe when the isolation level still allows lost updates.
  • Holding a transaction open across an HTTP call, so locks are held for the duration of a network timeout.
  • Choosing Serializable everywhere and then blaming the database for low throughput.
  • Confusing ACID consistency (rules hold) with CAP consistency (latest write visible).
  • Relying on the SQL standard's isolation table without checking the actual engine's behavior.
  • Believing cross-service operations are atomic because each service uses a transaction locally.
  • Writing a saga compensation that is not idempotent, so a retry reverses a step twice.
