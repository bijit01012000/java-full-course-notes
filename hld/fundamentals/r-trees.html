In one lineAn R-tree wraps every shape in a bounding rectangle, groups nearby rectangles into larger ones, and prunes whole groups whose boxes cannot touch the query — which is why it is the index behind most spatial databases.
R-tree
A height-balanced tree of nested bounding rectangles that indexes objects by the space they occupy rather than by a single point.
Minimum bounding rectangle (MBR)
The smallest axis-aligned rectangle that fully contains an object or a group of objects.
Fanout
The maximum number of entries in one node, usually chosen so a node fits one disk page.
Least enlargement
The insertion heuristic that places a new rectangle in the child whose MBR grows the least to include it.
Node split
Dividing an overfull node into two groups so each MBR covers as little area and overlap as possible.
Condensation
The deletion cleanup that removes underfull nodes and reinserts their orphaned entries.
Mindist
The minimum possible distance from a query point to a node's rectangle, used to order best-first nearest-neighbor search.
R* tree
A variant that chooses splits and reinserts entries to minimize MBR overlap, not just area.

01The problem: objects with extent

A food-delivery app stores a delivery zone per restaurant. The zones are irregular polygons that follow streets, rivers, and neighborhood boundaries.

  • A customer's request becomes the question "which zones contain this point?"
  • Answering it means a point-in-polygon test per zone, and polygons can have hundreds of edges.
  • With a very large number of restaurants, testing every polygon per request is far too slow.
  • The real cost is not the geometry alone but doing it for every object on every query.
  • The fix must eliminate zones that are nowhere near the customer before any geometry runs.
  • That is a filtering problem: cheap approximate rejection first, exact computation on the survivors.

02Why point indexes struggle with shapes

  • Geohash and quadtrees assign each point to exactly one cell, which makes them easy to organize and search.
  • A shape has extent: a delivery zone can cover many cells at once.
  • With a geohash, the same zone must be written into every cell it overlaps, and a large zone can overlap a very large number of small cells.
  • That duplication inflates storage and forces the write path to touch many keys when a zone changes.
  • In a quadtree, a zone crossing a node boundary does not fit in a single child.
  • The options are to store it in several children or keep it at an ancestor, where more queries must inspect it.
  • The conclusion: instead of cutting space into fixed regions, organize objects by the space they actually occupy.

03The core idea: bounding rectangles

  • Wrap every object in its minimum bounding rectangle, the tightest axis-aligned box that contains it.
  • Group nearby rectangles and wrap the group in a larger bounding rectangle.
  • Repeat upward until one root rectangle contains everything.
  • The tree therefore stores rectangles at every level: leaves point at the real geometry, internal nodes point at children.
  • A search compares the query region with these rectangles and skips any subtree whose box cannot intersect it.
  • For most queries the boxes reject almost everything, so exact geometry runs on very few objects.
  • The hierarchy is approximate by design: a rectangle is a cheap, conservative summary of a shape.
Bounding boxes only ever grow: they must contain their contents, so they can overlap each other even when the underlying shapes do not.

04Tree structure

  • The tree is height-balanced: every leaf sits at the same depth, so search cost is bounded.
  • Leaf entries hold an MBR plus a reference to the object, or the object's identifier.
  • Internal entries hold an MBR plus a pointer to a child node.
  • Each node has between a minimum and maximum number of entries; the maximum (fanout) is usually sized to one disk page.
  • The minimum fill keeps nodes from becoming nearly empty after deletions, at the cost of more complex maintenance.
  • A node's MBR is exactly the bounding box of all entries beneath it, so ancestors must be updated when descendants change.
  • Because nodes map to pages, a query typically costs a handful of page reads rather than a scan.

05Search

  • Start at the root and compare each entry's MBR with the query region.
  • If the boxes are disjoint, prune that subtree entirely — no geometry, no page reads below it.
  • If they intersect, descend and repeat; at the leaves, run the exact predicate.
  • The exact predicate depends on the query: point-in-polygon, rectangle intersection, containment, or distance.
  • A point query is just a degenerate region, so it follows the same path.
  • Boxes are conservative, so survivors include false hits; exact geometry removes them.
  • The cost is driven by how much the MBRs overlap, not by how many objects exist.
Test root MBR against query→Prune disjoint subtrees→Descend into overlapping children→At leaf: run exact geometry→Return matches

06Insertion

  • Descend from the root, at each level choosing the child whose MBR must grow least to include the new rectangle.
  • Ties are broken by smallest resulting area, which keeps boxes tight.
  • Insert the entry at the chosen leaf.
  • If the leaf overflows, split it into two groups and propagate the new rectangles upward.
  • If the root splits, a new root is created, which is the only way the tree grows in height.
  • Then enlarge the MBRs along the path back to the root.
  • The choice of path is greedy and local: a locally cheap insertion can make later searches worse, which is why split quality matters.

07Splits and tree quality

  • A split partitions the overfull entries into two groups, and the quality of that partition decides future query cost.
  • The quadratic split picks the two seeds that waste the most space together, then assigns each remaining entry to the group needing less enlargement.
  • The linear split approximates the same idea with a single pass, trading quality for build speed.
  • Good splits minimize total area, because smaller boxes prune more.
  • They also minimize overlap, because overlapping boxes force a query to follow several paths at once.
  • R* adds forced reinsertion: instead of splitting immediately, it removes some entries and reinserts them, which often avoids a bad split altogether.
  • Bulk loading from spatially sorted data produces far better trees than random insertion.
  • A poorly built tree still answers correctly; it just degenerates toward scanning many leaves.

08Deletion and condensation

  • Find the leaf containing the entry, then remove it.
  • If the node drops below the minimum fill, remove the node and reinsert its remaining entries from the top of the tree.
  • Condensation keeps the tree balanced and prevents nearly empty pages from lingering.
  • Reinsertion is chosen over merging because it can place orphans in better-fitting nodes.
  • Ancestor MBRs must shrink or grow to match their remaining contents; a stale box only costs pruning quality, not correctness.
  • Deleting a shape that spans many leaves is cheap here, unlike cell-based indexes that store duplicates.
  • Frequent updates make R-trees expensive, because each change can touch several pages.

09Nearest-neighbor search

  • Nearest-neighbor queries ask for the closest object, not for everything inside a region.
  • Use mindist: the minimum possible distance from the query point to an MBR.
  • Explore entries in increasing mindist order with a priority queue.
  • Stop when the smallest remaining mindist exceeds the best exact distance found so far.
  • This prunes subtrees that cannot contain a closer object without computing any geometry.
  • k-nearest-neighbor works the same way, stopping when the queue's bound exceeds the k-th best result.
  • The same machinery supports "within distance d" queries by treating d as the stopping bound.

10Variants

  • R+ tree: forbids overlap between sibling MBRs by duplicating objects that straddle a boundary — faster searches, more storage and more insert paths.
  • R* tree: minimizes overlap first and area second, with forced reinsertion; the common default in spatial databases.
  • Hilbert R-tree: orders entries by a space-filling curve so nodes group spatially coherent objects.
  • Priority R-tree: a bulk-loaded variant with provable worst-case query bounds.
  • Variants differ mainly in how they trade build and update cost against search pruning quality.
  • The right choice depends on whether the workload is read-mostly (favor pruning) or update-heavy (favor simpler maintenance).

11Limitations

  • Sibling rectangles may overlap, so a query can be forced to follow several branches at once.
  • As dimensionality rises, boxes overlap more and pruning collapses — the structure is built for two or three dimensions.
  • Updates are heavier than in a point index because they can restructure pages and change ancestor MBRs.
  • The index is approximate by construction, so every candidate still needs an exact predicate.
  • Fanout and fill factor must be tuned to the page size; a node that does not fit a page loses the disk advantage.
  • Large or oddly shaped objects produce large MBRs that cover other data and reduce pruning.
  • Building the index on a live, constantly updated table is often the operational bottleneck.

12Where it is used

  • Spatial databases expose R-trees through a general search-tree framework: PostGIS uses GiST, MySQL has spatial indexes, SQLite ships an R*Tree module.
  • Geographic information systems use them for polygon intersection, containment, and map-window queries.
  • Routing and logistics use them to find zones, road segments, and service areas near a point.
  • Computer-aided design and game engines use them for broad-phase collision and view culling.
  • Choose an R-tree when the objects are shapes, when overlap and containment matter, and when a spatial database is available.
  • Choose a geohash or quadtree when the objects are points, and S2 or H3 when the grid must be globally consistent.

↔Trade-offs to say out loud

  • Bounding rectangles make pruning cheap but are conservative, so candidates still need exact geometry.
  • Overlap minimization improves query pruning but makes splits and inserts more expensive to compute.
  • R+ duplication removes sibling overlap and speeds reads but multiplies storage and insert work.
  • Larger fanout reduces tree height but risks nodes that no longer fit a page.
  • Higher minimum fill keeps pages dense but triggers more condensation after deletions.
  • Forced reinsertion produces better trees but adds write amplification during load.
  • Bulk loading yields compact trees quickly but is a batch operation, not an online one.
  • An R-tree over a point-only workload adds update cost and overlap for capability you do not use.

?Interview questions

Answer aloud before opening the outline.

1. Why can't a geohash index a delivery zone efficiently?

A geohash indexes points, so a zone must be written into every cell it overlaps. A large zone can span a very large number of small cells, which duplicates the row many times and multiplies write cost on every zone change. An R-tree stores the zone once, wrapped in a rectangle sized to the shape.

2. What exactly is stored in an R-tree node?

Internal entries hold a bounding rectangle and a pointer to a child. Leaf entries hold a bounding rectangle and a reference to the actual object or its identifier. A node's rectangle is the bounding box of everything beneath it.

3. How does an R-tree answer "which zones contain this point?"

It descends from the root, testing each child's rectangle against the point and pruning disjoint subtrees. At the leaves it runs the exact point-in-polygon test on the few surviving candidates. The tree never tests polygons that cannot contain the point.

4. Explain the insertion heuristic.

At each level it picks the child whose rectangle has to grow the least to include the new object, breaking ties by smallest resulting area. Then it descends, inserts at the leaf, splits if the leaf overflows, and enlarges the rectangles on the way back up. It is greedy, so split quality matters for future searches.

5. Why is overlap between sibling rectangles so damaging?

If two sibling boxes overlap the query point, the search must follow both branches even though only one can hold the answer. That turns a single tree descent into several, and heavy overlap degenerates into scanning many leaves. This is why R* minimizes overlap before area.

6. What happens when a leaf becomes underfull after a delete?

The node is removed and its remaining entries are reinserted from the top of the tree, a process called condensation. That keeps the tree balanced and pages reasonably full. Reinsertion is preferred over merging because orphans often fit better elsewhere.

7. How does nearest-neighbor search avoid scanning everything?

It orders nodes by mindist, the minimum distance from the query point to their rectangle, and explores the closest first. Once the smallest remaining bound exceeds the best exact distance found, nothing left can be closer, so the search stops.

8. Compare an R-tree with a quadtree.

A quadtree cuts space into fixed nested quadrants, so an object spanning a boundary must be duplicated or stored high in the tree. An R-tree cuts the objects into groups, so each object is stored once regardless of size. Quadtrees suit points in memory; R-trees suit shapes on disk.

9. Why do R-trees degrade in high dimensions?

As dimensions grow, bounding boxes become large and overlap heavily, so the query cannot prune much and visits most of the tree. The structure is designed for two or three spatial dimensions; high-dimensional similarity search needs different indexes entirely.

10. What is the cost of frequent updates?

Each insert or delete can modify several pages, split nodes, and enlarge ancestor rectangles. That is far heavier than appending to a log-structured index, so R-trees are usually paired with read-mostly spatial data or batched updates.

11. How would you build an R-tree for a large existing table?

Bulk load it from data sorted by a spatial ordering such as a Hilbert curve, so each node packs spatially coherent objects. This produces a compact tree far faster than random insertion and avoids many splits. Afterwards, maintenance handles incremental changes.

12. When would you not choose an R-tree?

When the objects are points and a plain indexed column suffices, when the grid must be globally consistent near the poles and date line, or when updates dominate. It is also the wrong tool for high-dimensional vectors, which need approximate nearest-neighbor indexes.

!Traps

  • Treating an MBR intersection as the final answer instead of running the exact geometric predicate.
  • Assuming sibling rectangles never overlap; overlap is allowed and is what degrades search.
  • Using an R-tree for point-only data where a geohash column would add no query cost.
  • Building the index by random insertion and blaming the database for slow spatial queries.
  • Ignoring fanout versus page size, so each node spans multiple pages and loses its I/O advantage.
  • Expecting good pruning in many dimensions; boxes overlap and the tree becomes a scan.
  • Forgetting that an object update changes rectangles along the whole path to the root.
