In one lineA/B testing compares two variants on comparable user groups at the same time, so outside events affect both groups equally and the difference can be attributed to the change.
A/B test
A controlled experiment that sends comparable groups of users different variants simultaneously and compares outcomes.
Control
The existing behavior that the treatment is measured against; without it, differences cannot be attributed to the change.
Randomization unit
The entity that is randomly assigned to a variant, such as a user, session, device, or account.
Assignment
The deterministic mapping of a randomization unit to a variant, usually by hashing an identifier with a salt.
Exposure event
A logged record that a specific unit actually saw a specific variant, which is the basis for correct analysis.
Primary metric
The single outcome the experiment is designed to move, chosen before the test starts.
Guardrail metric
A metric that must not degrade, used to catch harm the primary metric would hide.
Sample ratio mismatch
A significant deviation from the intended traffic split, usually indicating a bug in assignment or logging.

01Why before-and-after comparisons mislead

A redesign ships on Monday and the purchase rate rises by Friday. It is tempting to credit the redesign, but the week also contained a discount campaign, a competitor outage, and a holiday.

  • Any change in the metric could be caused by the release, by external events, or by both.
  • Seasonality, marketing campaigns, competitor behavior, and app-store featuring all move metrics independently.
  • A before-and-after comparison has no way to separate the treatment effect from the calendar.
  • Concurrent comparison solves this: both groups live through the same external events.
  • The remaining difference is then attributable to the variant, within a stated level of uncertainty.
  • This is why experiments are infrastructure, not just a dashboard: assignment, logging, and analysis all have to be correct.

02What an A/B test actually is

  • Users are split into a control group that sees the current experience and a treatment group that sees the variant.
  • The split is random but deterministic per user, so each user gets a stable experience.
  • Both groups are measured over the same period, so external shocks affect them similarly.
  • The comparison is between groups, not between time periods, which is the whole point.
  • Multiple variants can be tested at once, but each additional arm divides the available sample.
  • A test that changes several unrelated things at once cannot attribute the effect to any one of them.

03Assigning users to variants

  • Hash a stable identifier — user ID, account ID, or device ID — together with an experiment salt to get a uniform bucket.
  • Deterministic hashing means reassignment does not happen on refresh, so experience stays stable.
  • Choose the randomization unit to match the decision: user-level for product changes, account-level for B2B features.
  • Session-level assignment is acceptable for low-risk UI tests but leaks across pages and breaks long-term measurement.
  • Device-level assignment splits a single person across variants if they use multiple devices.
  • The assignment function must be shared across services, or different services will disagree about a user's variant.

04Exposure logging

  • Log when a user is actually exposed to a variant, not merely when they were assigned one.
  • Users assigned but never exposed dilute the treatment effect and bias the estimate.
  • Exposure events must carry the experiment key, variant, unit ID, timestamp, and enough context to join with outcomes.
  • Logging from the client is easy to lose; logging on the server is more complete but may miss client-only rendering.
  • Deduplicate exposures so a page refresh does not double-count a user in the denominator.
  • Instrumentation bugs are the most common reason an experiment produces a confident but wrong answer.
Analyze on the exposed population and keep the assignment population as a cross-check; large divergence between them signals a logging problem.

05Choosing metrics before you look

  • Pick one primary metric that represents the decision, and define it precisely before the test starts.
  • Add guardrail metrics that must not degrade, such as latency, error rate, or cancellation rate.
  • Add counter-metrics for the obvious way to game the primary metric, such as revenue rising while refunds rise faster.
  • Define the metric window: immediate effects and delayed retention measure different things.
  • Pre-register the analysis plan so the result is not chosen after seeing several cuts of the data.
  • A metric that moves only in a segment may be a real insight or a multiple-comparison artifact; distinguish them deliberately.

06Sample size, power, and duration

  • Decide the minimum detectable effect before the test; it determines how much traffic and time are needed.
  • Underpowered tests produce inconclusive results that teams then interpret as 'no effect'.
  • Run for full weekly cycles so day-of-week composition is balanced across variants.
  • Stopping early when results look good inflates false positives; fix the horizon unless a sequential method is used.
  • Very large samples make trivial differences statistically significant, so judge practical significance too.
  • If traffic is split across many concurrent experiments, each test's effective sample shrinks.

07Reading the result honestly

  • Report an effect size with a confidence interval, not only a pass or fail verdict.
  • A confidence interval that includes both a meaningful gain and a meaningful loss is genuinely inconclusive.
  • Beware novelty effects: new designs often spike engagement, then regress as the novelty fades.
  • Beware primacy effects: users habituated to the old design may underperform initially on a better one.
  • Segment results are exploratory unless pre-registered; slicing until a win appears is p-hacking.
  • Check that the observed split matches the intended split before trusting any metric.

08Infrastructure pieces

  • An experiment configuration store holds definitions, variants, traffic allocation, and targeting.
  • An assignment service or SDK evaluates the experiment locally using cached configuration.
  • An exposure pipeline carries events into the analytics store, usually with buffering and retries.
  • A metrics layer joins exposures with outcomes and computes per-variant aggregates.
  • An analysis service or notebook layer produces effect estimates, confidence intervals, and diagnostics.
  • A monitoring layer watches assignment balance, event volume, and pipeline lag, because silent breakage invalidates results.
Define hypothesis and metrics→Configure variants and allocation→Assign users deterministically→Log exposures and outcomes→Analyze effect with intervals→Decide, ship, or stop

09Running many experiments at once

  • Orthogonal experiments assign on independent hash layers so a user can be in multiple tests without interference.
  • Overlapping experiments on the same layer correlate assignments and contaminate each other's results.
  • Interaction effects are real: two individually positive changes can be negative together.
  • Keep a holdout group across many experiments to measure cumulative product impact.
  • Document which experiments are active so a surprising result can be traced to a co-running test.
  • Sample dilution from too many concurrent tests is a common reason for inconclusive results.

10Validity threats

  • Sample ratio mismatch: the observed split deviates from the configured one, indicating a bug rather than a finding.
  • Instrumentation change mid-test: altering event definitions partway invalidates the comparison.
  • Bot and internal traffic: non-user requests distort conversion metrics unless filtered.
  • Cross-device identity: one person counted as two units weakens the experiment.
  • Spillover: treatment users interact with control users, as in social or marketplace features.
  • Selective exposure: a variant that only renders on some pages is not comparable to a control that renders everywhere.

11Operational lifecycle

  • Start with a hypothesis and the decision it informs; experiments without a decision are just data collection.
  • Define metrics, allocation, duration, and stopping rules in the experiment document.
  • Run a small pre-check that assignments are balanced and events are flowing before trusting results.
  • Monitor guardrails continuously so harm is caught during the test, not after.
  • Conclude with a recorded decision: ship, iterate, or abandon, with the evidence attached.
  • Clean up the experiment configuration and remove losing variant code, or the codebase accumulates dead paths.

12A/B tests versus canaries and feature flags

  • A canary asks whether the new version is safe; an A/B test asks whether it is better.
  • Canary analysis uses operational guardrails; experiment analysis uses statistical estimates of effect.
  • A canary is usually short and automatic; an experiment runs long enough to measure behavior.
  • Feature flags are the delivery mechanism that makes both possible by controlling exposure at runtime.
  • Running an experiment on top of a broken release measures noise; validate safety first, then measure benefit.
  • The same traffic-splitting infrastructure often serves both, but the decision rules are different.

↔Trade-offs to say out loud

  • Concurrent A/B testing removes calendar bias but requires assignment, logging, and analysis infrastructure that must itself be correct.
  • User-level assignment gives stable experience but splits a person across devices and reduces effective sample size.
  • Server-side exposure logging is more complete but misses client-only rendering; client-side logging captures rendering but loses events.
  • Longer tests capture novelty decay and weekly cycles but delay decisions and slow the product.
  • More concurrent experiments increase learning velocity but dilute samples and create interaction effects.
  • Strict pre-registration protects validity but limits exploratory discovery.
  • Segment analysis can reveal real heterogeneous effects but multiplies false positives.
  • Aggressive guardrail thresholds protect users but can stop experiments before a real effect is measurable.

?Interview questions

Answer aloud before opening the outline.

1. Why is a before-and-after comparison unreliable?

Because other things change at the same time: campaigns, seasonality, competitor events, and holidays. A before-and-after comparison cannot separate the release from the calendar. A concurrent control group experiences the same external conditions, which is what makes attribution possible.

2. What is the minimum viable A/B testing infrastructure?

Deterministic assignment of users to variants, exposure logging that records what each unit actually saw, outcome events joinable to those exposures, and an analysis that reports effect size with uncertainty. Monitoring for assignment balance and pipeline lag is part of the minimum, because silent breakage produces confident wrong answers.

3. Why is deterministic hashing used for assignment?

It gives the same user the same variant on every request without storing assignments, and it can be computed independently by any service. Random assignment per request would flip users between variants and destroy both experience and measurement.

4. Why is the randomization unit important?

It defines what is independent in the analysis. User-level assignment matches most product decisions but splits a person across devices; session-level assignment is unstable over time; account-level fits shared B2B features but shrinks the sample. Choosing the wrong unit creates contamination or an underpowered test.

5. Why log exposures rather than assignments?

Because assigned users may never actually see the variant, which dilutes the measured effect. Exposure logging restricts analysis to users who genuinely experienced the change. Divergence between assigned and exposed populations is also an early warning of instrumentation bugs.

6. What is sample ratio mismatch and why does it matter?

It is a significant deviation from the intended traffic split, such as a 50/50 test receiving 52/48. It almost always indicates a bug in assignment, targeting, or logging rather than a real effect. When it appears, the experiment should be investigated and usually discarded.

7. Why can't you stop a test as soon as it looks significant?

Repeatedly checking and stopping at the first significant result inflates the false-positive rate, because you are effectively taking many looks. Fixed-horizon tests assume a single analysis. Sequential methods exist, but they must be chosen in advance.

8. What is statistical power and why does it matter?

It is the probability of detecting an effect of a given size if that effect is real. Underpowered tests frequently return 'no significant difference' even when a meaningful effect exists. Power depends on sample size, baseline variance, and the minimum detectable effect you care about.

9. What are guardrail metrics?

Metrics that must not degrade while the primary metric is optimized, such as latency, error rate, support contacts, or refunds. They prevent a local win from becoming a systemic loss. A primary metric that improves while a guardrail collapses is not a successful experiment.

10. How do you run multiple experiments without contaminating them?

Use orthogonal assignment layers on independent hash inputs so a user's variant in one experiment is independent of another. Document active experiments and watch for interaction effects. Keep a long-lived holdout to measure cumulative impact.

11. What is a novelty effect?

An early change in behavior caused by the newness of a change rather than its quality, which typically decays. It inflates short tests and can reverse later. Running for full cycles and, where possible, re-measuring after the novelty fades keeps conclusions honest.

12. How does A/B testing relate to canary releases?

A canary answers whether a release is safe, using operational guardrails over a short window. An A/B test answers whether a variant is better, using statistical estimation over a longer period. Both rely on runtime traffic splitting, but they support different decisions.

!Traps

  • Comparing before and after the release and calling the difference the treatment effect.
  • Analyzing on assigned users instead of exposed users, diluting the measured effect.
  • Stopping the test at the first significant peek and reporting an inflated win.
  • Slicing segments after the fact until one shows an improvement.
  • Ignoring sample ratio mismatch and treating the resulting numbers as findings.
  • Changing event definitions or logging code partway through the experiment.
  • Choosing a primary metric after seeing which one moved.
