01The problem with fixed addresses

  • In a monolith, one component calls another in the same process; in microservices, that becomes a network call to an address that can change at any time.
  • Autoscaling changes the instance count: five payment instances today might be twenty tomorrow.
  • A crashed instance is replaced with a new IP, and a deployment replaces old instances with new ones.
  • On a container platform this churn happens many times a day, sometimes without any human involved.
  • A hardcoded list goes stale immediately: callers keep hitting dead addresses and never discover the new ones.
  • The result is failed requests during scale-out, traffic to removed instances during scale-in, and errors on every deployment.
  • Configuration management can distribute a list, but it cannot keep up with per-minute changes or react to a single crash.

02What service discovery is

  • Service discovery is the process of automatically finding the network locations of service instances.
  • A caller asks for payment by name and receives the healthy instances it can call right now.
  • Think of a phone book that keeps itself up to date: people move, but searching by name returns the current number.
  • It has two parts: a registry that tracks where instances are running, and a discovery mechanism that lets callers look them up.
  • The registry is the source of truth; the mechanism is how that truth reaches the caller — a client library, a load balancer, DNS, or a sidecar proxy.
  • Discovery answers "which instances exist and are healthy", not "which one is best for this request"; routing policy is layered on top.
  • The service name becomes the stable contract, and instance addresses become an implementation detail.

03The service registry

  • A registry is essentially a database of available instances, keyed by service name.
  • Each entry normally holds the IP address, port, and metadata such as version, zone, region, or weight.
  • For example, payment might currently map to three instances, each with an address and a zone tag.
  • As instances start, stop, or fail, the list changes continuously.
  • Metadata enables smarter routing: prefer the caller's own zone to cut latency and cross-zone data transfer, or send only a small share of traffic to a new version during a canary.
  • Keep metadata to keys that routing or operations actually use, and document each one; unused metadata rots.
  • Common registries include Consul, etcd, ZooKeeper, and Eureka; Kubernetes maintains its own internal view of running services.
  • The registry itself must be highly available, because if it is unreachable, new instances cannot be found.

04Self-registration

  • With self-registration, each instance is responsible for adding itself to the registry on startup.
  • It sends its service name, address, and port, and on a clean shutdown it sends a request to remove itself.
  • Services do not always shut down cleanly, so instances also send periodic heartbeats — for example every ten seconds.
  • If the registry stops receiving heartbeats for long enough, it assumes the instance is gone and removes it.
  • The advantage is that the application controls its own lifecycle and can register rich metadata directly.
  • The downside is that every service needs registration logic, usually through a registry-specific client library.
  • That couples application code to the discovery system and means every language needs a correct client that handles startup, heartbeats, and shutdown.
  • A bug in that library — a missed heartbeat, a registration before the port is listening — becomes a service-wide outage pattern.
Instance starts and registers payment, 10.0.1.5:8080→Registry acknowledges→Instance sends a heartbeat every 10 seconds→Instance crashes; heartbeats stop→Registry removes the instance after the timeout window

05Third-party registration

  • With third-party registration, the application does not register itself; a separate component, the registrar, watches the environment and updates the registry.
  • When the platform starts a new payment container, the registrar notices it and adds it; when the container stops, the registrar removes it.
  • Kubernetes works this way: the application does not need to know a registry exists, because the platform tracks running containers and keeps endpoints current.
  • Registration logic stays out of application code, so behavior is consistent across services written in different languages.
  • The trade-off is that the registrar or platform becomes another critical piece of infrastructure that must be reliable.
  • The application must still expose health signals the platform can interpret; third-party registration removes the client library, not the need for readiness.
  • If the registrar's view of the world is wrong — a stuck controller, a broken watch — the registry inherits that error.

06Health checks

  • Knowing an instance exists is not enough; a process can be running while unable to serve requests.
  • Discovery therefore tracks health, not just presence.
  • With heartbeats, the instance reports that it is alive; with active checks, the registry calls /health every few seconds.
  • After several consecutive failures the instance is marked unhealthy and removed from results; requiring multiple failures avoids reacting to one brief hiccup.
  • A useful check reflects whether the instance can actually serve: a payment service that lost its database connection pool should report not ready.
  • Kubernetes splits the question into readiness (should this instance get traffic?), liveness (should it be restarted?), and startup (has initialization finished?).
  • Keep liveness checks simple: if liveness fails whenever a downstream database is slow, every instance restarts at once and turns a degradation into an outage.
  • Use readiness to take an instance out of rotation and liveness only for a genuinely stuck process.

07Client-side discovery

  • In client-side discovery, the calling service talks to the registry directly.
  • The order service asks the registry for healthy payment instances, receives three addresses, chooses one, and sends the request straight to it.
  • The choice can be round robin, fewest active requests, same-zone preference, or consistent hashing so a key usually lands on the same instance.
  • There is no extra network hop, and the caller can apply routing logic the platform does not know about.
  • The cost is that every service needs discovery and load-balancing logic, implemented and maintained in each language.
  • Netflix popularized this style with Eureka plus a client library that combined discovery and load balancing inside each service.
  • Client-side discovery fits when application teams need fine control over routing decisions.
  • It also means every caller must cache the instance list and refresh it sensibly, or the registry becomes a per-request dependency.
Order service queries the registry for payment→Registry returns healthy instances with addresses→Client-side load balancer picks one→Order service calls that instance directly

08Server-side discovery

  • In server-side discovery, the client does not query the registry; it sends requests to a load balancer or router at a stable, well-known address.
  • The load balancer looks up healthy instances, chooses one, and forwards the request.
  • From the caller's point of view, the payment service has one stable address and everything behind it is invisible.
  • AWS load balancers work this way: instances register with a target group, and clients only talk to the load balancer.
  • Clients stay simple — any service, in any language, makes a normal network call with no discovery library.
  • The cost is an extra network hop and a critical component that must be highly available and sized for the full traffic volume.
  • It also centralizes routing policy, which is good for consistency and bad when a team needs per-request control.
  • Server-side discovery is a natural fit when a platform team owns routing.
Order service calls the load balancer's stable address→Load balancer looks up healthy payment instances in the registry→Load balancer selects an instance→Load balancer forwards the request

09DNS-based discovery

  • DNS already maps names to addresses, so the caller can use payment.internal instead of a hardcoded IP.
  • The DNS server returns the addresses of current instances; Consul, for example, exposes its registry as names like payment.service.consul.
  • The advantage is compatibility: almost every language and operating system understands DNS, so no special client library is needed.
  • The challenge is caching: answers live for a TTL, and some clients or operating systems hold them longer than expected.
  • A stale answer means a client keeps sending requests to an address that no longer exists.
  • A very short TTL shrinks that window but multiplies DNS lookups and load on the DNS servers.
  • Long-lived connections are a related problem: HTTP keep-alive, HTTP/2, and gRPC may resolve once and reuse the same instance for hours.
  • Those clients need periodic connection recycling, or they will ignore DNS changes entirely.

10Service discovery in Kubernetes

  • A Kubernetes Service gets a stable name and a stable virtual IP, so other services call payment by name.
  • Cluster DNS resolves the name to the Service's virtual IP rather than to individual pods.
  • Kubernetes tracks which pods belong to the Service and keeps the ready pod list current, usually in EndpointSlices.
  • Forwarding from the virtual IP to a pod is done by kube-proxy (iptables or IPVS) or by an eBPF layer such as Cilium.
  • This combines all three ideas: third-party registration from the platform, DNS for lookup, and server-side-style routing because the app sees one stable address.
  • Most clusters use CoreDNS for name resolution.
  • A headless Service skips the virtual IP and returns pod IPs directly, which is useful when the client must reach specific pods, such as members of a database cluster.
  • Because discovery is built in, teams on Kubernetes often do not need a separate registry such as Consul or Eureka.
Order pod looks up payment in cluster DNS→CoreDNS returns the Service virtual IP→Order pod sends the request to the virtual IP→Node networking forwards it to a ready payment pod

11The registry must stay available

  • Once discovery is central to communication, the registry becomes a critical dependency: if services cannot find each other, they cannot talk.
  • Registries are therefore deployed as multi-node clusters, not as a single server.
  • Consensus-based registries such as Consul, etcd, and ZooKeeper favor consistency; a node that cannot reach a majority may stop serving some operations.
  • Eureka favors availability and keeps serving its last known view during a network problem, even if some of it is stale.
  • For discovery, slight staleness is often acceptable because the caller can retry another instance.
  • Clients commonly cache discovery results locally, so a short registry outage does not stop traffic.
  • When the registry recovers, clients must not all refresh at the same instant; adding jitter to refresh intervals prevents a thundering herd.
  • An unavailable registry should degrade discovery, not take down every existing connection.

12Stale results, retries, and graceful shutdown

  • Discovery data is never perfectly current: there is always a delay between an instance failing and the registry noticing.
  • During that window, callers can still receive a failed instance, so they must never assume every discovered address works.
  • Calls need timeouts so a dead instance cannot hold a request open indefinitely.
  • Failed requests may be retried against another instance, but only operations that are safe to repeat — reads or requests carrying an idempotency key.
  • Retrying a payment without an idempotency key can charge a customer twice.
  • Load balancers can eject an instance after repeated failures even before the registry updates, which shortens the bad window.
  • On shutdown, an instance should first deregister or fail readiness so new traffic stops arriving, then wait for in-flight requests to finish before exiting.
  • That graceful shutdown avoids an error burst on every deployment, when instances are replaced quickly.
Shutdown signal received→Deregister or fail readiness→New traffic stops arriving→Finish requests already in flight→Process exits

13Service discovery and service mesh

  • In a service mesh, discovery and routing move out of the application and into a sidecar proxy such as Envoy.
  • A request from the order service first goes to its local sidecar, which gets the healthy payment instances from the mesh control plane.
  • The sidecar chooses an instance and forwards the request; the application contains no discovery code.
  • This resembles client-side discovery because the decision happens next to the caller, with no central load balancer in the request path.
  • The proxy also handles retries, timeouts, and service-to-service encryption, giving consistent behavior across languages.
  • The cost is another control plane and data plane to run, upgrade, and debug, plus latency and resource overhead per pod.
  • Many microservice systems work well without a mesh; adopt one when consistent traffic policy across many services justifies the operational burden.
  • The mesh does not remove stale data — the control plane still learns about failures after a delay, so timeouts and retries remain necessary.

14Comparing approaches and when you need discovery

  • The approaches differ mainly in who picks the instance and where the routing decision lives.
  • Client-side discovery puts control in the caller; server-side puts it in a load balancer; DNS puts it in the resolver; a mesh puts it in a sidecar.
  • The choice often comes down to ownership: platform teams tend toward server-side, Kubernetes Services, or a mesh; application teams wanting per-key routing tend toward client-side.
  • Adopt dedicated discovery when instances change frequently — autoscaling, containers, frequent deploys — or when many services must find each other.
  • On Kubernetes or a similar platform, use the built-in discovery instead of adding another registry.
  • Services on virtual machines across several environments may justify a tool such as Consul.
  • A small application with a handful of rarely changing servers may need nothing more than a load balancer with a stable address.
  • Discovery adds a critical dependency; if addresses are genuinely static, it is complexity without benefit.

↔Trade-offs to say out loud

  • Service discovery removes hardcoded addresses and supports autoscaling, but adds a registry and a lookup path that must themselves be highly available.
  • Self-registration keeps lifecycle control in the service but couples every language to a registry client library and its bugs.
  • Third-party registration keeps application code clean and consistent, but makes the platform or registrar a critical dependency.
  • Client-side discovery avoids an extra hop and enables fine-grained routing, but duplicates discovery and load-balancing logic in every service.
  • Server-side discovery keeps clients simple but inserts a critical, high-traffic load balancer and an extra network hop.
  • DNS-based discovery works everywhere with no library, but TTL caching and long-lived connections make results stale.
  • A consistency-first registry avoids serving conflicting data but may refuse operations during a partition; an availability-first registry keeps serving but can return stale instances.
  • A service mesh gives consistent retries, timeouts, encryption, and discovery across languages, at the cost of a control plane, sidecars, and harder debugging.
  • Graceful shutdown prevents error bursts during deploys but lengthens rollout time and requires drain logic in every service.

?Interview questions

Answer aloud before opening the outline.

1. Why do microservices need service discovery?

Because instance addresses change constantly with autoscaling, crashes, and deployments, especially on container platforms. Discovery lets a caller ask for a service by name and receive the currently healthy instances, instead of maintaining a configuration list that is stale within minutes.

2. What are the two main parts of service discovery?

A service registry that tracks where instances are running and whether they are healthy, and a discovery mechanism that gets that information to callers — through a client library, a load balancer, DNS, or a sidecar proxy.

3. Self-registration versus third-party registration?

Self-registration has each instance register itself and send heartbeats, often through a client library; it puts logic in every service and can differ by language. Third-party registration has a registrar or platform track instances and update the registry, as Kubernetes does; code stays clean but the platform becomes critical infrastructure.

4. Why are heartbeats not enough on their own?

A heartbeat only shows the process is alive, not that it can serve requests. An instance may have lost its database connection or be stuck in a bad state. Active readiness checks against a meaningful health endpoint catch failures that heartbeats miss.

5. What is the difference between readiness and liveness?

Readiness answers "should this instance receive traffic?" and failing it removes the instance from discovery. Liveness answers "is the process stuck beyond recovery?" and failing it restarts the process. Confusing them causes restart storms and outages.

6. How does client-side discovery work?

The caller queries the registry, gets the healthy instances, picks one with its own load-balancing policy, and calls it directly. There is no extra hop and routing can be sophisticated, but every service needs discovery and balancing logic in its language.

7. How does server-side discovery work?

The caller sends requests to a load balancer at a stable address. The load balancer resolves healthy instances from the registry and forwards the request. Clients stay simple and language-agnostic, but the load balancer is a critical component and adds a hop.

8. What are the problems with DNS-based discovery?

DNS answers are cached for a TTL that clients may exceed, so callers can keep using a dead address. Very short TTLs increase lookup volume. Long-lived HTTP/2 or gRPC connections resolve once and may never notice a change unless connections are recycled.

9. How does discovery work in Kubernetes?

A Service gets a stable name and virtual IP. Cluster DNS resolves the name to that IP, EndpointSlices track ready pods, and kube-proxy or an eBPF layer forwards to a pod. It combines third-party registration, DNS lookup, and server-side-style routing.

10. What is a headless Service and when do you use one?

A Service without a virtual IP that returns pod IPs directly through DNS. It is used when the client must address specific pods, such as database cluster members or stateful workloads that need stable identities.

11. How do you keep the registry highly available?

Run it as a multi-node cluster. Consensus systems such as Consul, etcd, and ZooKeeper favor consistency and may refuse some operations without a majority; Eureka favors availability and serves its last known view. Clients should cache results and refresh with jitter.

12. Discovery data is stale — how do callers cope?

Treat every discovered address as possibly dead: use timeouts, retry idempotent operations on another instance, and let load balancers eject failing instances. For writes, require an idempotency key before retrying. Combine this with graceful shutdown to reduce the stale window.

13. What is graceful shutdown and why does it matter for discovery?

On shutdown, deregister or fail readiness first so new traffic stops, then finish in-flight requests before exiting. Without it, deployments send requests to instances that are already terminating, producing a burst of errors on every rollout.

14. When do you not need service discovery?

When there are only a few servers and addresses rarely change, a load balancer with a stable address is enough. On Kubernetes, the platform already provides discovery, so adding a second registry usually adds complexity without value.

!Traps

  • Hardcoding instance IPs and calling the deployment "auto-scaling" because new machines start successfully but receive no traffic.
  • Using a heartbeat as the only health signal, so an instance with a broken database connection keeps receiving requests.
  • Pointing liveness at a downstream dependency and restarting every instance when that dependency slows down.
  • Forgetting that DNS TTLs and long-lived HTTP/2 or gRPC connections can keep a client on a dead instance.
  • Retrying a non-idempotent write against another instance without an idempotency key and double-charging the customer.
  • Shutting instances down without deregistering or draining, producing errors on every deployment.
  • Running a single-node registry and discovering that discovery itself is the outage.
  • Caching discovery results forever to avoid registry load, so the cache never learns about new or failed instances.
