Introduction to System Design

2 topics
01 What is System Design?System design is the process of deciding which components a system needs, what each one owns, how they communicate, and how data flows between them — so the system meets its functional and non-functional requirements at a level above writing code. → 02 Top 30 System Design ConceptsThirty building blocks, grouped from the network upward: how machines connect, how applications exchange data, where data lives, how systems scale, what breaks across multiple machines, and how to organize the whole thing. →

Core Concepts

5 topics
03 ScalabilityScalability is the ability to handle more users, traffic, and data without collapsing — but only after you identify the resource that is actually the bottleneck. → 04 AvailabilityAvailability is how often users can actually reach and use the system — engineered by removing single points of failure, adding redundancy that survives correlated failures, and containing the blast radius when a dependency breaks. → 05 Latency vs ThroughputLatency is how long one request takes, throughput is how much work finishes per second, and bandwidth is the ceiling a connection could reach — improving one does not automatically improve the others. → 06 Consistent HashingConsistent hashing maps keys and servers onto the same ring so that adding or removing one server moves only a small slice of the keys instead of reshuffling the whole cluster. → 07 CAP TheoremWhen a network partition splits replicas, CAP says you cannot keep both a single up-to-date view and a successful response for every affected request — and the choice belongs to each operation, not to the whole database. →

Networking

7 topics
08 OSI ModelThe OSI model divides network communication into seven layers, each providing a service to the layer above and relying on the layer below, so you can reason about what is built where and where a request breaks. → 09 IP AddressAn IP address is a network location, not a machine's permanent identity: routers forward packets toward it, and CIDR, subnets, NAT, and DNS decide how those locations are organised and reached. → 10 TCP vs UDPTCP and UDP both carry data between ports on top of IP, but TCP buys reliable, ordered delivery with handshakes and retransmissions, while UDP stays fast and simple and leaves those guarantees to the application. → 11 HTTP/HTTPSHTTP is a stateless request-response protocol carried over TCP or QUIC; HTTPS is the same protocol wrapped in TLS, which adds encryption, integrity, and proof of the server's identity. → 12 Domain Name System (DNS)DNS is the internet's hierarchical, heavily cached naming system: it turns a domain name into the records a client needs, and its TTLs decide how quickly a change can reach everyone. → 13 Proxy vs Reverse ProxyA forward proxy speaks for the client, a reverse proxy speaks for the servers — the difference is whose side of the connection it represents. → 14 ChecksumsA checksum is a small value computed from data so a later reader can detect that the bytes changed; it detects corruption, but recovery still comes from a retry, a replica, or a backup. →

Load Balancing

4 topics
15 Load BalancersA load balancer gives many backend servers one stable endpoint, spreading traffic across healthy instances and removing failed ones from rotation without the client noticing. → 16 Load Balancing AlgorithmsA load balancing algorithm is the rule that picks which backend serves a request; the right choice depends on what the balancer can actually observe and on how uneven request cost and duration are. → 17 DNS Load BalancingDNS load balancing spreads traffic by returning different IP addresses during name resolution, which makes it the only layer that can choose a region before a connection exists. → 18 Anycast RoutingAnycast lets many locations announce the same IP address, and the internet's routing system sends each packet to whichever one is nearest according to BGP. →

API Fundamentals

7 topics
19 What is an API?An API is the contract that lets one piece of software call another: it fixes the operations, the data to send, and the response to expect, while hiding everything behind the boundary. → 20 API Architectural StylesAn API style is the pattern a communication follows — resource-based, query-based, action-based, streaming, or event-driven — and real systems pick a different one for each communication path. → 21 IdempotencyAn operation is idempotent when repeating it has the same intended effect as doing it once, which is what makes safe retries possible when the client cannot tell whether the first attempt worked. → 22 REST FundamentalsA good REST API is predictable: the same conventions for resources, methods, status codes, errors, pagination, and versioning everywhere, so learning one endpoint teaches you the rest. → 23 GraphQL FundamentalsGraphQL lets the client describe the response shape against a typed schema, which removes over-fetching and multiple round trips but moves cost, caching, and abuse control onto the server. → 24 gRPC FundamentalsgRPC turns a method call in a .proto contract into a network call over HTTP/2 with compact binary messages, which suits internal service-to-service communication. → 25 JWTA JWT is a signed, self-contained token that lets any service holding the issuer's public key verify who the user is without a session lookup — at the cost of revocation and exposure. →

Communication Patterns

9 topics
26 Long PollingLong polling keeps a normal HTTP request open on the server until an event arrives or a timeout fires, giving near-real-time delivery without leaving the request-response model. → 27 Server-Sent Events (SSE)SSE keeps one long-lived HTTP response open and lets the server push a stream of events to the browser, one direction only, with automatic reconnection and resumable event IDs. → 28 WebSocketsA WebSocket is one persistent, full-duplex TCP connection upgraded from HTTP, so either side can send a message the moment it has one instead of the client repeatedly asking. → 29 WebhooksA webhook is an HTTP callback: the provider POSTs an event to a URL you registered, so you stop polling and start reacting — but reliable delivery is entirely your problem. → 30 Message QueuesA message queue is a durable buffer between producers and consumers that turns slow, bursty, failure-prone work into independent background tasks — at the price of duplicates, retries, and eventual completion. → 31 Pub/SubPub/sub lets a publisher announce that something happened once, while any number of independent subscribers receive their own copy — decoupling the producer from everyone who cares. → 32 Message BrokersA message broker is shared infrastructure that stores, routes, delivers, and acknowledges messages between producers and consumers, so services can talk without knowing each other's addresses, availability, or speed. → 33 Delivery SemanticsDelivery semantics describe what a messaging system promises about loss and duplication — and every promise is really a choice about when to retry and when to acknowledge. → 34 Dead Letter QueuesA dead letter queue is a quarantine for messages that fail repeatedly, so one poison message cannot stall a stream or be silently thrown away. →

Caching

5 topics
35 What is Caching?A cache keeps a copy of frequently used data in a faster layer so repeat requests avoid the database — cutting latency, reducing load, and raising throughput at the cost of staleness and invalidation work. → 36 Caching StrategiesCaching strategies answer one question: who moves data between cache and database, and when — with cache-aside as the default read pattern and write-through, write-behind, or write-around chosen to fit the write path. → 37 Cache Eviction PoliciesAn eviction policy decides which valid entry leaves when the cache is full — LRU by default, LFU for stable hot keys, FIFO or random for low overhead, with TTL handling freshness and admission control protecting against pollution. → 38 Cache InvalidationCache invalidation is how a cached copy is expired, deleted, or refreshed when the source of truth changes — the hard part is doing it without races, misses, or stampedes. → 39 Content Delivery Network (CDN)A CDN is a globally distributed cache that serves content from an edge location near the user, so latency and origin load drop — as long as the content is shareable, cacheable, and safely invalidated. →

Databases

13 topics
40 Database TypesNo single database is best at transactions, single-key lookups, text ranking, and time-window aggregates — pick the engine whose storage layout and index structure match how the data is actually queried. → 41 SQL vs NoSQLThe SQL vs NoSQL decision trades a fixed schema and flexible queries against a flexible schema and queries designed in advance; it is decided by the shape of the data, the access patterns, and how much consistency each part of the system needs — not by which label sounds more modern. → 42 ACID TransactionsACID transactions let an application group several operations into one all-or-nothing unit, so a crash or a concurrent request cannot leave the data half-updated — at the cost of latency, locking, and throughput. → 43 B-Trees and B+ TreesA B-tree is a wide, shallow, self-balancing search tree whose nodes are disk pages, so a lookup needs only a few page reads instead of a table scan — and its sorted order also makes range queries cheap, at the price of write amplification on splits. → 44 LSM TreesAn LSM tree turns random writes into sequential ones by buffering changes in memory and flushing sorted immutable files, then merging those files in the background — which makes writes fast and reads more complicated. → 45 Relational DatabasesA relational database stores each fact once in typed tables, links tables with keys, and rebuilds answers at query time with SQL and joins — giving strong correctness and flexible querying in exchange for join cost and a single write primary. → 46 Document DatabasesA document database stores each entity as one self-contained JSON-like record, so a request that touches one entity is a single read of one document — as long as you model around embedding, references, and the queries you actually run. → 47 Key-Value StoresA key-value store is the simplest useful database: a value under a unique key, with get, put, and delete — extremely fast and easy to partition, but blind to what is inside the value. → 48 Full-Text Search EnginesA full-text search engine replaces row scans with an inverted index from words to documents, so it can match, rank, and filter free text — at the cost of a second data store that must be kept in sync with the source of truth. → 49 Wide Column DatabasesA wide-column database stores rows that can have many sparse columns, groups them into a partition by a partition key, and sorts them inside the partition by a clustering key — so a huge, write-heavy, single-partition query becomes a cheap sequential read. → 50 Time Series DatabasesA time-series database assumes every row is an append-only sample tagged with a timestamp, so it can compress time-ordered data aggressively, answer range-and-aggregate queries quickly, and expire old data cheaply. → 51 Graph DatabasesA graph database stores relationships as first-class edges that point directly at their endpoints, so a multi-hop traversal follows pointers instead of performing one index join per hop — which is exactly where relational queries degrade as depth grows. → 52 Vector DatabasesA vector database stores embeddings and answers what is most similar to this? with an approximate nearest-neighbor index, trading exactness for speed — and it only works if the embedding model, distance metric, and filters are designed together. →

Database Scaling Techniques

8 topics
53 IndexingAn index is a small, sorted structure that turns a full table scan into a few page reads — but each one adds write cost, storage, and memory pressure, so the goal is the smallest set of indexes that supports the real query patterns. → 54 PartitioningPartitioning splits one logical table into smaller physical pieces so queries can skip most of the data and old data becomes cheap to drop — but only if the partition key matches how the table is actually queried. → 55 ReplicationReplication keeps copies of the same data on several servers, buying availability, read throughput, and regional latency — at the cost of lag, failover complexity, and the illusion that a copy is a backup. → 56 ShardingSharding splits one large dataset across multiple independent database instances, so each shard stores and serves only a slice — trading cross-shard simplicity for horizontal write and storage scale. → 57 Query OptimizationQuery optimization is the work of making a query read only the rows it needs — usually a far better return than a bigger server, a read replica, or a cache layered over a query that scans 50 million rows to return 20. → 58 DenormalizationDenormalization intentionally stores duplicate or precomputed data so reads avoid expensive joins — trading write complexity and consistency risk for faster, simpler read paths. → 59 Materialized ViewsA materialized view stores the result of a query on disk, so an expensive join or aggregation is computed once instead of on every request — at the cost of storage and controlled staleness. → 60 Connection PoolingA connection pool keeps a set of already-open database connections and lends them to requests, so the application pays the TCP, TLS, and authentication cost once instead of on every query. →

Storage Systems

4 topics
61 Block StorageBlock storage exposes a volume as a numbered array of fixed-size blocks, so a server can do small random in-place reads and writes — exactly the access pattern databases, message brokers, and virtual machines need. → 62 Distributed File SystemsA distributed file system (DFS) presents one familiar namespace — /logs/2026/05/24/app.log — while the bytes behind that path are chunked and replicated across many machines. → 63 Object StorageObject storage is a flat, HTTP-addressable store for whole blobs — images, video, backups, model datasets — built to scale capacity and durability far beyond a single filesystem, at the cost of POSIX semantics and cheap queries. → 64 Erasure CodingErasure coding splits data into k chunks, computes m parity chunks, and spreads all k+m across failure domains, so the data survives losing any m of them while storing far less overhead than full copies. →

Architectural Patterns

9 topics
65 Client-Server ArchitectureClient-server architecture splits responsibilities between clients that handle interaction and servers that own shared data, business rules, and permissions — communicating over a network through a request-response contract. → 66 Monolithic ArchitectureA monolith builds, deploys, and runs every feature as one unit — the simplest way to start, but its coupling, shared releases, and shared process become the constraints as the system and the team grow. → 67 Microservices ArchitectureMicroservices split a system into small, independently deployable services, each owning its data and exposing a contract — trading in-process simplicity for network boundaries, distributed data, and serious operational machinery. → 68 Serverless ArchitectureServerless hands server provisioning, patching, and capacity planning to a cloud provider: you deploy code and managed services, and the platform runs, scales, and bills them per use — while retries, cold starts, limits, and lock-in stay your problem. → 69 Event-Driven ArchitectureEvent-driven architecture replaces direct calls with facts: a producer announces that something happened, a broker stores and delivers it, and any number of consumers react on their own — trading immediate consistency and simple debugging for decoupling and resilience. → 70 Peer-to-Peer (P2P) ArchitecturePeer-to-peer architecture spreads bandwidth, storage, and compute across the participants themselves, so capacity grows with demand — at the price of churn, unreliable connectivity, and having to trust nobody in particular. → 71 Hexagonal ArchitectureHexagonal architecture — ports and adapters — keeps business logic in a technology-free core and connects every transport, database, and external service to it through explicit interfaces. → 72 CQRSCQRS separates the model that changes data from the model that reads it, so writes can protect invariants and reads can be shaped for the screen — at the cost of a second model that must be kept in sync. → 73 Event SourcingEvent sourcing stores every state change as an immutable event and derives current state by replaying them, trading simple reads and easy deletes for a complete, replayable history. →

Microservices Patterns

8 topics
74 Service DiscoveryService discovery lets a caller find a service by name and receive its currently healthy instances, so addresses can change with autoscaling, crashes, and deploys without anyone editing configuration. → 75 API Gateway PatternAn API gateway is the single stable front door for outside clients: it routes each request to the right service and centralizes authentication, rate limiting, TLS, and response shaping. → 76 Backend for Frontend (BFF)A Backend for Frontend gives each client type its own thin backend that aggregates and shapes service data for that experience, so mobile, web, and TV stop compromising inside one shared API. → 77 Sidecar PatternThe Sidecar pattern runs a helper process next to every application instance so cross-cutting work like logging, secrets, TLS, and traffic management lives in infrastructure instead of being rebuilt in every service and language. → 78 Circuit Breaker PatternA circuit breaker watches calls to one dependency and, once failures or slow calls cross a threshold, stops calling it so a local slowdown does not consume every thread and become a system-wide outage. → 79 Bulkhead PatternThe Bulkhead pattern divides finite resources into isolated pools so that one slow dependency or heavy workload cannot consume all capacity and take down unrelated features. → 80 Strangler Fig PatternThe Strangler Fig pattern replaces a legacy system incrementally: a routing layer sends one slice of traffic to new code at a time until the old system has nothing left to serve. → 81 Service MeshA service mesh moves timeouts, retries, encryption, routing, and telemetry out of application code and into a fleet of proxies that the platform configures centrally. →

Distributed System Fundamentals

5 topics
82 HeartbeatsA heartbeat is a small periodic message that says I am still running; the engineering is in choosing an interval and timeout that catch real failures without turning a brief hiccup into a failover. → 83 Raft AlgorithmRaft keeps a replicated log identical across a group of servers by electing one leader per term, appending entries through it, and committing only what a majority has stored — consensus designed to be explainable. → 84 Gossip ProtocolGossip spreads cluster state without a coordinator: every node periodically tells a few random peers what it knows, and the news reaches the whole cluster in a handful of rounds. → 85 CRDTsA CRDT is a data type whose concurrent updates can be merged deterministically, so every replica accepts writes locally and still ends up in the same state without agreeing first. → 86 Operational TransformationOperational transformation lets several people edit one document at once: each edit applies instantly on its author's screen, and remote edits are rewritten to still mean the same thing once they arrive. →

Data Structures for Scale

11 topics
89 GeohashA geohash turns a latitude and longitude into a short sortable string, so an ordinary B-tree index can answer "what is near this point?" with a few prefix scans instead of a two-dimensional search. → 90 Quad TreesA quadtree subdivides a map into four children per node, splitting only where the data is dense — so a nearby search can skip whole regions that cannot contain a match. → 91 R-TreesAn R-tree wraps every shape in a bounding rectangle, groups nearby rectangles into larger ones, and prunes whole groups whose boxes cannot touch the query — which is why it is the index behind most spatial databases. → 92 S2 and H3S2 and H3 replace the flat latitude/longitude grid with cells laid out on the sphere itself, so a compact numeric cell ID can serve as an index key, a grouping key, or a shard key anywhere on Earth. → 93 Bloom FiltersA Bloom filter answers "definitely not here" or "maybe here" from a few bits per item, letting a system skip expensive lookups — and it is safe precisely because a false positive only costs extra work. → 94 Cuckoo FilterA cuckoo filter stores short fingerprints in two candidate buckets per item and relocates existing entries to make room, which gives Bloom-like membership checks with deletion and without a separate counter array. → 95 Skip ListsA skip list is a sorted linked list with probabilistic express lanes above it, giving expected logarithmic search, insertion, and deletion without the rotations that make balanced trees hard to implement and hard to update concurrently. → 96 Count-Min SketchA Count-Min Sketch estimates how often each item appeared in a stream using a fixed grid of counters and a minimum across rows, so memory stays constant while estimates never come in under the true count. → 97 HyperLogLogHyperLogLog estimates how many distinct items a stream contains by recording the longest run of leading zeros seen per register, so cardinality fits in kilobytes instead of a set of every ID. → 98 Merkle TreesA Merkle tree hashes data into leaves and hashes pairs upward to a single root, so two machines can prove their datasets match with one hash and locate any difference by exchanging only a few more. → 99 MinHashMinHash compresses a set into a small signature whose matching rate estimates Jaccard similarity, and locality-sensitive hashing turns those signatures into cheap candidate pairs instead of comparing every pair. →

Big Data Processing

9 topics
100 Batch vs Stream ProcessingBatch processing runs finite jobs over bounded data for throughput and exact reprocessing; stream processing runs forever over unbounded events for low latency, at the cost of windows, watermarks, state, and delivery guarantees. → 101 MapReduceMapReduce is a batch framework that splits a huge dataset into independent map tasks, groups intermediate results by key through shuffle and sort, and aggregates them in reduce tasks — while the framework handles distribution and failure. → 102 ETL PipelinesAn ETL pipeline moves data from many source systems into one trusted analytical store by extracting changes, transforming them into agreed shapes, and loading them in a repeatable, monitored, and replayable way. → 103 Data LakesA data lake stores raw data from many sources in cheap object storage and applies schema when it is read, which makes it flexible and inexpensive but puts the burden of cataloging, governance, and quality on the organization. → 104 Data WarehousingA data warehouse is a separate analytical database that enforces a schema before loading, stores data column-wise across many machines, and models it into facts and dimensions so business questions can scan history without slowing production. → 105 Data LakehouseA data lakehouse keeps analytical data as open columnar files on cheap object storage and adds a table format on top, so one copy of the data supports both reliable SQL reporting and machine learning without a second warehouse copy. → 106 Lambda ArchitectureLambda architecture runs a batch pipeline for correctness and a streaming pipeline for freshness over the same immutable data, then merges their outputs at query time so results are immediate and eventually exact. → 107 Kappa ArchitectureKappa architecture keeps one streaming pipeline and treats the retained event log as the system of record, so historical reprocessing is just a new job replaying the log from the beginning. → 108 Streaming EnginesA streaming engine turns a simple read from a log into a fault-tolerant distributed computation, handling parallelism, state, event time, checkpoints, and backpressure so application teams do not rebuild those mechanisms themselves. →

Deployment Patterns

9 topics
109 Deployment Strategies OverviewA deployment strategy is the plan for moving traffic from the old version to the new one, trading off downtime, blast radius, rollback speed, and extra infrastructure. → 110 CI/CD PipelinesA CI/CD pipeline automates the path from commit to production — build, test, package, deploy, verify — so that every change passes the same checks and no step depends on someone remembering a command. → 111 Rolling DeploymentsA rolling deployment replaces instances a few at a time so the service stays online without a second full copy of production — at the cost of running two versions side by side and rolling back slowly. → 112 Blue-Green DeploymentsBlue-green deployment keeps two identical production environments and switches traffic between them, so a release becomes a router change and recovery becomes the same change in reverse. → 113 Canary ReleasesA canary release sends a small slice of real production traffic to the new version, compares its behavior against the old version, and widens the slice only while the evidence stays healthy. → 114 Feature FlagsFeature flags put behavior behind a runtime switch, so code can be deployed without being released and a risky feature can be turned off in seconds without a redeploy. → 115 A/B Testing InfrastructureA/B testing compares two variants on comparable user groups at the same time, so outside events affect both groups equally and the difference can be attributed to the change. → 116 Schema MigrationsThe hard part of a schema migration is not changing the schema — it is changing it while old and new application versions both run against the same database. → 117 Rollbacks & Immutable InfrastructureRollback is only fast if the last good version still exists and can be deployed without rebuilding it — which is exactly what immutable infrastructure makes possible. →

Observability

7 topics
118 Three Pillars of ObservabilityMetrics tell you whether something is wrong, traces tell you where, and logs tell you why — but only when the three are linked by a shared trace ID. → 119 LoggingGood logging is not more logging: it is structured events with consistent fields, honest levels, a correlation ID, and enough context to explain an incident — while keeping secrets out and volume affordable. → 120 Log AggregationLog aggregation ships logs from every instance into one searchable, time-ordered store, so an engineer can answer what happened to this request without logging into twenty machines. → 121 Metrics and InstrumentationMetrics turn system behavior into a small set of numeric time series, so you can see a slowdown building minutes before customers report it — provided the instrumented signals and their labels are chosen carefully. → 122 Distributed TracingDistributed tracing records the tree of work a single request triggers across services, so you can say exactly which hop consumed the six seconds instead of guessing from per-service averages. → 123 Alert & MonitoringMonitoring records what the system is doing; alerting decides which of those facts is worth waking a human for. A good alerting system fires quickly when something important breaks and stays quiet the rest of the time. → 124 Dashboards & RunbooksA dashboard should answer what is broken in seconds and a runbook should answer what do I do now — together they turn a twenty-minute hunt into a two-minute fix. →

Advanced Security

6 topics
125 SSL/TLSTLS turns an untrusted network into a channel that is private, tamper-evident, and bound to a verified server identity — confidentiality, integrity, and authentication for data in transit. → 126 Encryption at RestEncryption at rest assumes the storage itself will be stolen — a discarded disk, a public backup bucket, a shared snapshot — and makes the bytes useless without a key that lives somewhere else. → 127 Secrets ManagementA secret is a value where merely possessing it grants access, so secrets management is really about four questions: where the value lives, who can read it, how it rotates, and who used it. → 128 Password ManagementDesign password storage around one assumption — the database will be stolen — and make the stolen data as useless as possible with per-user salts, a deliberately slow hash, and a reset flow that does not become the weakest link. → 129 RBACRBAC replaces per-user permission assignments with roles: permissions are grouped into named bundles, roles are assigned to users, and every request is checked against the result — which stays manageable only if roles are designed and reviewed deliberately. → 130 SAMLSAML lets many applications trust one central identity provider, so employees log in once and IT disables access in one place — provided every service provider validates the signed XML assertion correctly. →
