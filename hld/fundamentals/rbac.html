In one lineRBAC replaces per-user permission assignments with roles: permissions are grouped into named bundles, roles are assigned to users, and every request is checked against the result — which stays manageable only if roles are designed and reviewed deliberately.
RBAC
Role-Based Access Control: an authorization model where permissions are grouped into roles and roles are assigned to subjects.
Principal
The entity being authorized: a user, group, service account, or API client.
Permission
A single allowed action on a resource, such as orders:refund or reports:read.
Role
A named bundle of permissions that represents a job function or responsibility, not an individual.
Least privilege
Granting only the permissions required for the task, for only as long as they are needed.
Default deny
The authorization decision is deny unless an explicit grant matches; failures and missing policy fail closed.
Role explosion
A combinatorial growth of near-duplicate roles that becomes as unmanageable as per-user permissions.
Role hierarchy
Inheritance where a senior role includes the permissions of junior roles, reducing duplication.
Separation of duties
A constraint that no single principal can complete a sensitive workflow alone, enforced through mutually exclusive roles.
ABAC / ReBAC
Attribute-based and relationship-based access control: decisions use attributes or graph relationships instead of static roles.

01The problem: permissions assigned directly to users

An internal tool with five people and a handful of permissions is easy: assign each permission to each person. Growth breaks that model.

  • At five users, direct assignment is clear and nobody needs a system for it.
  • At thousands of users and a hundred permissions, onboarding requires remembering exactly which subset a new hire needs.
  • When a policy changes, someone must edit hundreds of users individually, and some will be missed.
  • When an employee moves teams, old permissions usually stay behind — this is privilege creep.
  • Nobody can answer the basic audit question: who can do what in this system?
  • The fix is indirection: group permissions into roles, then assign roles to users.
  • The indirection also gives you one place to review, version, and change a permission set.
User→Role assignment→Role→Permission set→Resource
If adding a person means choosing twenty checkboxes by memory, the model is already broken.

02The RBAC model

  • A principal is the thing being authorized: user, group, service account, or API client.
  • A permission is one action on one resource type, expressed as a stable identifier.
  • A role is a named collection of permissions, chosen to match a job or responsibility.
  • Assignments are many-to-many: a user can hold several roles, and a role can be held by many users.
  • The check is a join: resolve the principal's roles, union their permissions, and test the requested action.
  • Sessions can activate a subset of roles, so an admin role is only live when explicitly assumed.
  • Resources are usually scoped — tenant, organization, project — and the scope is part of the decision, not an afterthought.

03Designing permissions

  • Model resources and actions first; roles are a packaging decision made afterwards.
  • Use stable identifiers such as resource:action, not UI labels or database column names.
  • Granularity is a trade-off: a single admin permission destroys least privilege, while one permission per button becomes unmanageable.
  • Put scope in the permission or the assignment (project:123:read), and check it on every decision.
  • Separate read, write, and destructive actions so a read-only role is genuinely read-only.
  • Do not encode fast-changing business rules as permissions; keep those in policy or application logic.
  • Treat the permission catalog as an API: version it, document it, and make breaking changes deliberately.

04Least privilege

  • Grant the minimum permissions needed for the task, for the minimum time.
  • New accounts should start with no roles, not a broad default role that nobody revisits.
  • Use time-bound or just-in-time elevation for rare administrative tasks instead of permanent admin roles.
  • Scope service accounts to one workload; shared accounts with broad permissions destroy accountability.
  • Missing permissions are visible — someone complains. Extra permissions are invisible until they are abused.
  • Least privilege limits blast radius: a compromised account or token can do less damage.
  • Review permissions after incidents and role changes; drift is normal unless it is actively corrected.

05Default deny

  • The decision must fail closed: if no grant matches, deny.
  • When the model supports explicit deny, it should override any allow, so exceptions are unambiguous.
  • New resources start private; sharing or publishing is an explicit action with an audit trail.
  • A missing role, an unavailable policy service, or an evaluation error must result in deny, not allow.
  • Default allow appears accidentally when checks are optional, applied only in the UI, or skipped for internal callers.
  • Test the deny path explicitly — most test suites only cover the happy path.
  • A 403 should be logged and observable, because repeated denials often indicate a broken role assignment or an attack.
decision = DENY
for grant in principal.grants(scope):
    if grant.permission == requested and grant.scope covers resource:
        decision = ALLOW
if explicit_deny_matches(principal, requested, resource):
    decision = DENY
if policy_engine_error:
    decision = DENY
return decision
A missing policy is a denial, not an exception. Authorization failures must never fall through to allow.

06The permission check on each request

Authentication establishes who is calling; authorization decides whether that principal may perform this action on this resource.

  • Authenticate first, then authorize — never derive identity from a client-supplied role or user ID.
  • Evaluate the tuple (principal, action, resource, scope) against the resolved grants; a role name alone is not enough.
  • Return 401 when the caller is unauthenticated and 403 when authenticated but not permitted.
  • Enforce at every entry point: gateway, service, and data layer for critical operations. One unchecked path defeats the model.
  • Hiding a button is user experience, not authorization; the API must reject the call anyway.
  • Check against the resource actually fetched, not an ID supplied by the client — otherwise you have an IDOR vulnerability.
  • Cache resolved permissions carefully and invalidate on role change; a stale cache is a silent privilege bug.
  • Log both allows and denials for sensitive actions so audits and investigations have evidence.
Authenticate the principal→Resolve roles and scope→Evaluate action on resource→Allow or deny→Record the decision

Authorization: Bearer ...

-> authenticated: user:42
-> roles in tenant:acme: support_agent
-> permission orders:refund? yes

07Role design: functional vs organizational

  • Functional roles describe a job: support agent, billing administrator, auditor, read-only analyst.
  • Organizational or scope roles describe where access applies: team lead for EMEA, owner of project Apollo.
  • Prefer a small set of functional roles plus scopes over many narrow roles encoding every combination.
  • Never create roles named after individuals or one-off exceptions; those are assignments, not roles.
  • Roles should be stable. A role that changes every sprint usually means context belongs somewhere else.
  • Every role needs a description, an owner, and a documented reason to exist.
  • Keep the role count small enough that a reviewer can actually understand the whole set.

08Role explosion

  • Role explosion is the combinatorial growth of roles created for every team, region, tenant, or exception.
  • It happens when roles are used to encode context instead of using scopes, attributes, or relationships.
  • Symptoms: hundreds of near-duplicate roles, roles with a single member, and no clear owner for most of them.
  • Fixes: role hierarchy to share common permissions, scopes for where access applies, and permission groups for reuse.
  • When the variation is genuinely contextual, move that part to ABAC or ReBAC instead of multiplying roles.
  • Merging roles reduces administration but increases the permissions each holder gets — re-check least privilege afterwards.
  • Creating a new role should require review, a name, an owner, and a justification; otherwise the set only grows.
  • Measure roles per user, orphaned roles, and single-member roles to detect the pattern early.
A role per customer is usually a sign that tenancy belongs in the scope or the data model, not in the role name.

09Inheritance and hierarchy

  • A role hierarchy lets a senior role include all permissions of a junior role instead of duplicating the list.
  • Inheritance keeps changes consistent: adding a permission to the base role updates every role above it.
  • It is transitive, so a change high in the tree affects many users — powerful and easy to over-grant.
  • Keep hierarchies shallow; a deep tree is hard to reason about and harder to audit.
  • Scope inheritance mirrors reality: organization roles flow to teams, team roles flow to projects, with explicit overrides.
  • Mix of inheritance and explicit deny can produce confusing outcomes, so define precedence once and document it.
  • Provide a why can this user do X tool that shows the resolved permission and the path that granted it.

10Separation of duties and constraints

  • Separation of duties ensures no single principal can complete a sensitive workflow alone: create a vendor and approve its payment, for example.
  • Enforce it with mutually exclusive roles, not just a written policy nobody checks at runtime.
  • Static separation forbids assigning conflicting roles to the same principal at all.
  • Dynamic separation forbids holding them active in the same session, allowing the person to switch hats.
  • Cardinality constraints limit how many principals may hold a sensitive role.
  • Prerequisite constraints require another role or an approval before a role can be granted.
  • Break-glass access should be temporary, require justification, and generate an alert and a review item.
  • Small teams often cannot satisfy strict separation; use compensating controls such as approval workflows and audit review.

11The limits of RBAC: ABAC and ReBAC

  • RBAC answers does this role allow this action? It does not naturally answer is this the user's own record? or is this during business hours?
  • ABAC evaluates attributes of the subject, resource, action, and environment through policy rules.
  • ReBAC evaluates relationships — owner, editor, member of team, parent folder — which fits sharing and nested resources.
  • ABAC and ReBAC handle context and per-object sharing but are harder to reason about, test, and audit.
  • Hybrid is normal: RBAC for job function, ABAC or ReBAC for ownership, tenant scope, and sharing.
  • Policy-as-code with unit tests keeps complex rules reviewable and prevents regressions.
  • Choose the simplest model that expresses the requirement; start with RBAC and add context only when a real case demands it.

12Multi-tenancy and delegated administration

  • Every permission should be scoped to a tenant, and cross-tenant access must be an explicit, rare grant.
  • Tenant isolation must be enforced in data access, not only in the API layer; a missing filter leaks another customer's data.
  • Delegated administration lets tenant admins manage their own users inside a permission boundary.
  • An admin must not be able to grant permissions they do not hold — otherwise delegation becomes privilege escalation.
  • Keep a canonical role catalog and let tenants choose from it; per-tenant custom roles drift and multiply.
  • Test with two tenants and a guessed resource ID to catch tenant-leak and IDOR bugs before attackers do.
  • Platform administrator and tenant administrator are different roles with very different blast radius; never merge them.
Request with tenant context→Authenticate principal→Resolve roles within that tenant→Authorize action + resource ownership→Scope the data query→Respond
If the tenant is inferred from the request body rather than the authenticated principal, isolation is already broken.

13Audit, review, and lifecycle

  • Log every grant, revoke, role change, and sensitive authorization decision with actor, target, scope, time, and reason.
  • Audit logs should be append-only or tamper-evident, and retained according to policy and regulation.
  • Run periodic access reviews where managers certify that each principal still needs each role.
  • Joiner, mover, leaver: provision on day one, change roles on transfer, and revoke everything on exit.
  • Stale access is the most common audit finding; detect unused roles and permissions rather than waiting for a review cycle.
  • Reviews only work if reviewers can see effective permissions, not just raw role names.
  • Measure time to revoke access, orphaned accounts, and roles without owners; these expose lifecycle failures.

↔Trade-offs to say out loud

  • Roles as indirection make permissions manageable at scale but add a layer that must be designed, documented, and audited.
  • Fine-grained permissions enable least privilege but multiply the permission catalog and the chance of misconfiguration; coarse permissions are simpler but over-grant.
  • Few broad roles are easy to administer but give each user more access; many narrow roles improve least privilege but cause role explosion.
  • Role inheritance removes duplication and keeps changes consistent but makes a single edit affect many users and complicates reasoning.
  • Centralized enforcement gives consistency and auditability but creates a shared dependency and a potential latency or availability bottleneck.
  • Permission caching keeps authorization fast but risks stale grants after a role change; no cache is correct but slower.
  • Static separation of duties is easy to verify but inflexible for small teams; dynamic separation is flexible but harder to enforce and audit.
  • ABAC/ReBAC express ownership and context that RBAC cannot, at the cost of policy complexity, testing burden, and explainability.

?Interview questions

Answer aloud before opening the outline.

1. What is RBAC?

Role-Based Access Control: permissions are grouped into roles, roles are assigned to principals, and each request is checked against the permissions those roles grant. It replaces per-user permission lists with a manageable indirection layer.

2. Why not assign permissions directly to users?

It does not scale. Onboarding depends on memory, policy changes require editing hundreds of users, transfers leave stale permissions, and nobody can answer who can do what. Roles centralize the permission set so it can be reviewed and changed once.

3. How does a permission check work on a request?

Authenticate the principal, resolve the roles assigned in the relevant scope, union their permissions, and test whether the requested action on that specific resource is allowed. Then enforce it at the service and data layer, and log the decision. Role names alone are not a decision.

4. What is least privilege and how do you enforce it?

Grant only what the task requires, for only as long as it is required. Start accounts with no roles, scope permissions to a tenant or project, use just-in-time elevation for admin work, and review grants regularly. Missing access is visible; excess access is not.

5. What does default deny mean in practice?

No matching grant means deny, and any evaluation failure also denies. Explicit denies override allows, new resources start private, and every entry point enforces the check. Optional or UI-only checks create accidental default allow.

6. What is role explosion and how do you fix it?

It is the runaway growth of near-duplicate roles per team, tenant, or exception. Fix it by using scopes for where access applies, hierarchy and permission groups for reuse, and moving genuinely contextual rules to ABAC/ReBAC. Review new role requests and track single-member roles.

7. How does role inheritance help and what is the risk?

Inheritance lets senior roles reuse junior permission sets, so a change is made once. The risk is that edits high in the hierarchy silently affect many users, and deep trees become hard to audit. Keep hierarchies shallow and provide an effective-permissions view.

8. What is separation of duties?

A constraint that no single principal can complete a sensitive workflow alone — for example, the person who creates a vendor cannot also approve its payment. Enforce it with mutually exclusive roles, either statically (never assign both) or dynamically (never active in the same session).

9. When does RBAC stop being enough?

When decisions depend on attributes (time, department, data classification) or relationships (owner of this document, member of this team). Then add ABAC for attribute policy or ReBAC for relationship graphs, usually alongside RBAC rather than replacing it.

10. What is the difference between RBAC, ABAC, and ReBAC?

RBAC decides from assigned roles, ABAC from attributes of subject, resource, action, and environment, and ReBAC from relationships in a graph such as ownership or group membership. RBAC is simplest to audit; ABAC and ReBAC are more expressive but harder to reason about.

11. How do you prevent privilege escalation through role administration?

Only allow a principal to grant roles and permissions it already holds, require approval for sensitive roles, and restrict who can edit role definitions. Log every grant. Treat role administration itself as a privileged permission.

12. Where should authorization be enforced?

At the service boundary for every operation, and again at the data layer for critical or tenant-scoped access. The gateway can do coarse checks, but it cannot know object ownership. UI hiding is not enforcement — the API must reject unauthorized calls on its own.

13. How do you handle multi-tenancy with RBAC?

Scope every role assignment and permission to a tenant, derive the tenant from the authenticated principal rather than the request body, and filter all data access by it. Give tenant admins delegated control within a boundary so they cannot grant more than they hold. Never merge tenant admin with platform admin.

14. What should an access audit include?

Every grant, revoke, role-definition change, and sensitive allow/deny decision with actor, target, scope, timestamp, and reason. Plus periodic reviews that certify each principal's effective permissions, and lifecycle checks for joiners, movers, and leavers. Tamper-evident retention matters for compliance.

!Traps

  • Checking permissions only in the UI while the API accepts any authenticated request.
  • Creating a role per user, team, or customer instead of using scopes — role explosion by another name.
  • Granting a broad default role to new accounts and never reviewing it.
  • Letting a missing policy or a failed policy service fall through to allow.
  • Authorizing against a client-supplied user ID or role instead of the authenticated principal.
  • Trusting a stale permission cache after a role change or termination.
  • Letting admins grant permissions they do not hold, which turns delegation into escalation.
  • Assuming RBAC handles object ownership and tenant isolation without explicit checks.
