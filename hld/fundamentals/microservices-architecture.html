Service
A small, independently deployable unit aligned to a business capability, with its own process, pipeline, and data store.

A domain-driven design boundary inside which one model and its vocabulary are consistent; different contexts translate at the edge.

API contract
The versioned shape of a service's requests and responses (or published events) that consumers depend on.
Service discovery
A registry or DNS mechanism that lets callers find healthy instances as they scale, move, and restart.
Saga
A sequence of local transactions across services where each step has a compensating action if a later step fails.
Transactional outbox
Writing the state change and its outgoing event in one local transaction, then relaying the event, to avoid dual-write inconsistency.

The edge component that handles routing, authentication, rate limiting, and request IDs for clients.

Propagating a trace context across service calls so one request can be reconstructed end to end.

A single deployable with enforced internal module boundaries — most of the code discipline of microservices without the network.

01The problem microservices solve

As an application and its team grow, one large codebase starts to slow everyone down. The pain is organizational as much as technical.

  • A small change touches shared code, so every release carries risk for features nobody intended to change.
  • Deployments become all-or-nothing: one team's unfinished work blocks another team's urgent fix.
  • Scaling is coarse — the whole application is replicated even when only one feature is hot.
  • Technology choices are frozen for the entire codebase, including parts with very different needs.
  • Failures are process-wide: a memory leak or crash in one module takes down everything in that process.
  • Coordination cost grows with headcount: more teams means more merge conflicts and more release meetings.
  • These are symptoms of coupling, not proof that the answer is many services.
The real question is not monolith or microservices — it is which boundaries would let teams change and ship independently.

02What microservices architecture is

  • The system is decomposed into small services aligned to business capabilities, not to technical layers.
  • Each service runs in its own process and is deployed independently on its own schedule.
  • Services communicate over the network using synchronous APIs (HTTP/REST, gRPC) or asynchronous messages and events.
  • Each service owns its data store; there is no shared schema and no direct cross-service table access.
  • Services may use different languages or databases where that genuinely helps, at the cost of more operational surface.
  • A team owns its service end to end: build, deploy, run, and on-call.
  • Small means a clear boundary and a small enough surface for one team to hold in their heads — not a line-count target.
  • The architecture is a sociotechnical choice: it works when team structure and ownership match service boundaries.
Client→API gateway→Order service→Order database

03Drawing service boundaries

Boundary choice is the single most important decision. Bad boundaries produce the worst of both worlds: network calls plus tight coupling.

  • Decompose by business capability — orders, payments, inventory, shipping, notifications — not by controller, service, and repository layers.
  • Use bounded contexts: a model is internally consistent inside the boundary and translated at the edge, so the same word can mean different things in different services.
  • Things that must change together should live together; if two services always ship in lockstep, they are one service with extra latency.
  • Avoid entity services (one service per table); they turn every read into a chatty CRUD call and every query into a distributed join.
  • Look for transaction boundaries: an operation that must be atomic usually belongs inside one service.
  • Start from existing seams — modules, team ownership, and natural data partitions — rather than a full rewrite.
  • Treat boundaries as hypotheses and expect to merge or split them once real usage appears.

04Own your data

  • Database per service is the defining rule: only the owning service reads or writes its schema directly.
  • Consumers get data through an API or by subscribing to events, never by querying another service's tables.
  • A private schema lets a service change indexes, columns, or even the database engine without coordinating with consumers.
  • A shared database is the most common way microservices quietly decay into a distributed monolith.
  • Cross-service reads become API composition or read models (projections) built from events.
  • Some duplication is expected and healthy: each service keeps a copy shaped for its own access pattern.
  • Reporting and analytics should read from a warehouse or a change-data-capture stream, not from live service databases.
  • Polyglot persistence is allowed, but each added datastore adds backup, upgrade, and on-call burden.
If two services must read and write the same table, you probably have one service, not two.

05Communication: synchronous APIs

  • Request/response over REST, gRPC, or GraphQL: the caller sends a request and waits for a result.
  • Easy to reason about, and the caller learns immediately whether the operation succeeded.
  • Creates runtime coupling: if the callee is slow or down, the caller is affected.
  • Requires timeouts, bounded retries with backoff and jitter, circuit breakers, and per-dependency connection pools.
  • Chains of synchronous calls multiply latency and multiply the chance that at least one hop fails.
  • Best for queries and user-facing reads where an answer is needed now.
  • Contracts must be versioned and backward compatible because consumers deploy on their own schedule.
  • Prefer coarse-grained calls: one meaningful operation beats ten chatty lookups.

06Communication: asynchronous events and messages

  • A producer publishes a message or event to a broker; consumers process it later, independently.
  • This decouples in time: the producer does not wait, and a consumer can be down and catch up afterwards.
  • Queues distribute work across competing consumers; topics/logs fan out to many independent consumer groups and allow replay.
  • The price is eventual consistency, duplicate delivery, ordering ambiguity, and another stateful system to operate.
  • Use asynchronous flows for side effects: emails, notifications, search indexing, analytics, and propagation to other services.
  • Message schemas are contracts too; a schema registry or versioned event types keeps producers and consumers compatible.
  • Consumers must be idempotent, because at-least-once delivery is the normal guarantee.
  • Keep the payload focused on facts plus identifiers rather than dumping an entire internal model.
Producer commits state and event→Broker stores the event→Consumers process independently→Retry, then dead-letter on repeated failure

07Independent deployment

  • Each service has its own pipeline, artifact, and release cadence — this is the main payoff of the architecture.
  • It only works if APIs and events stay backward compatible, so old and new versions can run side by side during a rollout.
  • Database changes use expand and contract: add the new column, dual-write and backfill, switch reads, then drop the old column in a later release.
  • Deploy and release are separate: feature flags let code ship dark and be enabled later.
  • Rollback must be safe; once downstream services consume a new event, rolling back the producer may not undo the effect.
  • Version and label every instance so logs and metrics show which build produced an anomaly.
  • If services can only be released together, you have a distributed monolith and pay the network cost for nothing.
Build→Contract tests→Deploy canary→Observe→Full rollout or rollback

08Independent scaling

  • Scale only the service that is hot instead of replicating the entire application.
  • Each service has its own resource profile — CPU-heavy encoding, memory-heavy caching, IO-heavy queries — and can be sized separately.
  • Autoscaling requires stateless instances, fast startup, and a load balancer that can add and remove targets.
  • Shared bottlenecks still cap the system: one primary database, one broker partition, or one gateway can undo per-service scaling.
  • More instances mean more coordination, more connections to downstream systems, and more telemetry.
  • Set SLOs and capacity targets per service rather than one global average.
  • Connection pooling and concurrency limits protect downstream systems from a scaled-out caller.

09Failure isolation and resilience

  • Design for partial failure: a request that touches five services has five chances to fail or stall.
  • Timeouts bound how long a caller waits; without them, threads and connections pile up.
  • Retries must be bounded, jittered, and applied only to idempotent operations — otherwise they amplify an outage.
  • Circuit breakers fail fast while a dependency is unhealthy and probe for recovery instead of hammering it.
  • Bulkheads give each dependency its own pool, so one slow dependency cannot starve all request handling.
  • Idempotency keys make retried writes safe and are essential for payments and order creation.
  • Graceful degradation — cached or partial content, queued writes — beats failing the whole page.
  • Health checks and readiness gates keep traffic away from instances that cannot serve it.
Call dependency→Timeout or breaker opens→Fallback, queue, or error→Probe and close breaker

10Operational prerequisites

Microservices move complexity from code into operations. Without the platform, the architecture fails for reasons unrelated to design.

  • Containers and orchestration (or an equivalent platform) to schedule, restart, and place many small deployments.
  • Service discovery and load balancing, because instances appear and disappear constantly.
  • An API gateway at the edge for authentication, routing, rate limits, and request IDs.
  • Centralized logs, metrics, and distributed tracing with a correlation ID propagated across every hop.
  • Externalized configuration and secret management instead of baked-in environment values.
  • Per-service SLOs, alerting, and a clear on-call owner; anonymous services become nobody's problem.
  • CI/CD with contract tests, canaries, and automated rollback.
  • Cost visibility per service, because many small workloads can cost more than one large one.
A useful test: could you deploy this service on a Friday afternoon without a meeting? If not, the platform or the boundaries are not ready.

11Data consistency across services

  • ACID transactions stop at the service boundary; there is no cheap distributed transaction across independent databases.
  • A saga is a sequence of local transactions with compensating actions when a later step fails.
  • Compensations are business actions (refund, release reservation), not a rollback — some effects may be visible briefly.
  • Orchestration uses a central coordinator that knows the steps; choreography lets each service react to events.
  • The transactional outbox solves the dual-write problem: write state and the outgoing event in one local transaction, then relay the event.
  • Consumers must deduplicate or be idempotent, since events can be delivered more than once.
  • Eventual consistency must reach the UX: show pending or processing states instead of pretending the write already propagated.
  • Reconciliation jobs catch drift when compensations or retries fail in ways the saga did not anticipate.

12Benefits and costs

  • Benefits: team autonomy, independent deploys, targeted scaling, fault isolation, and freedom to choose tools per service.
  • Costs: network latency, partial failure, distributed data, duplicated infrastructure, and much harder debugging.
  • A remote call is orders of magnitude slower and less reliable than an in-process call; design coarse boundaries to keep the count low.
  • Testing shifts: unit tests stay easy, but integration and contract tests are required to catch breakage between independently deployed services.
  • Every engineer needs baseline distributed-systems literacy: retries, idempotency, consistency, and observability.
  • Organizational fit matters: teams must be able to own a service end to end, or the autonomy is fictional.
  • Microservices are primarily a scaling tool for organizations and change rate, not a default for good code.

13Monolith, modular monolith, microservices

  • A monolith is one deployable with shared memory and one database; simplest to build, test, and operate.
  • A modular monolith keeps one deployable but enforces internal module boundaries and private data per module.
  • A well-modularized monolith can be split later; a tangled one usually has to be rewritten first.
  • Choose microservices when independent deploy cadence, team autonomy, or per-component scaling is the real constraint.
  • Fewer services is usually better — each one adds a network boundary, a pipeline, and an on-call rotation.
  • Serverless functions, containers, and services are orthogonal choices; a system can mix all three.

14Deciding and migrating

  • Do multiple teams genuinely block each other on releases? If not, microservices buy little.
  • Can you fund the platform, observability, and on-call work? If not, the architecture will fail operationally.
  • Is the domain understood well enough to draw stable boundaries? If not, start with a modular monolith.
  • Can the key flows tolerate eventual consistency? If not, keep those flows inside one service.
  • Do you have a plan for cross-service reporting and historical data before you split the schema?
  • Migrate with the strangler fig pattern: put a facade in front of the capability, extract it, route traffic over, then delete the old path.
  • Extract the least entangled, highest-pain capability first to prove the platform and the team model.

↔Trade-offs to say out loud

  • Independent deployment speeds up teams but turns every interface into a versioned contract that must stay backward compatible.
  • Database per service enables autonomous change but makes joins, transactions, and reporting into distributed problems.
  • Synchronous APIs give immediate answers but create runtime coupling and cascading failure across hops.
  • Asynchronous events decouple services in time but introduce eventual consistency, duplicates, and ordering questions.
  • Targeted scaling saves capacity but shared bottlenecks and per-service overhead can erase the gain.
  • Fault isolation contains failures to one service but forces every caller to handle partial failure and fallbacks.
  • Technology heterogeneity lets each team pick the right tool but multiplies operational and hiring surface.
  • Fine-grained services maximize isolation and reuse but multiply network calls, latency, and coordination cost.
  • Team autonomy increases throughput but requires a real platform team and end-to-end ownership.
  • Starting with a monolith is faster and simpler but can delay the organizational scaling the business needs.

?Interview questions

Answer aloud before opening the outline.

1. What is microservices architecture?

A style where the system is split into small services aligned to business capabilities, each independently deployable, owning its own data, and communicating over the network through APIs or events. The goal is independent change and scaling per team, at the cost of distributed-systems complexity.

2. How do you decide where service boundaries go?

Start from business capabilities and bounded contexts, then test the boundary against change cadence: do changes ship with one service, is there a single writer of the data, and does one team own it end to end? Avoid one-service-per-table designs and split only where atomicity is not required across the seam.

3. Why does each service need its own database?

Private schema is what makes independent evolution real: the service can change storage without coordinating with consumers. A shared database recreates compile-time-style coupling over the network, so schema changes require cross-team releases and services silently depend on each other's internals.

4. When would you use synchronous calls instead of events?

Use synchronous calls for queries and user-facing reads where the caller needs an answer now. Use events for side effects and propagation where the caller does not need to wait. Synchronous chains are acceptable when short and bounded; long chains of blocking calls multiply latency and failure probability.

5. How do you handle a transaction that spans services?

You cannot use a single ACID transaction. Use a saga: a sequence of local transactions, each with a compensating action if a later step fails. Pair writes with a transactional outbox so state and events commit together, and make consumers idempotent because delivery is at least once.

6. What is a distributed monolith and how do you spot one?

It is a system split into services that still must be deployed, versioned, or changed together, so you pay network and operational costs without gaining autonomy. Signals: shared databases, lockstep releases, chatty synchronous chains, and services that cannot be tested alone.

7. How do you deploy independently without breaking consumers?

Keep APIs and events backward compatible, version contracts, and use expand-and-contract for schema changes: add the new field, dual-write and backfill, migrate readers, then remove the old field later. Contract tests and canary releases catch breakage before full rollout.

8. How do you prevent one slow service from taking down the system?

Use timeouts, bounded jittered retries only for idempotent calls, circuit breakers to fail fast, and bulkheads so each dependency has its own pool. Add graceful degradation such as cached or partial responses, and monitor error rates and saturation per dependency.

9. What operational capabilities are required before adopting microservices?

Automated per-service CI/CD, container orchestration, service discovery and load balancing, an API gateway, centralized logs and metrics, distributed tracing, secret management, and per-service SLOs with on-call ownership. Without them, the team spends its time firefighting infrastructure instead of shipping.

10. How do you debug a request that crosses many services?

Propagate a correlation or trace ID from the edge through every call and message, and include it in every log line. Centralized logs plus distributed tracing reconstruct the request path, timings, and errors. Without a shared identifier, cross-service debugging is guesswork.

11. When would you not use microservices?

When the domain is poorly understood, the team is small, release coordination is not actually a bottleneck, or there is no platform and observability investment. A modular monolith gives most of the code-level discipline with far less operational cost, and can be split later.

12. How do you migrate a monolith to services?

Use the strangler fig approach: pick a capability with clear boundaries, put a facade in front of it, extract the implementation into a service, shift traffic gradually, and delete the old code path. Extract the least entangled high-pain capability first to validate the platform and team model.

13. How do you test microservices?

Unit-test business logic inside each service, contract-test the interfaces consumers depend on, and run a small number of end-to-end tests for critical flows. Test failure paths deliberately: timeouts, retries, duplicate events, and dependency outages. Heavy end-to-end suites become slow and flaky as service count grows.

14. How do you handle reporting when data is spread across services?

Do not query live service databases. Stream changes into a warehouse or data lake using CDC or events, and build read models there. This keeps service schemas private and gives analytics a stable, queryable copy without adding load to transactional systems.

!Traps

  • Splitting by technical layer (UI service, logic service, data service) instead of business capability.
  • Keeping a shared database and calling the result microservices.
  • Creating one service per entity, which turns every screen into a chain of chatty CRUD calls.
  • Using distributed transactions or two-phase commit across service databases instead of sagas.
  • Shipping services that can only be released together — a distributed monolith.
  • Adding unbounded retries without idempotency, turning a small outage into a retry storm.
  • Adopting microservices before observability, CI/CD, and on-call ownership exist.
  • Measuring success by service count rather than by deploy frequency, lead time, and reliability.
