Failure domain
A unit whose failure is independent of others, such as a disk, node, rack, or availability zone.

01The problem with keeping full copies

  • Disks and servers fail constantly in large storage systems, so every byte needs redundancy.
  • The simplest defense is replication: keep two or three complete copies of everything.
  • Three copies means storing three times the data, so most of the budget buys durability rather than capacity.
  • Replication also triples the write traffic and the bytes moved during repair.
  • At very large scale, the storage overhead becomes the dominant cost of the cluster.
  • Erasure coding keeps comparable failure tolerance while storing far less extra data.

02What erasure coding is

  • The object is split into k equal-sized data chunks.
  • The system computes m additional parity chunks from those data chunks.
  • All k+m chunks are stored on different disks or servers.
  • Any k of the k+m chunks are enough to rebuild the original object.
  • If up to m chunks are lost, nothing is lost permanently.
  • The trade is storage efficiency for extra CPU and repair traffic.
Erasure coding is redundancy without full copies: the parity chunks carry information about the data chunks rather than duplicate bytes.

03The k+m layout

A code is described by how many data chunks it needs and how many it can lose. With k=10 and m=4, an object becomes fourteen stored chunks and survives any four losses.

  • Total stored bytes are (k+m)/k times the object size — in that example, 1.4× instead of 3× for triple replication.
  • Increasing m raises durability but also overhead.
  • Increasing k lowers overhead but means each chunk is larger and repair reads more data.
  • A larger k also requires more chunks to be available for a normal read.
  • Extremely wide codes reduce overhead further but make reconstruction and repair more expensive.
  • The chosen ratio is a direct statement about how much durability you are willing to pay for.

04Why any k chunks are enough

  • The parity chunks are linear combinations of the data chunks over a finite field.
  • That produces k+m equations in k unknowns.
  • Any k independent equations can solve for the original k data chunks.
  • Reed-Solomon codes are the standard construction and guarantee recovery from any m erasures.
  • The arithmetic is more than simple XOR; it needs multiplication in a Galois field.
  • Practically, the encoder computes parity in software or with hardware acceleration.
  • Not every code has this any-m property: simple XOR parity schemes only tolerate specific failure patterns.

05Failure tolerance in practice

  • Failure tolerance is m chunks, but only if no two chunks share a failure domain.
  • Chunks must be spread across disks, nodes, racks, and sometimes zones.
  • Placing two chunks of the same object on one server halves the effective tolerance for that server's failure.
  • A rack loss can remove several chunks at once, so placement must account for correlated failure.
  • Durability also depends on repair speed: the longer data stays degraded, the more chances for another loss.
  • This is why placement policy and repair scheduling are part of the durability guarantee, not just the code.

06The read path

  • Normal read: fetch the k data chunks, optionally in parallel, and reassemble.
  • Reading k chunks instead of one full copy means more requests but less total data than replication.
  • Latency is set by the slowest of the parallel requests, so tail latency matters.
  • Degraded read: if some chunks are missing, fetch enough survivors and decode.
  • A degraded read costs extra network and CPU, so it should be rare and observable.
  • Clients usually verify checksums per chunk before trusting a reconstructed result.
  • Small objects do not suit this model well, because splitting and parity add overhead per object.
Client requests an object→System looks up chunk locations from metadata→Client fetches chunks in parallel→If all data chunks arrive, assemble and return→If some are missing, fetch extra survivors and decode

07Repair and reconstruction

  • When a chunk is lost, the system reads k surviving chunks and recomputes the missing one.
  • This is cheaper in bytes than copying a full replica, but costs CPU and network.
  • Repair traffic competes with normal client traffic and must be throttled.
  • Repair is usually scheduled in the background with priority for the most degraded objects.
  • A single disk replacement may require reading from many other disks, creating a repair storm.
  • Placement should limit how many chunks of one object a single repair job must touch.
  • Faster repair directly improves durability because degraded windows shrink.

08Erasure coding versus replication

  • Replication is simple: write the same bytes to several places and read from any one.
  • Erasure coding stores far less overhead for the same failure tolerance.
  • Replication has lower read latency and no decode cost.
  • Replication repairs by copying one replica; erasure coding repairs by decoding from many chunks.
  • Erasure coding costs CPU on write, on degraded read, and on repair.
  • Replication handles small objects and random overwrites naturally; coding does not.
  • The usual pattern is replication for hot, small, latency-sensitive data and coding for large, cold, or archival objects.

09Where erasure coding is used

  • Object storage backends storing large immutable blobs where storage cost dominates.
  • Archival and backup tiers that tolerate higher read latency.
  • Distributed file systems that apply coding to cold files while keeping hot files replicated.
  • Large-scale storage clusters that need high durability without tripling disk purchases.
  • Content-addressed or append-only stores where objects are written once and read rarely.
  • Any system where a lower redundancy ratio meaningfully changes the cost curve.

10Costs and limitations

  • CPU: encoding and decoding are real work, especially for wide codes.
  • Write amplification: one logical write produces k+m chunk writes.
  • Update cost: changing a chunk means recomputing parity, so in-place mutation is expensive.
  • Small objects: splitting a tiny object into many chunks is pure overhead.
  • Latency: reads touch many chunks, so tail latency is worse than a single replica read.
  • Operational complexity: placement, repair scheduling, and degraded-read monitoring are all required.
  • Coding is therefore a cost optimization for the right data class, not a universal replacement for replication.

11Choosing a code and placement

  • Pick m from the number of simultaneous failures you must survive.
  • Pick k to balance overhead against repair cost and read fan-out.
  • Never place two chunks of the same object in the same failure domain.
  • Match the code to the object size: tiny objects stay replicated or bundled.
  • Keep hot data replicated and transition cold data to coded form.
  • Set a repair priority policy so the most degraded objects are fixed first.
  • Measure degraded-read rate and repair backlog as first-class health signals.

12Decision rules

  • Use erasure coding when storage cost dominates and data is large, immutable, or cold.
  • Use replication when latency, simplicity, or small-object throughput dominates.
  • Use a hybrid when workloads differ: replicate the hot tier and code the cold tier.
  • Do not apply coding to a database's live data files.
  • Always validate that placement actually matches the failure domains you claim to survive.
  • State the redundancy target as survive m concurrent failures, not as a vague durability claim.

↔Trade-offs to say out loud

  • Erasure coding cuts storage overhead sharply, but adds CPU cost on write, read, and repair.
  • A larger m survives more concurrent failures, but raises the storage multiplier and write cost.
  • A larger k lowers overhead, but increases chunk size, read fan-out, and repair work per lost chunk.
  • Degraded reads keep data available after loss, but cost extra network and CPU and raise tail latency.
  • Faster repair shortens the vulnerable window, but competes with client traffic for bandwidth.
  • Wide placement across racks improves failure independence, but increases cross-rack traffic and latency.
  • Hybrid tiers get the best of both, but add a migration policy and two code paths to operate.
  • Low-overhead storage makes capacity cheap, but concentrates risk in the repair system's ability to keep up.

?Interview questions

Answer aloud before opening the outline.

1. What is erasure coding?

A redundancy technique that splits data into k chunks, computes m parity chunks, and stores all of them across independent failure domains. Any k of the k+m chunks can rebuild the original. It provides replication-like durability with much less extra storage.

2. Why not just keep three copies?

Three copies triple storage, write traffic, and repair bytes, which dominates cost at large scale. Erasure coding can survive a comparable number of failures with overhead closer to 1.4× or 1.5×. The price is CPU for encoding and decoding plus more complex repair.

3. What do k and m mean?

k is the number of data chunks the object is split into, and m is the number of parity chunks computed from them. The system tolerates any m lost chunks and stores (k+m)/k times the original size. Larger m means more durability and more overhead.

4. How can any k chunks reconstruct the data?

Parity chunks are linear combinations of the data chunks, so the k+m stored chunks form k+m equations over k unknowns. Any k independent equations are enough to solve for the originals. Reed-Solomon codes guarantee this for any m erasures.

5. What is a degraded read?

A read served while some chunks are missing, so the system fetches enough surviving chunks and decodes the object. It keeps data available after a failure but costs extra network and CPU. A high degraded-read rate means repair is falling behind.

6. How does repair work?

The system reads k surviving chunks, recomputes the lost chunk, and writes it to a new location. That is less data than copying a whole replica but more nodes are involved. Repair must be throttled and prioritized so it does not starve client traffic.

7. Why does placement matter as much as the code?

Because tolerance is counted in independent failures. If two chunks of one object sit on the same server or rack, a single failure consumes two of the m allowed losses. Placement across disks, nodes, racks, and zones is what makes the theoretical guarantee real.

8. When is erasure coding a bad choice?

For small objects, hot data, and workloads with frequent in-place updates. Splitting tiny objects wastes effort, reads fan out and hurt tail latency, and updating a chunk forces parity recomputation. Those cases are better served by replication.

9. Why is updating coded data expensive?

A logical update changes data chunks, which invalidates the parity computed from them. The system must recompute and rewrite parity, producing write amplification. Append-only or immutable objects avoid this, which is why coding suits cold and archival data.

10. Erasure coding vs replication — what is the rule of thumb?

Replicate what is hot, small, and latency-sensitive; code what is large, cold, and cost-sensitive. Many systems do both, keeping recent data replicated and moving aged data into coded form. The decision is about which cost dominates: latency and CPU, or raw capacity.

11. Does erasure coding replace backups?

No. It protects against losing chunks to hardware failure, not against deleting or corrupting the logical object. A delete propagates to every chunk and parity piece. Versioning, snapshots, and off-cluster backups are still required for logical damage.

12. What operational signals should you watch?

Degraded-read rate, under-repaired chunk count, repair backlog and throughput, and decode CPU usage. Placement drift matters too, since a rebalance can accidentally co-locate chunks. These signals tell you whether the durability you designed is the durability you have.

!Traps

  • Quoting a failure-tolerance number without checking that chunks are actually spread across independent failure domains.
  • Applying erasure coding to small or hot objects and paying decode latency for no real saving.
  • Forgetting that repair consumes real bandwidth and can collide with production traffic.
  • Assuming erasure coding protects against deletion or corruption of the logical object.
  • Choosing a very wide code to minimize overhead and then being unable to repair it fast enough.
  • Ignoring degraded-read rate, so a cluster looks healthy while every read decodes.
