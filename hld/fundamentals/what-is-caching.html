01What a cache is

Reading from a database or calling another service takes time. Under heavy traffic, that cost repeats on every request.

  • A cache is a fast storage layer holding copies of data that would otherwise be fetched from a slower system.
  • It usually sits in memory or at the edge, where access is far cheaper than a database query or a remote call.
  • The cache does not replace the source of truth; it holds a copy that can be discarded.
  • Caching works because real traffic repeats: many users request the same product, profile, or configuration.
  • The core trade is explicit: faster repeat reads in exchange for a copy that can be stale.

02How caching works: hits and misses

The basic flow is check the cache first, then fall back to the source of truth.

  • On a hit, the value is already cached and is returned immediately without touching the database.
  • On a miss, the application fetches from the database, stores the result in the cache, then returns it.
  • A miss costs slightly more than an uncached request because the cache check happens first.
  • The payoff comes from later requests: once the value is cached, every repeat request becomes a hit.
  • The first request for any key is therefore the slowest; steady-state performance depends on reuse.
  • Who performs the miss handling depends on the strategy — the application in cache-aside, the cache layer in read-through.
Request arrives→Check cache→Hit: return value→Miss: read database→Store in cache→Return value

03Why caching helps

Caching improves three things at once, which is why it is one of the highest-leverage additions to a read-heavy system.

  • Lower latency: reads come from memory or a nearby edge instead of a database or remote service.
  • Reduced load: fewer requests reach the database or downstream service, freeing capacity for other work.
  • Higher throughput: the same infrastructure handles more traffic when most requests are served cheaply.
  • It protects expensive components, so a traffic spike hits the cache rather than the database.
  • It can postpone or avoid more complex scaling work such as sharding.
  • It is not only about individual request speed; it changes how much traffic the whole system can absorb.

04Understanding the cache hit ratio

The hit ratio is the percentage of requests served from the cache. It is the primary measure of cache effectiveness.

  • Formula: hit ratio = hits / (hits + misses).
  • If 900,000 of one million requests are served from cache, the hit ratio is 90 percent.
  • Higher is generally better because more requests avoid the backend.
  • Hit ratio must be read alongside total traffic, not in isolation.
  • At 10 million requests per second, a 95 percent hit ratio still sends 500,000 requests per second to the backend.
  • A small miss rate becomes a large absolute load at scale, so the miss path must still be sized properly.
  • When sizing the database behind a cache, size it for the misses, not for total traffic.

05Caching layers in a system

A request can pass through several caches before reaching the database. Each layer has a different job and a different scope.

  • Browser cache: stores images, JavaScript, CSS, and sometimes API responses; the closest cache to the user.
  • CDN cache: stores content at edge locations near users, best for static content, media, and shared public pages.
  • Application cache: in-process memory on each server; fastest, but per-instance and duplicated.
  • Distributed cache: a shared Redis or Memcached tier; slower than local memory but consistent across servers and much larger.
  • Database cache: the database's internal buffer pool for pages and query data, managed automatically.
  • Layers are complementary: a CDN hit may avoid the request entirely, while an application hit avoids only the database call.
  • Where you cache determines both the latency saved and who is responsible for invalidation.

06Browser and CDN caching

  • The browser can serve a valid copy without any network request, which is the cheapest possible hit.
  • Its behaviour is controlled by HTTP headers such as Cache-Control and validators such as ETag.
  • A CDN caches content at edge locations, so users download from nearby rather than from origin servers.
  • CDNs work best for static content, media files, public pages, and anything many users can share.
  • User-specific or highly dynamic responses are poor CDN candidates unless varied correctly by headers or keys.
  • Invalidation at the edge is usually coarse, so versioned URLs or short TTLs are common.

07Application, distributed, and database caches

  • An application cache lives inside the running process, so lookups are extremely fast and require no network hop.
  • The cost is that each instance has its own copy: memory is duplicated and values can differ between instances.
  • A distributed cache gives every server the same view and can hold far more data, at the cost of a network round trip.
  • Distributed caches also centralize invalidation, which is simpler than telling every app instance to drop a key.
  • Databases maintain their own internal caches for frequently accessed pages; application code usually cannot see or control them.
  • Choosing between local and distributed is a choice between speed and shared consistency.

08Choosing what to cache

Caching works best when the same data is requested repeatedly and is expensive to fetch or compute.

  • Good fits: frequently viewed product details, expensive queries, API responses, configuration, sessions, and complex computations.
  • The more often a value is reused, the more useful caching it becomes.
  • Poor fit — changes constantly: the cached copy is stale almost immediately.
  • Poor fit — must be fresh: serving an outdated value is unacceptable, such as an account balance.
  • Poor fit — huge and rarely read: a large object requested once every few hours wastes memory.
  • Before caching, ask how expensive the data is to retrieve, how often it is requested, how often it changes, and how much staleness is tolerable.

09Designing cache keys

A cache key identifies a cached value. It decides which requests are allowed to share a result.

  • A cache is usually a key-value store: the application supplies a key and receives the value stored under it.
  • Examples: product:123, user:456, search:shoes:page:2.
  • Too broad: different requests collide and return the wrong data — two users' carts both stored under cart.
  • Too specific: keys like product:123:<timestamp> create duplicates and almost every lookup misses.
  • Include every parameter that changes the result, such as search term, sort order, filters, and page number.
  • Use namespaces such as user, product, or session to keep key spaces separate.
  • A version prefix such as v2: lets a format change invalidate a whole group at once by switching reads to new keys.

user:456

10TTL: freshness versus performance

A TTL defines how long an entry stays valid before it expires.

  • During the TTL window, requests are served from the cache; after expiry, the next request refetches and repopulates.
  • A short TTL keeps data fresher but causes more misses and more backend traffic.
  • A long TTL improves the hit ratio and reduces backend load but increases the chance of stale data.
  • There is no universal best TTL; it depends on how fast the data changes and how much staleness the feature tolerates.
  • Static configuration can tolerate hours; product data might use minutes; highly dynamic data needs a very short TTL or a different invalidation strategy.
  • TTL alone does not guarantee freshness if the write path does not invalidate, and it does not solve memory pressure.
  • Add jitter to TTLs so many keys cached together do not all expire at the same moment.

11When to add a cache

  • First confirm there is a performance problem; if queries are fast and traffic is low, a cache adds little.
  • Look for three conditions: high read frequency, expensive reads or computation, and repeated access to the same data.
  • Check that the data can tolerate some staleness; if not, caching reads may not be appropriate.
  • Confirm the database or downstream service is actually the bottleneck the cache would relieve.
  • Weigh the new complexity: expiration, invalidation, stale reads, cache failures, and consistency.
  • A cache is justified when the read savings clearly exceed the operational and correctness cost.
Measure latency and load→Find repeated expensive reads→Check staleness tolerance→Choose layer and key→Set TTL and invalidation→Measure hit ratio

12What goes wrong in production

  • Stale reads: invalidation is delayed or missing, so users see old values after a write.
  • Stampede: a popular key expires and many concurrent requests all miss and hit the database at once.
  • Hot key: one very popular key concentrates load on a single cache node or database shard.
  • Cold start: a restarted or empty cache sends the full read load to the database until it warms up.
  • Cache outage: losing the cache exposes the backend to traffic it was never sized to handle.
  • Mitigations include request coalescing, locking on miss, jittered TTLs, serving stale data during failure, and load shedding.
  • A cache is now part of the critical path, so its failure modes must be designed and tested.

↔Trade-offs to say out loud

  • Caching lowers latency and backend load but introduces a copy that can be stale.
  • Longer TTLs raise the hit ratio and reduce database traffic but widen the staleness window.
  • Shorter TTLs keep data fresh but increase misses and backend load.
  • Application-local caches are fastest but duplicate memory and can diverge across instances.
  • Distributed caches share one view across servers but add a network hop and another service to operate.
  • Broad cache keys increase hit ratio but risk serving the wrong data to the wrong request.
  • Adding a cache absorbs read traffic but can hide capacity problems until the cache fails.
  • Aggressive invalidation improves freshness but reduces hit ratio and pushes more work to the database.

?Interview questions

Answer aloud before opening the outline.

1. What is a cache?

A fast storage layer that keeps copies of data so repeat requests can be served without going to the slower source of truth. It does not replace the database; it holds a copy that can be discarded and rebuilt. The benefit is lower latency and less backend load, at the cost of possible staleness.

2. What happens on a cache hit versus a miss?

On a hit, the value is returned directly from the cache without touching the database. On a miss, the application fetches from the database, stores the result in the cache, and returns it. A miss is slightly more expensive than no cache at all because of the extra lookup, but subsequent requests become hits.

3. What is a good cache hit ratio?

There is no universal number; it depends on traffic volume and the cost of a miss. The ratio must be read in absolute terms: at 10 million requests per second, a 95 percent hit ratio still leaves 500,000 requests per second reaching the backend. Size the database for the miss rate, not the total traffic.

4. Where can caching happen in a system?

In the browser, at a CDN edge, inside the application process, in a shared distributed cache such as Redis or Memcached, and inside the database itself. Each layer saves a different amount of work and has a different invalidation model. Browser and CDN caches serve shared content closest to the user; application and distributed caches hold computed or queried data.

5. Application cache vs distributed cache?

An application cache is in-process, so it is the fastest option but each instance has its own copy, duplicating memory and allowing values to diverge. A distributed cache is shared over the network, giving every server the same view and much larger capacity, but each lookup costs a round trip. The choice is speed versus shared consistency.

6. What data should not be cached?

Data that changes constantly, data that must always be exact such as account balances, and large objects that are rarely read. Each case either makes the cached copy stale almost immediately or wastes memory without meaningful reuse. Caching also adds little when traffic is low and the underlying query is already fast.

7. How do you design a cache key?

Include every parameter that changes the result, so two different requests never share a value incorrectly. At the same time, avoid keys so specific that they create duplicate entries and always miss. Use namespaces for key groups and optional version prefixes so a format change can invalidate an entire generation of entries at once.

8. What does a TTL control?

How long an entry remains valid before it expires. A short TTL improves freshness but increases misses and backend load; a long TTL improves the hit ratio but widens the staleness window. The right value depends on how quickly the data changes and how much staleness the feature can tolerate.

9. When should you add a cache?

When reads are frequent, repeated, and expensive, and the data can tolerate some staleness. Confirm the database or downstream service is the actual bottleneck. If traffic is low and queries are already fast, a cache adds invalidation and consistency complexity for little gain.

10. What is a cache stampede, and how do you prevent it?

A popular key expires and many concurrent requests miss at once, all hitting the database for the same value. Prevent it with request coalescing or a per-key lock so only one request fetches while others wait, jittered TTLs to avoid synchronized expiry, or serving stale data briefly when a refresh is in progress.

11. What happens if the cache goes down?

All traffic that was being served from cache reaches the backend at once, which may exceed its capacity. A resilient design treats the cache as optional, applies timeouts and circuit breakers, rate-limits or sheds load, and may serve stale data. The database should be sized for a miss rate the system can survive, not only the steady-state rate.

12. How do you measure whether a cache is working?

Track the hit ratio overall and per key pattern, along with hit and miss latency, backend request rate, cache memory usage, eviction rate, and error rate. A high aggregate hit ratio can hide a bad path where a critical key always misses, so break the metric down by route or key family.

13. Caching vs denormalization?

Caching stores a transient copy that can be evicted or lost and rebuilt from the source. Denormalization changes the stored schema so duplicated data is durable and queryable. Caching is easier to add and remove; denormalization must be maintained on every write and is part of the data model.

!Traps

  • Adding a cache without measuring whether the database is actually the bottleneck.
  • Judging a cache only by hit ratio without checking the absolute miss rate at peak traffic.
  • Using a cache key that omits a parameter that changes the response, so users see each other's data.
  • Using a key so specific that it effectively never hits.
  • Setting one long TTL for all data regardless of how quickly it changes.
  • Letting many keys expire at the same instant and creating a refresh wave against the database.
  • Assuming the cache will always be available and never testing the backend under full miss load.
  • Treating a cached value as authoritative and losing the ability to rebuild it from the source.
