In one lineAn LSM tree turns random writes into sequential ones by buffering changes in memory and flushing sorted immutable files, then merging those files in the background — which makes writes fast and reads more complicated.
LSM tree
Log-structured merge tree: a storage design that collects writes in memory, flushes them as sorted files, and merges those files in the background.
Memtable
The in-memory sorted structure that absorbs writes; when it fills, it is flushed to disk as a new file.
SSTable
A sorted string table — an immutable, sorted file of key-value entries written once and never modified in place.
Write-ahead log
An append-only log written before the memtable so an unflushed write survives a crash.
Compaction
The background merge of several sorted files into fewer, larger ones, discarding overwritten values and tombstones.
Tombstone
A delete marker written as a value so the deletion can hide older versions until compaction removes them all.
Bloom filter
A compact probabilistic structure that answers definitely not here or maybe here, letting reads skip files that cannot hold the key.
Write amplification
The ratio of bytes physically written to bytes logically written; compaction rewrites data repeatedly, which inflates it.
Read amplification
The number of files or blocks a read must consult before the newest version of a key is found.
Leveled compaction
A strategy with non-overlapping sorted runs per level, each level larger than the one above, which keeps reads cheap but rewrites data more often.

01The problem with updating in place

A B-tree updates pages where they already live. That is excellent for reads, but poor at absorbing a constant stream of writes.

  • Each write dirties a page somewhere in the file, so writes arrive as random I/O rather than sequential.
  • A single logical insert can touch a leaf, a parent, and several index pages — the tree's own write amplification.
  • Random page updates are expensive on spinning disks and still costly on SSDs, which prefer large sequential writes.
  • Write-heavy systems — metrics, events, messages, logs — can outrun what in-place updates sustain.
  • The alternative is to stop updating in place entirely and append new sorted data instead.
  • That is the core idea of the LSM tree: make every write sequential and defer the tidying up.

02What an LSM tree is

  • Writes land in an in-memory sorted buffer and are also appended to a log for durability.
  • When the buffer fills, it is written out as one immutable sorted file — an SSTable.
  • Files are never modified after they are written; a change to a key becomes a new entry in a newer file.
  • A background compaction process merges files, keeping only the newest version of each key.
  • So the structure is a set of sorted runs, newest first, rather than one tree of pages.
  • Sequential appends make writes cheap; merging keeps the number of files from growing without bound.
  • This design powers engines such as LevelDB, RocksDB, Cassandra, ScyllaDB, and HBase.

03The write path

  • Append the record to the write-ahead log so it survives a crash before it reaches disk as data.
  • Insert the key and value into the memtable, an in-memory sorted structure such as a skip list.
  • When the memtable reaches its size threshold, it becomes immutable and a fresh memtable takes new writes.
  • The immutable memtable is flushed to disk as a new SSTable, typically at level zero.
  • The flush is a sequential write of already-sorted data, which is the cheapest kind of disk write.
  • The write is acknowledged after the log append, not after the flush, so latency does not include compaction.
  • A group commit batches many log appends into one flush, which keeps throughput high under concurrency.
Append to WAL→Insert into memtable→Memtable full: freeze it→Flush frozen memtable to L0 SSTable→Compaction merges files in the background

04Levels and runs

  • Level zero holds freshly flushed files whose key ranges usually overlap, so a read may have to check several of them.
  • Deeper levels hold non-overlapping sorted runs, so a read can pick the one file whose key range contains the target.
  • Each deeper level is larger than the one above, so data migrates downward as it ages.
  • Compaction takes files from one level, merges them with the overlapping files in the next, and writes new files.
  • Because each level's ranges do not overlap, lookups at deeper levels need one binary search plus one file read.
  • The hierarchy bounds the number of files a read must consider, which is what keeps read cost predictable.
  • A manifest records which files belong to which level so the set can be recovered after a crash.

05The read path

  • Check the mutable memtable first, since it holds the newest writes.
  • Then check any frozen memtables waiting to be flushed.
  • Then search level-zero files newest to oldest, because their ranges overlap.
  • Then, at each deeper level, binary search the file ranges and read the single candidate file.
  • Use a Bloom filter per file to skip files that certainly do not contain the key.
  • Inside a file, a sparse index or fence pointers locate the block, and a block cache may already hold it.
  • The first version found wins, because newer data always lives in newer files.
  • A read that must consult many files is slow, which is exactly what compaction exists to prevent.

06Deletes and tombstones

  • Files are immutable, so a delete cannot remove an entry in place.
  • Instead the engine writes a tombstone for the key in the newest file.
  • A read stops at the tombstone and reports the key as missing, even though older values still exist on disk.
  • The old values are physically removed only when compaction merges the tombstone with the files below it.
  • Until then the deleted data still occupies space — the source of space amplification.
  • A tombstone cannot be dropped at a level above the oldest surviving version, or a deleted value would reappear.
  • TTL expiry works the same way: an expired entry is hidden immediately but reclaimed later.

07Compaction

  • Compaction reads several sorted files, merges them in key order, and writes the result back out.
  • During the merge it drops values superseded by a newer version and drops tombstones once nothing older remains.
  • The output is fewer, larger, non-overlapping files, so future reads touch less data.
  • It runs in the background so writes are not blocked, but it competes for disk bandwidth and CPU.
  • If writes arrive faster than compaction can keep up, the engine applies back-pressure and write stalls appear.
  • Compaction is where LSM write amplification comes from: the same bytes are rewritten at every level they pass through.
  • Its scheduling — how many threads, which files, when — is the main operational knob of an LSM store.
Pick overlapping files→Merge in key order→Drop obsolete versions and tombstones→Write new sorted files→Update the manifest and delete old files

08Compaction strategies

  • Size-tiered compaction merges files of similar size into a larger one, so each byte is rewritten a limited number of times — cheap writes, more temporary space.
  • Leveled compaction keeps each level non-overlapping and small relative to the next, which reduces read amplification at the cost of more rewriting.
  • Tiered variants keep several runs per level and merge them in batches, trading read cost for lower write amplification.
  • The choice is really a choice of which amplification to minimize.
  • Workloads that read a lot of point lookups favor leveled; ingest-heavy workloads favor tiered or size-tiered.
  • Some engines let you tune the strategy per table or per column family.
  • Changing strategy on a live system triggers a large rewrite, so plan capacity for it.

09The three amplifications

  • Write amplification: bytes written to storage divided by bytes the application wrote.
  • Read amplification: files or blocks consulted to answer one read.
  • Space amplification: disk used divided by the logical size of live data.
  • The three pull against each other: making reads cheap with leveled compaction rewrites data more often.
  • Aggressive compaction lowers read and space amplification but spends write bandwidth and can stall ingestion.
  • Lazy compaction lowers write cost but leaves more files to check and more garbage on disk.
  • So tuning is choosing which resource you have spare — usually disk bandwidth or read latency.

10Bloom filters and block indexes

  • A Bloom filter summarizes the keys in one file in a few bits per key.
  • It can prove a key is absent, which lets the read skip that file without any I/O.
  • It can never prove presence — a false positive sends the read to a file that does not hold the key.
  • More bits per key lowers the false-positive rate at the cost of memory.
  • Bloom filters do not help range scans, which must read a span of keys rather than test membership.
  • For ranges, the engine uses the sorted order plus fence pointers and a block index to seek and then scan.
  • Caching filters and index blocks in memory is what keeps point-read latency stable as data grows.

11Durability and crash recovery

  • Writes are durable once appended to the log, even though the data is still only in memory.
  • On restart the engine replays the log to rebuild the memtable.
  • Flushed SSTables are installed through a manifest update, so a half-written file is never referenced.
  • Files are written under a temporary name and renamed only when complete, which makes installation atomic.
  • Old files are deleted only after the manifest no longer references them, so a crash mid-compaction is recoverable.
  • Durability can be relaxed by acknowledging before the log is flushed, which risks losing the last writes.
  • Snapshots and backups must account for compaction: copying files while they are being merged yields an inconsistent set.

12LSM trees versus B-trees

  • B-trees update in place: predictable point reads, but random writes and page splits.
  • LSM trees append: very fast writes, but reads may consult several files and compaction runs constantly.
  • LSM space grows during compaction, so capacity planning needs headroom that a B-tree does not require.
  • B-tree range scans walk linked leaves; LSM range scans merge several sorted runs through an iterator.
  • B-trees have a single version per key; LSM trees may hold several versions until compaction catches up.
  • Most write-heavy, distributed stores choose LSM; most transactional, read-latency-sensitive engines choose B-trees.
  • The question is rarely which is better in general, but which amplification your workload can afford.

13Operating an LSM store

  • Watch compaction backlog and write stalls; both mean ingest is outrunning the merge pipeline.
  • Keep disk headroom, because compaction needs space for both its inputs and its outputs.
  • Very large values inflate compaction work; storing big blobs separately keeps the LSM small.
  • A hot key still writes to the same place, so compaction cannot fix a skewed access pattern.
  • Range scans over old data may read many files; iterator merging makes them correct but not free.
  • Tune compaction threads and file sizes to the storage: sequential-friendly devices reward larger files.
  • Choose an LSM store when writes dominate and you can accept background work; choose a B-tree when read latency and simplicity dominate.

↔Trade-offs to say out loud

  • Sequential writes make ingestion cheap but leave many overlapping files that reads must search.
  • Leveled compaction keeps reads fast and space low but rewrites data repeatedly, raising write amplification.
  • Size-tiered compaction lowers write cost but leaves more overlapping runs and more temporary garbage.
  • Bloom filters skip irrelevant files cheaply but consume memory and cannot help range scans.
  • Tombstones make deletes append-only and fast but hold space until compaction meets the oldest version.
  • Larger memtables reduce flush frequency but increase memory pressure and the replay cost after a crash.
  • Durability via WAL protects acknowledged writes but adds a flush per commit unless commits are grouped.
  • Background compaction keeps the write path fast but competes with foreground reads for disk bandwidth and causes latency spikes.
  • Deferred cleanup keeps writes cheap but means deleted data is still readable at the storage layer until compaction runs.

?Interview questions

Answer aloud before opening the outline.

1. Why do write-heavy systems use LSM trees?

Because every write becomes a sequential append — to the log and then to a new sorted file — instead of a random update to an existing page. Sequential I/O is far cheaper, and compaction tidies up in the background. The cost is later paid in read amplification and compaction bandwidth.

2. Walk through a write end to end.

The record is appended to the write-ahead log and inserted into the in-memory memtable. When the memtable fills, it is frozen and flushed as a new sorted SSTable at level zero. Later, compaction merges that file with overlapping files in deeper levels.

3. How does a read find the newest value?

It checks the mutable memtable, then frozen memtables, then level-zero files newest first, then one file per deeper level located by binary search. The first version found wins. Bloom filters and cached index blocks let it skip files that cannot contain the key.

4. What is a tombstone and why does it matter?

Because files are immutable, a delete is written as a marker rather than by removing data. Reads stop at the marker and report the key as gone, but the older value stays on disk until compaction merges the tombstone down to it. That leftover data is space amplification.

5. What does compaction actually do?

It merges several sorted files into fewer, larger non-overlapping ones, keeping only the newest version of each key and dropping tombstones once nothing older remains. It bounds read amplification and reclaims space, but it rewrites data, which is where LSM write amplification comes from.

6. Compare size-tiered and leveled compaction.

Size-tiered merges files of similar size, so each byte is rewritten fewer times — cheap writes, more overlapping runs and temporary space. Leveled keeps each level non-overlapping and progressively larger, so reads touch one file per level but data is rewritten more often.

7. What are the three amplifications?

Write amplification is bytes written to storage per byte the application wrote. Read amplification is how many files or blocks a read must consult. Space amplification is disk used versus live logical data. They trade against each other, so tuning picks which one to accept.

8. Why do reads get slower as an LSM tree grows?

More data means more files and deeper levels, so a lookup may consult more candidates unless compaction keeps the level structure tight. Bloom filters skip absent keys, and block caches hide repeated reads, but a cold cache plus a compaction backlog shows up as read latency.

9. What causes write stalls?

Writes arrive faster than compaction can drain level zero, so the engine throttles or pauses ingestion until files are merged. The usual fixes are more compaction throughput, a different strategy, higher write capacity, or reducing the write rate.

10. Are LSM deletes immediately durable?

The tombstone is durable as soon as it is logged, so the key reads as deleted right away. What is not immediate is physical reclamation — the old bytes remain until compaction. Backups taken before that point can still contain the old value, which matters for compliance.

11. B-tree or LSM: how do you choose?

Choose an LSM when writes dominate, the data set is large, and you can absorb compaction work — event logs, metrics, messages, time-ordered data. Choose a B-tree when read latency must be predictable and simple, or when the workload is transactional with random point updates.

12. Why not put large blobs in the LSM store?

Compaction rewrites every byte it merges, so a large value is copied at every level it passes through. Keeping blobs in object storage and the LSM entry holding only a pointer keeps compaction work proportional to the metadata, not the payload.

!Traps

  • Saying LSM reads are always faster because writes are sequential — reads may consult many files.
  • Forgetting that deletes are tombstones, so disk usage does not drop when rows are deleted.
  • Tuning compaction for write throughput and then blaming the database for slow point reads.
  • Assuming a Bloom filter can accelerate range scans; it only proves absence of a specific key.
  • Running an LSM store near full disk, where compaction has no room for its temporary output.
  • Treating compaction as free background work instead of IO and CPU that competes with foreground traffic.
  • Backing up files during compaction and assuming the copied set is consistent.
