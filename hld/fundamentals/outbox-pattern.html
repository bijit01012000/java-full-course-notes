In one lineThe transactional outbox writes the business row and the event to publish in one local transaction, then a relay publishes the event — so no committed change is ever left without its message.
Dual-write problem
The impossibility of atomically committing a database change and a message publish as one transaction.
Outbox table
A table in the same database that stores events in the same transaction as the business change.
Relay
The component that reads unpublished outbox rows and forwards them to the broker.
Polling publisher
A relay that periodically queries the outbox for unsent rows and publishes them.
Transaction log tailing
A relay that reads the database's write-ahead log or binlog and emits changes as events (CDC).
At-least-once delivery
A guarantee that every event is delivered, possibly more than once, so consumers must deduplicate.
Idempotent consumer
A consumer that can process the same event twice without changing the outcome.
Aggregate ID
The entity identifier used as the partition key so all events for one entity stay ordered.
Poison message
An event that always fails processing and would block the relay or partition forever.
Change data capture
Reading a database's change log to stream committed rows as events without polling.

01The dual-write problem

An order service must save the order and announce it. Those are two systems, and nothing makes them commit together.

  • Placing an order writes a row to the orders database and publishes an OrderCreated event to a broker.
  • Downstream services depend on that event: inventory reserves stock, email confirms the purchase, analytics records the sale.
  • A normal database transaction cannot span the database and the broker, so there is always a window where one succeeds and the other fails.
  • If the commit succeeds and the publish fails, the order exists but inventory never reserves — a silent inconsistency.
  • If the publish succeeds and the commit fails, consumers act on an order that does not exist.
  • Retrying the failed half does not fix it: the two operations are not atomic and cannot be made so by the application.
  • This is the dual-write problem, and it appears in every service that both stores state and emits events.
Begin database transaction→Insert order row→Commit→Publish event→Publish fails → order exists, no event

02Why one transaction cannot cover both

  • The database and the broker are separate systems with separate commit protocols and failure modes.
  • Distributed transactions across them require two-phase commit, which most brokers and cloud services do not support well.
  • Even with XA, the coordinator becomes a single point of failure and participants hold locks while waiting.
  • A broker acknowledgement is not a durable commit from the database's point of view; it can be lost after the fact.
  • Network timeouts leave the application unable to tell whether the publish happened.
  • The outbox pattern sidesteps this by making only one system part of the critical transaction: the database.
The key move is to stop treating the broker as a participant and start treating the event as data.

03The outbox table

  • An outbox table lives in the same database as the business data.
  • The business insert and the outbox insert happen in one local ACID transaction, so both commit or neither does.
  • Each row carries an event ID, type, aggregate ID, payload, creation time, and a delivery status or sequence.
  • The event ID is generated at write time so consumers can deduplicate later.
  • The payload should be a stable contract, not a serialised internal row that changes with schema refactors.
  • A monotonically increasing sequence column gives the relay an order and a resume point.
  • Because the event is just a row, it inherits the durability, backup, and replication of the database.
BEGIN;
INSERT INTO orders (id, customer_id, total) VALUES (:id, :customer, :total);
INSERT INTO outbox (id, aggregate_id, type, payload, created_at)
VALUES (:event_id, :id, 'OrderCreated', :json, now());
COMMIT;
One transaction, one commit point, two rows — the event cannot be lost independently of the order.

04The relay: polling publisher

  • A separate relay process polls for rows that have not yet been published.
  • It publishes each row to the broker, waits for acknowledgement, then marks the row as sent or deletes it.
  • Batching and FOR UPDATE SKIP LOCKED let several relay instances share the work without contention.
  • Polling introduces latency equal to the poll interval, which is fine for most business events.
  • The relay must be idempotent on restart: publishing before marking sent can produce duplicates, which consumers must tolerate.
  • Ordering is preserved if a single relay processes rows by sequence and publishes to one partition.
  • Polling is simple, portable, and easy to reason about, which is why it is the default choice.
Select unsent rows ordered by sequence→Publish to the broker→Await broker acknowledgement→Mark rows sent or delete them→Repeat on the next interval

05The relay: transaction log tailing

  • Instead of polling, a connector tails the database's write-ahead log or binlog and emits row changes as events.
  • This is change data capture, and it avoids poll queries and their load on the primary.
  • Latency is much lower because events stream as transactions commit.
  • The connector must understand the table schema and map rows to event contracts.
  • Log retention matters: if the connector falls too far behind, the database may discard the log it needs.
  • It couples the event stream to physical schema changes, so column renames leak into events unless you project a stable view.
  • Log tailing is operationally heavier but scales better than polling on high-write databases.

06Delivery guarantees and duplicates

  • The outbox gives at-least-once delivery: an event is published one or more times, never silently dropped.
  • A crash between publish and mark-sent causes a duplicate, which is the normal case rather than a bug.
  • Exactly-once delivery end to end is not achievable across a database and a broker without cooperation.
  • The practical target is effectively once: at-least-once delivery plus idempotent consumers.
  • Consumers deduplicate on the event ID, often with a unique constraint in a processed-events table.
  • Deduplication must be part of the same transaction as the consumer's own write, or it just moves the dual-write problem.
  • Broker-side deduplication helps but does not cover the database write, so it is not sufficient alone.

07Ordering

  • The outbox sequence gives a total order of commits, but the broker only preserves order within a partition.
  • Publish with the aggregate ID as the partition key so all events for one entity land on one partition in order.
  • Global ordering across all entities requires a single partition, which caps throughput.
  • Multiple relay instances must not publish the same aggregate concurrently, or order is lost.
  • Consumers must not process a partition's events in parallel without preserving per-key order.
  • Out-of-order delivery is a correctness bug for state-machine consumers; design for per-key ordering rather than hoping.
  • If events carry a version number per aggregate, consumers can reject stale updates and stay correct under reordering.

08Retries, failures, and poison messages

  • The relay must retry transient broker failures with backoff and jitter.
  • A permanently failing event must not block the entire outbox behind it.
  • After a bounded number of attempts, move the event to a dead-letter queue and alert.
  • Track attempt counts and last error on the outbox row so operators can diagnose a stuck event.
  • A relay that dies mid-batch should resume from the last acknowledged sequence, not from scratch.
  • Broker outages should back-pressure the relay, not cause it to drop rows.
  • Alert on outbox lag, not just on relay uptime; a running relay that publishes nothing is still an outage.

09Cleanup and retention

  • Published rows must be deleted or archived, or the table grows without bound.
  • Deleting in small batches avoids long locks and heavy vacuum work on the primary.
  • Partition the outbox by time so old partitions can be dropped instead of deleted row by row.
  • Keep a retention window long enough to debug incidents, but reconcile it with storage cost.
  • An index on the unpublished status keeps relay queries cheap as the table grows.
  • Beware of bloat: frequent delete/insert cycles on a small table still generate dead tuples in MVCC databases.
  • Archive to object storage if events are needed for audit or replay.

10Event contracts and schema evolution

  • The event payload is a public contract consumed by other teams, so it must be versioned.
  • Do not serialise an internal table row directly; project an explicit schema that you control.
  • Additive changes are safe; removals and type changes break consumers and need a new version.
  • Include an event ID, type, aggregate ID, occurred-at timestamp, and aggregate version in every message.
  • Validate the payload at write time so malformed events never enter the outbox.
  • Keep the payload small; large blobs belong in object storage with a reference in the event.
  • Document the compatibility rule and enforce it in CI rather than in review comments.

11Alternatives and how they compare

  • Two-phase commit / XA is atomic but blocking, poorly supported by brokers, and operationally fragile.
  • Listen to yourself (publish after commit, then consume your own event) still leaves a window where the publish is lost.
  • Event sourcing makes the event log the source of truth, removing the dual write entirely but changing the data model deeply.
  • Sagas coordinate multi-service transactions with compensations; they solve a different problem and often use an outbox to publish their steps.
  • Broker transactions make broker-side writes atomic but cannot include the database commit.
  • The outbox is the smallest change that fixes the dual write while keeping the existing database and broker.
  • Choose log tailing over polling when write volume is high or latency matters; otherwise polling is simpler.

12Monitoring and common failure modes

  • Monitor outbox lag — the age of the oldest unpublished row — rather than relay heartbeats.
  • A relay that runs but publishes nothing usually means a publish error being swallowed.
  • Watch duplicate rates at consumers; a spike means the relay is crashing between publish and mark.
  • Track dead-letter growth and the age of the oldest dead-lettered event.
  • Table growth is a leading indicator of a broken cleanup job.
  • The most dangerous failure is silent: the order commits, the relay is down, and only outbox lag reveals it.
  • Run the relay as a separately scaled deployment so a busy API does not starve publishing.

13When to use it

  • Use an outbox whenever a service must both change its own state and announce that change.
  • It is not needed for pure read models or for events that are merely telemetry and can be dropped.
  • It is the right tool when the database is the source of truth and the broker is a downstream transport.
  • It does not replace idempotency: consumers still need deduplication to reach effectively-once.
  • It does not provide ordering across aggregates, and it does not roll back the database if a consumer fails.
  • Combine it with a saga when a business process spans services and needs compensation.
  • Start with polling, an indexed status column, and a cleanup job; move to log tailing only when the load justifies it.
Write business row and event in one transaction→Commit locally→Relay publishes with broker acknowledgement→Mark or delete the outbox row→Consumer deduplicates by event ID→Cleanup removes old rows

↔Trade-offs to say out loud

  • One local transaction removes the dual write but makes the database the bottleneck for event publication.
  • Polling relays are simple and portable but add latency and repeated query load.
  • Log tailing is fast and low-impact but couples events to physical schema and adds operational complexity.
  • At-least-once delivery guarantees no lost events but forces every consumer to deduplicate.
  • Per-aggregate ordering keeps state machines correct but limits parallelism to one consumer per key.
  • Long retention aids debugging and replay but grows the table and vacuum cost.
  • Small batches avoid lock contention but reduce throughput and increase relay overhead.
  • Outbox instead of 2PC avoids blocking coordination but accepts asynchronous, eventually consistent consumers.

?Interview questions

Answer aloud before opening the outline.

1. What is the dual-write problem?

It is the impossibility of atomically committing a database change and publishing a message to a broker. One can succeed while the other fails, leaving either a committed change with no event or an event describing a change that never happened.

2. How does the outbox pattern solve it?

The event is written as a row in an outbox table inside the same local transaction as the business change. Both commit or neither does. A separate relay then publishes outbox rows to the broker, so publication becomes retryable without risking the database state.

3. Polling publisher or transaction log tailing?

Polling is simple, portable, and easy to operate, but adds poll-interval latency and query load. Log tailing streams changes as they commit with low latency and little database load, but is more complex and couples events to physical schema changes.

4. Does the outbox give exactly-once delivery?

No. A crash between publishing and marking the row sent produces a duplicate, so the guarantee is at-least-once. You reach effectively-once by making consumers idempotent and deduplicating on the event ID.

5. How should consumers deduplicate?

Record processed event IDs in a table with a unique constraint, and commit that insert in the same transaction as the consumer's own state change. Broker-level deduplication alone does not cover the database write.

6. How do you preserve event ordering?

Use the aggregate ID as the partition key so all events for one entity go to one partition, and have a single relay publish each aggregate in sequence. Global ordering requires a single partition and sacrifices throughput.

7. What happens when the broker is down?

The relay retries with backoff and the outbox rows accumulate. Publication resumes from the last acknowledged sequence when the broker returns, so no events are lost, but outbox lag grows and consumers fall behind.

8. How do you handle a poison message?

Bound the retries, then move the event to a dead-letter queue and alert. It must not block the rest of the outbox behind it, or one bad event stalls every downstream consumer.

9. Why does the outbox table need cleanup?

Published rows accumulate forever otherwise, bloating the table, indexes, and vacuum work. Delete in small batches, or partition by time and drop old partitions, keeping a retention window for debugging.

10. What should an outbox event contain?

At minimum an event ID, type, aggregate ID, aggregate version, occurred-at timestamp, and a stable payload. The payload should be an explicit contract rather than a serialised internal row.

11. Is the outbox a replacement for 2PC?

It replaces 2PC for the specific case of publishing an event alongside a local write. It does not provide atomicity across multiple services databases; that needs a saga with compensations, often built on top of an outbox.

12. How do you monitor an outbox deployment?

Track the age of the oldest unpublished row, duplicate rates at consumers, dead-letter growth, and table size. Relay uptime alone is misleading because a running relay can be silently failing to publish.

!Traps

  • Publishing to the broker inside the same try block as the commit and assuming they are atomic.
  • Marking an outbox row sent before the broker acknowledges the publish.
  • Assuming at-least-once delivery means consumers need no deduplication.
  • Deduplicating in memory or in a separate transaction, which recreates the dual-write problem.
  • Letting one poison message block the entire outbox behind it.
  • Never cleaning up published rows until the table dominates the database.
  • Publishing with a random partition key and then expecting per-entity ordering.
