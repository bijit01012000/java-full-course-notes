In one lineHexagonal architecture — ports and adapters — keeps business logic in a technology-free core and connects every transport, database, and external service to it through explicit interfaces.
Domain core
The part of the code that holds business rules and use cases, written without knowledge of HTTP, SQL, frameworks, or vendors.
Port
An interface owned by the core that describes what the application needs or offers, independent of any technology.
Adapter
A concrete implementation that connects a port to a specific technology such as a REST controller, a repository, or a payment SDK.
Driving adapter
An inbound adapter that starts a use case — an HTTP controller, CLI command, queue consumer, or scheduled job.
Driven adapter
An outbound adapter the core calls — a database repository, message publisher, cache client, or external API client.
Use case
A single application operation, such as place order, that coordinates domain objects through ports.
Dependency inversion
Making the core depend on abstractions it owns while infrastructure code depends on and implements those abstractions.
Composition root
The single startup location where concrete adapters are constructed and wired into the core.
Anti-corruption layer
A translation boundary that maps an external model into the core's own model so foreign concepts do not leak inward.

01The problem: business logic tangled with technology

Business logic should not care whether a request arrived over HTTP, from a queue, or from a scheduled job, nor whether data lives in PostgreSQL, MongoDB, or a file.

  • In practice the details mix: a controller starts making pricing decisions.
  • A use case imports an ORM model, so persistence shape dictates domain shape.
  • A service calls a payment SDK directly, so the vendor's API appears inside business rules.
  • After a while, changing a database, framework, or provider means touching business logic.
  • Tests then need a database or a running vendor sandbox just to check a rule.
  • The root cause is direction of dependency: the core depends on details instead of details depending on the core.

02The core idea: inside versus outside

  • Split the system into an inside that holds business rules and an outside that holds technology.
  • The inside is the domain model plus the use cases that operate on it.
  • The outside is everything that talks to the world: web, CLI, queues, databases, caches, payment providers.
  • All communication crosses the boundary through explicit interfaces rather than direct references.
  • The core must be compilable and testable with no framework, no database, and no network.
  • The pattern was introduced by Alistair Cockburn as ports and adapters.

03Ports: the core's contract with the world

  • A port is an interface owned by the core, expressed in the core's own vocabulary.
  • Driving ports describe what the application can do: place an order, refund a payment, cancel a subscription.
  • Driven ports describe what the application needs: load an order, save an order, charge a card, send a notification.
  • Ports take and return domain types, never HTTP request objects, ORM entities, or vendor response objects.
  • A port is a design decision about capability, not a thin wrapper around a specific library.
  • One port may have several adapters, for example a real payment provider and a fake one for tests.
If a port signature mentions a framework type, the technology has already leaked inward.

04Adapters: the technology-specific edge

  • An adapter implements or calls a port and contains all technology detail: annotations, SQL, serialization, retries, credentials.
  • Adapters translate between the outside representation and the core's model.
  • A REST controller maps JSON into a command, invokes a use case, and maps the result back into a response.
  • A repository adapter implements a driven port on top of JPA, JDBC, or a document store.
  • Adapters should be replaceable without changing a line in the core.
  • Multiple adapters per port is normal and expected, not duplication.

05Driving versus driven sides

The two sides of the hexagon differ in who initiates the call and therefore in how the port is used.

  • Driving (inbound) adapters call into the core: controllers, CLI handlers, message listeners, cron jobs.
  • Driving ports are implemented by the core's use-case classes.
  • Driven (outbound) adapters are called by the core: repositories, gateways, event publishers.
  • Driven ports are implemented by infrastructure classes, and the core holds only the interface.
  • A single capability often appears on both sides: HTTP in, database out.
  • Getting the direction right is what keeps the dependency arrows pointing inward.

06Why a hexagon: the shape is not the point

  • The hexagon is a drawing convention: enough sides to show several inbound and outbound channels without implying a top or bottom layer.
  • It deliberately avoids the layered diagram, where the database sits underneath and looks like the foundation.
  • There is no privileged direction such as up or down; every outside channel is equal.
  • Nothing in the pattern requires six adapters or a hexagonal folder.
  • The real content is the inside/outside boundary plus the dependency rule.
  • Interview answers should describe ports, adapters, and dependency direction, not the drawing.

07The dependency rule

  • Source-code dependencies point inward, toward the domain core.
  • The core defines interfaces for what it needs; infrastructure implements them.
  • This inverts the usual flow, where business code imports the database library.
  • Wiring happens once at startup in a composition root, which knows every concrete adapter.
  • The domain must not import framework annotations, ORM base classes, or vendor SDK types.
  • Enforce it with architecture tests that fail the build on forbidden imports.
  • This is the same rule used by clean architecture and onion architecture.
Adapter receives external input→Adapter translates into a core command→Use case executes domain rules→Core calls a driven port→Adapter fulfils it with a real technology→Result translated back to the outside

08A request through the hexagon

  • An HTTP controller parses the request and validates transport-level concerns such as content type.
  • It builds a command object in domain terms and passes it to a use case through a driving port.
  • The use case loads aggregates through driven ports, applies rules, and decides the outcome.
  • It saves through a repository port and may publish a domain event through another port.
  • The adapter translates the outcome into an HTTP status and response body.
  • Business rules never see the HTTP request, the SQL, or the vendor payload.
  • The same use case can be invoked by a queue consumer with no changes.

09Testing the core without infrastructure

  • Use-case tests instantiate the core with in-memory fakes for driven ports.
  • Rules are tested in milliseconds with no database, container, or network.
  • Fakes double as documentation of what the core expects from each port.
  • Adapter tests are separate and focus on mapping, queries, and error translation.
  • A thin set of end-to-end tests covers the wiring that unit tests cannot.
  • Because the core has no framework dependency, tests do not break on framework upgrades.
  • This test pyramid is a direct consequence of the dependency rule.

10Replacing technology

  • Swapping a database means writing a new driven adapter, not editing use cases.
  • Swapping a payment provider means a new gateway adapter plus mapping tests.
  • Adding a gRPC or GraphQL surface means a new driving adapter over the same use cases.
  • Adding a batch job means a scheduler adapter invoking an existing port.
  • Migrations become contained because no domain code imports the old technology.
  • Vendor-specific quirks stay in the adapter, where an anti-corruption layer can absorb them.
  • The core becomes the stable part while the edges churn.

11Relationship to other architecture styles

  • Layered architecture also separates concerns but usually lets business code depend on data access.
  • Clean architecture and onion architecture share the dependency rule with different diagrams and naming.
  • Hexagonal emphasizes ports and adapters, that is, the boundary mechanics rather than the rings.
  • Domain-driven design is complementary: it shapes the core, not the boundary.
  • Microservices is a deployment style; a service can be hexagonal or a layered mess internally.
  • The pattern is intra-application, so it does not by itself solve distributed transactions or service discovery.
  • Choosing hexagonal says nothing about how many deployables you run.

12What it costs and when it pays off

  • Every external interaction gains an interface, a mapping layer, and wiring code.
  • Small CRUD services get little benefit and noticeable indirection.
  • It pays off when business rules are non-trivial and change independently of technology.
  • It pays off when multiple entry points exist: web, mobile API, queue, batch, CLI.
  • It pays off when a database, vendor, or framework swap is plausible.
  • It pays off when the domain must be tested quickly and deterministically.
  • Apply it to the core domain, not uniformly to every module.
A common compromise is to keep thin CRUD modules plain and apply ports and adapters only where rules are dense.

13Applying it in practice

  • Package by domain first, then by inside and outside within that domain.
  • Name ports after intent — OrderRepository, PaymentGateway — not after technology.
  • Keep commands, results, and errors in domain vocabulary, not HTTP status codes.
  • Construct adapters only in the composition root; do not let the core instantiate infrastructure.
  • Use architecture tests to forbid framework imports inside the domain package.
  • Do not confuse the pattern with a folder named hexagonal over the same tangled dependencies.
  • Start with one bounded context, prove the testing benefit, then expand.

↔Trade-offs to say out loud

  • Technology independence improves testability and replaceability but adds interfaces, mappers, and wiring.
  • Multiple entry points reuse one core cleanly but require each driving adapter to handle its own validation and error mapping.
  • Isolated domain tests run fast and reliably but do not prove that real SQL or vendor calls work.
  • Adapter abstraction contains vendor quirks but can hide useful provider features behind a lowest-common-denominator port.
  • Boundary discipline prevents coupling but needs architecture tests and ongoing review to survive deadlines.
  • Uniform application is consistent but over-engineering for simple CRUD modules.
  • Decoupled core makes large refactors cheaper but can slow small feature work with extra layers.

?Interview questions

Answer aloud before opening the outline.

1. What problem does hexagonal architecture solve?

It stops business logic from depending on delivery mechanisms, databases, frameworks, and vendors. Instead of the domain importing an ORM or payment SDK, the core defines ports and infrastructure implements them, so technology changes stay at the edge.

2. What is a port and what is an adapter?

A port is an interface owned by the core describing a capability or a need, expressed in domain terms. An adapter is the technology-specific implementation that connects that port to HTTP, SQL, a queue, or a vendor API.

3. Why is it called hexagonal?

The hexagon is a diagram convention that gives room to draw several inbound and outbound channels without implying a top or bottom. It signals that all outside channels are equal and that dependencies point inward. The shape has no functional meaning.

4. What is the difference between driving and driven adapters?

Driving adapters call into the application — controllers, CLI handlers, queue listeners. Driven adapters are called by the application — repositories, gateways, notifiers. The first implements a core use case; the second implements an interface the core owns.

5. Where does dependency inversion appear here?

The core declares interfaces for what it needs instead of importing concrete libraries. Infrastructure classes depend on those interfaces and implement them. Wiring happens at startup in a composition root, so source dependencies point toward the domain.

6. How does this change testing?

Use cases can be tested with in-memory fakes for driven ports, with no database or network. Adapter tests cover mapping and real queries separately. The result is fast, deterministic domain tests that survive framework upgrades.

7. Can you swap a database without touching business logic?

Yes, if the domain only sees a repository port and domain types. You write a new adapter and mapping tests; use cases stay unchanged. In practice some assumptions leak through query shapes and transaction boundaries, so the port should be designed around use cases, not tables.

8. Is hexagonal architecture the same as clean architecture?

They share the dependency rule and the goal of an isolated core. Clean architecture draws concentric rings and names layers entities, use cases, interface adapters, and frameworks. Hexagonal focuses on the port-and-adapter boundary. Onion architecture is another close variant.

9. Does hexagonal architecture mean microservices?

No. It is an intra-application code structure. A single monolith can be hexagonal, and a microservice can be a layered tangle internally. Service count is a deployment decision, independent of how each service is organized.

10. When is it overkill?

For small CRUD services with little business logic and a single entry point, the extra interfaces and mappers add indirection with little payoff. Apply it where rules are non-trivial, entry points are multiple, or technology replacement and fast domain tests matter.

11. How do you keep the boundary from eroding?

Enforce it mechanically: architecture tests that fail on forbidden imports, a composition root that owns all construction, ports named after intent, and review rules that reject framework types in domain signatures.

12. What does a request look like end to end?

A controller adapter parses HTTP and builds a command, a use case applies domain rules and calls driven ports, repository and gateway adapters perform real I/O, and the controller maps the result back to a response. The core never sees HTTP or SQL.

!Traps

  • Drawing a hexagon while business code still imports the ORM and the vendor SDK.
  • Creating one port per class instead of one port per capability, which produces shallow indirection.
  • Putting HTTP status codes or framework annotations inside port signatures.
  • Letting domain code instantiate repositories or clients instead of receiving them from the composition root.
  • Applying the full pattern to trivial CRUD modules and slowing delivery for no benefit.
  • Assuming hexagonal architecture solves distributed transactions or service decomposition.
  • Treating a folder rename as the refactor and leaving the same dependency graph underneath.
