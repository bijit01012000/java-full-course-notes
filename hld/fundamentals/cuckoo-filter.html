Cuckoo filter
A probabilistic membership structure that keeps short fingerprints in a table of buckets and supports insertion, lookup, and deletion.
Fingerprint
A few bits derived from the item's hash; it stands in for the item so the filter never stores the key itself.
Bucket
A small fixed-size slot group holding several fingerprints, commonly four, that fits in one cache line.
Candidate buckets
The two positions where an item's fingerprint may live, derived from its hash and the fingerprint's own hash.
Kicking
Evicting a fingerprint from a full bucket and reinserting it into its alternate bucket, repeating until a slot is free.
Max kicks
The retry limit that stops an insertion loop and signals the table is too full to place the item.
Load factor
The fraction of bucket slots that are occupied; higher is more memory-efficient but makes insertion harder.
Semi-sorted filter
A variant that keeps fingerprints ordered inside buckets so lookups can stop early and stay cache-friendly.

01The problem: membership checks that must shrink

A service with a very large user base uses a Bloom filter to answer "is this username already taken?" without a database read.

  • The filter is replicated in memory on every application server, and a "definitely not" answer skips the lookup entirely.
  • Then users start deleting their accounts, and their usernames become available again.
  • The set must shrink, which means items have to be removed, not just added.
  • A standard Bloom filter cannot do this, because an item's bits are shared with other items.
  • If the deleted usernames stay in the filter, more and more available names are reported as possibly taken.
  • Every one of those false positives becomes an unnecessary database query, so the filter quietly stops doing its job.

02Why the usual workarounds cost too much

  • Periodic rebuild: rescan the source of truth and construct a fresh filter every few hours.
  • Rebuilding is correct but expensive at large scale, and the filter is stale between rebuilds.
  • Counting Bloom filter: store a small counter per position instead of one bit, increment on add, decrement on remove.
  • Counters are usually a few bits wide, which makes the structure several times larger than the bit version.
  • Counting filters also need discipline: decrementing for an item that was never added corrupts the counters and causes false negatives.
  • What is wanted is deletion, a comparable false positive rate, and roughly Bloom-like memory — three properties that conflict in a bit array.

03What a cuckoo filter is

  • It answers the same question as a Bloom filter: possibly in the set or definitely not.
  • Instead of shared bits, it stores a short fingerprint per item inside a table of buckets.
  • Because a fingerprint belongs to one item, removing that fingerprint removes that item and nothing else.
  • Each item has exactly two candidate buckets, and its fingerprint lives in one of them.
  • When both buckets are full, the filter moves existing fingerprints to their alternate buckets to make room, in the manner of cuckoo hashing.
  • Lookups touch at most two buckets, so the cost is small and predictable.
  • The price is that it cannot enumerate items and that insertion can fail when the table is crowded.

04Fingerprints and the two candidate buckets

  • The fingerprint is a truncated hash of the item, kept to a few bits.
  • The first bucket is h1 = hash(item), reduced modulo the bucket count.
  • The second bucket is derived by XOR-ing the fingerprint's hash into the first bucket index, so h2 = h1 XOR hash(fingerprint).
  • The XOR form is reversible: from h2 and the fingerprint you can recompute h1, which is what makes relocation work without the original key.
  • That symmetry is the trick that lets the filter move fingerprints while storing only a few bits.
  • Fingerprint length drives the false positive rate: more bits mean fewer accidental matches and more memory.
  • The item itself is never stored, so the structure cannot tell you what it contains.

05Insertion by kicking

  • Compute both candidate buckets and place the fingerprint in any free slot.
  • If both are full, choose a slot at random, evict its fingerprint, and put the new one there.
  • Reinsert the evicted fingerprint into its own alternate bucket, which may trigger another eviction.
  • Repeat until a slot is free or the max kicks limit is reached.
  • A cycle of evictions is possible, so the retry limit is mandatory rather than an optimization.
  • When the limit is hit, the insertion fails and the table must be grown and rebuilt with a larger fingerprint space.
  • Duplicates need explicit handling: either allow repeated fingerprints or keep a small counter, otherwise deleting one copy removes another.

06Lookup and false positives

  • Compute the fingerprint and both candidate buckets, then scan the slots of those two buckets.
  • A matching fingerprint means possibly present.
  • No match means definitely not present, assuming the filter is current.
  • A false positive occurs when a different item's fingerprint happens to sit in one of the two buckets.
  • The rate depends on fingerprint width, bucket size, and load factor, not on the number of items directly.
  • As with a Bloom filter, a positive answer must be verified if correctness matters.
  • The scan is tiny — two buckets, each a few slots — which is why latency is low and predictable.

07Deletion and its safety rule

  • Deletion computes the two candidates and removes a matching fingerprint from one of them.
  • Because the fingerprint is specific to the item, other items are unaffected — the property a Bloom filter lacks.
  • Deleting an item that was never inserted is dangerous: if its fingerprint matches another item's, that other item is silently removed.
  • The result is a false negative, so deletion must be driven by a real removal in the source data.
  • Duplicate fingerprints make the rule stricter: delete exactly one copy, not all matches.
  • After deletions, the filter has free slots again, so capacity is reclaimed gradually without a full rebuild.
  • Some implementations periodically rebuild anyway to restore ideal bucket distribution after heavy churn.

08Sizing, bucket size, and load factor

  • Capacity is the number of buckets times the slots per bucket.
  • Larger buckets raise the achievable load factor but make each lookup scan more slots and increase collision odds.
  • Smaller buckets keep lookups cheap but fill up sooner and trigger more evictions and failures.
  • Four slots per bucket is the common default because it balances these forces and fits a cache line.
  • A higher load factor means less memory for the same item count, at the cost of longer insertion chains.
  • Fingerprint width is the other knob: every extra bit halves the false positive rate and adds memory per slot.
  • Size for the expected peak, because growing means allocating a new table and reinserting every fingerprint.

09Failure modes

  • Insertion failure: max kicks reached, usually because the table is near capacity or fingerprints cluster.
  • Repeated failures on the same key suggest a bad hash or a bucket count that interacts poorly with the hash.
  • Silent false negatives: caused by deleting absent items or by mishandling duplicates.
  • Saturation: at very high load, eviction chains lengthen and insertion latency spikes.
  • Growth: resizing is a full rehash, not an incremental split, so it needs a pause or a shadow table.
  • No enumeration: the filter cannot list its contents, so recovery requires the source data.
  • Because fingerprints are lossy, two distinct items sharing a fingerprint are indistinguishable forever.

10Comparison with Bloom variants

  • Bloom: smallest and simplest for add-only sets, no deletion, no false negatives.
  • Counting Bloom: deletion via counters, but several times the memory of a bit array.
  • Cuckoo: deletion without a counter array, typically close to Bloom memory at comparable rates.
  • Cuckoo lookups touch a fixed two buckets, while Bloom touches k scattered positions.
  • Bloom insertion never fails; cuckoo insertion can fail and requires a resize path.
  • Cuckoo needs accurate deletion semantics, which pushes correctness requirements onto the caller.
  • Both are approximate, so neither may be used as the sole basis for a definitive yes.

11Where it fits and what to watch

  • Username and handle availability with account deletion.
  • Deduplication of recently seen requests, URLs, or event IDs where entries expire.
  • CDN and cache admission decisions that must be reversible when an object is purged.
  • Storage engines that need per-file key summaries and must rewrite those summaries as files come and go.
  • Adopt it only when deletion is a real requirement; otherwise a plain Bloom filter is simpler and smaller.
  • Track insertion failures, load factor, and rebuild frequency, because those signal an undersized table.
  • Log deletions that found no fingerprint: they usually indicate a bug or a stale view of the data set.

↔Trade-offs to say out loud

  • Fingerprints instead of shared bits make deletion safe but cap how much information a slot holds.
  • Two candidate buckets keep lookups cheap but limit placement flexibility, so insertion can fail.
  • Kicking maintains high occupancy without a counter array but makes insert latency variable.
  • Larger buckets raise the achievable load factor but widen every lookup scan.
  • Wider fingerprints lower false positives but increase memory per slot.
  • High load factor saves memory but lengthens eviction chains and raises failure rates.
  • Accurate deletion reclaims capacity but makes correctness depend on the caller's bookkeeping.
  • Resizing restores headroom but requires a full rehash and a temporary doubling of memory.

?Interview questions

Answer aloud before opening the outline.

1. Why does a Bloom filter fail when items must be deleted?

Each item sets several bits that other items may also use. Clearing them to remove one item also removes evidence of the others, which creates false negatives. A filter that reports present keys as absent is worse than no filter, so deletion is simply unsupported.

2. How does a cuckoo filter store an item?

It stores only a short fingerprint in one of two candidate buckets. The first bucket comes from hashing the item, the second from XOR-ing the fingerprint's hash into the first. No key is stored, so the filter can answer membership but never return the item.

3. Why can the second bucket be computed from the first?

Because the relationship is XOR, which is its own inverse. From either bucket index and the fingerprint hash you can recover the other. That is what allows a displaced fingerprint to be reinserted without knowing the original key.

4. Walk through an insertion that finds both buckets full.

The filter evicts a random fingerprint from one bucket, places the new fingerprint, and tries to reinsert the evicted one into its alternate bucket. If that bucket is also full, the process repeats. It stops when a slot is free or when the max-kick limit signals that the table needs to grow.

5. Why is a max-kick limit necessary?

Evictions can cycle between two or more buckets forever, since each displacement just moves a fingerprint to its alternate location. The limit bounds insertion time and converts a hopeless placement into an explicit failure that the caller handles by resizing.

6. How is deletion different from Bloom deletion?

A cuckoo filter removes one fingerprint that belongs to one item, so other items are untouched. A Bloom filter would have to clear shared bits, damaging other items. The cuckoo approach is safe only when you delete items that are actually present, because deleting an absent item can match someone else's fingerprint.

7. What determines the false positive rate?

Fingerprint width, bucket size, and load factor. A lookup scans two buckets, so more slots or fuller buckets mean more chances of an accidental match. Every extra fingerprint bit roughly halves the rate; the item count matters only through how full the table is.

8. What happens when insertion keeps failing?

The table is effectively full or badly clustered, so the filter must allocate a larger table and reinsert every fingerprint. That is a full rehash, not an incremental operation, so it needs spare memory and a brief pause or a shadow-table swap.

9. Cuckoo filter or counting Bloom filter?

Choose cuckoo when memory matters and deletions are routine, since it avoids the counter array and usually uses less space at a comparable rate. Choose counting Bloom when the implementation must never fail an insert or when the existing codebase already relies on it.

10. Can a cuckoo filter tell you which items it holds?

No. It stores truncated fingerprints, not keys, so there is no way to reconstruct the set or enumerate it. Any rebuild, audit, or migration needs the original data source, exactly as with a Bloom filter.

11. What happens if the same item is inserted twice?

Both copies occupy slots, so the table fills faster and a single deletion removes only one copy. If duplicates are possible, the filter needs a small counter per fingerprint or a rule that insertion is idempotent. Otherwise the structure silently misrepresents the set.

!Traps

  • Deleting an item that was never inserted, which can match another fingerprint and cause false negatives.
  • Ignoring insertion failure and assuming every add succeeded.
  • Treating duplicate inserts and duplicate deletes as symmetric when the filter has no reference counts.
  • Choosing bucket and fingerprint sizes without measuring the resulting false positive rate and load factor.
  • Expecting to enumerate or export the filter contents for a rebuild.
  • Resizing without planning for the temporary double memory and rehash pause.
  • Using a cuckoo filter where a plain Bloom filter would do, and paying for deletion support that is never used.
