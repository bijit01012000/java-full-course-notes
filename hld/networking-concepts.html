MODELThe 30-second model

The one idea to hold onto

Every request pays for distance and round trips before your code runs. DNS finds the address, TCP gives you reliable bytes, TLS secures them, the edge accepts the connection, and the app fans out to caches, databases, and services. Optimize the path — not just the handler.

1 DNS 2 TCP + TLS 3 edge / LB 4 app 5 cache · DB · services

Use this note in two passes. First read the model and the request path. Then cover the tables and redraw the diagrams from memory. The interview test is not naming components — it is explaining where time goes and what happens when a hop fails.

01Why networking matters

A request that crosses an ocean takes longer than one inside a data centre — no matter how fast the application code is. Network time is often the largest and least controllable part of a distributed request.

  • Placement: where you put servers and data determines the distance users pay on every request.
  • Performance: round-trip time (RTT), connection setup, and packet loss can dominate p99 latency.
  • Failure: every hop — DNS, handshake, load balancer, dependency — is a new failure mode.
Interview line

“Before I choose components, I map the request path. Each hop has a latency budget and a failure mode, and those drive the design.”

02Following a request

Picture a user opening a photo-sharing app and waiting for the feed. The request passes through four stages before a response appears.

StageQuestionTypical piecesWhat can go wrong
1. DNS lookupWhich IP address?Device cache, recursive resolver, authoritative serverStale cache, resolver outage, NXDOMAIN, TTL delay
2. Connection setupCan I connect securely?TCP handshake, TLS handshakeExtra RTTs, certificate failure, packet loss
3. Entry pointWhich server handles it?CDN, load balancer, API gatewayUnhealthy target, TLS termination, queueing
4. Backend workCan dependencies answer?App server, cache, database, other servicesSlow query, pool exhaustion, retries, cascade
Interview line

“I’ll walk the request path first — DNS, connection, edge, backend — then name the component I’d add at each step.”

03DNS

DNS translates a domain such as api.example.com into an IP address. If the device has no cached answer, it asks a recursive resolver — usually the ISP or a public DNS service. If the resolver also has no cached answer, it walks the DNS hierarchy to the domain’s authoritative name server.

  • Recursive resolver: does the legwork and caches the result.
  • Authoritative server: holds the actual record for the domain.
  • TTL: how long the answer may be cached. It avoids repeating the full lookup on every request.

Routing with DNS

PolicyWhat it doesExample use
GeographicDirects users to servers based on estimated locationSend users to the nearest region
WeightedSplits traffic across destinations in chosen proportionsGradually move traffic to a new deployment
FailoverDirects new lookups away from an unhealthy destinationRecover from a regional outage
Trap

DNS changes are not instant. A failed region can keep receiving traffic from clients that hold a cached IP until the TTL expires. DNS failover is therefore a TTL-bounded recovery mechanism, not a real-time health check.

Interview line

“DNS is a globally cached database. I treat the TTL as the failover delay I have to budget for.”

04IP addresses, ports, and private networks

An IP address identifies the host; a port identifies which service on that host should receive the traffic. HTTPS uses port 443 by default.

In a typical cloud architecture, not every server is internet-facing:

  • A public load balancer accepts requests from the internet.
  • Application servers sit on private IPs inside a network such as an AWS VPC.
  • Databases are kept private and are not directly reachable from the internet.

Private servers sometimes need to call external services, such as a payment provider. For outbound IPv4, a NAT gateway lets private-subnet servers initiate connections without becoming directly reachable by unsolicited inbound traffic.

Interview line

“I keep the public edge public and the data plane private. If a private service needs the internet, it goes out through NAT; inbound access stays closed.”

Trap

Private addressing is topology, not authentication. A private IP still needs network policy and service-level authentication.

05TCP and UDP

TCP

Reliable, ordered bytes

  • Handshake before data.
  • Retransmits lost packets.
  • Delivers data in order.
  • Adjusts rate for receiver capacity and congestion.

Cost: head-of-line blocking — later data waits for a missing packet.

UDP

Independent datagrams

  • No connection setup.
  • No automatic retransmission.
  • No ordering guarantee.
  • No guarantee data arrives at all.

Win: latest data matters more than recovering old data. Reliability can be built above it.

TCPUDP
ConnectionHandshake before sending dataNo connection setup
DeliveryReliable; retransmits lost packetsNo guarantee
OrderingIn orderNo ordering
Main trade-offHead-of-line blocking when a packet is lostLost data stays lost unless the app handles it
Common usesAPIs, database connections, messaging systemsReal-time video, online games, DNS queries

Default: TCP for APIs, database connections, and messaging — reliable delivery matters. UDP-based protocols for real-time work where waiting for lost data creates a noticeable delay. DNS traditionally uses UDP; larger responses can fall back to TCP.

Interview line

“I choose transport by failure semantics: do I need every byte in order, or do I need the latest packet on time?”

Trap

UDP is not “unreliable by accident.” It removes guarantees so the application — or a protocol such as QUIC — can decide which guarantees are worth paying for.

06The cost of setting up a connection

A new connection adds latency before the client can send its first request. The cost is counted in round trips, not just server processing time.

  • TCP handshake: typically 1 RTT.
  • TLS 1.3 handshake: 1 additional RTT.
  • TLS 1.2 handshake: typically 2 additional RTTs.

So a fresh HTTPS connection over TCP + TLS 1.3 takes about 2 round trips before the first HTTP request can be sent. At a 100 ms RTT, that is roughly 200 ms spent before DNS or application work is counted.

Reducing connection overhead

  • Reuse connections: HTTP keep-alive lets multiple requests use one connection; internal services use connection pools, especially for databases.
  • Move the endpoint closer: a nearby CDN edge can handle the handshakes and forward to the backend over an existing connection — even when the content is not cached.
Interview line

“I count round trips, not just milliseconds. Handshakes are part of p99, so connection reuse and edge termination are real latency decisions.”

Trap

A CDN still helps on a cache miss: the nearby edge absorbs the TCP/TLS handshake and may reuse a warm connection to the origin.

07TLS

TLS is what makes HTTPS secure. It provides three things:

  • Confidentiality: data is encrypted in transit.
  • Integrity: tampering is detected.
  • Identity: the client verifies the server with a trusted certificate.

TLS termination

In many systems, TLS terminates at a load balancer or reverse proxy. The load balancer handles the handshake, manages certificates, decrypts the request, and forwards it to application servers. It can then inspect HTTP paths and headers to make routing decisions.

This simplifies certificate management and reduces encryption work for application servers. But terminating TLS at the edge does not require plaintext to the backend: the load balancer can open a separate TLS connection to the app servers. Internal services can also use mutual TLS (mTLS), where both sides verify each other’s identity.

Interview line

“TLS at the edge gives me certificate management and HTTP-aware routing. If the threat model requires it, I re-encrypt to the backend or use mTLS between services.”

Trap

“TLS termination” does not automatically mean “plaintext inside the network.” That is a separate design decision.

08HTTP versions

HTTP defines how clients and servers exchange requests and responses. The version changes how connections and streams are managed.

HTTP/1.1

One at a time

Clients typically wait for a response before sending another request on the same connection. Pipelining exists, but responses must still arrive in order. Browsers often open several connections to fetch resources in parallel.

HTTP/2

Multiplexed streams

Multiple requests and responses share one connection at the same time. Headers are compressed. But HTTP/2 still runs over TCP: one lost packet can delay every stream on that connection.

HTTP/3

QUIC over UDP

Independent streams mean a lost packet only blocks streams that need the missing data, though congestion can still affect the whole connection. TLS is integrated into connection setup, so a new secure connection typically takes 1 RTT. QUIC also supports connection migration — a device can keep its connection when switching from Wi-Fi to mobile data.

VersionTransportRequests per connectionEffect of a lost packet
HTTP/1.1TCPOne at a time; browsers open several connectionsDelays that connection
HTTP/2TCPMany at once, multiplexedCan delay every stream on the connection
HTTP/3QUIC over UDPMany independent streamsOnly blocks streams missing that data

In an interview you rarely need to pick an HTTP version. The useful move is explaining the consequence: gRPC commonly uses HTTP/2 for multiplexed RPC, and HTTP/3 can perform better on lossy networks.

Interview line

“HTTP/2 fixes application-level head-of-line blocking; HTTP/3 fixes the TCP-level blocking underneath it.”

Trap

HTTP/3 is not automatically faster. It wins when packet loss or network changes would otherwise stall a TCP connection.

09Latency and bandwidth

Latency

How long data takes

The time for data to travel across the network. Dominated by distance, routing, queueing, and round trips.

Bandwidth

How much data fits

The capacity of a network path per second. Important for large transfers, not for making a tiny request faster.

Distance sets the floor

Light travels through optical fibre at roughly 200 km per millisecond. New York and London are about 5,600 km apart, so even a direct fibre path has a round-trip floor of about 56 ms. Real routes are longer, and processing adds more.

PathTypical round-trip time
Within a data centreLess than 1 ms
Between regions on the same continentTens of ms
Across continentsOver 100 ms

Sequential calls multiply latency

If a service makes 10 sequential calls, each with a 100 ms RTT, that is roughly 1 second of waiting on the network alone. Independent calls should be made in parallel; frequently communicating services should be placed close together; requests can sometimes be batched.

Large transfers are different

For video streaming, file uploads, and cross-region replication, bandwidth becomes the constraint because it decides how much data can move per second. Actual throughput depends on congestion and protocol overhead. Moving large volumes across regions also increases cloud networking cost, especially egress.

Interview line

“For small requests, RTT dominates. For large transfers, bandwidth and cross-region egress cost dominate. They are different optimization problems.”

10Load balancers

A load balancer distributes traffic across servers, lets you scale horizontally, and stops sending new requests to unhealthy instances.

Layer 4

Transport layer

Routes connections or flows using IP addresses and ports. It does not need to understand HTTP, so it can handle other TCP and UDP applications.

Layer 7

Application layer

Understands HTTP. Routes by URL path, headers, or cookies; terminates TLS; can modify HTTP headers. Example: /api to API servers, images to an image fleet.

Algorithms and health

  • Routing: round robin, least connections, hashing.
  • Layer constrains information: layer 4 can use client IP; routing on a user ID in an HTTP header requires layer 7.
  • Health checks: periodically connect or call a health endpoint; stop routing after repeated failures.

Default for HTTP APIs: a layer 7 load balancer in front of stateless application servers. It gives health-aware routing and HTTP-level decisions without much added complexity.

Interview line

“L4 routes flows; L7 routes requests. If the decision depends on a path, header, or cookie, I need L7.”

Trap

A layer 4 load balancer cannot route on a user ID inside an HTTP header. It only sees IP and port information for the flow.

11Reverse proxies and API gateways

Load balancers, reverse proxies, and API gateways overlap in practice. Explain them by their main job rather than by product name.

ComponentMain jobAlso commonly handles
Load balancerSpreads traffic across healthy serversHealth checks, TLS termination (L7)
Reverse proxyHandles requests on behalf of backend serversTLS termination, compression, caching, static files, forwarding
API gatewayCommon entry point that routes API requests to servicesToken validation, rate limiting, request logging

API gateway trade-offs

  • Consistency: one place for auth, rate limits, and logging instead of reimplementing them in every service.
  • Capacity: it handles traffic for many services, so it needs enough throughput.
  • Redundancy: a single gateway failure must not take down the whole application.
  • Cost: it is another hop, so it adds some processing overhead and latency.
Interview line

“The load balancer spreads load, the reverse proxy fronts the servers, and the gateway centralizes API concerns. If they overlap, I explain which job I am relying on.”

Trap

An API gateway is a shared failure domain. Redundancy and capacity are part of the design, not an afterthought.

12CDNs

A content delivery network is a set of servers distributed across locations — edge locations or points of presence. It serves content closer to users, reducing latency and offloading the origin.

When a user requests an image or video segment, a nearby edge first checks its cache. A fresh copy is served directly. Otherwise the edge fetches from the origin — object storage or an application server — and caches it if allowed.

Controlling the cache

  • Use HTTP headers such as Cache-Control plus CDN configuration.
  • For static assets, put a version number or content hash in the filename. Then the file can be cached for a long time; an update produces a new URL instead of replacing the cached file.
  • CDNs commonly deliver images, video, JavaScript, and stylesheets.

Dynamic requests: even when a response cannot be cached, a nearby edge can accept the initial connection and reuse an existing connection to the origin. That reduces handshake overhead.

Interview line

“A CDN shortens distance and absorbs connection setup; caching is the bonus. That is why it helps even for some uncacheable traffic.”

Trap

Content-hashed filenames let you cache aggressively without a painful invalidation problem. Reusing the same filename is what creates stale-cache pain.

13Routing users across regions

When the application runs in multiple regions, something must send each user to a sensible location. The two common approaches are geographic DNS and anycast.

Geographic DNSAnycast
How it picks a locationDNS returns a different IP based on estimated locationMany locations share one IP; internet routing picks one
When a location failsUsers may keep the old IP until the TTL expiresTraffic moves once the route is withdrawn
Main limitationLocation estimates and DNS cachingDepends on routing policy; not always the closest location
Commonly used byMulti-region applicationsCDNs and DNS providers

Geographic DNS

A user in India might be sent to Mumbai; a user in the US to Virginia. DNS providers usually estimate location from the IP address of the DNS resolver, not the user’s actual IP. Some resolvers share client-network information to improve accuracy.

Limits: estimates can be wrong, and DNS responses are cached. During a regional failure, some users keep connecting to the failed region until their cached record expires.

Anycast

Servers in multiple locations advertise the same IP address. Internet routing decides which location receives a connection, often a nearby one. If a location stops advertising its route, traffic can move without waiting for DNS caches to expire. But routing changes still take time, existing connections may break, and the chosen location is not guaranteed to be the closest or fastest.

Interview line

“Geo DNS failover waits for the TTL; anycast failover waits for the route to be withdrawn. Neither is instantaneous, and neither guarantees the absolute closest server.”

Trap

Geographic DNS usually geolocates the resolver, not the user. VPNs, corporate DNS, and public resolvers can make the estimate wrong.

14Service discovery

Inside a system, services must find each other. An order service calling a payment service cannot hard-code instance IPs: instances scale up, scale down, and restart.

Option 1

Internal load balancer

Provides a stable endpoint such as payments.internal. The caller sends requests there, and the load balancer spreads them across healthy instances.

Option 2

Service registry

Keeps track of available instances and their addresses. Callers query the registry and send requests directly. Instances register themselves as they start and disappear as they stop.

Interview line

“Instances are ephemeral, so I never hard-code their addresses. I use a stable internal endpoint or a registry, and I assume both can be stale.”

Trap

A service registry is itself a critical shared dependency. Clients need caching, health checks, and a plan for registry unavailability.

15Timeouts and retries

Every network call can fail or take longer than expected. The default behaviour — wait forever — is how a slow dependency exhausts threads, memory, and connections in the caller.

Timeouts and deadlines

  • Base timeouts on expected response time and the overall request deadline.
  • If the client expects a response in 2 seconds, a downstream call should not wait 30 seconds.
  • Pass the remaining deadline through the call chain so each service knows its budget.

Retries

  • Exponential backoff: increase the delay after each failure.
  • Jitter: add randomness so many clients do not retry in lockstep.
  • Limited attempts: cap retries and do not retry at every layer.
  • Idempotency: only retry operations that are safe to repeat, or make them idempotent with a key.

If three layers each make up to three attempts, one request can become 27 calls to the final dependency. Retrying at one carefully chosen layer is easier to control.

Interview line

“A timeout is a budget; a retry is extra load. I set both deliberately, add jitter, cap attempts, and retry at one layer rather than every layer.”

Trap

Retries during an outage can become a denial-of-service attack on your own dependency. Backoff without jitter synchronizes clients instead of protecting the system.

Rapid recall

Walk me through a request from a phone to a database.

DNS resolves the API name to an IP. The client opens TCP, then TLS. The request reaches a CDN edge or load balancer, which forwards it to a healthy app server. The app may read a cache, query a database, and call other services before responding. Each hop adds latency and a failure mode.

Why can DNS failover be slow?

Resolvers and clients cache the answer for the TTL. During a regional failure, some clients keep using the old IP until that TTL expires. DNS is not a real-time health signal.

When would you choose UDP over TCP?

When timely delivery matters more than recovering every packet — real-time video, games, or when the application or QUIC implements its own reliability and congestion control. TCP remains the default for APIs, databases, and messaging.

How many round trips before the first HTTPS request?

About two with TCP + TLS 1.3: one for TCP, one for TLS. At 100 ms RTT, that is roughly 200 ms before the request is sent, excluding DNS and server processing. TLS 1.2 typically adds another round trip.

What is the difference between L4 and L7 load balancing?

L4 routes connections using IP and port, and can handle any TCP/UDP protocol. L7 understands HTTP and can route on path, headers, or cookies; it can also terminate TLS. Routing on a user ID in a header requires L7.

Why does HTTP/3 help on a lossy network?

HTTP/3 runs over QUIC on UDP with independent streams. A lost packet only blocks the streams that need it, instead of stalling every stream on a TCP connection. QUIC also integrates TLS and supports connection migration.

How do services find each other without hard-coded IPs?

Use a stable internal load-balancer endpoint, or a service registry that tracks instance addresses. Instances register and deregister as they scale and restart. Either way, callers should handle staleness and registry/load-balancer failure.

What is wrong with retrying at every layer?

Retries multiply. Three layers with three attempts each can turn one request into 27 calls to the final dependency, just when it is already struggling. Use capped exponential backoff with jitter, and retry at one chosen layer.

The closing sentence

“Networking choices are latency and failure choices. I connect them to where users are, how services communicate, and how much downtime or delay the product can tolerate.”
