MODELThe 30-second model

The one idea to hold onto

System design is the bridge between requirements and components. Decide what the system must do, how well, which building blocks earn their place, how requests and data flow, and what you trade away. The output is not a diagram — it is a set of defended decisions.

requirements components communication data flow trade-offs

Read once for the picture. Then close the diagrams and answer the questions aloud. Naming Kafka is easy; explaining why it belongs is the test.

01The problem

One server works for a few thousand users. Ten million users change the constraints — not the feature.

  • Storage: hundreds of terabytes of photos do not fit on one app server.
  • Failure: one server is one failure domain; one crash takes the product down.
  • Distance: a US server makes an India feed slow; physics sets a latency floor.
  • Spikes: a viral post creates a traffic and fan-out problem, not a code-style problem.

02What system design means

System design = choosing components, responsibilities, communication, data flow, and trade-offs.

  • Code level: functions, classes, algorithms; is it correct and efficient?
  • System level: servers, databases, caches, queues, network; can it handle load and failure?
  • Output: a defended set of decisions, not a technology list.
  • Rule: every component must earn its place by solving a problem.

03Starting with requirements

You cannot evaluate a design until you know what it must do. Split requirements into two groups:

  • Functional: what it does — upload, follow, like, feed.
  • Non-functional: how well — <200 ms feed, available if a server fails, no photo loss.

From feature to component

Same features, different NFRs, different design:

  • 200 ms feed → cache or CDN.
  • Survive server failure → multiple servers and health checks.
  • Never lose a photo → durable object storage and replication.
Opening line

Weak: “I’ll use Kafka, Redis, and Kubernetes.”
Strong: “We need high write volume, spike absorption, and async processing. That points to a queue — let me confirm scale first.”

04The building blocks

Most large systems are a small set of blocks arranged around the request path.

ClientsMobile apps and browsers that send requests.
DNSTranslates a domain name into a server address.
Load balancerSpreads requests across application servers.
Application serversRun the business logic and orchestrate calls.
DatabasesStore structured data: users, follows, photo metadata.
Object storageStores large files such as the photos themselves.
CachesKeep hot data in memory to avoid repeated database reads.
CDNServes static content from locations closer to users.
Message queuesMove slow work out of the request path for background workers.

05Following a request through the system

Upload path

  1. Client → load balancer → app server.
  2. App server writes metadata to the database.
  3. App server returns a pre-signed URL.
  4. Client uploads the image directly to object storage.
  5. App server adds a processing job to the queue.
  6. Worker generates thumbnails / updates feeds.

Why: image bytes bypass the app server; slow work is asynchronous.

Feed read path

  • App server checks the cache for the post list.
  • Hit: return cached posts.
  • Miss: read the database, store in cache, return.
  • Images are served separately from the CDN.
ComponentWhy it is there
CDNReduces latency for image downloads and removes repeated image traffic from the origin.
Message queueKeeps slow work — thumbnails, feed updates — out of the request path.
CacheReduces database load for repeated feed reads.
Object storageGives a scalable, durable place to store large files without putting them in the database.

06What we design for

When we evaluate a design, we look at a few common qualities. They are not independent; improving one usually costs another.

QualityWhat it meansPhoto app example
ScalabilityHandle more users, traffic, and data as demand grows.Going from a few thousand users to ten million.
AvailabilityStay accessible when users need it, even when components fail.The app stays up when one server crashes.
ReliabilityBehave correctly without losing, duplicating, or corrupting data.An uploaded photo is never lost or saved twice.
PerformanceLow latency and sufficient throughput.The feed loads in under 200 ms.
ConsistencyDifferent users and services see the same up-to-date view.Everyone sees the same like count.
MaintainabilityEasy to operate, debug, update, and extend.Add a feature without breaking uploads.
CostMeet requirements without excess servers, storage, bandwidth, or effort.Do not pay for ten servers when two are enough.

Every choice is a trade-off

  • Cache: faster reads, lower DB load; accepts staleness.
  • Replicas: better availability and performance; more cost and complexity.
  • Rule: if you cannot name what gets worse, you have not finished evaluating it.

07Designs evolve

Start simple; add components only when a specific bottleneck appears.

  • Start with one app server and one database.
  • Add a component only when a specific bottleneck is measured.
  • Early complexity costs debugging time, failure modes, and money.

08Why learn system design

Even small features force system-level choices. Example: the Like button.

  • Cache the count? Yes — read-heavy; accepts brief staleness.
  • Sync or async? Queue the update; more moving parts to monitor.
  • Traffic spike? Add servers; higher cost.

09System design in interviews

45–60 minutes, open-ended, no single correct answer. Performance can affect your level and compensation.

  • Clarify scope and non-functional targets.
  • Estimate users, QPS, storage, and the hot path.
  • Sketch components and one write/read flow.
  • Go deeper on the one or two bottlenecks that matter.
  • Explain trade-offs throughout, not just at the end.

What they assess

  • Structure: drive the problem, state assumptions, avoid wandering.
  • Judgment: defend each component and its cost.
  • Depth: data flow, failure modes, consistency, caching.
  • Communication: narrate the diagram, define terms, check in.

★Cheat sheet

  • Definition: requirements → components → responsibilities → communication → data flow → trade-offs.
  • Functional requirements say what the system does; non-functional requirements say how well.
  • Start with requirements, not technologies. A component must earn its place by solving a problem.
  • One write, one read: explain the upload path and the feed path before adding depth.
  • Object storage for bytes; database for metadata; CDN for distance; cache for repeated reads; queue for slow work.
  • Pre-signed URL: direct upload without routing large files through the app server.
  • Every choice is a trade-off. Name what gets better and what gets worse.
  • Add components when a bottleneck is real, not because they are on a architecture diagram checklist.
  • Interview flow: clarify → estimate → sketch → deep dive → trade-offs.
  • No single correct answer. Explain the reasoning; do not recite a design.
60-second answer

“System design turns requirements into components, responsibilities, data flow, and trade-offs. I clarify functional and non-functional needs, estimate scale, sketch one write and one read, then go deeper on the bottlenecks. For a photo app: object storage for bytes, database for metadata, pre-signed URL for uploads, queue for background work, cache for feeds, CDN for images — each justified by a requirement.”

!Traps to avoid

  • Technology-first: naming Kafka, Redis, or Kubernetes before the requirement that justifies them.
  • Boxes without flow: drawing components but never explaining what moves between them.
  • Happy-path only: ignoring failures, retries, timeouts, and partial data.
  • Premature scale: adding components “for scale” before the current scale needs them.
  • Free cache: pretending caching has no staleness or invalidation cost.
  • Quality confusion: treating scalability, availability, reliability, and performance as the same thing.
  • No requirements: designing before agreeing on features and non-functional targets.
  • No trade-off: claiming a design is simply “better” without naming what it makes worse.
  • Memorized design: reciting a known architecture instead of reasoning from the problem.
  • Silent drawing: not narrating assumptions, decisions, or open questions.
One rule

If you cannot name what a choice makes worse, you have not finished evaluating it.

?Most-asked interview questions

Answer these aloud, with the photo app as the running example. The goal is a defensible chain of reasoning, not a memorized script.

How to answer any system design question

  1. Restate the goal: “So the system needs to let users upload photos, follow people, and read a feed.”
  2. Separate requirements: list functional requirements, then non-functional targets and assumptions.
  3. Estimate: users, read/write ratio, QPS, storage, and the hot path. Round aggressively.
  4. Sketch: clients → edge → app → data → async work. Narrate one write and one read.
  5. Go deeper: pick the bottleneck the interviewer cares about — database, cache, queue, consistency, failure.
  6. Close with trade-offs: what you optimized, what you accepted, and what you would change at the next scale.
Trade-off formula: “X improves quality A, but costs B. I’d accept that because the requirement is C.”

Drill mode: cover the answer, say it aloud, then open it.

1. What is system design, and how is it different from coding?

System design chooses components, responsibilities, communication, data flow, and trade-offs. Coding asks whether a function is correct and efficient; system design asks whether the system handles load and failure.

2. What are functional and non-functional requirements?
  • Functional: what it does — upload, follow, like, feed.
  • Non-functional: how well — <200 ms feed, availability, durability.
  • Impact: functional → features and APIs; non-functional → capacity, failure handling, placement.
3. How do you start a system design interview?

Clarify scope and non-functional targets, estimate scale, sketch components and one write/read flow, then go deeper on one or two bottlenecks. State assumptions explicitly.

4. What are the main building blocks of a large system?

Clients, DNS, load balancer, app servers, database, object storage, cache, CDN, and queue with workers. Pick only the blocks the requirements justify.

5. Walk me through a photo upload.

Client → load balancer → app server. The app writes metadata, returns a pre-signed URL, and enqueues a job. The client uploads the image directly to object storage; a worker generates thumbnails or updates feeds.

6. Walk me through a feed read.

The app checks the cache. On a hit it returns posts; on a miss it reads the database, stores the result in cache, and returns. Images come separately from the CDN.

7. Why use object storage for photos instead of a database?

Photos are large blobs. Object storage is cheap, durable, scalable, and CDN-friendly; the database keeps metadata and ownership.

8. Why use a pre-signed URL?

It lets the client upload directly to object storage without sending bytes through the app server or exposing long-lived credentials. The URL is time-limited and authorized by the app.

9. Why put a message queue between upload and processing?

It moves slow work out of the request path, absorbs spikes, and lets workers retry and scale independently. Cost: more moving parts and eventual completion.

10. Why use a cache, and what does it cost?

A cache lowers read latency and database load. The cost is staleness and invalidation. Acceptable for feeds; usually not for balances.

11. Scalability vs availability vs reliability vs performance?
  • Scalability: handle growth in users, traffic, and data.
  • Availability: stay accessible when needed.
  • Reliability: behave correctly without loss, duplication, or corruption.
  • Performance: latency and throughput.
12. How do you decide when to add a component?

Add it when a measured bottleneck or requirement justifies it: DB overload → cache or replicas; slow images → CDN; blocking work → queue. Early complexity costs money and debugging time.

13. How do you handle a celebrity post with millions of views?

Cache the post and feed fragments, serve images from the CDN, queue writes and processing, scale stateless app servers, and consider fan-out and rate limits. Each choice accepts staleness, delay, or write amplification.

14. When would you choose synchronous vs asynchronous processing?

Sync when the user needs the result and it fits the latency budget. Async when work is slow, bursty, or retryable. Async adds eventual consistency and operational complexity.

15. How do you estimate scale in an interview?

Average QPS ≈ (DAU × actions/day) ÷ 86,400; peak is a small multiple. Storage = objects × average size × replication and metadata overhead. Round aggressively and show where the pressure is.

16. How would the design change from 1,000 users to 10 million?

The features stay the same; the bottlenecks change. At 1K, one server and one database are fine. At 10M, expect a load balancer, multiple app servers, cache, object storage plus CDN, and a queue. Add each only when needed.

17. What is the biggest mistake candidates make?

Starting with technology instead of requirements, skipping non-functional targets, drawing boxes without data flow, ignoring failures, and not stating trade-offs. A simpler design with clear reasoning wins.

18. What if you do not know a requirement or technology?

State the assumption, explain how it changes the design, and ask the interviewer to confirm. If you do not know a technology, reason from the problem and trade-offs; do not fake internals.
