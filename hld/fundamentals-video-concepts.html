Introduction to System Design

01

What is System Design?

source ↗

Core ideaSystem design is the process of deciding which components a system needs, what each one owns, how they communicate, and how data flows between them — so the system meets its functional and non-functional requirements at a level above writing code.

  • Storage: hundreds of terabytes of photos do not belong in the same database rows as user profiles and captions.
  • Failure: when one server holds the app, the database, and the files, a single crash removes all three at once.
  • Distance: a feed request from India to a server in the United States pays a round-trip penalty on every call.

Top 30 System Design Concepts

source ↗

Core ideaThirty building blocks, grouped from the network upward: how machines connect, how applications exchange data, where data lives, how systems scale, what breaks across multiple machines, and how to organize the whole thing.

  • Learn the order: name resolution → IP routing → transport connection → HTTP exchange.
  • The same primitives reappear at every scale: a load balancer is a server to its clients and a client to its backends.
  • Networking problems — DNS errors, packet loss, added round trips — surface as application failures, so they belong in the design.

Core Concepts

03

Scalability

source ↗

Core ideaScalability is the ability to handle more users, traffic, and data without collapsing — but only after you identify the resource that is actually the bottleneck.

  • More users mean more concurrent requests, more connections, and more CPU contention.
  • More data means larger tables, larger indexes, slower backups, and more disk I/O.
  • A read-heavy product stresses the database differently from a write-heavy one.
Full topic note: Scalability →
04

Availability

source ↗

Core ideaAvailability is how often users can actually reach and use the system — engineered by removing single points of failure, adding redundancy that survives correlated failures, and containing the blast radius when a dependency breaks.

  • The database is still healthy, but customers cannot reach the store because the only path to it is gone.
  • A system can be fast and scalable and still fail users if one required component takes the whole thing down.
  • Handling more load and staying online during failures are related but separate problems.
Full topic note: Availability →
05

Latency vs Throughput

source ↗

Core ideaLatency is how long one request takes, throughput is how much work finishes per second, and bandwidth is the ceiling a connection could reach — improving one does not automatically improve the others.

  • Bandwidth is the number of lanes: how many cars the road can carry at once.
  • Throughput is the number of cars that actually arrive per hour; congestion, accidents, or roadwork can push it well below capacity.
  • Latency is how long one car takes to travel between the two cities.
Full topic note: Latency vs Throughput →
06

Consistent Hashing

source ↗

Core ideaConsistent hashing maps keys and servers onto the same ring so that adding or removing one server moves only a small slice of the keys instead of reshuffling the whole cluster.

  • Suppose user profiles are cached across five servers, S0 through S4.
  • Sending a request to a random server is wasteful: the profile may already be cached elsewhere, so the hit rate collapses.
  • The key must map deterministically, so every request for user:42 reaches the same server while membership is stable.
Full topic note: Consistent Hashing →
07

CAP Theorem

source ↗

Core ideaWhen a network partition splits replicas, CAP says you cannot keep both a single up-to-date view and a successful response for every affected request — and the choice belongs to each operation, not to the whole database.

  • Before the change reaches Region B, the network link between the regions fails.
  • Both regions are still running, and customers can reach both of them.
  • A customer asks Region B for the price, but Region B still has the old value and cannot contact Region A.

Networking

7 topics
08

OSI Model

source ↗

Core ideaThe OSI model divides network communication into seven layers, each providing a service to the layer above and relying on the layer below, so you can reason about what is built where and where a request breaks.

  • The OSI model is a mental map of that journey, not a protocol you implement.
  • It separates concerns so each layer can change without rewriting the others: Wi-Fi became 5G, Ethernet became fiber, and HTTP still worked.
  • It gives a shared vocabulary for debugging: “is this a Layer 3 problem or a Layer 7 problem?” is a faster question than “is the network broken?”.
Full topic note: OSI Model →
09

IP Address

source ↗

Core ideaAn IP address is a network location, not a machine's permanent identity: routers forward packets toward it, and CIDR, subnets, NAT, and DNS decide how those locations are organised and reached.

  • An IP address is assigned to a network interface, not to a machine: a laptop's Wi-Fi adapter, a VM's NIC, or a container's virtual interface.
  • One server can have several interfaces and therefore several addresses, each on a different network.
  • Routers only need to know the next hop, not the full path, which is what makes the internet scale.
Full topic note: IP Address →
10

TCP vs UDP

source ↗

Core ideaTCP and UDP both carry data between ports on top of IP, but TCP buys reliable, ordered delivery with handshakes and retransmissions, while UDP stays fast and simple and leaves those guarantees to the application.

  • At the top are application protocols such as HTTP, DNS, and database wire protocols.
  • Below them is the transport layer, where TCP and UDP live.
  • Below that is IP, which moves packets between machines across networks.
Full topic note: TCP vs UDP →
11

HTTP/HTTPS

source ↗

Core ideaHTTP is a stateless request-response protocol carried over TCP or QUIC; HTTPS is the same protocol wrapped in TLS, which adds encryption, integrity, and proof of the server's identity.

  • It follows a simple request-response model: the client asks for something, the server answers.
  • A page load is many requests: HTML first, then images, scripts, and stylesheets discovered in it.
  • HTTP does not move bytes itself; it relies on a transport underneath.
Full topic note: HTTP/HTTPS →
12

Domain Name System (DNS)

source ↗

Core ideaDNS is the internet's hierarchical, heavily cached naming system: it turns a domain name into the records a client needs, and its TTLs decide how quickly a change can reach everyone.

  • DNS translates a human-readable name such as api.example.com into the records a client needs, usually an IPv4 or IPv6 address.
  • It is a distributed directory, not one central database: each zone is served by its own authoritative name servers.
  • The name is a stable indirection layer; the address behind it can change without any client changing configuration.
Full topic note: Domain Name System (DNS) →
13

Proxy vs Reverse Proxy

source ↗

Core ideaA forward proxy speaks for the client, a reverse proxy speaks for the servers — the difference is whose side of the connection it represents.

  • If the middle server acts on behalf of the client, it is a forward proxy.
  • If it acts on behalf of the backend servers, it is a reverse proxy.
  • Both forward traffic and both hide one side from the other; only the direction and intent differ.
Full topic note: Proxy vs Reverse Proxy →
14

Checksums

source ↗

Core ideaA checksum is a small value computed from data so a later reader can detect that the bytes changed; it detects corruption, but recovery still comes from a retry, a replica, or a backup.

  • Electrical noise can flip a bit while a packet travels over a cable or radio link.
  • Faulty memory in a router or server can alter data while it waits in a buffer.
  • Bit rot: a storage device can lose or alter bits over months or years.

Load Balancing

4 topics
15

Load Balancers

source ↗

Core ideaA load balancer gives many backend servers one stable endpoint, spreading traffic across healthy instances and removing failed ones from rotation without the client noticing.

  • One server works fine until traffic exceeds its CPU, memory, connection, or disk capacity.
  • Past that point requests queue, latency climbs, and the server may fail under load.
  • If that server is the only one, its failure takes the entire application down with it.
Full topic note: Load Balancers →
16

Load Balancing Algorithms

source ↗

Core ideaA load balancing algorithm is the rule that picks which backend serves a request; the right choice depends on what the balancer can actually observe and on how uneven request cost and duration are.

  • Static algorithms follow a fixed rule: fixed order, fixed weights, or random choice, with no live state.
  • Dynamic algorithms read server state first: active connections, active requests, response time, or reported load.
  • Static is cheap and predictable but blind: it keeps sending to an overloaded server because it never looks.
Full topic note: Load Balancing Algorithms →
17

DNS Load Balancing

source ↗

Core ideaDNS load balancing spreads traffic by returning different IP addresses during name resolution, which makes it the only layer that can choose a region before a connection exists.

  • A single-region load balancer gives you no answer when the whole region fails.
  • Sending a user in Singapore to a data centre in Virginia adds round-trip latency to every request, including the TLS handshakes.
  • DNS is the first step of every connection: the client must resolve api.example.com to an address before it can connect.
Full topic note: DNS Load Balancing →
18

Anycast Routing

source ↗

Core ideaAnycast lets many locations announce the same IP address, and the internet's routing system sends each packet to whichever one is nearest according to BGP.

  • A DNS provider can return the address of a nearby region based on the query location, and that works for the steady state.
  • The first problem is caching: if Tokyo fails, users keep connecting to its old address until their cached answer expires.
  • The second problem is location accuracy: DNS often sees the user's recursive resolver, not the user.

API Fundamentals

7 topics
19

What is an API?

source ↗

Core ideaAn API is the contract that lets one piece of software call another: it fixes the operations, the data to send, and the response to expect, while hiding everything behind the boundary.

  • A food delivery app calls one API for nearby restaurants, another to place an order, another to take payment, and another to track delivery.
  • Each of those capabilities is owned by a different system, often a different team, with its own database and deployment.
  • The app does not need to know how any of those systems work internally; it only needs to know how to talk to them.
Full topic note: What is an API? →
20

API Architectural Styles

source ↗

Core ideaAn API style is the pattern a communication follows — resource-based, query-based, action-based, streaming, or event-driven — and real systems pick a different one for each communication path.

  • How does the client ask? Does it request a resource, call a function, or subscribe to a stream?
  • How is data structured? Text JSON, XML, or a compact binary format?
  • What is the interaction model? One-shot request-response, or continuous two-way traffic?
Full topic note: API Architectural Styles →
21

Idempotency

source ↗

Core ideaAn operation is idempotent when repeating it has the same intended effect as doing it once, which is what makes safe retries possible when the client cannot tell whether the first attempt worked.

  • The client cannot distinguish three cases: the payment succeeded, it failed, or the request never arrived.
  • Retrying is the standard reaction, and it is correct when the first attempt failed.
  • Retrying is destructive when the first attempt succeeded, because the user is charged twice.
Full topic note: Idempotency →
22

REST Fundamentals

source ↗

Core ideaA good REST API is predictable: the same conventions for resources, methods, status codes, errors, pagination, and versioning everywhere, so learning one endpoint teaches you the rest.

  • Once other teams, mobile apps, or external customers depend on it, every rename is a potential outage for someone else.
  • Inconsistent conventions force developers to relearn each endpoint instead of generalising from one example.
  • Inconsistent error handling pushes bespoke branching logic into every client.
Full topic note: REST Fundamentals →
23

GraphQL Fundamentals

source ↗

Core ideaGraphQL lets the client describe the response shape against a typed schema, which removes over-fetching and multiple round trips but moves cost, caching, and abuse control onto the server.

  • A mobile screen needs a name and avatar but the endpoint returns the full profile, so bandwidth and parsing work are wasted: over-fetching.
  • A screen needs an order plus its customer plus line items, but no single endpoint returns all three, so the client makes several calls: under-fetching.
  • Each new screen shape encourages either a new bespoke endpoint or a bloated general one.
Full topic note: GraphQL Fundamentals →
24

gRPC Fundamentals

source ↗

Core ideagRPC turns a method call in a .proto contract into a network call over HTTP/2 with compact binary messages, which suits internal service-to-service communication.

  • You describe a service and its methods in a .proto file, and tooling generates client and server code.
  • Calling a remote method looks like calling a local function, which keeps service code readable.
  • The framework handles serialization, transport, deadlines, and status propagation.
Full topic note: gRPC Fundamentals →
25

JWT

source ↗

Core ideaA JWT is a signed, self-contained token that lets any service holding the issuer's public key verify who the user is without a session lookup — at the cost of revocation and exposure.

  • On login, the server verifies credentials, creates a session, and stores it in a database or in Redis.
  • The client receives an opaque session ID — usually in a cookie — and sends it with every request.
  • The server looks up the session, resolves the user, and processes the request.

Communication Patterns

9 topics
26

Long Polling

source ↗

Core ideaLong polling keeps a normal HTTP request open on the server until an event arrives or a timeout fires, giving near-real-time delivery without leaving the request-response model.

  • Regular polling, also called short polling, repeats an identical request on a fixed interval and gets an immediate answer, often empty.
  • Most requests can be useless: at 100,000 clients polling every 5 seconds you already run about 20,000 requests per second even when nothing happened.
  • There is always residual delay: polling every 10 seconds means an event can sit unseen for almost 10 seconds.
Full topic note: Long Polling →
27

Server-Sent Events (SSE)

source ↗

Core ideaSSE keeps one long-lived HTTP response open and lets the server push a stream of events to the browser, one direction only, with automatic reconnection and resumable event IDs.

  • Polling makes the browser ask repeatedly, so frequent polling wastes requests that return nothing.
  • Infrequent polling reduces traffic but adds delay before updates are seen.
  • Long polling improves on that, yet every response still closes the request and forces the browser to ask again.
Full topic note: Server-Sent Events (SSE) →
28

WebSockets

source ↗

Core ideaA WebSocket is one persistent, full-duplex TCP connection upgraded from HTTP, so either side can send a message the moment it has one instead of the client repeatedly asking.

  • Real-time data arrives when the server learns about it, which the client cannot predict: a chat message, a price change, a cursor move.
  • With plain HTTP the client must keep asking, so requests are spent on asking rather than on data.
  • Short polling asks every few seconds; most responses are empty and an update that lands just after a poll waits for the next one.
Full topic note: WebSockets →
29

Webhooks

source ↗

Core ideaA webhook is an HTTP callback: the provider POSTs an event to a URL you registered, so you stop polling and start reacting — but reliable delivery is entirely your problem.

  • One option is polling: ask the provider every N seconds whether anything changed.
  • Polling wastes work when most checks return nothing, and it adds latency up to one full poll interval.
  • The other option is a webhook: the provider sends an HTTP request to your server when the event happens.
Full topic note: Webhooks →
30

Message Queues

source ↗

Core ideaA message queue is a durable buffer between producers and consumers that turns slow, bursty, failure-prone work into independent background tasks — at the price of duplicates, retries, and eventual completion.

  • If the upload request waits for all of that work, the user stares at a spinner and the request may time out before processing finishes.
  • A hundred simultaneous uploads make the servers attempt a hundred transcodes at once, exhausting CPU and memory.
  • If transcoding fails halfway, the whole upload request fails even though the file was stored successfully.
Full topic note: Message Queues →
31

Pub/Sub

source ↗

Core ideaPub/sub lets a publisher announce that something happened once, while any number of independent subscribers receive their own copy — decoupling the producer from everyone who cares.

  • The order service must know every downstream service and be redeployed whenever a new team wants to react to orders.
  • A slow email provider lengthens the customer's checkout request even though email has nothing to do with placing the order.
  • If analytics is down, the order service must invent a policy: fail the order, retry, buffer, or silently drop the event.
Full topic note: Pub/Sub →
32

Message Brokers

source ↗

Core ideaA message broker is shared infrastructure that stores, routes, delivers, and acknowledges messages between producers and consumers, so services can talk without knowing each other's addresses, availability, or speed.

  • Every service must know every peer's address, retry policy, and availability assumptions.
  • Each team re-solves the same problems: where messages wait when a receiver is down, how many times to retry.
  • No one centrally understands who subscribes to which events, so adding a consumer means changing producers.
Full topic note: Message Brokers →
33

Delivery Semantics

source ↗

Core ideaDelivery semantics describe what a messaging system promises about loss and duplication — and every promise is really a choice about when to retry and when to acknowledge.

  • The message may have been lost before delivery, so nothing happened.
  • The message may have been processed and the response lost, so the charge already happened.
  • The service may simply be slow and the response is still in flight.
Full topic note: Delivery Semantics →
34

Dead Letter Queues

source ↗

Core ideaA dead letter queue is a quarantine for messages that fail repeatedly, so one poison message cannot stall a stream or be silently thrown away.

  • Because the message was never acknowledged, the broker delivers it again.
  • The consumer fails again, and under at-least-once delivery the cycle repeats indefinitely.
  • A message that consistently fails is called a poison message.
Full topic note: Dead Letter Queues →

Caching

5 topics
35

What is Caching?

source ↗

Core ideaA cache keeps a copy of frequently used data in a faster layer so repeat requests avoid the database — cutting latency, reducing load, and raising throughput at the cost of staleness and invalidation work.

  • A cache is a fast storage layer holding copies of data that would otherwise be fetched from a slower system.
  • It usually sits in memory or at the edge, where access is far cheaper than a database query or a remote call.
  • The cache does not replace the source of truth; it holds a copy that can be discarded.
Full topic note: What is Caching? →
36

Caching Strategies

source ↗

Core ideaCaching strategies answer one question: who moves data between cache and database, and when — with cache-aside as the default read pattern and write-through, write-behind, or write-around chosen to fit the write path.

  • For reads, either the application checks the cache itself or the cache automatically fetches missing data.
  • For writes, the system can update the database first, update cache and database together, or write the cache and persist later.
  • Each arrangement produces a different strategy with different latency, consistency, and durability.
Full topic note: Caching Strategies →
37

Cache Eviction Policies

source ↗

Core ideaAn eviction policy decides which valid entry leaves when the cache is full — LRU by default, LFU for stable hot keys, FIFO or random for low overhead, with TTL handling freshness and admission control protecting against pollution.

  • As requests arrive, more objects are added until the cache reaches its memory limit.
  • At that point there are two options: reject the new object, or remove an existing entry to make room.
  • Most caching systems choose to remove an existing entry.
Full topic note: Cache Eviction Policies →
38

Cache Invalidation

source ↗

Core ideaCache invalidation is how a cached copy is expired, deleted, or refreshed when the source of truth changes — the hard part is doing it without races, misses, or stampedes.

  • Product 123 is cached at $100; the database later says $90 and the cache still says $100.
  • Any read served from the cache now returns the wrong price to users.
  • The system holds multiple copies of the same fact, and copies diverge whenever a write happens.
Full topic note: Cache Invalidation →
39

Content Delivery Network (CDN)

source ↗

Core ideaA CDN is a globally distributed cache that serves content from an edge location near the user, so latency and origin load drop — as long as the content is shareable, cacheable, and safely invalidated.

  • Distance is latency: a request from India to a Virginia origin crosses a long network path in both directions, and TCP plus TLS setup multiplies the round trips.
  • Popular static files are byte-identical for every user, so the origin re-sends the same image, script, or video segment millions of times.
  • Origin bandwidth, connection counts, and CPU saturate first during launches, sales, and viral traffic.
Full topic note: Content Delivery Network (CDN) →

Databases

13 topics
40

Database Types

source ↗

Core ideaNo single database is best at transactions, single-key lookups, text ranking, and time-window aggregates — pick the engine whose storage layout and index structure match how the data is actually queried.

  • Payments and orders need correctness: a partial write must never leave money taken without an order.
  • Shopping carts and login sessions need lookup by a single key with very low latency.
  • The search bar needs to rank products by how well they match free text, tolerate typos, and match word variants.
Full topic note: Database Types →
41

SQL vs NoSQL

source ↗

Core ideaThe SQL vs NoSQL decision trades a fixed schema and flexible queries against a flexible schema and queries designed in advance; it is decided by the shape of the data, the access patterns, and how much consistency each part of the system needs — not by which label sounds more modern.

  • The choice shapes how data is modeled: tables joined at read time, or documents and partitions shaped for the read.
  • It shapes how queries are written: arbitrary SQL, or queries planned around known access paths.
  • It shapes failure behavior: a write either commits everywhere it must, or becomes visible in stages.
Full topic note: SQL vs NoSQL →
42

ACID Transactions

source ↗

Core ideaACID transactions let an application group several operations into one all-or-nothing unit, so a crash or a concurrent request cannot leave the data half-updated — at the cost of latency, locking, and throughput.

  • The server can crash between the two writes, leaving money deducted from Alice and never credited to Bob.
  • Two transfer requests can arrive at the same time, both read a $100 balance, and both proceed.
  • Both problems come from the same root cause: several operations that must behave as one, plus concurrency.
Full topic note: ACID Transactions →
43

B-Trees and B+ Trees

source ↗

Core ideaA B-tree is a wide, shallow, self-balancing search tree whose nodes are disk pages, so a lookup needs only a few page reads instead of a table scan — and its sorted order also makes range queries cheap, at the price of write amplification on splits.

  • A scan costs time proportional to table size, so it gets slower every month as data grows.
  • It also reads pages it does not need into the buffer pool, evicting useful pages and hurting other queries.
  • An index adds a small, sorted structure that maps key values to row locations.
Full topic note: B-Trees and B+ Trees →
44

LSM Trees

source ↗

Core ideaAn LSM tree turns random writes into sequential ones by buffering changes in memory and flushing sorted immutable files, then merging those files in the background — which makes writes fast and reads more complicated.

  • Each write dirties a page somewhere in the file, so writes arrive as random I/O rather than sequential.
  • A single logical insert can touch a leaf, a parent, and several index pages — the tree's own write amplification.
  • Random page updates are expensive on spinning disks and still costly on SSDs, which prefer large sequential writes.
Full topic note: LSM Trees →
45

Relational Databases

source ↗

Core ideaA relational database stores each fact once in typed tables, links tables with keys, and rebuilds answers at query time with SQL and joins — giving strong correctness and flexible querying in exchange for join cost and a single write primary.

  • A customer with twenty orders has their address copied twenty times.
  • When they move, every one of those rows must be found and updated, or the data disagrees with itself.
  • Deleting a customer's only order erases the customer entirely, because the contact details lived in that row.
Full topic note: Relational Databases →
46

Document Databases

source ↗

Core ideaA document database stores each entity as one self-contained JSON-like record, so a request that touches one entity is a single read of one document — as long as you model around embedding, references, and the queries you actually run.

  • One wide table needs a column for every possible attribute, and most columns stay empty for most rows.
  • One table per product type avoids empty columns but requires a schema change for every new product type.
  • A generic (product_id, attribute, value) table is flexible but makes every query a join and a pivot.
Full topic note: Document Databases →
47

Key-Value Stores

source ↗

Core ideaA key-value store is the simplest useful database: a value under a unique key, with get, put, and delete — extremely fast and easy to partition, but blind to what is inside the value.

  • The lookup is always identical: fetch one record by its session id.
  • There is no join, no search by content, no aggregation — just a fetch that must be fast, thousands of times per second.
  • A relational database can store it, but each fetch pays for parsing, planning, and possibly disk reads to answer a trivial question.
Full topic note: Key-Value Stores →
48

Full-Text Search Engines

source ↗

Core ideaA full-text search engine replaces row scans with an inverted index from words to documents, so it can match, rank, and filter free text — at the cost of a second data store that must be kept in sync with the source of truth.

  • A leading-wildcard pattern cannot use a normal index, so the database reads every row.
  • Pattern matching is literal: it misses run versus running, plurals, synonyms, and misspellings.
  • It produces a set, not an ordering; the best match is indistinguishable from the weakest.
Full topic note: Full-Text Search Engines →
49

Wide Column Databases

source ↗

Core ideaA wide-column database stores rows that can have many sparse columns, groups them into a partition by a partition key, and sorts them inside the partition by a clustering key — so a huge, write-heavy, single-partition query becomes a cheap sequential read.

  • The write rate is enormous and mostly append-only, so most of the cost of joins, constraints, and multi-row transactions is wasted.
  • The data set outgrows one machine, so partitioning must be built in rather than bolted on.
  • The dominant query is narrow and identical every time: the latest messages in one conversation, already in order.
Full topic note: Wide Column Databases →
50

Time Series Databases

source ↗

Core ideaA time-series database assumes every row is an append-only sample tagged with a timestamp, so it can compress time-ordered data aggressively, answer range-and-aggregate queries quickly, and expire old data cheaply.

  • The write rate is high and constant, and writes are nearly all appends of new timestamps.
  • Rows are rarely updated or deleted individually; they simply age out.
  • Queries ask for a range — last hour, last day — grouped by host, endpoint, or region.
Full topic note: Time Series Databases →
51

Graph Databases

source ↗

Core ideaA graph database stores relationships as first-class edges that point directly at their endpoints, so a multi-hop traversal follows pointers instead of performing one index join per hop — which is exactly where relational queries degrade as depth grows.

  • A relational database answers these with joins, and each additional hop adds another join.
  • At two or three hops the query is still manageable; at five or more it becomes a chain of joins whose intermediate result sets explode.
  • The database also does index lookups per hop, so cost grows with depth and with the size of intermediate sets.
Full topic note: Graph Databases →
52

Vector Databases

source ↗

Core ideaA vector database stores embeddings and answers what is most similar to this? with an approximate nearest-neighbor index, trading exactness for speed — and it only works if the embedding model, distance metric, and filters are designed together.

  • Keyword search matches tokens, so it misses paraphrase, synonyms, and language differences.
  • The meaning of a piece of text can be represented as a numeric vector, and similar meanings produce nearby vectors.
  • Finding the nearest vectors answers what is semantically closest to this? rather than what contains this word?
Full topic note: Vector Databases →

Database Scaling Techniques

8 topics
53

Indexing

source ↗

Core ideaAn index is a small, sorted structure that turns a full table scan into a few page reads — but each one adds write cost, storage, and memory pressure, so the goal is the smallest set of indexes that supports the real query patterns.

  • An index is a separate structure built to make certain lookups fast; the table still holds the full rows.
  • It stores the indexed column values in sorted order along with a reference to the row that owns each value.
  • The table rows themselves are in no particular order — only the index is sorted.
Full topic note: Indexing →
54

Partitioning

source ↗

Core ideaPartitioning splits one logical table into smaller physical pieces so queries can skip most of the data and old data becomes cheap to drop — but only if the partition key matches how the table is actually queried.

  • Indexes grow until they no longer fit comfortably in memory, so more lookups go to disk.
  • Queries may scan far more data than they used to, even when the query shape has not changed.
  • Deleting or archiving old records becomes an expensive, long-running operation.
Full topic note: Partitioning →
55

Replication

source ↗

Core ideaReplication keeps copies of the same data on several servers, buying availability, read throughput, and regional latency — at the cost of lag, failover complexity, and the illusion that a copy is a backup.

  • If the only database server fails, the application loses access to all of its data.
  • As traffic grows, one machine must absorb every read and every write.
  • Read-heavy products exhaust the database long before the application tier is stressed.
Full topic note: Replication →
56

Sharding

source ↗

Core ideaFeature flags put behavior behind a runtime switch, so code can be deployed without being released and a risky feature can be turned off in seconds without a redeploy.

Core ideaThe hard part of a schema migration is not changing the schema — it is changing it while old and new application versions both run against the same database.

Three Pillars of Observability

source ↗

Core ideaMetrics tell you whether something is wrong, traces tell you where, and logs tell you why — but only when the three are linked by a shared trace ID.

  • On one machine you would read the log file and check CPU. In a distributed system there is no single file and no single CPU graph.
  • The request may touch many services, each with many replicas, so the evidence is scattered across hosts and containers.
  • Short-lived containers take their filesystem logs with them when they are replaced, so evidence can disappear before you look.

Logging

source ↗

Core ideaGood logging is not more logging: it is structured events with consistent fields, honest levels, a correlation ID, and enough context to explain an incident — while keeping secrets out and volume affordable.

  • Thousands of lines say only that something went wrong, with no order, user, or downstream call identified.
  • The opposite failure is just as bad: logging every cache lookup and health check buries the one error in noise.
  • A useful entry answers what happened, where, to whom, when, and with what outcome.

Log Aggregation

Core ideaLog aggregation ships logs from every instance into one searchable, time-ordered store, so an engineer can answer what happened to this request without logging into twenty machines.

  • A failing order may involve five services and dozens of instances; the relevant lines are spread across all of them.
  • Connecting to hosts one at a time and grepping files does not scale past a handful of machines, and it is impossible during an incident.
  • Containers are ephemeral: when a container is replaced, its filesystem logs usually disappear with it.

Metrics and Instrumentation

Core ideaMetrics turn system behavior into a small set of numeric time series, so you can see a slowdown building minutes before customers report it — provided the instrumented signals and their labels are chosen carefully.

Distributed Tracing

Core ideaDistributed tracing records the tree of work a single request triggers across services, so you can say exactly which hop consumed the six seconds instead of guessing from per-service averages.

Alert & Monitoring

source ↗

Core ideaMonitoring records what the system is doing; alerting decides which of those facts is worth waking a human for. A good alerting system fires quickly when something important breaks and stays quiet the rest of the time.

  • Too few alerts: the payment service starts failing on a Saturday night, nothing fires, and the team learns about it from customer complaints and a revenue drop.
  • Too many alerts: on-call receives dozens of pages a night for brief CPU spikes and disks at 70% that resolve themselves, so the engineer starts ignoring the pager.
  • Once ignoring becomes a habit, a real outage alert arrives and gets ignored with the rest.

SSL/TLS

source ↗

Core ideaTLS turns an untrusted network into a channel that is private, tamper-evident, and bound to a verified server identity — confidentiality, integrity, and authentication for data in transit.

  • Every machine on that path can read the request, including credentials, session cookies, and personal data.
  • Reading is not the only risk: an attacker in the middle can modify the response — injecting scripts, changing a payment amount, altering content.
  • An attacker can also impersonate the site entirely with their own server and collect the credentials directly.

Core ideaEncryption at rest assumes the storage itself will be stolen — a discarded disk, a public backup bucket, a shared snapshot — and makes the bytes useless without a key that lives somewhere else.

  • A disk or drive is decommissioned or resold without being properly wiped.
  • A backup file is written to a storage bucket that was accidentally made public.
  • A database snapshot is shared with the wrong account or copied to a test environment.

Secrets Management

source ↗

Core ideaA secret is a value where merely possessing it grants access, so secrets management is really about four questions: where the value lives, who can read it, how it rotates, and who used it.

  • Normal configuration is safe to read: a timeout value or feature flag leaks little when exposed.
  • A secret grants access on possession alone, so reading it is equivalent to being authorized.
  • Applications need secrets constantly: database passwords, API keys, TLS private keys, queue tokens, signing keys.

Password Management

source ↗

Core ideaDesign password storage around one assumption — the database will be stolen — and make the stolen data as useless as possible with per-user salts, a deliberately slow hash, and a reset flow that does not become the weakest link.

  • Leaks happen through SQL injection, a misconfigured backup, a stolen admin credential, or a compromised vendor.
  • The attacker then holds every user's password in plain text, with no work required.
  • Damage does not stop at your system: password reuse lets the same email-password pairs be tried against email, banking, and shopping sites.

RBAC

source ↗

Core ideaRBAC replaces per-user permission assignments with roles: permissions are grouped into named bundles, roles are assigned to users, and every request is checked against the result — which stays manageable only if roles are designed and reviewed deliberately.

  • At five users, direct assignment is clear and nobody needs a system for it.
  • At thousands of users and a hundred permissions, onboarding requires remembering exactly which subset a new hire needs.
  • When a policy changes, someone must edit hundreds of users individually, and some will be missed.
