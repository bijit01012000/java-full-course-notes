Introduction

2 topics

What system design is, plus the 30-concept map the rest of the course expands.

01

What is System Design?

source ↗

Core ideaTurn requirements into components, responsibilities, data flow, and defended trade-offs.

  • Definition: system design is one level above code — servers, databases, caches, queues, network, and failure.
  • Requirements first: functional = what it does; non-functional = how well (latency, availability, durability).
  • One server works for a few thousand users; storage, failure, distance, and spikes change the constraints at scale.
  • Photo app path: client → LB → app → DB/object storage; add cache, CDN, and queue only when the bottleneck justifies them.
  • Every component earns its place by solving a problem; every choice makes something else worse.
  • Interview flow: clarify → estimate → sketch → deep dive → trade-offs.

Core Concepts

5 topics

The five qualities and scaling ideas that every design decision is measured against.

03

Scalability

source ↗

Core ideaHandle more load without collapsing — and know which resource is actually the bottleneck.

  • Load: users, requests/sec, data size, read/write ratio, and peak-to-average ratio.
  • Vertical (scale up): bigger machine; simple, but has a ceiling, costs more, and remains one failure domain.
  • Horizontal (scale out): more machines; needs stateless app servers, a load balancer, and shared state handled externally.
  • Database is usually the bottleneck: separate it from the app, add indexes, cache, read replicas, then shard.
  • Sessions: avoid per-server memory; use sticky sessions or a shared session store.
  • Measure first; add a component only when the bottleneck is real.
Trade-off: horizontal scaling improves capacity and fault isolation but adds coordination, data consistency, and operational cost.
04

Availability

source ↗

Core ideaKeep the system usable when components fail — measured in nines, not adjectives.

  • Availability: percentage of time the system is usable. 99.9% ≈ 8.8 h/year; 99.99% ≈ 52.6 min/year; 99.999% ≈ 5.3 min/year.
  • Series: availabilities multiply — more dependencies mean lower end-to-end availability.
  • Parallel: redundancy helps only when failures are independent: 1 − (1 − A)ⁿ.
  • Active-passive: standby takes over; simpler, but failover time and idle capacity.
  • Active-active: both serve traffic; better utilization, but needs conflict handling and routing.
  • Use health checks, load balancers, multi-AZ/region placement, queues for overload, and circuit breakers to contain cascades.
Trap: adding a redundant component that shares the same dependency, network, or control plane does not improve availability.
05

CAP Theorem

source ↗

Core ideaWhen a network partition happens, choose consistency or availability — and state which one you chose.

  • C: every read sees the latest write (linearizable consistency).
  • A: every non-failing node returns a response.
  • P: the system keeps working despite dropped or delayed messages between nodes.
  • Partitions are unavoidable in distributed systems, so the real choice is CP (reject or block to stay consistent) vs AP (serve potentially stale data).
  • CA is only meaningful when there is no partition — not a real distributed option.
  • PACELC: even without partitions, trade latency vs consistency.
Examples: CP-leaning systems reject writes during partitions; AP-leaning systems accept writes and reconcile conflicts later. Many systems are tunable per operation.
06

Consistent Hashing

source ↗

Core ideaDistribute keys across changing servers while moving as few keys as possible.

  • Modulo hashing (hash(key) % N) remaps almost every key when N changes.
  • Consistent hashing maps keys and servers onto a ring; a key belongs to the next server clockwise.
  • Adding or removing one server moves roughly 1/N of the keys, not all of them.
  • Virtual nodes: each physical server appears many times on the ring, smoothing uneven ranges and hot spots.
  • Replication: store each key on the next N distinct physical nodes clockwise.
  • Use it for distributed caches, sharded databases, and load balancers that need stable key affinity.
Trade-off: better distribution and elasticity, but more metadata, rebalancing, and ring-management complexity.
07

Latency vs Throughput

source ↗

Core ideaLatency is how long one request takes; throughput is how many finish per unit time.

  • Latency: time for one request; report p50/p95/p99, not just averages.
  • Bandwidth: capacity of the path; throughput: actual work completed per second.
  • Small requests are latency-bound; large transfers are bandwidth-bound.
  • Distance, round trips, queueing, and tail latency dominate user experience.
  • Batching and concurrency improve throughput but can increase per-request latency.
  • Find the bottleneck: CPU, memory, disk, network, lock contention, or a downstream dependency.
Trade-off: optimizing for throughput often means accepting higher latency; optimizing for latency often means less batching and more parallelism.

Networking

6 topics

The request path: names, connections, protocols, and the checks that catch corruption.

08

Load Balancers

source ↗

Core ideaSpread traffic across healthy servers and remove failed instances from rotation.

  • Algorithms: round robin, least connections, weighted, and hashing.
  • L4 routes connections by IP/port and can handle TCP/UDP without understanding HTTP.
  • L7 understands HTTP: path, headers, cookies, TLS termination, and request-level routing.
  • Health checks remove unhealthy targets; connection draining lets in-flight requests finish.
  • Stateless app servers make horizontal scaling and load balancing simple; stateful servers need sticky sessions.
  • The load balancer itself needs redundancy — active-passive, active-active, or anycast/DNS.
Default: L7 in front of stateless HTTP app servers; L4 when you need protocol-agnostic, high-throughput forwarding.
09

Proxy vs Reverse Proxy

source ↗

Core ideaA proxy is an intermediary; the difference is whose side it represents.

  • Forward proxy: sits in front of clients; hides client identity, controls egress, caches, and logs.
  • Reverse proxy: sits in front of servers; hides backend topology, terminates TLS, compresses, caches, and routes.
  • A reverse proxy can serve static files and protect backend services from direct exposure.
  • Reverse proxy vs load balancer: load balancing is one possible job of a reverse proxy; the categories overlap.
  • Common implementations: NGINX, Envoy, HAProxy, cloud gateways.
  • Use a reverse proxy for TLS offload, routing, compression, and a single controlled entry point.
Trap: a forward proxy protects the client; a reverse proxy protects and fronts the server. Do not use the terms interchangeably.
10

Domain Name System (DNS)

source ↗

Core ideaA globally cached, hierarchical name-to-address system — and a coarse traffic-routing tool.

  • Resolution: device cache → recursive resolver → root/TLD → authoritative name server.
  • Record types: A/AAAA (address), CNAME (alias), MX (mail), TXT (verification), NS (delegation).
  • TTL controls cache lifetime; failover is delayed until caches expire.
  • Recursive resolvers do the walking; authoritative servers hold the record.
  • DNS supports geographic, weighted, and failover routing.
  • Propagation is mostly cache expiry, not an instant global update.
Trap: DNS failover is not real-time health checking. Clients may keep using a stale IP until TTL expiry.
11

HTTP/HTTPS

source ↗

Core ideaHTTP is a stateless request/response protocol; HTTPS adds encryption, integrity, and identity.

  • Request: method, path, headers, optional body. Response: status code, headers, body.
  • Idempotent methods: GET, PUT, DELETE; POST is not idempotent by default.
  • HTTP is stateless; cookies or tokens carry user state across requests.
  • HTTPS = HTTP over TLS; it protects against eavesdropping and tampering and verifies the server certificate.
  • HTTP/1.1: one request at a time per connection; HTTP/2: multiplexed streams over TCP; HTTP/3: QUIC over UDP.
  • Caching headers (Cache-Control, ETag) are part of the protocol contract.
Interview line: “HTTP defines the contract; TLS protects the pipe; HTTP/2 and HTTP/3 change how the pipe is shared.”
12

TCP vs UDP

source ↗

Core ideaTCP gives reliable ordered bytes; UDP gives independent datagrams with fewer guarantees.

  • TCP: three-way handshake, retransmission, ordering, flow control, and congestion control.
  • TCP is a byte stream, not a message stream; the application must frame messages.
  • TCP head-of-line blocking: one lost packet delays later data on that connection.
  • UDP: no handshake, no retransmission, no ordering guarantee; lower overhead and no built-in recovery.
  • Use TCP for APIs, databases, and messaging; UDP for real-time media, games, DNS, and QUIC.
  • QUIC builds reliability and congestion control on top of UDP, avoiding TCP-level HOL blocking.
Trade-off: reliability vs timeliness. Choose by failure semantics, not by which protocol sounds faster.
13

Checksums

source ↗

Core ideaDetect accidental corruption — not prove authenticity.

  • A checksum is a compact fingerprint of data used to detect changes or transmission errors.
  • Simple sums catch some errors; Internet checksum and CRC catch more; cryptographic hashes catch changes with very high probability.
  • Checksums detect corruption; they do not repair it.
  • A hash alone does not prove who created the data; use a MAC or digital signature for authenticity.
  • Used in packets, storage systems (HDFS, ZFS), databases, and object storage.
  • Stronger checks cost more CPU; choose based on threat model and data volume.
Trap: “checksum” and “cryptographic hash” are not interchangeable — CRC is for accidental errors, not attackers.

API Fundamentals

4 topics

Contracts, interaction styles, and the real-time and event-driven edges of APIs.

14

What is an API?

source ↗

Core ideaA contract that lets one system use another without knowing its internals.

  • An API defines endpoints, methods, inputs, outputs, errors, and auth requirements.
  • Request anatomy: method, path, headers, query parameters, optional body.
  • Response anatomy: status code, headers, body.
  • The contract hides implementation details and allows independent evolution; version it deliberately.
  • Public, private, and partner APIs differ in audience, stability, and access control.
  • Good APIs are predictable, documented, idempotent where needed, and rate-limited.
Interview angle: define the contract before discussing the database or framework behind it.
15

API Architectural Styles

source ↗

Core ideaPick the interaction style that matches the client’s access pattern — not the trendiest acronym.

  • REST: resources + HTTP verbs; stateless, cacheable, simple; can over- or under-fetch.
  • GraphQL: one endpoint, typed schema, client-selected fields; caching and query complexity are harder.
  • RPC/gRPC: action-oriented, protobuf contracts, HTTP/2, streaming; fast and typed, less browser-native.
  • WebSockets: full-duplex, persistent, real-time; not request/response.
  • Webhooks: provider pushes an event to a consumer URL; retries and duplicates are normal.
  • Choose by latency, coupling, browser support, streaming needs, and operational complexity.
Default: REST for public CRUD APIs; gRPC for internal low-latency service calls; WebSockets for two-way real-time; webhooks for event notifications.
16

WebSockets

source ↗

Core ideaOne persistent, full-duplex connection for real-time bidirectional communication.

  • Starts as an HTTP upgrade handshake, then switches to the WebSocket protocol.
  • Messages are frames over a long-lived TCP connection; server can push without polling.
  • Scaling requires many connections per server, connection draining, and a pub/sub layer to route messages across servers.
  • Heartbeats detect dead connections; clients reconnect with backoff.
  • Use for chat, live dashboards, collaboration, multiplayer, and notifications.
  • Not ideal for simple request/response or infrequent updates; HTTP may be simpler.
Trade-off: real-time responsiveness vs connection state, fan-out complexity, and resource usage.
17

Webhooks

source ↗

Core ideaAn event-driven HTTP callback: the provider pushes, the consumer must tolerate retries and duplicates.

  • Provider sends an HTTP POST to a consumer endpoint when an event occurs.
  • Return 2xx quickly; process heavy work asynchronously via a queue.
  • Retries are expected — make consumers idempotent with event IDs or idempotency keys.
  • Ordering is not guaranteed; include timestamps/sequence numbers and handle out-of-order events.
  • Secure with HMAC signatures, TLS, allowlists, and replay protection.
  • Provider concerns: retry policy, dead-letter handling, observability, and slow-consumer isolation.
Trap: a webhook is at-least-once in practice. Duplicate delivery is a design assumption, not an edge case.

Databases & Storage

3 topics

Choose the right storage shape, store blobs correctly, and make queries cheaper.

18

Database Types

source ↗

Core ideaChoose by access pattern, consistency, and scale — not by one database to rule them all.

  • Relational: rows/tables, joins, ACID transactions; the default for transactional systems.
  • Key-value: simple lookups, high throughput, low-latency (Redis, DynamoDB).
  • Document: flexible JSON-like documents; good for evolving aggregates (MongoDB).
  • Wide-column: huge sparse tables, write-heavy scale (Cassandra, HBase).
  • Graph: relationship-heavy queries (Neo4j); time-series: metrics/events; search: inverted indexes; vector: embeddings.
  • Polyglot persistence is valid, but every extra store adds consistency and operational cost.
Default: start relational unless a concrete access pattern or scale requirement clearly demands otherwise.
19

Object Storage

source ↗

Core ideaCheap, durable, scalable storage for large blobs — not a replacement for a database.

  • Objects live in buckets; each object has a key, bytes, and metadata.
  • Flat namespace and HTTP API; optimized for whole-object reads/writes, not random updates.
  • Designed for massive durability and scale (e.g., 11 nines) at low cost.
  • Store photos/video/backups in object storage; keep searchable metadata in a database.
  • Use pre-signed URLs for direct client upload/download without routing bytes through the app.
  • Integrates well with CDNs; versioning and lifecycle policies manage retention.
Trap: object storage is not a low-latency transactional database; do not put hot relational queries there.
20

Query Optimization

source ↗

Core ideaRead the plan, find the expensive step, then change the query, index, or schema.

  • Use EXPLAIN / EXPLAIN ANALYZE to see scans, joins, sort, and row estimates.
  • The cost-based optimizer uses statistics; stale stats can produce a bad plan.
  • Common fixes: add the right index, avoid SELECT *, reduce rows early, remove N+1 queries.
  • Watch for function calls on indexed columns, leading wildcards, and implicit type casts.
  • Denormalization/materialized views can help read-heavy paths; caching may beat query tuning.
  • Measure before and after; every index also slows writes.
Interview angle: optimize the query you can observe, not the query you imagine.

Database Scaling Techniques

3 topics

Reads first, then writes: indexes, partitioning, denormalization, and the cost of sharding.

21

Indexing

source ↗

Core ideaA sorted structure that lets the database find rows without scanning the whole table.

  • B-tree indexes support equality, range, and ordering; hash indexes mainly support equality.
  • Composite indexes follow the leftmost prefix rule: (a,b) helps queries on a or a,b, not b alone.
  • A covering index contains every column a query needs, avoiding table lookups.
  • Indexes cost storage, memory, and write amplification; too many slow inserts/updates.
  • High selectivity is better; low-selectivity indexes may not be used.
  • The database may ignore an index due to stats, cost, or a function on the column.
Rule: index for real query patterns, then verify with the plan.
22

Sharding

source ↗

Core ideaPartition data across databases by a shard key when one database can no longer handle the write volume or size.

  • Range: contiguous ranges per shard; good for range scans, risks hot spots.
  • Hash: even distribution; range queries become cross-shard.
  • Directory: lookup table maps keys to shards; flexible but adds a dependency.
  • The shard key determines routing, balance, and query cost — choose it carefully.
  • Cross-shard joins, transactions, and aggregations are expensive; plan for them.
  • Hot shards, resharding, and operational complexity are the price of scale.
Order: index → cache → read replicas → partition/shard. Shard late; it is hard to undo.
23

Denormalization

source ↗

Core ideaTrade write complexity and duplication for faster reads by precomputing or duplicating data.

  • Normalization reduces duplication but can require expensive joins.
  • Denormalize by copying fields, storing aggregates, or maintaining read models.
  • Good for read-heavy systems, feeds, counters, and expensive joins.
  • Costs: more storage, harder writes, and consistency logic across copies.
  • Keep one source of truth and define how derived data is updated/repaired.
  • Often paired with caching or materialized views; do not denormalize before measuring.
Trade-off: read speed vs write complexity and consistency risk.

Caching

4 topics

The fastest request is the one you do not make — but every cache introduces freshness debt.

24

What is Caching?

source ↗

Core ideaKeep frequently used data in a faster layer to reduce latency and load on the source.

  • Hit: data found in cache. Miss: fetch from the source and optionally populate.
  • Hit ratio determines how much benefit the cache actually provides.
  • Layers: browser, CDN, application, distributed cache, database buffer pool.
  • Choose cache keys that include every input that changes the response.
  • TTL balances freshness against hit rate; invalidation is the hard part.
  • Cache hot, repeated, expensive-to-compute data — not everything.
When to add: repeated reads, high latency, or database load. Do not add a cache before measuring.
25

Caching Strategies

source ↗

Core ideaDifferent read/write patterns need different cache responsibilities.

  • Cache-aside: app reads cache; on miss reads DB and populates; app invalidates on write.
  • Read-through: cache library loads from the source on a miss.
  • Write-through: write cache and DB synchronously; consistent but slower writes.
  • Write-behind: write cache, flush to DB asynchronously; fast but durability risk.
  • Write-around: write DB directly and bypass cache; avoids cache pollution.
  • Choose by read/write ratio, consistency requirement, and tolerance for lost writes.

26

Cache Eviction Policies

source ↗

Core ideaWhen the cache is full, the eviction policy decides which data is worth keeping.

  • Eviction removes entries to make room; expiration/TTL removes them by age.
  • LRU: evict least recently used; good locality, vulnerable to scans.
  • LFU: evict least frequently used; protects popular items, can retain stale popularity.
  • FIFO, random, MRU, and TTL-based policies fit narrower workloads.
  • Consider object size and cache pollution, not just hit count.
  • Match the policy to the access pattern; measure hit ratio and latency.
Trap: a high hit ratio can still hide expensive misses or stale data. Measure both.
27

Content Delivery Network (CDN)

source ↗

Core ideaServe content from edge locations close to users and offload the origin.

  • Edge locations/PoPs cache content near users; origin holds the authoritative copy.
  • Pull CDN fetches on demand; push CDN uploads content ahead of time.
  • Control caching with Cache-Control, TTLs, and cache keys.
  • Use versioned/hashed URLs for long-lived static assets; purge when necessary.
  • Routing uses DNS/anycast; origin shield reduces origin load.
  • Benefits: latency, bandwidth cost, origin offload; costs: staleness and cache management.
Trap: cache keys must include every input that changes the response — including device, language, or auth scope when relevant.

Asynchronous Communications

2 topics

Decouple producers and consumers with queues and pub/sub, then handle duplicates and ordering.

28

Pub/Sub

source ↗

Core ideaOne event fans out to many independent subscribers.

  • Publisher sends to a topic; every subscription receives a copy.
  • Contrast with a queue: queue = one consumer per message; pub/sub = fan-out to all subscribers.
  • Durable pub/sub retains messages and supports replay; ephemeral pub/sub drops them.
  • Push vs pull delivery; consumers acknowledge to prevent redelivery.
  • Ordering is usually per partition/key, not global.
  • Use for events, notifications, microservice decoupling, and fan-out.
Trap: at-least-once delivery means duplicates; consumers must be idempotent.
29

Message Queues

source ↗

Core ideaBuffer work between producer and consumer so slow or bursty tasks do not block the request path.

  • Producer sends to a queue; one consumer processes each message.
  • Consumer acknowledges after processing; a crash causes redelivery, so duplicates are possible.
  • Competing consumers scale throughput by queue depth; prefetch controls in-flight work.
  • Queues absorb spikes, decouple services, and enable retries.
  • Poison messages go to a dead-letter queue; ordering is per queue or partition/group.
  • A queue is not infinite storage — monitor depth, age, and consumer lag.
Trade-off: responsiveness and resilience vs eventual completion, duplicates, and operational complexity.

Microservices

5 topics

Service boundaries, discovery, and the resilience patterns that keep distributed calls from cascading.

30

Service Discovery

source ↗

Core ideaLet services find each other’s current instances without hard-coded addresses.

  • Instances scale, restart, and move; fixed IPs go stale.
  • A service registry tracks instances and health.
  • Self-registration: the instance registers itself; third-party registration: a platform does it.
  • Client-side discovery: caller queries the registry and chooses an instance; server-side: a load balancer/proxy decides.
  • DNS-based discovery and Kubernetes Services provide simpler variants.
  • Registry must be highly available; clients need caching and stale-result handling.
Default: use the platform’s built-in discovery (Kubernetes Service/DNS) unless you need finer control.
31

Sidecar Pattern

source ↗

Core ideaPut cross-cutting infrastructure next to the service instead of inside its code.

  • Sidecar runs alongside the app (same pod/host) and shares its network namespace.
  • Handles logging, metrics, tracing, proxying, mTLS, retries, and policy.
  • Language-agnostic: every service gets the same behavior without a shared library.
  • Service mesh data planes are typically sidecar proxies.
  • Costs: extra CPU/memory, added latency, and more moving parts.
  • Use for infrastructure concerns, not business logic.
Trade-off: uniform operational behavior vs per-pod resource overhead and complexity.
32

Circuit Breaker Pattern

source ↗

Core ideaStop calling a failing dependency so failures do not cascade.

  • Closed: requests flow normally; failures are counted.
  • Open: fail fast or use a fallback after a threshold.
  • Half-open: allow a probe to test recovery.
  • Trip on error rate, consecutive failures, or timeouts; reset after a cooldown.
  • Apply per dependency, not globally; combine with timeouts and a retry budget.
  • Prevents resource exhaustion and retry storms during outages.
Closed→Open→Half-open→Closed
33

SAGA Pattern

source ↗

Core ideaReplace a distributed transaction with local transactions and compensating actions.

  • A saga is a sequence of local transactions across services.
  • If a step fails, run compensating actions for completed steps.
  • Choreography: services react to events; simple, but harder to see the whole flow.
  • Orchestration: a coordinator drives steps; easier to reason about, but another component to run.
  • Provides eventual consistency, not atomicity; every step and compensation must be idempotent.
  • Use for long-running workflows; avoid when a single database transaction can do the job.
Local tx 1→Local tx 2→Local tx 3→Compensate on failure
34

Service Mesh

source ↗

Core ideaMove service-to-service networking concerns into a dedicated infrastructure layer.

  • Data plane: sidecar proxies handle traffic between services.
  • Control plane: configures routing, policies, certificates, and telemetry.
  • Features: mTLS, retries, timeouts, traffic splitting, circuit breaking, and observability.
  • Language-agnostic and consistent across services.
  • Costs: proxy latency, resource overhead, and a new operational layer.
  • Use when service count and policy complexity justify it; not needed for a small system.
Trap: a service mesh does not fix bad service boundaries or missing idempotency.

Big Data Processing

5 topics

Batch, stream, and the storage/processing layers that turn raw data into usable tables.

35

Batch vs Stream Processing

source ↗

Core ideaBatch processes bounded data on a schedule; stream processes unbounded events continuously.

  • Batch: high throughput, high latency, simple retries; good for reports and backfills.
  • Stream: low latency, continuous, stateful; good for alerts, feeds, and real-time metrics.
  • Streaming needs windowing, event time, watermarks, and late-data handling.
  • State and checkpoints enable recovery; processing guarantees are at-least-once or exactly-once with care.
  • Micro-batching blends the two; Lambda runs batch + speed layers; Kappa favors stream only.
  • Choose by latency requirement, data boundedness, and operational cost.

36

ETL Pipelines

source ↗

Core ideaExtract, transform, and load data reliably from sources into analytics storage.

  • Extract from databases, APIs, logs, or files; transform clean/join/aggregate; load into a warehouse or lake.
  • Batch ETL runs on schedules; streaming ETL processes events continuously.
  • ELT loads raw data first and transforms inside the warehouse/lake.
  • Orchestration (Airflow, Dagster), retries, and idempotent loads are essential.
  • Monitor data quality, schema changes, freshness, and row counts.
  • Design for replay/backfill; do not make pipelines one-shot scripts.
Trap: a pipeline that silently drops bad rows is worse than one that fails loudly.
37

MapReduce

source ↗

Core ideaA distributed batch model: map records, shuffle by key, reduce groups.

  • Map: transform each input record into key/value pairs.
  • Shuffle/sort: group values by key across the cluster.
  • Reduce: aggregate each key’s values.
  • Fault tolerance comes from recomputing failed tasks; data locality reduces network transfer.
  • Combiner reduces shuffle volume; skew (one huge key) is a common bottleneck.
  • High-latency and disk-heavy; Spark/Flink often replace it, but the model is foundational.
Input split→Map→Shuffle / sort→Reduce→Output
38

Data Lakes

source ↗

Core ideaStore raw data at scale and apply schema when reading.

  • Stores structured, semi-structured, and unstructured data in cheap object storage.
  • Schema-on-read: flexible ingestion, but consumers must interpret the data.
  • A catalog (e.g., Hive/Glue) provides tables and metadata; without governance it becomes a data swamp.
  • Supports analytics, data science, and ML on the same raw data.
  • Lakehouse formats add ACID, schema evolution, and performance on top of the lake.
  • Watch file sizes, small files, partitioning, retention, and access control.
Trade-off: flexibility and cost vs governance, performance, and consistency.
39

Data Warehousing

source ↗

Core ideaModeled, structured data optimized for analytics and BI.

  • Schema-on-write; data is cleaned and modeled before loading.
  • Columnar storage and MPP engines optimize large scans and aggregations.
  • Star schema: fact tables + dimension tables; snowflake normalizes dimensions further.
  • Separates OLAP analytics from OLTP production databases.
  • ETL/ELT pipelines populate it; data quality and freshness matter.
  • Warehouse vs lake: modeled/performance vs raw/flexibility; lakehouse converges them.
Interview angle: do not run heavy analytics on the production OLTP database.

Architectural Patterns

5 topics

How the major system shapes differ: client-server, microservices, serverless, events, and peer-to-peer.

40

Client-Server Architecture

source ↗

Core ideaClients request; a central server owns the data and business rules.

  • Client handles UI/input; server handles validation, business logic, and persistence.
  • The server is the source of truth; never trust client-side validation.
  • Thin client vs thick client changes where logic and state live.
  • Servers can be stateless (easy to scale) or stateful (sticky sessions/affinity).
  • Tiers: 1-tier (all-in-one), 2-tier (client + DB), 3-tier (client + app + DB), N-tier.
  • Server push can use polling, long polling, SSE, or WebSockets.
Default: 3-tier with stateless app servers is the baseline for most web systems.
41

Microservices Architecture

source ↗

Core ideaIndependent services organized by business capability, each owning its data.

  • Services communicate via APIs or events and deploy independently.
  • Pros: team autonomy, independent scaling, fault isolation, polyglot freedom.
  • Cons: distributed complexity, network latency, data consistency, debugging, and operations.
  • Requires service discovery, API gateway, observability, CI/CD, and idempotent messaging.
  • Shared database across services is usually an anti-pattern; each service owns its data.
  • Do not start here by default; a modular monolith is often the better first step.
Trade-off: autonomy and scaling vs operational and consistency overhead.
42

Serverless Architecture

source ↗

Core ideaRun code and managed services without provisioning or managing servers.

  • FaaS: event-triggered functions; BaaS: managed databases, auth, queues, storage.
  • Scales automatically, including to zero; pay per invocation/usage.
  • Stateless functions; local state does not survive between invocations.
  • Cold starts, execution time/memory limits, concurrency limits, and vendor lock-in.
  • Good for spiky, event-driven, glue, and low-ops workloads; poor for long-running or stateful services.
  • Watch per-request cost, observability, and local testing.
Trap: “serverless” does not mean no servers; it means you do not manage them.
43

Event-Driven Architecture

source ↗

Core ideaProducers emit events; consumers react asynchronously without direct coupling.

  • Events describe something that happened; producers do not know consumers.
  • Enables decoupling, fan-out, extensibility, and async workflows.
  • Patterns: event notification, event-carried state transfer, event sourcing.
  • Challenges: eventual consistency, ordering, duplicates, schema evolution, and debugging.
  • Use idempotent consumers, a schema registry, dead-letter queues, and tracing.
  • Best when workflows are naturally event-shaped, not as a default for every call.
Trade-off: loose coupling and responsiveness vs harder reasoning about state and failure.
44

Peer-to-Peer (P2P) Architecture

source ↗

Core ideaPeers act as both clients and servers; no central node is required.

  • Decentralized: each peer can request and serve data.
  • Structured P2P uses a DHT for deterministic lookup; unstructured uses flooding/gossip.
  • Resilient to individual node failure and scales with participants.
  • Hard problems: churn, NAT traversal, trust, security, and coordination.
  • Used in file sharing, blockchain, decentralized messaging, and some CDNs.
  • Trade-off: resilience and cost vs latency, consistency, and management complexity.
Interview angle: clarify whether the system needs decentralization or just scalability; a central service is often simpler.

Observability

2 topics

Know what the system is doing in production: logs, metrics, alerts, and the questions they answer.

45

Logging

source ↗

Core ideaStructured, contextual events that let you reconstruct what happened.

  • Use structured logs (JSON) with consistent field names.
  • Levels: DEBUG, INFO, WARN, ERROR, FATAL; avoid logging everything at INFO.
  • Add request ID, correlation ID, user/tenant, service, and version — but never secrets or PII.
  • Log key events, errors, state transitions, and decisions; avoid noisy loops and duplicate stack traces at every layer.
  • Use asynchronous/buffered logging; centralize logs (ELK/Loki) and set retention.
  • Sample high-volume logs; logs are for diagnosis, metrics are for trends.
Trap: logs without correlation IDs are nearly useless in a distributed system.
46

Alert & Monitoring

source ↗

Core ideaMonitoring shows what is happening; alerting tells a human when action is needed.

  • Golden signals: latency, traffic, errors, saturation.
  • Alert on user-impacting symptoms/SLOs, not every internal cause.
  • Every alert needs an owner, severity, runbook, and clear action.
  • Use thresholds for known limits and anomaly detection for unknown patterns.
  • Dashboards support investigation; logs/traces provide detail.
  • Fight alert fatigue: deduplicate, group, silence during maintenance, and review noisy alerts.
Rule: if nobody can act on an alert, it is noise.

Security

3 topics

Authentication, transport security, and authorization: JWT, TLS, and RBAC.

47

JWT

source ↗

Core ideaA signed, self-contained token for stateless authentication — not an encrypted secret container.

  • Structure: header.payload.signature, base64url-encoded.
  • Claims: iss, sub, aud, exp, iat; never put secrets in the payload.
  • The server verifies the signature, expiry, issuer, and audience.
  • Stateless verification scales well, but revocation is hard; use short-lived access tokens + refresh tokens.
  • Store tokens in HTTP-only cookies when possible; local storage is exposed to XSS.
  • Use JWKS for key rotation and validate the algorithm explicitly.
header.payload.signature
{ "alg": "RS256", "typ": "JWT" } . { "sub": "123", "exp": 1710000000 } . signature
48

SSL/TLS

source ↗

Core ideaTLS provides encryption, integrity, and server identity for data in transit.

  • HTTPS = HTTP over TLS; TLS protects against eavesdropping and tampering.
  • Handshake: ClientHello → ServerHello + certificate → key exchange → Finished.
  • Certificates are signed by a trusted CA; the client validates hostname, expiry, and chain.
  • TLS 1.3 reduces handshake round trips and removes weaker primitives.
  • Terminate TLS at a load balancer/reverse proxy; re-encrypt to the backend when required.
  • Use mTLS for service-to-service identity; use HSTS to prevent downgrade.
ClientHello→Certificate→Key exchange→Finished→Encrypted HTTP
49

RBAC

source ↗

Core ideaGrant permissions through roles, not directly to every user.

  • Users → roles → permissions; authorization checks the permission, not the person.
  • Apply least privilege and default deny.
  • Roles simplify administration but can explode or become too coarse.
  • Role inheritance and separation of duties need explicit design.
  • ABAC uses attributes; ReBAC uses relationships — better for fine-grained cases.
  • Enforce at the service/API boundary and audit changes.
Trap: authentication proves who you are; authorization decides what you can do. Do not conflate them.

Traps to avoid

12 traps

The mistakes that make a design sound busy instead of reasoned.

  • Technology-first: Naming Kafka, Redis, or Kubernetes before the requirement that justifies them.
  • No NFRs: Skipping latency, availability, durability, and consistency targets.
  • Boxes without flow: Drawing components but never explaining what moves between them.
  • Happy-path only: Ignoring failures, retries, timeouts, and partial data.
  • Premature scale: Adding components for imagined scale before the current bottleneck is measured.
  • Free cache: Pretending caching has no staleness or invalidation cost.
  • Retry storm: Retrying at every layer without a budget, jitter, or idempotency.
  • Single point of failure: Adding redundancy that still shares one dependency or control plane.
  • Shard too early: Reaching for sharding before indexes, caching, and replicas.
  • No idempotency: Making retries and duplicate messages unsafe.
  • No observability: Designing without logs, metrics, traces, or alert ownership.
  • Memorized design: Reciting a known architecture instead of reasoning from the problem.

Most-asked interview questions

22 questions

Cross-topic questions. Answer aloud before opening the outline.

Drill mode: cover the answer, say it aloud, then open it.

1. How do you start a system design interview?

Clarify scope and non-functional targets, estimate scale, sketch components and one write/read flow, then go deeper on one or two bottlenecks. State assumptions explicitly.

2. SQL vs NoSQL — how do you choose?

Start with access patterns, relationships, consistency, and scale. Relational is the default for transactions and joins; NoSQL fits specific shapes like key-value, document, wide-column, graph, time-series, or search.

3. How do you scale reads? How do you scale writes?

Reads: cache, read replicas, CDN, denormalization. Writes: batch, queue, partition/shard, and reduce write amplification. Measure the bottleneck first.

4. How do you handle a hot key or hot shard?

Cache the hot value, split the key, salt the shard key, isolate the hot tenant, or rate-limit. Add a dedicated cache/shard only when the pattern is understood.

5. How do you keep a cache consistent with the database?

Use TTLs, invalidate on writes, write-through where needed, and version keys. Accept temporary staleness only when the product permits it.

6. Explain CAP in one minute.

During a network partition, choose consistency or availability. CP rejects/blocks; AP serves possibly stale data. PACELC also trades latency vs consistency when the network is healthy.

7. Why consistent hashing?

It maps keys and servers on a ring so adding/removing a server moves roughly 1/N of keys. Virtual nodes smooth distribution and replication uses the next N nodes.

8. How would you design a rate limiter?

Choose token bucket, leaky bucket, fixed window, or sliding window. Keep counters in a fast shared store, return 429 with retry info, and decide fail-open vs fail-closed.

9. How do you make an API idempotent?

Use an idempotency key with a unique constraint/dedupe store, make the operation safe to repeat, and return the original result for duplicates.

10. WebSockets vs SSE vs polling?

WebSockets: bidirectional real-time. SSE: server-to-client stream over HTTP. Polling: simple periodic requests. Choose by direction, frequency, and infrastructure.

11. Queue vs pub/sub?

Queue: one consumer per message; buffer and load-level. Pub/sub: every subscriber gets a copy; fan-out and events. They are often combined.

12. How do you handle duplicate messages?

Assume at-least-once delivery. Use idempotent consumers, dedupe keys, and unique constraints; make retries safe.

13. How do you prevent cascading failures?

Timeouts, retry budgets, circuit breakers, bulkheads, queues/backpressure, and graceful degradation. Do not retry aggressively during an outage.

14. How does service discovery work?

Instances register with a registry or platform; callers use client-side or server-side discovery. Health checks remove bad instances; clients cache and handle staleness.

15. Monolith or microservices?

Start with a modular monolith unless team autonomy, independent scaling, or deployment cadence justify microservices. Microservices add network, data, and operational complexity.

16. How do you handle a distributed transaction?

Avoid it if one database transaction suffices. Otherwise use 2PC for strong atomicity (with availability cost) or a saga with local transactions and compensations for eventual consistency.

17. How do you design observability?

Logs for events, metrics for trends and alerts, traces for request paths. Add correlation IDs, SLOs, dashboards, and owned runbooks.

18. JWT vs server-side sessions?

JWT is stateless and scales across services, but revocation is hard and tokens must be stored safely. Sessions are easy to revoke but need shared storage. Often: short-lived JWT + refresh token.

19. How do you secure service-to-service calls?

mTLS for identity, least-privilege authorization, network policy, short-lived credentials, and secret management. Encrypt in transit and audit access.

20. Batch or stream processing?

Batch for bounded data, high throughput, and tolerance for latency. Stream for unbounded events and low latency. Many systems use both (Lambda) or stream-first (Kappa).

21. How would you design a URL shortener?

Generate a unique short key (base62/counter/hash), store key → long URL in a KV store, redirect with 301/302, cache hot keys, and handle collisions/analytics asynchronously.

22. How would you design a news feed?

Clarify read/write ratio. Fan-out on write for fast reads but costly for celebrities; fan-out on read for cheap writes but slower reads. Cache timelines and rank asynchronously.
