01Why the question type matters

Most interviews follow the same format — a short prompt and about 45 minutes — but the skills being tested change with the question.

TypeSounds likeMain focus
Product design“Design Twitter,” “Design Uber”Narrow scope, then design the full application end to end
Infrastructure design“Design a rate limiter,” “Design a KV store”Make one shared component efficient and reliable at scale
API / product architecture“Design a comment system”Endpoints, contracts, data model, client interaction
Data processing“Design an ad click aggregator”Process large event streams accurately, including failures
  • Product design: a rate-limiter answer would waste time on “features,” while an Instagram answer without scope would never finish.
  • Infrastructure design: the API is simple; the interview is in distribution, replication, consistency, latency, and failure.
  • API design: scalability still matters, but the contract and data model are the centre of the discussion.
  • Data processing: correctness under late, duplicate, and out-of-order events is the hard part.
Interview line: “Before I design, I’ll confirm what kind of problem this is and where you want the depth.”

02Product design

The most common type: design a user-facing application such as Twitter, Instagram, YouTube, Uber, or Ticketmaster.

  • Start by narrowing scope. These apps have many features; you cannot cover all of them in one interview.
  • Agree on 2–4 core features. Example for Twitter: post tweets, follow users, view the home timeline.
  • Explain the end-to-end flow for each feature: storage, read path, write path, and fan-out.
  • Then go into scale and trade-offs: timeline generation on write vs read; celebrity fan-out; cache strategy.
  • What is tested: prioritization, architecture, component interaction, and the ability to connect features to the system.
Trap: spending 30 minutes on login and profile pages before touching the feed. Scope the core product first.

03Infrastructure design

These questions ask you to build a component that other services depend on: a rate limiter, distributed cache, key-value store, message queue, job scheduler, or unique ID generator.

  • The API is usually simple. A KV store needs get and put; a rate limiter decides allow/reject.
  • Depth is in the internals: data distribution, replication, consistency, failure handling, and tail latency.
  • Availability matters because other services depend on it. If the rate limiter is down, do you fail open or fail closed?
  • Explain the operational cost: coordination, hot keys, rebalancing, and monitoring.
  • Common in senior and infrastructure-focused interviews.
Simple contract→ Distribution→ Replication→ Failure modes→ Latency + availability
Interview line: “The API is small, so I’ll spend the time on how the component behaves at scale and when a node fails.”

04API design and product architecture

These questions focus on how clients interact with the backend: endpoints, request/response formats, data models, and edge cases.

  • Start from user actions: post a comment, reply, fetch comments for an article.
  • Define the contract: method, path, request body, response, status codes, auth.
  • Model the data: entities, relationships, ordering, pagination.
  • Call out client-facing edge cases: nested replies, live updates, duplicate comments, stable pagination.
  • Scalability still matters, but the interviewer is mainly testing API judgment and contract design.
Example: page-number pagination can duplicate or skip comments when new ones arrive; cursor-based pagination with stable ordering avoids that.

05Data processing

These systems collect and process large amounts of data: ad click aggregators, top-K trending videos, monitoring pipelines, and log collection.

  • Decide batch, stream, or both. The choice depends on freshness and correctness requirements.
  • Handle time: windows (per minute/hour), event time vs processing time, and late-arriving events.
  • Handle duplicates: retries and at-least-once delivery are normal; make aggregation idempotent.
  • Name the role of each technology: Kafka for transport, Flink/Spark for processing, storage for query.
  • Correctness is the point: for billing or metrics, a small error can be expensive.
Events→ Queue / log→ Stream or batch→ Aggregates→ Query / dashboard

07The same question can go in different directions

  • “Design Instagram” could focus on the feed, photo upload, search, or notifications.
  • “Design Uber” could focus on location matching, pricing, trip state, or payments.
  • “Design a chat app” could focus on real-time delivery, history, ordering, or multi-device sync.
  • Ask which direction matters; a good answer is not “everything.”
  • State the scope in one sentence so the interviewer can correct you early.
Interview line: “There are several directions we could take this. I’d suggest focusing on X because it drives the most interesting trade-offs. Does that match what you want?”

08Other interview rounds

  • Coding: algorithms and data structures; system design may be a separate round or a follow-up.
  • Behavioral: ownership, conflict, failure, influence; stories should connect to engineering decisions.
  • Deep dives: a focused follow-up on one part of your design — database, cache, consistency, failure.
  • Domain rounds: frontend, infrastructure, data, or ML-specific design.
  • Level expectations differ: a mid-level candidate is not expected to lead a staff-level discussion.

09How to identify the type

  1. Listen to the noun: a product (“Instagram”) vs a component (“rate limiter”) vs an API (“comment system”) vs a pipeline (“click aggregator”).
  2. Clarify the focus: “Do you want the full product, or primarily the API/contract?”
  3. Choose the depth: product → end-to-end; infrastructure → internals; API → contract and data model; data → correctness and time.
  4. State the plan: “I’ll spend five minutes on scope, then go deep on X.”
  5. Adjust if the interviewer redirects. The type is a hypothesis, not a lock-in.
For a 3–5 YOE candidate: you are usually expected to identify the type correctly, scope it, and produce a complete design with clear trade-offs — not to deliver a staff-level multi-team strategy.

✓What to prioritize

  • Product design: scope, core flows, data model, scale, fan-out.
  • Infrastructure design: contract, partitioning, replication, consistency, failure, hot keys.
  • API design: endpoints, payloads, status codes, pagination, idempotency, versioning.
  • Data processing: windows, event time, duplicates, late data, correctness, backfills.
  • All types: requirements, estimates, trade-offs, failure modes, and what you would monitor.

!Traps

  • Approaching every question as a full product design.
  • Scoping too broadly and never finishing a core flow.
  • Diving into database internals before explaining the product.
  • Treating an API question as a scalability question.
  • Ignoring late, duplicate, and out-of-order events in data pipelines.
  • Waiting for the interviewer to tell you the question type.
