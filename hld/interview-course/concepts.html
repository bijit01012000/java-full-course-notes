01How these concepts show up in interviews

Interviewers usually state a requirement or constraint, not a concept name. Your job is to translate the pressure into a component and a trade-off.

Requirement signalConcept to consider
“100,000 reads per second”Caching, read replicas, CDN
“One server is running out of CPU”Vertical or horizontal scaling
“A server failure must not take us down”Load balancer, redundancy, availability zones
“Queries are slow as the table grows”Indexing, query optimization
“Data is too large for one database”Sharding
“Images must load fast worldwide”Object storage + CDN
“The user should not wait for transcoding”Queue + background workers
  • Explain the problem first: what pressure the system is under.
  • Name the mechanism: how the component actually solves it.
  • State the trade-off: what gets worse, what becomes more complex.
  • Say when not to use it: this is what separates a senior answer from a vocabulary list.
Interview line: “I don’t add components because they’re common. I add them when a requirement creates a bottleneck they solve.”

02Scaling

As traffic grows, one machine eventually runs out of CPU, memory, or storage. There are two directions: scale up or scale out.

  • Vertical: simplest, no application changes; limited by hardware, cost, and a single failure domain.
  • Horizontal: add stateless app servers behind a load balancer; move sessions and shared state to a database/cache.
  • Stateless is the enabler: no local session or file; any instance can handle any request.
  • Measure first: scaling the app tier does not help if the database is the bottleneck.
Trap: calling the app tier stateless while keeping sessions on individual servers. That forces sticky routing and makes failover messy.

03Load balancing

With multiple application servers, a load balancer distributes requests, checks health, and removes failed instances from rotation.

  • L4: routes by IP and port; protocol-agnostic and efficient, but cannot inspect HTTP paths or headers.
  • L7: understands HTTP; can route /api and /images differently, terminate TLS, and rewrite headers.
  • Algorithms: round robin for similar servers/requests; least connections when connection lifetimes vary.
  • Health checks: stop sending traffic to unhealthy instances; connection draining finishes in-flight work.
  • The load balancer itself needs HA, or it becomes the new single point of failure.
Interview line: “L4 routes flows; L7 routes requests. If the decision depends on a path or header, I need L7.”

04Availability

Availability is the percentage of time the service is operational. Higher nines cost more infrastructure and operational effort.

AvailabilityDowntime per yearWhat it implies
99.9% — 3 nines≈ 8.8 hoursBasic redundancy and monitoring
99.99% — 4 nines≈ 53 minutesMulti-AZ, automated failover, tested operations
  • Redundancy: run multiple app servers; keep database replicas and a promotion path.
  • Availability zones: physically separate locations within a region; one zone failure should not take down the service.
  • Capacity after failure: if two zones normally share load, the remaining zone must handle the full load or degrade gracefully.
  • SPOF exercise: ask “what happens if this component fails?” for every box and dependency.
Trap: redundancy that shares the same zone, network, or control plane does not protect against that shared failure.

05Caching

A cache stores frequently accessed data in a faster layer. It reduces latency and database load, but introduces freshness risk.

  • Cache-aside: app checks cache; on a hit returns; on a miss reads the database, stores a copy, and returns it.
  • Good fit: read-heavy, not-too-volatile data such as profiles, product details, and popular posts.
  • Invalidate on write: update the database and remove/refresh the cache entry.
  • TTL: let entries expire automatically; simpler, but data can be stale for the TTL window.
  • Cache layers: browser, CDN, application memory, shared cache such as Redis, and database buffer pool.
  • Stampede risk: many simultaneous misses can hammer the database; coordinate or add jitter.
Interview line: “Caching improves latency and database load, but every cache accepts staleness and an invalidation policy.”

06Indexing

Without a suitable index, the database may scan every row. An index is a separate structure that lets it find matching rows efficiently.

Without indexWith index
LookupScan row by rowB-tree lookup → matching row
CostGrows with table sizeGrows logarithmically with index size
Range queryScan and filterIndex range walk
Write costLowerHigher: every write maintains the index
  • B-tree: keeps values sorted; supports equality, range, and ordered queries in a few steps.
  • Composite index: column order matters; a (user_id, created_at) index helps queries that filter on the leftmost columns.
  • Covering index: contains every column a query needs, so the database can avoid a table lookup.
  • Trade-off: indexes cost storage and slow writes; do not index every column.
  • Selectivity: an index on a low-cardinality column may not help; the optimizer may ignore it.
  • In an interview: name the frequent queries first, then the indexes that support them.
Interview line: “I index the access patterns I actually have. Every index makes reads cheaper and writes more expensive.”

07Replication

Replication keeps copies of the same data on multiple machines. It scales reads and provides a failover candidate, but introduces replication lag.

ModeWrite latencyRisk
SynchronousHigher; leader waits for followersWrites may stall or fail if too few followers are available
AsynchronousLower; leader does not waitReplication lag; recent writes may be lost on failover
  • Read scaling: send read traffic to followers, writes to the leader.
  • Failover: promote a follower if the leader fails; requires detection and a safe promotion process.
  • Read-after-write: a user may write to the leader and immediately read a lagging follower; route that read to the leader or wait.
  • Replication does not scale writes — every replica still receives every write.
Trap: promising strong consistency while reading from asynchronous replicas without explaining read-after-write handling.

08Sharding

Sharding splits different data across machines. It scales storage and write capacity, but makes queries and transactions harder.

  • Shard key: decides placement, balance, and which queries are single-shard.
  • Good example: chat messages by conversation ID — one conversation stays on one shard.
  • Bad example: users by country — one country can dominate a single shard.
  • Cross-shard cost: joins, transactions, pagination, and aggregations need coordination.
  • When to shard: only after indexes, caching, and read replicas are insufficient for storage or write throughput.
  • Replication vs sharding: replication copies the same data; sharding partitions different data.
Interview line: “Sharding is the write-scale and data-size tool, not the first read-scale tool.”

09Consistent hashing

Consistent hashing minimizes data movement when shards join or leave the cluster.

  • Modulo problem: hash(key) % N changes almost every mapping when N changes.
  • Ring: hash keys and shards onto a circle; a key belongs to the next shard clockwise.
  • Join/leave: adding a fifth shard moves roughly one-fifth of the keys, not all of them.
  • Virtual nodes: give each physical shard several ring positions to smooth uneven ranges and hot spots.
  • Replication: place copies on the next N distinct physical nodes clockwise.
  • Used by: Cassandra, Dynamo-style stores, distributed caches, and systems with frequent membership changes.
Interview line: “Consistent hashing is about minimizing movement when the cluster changes, not about magic distribution.”

10Object storage and CDNs

Large files belong in object storage, not database rows. Pre-signed URLs keep uploads off the app server; CDNs keep downloads close to users.

  • Object storage: files as objects with a unique key; designed for large blobs, durability, and scale.
  • Metadata: keep owner, size, content type, and object key in the database; keep bytes in object storage.
  • Pre-signed URL: temporary permission to upload to a specific key; bytes never pass through the app server.
  • CDN: caches static/popular content at edge locations closer to users, reducing latency and origin traffic.
  • Cache control: use TTLs, versioned URLs, and purge for changes; personalized content is harder to cache.
  • Trade-off: object storage is not a low-latency transactional store; CDNs can serve stale content.
User requests image→ Nearby edge cache→ Hit: serve/ Miss: origin fetch
Interview line: “Object storage for bytes, database for metadata, pre-signed URL for direct upload, CDN for distance.”

11Asynchronous processing

Not every task must finish before the user gets a response. Slow work can move to a queue and background workers.

Upload video→ Object storage→ Queue job→ Workers transcode→ Update status
  • Decouple: the API responds after storing the upload and enqueuing the job; transcoding happens later.
  • Scale workers independently: video processing can grow without scaling the API tier.
  • Absorb spikes: the queue buffers work when producers are faster than workers.
  • Eventual completion: the user sees “processing,” not an immediate result.
  • Reliability: retries, idempotency, dead-letter queues, and queue-depth monitoring are part of the design.
  • Limit: a queue is not infinite storage; if workers stay behind, latency and storage grow.
Interview line: “Async is a latency decision and a failure decision. I use it when the user doesn’t need the result immediately and the work is safe to retry.”

12Putting it together: URL shortener

A URL shortener is mostly a read problem: 10,000 new links/sec and 1,000,000 redirects/sec is roughly a 100:1 read/write ratio.

RequirementDecision
High read trafficCache popular short codes
Simple key-based lookupKey-value store
Growing trafficStateless app servers + load balancer
High availabilityReplication + failover across AZs
Analytics need not block redirectsQueue/stream + background workers
Interview line: “I start from the read/write ratio and the redirect latency budget, then add only the components those requirements justify.”

13Key takeaways

  • Requirements first: users, QPS, read/write mix, data size, latency, availability, consistency.
  • Components earn their place: each one should solve a named bottleneck or risk.
  • Explain the trade-off: what improves, what gets worse, what becomes operationally harder.
  • Design for failure: identify single points of failure and what happens when they fail.
  • Prefer the simpler design until the requirement clearly demands more.
  • Use numbers for scale, but do not invent precise benchmarks you cannot defend.
The one sentence to remember: “I choose building blocks from requirements, and I defend them with trade-offs — not from a list of popular technologies.”

↔Trade-offs to say out loud

  • Vertical vs horizontal: simplicity and no distributed state vs capacity ceiling and single failure domain; horizontal adds coordination and operational cost.
  • L4 vs L7: protocol-agnostic efficiency vs HTTP-aware routing, TLS termination, and header decisions.
  • Synchronous vs asynchronous replication: durability and consistency vs write latency and availability when followers are slow.
  • Cache invalidation vs TTL: fresher data and more write-path complexity vs simpler operations and bounded staleness.
  • Index: faster reads and range scans vs storage and write amplification.
  • Replication vs sharding: read scale and failover vs write/storage scale; sharding makes cross-shard queries expensive.
  • Object storage + CDN: scalable, cheap delivery vs weaker transactional semantics and possible staleness.
  • Async processing: responsiveness and spike absorption vs eventual completion, duplicates, and operational complexity.

✓Interview checklist

  1. Restate the requirement and the constraint that creates pressure.
  2. Name the concept only after you explain the problem it solves.
  3. Describe the mechanism in one or two sentences.
  4. State the trade-off and the failure mode.
  5. Say what you would monitor or test.
  6. Say when you would not use it.

!Traps

  • Naming a concept before the requirement that justifies it.
  • Sharding before indexes, caching, and read replicas.
  • Caching without an invalidation or TTL policy.
  • Calling a tier stateless while keeping sessions on individual servers.
  • Adding replicas and claiming strong consistency without handling lag.
  • Making the load balancer a single point of failure.
  • Assuming the remaining availability zone has enough capacity after a failure.
  • Adding a queue without idempotency, retries, and a dead-letter path.
  • Forgetting cross-shard queries, joins, and transactions.
  • Using a cache key that omits an input that changes the response.
