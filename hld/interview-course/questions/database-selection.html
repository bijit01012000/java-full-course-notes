SQL vs NoSQL / Choose a Database

The database choice is the hardest design decision to undo, and interviewers want to hear you reason from access patterns and consistency requirements rather than from product reputations.

One-line answerPick the engine whose storage layout matches the hardest access pattern, start with one relational database, and add specialised stores only when a measured workload outgrows it.

01Requirements

Functional
  • Store users, orders, order items, and payments with multi-row atomicity.
  • Serve product detail, category browsing, and ranked text search.
  • Store sessions and carts with fast lookup by a known key and a TTL.
  • Record metrics and events for dashboards with time-window queries and retention.
  • Keep derived copies in sync and make each one rebuildable from the source.
  • Run sales reporting without adding load to the checkout database.
Non-functional
  • Orders and payments need strong consistency and must never lose an acknowledged write.
  • Checkout p99 under 200 ms; catalog reads p99 under 100 ms at 10k reads/s.
  • Search results may lag the catalog by up to 5 s; a just-created product can be briefly missing.
  • Session and cart lookups p99 under 10 ms.
  • Checkout availability 99.99%; a search or analytics outage must not block orders.
  • Every additional engine must be operable by the same small team, with backups, monitoring, and upgrades.
  • 5M users and 1M orders/day is about 12 order writes/s on average and roughly 50/s at peak.
  • Catalog reads are about 10k/s at peak, which is a read-scaling problem rather than a write problem.
  • 100k SKUs at about 5 KB each is about 500 MB of catalog data and roughly 1 GB in the search index.
  • 1M orders/day at about 2 KB each is about 2 GB/day, or roughly 730 GB/year before indexes and replicas.
  • 2M active carts at about 2 KB each is about 4 GB in Redis; 50k metric points/s fits a time-series store with a 7-day raw retention.

04Data modelling

DecisionChoiceWhy
Orders and paymentsPostgreSQL with foreign keys, unique constraints, integer minor units, and an append-only ledgerMulti-row correctness, refunds, and reconciliation need ACID; the write volume is small enough for one primary.
Large order tablesRange-partition by month and archive closed partitionsKeeps the active working set small and makes retention a partition drop instead of a mass delete.
Sessions and cartsRedis hash with a TTL, and a durable order on checkoutReads are by a known key and must be fast; losing an unsubmitted cart is acceptable, losing a placed order is not.
Catalog and attributesPostgreSQL rows with a JSONB column for variable attributesKeeps prices and inventory transactional while avoiding a migration for every new product attribute.
SearchElasticsearch index fed from an outbox or CDC streamAn inverted index provides ranking, stemming, and facets that a B-tree LIKE query cannot; the index stays a derived copy.
Metrics and reportingTime-series database for metrics and a columnar warehouse for sales aggregatesTime-ordered compression and window queries fit metrics, while columnar scans fit reporting without touching the checkout primary.

One transactional core owns orders and catalog, while Redis, search, metrics, and the warehouse are derived stores fed from the primary and kept rebuildable.
  • Start with one well-tuned relational database; JSON columns, full-text search, and extensions cover many early needs before another engine is justified.
  • Choose from the access pattern, consistency need, write volume, schema churn, and team expertise, not from which database is currently popular.
  • Keep the transactional core small: orders, payments, and inventory live together so one local transaction protects the invariant.
  • A search index, cache, and warehouse are derived copies; each needs a propagation path, a reconciliation job, and a full rebuild procedure.
  • Reporting and analytics read from a replica or warehouse, never from the checkout primary during peak traffic.
  • Do not shard until a measured write or storage limit requires it; at 50 order writes/s, one primary is not the bottleneck.

06Optimisation & trade-offs

DecisionGainCost / risk
Relational as the defaultACID transactions, constraints, joins, and mature backup and recoveryWrites are bound to one primary, and schema changes need migrations
Key-value storeSub-millisecond lookup by a known key with native TTLCannot query fields inside the value, and a hot key lands on one node
Document storeWhole-object reads and a flexible schema for evolving payloadsConnected data needs duplication or application-side joins that drift
Wide-column storeVery high write throughput and partition-local range readsQuery-first modelling means a second table for each new access path
Search engineRelevance ranking, stemming, typo tolerance, and facetsIt is a derived copy that lags, must be rebuilt, and adds an engine to operate
Time-series databaseCompression and fast time-window aggregates with automatic retentionHigh-cardinality labels and non-time predicates perform badly
Polyglot persistenceEach workload gets the engine that fits it bestEvery extra store adds deployment, monitoring, backup, upgrades, and a sync path
DenormalizationCheap reads without joinsWrite amplification and duplicated facts that must be kept consistent
  • Verify the top queries with EXPLAIN ANALYZE and add the composite or covering indexes they actually need.
  • Use cursor pagination for catalog and order history instead of OFFSET, which scans and discards rows as the page number grows.
  • Partition orders by month and archive closed partitions to keep indexes shallow.
  • Serve product detail from a cache with delete-on-write invalidation rather than denormalizing the whole catalog.
  • Feed search and the warehouse from an outbox or CDC stream with idempotent consumers and reconciliation counts.
  • Precompute sales aggregates in the warehouse instead of running large GROUP BY queries against live orders.
  • Keep time-series labels low-cardinality; a user ID on every metric destroys the index and compression.

07Follow-ups — one-line answers

SQL or NoSQL first? Start with a relational database unless a measured access pattern clearly needs something else, because transactions, constraints, and ad hoc queries are expensive to add later.
When would you actually choose NoSQL? When the access pattern is known-key lookups at very high volume, append-heavy events, or a rapidly changing document shape, and multi-row transactions are not the hard requirement.
Does NoSQL automatically scale writes? No; many systems still have a single primary or a partition limit, and all of them need a shard key, hot-partition handling, and operational work.
How do you choose a shard key? It should spread writes evenly and keep data that is read together on one shard; hash a high-cardinality entity ID and avoid timestamps and auto-increment columns.
Why is the search index not the source of truth? It is a denormalised index optimised for ranking, it lags the primary, and it can be rebuilt; using it as the source loses transactional guarantees.
How do you keep search in sync? Write an outbox row in the same transaction as the catalog change, relay it to the index with an idempotent consumer, and reconcile counts and checksums periodically.
Can Redis hold carts durably? It can hold the active cart with a TTL, but on checkout the cart must be persisted to the transactional database before the order is confirmed.
Why a time-series database instead of a relational table? Append-only timestamped data compresses well in time order, and the access pattern is window aggregates with retention, which a row-store primary handles poorly.
When is a graph database worth it? When variable-depth relationship traversal is central, such as fraud rings or friends-of-friends; for one-hop lookups and bulk scans a relational store is simpler.
When is polyglot persistence a mistake? When it is adopted before a workload needs it, because every additional engine multiplies operational cost and adds another copy of the data that can drift.
How do you run reporting without hurting checkout? Send reads to a replica or a warehouse and precompute aggregates; never run large analytical scans on the primary during peak order traffic.
What would you monitor across these stores? Replication lag, slow queries and index bloat, search-index lag and mismatch rate, cache hit ratio, shard skew, and the age of the oldest unreconciled copy.

08Traps

  • Choosing a database from its reputation instead of the queries it must serve.
  • Assuming NoSQL always scales writes and skipping the shard-key and hot-partition work.
  • Using a search engine or vector index as the authoritative store.
  • Putting a high-cardinality label such as user_id on every time-series metric.
  • Forgetting that every copied fact needs a sync path, a reconciliation check, and a rebuild plan.
  • Storing money as a floating-point value instead of integer minor units.
