API Pagination and Versioning

Pagination and versioning are where API design meets database behaviour and long-lived clients. Interviewers test whether you can keep a page stable under writes, avoid deep-offset scans, and evolve a contract without breaking callers.

01Requirements

Functional
  • List resources with a bounded page size and an opaque cursor for the next page.
  • Keep ordering stable when rows are inserted, updated, or deleted between requests.
  • Allow filtering and a small set of approved sort orders, with the filters preserved across pages.
  • Expose a major API version and let old and new clients call concurrently.
  • Signal deprecation and sunset dates in responses and documentation.
  • Support deep exports without holding a database transaction open.
Non-functional
  • A page request stays within the read latency budget regardless of how deep the cursor is.
  • A client walking pages sees no duplicates or skipped rows under normal concurrent writes.
  • Cursors are opaque, tamper-evident, and expiring, so a client cannot forge another tenant's position.
  • A new minor release is backward compatible; a breaking change requires a new major version.
  • At most two major versions are supported at once, with a defined deprecation window.
  • Reads are idempotent and safe to retry, and page tokens do not leak internal SQL or primary keys.
  • Assume 50M orders and a page size of 50: one million pages if a client walks the whole set, so cursor cost matters.
  • An offset of 500,000 makes the database scan and discard 500,000 rows before returning 50, so deep offset cost grows with depth.
  • Assume 2k list requests/s at peak; a 50 ms p95 budget leaves little room for a COUNT star on every page.
  • Keep the default page at 25 to 50 items and cap limit at 100 so one client cannot request a 10k-row page.
  • Support at most two or three major versions; each extra version multiplies test, documentation, and on-call surface.
  • A six-to-twelve-month deprecation window is common for public APIs; internal APIs can move faster with coordinated clients.

A version router sends each major version to its own handler, both handlers share a signed keyset cursor codec, and telemetry on the deprecation registry shows which clients still need migration.
  • Paginate in the database, not in the application: fetch limit plus one row to learn whether a next page exists.
  • The cursor must encode every input that changes the result set, including filters and sort direction, or page two can silently use different rules.
  • Never expose raw primary keys or SQL offsets as the cursor; sign the payload and bind it to the tenant.
  • Version the contract, not the implementation: a new database column does not require a new API version if the response stays compatible.
  • Deprecation is an operational process: announce, measure, migrate, then remove, with a named owner and a date.

06Optimisation & trade-offs

DecisionGainCost / risk
Keyset pagination instead of offsetConstant cost with depth and stable pages when rows are inserted.No random jump to page N, and the cursor must encode the sort and filters.
Return total count with every pageThe UI can show a total and a page count.An expensive COUNT on every large filtered request.
Path versioningVisible, cache-friendly, and easy to route at the gateway.URL churn and duplicated routes for each major version.
Header versioningCleaner URLs and content negotiation.Easier for clients to omit and harder to test, share, and route.
Long deprecation windowClient goodwill and time for coordinated migrations.Parallel maintenance, duplicated tests, and a larger security surface.
Opaque signed cursorTamper resistance and freedom to change the internal query shape.Harder debugging and a server-side codec on every page request.
Snapshot export for full scansA consistent copy without millions of interactive page calls.Storage, job infrastructure, and data that is already stale when it finishes.
  • Fetch limit plus one row and drop the extra row instead of running a separate count.
  • Match the index to the exact WHERE and ORDER BY so a cursor seek is a range scan.
  • Return only the fields the list screen needs and move heavy detail to the single-resource endpoint.
  • Cache the first page of popular filters for a short TTL and bypass the cache for deep cursors.
  • Use ETag and If-None-Match for unchanged pages and conditional single-resource reads.
  • Use an asynchronous export job for full scans instead of walking millions of pages synchronously.
  • Emit a per-version request metric and a Sunset header so migration progress is visible.
  • Cap limit, cursor age, and pages per client to protect the database from abusive walks.

07Follow-ups — one-line answers

Why not use offset pagination? A deep offset scans and discards every skipped row, and concurrent inserts or deletes shift rows across page boundaries.
How do you prevent duplicates and skips? Seek on a stable sort key plus a unique tiebreaker, so each page starts after an exact position rather than a row count.
How do you encode the cursor? As an opaque, signed payload containing the sort key, id, direction, filter hash, tenant, and issue time.
How do you support multi-column sorting? Include every sort column plus a unique id in the cursor and create a composite index matching that order.
Can the client jump to page 100? Not with keyset pagination; offer filters or search, use offset for small bounded sets, or provide an export for deep scans.
How do you return a total count? Omit it by default and return an approximate or cached count only when the product needs it, never on every request.
Path versus header versioning? Path versions are explicit and cache-friendly for public APIs, while header versions keep URLs clean but are easier to omit and harder to route.
What counts as a breaking change? Removing or renaming a field, changing a type, tightening validation, or changing status-code semantics breaks existing clients.
How do you deprecate an API version safely? Announce a sunset date, add Deprecation and Sunset headers, measure per-version usage, migrate clients, then remove the version.
How do you test backward compatibility? Run contract tests against the published schema and replay recorded client requests in CI for every supported major version.
Should cursors expire? Yes, a short TTL bounds stale snapshots and the damage from a leaked token, and an expired cursor returns 400 with a restart hint.
How do you export the full dataset? Use a point-in-time snapshot or an asynchronous export job rather than millions of sequential page calls.

08Traps

  • Using a large OFFSET and calling it scalable because the first page is fast.
  • Building the next cursor from the last row without a unique tiebreaker, so rows duplicate or vanish.
  • Letting the client send a sort or filter that is not encoded in the cursor, so page two silently changes shape.
  • Running COUNT star on every list request over a large filtered table.
  • Calling a field rename a minor change and breaking clients without a new major version.
  • Keeping five major versions alive with no owner, telemetry, or sunset date.
