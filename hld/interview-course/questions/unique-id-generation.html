Generate Unique IDs

It tests whether you can reason about coordination, clock behaviour, and the storage consequences of an ID format, not just recite Snowflake.

One-line answerGenerate IDs locally from a timestamp, worker, and sequence layout, lease worker identities, and keep a separate random public identifier when enumeration matters.

01Requirements

Functional
  • Generate globally unique 64-bit IDs at high throughput.
  • Support batch generation for bulk inserts and imports.
  • Keep IDs roughly ordered by creation time for pagination and index locality.
  • Expose an opaque public identifier for URLs and APIs.
  • Assign and reclaim worker identities across restarts and autoscaling.
  • Provide a migration path from existing sequential IDs.
Non-functional
  • No network hop per ID; local generation under about 1 ms p99.
  • Unique across services, regions, restarts, and retries.
  • Available when the central allocator is briefly unreachable.
  • Monotonic per worker; never reuse a timestamp and sequence pair.
  • Compact enough to be a primary key in every secondary index.
  • Recover safely from clock skew and rollback.
  • Assume 20k IDs/s average and 100k/s peak across all writers.
  • A 41-bit millisecond timestamp with a custom epoch lasts about 69 years.
  • 10 worker bits allow 1024 live generators; 12 sequence bits allow 4096 IDs per ms per worker.
  • A 64-bit ID as BIGINT is 8 B, versus 16 B for raw UUID bytes or 36 B as text.
  • Segments of 10k IDs keep allocator calls to a handful per minute per node at typical rates.
  • At 100k IDs/s the 64-bit space is not the limit; worker-ID space and clock discipline are.

Generators issue IDs locally from clock, worker, and sequence state, while the allocator and lease registry supply durable ranges and unique worker identities.
  • Generation is in-process; the only coordination is worker identity and occasional range allocation.
  • Worker IDs are leased, not configured, so a cloned instance cannot keep the same identity.
  • A node with a cached range keeps serving through a short allocator outage.
  • The timestamp gives ordering, the worker bits prevent collisions, and the sequence handles same-millisecond bursts.
  • When the sequence overflows, spin to the next millisecond; never reset the sequence against an old timestamp.
  • Internal IDs stay compact; public IDs are separate and every read still enforces authorization.
  • Retries reuse the ID generated for the logical operation rather than minting a second record.
  • Regions get disjoint worker-ID slices so one registry outage does not block another region.

06Optimisation & trade-offs

DecisionGainCost / risk
Auto-incrementCompact, ordered, and trivially simple on one databaseSingle writer bottleneck, cross-shard collisions, and enumerable values

Snowflake-style 64-bit IDCompact, time-sortable, and local generationRequires unique worker IDs and disciplined clocks

Separate random public IDResists enumeration and scrapingAn extra mapping and lookup on public reads
Larger random identifiersStronger unguessabilityMore storage in every primary and foreign key
  • Batch ID allocation for bulk inserts instead of one call per row.
  • Keep generation in-process to avoid a network hop on the write path.
  • Use time-ordered 64-bit keys so inserts stay near the end of the index.
  • Preallocate ranges sized for a few minutes of traffic rather than one ID per call.
  • Monitor clock offset continuously and alert before rollback becomes a duplicate risk.
  • Shard application tables by an entity key unless the ID deliberately embeds the shard.
  • Cache the worker lease locally and renew well before expiry.
  • Use a public-ID mapping only where an opaque identifier is required.

07Follow-ups — one-line answers

Why does auto-increment break in a distributed system? It depends on one database writer, so it becomes a throughput bottleneck and a single point of failure, and independent databases each start their own sequence and collide.
How do UUIDs guarantee uniqueness without coordination? They draw from a very large random or time-plus-random space, making collisions negligibly unlikely, so any node can generate one offline.
What is the downside of a random UUID primary key? Random inserts scatter across the B-tree, causing page splits and write amplification, and the 128-bit width makes every index larger.
Explain a Snowflake ID. It packs a timestamp, a worker identifier, and a per-tick sequence into 64 bits, so each worker generates locally, time orders the result, and the worker bits prevent collisions.
What happens if the clock moves backwards? Wait for small drift, refuse to issue and alert for large drift, and never reuse an old timestamp with a reset sequence.
How do you assign worker IDs? Lease a unique ID from a registry such as etcd or ZooKeeper with a TTL and fencing epoch, and reclaim it only after the old lease has expired.
How does a segment allocator work? A central service durably reserves a disjoint block of IDs for a node, the node issues locally until the block is exhausted, and then requests another.
When would you choose ULID over UUID v4? When you want local generation plus lexical time ordering for pagination and recent-first queries, accepting a larger text form and the same clock concerns.
How do IDs affect sharding? An ID can embed a shard or region for explicit routing, or stay independent and be mapped through a directory; embedding simplifies routing but makes rebalancing harder.
How do you expose IDs safely in a public API? Use random or signed public identifiers and enforce authorization on every request, because secrecy alone is not access control.
How would you migrate from sequential IDs? Add the new column, backfill in batches, dual-write, update foreign keys and caches, switch reads, then retire the old column while keeping a rollback path.
What would you monitor? Generation rate and latency, duplicate-key errors, clock offset and rollback events, worker-lease conflicts, range exhaustion, and allocator availability.

08Traps

  • Assuming a UUID is automatically a good primary key without considering index locality.
  • Letting two nodes share a worker ID after cloning or autoscaling.
  • Ignoring clock rollback and reusing an old timestamp with a reset sequence.
  • Using sequential IDs in public URLs and treating unguessability as authorization.
  • Making every ID a string because it is convenient, then paying for it in every index.
  • Choosing a scheme without a migration plan for existing primary and foreign keys.
