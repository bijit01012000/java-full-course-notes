Caching and Cache Consistency

Every cache buys latency with a second copy of the truth, and interviewers probe whether you can name the staleness window, the invalidation path, and the failure mode instead of just saying add Redis.

One-line answerUse cache-aside for reads, delete after commit plus a TTL for writes, and propagate invalidation as an event so every copy converges without treating the cache as the source of truth.

01Requirements

Functional
  • Serve reads through cache-aside with a per-key TTL and a database fallback.
  • Commit writes to the database and invalidate the affected cache entries.
  • Propagate invalidation to every application instance, including local caches.
  • Guarantee read-your-writes for the user who just wrote.
  • Support an operator purge for a key, a prefix, or a bulk correction.
  • Expose hit ratio, miss latency, evictions, and invalidation lag per key family.
Non-functional
  • p99 under 20 ms for a cache hit and under 200 ms for a miss that reaches the database.
  • 99.95% read availability; losing the cache degrades latency, not correctness.
  • Staleness budgets: catalog 60 s, stock 5 s, checkout price and balance 0 s.
  • No stale value survives longer than its TTL even if an invalidation is lost.
  • Invalidation propagation p99 under 1 s across all app instances.
  • Cache memory is bounded by bytes and every key has an expiry.
  • Assume 100k reads/s peak and 1k writes/s, so invalidation volume is modest compared with read volume.
  • 10M cached objects at about 2 KB each is about 20 GB of values before overhead.
  • At a 95% hit ratio, 5,000 reads/s reach the database; at 99%, only 1,000 reads/s do.
  • A 60 s TTL means an untouched key can be stale for up to 60 s and on average about 30 s.
  • One invalidation message per write, broadcast to 20 app instances, is about 20k small messages/s at peak.

Read strategyCache-aside with a database fallback and a per-key TTLIt works with plain Redis, caches only data that is actually read, and still serves reads if the cache is unavailable.

Reads fall through local cache, Redis, then the database, while writes commit once and invalidate every copy through an outbox and broadcast bus.
  • The database is the source of truth and the cache is derived data; losing the cache must cost latency, never correctness.
  • The write path is one database transaction that also writes an outbox row, so the state change and the intent to invalidate commit atomically.
  • Delete rather than update the cache on writes, because concurrent writers can otherwise finish in the reverse order and leave an old value cached.
  • Invalidation must reach local in-process caches too; a shared Redis delete alone leaves per-instance copies stale.
  • Every key has a TTL even when explicit invalidation exists, so a lost event becomes bounded staleness rather than permanent divergence.
  • Read-your-writes is a per-request guarantee: pin the writer to the primary briefly or wait for a version watermark, not for every reader.

06Optimisation & trade-offs

DecisionGainCost / risk
Cache-asideSimple, works with any key-value store, and falls back to the database when the cache is downThe application owns misses and invalidation, and the first read of each key is slower
Delete on write instead of updateAvoids the write-order race that leaves an older value in the cacheThe next read pays a miss and must repopulate the entry
Short TTLBounds staleness and recovers automatically from missed invalidationsMore misses and more load on the database
Write-throughCache and database stay fresh for the next readEvery write still waits for the database, and the cache can fill with rarely read values
Write-behindVery fast writes and natural batchingAn acknowledged write can be lost before it reaches durable storage, so it is unsuitable for payments or orders
Local in-process cacheLowest possible latency and no network hopPer-instance copies that must be invalidated separately and can diverge briefly
Event-based invalidationOne committed change reaches every service and instance that caches the factQueue lag, at-least-once duplicates, and another pipeline to operate and monitor
Strong read-your-writesThe writer never sees a stale value after a successful updatePushes some reads back to the primary and reduces the benefit of read scaling
  • Cache only data that is read often, changes slowly, and tolerates a stated staleness window.
  • Add 10% jitter to TTLs so keys cached together do not expire in a single wave.
  • Use single-flight or a short refresh lock on misses to protect the database from a hot-key stampede.
  • Refresh popular entries in the background before they expire, while serving the current value.
  • Keep a very short-TTL local cache for the hottest keys, and invalidate it from the broadcast bus.
  • Pipeline Redis calls and cap value size; compress large objects or split them into smaller keys.
  • Negative-cache missing keys briefly and clear that entry when a create commits.
  • Track hit ratio per route rather than in aggregate, because a high overall ratio can hide one path that always misses.

07Follow-ups — one-line answers

Why not update the cache with the new value after a write? Two concurrent writers can reach the database and cache in opposite orders, leaving the older value cached; deleting forces the next read to load the authoritative value.
Should you delete before or after the database commit? After the commit, because deleting before opens a window in which a concurrent read can repopulate the cache with the old value.
What if the cache delete fails? Retry it from the outbox relay and rely on the TTL as a backstop, so the worst case is bounded staleness rather than permanent divergence.
Can the cache be the source of truth? No; it is a derived copy that must be rebuildable from the database, and treating it as authoritative turns an eviction into data loss.
How do you give a user read-your-writes? Pin that user's reads to the primary for a short window after a write, or return a version watermark and wait until the cache or replica has reached it.
What is a cache stampede and how do you stop it? A popular key expires and every concurrent request misses at once; a per-key lock or single-flight lets one request rebuild while the others wait or receive stale data.
How do you handle a hot key? Keep a short-TTL local copy and replicate the key under suffixed names that hash to different cache nodes, deleting all copies on write.
Is negative caching safe? It is safe with a short TTL and an explicit invalidation on create, otherwise a newly created item can appear missing for the length of the TTL.
Write-through or cache-aside? Cache-aside is the default for read-heavy data; write-through is worth it only when recently written values are read again immediately and every writer goes through the cache.
When is write-behind acceptable? Only for high-volume, low-value data with a durable pending-write buffer, never for payments, orders, balances, or audit records.
How long should a TTL be? As long as the feature's staleness budget allows and no longer; derive it from how fast the data changes and how bad an old value is, then add jitter.
What should you monitor? Hit ratio per route, miss latency, eviction rate, memory and key size, invalidation lag, duplicate invalidations, and user reports of stale reads.

08Traps

  • Updating the cache before the database commit and calling the pair consistent.
  • Relying on invalidation alone with no TTL, so one lost event leaves data stale forever.
  • Caching user-specific data under a shared key or at the CDN.
  • Treating the cache as the source of truth and being unable to rebuild it.
  • Using write-behind for payments or orders where an acknowledged write must never be lost.
  • Invalidating only Redis and forgetting the local caches on each application instance.
