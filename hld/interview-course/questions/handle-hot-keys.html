Handle Hot Keys

Interviewers ask it to see whether you can tell a per-key concentration problem from a general capacity problem, and whether you know that adding nodes never splits a single key.

One-line answerA hot key saturates one node while the rest of the fleet is idle, so spread reads with a local cache and N key copies, spread writes with split counters, and protect the origin with coalescing, negative caching, and a per-key limit.

01Requirements

Functional
  • Detect which keys receive a disproportionate share of reads or writes.
  • Serve a viral read key without saturating the one node that owns it.
  • Accept write-heavy updates to one logical counter or inventory row.
  • Invalidate or refresh every copy when the underlying value changes.
  • Degrade to a cached or stale value instead of failing all requests for that key.
  • Apply per-key policy: copy count, TTL, and request ceiling.
Non-functional
  • Hot-key reads stay at cache latency; no request fans out to more than a bounded number of copies.
  • No single cache node, shard, or queue partition stays above roughly 70 to 80 percent utilisation because of one key.
  • Staleness is stated per data type: seconds for counters, minutes for descriptions.
  • Invalidation completes in bounded time, and any missed copy still expires by TTL.
  • Detection uses per-key and per-node metrics, not service-wide averages.
  • The mitigation must be reversible and measurable; skew should visibly move after the change.
  • Assume a viral item gets 1M reads per second while one cache node safely serves about 100k ops per second, so the key needs roughly 10 copies or a per-instance local cache.
  • Assume a top item's like counter takes 200k writes per second; one row absorbs about 2k writes per second, so split it into roughly 100 sub-counters.
  • A local cache holding the top 1,000 keys at about 2 KB each is roughly 2 MB per application instance, which is cheap next to the traffic it removes.
  • With N = 10 key copies, every write becomes 10 invalidation messages, so a 2k writes-per-second hot value produces 20k invalidations per second at peak.

Reads are absorbed by the per-instance L1 cache and the N shared-cache copies; writes go to split sub-counters, and every write fans out an invalidation to all copies.
  • Start with detection: the signature is one node or shard saturated while its peers are nearly idle, plus a hot-to-median request ratio that jumps.
  • Split the remedy by direction. Reads get a local cache, then key copies; writes get split counters, then batching or aggregation.
  • The invalidation path is the real cost of replication: every copy must be updated or deleted, and a missed copy serves stale data until its TTL fires.
  • Distinguish a hot key from a hot shard. A hot key is one record; a hot shard is usually a bad partition key such as a timestamp or a tenant id.
  • Protect the origin as well as the cache: single-flight on a miss, TTL jitter, negative caching, and a per-key QPS ceiling.
  • Keep the copy and sub-counter counts stable. Changing them later requires reconciling totals or draining old copies.

06Optimisation & trade-offs

DecisionGainCost / risk
Local in-process cacheLowest possible read latency and near-zero shared-cache traffic for the hot keyPer-instance copies that cannot be purged precisely; staleness is bounded only by the TTL
Key replication (N copies)Spreads reads across N cache nodes without changing the read APIStorage multiplies by N and every write must invalidate all N copies
Request coalescingOne origin read per key per miss instead of a stampedeRequests that lose the race wait for the leader, adding tail latency
Split countersRestores write parallelism on one logical aggregateReads become a sum of N values, and exact reconciliation is harder
Aggregating writesLarge reduction in write volume for counters and viewsDelayed visibility and possible loss of the last few seconds of updates
Per-key rate limitingStops one key from starving the rest of the serviceRejects or delays legitimate users during a genuine surge
Bounded local cache with short TTLPredictable memory use and fast expiry of stale dataMore origin reads than an unbounded cache, and visible staleness for a few seconds
  • Add a small in-process LRU cache for the top keys so most reads never leave the application process.
  • Replicate a read-hot key into N suffixed copies and choose one per request with a cheap local random pick.
  • Coalesce misses per key with a single-flight lock, so an expiry triggers one rebuild instead of thousands.
  • Refresh ahead: keep serving the previous value while one background worker rebuilds it.
  • Split a write-hot counter into N sub-counters and cache the summed total for a short window.
  • Buffer increments in a stream processor and write one aggregated delta per interval when per-event detail is not needed.
  • Set a per-key QPS ceiling with priority so a viral key cannot consume the capacity of everything else.
  • Negative-cache missing keys briefly and add TTL jitter to every related key.

07Follow-ups — one-line answers

Why does adding cache nodes not fix a hot key? A distributed cache maps each key to exactly one node, so extra nodes spread the other keys and leave the hot one where it was.
How do you tell a read-hot key from a write-hot key? Compare per-key read and write rates and the latency of the owning node: reads saturate CPU and network on the cache, writes serialise on one row or partition.
How do you invalidate N copies? Publish one invalidation per copy with a version, delete or overwrite all of them, and rely on a short TTL to clean up any copy that was missed.
What TTL would you set on the local cache? One to five seconds for values that must feel fresh, with a documented staleness budget; longer only for data that rarely changes.
How do you pick the number of copies or sub-counters? From the per-key load divided by what one node or row can safely handle, not from total system traffic, and then keep the number stable.
What is a cache stampede and how do you stop it? Many simultaneous misses for the same expired key; a per-key single-flight lock, background refresh, and TTL jitter prevent it.
Hot key versus hot shard? A hot key is one record with extreme traffic, while a hot shard is a partition receiving too much traffic, often from a bad partition key, and they need different fixes.
When is the partition key itself the bug? When skew comes from a monotonic key such as a timestamp or an auto-increment id that sends all new writes to the newest partition; fix the key instead of masking it.
What do you monitor after applying a fix? Per-key request rate and p99, per-node and per-shard load, cache hit ratio, invalidation failures, and the hot-to-median skew ratio.
Can you serve stale data during an incident? Yes for descriptions and counters if you state the window and label the response; never for inventory, prices, or anything that must be exact.
How do you protect against requests for keys that do not exist? Negative-cache the not-found result for a short time so invented or deleted keys cannot reach the origin repeatedly.
What is the hidden cost of split counters? Every read becomes an aggregation and changing the shard count later forces a reconciliation of old and new totals, so the count must be chosen deliberately.

08Traps

  • Answering a viral post with more cache servers or shards instead of splitting or replicating the key.
  • Replicating a key but invalidating only one copy on write, so readers see stale values until TTL.
  • Using a local cache with a long TTL and serving visibly stale data to everyone on one instance.
  • Splitting a counter into sub-counters and then reading only one of them.
  • Sharding time-series data by timestamp, creating a hot partition and calling it a traffic spike.
  • Applying a mitigation without per-key metrics, so you cannot prove the skew moved rather than moved elsewhere.
