Design Ticket Booking

It is the canonical concurrency question: the interviewer wants to see you protect a scarce unit of inventory from double booking without holding database locks during payment.

One-line answerModel every seat as a row, claim it with one conditional update inside a short transaction, hold it with a database-enforced expiry, and confirm the booking only after an idempotent payment.

01Requirements

Functional
  • Users can browse events, view a seat map or availability, and select one or more seats.
  • A selected seat is held for a short window, for example 5-10 minutes, while the user pays.
  • A successful payment confirms the booking; an expired or cancelled hold releases the seats.
  • Users can cancel a confirmed booking and receive a refund according to policy.
  • Retries of hold, booking, and payment requests must be idempotent.
  • A flash sale must admit users through a waiting room rather than letting everyone hit the inventory database.
Non-functional
  • One seat has at most one active owner at any instant; a second confirmed booking for the same seat is a data-integrity incident.
  • The claim path is strongly consistent and must read from the primary, never a stale replica.
  • Browsing can tolerate a few seconds of staleness, but the checkout decision cannot.
  • Hold, booking, and payment transitions must survive crashes and ambiguous timeouts.
  • Support a popular event with tens of thousands of seats and hundreds of thousands of waiting users.
  • Every state change is auditable: who held, who paid, when it expired, and who released it.
  • Assume a popular event has 50k seats and 200k users waiting at sale start, with a burst of 20k claim attempts per second.
  • A 5-minute hold means a user who abandons checkout strands seats for 5 minutes unless a sweeper releases them promptly.
  • One row per seat for a 50k-seat event is small; the bottleneck is contention on the same rows, not storage.
  • At 20k attempts per second, most requests must be rejected by the waiting room before they reach the primary; the database can only serialize a much smaller claim rate.
  • A 10 percent conversion from waiting users to buyers still means 20k bookings and roughly 40k ledger or payment records for one event.

03API design

04Data modelling

DecisionChoiceWhy
Inventory model and atomic claimOne row per seat per event keyed by (event_id, seat_id); claim every requested seat in one transaction with a conditional update from available to held and a check that the affected row count equals the number of seats.A counter cannot identify an owner, and the conditional update makes the database the single point of serialization so only one claim can win; checking the row count keeps a partial multi-seat claim from committing.
Hold expiryStore expires_at in the database and enforce it in the confirm query; a background sweeper releases expired holds.A client-side timer cannot be trusted after a crash, and a lock held for the whole payment window would block every other buyer.
Booking idempotencyUnique idempotency_key on the booking request and a unique hold_id on the booking, so one hold produces at most one booking.A timeout followed by a retry is the normal mobile case; both constraints make the second request return the original result instead of double-selling.
Payment boundaryCreate a pending booking, call the payment provider outside the database transaction, then confirm the booking with a conditional state update.Holding a database transaction open across a network call destroys throughput; a pending state plus an idempotent confirm handles the ambiguous outcome.
Seat map read modelA Redis or CDN-backed seat map refreshed from inventory change events, with a short TTL and a clear 'availability may change' label.Millions of browsers should not query the primary for a picture of the venue; the authoritative check still happens on claim.
ShardingShard inventory, holds, and bookings by event_id so all seats and their claims for one event live on one shard and can be changed transactionally.Splitting one event's seats across shards destroys the single-transaction guarantee, while different events scale independently.

05Architecture

The waiting room and seat-map cache absorb browsing traffic; only the booking service touches the event's inventory shard, claiming seats and writing the hold in one transaction and confirming after an idempotent payment.
  • State the invariant first: one seat has at most one active owner. Everything else in the design exists to enforce or recover that invariant.
  • A pre-check read is advisory. The claim must be a conditional write such as status = 'available' to 'held' with a row-count check, because two users can read 'available' at the same time.
  • Claim all requested seats in one transaction. If any seat update affects zero rows, roll back the whole claim and tell the user which seat was taken; a partial hold is worse than a clean rejection.
  • Sort seat ids before updating them so two concurrent multi-seat claims acquire rows in the same order; inconsistent lock ordering is a common source of deadlocks on this table.
  • Keep the claim transaction short: update seat rows and insert the hold, then commit. Never call the payment provider while the transaction or a row lock is open.
  • Confirm with a conditional update that checks hold ownership, hold status, and expires_at in the same statement. If the hold expired while payment was in flight, do not confirm; refund or void the payment instead.
  • Model booking states explicitly: pending_payment, confirmed, cancelled, refunded. Every transition is conditional on the current state, so a duplicate webhook cannot move a cancelled booking back to confirmed.
  • Run a sweeper on an indexed expires_at column, using SKIP LOCKED or small batches so it does not contend with live claims. It must release seats only when the hold is still active.
  • Admission control is part of correctness at scale: a waiting-room token bounds how many users can attempt a claim, so the primary sees a rate it can actually serialize.

06Optimisation & trade-offs

DecisionGainCost / risk
Conditional update instead of SELECT FOR UPDATENo long-held row locks, a clear conflict signal from the affected row count, and good throughput when contention is spread across seats.Under extreme contention on one seat, many attempts fail and retry, so retries must be bounded and jittered.
Pessimistic row locksSimple to reason about and prevents any other writer from slipping between the check and the update.Locks are held for the transaction duration, and a slow query or a lock ordering mistake causes waits and deadlocks.
Database holds with TTLDurable, auditable, and enforceable in the same transaction as the claim; a crash cannot leave a seat held forever.Every hold is a write and a sweeper burden, and the database must handle the hold lifecycle in addition to the sale.
Redis hold locksVery fast claims and automatic TTL expiry, which absorbs a flash crowd without touching the primary.A lock is not the inventory record; a lease can expire while the holder still acts, so correctness needs fencing or a database confirmation.
Waiting roomBounds concurrency to what the inventory shard can serve and gives users a fair, predictable queue instead of random errors.Extra infrastructure and a worse experience for users who must wait; tokens must be signed and rate-limited to prevent bypass.
Cached seat mapFast browsing for a huge audience and far less read load on the primary.The map can show a seat as free that was just taken, so the UI must treat the claim response as the source of truth.
Async payment confirmationCheckout does not hold a database transaction or an HTTP connection across a slow provider call.The user sees a pending state, and the system must handle payment success after hold expiry and webhook duplication.
Deliberate overbookingSelling more than capacity can protect revenue against cancellations and no-shows, and it is a normal airline or hotel policy.It must be an explicit business rule with a compensation plan, never an accident caused by a race, and it needs inventory headroom the venue can actually honor.
  • Cache the seat map and venue metadata, and invalidate by event on hold, release, or booking events; never use the cache for the final claim.
  • Shard by event_id and route all requests for one event to the same inventory shard, so claims stay transactional and unrelated events do not interfere.
  • Use short holds with a clear countdown, and release aggressively when the user navigates away; abandoned holds are the main source of recoverable inventory.
  • Batch the expiry sweep and run it frequently, so stranded seats return to sale within seconds rather than minutes.
  • Precompute price tiers and fees per seat so checkout does not recalculate a complex pricing model under lock.
  • Use a virtual waiting room with a signed, time-limited token and a bounded admission rate; reject obviously impossible requests before they reach the database.
  • Keep payment confirmation asynchronous via webhook, and let the client poll a booking status endpoint instead of holding an HTTP request open.
  • Add per-user purchase limits and a bot check at admission, so one script cannot claim the whole front row.

07Follow-ups — one-line answers

How do you stop two users booking the same seat? Make the claim a conditional update from available to held with a check on the affected row count, so the database decides a single winner.
What if the hold expires while the user is paying? The confirm statement requires expires_at in the future, so confirmation fails and the payment is voided or refunded rather than overselling the seat.
What if payment succeeds after the hold expired? Do not confirm the seat; record the payment, attempt to reacquire the same seat, and otherwise refund automatically and notify the user.
How do you make retries safe? Require an idempotency key on hold and booking requests, enforce uniqueness, and return the original hold or booking when the same key arrives again.
Why not use only a Redis distributed lock? A lease can expire while the holder is still working, so a Redis lock alone cannot guarantee one owner; the database row and its conditional update remain the authority.
How do you scale a hot event? Shard by event, admit through a waiting room at a rate the shard can serialize, reject impossible requests early, and keep browsing on a cache.
How stale can the seat map be? A few seconds is fine for browsing, but the claim always reads the primary and the UI must treat 'seat taken' as a normal response.
How do cancellations release inventory? A conditional transition from confirmed to cancelled frees the seat and records the refund; if the refund fails, a compensation retries it rather than silently reselling.
What if the payment webhook arrives twice? Deduplicate by provider event id and make the booking transition conditional on the current state, so the second delivery is a no-op.
What if the service crashes after charging but before confirming? The booking stays pending, a reconciliation job compares provider payments with bookings, and the confirm step is retried idempotently.
How do you claim four adjacent seats atomically? Update all four rows in one transaction with the same hold_id and commit only if all four updates report success.
How does the waiting room actually work? Users receive a signed, time-limited token at a controlled rate, and the booking endpoint rejects requests without a currently valid token.

08Traps

  • Checking availability with a SELECT and then updating in a separate statement, which leaves a race where both users believe they won.
  • Holding a database transaction or row lock open while the user completes payment, which blocks other buyers and exhausts the connection pool.
  • Using a single remaining-seat counter for assigned seating, which cannot enforce that a specific seat has one owner.
  • Relying on a client-side timer or a Redis TTL alone to expire holds, so a crashed client can strand inventory or a stale lock can be bypassed.
  • Trusting a read replica or a cached seat map for the final claim, which turns a stale read into a double booking.
  • Treating a payment timeout as a failure and retrying the charge without an idempotency key, which produces a duplicate charge.
