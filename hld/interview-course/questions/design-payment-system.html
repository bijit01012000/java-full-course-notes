Design a Payment System

Money makes every ordinary distributed-systems problem visible: ambiguous timeouts, duplicate requests, partial failure, and the need for an audit trail that can survive an argument with a customer or a regulator.

One-line answerModel each payment as an explicit state machine, make every mutation idempotent with a client key, record value movements in an append-only double-entry ledger, and reconcile against the provider's settlement report.

01Requirements

Functional
  • Create a payment for an order with an amount, currency, merchant, and customer reference.
  • Authorize and capture funds through an external payment service provider, with support for immediate capture.
  • Query payment status reliably after a timeout or an app restart.
  • Issue full or partial refunds and track their provider references and settlement state.
  • Expose a merchant-facing statement derived from ledger entries.
  • Ingest signed provider webhooks for authorization, capture, failure, refund, and chargeback events.
Non-functional
  • Never lose or duplicate a value movement; every state change is durable and auditable.
  • A retry with the same idempotency key must return the original result and must not charge twice.
  • Keep the API responsive while the provider is slow: charge calls time out in seconds, so confirmation may be asynchronous.
  • Maintain an append-only ledger whose entries can be replayed and whose debits equal credits per transaction.
  • Keep card data out of scope by tokenizing at the provider and never storing a primary account number.
  • Detect and repair drift with a daily reconciliation against provider settlement files.
  • Assume 5M payments per day: about 58 per second average and roughly 500 per second at peak.
  • At two ledger entries per captured payment, the ledger grows by about 10M entries per day before refunds and adjustments.
  • A provider call can take hundreds of milliseconds to several seconds and may time out with an unknown outcome, so the API cannot assume a synchronous answer.
  • Retention is measured in years, so the ledger and payment tables must be partitioned by month and archived, not kept in one ever-growing hot table.
  • One payment may produce several provider attempts after timeouts, so attempt records and idempotency keys must be retained longer than the maximum retry window.

03API design

MethodPathPurpose
POST/v1/paymentsCreate and charge a payment; requires an Idempotency-Key header and returns the payment id plus current status.
GET/v1/payments/{payment_id}Return the authoritative payment, charge, and refund state so a client can resolve an ambiguous timeout.
POST/v1/payments/{payment_id}/captureCapture a previously authorized payment, idempotently and only from the authorized state.
POST/v1/refundsCreate a full or partial refund with its own idempotency key; the total refunded can never exceed the captured amount.
POST/v1/webhooks/providers/{provider}Verify the provider signature, store the event idempotently, and trigger the matching state transition.
GET/v1/merchants/{merchant_id}/statement?from=...&to=...Return a statement built from ledger entries for a period, with opening and closing balances.

04Data modelling

DecisionChoiceWhy
Money representationStore integer minor units plus an ISO currency code; never use floating point, and fix rounding rules at the boundary.Binary floating point cannot represent most decimal amounts exactly, and a one-cent drift in a ledger is a correctness bug, not a display issue.
Payment stateAn explicit state machine: requires_payment_method, requires_confirmation, processing, authorized, captured, partially_refunded, refunded, failed, cancelled. Every transition is a conditional update.A status field updated blindly lets a duplicate webhook move a refunded payment back to captured; conditional transitions make out-of-order events harmless.
LedgerAppend-only double-entry entries grouped by transaction_id, with a debit and a credit of equal amount for every movement; balances derived by aggregation.An append-only ledger is auditable and replayable, and double entry makes it impossible to create value from nowhere; a mutable balance row hides how it got there.
Idempotency and provider referencesA durable table keyed by (merchant_id, idempotency_key) holding a request hash, status, and stored response, optionally fronted by Redis; each provider attempt stores its reference with a unique constraint.A timeout gives the client no way to know whether the charge happened, so the retry must replay the original outcome, while the provider reference is needed for lookup and reconciliation and keeping every attempt preserves the audit trail.
Webhook ingestionAn inbox table keyed by provider event id, processed asynchronously after signature verification, with the event marked processed in the same transaction as the state change.Providers deliver at least once and out of order; a durable dedupe record plus conditional transitions prevents double application and survives a crash.
Event publicationWrite an outbox row in the same transaction as the payment or ledger change, and let a relay publish to downstream consumers.A direct publish can fail after commit, leaving orders and analytics unaware of a real payment; the outbox makes the database commit the source of truth.

05Architecture

The API records intent, idempotency, and ledger state in one database before and after the provider call; signed webhooks drive conditional transitions, and reconciliation compares internal records with provider settlement.
  • Keep the payment database as the source of truth and the provider as an external system with an unknown outcome. A timeout is not a failure; it is an unresolved state that must be queried or reconciled.
  • Create the payment row and its idempotency record in one transaction before the provider call. If the process crashes after the call, the retry finds the in-progress record and resolves it instead of charging again.
  • Pass a stable idempotency key to the provider on every attempt for the same logical charge. If the provider does not support one, use its lookup-by-reference API before retrying.
  • Confirm the charge with a conditional update from processing to captured, guarded by the provider reference. A duplicate or late webhook then becomes a no-op.
  • Write ledger entries in the same local transaction as the status change they represent. Two entries, one debit and one credit, with the same transaction_id and equal amounts. The ledger tables can live in the same database as payments but are partitioned and indexed separately.
  • Never mutate or delete a ledger entry. Corrections are new reversing entries, so the history remains complete and an auditor can replay it.
  • Verify webhook signatures before parsing, deduplicate by provider event id, and acknowledge quickly; do the state transition synchronously if it is small, otherwise enqueue it with the inbox row committed first.
  • Reconcile daily: pull the provider settlement report, match every captured charge and refund, and put unmatched items in a break queue with an owner and an SLA.

06Optimisation & trade-offs

DecisionGainCost / risk
Synchronous charge APIThe client gets an immediate outcome for the common case and the user experience is simple.The API is coupled to provider latency and timeouts, and an ambiguous timeout still forces a pending state and a status lookup.
Asynchronous confirmationThe service survives slow providers and can absorb bursts without holding connections or transactions open.The client must poll or receive a webhook, and the UI needs a pending state that is honest about uncertainty.
Append-only double-entry ledgerFull auditability, replayability, and a mathematical invariant that catches missing or duplicated entries.More rows and more complex queries; balances require aggregation or snapshots, and corrections require reversing entries.
Database-backed idempotencyDurable across restarts and transactional with the payment record, so a crash cannot forget that a request was already accepted.An extra write and lookup on every request and a growing table that needs retention and partitioning.
Transactional outboxDownstream systems eventually see every committed change without a distributed transaction or a dual-write failure.Consumers must be idempotent, events arrive later, and the relay plus outbox table need monitoring and cleanup.
Auth and capture as separate stepsSupports order fulfillment, partial captures, and cancellation before settlement, which many businesses need.More states and more failure paths, and an authorization can expire before capture.
Retry unknown provider outcomesRecovers from transient network failures without failing a payment that may have succeeded.Requires provider-side idempotency or lookup; without it, a retry is a duplicate-charge risk.
Tokenize card data at the providerThe service never stores a PAN, dramatically reducing PCI scope and breach impact.The provider becomes a critical dependency, and token portability across providers is limited.
  • Cache merchant configuration, fee schedules, and payment method metadata so the charge path avoids repeated lookups.
  • Keep the synchronous API path short: validate, persist, call the provider once, and return; move notifications, downstream projections, and analytics to the outbox.
  • Partition payment and ledger tables by month and archive closed periods, while keeping indexes on payment_id and provider_reference for lookups.
  • Derive merchant balances from ledger entries and cache periodic snapshots rather than summing the full history on every statement request.
  • Use provider tokenization and a hosted card field so card data never reaches the payment service, which keeps PCI scope small.
  • Retry only idempotent provider operations, with exponential backoff, jitter, and a cap; never retry a charge with a new key.
  • Prefer a single provider adapter interface with explicit capability flags, so adding a provider does not leak its status codes into business logic.
  • Alert on reconciliation breaks, duplicate charge attempts, webhook signature failures, and payments stuck in processing beyond a threshold.

07Follow-ups — one-line answers

How do you prevent a double charge on retry? Require an idempotency key, persist it with the in-progress request before calling the provider, and pass the same key or reference on every retry.
What if the provider call times out? Treat it as unknown, keep the payment in processing, and resolve it by querying the provider or waiting for a webhook; never retry with a new key.
What if a webhook arrives twice or out of order? Deduplicate by provider event id and apply transitions only when they move the payment forward from its current state.
How do partial refunds work? Each refund is its own record with an idempotency key, and the sum of successful refunds is constrained never to exceed the captured amount.
How does reconciliation work? A daily job compares provider settlement records with internal charges and refunds, and unmatched items go to a break queue for investigation.
What guarantees does the ledger provide? Every movement has equal debits and credits under one transaction_id, entries are immutable, and balances can be recomputed from history.
How do you handle currency and rounding? Store integer minor units with a currency code, keep one currency per payment, and apply a documented rounding rule at the point of conversion.
How do you keep card data out of scope? Use provider-hosted fields or tokenization so the service only ever sees a token and never stores, logs, or transmits a primary account number.
What if the database commit succeeds but the response is lost? The client retries with the same idempotency key and receives the stored result, so the lost response never becomes a second payment.
What if the ledger write fails after a successful charge? The captured state and its ledger entries commit in one local transaction; if that transaction fails, the payment remains processing and is retried before any settlement or confirmation.
How are payouts handled? Payouts are a separate ledger transaction against the merchant's payable balance, usually batched on a schedule and reconciled with the bank statement.
Why not update a balance column directly? A mutable balance loses the history of how it changed, cannot prove that debits equal credits, and is vulnerable to lost updates and silent corrections.

08Traps

  • Treating a provider timeout as a failure and retrying with a fresh idempotency key, which is the classic path to a double charge.
  • Storing an amount as a float or double, which introduces rounding drift that no amount of later reconciliation can cleanly fix.
  • Mutating or deleting ledger rows to correct a mistake instead of posting a reversing entry, which destroys the audit trail.
  • Trusting a webhook without verifying its signature, or updating status unconditionally, so a forged, late, or duplicate event can undo a refund or a cancellation.
  • Publishing an event to a queue after the database commit without an outbox, leaving orders and analytics permanently unaware of a successful payment.
  • Storing card numbers or CVVs in the application database or logs, which expands PCI scope and turns a minor bug into a breach.
