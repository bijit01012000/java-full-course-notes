Event-Driven Architecture

It tests whether you can decouple services without hand-waving away the hard parts: delivery semantics, ordering, schema contracts, replay, and debugging a flow that has no single call stack.

One-line answerProducers publish immutable past-tense facts to a partitioned broker, and consumers subscribe and react idempotently, trading immediate consistency and simple debugging for temporal decoupling, buffering, and independent evolution.

01Requirements

Functional
  • Producers publish domain events to a topic without knowing which consumers exist.
  • The broker durably stores events for a retention window, and consumers subscribe in groups and can replay.
  • Guarantee ordering per entity by choosing a partition key that matches that entity.
  • Deliver at least once, with idempotent consumers, capped retries, and a dead-letter queue with replay.
  • Register and version event schemas with compatibility checks before publication.
  • Build projections or read models for queries, and keep an event timeline per entity for audit and debugging.
Non-functional
  • Publish latency must stay low, while consumption is asynchronous and scales with partitions.
  • No event is lost after it is acknowledged, and duplicates must not corrupt state.
  • Consumer lag must be bounded, monitored, and able to trigger backpressure or scale-out.
  • Consumers must deploy and scale independently without changing the producer.
  • Schema changes must not break existing consumers during a rolling migration.
  • Topics need authentication, authorization, encryption, and data minimization for sensitive payloads.
  • Assume 1M events per day, about 12/s average; a 20x peak reaches roughly 240/s, so partition count is sized for peak consumer parallelism rather than average traffic.
  • With 12 partitions and a key such as order_id, events for one order stay ordered while twelve consumers can process in parallel.
  • Keep event payloads under about 100 KB and pass large blobs by object-storage reference; a fatter event raises broker storage, network, and consumer cost.
  • Retain events on the broker for 7 days for replay and archive older history to object storage for audit instead of paying for hot retention.
  • Target projection lag under a minute for user-facing read models, and alert on sustained lag rather than a single spike.
  • Keep DLQ depth at zero; alert on any growth, because a DLQ without an owner becomes a graveyard.

03API design

MethodPathPurpose
POST/v1/topics/{topic}/eventsPublish one event with a producer-assigned event_id and a partition key.
GET/v1/topics/{topic}/events?cursor={partition}:{offset}Read a range of events for replay or for bootstrapping a new consumer.
POST/v1/subscriptionsCreate a consumer group with a topic, optional filter, and starting offset.

POST/v1/dlq/{dlq_id}/replayReplay a failed event to its original topic after the bug or configuration is fixed.

04Data modelling

DecisionChoiceWhy
Event logAn append-only partitioned log per topic with offsets and time-based retentionAppend-only storage gives durable replay and per-partition ordering, which a destructive queue cannot provide to new consumers.
Partition keyThe entity ID whose ordering matters, such as order_id or user_idOrdering is guaranteed only within a partition, so the key must match the business entity, while a coarse key concentrates load.
Event envelopeA standard envelope with event_id, type, version, occurred_at, producer, correlation_id, and partition_keyA stable envelope supports routing, tracing, deduplication, and schema evolution without changing every consumer.
Duplicate handlingA dedupe table keyed by event_id and consumer group, with a bounded TTLAt-least-once delivery and offset-commit crashes both produce duplicates, and unbounded dedupe history is itself a storage problem.
Publish consistencyA transactional outbox written in the same database transaction as the state change, with a relay publishing afterwardPublishing directly risks a commit without an event or an event without a commit, leaving state and consumers permanently inconsistent.
Read modelsMaterialized projections keyed by entity and advanced by consumer offsetsThe event log is history, not a query surface; projections give fast current-state reads and can be rebuilt by replay.

The order service writes state and an outbox record together, a relay publishes to partitioned topics, and independent consumer groups update their own databases or projections, with exhausted retries isolated in a dead-letter queue.
  • Publish after the local transaction commits, ideally through an outbox and relay, so consumers never read a state change that was rolled back or miss one that committed.
  • Separate events from commands: an event is a past-tense fact with many possible consumers, while a command has one intended recipient and can be refused.
  • Choose the event style per case: a thin notification for triggers, event-carried state for read models, and event sourcing only where full history is a real requirement.
  • Ordering is per partition, so pick the key from the entity whose order matters and accept the hot-key and parallelism limits that follow.
  • Process a partition sequentially inside a consumer; parallel threads or unordered batches break the ordering the broker preserved.
  • Operate the broker as a first-class stateful system: monitor lag, retention, disk, replication, and schema compatibility, and rehearse replay before you need it.

06Optimisation & trade-offs

DecisionGainCost / risk
Asynchronous decouplingProducers and consumers do not need to be available at the same time, and new consumers subscribe without producer changesThe end-to-end flow is emergent and much harder to see than a call stack
Eventual consistencyAbsorbs spikes and isolates consumer outagesRead models lag, so the UI must show pending states and some reads need the source of truth
At-least-once deliveryAvoids silent event loss during failuresEvery consumer needs idempotency or deduplication, and duplicate side effects are a real risk
Partitioned orderingScales consumption while preserving per-entity orderNo global order, and one hot key can limit parallelism for that partition
Event-carried stateConsumers avoid callback calls and runtime couplingDuplicated data, larger payloads, and a wider contract to evolve
Event sourcingA complete audit trail and the ability to rebuild any projectionSnapshots, projection rebuilds, and schema migration across all historical events
ReplayRecovers projections and bootstraps new consumersRe-triggers side effects unless consumers are idempotent and replay is scoped
ChoreographyFlexible, loosely coupled reactions with no central controllerThe workflow is implicit, so failures and timeouts are harder to trace and compensate
  • Batch consume and commit offsets after the batch, while handling per-record failures so one poison event does not block the partition.
  • Compress payloads and keep them small, referencing large objects by key instead of embedding bytes.
  • Size partition count for peak consumer parallelism, and remember that increasing partitions later changes key-to-partition mapping and ordering.
  • Autoscale consumers on lag rather than CPU, and use backpressure when the downstream store is saturated.
  • Cache projections or materialized views for the hottest reads instead of querying the broker or replaying events per request.
  • Use compacted topics when only the latest value per key matters, such as a configuration or entity snapshot.
  • Reply to failures into a DLQ with the original event, error, attempts, and consumer version so replay is deterministic.
  • Propagate the correlation ID and event ID through logs and traces, and keep an event timeline per entity for debugging.

07Follow-ups — one-line answers

What is the difference between an event and a command? An event is a past-tense fact that already happened and can have many consumers, while a command is a request to one recipient that can be refused.
Notification, state transfer, or event sourcing? Notification carries an ID and makes consumers call back, state transfer carries the changed fields, and sourcing stores events as the source of truth replayed into projections.
How do you guarantee ordering? Guarantee it per partition by keying on the entity, and process each partition sequentially; global ordering is expensive and rarely needed.
How do you handle duplicate events? Assume at-least-once delivery, use an event ID or natural key with a conditional write, and keep a dedupe table with a bounded retention window.
What does exactly-once delivery actually mean? Usually at-least-once delivery plus idempotent or transactional processing inside one broker ecosystem, not a guarantee that spans an arbitrary external database.
How do you deal with eventual consistency? Expose pending states, route reads that must see the latest write to the source, wait for a version marker, and reconcile projections that fall behind.
How do you evolve event schemas? Add optional fields, avoid renames and removals, register versions in a schema registry with compatibility checks, and support two versions during migration.
What happens when a consumer keeps failing? Retry transient errors with backoff, cap attempts, then move the event to a dead-letter queue so it stops blocking the partition.
How do you debug an event-driven system? Propagate correlation and event IDs through logs and traces, record which consumer version processed what, and keep a per-entity event timeline.
What is the transactional outbox? It writes the state change and the event record in one local transaction, then a relay publishes the event, avoiding the dual-write inconsistency.
Choreography or orchestration? Choreography suits simple fan-out and independent reactions, while orchestration gives a visible coordinator for multi-step workflows with compensation.
How do you stop a consumer from falling permanently behind? Monitor lag and processing rate, scale consumers up to the partition count, reduce per-event work, and add backpressure or repartition if lag is structural.

08Traps

  • Using events as remote procedure calls and expecting an immediate reply from a consumer.
  • Publishing the event before the database transaction commits, so consumers see stale state or the event is lost on rollback.
  • Assuming ordering across a whole topic instead of only within a partition.
  • Writing consumers that are not idempotent on an at-least-once broker.
  • Treating a dead-letter queue as a solution without an owner, alerting, and a replay procedure.
  • Changing a field's meaning without versioning the schema, silently corrupting replays and historical data.
