Scale Read Traffic

Almost every product question turns into a read-scaling question: one write is read thousands of times, so interviewers want to see whether you can keep those reads away from the database without breaking freshness.

One-line answerServe most reads from the edge, memory, or a replica, keep only a small fraction reaching the database, and state the staleness budget for every layer you add.

01Requirements

Functional
  • Serve product detail, category listing, and search-result pages by ID through one read API.
  • Serve anonymous responses that are identical for every user from the CDN and shared caches.
  • Return the requesting user's own recent write immediately, even while replicas lag.
  • Invalidate or refresh every cached copy when a product changes.
  • Expose hit ratio, replica lag, and per-route latency so a bad layer can be bypassed.
Non-functional
  • p99 under 100 ms at the edge and under 200 ms at origin for a cache hit.
  • Sustain 50k reads/s at peak with a roughly 100:1 read-to-write ratio.
  • 99.95% read availability; a cache outage degrades latency, not correctness.
  • Staleness budgets: public catalog 60 s, stock 5 s, the user's own write 0 s.
  • Scale horizontally with no downtime, no single hot node, and no shared mutable state in the app tier.
  • Assume 50k reads/s at peak and 500 writes/s at peak, a 100:1 read-to-write ratio.
  • 10M products at about 2 KB each is about 20 GB raw; the hot 5% is about 1 GB, which fits in memory.
  • At a 95% cache hit ratio, 2,500 reads/s reach the database; at 90%, 5,000 reads/s do.
  • Four replicas at about 10k simple reads/s each give about 40k reads/s, enough for the miss path with failover headroom.
  • If the CDN serves 60% of public traffic, origin sees about 20k reads/s before local and Redis caches.

Reads fall through the cheapest layer first: CDN, then local memory, then Redis, then a replica, with the primary reserved for fresh own-write reads.
  • Fix the query before adding infrastructure: a missing index or an N+1 pattern can consume the same capacity a cache would have saved.
  • Every layer has a stated staleness budget and an update mechanism; a layer with no invalidation plan is a bug waiting to surface.
  • Use cache-aside with delete-on-write and a TTL backstop; the cache is derived data and losing it must not lose correctness.
  • Read replicas are asynchronous by default, so route own-write reads to the primary briefly instead of pretending lag does not exist.
  • Precompute expensive pages and counters at write time when reads dominate; a feed or listing should not run the same join per request.
  • Design the full-miss path: timeouts, circuit breakers, request coalescing, and load shedding, because the cache will be cold or down at some point.

06Optimisation & trade-offs

DecisionGainCost / risk
CDN cachingAnswers requests before they reach origin and cuts latency for distant usersStale content and coarse purges; personal data can leak if responses are not marked correctly

Asynchronous replicationKeeps write latency low and writes available when a replica is slowReplication lag breaks naive read-your-writes and needs per-endpoint handling
Local in-process cacheFastest possible hit with no network hopOne copy per instance, duplicated memory, and short TTLs to bound divergence
Redis cache-asideRemoves most database reads and shares one view across app serversAdds a network hop, invalidation logic, and a second copy that can be stale
Denormalized read modelOne-row page loads and predictable read latencyWrite amplification and a second place that must be kept in sync
Long TTLHigher hit ratio and less database loadWider staleness window and slower propagation of corrections
Pin own reads to the primaryCorrect read-your-writes without special client logicPuts a slice of read traffic back on the primary and reduces read scaling
  • Add the composite and covering indexes that the top read queries need, and verify them with the query plan.
  • Cache public pages at the CDN with s-maxage plus stale-while-revalidate; mark anything user-specific private or no-store.
  • Keep a small local cache for the hottest keys to avoid a network hop on the majority of requests.
  • Use single-flight or a short lock on a miss so one request rebuilds a key while the rest wait briefly.
  • Add TTL jitter and refresh popular entries in the background so expirations do not arrive in a wave.
  • Negative-cache unknown IDs for about 30 s to stop repeated misses from reaching the database.
  • Precompute category listings, rating counts, and other aggregates instead of recalculating them on every read.
  • Monitor and rebalance hot shards; split or salt a key rather than adding cache nodes that cannot help one key.

07Follow-ups — one-line answers

How do you know reads are the real bottleneck? Measure the read-to-write ratio, peak reads per second, database CPU and I/O, query latency percentiles, and hit ratio; reads are the problem when the database saturates on read queries while writes are modest.
What would you fix before adding a cache or replicas? Indexes, query shape, and result-set size — a full scan or an N+1 pattern multiplies load without adding a single new component.
Why is replica scaling not linear? Every replica must apply every write and costs storage and operations, so read capacity grows with replica count but efficiency does not.
How do you preserve read-your-writes with lagging replicas? Route that user's reads to the primary for a short window after a write, or return a version watermark and wait until a replica has reached it.
A 95% hit ratio still overloads the database — why? Because the absolute miss rate is what reaches the database: at 50k reads/s, 5% is 2,500 queries/s, so size the database for misses, not total traffic.
TTL or delete-on-write? Use both: delete after the database commit so the next read reloads fresh data, and keep a TTL so a missed delete expires eventually.
How do you stop a cache stampede? Coalesce misses with a per-key lock or single-flight, refresh popular keys before expiry, and add jitter so keys do not expire together.
How do you handle one viral product? Replicate the key under suffixed names that hash to different cache nodes and keep a very short-TTL local copy so most reads never reach the cluster.
When is a CDN appropriate for API responses? When the response is identical for every user and a short staleness window is acceptable, such as a public product page or article.
What happens when the cache is down? The database sees the full read load, so use timeouts, a circuit breaker, load shedding, and possibly stale data, and size the database for a survivable miss rate.
How would you serve multiple regions? Terminate reads at the nearest edge or replica, keep writes in a primary region, and replicate asynchronously while respecting data-residency rules.
What would you monitor? Hit ratio per route, origin and CDN QPS, p99 latency, replica lag, eviction rate, cache errors, and per-key skew for hot keys.

08Traps

  • Adding a cache before checking for a missing index or an N+1 query pattern.
  • Routing every read to a replica and assuming the result is strongly consistent.
  • Caching a personalised response at the CDN because the page looked public.
  • Adding a cache with no invalidation strategy, then treating stale reads as a mystery.
  • Claiming replica throughput scales linearly with replica count.
  • Treating the cache as the source of truth and losing the ability to rebuild it from the database.
