Consistent Hashing

Consistent hashing is the standard follow-up to sharding and caching, because it tests whether you can keep key ownership stable while the cluster changes. Interviewers look for the ring mechanism, virtual nodes, replica placement, and the data movement the algorithm does not do for you.

One-line answerPlace servers and keys on the same fixed hash ring, give each server many virtual nodes for balance, and move only the arc owned by a joining or leaving node.

01Requirements

Functional
  • Map every key to exactly one primary owner deterministically while membership is stable.
  • Add or remove a node while moving only the keys whose ownership actually changes.
  • Support virtual nodes so each physical server owns many small arcs and capacity can be weighted.
  • Place replicas on distinct physical servers by walking clockwise around the ring.
  • Distribute one versioned membership view so all clients and servers agree on ownership.
  • Expose ring distribution and rebalance progress to operators.
Non-functional
  • Lookup is O(log V) over sorted vnode positions with a stable non-cryptographic hash.
  • Adding one node to N moves about 1/(N+1) of keys, not most of them.
  • Load is balanced within an acceptable band; virtual nodes reduce variance but do not guarantee equal load.
  • A node failure is absorbed by several successors rather than one, and reads degrade to misses or retries rather than corruption.
  • Membership changes converge quickly and are versioned to prevent split ownership.
  • Hash a stable server ID rather than an ephemeral IP so restarts do not reshuffle the ring.
  • Assume 100 cache nodes with 150 virtual nodes each: 15,000 ring positions, still small enough for a sorted array in memory.
  • Assume 50M keys at 1 KB per value: about 50 GB of cache data, roughly 500 MB per node before replicas.
  • Adding the 101st node moves about 1% of keys, roughly 500k keys, which is a bounded refill rather than a full cache flush.
  • At 20k lookups/s per client, binary search over 15k positions is negligible; the network hop dominates.
  • Target membership convergence in seconds, with a version and checksum so a stale client can detect that its ring is old.

The router hashes each key, binary-searches the vnode table for the first position clockwise, and routes to that physical node while a versioned membership service keeps every client's ring consistent.
  • The ring is logical: an in-memory sorted array of vnode positions plus a map to physical nodes, not a literal circle.
  • Every client must use the same hash function, vnode scheme, and membership version, or the same key routes to different owners.
  • Publish membership from one authority and include a version and checksum so a stale router can refresh or fail fast.
  • Replication chooses where copies live; write quorum, read repair, and anti-entropy are separate mechanisms.
  • Plan key movement as a throttled background transfer, and decide whether reads during the move go to the old owner, the new owner, or both.

06Optimisation & trade-offs

DecisionGainCost / risk
Consistent hashing instead of modulo hashingMembership changes move only the affected arcs, avoiding a near-total remap and a cache-miss storm.A ring structure, vnode metadata, and a shared membership view that must be kept in sync.
Many virtual nodes per serverBetter balance and a failed node's load is spread across several successors.More metadata and more routing-table work on every membership change.
One vnode per serverA tiny ring and trivial membership updates.Uneven arcs and a single neighbor inheriting the whole failed range.
Clockwise replicationAvailability and durability without a separate placement service.Storage and write amplification, plus a repair process for missed writes.
Rendezvous hashing instead of a ringNo ring state and graceful membership changes.O(N) work per lookup, which gets awkward for very large server sets.
Fixed partitions instead of a ringExplicit data movement and a stable modulo mapping on partition IDs.The partition count is a long-term commitment and hot partitions remain possible.
Client-side routingNo extra network hop and low latency per lookup.Every client must stay in sync with membership, and an old client silently routes to the wrong owner.
Server-side routing proxyOne authoritative ring view and simpler clients.An extra network hop and a potential bottleneck or single point of failure.
  • Use 100 to 200 vnodes per node as a starting point, then measure the actual key distribution instead of trusting theory.
  • Weight vnode counts by machine capacity instead of hand-tuning individual arcs.
  • Binary search the sorted positions and cache the ring in each client to avoid a central lookup per request.
  • Precompute the replica set per key when the ring version changes, not on every request.
  • Throttle rebalance transfers and keep serving from the old owner until the new owner confirms it has the keys.
  • Use a fast non-cryptographic hash with a fixed seed; cryptographic hashes add CPU without improving placement.
  • Alert on per-node key share and request rate, not just the cluster average.

07Follow-ups — one-line answers

What problem does consistent hashing solve? Modulo hashing remaps most keys whenever the server count changes, while consistent hashing changes ownership only for the arcs affected by the membership change.
Walk me through a lookup on the ring. Hash the key into the fixed space, binary-search for the first vnode position at or after the hash, and wrap to the first position if the key falls past the end.
Why does adding one server to five move about one sixth of the keys? A new node takes over the arc between its predecessor and itself, which is roughly 1/(N+1) of a balanced ring.
Does consistent hashing move the data for you? No, it changes ownership only; a cache simply misses and reloads, while persistent storage needs a separate transfer and repair process.
What happens if a server fails without virtual nodes? Its entire arc moves to the next server clockwise, which can multiply that neighbor's load and cause a cascading failure.
What are virtual nodes and why do they help? A vnode is an extra ring position for the same physical server, so many small arcs average out uneven gaps, spread failure load, and allow capacity weighting.
Do virtual nodes guarantee even load? No, they only reduce variance statistically; hot keys, skewed key distributions, and heterogeneous request costs can still overload one server.
How would you implement the ring efficiently? Keep a sorted array of vnode positions and a position-to-node map, hash the key, binary-search with wrap-around, and return the owner in O(log V).
What breaks if two clients have different ring views? The same key can route to two different owners, causing misses and divergent data, so membership must be published from one authority and versioned.
How do you place replicas on the ring? Take the primary vnode, then walk clockwise and choose the next vnodes on distinct physical servers until the replication factor is met, spreading them across failure domains.
Consistent hashing versus rendezvous hashing? Consistent hashing keeps ring state and looks up in O(log V), while rendezvous hashing scores every node per key in O(N) but needs no ring.
When is consistent hashing the wrong choice? For stateless services where any healthy server can handle any request, or when fixed partitions or a plain load balancer is simpler.

08Traps

  • Claiming consistent hashing moves data when it only changes ownership and the transfer is a separate process.
  • Using one vnode per server in production, creating hot spots and single-neighbor failure overload.
  • Hashing ephemeral IPs so every restart reshuffles the ring and invalidates caches.
  • Letting clients compute membership independently so they disagree about the owner of a key.
  • Placing a replica on the next vnode without checking that it belongs to a different physical server.
  • Assuming virtual nodes guarantee perfectly even load rather than reducing variance.
