Counting at Scale

It checks whether you match the counting mechanism to the semantics: exact for billing, approximate for reach, and sharded or streamed when one row would serialize every write.

One-line answerSplit hot counters into shards or aggregate a durable event stream, keep the display path cached and approximate, and reserve exact counts for money.

01Requirements

Functional
  • Increment and decrement a counter for an entity and metric.
  • Return the current total quickly.
  • Count distinct users for a time window.
  • Expose counts over time for charts and ranking.
  • Accept batched increments from edge or mobile clients.
  • Recompute counts from raw events for correction.
Non-functional
  • Absorb 500k increments/s at peak without a single hot row.
  • Read p99 under about 50 ms from cache or a serving table.
  • Exact and auditable for billing and votes; approximate is acceptable for views.
  • Idempotent per logical event, so retries never double count.
  • Lose no billable event; display counts may lag seconds.
  • Survive a region failure without corrupting totals.
  • Assume 200k events/s average and 500k/s peak across all counters.
  • 1M active counters, with the top 100 receiving most of the traffic.
  • An event at about 100 B is roughly 20 MB/s, around 1.7 TB/day before compression.
  • 30-day hot retention is roughly 50 TB; older events move to cold storage.
  • A counter with 64 shards turns one hot row into 64 rows; reads sum 64 values or a cached snapshot.
  • A HyperLogLog sketch of about 12 KB estimates millions of distinct users within a few percent.

Writes increment sharded counters and append to a durable log; the aggregator maintains serving totals, windowed series, and sketches, while reads come from the serving side.
  • The write path is append plus increment; the read path is a cached snapshot, never a live COUNT over events.
  • Billing, votes, and quotas read from the exact event-derived store; view counts read the approximate serving store.
  • Partition the event log by entity_id so all events for one counter stay ordered.
  • Windows close on a watermark; a late event either updates an open window or emits an explicit correction.
  • A batch job recomputes from the raw log to repair drift, duplicates, and logic bugs.
  • Hot entities get more shards or edge pre-aggregation, and the read path must not loop over shards synchronously.
  • Regional counters can accept local writes and merge later, but a global hard cap needs coordination.
  • Keep the raw events; without them a wrong number can only be guessed at, not repaired.

06Optimisation & trade-offs

DecisionGainCost / risk
Sharded exact counterScales writes and stays exactReads sum many shards and resizing is awkward

Stream aggregationFresh windowed results without request-path countingWatermarks, late events, and idempotent sinks add complexity
Batch recomputationAuthoritative and repairableSlow and expensive over long histories
HyperLogLogCheap, mergeable distinct countsApproximate and cannot answer which users were counted
CRDT countersLocal writes and convergence across regionsMetadata per replica and no global hard limit
Long dedupe windowCatches late retries and replaysMore storage and operational cost
  • Pre-aggregate at the edge for a few seconds before sending deltas.
  • Pipeline Redis increments and flush them as batched deltas.
  • Compact shards into a base value so the live shard count stays bounded.
  • Cache the displayed total with a short TTL and serve stale on failure.
  • Read rankings from a precomputed table instead of sorting live counts.
  • Filter bots and duplicate events before they reach the counter.
  • Use 64 shards for top counters and 8 to 16 for the long tail.
  • Compress and tier the event log, keeping only the window needed for replay.

07Follow-ups — one-line answers

Why is incrementing a counter hard at scale? All writers target the same row, so row locks serialize updates; the arithmetic is cheap but the coordination is not.
How does a sharded counter work? The logical counter is split into physical shards, each write increments one shard, and a read sums the shards or a base snapshot plus deltas.
How many shards do you use? Size from peak write rate with headroom, because more shards improve writes but increase read amplification and make resizing harder.
Can you just use Redis INCR? It is fast and atomic, but it is memory-bound, a hot key still lands on one node, and persistence can lose recent increments, so use it in front of a durable log.
How do you count unique viewers? Store distinct IDs per window at small scale, and use one HyperLogLog per window at large scale, merging sketches instead of adding daily counts.
How do you handle duplicate events? Attach a stable event ID, enforce it with a unique constraint or dedupe table at the sink, and size the dedupe window to cover retries and reprocessing.
What is a watermark in stream aggregation? It is the processor's estimate that all events up to a time have arrived, which decides when a window closes and how late events are handled.
How do you correct a wrong count? Recompute from the immutable event log for the affected key and window, then overwrite the serving value; without raw events you can only guess.
Why use batch processing if streaming is available? Batch recomputation is authoritative and repairs drift across long histories, while streaming supplies freshness; many systems run both.
How do you count a celebrity post without a hot key? Pre-aggregate at the edge, split the counter into more shards, cache the displayed total, and keep ranking on a separate pipeline.
How do multi-region counters converge? Use a CRDT such as a G-counter or PN-counter, where each region tracks its own contribution and replicas merge by combining state.
When is approximate counting unacceptable? For billing, quotas, rate limits, and votes, or any number a user can audit against their own actions.

08Traps

  • Running a live COUNT over a large event table on every page view.
  • Sharding a counter but then reading it with one query per shard on the hot path.
  • Treating Redis as durable when persistence can lose recent increments.
  • Adding daily unique counts to compute a weekly unique count.
  • Assuming exactly-once delivery without making the sink idempotent.
  • Letting a billing or ranking path depend on a stale display cache.
