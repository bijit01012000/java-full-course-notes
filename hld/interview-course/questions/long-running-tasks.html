Long-Running Tasks and Scheduling

Interviewers use it to check whether you can separate accepting work from doing it, and whether the design survives crashes, deploys, duplicate delivery, and missed schedules.

One-line answerAccept the work synchronously into a durable job record, return 202 with a job ID, and let leased workers plus a scheduler execute it idempotently with retries, progress, and dead-lettering.

01Requirements

Functional
  • Submit an asynchronous job and receive a job ID immediately.
  • Report status, coarse progress, attempt count, and a result link.
  • Cancel a queued or running job on a best-effort basis.
  • Retry transient failures and dead-letter jobs that exhaust attempts.
  • Run one-off delayed jobs and recurring schedules.
  • Notify the client on completion by polling, webhook, or push.
Non-functional
  • Return 202 within about 200 ms p99; never perform the work inline.
  • An accepted job must survive a crash or deploy, so persist before enqueue.
  • At-least-once execution; every step must be safe to run twice.
  • Scheduler lag under about 30 s for minute-level schedules.
  • Isolate job classes so a slow export cannot starve quick work.
  • No silent loss: every failure ends in a retry, a dead letter, or a visible failed state.
  • Assume 10M jobs per day: about 116/s average and roughly 600/s at a 5x peak.
  • About 90% finish under 30 s; the remaining 10% need chunking and checkpoints.
  • A job record is roughly 1 KB with a payload reference, around 900 GB for 90 days of hot retention.
  • At 10k due schedules per minute, claim in batches of 100 to 500 to keep polling cheap.
  • Worker capacity is set by downstream connection and provider limits, not by queue depth alone.

03API design

MethodPathPurpose

The API accepts and persists work, the scheduler claims due jobs, leased workers execute with heartbeats, and exhausted jobs go to a dead-letter queue for replay.
  • Only validation, authorization, quota, and the durable write are synchronous; everything else is a job.
  • The stored job record is the source of truth; the queue message carries only the job ID.
  • The scheduler decides and workers do. The scheduler claims due rows atomically and dispatches without running the work.
  • Workers are stateless and disposable, so any worker can run any job in its pool.
  • Use separate queues and pools for short interactive work, long exports, and scheduled jobs.
  • Large payloads live in object storage; the job row keeps a reference, not a megabyte blob.
  • A parent job fans out deterministic chunks, children are idempotent, and the parent counts completions before declaring success.
  • Cancellation is a flag checked between chunks; a side effect that already committed is compensated, not pretended away.

06Optimisation & trade-offs

DecisionGainCost / risk
Async job instead of inline workNo client or proxy timeout risk, and bursts are absorbedThe user gets eventual completion and needs a status API
Long lease with heartbeatSlow jobs are not executed twice while still runningRecovery waits for lease expiry when a worker actually dies
Coarse progress milestonesCheap writes and an honest UIThe percentage is less precise and updates less often
Small chunks with fan-outCheap retries, smooth progress, bounded leasesMore job rows and per-chunk coordination overhead
Per-job atomic claimScales without a global leader bottleneckMore complex conditional queries and index contention
Skip missed runsProtects capacity after an outageSilently loses occurrences that carried unique work
Replay every missed runPreserves billing or per-interval semanticsCan flood downstream systems during recovery
Polling the status endpointSimple, cache-friendly, and works everywhereWasted requests and slower notice than a push
  • Claim bounded batches with a conditional update rather than scanning the whole due-time index.
  • Add jitter to recurring schedules so a midnight cron does not create a periodic spike.
  • Checkpoint chunked jobs so a retry resumes near the failure point instead of restarting.
  • Scale workers on oldest job age and queue depth, capped by downstream connection and rate limits.
  • Cache the status response for a few seconds because progress changes slowly.
  • Archive terminal jobs to object storage after 30 to 90 days to keep the hot table small.
  • Route retries to a separate queue so poison jobs do not delay fresh work.
  • Cap dispatch rate during catch-up so recovery does not overload downstream systems.

07Follow-ups — one-line answers

Why not run the task inside the HTTP request? Clients, proxies, and load balancers time out, the connection holds capacity for the whole job, and a crash or deploy loses the work with no way to report progress.
What does the API return for accepted work? 202 Accepted with a job ID and status URL, returned only after the job record is durable.
How do you avoid losing an accepted job? Persist the job row before publishing, or write the row and an outbox entry in one transaction so a relay can republish after a crash.
What happens if a worker crashes mid-job? Heartbeats stop, the lease expires, and another worker claims the job; that is why steps must be idempotent and long jobs must checkpoint.
How do you prevent duplicate side effects? Use a per-job idempotency key, a conditional transition so only the first completion wins, and provider-side idempotency keys for external calls.
How do you handle a job that takes hours? Split it into deterministic chunk jobs with a coordinator, checkpoint each chunk, and keep each lease longer than one chunk rather than the whole job.
What do you do about a run missed while the system was down? Apply an explicit per-schedule policy: skip for cleanup, run once now for reports, or replay every missed occurrence for billing, with a bounded replay rate.
What if a recurring job takes longer than its interval? Decide whether to block the next run, queue it, or allow overlap, and enforce a maximum runtime so a stuck run cannot block the schedule forever.
How do you cancel a running job? Set a cancel flag that the worker checks at safe points between chunks; committed side effects are compensated because cancellation is best effort.
How does the client learn the job is done? Poll the status endpoint, receive a signed webhook, or subscribe over SSE or WebSocket; the status record remains authoritative.
How do you scale workers? Scale on oldest job age and queue depth per queue, within downstream limits, and keep separate pools so long work cannot starve short work.
What would you monitor? Scheduler lag, oldest job age, throughput, failure and retry rates, lease expiries, dead-letter growth, and duration percentiles per job type.

08Traps

  • Doing the work inline and raising the load balancer timeout instead of decoupling it.
  • Returning 200 with an empty result while the job is still queued.
  • Enqueueing before the job record is durable, so a crash loses accepted work.
  • Setting the lease or visibility timeout shorter than the job, causing two workers to run it at once.
  • Running cron on every app server, or on one server with no failover and no visibility into missed runs.
  • Scheduling in local time with no rule for daylight-saving gaps and duplicated hours.
