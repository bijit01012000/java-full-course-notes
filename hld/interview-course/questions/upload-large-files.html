Upload and Serve Large Files

It tests one instinct that separates a working design from a fragile one: file bytes should never flow through the application tier, and the hard parts are resumability, integrity, and delivery cost.

One-line answerAuthorize the transfer with a short-lived presigned URL, upload directly to object storage in resumable parts, verify checksums before the file becomes visible, process asynchronously, and serve through a CDN with range support.

01Requirements

Functional
  • Upload files from web and mobile, from a few megabytes up to several gigabytes.
  • Resume an interrupted upload from the last completed part instead of restarting.
  • Verify size and checksum and reject corrupt or truncated objects.
  • Serve downloads quickly and let clients seek or resume partial downloads.
  • Generate derived artifacts such as thumbnails, previews, and transcoded renditions.
  • List, delete, and share files with scoped access.
Non-functional
  • No file bytes pass through application servers; app capacity stays independent of file size.
  • Upload survives flaky mobile networks with only failed parts retried.
  • A file is never visible to readers before verification and processing complete.
  • Download p99 is low and mostly served from edge caches; origin egress is a small fraction.
  • Storage is durable and private by default, with access granted per file and per user.
  • Cost is bounded by retention rules, lifecycle policies, and cleanup of abandoned uploads.
  • Assume 10M uploads per day at 20 MB average, about 200 TB per day of ingress, with a peak near 200 MB per second.
  • Assume 1M downloads per day at 50 MB average, about 50 TB per day of egress; a 95 percent CDN hit ratio leaves roughly 2.5 TB per day from origin.
  • With 8 to 16 MB parts, a 5 GB file is roughly 320 to 640 parts, which is small enough to track per part and large enough to limit overhead.
  • A presigned URL TTL of 15 minutes and an upload session TTL of 24 hours balance leakage risk against slow mobile uploads.
  • Metadata is about 1 KB per file, so 10M uploads per day is roughly 10 GB of rows, negligible next to the bytes.

03API design

MethodPathPurpose
POST/filesCreates the file record and upload session, and returns a server-chosen object key plus presigned part URLs.
POST/uploads/{upload_id}/partsReturns a fresh presigned URL for one part, or records a part as completed after a client resume.
POST/uploads/{upload_id}/completeIdempotently completes the upload with the part list and whole-file checksum, then triggers verification.

GET/files/{file_id}/statusReports pending, verified, processing, ready, or failed, so the client can poll or subscribe.

The metadata path and the byte path are separate: the API only authorizes and records state, clients write parts straight to object storage, and readers are served from the CDN with storage as origin.
  • Two paths, deliberately separated: small JSON requests on the API, large immutable byte streams on storage. This is what keeps app memory and request timeouts out of the picture.
  • A presigned URL is a bearer capability: it grants one operation on one key for a short time, so scope the key, method, expiry, content type, and size, and never log the full URL.
  • Completion is the gate. Verify size and checksum, keep the object in a pending state, then process asynchronously and only then mark it ready.
  • Downloads go through a CDN with signed URLs. Application servers issue the signature and never carry the bytes.
  • Failure modes to plan for: dropped parts, checksum mismatch, abandoned multipart uploads, stuck processing jobs, and a CDN rule that caches a private object.
  • Abuse and safety: validate content type, scan untrusted uploads before serving, enforce per-user quotas, and keep buckets private by default.

06Optimisation & trade-offs

DecisionGainCost / risk
Direct-to-storage uploadApp capacity is independent of file size and slow clients no longer hold worker slotsA two-step flow and a new place for key and permission mistakes
Presigned URLsNo long-lived credentials in browsers or apps, and no proxying through the APIThe URL is a bearer token, so a leak is usable until expiry
Multipart uploadParallel transfer and retry of only failed partsUpload state, part bookkeeping, and orphan cleanup
Resumable sessionsSurvives flaky mobile networks without restarting a multi-gigabyte transferPersistent session state and an idempotent completion path
Asynchronous processingFast uploads and isolated, retryable heavy workThe file is temporarily unavailable and the pipeline needs monitoring
CDN delivery with signed URLsLow download latency and much less origin egressSigning complexity, cache configuration risk, and egress cost
Keeping original plus variantsFlexibility to re-render and support many devices and formatsStorage multiplies, and every variant needs its own lifecycle
Content-addressed deduplicationOne stored object for identical files and natural integrity checkingAn extra lookup and careful reference counting before deletion
  • Move bytes off the app tier with presigned uploads scoped to a server-generated key and a short expiry.
  • Use multipart upload with 8 to 16 MB parts and bounded parallelism so only failed parts are retried.
  • Persist an upload session so a resumed client asks which parts are missing instead of restarting from zero.
  • Verify a checksum per part and for the whole file server-side before the object can become visible.
  • Run scanning, thumbnails, and transcoding from a queue so upload latency stays flat.
  • Cache immutable, versioned objects at the CDN for a long time and keep origin egress small.
  • Support HTTP range requests so video can seek and downloads can resume without refetching the whole object.
  • Abort incomplete multipart uploads and tier or expire cold objects with lifecycle rules.

07Follow-ups — one-line answers

Why not upload large files through the application servers? It holds memory, worker slots, and connections for the whole transfer, hits gateway timeouts, and makes retries expensive, which is exactly what object storage is built to avoid.
How does a presigned URL work? The backend signs a URL that grants one operation on one object for a short time, so the client talks to storage directly and no credentials ever reach the client.
What do you scope in a presigned upload URL? The exact object key, the allowed method, a short expiry, and where supported the content type and maximum size, with the key always chosen by the server.
How do you make an upload resumable? Split the file into parts, record which parts succeeded in an upload session, and have the client query the session and send only the missing parts.
Multipart versus a single PUT? A single PUT restarts from zero on failure and cannot use bandwidth in parallel, while multipart retries only failed parts and lets storage assemble the object.
How do you verify integrity? Send a checksum per part and for the whole file, store and compare them server-side, and fail closed rather than marking a mismatched object ready.
What happens after the bytes land? Completion enqueues scanning, validation, thumbnails, and transcoding; the file stays pending until those succeed and the client polls or subscribes for status.
How do you serve downloads at scale? Authorize the user, return a short-lived signed CDN URL, and serve immutable versioned objects from the edge with storage as the origin.
What are range requests for? Fetching part of an object, which enables video seeking, resumable downloads, and parallel fetching, as long as partial responses and authorization are correct.
How do you keep private files private? Private buckets, per-file authorization at signing time, short-lived signed URLs, content scanning, and access logging rather than public objects.
How do you control storage and egress cost? Lifecycle-tier or expire cold objects, abort incomplete multipart uploads, deduplicate by content hash, cap versions, and watch egress since media traffic usually dominates.
How do you avoid showing a half-uploaded file? Keep it pending or quarantined, verify size and checksum, finish processing, and only then mark it ready and expose a URL.

08Traps

  • Proxying file bytes through the application tier and then wondering why memory and timeouts spike.
  • Letting the client choose the object key, which allows overwriting another user's file.
  • Issuing presigned URLs with long expiries or permissions broader than one object and one method.
  • Treating a single large PUT as reliable on a mobile network.
  • Not tracking upload state, so every failure restarts from byte zero.
  • Marking a file ready before checksum verification and scanning complete, or caching private objects publicly.
