Why interviewers ask it

One question, many fundamentals

  • Unique ID generation and collision handling
  • Key-value modelling and secondary indexes
  • Cache-aside and hot links
  • Read-heavy scaling and replication
  • Async analytics and failure handling
What strong candidates do

Make the read path obvious

  • Scope the product before drawing boxes
  • Define entities and keys before the architecture
  • Draw one clean diagram, not five sketches
  • Explain 301 vs 302 and cache behaviour
  • Move analytics off the redirect path
60-second answer

“A URL shortener is a read-heavy key-value system. The write path validates the URL, generates a unique short code, stores code → long URL in a sharded, replicated KV store, and caches it. The redirect path reads the cache, falls back to the KV store on a miss, returns a 301 or 302, and publishes the click event asynchronously. I’d keep app servers stateless, shard by short code, and use a queue for analytics so the redirect stays fast.”

Design a URL ShortenerRequirements & estimates

1. Requirements

Functional

What it must do

  • Create a short link from a long URL.
  • Redirect GET /{code} to the original URL.
  • Optional custom alias and expiry.
  • Optional click analytics.
  • Disable or delete a link.
Non-functional

How well

  • Redirect p99 under ~100–200 ms.
  • Very high availability; redirects must not depend on analytics.
  • Read-heavy: ~100 redirects per write.
  • Short codes unique and hard to guess if security matters.
  • Analytics can be eventually consistent.

Assumptions and estimates

  • 100 million new links per day; 10 billion redirects per day.
  • Peak traffic is 2–3× average; average mapping is ~500 bytes.
  • Over five years: ~183 billion links, ~91 TB raw, ~300 TB with replication/index overhead.

The exact numbers are assumptions. What matters is the ratio: reads dominate, so the redirect path gets the cache and the simplest lookup. Analytics and other slow work stay off that path.

2. Key entities

Core entities

Three entities are enough

  • User — optional owner of a link.
  • UrlMapping — short code, long URL, owner, expiry, status.
  • ClickEvent — append-only event for analytics.
Relationships

Simple ownership

  • User 1 → N UrlMapping.
  • UrlMapping 1 → N ClickEvent.
  • A mapping is uniquely identified by code.
  • Click events are never queried during redirect.

No body required; cache headers only if the redirect is permanent.

API decisions worth stating

Use an Idempotency-Key on create to survive client retries. Use 302 by default if you need analytics or revocable links. Add Cache-Control only when the redirect is truly permanent; otherwise a CDN/browser may keep sending users to the old destination.

Short-code generation

ApproachHowTrade-off
Counter + base62Increment a segment counter; encode in base62.Short, no collisions; needs an ID service or preallocated ranges.
Hash + collision checkHash URL, take N chars, retry on collision.No ID service; collisions and extra writes.
Random code7 random base62 chars; unique constraint.Hard to guess; collision probability grows with volume.
Default

A 7-character base62 code gives roughly 62⁷ ≈ 3.5 trillion combinations. Use a counter with preallocated ranges when you want no collisions; use random codes when guessability and central coordination matter. Always enforce uniqueness with a conditional write.

5. Architecture diagram

Critical path

Only what the redirect needs

  • Gateway: TLS, auth, rate limit, routing.
  • URL service: stateless; scales horizontally.
  • KV store: O(1) lookup by code.
  • Cache: absorbs hot-link traffic.
Off the critical path

Async by design

  • ID generator: only on create.
  • Queue + workers: analytics.
  • Analytics DB: counters and reports.
  • Analytics lag does not break redirects.

Design a URL ShortenerWrite flow

6. Write flow: create a short link

What can go wrong

  • Collision: retry with a new code; custom alias returns 409.
  • Duplicate create: idempotency key or unique (owner_id, long_url).
  • ID service down: preallocate ranges per app instance or fall back to random codes.
  • Partial failure: persist before returning success; never rely on cache as the source of truth.
  • Malicious URL: validate scheme/domain, use safe-browsing/allowlist, rate-limit creates.
What to say

“I generate a unique code, write it with a conditional put, and only then return success. Cache population is an optimization, not the source of truth.”

7. Redirect flow: the hot path

Happy path

Cache hit

  • Gateway routes the request.
  • URL service reads the code from cache.
  • Return 301/302 immediately.
  • Publish click event without waiting.
Fallback

Cache miss

  • Read the KV store by code.
  • Repopulate cache with a TTL.
  • Return the redirect; never block on analytics.
  • 404 unknown / 410 expired.
Hot-link protection

Cache hot codes, use request coalescing or a short lock against stampedes, add jitter to TTLs, and negative-cache missing codes briefly. A viral link should not turn into thousands of identical KV reads.

8. Optimisation and trade-offs

What to optimise, and in what order

  1. Read path first: cache hot codes; keep the redirect to one cache lookup.
  2. KV sharding: shard by hash(code) and replicate each shard across zones.
  3. Write path: preallocate ID ranges; use conditional writes for uniqueness.
  4. Analytics: queue/stream clicks; aggregate offline; never block redirects.
  5. Abuse: rate-limit creates, validate destinations, block malicious domains.

9. Follow-ups — one-line answers

Custom alias collision? Use a conditional put on the alias; return 409 instead of overwriting.
Link expiry? Store expires_at, check lazily on redirect, return 410, and reclaim space with a cleanup job.
Deleted link still cached? Soft-delete, invalidate the cache, and keep a short negative-cache entry.
Hot/viral link? Cache it, coalesce requests, add a local cache layer, and rate-limit abusive traffic.
Analytics without slowing redirects? Publish a click event to a queue/stream; aggregate asynchronously.
Multi-region? Route users to a nearby read cache; keep writes in a primary region and replicate asynchronously.
Malicious destinations? Validate scheme/domain, use safe-browsing/allowlists, rate-limit creates, and block reported domains.
ID generation down? Preallocate ranges per instance; if exhausted, fall back to random codes with retries.
301 or 302? 301 is cacheable and fewer origin hits; 302 keeps control and analytics visibility.
Cache down? Fall back to the KV store with timeouts and a circuit breaker; serve stale if the product allows it.
Shard key? Hash code for even distribution; avoid keys that create one hot shard.
Duplicate create? Use an idempotency key or a unique (owner_id, long_url) constraint.
Storage growth? Expire links, archive cold mappings, compress values, and avoid storing media in the KV store.
How many servers? Peak QPS ÷ safe per-server QPS, then add 30–50% headroom.

Traps

Avoid these
  • Forgetting collision handling.
  • Returning a short URL before the mapping is stored.
  • Writing analytics synchronously on the redirect path.
  • No cache fallback when the cache is down.
  • Using a raw auto-increment ID, leaking volume and order.
  • Assuming 301 and 302 are interchangeable for analytics.
  • Ignoring malicious URLs, expiry, and abuse.
  • Sharding before a single KV store is the measured bottleneck.
Closing answer

“The design is a read-optimized key-value system: a unique short code maps to a long URL, the redirect path is cache-first with a KV fallback, and analytics is asynchronous. The main trade-offs are 301 vs 302, counter vs random codes, and how much cache staleness the product can tolerate.”
