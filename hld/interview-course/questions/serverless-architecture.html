Serverless Architecture

It checks whether you can choose compute for a workload honestly: where per-use scaling and managed services win, and which operational problems cold starts, concurrency, retries, limits, cost, and lock-in remain yours.

One-line answerServerless is managed event-driven compute plus managed services: the provider handles provisioning and patching, while idempotency, concurrency limits, cold starts, peak-cost economics, and lock-in stay design problems.

01Requirements

Functional
  • Run handlers triggered by HTTP requests, queue or stream messages, object uploads, schedules, and database changes.
  • Scale automatically per event without manual capacity planning, and buffer bursts through a queue where needed.
  • Keep handlers stateless, with durable state in a managed database, cache, or object store.
  • Deliver asynchronous events at least once, with idempotent handlers, capped retries, and a dead-letter queue.
  • Use managed auth, storage, queues, and secrets, with least-privilege permissions per function.
  • Support versioned deployments and a rollback or canary path for handler code and configuration.
Non-functional
  • Interactive endpoints must meet a latency budget that includes cold starts; background work should stay asynchronous.
  • Scale-out must not overwhelm downstream databases or third-party APIs; cap concurrency and add backpressure.
  • Cost must be modelled at both average and peak load, not only at demo traffic.
  • One failed invocation or poison event must not block a stream or take down unrelated functions.
  • Secrets must come from a managed secret store, never from code, logs, or plaintext environment variables.
  • Business logic should stay portable behind thin handlers, even if the trigger wiring is provider-specific.
  • Assume 5M invocations per day at 200 ms average and 512 MB: about 1M invocation-seconds per day, so duration and memory drive cost as much as request count.
  • That averages about 58 invocations/s; a 10x burst at 200 ms needs roughly 116 concurrent executions, so concurrency limits and downstream connections matter more than the average.
  • One function holding a database connection at 100 concurrency can exhaust a small pool, so cap concurrency or put a connection pooler in front.
  • Keep event payloads small, roughly tens of KB, and pass object keys for files instead of pushing multi-MB bodies through an invoke.
  • Set the function timeout below the caller or upstream deadline, for example a 10s handler behind a 15s API deadline, and split longer work into chunks.
  • Keep a 7-day replay window for queue or stream events and 14 days of dead-letter retention so incidents can be investigated and replayed.

04Data modelling

DecisionChoiceWhy
Function versioningImmutable code-plus-config versions, with an alias that shifts traffic between themRollback and canary need a known artifact; mutating a live function makes both impossible.
Handler stateExternalize all durable state to a database, cache, or object store; memory is only a best-effort warm cacheConcurrent environments are isolated and can be destroyed at any time, so in-memory state is neither shared nor durable.
IdempotencyA conditional write keyed by event_id or a natural business key, with a bounded TTLAsynchronous triggers retry, and a crash after the side effect but before the acknowledgement causes redelivery.
Large payloadsStore files in object storage and pass a key or pre-signed URL in the eventInvocation payloads and local disk are limited, and moving bytes through a function adds cost and latency.
Buffering and failuresA managed queue in front of bursty work plus a dead-letter queue with retentionThe queue absorbs spikes and lets consumers retry without losing events, while the DLQ isolates poison messages.
Invocation telemetryStructured logs and spans keyed by request_id and trace_id, stored outside the functionExecution environments are ephemeral, so host files and local metrics disappear with them.

HTTP, queue, object, and schedule triggers invoke stateless functions that use managed data services and emit telemetry, with exhausted retries isolated in a dead-letter queue.
  • Functions are glue; the real architecture is the set of managed services around them, and each one brings its own limits and failure modes.
  • Initialize SDK clients and configuration outside the handler and lazy-load heavy dependencies, so warm invocations skip most of the cold-start cost.
  • Put a queue between a burst and the downstream system, then cap function concurrency so auto-scaling cannot exhaust database connections.
  • Treat every asynchronous trigger as at-least-once: assign the event ID before the first attempt and make the side effect idempotent.
  • Use provisioned concurrency only on latency-critical paths; asynchronous work can usually tolerate a cold start.
  • Keep the handler thin and the business logic in a portable module so the provider-specific trigger and SDK code stays at the edge.

06Optimisation & trade-offs

DecisionGainCost / risk
Scale to zeroNo idle cost and automatic capacity for spiky workloadsCold starts on scale-out and a latency tail that interactive users notice
Per-use pricingCheap for low average and unpredictable trafficAt sustained high throughput, reserved containers or servers can be substantially cheaper
Managed servicesNo patching, backups, or cluster operationsPer-service quotas, connection limits, and a bill that is hard to attribute
Fine-grained functionsSmall permissions and failure domains that scale independentlyMore invocations, more network hops, and harder end-to-end tracing
Stateless handlersAny environment can serve any event, so scaling is trivialEvery piece of state becomes another network call and another managed dependency
Automatic scale-outAbsorbs a burst without a capacity planCan overwhelm the database or a third-party API faster than they can react
Provisioned concurrencyRemoves cold starts from the interactive pathReintroduces paying for idle capacity and needs capacity planning after all
Deep provider integrationFastest path to triggers, identity, and managed glueHigher lock-in and a larger migration cost for core business logic
  • Shrink the deployment package, avoid heavy module-level work, and choose a fast-starting runtime to reduce cold-start time.
  • Right-size memory, because CPU usually scales with it; measure cost per invocation instead of assuming the smallest size is cheapest.
  • Batch queue records where the work allows it, but handle per-record failures so one bad record does not fail the batch.
  • Reuse connections and clients within a warm environment, and use a pooler in front of the database for high concurrency.
  • Serve large files directly from object storage with pre-signed URLs rather than proxying bytes through a function.
  • Cache hot reads in a managed cache instead of calling the primary database on every invocation.
  • Emit structured logs and tail-sampled traces, and track throttles and cold starts as first-class metrics.
  • Alert on queue age, DLQ depth, and concurrency saturation rather than only on function error rate.

07Follow-ups — one-line answers

What does serverless mean if servers still exist? It means the provider owns provisioning, patching, scaling, and availability, while you deploy code and managed services and pay per use.
What is the difference between FaaS and BaaS? FaaS runs event-triggered code per invocation, while BaaS is the managed backing set such as databases, storage, queues, and auth; real systems combine both.
What causes cold starts? A new execution environment must be scheduled, have code or an image pulled, start its runtime, and run module initialization, so package size and startup work dominate.
How do you reduce cold starts? Use a smaller package, lazy-load dependencies, initialize clients outside the handler, pick a fast runtime, and reserve provisioned concurrency where latency matters.
Why must handlers be stateless? Concurrent invocations run in isolated environments, so memory is neither shared nor durable; warm reuse is best-effort and state belongs in an external store.
How do you handle duplicate events? Assume at-least-once delivery and make handlers idempotent with an event ID or natural key plus a conditional write, then cap retries and dead-letter the rest.
How does automatic scaling become a problem? The platform opens concurrency as fast as events arrive, so a burst can exhaust database connections or third-party rate limits unless you queue, cap concurrency, and add backpressure.
When is serverless more expensive than servers? At sustained high utilization, because per-invocation and per-duration charges plus managed-service fees can exceed reserved capacity.
What are the main platform limits? Maximum duration, memory, payload size, temporary disk, and concurrency quotas; they force long jobs into chunks, large files into object storage, and bursts into queues.
How do you observe a serverless system? Use structured logs with trace IDs, distributed tracing across gateway, function, queue, and database, and metrics for invocations, errors, duration, throttles, cold starts, and concurrency.
How do you reduce lock-in? Keep handlers thin, put business logic behind interfaces, prefer standard protocols, and accept deliberate coupling only for commodity glue.
When would you choose containers instead? For steady high throughput, long-running work, custom runtimes or networking, and predictable latency where reserved capacity beats per-request pricing.

08Traps

  • Assuming function instances are reused, so an in-memory cache appears to work in testing and then silently misses in production.
  • Writing non-idempotent handlers on an at-least-once queue or stream trigger.
  • Ignoring concurrency limits until scale-out exhausts the database connection pool.
  • Doing work in the request path that exceeds the execution timeout instead of moving it to a queue or a long-running compute service.
  • Passing large files or multi-MB payloads through function arguments instead of object-storage references.
  • Estimating cost only at low traffic and being surprised by retries, polling, and peak concurrency.
