Scale Write Traffic

Caches and replicas cannot absorb new data, so interviewers use write-heavy designs to see whether you understand write amplification, batching, queues, sharding, and which writes may be delayed or lost.

One-line answerWrites scale by making each write cheaper, writing fewer of them, absorbing bursts in a durable log, and only then spreading them across shards keyed for even distribution.

01Requirements

Functional
  • Accept single and batched device or order events over HTTP.
  • Persist events durably for history, audit, and analytics.
  • Maintain the latest state per entity for low-latency reads.
  • Deduplicate retried writes and redelivered queue messages.
  • Replay a partition range after a consumer crash or a bad deploy.
  • Report ingestion lag per partition and apply backpressure when consumers fall behind.
Non-functional
  • Sustain 100k writes/s at peak and 30k writes/s on average.
  • p99 acknowledgement under 100 ms for async events and under 300 ms for durable order writes.
  • No acknowledged order or payment is lost; analytics and view counts may lag by seconds.
  • Ordering is guaranteed per entity, not globally across the whole stream.
  • Scale out by adding partitions, consumers, and shards without downtime.
  • A consumer restart or rebalance must not double-apply an effect.
  • Assume 30k writes/s average and 100k writes/s peak at roughly 3x average.
  • At 1 KB per event, average ingest is about 30 MB/s, peak is about 100 MB/s, and a day is about 2.6 TB raw.
  • At 3x replication and 7-day hot retention, about 55 TB of hot copies exist before compression.
  • Batching 500 events turns 100k HTTP requests/s into about 200 requests/s.
  • At a measured 8k writes/s per shard, 100k/s needs 13 shards; provision 20 for headroom and growth.
  • Use 60 partitions so up to 60 consumers can run while each entity's events stay in one partition.

Producers append to a partitioned log, one consumer group maintains current state, another batches history into a sharded LSM store, and lag drives backpressure.
  • Writes are harder than reads because every write must be durable, applied to the table, applied to every index, and replayed to every replica.
  • Keep only the indexes the queries use; on a write-heavy table, an unused index is pure overhead on every insert.
  • Use a log between the API and the database when traffic is spiky or the client does not need immediate persistence.
  • Partition by entity ID so one entity's events stay ordered and one consumer group can scale without cross-partition coordination.
  • Make consumers idempotent with a producer-assigned event ID and a dedupe record committed in the same transaction as the effect.
  • Separate durability classes: payments and orders wait for a durable, replicated commit; view counts and analytics can be aggregated or sampled.

06Optimisation & trade-offs

DecisionGainCost / risk
Queue between API and databaseAbsorbs bursts, decouples acceptance from persistence, and lets consumers run at a sustainable rateDelayed visibility, duplicate delivery, consumer lag, and another system to operate
BatchingAmortises network round trips, transactions, and log writes across many recordsAdds latency and can lose the buffered batch if the process crashes
LSM-tree storageHigh write throughput through sequential appends and sorted flushesSlower reads from multiple files and background compaction that consumes CPU and disk
Overwrite latest stateKeeps the working set small and makes current-state reads cheapDiscards history that analytics, audit, or debugging may later need
ShardingSpreads storage and write throughput across many machinesCross-shard queries and transactions become hard, and resharding needs a migration plan
Consistent hashingMoves only about 1/N of keys when a shard is addedAdds ring management and still requires dual reads or writes during the move
acks=allAcknowledged writes survive a broker failureHigher write latency and lower throughput than a single-broker acknowledgement
Aggregation and samplingCuts write volume by orders of magnitudeLoses fine-grained detail and can lose the recent window if the aggregator crashes
  • Batch writes on both the client and consumer side, flushing on a size limit or a short time limit, to amortise round trips and commits.
  • Choose an LSM-based store for append-only volume and accept background compaction as a real operational cost.
  • Overwrite latest state instead of appending history when reads only need the current value.
  • Aggregate counters in memory or a stream processor and write one delta per interval instead of one row per event.
  • Hash the entity ID for sharding and use consistent hashing so adding a shard moves roughly 1/N of keys.
  • Split a hot counter into several counters, update one at random, and sum on read.
  • Raise partition count before adding consumers, and increase consumer batch size when lag rises.
  • Use compression and time-based retention tiers so raw detail expires while rollups remain.

07Follow-ups — one-line answers

Why do caches and read replicas not fix write throughput? Every write still carries new data that must be stored durably and replayed to every replica, so duplicating reads does not remove any write work.
What does one insert actually cost? A log append, a table or page update, an update to every index, row locks where needed, and replication, which is why measured write throughput is lower than expected.
When is a queue the right answer? When traffic is spiky or the client can accept delayed persistence, because a queue turns a burst into a backlog rather than a database outage.
Does a queue fix sustained overload? No; it only smooths a burst, and if consumers are permanently slower than producers the lag grows until you add capacity or apply backpressure.
Why must queue consumers be idempotent? Most brokers deliver at least once, so a consumer can commit an effect and crash before acknowledging; a producer-assigned event ID and a dedupe record make the redelivery harmless.
What do you watch on a queue pipeline? Consumer lag in events and in time, produce versus consume rate, partition skew, retry and dead-letter counts, and database write latency.
What makes a good shard key? It spreads writes evenly and keeps data that is read together on one shard, such as hash(entity_id) rather than a timestamp.
Why is a timestamp a poor range shard key? Every new write has the latest timestamp and lands on the newest shard, leaving older shards idle and the hot shard saturated.
How do you handle one record with enormous write traffic? Split it: keep several counters, update one at random, and sum them on read, because sharding spreads data but cannot split a single row.
What breaks when you add shards later? Modulo hashing moves almost every key when N changes; consistent hashing limits movement to about 1/N, but you still need dual reads or writes during migration.
Which writes can be asynchronous? Only those where delay or small loss is acceptable, such as views, analytics, and replaceable location pings; payments, orders, and chat messages must be durable before acknowledgement.
How do you get exactly-once processing? You do not get exactly-once delivery end to end; you get effectively-once effects from at-least-once delivery plus idempotent or deduplicated consumers.

08Traps

  • Trying to fix write throughput by adding read replicas or caches.
  • Keeping many unused indexes on a write-heavy table and wondering why inserts are slow.
  • Claiming a queue solves sustained overload rather than only smoothing a burst.
  • Building consumers that are not idempotent, then discovering duplicates after a restart.
  • Choosing a timestamp or auto-increment column as a range shard key.
  • Acknowledging a write after placing it in a volatile buffer and calling it durable.
