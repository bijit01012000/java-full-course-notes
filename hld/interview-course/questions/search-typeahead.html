Search and Typeahead

Search tests whether you understand inverted indexes, relevance, and the difference between a cold analytical query and a hot low-latency suggestion path. Typeahead adds a second workload with a much tighter budget and a much higher request rate.

One-line answerKeep the transactional database as the source of truth, build a sharded inverted index for ranked search, and serve typeahead from cached prefix top-k with debouncing and a separate latency budget.

01Requirements

Functional
  • Full-text search over documents with ranked results, highlighting, filters, and facets.
  • Prefix suggestions for typeahead, ranked by popularity, recency, and context.
  • Near-real-time indexing of creates, updates, deletes, and permission changes.
  • Tolerate typos and synonyms without silently rewriting high-confidence queries.
  • Rebuild the index from the source of truth and swap it atomically.
  • Degrade to partial results or a safe fallback when a shard or the cluster is unhealthy.
Non-functional
  • Search p95 target around 200 ms and typeahead p99 under 100 ms, measured as separate budgets.
  • Typeahead absorbs a much higher query rate than full search and must never block the search box.
  • Index lag is bounded and monitored; discovery tolerates seconds of staleness, permission changes do not.
  • Relevance is evaluated offline with NDCG and online with click-through and zero-result rate.
  • A failed shard returns partial results with a degraded signal rather than a 500 for the whole query.
  • The index is a derived view that can be rebuilt without losing source data.
  • Assume 50M documents at 2 KB each: 100 GB of raw text before index overhead, positions, doc values, and replicas.
  • Assume 5k search QPS and 50k typeahead QPS at peak, so typeahead is ten times the traffic and needs its own capacity.
  • Twenty document shards with two replicas means 40 index copies to store, operate, and reindex.
  • A query fans out to all 20 shards, so p99 is set by the slowest shard unless requests are hedged or timed out.
  • Cache the top 100k prefixes; the head of the query distribution is small and highly repetitive.
  • Assume 500 document writes/s; a ten-second visibility target sets the indexing pipeline's throughput and queue-depth budget.

04Data modelling

DecisionChoiceWhy
Core index structureAn inverted index mapping each analyzed term to posting lists with document IDs, frequencies, and positionsQueries look up only their terms and intersect posting lists instead of scanning every document, and positions enable phrase queries and highlighting.
Text analysisUnicode normalization, lowercasing, stemming, and curated synonyms, with the same analyzer at index and query timeMatching depends on both sides producing the same normalized terms, and richer analysis trades precision and CPU for recall.
Index shardingPartition by document ID; each query fans out to all shards and merges top-k resultsMulti-term queries stay local to a shard, and scoring is comparable across shards, at the cost of tail latency from the slowest shard.
Typeahead storagePrecomputed top-k suggestions per prefix in a KV cache, with a trie or finite-state transducer fallback for long-tail prefixesMost suggestions are served without traversing an index, and the fallback keeps rare prefixes useful without precomputing every string.
Ingestion pathDatabase plus outbox or change stream feeding idempotent, versioned indexing workers; full rebuild behind an alias swapThe transactional store remains the source of truth, retries cannot duplicate documents, and a bad mapping can be replaced without downtime.
RankingRetrieve candidates with the inverted index, score with BM25 and field boosts, then rerank the top candidates with popularity, recency, and business signalsCheap lexical retrieval keeps recall high, while expensive signals only run on a small candidate set.

Search and typeahead have separate services and budgets but share derived indexes, which are fed from the source database through an outbox and idempotent indexing workers.
  • Search is a derived read model: the transactional database owns truth, and the index can be rebuilt from it.
  • Analyzer choice is part of the contract; index-time and query-time analysis must match or terms will not line up.
  • Typeahead is a separate service with its own cluster, cache, and latency budget so a search outage does not break the search box.
  • Deletes and permission changes propagate at higher priority than creates, because a stale index can leak content.
  • Use aliases for blue-green reindexing and verify document counts and relevance before switching traffic.

06Optimisation & trade-offs

DecisionGainCost / risk
Dedicated search index instead of database queriesRelevance ranking, tokenization, facets, and fast free-text matching.A second data store to operate and keep in sync with the source of truth.
Near-real-time indexingNew and updated documents become searchable within seconds.More segment merges, lower indexing throughput, and visible index lag.
More shardsMore parallelism and isolation for large corpora.Higher fan-out, worse tail latency, and expensive resharding later.
More replicasMore query throughput and availability during a node loss.More storage and multiplied indexing work.
Precomputed typeahead listsVery low latency for the hot prefix head.Memory footprint and staleness as query popularity shifts.
Fuzzy matching and synonymsHigher recall for typos and alternate wording.Lower precision, more candidate work, and surprising matches if not curated.
Partial results on shard failureThe query still returns something instead of failing entirely.Relevant documents can be silently missing, so the degraded state must be signalled.
Aggressive result cachingProtects the cluster from repeated head queries.Stale results and invalidation bugs when filters, permissions, or inventory change.
  • Cache the head of the query distribution at the edge with normalized keys and short TTLs for volatile results.
  • Precompute top-k suggestions per prefix and refresh them on a schedule, falling back to lexical completion for rare prefixes.
  • Debounce on the client, require a minimum prefix length, and cancel stale in-flight requests.
  • Fetch limit plus one candidate per shard, merge top-k, and hedge or time out slow shards.
  • Bulk-index in batches and throttle segment merges so indexing does not destroy search latency.
  • Use request coalescing and circuit breakers so a hot cache miss or retry storm does not stampede the cluster.
  • Return partial results with a degraded flag when a shard is unavailable.
  • Monitor zero-result rate and first-click rank, not just latency.

07Follow-ups — one-line answers

Why not just use a SQL LIKE query for search? A leading-wildcard LIKE cannot use a normal index and cannot rank by relevance, and it lacks tokenization, synonyms, phrase proximity, and facet aggregation.
What is an inverted index and why is it fast? It maps each analyzed term to a posting list of documents and positions, so a query intersects only the terms it contains instead of scanning every document.
How do you keep the search index in sync with the database? Write to the database as the source of truth, publish changes through an outbox or change stream, and apply idempotent versioned updates with a rebuild and reconcile path.
How do you handle a document update arriving out of order? Attach a monotonically increasing version or timestamp and reject older writes so retries stay idempotent and stale updates cannot overwrite newer ones.
How does ranking work? Retrieve candidates with the inverted index, score them with BM25 and field boosts, then rerank the top candidates with popularity, recency, and business rules.
Why is search eventually consistent, and is that acceptable? Indexing is asynchronous and search engines refresh in batches, which discovery tolerates, but a user's own new listing or a permission revocation needs a source-of-truth read.
How would you design typeahead? Precompute or cache top-k completions per prefix, rank and filter them, debounce on the client, and run the service separately from full search.
How do you scale a search index? Partition documents across shards, add replicas for query throughput, fan out each query, merge top results, and plan shard count for future growth.
What is the tail-latency problem in search? Every query waits for every shard, so the slowest shard sets latency; hedge, time out, or return partial results to bound it.
How do you deploy a new analyzer or schema? Build a new index with the new mapping, backfill from the source of truth, verify counts and relevance, then switch an alias atomically.
How do you prevent a stale index from leaking deleted content? Propagate deletes and permission changes at high priority, keep tombstones until physical removal, and enforce authorization at read time.
When would you not use a dedicated search engine? When the corpus is small, queries are exact or simple prefix matches, and the database can meet the latency budget without a second store to synchronize.

08Traps

  • Treating the search index as the source of truth and losing data when it is rebuilt.
  • Using LIKE with a leading wildcard and calling it search.
  • Mismatching the analyzer at index time and query time so terms never line up.
  • Ignoring index lag and then wondering why newly created records are missing.
  • Putting typeahead on the full search path with no cache, debounce, or separate budget.
  • Letting one slow shard determine the latency of every query through unbounded scatter-gather.
