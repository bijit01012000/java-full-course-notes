Design a Rate Limiter

It tests whether you can enforce a shared limit atomically under concurrency, and whether you can reason about availability when the limiter itself is the failing component.

One-line answerCount requests per key in Redis with one atomic token-bucket script, keep versioned rules in a local policy cache, and pick fail-open or fail-closed per route so the limiter never becomes the outage.

01Requirements

Functional
  • Enforce limits per API key, user, IP, tenant, and route, with different limits per plan or endpoint.
  • Support sustained rate plus a short burst allowance, for example 100 requests per minute with a burst of 20.
  • Return HTTP 429 with Retry-After and rate-limit headers (limit, remaining, reset) on rejection.
  • Allow operators to create, update, and disable rules without redeploying the gateway.
  • Expose current usage per key and aggregate allow/deny metrics for dashboards.
  • Choose a failure mode per route: fail-open for browsing, fail-closed for login, payments, and expensive writes.
Non-functional
  • Add no more than a few milliseconds at p99 to every request; the limiter is on the hot path.
  • Stay available and correct enough during a Redis node or zone failure, without a global stop-the-world.
  • Scale horizontally with the gateway fleet and support at least 100k checks per second at peak.
  • Rule changes propagate within a few seconds and are versioned so a bad rule can be rolled back.
  • Never let one hot tenant or key consume the capacity of the whole limiter cluster.
  • Assume 100k rate-limit checks per second at peak and 20M active keys across users, keys, IPs, and tenants.
  • One token-bucket hash per active key; at roughly 100 bytes plus Redis overhead, 20M keys is a few GB, which fits a small Redis cluster.
  • Each check is one Redis round trip plus one Lua script, so the limiter's own capacity is bounded by Redis ops and network latency.
  • Keep counters only as long as the longest window plus a safety margin; a 1-day window needs a 25-hour TTL, not permanent storage.
  • Budget roughly 2-3 limiter checks per user request when both a global tenant limit and a per-route limit apply.

03API design

MethodPathPurpose
POST/v1/checkInternal endpoint used by gateway middleware: evaluate one key against the matching rules and return allow/deny plus headers.
GET/v1/usage/{key}Return current consumption, limit, and reset time for a key so support and customers can debug throttling.
POST/admin/rulesCreate a rule with scope, route, limit, window, burst, and failure mode.
PUT/admin/rules/{rule_id}Update an existing rule and bump its version so caches invalidate deterministically.
GET/admin/rulesList and filter rules by scope, route, or tenant for review and rollback.

04Data modelling

DecisionChoiceWhy
Counter storageRedis hash per key, mutated by a Lua script that refills and consumes in one atomic step.The read-modify-write must not race; a single script avoids lost updates and extra round trips, and Redis gives sub-millisecond local latency and TTL for free.
Key layoutrl:rule_id:scope:value, for example rl:r123:api_key:abc, with no Redis hash tag, so different tenants and rules spread across cluster slots.Each check touches one key, so cross-slot scripts are not needed; forcing related keys onto one slot would concentrate load and create a hot node.
Rule storageRules in a small SQL table as the source of truth, replicated to an in-process policy cache keyed by route and scope.The check path should not query a database; a versioned cache makes rule evaluation local while a pub/sub invalidation keeps it fresh within seconds.
AlgorithmToken bucket for most routes, with a fixed-window counter only for coarse daily quotas.Token bucket allows a controlled burst and enforces a smooth sustained rate, while daily quotas are cheaper and more intuitive as a window counter.
Failure fallbackPer-instance in-memory token bucket with conservative limits when Redis is unreachable, plus a circuit breaker.It keeps low-risk traffic flowing and bounds over-admission, but the local state is approximate and must never be the only enforcement for money-moving routes.
ObservabilityEmit counters and sampled decision events asynchronously; never write an audit row synchronously per check.A synchronous log write would multiply latency and couple availability to the metrics pipeline; sampling is enough to see deny rates and hot keys.

05Architecture

The gateway asks a local policy cache for the matching rule, then makes one atomic token-bucket call to Redis; a local bucket and metrics pipeline keep the check path alive when Redis or the rule store is unhealthy.
  • Run the check as gateway middleware or a sidecar so every request passes through it before touching application code; a separate network hop per service is easy to forget and bypass.
  • Load the matching rule from an in-process cache keyed by route and identity type; rebuild the cache on a version change delivered by pub/sub, not on every request.
  • Execute refill and consume in one Lua script. Read the clock inside Redis, not in the application, so multiple gateway hosts do not disagree about elapsed time.
  • Use token bucket state of tokens and last_refill_ms; on each check add elapsed time times the refill rate, cap at burst, and subtract one only if a token is available.
  • Set a TTL of window plus a safety margin on every key so idle keys disappear; otherwise memory grows with every IP that ever made a request.
  • Put a circuit breaker around Redis with a short timeout. When it opens, switch to the local fallback for routes marked fail-open and reject fail-closed routes immediately with 503, not 429.
  • Apply multiple rules in a defined order: global tenant limit first, then per-user or per-key, then per-route cost. Deny on the first failure and report which rule fired.

06Optimisation & trade-offs

DecisionGainCost / risk
Token bucketAllows a controlled burst and enforces a smooth long-run rate with only two numbers of state per key.A key can spend its whole burst instantly, so downstream capacity must tolerate that spike; the bucket is not a strict per-second guarantee.
Central Redis countersOne shared view across all gateway instances, so limits are accurate no matter which node serves the request.Every check pays a network round trip and Redis becomes a critical dependency; a hot key or cluster outage affects the whole fleet.
Local-only countersNo network hop and no shared failure domain, so the limiter is extremely fast and available.Each instance enforces its own limit, so the effective global limit is the per-instance limit times the fleet size and drifts as instances scale.
Fail-open for low-risk routesBrowsing and read traffic keep working when the limiter is down, which protects the user experience.A misbehaving client can overrun limits during the outage and pressure downstream services exactly when they are already fragile.
Fail-closed for sensitive routesLogin, payment, and expensive write paths cannot be abused when the limiter cannot make a decision.A limiter outage becomes a product outage for those flows; it needs a very high availability target and a tested manual override.
Sliding-window counterSmoother than a fixed window and much cheaper than storing every request timestamp.It is an approximation that can still allow a small burst at the boundary, and it needs two counters and a weighted calculation.
Gateway middlewareOne enforcement point that covers every route and cannot be bypassed by a forgotten service call.The gateway team owns policy plumbing, custom per-route logic is harder, and a gateway incident now affects all rate limiting.
  • Keep rule evaluation local and versioned so the common path is a map lookup plus one Redis call.
  • Cache the parsed rule per route in the gateway worker; avoid regex evaluation on every request.
  • Batch or pipeline limit checks when one request must satisfy several rules, rather than making one round trip per rule.
  • Use Redis Cluster so counters spread across nodes; each check touches one key, and a hot tenant can be split into several counter keys if one node saturates.
  • Return Retry-After based on the actual refill time, and add jitter guidance so clients do not retry in lockstep.
  • Sample decision logs at a low rate and aggregate per-rule allow/deny counts; do not log every allowed request.
  • Pre-warm policy caches and Redis connections before a known traffic spike, and load-test the limiter at the target peak rather than at average traffic.
  • Separate cheap request-count limits from expensive-operation quotas so a costly endpoint cannot be hammered within a generous request limit.

07Follow-ups — one-line answers

What happens if Redis is down? The circuit breaker opens, low-risk routes fall back to a conservative per-instance token bucket, and money-moving routes fail closed with 503 until Redis recovers.
Why use a Lua script instead of GET then SET? GET then SET has a race where two gateway hosts both read the same token count and both allow, so the refill and consume must be one atomic operation.
Why token bucket instead of fixed window? A fixed window lets a client send two full quotas around the boundary, while token bucket smooths the rate and still permits a bounded burst.
How do you enforce a global limit across regions? Enforce a regional share locally and reconcile a global counter asynchronously, or lease a block of quota from a central store so each region can spend without a cross-region call per request.
How do you handle a hot tenant key? Split its counter into N sub-keys, sum them for reads, and cap the tenant at the gateway so one key cannot saturate a single Redis node.
How do rule updates reach all gateways quickly? Write the rule with a new version, publish an invalidation event, and have each gateway reload the full rule set or the changed route within a few seconds.
What do you return to a throttled client? HTTP 429 with Retry-After, the applicable limit, remaining quota, and reset time, so well-behaved clients can back off instead of retrying immediately.
Can the check and the request race? Yes, because the token is consumed before the work finishes; for expensive operations use a reservation that is released on failure, or accept a small over-admission and enforce a concurrency limit separately.
How do you avoid clock skew affecting refill? Use Redis server time inside the Lua script and a monotonic elapsed calculation, never the application host clock.
How would you test it? Unit-test boundary cases for each algorithm, load-test at the target peak, and run chaos tests that kill Redis and confirm the intended fail-open or fail-closed behavior.
Should limits be per request or per unit of work? Charge weighted cost per endpoint, so a cheap read costs one token and an expensive export costs many, otherwise clients can bypass the intent of the limit with one heavy call.

08Traps

  • Using a read-then-write check without an atomic operation, which allows two gateway instances to admit the same last token.
  • Forgetting TTLs on counter keys, so Redis memory grows with every IP and one-off API key forever.
  • Making the limiter a synchronous database call, which turns a protection mechanism into the slowest and most fragile part of the request path.
  • Enforcing only at the public edge and leaving internal service-to-service calls unlimited, so a retry storm inside the network is never throttled.
  • Choosing fail-open globally, including for payments, or fail-closed globally, including for read-only browsing, instead of deciding per route.
  • Reporting a limit in headers that does not match the rule actually enforced, which makes client backoff behavior wrong and support tickets noisy.
