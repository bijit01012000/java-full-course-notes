JWT vs Server-side Sessions

Authentication appears in almost every system-design prompt, and the JWT-versus-session choice exposes whether you understand revocation, token storage, and browser threat models. Interviewers probe for a defensible default and a hybrid, not a slogan.

One-line answerDefault to server-side sessions for a first-party app, use short-lived JWTs when many services must verify identity locally, and keep refresh tokens opaque, rotated, and revocable.

01Requirements

Functional
  • Log a user in with credentials or an OIDC provider and issue a credential for subsequent requests.
  • Authenticate API calls and enforce scopes or roles per endpoint.
  • Refresh an expired access credential without forcing the user to log in again.
  • Log out one device or all devices, and revoke access after a password change or role change.
  • Support multiple services verifying identity without a per-request call to the auth service.
  • Rotate signing keys and publish the current public keys for verifiers.
Non-functional
  • Access-token lifetime is short, on the order of minutes, to bound the damage from theft.
  • Revocation takes effect within a defined window, and high-risk actions check current state and fail closed.
  • The auth service stays off the hot path for normal API calls.
  • Tokens are protected against XSS and CSRF according to the client type.
  • Signing keys rotate without breaking verification, with old keys kept until their tokens expire.
  • Auth failures return 401 and authorization failures return 403, with no token material in logs.
  • Assume 5M monthly users and 20M API requests/day: about 230 average RPS, with peaks several times higher.
  • Fifteen-minute access tokens mean at most 96 refreshes per continuously active user per day, far below request volume.
  • A 1 KB JWT travels on every request; at 1k RPS that is about 1 MB/s of extra header traffic, so keep claims small.
  • An opaque session lookup in Redis adds a sub-millisecond store hop but makes that store a shared dependency on every authenticated request.
  • A deny-list check at 1k RPS needs a highly available store; reserve it for high-risk actions rather than every read.
  • Refresh tokens live for days to weeks and are tracked server-side, so storage grows with active devices rather than request rate.

04Data modelling

DecisionChoiceWhy
Default credential for first-party webServer-side session with an opaque ID in a Secure, HttpOnly, SameSite cookieThe server can revoke it instantly and reason about it centrally, which is simpler than token revocation for a single application.
Access token formatShort-lived JWT with minimal claims: sub, iss, aud, exp, iat, jti, tenant, and scopesMany services can verify it locally without an auth-service call, while the short lifetime bounds the revocation gap.
Refresh tokenAn opaque random value, hashed at rest, tracked per device, and rotated on every use with reuse detectionThe auth server can revoke it, bind it to a device, and detect a stolen token when an old value is replayed.
RevocationPer-user token_version for global invalidation plus a jti deny list only for high-risk or immediate casesNormal reads stay stateless, while a role change, logout-all, or compromise can still invalidate tokens quickly.
Signing and key distributionRS256 or ES256 with a kid header and a cached JWKS endpoint; overlap old and new keys during rotationVerifiers can check tokens without holding a signing secret, and rotation does not require a synchronized redeploy.
Browser storageAccess token in memory and refresh token in a Secure, HttpOnly, SameSite cookie with CSRF protectionThis keeps the long-lived credential away from JavaScript while reducing, not eliminating, both XSS and CSRF exposure.

A hybrid design issues a short-lived JWT for API calls, keeps the refresh and optional session state server-side, and lets the edge verify tokens locally from a cached JWKS.
  • Verify the signature and then iss, aud, exp, and nbf with a small clock skew; a valid signature alone is not authentication.
  • Allowlist algorithms server-side and never let the alg header choose the verification method.
  • Cache JWKS by kid, refresh on an unknown kid with rate limiting, and keep old keys until their tokens have expired.
  • Treat claims as a snapshot: role changes need a token version bump or a server-side check for privileged actions.
  • Do not log Authorization headers, and keep access tokens out of URLs, analytics events, and crash reports.

06Optimisation & trade-offs

DecisionGainCost / risk
Server-side sessionsInstant revocation and a simple, centralized model.A shared session-store lookup on every request and another store to scale and keep available.
Stateless JWTsLocal verification with no auth-service hop on the hot path.Revocation is hard and claims go stale until the token expires.
Short access-token lifetimesA stolen token has a small usable window.More refresh traffic and a dependency on the auth server for renewal.
Asymmetric signingMany verifiers can check tokens without being able to mint them.More CPU and the JWKS and key-rotation machinery.
Symmetric signingSimple and fast, with one shared secret.Every verifier holds the signing secret, so one compromised service can forge tokens for all.
HTTP-only cookiesJavaScript cannot read the credential after an XSS bug.The browser sends it automatically, so CSRF protection is required.
Local storage for tokensEasy to use with an Authorization header and no CSRF exposure.Any XSS bug becomes full token theft.
Deny list or token versionImmediate revocation for high-risk cases.Reintroduces the per-request state lookup that JWTs were meant to remove.
  • Keep access tokens short-lived and refresh tokens long-lived, opaque, and rotated.
  • Verify JWTs locally at the edge and cache the JWKS to avoid an auth-service call per request.
  • Store minimal stable claims and fetch volatile profile data from a cache or service.
  • Use a session lookup only where immediate revocation matters, and keep that store highly available.
  • Enable refresh-token reuse detection to revoke an entire token family on theft.
  • Bind refresh tokens to a device and support revoke-all on password change.
  • Reuse TLS connections and HTTP/2 to amortize authentication overhead.
  • Use separate signing keys and issuers per environment so a staging token cannot work in production.

07Follow-ups — one-line answers

What problem does a JWT solve? It carries signed claims that many services can verify locally without a central session lookup, but it is a token format rather than an authentication protocol.
When would you choose sessions over JWTs? For a first-party app or monolith where immediate revocation matters and no third party needs to verify tokens, sessions are simpler and easier to invalidate.
What are the three parts of a JWT? Header, payload, and signature, each Base64URL-encoded and joined by dots, where the signature covers the encoded header and payload.
Is a JWT encrypted? Normally no, it is only signed and encoded, so anyone holding it can read the claims and no secret or sensitive personal data belongs in the payload.
HS256 versus RS256? HS256 shares one secret between issuer and verifier, while RS256 or ES256 lets many services verify with a public key without the ability to mint tokens.
How does a service verify a token from another service? It fetches and caches the issuer's JWKS, selects the key by kid, verifies the signature, and then checks exp, iss, aud, and the required scopes.
How does key rotation work without breaking clients? Publish the new public key, start signing with the new private key, keep the old key until all tokens it signed have expired, then remove it.
Why split access and refresh tokens? The short-lived access token limits theft, while the long-lived refresh token is sent only to the auth server and can be tracked, rotated, and revoked.
Where should a browser store a JWT? A common pattern is a short-lived access token in memory plus a refresh token in a Secure, HttpOnly, SameSite cookie, with CSRF protection.
How do you revoke a JWT before it expires? Use short lifetimes and refresh-token revocation for routine logout, plus a jti deny list or per-user token version for immediate cases.
Which claims must an API validate? Signature first, then exp and nbf with a small skew, iss against the expected issuer, aud against this API, and finally the scopes the operation requires.
What is the algorithm-confusion attack? An attacker sets alg to HS256 and signs a forged token using the issuer's public key as the HMAC secret, so verifiers must allowlist algorithms and never use a public key as an HMAC key.

08Traps

  • Treating a signed JWT as encrypted and putting secrets or sensitive personal data in the payload.
  • Validating only the signature and skipping iss, aud, and expiry checks.
  • Trusting the alg header or accepting alg none and RS256-to-HS256 confusion.
  • Issuing long-lived access tokens so a stolen token stays usable for days.
  • Accepting an OIDC ID token as an API access token.
  • Putting roles in the token and expecting permission changes to take effect immediately.
