Design a Chat Application

It combines a stateful real-time transport with durable ordered history, so it exposes whether you understand connection routing, sequence numbers, and reconnect recovery.

One-line answerTerminate WebSockets at a connection tier, persist every message with a per-conversation sequence before publishing it, and let reconnecting clients replay everything after their last seen sequence.

01Requirements

Functional
  • One-to-one and group conversations, with group sizes from a few users to a few hundred members.
  • Send and receive text, media, and small files in real time, with delivered and read receipts.
  • Show conversation history with pagination, plus an inbox ordered by most recent activity.
  • Support multiple devices per user, with the same messages and read state synchronized across them.
  • Deliver push notifications to offline users and replay missed messages when they reconnect.
  • Support online presence, typing indicators, and message edit or delete within a limited window.
Non-functional
  • Deliver a message to an online recipient in well under a second in the same region, with a p99 target around a few hundred milliseconds.
  • Preserve per-conversation ordering for all participants, and never lose an acknowledged message.
  • Deliver at least once and deduplicate on the client, so a retry does not create a second visible message.
  • Support around 10M concurrent connections and tens of thousands of message writes per second.
  • Keep history durable and readable for years, while keeping the hot path independent of the history store's query load.
  • Survive a connection-server failure without a mass reconnect that takes down the rest of the fleet.
  • Assume 50M daily active users sending 40 messages a day: about 2B messages per day, roughly 23k writes per second average and 3x that at peak.
  • At 10M concurrent connections and roughly 100k connections per tuned gateway, the connection tier needs on the order of 100 gateway nodes plus headroom.
  • A 300-byte average message plus indexes and replicas is roughly 1TB per day before compression, so history must be partitioned and aged out of hot storage.
  • Most conversations are small, but a 500-member group makes one send become 500 delivery decisions; fan-out cost is per recipient device, not per conversation.
  • Read receipts and typing events are far more frequent than messages, so they must be coalesced and must never be stored per event.

03API design

MethodPathPurpose
GET/v1/wsUpgrade to a WebSocket, authenticate the device, register the connection, and start receiving live events.

04Data modelling

DecisionChoiceWhy
Message storageA wide-column store partitioned by conversation_id and clustered by seq descending, with the message body stored once per conversation.History is always read by conversation in reverse order, so this makes a page a single partition range read and avoids copying one message into every member's mailbox.
OrderingAssign a per-conversation sequence by atomically incrementing next_seq on the conversation row, store it with the message under a unique (conversation_id, seq) constraint, and sort by seq.Timestamps and Snowflake ids can tie or skew across senders, while one durable sequence gives every participant the same total order and a simple cursor that survives a cache restart.
IdempotencyStore client_message_id in a dedupe table unique per conversation and return the existing message when the same id is retried.A mobile client that times out will retry, and without a dedupe key the recipient sees the same message twice; the database constraint also resolves two concurrent retries.
Inbox and per-user stateA per-user conversation summary sharded by user_id containing last_message_seq, unread_count, and a short preview; read receipts are a per-conversation watermark, and presence is a heartbeat-backed TTL key.The inbox query stays cheap and independent of history, a watermark avoids one receipt row per message, and presence is ephemeral enough not to need durable storage.
Connection routingA Redis registry mapping user and device to gateway with a short TTL, plus pub/sub channels for delivery.With many gateways the application must find the node holding a socket; TTL entries expire automatically when a gateway crashes.
MediaUpload directly to object storage with a pre-signed URL, send only the media id in the message, and serve through a CDN.Large binaries should not flow through the chat service or sit in the message row, and a CDN keeps repeated downloads off the origin.

The gateway holds sockets and looks up where a user is connected; the chat service persists the message with a conversation sequence, publishes it for live delivery, and falls back to a push queue for offline devices.
  • Use WebSockets because chat needs both directions frequently: sending, typing, and receipts travel client to server while messages and presence travel back. SSE would need a separate HTTP path for every send.
  • Split the connection tier from the application tier. The gateway authenticates, tracks heartbeats, and delivers bytes; the chat service owns membership, sequencing, persistence, and fan-out.
  • Save before send. Persist the message and its sequence, then publish to the gateway. Redis Pub/Sub does not retain messages, so a live publish alone can silently lose an update for a disconnected device.
  • On reconnect, the client sends its highest contiguous sequence per conversation and the server returns everything after it. Live and replayed messages are deduplicated by sequence on the client.
  • Route with a registry or per-user pub/sub. The registry approach sends only where needed but must be updated on every connect, disconnect, and gateway move; the pub/sub approach is simpler but broadcasts to all gateways.
  • Group fan-out is one write to the conversation store plus one delivery decision per member device. Resolve membership once per message and cache it briefly rather than querying per recipient.
  • Coalesce receipts and typing events: keep only the latest value per user and conversation, and send at most a few updates per second. Never persist typing events.

06Optimisation & trade-offs

DecisionGainCost / risk
WebSocketsLow per-message overhead and true bidirectional communication for sends, typing, receipts, and presence.Stateful connections are harder to load balance, need heartbeats and reconnect logic, and a gateway failure affects every socket it holds.
Save then publishA message is durable before anyone is told it exists, so a crash or a missed pub/sub event does not lose it.Adds a write before delivery latency and doubles the path length compared with fire-and-forget broadcast.
Per-conversation sequenceA simple total order and a stable cursor that every participant and device can use for catch-up.The sequence allocator is a per-conversation hot spot, and a failed allocation can stall sends for that conversation.
Store one copy per conversationStorage does not multiply by group size, edits and deletes are a single row update, and history has one source of truth.Delivery still fans out to every member, and a per-user mailbox view requires a separate inbox read model.
Per-device deliveryEvery device stays in sync and a user can move between phone and laptop without losing messages.Fan-out multiplies by device count, and read state must be reconciled across devices.
Watermark receiptsOne small update per user per conversation instead of one row per message, which keeps receipt traffic manageable.It cannot express per-message exceptions and relies on monotonically advancing sequence numbers.
Presence as best effortCheap, eventually consistent indicators that do not need a durable record or a transaction.A user may briefly appear online after a crash until the TTL expires, and presence can flap on unreliable networks.
  • Batch message inserts and sequence allocation for a busy conversation instead of one round trip per message.
  • Cache recent conversation history in the gateway or chat service so scrolling back a few pages does not hit the history store every time.
  • Use a separate read model for the inbox, updated asynchronously, so the inbox query never scans message partitions.
  • Compress and batch WebSocket frames for typing and presence, and avoid sending presence updates to users who are not viewing the conversation.
  • Back off reconnects with full jitter and spread clients across gateways, so one gateway failure does not create a synchronized reconnect storm.
  • Keep a small per-device outbound buffer and drop presence or typing updates before dropping message events when the client is slow.
  • Archive old messages to cheaper storage and keep a recent window hot; history pagination beyond the hot window can tolerate higher latency.
  • Use pre-signed uploads and CDN delivery for media, and send a placeholder message before the upload completes so the UI feels immediate.

07Follow-ups — one-line answers

How do you guarantee message ordering? Assign one monotonically increasing sequence per conversation on the write path and have every client and device sort by it.
What happens if a client disconnects and misses messages? On reconnect it sends its last contiguous sequence per conversation, and the server replays everything newer from durable storage.
How do multiple devices stay in sync? Every device gets its own connection and delivery, and read state advances by sequence watermark so a read on one device updates the others.
How does a group message reach 500 members? Write the message once, resolve membership once, then publish one delivery event per online member device and one push per offline user.
Is presence strongly consistent? No, it is best effort: a heartbeat refreshes a short TTL, so presence can be stale for a few seconds after a crash.
How do you prevent duplicate messages on retry? Require a client_message_id per send, enforce uniqueness per conversation, and return the original message when the same id arrives again.
What if a gateway with 50k connections dies? Clients reconnect with exponential backoff plus jitter to other gateways, and catch-up queries are bounded by sequence so the history store is not stampeded.
How are offline users notified? The chat service enqueues a push job after persisting the message, and a worker sends through APNs or FCM using the device token.
Why not use Kafka as the message store? Kafka is a delivery log, not a low-latency random-access history store; it is useful for fan-out and events, while message history needs indexed reads by conversation and sequence.
How do read receipts scale? Store only a per-user, per-conversation watermark, coalesce rapid updates, and broadcast the latest value rather than one event per message.
How would end-to-end encryption change the design? The server stores and routes ciphertext and cannot read message bodies, which breaks server-side search and requires per-device key management and encrypted group keys.
How do you paginate history? Use before_seq with a fixed limit and return a next cursor, so new messages do not shift the page and repeated reads are stable.

08Traps

  • Publishing a message over pub/sub before persisting it, so a subscriber crash or a disconnected recipient loses the message permanently.
  • Using wall-clock timestamps for ordering, which allows ties and clock skew to show messages out of order to different users.
  • Keeping one global sequence for all conversations, which creates a hot allocator and unnecessary contention.
  • Forgetting reconnect catch-up, so a user with a brief network drop silently misses messages even though the socket reconnects.
  • Fanning out group messages by copying the full body into every member's inbox, which multiplies storage and makes edits and deletes inconsistent.
  • Treating presence or typing indicators as durable messages, which adds write load for data that is useful for only a few seconds.
