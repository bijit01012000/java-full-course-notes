WebSockets vs SSE vs Polling

It tests whether you choose a transport from direction and freshness instead of naming a technology, and whether you know the second half of the problem: routing an update to the server that holds the connection.

One-line answerPick the transport from direction and freshness, then solve routing separately: polling for rare updates, SSE for one-way streams, WebSockets for frequent two-way traffic, with pub/sub or a connection registry to find the right server and sequence numbers to recover what was missed.

01Requirements

Functional
  • Deliver server-initiated updates to connected clients within a stated delay.
  • Support one-way workloads such as notifications, live scores, and token streaming.
  • Support two-way workloads such as chat, typing indicators, and collaborative editing.
  • Recover updates missed while offline, during a deploy, or across a network switch.
  • Expose approximate presence with a last-seen timestamp.
  • Fall back to a plain HTTP path where long-lived connections are blocked.
Non-functional
  • p99 delivery under about one second for online users, with catch-up bounded by one query.
  • Scale to millions of concurrent connections, sized by connections and file descriptors rather than requests per second.
  • No silent message loss: persist before publishing, and let clients replay from a sequence number.
  • Reconnects use exponential backoff with jitter so a server loss does not cascade.
  • Deploys drain connections gradually instead of dropping a server's worth at once.
  • Dead connections are detected by heartbeat, not by waiting for the next write to fail.
  • Assume 10M concurrent connections and about 50k connections per server, which implies roughly 200 connection servers before headroom.
  • Short polling at 1M users every two seconds is 500k requests per second, and almost all of them return nothing.
  • Heartbeats every 30 seconds across 10M connections is about 333k small messages per second, which is cheap per message but not free.
  • A room broadcast to 100k members is 100k deliveries per message, so rooms need pub/sub rather than per-user lookups.
  • Catch-up after a reconnect must be indexed by (channel_id, seq) so replay is a range scan, not a scan of the conversation.

A separate connection tier holds sockets, pub/sub or the registry finds the right server, and every update is persisted with a sequence number so a reconnecting client can catch up.
  • Name both halves before choosing anything: the client transport, and the backend routing that finds the server holding the recipient's socket.
  • Polling keeps servers stateless and any server can answer; SSE and WebSockets pin a user to one server for the life of the connection, which changes deploys and scaling.
  • Separate the connection tier from business logic so connection count and request throughput scale independently.
  • Save first, then publish. Pub/sub is fire-and-forget, so an offline or slow client silently loses anything not persisted.
  • Sequence numbers give ordering, deduplication, and a resumable cursor with one mechanism.
  • The dangerous moments are deploys and mass disconnects: drain connections gradually and make clients reconnect with backoff plus jitter.

06Optimisation & trade-offs

DecisionGainCost / risk
Short pollingTrivial to build, stateless servers, works everywhereWasted requests and battery, with delay bounded by the interval
Long pollingNear-instant updates over plain HTTP that passes restrictive proxiesOne held connection per client and full HTTP overhead per update
SSESimple one-way streaming with browser-managed reconnection and Last-Event-IDText only, one-way, and about six connections per domain on HTTP/1.1
WebSocketsLow-overhead two-way messaging for chat, games, and collaborationStateful connections that complicate deploys, load balancing, and reconnect logic
Separate connection tierConnections and business logic scale independentlyAnother stateful service to deploy, drain, and monitor
Connection registryPrecise targeting and easier debugging of where a user is connectedA mapping to maintain and expire on every connect, disconnect, and move
Pub/sub routingSenders stay ignorant of topology and rooms fan out with one publishFire-and-forget delivery that depends on broker health
Save-first with sequence numbersMissed updates are recoverable and duplicates are detectableA database write and a catch-up read path on every update
  • Choose the cheapest transport that meets the freshness target; do not reach for WebSockets when SSE or polling is enough.
  • Persist with a sequence number, publish best effort, and let reconnect resolve any gap with one indexed range query.
  • Use pub/sub rooms for group fan-out and a registry only where precise per-user targeting is needed.
  • Send heartbeats around every 30 seconds and treat silence or a failed write as a dead connection.
  • Client reconnect with exponential backoff and jitter, capped, plus a resume token so retries are cheap.
  • Drain connection servers gracefully on deploy and let clients reconnect to peers instead of all at once.
  • Raise file-descriptor limits and size the tier by concurrent connections and memory per connection.
  • Batch or compress small frames and avoid a database read per delivered message; hydrate bodies from cache.

07Follow-ups — one-line answers

Why can't the server just push over plain HTTP? HTTP is request-response, so once the response is sent there is no open channel; every technique either reopens requests or keeps a connection open.
What are the two parts of a real-time design? The client transport (polling, SSE, or WebSockets) and the backend routing that finds the server holding the recipient's connection.
When is short polling good enough? When updates are rare and a few seconds of delay is acceptable, such as checking whether a background export finished.
SSE or WebSockets? SSE when data flows only server to client and you want automatic reconnection over ordinary HTTP; WebSockets when the client also sends frequently.
What are the limits of SSE? It is one-way and text-only, limited to about six connections per domain on HTTP/1.1, and EventSource cannot set custom headers, so auth uses cookies or a short-lived URL token.
How does SSE reconnect work? The browser reconnects automatically and sends Last-Event-ID, so the server replays everything after that id from stored events.
How does an update reach a user connected to another server? Look up the user's server in a connection registry and send directly, or publish to a channel that the user's connection server subscribes to.
What limits one connection server? Usually memory and open file descriptors, not CPU, since every connection holds a socket and buffers, so capacity is measured in connections.
How do you handle users who were offline? Persist every update with a sequence number, notify through APNs or FCM, and have the client fetch everything after its last sequence when it reopens.
What is a reconnection storm? When a server dies, all its clients reconnect at once and overload the survivors and the database, so clients need backoff with jitter and deploys need draining.
How do you deploy a WebSocket fleet? Drain one server at a time: stop accepting new connections, let existing ones finish or migrate, then terminate, while clients reconnect with jitter to healthy peers.
What do you monitor? Concurrent connections, connect and disconnect rate per server, publish latency, catch-up query load, heartbeat failures, and reconnect rate.

08Traps

  • Designing the client transport and forgetting that the backend must find the server holding the recipient's connection.
  • Saying WebSockets are required for real-time when updates are one-way and SSE is simpler.
  • Forgetting that pub/sub is fire-and-forget, so an offline or slow client silently loses updates.
  • Not persisting updates before delivery, leaving no way to catch up after a disconnect.
  • Sizing connection servers by requests per second instead of concurrent connections and file descriptors.
  • Letting all clients retry immediately after a failure and turning one lost server into a cascade.
