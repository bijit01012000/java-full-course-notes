Diagramming Tips

A diagram is a communication tool, not art. It should make the request flow easier to follow and leave a clear record of your decisions.

01Why the diagram matters

  • It makes your explanation easier to follow by showing how components fit together.
  • It is a visual record of your decisions; interviewers may refer back to it when evaluating you.
  • It exposes missing pieces early: no entry point, no data store, no async path, no failure handling.
  • It keeps you from repeating yourself; point to the diagram instead of re-describing every box.
  • A clear diagram supports a stronger narrative; a messy one makes a good design look weaker.

02Get comfortable with the drawing tool

  • Virtual interviews often use Excalidraw, Miro, or a company whiteboard; onsites may use a physical board.
  • Ask the recruiter which tool will be used and practise with it beforehand.
  • Know how to create boxes, add labels, connect arrows, move groups, add notes, and change colours.
  • Ten minutes of practice can save you from fumbling with basic controls during the interview.
  • On a physical whiteboard, start small and leave space on the right and bottom for expansion.
Interview line: “I’ll build the diagram one request at a time and label the paths as I go.”

03Plan your layout

  • Left: clients and user entry.
  • Next: API gateway or load balancer.
  • Middle: application services.
  • Right: databases, caches, object storage, and queues.
  • Leave room for a queue between services or a cache in front of a database discovered during the deep dive.
  • Reserve space at the top or side for requirements, traffic estimates, and API definitions.
Default: left-to-right follows the natural request flow and is easiest for an interviewer to follow.

04Keep requirements and APIs visible

  • Write down 2–4 core requirements in short phrases.
  • Note non-functional targets: latency, availability, consistency, scale.
  • List the main APIs next to the diagram: method + path + purpose.
  • Use these notes during the deep dive: “This async fan-out is acceptable because the feed only needs eventual consistency.”
  • At the end, revisit each requirement and confirm the design addresses it.
Example notes: “POST /posts”, “GET /feed”, “Feed p99 < 200 ms”, “Eventual consistency allowed”, “100k feed reads/sec”.

  • Specific labels explain what the component stores or does and which technology it uses.
  • Data stores: add key fields, e.g. “Posts: post ID, author ID, content, created_at”.
  • Shapes: rectangles for services, cylinders for databases/caches, solid arrows for synchronous calls, dashed arrows for async.
  • Consistency: stick to one convention; add a small legend if needed.
  • Do not show the entire schema; show enough to explain the design.

06Draw arrows that explain the flow

  • Direction: draw the arrow in the direction of the request; the response is usually implied.
  • Label non-obvious interactions: “Read feed”, “Publish post event”, “Write post”.
  • Solid vs dashed: solid for synchronous calls; dashed for asynchronous messages.
  • Number multi-step flows: 1 request → 2 save → 3 publish → 4 consume → 5 update feed.
  • Avoid crossing arrows where possible; crossing lines hide the flow.
  • If the line style is not obvious, add a legend.
Trap: unlabeled arrows between generic “Service” boxes. The interviewer cannot tell whether it is a read, a write, or an event.

07Build the diagram one request at a time

  1. Start with the main write API: client → gateway → service → database.
  2. Explain each component as you add it: auth, validation, persistence.
  3. Move to the read API: client → service → cache → database on miss.
  4. Reuse components already on the canvas; do not redraw duplicates.
  5. Add async work when the write flow needs it: service → queue → worker → cache.
  6. Number the arrows for multi-step flows.
This narration is the interview: the diagram is the visual aid; your explanation is the answer.

08Show read and write paths separately

Many systems are read-heavy; showing both paths exposes where the cache sits and which path is asynchronous.

  • Place the write path on top and the read path below, or use different colours.
  • Show where async work enters: post service → queue → fan-out workers → feed cache.
  • Show the read fallback: feed service → cache; on miss, database.
  • This exposes the key design decision: precomputed feeds vs read-time assembly.

09Update the diagram during deep dives

  • Add detail when the interviewer drills into a component: indexes, replication, partitions, retries.
  • Do not redraw the whole system; extend the relevant part.
  • Label the new detail and explain why it exists.
  • Keep the high-level view visible so the interviewer does not lose context.
  • If the design changes, update the diagram instead of describing a contradictory one.

10Leave out what doesn't matter

  • Do not draw login, profile settings, or admin screens unless they are part of the question.
  • Do not add components you cannot explain or defend.
  • Keep notes short; the diagram is not a specification document.
  • Omit implementation details that do not change the architecture.
  • Clarity beats completeness: a smaller, coherent diagram is stronger than a crowded one.

11Two common mistakes

Too many boxes: the interviewer cannot tell what matters. Start with the main request path and add depth only when needed.
No flow: boxes with unlabeled arrows are not a design. Explain what moves, in which direction, and whether it is synchronous.
  • Inconsistent shapes: rectangles and cylinders used for the same thing.
  • Unlabeled data stores: “DB” with no indication of what it stores.
  • Arrows crossing through boxes, making the path unreadable.
  • Drawing everything before explaining anything.

✓Recap

  • Layout: clients left, entry point next, services middle, data right.
  • Notes: requirements and APIs visible throughout.
  • Labels: specific; shapes consistent; data stores show key fields.
  • Arrows: direction of request; label non-obvious flows; solid vs dashed for sync/async.
  • Build one request at a time; separate read and write paths.
  • Update during deep dives; omit what does not matter.
Final check: can the interviewer trace one write and one read through your diagram without asking where anything goes?
