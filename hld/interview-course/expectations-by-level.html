01Same question, different expectations

A mid-level engineer and a staff engineer may both be asked “Design a chat application.” The difference is what the interviewer expects the answer to demonstrate.

  • Entry: can explain the basic components and request flow.
  • Mid: can produce a complete working design for the core requirements.
  • Senior: can lead the discussion and proactively address the hard parts.
  • Staff: can connect the design to product priorities, operations, migration, and future needs.
  • A design that is strong for mid-level may be insufficient for senior; a staff-level answer may be unnecessary for a mid-level interview.
Interview line: “I’ll aim for a complete working design first, then go deeper on the bottlenecks that matter for this role.”

03Entry-level

  • Many companies do not run a separate system design round for new graduates.
  • When they do, questions are simpler: design a basic service, extend code to a larger dataset, or trace a request from browser to database.
  • Expected: understand the fundamental components and how they work together.
  • Know when a relational database fits, why caching helps, and why a load balancer is useful.
  • Not expected: consensus algorithms, multi-region failover, or deep distributed-systems internals.
  • The priority is clear explanation and reasoning through an unfamiliar problem.

04Mid-level

The main expectation: design a complete system that meets the core requirements, and explain how the components work together.

  • Clarify requirements and choose appropriate components.
  • Explain every component you add: what it stores, why it is needed, and how it fits.
  • Describe the main request flow end to end.
  • Some guidance is normal: the interviewer may point out a traffic spike and expect you to reason through it.
  • Cover the core requirements before optimizing. A working design is better than a half-finished advanced one.

Example: chat application

  • Core requirements: one-to-one messaging, real-time delivery, conversation history.
  • Components: WebSocket connections, message database, connection registry (e.g. Redis) mapping users to chat servers.
  • Flow: Alice’s server stores the message, acknowledges the sender, looks up Bob’s server, and forwards the message.
  • If Bob is offline, the message stays stored and is retrieved when he reconnects.
  • Failure cases can be discussed, but the priority is a complete, coherent design.
What strong mid-level sounds like: “Here is the complete flow, here is why each component exists, and here is one trade-off I considered.”

05Senior

Senior candidates are expected to go beyond “it works”: lead the discussion, find the hard parts, and defend the decisions.

  • Lead: clarify requirements, sketch quickly, identify challenges, and propose where to go deeper.
  • Technical depth: explain database choice, partitioning, failure behavior, and scale limits.
  • Trade-offs: if you add a cache, explain what you gain, how stale data can get, and whether that is acceptable.
  • Proactive: bring up the bottleneck before the interviewer does.
  • Failure modes: what happens when a component dies, slows down, or becomes a hot spot.

Example: chat application

  • Message ordering: route a conversation through a designated server that assigns sequence numbers; handle failover without conflicting numbers.
  • Storage growth: partition messages by conversation ID; consider hot conversations and distribution.
  • Failure: what happens when the ordering server or a chat server dies?
  • Trade-off: routing through one server simplifies ordering but can create a bottleneck.
Habit: once the design works, ask “What breaks first as this grows?” Then answer it before the interviewer asks.

06Staff

Staff-level interviews add product judgment, operational realism, migration thinking, and ambiguity.

  • Prioritization: which problems matter most for the product, which can wait, and why.
  • Operations: deployment strategy, monitoring, alerting, failure recovery, and cost.
  • Evolution: what to build first, when the complex design becomes necessary, and how to migrate without disruption.
  • Ambiguity: unusual constraints, open requirements, and choosing which areas to explore.
  • Multi-team impact: platform concerns, shared ownership, and long-term maintenance.

Example: chat application

  • Production behavior: WebSocket reconnects during deploys can overload servers; drain connections and add randomized reconnect delays.
  • Reliability: track delivery latency and alert before users are broadly affected.
  • Future requirements: group messaging, multi-region, end-to-end encryption — each changes the architecture.
  • Product context: internal chat and a consumer app with hundreds of millions of users need different trade-offs.

07How to prepare

LevelPreparation focus
Mid-levelBuild strong fundamentals; practise a complete high-level design in ~20 minutes; understand every component and the main request flows.
SeniorPractise leading; identify bottlenecks, failures, and trade-offs proactively; understand common technologies and their failure modes.
StaffPractise real engineering judgment: deployments, monitoring, migrations, cost, prioritization, and ambiguity.
Practice method: design the same problem at two levels. First produce a complete mid-level design; then add the senior deep dives; then add staff-level operational and product concerns.

08For a 3–5 YOE candidate

Most 3–5 YOE candidates are interviewed around the mid-level bar, sometimes with senior-leaning expectations depending on the company and role.

  • Must have: a complete design for core requirements, clear component roles, and one end-to-end request flow.
  • Must have: basic estimates, failure handling, and at least one explicit trade-off.
  • Should have: proactive identification of one bottleneck and a reasonable mitigation.
  • Nice to have: deeper database/cache/queue internals and operational awareness.
  • Do not optimize for: staff-level multi-team strategy or exotic technologies you cannot defend.
  • Common failure: a broad but shallow design with no completed flow, or a deep dive that never returns to the whole system.
Target answer shape: requirements → high-level design → one complete write flow → one complete read flow → bottleneck → trade-off → failure mode.

!Traps

  • Preparing only for the level you want, not the level you are interviewing for.
  • Producing a broad design with no completed end-to-end flow.
  • Going deep on an advanced topic before covering core requirements.
  • Waiting for the interviewer to identify every bottleneck.
  • Listing technologies without explaining the trade-offs.
  • Ignoring operations, failure handling, and cost at senior level.
  • Over-engineering a mid-level answer with staff-level concerns.
