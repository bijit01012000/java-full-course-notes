01Where this pattern shows up

Many interview problems are read-heavy: something is written once and then read constantly. The same design pressure appears across very different products.

  • A URL shortener creates a link once and may redirect on it millions of times.
  • A social feed writes a post once and reads it for every follower who opens the app.
  • A video page changes its title, description, and view count rarely but loads them on every view.
  • An e-commerce product page is updated occasionally and viewed far more often.
  • A ticket event page is bought from once but checked continuously by thousands of users before the sale.
  • Read-to-write ratios of 100:1 or higher are common, and popular content can be far more lopsided.
  • The goal is not to make the database generally faster, but to keep most reads away from it.

02Why reads become a problem

Take a URL shortener handling 1 billion redirects per day. That averages roughly 11,500 reads per second, and peak traffic at about three times the average is roughly 35,000 reads per second.

  • If every redirect goes to one database, every query consumes CPU, memory, and sometimes disk reads on that server.
  • Depending on hardware and query shape, a single database usually handles somewhere between a few thousand and a few tens of thousands of simple queries per second.
  • At 35,000 reads per second, one database is not enough: queries queue, response times rise, and requests start timing out.
  • Throughput is not the only limit. User-facing reads have a latency budget of tens of milliseconds, and a query queued behind thousands of others misses it.
  • Database capacity is expensive because it bundles CPU, memory, storage, replication, and backups; serving a repeated read from memory or a CDN costs far less per request.
  • The practical objective is to reduce database load, not merely to add capacity somewhere in the stack.
1B redirects/day→~11,500 reads/sec average→~35,000 reads/sec peak→Single database saturates

03Start with the database itself

Before adding caches or replicas, check whether the database is being used efficiently. Fixing queries reduces load without adding a single new component.

  • A missing index turns a point lookup into a full table scan, which gets worse as the table grows.
  • An index makes the same lookup take only a few reads even when the table has billions of rows.
  • The N+1 query problem turns one page load into dozens of queries, multiplying database work invisibly.
  • Oversized result sets and repeated aggregations waste capacity that caching would otherwise have to compensate for.
  • Use EXPLAIN ANALYZE to see whether a query uses an index and how many rows it actually touches.
  • In an interview, mention that indexes and query shape were checked before you reached for infrastructure.

Indexes

  • Index the columns used for lookup, filtering, and joins.
  • For multi-column filters, a composite index should put filter columns first and sort columns after them.
  • Indexes are not free: every write must update every index, so keep only those the queries use.
  • Verify with the query plan rather than assuming an index is being used.

The queries themselves

  • Replace N+1 patterns with a JOIN or a batched IN (...) fetch.
  • Add LIMIT and paginate instead of returning a large result set.
  • Precompute expensive aggregations instead of recomputing them on every read.
  • Measure the number of queries per page, not just the latency of each query.
ProblemFix
Full table scanAdd an index on the lookup column
N+1 queriesUse a JOIN or batch fetch with IN (...)
Large result setAdd LIMIT and paginate
Expensive aggregation on every readPrecompute it

04Read replicas

Once queries are efficient, the next step is to spread reads across more machines. Replicas copy the primary and serve read traffic while all writes still go to one place.

  • All writes go to the primary, which streams changes to one or more replicas.
  • Reads can be routed to any replica, so read capacity grows with the number of replicas.
  • If one database handles 10,000 reads per second, a primary plus four replicas gives roughly 50,000 reads per second in total.
  • Scaling is not perfectly linear: every replica must apply every write and adds storage and operational cost.
  • Routing can live in the application, or in a proxy such as ProxySQL that splits queries by type.
  • Replicas do not help when load is concentrated on one row; a popular item hits every replica equally.
  • Replicas also provide failover capacity, but they do not increase write throughput.
Writes → primary→Primary streams changes → replicas→Reads → any healthy replica

05Replication lag and read-your-writes

Most systems replicate asynchronously: the primary confirms a write once it is durable locally, without waiting for replicas. The result is a short window where a replica is behind.

  • Lag is usually milliseconds, but under heavy load a replica can fall seconds behind.
  • Synchronous replication removes most lag but makes every write wait on a replica, raising write latency and letting a slow replica block writes.
  • That is why asynchronous replication is the common default, with lag treated as a design constraint.
  • A user who updates a profile picture and immediately reloads may see the old picture and conclude the update failed.
  • This is the read-your-own-writes problem: a consistency guarantee that replica routing silently breaks.
  • Ask which reads must be fresh and which can tolerate a second or two of staleness; do not apply one rule to everything.
FixHow it worksTrade-off

Replication lag is a consistency budget, not just an operations metric. Decide the budget per endpoint.

06Caching and cache-aside

Replicas add capacity, but every read still runs a full database query. A cache avoids that query for most reads, which is why it is usually the first new layer to add.

  • A cache stores frequently read data in memory, typically in Redis or Memcached.
  • A memory read is often under a millisecond, far faster than a database query.
  • The cache absorbs repeated reads of the same data, which is exactly the read-heavy pattern.
  • Caching works best when a small set of data receives most of the traffic.
  • A cache is not a source of truth: losing it should degrade performance, not correctness.
  • The hard part is not reading from the cache, but keeping it consistent with the database.

Cache-aside

  • On a request, check the cache first.
  • On a hit, return the cached value immediately.
  • On a miss, read from the database, store the result in the cache with a TTL, then return it.
  • The application owns both the read path and the invalidation logic.
GET /a1B9xQ→GET link:a1B9xQ from cache→Miss → SELECT from database→SET link:a1B9xQ with TTL→Return redirect

The cache hit ratio

  • The hit ratio is the percentage of reads served from the cache, and it decides how much load reaches the database.
  • At 35,000 reads per second and a 95% hit ratio, only 5% miss: about 1,750 reads per second reach the database.
  • At a 90% hit ratio the database sees 3,500 reads per second — twice as many for a small change in the ratio.
  • Stating an expected hit ratio is far more convincing in an interview than saying "add a cache".

What to cache

  • Good candidates are read often, change rarely, and tolerate a little staleness.
  • Short-link mappings, product details, posts, profiles, and configuration data fit.
  • Bank balances, checkout prices, and one-time authentication tokens do not.
  • Data that is rarely read gains nothing but adds invalidation work.

07Keeping the cache up to date

Caching creates two copies of the same data. When the database changes, the cache can still hold the old value, so you need an invalidation strategy.

  • TTL expires an entry after a fixed time; simple, but users can see old data until it expires.
  • Delete on write removes the entry when data changes, so the next read reloads the new value.
  • Deleting is usually safer than writing the new value into the cache: racing writes can leave the older value behind, while a delete forces a reload from the database.
  • In practice, use both: delete on write and keep a TTL so a missed delete still expires eventually.
  • Write-through updates the cache in the same write path, keeping it fresher but slowing every write and raising a partial-failure question.
  • Event-based invalidation publishes a change event so each service deletes its own copy, which helps when many services cache the same data.

08Cache stampedes

A popular entry expiring can be worse than a cold cache. Suppose a trending video page is cached and tens of thousands of users request it every second. When the entry expires, every request misses at the same instant and runs the same query.

  • All of those misses hit the database simultaneously with the identical query.
  • The database sees a sudden spike that can overload it even though average load was fine.
  • The event is a cache stampede: one expiry, many concurrent rebuilds.
  • The risk grows with popularity, so it matters most for exactly the data you most want to cache.
  • Prevention is about ensuring only a small number of rebuilds happen, not about making the rebuild faster.
TechniqueHow it worksTrade-off
Lock on rebuildOne request reloads the entry; the rest wait or get the old valueWaiting requests add a little latency
Background refreshPopular entries are reloaded before they expireExtra work for entries that are no longer read
TTL jitterRandom variation spreads expirations over timeDoes not help a single hot key on its own
Hot entry expires→All requests miss→Same query hits the database→Lock / refresh / jitter prevents the pile-up

09Hot keys

Even a healthy cache can be defeated by one key. In a distributed cache, each key lives on one cache server, so a single extremely popular key sends all of its traffic to one node.

  • A celebrity post, a viral video, or a flash-sale product can concentrate reads on a single key.
  • That key's cache server becomes the bottleneck while other cache servers sit mostly idle.
  • Adding more cache servers does not help, because the traffic is on one key rather than spread across many.
  • One fix is to store several copies of the key with suffixes such as post:123:copy1 and pick one at random per read.
  • The suffixed keys hash to different servers, splitting the load; on a write, every copy must be deleted.
  • Another fix is a small in-process cache on each application server, so most reads never reach the cache cluster.
  • Local copies can be slightly stale, so give them a very short TTL.
  • Negative caching short-lived "not found" results stops requests for deleted or invented keys from reaching the database.

10CDNs and edge caching

Everything so far still sends the request to your infrastructure. For responses that are the same for every user, a CDN can answer before the request ever reaches your data center.

  • A CDN stores copies of content on servers around the world, close to users.
  • It is standard for images, video, JavaScript, and CSS, but it can also cache full pages and API responses when the response is identical for everyone.
  • A user in India can be served by a CDN node in India, reducing origin load and improving latency for distant users.
  • Cache-Control tells both the browser and the CDN how long a response may be reused.
  • s-maxage applies only to shared caches, letting the CDN hold a response longer than the browser.
  • stale-while-revalidate lets the CDN serve the old copy briefly while fetching a fresh one in the background.
  • The main risk is caching something personal; anything user-specific must be marked private or split into a public shell plus a small private fragment.

11Precomputing results

The techniques so far make each read cheaper by storing its result somewhere faster. Another approach is to do the expensive work at write time so reads become simple lookups.

  • Building a home feed at read time means looking up every followee, fetching recent posts, and sorting — a lot of work per read.
  • Fanout on write instead adds a new post to each follower's precomputed feed when it is published, so opening the app reads one list.
  • Accounts with millions of followers make write-time fanout too slow, so many systems use a hybrid: normal accounts fan out on write, very large accounts merge at read time.
  • Counters follow the same idea: keep a like count and update it on each like instead of counting rows on every view.
  • Materialized views and denormalized tables store the result of an expensive join or aggregation inside the database.
  • Precomputation makes writes more expensive and uses more storage, which is usually a good trade when reads far outnumber writes.

12Putting the layers together

A read request should fall through layers from cheapest and closest to most expensive and authoritative, so each layer absorbs part of the traffic.

  • The CDN answers first if it has the response.
  • On a CDN miss, the request reaches the application server, which may check its in-memory cache.
  • On a local miss, it checks the distributed cache such as Redis or Memcached.
  • Only if that misses does it reach a read replica, or the primary when fresh data is required.
  • In one worked example, a CDN serves 60% of 35,000 reads/sec, local caches 30% of the rest, and Redis 95% of what remains — leaving roughly 490 reads/sec for the database.
  • Every layer is another place where data can be stale, so each needs its own staleness budget and update mechanism.
  • The exact percentages depend on how cacheable the traffic is; the point is the shape of the funnel, not the specific numbers.

13Discussing high read traffic in an interview

Follow a fixed order so every component you add is tied to a requirement or number you established earlier.

  • Clarify requirements: read-to-write ratio, peak reads per second, freshness needs, and whether responses are user-specific.
  • Estimate peak read load to decide whether one database is enough.
  • Add caching, and say what you cache, how you invalidate it, and what hit ratio you expect.
  • Add read replicas for reads that miss the cache, and explain how you handle replication lag.
  • Add a CDN for content that is identical for all users.
  • Discuss edge cases such as stampedes and hot keys, especially for data that can suddenly become popular.
  • Tie each component to the problem it solves rather than listing technologies.

14Key takeaways

  • Start with efficient queries and indexes; they cut load without adding infrastructure.
  • Cache frequently read data, and use the hit ratio to reason about what still reaches the database.
  • Keep the cache fresh with delete on write plus a TTL as the default combination.
  • Add replicas for reads that miss the cache, and handle lag for users who just wrote.
  • Use a CDN for content that is identical for every user, including public pages and API responses.
  • Precompute expensive reads such as feeds and counters when reads dominate writes.
  • Plan for popular data: stampedes and hot keys can overload a single node even when the overall design is sound.
  • At every layer, state how stale the data may be and how it gets updated.

↔Trade-offs to say out loud

  • Indexes make reads fast but add work to every write, so a write-heavy table should keep only the indexes it needs.
  • Read replicas add read capacity and failover but scale sub-linearly, because every replica applies every write and costs storage and operations.
  • Asynchronous replication keeps write latency low but introduces lag and read-your-own-writes anomalies; synchronous replication does the reverse.
  • Caching removes most database reads but adds staleness, invalidation logic, and a second copy of the truth to reason about.
  • Delete-on-write plus TTL is simple and safe but leaves a brief window of staleness and relies on the delete actually happening.
  • Write-through caching keeps the cache fresher but slows every write and raises the question of what happens when the cache write fails.
  • CDN caching offloads the origin and improves latency but risks serving personalized data unless responses are carefully marked and segmented.
  • Precomputing and fanout on write make reads cheap but shift cost to writes and storage, and need a hybrid for very large accounts.
  • Local in-process caches are the fastest layer but are per-instance, hard to invalidate, and only safe with very short TTLs.

?Interview questions

Answer aloud before opening the outline.

1. How do you know reads are the real bottleneck?

Measure the read-to-write ratio, peak reads per second, database CPU and I/O, query latency percentiles, and cache hit ratio. If the database saturates on read queries while writes are modest, reads are the bottleneck.

2. What would you fix before adding a cache or replicas?

Indexes, query shape, and result-set size. A missing index causes a full table scan, and N+1 queries multiply one page load into dozens of queries. Both fixes reduce load without new infrastructure.

3. How do read replicas scale reads, and why is it not linear?

Writes go to the primary, which streams changes to replicas that serve reads. Adding replicas adds read capacity, but every replica must apply every write and costs storage and operations, so throughput does not scale perfectly.

4. Why don't read replicas fix a single popular row?

Every replica receives the same read for that row, so each one does the same work. The load is concentrated on one item, not spread across machines. That case needs caching or key replication instead.

5. What is replication lag and when does it hurt?

It is the delay before a write on the primary becomes visible on a replica. It hurts read-your-own-writes: a user updates data, reloads from a lagging replica, and sees the old value. Fixes include routing that user's reads to the primary briefly, always reading their own data from the primary, or monitoring lag and removing slow replicas.

6. Walk me through cache-aside.

Check the cache. On a hit, return the value. On a miss, read from the database, store the result in the cache with a TTL, and return it. The application owns both the read path and invalidation.

7. Why is the cache hit ratio the number that matters?

It determines how much load reaches the database. At 35,000 reads per second, a 95% hit ratio leaves about 1,750 reads per second for the database; 90% leaves 3,500. Small changes double the database load, so the ratio must be part of the design, not an afterthought.

8. TTL or delete-on-write?

Use both. Delete on write so the next read reloads fresh data, and keep a TTL so a missed delete still expires eventually. Deleting is safer than writing the new value into the cache because racing writes can leave the older value behind.

9. What is a cache stampede and how do you prevent it?

A popular key expires and every concurrent request misses and runs the same query. Prevent it with a lock so one request rebuilds while others wait or get the old value, background refresh of popular entries before expiry, or TTL jitter to spread expirations.

10. How do you handle a hot key in a distributed cache?

Replicate the key under several suffixed names that hash to different cache servers and pick one at random per read, deleting all copies on write. Alternatively keep a very short-TTL copy in each application's memory so most reads never reach the cache cluster.

11. When would you use a CDN for API responses?

When the response is identical for every user and can tolerate a short TTL, such as a public product page or article. Use Cache-Control with s-maxage and stale-while-revalidate, and keep user-specific data private or in a separate request.

12. What is fanout on write and what is its limit?

Precomputing each follower's feed when a post is created, so reading the feed is one lookup. It fails for accounts with millions of followers because writing to every feed is too slow, so systems often fan out normal accounts on write and merge large accounts at read time.

13. What does the full read path look like?

CDN, then application in-memory cache, then distributed cache, then read replica, then the primary when fresh data is required. Each layer absorbs traffic so only a small fraction of reads reaches the database.

14. What would you monitor?

Cache hit ratio, database queries per second and latency percentiles, replica lag, cache eviction and memory pressure, origin and CDN hit rates, error rate, and per-key request skew for hot keys.

!Traps

  • Adding a cache before checking for a missing index or an N+1 query pattern.
  • Assuming read replicas are strongly consistent and routing every read to them.
  • Caching user-specific data at the CDN because the page looked public.
  • Adding a cache with no invalidation strategy, then being surprised by stale data.
  • Ignoring cache stampedes on the one key that is popular enough to matter.
  • Trying to fix a single hot key by adding more cache servers.
  • Claiming replica throughput scales linearly with replica count.
  • Caching data that is rarely read, adding invalidation cost for no benefit.
