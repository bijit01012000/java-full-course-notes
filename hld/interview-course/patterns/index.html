Scaling Under Load

4 topics
01 Scaling Read TrafficRead-heavy systems should serve most requests from memory or the edge, so only a small fraction of reads ever reaches the database — but every layer you add introduces its own staleness and failure modes. → 02 Scaling Write TrafficWrites are harder to scale than reads because every write must be durably stored, applied to indexes, and replayed to replicas — so the fix is to make each write cheaper, write fewer of them, absorb bursts, and eventually spread them across shards. → 03 Handling Hot KeysA system can have plenty of aggregate capacity and still fail when too much traffic lands on one key — the fix is to spread, replicate, coalesce, or split that key rather than adding more nodes. → 04 Absorbing Traffic SpikesA spike is a short, extreme deviation from normal load, so the design goal is to absorb or reject excess traffic without letting it cascade — not to provision forever for a peak that lasts minutes. →

Delivering Content

4 topics
05 Pushing Real-time UpdatesHTTP only lets the client ask, so pushing updates means choosing a transport (polling, SSE, or WebSockets) and solving a second problem: routing each update to the server that holds the recipient's connection. → 06 Fanning Out UpdatesFan-out is the choice between doing the distribution work when content is published and doing it when a reader opens the app, and real systems usually need a hybrid because neither extreme survives celebrity accounts. → 07 Uploading and Serving Large FilesLarge files should not flow through the application tier: upload directly to object storage with short-lived credentials, transfer in resumable parts, and serve through a CDN with range support. → 08 Streaming Video and AudioStreaming replaces one giant download with a manifest plus short segments, so the player can start quickly, switch quality as the network changes, and fetch each segment from a nearby CDN. →

Staying Reliable

3 topics
09 Surviving Component FailuresEvery dependency will fail eventually, so design for partial failure: detect it quickly, contain the blast radius, retry only what is safe, and degrade in a planned order instead of cascading. → 10 Preventing Duplicate ProcessingDuplicates are inevitable once clients retry and queues redeliver, so make every effect idempotent and keep a durable record of what has already been done. → 11 Running Across Multiple RegionsMulti-region buys latency and regional fault tolerance by paying for it twice: every extra region must be provisioned, and every write across regions becomes a consistency decision. →

Keeping Data Correct

3 topics
12 Coordinating Transactions Across ServicesWhen one business operation spans several services, you cannot get a single ACID transaction; you choose between two-phase commit for short, tightly coupled writes and sagas for long-running work with compensations. → 13 Keeping Data in SyncMost real systems store the same fact in several places — a database, a cache, a search index, a warehouse — and every one of those copies is a chance for the data to disagree. The pattern is about choosing a source of truth, propagating changes from it, and repairing drift when propagation fails. → 14 Preventing Double BookingA booking is correct only if one unit of inventory — a seat, a room, a slot — is assigned to exactly one owner, even when thousands of users hit the same unit at the same instant. The pattern is atomic claim of a uniquely identified unit, surrounded by holds, idempotency, and expiry. →

Running Background Work

2 topics
15 Handling Long-Running TasksA request that takes minutes cannot live inside a request/response cycle. The pattern is to accept, persist, and acknowledge the work, run it on durable workers, expose progress, and make every step retryable and resumable. → 16 Scheduling Delayed and Recurring JobsSome work must happen at a chosen time (send a reminder, cancel an unpaid order) and some must happen on a rhythm (nightly report, hourly cleanup). The pattern is a durable store of due times, a scheduler that decides what is due, and workers that run each job exactly once in practice. →

Specialized Data

4 topics
17 Search and TypeaheadFull-text search turns documents into an inverted index so matching and ranking happen without scanning every record; typeahead adds a second, much hotter path that predicts queries from a prefix before the user finishes typing. → 18 Finding and Tracking LocationsLocation systems answer proximity questions that a one-dimensional index cannot: nearby drivers, restaurants, or places. The core move is to map two-dimensional geography onto cells or tree nodes so the database can prune most of the world before computing exact distances. → 19 Generating Unique IDsA single database sequence is easy, but it is a bottleneck and a single point of failure. Distributed ID generation trades coordination for uniqueness, and the right design depends on whether you need sortability, compactness, unpredictability, or offline generation. → 20 Counting at ScaleA counter looks like a single increment, but one hot row serializes every write. Counting at scale means choosing between sharded exact counters, stream or batch aggregation, and approximate sketches based on how exact, fresh, and durable the number really needs to be. →
