In one lineWrites are harder to scale than reads because every write must be durably stored, applied to indexes, and replayed to replicas — so the fix is to make each write cheaper, write fewer of them, absorb bursts, and eventually spread them across shards.
Write amplification
The extra work one logical write causes: the log record, the table update, every index update, and replication.
B-tree
A storage structure used by databases like PostgreSQL and MySQL that updates pages in place, giving fast reads but scattered writes.
LSM tree
A log-structured merge tree that appends writes to memory and a log, then flushes sorted files sequentially, favoring write throughput.
Batching
Grouping many rows or events into one round trip and one commit instead of paying the fixed cost per row.
Consumer lag
The number of messages produced but not yet processed; a rising value means consumers cannot keep up with producers.
Backpressure
A bounded buffer or signal that tells producers to slow down or retry later instead of accepting unbounded work.
Sharding
Partitioning data across multiple databases so each shard stores and writes only part of the dataset.
Shard key
The value whose hash or range decides which shard owns a record; it controls write spread and query locality.
Consistent hashing
A ring-based assignment where adding a shard moves only roughly 1/N of keys instead of remapping almost everything.
Idempotency
Making the same write safe to apply twice, usually with a unique event ID, so at-least-once delivery causes no double effect.

01Where this pattern shows up

Some systems generate new data continuously at a very high rate. Every update becomes a write, and the database must keep up with all of it.

  • Uber: every active driver's phone sends a location update every few seconds.
  • WhatsApp: every message is a new write, adding up to billions of messages per day.
  • YouTube: every view increments a count and every like updates a like count.
  • Ad click tracking: every click must be recorded because advertisers are billed from it.
  • Metrics and logging: thousands of servers emit new data points every few seconds.
  • In all of these, new data keeps arriving and the database has to keep up.
  • The common interview signal is a write rate that exceeds what one well-tuned database can absorb.

02Why writes are harder to scale than reads

Reads had many escape routes: cache results, add replicas, push content to a CDN. Those tools do not reduce the work of storing new data.

  • A cache can serve the same result to many readers, but every write carries new data that must be stored.
  • Read replicas do not help: every write still goes to the primary and then must be applied by every replica.
  • Each write does more work than it appears: append to a log on disk, update the table, update every index, and sometimes lock rows.
  • That hidden work is write amplification, and it grows with every index and every replica.
  • Relational databases handle writes in place, which becomes scattered disk I/O as data grows.
  • A write also has to be durable, so it must survive a crash before you can confirm it.
  • Losing an acknowledged write is a correctness failure, while losing a cache entry is only a performance failure.
One INSERT→Append to log on disk→Update the table→Update every index→Lock rows if needed→Replicate to replicas

03Start with the database itself

The first step is to make each write cheaper before spreading writes across more machines.

  • Every index on a table must be updated on every insert, so five indexes cost far more per write than one.
  • In a read-heavy system extra indexes are worth it; in a write-heavy system keep only the indexes the queries use.
  • Choose a storage engine that fits the write pattern rather than forcing a B-tree database to absorb append-only volume.
  • Match the data model to the access pattern so common writes touch a single row and a single shard.
  • Avoid unnecessary uniqueness constraints, triggers, and synchronous secondary work in the hot write path.
  • Measure writes per second achievable with your indexes and durability settings before assuming one database is enough.

Keep only the indexes you need

  • Audit which indexes are actually used by queries; unused indexes are pure write overhead.
  • Composite indexes multiply the cost of each insert, not just the number of indexes.
  • Removing an index can improve write throughput while degrading a read path, so check both sides.

Choose a write-friendly database

  • B-tree databases update pages in place, giving fast point and range reads but scattered writes.
  • LSM-tree databases append to memory and a log, then flush sorted files sequentially, which is much faster for high write volume.
  • LSM reads can be slower because a value may live in several files; Bloom filters and compaction reduce that cost.
  • Compaction uses disk and CPU in the background, so it is a real operational cost rather than free throughput.

04Batching writes

Each write to a database has a fixed cost: a network round trip, a transaction, and a log write. Batching pays that cost once for many rows.

  • Inserting 1,000 rows one at a time pays the fixed cost 1,000 times; one multi-row insert pays it once.
  • A batch buffer flushes on whichever comes first: the batch reaching a size limit or a time limit passing.
  • The size limit keeps batches efficient under heavy traffic; the time limit stops data sitting in the buffer when traffic is light.
  • Typical tools are a multi-row INSERT ... VALUES (...), (...), PostgreSQL's COPY, or a Cassandra batch statement.
  • Batching adds delay because data waits in the buffer before it is written.
  • Buffered data can be lost if the process crashes before the flush, so batching suits metrics and logs more than payments.
  • Batching is also useful on the consumer side, where one database write can represent many queued events.
Collect events in memory→Flush on size limit or time limit→One round trip, one commit→Repeat

05Using a queue to absorb writes

Write traffic is rarely steady. A flash sale, a big match, or a viral post can multiply traffic for a short period, and sending all of it straight to the database overloads it.

  • Put a message queue such as Kafka between the application and the database.
  • The application appends the write to the queue and can respond to the client immediately.
  • A group of consumers reads from the queue and writes to the database at a rate it can sustain.
  • During a spike the queue grows, and consumers catch up once traffic falls.
  • Kafka suits this because it appends messages to logs on disk and handles very high write rates.
  • A topic is split into partitions, and messages with the same key go to the same partition, preserving per-key order.
  • Multiple independent consumer groups can read the same topic for different purposes without affecting each other.

How the buffer works

  • The producer appends an event and receives an acknowledgement from the broker, not from the database.
  • Consumers pull at their own pace, so a short spike becomes a backlog rather than a database outage.
  • Ordering is preserved only within a partition, which is why the partition key matters.
Client write→API server appends to queue→Respond immediately→Consumers read at a steady pace→Database

Trade-offs

  • Delayed visibility: the data is not in the database when the client gets a response.
  • Duplicates: most queues deliver at least once, so a worker may process the same message twice.
  • Writes should be idempotent; a unique event ID lets the database ignore an event it has already stored.
  • Backlog growth: a queue absorbs a short spike, but a permanently slow consumer group falls further behind.
  • Watch consumer lag; if it keeps rising, add consumers up to the partition count or increase batch size.
  • If that is not enough, apply backpressure with a bounded buffer that makes producers slow down or retry later.

06Sharding

Batching and queues reduce and smooth the load, but at some point one database still cannot keep up. Then the data must be split across multiple databases.

  • Each database is a shard that stores only part of the data and handles only the writes for that part.
  • In the Uber example, location data can be sharded by driver ID, with a hash deciding the shard.
  • If one shard handles 50,000 writes per second, 1.25 million writes per second needs at least 25 shards, and in practice more for growth and spikes.
  • Sharding adds routing, rebalancing, and operational complexity, so use it after cheaper techniques.
  • A write that must update two shards, such as moving money between accounts, needs coordination like a saga or two-phase commit.
  • Model data so the common write touches one shard; cross-shard writes are the exception, not the design.

Choosing the shard key

  • A good shard key spreads writes evenly across all shards.
  • It should also keep data that is read together on the same shard, so most queries touch one shard.
  • Driver ID works because writes spread across millions of drivers and one driver's history stays together.
  • Timestamp ranges send every new write to the newest shard, leaving older shards idle.
  • A random ID spreads writes evenly but scatters related data, so queries fan out to every shard.

Adding shards later

  • With hash(key) % N, changing the number of shards moves almost every key.
  • Consistent hashing places shards on a ring and assigns each key to the next shard around it.
  • Adding a shard then moves only the keys in its new range, roughly 1/N of the data.
  • Resharding still needs a plan for dual reads or writes during the move.

07Hot shards and hot keys

Even with sharding, writes can concentrate on one place. The cause is either a bad shard key or a single record that receives enormous traffic.

  • A hot shard receives most writes while other shards sit idle, so adding shards does not help.
  • Monotonically increasing values such as timestamps or auto-incrementing IDs are poor range shard keys.
  • A single very popular record becomes a bottleneck because updates to one row cannot run in parallel.
  • Sharding spreads data across machines, but it does not split one row.
  • You need a different fix for each case: change the key for skew, split the record for a single hot item.
  • Detect both by tracking per-shard and per-key write rates rather than only overall throughput.

A bad shard key

  • Sharding events by timestamp means every new event has the latest timestamp and hits the newest shard.
  • For time-series data, a composite key such as (device_id, day) spreads writes by device and keeps each device's data grouped for range scans.
  • Check that the key's distribution matches the actual write pattern, not just the data volume.

A single popular record

  • Suppose a celebrity video receives 100,000 likes per second; every like updates the same counter row on one shard.
  • Split the counter into several smaller counters and have each like update one at random.
  • The total is the sum of the counters, which spreads writes across rows that can live on different shards.
  • The read becomes slightly more expensive, but popular counts are usually cached anyway.

08Reducing the number of writes

So far the techniques make writes cheaper and spread them out. Often the best option is to write less data in the first place.

  • Aggregate before writing: count views in memory or a stream processor for a few seconds, then write one update such as "views += 500" instead of 500 updates.
  • Metrics agents like StatsD collect counters in memory and write one summary per interval.
  • Time-series databases keep recent data at full detail and roll older data into larger buckets.
  • Overwrite instead of adding rows: keep only a driver's latest location in Redis, replacing the previous value.
  • Send only a sampled or batched version of history to the permanent database.
  • Sample high-volume streams, for example storing one in every ten location pings for trip history.
  • Ask in the interview whether every write truly needs to be stored, or only the latest value.

09Deciding which writes can be lost

Many write-scaling techniques are fast because they accept some risk. The design decision is which writes may take that risk.

  • Batching in memory can lose buffered data if the server crashes.
  • Aggregating view counts in memory can lose a few seconds of counts.
  • Write-behind acknowledges a write after it reaches a fast buffer such as Redis and persists it later, so a buffer failure can lose acknowledged writes.
  • Even a queue has a durability setting: Kafka can wait for several brokers (acks=all) or just one (acks=1).
  • Writes that must never be lost, such as payments, orders, and chat messages, should be durable and ideally replicated before confirmation.
  • Writes where small loss is acceptable, such as view counts, analytics events, and replaceable location pings, can use faster techniques.
  • State which group each write belongs to in the interview; it determines which techniques are allowed.

10Putting it all together

The Uber location pipeline combines the techniques, with each component solving one specific problem.

  • Each driver's phone sends a location update every 4 seconds.
  • An API server appends the update to a Kafka topic partitioned by driver ID.
  • One consumer group overwrites each driver's latest location in Redis.
  • The matching service reads Redis when it needs nearby drivers.
  • Another consumer group batches updates and writes them to a sharded Cassandra cluster for history and analytics.
  • Because both groups read the same topic, each can fall behind or restart without affecting the other.
  • Because Kafka is partitioned by driver ID, each driver's updates are processed in order.

11Discussing high write traffic in an interview

Follow a fixed order so every component is tied to a number or requirement established earlier.

  • Clarify requirements: peak writes per second, how spiky traffic is, and whether writes can be delayed or lost.
  • Estimate peak write load to decide whether one database is enough.
  • Reduce the number of writes with aggregation, overwriting, or batching.
  • Choose a database that fits the write pattern, such as an LSM-based store for append-only volume.
  • Add a queue if traffic is spiky or the client does not need immediate persistence.
  • Shard the data, justify the shard key, and describe how you would handle hot keys.
  • Separate durability classes: say which writes need strong guarantees and which can trade safety for speed.

12Key takeaways

  • Writes do not scale like reads: caches and replicas do not reduce the work of storing new data.
  • Make each write cheaper by keeping only necessary indexes and choosing a write-friendly, often LSM-based, database.
  • Reduce the number of writes with batching, aggregation, and overwriting the latest value instead of appending rows.
  • Use a queue to absorb spikes, and make consumers idempotent because messages can be delivered more than once.
  • Use sharding to spread writes, with a key that distributes writes evenly and keeps related data together.
  • Watch for hot spots: avoid increasing values as range shard keys, and split counters for a single popular record.
  • Decide which writes can tolerate delay or loss; that decision unlocks or forbids most of the fast techniques.

↔Trade-offs to say out loud

  • Removing indexes speeds up writes but can make read queries fall back to scans, so the trade depends on the read path.
  • LSM-tree databases handle high write throughput but can serve slower reads and spend background CPU and disk on compaction.
  • Batching amortizes fixed write cost but adds latency and can lose the buffered batch on a crash.
  • Queues absorb spikes and decouple producers but introduce delayed visibility, duplicate delivery, and a new system to operate.
  • Idempotent consumers make retries safe but require event IDs and deduplication state that must itself be stored and cleaned up.
  • Sharding spreads writes but makes cross-shard queries, transactions, and resharding substantially harder.
  • Consistent hashing limits key movement when adding shards but adds ring management and still requires moving data for the new range.
  • Aggregation and sampling cut write volume but lose fine-grained detail and can lose recent data if the aggregator fails.
  • Overwriting current state is extremely cheap but discards history that analytics or auditing may later need.
  • Weaker durability settings increase throughput but can lose acknowledged writes when a broker or node fails.

?Interview questions

Answer aloud before opening the outline.

1. Why are writes harder to scale than reads?

Reads can be duplicated: a cache or replica can serve the same result many times. A write carries new data that must be stored durably, applied to the table, applied to every index, and replayed to every replica, so more machines do not remove the work.

2. What does one insert actually cost?

A log write on disk, a table update, updates to every index on that table, row locks where needed, and replication to each replica. That amplification is why write throughput is often much lower than expected.

3. How do indexes affect write throughput?

Every index must be updated on every insert, so a table with five indexes does much more work per write than one with a single index. In a write-heavy system, keep only the indexes the queries actually use.

4. B-tree or LSM tree for a write-heavy workload?

LSM trees append to memory and a log and flush sorted files sequentially, which suits high-volume append-only data. B-trees update pages in place and are better for mixed workloads and transactions. The LSM trade-off is slower reads and background compaction cost.

5. When is batching appropriate?

When a short delay and the risk of losing the buffer are acceptable, such as metrics, logs, and analytics. It is not appropriate for a payment, where the write must be durable before you confirm it to the user.

6. How does a queue help with writes?

It decouples acceptance from persistence. Producers append to the queue and respond quickly, while consumers write to the database at a sustainable rate. During a spike the backlog grows and then drains.

7. Why must queue consumers be idempotent?

Most queues deliver at least once. A worker can write to the database and crash before acknowledging, so the message is delivered again. A unique event ID lets the database ignore the duplicate.

8. What do you monitor on a queue-based pipeline?

Consumer lag, produce and consume rates, partition skew, retry and dead-letter counts, and database write latency. If lag rises monotonically, consumers are slower than producers and the queue is only hiding the problem.

9. What is backpressure and when do you need it?

A bounded buffer that makes producers slow down or retry later instead of accepting work until memory runs out. It is needed when consumers cannot keep up for a sustained period, not just during a short spike.

10. How do you choose a shard key?

It should spread writes evenly and keep data that is read together on the same shard. Driver ID works for location data because it distributes across millions of drivers while keeping one driver's history together. Timestamps are poor because all new writes hit the newest shard.

11. What breaks when you add shards later?

With hash modulo N, almost every key moves when N changes. Consistent hashing limits movement to roughly 1/N of the data, but you still need dual reads or writes and a migration plan during the move.

12. How do you handle a single record that gets enormous write traffic?

Split the record. For a like counter, keep several counters and have each write update one at random, then sum them on read. This trades a slightly more expensive read for parallel writes.

13. Which writes can you make asynchronous?

Only those where a small delay or loss is acceptable, such as view counts, analytics, and replaceable location pings. Payments, orders, and chat messages must be durable and ideally replicated before you confirm them.

14. Walk through a high-write architecture end to end.

API servers append events to a partitioned log, one consumer group overwrites the latest state in an in-memory store, and another batches events into a sharded LSM database for history. The log absorbs spikes, each consumer group scales independently, and per-key ordering is preserved by the partition key.

!Traps

  • Trying to fix write throughput by adding read replicas or caches.
  • Keeping many unused indexes on a write-heavy table.
  • Claiming a queue solves sustained overload rather than only smoothing a burst.
  • Building consumers that are not idempotent, then being surprised by duplicates.
  • Choosing a timestamp or auto-increment column as a range shard key.
  • Sharding a single hot counter instead of splitting the counter.
  • Acknowledging a write after placing it in a volatile buffer and calling it durable.
  • Ignoring consumer lag until the backlog is hours deep.
