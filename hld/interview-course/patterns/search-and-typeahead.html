Inverted index
A mapping from each term to the documents (and positions) that contain it, so a query looks up terms instead of scanning rows.
Analyzer
The pipeline that normalizes text before indexing and querying: character filtering, tokenization, lowercasing, stemming, stop words, and synonyms.
Posting list
The ordered list of document IDs, term frequencies, and positions stored for one term in an inverted index.
Relevance score
A numeric ranking of how well a document matches a query, usually from BM25 or a learned ranking model.
BM25
A probabilistic ranking function that rewards term frequency but saturates it and normalizes for document length.
Typeahead
Query suggestions computed from a partial prefix, ranked by popularity, recency, or personalization and returned with very low latency.
Trie / prefix index
A data structure or index that stores strings by prefix so all completions of a prefix can be enumerated efficiently.
Facet
A filterable dimension such as category, brand, or price range, usually computed as counts over the current result set.
Index lag
The delay between a source-of-truth write and that change becoming searchable, caused by ingestion, refresh, or segment merges.
NDCG
Normalized Discounted Cumulative Gain, an offline ranking metric that rewards relevant results appearing near the top.

01The problem

A search box looks trivial from the client side: send a few words, get a ranked list back in milliseconds. Behind it, the system must match free text against a large corpus, ignore spelling and morphology differences, respect filters, and order results by a blend of relevance and business value.

  • The corpus may contain far more documents than fit comfortably in memory, and it changes continuously.
  • Users type short, ambiguous, often misspelled queries, so exact string matching produces poor results.
  • Ranking matters as much as matching: the best answer on page three is effectively a failure.
  • Typeahead adds a second workload with a much tighter latency budget and a much higher request rate.
  • Requirements differ by product: exact lookup, relevance-ranked discovery, prefix suggestion, and filtering are not the same problem.
  • The system must stay useful while the index is catching up, partially unavailable, or under a traffic spike.

02Where this pattern shows up

  • E-commerce catalog search with facets, price filters, and business-boosted placements.
  • Documentation, support, and code search where exact terms and phrase matching matter.
  • Social and content platforms searching posts, creators, hashtags, and comments.
  • Local and maps search combining text relevance with distance and opening hours.
  • Log and observability search over high-volume, time-partitioned event data.
  • Autocomplete for products, places, users, and previous queries in a search bar.
  • Any interview problem with a search box, a feed filter, or a 'find the best match' requirement.

03Why a normal database index is not enough

  • A B-tree index accelerates exact matches and range scans on a column, not relevance ranking across free text.
  • LIKE '%term%' cannot use a normal index and degrades into scanning or a full-text side index.
  • Relational engines do not tokenize, stem, apply synonyms, or score by term frequency out of the box.
  • Multi-word queries need AND/OR semantics, phrase proximity, and per-field boosts that a simple column predicate cannot express.
  • Facet counts, highlighting, spell correction, and fuzzy matching are separate concerns that a transactional database handles poorly.
  • The source of truth should remain the transactional database; search is a derived, eventually consistent read model.
Do not replace the primary database with a search engine. Treat the search index as a derived view that can be rebuilt from the source of truth.

04The inverted index

Instead of asking which terms a document contains at query time, the indexer precomputes the reverse mapping once and updates it as documents change.

  • Each document is passed through an analyzer that emits normalized terms in order.
  • The index stores a posting list per term: document IDs, term frequencies, and token positions.
  • Query terms are analyzed the same way, then their posting lists are intersected, unioned, or proximity-checked.
  • Positions enable phrase queries and highlighting; frequencies feed relevance scoring.
  • Skip pointers or compressed blocks let the engine jump through long posting lists without reading every entry.
  • Term-level sharding is possible in theory but document-level sharding is the usual choice because multi-term queries stay local to a shard.

Analysis choices change results

  • Lowercasing and Unicode normalization make matching case- and accent-insensitive.
  • Stemming conflates related forms but can create surprising matches; lemmatization is more precise and more expensive.
  • Stop-word removal shrinks the index but can break phrase queries and exact titles.
  • Synonyms expand recall but may dilute precision if applied at query time without care.
  • The same analyzer must be used consistently at index time and query time, or terms will not line up.

05Building and updating the index

The index is a pipeline, not a single write. Correctness depends on every stage being retryable and idempotent.

  • The transactional database remains the source of truth; a change stream or outbox publishes inserts, updates, and deletes.
  • Indexing workers transform records into search documents, enrich them with denormalized fields, and write them to the index.
  • Each document carries a stable ID and a version so out-of-order updates can be rejected or overwritten safely.
  • Deletes are represented as tombstones or versioned updates, then physically removed during segment merges.
  • Bulk indexing is far more efficient than one document per request, but it increases the visibility delay.
  • A full reindex builds a new index in parallel, then swaps an alias so readers never see a half-built index.
  • Backfills and schema changes must be replayable from the source of truth, not from the old index.
Source database write→Change event / outbox→Indexing worker→Analyzer and enrichment→Index segment→Refresh and alias swap

06Ranking results

  • Retrieve a candidate set cheaply with the inverted index, then rerank the top candidates with more expensive signals.
  • BM25 or TF-IDF provides a strong lexical baseline and handles term saturation better than raw term counts.
  • Field boosts let a title match outrank a body match; phrase and exact matches usually deserve an extra boost.
  • Popularity, recency, conversion rate, and business rules are combined with lexical relevance, often through a weighted score.
  • Learning-to-rank models can improve quality but need training data, feature pipelines, and careful online evaluation.
  • Diversity and deduplication prevent ten near-identical results from occupying the first page.
  • Ranking is product-specific: an e-commerce query and a documentation query should not share the same default weights.

07Query understanding and filtering

  • Spell correction and did-you-mean suggestions recover from typos, but should not silently rewrite high-confidence queries.
  • Synonym and query expansion increase recall; they must be curated to avoid nonsense matches.
  • Intent classification can route navigational queries to an exact page and exploratory queries to ranked results.
  • Filters and facets are applied alongside relevance, not after pagination, or result counts and pages become inconsistent.
  • Facet counts are aggregations over the matching set and can be expensive; cache or approximate them when the corpus is large.
  • Prefix matching, wildcard matching, and fuzzy matching have very different cost profiles and should be opt-in.
  • Multi-language search needs per-language analyzers and possibly separate fields or indexes.

08Typeahead and autocomplete

Typeahead answers a different question from search: not 'which documents match' but 'which queries are other people likely to complete this prefix with'.

  • A prefix index, trie, or finite-state transducer enumerates completions; precomputed top-k lists per prefix avoid traversal at request time.
  • Suggestions are ranked by popularity, recency, trending signals, and personalization, with unsafe or low-quality terms filtered out.
  • The client should debounce keystrokes, require a minimum prefix length, and cancel stale in-flight requests.
  • The server should cap the suggestion count and the work per prefix; typeahead traffic often dwarfs full search traffic.
  • New or rare queries may have no history, so fall back to lexical completions from the document index.
  • Trending suggestions need a short cache TTL and a way to evict abusive or spammy terms quickly.
  • Prefixes that cross word boundaries and non-Latin scripts need explicit handling; naive character splits behave badly.
User types prefix→Debounce and cancel stale request→Prefix lookup or cache→Filter and rank suggestions→Return top-k→Log impression for evaluation

09Scaling the index

  • Document-partitioned shards each hold a subset of the corpus; a query fans out to every shard and merges the top results.
  • Replicas increase query throughput and availability but multiply indexing work and storage.
  • The scatter-gather tail is the limiting factor: one slow shard delays the whole response, so hedge or time out slow shards.
  • Shard count should be chosen for future growth; resharding a large index is slow and operationally risky.
  • Index size is driven by stored fields, positions, doc values, and replicas, not just the raw text.
  • Segment merges consume CPU and I/O; they must be throttled so search latency does not collapse during heavy indexing.
  • Routing by tenant or category can reduce fan-out for common queries but risks hot shards.

10Freshness, consistency, and reindexing

  • Most search engines refresh near-real-time rather than per document, so a just-written record may not be immediately searchable.
  • Users usually accept eventual consistency for discovery, but the author of a new listing often expects to see it immediately.
  • Read-your-writes can be handled by pinning that user to a fresh view, showing an optimistic placeholder, or querying the source of truth for their own records.
  • Deletes and permission changes must propagate as fast as creates; a stale index can leak content that should no longer be visible.
  • Index aliases enable blue-green reindexing: build the new index, verify counts and quality, then switch traffic atomically.
  • A reconcile job compares source-of-truth records with index documents and repairs drift.
  • Schema and analyzer changes require a full rebuild because existing terms were analyzed differently.

11Caching and protecting the hot path

  • Cache popular query results and top prefixes at the edge or in a shared cache; the head of the query distribution is extremely repetitive.
  • Normalize cache keys carefully: filters, locale, page, and personalization change the correct result.
  • Use short TTLs for trending or inventory-sensitive results and longer TTLs for stable reference content.
  • Request coalescing prevents a cache miss on a hot key from stampeding the search cluster.
  • Negative caching avoids repeatedly searching for queries that reliably return nothing, but must expire quickly.
  • Circuit breakers and concurrency limits protect the cluster from typeahead retry storms.
  • Serve a safe fallback, such as popular items or cached results, when the search cluster is degraded.

12Failure modes and graceful degradation

  • If a shard is unavailable, return partial results with a clear signal rather than failing the entire query.
  • If the search cluster is down, fall back to database-backed exact lookup, curated popular results, or a cached page.
  • If indexing lags, search results become stale; monitor lag and alert before users notice missing content.
  • If ranking features are unavailable, fall back to lexical scoring instead of returning an arbitrary order.
  • If typeahead is slow, return fewer suggestions or nothing; never block the search box.
  • Retry only idempotent reads, with jitter and a strict budget; aggressive retries turn a slowdown into an outage.
  • Protect against abusive queries with complexity limits, timeouts, and rate limits per client.

13Measuring quality and operations

  • Track p50, p95, and p99 latency separately for full search and typeahead; they have different budgets.
  • Track zero-result rate, query volume, click-through rate, and the rank of the first click.
  • Use offline judgments and metrics such as NDCG or mean reciprocal rank to compare ranking changes before launch.
  • Run online A/B tests because offline relevance metrics do not capture business or user behavior fully.
  • Monitor index lag, document count drift, failed indexing events, and dead-letter queues.
  • Watch shard skew, segment count, merge pressure, cache hit ratio, and CPU during reindexing.
  • Sample slow queries and log their shard timings to find the tail-latency source.

14How to approach it in an interview

  • Clarify corpus size, document shape, query types, freshness needs, languages, and whether typeahead is in scope.
  • Define the API and response shape first: results, scores, facets, suggestions, cursor, and total count.
  • Separate the source of truth from the derived index, and describe the ingestion and reindex path.
  • Explain the inverted index and analyzer choices before naming a product; the mechanism is what is being tested.
  • Describe ranking as retrieval plus reranking, with explicit signals and a fallback.
  • Treat typeahead as a separate low-latency service with prefix indexes, caching, and debouncing.
  • Finish with scaling, freshness, failure handling, and the metrics you would watch.
A strong answer explains why search is not a database query, how the index is kept fresh, and what degrades when the cluster is unhealthy.

↔Trade-offs to say out loud

  • Dedicated search index gives relevance, facets, and fast text matching but adds a second data store to operate and keep in sync.
  • Near-real-time indexing improves freshness but increases merge pressure and reduces indexing throughput.
  • More shards improve parallelism and isolation but increase fan-out, tail latency, and reindex cost.
  • More replicas improve query availability and throughput but multiply storage and indexing work.
  • Richer analysis (stemming, synonyms, fuzzy matching) improves recall but can hurt precision and increase query cost.
  • Precomputed typeahead lists are fast but consume memory and become stale as query popularity shifts.
  • Personalization and business boosts improve engagement but complicate evaluation, caching, and fairness.
  • Aggressive caching protects the cluster but serves stale results and risks incorrect invalidation.
  • Partial results on shard failure preserve availability but can silently hide relevant documents.

?Interview questions

Answer aloud before opening the outline.

1. Why not just use a SQL LIKE query for search?

A leading-wildcard LIKE cannot use a normal B-tree index, so it scans rows and cannot rank by relevance. It also lacks tokenization, stemming, synonyms, phrase proximity, and facet aggregation. A search index is a derived read model built for those operations.

2. What is an inverted index and why is it fast?

It maps each analyzed term to a posting list of documents and positions. A query looks up only the terms it contains and intersects their lists, instead of scanning every document. Positions support phrase queries and highlighting.

3. How do you keep the search index in sync with the database?

Write to the database as the source of truth, publish changes through an outbox or change stream, and have idempotent indexing workers apply versioned updates. Use a full reindex plus alias swap for rebuilds, and a reconcile job to repair drift.

4. How do you handle a document update arriving out of order?

Attach a monotonically increasing version or timestamp to each document and reject or overwrite older versions. The index operation must be idempotent so retries do not create duplicates.

5. How does ranking work?

Retrieve candidates with the inverted index, score them with a lexical model such as BM25, then rerank the top candidates using popularity, recency, personalization, and business rules. Keep the signals explicit and evaluate changes offline and online.

6. Why is search eventually consistent, and is that acceptable?

Indexing is asynchronous and search engines refresh in batches, so new writes appear after a delay. Discovery usually tolerates this. Cases that do not, such as the author viewing their own new listing or a permission revocation, need a targeted read from the source of truth or a faster path.

7. How would you design typeahead?

Build a prefix index or precompute top-k completions per prefix, rank by popularity and context, filter unsafe terms, cache hot prefixes, and debounce on the client. Keep the service independent from full search so a search outage does not break the search box.

8. How do you scale a search index?

Partition documents across shards, add replicas for query throughput, route queries to all shards, and merge top results. Control fan-out, hedge slow shards, throttle merges, and plan shard count for growth because resharding is expensive.

9. What is the tail-latency problem in search?

A query must wait for every shard, so the slowest shard sets the latency. With many shards, the chance that at least one is slow rises. Mitigate with hedged requests, timeouts, partial results, and fewer or better-balanced shards.

10. How do you deploy a new analyzer or schema?

Build a new index with the new mapping, backfill from the source of truth, verify document counts and relevance, then switch an alias atomically. Old and new indexes cannot share analyzed terms reliably.

11. How do you prevent a stale index from leaking deleted content?

Propagate deletes and permission changes with high priority, keep tombstones until physically removed, and verify authorization at read time for sensitive documents. Do not rely on index freshness as the only access control.

12. What would you monitor in production?

Latency percentiles for search and typeahead, error and timeout rates, zero-result rate, click metrics, index lag, indexing failures, shard skew, segment and merge pressure, cache hit ratio, and reindex progress.

13. When would you not use a dedicated search engine?

When the corpus is small, queries are exact or simple prefix matches, and the database can serve them within budget. Adding a search cluster brings synchronization, operations, and consistency costs that are not justified for a simple lookup.

!Traps

  • Treating the search index as the source of truth and losing data when it is rebuilt.
  • Using a leading-wildcard SQL query and calling it search.
  • Forgetting that the analyzer used at index time must match the analyzer used at query time.
  • Ignoring index lag and then wondering why newly created records are missing.
  • Building typeahead on the full search path without caching, debouncing, or a separate latency budget.
  • Letting one slow shard determine the latency of every query through unbounded scatter-gather.
  • Optimizing offline relevance metrics without checking clicks and business outcomes online.
  • Assuming deletes and permission changes propagate as quickly as they should.
