At-least-once delivery
A messaging guarantee that every message is delivered, but possibly more than once. Most queues default to this.
Idempotency
The property that repeating the same operation produces the same result and the same side effects as doing it once.
Idempotency key
A client-generated identifier that lets the server recognize a retry of the same logical request.
Deduplication window
The period during which previously seen message or request IDs are remembered and rejected.
Effectively-once
Exactly-once results achieved by combining at-least-once delivery with idempotent or deduplicated processing.
Processed-message table
A durable store of message IDs already handled, written in the same transaction as the side effect.
Unique constraint
A database guarantee that prevents a second row with the same business key, acting as a final duplicate barrier.
Compare-and-set
A conditional write that succeeds only if the current value or version matches, preventing double application.
Transactional outbox
Writing the event to an outbox table in the same transaction as the state change, then publishing it reliably.

01The problem

Networks fail, responses get lost, clients retry, and message queues may deliver the same message more than once. As a result, the same request can reach a system multiple times.

  • If every delivery is processed as new work, a payment can be charged twice or an order created twice.
  • The client often cannot tell whether its request succeeded: the write may have committed and only the response was lost.
  • Retrying is the correct client behavior for reliability, which makes duplicates a design assumption, not an edge case.
  • Queues with at-least-once delivery guarantee no loss but explicitly allow redelivery after a crash or timeout.
  • Duplicate processing is usually discovered by users, through double charges, duplicate emails, or inflated counters.
  • The goal is not to prevent duplicates from arriving, but to make their arrival harmless.

02Where duplicates come from

  • Client retries: a timeout triggers a retry while the original request is still being processed.
  • Load balancer or proxy retries: infrastructure resends a request that appears to have failed.
  • Queue redelivery: the consumer crashes or exceeds the visibility timeout before acknowledging.
  • Producer retries: a publish is retried after an ambiguous acknowledgement, creating two messages.
  • Worker crash after the side effect: the database write committed but the acknowledgment never happened.
  • Upstream duplication: two services emit the same business event, or a replay reprocesses history.
  • Mobile and offline clients resend aggressively after reconnect, so bursts of identical requests are normal.

03Idempotency as the foundation

The most robust defense is an operation that is safe to run repeatedly. Detection is a fallback for operations that cannot be made naturally idempotent.

  • A naturally idempotent operation converges to the same state: set status to shipped, delete by ID, or write a full record.
  • A non-idempotent operation accumulates: increment a balance, append a row, send an email, or charge a card.
  • Convert accumulation into assignment where possible: set the balance to a known value rather than adding a delta.
  • Use upserts keyed by a business identifier so a repeated write updates instead of inserting.
  • Design commands to carry the intended end state, and make the handler tolerant of the state already being reached.
  • Idempotency at the handler level protects against every duplicate source, not just the one you anticipated.

04Idempotency keys

  • The client generates a unique key per logical operation and reuses it for every retry of that operation.
  • A UUID or a hash of the request payload plus a client-scoped nonce are common choices; the key must not change between retries.
  • Scope keys per customer or account so one client cannot collide with or probe another client's keys.
  • Store the key with the operation's status and the original response, so a retry can replay the same result.
  • Define behavior for a reused key with a different payload: reject it rather than silently returning the old result.
  • Expire keys after a window longer than the maximum retry period; keeping them forever is expensive, expiring too early reopens the duplicate window.
  • The key must be checked and recorded atomically with the effect, or two concurrent retries can both pass the check.

05The idempotent request lifecycle

A typical API path records the key first, performs the work, and stores the outcome so retries replay rather than repeat.

  • Receive the request with its idempotency key and look up the key record.
  • If a completed record exists, return the stored response without re-running the work.
  • If a record is in progress, return a conflict or wait; do not start a second execution.
  • If no record exists, insert it as in-progress and proceed; a unique constraint on the key resolves the race.
  • Perform the business effect and record the result in the same transaction where possible.
  • Mark the record complete with the response and status code, then return it.
  • On failure, either delete the record so a retry can run, or store a terminal failure the retry can replay.
Receive key→Lookup record→Completed? return stored response→In progress? reject or wait→Insert in-progress→Execute effect→Store result→Return response
def handle(request):
    key = request.idempotency_key
    rec = store.get(key)
    if rec and rec.status == 'done':
        return rec.response
    if rec and rec.status == 'in_progress':
        return conflict('request already processing')
    try:
        store.put_if_absent(key, status='in_progress', fingerprint=hash(request.body))
    except AlreadyExists:
        return conflict('duplicate request')
    result = perform_effect(request)
    store.complete(key, response=result)   # atomic with the effect
    return result

06Consumer-side deduplication

  • Every message carries a stable message ID assigned by the producer, not generated on delivery.
  • Before processing, check whether that ID is already in the processed table; skip if it is.
  • Write the processed ID in the same transaction as the business change so neither can exist alone.
  • Acknowledge the message only after the transaction commits; a crash before the ack causes redelivery, which is now harmless.
  • Keep the dedupe record keyed by message ID with a TTL longer than the maximum redelivery window.
  • For partitioned consumers, remember that redelivery after a rebalance can replay a batch, so dedupe must be per message, not per batch.
Receive message→Begin transaction→Already processed?→Apply change→Record message ID→Commit→Acknowledge

07Exactly-once is really effectively-once

True exactly-once delivery across arbitrary systems is not achievable; what systems offer is exactly-once processing effects built on at-least-once delivery plus deduplication.

  • A network cannot guarantee a message is delivered once and only once, because the sender cannot distinguish a lost message from a lost acknowledgment.
  • Streaming platforms can provide exactly-once semantics inside their own boundary using transactions and idempotent producers.
  • Crossing the boundary to an external database or API brings the problem back, so the sink must still be idempotent.
  • Say effectively-once in an interview and explain the mechanism; claiming true exactly-once invites a well-aimed follow-up.
  • The cost is extra state, extra latency from transactions, and a dedupe window that must cover the retry horizon.
  • If the effect is naturally idempotent, you get the same outcome with far less machinery.

08Unique constraints and conditional writes

  • A unique index on the business key (order ID, payment ID, user plus date) makes the database reject the second write.
  • Catch the duplicate-key error and treat it as success if the existing row represents the same intent.
  • Use compare-and-set on a version or status column so a transition happens only once.
  • Prefer conditional updates such as UPDATE ... WHERE status = 'pending' over read-then-write sequences.
  • For counters, store per-key aggregates or apply a delta keyed by event ID rather than incrementing twice.
  • The database constraint is the last line of defense; it works even when application-level checks race.

09Choosing a deduplication store

  • A database table gives durability and transactional coupling with the effect, at the cost of write latency and growth.
  • A Redis or cache gives fast lookups and TTLs, but eviction or loss widens the duplicate window.
  • Use the database when the duplicate is expensive and correctness matters more than throughput.
  • Use a cache or bloom filter as a fast pre-check in front of the durable store, not as the only record.
  • Partition the dedupe store by key so it scales with traffic and does not become a single hot spot.
  • Budget for retention: dedupe tables grow with every request, so TTL, partitioning, and archival are part of the design.
  • A bloom filter can rule out most repeats cheaply but has false positives and cannot be the source of truth.

10Races, crashes, and partial failures

  • Two concurrent retries can both read 'not seen' and both proceed; the insert of the key must be atomic and unique.
  • A crash between the effect and recording the key creates a duplicate on retry unless both happen in one transaction.
  • A crash after recording the key but before the effect creates a lost request; store in-progress state with a timeout and recovery path.
  • Long-running work should record progress so a retry can resume or safely restart rather than repeat side effects.
  • External side effects such as emails or third-party charges need their own idempotency key passed downstream.
  • Timeouts on the dedupe lookup must fail closed for expensive operations: if you cannot confirm, do not charge twice.
  • Test the crash points deliberately; most duplicate bugs live between the effect and the acknowledgment.

11Ordering, versions, and late duplicates

  • A duplicate can arrive long after the original, so the dedupe window must cover the longest realistic retry or replay.
  • Attach a sequence number or version to events and ignore updates older than the state already applied.
  • Last-write-wins by timestamp is fragile when clocks skew; prefer per-entity versions or server-assigned order.
  • Out-of-order delivery is a different problem from duplication, but both are solved by making handlers state-aware.
  • Idempotent handlers plus version checks tolerate replay, redelivery, and late arrivals without special cases.
  • If ordering matters for correctness, partition by entity key so one consumer handles that entity's events in order.

12Deduplication in batch and streaming

  • Batch jobs that reprocess a date range must be idempotent by partition or output key, not by run ID alone.
  • Overwrite the target partition instead of appending, or merge on a deterministic key.
  • Streaming consumers should checkpoint offsets only after the effect is committed, and still dedupe on replay.
  • Windowing helps: count distinct IDs within a window when exact global dedupe is too expensive.
  • Fingerprinting the payload can catch duplicates that arrive with different message IDs but identical content.
  • Replays for backfills are a common source of double counting; run them through the same idempotent path as live traffic.

13What to monitor and how to answer

  • Count duplicate detections by source: API key replay, queue redelivery, unique-constraint violations.
  • Alert on a rising duplicate rate; it usually signals retry storms, timeouts, or consumer crashes.
  • Track dedupe-store size, hit rate, eviction, and lookup latency.
  • In an interview, start by naming the duplicate sources, then make the effect idempotent, then add keys or dedupe tables, then a unique constraint.
  • State the window and the storage cost, because 'we dedupe forever' is not a design.
  • Explain what happens on a crash between effect and record, since that is where interviewers probe.
  • Tie the answer back to the user-visible guarantee: at most one charge, one order, one email.
Name duplicate sources→Make effect idempotent→Add idempotency key→Dedupe at consumer→Enforce unique constraint→Set retention→Monitor duplicate rate

14When deduplication is overkill

  • Read-only and naturally idempotent operations need no key or table.
  • Analytics that tolerate approximate counts may prefer distinct counting over exact dedupe state.
  • A short dedupe window is enough when retries are bounded and clients stop after a few attempts.
  • Every dedupe store adds a write, a lookup, and a retention problem; measure whether duplicates actually occur.
  • For low-value, low-frequency actions, a unique constraint may be the only mechanism worth maintaining.
  • Do not build a global dedupe service before proving that per-handler idempotency is insufficient.

↔Trade-offs to say out loud

  • Idempotency keys make retries safe but add a lookup, storage, and a retention policy to every write path.
  • Database-backed dedupe is durable and transactional but adds write latency and grows without bound.
  • Cache-backed dedupe is fast and self-expiring but loses protection when entries are evicted or the cache fails.
  • Unique constraints are race-proof but only apply when the business key has a natural uniqueness rule.
  • Long dedupe windows catch late replays but increase storage and lookup cost.
  • Short windows keep state small but let slow retries and backfills slip through.
  • Exactly-once processing simplifies the consumer contract but costs transactions, latency, and platform coupling.
  • Fail-closed dedupe checks prevent double charges but turn a dedupe-store outage into a write outage.
  • Producer-assigned IDs make dedupe reliable but require coordination and discipline across services.

?Interview questions

Answer aloud before opening the outline.

1. Why do duplicates happen in a distributed system?

Because a client cannot distinguish a lost request from a lost response, so it retries. Queues guarantee at-least-once delivery, and consumers can crash after doing the work but before acknowledging. Duplicates are therefore expected, not exceptional.

2. What does idempotent mean?

Repeating the operation has the same effect as performing it once. Setting a status or upserting a record is naturally idempotent; incrementing a balance or sending an email is not.

3. How does an idempotency key work?

The client sends a unique key per logical operation and reuses it on retries. The server records the key with the operation's status and response, atomically with the effect. A retry finds the record and replays the stored response instead of running the work again.

4. What if the same key arrives with a different payload?

Reject it with a conflict error. The key identifies one logical operation; a different body means a client bug or misuse, and silently returning the old response would hide it.

5. Where should the dedupe record be written?

In the same transaction and the same database as the business effect when correctness matters. Otherwise a crash between the effect and the record creates a duplicate, and a crash between the record and the effect loses the request.

6. Is exactly-once delivery possible?

Not end-to-end over an unreliable network. Systems provide exactly-once processing effects by combining at-least-once delivery, idempotent producers, transactions, and deduplication at the sink. Say effectively-once and describe the mechanism.

7. How long should you keep deduplication records?

Longer than the maximum retry, redelivery, and replay horizon. That horizon comes from queue retention, client retry policy, and backfill practice. Then expire or archive to control storage.

8. How do you handle two concurrent retries?

Use an atomic insert with a unique constraint on the key. One request wins and proceeds; the other sees the existing in-progress or completed record and waits, rejects, or replays the result.

9. What is the difference between deduplication and idempotency?

Deduplication detects and drops repeats using stored identifiers. Idempotency makes the operation safe even if a repeat gets through. Idempotency is the stronger property; dedupe is one way to approximate it.

10. How do you deduplicate queue messages?

Give each message a stable producer-assigned ID, keep a processed table, and commit the ID in the same transaction as the side effect. Acknowledge only after commit, so redelivery is harmless.

11. What is a transactional outbox and why does it help?

It writes the event to an outbox table in the same local transaction as the state change, then publishes from the outbox. That avoids the gap where the database commits but the event is never sent, and it makes retries safe.

12. How do you stop duplicate emails or third-party charges?

Pass an idempotency key to the downstream provider when it supports one, and record the send attempt locally with its own key. For email, a dedupe table keyed by event plus recipient is usually enough.

13. What would you monitor?

Duplicate detection rate by source, unique-constraint violations, dedupe-store size and eviction, retry rate, and consumer redelivery counts. A sudden rise points to timeouts, crashes, or a retry storm upstream.

14. When is deduplication unnecessary?

For read-only or naturally idempotent operations, or when duplicates are harmless and cheap. Adding a key store to every write has real cost, so match the mechanism to the value at risk.

!Traps

  • Checking for a duplicate and then writing in two separate steps, leaving a race between concurrent retries.
  • Recording the idempotency key outside the transaction that performs the effect.
  • Deduplicating only at the API and forgetting queue redelivery and replays.
  • Using a client-generated key that changes on every retry, which defeats the whole mechanism.
  • Claiming exactly-once delivery instead of explaining effectively-once processing.
  • Expiring dedupe records before the maximum retry or backfill window has passed.
  • Keying deduplication on message ID only when the same business event can arrive with two different IDs.
  • Returning a cached success for a reused key whose payload has changed.
