In one lineMost real systems store the same fact in several places — a database, a cache, a search index, a warehouse — and every one of those copies is a chance for the data to disagree. The pattern is about choosing a source of truth, propagating changes from it, and repairing drift when propagation fails.
Source of truth
The one store whose value is authoritative when copies disagree; every other copy is derived.
Derived store
A copy built from the source of truth for a specific access pattern: cache, search index, read model, analytics warehouse.
Dual write
Application code writing to two systems in the same request. Simple to read, but not atomic, so partial failure leaves copies divergent.
Transactional outbox
A table in the same database as the business write that records the event to publish. One local transaction makes the state change and the event atomic.
Change data capture (CDC)
Reading the database's replication log and turning committed row changes into an ordered event stream.
Reconciliation
A periodic comparison between source and copy that finds and repairs differences the streaming path missed.
Idempotency
Making a consumer safe to apply the same event more than once, usually by tracking processed event IDs or by making the write naturally repeatable.
Eventual consistency
A promise that copies converge when writes stop, not that every read sees the latest value.
Read-your-writes
A session guarantee that a user sees their own recent write, usually by routing that read to the source or by tracking a version.
Tombstone
A deletion marker kept in the event stream so consumers learn about deletes that no longer exist as rows.

01The problem

One fact, several representations. A product lives in the primary database, its document in a search index, its hot fields in a cache, its sales in a warehouse. Each copy exists because a different read pattern is too expensive against the primary.

  • The primary database is optimized for transactional writes, not for full-text search, feed ranking, or analytics.
  • So the system denormalizes: the same fact is materialized into stores shaped for each query.
  • Every copy must be updated when the fact changes, and every update path can fail independently.
  • Users notice drift quickly: a renamed product still shows the old title in search, a deleted post stays visible in the feed.
  • The hard part is not the happy path; it is what happens when the second write fails, is delayed, or arrives twice.
  • This pattern appears in almost every design: search, feeds, caches, analytics, notifications, and read models.

02Why copies drift

Drift has a small number of root causes. Naming them makes the fix obvious in an interview.

  • Partial failure: the primary write commits and the secondary write times out.
  • Ordering: an update and a delete are applied out of order, so the older value wins.
  • Duplicates: a retried message applies a non-idempotent change twice, such as incrementing a counter.
  • Lost events: the process crashes between committing and publishing, so the change is never propagated.
  • Schema drift: a new column is added but the projection code does not consume it.
  • Consumer lag: the copy is simply behind, and a read at the wrong moment looks like corruption.
  • Distinguish temporary lag from permanent divergence; they need different fixes and different monitoring.
If you cannot name how a copy gets updated, you have not designed synchronization — you have hoped for it.

03Choose a source of truth and a consistency promise

  • Declare exactly one writer-owned source of truth per fact; ambiguity here causes conflicting writes later.
  • Derived stores should be rebuildable: given the source and the event history, you can recreate them from scratch.
  • State the promise explicitly: strong for the primary, eventual for search and analytics, bounded staleness for caches.
  • Decide which reads must see fresh data and which can tolerate lag; do not apply one promise to every query.
  • A user editing their own profile usually needs read-your-writes; another user browsing it does not.
  • Write the promise into the API contract so clients know whether to refresh or retry.

04The dual-write problem

The intuitive design is to write to the database and then write to the cache or index in the same request handler. It fails in a way that is easy to demonstrate.

  • The two writes are not in one transaction, so there is no atomic commit across them.
  • If the second write fails, the request may still return success, leaving the copies divergent until someone notices.
  • Retrying the whole request can duplicate side effects unless every step is idempotent.
  • Ordering is not guaranteed when two requests write the same entity concurrently: the slower one may land last with older data.
  • Wrapping both writes in a distributed transaction is usually worse — it couples availability and adds a coordinator.
  • Rule: do not dual-write to systems you cannot commit atomically. Write once, then propagate.

Cache-aside still dual-writes

  • Updating the database then deleting the cache key is a dual write with a race: a concurrent read can repopulate the key with the stale value.
  • A common mitigation is delete-after-commit plus a short TTL, accepting a small window of staleness rather than pretending it is atomic.
  • Versioned cache values or write-through to a single owner are stronger but more invasive.

05Transactional outbox

The outbox removes the gap between committing state and announcing it by putting both in the same local transaction.

  • The business write and an outbox row are inserted in one database transaction; either both commit or neither does.
  • A separate relay reads unsent outbox rows in order and publishes them to the broker.
  • After a successful publish the relay marks the row sent, or deletes it after a retention window.
  • If the relay crashes after publishing but before marking, the event is published again — so consumers must be idempotent.
  • The outbox table needs an index on status and creation time, plus a cleanup job, or it becomes an unbounded hot table.
  • It works with any broker and needs no log access, which makes it the default answer for service-to-service propagation.
Begin transaction→Write business rows + outbox row→Commit→Relay polls unsent rows→Publish event→Mark sent (or retry)

06Change data capture

CDC inverts the direction: instead of the application publishing, a connector tails the database log and emits every committed change.

  • Reads the replication log (binlog, WAL, oplog), so it captures changes made by any writer, including migrations and admin scripts.
  • Because it follows commit order, it gives a per-key ordering that application-level publishing often loses.
  • No extra write in the request path, so latency and failure surface of the API are unchanged.
  • Requires log retention long enough to survive connector downtime; a long outage can mean a full re-snapshot.
  • Row-level events are schema-coupled: a column rename must be handled by consumers, and raw events leak internal table structure.
  • Deletes must be represented explicitly, which usually means row images or an application-level tombstone.

07Consumers and derived stores

  • Each derived store has a consumer that translates the canonical event into its own write: index document, cache entry, feed row.
  • Consumers must be idempotent because delivery is usually at-least-once.
  • Keep the consumer's write and its offset/checkpoint in the same transaction where possible, so it does not skip or repeat work on restart.
  • Per-entity ordering matters more than global ordering: use a partition key derived from the entity ID.
  • A consumer that falls behind should lag visibly, not silently drop events to catch up.
  • Backfills should write through the same code path as live events, or the two will produce different shapes.

08Idempotency, ordering, and replay

  • Attach a stable event ID (or entity ID plus version) so duplicates are detectable.
  • Prefer last-writer-wins by version over blind overwrite; a late older event must not clobber a newer value.
  • For counts and balances, store the source value or a delta keyed by event ID rather than applying an increment.
  • Deletes need tombstones so a replayed older update cannot resurrect a removed record.
  • Replay is a feature: you should be able to rebuild a derived store from the log after a bug or a bad deploy.
  • Replays interact badly with non-deterministic transforms (timestamps, random IDs); make those deterministic or version the output.
At-least-once delivery plus a non-idempotent consumer is the single most common cause of duplicated derived data.

09Reconciliation and repair

Streaming is best-effort in practice. Reconciliation is the safety net that turns silent divergence into a bounded, detectable condition.

  • Periodically compare counts and checksums per partition or time window to detect missing or extra records.
  • Repair by re-emitting the authoritative record for the mismatched keys, not by patching the copy directly.
  • Keep a full rebuild path: drop the index and replay from the source or a snapshot.
  • Track the age of the oldest unreconciled window; if it grows, the repair path is not keeping up.
  • Make repairs idempotent so a reconciliation job that runs twice is harmless.
  • Reconciliation cost grows with data volume; sample or prioritize recently changed and high-value records.
Snapshot source→Compare with copy→Diff keys→Re-emit authoritative records→Verify convergence

10Read-path consistency

  • After a write, route the user's next read to the source of truth for a short window, or until their write version is visible.
  • Expose a version or watermark in the write response so the client can wait for a copy that has caught up.
  • Read from a replica only when the read can tolerate lag; do not mix replicas casually inside one user flow.
  • For caches, prefer deleting after commit over updating before commit, and accept a TTL-bounded window.
  • UI-level optimism (show the value you just saved) hides lag without fixing it, and must reconcile on refresh.
  • Document which endpoints are strongly consistent; otherwise clients assume all reads are.

11Failure modes to design for

  • Broker outage: outbox grows; alert on row count and age, not just on publish errors.
  • Consumer crash mid-batch: partial application; checkpoint after the write, and make the write idempotent.
  • Poison event: one record fails forever and blocks the partition; route it to a dead-letter path with the original payload.
  • Schema change: a consumer deployed against the old contract breaks silently; version events and run consumers before producers.
  • Replication lag: reads look stale but data is correct; separate lag metrics from corruption metrics.
  • Thundering rebuild: a full reindex saturates the source; throttle reads and write in batches.

12What to monitor

  • Consumer lag per partition, in events and in time — time is what users feel.
  • Publish-to-apply latency percentiles, not just averages, because tail lag is what shows up as bugs.
  • Outbox depth and oldest unsent age, which together reveal a stuck relay.
  • Reconciliation mismatch rate per store, with a threshold that triggers a rebuild.
  • Dead-letter volume and the age of the oldest message in it.
  • Duplicate-apply rate, to verify idempotency guards are actually working.

13Choosing a design in an interview

  • Name the copies first: which stores hold this fact, and why each exists.
  • Pick one source of truth and say what consistency each derived store needs.
  • Choose the propagation mechanism: outbox for service-owned events, CDC when external writers or tables must be captured.
  • State the delivery guarantee honestly — usually at-least-once — and then make consumers idempotent.
  • Add reconciliation and a rebuild path before you are asked; that is the difference between a diagram and a design.
  • Close with what you would monitor and what you would do when a consumer falls behind.
List copies→Pick source of truth→Choose outbox or CDC→Idempotent consumers→Reconcile→Monitor lag

↔Trade-offs to say out loud

  • Outbox gives atomic state-plus-event with no log access, but adds a table, a relay, and a cleanup job to the write path.
  • CDC captures every writer and preserves commit order, but couples consumers to table schema and needs log retention and re-snapshots.
  • Synchronous propagation keeps copies fresh but couples availability and latency to every derived store.
  • Asynchronous propagation isolates failures and absorbs bursts but exposes users to lag and requires reconciliation.
  • Strong read-your-writes removes confusing stale reads but pushes traffic back to the primary and reduces read scaling.
  • Aggressive caching cuts latency and load but increases the number of copies that can drift.
  • Full reconciliation catches everything but is expensive at volume; sampled reconciliation is cheaper but can miss divergence.
  • Event versioning and contracts protect consumers from breaking changes but slow down producer teams and add schema governance.

?Interview questions

Answer aloud before opening the outline.

1. Why does the same data end up in multiple systems?

Because each access pattern wants a different physical layout. The primary database is tuned for transactional writes; search needs an inverted index, feeds need precomputed read models, analytics needs columnar scans. Denormalizing into derived stores is cheaper than making one store serve every query.

2. What is the dual-write problem?

Writing to two independent systems in one request has no atomic commit. One write can succeed while the other fails or is delayed, and concurrent requests can apply in the wrong order, leaving the copies permanently divergent.

3. How does a transactional outbox fix it?

The business rows and an outbox row are written in the same local transaction, so the intent to publish commits atomically with the state change. A relay then publishes the row and marks it sent. The publish may repeat, so consumers must be idempotent.

4. When would you use CDC instead of an outbox?

When changes come from sources the application does not control — admin tools, batch scripts, other services sharing the database — or when you want zero extra writes in the request path. CDC reads the replication log, so it sees every committed change in commit order, at the cost of schema coupling and log-retention operations.

5. What delivery guarantee do these systems usually give?

At-least-once. Exactly-once end-to-end requires transactional coordination between the broker and every sink, which is rarely worth it. The practical answer is at-least-once delivery plus idempotent consumers keyed by event ID.

6. How do you prevent an old event from overwriting a new value?

Carry a version or timestamp per entity and apply last-writer-wins on that version, or partition by entity so events for the same key are processed in order. Blind overwrite without a version is the bug.

7. How do you handle deletes in a derived store?

Emit an explicit tombstone event, because a deleted row produces no positive value to project. The consumer removes or marks the document, and tombstones must be retained long enough for slow consumers and replays.

8. What is reconciliation and why is it necessary?

It is a periodic comparison between the source of truth and a derived copy, followed by repair of mismatched keys. Streaming paths lose events, have bugs, and lag; reconciliation bounds how long divergence can survive and gives you a way to detect it.

9. How would you rebuild a search index without downtime?

Build a new index alongside the old one from a snapshot, replay recent changes to catch up, verify counts and samples, then switch reads with an alias and delete the old index. Throttle the rebuild so it does not starve the primary.

10. How do you give a user read-your-writes across copies?

Pin that user's reads to the primary briefly, or return a version/watermark with the write and have the read wait for a replica or projection that has reached it. Reads by other users can stay on the stale copy.

11. What happens when a consumer falls behind?

The copy is stale but correct in the end. Alert on lag in time, scale consumers or reduce per-event work, and protect the source from a catch-up storm. If the backlog exceeds retention, you need a re-snapshot instead of a replay.

12. How do you stop a poison message from blocking a partition?

Bound the retries, then move the event and its payload to a dead-letter queue with context, and continue. A poison message left in place blocks all later events for that partition, which turns one bad record into total lag.

13. What should you monitor for data sync?

Consumer lag in time, publish-to-apply latency percentiles, outbox depth and oldest unsent age, reconciliation mismatch rate, dead-letter volume, and duplicate-apply rate. Counts alone hide the problem until users report it.

!Traps

  • Dual-writing to the database and a search index or cache and calling it consistent.
  • Assuming the message broker gives exactly-once delivery to every consumer.
  • Building a derived store with no rebuild or reconciliation path.
  • Letting raw table rows leak into event contracts, so a column rename breaks every consumer.
  • Partitioning events by something other than the entity ID and then expecting per-entity order.
  • Applying increments and other non-idempotent deltas to duplicated events.
  • Forgetting tombstones, so replayed updates resurrect deleted records.
  • Monitoring publish errors but not consumer lag, so a silently stuck relay looks healthy.
