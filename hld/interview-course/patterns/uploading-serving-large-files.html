A service that stores opaque blobs by key, scales horizontally, and serves them over HTTP, such as Amazon S3.
Presigned URL
A time-limited URL signed by the backend that lets a client upload or download directly from object storage.
Multipart upload
Splitting a large file into parts that are uploaded independently and assembled by the storage service.
Resumable upload
An upload that can continue from the last acknowledged offset after a network failure instead of restarting.
Checksum
A hash of the file or part used to detect corruption and verify that what was stored matches what was sent.
CDN
A geographically distributed cache that serves file bytes from a location near the viewer and shields origin storage.

An HTTP request for a byte range of a file, enabling seeking, partial downloads, and parallel fetching.
Signed URL
A URL carrying a time-limited signature that authorizes access to a private object without exposing credentials.
Transcode
Converting media into other formats, resolutions, or bitrates as part of post-upload processing.
Lifecycle policy
Rules that move, expire, or delete objects automatically based on age or storage class.

01The problem: files are far larger than API requests

A typical API request carries a few kilobytes of JSON. A video, backup, or design file can be hundreds of megabytes or several gigabytes.

  • Sending the file through the same application servers that handle API traffic ties up those servers for the entire transfer.
  • Upload duration is dominated by the client's network, so a slow or unstable connection can hold resources for minutes.
  • The larger the transfer, the more likely it is to fail partway and have to start over.
  • Download traffic has the same shape: serving bytes from application servers competes with request processing.
  • The file itself is usually immutable, which makes it a poor fit for a relational row or a normal request body.
  • The design goal is to move bytes on a path optimized for bytes and keep application logic on the metadata path.

02Where this pattern shows up

  • Cloud drives (Dropbox, Google Drive): users upload and sync files that can be several gigabytes.
  • Video platforms (YouTube): creators upload large source videos that must be processed and served to many viewers.
  • Messaging (WhatsApp, Instagram): photos and videos sent over slow or unstable mobile networks.
  • Object storage itself (Amazon S3): the whole service is built around storing and serving files of any size.
  • Backups, logs, and data exports: large archives produced and downloaded on a schedule.
  • Design and CAD tools: large binary documents that are opened, edited, and re-uploaded.
  • In each case the hard parts are transfer reliability, integrity, and delivery cost, not the business logic.

03Why large files are hard

  • Memory: buffering a whole file in the application process can exhaust memory and trigger restarts under concurrency.
  • Time: long requests exceed gateway and load-balancer timeouts, producing failures that look like client errors.
  • Retries: a dropped connection near the end forces a full restart unless the transfer is chunked and resumable.
  • Slow clients: a few slow uploads can occupy worker slots and connections that should serve many small requests.
  • Proxies and limits: request-size limits, buffering proxies, and idle timeouts interfere with long transfers.
  • Integrity: partial writes and truncated transfers must be detected, or corrupt files enter storage silently.
  • Cost: bandwidth through application servers is more expensive and less cacheable than object storage plus a CDN.
  • These problems compound: a design that fixes memory but not retries still fails on mobile networks.

04The core move: keep bytes off the application tier

The backend authorizes the transfer and records metadata; the client talks directly to storage for the bytes.

  • The client asks the API for permission to upload a file and describes its size, type, and name.
  • The API authenticates the user, checks quotas and permissions, and returns a presigned URL or temporary credentials.
  • The client sends the file bytes directly to object storage, bypassing application servers entirely.
  • Storage returns an identifier or ETag that the client reports back to the API.
  • The API verifies the object exists and matches expectations, then records the file in its metadata store.
  • Application servers now handle only small JSON requests, so their capacity is no longer tied to file size.
  • The same pattern in reverse serves downloads: the API authorizes, and the client fetches bytes from storage or a CDN.
Client requests upload→API checks auth and quota→API returns presigned URL→Client uploads to object storage→Client reports completion→API verifies and saves metadata

05Presigned URLs in detail

  • A presigned URL embeds the operation, object key, expiry, and a signature, so storage can authorize the request without calling the API.
  • Scope the signature tightly: a specific key, a specific method, a short expiry, and a maximum size where supported.
  • The key should be generated by the server, not chosen by the client, to prevent overwriting another user's object.
  • Include content-type and checksum constraints when the storage service supports them, so the client cannot substitute a different payload.
  • Never expose long-lived storage credentials to a browser or mobile app; short-lived scoped URLs are the substitute.
  • If the upload must be validated before it is visible, write to a quarantine prefix and promote after processing.
  • Presigned URLs also work for downloads, which keeps private objects private while allowing direct CDN or storage access.
The URL is a bearer capability: anyone who obtains it before expiry can use it. Keep expiries short and avoid logging full URLs.

06Multipart and resumable uploads

For large files, a single PUT is fragile. Split the file into parts that can be retried independently.

  • The client initiates a multipart upload and receives an upload id from storage.
  • It splits the file into fixed-size parts and uploads them, potentially in parallel to use available bandwidth.
  • Each part is acknowledged separately, so only failed parts are retried.
  • The client completes the upload with the list of part numbers and ETags, and storage assembles the object.
  • Resumability requires server-side or client-side upload state: which parts succeeded and where to continue.
  • Parts can be uploaded in any order, but assembly order is defined by part number, not arrival time.
  • Abandoned multipart uploads leave orphaned parts that cost money until aborted, so they need cleanup.
  • For very large files, parallelism must be bounded so the client does not saturate its own uplink or storage throughput.
Initiate multipart upload→Receive upload id→Upload parts in parallel→Retry failed parts only→Complete with part list→Storage assembles object

07Tracking upload state and integrity

  • Persist an upload session with file id, owner, expected size, parts completed, and expiry.
  • The client can query the session after a crash and resume from the last acknowledged part.
  • Use a checksum per part and for the whole file so corruption is detected before the object is accepted.
  • Compare the stored size and checksum against what the client declared; reject mismatches rather than trusting the client.
  • Mark the file as pending until verification and processing finish, so readers never see a partial object.
  • Upload sessions need a TTL and a cleanup job; otherwise abandoned uploads accumulate in storage and metadata.
  • Idempotency matters: a retried completion call should not create a second file record for the same object.

08Asynchronous post-processing

Once bytes are stored, expensive work should happen in the background, not in the upload request.

  • The upload completion event enqueues a processing job and returns immediately to the client.
  • Processing may include virus scanning, format validation, thumbnails, metadata extraction, or transcoding.
  • Workers read from storage, write derived artifacts back to storage, and update the metadata record.
  • The file stays in a pending state until processing succeeds, and the client polls or subscribes for status.
  • Failures are retried with backoff and eventually moved to a dead-letter queue for inspection.
  • Processing is idempotent by object key and version, so a retry overwrites derived artifacts rather than duplicating them.
  • Heavy processing should be isolated from upload handling; otherwise a backlog delays user-visible completion.
Upload completes→Emit event→Queue processing job→Scan and validate→Derive variants→Mark file ready

09Serving downloads through a CDN

  • Serve file bytes from a CDN backed by object storage, not from application servers.
  • The CDN caches popular objects at edge locations, reducing latency and origin egress.
  • Use signed CDN URLs or signed cookies so only authorized users can fetch private objects.
  • Set cache-control deliberately: immutable content can be cached for a long time, while private content should not be cached publicly.
  • Use versioned or content-addressed keys so a changed file gets a new URL and caches never serve stale bytes.
  • The origin should be protected from cache misses and abusive clients by rate limits and request collapsing.
  • For very large audiences, most requests should be served from edge caches, with origin traffic a small fraction of total.
Viewer requests file→CDN edge cache hit?→Yes: serve bytes→No: fetch from object storage→Cache at edge→Serve and bill egress

10Range requests and partial delivery

  • HTTP range requests let a client fetch a byte range instead of the whole object.
  • This enables video seeking, resumable downloads, and parallel downloads of different ranges.
  • The server responds with a partial-content status and the requested range, and advertises range support.
  • CDNs and object storage support ranges natively, which is another reason not to proxy bytes through the app.
  • Range support must respect authorization: a signed URL should not let a client enumerate the whole object beyond its permission.
  • For media, ranges are the basis of segment-based streaming, where the player fetches small chunks rather than one huge file.
  • Incorrect range handling produces confusing player errors and broken resume behavior.

11Security and access control

  • Authorize every upload and download against the user's rights to that specific file, not just to the service.
  • Keep buckets private by default; public access should be an explicit, reviewed decision.
  • Validate content type and extension, and scan untrusted uploads before serving them to other users.
  • Prevent path traversal and key collisions by generating keys server-side from ids.
  • Short-lived signed URLs limit the damage of a leaked link but do not replace authorization checks at issuance.
  • Log access to sensitive files and support revocation, especially for shared links.
  • Encrypt at rest and in transit, and consider per-tenant keys where isolation is a requirement.

12Cost, lifecycle, and storage layout

  • Storage cost grows with every version and derived artifact, so define what must be retained.
  • Use lifecycle policies to move cold objects to cheaper tiers and expire temporary uploads.
  • Content-addressed keys deduplicate identical files and make caching and integrity checks natural.
  • Derived artifacts such as thumbnails and transcoded renditions can dwarf the original in count.
  • Egress is often the largest cost for media-heavy products, which is why CDN caching and range delivery matter.
  • Delete or abort incomplete multipart uploads; orphaned parts are invisible but billable.
  • Quotas and per-user limits prevent a single account from consuming unbounded storage.

13Failure modes, monitoring, and interview framing

  • Partial uploads must never become visible; gate visibility on verification and processing state.
  • Stalled transfers need timeouts and resumable sessions, not silent retries from zero.
  • Checksum mismatches should fail closed and be recorded, since they indicate corruption or tampering.
  • Processing backlogs delay availability, so track queue depth and time from upload to ready.
  • CDN misconfiguration can leak private objects or serve stale versions; test cache and signing behavior.
  • Monitor upload success rate by network type, p99 time to ready, origin egress ratio, and storage growth.
  • Interview flow: separate metadata from bytes, authorize with presigned URLs, use multipart and resume, process asynchronously, serve via CDN with ranges, then cover security and cost.
Authorize→Upload in parts→Verify checksum→Process asynchronously→Publish→Serve via CDN

↔Trade-offs to say out loud

  • Direct-to-storage uploads remove file size from application capacity, but add a two-step flow and require careful key and permission design.
  • Presigned URLs avoid exposing credentials, but act as bearer tokens that anyone holding the link can use until expiry.
  • Multipart uploads improve resilience and parallelism, but add session state, part bookkeeping, and orphan cleanup.
  • Resumable sessions survive flaky networks, but require persistent upload state and idempotent completion.
  • Asynchronous processing keeps uploads fast, but the file is temporarily unavailable and the pipeline needs retries and monitoring.
  • CDN delivery cuts latency and origin load, but adds cost, cache invalidation concerns, and signing complexity.
  • Range requests enable seeking and resume, but complicate authorization and byte-range correctness.
  • Keeping originals plus derived variants improves flexibility, but multiplies storage and lifecycle management work.
  • Private buckets with signed access are safer, but every consumer, including the CDN, must participate in signing.

?Interview questions

Answer aloud before opening the outline.

1. Why not upload large files through the application servers?

It ties up memory, worker slots, and connections for the duration of a slow transfer, hits gateway timeouts, and makes retries expensive. Moving bytes directly to object storage keeps application capacity independent of file size.

2. How does a presigned URL work?

The backend signs a URL that grants a specific operation on a specific object for a short time. The client uses it to talk to storage directly, so credentials never reach the client and the app tier never sees the bytes.

3. What do you scope in a presigned upload URL?

The object key, the allowed method, a short expiry, and where supported the content type and size. The server generates the key so a client cannot overwrite another user's object.

4. How do you make a large upload resumable?

Split the file into parts, track which parts succeeded in an upload session, and resume from the last acknowledged part. Only failed parts are retried, and completion is idempotent.

5. Why use multipart upload instead of one PUT?

A single request must restart from zero on failure and cannot use bandwidth in parallel. Multipart uploads retry only failed parts, can upload in parallel, and let storage assemble the object.

6. How do you verify file integrity?

Send a checksum per part and for the whole file, store it with the metadata, and compare after upload. Reject mismatches and never mark the file ready until verification passes.

7. What happens after the bytes are uploaded?

The completion event enqueues asynchronous work such as scanning, validation, thumbnails, and transcoding. The file stays pending until processing succeeds, and the client polls or subscribes for status.

8. How do you serve downloads at scale?

Authorize the user, then serve bytes from a CDN backed by object storage using signed URLs. Immutable, versioned keys maximize cache hits and avoid stale content.

9. What are range requests used for?

Fetching part of a file: video seeking, resumable downloads, and parallel downloads. They require correct partial-content responses and careful authorization.

10. How do you keep private files private?

Keep buckets private, authorize each request against the specific file, issue short-lived signed URLs, validate and scan untrusted content, and log access to sensitive objects.

11. How do you control storage cost?

Cap feed and version retention, use lifecycle policies to tier or expire objects, abort incomplete multipart uploads, deduplicate by content hash, and watch egress, which often dominates for media.

12. What would you monitor?

Upload success rate by network type, time from upload to ready, processing queue depth, checksum failures, CDN hit ratio, origin egress, and storage growth per tenant.

13. How do you avoid showing a partially uploaded file?

Keep the object in a pending or quarantine state, verify size and checksum, finish processing, and only then mark it ready and expose it to readers.

!Traps

  • Proxying file bytes through the application tier and then wondering why memory and timeouts spike.
  • Letting the client choose the object key, which enables overwriting another user's file.
  • Issuing presigned URLs with long expiries or broad permissions.
  • Treating a single large PUT as reliable on mobile networks.
  • Forgetting to track upload state, so every failure restarts from byte zero.
  • Marking a file ready before checksum verification and processing complete.
  • Leaving abandoned multipart uploads to accumulate invisible storage cost.
  • Caching private objects publicly or using unversioned keys that serve stale bytes.
