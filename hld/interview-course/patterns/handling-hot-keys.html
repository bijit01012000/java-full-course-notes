In one lineA system can have plenty of aggregate capacity and still fail when too much traffic lands on one key — the fix is to spread, replicate, coalesce, or split that key rather than adding more nodes.
Hot key
A single key that receives a disproportionate share of requests, overloading the node or shard that owns it.
Key skew
An uneven distribution of traffic or data across keys, so some partitions do far more work than others.
Hot partition
A shard, cache node, or queue partition that receives most of the traffic because of key placement or a bad partition key.
Consistent hashing
A ring-based placement where each key maps to one node; useful for adding capacity, but it still puts a single key on a single node.
Key replication
Storing several copies of a hot key under suffixed names that land on different nodes, then picking one per read.
Local cache
A small in-process cache on each application server that absorbs repeated reads before they reach the shared cache.
Request coalescing
Letting one in-flight request compute or load a value while concurrent requests for the same key wait for that result.
Split counter
Replacing one hot counter with several sub-counters that are updated independently and summed on read.
Negative caching
Briefly caching a "not found" result so repeated requests for a missing key do not reach the database.
Backpressure
Slowing or rejecting producers when a node is saturated, instead of queueing unbounded work.

01What a hot key is

A hot key is one key whose request rate is far above the rest of the dataset. The overall system may be underloaded, but the single node responsible for that key is not.

  • Traffic concentrates on one item: a viral post, a popular product, a trending topic, or a heavily updated counter.
  • The key's owner — a cache server, a database shard, or a queue partition — receives most of the load.
  • Other nodes holding the rest of the data may be almost idle, so average utilization looks healthy.
  • The problem is per-key concentration, not total capacity.
  • Hot keys appear on both the read path and the write path, and the fixes differ.
  • A hot key can be temporary, lasting minutes during an event, or structural, lasting as long as the data model does.

02Why one key can sink a healthy system

Distribution is the assumption behind most scaling techniques. Hashing spreads keys across nodes, and sharding spreads rows across databases — but neither splits a single key.

  • A distributed cache stores each key on one node, so every request for that key goes to the same machine.
  • A sharded database stores each row on one shard, so every update to that row serializes on one shard.
  • Adding cache servers or shards redistributes the other keys but leaves the hot key exactly where it was.
  • The hot node hits CPU, network, or connection limits first, and its latency rises for every key it owns.
  • Timeouts and retries then add even more traffic to the already saturated node.
  • The failure looks like a capacity problem but behaves like a single-point-of-failure problem.
  • This is why "scale out" alone is the wrong answer when the interviewer asks about a viral post.

03Where this pattern shows up

  • A viral social post read by millions of users at once, all mapped to one cache key.
  • A celebrity account whose profile or feed is requested far more than anyone else's.
  • A flash-sale product where every user loads the same product row and inventory counter.
  • A ticket on-sale page that thousands of users refresh while waiting to buy.
  • A trending hashtag or live event that concentrates reads and writes on a few keys.
  • A like, view, or vote counter updated for one very popular item.
  • A leaderboard or global stats key that every request reads or updates.
  • A single large tenant in a multi-tenant system whose partition key routes all of its traffic to one shard.

04Detecting hot keys

Hot keys are invisible in system-wide averages. You need per-key and per-node visibility, sampled if necessary, to see the concentration.

  • Track request rate and latency per key, not just per service.
  • Track per-node and per-shard load; one saturated node beside idle peers is the signature.
  • Use cache-provider tooling or sampled key logging to find the top keys by request count.
  • Watch for partition skew in queues and shards, where one partition's lag or write rate diverges.
  • Alert on the ratio between the hottest key and the median key, not only on absolute traffic.
  • Correlate hot keys with deploys, marketing events, and external news so the cause is not mistaken for a code regression.
  • Sample aggressively; logging every key access can itself become the bottleneck.
A useful interview move is to say how you would detect the problem before proposing a fix. That shows you are designing an operable system, not reciting techniques.

05Read fix: cache close to the request

The cheapest read for a hot key is the one that never reaches the shared cache. Keeping a small copy in each application process absorbs most of the traffic.

  • Store very popular values in a small in-process cache on every application server.
  • Most reads for the hot key are served locally, so the shared cache and database see far less traffic.
  • A process-local cache adds no network hop, making it the lowest-latency option.
  • The copies are per-instance, so invalidation must be handled or tolerated.
  • Use a very short TTL so stale data expires quickly without explicit coordination.
  • Bound the local cache size with an LRU policy so it cannot grow without limit.
  • This is a good fit for data that is read constantly and changes rarely, such as a viral post's text or a product description.

06Read fix: replicate the key

If the hot value cannot live in every process, the next option is to make several copies of the key so the reads spread across nodes.

  • Create N copies under distinct names, such as post:123:copy1 through post:123:copyN.
  • The suffixed names hash to different cache servers, so reads distribute across them.
  • Each reader picks a copy at random, or uses a cheap local random choice per request.
  • On a write or invalidation, every copy must be updated or deleted; missing one leaves stale data.
  • The value in each copy is identical, so the storage cost multiplies by the number of copies.
  • This is often called key salting or key fan-out, and it directly targets read concentration.
  • Choose N based on how far above a single node's capacity the hot key is, not on total system traffic.

07Read fix: coalesce and protect the origin

When a hot key expires or is missing, the danger is many identical requests doing the same expensive work at once. Coalescing and admission control keep that burst from reaching the backend.

  • Request coalescing lets one request load the value while concurrent requests for the same key wait for that result.
  • A per-key lock or single-flight mechanism prevents a thundering herd on rebuild.
  • Serving the previous value briefly while a refresh runs in the background avoids a hard miss.
  • Add TTL jitter so related keys do not all expire at the same moment.
  • Apply per-key rate limiting or admission control so one key cannot consume the whole service's capacity.
  • Cache negative results briefly so requests for deleted or invented keys do not hit the database repeatedly.
  • Return a degraded but useful response, such as a cached summary, instead of failing all requests for that key.

08Write fix: split the counter

For a hot write, the bottleneck is one row that cannot be updated in parallel. Splitting the logical value into several physical rows restores concurrency.

  • Replace a single counter row with several sub-counters, for example likes:video42:0 through likes:video42:9.
  • Each write updates one sub-counter chosen at random, so writes spread across rows and potentially shards.
  • The logical total is the sum of all sub-counters, computed on read.
  • The read becomes slightly more expensive, but popular counts are usually cached.
  • Choose the number of sub-counters from the write rate relative to what one row can absorb.
  • Keep the sub-counter count stable; changing it later requires reconciling old and new totals.
  • The same idea applies to inventory, votes, and any single hot aggregate.

09Write fix: batch and aggregate

If the system does not need every individual update persisted, reduce the number of writes before they reach the hot row.

  • Buffer updates in memory or a stream processor and write a single aggregated delta.
  • For a counter, write "add the accumulated amount" instead of one update per event.
  • Use a queue to absorb the burst, then let consumers write at a controlled rate.
  • Make the consumer idempotent so retries do not double-count the aggregate.
  • If only the latest state matters, overwrite it rather than appending a new row.
  • If full detail is not needed, sample the stream and store fewer events.
  • These techniques trade freshness or completeness for a large reduction in write pressure.

10Choosing a better partition key

  • A hot key is sometimes a symptom of a bad partition key rather than a genuinely popular item.
  • Avoid monotonically increasing keys such as timestamps or auto-increment IDs for range partitioning; all new data lands on the newest partition.
  • Use a high-cardinality key that matches how the data is written and read.
  • For time-series data, a composite key such as (device_id, day) spreads writes while keeping one device's data together.
  • Check that related records which are read together still land on the same partition.
  • Adding a hash prefix or salt to a key can spread writes, but it also makes range queries harder.
  • Changing the partition key later means migrating data, so justify the choice before committing to it.

11Failure modes and limits

  • Replicating a key increases read capacity but multiplies invalidation work and storage.
  • Local caches can serve stale data and make a global purge difficult.
  • Request coalescing adds waiting latency for requests that lose the race.
  • Split counters make reads more expensive and complicate exact reconciliation.
  • Batching can lose buffered updates and delays visibility.
  • A queue absorbs a burst but cannot fix a sustained consumer deficit; lag keeps growing.
  • Every mitigation shifts load somewhere else, so re-measure after applying it.

12A decision guide

  • First confirm the key really is hot, using per-key metrics rather than a guess.
  • If the key is read-heavy, start with a local cache, then replicate the key if one node is still saturated.
  • If the key is write-heavy, split the counter or aggregate before reaching for more shards.
  • If the hot key is a missing or deleted item, add negative caching.
  • If the cause is a monotonic partition key, fix the key instead of adding mitigations.
  • If the spike is temporary, a queue plus coalescing may be enough; if it is structural, change the data model.
  • State the trade-off you are accepting and the metric that will tell you whether it worked.
Detect per-key skew→Read or write hot?→Read → local cache / replicate key→Write → split counter / aggregate→Re-measure skew and latency

13Discussing hot keys in an interview

  • Mention the possibility of a hot key when you design any cache or shard, not only when asked.
  • Explain why adding nodes does not help a single key.
  • Separate read-side and write-side mitigations and pick according to the workload.
  • Say how you would detect the problem in production.
  • Describe invalidation for any replicated or local cache you propose.
  • Name the trade-off and the fallback if the mitigation is not enough.
  • Tie the answer to the specific product: viral post, flash sale, celebrity account, or live event.

14Key takeaways

  • A hot key is a concentration problem: total capacity is irrelevant if one node owns the traffic.
  • Hashing and sharding spread many keys but never split a single key.
  • For reads, move the value closer (local cache) or spread copies of the key across nodes.
  • For writes, split the logical value into independent sub-values or reduce the write rate.
  • Protect the origin with coalescing, TTL jitter, negative caching, and per-key limits.
  • Fix a bad partition key at the source instead of layering mitigations on top.
  • Always explain invalidation and re-measure skew after applying a fix.

↔Trade-offs to say out loud

  • Local caching gives the lowest latency and offloads the shared cache but creates per-instance copies that are hard to invalidate.
  • Key replication spreads reads across nodes but multiplies storage and requires every copy to be invalidated on write.
  • Request coalescing prevents duplicate work but adds waiting latency for requests that must wait on the leader.
  • Split counters restore write parallelism but make reads an aggregation and complicate exact totals.
  • Batching and aggregation cut write volume but delay visibility and can lose recent updates.
  • Queueing absorbs a burst but cannot fix sustained overload; it converts a latency problem into growing lag.
  • Negative caching protects the database from missing-key traffic but can briefly hide a newly created record.
  • Salting the partition key spreads writes but makes range queries and related-data lookups harder.
  • Per-key rate limiting protects shared capacity but rejects or delays legitimate users during a genuine surge.

?Interview questions

Answer aloud before opening the outline.

1. What is a hot key?

A key that receives a disproportionate share of traffic, so the single cache node, shard, or partition that owns it is overloaded while the rest of the system is underloaded.

2. Why doesn't adding more cache servers fix a hot key?

A distributed cache maps each key to one server. Adding servers redistributes the other keys but the hot key still maps to exactly one node, so its traffic remains concentrated.

3. How do you detect a hot key in production?

Track request rate and latency per key, per-node and per-shard load, partition skew, and consumer lag. Look for one node saturated while its peers are idle, and alert on the ratio between the hottest key and the median.

4. How would you handle a viral post being read millions of times?

Serve it from a local in-process cache with a short TTL on each application server, or replicate the key under several suffixed names across cache servers and pick one per read. Add coalescing so an expiry does not cause a stampede.

5. How do you invalidate replicated keys?

On write, delete or update every copy. That is the main cost of replication: the write becomes N operations and a missed copy leaves stale data, so keep N modest and pair it with a TTL.

6. What is the difference between a hot key and a hot shard?

A hot key is one record with extreme traffic. A hot shard is a partition receiving too much traffic, often from a bad partition key such as a timestamp. Fixing the key or splitting the record are different remedies.

7. How do you scale writes to one popular counter?

Split it into several sub-counters, update one at random per event, and sum them on read. This spreads writes across rows and shards at the cost of a more expensive read, which is usually cached.

8. When would you aggregate instead of splitting?

When individual updates do not need to be persisted, such as view counts or analytics. Buffer and write one delta, accepting a short delay and possible loss of recent data.

9. What is a cache stampede and how does it relate to hot keys?

A stampede is many simultaneous misses for the same expired key. It is worst for hot keys because the request volume is highest there. Locks, background refresh, and TTL jitter prevent it.

10. How do you protect against requests for keys that do not exist?

Negative caching: store the "not found" result for a short time so repeated requests for a deleted or invented key do not reach the database.

11. How do you choose the number of key copies or sub-counters?

From the per-key load relative to what one node or row can handle, not from total system traffic. Keep the number stable because changing it requires reconciling copies or totals.

12. What trade-off are you making with a local cache?

Latency and offload improve, but each instance holds its own copy. Invalidation is difficult, so use a very short TTL and accept brief staleness for data that can tolerate it.

13. When is the right fix to change the partition key?

When the skew comes from the key itself, such as a timestamp sending every new write to the newest partition. A high-cardinality or composite key spreads the load at the source instead of masking it.

14. What would you monitor after applying a hot-key fix?

Per-key request rate, per-node and per-shard load, cache hit ratio, p99 latency for the hot key, invalidation failures, and queue lag. Confirm the skew actually moved rather than just moving elsewhere.

!Traps

  • Responding to a hot key by adding more cache servers or shards.
  • Treating a viral item as a general capacity problem instead of a per-key concentration problem.
  • Replicating a key but forgetting to invalidate every copy on write.
  • Using a local cache with a long TTL and serving visibly stale data.
  • Splitting a counter and then reading only one sub-counter.
  • Sharding time-series data by timestamp and calling the resulting hot shard a traffic spike.
  • Blaming a hot key for a problem that is actually a queue backlog or a missing index.
  • Applying a fix without per-key metrics to prove the skew moved.
