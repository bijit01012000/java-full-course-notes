Hot row
A single counter record that every write must lock and update, serializing throughput and concentrating contention.
Sharded counter
A counter split across multiple rows or keys; writers increment different shards and readers sum them.
Write-behind
Buffering increments in a fast store and persisting them to durable storage asynchronously in batches.
Windowed aggregation
Grouping events into fixed or sliding time windows and computing counts per window in a stream processor.
Watermark
A stream-processing estimate of when all events up to a given time have arrived, used to close windows and emit results.
HyperLogLog
A compact, mergeable sketch that estimates the number of distinct values with controlled error instead of storing every value.
Count-Min Sketch
A fixed-size sketch that estimates item frequencies and may overestimate but never underestimates.
CRDT counter
A conflict-free replicated data type whose increments and decrements merge deterministically across replicas.
Idempotency key
A unique identifier attached to an event or request so retries can be recognized and counted only once.
Reconciliation
A periodic comparison of a derived counter against the event log or source of truth, followed by correction.

01The problem

Every product counts something: views, likes, clicks, followers, downloads, or votes. On one server, counting is an atomic increment. At scale, millions of events per second arrive across many servers, and a single counter row becomes a serialization point.

  • The write path must absorb bursts without losing events or blocking on a hot record.
  • The read path must return a number quickly, even if it is slightly behind.
  • Different counts have different correctness needs: billing cannot be approximate, view counts often can.
  • Events arrive late, out of order, and more than once because producers retry.
  • Counts feed ranking and recommendations, so a slow counter can affect what users see elsewhere.
  • The design must define what one unit means before optimizing how to add it.

02Where this pattern shows up

  • View counts on videos, posts, and articles, often tolerant of small errors and short delays.
  • Likes, reactions, and votes, which are expected to be exact per user and idempotent.
  • Ad clicks and impressions, where billing demands auditability and duplicate protection.
  • Follower and subscriber counts, which drive profiles and ranking.
  • Rate limiting and quota counters, where approximate counts are usually unacceptable.
  • Analytics dashboards counting events by dimension, time window, and cohort.
  • Any interview problem that asks for a trending list, a popular post, or a real-time metric.

03Define the count semantics first

  • Total versus unique: every view is a different unit from every distinct viewer.
  • Exact versus approximate: can the product display an estimate, and can billing tolerate an error?
  • Freshness: must the number update immediately, within seconds, or is a periodic snapshot acceptable?
  • Durability: can a crash lose the last few seconds of increments, or must every event survive?
  • Idempotency: what makes two events the same event, and how long must duplicates be remembered?
  • Dimensions: counts per post, per user, per region, per hour, or all of them at once.
  • Monotonicity: can a count go down because of deletion, fraud correction, or a refund?

04Why a single counter row fails

  • Every increment takes a row lock, so concurrent writers queue behind each other.
  • The row becomes a hot row: one page, one lock, one write-ahead log position at a time.
  • Transaction overhead and fsync make each increment far more expensive than the arithmetic itself.
  • Contention grows with traffic, so latency rises and throughput flattens instead of scaling.
  • Replication amplifies the write traffic to every replica and can create apply lag.
  • Reads of the same hot row compete with writes, and reporting queries make it worse.
  • Caching the read does not fix the write bottleneck; it only hides the symptom.
The arithmetic is trivial. The cost is coordination: every writer wants the same record at the same time.

05Sharded exact counters

  • Split one logical counter into multiple physical counter rows or keys, each holding a partial total.
  • A writer picks a shard at random, by hash of user, or by node, and increments only that shard.
  • A reader sums all shards, or sums a cached snapshot plus recent deltas.
  • Write throughput scales with the number of shards; read cost also scales with it.
  • Shard count is hard to change because old and new shard layouts must be summed consistently during migration.
  • Random sharding spreads load but makes per-user idempotency harder; per-user sharding helps dedupe but can still skew.
  • Use a background job to compact shards into a base total and keep the number of live shards bounded.
Event arrives→Choose shard→Increment shard atomically→Cache invalidated or delta published→Reader sums base plus shards

06In-memory counters and write-behind

  • An in-memory store such as Redis performs atomic increments without touching the transactional database on every event.
  • A single-threaded atomic increment is fast, but a hot key still maps to one node and one core.
  • Persistence settings determine the loss window: snapshotting loses recent writes, while append-only logging reduces but does not eliminate loss.
  • A common design buffers increments in memory and flushes aggregated deltas to durable storage in batches.
  • The cache is not the source of truth; the durable event log or counter table must be able to reconstruct it.
  • A crash can lose buffered increments, so critical counts need an event log that is replayed after restart.
  • Expiry and eviction must never silently delete a counter that has not been persisted.

07Event streaming and windowed aggregation

  • Append each event to a durable, partitioned log keyed by the counter or entity.
  • A stream processor aggregates events per key and window, then writes results to a serving store.
  • Tumbling windows cover fixed intervals; sliding windows answer recent-rate questions; session windows group activity per user.
  • Watermarks decide when a window is complete enough to emit, balancing latency against late events.
  • Late events either update a still-open window, trigger a correction, or are dropped, and that policy must be explicit.
  • Exactly-once effects require idempotent sinks, transactional writes, or deduplication, not just an exactly-once label on the framework.
  • The log can be replayed to rebuild counters after a bug or a bad deployment.
Produce event with key and event ID→Partitioned durable log→Windowed aggregation→Idempotent sink write→Serving store→Dashboard or API read

08Batch recomputation, lambda, and kappa

  • Batch jobs recompute counts from immutable events over a long horizon, producing authoritative totals.
  • Recomputation corrects drift, duplicate processing, and logic bugs that streaming alone cannot fix.
  • The cost is latency: batch results are hours old and expensive to rerun over large histories.
  • A lambda architecture combines a batch layer for correctness with a speed layer for freshness, at the cost of two code paths.
  • A kappa architecture keeps one streaming path and replays the log when logic changes, reducing duplicated logic but requiring long retention.
  • Incremental materialization is cheaper than full recomputation when only recent data changes.
  • Always keep the raw events; without them, a wrong counter cannot be repaired.

09Approximate counting

  • HyperLogLog estimates distinct cardinality with a small, fixed memory footprint and mergeable sketches.
  • HLL error is controlled by the number of registers, not by the number of distinct items, which is why it scales.
  • Sketches for different windows can be merged, but you cannot add daily unique counts to get a weekly unique count.
  • Count-Min Sketch estimates frequencies and may overestimate, making it suitable for heavy hitters and rate estimates.
  • Sampling a fraction of events and scaling up is simple but adds variance and interacts badly with rare events.
  • Approximate counts are inappropriate for billing, quotas, or anything a user can audit against their own actions.
  • Label approximate numbers in the UI and document the error budget so product decisions do not treat them as exact.

10Unique counts and deduplication

  • Exact distinct counting requires remembering every distinct key, which does not scale to millions of viewers.
  • A dedupe store keyed by user and content can enforce one count per window, at the cost of storage and expiry management.
  • For approximate unique counts, maintain one sketch per window and merge sketches for the union of windows.
  • Summing per-day unique counts overcounts people who appear on multiple days; union the sketches instead.
  • Define the identity used for uniqueness: user ID, device ID, cookie, or IP, each with different privacy and accuracy properties.
  • Bots, crawlers, and repeated refreshes inflate counts; filter or classify them before they enter the counter.
  • Idempotency keys and dedupe windows must be long enough to cover retries, but not so long that storage grows without bound.

11Idempotency and correctness

  • Producers retry, networks duplicate, and consumers reprocess after rebalance, so at-least-once delivery is the normal case.
  • Attach a stable event ID and enforce uniqueness at the sink with a conditional write or a dedupe table.
  • Make increments idempotent per logical event, not per HTTP request; a retry of the same event must not add again.
  • Ordering matters for decrements and corrections; a delete that arrives before its create must not drive a count negative.
  • Recompute from the event log when drift is detected instead of trying to guess which increment was wrong.
  • Track a checksum or per-window event count so reconciliation can detect missing or extra updates.
  • Guard against double-counting from both the streaming path and the batch path when they overlap.

12Read path, hot keys, and ranking

  • Serve counts from a cache or serving table; never run a COUNT(*) over a large event table on the request path.
  • Display a cached snapshot with a short TTL, and accept that the number may lag by seconds or minutes.
  • For very large numbers, show a rounded or abbreviated value to avoid implying precision the system does not have.
  • A celebrity post or viral video creates a hot key; pre-aggregate at the edge or split the key into more shards.
  • Ranking by count should read from a separate, precomputed pipeline rather than triggering an expensive live count per item.
  • Rate-limit and sample abusive traffic before it reaches the counter, or a bot can distort both the number and the ranking.
  • When the count is used for money or eligibility, read from the authoritative store rather than the display cache.

13Multi-region, durability, and operations

  • Regional counters can accept writes locally and merge later, trading immediate global accuracy for availability and latency.
  • G-counters merge by summing per-replica increments; PN-counters add decrements with per-replica state.
  • CRDT counters converge without coordination but carry metadata per replica and cannot enforce global invariants such as a hard cap.
  • Async replication means two regions can briefly disagree; define which reads need the global value and which can use the local one.
  • Monitor drift between the counter and the event log, aggregation lag, shard skew, duplicate rate, and sink errors.
  • Run periodic reconciliation and keep an audit trail so a wrong number can be explained and repaired.
  • Capacity planning must account for the event log and sketches, not just the counter rows.

14How to approach it in an interview

  • Ask what is being counted, whether it is total or unique, how exact it must be, and how fresh it must be.
  • Estimate event rate and read rate, then show why a single-row increment becomes the bottleneck.
  • Choose a mechanism explicitly: sharded exact counter, in-memory buffer with durable log, stream aggregation, or a sketch.
  • Describe the event schema, the partition key, and the idempotency strategy before discussing storage products.
  • Explain how the read path serves a fast number and how it handles staleness.
  • Cover hot keys, late events, retries, and reconciliation from the raw log.
  • Finish with the metrics you would monitor and the cases where approximate counting is not acceptable.
The key interview signal is matching the counting mechanism to the required semantics. Exact billing and a view counter should not share a design.

↔Trade-offs to say out loud

  • Sharded counters scale writes but multiply read cost and make shard resizing and per-user deduplication harder.
  • In-memory counters are fast but risk losing recent increments and require a durable log for recovery.
  • Write-behind batching reduces database load but widens the window in which acknowledged events can be lost.
  • Stream aggregation gives fresh results but adds late-event, watermark, and exactly-once complexity.
  • Batch recomputation is authoritative and repairable but slow and expensive over long histories.
  • HyperLogLog makes unique counting cheap but gives an estimate and cannot answer per-item questions.
  • Count-Min Sketch is compact and fast but overestimates and cannot produce exact totals.
  • CRDT counters enable local writes and convergence but carry metadata and cannot enforce global limits.
  • Aggressive caching protects the read path but shows stale counts and complicates corrections.
  • Long dedupe windows improve idempotency but increase storage and operational cost.

?Interview questions

Answer aloud before opening the outline.

1. Why is incrementing a counter hard at scale?

All writers target the same row, so row locks serialize the updates. Transaction overhead and replication add cost, and throughput flattens while latency rises. The arithmetic is cheap; the coordination is not.

2. How does a sharded counter work?

The logical counter is split into many physical shards. Each write increments one shard, and a read sums the shards or a base snapshot plus deltas. Writes scale with the shard count, but reads and migrations become more expensive.

3. How do you choose the number of shards?

Base it on peak write rate and contention, with headroom for growth. More shards improve write throughput but increase read amplification and make resizing harder. Use a base-plus-delta scheme to keep the live shard count manageable.

4. Can you just use Redis INCR?

It is fast and atomic, but Redis is memory-bound, a hot key still lands on one node, and persistence may lose recent increments. Use it as a buffer in front of a durable event log or counter store, not as the only source of truth for critical counts.

5. How do you count unique viewers?

At small scale, store distinct user IDs per window. At large scale, use a HyperLogLog per window and merge sketches for unions. Do not add daily unique counts to get a weekly unique count.

6. What is HyperLogLog good for?

Estimating distinct cardinality with small, mergeable state. It is ideal for unique viewers and reach metrics, but it cannot tell you which users were counted or produce an exact billable number.

7. How do you handle duplicate events?

Attach a stable event ID and enforce it at the sink with a conditional write, unique constraint, or dedupe table. Make the increment idempotent for the logical event, and size the dedupe window to cover retries and reprocessing.

8. What is a watermark in stream aggregation?

It is the processor's estimate that all events up to a certain time have arrived. It decides when a window can close and emit a result, trading result latency against the risk of late events.

9. How do you correct a wrong count?

Recompute from the immutable event log for the affected key and window, then overwrite or adjust the serving value. Without the raw events, you can only guess. Reconciliation jobs should detect drift before users do.

10. Why use batch processing if streaming is available?

Batch recomputation is authoritative and can repair drift, duplicates, and logic bugs across long histories. Streaming gives freshness; batch gives correctness and replayability. Many systems run both.

11. How do you count a celebrity's post without a hot key?

Pre-aggregate at the edge, split the counter into many shards, and combine locally before a global write. Cache the displayed total, rate-limit abusive traffic, and keep ranking on a separate pipeline.

12. How do multi-region counters converge?

Use a CRDT such as a G-counter or PN-counter: each region tracks its own contribution and replicas merge by combining state. This converges without coordination but cannot enforce a global hard limit.

13. When is approximate counting unacceptable?

For billing, quotas, rate limits, votes, and any number a user can audit against their own actions. Approximate counts are fine for display metrics, reach estimates, and trending scores where small errors do not change the decision.

!Traps

  • Running a live COUNT(*) over a large event table on every page view.
  • Sharding a counter but then reading it with one query per shard on the hot path.
  • Treating a cache or Redis as durable when persistence can lose recent increments.
  • Adding daily unique counts to compute a weekly unique count.
  • Assuming exactly-once delivery without making the sink idempotent.
  • Closing a stream window before late events can arrive and then ignoring corrections.
  • Letting a trending or billing pipeline depend on a stale display cache.
  • Forgetting that bot traffic and retries inflate both counts and rankings.
