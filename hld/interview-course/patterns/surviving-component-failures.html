01The problem

Large systems are built from components that fail independently: servers crash, databases become unavailable, networks drop requests, and downstream services go down. A well-designed system expects this and keeps working, or degrades gracefully, when part of it breaks.

  • A partial failure is the normal case: one node, shard, or dependency is broken while everything else is healthy.
  • Failures are often slow rather than binary; an instance that answers after many seconds holds threads and connections hostage, which is worse than one that refuses immediately.
  • A caller cannot reliably distinguish a slow response, a lost response, and a failed request, so it must choose between waiting, retrying, or giving up.
  • Retries are the natural client reaction, and they add load precisely when the system is already struggling.
  • One slow dependency can exhaust the thread pool, connection pool, or memory of a healthy service and take it down indirectly.
  • Interviewers judge the failure story as much as the happy path: what breaks, how it is detected, and what the user sees.

02Failure modes to design for

Different failures need different containment. Naming the failure mode first makes the mechanism choice obvious.

  • Crash-stop: the process or machine disappears; detection is fast and redundancy handles it.
  • Slow or degraded: responses arrive late, timeouts fire, and queues build; this is the hardest case because the component still looks alive.
  • Network partition: two parts of the system can each serve requests but cannot see each other, which risks split brain and divergent writes.
  • Dependency outage: a third-party API, DNS, or identity provider fails and every instance fails the same way at the same time.
  • Resource exhaustion: disk full, connection limit reached, memory pressure, or file descriptor leak causes a gradual collapse.
  • Operator error and bad deploys: a configuration change or rollout removes capacity faster than any hardware fault.
  • Correlated failures matter most: replicas in the same rack, region, or deployment pipeline fail together.

03Redundancy: removing single points of failure

  • Run at least N+1 capacity: enough replicas that losing one still leaves the system within its latency budget.
  • Spread replicas across availability zones, racks, and power domains so one physical event cannot take all copies.
  • Keep the application tier stateless so any healthy instance can serve any request after a failure.
  • Replicate the database and make the failover path explicit: who promotes, how clients find the new primary, and what data may be lost.
  • Load balancers, DNS, and configuration services are components too; redundant entries and health-aware routing are required.
  • Watch for correlated failure: two replicas on the same host, the same image, or the same config push are effectively one replica.
  • Redundancy converts a hard outage into a smaller event only if traffic actually moves away from the failed copy.

04Detecting failure

Nothing else works if the system cannot tell that a component is unhealthy. Detection is a design decision with its own false-positive and false-negative costs.

  • Liveness asks whether the process should be restarted; readiness asks whether it should receive traffic. Conflating them restarts healthy-but-warming instances or routes traffic to broken ones.
  • A readiness check should exercise the dependencies needed to serve the request, but not so deeply that one shared dependency marks the whole fleet unhealthy.
  • Heartbeats and leases detect silent nodes; a missed heartbeat must be treated as suspicion, not proof, until a timeout or quorum confirms it.
  • Client-side timeouts are a failure detector too: if the deadline passes, the caller must decide and move on.
  • Use several signals — error rate, latency, saturation, and active probes — instead of trusting one threshold.
  • Detection has a cost in both directions: too sensitive causes flapping and failover storms, too slow leaves users waiting on dead components.

05Timeouts, retries, and backoff

Timeouts bound how long a failure can hurt, and retries recover from transient faults. Both are dangerous when applied without a budget.

  • Set a timeout for every network call; a call with no deadline can wait forever and pin resources.
  • Propagate a deadline through the call chain so downstream work is abandoned when the caller has already given up.
  • Retry only idempotent or safe operations; blindly retrying a charge or an order creation creates duplicates.
  • Use exponential backoff with jitter so retries spread out instead of arriving in synchronized waves.
  • Cap attempts and total retry time, and allow retries at only one layer so they do not multiply across the stack.
  • Use a retry budget (retries as a fraction of total requests); when the budget is exhausted, fail fast instead of amplifying load.
  • Distinguish retryable errors (timeouts, 503, connection reset) from permanent ones (400, validation, auth failure).
Request fails→Classify error→Retryable?→Backoff with jitter→Retry within budget→Give up with a clear error

06Circuit breakers

  • A breaker watches calls to one dependency and trips after a threshold of failures or slow calls.
  • While open it fails fast, returning a fallback or an error instead of consuming threads on a dead dependency.
  • After a cool-down it moves to half-open and lets a small number of probes through to test recovery.
  • Track slow calls as failures; a dependency that answers in ten seconds is failing from the caller's point of view.
  • Scope breakers per dependency and, where useful, per tenant or endpoint so one bad route does not close everything.
  • A breaker without a fallback only converts a timeout into an error; the user-visible behavior still has to be designed.
  • Use breakers together with timeouts: the timeout bounds one call, the breaker bounds the whole dependency.

07Bulkheads and isolation

Bulkheads limit how much of the system one broken dependency or noisy tenant can consume.

  • Give each downstream dependency its own connection and thread pool so a slow one cannot starve the others.
  • Partition consumers and queues by workload so a backlog in image processing does not delay payments.
  • Apply per-tenant or per-api-key quotas to stop one customer from consuming shared capacity.
  • Cell-based architecture splits users into independent stacks; a failure or bad deploy affects one cell, not everyone.
  • Use shuffle sharding so each request touches a small random subset of instances, limiting the reach of a single bad node.
  • Isolation reduces blast radius but wastes capacity and complicates routing, deployment, and capacity planning.

08Load shedding and graceful degradation

  • When demand exceeds capacity, admission control decides what to reject before queues grow without bound.
  • Rank work by importance: keep checkout and authentication, and drop recommendations, analytics, or prefetching first.
  • Reject early with a clear 429 or 503 and a retry hint rather than accepting work that will time out anyway.
  • Serve stale or static fallbacks — cached catalog, previous recommendations, last known balance — when a dependency is down.
  • Disable non-essential features behind flags so the core journey survives an incident.
  • Degradation must be planned and tested; inventing a fallback during an outage usually produces a second incident.
  • Tell the user what happened and what still works; silent partial failure erodes trust faster than a clear error.
Load rises→Saturation detected→Shed low-priority work→Serve fallback where possible→Protect core path→Recover and drain

09Failing over stateful components

Stateless tiers fail over by rerouting traffic. Databases and leaders need a coordination protocol, and that protocol is where most outages hide.

  • Use a single writer per shard with leader election through a consensus service or the database's own failover mechanism.
  • Require a quorum before a new leader accepts writes; a minority partition must stop writing rather than diverge.
  • Use fencing tokens so an old leader that has not noticed its demotion cannot overwrite newer data.
  • Prefer automated failover for availability, but keep a tested manual path for cases where automation is unsure.
  • State the trade-off explicitly: synchronous replication reduces data loss and increases write latency; asynchronous replication is faster but can lose recent writes.
  • Clients must reconnect to the new primary; connection strings, DNS, or a proxy layer have to support that.
  • A failover you have never rehearsed is a hypothesis, not a mechanism.

10Cascading failures and retry storms

  • A slow dependency fills queues, which increases latency, which triggers more retries, which increases load further — a self-sustaining loop.
  • Synchronized retries after a blip create a thundering herd; jitter and backoff break the synchronization.
  • Timeouts set too close to normal latency cause healthy calls to be retried, adding load for no benefit.
  • Queue-based systems can amplify: every retry adds messages, and consumers fall further behind while producers keep publishing.
  • Metastable failures persist after the original trigger is gone because the retry and queue state keeps the system overloaded.
  • Break the loop with load shedding, breaker state, bounded queues, and a way to drain or reset backlog deliberately.
  • Watch in-flight requests, queue age, and retry rate — not just error rate — to catch the loop early.

11Testing the failure path

  • Fault injection kills instances, adds latency, or breaks dependencies to verify the design actually reacts.
  • Start in staging with a clear hypothesis: which component fails, what should happen, and what the user should see.
  • Run game days where the team executes the failover runbook and measures detection and recovery time.
  • Test correlated failures, such as losing a whole zone or a shared dependency, not only single processes.
  • Chaos experiments in production need a small blast radius, a kill switch, and a rollback plan.
  • Every experiment should produce a fix: a missing timeout, a misleading alert, or an untested runbook step.
  • Track the time from injected failure to detection, to mitigation, and to full recovery.

12Monitoring the failure path

  • Define SLIs (success rate, latency, freshness) and an SLO with an error budget that justifies reliability work.
  • Alert on user-visible symptoms first, then on saturation and dependency health as leading indicators.
  • Track retries, breaker state, timeouts, queue depth, and in-flight requests per dependency.
  • Use distributed tracing to see where a request stalls across services; a single slow hop explains most tail latency.
  • Dashboards should show capacity versus current load so an on-call engineer knows how much headroom is left after a failure.
  • Log the decision, not just the error: which fallback was used, which instance was ejected, which region took over.
  • Review incidents for detection gaps and add a test or alert that would have caught them earlier.

13Interview walkthrough

For almost any design, the interviewer will ask what happens when a component goes down. Answer in a fixed order so the story stays complete.

  • List the critical path and every dependency on it: client, DNS, load balancer, app tier, cache, database, queue, third parties.
  • For each dependency, name the failure mode and whether the system can serve without it.
  • Explain detection: health checks, timeouts, and what marks an instance or region unhealthy.
  • Explain containment: redundancy, isolation, breakers, and load shedding.
  • Explain the user-visible behavior during the failure, including what is degraded and what is unavailable.
  • Explain recovery: how traffic returns, how state is repaired, and how you avoid a second outage during failback.
  • Close with what you would monitor and which failure you would test first.
Map critical path→Enumerate failures→Detect→Contain→Degrade→Recover→Monitor

14When not to over-engineer

  • Redundancy multiplies cost: every additional copy needs capacity, patching, monitoring, and a failover path.
  • For a small internal system, a single well-backed-up database and a clear restore procedure may be the honest answer.
  • Multi-region active-active is usually unjustified until the availability target or latency requirement demands it.
  • Complex failover automation can cause more outages than it prevents if it is untested and poorly understood.
  • Match the mechanism to the requirement: a 99.9% target does not need the same design as a payment ledger.
  • State the cost of each reliability feature out loud; interviewers reward justified simplicity.

↔Trade-offs to say out loud

  • Redundancy removes single points of failure but multiplies infrastructure cost and adds replication consistency problems.
  • Aggressive timeouts free resources quickly but turn slow responses into failures and generate extra retries.
  • Retries improve success under transient faults but amplify load during overload and can create duplicates.
  • Circuit breakers protect the caller and the dependency but convert a partial outage into a full feature outage for users.
  • Load shedding keeps the core system healthy but rejects legitimate work, which must be visible and fair.
  • Automatic failover reduces recovery time but risks split brain, flapping, and data loss if quorum and fencing are missing.
  • Bulkheads and cells contain blast radius but waste capacity and complicate routing and deploys.
  • Graceful degradation preserves the core journey but serves stale or reduced data that product and support must understand.
  • Chaos testing exposes real weaknesses but injects risk and consumes engineering time.
  • Multi-region redundancy survives a regional outage but makes every write path a consistency decision.

?Interview questions

Answer aloud before opening the outline.

1. What does it mean for a system to survive component failure?

It keeps serving its core function, or degrades in a defined way, when any single component fails. That requires redundancy, fast detection, containment of the blast radius, and a tested recovery path — not just extra servers.

2. How do you find single points of failure?

Map the critical request path and list every hop: DNS, load balancer, app instance, cache, database, queue, third-party API. For each, ask what happens if it disappears and whether a healthy copy takes over automatically.

3. What is the difference between liveness and readiness?

Liveness asks whether the process should be restarted; readiness asks whether it should receive traffic. A warming instance should be live but not ready. Conflating them causes restart loops or traffic sent to instances that cannot serve.

4. How do you choose a timeout?

Start from the caller's end-to-end deadline and the dependency's normal latency distribution. The timeout should be above normal p99 but well below the caller's budget, and it must be shorter than any upstream timeout so work is abandoned coherently.

5. Why exponential backoff with jitter?

Backoff reduces retry pressure while the dependency recovers; jitter prevents all clients from retrying at the same instant. Without jitter, synchronized retries create a second traffic spike that can re-break the service.

6. When do retries make things worse?

When the failure is overload rather than a transient fault, when the operation is not idempotent, or when retries are layered so one request becomes many. Retry budgets and breakers bound this amplification.

7. How does a circuit breaker work?

It counts failures or slow calls to a dependency. Above a threshold it opens and fails fast, optionally returning a fallback. After a cool-down it half-opens, lets a few probes through, and closes if they succeed.

8. What is a bulkhead and why does it matter?

A bulkhead isolates resources so one failing dependency or noisy tenant cannot consume all threads, connections, or queue capacity. It limits blast radius at the cost of some idle capacity and more configuration.

9. How do you stop a cascading failure?

Bound every wait with timeouts, fail fast with breakers, limit in-flight work and queue size, shed low-priority traffic, and break retry storms with backoff, jitter, and retry budgets. Then drain backlog deliberately rather than letting it grow.

10. Load shedding versus rate limiting?

Rate limiting enforces a quota per client over time. Load shedding protects the system when it is saturated, dropping or rejecting work by priority regardless of who sent it. They are complementary.

11. How do you fail over a database safely?

Elect a single leader with quorum, fence the old leader with a token, promote a replica that is caught up enough for the RPO, and redirect clients. Then verify replication and repair any divergence before failing back.

12. How do you test failure handling?

Inject faults in staging and controlled production experiments: kill instances, add latency, block a dependency. State the expected behavior first, measure detection and recovery time, and turn every surprise into a fix or a test.

13. What would you monitor during an incident?

User-facing success rate and latency, saturation and queue depth, retry rate, breaker state, dependency latency, and error budget burn. Traces show which hop is failing; capacity dashboards show remaining headroom after the loss.

14. How much redundancy is enough?

Enough to meet the availability target with the failure you must survive. That usually means N+1 within a region, multi-AZ placement, and a tested disaster-recovery path. More than that must be justified by the cost of downtime.

!Traps

  • Saying 'we add replicas' without explaining how failure is detected and how traffic is rerouted.
  • Retrying every failed request, including non-idempotent writes such as payments.
  • Setting a dependency timeout longer than the caller's own deadline, so the caller gives up while work continues.
  • Treating a process-level health check as proof that the instance can serve real traffic.
  • Assuming a standby region or replica works without ever rehearsing the failover.
  • Ignoring correlated failures: replicas in one zone, one image, or one shared dependency.
  • Designing for machine failure but not for bad deploys, configuration changes, or operator error.
  • Opening a circuit breaker with no fallback, which turns a timeout into a hard error for the user.
