In one lineA single database sequence is easy, but it is a bottleneck and a single point of failure. Distributed ID generation trades coordination for uniqueness, and the right design depends on whether you need sortability, compactness, unpredictability, or offline generation.
Auto-increment
A database-managed counter that produces the next integer for each insert; simple and compact but tied to one writer.
UUID
A 128-bit identifier, commonly random (v4) or time-based (v1/v7), that can be generated without contacting a central service.
Snowflake ID
A 64-bit ID composed of a timestamp, a worker or machine identifier, and a per-millisecond sequence.
Worker ID
The unique identifier assigned to each ID-generating node so two nodes cannot produce the same timestamp-and-sequence pair.
Epoch
The fixed starting time subtracted from the current time when encoding a timestamp, which extends the usable lifetime of the ID.
Sequence
A small counter that distinguishes multiple IDs generated within the same timestamp tick.
Ticket / segment allocation
A central service hands out blocks of IDs so each node can generate locally without asking for every ID.
ULID
A 128-bit, lexicographically sortable identifier combining a timestamp with random bits, usually rendered in base32.
Clock skew
A difference between node clocks; it can make time-based IDs non-monotonic or cause collisions if not handled.
IDOR
Insecure Direct Object Reference: exposing guessable IDs lets a user access another user's records by changing the identifier.

01The problem

Every order, message, user, and event needs an identifier. With one database, an auto-incrementing column solves it. Once multiple services and databases create records concurrently, each generator must produce a unique value without a round trip to a central authority on every write.

  • Two servers generating IDs independently must never choose the same value.
  • The generator should stay available even when another service or region is unreachable.
  • IDs often appear in URLs, logs, and APIs, so size and readability matter.
  • Some systems need IDs that sort by creation time; others only need uniqueness.
  • A poor ID choice leaks into database layout, sharding, pagination, and security for years.
  • The design must survive restarts, clock changes, network partitions, and scale-out.

02Where this pattern shows up

  • Orders, payments, and ledger entries, where duplicate IDs mean double charging or lost money.
  • Messages, posts, and comments, where IDs are exposed in APIs, links, and pagination cursors.
  • User and tenant records, where identifiers appear in URLs and must not be trivially enumerable.
  • Event and log pipelines, where every event needs an ID for deduplication and replay.
  • File and object storage, where content hashes or generated keys identify blobs.
  • Multi-region and active-active systems, where independent writers must not collide.
  • Any interview problem that creates records concurrently or asks how to scale a database writer.

03Requirements to pin down first

  • Uniqueness: globally unique across services, regions, and retries, or only unique within a table.
  • Ordering: must IDs sort by creation time, or is random order acceptable?
  • Compactness: 64-bit integers are cheaper to store and index than 128-bit strings.
  • Availability: can generation depend on a central service, or must it work offline?
  • Throughput: how many IDs per second per node and in total, including bursts?
  • Unpredictability: can an attacker enumerate IDs, and does that expose data?
  • Operability: can you assign and recycle worker identities safely, and can you migrate existing IDs?

04Auto-increment and why it breaks

  • The database maintains a counter and returns the next value inside the insert transaction.
  • It is compact, monotonic, and easy to index, which is why it is the default for a single database.
  • Every write depends on one primary, so the sequence becomes a throughput bottleneck and a single point of failure.
  • Separate databases each start their own sequence, so IDs collide across shards unless ranges or offsets are assigned.
  • Sequential IDs are trivially enumerable, which is dangerous when they are exposed in URLs or APIs.
  • Creating a record before its ID is known complicates application flows and distributed transactions.
  • A sequence is still a good choice for internal, single-writer tables where none of these constraints apply.

05UUIDs

  • A UUID is 128 bits, so it can be generated locally without coordination and with negligible collision probability when enough random bits are used.
  • Version 4 is essentially random; it is simple and safe to generate anywhere, but it has no order.
  • Version 1 combines time and a node identifier, which can leak MAC address and creation time.
  • Version 7 puts a timestamp first and randomness after it, giving time-ordered UUIDs that still fit the UUID format.
  • Random UUIDs scatter B-tree inserts across the index, causing page splits, write amplification, and larger indexes.
  • The textual form is long, so storing it as a string is more expensive than storing the 16 raw bytes.
  • UUIDs are a strong default when coordination-free generation matters more than compactness or scan locality.

06Ticket and segment allocation

A central service can hand out a block of IDs rather than one ID at a time. Each node then serves its own traffic locally from the reserved block.

  • The allocator reserves a range, for example a start and a step, and gives each node a disjoint block.
  • Nodes generate IDs in memory until the block is exhausted, then request another block.
  • This drastically reduces round trips and central load while keeping IDs compact and roughly ordered.
  • If a node crashes, the unused tail of its block is lost; that is usually acceptable because gaps do not break uniqueness.
  • A single allocator is still a failure domain, so use replication, multiple allocators with disjoint ranges, or a consensus-backed store.
  • Range size trades allocation frequency against the size of gaps after crashes and the risk of exhausting a range.
  • The allocator must persist the high-water mark durably before returning a block, or a restart can reissue IDs.

07Snowflake-style IDs

Snowflake IDs pack a timestamp, a worker identifier, and a sequence into a 64-bit integer. The timestamp leads, so IDs generated later generally sort later, and each node can generate without coordination.

  • The timestamp uses a custom epoch and gives coarse time ordering and a bounded lifetime.
  • The worker ID separates nodes so identical timestamps do not collide.
  • The sequence distinguishes multiple IDs generated by the same worker in the same time unit.
  • When the sequence overflows, the generator waits for the next timestamp tick rather than reusing values.
  • IDs are compact integers, which keeps primary keys and indexes small.
  • Correctness depends on synchronized clocks and on every worker having a distinct ID.
  • A clock that moves backwards can produce duplicate or out-of-order IDs, so the generator must wait, refuse, or use a logical clock.

Handling a clock rollback

  • Detect that the current time is behind the last issued timestamp.
  • Wait until the clock catches up if the drift is small.
  • Refuse to issue IDs and alert if the drift is large.
  • Never blindly reuse the previous timestamp with a reset sequence, because that repeats IDs.

08Assigning and protecting worker identities

  • Worker IDs must be unique across all live generators, including autoscaled and restarted instances.
  • Static configuration is simple but breaks when instances are cloned or replaced.
  • A registry backed by ZooKeeper, etcd, or a database can lease an ID to a node and reclaim it after the lease expires.
  • A restart must not reuse an ID until the previous lease has definitively expired and its clock state is gone.
  • Fencing tokens or generation numbers prevent an old node from continuing to write after losing its lease.
  • Running out of worker IDs is a real capacity limit; plan the ID space and reuse policy before scale-out.
  • Container orchestration can supply stable ordinals, but they are not automatically a safe global ID without a range check.

09Time-sortable alternatives: ULID, KSUID, and friends

  • ULID uses a timestamp plus random bits and encodes the result in a lexicographically sortable base32 string.
  • Sortable string IDs work well in logs and APIs, but their text form is larger than a 64-bit integer.
  • Monotonic variants increment the random portion when two IDs are generated in the same millisecond.
  • KSUID and similar formats make a different timestamp/randomness trade-off while keeping lexical order.
  • Time sortability helps keyset pagination and recent-first queries, but it also reveals approximate creation time.
  • These formats need the same clock-rollback thinking as Snowflake, even if collisions remain unlikely.

10Hash-based, composite, and custom IDs

  • A content hash gives natural deduplication for immutable blobs, but it is not a good primary key for mutable records.
  • Hash collisions must be handled explicitly, and the ID reveals information about the content if the hash is unsalted.
  • A composite ID such as shard plus local sequence keeps IDs compact and makes routing explicit.
  • Embedding a tenant or region in the ID can simplify sharding, but it makes the ID harder to change later.
  • Client-supplied idempotency keys are not record IDs; they should be stored separately to deduplicate retries.
  • A random public token can sit alongside an internal integer ID, keeping storage compact while hiding enumerable keys.
  • Never encode secrets, personal data, or authorization claims in an ID that clients can read.

11Consequences for storage, sharding, and APIs

  • Random IDs hurt B-tree locality: inserts land on many pages, causing splits and more I/O than append-only keys.
  • Time-ordered IDs make inserts roughly sequential and improve range scans and recent-first queries.
  • A 128-bit ID stored as text can be several times larger than a 64-bit integer, and every secondary index pays that cost.
  • Keyset pagination needs a stable, unique sort key; a time-ordered ID is convenient but duplicate timestamps need a tiebreaker.
  • If IDs encode the shard, moving data later requires rewriting IDs or maintaining a mapping.
  • Exposing sequential IDs invites enumeration; use random public IDs, signed URLs, or authorization checks on every read.
  • Changing an ID scheme after launch is a migration across primary keys, foreign keys, caches, and external references, so choose deliberately.

12Failure modes and security

  • Clock skew or rollback produces duplicate or non-monotonic IDs; monitor drift and enforce a rollback policy.
  • Worker ID collision happens when an instance is cloned, a lease is reclaimed too early, or configuration is copied.
  • A restarted node that reuses its previous sequence state can reissue IDs if the timestamp has not advanced.
  • An allocator outage blocks new blocks; nodes should have enough reserve to survive a short outage.
  • A sequence or worker-ID space that is too small overflows under burst load.
  • Retries can create duplicate records if the ID is generated per attempt instead of once per logical operation.
  • Guessable IDs enable IDOR and scraping; enforce authorization independent of ID secrecy.
  • Monitoring must cover generation rate, clock offset, worker-ID leaks, allocator latency, and duplicate-key errors.

13Choosing an approach

  • Single database and simple internal records: auto-increment is still the cheapest correct option.
  • Coordination-free public identifiers: UUID v4 or a random token, accepting index locality costs.
  • Compact, time-ordered IDs at high throughput: Snowflake or a segment allocator with durable ranges.
  • Sortable IDs with simple local generation: ULID or UUID v7, accepting a larger text representation.
  • Multi-region active-active: avoid a single global sequence; combine region/worker identity with local generation.
  • Legacy systems: add a new ID column, backfill, dual-write, then switch reads and writes rather than rewriting in place.
  • Whichever you choose, document the clock, worker-ID, and migration assumptions; they are part of the contract.

14How to approach it in an interview

  • Ask whether IDs must be globally unique, time-sortable, compact, or unguessable before proposing a scheme.
  • State the failure model: what happens on clock rollback, allocator outage, and worker restart?
  • Explain how worker identities are assigned and reclaimed, not just how bits are packed.
  • Call out the storage and index consequences of 64-bit versus 128-bit IDs.
  • Separate internal database IDs from public API identifiers when enumeration is a risk.
  • Describe a migration path for an existing table rather than assuming a greenfield system.
  • Finish with monitoring for duplicates, clock drift, and generation latency.
The strongest answers connect the ID format to the database's write pattern and to the system's security model, not just to uniqueness.

↔Trade-offs to say out loud

  • Auto-increment is compact and ordered but centralizes writes and fails across independent databases.
  • Random UUIDs remove coordination but hurt B-tree locality and consume more index space.
  • Time-ordered IDs improve insert locality and pagination but depend on clock behavior and reveal creation time.
  • Segment allocation reduces central load but creates gaps and requires durable allocator state.
  • Snowflake IDs are compact and sortable but require unique worker IDs and clock discipline.
  • Longer random IDs resist enumeration better but cost storage in every index and foreign key.
  • Embedding shard or tenant in the ID simplifies routing but makes IDs hard to change and can leak structure.
  • Client-supplied idempotency keys simplify retry deduplication but are not a substitute for a record identifier.
  • Multiple active generators improve availability but increase the coordination needed to avoid collisions.

?Interview questions

Answer aloud before opening the outline.

1. Why is auto-increment hard in a distributed system?

It depends on one database writer, so it becomes a throughput bottleneck and a single point of failure. Independent databases each have their own counter and will collide. Sequential values are also easy to enumerate.

2. How do UUIDs guarantee uniqueness without coordination?

They use a very large random or time-plus-random space, making collisions negligibly unlikely. Version 4 is effectively random; version 7 puts a timestamp first for sortability. No central service is needed.

3. What is the downside of random UUID primary keys?

Random inserts scatter across the B-tree, causing page splits, cache misses, and write amplification. The 128-bit width also makes every index larger than with a 64-bit integer.

4. Explain a Snowflake ID.

It packs a timestamp, a worker identifier, and a per-tick sequence into a 64-bit integer. Each worker generates locally, the timestamp gives rough ordering, and the worker ID prevents collisions between nodes.

5. What happens if the clock moves backwards on a Snowflake generator?

The node may reissue timestamps it already used. It should wait for the clock to catch up if the drift is small, or refuse to issue and alert if the drift is large. It must never reset the sequence and reuse an old timestamp.

6. How do you assign worker IDs?

Use a registry or lease service such as etcd or ZooKeeper, assign a unique ID per live generator, and reclaim it only after the lease expires. Static configuration is fragile under cloning and autoscaling.

7. How does a ticket or segment allocator work?

A central service reserves a disjoint block of IDs for a node and persists the high-water mark. The node issues IDs locally until the block runs out, then requests another. It reduces round trips at the cost of gaps and allocator dependency.

8. When would you choose ULID over UUID v4?

When you want local generation plus lexical time ordering for pagination, logs, or recent-first queries. The cost is a larger text representation and the same clock considerations as other time-based schemes.

9. Can you use a hash as a primary key?

It works for immutable content-addressed data and deduplication, but mutable records need a stable identity independent of content. Hashes also collide in theory and can leak information about the input.

10. How do IDs affect sharding?

An ID can embed a shard or region to make routing explicit, or it can be independent and mapped through a directory. Embedding simplifies routing but makes rebalancing and ID changes harder.

11. How do you expose IDs safely in a public API?

Use random or signed public identifiers and enforce authorization on every request. Never rely on an ID being hard to guess as the only access control; that is an IDOR vulnerability.

12. How would you migrate from integer IDs to UUIDs?

Add a new column, backfill in batches, dual-write both IDs, update foreign keys and caches, switch reads, then retire the old column. Plan for external references and rollback during the transition.

13. What would you monitor for an ID service?

Generation rate and latency, duplicate-key errors, clock offset and rollback events, worker-ID lease conflicts, allocator availability, and range exhaustion. Alert on any duplicate detection immediately.

!Traps

  • Assuming a UUID is automatically a good database primary key without considering index locality.
  • Letting two nodes share a worker ID after cloning or autoscaling.
  • Ignoring clock rollback and reusing a timestamp with a reset sequence.
  • Using sequential IDs in public URLs and treating secrecy as authorization.
  • Making every ID a string because it is convenient, then paying for it in every index.
  • Forgetting that retries can generate a second ID for the same logical operation.
  • Choosing a scheme without a migration plan for existing primary and foreign keys.
  • Believing a central ticket service is highly available just because it is simple.
