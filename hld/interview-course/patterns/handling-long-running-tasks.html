In one lineA request that takes minutes cannot live inside a request/response cycle. The pattern is to accept, persist, and acknowledge the work, run it on durable workers, expose progress, and make every step retryable and resumable.
Asynchronous job
Work accepted now and executed later by a worker, decoupled from the client connection that requested it.
Job record
The durable row describing the work: type, payload, owner, status, attempt count, progress, result location, and timestamps.
Job status API
A stable endpoint returning state (queued, running, succeeded, failed, cancelled) plus progress and result links.
Worker
A process that leases a job, executes it, and reports completion. Workers are disposable and horizontally scalable.
Visibility timeout / lease
The window during which a leased job is invisible to other workers; if the worker dies without completing, the job becomes claimable again.
Heartbeat
A periodic signal from a running worker that renews its lease and proves the job is not orphaned.
Checkpoint
A saved position in a long job so a retry resumes near the failure point instead of restarting from zero.
Idempotency
Designing each step so executing it twice produces the same result, which is required under at-least-once delivery.
Dead-letter queue
Where jobs go after exhausting retries, preserved for inspection and manual replay.
Backpressure
Limiting acceptance or slowing producers when workers cannot keep up, instead of letting the queue grow without bound.

01The problem

Normal API requests are designed to finish in milliseconds. Some work fundamentally cannot: transcoding a video, generating a year-end report, exporting a large dataset, running a model.

  • HTTP clients, load balancers, and proxies impose timeouts well below the duration of this work.
  • Holding a connection open consumes a worker thread or socket for the entire job, which is capacity you cannot spare.
  • A network blip or a client navigating away loses the connection, and the work dies with it if it lives in that request.
  • If the process restarts mid-job, in-memory progress disappears and the work is lost.
  • Users need to know what is happening, which a single blocking response cannot express.
  • The work is usually bursty: many submissions at once, then quiet, so provisioning for the peak inline is wasteful.

02What counts as long-running

  • Anything whose p99 exceeds the client or infrastructure timeout budget is effectively long-running.
  • Work whose duration is unpredictable, even if usually fast, is a candidate because the tail will break timeouts.
  • Work that must survive a deploy or a crash cannot be held only in process memory.
  • Work with external dependencies that can be slow or unavailable (third-party APIs, file scanning) benefits from retry isolation.
  • Quick work done inline is fine; do not queue everything, because the queue adds latency and operational surface.
  • The decision is about reliability and timeout budget, not about a fixed number of seconds.

03Accept, persist, acknowledge

The API's job changes from doing the work to recording the intent to do it.

  • Validate the request and authorization synchronously; reject bad input immediately.
  • Write a job record to durable storage with status queued, then enqueue its ID.
  • Return 202 Accepted with a job ID and a status URL — not a fake success.
  • Persist before enqueueing (or use an outbox) so a crash cannot lose an accepted job.
  • The payload in the queue should reference the stored record, not replace it; the record is the source of truth.
  • The client now has a handle it can poll or subscribe to, independent of the original connection.
Validate request→Write job row (queued)→Enqueue job ID→Return 202 + job ID→Worker executes→Client reads status

04Queue and worker architecture

  • A broker holds pending job IDs; workers pull rather than being pushed, so load self-balances.
  • Workers are stateless and disposable: any worker can run any job of a type it supports.
  • Separate queues by job type or cost so a slow export cannot starve quick thumbnail work.
  • Scale workers on queue depth and age, not just CPU; a backlog with idle CPU means external I/O is the limit.
  • The visibility timeout must exceed the expected job duration, or the job is redelivered while still running.
  • Concurrency per worker must respect downstream limits such as database connections or third-party rate limits.

05Job state machine and status API

  • Model explicit states: queued, running, succeeded, failed, cancelled, and optionally retrying.
  • Allow only legal transitions, enforced conditionally, so a late worker cannot overwrite a cancelled job.
  • The status API returns state, progress, timestamps, attempt count, and a result reference.
  • Never block a status request; read the stored record and return immediately.
  • Include an estimated completion or at least an age, so the client can decide whether to keep waiting.
  • Store large results in object storage and return a link; do not put megabytes in the status response.

06Progress tracking and heartbeats

  • Persist progress as coarse milestones (percent, items processed, current stage), not per-item write amplification.
  • Throttle progress writes; updating the record on every unit of work can cost more than the work.
  • A heartbeat renews the lease, proving the worker is alive and letting the system detect orphans.
  • Without heartbeats, a long job looks stuck and gets redelivered, causing duplicate side effects.
  • Progress must be monotonic and safe to read from a replica if slight staleness is acceptable.
  • For user-facing jobs, stage labels are more useful than a precise percentage that is often wrong.
A percentage that goes backwards destroys trust faster than no percentage at all.

07Failure handling: retries, backoff, dead letters

  • Classify errors: transient (timeout, throttling) retry; permanent (invalid input) fail fast.
  • Use exponential backoff with jitter so retries do not synchronize into a thundering herd.
  • Cap attempts and record each failure with its reason on the job record.
  • Make every step idempotent, because at-least-once delivery means duplicates are normal.
  • After the cap, move the job to a dead-letter queue with full context for inspection and replay.
  • Alert on dead-letter growth and on jobs whose age exceeds the expected duration.
Attempt fails→Transient?→Backoff + jitter→Retry→Cap reached→Dead letter + alert

08Very large jobs: chunk, checkpoint, fan out

  • Split the work into chunks that each fit comfortably inside one lease and one retry budget.
  • Persist a checkpoint per chunk so a retry resumes from the last completed unit.
  • Use a coordinator job that fans out chunk jobs and aggregates results, rather than one heroic worker.
  • Make chunk boundaries deterministic so a retry recomputes exactly the same partition.
  • Handle partial completion: define whether the final result requires all chunks or can be assembled incrementally.
  • For ordered output, aggregate by chunk index; parallel completion order is not output order.

Fan-out shape

  • A parent job records total chunks and counts completed ones.
  • Child jobs are independent and idempotent, so a lost child is simply retried.
  • The parent decides success only when every child has reported, or applies a documented partial-success rule.
  • This mirrors map-reduce and is the standard answer for exports and batch transforms.

09Cancellation and timeouts

  • Cancellation is a request, not a guarantee; the worker must observe a cancel flag or signal at safe points.
  • Check the flag between chunks, not mid-write, to avoid leaving inconsistent partial state.
  • A cancelled job should release resources (temp files, external sessions) and mark itself cancelled.
  • Enforce a maximum runtime so a hung job cannot hold a worker forever.
  • On timeout, treat it as a failure with a distinct reason, and decide whether it is retryable.
  • Clients must be told that cancellation is best-effort if the job already committed a side effect.

10Isolation, priorities, and fairness

  • Run untrusted or expensive jobs in separate worker pools so they cannot starve interactive work.
  • Assign priorities and use weighted queues; strict priority can starve low-priority jobs indefinitely.
  • Apply per-tenant quotas so one customer's bulk export does not consume the whole pool.
  • Bound concurrency per downstream dependency, not only per worker.
  • Use separate queues for retries so poison jobs do not delay fresh work.
  • Consider dedicated capacity for jobs with hard deadlines, such as nightly reports.

11Delivery semantics and exactly-once illusions

  • Most queues give at-least-once delivery; duplicates happen on redelivery, lease expiry, and retries.
  • Exactly-once end-to-end requires transactional coupling between queue, state, and side effects, which is rarely available.
  • The practical recipe: idempotency key per job plus a conditional state transition so only the first completion wins.
  • External side effects (email, payment, third-party API) need their own idempotency or dedupe layer.
  • Record completion before acknowledging the message; acknowledging first loses the job on a crash.
  • Design the job to be safe to run twice, and you no longer need to fear redelivery.

12Notifying the client

  • Polling the status endpoint is simple, cache-friendly, and works everywhere; it costs wasted requests.
  • Webhooks push completion to a server, but need signing, retries, and a receiver that is idempotent.
  • Server-sent events or WebSocket give live progress in a UI without polling storms.
  • Email or in-app notification suits jobs that finish long after the user leaves.
  • Whatever the channel, the status record remains the source of truth; notifications are hints to go read it.
  • Back off polling intervals and stop when the job reaches a terminal state.

13Operating the system

  • Monitor queue depth, oldest job age, throughput, failure rate, and retry rate per job type.
  • Alert on age, not depth: a deep queue draining fast is healthy, one stuck job is not.
  • Track execution duration percentiles to right-size leases and timeouts.
  • Log a correlation ID from submission through every worker attempt.
  • Watch cost per job type; transcoding and model inference can dominate spend.
  • Provide an admin path to inspect, retry, and cancel jobs without direct database edits.

14Choosing a design in an interview

  • Say up front which operations are synchronous and which become jobs, and why.
  • Describe the accept-persist-acknowledge flow with the 202 and job ID.
  • Name the queue, the worker pool, and the durable job record.
  • Show the state machine and the status endpoint the client polls.
  • Handle failure explicitly: retries with backoff, idempotency, dead letters, lease expiry.
  • Scale the hard part — chunking, checkpoints, and fan-out for very large jobs.
  • Finish with monitoring: oldest job age, failure rate, and dead-letter volume.

↔Trade-offs to say out loud

  • Async processing removes timeout risk and absorbs bursts but converts an immediate answer into eventual completion and a status API.
  • Polling is trivially reliable but wastes requests; push channels are efficient but add connection or webhook infrastructure.
  • Fine-grained progress pleases users but multiplies writes; coarse milestones are cheaper and often more honest.
  • Long leases avoid duplicate execution for slow jobs but delay recovery when a worker dies.
  • Small chunks make retries cheap and progress smooth but add coordination and per-job overhead.
  • Aggressive retries improve success under transient failures but amplify load on a struggling dependency.
  • Separate worker pools isolate noisy jobs but fragment capacity and reduce utilization.
  • Exactly-once attempts simplify reasoning but cost coordination; at-least-once plus idempotency is usually the better trade.

?Interview questions

Answer aloud before opening the outline.

1. Why can't a long task just run inside the HTTP request?

Because clients, proxies, and load balancers time out, and holding the connection consumes capacity for the whole job. A disconnect or deploy loses the work, and there is no way to report progress. The request should record the intent and return immediately.

2. What does the API return for an accepted job?

202 Accepted with a job ID and a status URL. The job record is already durable at that point, so a crash after the response does not lose the work.

3. How do you make sure an accepted job is not lost?

Persist the job record before enqueueing, or write the record and an outbox entry in one transaction and let a relay publish it. Acknowledge only after durability. Then a lost message can be recovered from the record.

4. What happens if a worker crashes mid-job?

Its lease expires because heartbeats stop, and the job becomes claimable again. Another worker retries it. That is why steps must be idempotent and why long jobs should checkpoint.

5. How do you avoid duplicate execution?

You cannot fully avoid it under at-least-once delivery, so you contain it: a job-level idempotency key, a conditional transition from running to succeeded so only the first completion wins, and idempotent external side effects.

6. How would you track progress for a large export?

Split the work into deterministic chunks, persist the count completed, and update progress at coarse intervals. A heartbeat renews the lease. On retry, resume from the last completed chunk rather than restarting.

7. How do you handle a job that takes hours?

Break it into chunk jobs with a coordinator, checkpoint each chunk, and keep leases and timeouts longer than one chunk rather than the whole job. A single multi-hour lease is fragile because any deploy or pause causes a duplicate run.

8. When do you retry versus fail immediately?

Retry transient errors such as timeouts, throttling, and temporary unavailability, with exponential backoff and jitter. Fail immediately on permanent errors like invalid input or missing authorization. Cap attempts and dead-letter the rest.

9. What is a dead-letter queue for?

It holds jobs that exhausted retries so they do not block the main queue and can be inspected, fixed, and replayed. Growing dead-letter volume is a signal of a systemic bug or a downstream outage.

10. How do you cancel a running job?

Set a cancel flag on the job record and have the worker check it at safe points between chunks. Cancellation is best-effort: if a side effect already committed, the system compensates instead of pretending nothing happened.

11. How do clients learn the job is done?

Poll the status endpoint, receive a webhook, subscribe over SSE or WebSocket, or get a notification. The status record is authoritative; the notification just tells the client to read it.

12. How do you scale workers?

Scale on queue depth and oldest job age per queue, within downstream limits. Workers should be stateless and disposable, with separate pools or queues by job type so expensive work does not starve quick work.

13. What would you monitor?

Queue depth, oldest job age, throughput, failure and retry rates, execution duration percentiles, lease-expiry counts, dead-letter growth, and per-job cost. Alert on age and failure rate, not only depth.

!Traps

  • Doing the work inline and raising the load balancer timeout instead of decoupling it.
  • Returning 200 OK with an empty result while the job is still queued.
  • Enqueueing before persisting, so a crash loses an accepted job.
  • Setting a visibility timeout shorter than the job, causing duplicate concurrent execution.
  • Writing progress on every item and doubling the cost of the job.
  • Retrying permanent errors forever and calling the resulting load a capacity problem.
  • Assuming exactly-once delivery and skipping idempotency guards.
  • Scaling workers without respecting downstream connection or rate limits.
