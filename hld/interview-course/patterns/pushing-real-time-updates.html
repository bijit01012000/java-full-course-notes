01The problem: HTTP cannot push

HTTP is a request-response protocol. The client asks, the server answers, and the exchange is over. When something changes later, the server has no open channel to tell anyone.

  • A client that already received its response has no open request, so the server cannot deliver a new message to it.
  • Users now expect chat messages, scores, presence, and collaborative edits to appear as they happen, without a refresh.
  • The naive fix is to have the client ask again and again, which trades freshness against a large amount of wasted traffic.
  • Every technique in this pattern is a different way of keeping a delivery path open between updates.
  • The requirement is not really real-time delivery, it is server-initiated delivery with an acceptable delay.
  • Clarify the acceptable delay early: an update that can be a few seconds late permits much simpler designs than one that must be immediate.

02Where this pattern shows up

The same underlying requirement appears across many interview problems, so the transport choice and backend routing are reusable.

  • Messaging (WhatsApp, Slack): messages, typing indicators, read receipts, and online status must appear immediately.
  • Location tracking (Uber, delivery): the driver sends location every few seconds and the rider watches the car move.
  • Live feeds and notifications: comments, sports scores, and badge counts update without a refresh.
  • Collaborative editing (Google Docs, Figma): one user's typing or cursor must reach the others almost immediately.
  • Auction bids, stock prices, seat availability: many viewers watch a value that changes constantly.
  • AI chat: tokens are streamed as they are generated instead of appearing all at once.
  • The technique is the same; only the direction, fan-out, and loss tolerance differ.

03The two parts of the problem

A complete answer has a client-server transport half and a backend routing half. Most candidates solve only the first.

  • Part 1, transport: how the client and server exchange updates, chosen from polling, SSE, or WebSockets.
  • Part 2, routing: given a new update, how the backend finds the server that holds the recipient's connection.
  • With one server, routing is trivial because every user is connected to that same server.
  • With hundreds of connection servers, the application does not know where a given user is connected.
  • The two halves are independent: you can pair SSE with pub/sub, or WebSockets with a connection registry.
  • In an interview, state both halves explicitly before diving into either one.

04Short polling

The client asks for new data on a fixed interval, for example every two seconds with a cursor such as GET /messages?after=500.

  • The server returns new items if any exist, otherwise an empty response.
  • It needs no special server, proxy, or load-balancer support beyond ordinary HTTP.
  • It is wasteful: at one million users polling every two seconds, that is 500,000 requests per second, and most return nothing.
  • Frequent polling also drains phone batteries and keeps radios awake.
  • Delay is bounded by the interval: an update arriving just after a poll waits almost the full interval.
  • Worst-case delay and request rate trade off directly, so you cannot tune both down at once.
  • Short polling is a reasonable choice when updates are rare and a few seconds of staleness is fine, such as checking whether a file export finished.

05Long polling

Long polling keeps the request open. If no data exists, the server holds the request until something arrives or a timeout, commonly around 30 seconds.

  • When an update arrives, the server responds immediately and the client opens a new request for the next one.
  • Users see updates almost instantly without a stream of empty responses.
  • It still uses plain HTTP, so it passes through firewalls, proxies, and older corporate infrastructure.
  • Every update still costs a full HTTP request and response, including headers.
  • A gap exists between the response and the next request; an update created in that gap can be missed unless the client sends its cursor.
  • Passing the last received id, such as after=501, makes catch-up correct rather than luck-based.
  • Each waiting client occupies a connection and a small amount of server state for up to the timeout.
Client sends request with cursor→Server holds it open→Update arrives or timeout fires→Server responds→Client immediately re-requests

06Serving many waiting requests

A long-polling server cannot afford a dedicated thread per waiting client.

  • With a thread per request, 100,000 waiting clients means 100,000 mostly idle threads, each with its own stack memory.
  • Real servers use an async, event-driven model where a waiting request is just a registered callback.
  • When an update is published, often through pub/sub, the server finds matching waiters and responds to them.
  • Capacity is then limited by memory, file descriptors, and connection tracking rather than threads.
  • Timeouts must be shorter than idle-connection limits in load balancers and proxies, or requests are cut silently.
  • The client must reconnect after every timeout, so timeout length and reconnect behavior have to be designed together.
This is the same resource shift that appears with SSE and WebSockets: cost moves from CPU per request to memory and file descriptors per connection.

07Server-Sent Events

SSE opens one long-lived HTTP connection and lets the server write a stream of small text events over it.

  • The server sets the content type to text/event-stream and each event is a small text block with optional id and event type.
  • Data flows only server to client; when the client needs to send something, such as posting a comment, it uses a normal HTTP request.
  • The browser's EventSource API reconnects automatically, which removes a common source of client bugs.
  • On reconnect the browser sends Last-Event-ID, so the server can resume from the last event the client saw.
  • The server must still store recent events, because the browser only reports the id, not the missed payloads.
  • It fits live feeds, notifications, stock tickers, dashboards, and token-by-token AI responses.
  • It is simpler to operate than WebSockets because it is still ordinary HTTP.

08SSE limitations

  • SSE carries only text; binary payloads must be encoded, for example as Base64, which adds size and CPU.
  • On HTTP/1.1 browsers allow only about six connections per domain, so many tabs can exhaust the limit.
  • HTTP/2 largely removes that constraint because many streams share a single connection.
  • The browser's EventSource cannot set custom headers, so auth usually relies on a cookie or a short-lived token in the URL.
  • Tokens in URLs can leak through logs and referrers, so they should be short-lived and scoped.
  • Proxies and load balancers must not buffer the response, or events arrive in bursts instead of immediately.
  • A dead connection can look healthy until a write fails, so heartbeats are still needed.

09WebSockets

When both sides send data often, a WebSocket is the better fit.

  • The connection begins as an HTTP request with an Upgrade: websocket header.
  • The server answers 101 Switching Protocols and the same TCP connection becomes two-way.
  • Either side can send at any time, and per-message overhead is only a few bytes.
  • It suits chat, multiplayer games, collaborative editing, and trading, where the client sends as often as it receives.
  • Connections are stateful: a user stays pinned to one server for the life of the connection.
  • The load balancer must pass the upgrade header through, support long-lived connections, and not close idle sockets too early.
  • The browser API does not reconnect for you, so client code must implement retry, backoff, and resubscription.

10Choosing an approach

Start from direction and freshness, then fall back to what the infrastructure supports.

  • Updates rare and seconds of delay acceptable: short polling, the simplest option.
  • Updates server-to-client only: SSE, which gives real-time delivery with less operational work than WebSockets.
  • Client and server both send frequently: WebSockets.
  • Long-lived connections poorly supported by proxies or corporate networks: long polling as a fallback.
  • Justify the choice against requirements instead of saying a technology is real-time; explain what makes it fit.
  • State the cost you accepted: extra connections, statefulness, reconnect logic, or wasted requests.

11Connection servers

With polling, any server can handle any request. With SSE and WebSockets, only the server holding the socket can push to that user.

  • Split the system into a connection tier (a gateway) that holds sockets and an application tier that runs business logic.
  • The gateway does not save messages or compute scores; it terminates connections and delivers payloads.
  • This separation lets connection capacity and application capacity scale independently.
  • A single connection server can typically hold tens of thousands of connections, and with careful tuning some systems reach hundreds of thousands.
  • Ten million concurrent users therefore implies a few hundred connection servers, not a handful.
  • The limit is usually memory and open file handles, not CPU, since each connection holds a socket and buffers.
  • Operating-system file-descriptor limits, often 1,024 per process by default, must be raised, and the tier is sized by connections rather than requests per second.
  • Connection servers are often the longest-lived and most state-heavy part of the stack, so graceful deploys matter.

12Routing updates to the right server

If user B is connected to server 7 and a message arrives on server 1, something must bridge that gap.

  • The application service that accepted the write must discover the destination connection server.
  • A connection registry stores user-to-server mappings in a fast store such as Redis and looks them up per message.
  • A pub/sub system instead has each connection server subscribe to channels for its connected users or rooms.
  • Registry entries usually carry a TTL refreshed by the connection server, so a crashed server's entries expire automatically.
  • Registry routing sends each message only where it is needed, but the mapping must be maintained on every connect, disconnect, and move.
  • Pub/sub removes that bookkeeping from the sender, but delivery depends on the broker and is typically fire-and-forget.
  • For rooms and live matches, one publish to a room channel reaches every server with a member, which is far cheaper than per-member lookups.

Registry vs pub/sub

  • The registry tells you exactly where a user is, which helps with targeted delivery, debugging, and very large systems.
  • Pub/sub keeps the sender ignorant of topology and scales naturally to groups.
  • Pub/sub can waste work if a publish reaches servers with no interested connection, depending on channel design.
  • Most interview answers use pub/sub for simplicity; reach for a registry when you need control or per-user routing.

13Disconnects and missed updates

Phones switch networks, laptops sleep, and servers restart during deploys, so every client will sometimes be disconnected exactly when an update is sent.

  • Redis Pub/Sub does not store messages; if no server is subscribed when a message is published, it is lost.
  • The fix is save first, then send: persist the update with a sequence number before attempting real-time delivery.
  • On reconnect the client sends its last sequence number and the server returns everything after it from the database.
  • This covers dropped connections, server crashes, and users who were offline for a long time with one mechanism.
  • Because an update can arrive both live and from the catch-up query, the client must deduplicate by sequence number.
  • An idle connection looks like a broken one, so client and server exchange heartbeats roughly every 30 seconds and treat silence as a closed connection.
  • Mobile operating systems close background connections to save battery, so those users are reached through APNs or FCM and fetch missed data when the app opens.
  • Sequence numbers also give a natural ordering and a resumable cursor for the client.
Sender writes message with seq 902→Persist to database→Publish seq 902→Delivery fails while offline→Client reconnects after 901→Server queries seq > 901→Client renders and deduplicates

14Reconnection storms and interview framing

A failure that disconnects many clients at once creates a second, larger load spike when they all come back.

  • If a server holding 50,000 users dies, all 50,000 reconnect simultaneously to the remaining servers.
  • Those servers also receive a burst of catch-up queries, so the database can become the next component to fail.
  • Failure then cascades: overloaded servers drop more connections, which produce more reconnects.
  • Clients should reconnect with exponential backoff plus random jitter, for example a random wait between 0 and 1 second, then 0 and 2, then 0 and 4.
  • Jitter spreads retries over time so the herd never arrives in one instant.
  • Planned deploys should close a server's connections gradually rather than all at once.
  • Interview flow: clarify direction, volume, and freshness; choose the transport; explain routing; explain save-first recovery; then discuss connection scaling and reconnect storms.
  • Name what you would monitor: concurrent connections, connect/disconnect rate, publish latency, catch-up query load, and reconnect rate per server.
Clarify requirements→Choose transport→Route to the right server→Persist before publishing→Recover missed updates→Scale and protect reconnects

↔Trade-offs to say out loud

  • Short polling is trivial to build and needs no special infrastructure, but wastes requests and battery and has delay bounded by the interval.
  • Long polling gives near-instant delivery over plain HTTP, but holds a connection per client and still pays full request overhead per update.
  • SSE is simple, text-only, and reconnects in the browser, but supports one-way flow and is constrained by per-domain connection limits on HTTP/1.1.
  • WebSockets give low-overhead two-way messaging, but connections are stateful, so deploys, load balancers, and client reconnect logic all get harder.
  • A separate connection tier lets connections and business logic scale independently, at the cost of another service to deploy and monitor.
  • A connection registry gives precise targeting, but you must keep mappings correct and expire them when servers die.
  • Pub/sub decouples senders from topology and handles rooms cheaply, but delivery is fire-and-forget and depends on broker health.
  • Save-first with sequence numbers makes delivery recoverable, but adds a database write and a catch-up read path to every update.
  • Heartbeats detect dead connections, but consume bandwidth and battery across millions of idle clients.
  • Aggressive reconnects restore service quickly per client, but synchronized retries can take down the remaining fleet.

?Interview questions

Answer aloud before opening the outline.

1. Why can't the server just push updates over HTTP?

HTTP is request-response: once the response is sent, the exchange is closed and there is no open channel for the server to use later. Every real-time technique either re-opens requests (polling) or keeps a connection open (SSE, WebSockets).

2. What are the two parts of a real-time design?

The transport between client and server (polling, SSE, or WebSockets) and the backend routing that finds the connection server holding the recipient. Most candidates cover only the transport.

3. When is short polling good enough?

When updates are rare and a few seconds of delay is acceptable, for example checking whether a background export finished. It requires no special infrastructure and is the simplest thing that works.

4. How does long polling improve on short polling?

The server holds the request until data exists or a timeout fires, so updates arrive almost instantly and empty responses disappear. The cost is one open request per client and full HTTP overhead per update.

5. How do you avoid missing a message between long-poll requests?

Have the client send the id of the last message it received, and have the server return everything after that id. The cursor makes the gap harmless.

6. Why do long-polling servers use async I/O?

A thread per waiting client would mean tens of thousands of mostly idle threads and large memory overhead. Event-driven servers register a callback per waiting request and respond when a matching update is published.

7. How does SSE reconnect work?

The browser's EventSource reconnects automatically and sends the Last-Event-ID header. The server must have stored recent events so it can replay everything after that id.

8. What are the limitations of SSE?

It is server-to-client only, text only, limited to about six connections per domain on HTTP/1.1, and EventSource cannot set custom headers, so auth uses cookies or a short-lived token in the URL.

9. When would you choose WebSockets over SSE?

When the client also sends frequently, such as chat, games, or collaborative editing. WebSockets give low overhead in both directions but require you to handle stateful connections and reconnect logic yourself.

10. Why split out connection servers?

Only the server holding a socket can push to that user, and holding millions of sockets is a different workload from business logic. A separate gateway tier lets each scale independently and keeps stateful connections away from stateless application servers.

11. What limits a single connection server?

Usually memory and open file descriptors rather than CPU, since each connection holds a socket and buffers. File-descriptor limits must be raised, and capacity is measured in connections, not requests per second.

12. How does an update reach a user connected to another server?

Either look up the user's server in a connection registry and send directly, or publish to a channel that the user's connection server subscribes to. Pub/sub is simpler to explain; a registry gives more control.

13. How do you handle updates sent while a user is offline?

Persist every update with a sequence number before publishing it. On reconnect the client sends its last seen sequence number and the server returns everything after it, so real-time delivery becomes an optimization rather than a requirement.

14. What is a reconnection storm and how do you prevent it?

When a server dies, all of its clients reconnect at once, overloading remaining servers and the database, which causes more failures. Clients should retry with exponential backoff and random jitter, and deploys should drain connections gradually.

!Traps

  • Designing only the client transport and forgetting that the backend must find the server holding the recipient's connection.
  • Saying WebSockets are required for real-time when updates are one-way and SSE would be simpler.
  • Forgetting that pub/sub is fire-and-forget, so an offline or slow client silently loses updates.
  • Not persisting updates before delivery, leaving no way to catch up after a disconnect.
  • Ignoring that WebSocket connections are stateful, which breaks naive rolling deploys and autoscaling.
  • Sizing connection servers by requests per second instead of by concurrent connections and file descriptors.
  • Letting all clients retry immediately after a failure and causing a cascading reconnection storm.
  • Assuming an idle connection is healthy without heartbeats or a write timeout.
