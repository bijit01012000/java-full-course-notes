In one lineA booking is correct only if one unit of inventory — a seat, a room, a slot — is assigned to exactly one owner, even when thousands of users hit the same unit at the same instant. The pattern is atomic claim of a uniquely identified unit, surrounded by holds, idempotency, and expiry.
Inventory unit
The smallest thing that can be booked exactly once: a specific seat, a room-night, a doctor's slot. Bookability must be modeled at this granularity, not as a free-form count.
Reservation (hold)
A temporary claim on a unit that is not yet a confirmed booking, with an expiry, so a user can finish payment without losing the seat.
Overbooking
Deliberately selling more reservations than capacity, betting on cancellations and no-shows. A business policy, not a race-condition fix.
Pessimistic locking
Taking a lock on the row before checking availability, so competing transactions queue instead of racing.
Optimistic concurrency control
Reading a version, then committing only if the version is unchanged. Conflicts fail fast and the caller retries.
Compare-and-set (CAS)
An atomic conditional update such as SET owner = ? WHERE id = ? AND owner IS NULL; the database decides the winner.
Distributed lock
A lock held in an external store so multiple services or nodes can coordinate. Correctness still depends on the resource honoring a fencing token.
Fencing token
A monotonically increasing number issued with each lock acquisition, so a stale lock holder's late write can be rejected.
Idempotency key
A client-supplied identifier that makes retrying the same booking request return the original result instead of creating a second booking.
Hot row contention
The bottleneck where many transactions target the same row, serializing throughput to what one row lock can sustain.

01The problem

Double booking is a correctness problem disguised as a performance problem. The business rule is trivial — one unit, one owner — but enforcing it under concurrency is where designs fail.

  • Two users read the same availability, both see the seat free, both write, and both think they succeeded.
  • The failure is not slow response or high load; it is a lost update that violates a uniqueness rule.
  • It shows up in flights, hotels, concert seats, restaurant tables, doctor appointments, and delivery time slots.
  • The same race exists in inventory counts, coupon redemption, and username or handle registration.
  • Reads cannot fix this: any check performed before the write is advisory unless the write itself is conditional.
  • The design question is where the single point of serialization lives, and how much contention it can absorb.

02Why double booking happens

  • Check-then-act: availability is read in one step and written in another, with a window in between.
  • Lost update: two transactions overwrite each other because neither observed the other's change.
  • Retries: a client times out, retries, and the first attempt actually succeeded — creating two bookings for one intent.
  • Multiple channels: web, mobile, call center, and partner APIs write through different paths with different rules.
  • Async confirmation: the booking is accepted into a queue and the final check happens later, after the user was told yes.
  • Cache and read replicas: availability shown from a stale copy makes users believe a sold-out unit is free.
  • Most real incidents are a retry plus a non-idempotent write, not a textbook race in a single query.
If the availability check and the claim are not the same atomic operation, you have a race regardless of how fast the code runs.

03Model the unit of inventory

You cannot make an aggregate atomic if the aggregate is a number. Model what is actually scarce.

  • Convert a slotted resource into individually identified units (seat 14A, room 302 on a given night) and give each a uniqueness constraint.
  • For genuinely interchangeable capacity, keep a counter with a check constraint that it never goes below zero.
  • Separate the reservation (temporary claim) from the booking (confirmed, paid, committed).
  • Store an explicit status — held, confirmed, cancelled, expired — rather than deleting rows, so history and disputes are auditable.
  • Every state transition should be conditional on the current state, not a blind update.
  • Pick the shard/partition key so units that compete for the same resource live together; splitting a seat's row across nodes destroys atomicity.

04Atomic conditional writes in one database

The strongest and simplest answer is to let a single database decide the winner.

  • Use a unique constraint on the unit so a second insert fails loudly instead of silently overwriting.
  • Use a conditional update: claim only if the row is still free, and inspect the affected-row count.
  • If the update affects zero rows, the unit was taken; return a clear conflict rather than a success.
  • Do the claim and the booking record in one transaction so a crash cannot leave a half-state.
  • Keep the transaction short; never hold it open while calling a payment provider or sending email.
  • This is the default design in an interview: one primary, one row per unit, one atomic claim.
-- Atomic claim: the affected-row count is the answer
UPDATE inventory
   SET status = 'held', owner_id = :user, hold_expires_at = :ts
 WHERE unit_id = :unit
   AND status = 'available';
Returning the number of affected rows is the correctness signal. A 200 response with zero rows updated is a double booking.

05Pessimistic locking

  • Lock the row (SELECT ... FOR UPDATE) before checking availability, then update and commit.
  • Competing transactions wait, so there is no window between check and write.
  • Clean and easy to reason about when contention per unit is low.
  • Lock ordering matters: acquiring multiple locks in inconsistent order causes deadlocks.
  • Lock duration is the throughput limit; holding a lock across a network call can stall every request for that unit.
  • Use a bounded lock wait and fail fast with a retry or a friendly 'seat being held' response.

06Optimistic concurrency

  • Read the row and its version; write with WHERE version = :v and increment on success.
  • Conflicts are detected at commit time and surface as zero rows updated, which the service maps to a retry or a conflict response.
  • No locks are held while the user thinks, which suits long human flows like checkout.
  • Under heavy contention on one unit, most attempts fail and retry storms make throughput worse.
  • Retries must be bounded and jittered; unbounded retry loops turn a conflict into an outage.
  • Works well when contention is naturally spread across many units.

07Distributed locks and their limits

  • A lock in Redis or another external store can coordinate services, but it is not a correctness guarantee by itself.
  • A holder can pause (GC, network partition) past its lease, and a second holder can acquire the lock while the first still believes it owns it.
  • Every write must verify a fencing token, or the late writer silently overwrites the new owner.
  • Lease expiry trades safety against liveness: short leases recover fast but expire during slow work.
  • If the resource is a single database row, prefer the row's own conditional update; it needs no separate lock service.
  • Use distributed locks for coarse coordination (one scheduler active, one job running), not as the primary booking primitive.

08The reservation (hold) pattern

Users need time to pay, and holding a database lock for that long is not viable. A hold decouples the claim from the payment.

  • The claim creates a hold with an expiry, owned by one user or session.
  • The seat is unavailable to others while held, but not yet sold.
  • Payment confirmation converts the hold to a confirmed booking in one conditional update.
  • Expiry releases the hold back to available; a background job sweeps expired holds so a crashed client cannot strand inventory.
  • Expiry must be enforced by the database or a sweeper, never by a client-side timer.
  • Distinguish 'hold expired and released' from 'hold still valid' in the confirm path; a late payment should fail cleanly, not double-sell.
Select unit→Atomic claim → hold with TTL→User pays→Conditional confirm→Confirmed or hold released on expiry

09Flash crowds: thousands competing for the same units

  • The bottleneck is contention on a few rows, so more app servers do not help; they add retries.
  • Admit users through a virtual waiting room or queue, issuing a token that grants a time-limited right to book.
  • Issue a token only for units that exist, so the crowd is bounded by real inventory rather than by request volume.
  • Reject obviously impossible requests early (sold-out event, past date) before they reach the database.
  • Shard inventory by event or region so unrelated bookings do not share a hot row.
  • Show accurate remaining inventory from the authoritative path; a stale cache turns the queue into a lottery of errors.
  • Accept that most contenders will fail; make failure fast, informative, and free of side effects.
At flash-sale scale, the design goal shifts from 'everyone can try' to 'everyone gets a fast, honest answer'.

10Idempotent booking requests

  • Require an idempotency key per booking attempt, stored with the resulting booking.
  • A retry with the same key returns the original result instead of claiming a second unit.
  • Keys must be scoped to the user or session and expired eventually, or the table grows without bound.
  • The key must be recorded in the same transaction as the booking, otherwise a crash between them reopens the duplicate window.
  • Client-side timeouts are ambiguous: the server may have succeeded, so retries are expected, not exceptional.
  • Payment capture needs its own idempotency key with the provider; a duplicate charge is worse than a duplicate seat.

11Expiry, cancellation, overbooking, and waitlists

  • Cancellation frees the unit only if the booking is currently confirmed; make that a conditional state change.
  • Refund and inventory release should be consistent: release after the refund is recorded, or compensate if it fails.
  • Overbooking is a deliberate policy with a compensation plan; it must never be the accidental result of a race.
  • A waitlist converts failed claims into demand you can notify when a hold expires or a booking cancels.
  • Expired holds and abandoned checkouts are the main source of recoverable inventory; sweep them aggressively but safely.
  • Report sold-out and released inventory so the business can see whether holds are too long or too short.

12Failure modes and what to monitor

  • Duplicate confirmations: two confirmed bookings for one unit — alert immediately; this is a data-integrity incident, not a latency issue.
  • Stranded holds: units stuck in held state because the sweeper is down; monitor hold age.
  • Retry storms: conflict rate and retry counts rising together with latency.
  • Deadlocks: lock-wait timeouts and deadlock counters on the inventory tables.
  • Queue or token leakage: admitted users far exceeding available inventory.
  • Clock and expiry skew: sweeper and confirm path disagreeing about whether a hold is still valid.

13Choosing a design in an interview

  • Start by stating the invariant: one unit, at most one active owner, at every instant.
  • Model the unit explicitly and put a unique constraint or conditional update on it.
  • Explain why a pre-check read is insufficient, then show the atomic claim.
  • Add holds with TTL so payment does not hold a database lock.
  • Add idempotency keys for retries, and say how expired holds are swept.
  • Only then discuss scale: admission queue, sharding by event, read replicas for browsing.
  • Close with the failure you would page on: a second confirmed booking for the same unit.
State invariant→Model unit→Atomic claim→Hold + TTL→Confirm conditionally→Idempotent retries→Sweep + monitor

↔Trade-offs to say out loud

  • Pessimistic locking gives simple correctness but serializes access to the unit and risks deadlocks and lock-held-too-long stalls.
  • Optimistic concurrency avoids held locks and suits human-paced checkout, but collapses into retry storms when many users target one unit.
  • Unique constraints are the cheapest guard but throw errors as normal control flow, so the API must translate them into a clean conflict response.
  • Distributed locks coordinate across services but are unsafe without fencing tokens and add a dependency and a failure mode.
  • Holds with TTL protect the user during payment but strand inventory when clients abandon or sweepers fail.
  • Virtual waiting rooms protect the database during flash crowds but add latency and a second system to operate and get right.
  • Overbooking raises utilization and revenue but creates a compensation obligation and can damage trust.
  • Caching availability for browsing reduces read load but shows stale inventory and makes users angry when the claim fails.

?Interview questions

Answer aloud before opening the outline.

1. Why can't you just check availability and then insert the booking?

Because the check and the insert are separate operations. Two requests can both observe the unit as free before either writes, so both inserts succeed and the invariant breaks. The claim itself must be conditional and atomic.

2. What is the simplest correct design for booking a seat?

One row per seat with a unique identity, and a conditional update that claims it only if its status is available. The affected-row count tells you whether you won. Wrap the claim and the booking record in one short transaction.

3. Pessimistic or optimistic locking?

Pessimistic when contention per unit is low and the critical section is short — it is easier to reason about. Optimistic when users spend real time deciding, so you cannot hold a lock, and conflicts are naturally spread out. Both need bounded retries and a clean conflict response.

4. When is a distributed lock the right tool?

For coarse coordination such as electing one active scheduler or ensuring a single job runs, and only with fencing tokens so a stale holder's writes are rejected. For a single row's uniqueness, the database itself is the better lock.

5. Why is a Redis lock dangerous for booking?

Because a lock holder can pause past its lease and keep writing after another process has acquired the lock. Without a fencing token checked by the resource, the late write wins and you double-book. Redis locks also depend on the store's availability and clock assumptions.

6. Why do you need a hold instead of a long transaction?

A payment can take minutes, and holding a database lock that long blocks every other request for that unit and risks timeouts. A hold is a persisted, expiring claim: it reserves the unit without holding a lock, and a sweeper releases it if the user never completes checkout.

7. How do you handle a user who pays after their hold expired?

Confirm conditionally on the hold still being valid. If it expired and the unit was resold, do not confirm — refund or rebook and tell the user clearly. The failure must be explicit, never a silent second booking.

8. How do you prevent duplicate bookings from retries?

An idempotency key supplied per attempt, stored in the same transaction as the booking. A retry with the same key returns the original result. Also make the payment capture idempotent with its own key.

9. How would you handle a flash sale with far more users than seats?

Admit through a waiting room or queue and issue time-limited tokens for units that actually exist. Reject impossible requests early, shard inventory by event, serve accurate availability, and make failures fast. More app servers alone will not help because the bottleneck is contention on the same rows.

10. What does overbooking have to do with this pattern?

Nothing mechanically. Overbooking is a deliberate business policy based on expected cancellations. It must be implemented as an explicit capacity setting, never as a side effect of a race, and it needs a compensation plan when more guests arrive than rooms exist.

11. How do you model hotel inventory where any room of a type will do?

Use a counter per room type per night with a conditional decrement that cannot go below zero, or one row per physical room-night if assignment matters. Per-night rows make multi-night bookings require claiming every night atomically, usually in a fixed order.

12. What breaks when you shard inventory across databases?

Atomicity across shards. A booking spanning several units on different shards needs a single owner per shard, ordered claims, and compensation if a later claim fails. Shard by the resource that must be claimed together, such as event or property.

13. What would you monitor and page on?

Page on any second confirmed booking for the same unit — that is the invariant breaking. Also watch hold age, conflict and retry rates, deadlock counts, sweep failures, and admitted-versus-available ratios during sales.

!Traps

  • Reading availability, then inserting the booking, and treating that as atomic.
  • Returning HTTP 200 without checking how many rows the conditional update affected.
  • Holding a database transaction open while calling the payment provider.
  • Using a Redis lock without a fencing token and assuming it guarantees exclusivity.
  • Shrinking the problem to 'add a unique index' while ignoring retries and multi-night claims.
  • Trusting a client-side timer to release expired holds.
  • Caching availability for browsing and then showing users seats they cannot actually book.
  • Treating overbooking as an implementation detail instead of an explicit policy with compensation.
