Capacity Estimation

Back-of-the-envelope numbers that change design decisions — request rates, storage, bandwidth, cache memory, and server count.

The purpose Estimation is not a math test. It is a way to decide whether data fits on one machine, whether the database can handle the traffic, whether you need a CDN, and where the architecture will break first.
QPS
Queries or requests per second; distinguish average from peak.
DAU
Daily active users — a starting point for request-rate estimates.
Peak traffic
Common assumption: 2–3× average, depending on the product.
Throughput
Work completed per second; limited by the bottleneck component.
Bandwidth
Data carried per second; bits vs bytes matters by a factor of 8.
Replication factor
Number of copies of data; multiplies raw storage.

01When to estimate

  • Estimate when the number changes a design decision: single machine vs distributed, cache size, CDN, sharding.
  • Skip detailed math when it will not change the architecture — e.g. total storage for a ticket-booking system may not matter.
  • For a video platform, storage and bandwidth are central: they decide object storage, transcoding, and CDN design.
  • Ask: “What decision will this estimate help me make?” If there is no answer, skip it.
  • A few minutes of estimation is usually enough; do not spend the interview doing arithmetic.
DAU→ actions/day→ average QPS→ peak QPS→ storage / bandwidth / servers

02Powers of ten

NumberPowerData size
Thousand10³1 KB = 1,000 bytes
Million10⁶1 MB = 1 million bytes
Billion10⁹1 GB = 1 billion bytes
Trillion10¹²1 TB = 1 trillion bytes
Quadrillion10¹⁵1 PB = 1,000 TB
  • Use powers of ten for quick estimates; keep the leading digits and add exponents.
  • Binary units (KiB, MiB, GiB) are based on 1,024; they matter for memory but not rough interview math.
  • Example: 1 billion records × 1 KB = 10⁹ × 10³ bytes = 10¹² bytes = 1 TB.

03Time conversions

  • Round a day to 100,000 seconds for quick math; it is close enough and easy to divide.
  • Round a year to 400 days for annual storage; it adds a safety margin.
  • Peak is not average. Multiply average QPS by 2–3 for typical peaks, more for event-driven products.

04Latency numbers

OperationApproximate latency
Read from main memory~100 ns
Random read from SSD~100 μs (about 1,000× memory)
Network round trip within one data centre~0.5 ms
Random seek on a hard diskSeveral ms
Network round trip US ↔ Europe~100–150 ms
  • Memory is far faster than disk; this is why caches such as Redis can serve sub-millisecond reads.
  • Cross-region round trips dominate user latency; CDNs and regional deployments reduce the distance.
  • You do not need exact values; know the order of magnitude and the relative gaps.

  • Media dominates storage. Video platforms often store multiple resolutions, multiplying the raw size.
  • Always include replication, indexes, and metadata overhead in production storage estimates.

  • These are rough guidelines; hardware, workload, and data size change the real number.
  • Complex requests and downstream calls reduce app-server throughput.
  • Database writes are usually more expensive than reads, especially with multiple indexes.
  • 500 writes/sec may fit one primary; 500,000 writes/sec likely needs sharding or a write-optimized design.

07Worked example: social media platform

Assume 200 million daily active users, 2 posts per user per day, and 50 feed views per user per day. Peak traffic is 2–3× average.

Requests per second

  • Posts per day = 200M × 2 = 400M.
  • Average posts/sec = 400M ÷ 86,400 ≈ 4,600; peak ≈ 10,000 posts/sec.
  • Feed reads per day = 200M × 50 = 10B.
  • Average feed reads/sec ≈ 115,000; peak ≈ 250,000–300,000/sec.
  • The read rate is about 25× the write rate → optimize for reads.

Storage, bandwidth, cache, servers

EstimateApproximate resultDesign decision
Post text over 5 years~800 TBPartition across multiple database nodes
Images over 5 years~40 PBObject storage; database stores references
Outgoing image bandwidth~50 GB/secCDN to distribute traffic
Cached feeds~1–1.5 TBDistribute across ~10–15 Redis nodes
Peak feed requests~300,000/sec~80–90 app servers with 30–50% headroom
What the numbers tell you: read-heavy → precompute/cache feeds; huge images → object storage; huge outbound bandwidth → CDN; cache too large for one node → distributed cache; ~300k req/sec → horizontal app tier.

08Presenting your estimates

  • State assumptions first: “200M DAU, 2 posts/day, 1 KB per post.” Let the interviewer correct you.
  • Round aggressively: 86,400 → 100,000; one or two significant digits.
  • Show the decision: “This is ~800 TB, so it will not fit on one database node.”
  • Do not calculate everything: focus on the numbers that change the architecture.
  • Separate average and peak; peak drives capacity.
  • Include overhead: replication, indexes, metadata, and safety headroom.
Interview line: “These are rough numbers, but the ratio is what matters: reads are ~25× writes, so I’ll design for read scale first.”

For 3–5 YOE: use two or three estimates to justify a component choice. You do not need a perfect model; you need a defensible direction.

!Traps

  • Doing math for ten minutes without connecting it to a design decision.
  • Using daily average as peak capacity.
  • Forgetting replication and metadata overhead.
  • Mixing bits and bytes.
  • Assuming one database or one cache node can hold everything.
  • Quoting overly precise numbers that imply false confidence.
  • Ignoring read/write ratio — it changes the whole architecture.
  • Estimating storage but forgetting bandwidth and cache memory.
