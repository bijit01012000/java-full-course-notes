    Part 6 · Optional, Exceptions & Memory · Lecture 45

    Java Memory Management Explained in Depth — Stack, Heap, Method Area & PC

    15 sections · interview-oriented · both themes

    Scope evidence: "Java Memory Management Explained in Depth | Stack, Heap, Method Area & PC" (playlist map, verified). Repo evidence: 2 Demo files.

    Every Java program runs inside a JVM whose memory is divided into well-defined runtime data areas, and the split between the stack and the heap is the most examined memory topic in Java interviews. Some areas belong to a single thread and die with it, while others are shared by every thread and live as long as the JVM. Understanding which area holds what explains recursion failures, object lifetimes, static state and garbage collection. This lecture maps the JVM runtime data areas — Heap, Method Area (Metaspace), Stack, PC Register and Native Method Stack — and follows a reference on the stack to the object it points to on the heap.

    1. The Runtime Data Areas: Per-Thread vs Shared

    The JVM specification divides runtime memory into five data areas. The first cut is ownership: three areas are created per thread, and two are created once and shared by all threads.

    1. Per-thread areas — JVM Stack, PC (Program Counter) Register, Native Method Stack. Each thread gets its own copy, created when the thread starts and destroyed when it ends.
    2. Shared areas — Heap and Method Area. Created at JVM start-up and shared by every thread.
    Area Ownership Holds Error thrown
    Heap shared by all threads every object and array; string-pool literals OutOfMemoryError
    Method Area / Metaspace shared by all threads class metadata, field and method data, bytecode, static variables OutOfMemoryError
    JVM Stack one per thread frames: local variables, operand stack, return address StackOverflowError
    PC Register one per thread address of the instruction the thread is executing none
    Native Method Stack one per thread frames for native (non-Java) methods via JNI StackOverflowError / OutOfMemoryError

    Memory aid: two shared, three per-thread; the CPU-tracked areas are per-thread, the data areas are shared.

    2. The Stack: Frames, Locals, and LIFO Discipline

    Each thread has its own JVM stack, a last-in-first-out (LIFO) region of memory. Every method call pushes one frame onto the thread's stack, and every return pops it. A frame holds three things:

    1. Local variables — the method's parameters and locals. A primitive local (int, double, boolean) is stored directly in the frame. A local object variable stores a reference, not the object.
    2. Operand stack — the working area where the bytecode pushes and pops intermediate values while computing an expression.
    3. Return address / frame data — enough bookkeeping to resume the caller after the method returns.

    The LIFO order matches the call graph: a method that is called last must finish first. Because the stack is small and its top moves by a simple pointer, allocation and deallocation of frames are extremely fast — faster than heap allocation, which must find space and later be reclaimed.

    // Demo.java — each call pushes a frame; each return pops it (sketch)
static int add(int a, int b) {
    int sum = a + b;      // a, b, sum live in this frame on the stack
    return sum;           // frame popped; locals gone
}

    Important A local statement such as Object o = new Object(); creates the object on the shared heap and stores only the reference o in the frame. The stack never holds the object itself.

    3. StackOverflowError: When the Stack Runs Out

    The stack has a fixed maximum size — typically a fraction of a megabyte to a couple of megabytes, tunable with -Xss. Because each call consumes a frame and frames are only released on return, an unbounded chain of calls exhausts the stack. The JVM then throws StackOverflowError. This is the classic outcome of recursion without a base case (cross-ref Lecture 11).

    // Demo.java — unbounded recursion exhausts the stack
public class Demo {
    static void recurse(int depth) {
        System.out.println("depth = " + depth);
        recurse(depth + 1);            // no base case -> frames never pop
    }
    public static void main(String[] args) {
        try {
            recurse(0);
        } catch (StackOverflowError e) {
            System.out.println("caught StackOverflowError");
        }
    }
}

    Two facts separate this from a heap failure:

    1. StackOverflowError is thrown when the stack is full — usually deep or infinite recursion — not because the heap is full.
    2. The size is controlled by -Xss (for example -Xss1m). Increasing it delays the error but never removes the missing base case.

    Common mistake Catching StackOverflowError and continuing can leave the thread in a damaged state; the correct fix is a terminating condition or the removal of the recursion.

    4. The Heap: Where Every Object and Array Lives

    The heap is the shared region where every object and every array is allocated, whatever method or thread created it (cross-ref Lecture 10 and Lecture 12). The heap is the largest area and the one the Garbage Collector (forward-ref Lecture 46) manages: an object stays alive as long as some reachable reference points to it, and it is reclaimed once no such reference remains.

    The heap is sized by two flags: -Xms sets the initial size and -Xmx sets the maximum. If the collector cannot free enough space before the maximum is reached, the JVM throws OutOfMemoryError: Java heap space.

    // Demo2.java — the reference is on the stack, the object is on the heap
public class Demo2 {
    public static void main(String[] args) {
        StringBuilder sb = new StringBuilder("hello");   // sb (stack) -> heap object
        StringBuilder ref = sb;                          // second reference to the SAME object
        ref.append(" world");                            // mutate the heap object
        System.out.println(sb);                          // hello world
        sb = null;                                       // only the reference is cleared
        System.out.println(ref);                         // hello world -- object still reachable
    }
}

    The last two lines are the whole point of references: clearing sb does not destroy the object, because ref still points to it. The object on the heap outlives any single reference.

    5. Stack vs Heap: Ownership, Size, Speed, Errors

    Aspect Stack Heap
    Ownership one stack per thread shared by all threads
    Data stored primitive locals, references, operand stack, return address all objects and arrays
    Size small and limited, set by -Xss large, set by -Xms and -Xmx
    Speed very fast, LIFO pointer movement slower, allocation plus later GC
    Lifetime ends when the method returns until no reachable reference remains
    Error thrown StackOverflowError OutOfMemoryError
    Who manages it the JVM, automatically as calls enter and leave the Garbage Collector (forward-ref Lecture 46)

    The asymmetry is the lesson: the stack is automatic, tiny and fast; the heap is shared, large and GC-managed. Neither replaces the other — a program needs both the bookkeeping of calls and the long-lived storage of objects.

    6. The Method Area / Metaspace: Class Metadata and Statics

    The Method Area is the shared region that stores per-class information: the run-time constant pool, field and method data, the bytecode of methods, and all static variables. In HotSpot it is physically implemented as Metaspace, which lives in native memory outside the Java heap. One class's metadata exists once, no matter how many threads or objects use it.

    // Demo.java — a static field lives with the class, not with any object
public class ClassStats {
    static int classCounter = 0;   // Method Area / Metaspace -- one copy per class
    int instanceCounter = 0;       // heap -- one copy inside each object
    ClassStats() {
        classCounter++;
        instanceCounter++;
    }
    public static void main(String[] args) {
        ClassStats a = new ClassStats();
        ClassStats b = new ClassStats();
        System.out.println(a.instanceCounter);    // 1 -- per object, on the heap
        System.out.println(ClassStats.classCounter);  // 2 -- per class, in Metaspace
    }
}

    Two consequences follow from statics living in the shared Method Area:

    1. A static field is shared by every thread and every object of the class — a natural place for shared state and a natural source of leaks.
    2. A static reference keeps the object it points to reachable for the entire life of the class, so it can never be collected while the class is loaded (forward-ref Lecture 46).

    Important Since Java 7, string literals that used to sit in the Method Area were moved to the heap as part of the string constant pool (cross-ref Lecture 25).

    7. PermGen vs Metaspace: The Java 8 Change

    Before Java 8, class metadata was stored in PermGen (Permanent Generation), a fixed-size region inside the Java heap. Its small default size made OutOfMemoryError: PermGen space a common failure when many classes were loaded. Java 8 removed PermGen and replaced it with Metaspace, which uses native memory and grows by default.

    Aspect PermGen (Java 7 and earlier) Metaspace (Java 8 and later)
    Location inside the Java heap native memory, outside the heap
    Size behaviour fixed at start-up grows on demand by default
    Default limit small; frequent OutOfMemoryError limited only by available native memory
    Main tuning flags -XX:PermSize, -XX:MaxPermSize -XX:MetaspaceSize, -XX:MaxMetaspaceSize
    String literals PermGen up to Java 6; heap from Java 7 on the heap (since Java 7)
    Status removed in Java 8 current implementation

    The practical difference: a bounded Metaspace can still throw OutOfMemoryError: Metaspace, but only when -XX:MaxMetaspaceSize caps it or native memory runs out — not because of a small fixed default.

    8. The PC Register and the Native Method Stack

    The last two areas are per-thread and small:

    1. PC (Program Counter) Register — holds the address of the bytecode instruction the thread is currently executing. Because each thread has its own PC register, the JVM can suspend one thread, remember exactly where it was, switch to another, and later resume the first at the same instruction. This is the mechanism behind thread switching. For a thread executing a native method, the PC register is undefined.
    2. Native Method Stack — holds frames for methods written in languages other than Java (for example C or C++) and invoked through JNI. It parallels the JVM stack but serves non-Java code; a native implementation may also throw StackOverflowError or OutOfMemoryError.

    Memory aid: the PC register is the bookmark, the stack is the call history, and the native stack is the same idea for foreign code.

    9. References, Reassignment, and Escape Analysis

    A reference variable on the stack holds an address, and reassigning it does not move or duplicate the object (cross-ref Lecture 14):

    object → p = new Point(2, 3);   // heap object allocated
p = new Point(5, 6);            // p now points to a NEW object
// the first object is unchanged; it simply has no reference and becomes eligible for GC

    There is one deliberate exception to "objects always live on the heap": the JIT compiler can apply escape analysis with scalar replacement. If it proves that a newly created object never escapes its method — no reference to it is stored or returned — it may decompose the object into its fields and keep them on the stack, avoiding a heap allocation and the GC cost entirely.

    // Demo2.java — escape analysis can scalar-replace a non-escaping object
public class EscapeDemo {
    record Point(int x, int y) {}
    static int sum() {
        Point p = new Point(2, 3);   // p never escapes sum()
        return p.x() + p.y();        // JIT may keep p's fields on the stack
    }
    public static void main(String[] args) {
        System.out.println(sum());   // 5
    }
}

    Interviewer's perspective Escape analysis is a JIT optimization, not the language rule. The specification still says objects are heap-allocated; you should never rely on stack allocation for correctness, only understand it as a performance possibility.

    10. Pitfalls and Common Traps

    Pitfall Reality
    "Objects live on the stack because methods create them." Objects live on the heap; the method frame holds only the reference. Scalar replacement is a rare JIT exception.
    Confusing ownership across threads Each thread has its own stack, PC register and native stack; the heap and Method Area are shared.
    PermGen vs Metaspace confusion PermGen was a fixed heap region removed in Java 8; Metaspace is native, unbounded by default.
    Mixing up the two errors StackOverflowError = exhausted stack (deep recursion); OutOfMemoryError = exhausted heap or Metaspace.
    "A primitive is always on the stack." A primitive local is on the stack, but a primitive field of an object lives on the heap inside that object.
    Memory leak through static references A static collection in the Method Area keeps its entries reachable forever (forward-ref Lecture 46).

    11. Myth vs Reality

    Myth Reality
    "Objects are created on the stack." Objects are allocated on the heap; the stack stores a reference to the object (unless the JIT scalar-replaces a non-escaping object).
    "Primitives always live on the stack." A local primitive is in the frame, but a primitive field is stored on the heap as part of its object.
    "Each thread gets its own heap." The heap and Method Area are shared; only the stack, PC register and native stack are per-thread.
    "PermGen was simply renamed Metaspace." PermGen was a fixed region inside the heap; Metaspace uses native memory and grows by default.
    "StackOverflowError and OutOfMemoryError mean the same thing." StackOverflowError signals an exhausted stack; OutOfMemoryError signals an exhausted heap or Metaspace.
    "Reassigning a reference moves the object." The reference changes target; the original object stays where it was until it is garbage collected.
    "Static variables live on the heap with the objects." Static variables belong to the class and live in the Method Area / Metaspace.

    12. Common Trap Questions

    Trap 1 — "Since methods create objects, objects live on the stack." Objects are allocated on the shared heap; the frame holds only a reference. Stack allocation appears solely through JIT escape analysis, which is an optimization and not guaranteed.

    Trap 2 — "Every thread has its own heap, so threads cannot share objects." The heap and Method Area are shared. Only the JVM stack, PC register and native method stack are per-thread; shared objects are exactly why concurrency control is needed.

    Trap 3 — "Where do static variables live?" In the Method Area / Metaspace, with the class metadata — one copy per class, shared by all threads and all instances.

    Trap 4 — "A StackOverflowError means the heap is full." It means the current thread's stack is full, normally from recursion without a base case. The heap is unrelated, so raising -Xmx does not help.

    Trap 5 — "A primitive variable is always stored on the stack." Only a primitive local is. A primitive field is laid out inside its object on the heap, so it is collected with the object.

    Trap 6 — "What happened to PermGen, and can Metaspace still overflow?" It was removed in Java 8 and replaced by Metaspace in native memory. Metaspace can still throw OutOfMemoryError if -XX:MaxMetaspaceSize caps it or native memory is exhausted.

    Trap 7 — "Reassigning a reference destroys the object it used to point to." It only retargets the reference. The object becomes eligible for collection only when no reachable reference points to it (Lecture 46).

    13. Points to Remember

    1. The JVM has five runtime data areas: Heap, Method Area (Metaspace), Stack, PC Register and Native Method Stack.
    2. Heap and Method Area are shared by all threads; Stack, PC Register and Native Method Stack are per-thread.
    3. One JVM stack per thread; every method call pushes a frame holding locals, operand stack and return address, and every return pops it (LIFO).
    4. Primitive locals live directly in the frame; object variables hold references whose targets live on the heap.
    5. All objects and arrays are allocated on the heap; the heap is sized by -Xms and -Xmx and cleaned by the Garbage Collector (forward-ref Lecture 46).
    6. An overly deep call chain throws StackOverflowError; the stack size is set by -Xss.
    7. The Method Area / Metaspace stores class metadata and static variables; one copy per class, shared by all threads.
    8. PermGen, a fixed region in the heap, was replaced in Java 8 by Metaspace, which uses native memory and grows by default.
    9. Each thread has a PC register holding the address of the instruction being executed, which enables thread switching; it is undefined for native methods.
    10. Native (non-Java) methods run on the per-thread Native Method Stack through JNI.
    11. Since Java 7 the string constant pool lives on the heap (cross-ref Lecture 25); reassigning a reference does not move the object (cross-ref Lecture 14).
    12. Escape analysis with scalar replacement may place a non-escaping object's fields on the stack — a JIT optimization, not a language guarantee.

    14. Likely Interview Questions

    Question Crisp Answer
    What are the JVM runtime data areas? Heap, Method Area (Metaspace), JVM Stack, PC Register and Native Method Stack.
    Which areas are shared and which are per-thread? Heap and Method Area are shared; Stack, PC Register and Native Method Stack are per-thread.
    What does a stack frame contain? Local variables (primitives and references), the operand stack, and return/frame data.
    Where do objects live? On the heap. The stack stores only a reference to the object (apart from JIT scalar replacement).
    Where do primitives live? A primitive local lives in its stack frame; a primitive field lives on the heap inside its object.
    What causes StackOverflowError? The thread's stack is exhausted, usually by deep or infinite recursion; it is unrelated to the heap.
    What causes OutOfMemoryError? The heap or Metaspace is exhausted; sized by -Xmx and -XX:MaxMetaspaceSize respectively.
    What is the Method Area / Metaspace? The shared area storing class metadata, method bytecode and static variables.
    PermGen vs Metaspace? PermGen was a fixed heap region (Java 7 and earlier); Metaspace uses native memory and grows by default (Java 8+).
    What does the PC register do? Per thread, it holds the address of the instruction being executed, enabling suspend/resume and thread switching; it is undefined for native methods.
    What is the Native Method Stack? The per-thread stack for methods written in native code and called through JNI.
    What is escape analysis? A JIT optimization that can scalar-replace a non-escaping object, keeping its fields on the stack instead of the heap.

    15. Final Summary

    source → class metadata (Method Area / Metaspace, shared)
       → static variables (Method Area, shared, one copy per class)
       → reference in a frame (Stack, per thread) → new object (Heap, shared)
       → method call (push frame) → return (pop frame) → deep recursion → StackOverflowError
       → each thread also owns a PC Register (current instruction) and a Native Method Stack (JNI)
       → no reachable reference → object eligible for GC (Lecture 46)
    • Five areas → Heap and Method Area shared; Stack, PC Register and Native Method Stack per-thread
    • Stack → one per thread, frames hold locals, operand stack and return address, LIFO, -Xss
    • Heap → all objects and arrays, -Xms/-Xmx, GC-managed, OutOfMemoryError when full
    • Method Area → class metadata and statics; PermGen (fixed, Java 7) became Metaspace (native, Java 8)
    • PC Register and Native Method Stack → per-thread execution bookkeeping, including native code via JNI
    • References → a stack variable points to a heap object; reassignment does not move the object

    Golden rule The stack is per-thread and short-lived and holds references; the heap and Method Area are shared and long-lived and hold the objects and class metadata those references name.

    One-line takeaway: memory is split into shared data areas (Heap, Method Area/Metaspace) and per-thread execution areas (Stack, PC Register, Native Method Stack), and a reference on the stack is the only bridge to an object on the heap.
