    Part 4 · Strings, Generics & Collections · Lecture 29

    Java Collection Framework Explained | Data Structures + Complete Hierarchy

    15 sections · interview-oriented · both themes

    Scope evidence: "Java Collection Framework Explained | Data Structures + Complete Hierarchy" (playlist map, verified). Repo evidence: notes.pdf only.

    The Java Collections Framework (JCF) is the standard toolkit for storing and manipulating groups of objects, and almost every real Java program depends on it. It is not a single class but a coordinated set of interfaces, concrete implementations and reusable algorithms packaged under java.util. Understanding its hierarchy is what lets you pick the right structure for a problem instead of reaching for an array by reflex. This lecture maps the whole hierarchy, explains what each interface guarantees, compares the implementations by their underlying data structures and Big-O costs, and clears up the classic Collection versus Collections confusion.

    1. What the Collections Framework Is

    The JCF is a unified architecture with exactly three parts:

    1. Interfaces - the abstract data types that define the contract: List, Set, Queue, Deque, Map and their sorted variants.
    2. Implementations - the concrete, reusable classes that fulfil those contracts: ArrayList, HashSet, HashMap, TreeMap, ArrayDeque and many others.
    3. Algorithms - the static methods in the Collections utility class (sort, binarySearch, reverse, shuffle, unmodifiableList) that operate on collections.

    The design payoff is reuse and substitutability: you program to an interface and can swap the implementation without rewriting calling code.

    // Demo.java - program to the interface, not the implementation
import java.util.*;

public class Demo {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();       // List is the interface
        Map<String, Integer> ages = new HashMap<>();  // Map is a separate root
        names.add("Ada");
        ages.put("Ada", 36);
        System.out.println(names.size() + " " + ages.get("Ada"));  // 1 36
    }
}

    Important Interfaces are the vocabulary, implementations are the choices, and algorithms are the verbs. A well-written method takes the interface type and lets the caller decide the implementation.

    2. The Complete Hierarchy

    Everything begins at Iterable, which supplies the for-each loop. Collection extends Iterable, and the three primary sub-interfaces branch from it. Map sits on its own.

    Iterable
  -> Collection
       -> List
       -> Set  -> SortedSet -> NavigableSet
       -> Queue -> Deque
Map (separate root, NOT a Collection)
  -> SortedMap -> NavigableMap

    The single most important fact in the whole framework: Map is NOT a Collection. Map does not extend Collection and does not extend Iterable; it is a separate root interface because it stores key -> value pairs rather than a sequence of elements. A HashMap therefore cannot be passed where a Collection is expected.

    Interviewer's perspective The question "is Map a Collection?" is asked to see whether you memorised a diagram or understood it. The precise answer: Map is an independent root; only its views (keySet(), values(), entrySet()) are Collection instances.

    3. Interface Characteristics

    Interface Ordering Duplicates Positional index Access by key Purpose
    List insertion order allowed yes no ordered sequence
    Set unspecified rejected no no uniqueness
    SortedSet / NavigableSet sorted rejected no no sorted, range views
    Queue FIFO allowed no no process at the head
    Deque both ends allowed no no queue or stack
    Map unspecified unique keys no yes key -> value lookup
    SortedMap / NavigableMap sorted by key unique keys no yes sorted keys, range views

    Reading the table: List is about position and order; Set is about uniqueness; Queue/Deque are about ends and processing order; Map is about key lookup; the sorted variants add ordering that the plain forms never promise.

    4. Implementations Map

    Each interface has a family of implementations, and each implementation is a particular data structure.

    Interface Implementations Underlying structure
    List ArrayList, LinkedList, Vector, Stack dynamic array / doubly linked list / dynamic array (legacy)
    Set HashSet, LinkedHashSet, TreeSet hash table / hash table + linked list / red-black tree
    Queue PriorityQueue, ArrayDeque, LinkedList binary heap / resizable array / doubly linked list
    Map HashMap, LinkedHashMap, TreeMap, Hashtable, ConcurrentHashMap hash table / hash + linked list / red-black tree / hash table (legacy) / concurrent hash table

    5. Underlying Data Structures

    The behaviour of every implementation follows directly from the structure beneath it:

    Structure One-line description Implementations
    Dynamic array contiguous, resizable, O(1) index access ArrayList, Vector, Stack
    Doubly linked list node chain, O(1) insert/remove at ends LinkedList
    Hash table buckets from hashCode, average O(1) lookup HashSet, HashMap, Hashtable, ConcurrentHashMap
    Balanced tree (red-black) self-balancing sorted tree, O(log n) TreeSet, TreeMap
    Binary heap partially ordered array, O(1) peek, O(log n) add/poll PriorityQueue

    A LinkedHashSet/LinkedHashMap is a hash table whose entries are threaded onto a doubly linked list to remember insertion order.

    6. Big-O of Common Operations

    get means get(index) for lists and get(key) for maps; sets and PriorityQueue have no positional or keyed get.

    Structure add / put get remove contains
    ArrayList O(1) amortized at end; O(n) by index O(1) O(n) O(n)
    LinkedList O(1) at ends; O(n) by index O(n) O(1) at ends; O(n) search O(n)
    HashSet O(1) average n/a O(1) average O(1) average
    TreeSet O(log n) n/a O(log n) O(log n)
    HashMap O(1) average O(1) average O(1) average O(1) average
    TreeMap O(log n) O(log n) O(log n) O(log n)
    PriorityQueue O(log n) O(1) peek only O(log n) poll O(n)

    Memory aid Hash structures buy O(1) average and lose order; tree structures buy sorted order at O(log n); arrays buy O(1) index access and pay O(n) for insert/remove in the middle. The worst case for HashMap is O(n) under heavy collisions, reduced to O(log n) since Java 8 by treeifying a bucket.

    7. Collection vs Collections

    This is the single most common naming trap in the framework: one is an interface, the other is a utility class. They are unrelated.

    Aspect Collection Collections
    Kind interface (root of List, Set, Queue) final utility class
    Package java.util java.util
    Instantiable no, implemented by classes no, private constructor, only static methods
    Purpose contract for a group of elements algorithms and wrappers for collections
    Representative members add, remove, contains, size, iterator, stream sort, reverse, shuffle, binarySearch, unmodifiableList, emptyList, singletonList, synchronizedList
    Typical use Collection<String> c = new ArrayList<>(); Collections.sort(list); 
    // Demo2.java - the Collections utility class in action
import java.util.*;

public class Demo2 {
    public static void main(String[] args) {
        List<Integer> nums = new ArrayList<>(List.of(3, 1, 2));
        Collections.sort(nums);                                  // [1, 2, 3]
        Collections.reverse(nums);                               // [3, 2, 1]
        List<Integer> frozen = Collections.unmodifiableList(nums); // read-only view
        List<String> none = Collections.emptyList();             // immutable empty list
        System.out.println(frozen + " " + none);                 // [3, 2, 1] []
    }
}

    Important Collections.unmodifiableList returns a view, not a copy: writes through the original list are still visible, and any write through the returned view throws UnsupportedOperationException.

    8. Legacy vs Modern

    Several early classes still compile but should not appear in new code. They are synchronized internally, which makes them slow under single-threaded use and coarse under concurrency.

    Legacy Modern replacement Reason
    Vector ArrayList (or CopyOnWriteArrayList) method-level synchronization is unnecessary and slow
    Hashtable HashMap / ConcurrentHashMap disallows null; coarse locking
    Stack ArrayDeque Stack extends Vector; Deque has a cleaner LIFO API
    Enumeration Iterator lacks remove and fail-fast semantics

    The modern concurrency story moves to java.util.concurrent (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue), the subject of Lecture 33; the broader inheritance caveats that make legacy classes risky are revisited in Lecture 56.

    9. Choosing a Collection: A Decision Guide

    Question If yes If no
    Need key -> value mapping? Map family Collection family
    Duplicates allowed? List or Queue Set
    Need sorted order? TreeSet / TreeMap / PriorityQueue HashSet / HashMap
    Need insertion-order iteration? LinkedHashSet / LinkedHashMap plain hash variants
    FIFO or LIFO processing? Queue / Deque (ArrayDeque) List
    Frequent random access by index? ArrayList LinkedList
    Need thread safety? ConcurrentHashMap / CopyOnWriteArrayList ordinary implementations

    Interviewer's perspective Interviewers rarely want a memorised answer; they want your reasoning. Walk the decision table aloud - mapping, duplicates, ordering, access pattern, concurrency - and the correct class falls out of the requirements instead of a guess.

    10. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Treating Map as a Collection Collection<...> c = new HashMap<>(); does not compile Map is a separate root; iterate keySet, values or entrySet
    Mutating while iterating ConcurrentModificationException from a fail-fast iterator use Iterator.remove or removeIf (Lecture 30)
    Ignoring boxing autoboxing allocates wrapper objects for primitives be aware of the cost; use primitive arrays when needed (Lecture 18)
    Relying on HashMap/HashSet order iteration order is unspecified and may change use LinkedHashMap/LinkedHashSet for predictable order
    Using Vector/Stack in new code legacy, fully synchronized, slower use ArrayList/ArrayDeque; use java.util.concurrent for sharing
    Using LinkedList for random access get(i) is O(n) and kills performance use ArrayList when index access is frequent
    Bad equals/hashCode keys duplicate keys leak in, lookups fail keep equals and hashCode consistent (Lecture 22)
    Writing through an unmodifiable view UnsupportedOperationException copy the collection before modifying it 
    // Demo3.java - the classic fail-fast trap (see Lecture 30)
import java.util.*;

public class Demo3 {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("a", "b", "c"));
        for (String s : list) {
            if (s.equals("b")) list.remove(s);   // throws ConcurrentModificationException
        }
    }
}

    11. Myth vs Reality

    Myth Reality
    "Map extends Collection" No. Map is a separate root; only its views (keySet, values, entrySet) are Collections.
    "HashSet preserves insertion order" It does not; iteration order is unspecified. LinkedHashSet preserves insertion order.
    "Collections is an implementation you can instantiate" No. It is a final utility class of static methods with a private constructor.
    "TreeSet and TreeMap are O(1) like hash structures" No. They are O(log n); sorted order is the price.
    "Vector and ArrayList differ only in name" Vector synchronizes every method (legacy, slower); ArrayList does not.
    "LinkedList is fast for every operation" No. It is fast at the ends; index access and search are O(n).

    12. Common Trap Questions

    Trap 1 - Map versus Collection: "Does Map implement Collection?" No. Map is its own root interface. Only keySet(), values() and entrySet() are Collection-typed views.

    Trap 2 - The naming trap: "What is the difference between Collection and Collections?" Collection is the root interface for groups of elements; Collections is a final utility class of static algorithms and wrappers. They share only their package.

    Trap 3 - Add to a Set: "What does set.add(existing) return?" false, and the set is unchanged. Duplicate rejection is decided by equals (and hashCode for hash-based sets).

    Trap 4 - Iteration order: "In what order does a HashMap iterate?" Unspecified. Use LinkedHashMap for insertion order or TreeMap for sorted order; never rely on the plain hash order.

    Trap 5 - Fail-fast: "Why does removing an element inside a for-each throw?" The iterator detects a structural modification it did not perform and throws ConcurrentModificationException; use Iterator.remove or removeIf (Lecture 30).

    Trap 6 - Null handling: "Can a HashMap hold a null key?" Yes, exactly one null key and many null values. Hashtable and ConcurrentHashMap reject null keys, and TreeMap behaviour depends on the comparator.

    Trap 7 - Array vs ArrayList: "Is an ArrayList just an array?" It is backed by one, but it resizes automatically; size() is the number of elements and the internal capacity is larger and hidden.

    Trap 8 - Unmodifiable is not immutable: "Does Collections.unmodifiableList prevent all change?" No. It blocks writes through the returned view; the backing list remains mutable and its changes show through the view.

    13. Points to Remember

    1. The Collections Framework is interfaces plus implementations plus algorithms, all under java.util.
    2. Iterable ⊃ Collection; Collection branches into List, Set (SortedSet -> NavigableSet) and Queue (Deque).
    3. Map is not a Collection - it is a separate root with SortedMap -> NavigableMap.
    4. The Map views keySet(), values() and entrySet() are Collections even though Map is not.
    5. Program to interfaces and choose implementations by ordering, duplicates, key access, sorting and thread safety.
    6. Underlying structures are the dynamic array, the doubly linked list, the hash table, the red-black tree and the binary heap.
    7. Complexity anchors: hash O(1) average, tree O(log n), array index O(1) but middle insert/remove O(n), heap add/poll O(log n).
    8. Collection is an interface; Collections is a utility class (sort, reverse, unmodifiableList, emptyList, synchronizedList).
    9. Legacy Vector, Hashtable and Stack are synchronized and largely superseded; prefer modern classes and java.util.concurrent (Lecture 33/56).
    10. Set and Map correctness depends on consistent equals/hashCode (Lecture 22), and mutation during iteration throws ConcurrentModificationException (Lecture 30).

    14. Likely Interview Questions

    Question Crisp Answer
    What is the Java Collections Framework? A unified architecture of interfaces, implementations and algorithms in java.util for storing and manipulating groups of objects.
    Is Map part of Collection? No. Map is a separate root; only its keySet/values/entrySet views are Collections.
    Collection versus Collections? Collection is the root interface; Collections is a final utility class of static algorithms and wrappers.
    When to use List versus Set? List when order and duplicates matter; Set when uniqueness is required.
    ArrayList versus LinkedList? Dynamic array with O(1) index access versus doubly linked list with O(1) end operations but O(n) access.
    HashSet versus TreeSet? HashSet is O(1) average and unordered; TreeSet is O(log n) and sorted.
    HashMap versus Hashtable versus ConcurrentHashMap? HashMap is unsynchronized with one null key; Hashtable is legacy-synchronized with no nulls; ConcurrentHashMap is modern and thread-safe.
    How does HashMap work internally? An array of buckets indexed by hashCode; collisions chain in a linked list and treeify into a red-black tree past a threshold (Java 8); it resizes on load factor.
    What is the iteration order of HashMap? Unspecified; LinkedHashMap gives insertion order and TreeMap gives sorted order.
    Why prefer ArrayDeque over Stack? Stack extends Vector and is synchronized/legacy; ArrayDeque is a modern Deque with a cleaner LIFO API.
    What happens when you mutate a collection during iteration? Fail-fast iterators throw ConcurrentModificationException (Lecture 30).
    What does Collections.unmodifiableList do? Returns a read-only view that throws UnsupportedOperationException on writes; the backing list stays mutable.

    15. Final Summary

    Collection hierarchy : Iterable -> Collection -> { List, Set -> SortedSet -> NavigableSet, Queue -> Deque }
Separate root        : Map -> SortedMap -> NavigableMap   (Map is NOT a Collection)
Under the hood       : dynamic array · doubly linked list · hash table · red-black tree · binary heap
Complexity anchors   : hash O(1) avg · tree O(log n) · heap add/poll O(log n) · array index O(1)
Utility class        : Collections.sort / reverse / shuffle / unmodifiableList / emptyList / synchronizedList
    • Interfaces -> List, Set, Queue/Deque, Map; Map is a separate root, never a Collection.
    • Implementations -> chosen by ordering, duplicates, key access, sorting and thread safety from the decision guide.
    • Big-O -> hash structures average O(1) but unordered; tree structures O(log n) and sorted; arrays O(1) index but O(n) middle edits; heap O(log n) add/poll.
    • Collections -> the utility class of algorithms and wrappers, distinct from the Collection interface.
    • Legacy -> Vector, Hashtable and Stack are synchronized holdovers; prefer modern classes and java.util.concurrent (Lecture 33/56).
    • Correctness -> consistent equals/hashCode for Set/Map keys (Lecture 22); no mutation during iteration (Lecture 30).

    Golden rule Choose the interface by the guarantee you need and the implementation by the cost you can pay - and remember that Map stands apart from Collection.

    One-line takeaway: the Collections Framework is interfaces, implementations and algorithms under java.util, with Iterable ⊃ Collection branching into List, Set and Queue while Map remains a separate root chosen for key -> value lookup.
