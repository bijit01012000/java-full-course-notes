    Part 1 · Java Basics · Lecture 05

    Java Type Conversions & Type Promotions Explained — Casting in Java

    15 sections · interview-oriented · both themes

    Scope evidence: lecture title "Java Type Conversions & Type Promotions Explained | Casting in Java" (playlist map, verified). This lecture's repo folder contains two code files: Demo.java and Demo2.java.

    Type conversion is the set of rules the compiler uses to turn one primitive type into another, and it decides whether a line compiles or fails before the program ever runs. This lecture covers the two directions (widening and narrowing), what a cast really does to the bits, the promotion rules that fire inside every arithmetic expression, and the compound-assignment exception interviewers love. Primitive sizes and ranges are assumed from Lecture 3; the bit layouts behind them come from Lecture 4.

    1. What Is Type Conversion?

    Java is statically and strongly typed: every value has one declared type, and the compiler checks every assignment and expression against it. When the types do not match, Java either converts automatically or refuses to compile until a cast is written.

    1. Implicit conversion (widening) — the compiler converts a smaller type to a larger one silently, because no information can be lost.
    2. Explicit conversion (narrowing, a "cast") — the developer writes (type) in front of the expression to force a larger type into a smaller one and accepts the possible loss.

    A cast never changes the operand itself. It produces a new value converted to the target type; the original variable keeps its type and value.

    Important Conversion and casting are the same mechanism at two levels of control. Conversion is what the compiler does; a cast is the developer overriding the compiler's default refusal.

    2. The Two Directions: Widening vs Narrowing

    Every primitive conversion goes one of two ways along the size and range ladder:

    Aspect Widening (implicit) Narrowing (explicit cast)
    Language syntax No cast written — long l = i; Cast required — byte b = (byte) i;
    Direction Smaller type → larger type Larger type → smaller type
    Data loss Guaranteed none for integers Possible: truncation or wraparound
    When it happens Compile time, automatically Compile-time check, run-time conversion
    Compiler stance Silent approval Forced acceptance — you signed the risk
    Example double d = 42; int i = (int) 19.9; // 19

    The golden direction rule: a type fits into any type that appears to its right in the chain of Section 3; anything to the left needs a cast.

    3. Widening (Implicit) Conversion

    Widening follows one fixed chain. Each arrow is a step the compiler performs without being asked:

    byte → short → int → long → float → double
char → int → long → float → double
    Step From To Size change Loss possible
    1 byte (8) short (16) sign-extended No
    2 short (16) int (32) sign-extended No
    3 int (32) long (64) sign-extended No
    4 long (64) float (32) range adjusted Yes — precision (Section 8)
    5 float (32) double (32→64) precision extended No
    — char (16) int (32) zero-extended No

    char joins the chain at int, not at short: char is unsigned, so even widening it to short would be unsafe and requires a cast. Memory aid — the ladder: "Be Swift, In Life, Fly Down." (byte, short, int, long, float, double); the char climbs straight onto the int rung.

    // Demo.java — widening: no cast, no effort, no loss
public class Demo {
    public static void main(String[] args) {
        byte b = 42;
        short s = b;      // byte → short: automatic
        int i = s;        // short → int: automatic
        long l = i;       // int → long: automatic
        double d = l;     // long → double: fits exactly (53-bit mantissa)
        char c = 'A';
        int code = c;     // char → int: 65
        System.out.println(d + " / " + code);
    }
}

    Method call boundaries widen the same way: a byte argument lands in an int parameter with no cast, because the compiler can prove nothing is lost.

    4. Narrowing (Explicit) Casting

    Narrowing needs the cast operator (type) in front of the expression:

    // Demo2.java — narrowing: manual, and lossy by permission
public class Demo2 {
    public static void main(String[] args) {
        int i = 130;
        byte b = (byte) i;   // keeps low 8 bits → -126
        double d = 19.9;
        int t = (int) d;     // drops the fraction → 19
        long big = 123456789123456789L;
        float f = big;       // legal widening — but see Section 8
        System.out.println(b + " " + t + " " + (long) f);
    }
}

    The compiler still type-checks the cast itself: (byte) on a boolean or on an Object that is not a number will not compile. Narrowing among numeric types is always allowed syntactically; the risk runs at run time.

    5. What Narrowing Actually Does

    Three behaviors account for nearly every exam and interview question:

    1. Integer truncation (modulo wraparound). Casting int to byte keeps only the lowest 8 bits. Bits 8-31 are discarded and the sign comes from bit 7: 130 is 1000 0010 in 8 bits, so the result is -126.
    2. Floating-point truncation toward zero. Casting a double to int drops the fraction — it does not round, and it does not floor negative numbers: (int) 19.9 is 19, and (int) -19.9 is -19, not -20. Edge cases: (int) Double.NaN is 0; values beyond int range clamp to Integer.MAX_VALUE/MIN_VALUE.
    3. Range wraparound for char. (char) i keeps the lowest 16 bits modulo 65536, so the result is never negative — but converting back with (short) reintroduces the sign.
    Source value Cast Stored bits Result
    int 130 (byte) 1000 0010 -126
    int 128 (byte) 1000 0000 -128
    int -1 (char) 1111 1111 1111 1111 \uFFFF (65535)
    double 19.9 (int) fraction dropped 19
    double -19.9 (int) truncates toward zero -19

    Interviewer's perspective "Is (int) a floor or a round of the double?" Neither. It truncates toward zero, so -19.9 becomes -19. Candidates who answer "floor" reveal they never tested a negative number.

    6. Numeric Type Promotion in Expressions

    Conversion does not wait for assignment. The moment an operator is applied, the JVM promotes the operands to at least int:

    Expression Operands before Type after promotion
    byte + byte 8 + 8 bit int
    short * short 16 + 16 bit int
    char + char 16 + 16 bit int
    int + long 32 + 64 bit long
    long + float 64 + 32 bit float
    any + double — double

    The rule in one sentence: byte, short and char are promoted to int in every arithmetic expression; if any operand is already long, float or double, the other operand rises to that type, the widest one winning. This is why the classic line fails:

    byte b1 = 10, b2 = 20;
byte b3 = b1 + b2;          // compile error: int cannot be converted to byte
byte b4 = (byte) (b1 + b2); // legal: cast the promoted int result back
b1 = b1 + b2;               // same compile error on assignment

    The JVM has no 8-bit or 16-bit arithmetic instructions — only int and wider. Promoting small types to int is the compiler matching the bytecode reality, not a style choice.

    Important The unary plus +b also promotes: int x = +b; is legal while byte y = +b; is not. Promotion is triggered by operators, not only by mixing types.

    7. char and int: The Special Case

    char is a 16-bit unsigned integer that happens to print as a symbol, so arithmetic and casting behave unusually:

    char c = 'A';
char d = 'A' + 1;   // 'B' — a compile-time constant, 66 fits in char
c++;                // works: compound update ≡ (char)(c + 1)
c = c + 1;          // compile error: c is promoted to int in c + 1
int code = c - 'A'; // arithmetic on chars runs as int

    Three facts to state crisply:

    1. 'A' + 1 compiles because both operands are constants; the compiler evaluates 66 at compile time and accepts it where a char is expected. With a variable on the left, no such narrowing of constants happens.
    2. c++ compiles because ++ and all compound operators insert the hidden cast of Section 9.
    3. (char) never produces a negative value, so casting char back produces surprise-free unsigned values — but converting through int and casting onward to short or byte can flip the sign that char never had.

    8. Overflow vs Precision Loss: the long → float Trap

    "Loss" is two different phenomena, and interviews blur them on purpose:

    • Overflow — the value leaves the target type's range (integer wraparound, Section 5).
    • Precision loss — the value stays in range but can no longer be stored exactly.

    long is 64 bits and float is 32, yet long → float is a widening conversion and compiles with no cast. The loss hides in the mantissa: a float carries only 24 significant bits, far fewer than a long's 64. So float can hold a long's magnitude but not its exact value.

    long l = 123456789123456789L; // exact, 64-bit
float f = l;                  // widening — compiles silently
System.out.println((long) f); // 123456791348711424 — not the original

    The same applies to int → float once the value exceeds 2^24-1 (16,777,215): trailing bits are rounded away. int → double is exact, because a double has a 53-bit mantissa — more than an int ever needs.

    Interviewer's perspective "Widening can lose information — true or false?" True, and the proof is long → float. The conversion is widening by the JLS definition (it accepts every long value), but the stored value may differ. Say both halves: legal, yet lossy.

    Important long → double is exact for all practical program values; long → float is not. One extra letter changes the answer.

    9. Compound Assignment: The Hidden Cast

    The single most quoted conversion question in Java interviews:

    byte b = 10;
b = b + 1;   // compile error — b + b is int arithmetic (Section 6)
b += 1;      // compiles — the += operator casts for you

    The language specification defines E1 op= E2 as equivalent, when it compiles, to E1 = (TypeOfE1)(E1 op E2). The compound operator performs the narrowing cast at the end by itself. It is a documentable guarantee, not a compiler accident:

    1. b += 1 ≡ b = (byte)(b + 1).
    2. i *= 1.5 with int i ≡ i = (int)(i * 1.5) — it compiles and truncates.
    3. The same hidden cast applies to char (c++ in Section 7 is this rule in disguise).

    The trade: convenience for silence. The compound cast never warns that precision or range is being lost, exactly the warning the compiler gave you on the long form.

    10. Conversion at Method and String Boundaries

    Conversion is not only an assignment-list topic:

    1. Method calls widen automatically at the parameter boundary: passing a byte or char into an int parameter works without a cast; the reverse needs one at the call site.
    2. String to number is parsing, not casting: Integer.parseInt("42") returns an int, Double.parseDouble("3.14") returns a double. A malformed string throws NumberFormatException at run time. The wrapper classes behind these methods are covered in Lecture 18.
    3. Casting a String to a number does not parse anything — (int) "42" is a compile error, because a cast changes types, not text.

    11. Myth vs Reality

    Myth Reality
    "A cast changes the value stored in the variable" A cast produces a converted copy; the source variable and its bits are untouched.
    "Widening never loses data" long → float and int → float are widening yet lose precision (Section 8).
    "byte + byte gives a byte" Both operands promote to int; the result is int and needs a cast for byte.
    "Casting a double rounds it" (int) truncates toward zero; (int) -19.9 is -19.
    "200 fits in a byte after casting" (byte) 200 wraps modulo 256 to -56; range is fixed at [-128, 127].

    12. Common Trap Questions

    Trap 1 — The wraparound: "What is (byte) 130?" The low 8 bits survive: 1000 0010 → -126. The rule is modulo 256 mapped onto [-128, 127], not saturation to 127.

    Trap 2 — The silent widening: "long is bigger than float, so long → float is safe?" Backwards. It is widening by definition, but float has a 24-bit mantissa, so exact long values are lost. Widening is about range, not precision.

    Trap 3 — The compound operator: "If b = b + 1 fails for byte, does b += 1 fail too?" No. += performs the hidden cast and compiles. The pair is a stock interview question.

    Trap 4 — The signed char: "char is signed like byte, right?" No. char is 16-bit, unsigned, [0, 65535]. Casting int -1 to char yields \uFFFF; converting that back via (short) gives -1 again.

    Trap 5 — The boolean bridge: "Cast a boolean to int with (int)." Impossible. boolean sits outside the numeric chain and cannot be cast to or from anything numeric.

    Trap 6 — The promotion scope: "Promotion only applies to byte." short and char promote to int as well, and unary + triggers it too (+b is already an int).

    13. Points to Remember

    1. Implicit conversion is widening (no cast); explicit casting is narrowing ((type) required).
    2. The widening chains are fixed: byte → short → int → long → float → double and char → int → long → float → double.
    3. char joins at int because it is unsigned 16-bit; widening to short needs a cast.
    4. Narrowing truncates: integers lose high-order bits (int 130 → byte -126); doubles lose the fraction toward zero.
    5. In arithmetic, byte, short and char promote to int; long/float/double pull the whole expression up to the widest type.
    6. b = b + 1 fails on a byte; b += 1 passes because compound assignment casts implicitly.
    7. Widening can still lose precision: long → float and large int → float are lossy; int → double is exact.
    8. Overflow and precision loss are different failures: wraparound crosses a range boundary; precision loss keeps the range and drops the exactness.
    9. boolean can never be cast to or from a numeric type — wrappers aside, there is no numeric route at all (Lecture 18).
    10. Strings become numbers by parsing (Integer.parseInt, Double.parseDouble), never by casting.

    14. Likely Interview Questions

    Question Crisp Answer
    What is type conversion in Java? Automatic or explicit transformation of a value from one primitive type to another under fixed compiler rules.
    Widening vs narrowing? Widening goes up the chain automatically; narrowing goes down and requires a cast because loss is possible.
    State the widening order. byte → short → int → long → float → double; char widens to int and above.
    When must you cast explicitly? Whenever the source type does not fit the target by the widening chain — mostly larger into smaller.
    What is (byte) 130? -126: the low 8 bits 1000 0010 are reinterpreted as a signed byte.
    Why does byte b = 10; b = b + 1; fail? b promotes to int, the sum is int, and int → byte needs a cast.
    How is b += 1 different? Compound assignment is specified as b = (byte)(b + 1); it casts internally and compiles.
    Is (int) 19.9 a rounding? No — truncation toward zero. For negatives, (int) -19.9 is -19.
    Can widening lose data? Yes, by precision: long → float and int beyond 16,777,215 → float are inexact.
    Is char signed? No: 16-bit unsigned, [0, 65535]; arithmetic runs after promotion to int.
    Can boolean be cast to a number? Never — boolean is outside the numeric conversion chain entirely.
    How do you convert "42" to an int? Integer.parseInt("42") — parsing, not casting; bad input throws NumberFormatException.

    15. Final Summary

    byte → short → int → long → float → double      (widening: automatic, mostly lossless)
                     ↑                                     ↓
          promotion in expressions                  (type) forces the way back
     (byte/short/char → int)                        bits are kept or cut, never rounded
    • Widening → compiler's job, silent, exact for integers, exact for long → double.
    • Narrowing → developer's job, (type) cast, truncation and wraparound are your accepted risk.
    • Promotion → every operator computes in int at minimum; the widest operand type wins.
    • Compound assignment (+=, ++) → the one place Java hides a cast for you.
    • Precision ≠ range → long → float widens and still loses exactness.
    • boolean → outside the chain; String → number goes through parsing, not casting.

    Golden rule The compiler widens without asking and refuses to narrow without your signature — and once the cast is written, the lost bits are yours alone.

    One-line takeaway: widening is silent and usually safe, narrowing is signed-for and lossy, and every arithmetic expression quietly computes as int — three rules that answer nearly every conversion question an interviewer can ask.
