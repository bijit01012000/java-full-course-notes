    Part 6 · Optional, Exceptions & Memory · Lecture 48

    Java Thread Creation & Lifecycle Explained from Scratch

    16 sections · interview-oriented · both themes

    Scope evidence: "Java Thread Creation & Lifecycle Explained from Scratch" plus the lecture's own notes terms (extend Thread, implement Runnable, start vs run, lifecycle), playlist map, verified. Repo evidence: 6 Demo files.

    Lecture 47 built the conceptual model: a thread is the smallest independently executable sequence of instructions, every process starts with one main thread, and threads share the heap while owning their own stack and program counter. This lecture turns that model into code. It covers the Thread class itself, the difference between a Thread object and the thread of execution it controls, the two foundational creation techniques, the start() versus run() trap that catches almost every beginner, and the six states a Java thread passes through. The governing idea is that a thread is not the work, it is the mechanism that executes work, and the work is carried by a Runnable task.

    1. The Thread Class — an Object That Controls a Thread of Execution

    Java is object-oriented, so even concurrency is expressed through classes and objects. The unit of concurrency is the class Thread, declared as:

    public class Thread extends Object implements Runnable

    Two ideas must be kept separate, because confusing them causes most thread bugs:

    1. A Thread object is a Java object used to configure and control a thread.
    2. A thread of execution is an independent sequence of instructions executed by the JVM.

    Creating a Thread object does not start a thread of execution. The thread starts only when start() is called.

    Idea What it is Lifetime
    Thread object A Java object created with new, carrying name, priority and state Lives on the heap while referenced
    Thread of execution An independent instruction stream scheduled by the JVM and OS Exists only between start() and termination

    Each running thread owns its program counter, its Java stack (stack frames, local variables, current execution position). Threads in the same process normally share heap objects, static variables, class metadata and open process resources. This split — separate execution stacks plus a shared heap — is what makes threads useful and, at the same time, what creates concurrency problems (Lectures 45, 47).

    Memory aid The Thread object is the remote control; the thread of execution is the program being watched. Buying the remote (the new) does not turn on the television (start() does).

    2. Two Foundational Ways to Create a Thread

    The Thread API offers two foundational ways to create a platform thread.

    1. Extend Thread — create a subclass and override run().
    2. Implement Runnable — create a task and hand it to a Thread.
    // Demo.java — creation way 1: extend Thread and override run()
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Thread is running");
    }
}

public class Demo {
    public static void main(String[] args) {
        MyThread t1 = new MyThread();   // only a Java object; state = NEW
        t1.start();                      // schedules the new thread of execution
    }
}

    // Demo2.java — creation way 2: implement Runnable, hand the task to a Thread
class MyRunnable implements Runnable {
    @Override
    public void run() {
        System.out.println("Thread is running using Runnable");
    }
}

public class Demo2 {
    public static void main(String[] args) {
        MyRunnable task = new MyRunnable();     // represents the task
        Thread t1 = new Thread(task, "Worker-1"); // represents the execution mechanism
        t1.start();
    }
}

    The internal flow of the Runnable form matters: new Thread(task) stores the task; t1.start() begins a new thread; the default Thread.run() invokes task.run().

    Thread t1 = new Thread(task) → Thread stores the Runnable task
   → t1.start() → new thread begins execution → Thread.run() → task.run()

    Important The reason Thread has a run() method at all is that Thread itself implements Runnable. When you extend Thread, your subclass overrides that inherited run(). When you pass a Runnable, the thread's default run() delegates to the supplied task.

    3. Runnable Is a Functional Interface — the Lambda Form (Lecture 37)

    Runnable declares exactly one abstract method:

    @FunctionalInterface
public interface Runnable {
    void run();
}

    Because it is a functional interface (Lecture 37), a lambda can supply the single abstract method, and the task class disappears entirely.

    // Demo3.java — the Runnable lambda is the modern concise form (Lecture 37)
public class Demo3 {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println("Thread is running");
        Thread worker = new Thread(task, "Worker-1");
        worker.start();

        // The shortest form installs the lambda inline:
        new Thread(() -> System.out.println("Hello"), "Worker-2").start();
    }
}

    The lambda form works because the compiler target-types the lambda against Runnable. A block-bodied lambda with several statements is equally valid when the task needs more than one line.

    Interviewer's perspective "Why can a lambda replace a Runnable class?" Because Runnable is a SAM type — one abstract method — which is precisely the target a lambda requires. Method references and function composition were covered in Lecture 38.

    4. Extending Thread vs Implementing Runnable

    The task-oriented design is generally preferred. Runnable answers what work should be performed; Thread answers which thread executes that work.

    Aspect Extending Thread Implementing Runnable
    Main role Combines task and thread lifecycle Defines only the task
    Inheritance Consumes the class's single class inheritance Class can still extend another class
    Reusability Task is tied to the Thread object Same task can be submitted to many threads
    Separation of concerns Lower Better: task is separated from execution
    Works with executors Not the natural design Designed for task-based execution
    Lambda support Not applicable Direct, since Runnable is functional
    Preferred for normal code Less common Usually preferred

    The two strongest arguments for Runnable:

    1. Preserves inheritance. A class can extend only one class. class X extends Thread ends the ability to extend anything else; class X extends Base implements Runnable keeps it. This is not multiple class inheritance, only the freedom to also extend a class.
    2. Separation, reuse and executor fit. One task object can be run by Worker-1 and Worker-2; the same task can later be submitted to a thread pool without rewriting it. If the shared task holds mutable fields, those fields may need synchronization.

    Golden rule If a class only needs to describe work, have it implement Runnable. Extend Thread only when the class genuinely is a thread and must alter thread behaviour.

    5. start() vs run() — The Classic Trap

    start() creates a new thread of execution which then calls run(). Calling run() directly executes the method on the current thread, exactly like any other method call, and produces no concurrency at all.

    // Demo4.java — run() runs on the calling thread; start() spawns a new thread
public class Demo4 {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println(
                "Executed by: " + Thread.currentThread().getName());

        Thread first  = new Thread(task, "Worker-run");
        Thread second = new Thread(task, "Worker-start");

        first.run();      // normal call on main  -> "Executed by: main"
        second.start();   // new thread           -> "Executed by: Worker-start"
    }
}

    The thread name in the output is the proof: run() reports main, while start() reports Worker-start.

    Aspect run() start()
    Kind of call Ordinary method call Starts independent thread execution
    Thread it runs on The calling thread A newly created thread
    New execution stack No Yes; the new thread gets its own stack and PC
    Concurrent with caller No, by itself Yes, becomes eligible for scheduling
    How many times Can be invoked repeatedly as a method A Thread object can be started only once
    Internal effect Executes the task body inline Schedules the thread, which then invokes run()

    Important start() does not run run() on the current thread. It asks the JVM to create a new thread of execution; that new thread eventually calls run(). The current thread continues immediately afterward.

    6. The Thread Lifecycle — Thread.State

    A Java thread passes through a defined set of states, modelled by the enum Thread.State. There are six states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.

                              start()                 run() completes
   [ NEW ] ───────────────────────────► [ RUNNABLE ] ──────────────► [ TERMINATED ]
                                            │    ▲                    (normal end
                                            │    │                     or exception)
              waiting for a monitor ────────┤    │──── monitor acquired
              indefinite wait ──────────────┤    │──── notified / target ends
              timed wait ───────────────────┘    └──── timeout expires
                    │
                    ├──► [ BLOCKED ]        (waiting for a monitor lock)
                    ├──► [ WAITING ]        (indefinite wait)
                    └──► [ TIMED_WAITING ]  (wait with a timeout)

    This diagram is simplified: a thread may move between RUNNABLE, BLOCKED, WAITING and TIMED_WAITING many times before it terminates.

    State Meaning Entered by Returns to RUNNABLE when
    NEW Object created, start() not yet called new Thread(...) start() is called
    RUNNABLE Ready to receive CPU time, or executing in the JVM start() n/a (it is the running state)
    BLOCKED Waiting to acquire an intrinsic monitor Entering occupied synchronized code The monitor is acquired
    WAITING Waiting indefinitely for another thread's action wait(), join(), LockSupport.park() Notified, target terminates, unparked
    TIMED_WAITING Waiting for an action with a time limit sleep(), timed wait()/join(), parkNanos() Timeout, event, or interruption
    TERMINATED run() finished normally or abruptly End of run() n/a (terminal state)

    A few rules are worth stating precisely:

    • NEW means the Thread object exists but independent execution has not begun. Calling run() directly does not move the thread through its lifecycle, because start() was never called.
    • RUNNABLE combines two situations the JVM does not distinguish publicly: ready to receive processor time and currently executing. Java exposes no separate RUNNING state.
    • BLOCKED is specifically a monitor-lock acquisition problem — waiting to enter or re-enter synchronized code.
    • WAITING does not always mean waiting for notify(); join() wakes on target termination, and park() wakes on unpark.
    • TERMINATED is reached when run() completes normally or exits with an uncaught exception.
    // Demo5.java — observing the lifecycle through getState()
public class Demo5 {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> System.out.println("Running..."));

        System.out.println("Before start: " + worker.getState()); // NEW
        worker.start();
        System.out.println("After start:  " + worker.getState()); // RUNNABLE (timing-sensitive)
        worker.join();
        System.out.println("After join:   " + worker.getState()); // TERMINATED
    }
}

    Important getState() returns a momentary snapshot that can change the instant after it is read. If a task completes very quickly, the state printed immediately after start() may already read TERMINATED.

    7. Thread Identity — Names, IDs and currentThread()

    Every thread carries identity properties that help inspection and debugging: name, thread ID, state, priority, daemon status and interrupted status. The static method Thread.currentThread() returns the Thread object for the currently executing thread; inside main() it is normally named main.

    Thread current = Thread.currentThread();
System.out.println(current.getName());   // "main"
    • Name — read with getName(), changed with setName(). Passing the name to the constructor is usually cleaner: new Thread(task, "Worker-1").
    • ID — use Thread.currentThread().threadId() in modern Java. The older getId() has been deprecated since Java 19.
    • A meaningful name (payment-worker-2) is more useful in logs and thread dumps than an opaque Thread-8.

    Memory aid getName() is a non-static method, so it needs an object. That is exactly why Thread.currentThread() exists: it supplies the object for the thread you are already running on.

    8. Priorities and Daemon Threads

    Two configuration knobs are commonly asked about:

    • Priority — setPriority(int) accepts 1 (lowest) to 10 (highest); the default is 5. Priority is only a hint to the scheduler, not a guarantee. The operating system may ignore it, so code must never depend on priority for correctness or ordering.
    • Daemon status — setDaemon(true) marks a thread as a background thread. The JVM exits when only daemon threads remain; a live non-daemon thread keeps the JVM alive. setDaemon (and setPriority) must be called before start().

    Interviewer's perspective "Why does my program not exit?" A non-daemon worker thread is usually still running. Either let it finish, interrupt it, or create it as a daemon if its work should not keep the JVM alive.

    9. Start Once, Then Coordinate

    A Thread object represents exactly one lifecycle and can be started only once. A second start() — whether the thread is running, finished, or terminated by an exception — throws IllegalThreadStateException.

    Thread worker = new Thread(() -> System.out.println("Running"));
worker.start();
worker.start();   // java.lang.IllegalThreadStateException

    To run the same work again, reuse the task and create a fresh Thread object:

    Runnable task = () -> System.out.println("Running");
Thread first = new Thread(task);
first.start();
first.join();
Thread second = new Thread(task);   // new Thread object for a new lifecycle
second.start();

    Coordination methods are introduced here and detailed in Lecture 49:

    • join() — the calling thread waits until the target thread terminates.
    • sleep(ms) — pauses the current thread for a bounded interval; the thread enters TIMED_WAITING and does not release monitors.
    • interrupt() — requests that a blocked or waiting thread stop waiting; the target typically sees an InterruptedException.

    Execution order is not guaranteed. t1.start(); t2.start(); makes t1 eligible for scheduling first, but does not promise that t1 runs or prints before t2. The OS scheduler, JVM decisions, core count, system load and lock contention all influence the observed order. Multi-threaded execution is non-deterministic, and application code should never depend on accidental ordering.

    Golden rule Treat the order of output from two threads as unknowable. When an order is genuinely required, enforce it with coordination such as join(), locks or latches — never with the sequence of start() calls.

    10. Higher-Level Mechanisms (Forward References)

    This lecture deliberately teaches Thread and Runnable first because the higher-level APIs build on the same separation of task from execution.

    • Executor services and thread pools, plus Callable and Future, replace hand-created threads for most production work (Lecture 56). ExecutorService runs submitted tasks on pooled threads; the task does not need to know which thread executes it.
    • CompletableFuture, Fork/Join, ThreadLocal, virtual threads and structured concurrency are covered in Lecture 57.

    In production, tasks are generally submitted to executors rather than creating a new platform thread for every task. Understanding Thread and Runnable first is still essential, because executors schedule Runnable and Callable tasks on threads that obey the same lifecycle.

    11. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Calling run() instead of start() No new thread; the task runs on the current (often main) thread Call start() to create a new thread of execution
    Starting the same Thread twice IllegalThreadStateException Create a new Thread object; reuse the Runnable task
    Assuming priority guarantees order The OS may ignore the hint; output order varies Use coordination (join(), locks) when order matters
    Non-daemon thread keeps the JVM alive The program never exits after main returns Let it finish, interrupt it, or mark it daemon before start()
    Extending Thread when Runnable suffices The class loses its single inheritance opportunity Implement Runnable
    Ignoring InterruptedException The interrupt request is swallowed Catch it, restore the flag with Thread.currentThread().interrupt(), or propagate
    Assuming run order is deterministic Same program can print different order each run Never rely on scheduling order
    Blocking the main thread The UI or caller stalls while it waits Hand long work to a worker thread; coordinate explicitly
    Reading getState() as permanent A snapshot can change immediately Use it for observation and debugging only
    Sharing one mutable Runnable Fields are read and written by several threads Synchronize access to shared mutable state

    12. Myth vs Reality

    Myth Reality
    "Creating a Thread object starts a thread." Only start() starts a new thread of execution; new Thread(...) leaves it in NEW.
    "Calling run() runs the code on a new thread." run() is an ordinary method call and executes on the calling thread.
    "A finished thread can be started again." A Thread object has one lifecycle; a second start() throws IllegalThreadStateException.
    "Higher priority always runs first." Priority (1-10) is a hint, not a guarantee; scheduling order is not controlled by code.
    "Extending Thread is the standard way to make a task." Implementing Runnable is generally preferred: it separates task from execution and preserves inheritance.

    13. Common Trap Questions

    Trap 1 — Direct call: "I called worker.run() instead of worker.start(). Did a new thread run?" No. run() executed on the calling thread, typically main. No new execution stack was created and no concurrency occurred.

    Trap 2 — Double start: "What happens on the second worker.start()?" IllegalThreadStateException is thrown. A Thread object can be started only once; create a new Thread object to run the task again.

    Trap 3 — The RUNNING state: "Which Thread.State value means the thread is running?" There is none. Java folds "ready" and "executing" into RUNNABLE; the separate RUNNING state is not exposed publicly.

    Trap 4 — BLOCKED versus WAITING: "Is a thread waiting for notify() BLOCKED?" No. Waiting to acquire a monitor is BLOCKED; waiting indefinitely for another thread's action (as with wait()) is WAITING.

    Trap 5 — Order: "t1.start() was called before t2.start(), so t1 prints first, right?" Not necessarily. The calls only affect eligibility for scheduling; the actual order is non-deterministic.

    Trap 6 — Runnable identity: "If I pass the same Runnable to two threads, do they each get their own copy?" No. Both threads share the same task object; any mutable fields in it are shared and may need synchronization.

    Trap 7 — Daemon timing: "Can I mark a running thread as a daemon?" No. setDaemon() must be called before start(); calling it later throws IllegalThreadStateException.

    14. Points to Remember

    1. Thread is declared public class Thread extends Object implements Runnable; a Thread object controls a thread of execution.
    2. Constructing a Thread object does not start anything; start() schedules the new thread, which then invokes run().
    3. The two foundational creation ways are extending Thread (override run()) and implementing Runnable (pass the task to a Thread).
    4. Runnable is a functional interface, so a lambda is the modern concise form (Lecture 37).
    5. start() creates a new execution stack and runs on a new thread; calling run() directly runs on the current thread.
    6. Thread.State has six values: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
    7. RUNNABLE combines ready-to-run and currently-executing; Java exposes no separate RUNNING state.
    8. BLOCKED is specifically monitor-lock acquisition; WAITING and TIMED_WAITING are coordination and delay states.
    9. A Thread object can be started only once; to run the work again, reuse the task with a new Thread object.
    10. Priority is only a hint, execution order is non-deterministic, and non-daemon threads keep the JVM alive.

    15. Likely Interview Questions

    Question Crisp Answer
    What is the declaration of the Thread class? public class Thread extends Object implements Runnable — Thread is itself a Runnable.
    Thread object vs thread of execution? The Thread object is the Java object that configures and controls execution; the thread of execution is the independent instruction stream the JVM schedules.
    How do you create a thread in Java? Extend Thread and override run(), or implement Runnable and pass the task to a Thread.
    Why is Runnable generally preferred? It separates the task from the execution mechanism, allows the class to extend another class, supports reuse across threads, and works naturally with executors.
    What does start() actually do? It asks the JVM to create a new thread of execution; that thread then calls run().
    What happens if you call run() directly? It executes like a normal method on the current thread; no new thread is created.
    Difference between start() and run()? start() starts a new thread and schedules run(); run() is an ordinary method call on the calling thread.
    What happens if you call start() twice? The second call throws IllegalThreadStateException; a Thread object can be started only once.
    Name the six thread states. NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
    BLOCKED vs WAITING vs TIMED_WAITING? BLOCKED waits for an intrinsic monitor; WAITING waits indefinitely for another thread's action; TIMED_WAITING waits with a timeout.
    Why is there no RUNNING state? Java groups "ready for CPU" and "executing on CPU" into RUNNABLE; the OS decides when the thread actually runs.
    Are priority and execution order guaranteed? No. Priority is a scheduler hint (1-10), and the order the OS runs threads is not deterministic.

    16. Final Summary

    new Thread(task)  →  NEW
      │  start()
      ▼
   RUNNABLE  ────────────►  run() executes
      │  ▲
      │  └── BLOCKED / WAITING / TIMED_WAITING ──┘ (lock / signal / timeout)
      ▼
   run() completes or throws  →  TERMINATED

create : extend Thread (combines task + lifecycle)
       | implement Runnable (task only, preferred)
       | Runnable lambda  () -> ...  (Lecture 37)

start() : new thread of execution  →  calls run()          (concurrency)
run()   : ordinary method call on the current thread        (no concurrency)
    • Thread class → extends Object implements Runnable; the object controls a thread of execution, constructing it does not start it.
    • Creation → extend Thread, implement Runnable, or use a Runnable lambda; the Runnable form is preferred.
    • start() vs run() → start() creates a new thread and invokes run(); run() called directly stays on the current thread.
    • Lifecycle → NEW to RUNNABLE, with possible BLOCKED, WAITING and TIMED_WAITING round-trips, ending in TERMINATED.
    • Rules → start a Thread object only once; priority is a hint; execution order is non-deterministic; non-daemon threads keep the JVM alive.
    • Forward → executors, pools, Callable/Future (Lecture 56); CompletableFuture, Fork/Join, ThreadLocal, virtual threads, structured concurrency (Lecture 57).

    Golden rule The Thread is the mechanism, the Runnable is the work. Create the object, call start() (never run()), and let the JVM and OS own the scheduling and lifecycle.

    One-line takeaway: a Thread object controls a thread of execution, start() is what actually creates that thread, run() is only the method it calls, and every Java thread moves from NEW through RUNNABLE to TERMINATED.
