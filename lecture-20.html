    Java I/O Deep Dive | InputStreams, System.in, Scanner vs BufferedReader

    16 sections · interview-oriented · both themes

    Scope evidence: lecture title "Java I/O Deep Dive | InputStreams, System.in, Scanner vs BufferedReader" (playlist map, verified). Repo evidence: 4 Demo files (Demo.java, Demo2.java, Demo3.java, Demo4.java). The cached lecture PDF is image-only and is ignored per project rules.

    Every useful program must move data in and out of itself, and Java models that movement with streams. This lecture separates the two axes of any stream — direction (input or output) and unit (byte or character) — then follows the byte roots InputStream/OutputStream and the character roots Reader/Writer, the standard System.in/System.out/System.err trio, and the two console-reading tools every beginner meets: Scanner and BufferedReader. It also dissects the most notorious console bug in the language, the nextInt()-then-nextLine() trap, and closes with resource management through try-with-resources. Exceptions raised by I/O (IOException) are checked and are handled in depth in Lecture 43.

    1. The I/O Model: Streams, Direction and Unit

    A stream is an ordered sequence of data that flows from a source to a destination, one unit at a time. Java describes every stream along exactly two independent axes:

    1. Direction — an input stream reads data into the program; an output stream writes data out of the program. A source or destination may be the console, a file, a socket, or memory.
    2. Unit — a byte stream moves 8-bit bytes (binary data); a character stream moves 16-bit char values (text, with an encoding behind it).

    The four abstract roots follow from those axes:

                     Input                Output
Byte      InputStream         OutputStream
Character Reader              Writer

    Because the axes are independent, four base classes cover the whole library, and every concrete class (FileInputStream, FileReader, BufferedReader, PrintStream, ...) specializes one of the four cells. Memory aid: Input/Output for direction, Stream bytes / Reader-Writer chars for unit.

    Important A stream is consumed as it is read. Unless the underlying class explicitly supports mark()/reset(), you cannot rewind and read the same data twice — a fact the Pitfall Catalogue (Section 11) returns to.

    2. Byte Streams and the InputStream Hierarchy

    Byte streams are the foundation: every character stream is ultimately built on top of byte streams. InputStream (input) and OutputStream (output) are abstract classes; concrete classes either connect to a data source directly or wrap another stream to add behaviour (buffering, parsing, filtering).

    // Demo.java — the byte level: System.in.read() returns one byte (0..255) or -1 at EOF
import java.io.IOException;

public class Demo {
    public static void main(String[] args) throws IOException {
        int b;
        while ((b = System.in.read()) != -1) {   // -1 marks end of input
            System.out.print((char) b);          // narrow byte cast to char
        }
    }
}

    InputStream's central method is int read(), which returns the next byte as an int in 0..255, or -1 at end of stream. The int return type exists so -1 can be distinguished from a legitimate byte value 0xFF; this is a classic design detail interviewers probe.

    The InputStream family is a tree, and knowing who wraps whom prevents the double-buffering mistake:

    Class Kind Extends / wraps Unit produced Purpose
    InputStream Abstract root Object byte Base contract for all byte input
    FileInputStream Concrete source InputStream byte Reads bytes from a file
    ByteArrayInputStream Concrete source InputStream byte Reads bytes held in a byte[]
    FilterInputStream Abstract decorator InputStream byte Base for streams that wrap another stream
    BufferedInputStream Decorator FilterInputStream byte Adds an in-memory buffer to cut syscalls
    DataInputStream Decorator FilterInputStream byte Reads typed primitives (readInt, readDouble)
    System.in Static field InputStream (typically BufferedInputStream) byte Reads from the process console/pipe

    Interviewer's perspective "Why does read() return int, not byte?" Because the stream must signal end-of-input. A byte has no spare value, but an int can carry 0..255 plus the sentinel -1. The same -1-at-EOF convention applies to Reader.read().

    3. Character Streams, the Encoding Bridge and InputStreamReader

    Reader and Writer are the abstract roots for text. Their unit is the 16-bit char, and the crucial difference from byte streams is encoding: bytes are just numbers, while characters have to be decoded and encoded against a charset (UTF-8, UTF-16, ISO-8859-1, ...). InputStreamReader (bytes in) and OutputStreamWriter (bytes out) are the bridges that translate between the two worlds.

    // Demo2.java — bridge bytes to chars with an explicit charset
import java.io.InputStreamReader;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

public class Demo2 {
    public static void main(String[] args) throws IOException {
        InputStreamReader reader =
                new InputStreamReader(System.in, StandardCharsets.UTF_8);
        int c;
        while ((c = reader.read()) != -1) {   // -1 at end of stream
            System.out.print((char) c);
        }
    }
}

    The bridge has two jobs:

    1. Chunking — it reads enough bytes to assemble whole characters, which matters for multi-byte encodings such as UTF-8 where a single letter can span several bytes.
    2. Translation — it maps byte values to char values through the chosen charset. Choosing the wrong charset is the source of the "mojibake" garbage text seen when a UTF-8 file is read as the platform default.

    Important Both bridge constructors have a no-charset overload that uses the default platform charset. That default differs between operating systems and JVM launches, so the same program can read the same file correctly on one machine and corrupt it on another. Pass the charset explicitly whenever text may cross a machine boundary.

    4. Byte vs Character Streams

    Aspect Byte streams Character streams
    Root classes InputStream / OutputStream Reader / Writer
    Unit 8-bit byte 16-bit char
    Encoding-aware No — raw bytes Yes — via a charset at the bridge
    Bridge classes — InputStreamReader / OutputStreamWriter
    Common classes FileInputStream, BufferedInputStream, DataInputStream FileReader, BufferedReader, PrintWriter
    End of stream read() returns -1 read() returns -1, readLine() returns null
    Best for Images, audio, archives, serialized bytes Text files, console, network text
    Typical console wrap System.in used directly BufferedReader(new InputStreamReader(System.in))

    Reading the table by rows: the two families are not competitors but layers — character streams sit on top of byte streams. When you see text, use characters and name the charset; when you see binary, stay at the byte level.

    5. System.in, System.out and System.err

    java.lang.System exposes three ready-made streams as static fields. They are ordinary streams (not magic), which is why they can be wrapped and redirected.

    Field Java type Direction Unit Notes
    System.in InputStream Input byte Process standard input; usually a BufferedInputStream with an unbuffered FileInputStream underneath
    System.out PrintStream Output byte Standard output; a PrintStream with print/println/printf
    System.err PrintStream Output byte Standard error; keep error text off the normal output channel

    Two details matter in practice:

    1. System.out is a PrintStream, and a PrintStream auto-flushes when a newline is written on a console — that is why println output appears immediately during debugging. Its auto-flush does not trigger on every print; flush() forces it.
    2. System.err is separate so that error messages can be separated from normal output and captured independently.

    Interviewer's perspective "Is System.out a character stream or a byte stream?" It is a PrintStream, hence a byte output stream, but it offers print(char)/println(String) conveniences that internally encode characters to bytes. Scanner and BufferedReader are reading tools, not printing tools; their output counterpart is PrintWriter, which is a Writer and therefore character-based.

    6. Scanner: Tokenizing and Parsing Console Input

    java.util.Scanner is the beginner-friendly reader. It does not hand you bytes or lines; it tokenizes the input using a delimiter (whitespace by default) and parses each token into a typed value. nextInt(), nextDouble(), nextBoolean() read and convert; next() returns the next whitespace-delimited token; nextLine() returns the rest of the current line.

    // Demo3.java — parse a number, then read the rest of the line (with the fix)
import java.util.Scanner;

public class Demo3 {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        System.out.print("Age: ");
        int age = sc.nextInt();      // consumes the digits only, not the newline
        sc.nextLine();               // FIX: consume the leftover newline
        System.out.print("Name: ");
        String name = sc.nextLine(); // now reads the real line
        System.out.println(name + " is " + age);
    }
}

    Without the sc.nextLine() on the fix line, name would be the empty string and the program would print " is 42". Section 7 explains exactly why.

    The parse methods are strict about types: calling nextInt() on non-numeric input throws InputMismatchException and the offending token is not consumed, so an unhandled mismatch can leave the scanner stuck on the same bad input forever.

    7. The nextInt() - then - nextLine() Trap

    This is the single most reported console bug in first-year Java. The input 42\nAlice\n is not two tokens to the scanner; it is characters, and each call consumes only the part it needs. In sequence, int age = sc.nextInt(); reads "42" and stops before the newline; String name = sc.nextLine(); reads the remainder of that same line, which is an empty string ""; and the following sc.nextLine() is what actually returns "Alice". The mechanism has four steps:

    1. nextInt() reads digits and stops at the first non-digit — the newline \n.
    2. That newline stays in the buffer.
    3. nextLine() returns everything up to and including the newline, and "everything" is nothing, so it returns an empty string "".
    4. The next nextLine() therefore returns "Alice", and every subsequent answer appears shifted by one question.

    Two canonical fixes exist:

    Fix Code Trade-off
    Consume the leftover newline int age = sc.nextInt(); sc.nextLine(); String name = sc.nextLine(); One extra line; the idiomatic answer
    Read the whole line and parse it int age = Integer.parseInt(sc.nextLine()); String name = sc.nextLine(); Consistent line-based reading; bad input throws NumberFormatException

    Interviewer's perspective "Why does nextLine() return an empty string after nextInt()?" Because nextInt() leaves the line terminator in the buffer and nextLine() reads up to the terminator — nothing but the terminator is left, so the line is empty. The fix is the extra nextLine(), or reading everything as a line and parsing it with Integer.parseInt.

    8. BufferedReader + InputStreamReader: Line-Oriented Reading

    BufferedReader reads text through an internal character buffer and offers readLine(), which returns a whole line without its terminator, or null at end of input. Because it works in characters, it is paired with the InputStreamReader bridge over raw System.in.

    // Demo4.java — line-oriented reading; readLine() returns null at EOF
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.io.IOException;

public class Demo4 {
    public static void main(String[] args) throws IOException {
        BufferedReader in =
                new BufferedReader(new InputStreamReader(System.in));
        String line;
        while ((line = in.readLine()) != null) {   // null means no more input
            if (line.isEmpty()) break;             // blank line ends the session
            System.out.println(">" + line);
        }
    }
}

    Why it is faster than Scanner for large input:

    1. Fewer system calls — BufferedReader pulls a block of characters at a time, so the program makes far fewer trips into the operating system.
    2. No per-token parsing — it returns raw String lines; Scanner runs delimiter matching and numeric conversion on every token, which dominates the cost on large inputs.
    3. Predictable buffering — a default 8K character buffer smooths out slow producers such as terminals and pipes.

    The cost of that speed is convenience: readLine() gives strings, so numeric parsing is your job (Integer.parseInt), and the null-at-EOF return must be checked before use.

    9. Scanner vs BufferedReader

    Aspect Scanner BufferedReader
    Package java.util java.io
    Parsing Built in: nextInt(), nextDouble(), next() None — returns String; parse yourself
    Reading model Delimiter-based tokenizing (whitespace by default) readLine() reads a whole line
    Buffering Small internal buffer, regex scanning per token Large character buffer (8K default)
    Speed Slower on large input Faster — fewer syscalls, no parsing
    End of input hasNext() false / NoSuchElementException readLine() returns null
    Bad input InputMismatchException, token not consumed NumberFormatException at parseInt
    Thread-safe Not thread-safe Not thread-safe
    Typical use Beginners, typed parsing, small console input Large files, competitive input, line processing
    Construction new Scanner(System.in) new BufferedReader(new InputStreamReader(System.in))

    Interviewer's perspective "When would you choose BufferedReader over Scanner?" When throughput matters: large files or competitive-programming input, where Scanner's regex tokenizing becomes the bottleneck. Choose Scanner when you want typed tokens with minimal code, and BufferedReader when you want speed or raw lines. A strong answer also notes that Scanner can be tuned with useDelimiter and useLocale.

    10. try-with-resources, Closing, flush and IOException

    Streams and readers hold operating-system resources, so they must be released. Since Java 7, try-with-resources does this automatically for any AutoCloseable (the Closeable streams and readers are all AutoCloseable):

    // try-with-resources closes the reader even if an exception is thrown
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class Demo5 {
    public static void main(String[] args) {
        try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {
            String line;
            while ((line = br.readLine()) != null) {
                System.out.println(line);
            }
        } catch (IOException e) {          // IOException is a checked exception
            System.out.println("I/O error: " + e.getMessage());
        }
    }
}

    Rules worth memorizing:

    1. Declare it in the parentheses and the resource is closed automatically at block exit, in reverse order of declaration, even on exception.
    2. Closing flushes. A Writer/PrintWriter may hold data in its buffer; close() flushes and releases, while flush() only pushes buffered data out and keeps the stream open.
    3. IOException is checked. The compiler forces you either to catch it or to declare it with throws (Lecture 43).
    4. Closing a wrapper closes the stream underneath. Closing a BufferedReader over System.in closes System.in, so later reads fail — do not close a console reader you still need.

    Important Only the outermost wrapper must be closed. Closing BufferedReader(new InputStreamReader(System.in)) closes the InputStreamReader, which closes System.in; you do not (and must not) close each layer separately.

    11. The Pitfall Catalogue

    Pitfall Example What happens Fix

    Closing System.in try (Scanner sc = new Scanner(System.in)) The scanner closes System.in; later reads throw Do not close a reader over System.in, or flush instead
    Scanner on huge input new Scanner(System.in) for 10^6 tokens Slow — regex parse per token Use BufferedReader and parse manually
    Forgetting to close No close()/try-with-resources File handles leak Use try-with-resources

    Reading twice Reading a consumed stream again Data already gone; empty result Reopen the source; use mark/reset only if supported

    12. Myth vs Reality

    Myth Reality
    "System.in gives me text" It is an InputStream: raw bytes. Text needs InputStreamReader/Scanner on top.
    "nextInt() then nextLine() works fine" The newline is left in the buffer; nextLine() returns empty. Consume it first.
    "Scanner is faster than BufferedReader" The reverse for large input: tokenizing with regex is expensive; buffered lines are cheap.
    "System.in and System.out are character streams" System.in is an InputStream (bytes); System.out/err are PrintStreams (bytes with text conveniences).
    "close() and flush() are the same" flush() pushes buffered output but keeps the stream open; close() flushes and releases the resource.
    "Scanner is thread-safe because it is convenient" Neither Scanner nor BufferedReader is thread-safe; synchronize externally if shared.

    13. Common Trap Questions

    Trap 1 — The leftover newline: "After sc.nextInt(), why does sc.nextLine() return an empty string?" nextInt() consumes the digits but stops before the line terminator, so the newline remains unread. nextLine() reads up to that terminator, leaving nothing but the terminator, hence "". Fix: consume the newline with an extra nextLine(), or read the line and use Integer.parseInt.

    Trap 2 — Closing System.in: "A program wraps System.in in a Scanner inside try-with-resources; the next read throws. Why?" Scanner.close() closes the underlying System.in. Once the process standard input is closed it cannot be reopened, so later reads fail. Do not close a reader over System.in, or read it only once.

    Trap 3 — Non-numeric input: "nextInt() is given "abc". What happens, and is the token consumed?" It throws InputMismatchException and does not consume the offending token. Guard with hasNextInt() before calling nextInt() if the input may be dirty.

    Trap 4 — Byte or char: "Does (char) System.in.read() correctly read a non-English letter?" No. read() returns a single byte; a UTF-8 letter can span multiple bytes, so casting one byte to char corrupts it. Wrap System.in in an InputStreamReader with an explicit charset.

    Trap 5 — Charset drift: "The same file text is readable on one machine and garbage on another. Why?" A bridge constructor without a charset uses the platform default, which varies by OS and locale. Always pass the charset explicitly (StandardCharsets.UTF_8).

    Trap 6 — EOF sentinel: "readLine() and read() both announce the end of input — how do they differ?" read() returns the int value -1; readLine() returns the reference null. Using the wrong check (or none) leads either to an infinite loop or to a NullPointerException.

    Trap 7 — Double wrapping: "Is BufferedReader(new InputStreamReader(new BufferedInputStream(System.in))) better?" No. System.in is already buffered, and the character-level BufferedReader is the buffer that matters for readLine(). The inner BufferedInputStream adds a redundant layer. Wrap once, at the character level.

    14. Points to Remember

    1. A stream is an ordered sequence of data; classify it by direction (input/output) and unit (byte/character).
    2. Byte streams use InputStream/OutputStream and move 8-bit bytes; character streams use Reader/Writer and move 16-bit chars.
    3. System.in is an InputStream (bytes); System.out and System.err are PrintStreams with auto-flush on newline during console output.
    4. InputStreamReader/OutputStreamWriter bridge bytes to characters using a charset; always name the charset, never rely on the platform default.
    5. Scanner tokenizes with delimiters and parses typed tokens; nextInt() leaves the newline, so a following nextLine() returns "".
    6. The standard fix for the trap is one extra nextLine() to consume the newline, or reading whole lines and parsing with Integer.parseInt.
    7. BufferedReader.readLine() returns a line without its terminator, or null at end of input; check for null before use.
    8. BufferedReader is faster for large input because it buffers in big blocks and skips per-token parsing; Scanner is convenient but slower.
    9. Use try-with-resources for AutoCloseable streams; close() flushes and releases, flush() only pushes buffered data; closing a wrapper closes the underlying stream.
    10. IOException is a checked exception (Lecture 43): catch it or declare it, and never treat it as an unchecked runtime failure.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a stream in Java I/O? An ordered sequence of data moving between a program and a source/destination; classified by direction and by byte-versus-character unit.
    Difference between byte and character streams? Byte streams (InputStream/OutputStream) move raw 8-bit bytes; character streams (Reader/Writer) move 16-bit chars and are encoding-aware.
    What type is System.in? An InputStream — a byte stream — typically backed by a BufferedInputStream.
    What are System.out and System.err? Both are PrintStreams: byte output streams with print/println/printf conveniences and console auto-flush on newline.
    What does InputStreamReader do? It bridges a byte input stream to a character reader, decoding bytes into chars using a charset.
    Scanner vs BufferedReader — which is faster and why? BufferedReader, for large input: it reads big buffered blocks and skips Scanner's per-token regex parsing.
    Explain the nextInt() then nextLine() problem. nextInt() leaves the line terminator unread, so nextLine() returns an empty string; consume the newline (or parse whole lines) to fix it.
    What does readLine() return at end of input? null — not -1 and not an empty string. Check for null before using the line.
    How do you read a line from System.in without Scanner? new BufferedReader(new InputStreamReader(System.in)).readLine().
    What is try-with-resources? A syntax that declares AutoCloseable resources in a try header and closes them automatically, even on exception.
    Difference between flush() and close()? flush() forces buffered output out and keeps the stream usable; close() flushes and releases the resource.
    Is IOException checked or unchecked? Checked — the compiler requires catching it or declaring it with throws (Lecture 43).

    16. Final Summary

    System.in (bytes) --InputStreamReader(charset)--> chars
                     |
                     +--> Scanner        --> tokens (nextInt, next, nextLine)
                     +--> BufferedReader --> lines  (readLine, null at EOF)

System.out / System.err (PrintStreams, bytes) <-- encoded text <-- print/println/printf

byte streams: InputStream / OutputStream   |   character streams: Reader / Writer
    • Direction -> input reads in, output writes out; the four roots are InputStream, OutputStream, Reader, Writer.
    • Unit -> bytes for binary data, characters plus a charset for text; InputStreamReader is the bridge.
    • Standard streams -> System.in (byte InputStream), System.out/System.err (PrintStreams, auto-flush on newline).
    • Scanner -> tokenizing and typed parsing, convenient but slower; always mind the leftover newline.
    • BufferedReader -> buffered, line-oriented, fast, null at EOF; the tool for large input.
    • Resource handling -> try-with-resources; close() flushes and releases; closing a wrapper closes System.in too.
    • Failure -> IOException is checked (Lecture 43); guard against InputMismatchException and NullPointerException.

    Golden rule Choose the stream by unit: bytes for binary, characters (with an explicit charset) for text. Then choose the reader by need: Scanner for parsed tokens, BufferedReader for fast lines.

    One-line takeaway: Java I/O is a 2x2 grid of direction and unit, and console mastery reduces to wrapping the byte-level System.in in a character reader — Scanner when you want parsed tokens, BufferedReader when you want speed — while watching the leftover newline and the closed-stream trap.
